# Part 10: Kubernetes Storage, Security, and Cluster Operations

At mid-level, Kubernetes interviews should assume the candidate already understands basic Pods, Deployments, Services, and ConfigMaps.

This section should test whether the engineer can operate a real production cluster where storage, identity, node maintenance, certificates, and control-plane health all matter at the same time.

The focus is not:

What is a PersistentVolume?

The focus is:

Why will this PVC not bind, why is this volume stuck attached to another node, why did RBAC suddenly block the deployment, why did a node drain stall, and how do you upgrade the cluster without creating an outage?

A useful mental model is:

```text
WORKLOAD
   |
   +----> STORAGE
   |       |
   |       +----> PVC
   |       +----> PV
   |       +----> StorageClass
   |       +----> CSI
   |
   +----> IDENTITY
   |       |
   |       +----> ServiceAccount
   |       +----> RBAC
   |       +----> Secrets
   |
   +----> SECURITY
   |       |
   |       +----> SecurityContext
   |       +----> Pod security controls
   |
   +----> NODE
           |
           +----> Scheduling
           +----> Draining
           +----> Failure
           +----> Upgrade
```

The strongest candidate can connect all of these systems during one incident.

# Question 1: Walk me through how a PVC gets storage in Kubernetes.

## Interview Answer

A Pod usually requests persistent storage through a PersistentVolumeClaim, PVC.

For example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: gp3
```

The PVC asks Kubernetes for storage matching:

```text
Size
Access mode
Storage class
Volume mode
Selector, if used
```

If dynamic provisioning is available, the StorageClass and CSI provisioner may create a matching persistent volume.

Conceptually:

```text
Pod
 |
 v
PVC
 |
 v
StorageClass
 |
 v
CSI Provisioner
 |
 v
Cloud / Storage Platform
 |
 v
PV
 |
 v
PVC Bound
 |
 v
Pod Mount
```

I would distinguish:

```text
Volume provisioning
```

from:

```text
Volume attachment
```

and:

```text
Volume mount
```

because each can fail independently.

# Question 2: A PVC is stuck in `Pending`. How do you investigate?

## Interview Answer

I would start with:

```bash
kubectl describe pvc <pvc>
```

Then inspect:

```bash
kubectl get pvc
kubectl get pv
kubectl get storageclass
```

I want to know:

* Is dynamic provisioning expected?
* Does the StorageClass exist?
* Is the provisioner healthy?
* Is requested access mode supported?
* Is requested size valid?
* Are storage quotas exceeded?
* Is topology preventing provisioning?
* Is there a matching static PV?

The events are often the most useful evidence.

For example:

```text
failed to provision volume with StorageClass "gp3"
```

is very different from:

```text
no persistent volumes available for this claim
```

One points toward dynamic provisioning.

The other may indicate no matching static volume exists.

# Question 3: What conditions must match for static PV and PVC binding?

## Interview Answer

Kubernetes considers attributes such as:

```text
Storage capacity
Access mode
StorageClass
Volume mode
Selectors
Availability
```

Suppose:

PVC:

```text
20Gi
ReadWriteOnce
storageClassName: fast
```

PV:

```text
100Gi
ReadWriteMany
storageClassName: slow
```

That PV is not necessarily an acceptable match.

The most important point is:

```text
A PV existing
does not mean
the PVC can bind to it.
```

I would inspect both objects instead of assuming the storage controller is broken.

# Question 4: A PV is `Available`, but the PVC remains `Pending`. Why?

## Interview Answer

I would compare them directly.

Possible mismatches include:

* StorageClass
* Access mode
* Volume mode
* Label selector
* Capacity
* ClaimRef
* Node affinity

For example:

```text
PV:
storageClassName: gold

PVC:
storageClassName: silver
```

Even if the PV has enough space, it does not match the requested class.

This is a good example of Kubernetes being syntactically correct but operationally incompatible.

# Question 5: What is a StorageClass?

## Interview Answer

A StorageClass describes a class of storage and how it should be provisioned.

It may specify:

```text
Provisioner
Parameters
Reclaim policy
Volume binding mode
Expansion behavior
```

For example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
```

The StorageClass connects Kubernetes storage requests to an underlying storage system.

It is not the storage itself.

# Question 6: What is dynamic provisioning?

## Interview Answer

Dynamic provisioning means Kubernetes automatically requests new storage when a PVC is created, rather than requiring an administrator to create PVs manually in advance.

Flow:

```text
PVC created
    |
    v
StorageClass selected
    |
    v
Provisioner called
    |
    v
External storage created
    |
    v
PV created
    |
    v
PVC bound
```

This makes storage much easier to operate at scale.

But it also introduces dependencies on:

* CSI controller
* Cloud/storage API
* IAM or credentials
* Quotas
* Topology
* Provisioning limits

# Question 7: Why would you use `WaitForFirstConsumer`?

## Interview Answer

It delays storage provisioning or binding until a Pod actually needs the PVC and scheduling context is known.

This is important for topology-constrained storage.

Suppose a cloud block volume must exist in the same Availability Zone as the node using it.

Immediate provisioning might create:

```text
Volume -> AZ-A
```

while the Pod later wants:

```text
Node -> AZ-B
```

Now scheduling becomes difficult.

With:

```text
WaitForFirstConsumer
```

Kubernetes can consider:

```text
Pod scheduling
+
Storage topology
```

together.

# Question 8: A Pod is Pending because its PVC is in the wrong Availability Zone. How could that happen?

## Interview Answer

A statically provisioned or prematurely provisioned volume may be tied to one zone.

For example:

```text
PV:
AZ-A

Eligible application nodes:
AZ-B
```

A zonal block volume cannot simply attach across zones.

The scheduler then has a conflict:

```text
Pod requires storage in AZ-A
but
other constraints require node in AZ-B
```

I would inspect:

```bash
kubectl describe pod <pod>
kubectl describe pv <pv>
```

and any PV node affinity.

This is why storage topology is part of scheduling.

# Question 9: What are common Kubernetes access modes?

## Interview Answer

Common access modes include:

```text
ReadWriteOnce
ReadOnlyMany
ReadWriteMany
ReadWriteOncePod
```

But support depends on the underlying storage system and CSI driver.

For example, a typical cloud block volume may support a different access pattern than a shared network filesystem.

I would never assume:

```text
PVC requests ReadWriteMany
```

means:

```text
every storage backend can provide it.
```

Storage semantics come from the actual storage platform.

# Question 10: Why can a Deployment work with one replica but fail when scaled to five?

## Interview Answer

Storage access mode may be one reason.

Suppose all replicas mount the same PVC backed by storage that effectively supports one-node attachment.

Replica 1 runs successfully.

Additional replicas on other nodes may encounter attachment conflicts.

The architecture could be wrong for the workload.

If multiple replicas need shared writable storage, I would evaluate:

* Shared filesystem
* Object storage
* External database
* Different persistence model

Scaling stateless application replicas while coupling them to one node-bound disk is often a design problem.

# Question 11: What is a StatefulSet designed to help with?

## Interview Answer

StatefulSets are designed for workloads that need stable identity and often stable persistent storage.

Unlike interchangeable Deployment replicas:

```text
app-7f6d9
app-bb91c
```

StatefulSet Pods have stable ordinal identities:

```text
db-0
db-1
db-2
```

They can also receive distinct PVCs.

Conceptually:

```text
db-0 -> pvc-db-0
db-1 -> pvc-db-1
db-2 -> pvc-db-2
```

This is useful for distributed databases and other stateful systems.

But StatefulSet does not automatically solve database replication, consistency, backup, or failover.

# Question 12: A StatefulSet Pod is deleted. What happens to its storage?

## Interview Answer

The Pod may be recreated with the same stable identity and associated PVC depending on the configuration.

For example:

```text
db-1 deleted
   |
   v
db-1 recreated
   |
   v
same claim reused
```

That persistence is one of the reasons StatefulSets are useful.

But I would understand the retention and reclaim policies before deleting claims or StatefulSets.

Deleting a Pod is very different from deleting its PVC.

# Question 13: Why can scaling down a StatefulSet be dangerous?

## Interview Answer

Because stateful members may have application-level responsibilities.

Suppose:

```text
db-0
db-1
db-2
```

form a quorum-based system.

Scaling:

```text
3 -> 1
```

is not merely a Kubernetes replica-count change.

It may break:

* Quorum
* Replication
* Data availability
* Cluster membership

Kubernetes understands Pod lifecycle.

It does not necessarily understand the application's distributed systems rules.

# Question 14: A Pod is stuck with a `Multi-Attach` volume error. What does it mean?

## Interview Answer

It often means the same storage volume is still attached to one node while Kubernetes is trying to attach it to another, and the backend does not permit that attachment pattern.

For example:

```text
Volume
  |
  v
Node A

Pod rescheduled to Node B

Node B
  |
  X
Volume still attached to Node A
```

I would investigate:

* Old Pod state
* Old node state
* VolumeAttachment objects
* CSI logs
* Cloud/storage attachment state
* Access mode

A common cause is a failed or unreachable node that never cleanly detached its volume.

# Question 15: A node dies and the Pod is rescheduled, but storage will not attach to the new node. What would you do?

## Interview Answer

I would determine whether the old node is genuinely gone and whether the storage provider still considers the volume attached.

I would inspect:

```bash
kubectl get volumeattachments
kubectl describe volumeattachment <name>
```

and CSI components.

I would also inspect the external storage platform.

The dangerous action would be manually forcing detach without confirming the old node cannot still write to the volume.

That could create concurrent writers and possible corruption.

Storage recovery requires strong evidence.

# Question 16: What is CSI?

## Interview Answer

CSI, Container Storage Interface, provides a standard interface that storage vendors and platforms can implement for container orchestration systems.

In Kubernetes, a CSI driver may include components responsible for:

```text
Provisioning
Attachment
Mounting
Expansion
Snapshots
```

Conceptually:

```text
Kubernetes
   |
   v
CSI Controller
   |
   v
Storage API

Node
 |
 v
CSI Node Plugin
 |
 v
Mount storage
```

This separation matters during troubleshooting.

Provisioning failure and node-mount failure may occur in completely different CSI components.

# Question 17: How would you troubleshoot CSI failures?

## Interview Answer

I first identify the failure phase.

Is it:

```text
Provision
Attach
Mount
Expand
Snapshot
```

Then inspect Kubernetes events and relevant CSI Pods.

For example:

```bash
kubectl get pods -n kube-system
```

or the namespace used by the CSI driver.

I would inspect:

```text
Controller logs
Node plugin logs
VolumeAttachment
PVC
PV
Pod events
```

If only one node fails mounts, I focus on the node plugin.

If all provisioning fails cluster-wide, the controller or external API becomes more interesting.

# Question 18: PVC is Bound, volume attached, but Pod still cannot start. What storage stage might be failing?

## Interview Answer

Mounting.

The lifecycle is:

```text
Provision
   |
   v
Bind
   |
   v
Attach
   |
   v
Mount
   |
   v
Application
```

A Bound PVC only proves the claim has matched a volume.

It does not prove the node successfully mounted it.

I would inspect Pod events for errors such as:

```text
MountVolume.SetUp failed
```

and investigate:

* Filesystem
* Credentials
* Mount options
* CSI node plugin
* Permissions

# Question 19: What does a reclaim policy do?

## Interview Answer

It controls what happens to the underlying storage after its claim is released.

Common policies include:

```text
Retain
Delete
```

With `Delete`, underlying storage may be deleted when the associated lifecycle reaches the appropriate state.

With `Retain`, the storage remains and requires manual handling.

For production databases, this setting matters significantly.

Deleting a PVC should not be treated casually when the reclaim behavior could destroy storage.

# Question 20: How would you protect critical storage from accidental deletion?

## Interview Answer

I would use multiple controls.

Depending on platform:

* Appropriate reclaim policy
* Backup
* Snapshots
* RBAC
* Admission policies
* Change review
* Infrastructure-as-Code controls
* Cloud-side deletion protection where supported

No single Kubernetes setting should be considered a complete backup strategy.

# Question 21: What is RBAC in Kubernetes?

## Interview Answer

RBAC controls authorization using:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
```

Conceptually:

```text
Subject
User / Group / ServiceAccount
      |
      v
Binding
      |
      v
Role / ClusterRole
      |
      v
Allowed API actions
```

Permissions include:

```text
verbs
resources
namespaces
```

For example:

```text
get Pods
list Pods
create Deployments
delete Secrets
```

The goal is least privilege.

# Question 22: What is the difference between Role and ClusterRole?

## Interview Answer

A Role is namespace-scoped.

A ClusterRole can define permissions for cluster-scoped resources or reusable permissions that may be bound within namespaces.

For example:

```text
Role:
read Pods in namespace payments
```

versus:

```text
ClusterRole:
read nodes
```

A ClusterRoleBinding can apply cluster-wide.

I would be cautious with ClusterRoleBinding because its blast radius is larger.

# Question 23: A deployment pipeline suddenly receives `Forbidden`. How do you troubleshoot it?

## Interview Answer

I identify:

```text
Who is making the request?
What verb?
What resource?
Which namespace?
```

The error often contains much of this information.

I can test authorization with:

```bash
kubectl auth can-i create deployments \
  --as=system:serviceaccount:ci:deployer \
  -n production
```

or:

```bash
kubectl auth can-i --list \
  --as=system:serviceaccount:ci:deployer \
  -n production
```

I would inspect:

* ServiceAccount
* RoleBindings
* ClusterRoleBindings
* Roles
* ClusterRoles
* Recent RBAC changes

I would not solve it by immediately assigning `cluster-admin`.

# Question 24: Why is `cluster-admin` dangerous for applications?

## Interview Answer

Because it gives extremely broad permissions.

A compromised workload could potentially modify resources far beyond what it needs.

Most applications need little or no Kubernetes API access.

A deployment tool may need specific permissions.

For example:

```text
get Deployment
patch Deployment
get Pods
```

not:

```text
full cluster administration
```

Least privilege reduces blast radius.

# Question 25: What is a ServiceAccount?

## Interview Answer

A ServiceAccount provides an identity for processes running in Pods to interact with Kubernetes or integrated external identity systems.

For example:

```text
Pod
 |
 v
ServiceAccount: payments-api
 |
 v
RBAC permissions
```

The application can then be granted the specific API permissions it needs.

A ServiceAccount is not just a string on the Pod.

It is part of the workload identity model.

# Question 26: Why should workloads not all use the default ServiceAccount?

## Interview Answer

Because distinct workloads need distinct identities and permissions.

If everything runs as:

```text
default
```

then authorization becomes difficult to reason about.

A better model is:

```text
payments-api -> payments-sa
reporting -> reporting-sa
ci-deployer -> deployer-sa
```

Then each identity can have narrowly scoped permissions.

# Question 27: Why should automounted ServiceAccount tokens be considered carefully?

## Interview Answer

If an application does not need Kubernetes API access, giving it a token unnecessarily increases attack surface.

Where appropriate, token automounting can be disabled.

For example:

```yaml
automountServiceAccountToken: false
```

The general principle is:

```text
Do not give credentials
to a workload
that does not need them.
```

# Question 28: How should Kubernetes Secrets be treated?

## Interview Answer

As sensitive data requiring access control.

Kubernetes Secret objects provide a mechanism for storing and delivering sensitive values, but base64 representation is not encryption by itself.

I would consider:

* Encryption at rest
* RBAC
* External secret managers
* Rotation
* Audit logging
* Avoiding unnecessary mounting
* Secret lifetime

I would never say:

```text
It's base64 encoded,
so it is secure.
```

# Question 29: What can go wrong when a Secret is mounted into a Pod?

## Interview Answer

Possible problems include:

* Wrong Secret name
* Missing key
* Permission issue
* Application expects different path
* Secret not rotated as expected
* Pod requires restart depending on consumption pattern
* Secret exposed in logs

I would inspect:

```bash
kubectl describe pod <pod>
```

for mount errors without printing secret values unnecessarily.

# Question 30: Would you store production credentials directly in Deployment YAML?

## Interview Answer

No.

For example:

```yaml
env:
  - name: DB_PASSWORD
    value: super-secret-password
```

puts the secret directly into source-controlled configuration if committed.

I would instead reference a Secret or integrated external secret mechanism.

Even then, I would limit who can read the Secret.

# Question 31: What is `securityContext`?

## Interview Answer

`securityContext` configures security-related attributes for Pods or containers.

Examples include:

```text
runAsUser
runAsNonRoot
readOnlyRootFilesystem
allowPrivilegeEscalation
capabilities
fsGroup
seccomp profile
```

For example:

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
```

The goal is to reduce unnecessary privilege.

# Question 32: A container works locally but fails with `runAsNonRoot`. Why?

## Interview Answer

The image may default to root or lack a valid non-root user.

It may also need to write to root-owned paths.

I would inspect:

* Image user
* File permissions
* Mounted volumes
* Port requirements
* Runtime filesystem paths

I would fix the image or permissions instead of disabling the security control without analysis.

# Question 33: Why is `allowPrivilegeEscalation: false` useful?

## Interview Answer

It prevents a process from gaining more privileges than its parent process through mechanisms such as setuid binaries.

It reduces one path for privilege escalation inside the container.

It should be combined with other controls, not treated as complete isolation.

# Question 34: Why use a read-only root filesystem?

## Interview Answer

It prevents applications from writing arbitrary changes into the container's root filesystem.

Benefits include:

* Reduced tampering
* More immutable runtime
* Easier detection of inappropriate write behavior

But applications often need writable locations.

Those should be explicitly provided through suitable volumes such as:

```text
/tmp
cache
application working directory
```

where necessary.

# Question 35: What are Pod security controls?

## Interview Answer

Modern Kubernetes environments can enforce Pod security expectations through mechanisms such as Pod Security Admission and policy tooling.

Controls may restrict:

```text
Privileged containers
Host networking
Host PID
HostPath
Capabilities
Root execution
Privilege escalation
```

The objective is to prevent unsafe workload configurations from reaching the cluster.

# Question 36: Why is privileged mode dangerous?

## Interview Answer

A privileged container receives extremely broad access to the host environment.

It can significantly weaken container isolation.

Privileged mode should be reserved for workloads that genuinely require it and should be tightly controlled.

If an ordinary API requests:

```yaml
securityContext:
  privileged: true
```

I would treat that as a major security review issue.

# Question 37: Why are HostPath volumes sensitive?

## Interview Answer

HostPath exposes part of the node filesystem to a Pod.

For example:

```text
Host:
/var/log

mounted into Pod
```

Depending on path and permissions, this can expose sensitive host data or allow dangerous modification.

Mounting:

```text
/
```

or runtime sockets into ordinary workloads is particularly risky.

# Question 38: What happens when a Kubernetes node fails?

## Interview Answer

The control plane eventually detects that the node is unhealthy or unreachable.

Workloads may need to be recreated elsewhere depending on controller type and timing.

But recovery depends on workload architecture.

For stateless Deployment replicas:

```text
Node A fails
   |
   v
Replacement Pods schedule elsewhere
```

For stateful workloads:

```text
Node A fails
   |
   v
Storage detach?
   |
   v
Volume attach to Node B?
   |
   v
Application recovery?
```

Stateful recovery can take longer because storage and quorum may be involved.

# Question 39: How would you investigate one failing node?

## Interview Answer

I would inspect:

```bash
kubectl describe node <node>
```

and node conditions.

I would look for:

```text
Ready
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

I would compare against healthy nodes.

Then investigate:

* kubelet
* Container runtime
* CNI
* Disk
* Memory
* Network
* Kernel
* Certificates
* Cloud instance health

If workload impact is ongoing, I may cordon the node while investigating.

# Question 40: What is the difference between cordoning and draining?

## Interview Answer

Cordoning prevents new workloads from scheduling onto a node.

```bash
kubectl cordon node-a
```

Existing Pods remain.

Draining attempts to safely evict eligible workloads.

```bash
kubectl drain node-a
```

Conceptually:

```text
CORDON
No new Pods

DRAIN
Move existing eligible Pods away
```

I normally cordon before planned maintenance.

# Question 41: Why can node drain fail?

## Interview Answer

Possible reasons include:

* PDB
* DaemonSets
* Local storage
* Unmanaged Pods
* Eviction policy
* Insufficient capacity elsewhere

I would read the drain output before reaching for aggressive flags.

For example:

```text
Cannot evict pod as it would violate
the pod's disruption budget
```

means the cluster is protecting application availability.

# Question 42: How do PDBs interact with drain?

## Interview Answer

Drain uses eviction behavior that respects PDBs.

Suppose:

```text
replicas = 4
PDB minAvailable = 4
```

No replica can be voluntarily disrupted.

Drain may stall.

A better setup may be:

```text
replicas = 4
minAvailable = 3
```

depending on workload capacity.

PDB design must account for maintenance needs.

# Question 43: Why is deleting Pods manually not the same as draining?

## Interview Answer

Direct deletion may bypass the operational safety model you expected from voluntary eviction behavior.

Drain is designed for planned node maintenance and coordinates eviction semantics.

The broader principle is:

```text
Maintenance should use
maintenance-aware mechanisms.
```

not random Pod deletion.

# Question 44: How would you prepare for a Kubernetes cluster upgrade?

## Interview Answer

I would review:

* Kubernetes version skew policy
* Deprecated APIs
* CNI compatibility
* CSI compatibility
* Ingress controller
* Admission controllers
* Operators
* CRDs
* Workload PDBs
* Node capacity
* Backups
* Control-plane health
* Rollback/support plan

I would test in a lower environment when possible.

The upgrade is an ecosystem change, not just a Kubernetes binary update.

# Question 45: Why are deprecated APIs dangerous during upgrades?

## Interview Answer

A manifest may work in the current version but use an API removed in the target version.

For example:

```text
Old API
works today

Cluster upgrade
   |
   v
API removed
   |
   v
Deployment tooling fails
```

I would inventory deprecated APIs before upgrading.

This is much safer than discovering them during production maintenance.

# Question 46: How would you upgrade worker nodes safely?

## Interview Answer

A common rolling approach is:

```text
Select node
   |
   v
Cordon
   |
   v
Drain
   |
   v
Upgrade / replace
   |
   v
Verify kubelet/runtime/CNI
   |
   v
Uncordon
   |
   v
Move to next node
```

I would monitor:

* Application availability
* Pending Pods
* PDB blocks
* Node readiness
* Storage attachments
* Networking

I would not upgrade every worker node simultaneously.

# Question 47: What can go wrong during rolling node replacement?

## Interview Answer

Many things:

* Not enough spare capacity
* PDB prevents eviction
* Stateful storage cannot detach
* New node has wrong labels
* New node has wrong taints
* CNI fails
* CSI plugin unavailable
* Image pulls fail
* Node version incompatible
* Workloads become concentrated in one AZ

A technically healthy new node is not necessarily production-ready.

# Question 48: How much spare capacity should a cluster have before maintenance?

## Interview Answer

There is no universal percentage.

I would calculate based on:

* Workload requests
* PDB
* Failure domains
* Number of nodes being replaced simultaneously
* `maxUnavailable`
* Stateful requirements
* Surge needs

The question is:

```text
If I remove one node,
can all displaced critical workloads
schedule elsewhere?
```

That should be proven before maintenance.

# Question 49: A node drain causes Pods to become Pending. Why?

## Interview Answer

There may not be enough eligible capacity elsewhere.

Possible blockers include:

```text
CPU
Memory
Affinity
Taints
Topology constraints
Storage topology
```

The cluster may have plenty of total capacity, but not enough capacity that satisfies those Pods.

This is why pre-maintenance scheduling simulation and headroom matter.

# Question 50: What certificate problems can affect Kubernetes?

## Interview Answer

Certificates may be involved in:

* API server
* kubelet
* etcd
* Admission webhooks
* Ingress
* Internal components
* Client kubeconfigs

Possible failures include:

* Expiration
* Hostname/SAN mismatch
* Untrusted CA
* Missing intermediate
* Rotation failure
* Clock skew

Symptoms can vary from:

```text
kubectl fails
```

to:

```text
nodes become NotReady
```

to:

```text
admission webhook blocks deployments
```

# Question 51: `kubectl` suddenly reports `x509: certificate has expired`. What do you investigate?

## Interview Answer

I determine which certificate is involved.

Is it:

```text
Client certificate
API server certificate
Proxy certificate
```

I would inspect the kubeconfig and server endpoint.

I would also determine whether the failure affects:

```text
One administrator
all users
cluster components
```

If only one engineer is affected, the local client credential may be expired.

If every API interaction fails, the issue may be broader.

# Question 52: Why is clock synchronization important for certificates?

## Interview Answer

Certificate validity depends on time.

If a node clock is significantly incorrect, a valid certificate may appear:

```text
Not yet valid
```

or:

```text
Expired
```

Clock skew can create confusing authentication and TLS failures.

Time synchronization is foundational infrastructure.

# Question 53: Why should you care about etcd even if you do not manage it directly?

## Interview Answer

Because etcd stores Kubernetes control-plane state.

Conceptually:

```text
API Server
    |
    v
etcd
```

Objects such as:

```text
Deployments
Services
Secrets
ConfigMaps
Node state
```

are represented in cluster state stored through the control plane.

If etcd becomes unhealthy, the cluster control plane can become severely degraded.

Even in managed Kubernetes, understanding etcd's role helps interpret failures.

# Question 54: What are signs of etcd or control-plane storage problems?

## Interview Answer

Possible symptoms include:

* Slow API requests
* API timeouts
* Failed writes
* Controllers lagging
* Leader election issues
* Cluster state changes delayed

But I would not claim:

```text
kubectl is slow
therefore etcd is broken.
```

API server load, admission webhooks, networking, and other control-plane issues could also cause similar symptoms.

I would use control-plane metrics and logs where available.

# Question 55: Why is etcd backup important?

## Interview Answer

Because etcd contains critical cluster state.

In self-managed control planes, a valid etcd backup can be essential for disaster recovery.

But backup is only useful if:

```text
Restore procedure is understood
Backup integrity is validated
Backup is protected
Recovery time is acceptable
```

A backup nobody has tested is not a proven recovery strategy.

# Question 56: Should application data be backed up by backing up etcd?

## Interview Answer

No.

etcd stores Kubernetes state, not the actual contents of application databases or persistent volumes.

For example:

```text
PVC object
```

may be represented in cluster state.

But:

```text
10 TB PostgreSQL data
```

is stored in the underlying storage system.

Application data requires its own backup and recovery strategy.

# Question 57: What would you monitor during cluster maintenance?

## Interview Answer

I would monitor both infrastructure and customer-facing signals.

Cluster:

```text
Node Ready status
Pending Pods
Evictions
PDB violations
Volume attach/mount
CNI health
CSI health
API latency
```

Applications:

```text
Availability

Latency
Replica count

Business transactions
```

Maintenance is not successful merely because the node upgrade command finished.

Production must remain healthy.

# Question 58: Why should maintenance be performed one failure domain at a time?

## Interview Answer

Because simultaneous maintenance across multiple failure domains can defeat redundancy.

For example:

```text
AZ-A maintenance
+
AZ-B maintenance
```

while AZ-C already has degraded capacity could create an outage.

A safer approach preserves enough independent healthy capacity throughout the process.

# Question 59: How do you know whether a cluster is safe to drain a node?

## Interview Answer

I would check:

* What Pods run there?
* Which are critical?
* Which have PDBs?
* Is there replacement capacity?
* Are storage volumes portable?
* Any local storage?
* Any singleton workloads?
* Any strict affinity?
* Any topology constraints?

For example:

```bash
kubectl get pods -A -o wide \
  --field-selector spec.nodeName=<node>
```

Then reason about the blast radius.

# Production Scenario 1: PVC Stuck Pending

Deployment creates a PVC:

```text
StorageClass:
premium
```

Cluster StorageClasses:

```text
standard
gp3
```

There is no:

```text
premium
```

The Pod remains Pending because storage cannot be provisioned.

The correct fix is the storage-class configuration.

Not the Pod.

# Production Scenario 2: StatefulSet Volume Cannot Reattach

Node A becomes unreachable.

Stateful Pod:

```text
postgres-0
```

moves toward Node B.

Volume backend still reports:

```text
Attached to Node A
```

Node B receives:

```text
Multi-Attach error
```

The recovery must establish that Node A can no longer write before force-detaching.

The priority is data integrity.

# Production Scenario 3: CSI Node Plugin Fails on One Node

PVC:

```text
Bound
```

Volume:

```text
Attached
```

Pod on Node A:

```text
Mounted
```

Pod on Node B:

```text
MountVolume failure
```

This strongly suggests a node-specific mount or CSI node-plugin issue.

I would compare the CSI daemon on both nodes rather than investigating the provisioner first.

# Production Scenario 4: RBAC Change Breaks CI Deployment

At 12:00:

```text
CI works.
```

At 12:05:

```text
RoleBinding changed.
```

At 12:07:

```text
deployments.apps is forbidden
```

The pipeline itself is healthy.

The ServiceAccount has lost authorization.

I would inspect:

```text
Subject
Binding
Role
Verb
Resource
Namespace
```

rather than granting cluster-admin.

# Production Scenario 5: Secret Rotation Breaks Application

Database password is rotated.

Secret object is updated.

Application continues using the old value because it loaded the environment variable only at startup.

Result:

```text
New DB password
+
old app process credential
=
authentication failure
```

Secret rotation architecture must account for how the application consumes the secret.

Some workloads need controlled restart or dynamic secret reload.

# Production Scenario 6: SecurityContext Breaks Deployment

New policy requires:

```text
runAsNonRoot: true
readOnlyRootFilesystem: true
```

Application fails because it writes logs to:

```text
/var/log/app
```

inside the container root filesystem.

The security policy is doing what it was designed to do.

The application image needs an explicit writable location or stdout logging model.

The fix should not automatically be:

```text
Disable security controls.
```

# Production Scenario 7: Node Drain Stalls

Node maintenance begins.

Drain reports:

```text
Cannot evict payments-0
because PodDisruptionBudget would be violated.
```

Workload:

```text
replicas: 2
PDB minAvailable: 2
```

There is no voluntary disruption allowance.

Options may include:

```text
Increase replica count
Adjust PDB safely
Reschedule maintenance
```

Deleting the Pod manually defeats the availability protection.

# Production Scenario 8: Cluster Upgrade Breaks Deployment API

Old manifests use an API version removed by the new Kubernetes release.

Existing workloads continue running.

But new deployment automation fails.

This is especially dangerous because the upgrade may appear successful until teams attempt new changes.

API deprecation scanning should happen before the upgrade.

# Production Scenario 9: Certificate Rotation Failure Makes Node NotReady

Kubelet client certificate rotation fails.

Eventually node communication with the API server breaks.

Symptoms:

```text
Node -> NotReady
Pods -> still temporarily running
Scheduling -> affected
```

This can look like a node networking problem.

Certificate evidence matters.

# Production Scenario 10: Cluster Maintenance Causes Stateful Outage

Three-node database StatefulSet:

```text
db-0 -> AZ-A
db-1 -> AZ-B
db-2 -> AZ-C
```

Maintenance drains AZ-A and AZ-B too close together.

The database loses quorum.

Kubernetes Pods may still appear technically scheduled elsewhere, but the database cannot serve writes.

The lesson:

```text
Kubernetes availability
!=
Application-level quorum availability.
```

## Question 61: A cluster upgrade causes storage failures, blocked drains, RBAC errors, and intermittent application outages. Walk through your response.

Architecture:

```text
Kubernetes Cluster
   |
   +----> Stateless API Deployments
   |
   +----> PostgreSQL StatefulSet
   |
   +----> Redis StatefulSet
   |
   +----> CSI Driver
   |
   +----> Ingress
```

Maintenance plan:

```text
Upgrade 20 worker nodes
one pool at a time
```

At 01:00:

```text
Node pool upgrade starts
```

At 01:10:

```text
3 drains blocked by PDB
```

At 01:15:

```text
2 PostgreSQL volumes fail to attach
```

At 01:20:

```text
CI deployment receives Forbidden
```

At 01:25:

```text
API error rate rises to 12%
```

How do you proceed?

## Interview Answer

I would stop further node replacement.

There are already multiple active failure modes.

Continuing maintenance increases uncertainty and blast radius.

# Step 1: Establish service impact

I want:

```text
Which applications?
Which nodes?
Which AZs?
Which storage volumes?
Which CI identities?
```

I also identify how many healthy replicas remain.

# Step 2: Investigate blocked drains

Suppose the affected workload has:

```text
replicas: 3
PDB minAvailable: 3
```

Drain cannot evict any Pod.

I would determine whether temporary additional replicas can be safely added or whether the PDB can be adjusted within the application's real availability requirements.

I would not bypass it blindly.

# Step 3: Investigate storage

Two StatefulSet Pods moved after node replacement.

Their volumes remain attached to old instances.

I inspect:

```bash
kubectl get volumeattachments
```

and CSI events.

If the old nodes are confirmed terminated but attachments remain stale, I follow the storage provider's safe detach process.

The priority is avoiding simultaneous writers.

# Step 4: Investigate RBAC

The CI ServiceAccount now gets:

```text
Forbidden
```

Suppose an upgrade-related policy rollout replaced a RoleBinding.

I would use:

```bash
kubectl auth can-i
```

to confirm the exact lost permissions.

Then restore the minimum required authorization.

This may be unrelated to storage but occurred during the same change window.

# Step 5: Explain application errors

The API workload lost healthy capacity because some Pods could not be drained/recreated and some stateful dependencies were unavailable.

The causal chain may be:

```text
Node upgrade
   |
   +----> PDB prevents replacement
   |
   +----> Stateful volume detach delay
   |
   v
Reduced service capacity
   |
   v
Database availability reduced
   |
   v
API latency / errors
```

# Step 6: Stabilize

I would:

```text
Pause maintenance
Restore stateful service health
Restore adequate application replicas
Correct RBAC
Verify storage attachments
```

before continuing upgrades.

# Step 7: Verify

I would monitor:

```text
Node Ready
PVC/PV state
Volume attachment
StatefulSet readiness
API error rate
Latency
Pending Pods
PDB state
CI authorization
```

I want the environment stable before touching the next node.

# Step 8: Review maintenance design

Corrective actions might include:

* Pre-upgrade PDB validation
* Stateful volume failover test
* Storage detach monitoring
* RBAC regression tests
* Upgrade canary node pool
* Spare capacity validation
* Deprecated API audit
* CSI/CNI compatibility checks
* Automated maintenance gates

The maintenance failed because several dependencies were not tested together.

That is exactly what mid-level cluster operations should account for.

# Interviewer Follow-Up: Why not use `--force` on every drain?

## Interview Answer

Because force does not make the underlying application safe.

It may bypass or alter normal safeguards while creating:

* Availability loss
* Data risk
* Unexpected deletion
* Local storage loss

I would use aggressive options only when I understand exactly which workload is blocking drain and why.

# Interviewer Follow-Up: Why not scale every workload up before maintenance?

## Interview Answer

Because scaling also consumes:

```text
CPU
Memory
IP addresses
Storage
Database connections
```

and may exceed capacity.

I would scale selectively based on disruption requirements and available headroom.

# Interviewer Follow-Up: Would you continue the upgrade after fixing the first node?

## Interview Answer

Only after the cluster and applications return to a stable baseline and I understand the previous failure.

If the underlying maintenance design is still unsafe, continuing node by node simply reproduces the incident repeatedly.

   +----> PDB

# Final Takeaway

Kubernetes cluster operations become difficult when storage, identity, security, scheduling, and maintenance interact.

A strong mid-level engineer should be able to follow the complete lifecycle:

```text
WORKLOAD
   |
   v
IDENTITY
   |
   v
AUTHORIZATION
   |
   v
SCHEDULING
   |
   v
STORAGE PROVISION
   |
   v
VOLUME ATTACH
   |
   v
VOLUME MOUNT
   |
   v
APPLICATION
   |
   v
NODE LIFECYCLE
   |
   v
MAINTENANCE
   |
   v
RECOVERY
```

The goal is not just to keep Kubernetes objects in `Running` state.

The goal is to operate the cluster so that storage remains consistent, permissions remain controlled, nodes can be maintained safely, workloads remain available, and every production change has a predictable recovery path.
