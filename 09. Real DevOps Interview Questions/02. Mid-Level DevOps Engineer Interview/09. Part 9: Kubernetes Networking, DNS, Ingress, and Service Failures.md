# Part 9: Kubernetes Networking, DNS, Ingress, and Service Failures

At mid-level, Kubernetes networking questions should test whether the candidate can trace traffic through the cluster and identify exactly where communication breaks.

The focus is not:

What is a Kubernetes Service?

The focus is:

Why can one Pod reach the backend while another cannot, why does the Service have no endpoints, why does DNS fail intermittently, and why does traffic work through ClusterIP but fail through Ingress?

A useful traffic model is:

```text
External Client
      |
      v
Cloud Load Balancer
      |
      v
Ingress Controller
      |
      v
Service
      |
      v
EndpointSlice
      |
      v
Pod IP
      |
      v
Application
```

For internal communication:

```text
Pod
 |
 v
DNS
 |
 v
Service ClusterIP
 |
 v
kube-proxy / dataplane
 |
 v
Endpoint
 |
 v
Destination Pod
```

A mid-level engineer should be able to test each layer independently.

---

# Question 1: How does traffic reach a Pod through a Kubernetes Service?

## Interview Answer

Suppose a Service exposes an application:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payments
spec:
  selector:
    app: payments
  ports:
    - port: 80
      targetPort: 8080
```

Traffic might follow:

```text
Client Pod
   |
   v
payments:80
   |
   v
ClusterIP
   |
   v
Service dataplane
   |
   v
EndpointSlice
   |
   v
PodIP:8080
```

The Service itself is not a process listening on the ClusterIP in the traditional sense.

The ClusterIP is a virtual IP implemented by Kubernetes networking components.

I would therefore distinguish:

* Service configuration
* Endpoint discovery
* Dataplane rules
* Pod connectivity
* Application listener

# Question 2: What exactly is a ClusterIP?

## Interview Answer

A ClusterIP is a virtual Service IP used to provide stable internal access to a changing set of backend Pods.

Pods may change:

```text
10.244.1.7
10.244.2.14
10.244.3.9
```

but clients use:

```text
payments.default.svc.cluster.local
```

which resolves to something like:

```text
10.96.20.15
```

The Service abstraction gives clients a stable destination.

Conceptually:

```text
Client
  |
  v
10.96.20.15
  |
  +----> Pod A
  +----> Pod B
  +----> Pod C
```

The actual forwarding mechanism depends on the cluster networking implementation.

# Question 3: Can you normally connect directly to a ClusterIP from outside the cluster?

## Interview Answer

Usually no.

ClusterIP is designed for cluster-internal access.

For external exposure, common options include:

```text
Ingress
LoadBalancer Service
NodePort
Gateway/API gateway architectures
```

If someone tells me:

```text
ClusterIP works internally
but not from my laptop
```

that does not automatically indicate a failure.

It may simply reflect the intended Service scope.

# Question 4: What does kube-proxy do conceptually?

## Interview Answer

Traditionally, kube-proxy programs node-level networking rules that implement Service forwarding.

Depending on configuration and Kubernetes environment, implementations have historically used mechanisms such as:

```text
iptables
IPVS
```

Some modern CNI implementations can replace kube-proxy functionality using eBPF.

Conceptually:

```text
Service IP
   |
   v
Dataplane rules
   |
   v
Backend Pod
```

I care less about memorizing a definition and more about understanding that Service traffic depends on a node dataplane being correctly programmed.

# Question 5: A Service exists but connections time out. What do you check?

## Interview Answer

I work from the Service toward the workload.

First:

```bash
kubectl get svc payments
```

Then:

```bash
kubectl describe svc payments
```

Then inspect endpoints:

```bash
kubectl get endpoints payments
```

and:

```bash
kubectl get endpointslices
```

Then inspect Pods:

```bash
kubectl get pods -l app=payments -o wide
```

I want to establish:

```text
Does Service exist?
      |
      v
Does selector match?
      |
      v
Are endpoints populated?
      |
      v
Are Pods Ready?
      |
      v
Can Pod IP be reached directly?
      |
      v
Does ClusterIP work?
```

That isolates the failing layer.

# Question 6: A Service has no endpoints. What are the likely causes?

## Interview Answer

The first thing I inspect is the selector.

Suppose the Service has:

```yaml
selector:
  app: payment
```

but Pods have:

```yaml
labels:
  app: payments
```

That one-character difference means no matching backends.

Other causes include:

* Pods not matching selectors
* Pods not Ready
* Wrong namespace assumptions
* Manually managed endpoint configuration problems
* Workload not running

I would compare:

```bash
kubectl get svc payments -o yaml
```

with:

```bash
kubectl get pods --show-labels
```

The Service may be perfectly valid while pointing to nothing.

# Question 7: Why are Service selector mistakes dangerous?

## Interview Answer

Because Kubernetes does not necessarily treat a valid but incorrect selector as a configuration syntax error.

For example:

```yaml
selector:
  app: payment-api
```

is perfectly valid YAML.

But if the Pods use:

```yaml
app: payments-api
```

the result can be:

```text
Service
   |
   v
No endpoints
   |
   v
Traffic failure
```

The configuration is syntactically valid but operationally wrong.

# Question 8: What are EndpointSlices?

## Interview Answer

EndpointSlices represent groups of network endpoints associated with Services.

They provide a more scalable mechanism for endpoint information than the older Endpoints API for large environments.

Conceptually:

```text
Service
   |
   +---- EndpointSlice A
   |       Pod 1
   |       Pod 2
   |
   +---- EndpointSlice B
           Pod 3
           Pod 4
```

When debugging modern clusters, I would inspect:

```bash
kubectl get endpointslices
```

and:

```bash
kubectl describe endpointslice <name>
```

I want to verify that expected backend addresses exist and their readiness state is appropriate.


works,


fails,

# Question 11: ClusterIP works on some nodes but not others. What does that suggest?

## Interview Answer

A node-specific Service dataplane problem becomes a strong possibility.

I would compare:

```text
Working node
versus
Failing node
```

and inspect:

* kube-proxy or equivalent component
* CNI
* iptables/IPVS/eBPF state as appropriate
* Node networking
* Routes
* Firewall
* Kernel state

If Pods on Node A consistently access the Service while Pods on Node B cannot, I would avoid blaming the application first.

# Question 12: What is the role of the CNI?

## Interview Answer

The Container Network Interface ecosystem provides networking integration for containers and Kubernetes Pods.

Depending on implementation, the CNI solution may handle:

* Pod interfaces
* Pod IP allocation
* Routing
* Overlay networking
* NetworkPolicy
* Encapsulation
* eBPF dataplane behavior

Examples of Kubernetes networking implementations include Calico, Cilium, and cloud-specific CNI plugins.

Operationally, I care about this path:

```text
Pod
 |
 v
Virtual interface
 |
 v
Node networking
 |
 v
CNI dataplane
 |
 v
Other Pod / external network
```

## Interview Answer

Possible symptoms include:

* Pods cannot communicate across nodes
* New Pods fail to receive IP addresses

* Pod-to-external traffic fails
* Pod-to-Pod traffic becomes intermittent


# Question 15: Why can MTU cause intermittent Kubernetes networking failures?

## Interview Answer

Because smaller packets may work while larger packets fail.

Suppose the physical network supports:

```text
1500-byte MTU
```

but overlay encapsulation adds overhead.

If the Pod network still assumes an MTU that is too large:

```text
Pod packet
+
encapsulation
>
underlay MTU
```

traffic may require fragmentation or fail if path MTU discovery is broken.

Symptoms can include:

* Small HTTP requests work
* Large responses hang
* TLS handshakes behave strangely
* File transfers fail
* Cross-node traffic is unreliable

That is why:

```text
ping works
```

does not prove application traffic will work.

# Question 16: What is CoreDNS used for?

## Interview Answer

CoreDNS normally provides DNS services inside Kubernetes.

It allows workloads to resolve names such as:

```text
payments
```

or:

```text
payments.default
```

and fully qualified names such as:

```text
payments.default.svc.cluster.local
```

Conceptually:

```text
Application Pod
      |
      v
DNS query
      |
      v
CoreDNS
      |
      +----> Kubernetes Service records
      |
      +----> Upstream DNS
```

CoreDNS is therefore involved in both cluster service discovery and external DNS resolution paths.

# Question 21: Why can DNS failures be intermittent in Kubernetes?

## Interview Answer

Possible causes include:

* CoreDNS overload
* CPU throttling
* Packet loss
* Upstream DNS instability
* Node-specific networking
* Conntrack pressure
* NetworkPolicy
* Uneven CoreDNS replica health
* CNI problems

Suppose there are three CoreDNS replicas:

```text
CoreDNS A -> healthy
CoreDNS B -> healthy
CoreDNS C -> overloaded
```

Some requests succeed.

Others fail.

# Question 22: How can CPU limits affect CoreDNS?

## Interview Answer

If CoreDNS receives high query volume but has restrictive CPU limits, it can be throttled.

The sequence may become:

```text
Traffic increases
      |
      v
DNS query rate increases
      |
      v
CoreDNS hits CPU limit
      |
      v
DNS latency increases
      |
      v
Application DNS timeouts
```

Applications may then report connection errors even though the destination service itself is healthy.

This is why infrastructure DNS needs resource monitoring.

# Question 23: What is Kubernetes Ingress?

## Interview Answer

Ingress defines HTTP and HTTPS routing rules for external or internal traffic, depending on implementation.

An Ingress controller actually implements those rules.

Conceptually:

```text
Client
  |
  v
Load Balancer
  |
  v
Ingress Controller
  |
  +---- api.example.com -> API Service
  |
  +---- shop.example.com -> Shop Service
```

Creating an Ingress resource without a working controller does not magically route traffic.

---

# Question 24: What is the difference between an Ingress resource and an Ingress controller?

## Interview Answer

The Ingress resource describes desired routing.

For example:

```yaml
rules:
  - host: api.example.com
```

The Ingress controller watches those resources and configures an actual proxy or load-balancing dataplane.

Conceptually:

```text
Ingress YAML
    |
    v
Desired configuration
    |
    v
Ingress Controller
    |
    v
Actual traffic routing
```

Examples of controller technologies include NGINX-based controllers and cloud-provider integrations.

## Interview Answer

I separate the layers.

First verify:

```text
Pod IP
```

Then:

```text
Service ClusterIP
```

Then:

```text
Ingress controller -> Service
```

If ClusterIP works, the application and Service path are probably healthy.

I then inspect:

```bash

```

and controller logs.

I check:

* Host
* Path
* Service name
* Service port
* Endpoint availability
* Ingress class
* Controller configuration

The 503 is evidence from the proxy layer, not automatically the application.

# Question 26: Ingress returns 404, but the application works directly. What could be wrong?

## Interview Answer

A 404 from the Ingress layer often suggests the request did not match the intended routing rule.

I would inspect:

* Host header
* Path
* Path type
* Ingress class
* Rewrite configuration
* Default backend behavior

Suppose Ingress expects:

```text
Host: api.example.com
Path: /v1
```

```text

Path: /v1
```

The controller may route to its default backend.

# Question 29: What is TLS termination at Ingress?

## Interview Answer

The client establishes TLS with the Ingress endpoint.

The Ingress controller presents the certificate and decrypts the request.

For example:

```text
Client
   |
 HTTPS
   |
   v
Ingress
TLS terminates here
   |
 HTTP or HTTPS
   |
   v
Backend Service
```

Whether backend traffic remains encrypted depends on architecture.

TLS termination is separate from backend application routing.

It can control:

* Pod selectors

* IP blocks

```text

   |
```

```text

```

# Question 37: What is `externalTrafficPolicy`?

## Interview Answer

For relevant Service types, `externalTrafficPolicy` controls how externally arriving traffic is handled.

Common values are:

```text
Cluster
Local
```

`Cluster` can allow traffic to be forwarded to endpoints anywhere in the cluster.

`Local` restricts external traffic handling to local node endpoints and can help preserve original client source IP.

The trade-off affects:

* Source IP
* Traffic distribution
* Node endpoint availability

---

# Question 38: Why would you use `externalTrafficPolicy: Local`?

## Interview Answer

A major reason is preserving client source IP.

With some forwarding architectures:

```text
Client
 |
 v
Node
 |
 v
SNAT
 |
 v
Pod
```

the application may see a node address rather than the original client.

With Local policy, source IP preservation can improve.

This can matter for:

* Security logs
* Rate limiting
* Geo decisions
* Auditing
* Application access control

But there are trade-offs.

---

# Question 39: What problem can `externalTrafficPolicy: Local` create?

## Interview Answer

Only nodes with local eligible endpoints can successfully handle traffic for that Service.

Suppose:

```text
Node A -> 3 local Pods
Node B -> 0 local Pods
Node C -> 1 local Pod
```

Traffic distribution can become uneven depending on the external load balancer and health checks.

The trade-off is:

```text
Source IP preservation
versus
cluster-wide endpoint flexibility
```

I would understand the cloud load balancer behavior before enabling it.

# Question 48: Why can conntrack exhaustion cause intermittent Service failures?

## Interview Answer

Connection tracking maintains state for network flows on Linux systems.

If the conntrack table becomes exhausted, new connections may fail or packets may be dropped.

Symptoms can include:

* Intermittent connection timeouts
* DNS failures
* Service failures
* High-connection workloads failing first

This can be especially confusing because:

```text
Existing connections work
```

while:

```text
New connections fail
```

I would inspect node-level network state and connection volume.

---

# Question 49: What causes high conntrack usage?

## Interview Answer

Possible causes include:

* Very high connection rates
* Short-lived connections
* DNS traffic
* Lack of connection reuse
* NAT-heavy traffic
* Large numbers of Pods
* Misconfigured clients

For example:

```text
10,000 Pods
x
many short TCP connections
=
large conntrack pressure
```

Application connection pooling and keep-alive behavior can affect infrastructure networking.

# Question 50: Why can connection timeouts be difficult to troubleshoot?

## Interview Answer

Because timeout is an outcome, not a root cause.

A timeout could mean:

```text
Packet dropped
Firewall blocked
NetworkPolicy blocked
No route
Backend overloaded
DNS slow
Connection backlog full
Application stalled
Database slow
MTU problem
Conntrack exhausted
```

I trace the request rather than guessing.

# Question 51: How would you debug Pod-to-Pod connectivity?

## Interview Answer

Suppose:

```text
Pod A
```

cannot reach:

```text
Pod B
```

I first identify addresses:

```bash
kubectl get pods -o wide
```

Then test direct Pod IP connectivity from an appropriate debugging environment.

I determine:

```text
Same node?
Different node?
Same namespace?
Different namespace?
```

Then inspect:

* NetworkPolicy
* CNI
* Routes
* Node connectivity
* Application listener
* Port

The topology matters.

---

# Question 52: How would you debug Pod-to-Service connectivity?

## Interview Answer

I test progressively:

```text
1. Destination Pod IP
2. Service endpoints
3. Service ClusterIP
4. Service DNS name
```

Suppose:

```text
Pod IP works
ClusterIP fails
```

I investigate the Service dataplane.

If:

```text
ClusterIP works
DNS name fails
```

I investigate DNS.

This layered approach dramatically reduces guesswork.

# Question 55: Only one Kubernetes node has external connectivity problems. What would you do?

## Interview Answer

I compare the failing node with healthy nodes.

I inspect:

* Routes
* CNI state
* NAT
* Firewall
* Network interface
* Conntrack
* DNS
* Kernel logs

Operationally, I might:

```bash

```

to stop new workloads from landing there.

If impact is significant and capacity permits, I may safely drain the node while continuing investigation.

# Question 56: How can NetworkPolicy create intermittent failures instead of complete failure?

## Interview Answer

Suppose only some backend Pods have labels matching an allow policy.

Example:

```text
Pod A -> allowed
Pod B -> allowed
Pod C -> blocked
```

Traffic load-balances across all three.

The user sees:

```text
Success
Success
Timeout
Success
Timeout
```

The problem appears intermittent.

But it is deterministic based on which endpoint receives traffic.

This is why endpoint-level testing matters.

# Question 57: Service requests fail only after a deployment. What would you compare?

## Interview Answer

I compare old and new:

* Pod labels
* Container ports
* Readiness
* Service selector
* NetworkPolicy labels
* Ingress annotations
* TLS configuration
* Sidecars
* Application listener

A subtle label change can break several systems simultaneously.

For example:

```text
Old:
app=payments

New:
app=payment-api
```

Service selector still expects:

```text
app=payments
```

Now the new Pods receive no Service traffic.

# Question 58: Why should you avoid testing only through Ingress?

## Interview Answer

Because Ingress includes many layers.

If this fails:

```text
Client
  |
  v
Ingress
  |
  v
Service
  |
  v
Pod
```

I still do not know which layer is broken.

Testing:

```text
Pod IP
```

then:

```text
ClusterIP
```

then:

```text
Ingress
```

creates isolation.

# Final Production Simulation

## Question 61: After a Kubernetes network change, users report intermittent 503s, DNS failures, and external API timeouts. Walk through your investigation.

Architecture:

```text
Internet
   |
   v
Cloud Load Balancer
   |
   v
Ingress
   |
   v
Frontend Service
   |
   v
Frontend Pods
   |
   +----> API Service
              |
              v
           API Pods
              |
              +----> PostgreSQL
              |
              +----> External Payment API
```

At 11:00, three changes were deployed:

```text
New NetworkPolicy
New CNI configuration
New API Deployment
```

At 11:05:

```text
503 rate increases
DNS errors appear
External payment calls timeout
```

## Interview Answer

I would first stop additional networking changes and preserve evidence.

Then I would identify the blast radius.

Questions:

```text
All Pods?
One namespace?
One node?
One AZ?
Only new Pods?
Only external traffic?
```

### Step 1: Check DNS

From an affected Pod:

```text
Can Kubernetes names resolve?
Can external names resolve?
```

Suppose both fail intermittently.

I inspect CoreDNS and NetworkPolicy.

The new NetworkPolicy may be blocking UDP/TCP DNS traffic.

### Step 2: Test direct Service connectivity

I test:

```text
API Pod IP
```

then:

```text
API ClusterIP
```

then:

```text
API DNS name
```

Suppose:

```text
Pod IP -> works
ClusterIP -> works
DNS -> intermittent
```

That strongly isolates one problem to DNS.

### Step 3: Investigate external API

Suppose direct external IP connectivity also fails from some Pods.

Now DNS alone cannot explain everything.

I compare node placement.

Result:

```text
Node group A -> works
Node group B -> external timeout
```

The CNI change may have affected egress on Node group B.

### Step 4: Investigate 503

Ingress logs show:

```text
no live upstreams
```

I inspect Service endpoints.

Suppose new API Pods changed labels:

```text
Old:
app=api

New:
app=api-v2
```

Service selector still uses:

```text
app=api
```

As old replicas terminate, available endpoints disappear.

Now we have three independent failures introduced in one change window:

```text
NetworkPolicy
   |
   v
DNS disruption

CNI change
   |
   v
Node-specific egress failure

Label change
   |
   v
Service endpoint loss
```

This explains why the incident initially looked chaotic.

### Step 5: Mitigate

I would choose the safest reversible actions.

Potential sequence:

```text
Pause rollout
      |
      v
Restore Service-compatible labels
      |
      v
Correct DNS NetworkPolicy
      |
      v
Isolate affected nodes
      |
      v
Rollback CNI change if required
```

Then validate:

```text
DNS success
Service endpoints
503 rate
Pod-to-Pod connectivity
Cross-node connectivity
External API success
```

### Step 6: Prevent recurrence

I would improve:

* NetworkPolicy testing
* CNI rollout strategy
* Service selector validation
* DNS monitoring
* Endpoint alerts
* Cross-node synthetic tests
* External connectivity tests
* Canary infrastructure changes

The main lesson is that one user-visible symptom can have multiple simultaneous causes.

# Commands a Mid-Level DevOps Engineer Should Understand

| Command                          | Production Question                                 |
| -------------------------------- | --------------------------------------------------- |
| `kubectl get svc`                | What Services exist and how are they exposed?       |
| `kubectl describe svc`           | What selector and ports does the Service use?       |
| `kubectl get endpoints`          | Which backends are associated with the Service?     |
| `kubectl get endpointslices`     | What modern endpoint data exists?                   |
| `kubectl get pods -o wide`       | Which node and Pod IP are involved?                 |
| `kubectl describe ingress`       | What external routing rules exist?                  |
| `kubectl logs`                   | What does the Ingress/CNI/CoreDNS component report? |
| `kubectl get networkpolicy`      | What traffic policies exist?                        |
| `kubectl describe networkpolicy` | What traffic is supposed to be allowed?             |
| `kubectl get events`             | What recent networking failures were recorded?      |

For deeper investigation, a mid-level engineer should also understand when tools such as these are useful:

```bash
curl
dig
nslookup
ss
ip route
ip addr
traceroute
tcpdump
```

The goal is not to run every command.

The goal is to select the command that proves or disproves a hypothesis.

# What a Mid-Level Candidate Should Demonstrate

A junior candidate may say:

```text
"The Service is broken."
```

A mid-level candidate asks:

```text
Does direct Pod IP work?
Are EndpointSlices populated?
Does ClusterIP work?
Does DNS resolve?
```

A junior candidate may say:

```text
"Restart CoreDNS."
```

A mid-level candidate first asks:

```text
Are failures internal or external?
Are all CoreDNS replicas affected?
Is CoreDNS throttled?
Is NetworkPolicy blocking DNS?
```

A junior candidate may say:

```text
"Ingress gives 503,
so Ingress is broken."
```

A mid-level candidate traces:

```text
Ingress
   |
   v
Service
   |
   v
EndpointSlice
   |
   v
Pod
```

A junior candidate may say:

```text
"Pods can ping,
so networking works."
```

A mid-level candidate understands:

```text
ICMP success
does not prove
TCP, DNS, TLS,
MTU, policy,
or application traffic works.
```

A junior candidate may say:

```text
"Delete the NetworkPolicy."
```

A mid-level candidate determines:

```text
Which policy?
Which selector?
Which direction?
Which port?
Which source?
Which destination?
```

A junior candidate may say:

```text
"Kubernetes networking is broken."
```

A mid-level candidate identifies whether the actual failure is:

```text
DNS
Service
Selector
EndpointSlice
kube-proxy/dataplane
CNI
NetworkPolicy
Node
Ingress
TLS
Load balancer
NAT
or
the application itself.
```

# Final Takeaway

At mid-level, Kubernetes networking troubleshooting means following the packet instead of guessing.

```text
NAME
 |
 v
DNS
 |
 v
VIRTUAL SERVICE
 |
 v
ENDPOINT DISCOVERY
 |
 v
NETWORK POLICY
 |
 v
DATAPLANE
 |
 v
CNI
 |
 v
NODE
 |
 v
POD
 |
 v
APPLICATION
```

For external traffic, extend that model outward through TLS, Ingress, and the load balancer.

A strong mid-level DevOps engineer should be able to determine exactly where a connection stops, explain why that layer is failing, and make the smallest safe change needed to restore connectivity.
