# Part 3: DNS, TLS, HTTP, Proxies, and Load Balancer Failures

A production application can be running perfectly and still appear completely broken to users.

The request may fail before it ever reaches the application.

At mid-level, you should be able to troubleshoot the entire path:

```text
User
 |
 v
DNS
 |
 v
Load Balancer / CDN
 |
 v
TLS
 |
 v
Reverse Proxy
 |
 v
HTTP
 |
 v
Application
 |
 v
Downstream Services
```

The goal is not to say, "The website is down."

The goal is to determine exactly where the request fails, what evidence proves it, and what the safest mitigation is.

---

# Question 1: Users intermittently receive "host not found," but the application is healthy. How would you investigate?

## Interview Answer

I would first separate DNS resolution from application connectivity.

If users cannot resolve the hostname, troubleshooting the application server is premature.

I would test repeatedly:

```bash
dig api.example.com
```

and:

```bash
dig api.example.com @<resolver-ip>
```

I would also use:

```bash
getent hosts api.example.com
```

because applications often rely on the system resolver rather than directly performing a DNS query the same way `dig` does.

For intermittent failures, I would compare:

* Different recursive resolvers
* Different locations
* Different record types
* Different authoritative servers
* Successful versus failed responses
* TTL values
* DNS response codes

I would look specifically for:

```text
NOERROR
NXDOMAIN
SERVFAIL
REFUSED
Timeout
```

These mean very different things.

For example:

```text
NXDOMAIN
```

means the queried name does not exist according to the DNS response.

Whereas:

```text
SERVFAIL
```

means the resolver was unable to successfully complete the resolution process.

If only one recursive resolver fails while others consistently succeed, I would investigate that resolver or the path between it and the authoritative DNS infrastructure.

# Question 2: What is the difference between recursive and authoritative DNS?

## Interview Answer

The authoritative DNS server contains authoritative information for a DNS zone.

A recursive resolver performs resolution on behalf of clients.

Conceptually:

```text
Application
     |
     v
Recursive Resolver
     |
     v
Root
     |
     v
TLD
     |
     v
Authoritative DNS
     |
     v
Answer returned
```

In practice, caching means the resolver does not perform this entire chain for every request.

During troubleshooting, this distinction is critical.

Suppose:

```bash
dig api.example.com
```

against the normal resolver fails.

But:

```bash
dig @<authoritative-server> api.example.com
```

returns the correct answer.

That tells me the authoritative data may be correct while something involving recursion, caching, delegation, DNSSEC, or communication with the authoritative infrastructure is failing.

Conversely, if the authoritative server itself returns incorrect information, changing application configuration will not solve the problem.

# Question 3: How would you determine which authoritative servers are responsible for a domain?

## Interview Answer

I could query the NS records:

```bash
dig NS example.com
```

I could also trace delegation:

```bash
dig +trace example.com
```

This can help me understand the resolution chain.

During an incident, I might query individual authoritative servers directly:

```bash
dig @ns1.example-dns.com api.example.com
dig @ns2.example-dns.com api.example.com
```

Suppose:

```text
ns1 -> 10.10.10.20
ns2 -> 10.10.10.30
```

but both should return:

```text
10.10.10.30
```

That inconsistency could explain intermittent behavior.

Clients querying one authoritative path may receive one answer while others receive another.

# Question 4: DNS works for some users but fails for others. What possibilities would you investigate?

## Interview Answer

I would compare the successful and failing populations.

I would ask whether failures correlate with:

* Geographic region
* ISP
* Recursive resolver
* Corporate network
* VPN
* IPv4 versus IPv6
* Internal versus external network
* Cached versus uncached resolution

I would also investigate whether multiple authoritative servers return consistent records.

A useful troubleshooting principle is:

```text
Working users
      versus
Failing users

What differs?
```

If all users using Resolver A fail while users using Resolver B succeed, that dramatically reduces the search space.

# Question 5: Explain how DNS TTL can affect a production deployment.

## Interview Answer

TTL tells DNS caches how long a record may be cached.

Suppose:

```text
api.example.com
TTL = 3600
```

and the address changes from:

```text
192.0.2.10
```

to:

```text
192.0.2.50
```

Some resolvers may continue returning the old cached answer until the cached record expires.

That can produce:

```text
Users A -> New environment
Users B -> Old environment
```

This can look like an intermittent application problem even though different users are simply receiving different DNS answers.

Before a planned DNS migration, teams sometimes lower TTL in advance.

The important phrase is:

"in advance."

Changing TTL from 3600 to 60 at the same moment as the migration does not force existing caches that already stored the old record with the previous TTL to immediately discard it.

# Question 6: You changed a DNS record five minutes ago, but some users still reach the old server. Why?

## Interview Answer

The first possibility is cached DNS information.

I would inspect:

```bash
dig api.example.com
```

from multiple resolvers.

For example:

```bash
dig @1.1.1.1 api.example.com
dig @8.8.8.8 api.example.com
```

I would compare the answers and TTLs.

But I would not automatically blame "DNS propagation."

Other possibilities include:

* Local OS cache
* Browser cache
* Corporate resolver cache
* Application-level DNS caching
* Multiple authoritative servers with inconsistent data
* Proxy/CDN caching
* Old load-balancer targets
* Split-horizon DNS

The phrase "DNS propagation" is often used too broadly.

At mid-level, I want to identify exactly which layer still has the stale information.

# Question 7: What is split-horizon DNS?

## Interview Answer

Split-horizon DNS means the same hostname can return different answers depending on where or how the query is made.

For example:

```text
Internal user:

api.example.com
      |
      v
10.0.5.20


External user:

api.example.com
      |
      v
203.0.113.20
```

This can be intentional.

The internal address may route directly to a private service while external clients use a public load balancer.

It becomes a troubleshooting problem when the wrong DNS view is used.

For example:

```text
VPN users -> wrong resolver -> public address
```

while:

```text
Office users -> internal resolver -> private address
```

If the public path is unavailable from the private network, VPN users may experience failures even though everybody uses the same hostname.

# Question 8: An application works outside the corporate network but fails internally. How could split-horizon DNS be involved?

## Interview Answer

I would compare DNS answers.

From outside:

```bash
dig api.example.com
```

From inside:

```bash
dig api.example.com
```

Suppose:

```text
External:
203.0.113.50

Internal:
10.30.5.50
```

Now I know the two populations are not using the same destination.

I would test both destinations independently.

The internal record could be:

* Stale
* Pointing to a retired load balancer
* Missing
* Incorrectly configured
* Unreachable from certain internal networks

The important lesson is that:

```text
Same hostname
```

does not necessarily mean:

```text
Same destination
```

# Question 9: DNS resolves correctly, but HTTPS fails. What layer do you investigate next?

## Interview Answer

I would move through the connection sequentially.

```text
DNS
 |
 | successful
 v
TCP
 |
 v
TLS
 |
 v
HTTP
```

First, verify TCP connectivity to port 443.

For example:

```bash
nc -vz api.example.com 443
```

or simply use the real application client.

If TCP succeeds but TLS fails, the investigation moves to the TLS handshake.

I might use:

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com
```

This can provide information about:

* Presented certificate
* Certificate chain
* TLS negotiation
* Verification problems
* SNI behavior

The key is not to keep troubleshooting DNS after DNS has already been proven healthy.

# Question 10: Walk me through a TLS connection at a high level.

## Interview Answer

First, TCP normally needs to be established.

Then the TLS handshake negotiates secure communication.

Conceptually:

```text
Client                          Server

TCP connection established
          |
          v

ClientHello
------------------------------>

                         ServerHello
                         Certificate
<------------------------------

Certificate validation
Key establishment
TLS negotiation

          |
          v

Encrypted application traffic
```

The exact handshake varies with TLS version and configuration, but operationally I care about questions such as:

* Did TCP connect?
* Did the server present a certificate?
* Does the certificate match the hostname?
* Is the certificate trusted?
* Is the chain complete?
* Are compatible TLS versions available?
* Are compatible cryptographic parameters available?
* Did SNI route the client to the correct TLS configuration?

# Question 11: What are common causes of TLS handshake failure?

## Interview Answer

I would investigate:

* Expired certificate
* Certificate not yet valid
* Hostname mismatch
* Missing intermediate certificate
* Untrusted CA
* Unsupported TLS version
* Incompatible cipher configuration
* Incorrect SNI
* Client certificate problems in mTLS
* Load-balancer TLS configuration
* Proxy interference
* Wrong destination

I could start with:

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com
```

and:

```bash
curl -v https://api.example.com
```

The exact error matters.

For example:

```text
certificate verify failed
```

is a very different investigation from:

```text
handshake failure
```

or a TCP connection timeout.

# Question 12: The browser says the certificate is valid, but an application reports certificate verification errors. How can that happen?

## Interview Answer

Different clients may have different trust stores and certificate-handling behavior.

Possibilities include:

* Application container has an outdated CA bundle
* Intermediate certificate is missing
* Browser cached an intermediate
* OS and application use different trust stores
* Java truststore differs from the host
* Application uses a custom CA bundle
* Corporate TLS inspection is involved

I would test from the actual failing runtime.

This is important.

Running:

```bash
curl https://api.example.com
```

from my laptop does not prove that:

```text
production-container-47
```

has the same trust configuration.

I need evidence from the environment where the failure occurs.

# Question 13: What is a certificate chain problem?

## Interview Answer

A typical certificate chain may look like:

```text
Root CA
   |
   v
Intermediate CA
   |
   v
Server Certificate
```

The server generally presents its leaf certificate and required intermediate certificates.

The client uses its trusted root store to build and verify the chain.

If the server fails to provide a required intermediate certificate, some clients may fail validation.

This can produce an especially confusing incident where:

```text
Browser A -> works
Browser B -> works
Java service -> fails
Container -> fails
```

I would inspect the chain with tools such as:

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com \
  -showcerts
```

Then determine whether the expected chain is actually being presented.

# Question 14: What is SNI, and why does it matter?

## Interview Answer

SNI, Server Name Indication, allows the client to indicate the hostname it wants during TLS negotiation.

This is important when multiple HTTPS hostnames share the same IP address or load balancer.

For example:

```text
203.0.113.20

api.example.com
shop.example.com
admin.example.com
```

The server or load balancer needs to know which certificate and configuration to use.

The client provides the requested hostname through SNI.

This is why I often test with:

```bash
openssl s_client \
  -connect 203.0.113.20:443 \
  -servername api.example.com
```

Without the correct SNI value, I may receive the default certificate rather than the certificate for the hostname I am investigating.

# Question 16: TLS works, but the user receives HTTP 502. What does that tell you?

## Interview Answer

It tells me that several layers have already succeeded.

At minimum, from the user's perspective:

```text
DNS        -> likely succeeded
TCP        -> succeeded
TLS        -> succeeded
HTTP       -> response received
```

A `502 Bad Gateway` generally indicates that a gateway or proxy had a problem communicating successfully with an upstream service or received an invalid upstream response.

Architecture:

```text
Client
   |
   v
Reverse Proxy
   |
   X
Upstream Application
```

I would investigate:

* Upstream availability
* Upstream port
* DNS used by proxy
* Connection resets
* Protocol mismatch
* TLS between proxy and upstream
* Upstream crashes
* Proxy logs
* Application logs
* Network connectivity

The important point is that a 502 is not the same as "the load balancer is down."

The load balancer or proxy may be functioning well enough to generate the 502.

# Question 17: How would you investigate a 502 that appeared immediately after deployment?

## Interview Answer

The deployment timing makes the change highly relevant.

I would establish whether all targets are affected.

Suppose:

```text
Target 1 -> healthy responses
Target 2 -> 502
Target 3 -> healthy responses
Target 4 -> 502
```

I would compare:

* Application version
* Listening port
* Process state
* Protocol
* Readiness
* Logs
* Startup configuration

A common scenario could be:

```text
Load Balancer
     |
     v
Target:8080

New application version
     |
     v
Listening on :8081
```

The application may be "running," but the proxy cannot reach it on the expected port.

Another possibility is that the application accepts the TCP connection but resets or closes it before producing a valid HTTP response.

I would correlate proxy logs and upstream logs rather than guessing.

# Question 18: What does HTTP 503 usually suggest in a load-balanced architecture?

## Interview Answer

`503 Service Unavailable` can have multiple causes, but in a load-balanced architecture I would immediately investigate backend availability and routing.

For example:

```text
Load Balancer
     |
     +--> Target A unhealthy
     +--> Target B unhealthy
     +--> Target C unhealthy
```

If there are no eligible healthy targets, the load balancer may be unable to serve the request.

Other possibilities include:

* Application deliberately returning 503
* Overload protection
* Maintenance mode
* Reverse proxy with no usable upstream
* Service discovery failure

I would determine which component generated the 503.

That is critical.

An application-generated 503 and a load-balancer-generated 503 may require completely different investigations.

# Question 19: What is the difference between a 502, 503, and 504 during troubleshooting?

## Interview Answer

I treat them as clues, not complete diagnoses.

### 502 Bad Gateway

Often indicates:

```text
Gateway/proxy
    |
    X
Invalid or failed upstream communication
```

I investigate upstream connection and response behavior.

### 503 Service Unavailable

Often indicates:

```text
Service currently unavailable
```

Potentially:

* No healthy backend
* Overloaded application
* Maintenance
* Explicit application response

### 504 Gateway Timeout

Often indicates:

```text
Gateway
   |
   v
Upstream
   |
   ...
   |
TIMEOUT
```

The gateway waited for an upstream response and exceeded its timeout.

For all three, I first identify:

```text
Who generated the status code?
```

That prevents me from troubleshooting the wrong component.

# Question 20: An application suddenly returns 504 during peak traffic. How would you investigate?

## Interview Answer

I would build a latency chain.

Suppose:

```text
Client
  |
  v
Load Balancer
  |
  v
Reverse Proxy
  |
  v
Application
  |
  v
Database
```

A 504 at the load balancer does not automatically mean the load balancer itself is slow.

The application may be waiting on the database.

I would correlate:

```text
Load balancer response time
Application latency
Database latency
Connection pool usage
CPU
Memory
Request rate
Queue depth
Downstream API latency
```

Suppose:

```text
Normal:

DB query       50 ms
App response   100 ms


Peak:

DB query       35 sec
App response   > 35 sec
LB timeout     30 sec
```

Then the causal chain becomes:

```text
Database saturation
       |
       v
Application waits
       |
       v
Load balancer timeout exceeded
       |
       v
504
```

Increasing the load-balancer timeout to 60 seconds might reduce the number of 504 responses while making users wait longer.

That does not fix the database bottleneck.

# Question 21: What is a reverse proxy?

## Interview Answer

A reverse proxy sits in front of backend services and receives requests on their behalf.

For example:

```text
Users
  |
  v
Nginx
  |
  +----> App 1
  |
  +----> App 2
  |
  +----> App 3
```

It may handle:

* TLS termination
* Routing
* Load balancing
* Compression
* Header manipulation
* Authentication integration
* Caching
* Connection management
* Rate limiting

During troubleshooting, the proxy becomes another failure boundary.

I need to know:

```text
Did request reach proxy?

Did proxy select an upstream?

Did proxy connect?

Did upstream respond?

How long did each stage take?
```

# Question 22: Nginx returns 502, but the backend application is running. What would you check?

## Interview Answer

"Running" does not mean "reachable by Nginx."

I would check whether the backend is actually listening:

```bash
ss -lntp
```

Then test it directly from the proxy host:

```bash
curl -v http://<backend-ip>:<port>
```

I would verify:

* Upstream IP
* Upstream port
* Protocol
* DNS
* Firewall
* Bind address
* Unix socket permissions if applicable
* Application health
* TLS settings if HTTPS is used upstream

For example, if the application listens on:

```text
127.0.0.1:8080
```

but Nginx runs on another machine, the backend is not remotely reachable.

Or Nginx may expect:

```text
http://backend:8080
```

while the backend now expects HTTPS.

The process existing is not sufficient evidence of service health.

# Question 23: Explain connection timeout versus read timeout in a proxy.

## Interview Answer

A connection timeout relates to establishing the upstream connection.

Conceptually:

```text
Proxy
 |
 | trying to establish connection
 |
 v
Backend
```

If the backend cannot be reached or does not establish the connection within the configured period, the connection attempt times out.

A read timeout occurs after communication has progressed further.

The proxy connected, but it waits too long for expected data from the upstream.

```text
Proxy ------ connected ------ Backend
  |
  | waiting for response...
  |
TIMEOUT
```

This distinction is useful because:

```text
Connection timeout
```

pushes me toward connectivity, backlog, firewall, route, or listener issues.

Whereas:

```text
Read timeout
```

pushes me toward application processing, database latency, downstream dependencies, or stalled responses.

---

# Question 24: Why can blindly increasing timeouts make a production incident worse?

## Interview Answer

Longer timeouts consume resources for longer.

Suppose an application dependency becomes slow.

Originally:

```text
Timeout = 5 seconds
```

Engineers increase it to:

```text
Timeout = 60 seconds
```

Now connections, workers, memory, sockets, and possibly threads remain occupied for much longer.

The result could be:

```text
Slow dependency
      |
      v
Requests remain open
      |
      v
Workers exhausted
      |
      v
Connection pools exhausted
      |
      v
More requests queue
      |
      v
Latency increases
      |
      v
Cascading failure
```

Timeouts are part of system capacity and failure behavior.

They should not be changed simply to hide 504 errors.

# Question 25: Explain HTTP keep-alive and why it matters operationally.

## Interview Answer

Without connection reuse, clients may repeatedly establish new TCP connections.

For HTTPS, that may also mean repeated TLS negotiation.

Conceptually:

```text
Without reuse:

TCP -> TLS -> Request -> Close
TCP -> TLS -> Request -> Close
TCP -> TLS -> Request -> Close
```

With persistent connections:

```text
TCP -> TLS
       |
       +-> Request 1
       +-> Request 2
       +-> Request 3
       +-> Request 4
```

Connection reuse can reduce:

* TCP handshake overhead
* TLS handshake overhead
* Connection churn
* Ephemeral port pressure
* NAT pressure

But keep-alive settings also need to be coordinated across proxies, load balancers, clients, and applications.

---

# Question 26: How can mismatched keep-alive or idle timeouts create intermittent failures?

## Interview Answer

Suppose:

```text
Client idle timeout:       120 sec
Load balancer idle timeout: 60 sec
```

The client may believe a connection remains reusable after an intermediary has already closed it.

Depending on the client and timing, the next request may encounter a reset or require reconnection.

Another example:

```text
Load Balancer -> Proxy -> Application
```

Each layer may have different connection lifecycle settings.

If they are poorly aligned, symptoms may include:

* Intermittent resets
* Failed reused connections
* Unexpected 502s
* Increased connection churn

I would compare timeout configuration across the entire request path rather than examining one component in isolation.

# Question 27: Explain HTTP/1.1 versus HTTP/2 from an operational troubleshooting perspective.

## Interview Answer

I would avoid turning this into a protocol-history answer.

Operationally, one major difference is how requests are handled over connections.

HTTP/1.1 often relies on multiple connections for parallelism, although persistent connections can be reused.

HTTP/2 supports multiplexing multiple streams over a single TCP connection.

Conceptually:

```text
HTTP/1.1

Connection 1 -> Request A
Connection 2 -> Request B
Connection 3 -> Request C
```

Versus:

```text
HTTP/2

Single TCP connection
      |
      +-> Stream A
      +-> Stream B
      +-> Stream C
```

During troubleshooting, I would consider:

* Protocol negotiation
* Proxy support
* Load balancer support
* Connection behavior
* Header handling
* Backend protocol
* Whether HTTP/2 terminates at the frontend while HTTP/1.1 is used upstream

A user speaking HTTP/2 to a load balancer does not necessarily mean the load balancer speaks HTTP/2 to the backend.

# Question 32: What are sticky sessions?

## Interview Answer

Sticky sessions, or session affinity, attempt to route a client's requests to the same backend target for some period.

For example:

```text
User A ----> App 1
User A ----> App 1
User A ----> App 1

User B ----> App 2
User B ----> App 2
```

They are sometimes used when session state is stored locally on the application server.

Operationally, this can hide architecture problems.

Suppose App 2 is broken.

Without stickiness, many users may occasionally hit it.

With stickiness:

```text
Users pinned to App 1 -> fine
Users pinned to App 2 -> consistently fail
```

This can make incidents appear user-specific.


I would not assume authentication itself is broken until I have compared the request paths.

# Question 34: What is connection draining?

## Interview Answer

Connection draining allows an instance or backend to stop receiving new traffic while existing in-flight connections are given time to complete.

Conceptually:

```text
Before removal:

New requests ---> Target A
Existing -------> Target A


Draining:

New requests -----X Target A

Existing requests ---> Target A
                       |
                       v
                    complete
```

After the draining period, the target can be removed safely.

This matters during:

* Deployments
* Scaling down
* Maintenance
* Instance replacement
* Cluster operations

Without graceful draining, active requests may be terminated abruptly.

## Interview Answer

The short deployment-correlated window makes lifecycle handling a strong hypothesis.

I would investigate:

* Connection draining
* Deregistration delay
* Application shutdown behavior
* Readiness
* Startup time
* Load-balancer health thresholds
* Deployment ordering

A problematic sequence could be:

```text
Deployment tells application to stop
        |
        v
Application exits immediately
        |
        v
Load balancer still routes requests
        |
        v
Connection failures
        |
        v
502
```

A safer sequence is:

```text
Mark target unavailable for new traffic
        |
        v
Drain existing requests
        |
        v
Stop application
        |
        v
Deploy
        |
        v
Start application
        |
        v
Pass readiness/health checks
        |
        v
Receive traffic
```

This is a deployment architecture problem, not merely an HTTP error problem.

# Question 36: Why can a target pass health checks but fail real traffic?

## Interview Answer

Health checks may be too shallow.

For example:

```text
/health -> 200
```

could simply prove that the HTTP server process is alive.

Real traffic may require:

```text
Database
Redis
Authentication service
Message broker
External APIs
Correct configuration
```

Another possibility is that the health-check request differs from user traffic.

For example:

```text
Health check:
HTTP/1.1
Host: internal-target
GET /health

User:
HTTPS
Host: api.example.com
GET /checkout
```

Different routes, headers, dependencies, or protocols may be involved.

A health check should test the right thing without becoming so dependency-heavy that one minor downstream problem unnecessarily removes every target.

That is an architectural trade-off.

# Question 37: How would you troubleshoot an application through every network layer?

## Interview Answer

I would work from the user inward.

Suppose:

```text
https://api.example.com/orders
```

is failing.

### Layer 1: DNS

```bash
dig api.example.com
```

Question:

```text
Does the hostname resolve to the expected destination?
```

### Layer 2: Routing and reachability

Question:

```text
Can traffic reach that destination?
```

Use routing and packet evidence where needed.

### Layer 3: TCP

Question:

```text
Does port 443 establish a TCP connection?
```

Use:

```bash
ss
tcpdump
nc
```

where appropriate.

### Layer 4: TLS

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com
```

Question:

```text
Does TLS negotiate successfully?
```

### Layer 5: HTTP

```bash
curl -v https://api.example.com/orders
```

Question:

```text
What HTTP response is actually returned?
```

### Layer 6: Load balancer

Question:

```text
Which target received the request?
Was it healthy?
How long did the target take?
```

### Layer 7: Reverse proxy

Question:

```text
Did the proxy successfully communicate
with its upstream?
```

### Layer 8: Application

Question:

```text
Did the request reach application code?
```

### Layer 9: Dependencies

Question:

```text
What did the application wait for?
```

That might be:

```text
Database
Cache
Queue
Authentication
External API
```

The principle is:

```text
Find the last layer that worked
and the first layer that failed.
```

# Question 38: Users report "the site is slow." What measurements would you want before changing anything?

## Interview Answer

"The site is slow" is not sufficiently precise.

I would decompose latency.

For example:

```text
DNS lookup
      +
TCP connection
      +
TLS handshake
      +
Proxy processing
      +
Application processing
      +
Database/dependency time
      +
Response transfer
      =
User-perceived latency
```

I want to determine which component changed.

Suppose:

```text
DNS             20 ms
TCP             30 ms
TLS             50 ms
Load balancer   10 ms
Application    120 ms
Database        80 ms
```

That is very different from:

```text
DNS             20 ms
TCP             30 ms
TLS             50 ms
Load balancer   10 ms
Application   6200 ms
Database      6100 ms
```

Or:

```text
DNS           4500 ms
TCP             30 ms
TLS             50 ms
Application    120 ms
```

All three produce:

```text
"The website is slow."
```

But they require completely different fixes.

# Question 39: How can `curl` help separate these stages?

## Interview Answer

`curl` can expose useful timing information.

For example:

```bash
curl -s -o /dev/null \
  -w 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nstarttransfer=%{time_starttransfer}\ntotal=%{time_total}\n' \
  https://api.example.com
```

This can help distinguish:

* DNS delay
* TCP connection delay
* TLS delay
* Time to first byte
* Total request time

Suppose:

```text
dns=0.020
connect=0.050
tls=0.110
starttransfer=5.800
total=5.810
```

DNS, TCP, and TLS are relatively fast.

The large delay occurs before the first response byte.

That pushes me toward:

```text
Proxy
Application
Database
Downstream dependency
```

rather than DNS.

# Question 40: Why is "works from my laptop" weak evidence during a production incident?

## Interview Answer

My laptop may use a completely different path.

For example:

```text
My Laptop
   |
   v
Public DNS
   |
   v
Public Load Balancer


Production Service
   |
   v
Internal DNS
   |
   v
Private Load Balancer
```

They may differ in:

* DNS resolver
* DNS view
* Network route
* Proxy
* Certificate trust store
* Source IP
* Firewall policy
* IPv4/IPv6 preference
* Client protocol
* Geographic location

Therefore, I want to reproduce the problem from the failing environment.

If a Kubernetes Pod cannot connect, testing from my laptop proves very little about the Pod's DNS, routing, TLS trust, or network policy.

# Question 41: Production traffic intermittently receives both 200 and 502 responses. How would you approach it?

## Interview Answer

Intermittency often means I should look for differences between requests.

I would correlate failures with:

* Backend target
* Availability Zone
* Load-balancer node
* Application version
* Client type
* HTTP protocol
* Source location
* Session affinity
* Request path

Suppose:

```text
Target A -> 200
Target B -> 200
Target C -> 502
Target D -> 200
```

Now I have a target-specific incident.

Suppose instead:

```text
All targets occasionally fail
at exactly the same time
```

Then I would look for a shared dependency.

For example:

```text
                 +--> App A
                 |
Load Balancer ---+--> App B
                 |
                 +--> App C
                        |
                        v
                    Database
```

If the database becomes unavailable, every target may fail together.

Patterns matter.

# Question 42: How would you distinguish a load-balancer problem from an application problem?

## Interview Answer

I would compare traffic through the load balancer with direct backend testing where safe and architecturally possible.

Suppose:

```text
Through LB:
502

Direct backend:
200
```

That makes me investigate:

* Load-balancer target configuration
* Protocol
* Port
* Health check
* TLS
* Host header
* Routing rules

But if:

```text
Through LB:
502

Direct backend:
connection reset
```

the backend itself is clearly involved.

I would also compare:

```text
Load-balancer logs
Application logs
Proxy logs
Metrics
Packet captures
```

The goal is to identify the first component where expected behavior diverges.

# Question 43: A load balancer reports healthy targets, but users receive 503 errors during traffic spikes. What would you investigate?

## Interview Answer

I would not assume health checks prove capacity.

A backend may respond successfully to lightweight health checks while being unable to handle production workload.

I would inspect:

* Request rate
* Concurrent requests
* Application workers
* Thread pools
* Connection pools
* Queue depth
* CPU
* Memory
* Downstream dependency capacity
* Autoscaling behavior
* Rate limits

For example:

```text
Health check:
1 tiny request every 10 seconds -> 200

Production:
20,000 concurrent requests -> overloaded
```

Health and capacity are different concepts.

# Question 44: What is the danger of making health checks too aggressive?

## Interview Answer

Overly aggressive health checks can remove targets because of brief transient failures.

Imagine:

```text
One failed request
      |
      v
Target immediately marked unhealthy
      |
      v
Traffic shifts to remaining targets
      |
      v
Remaining targets overloaded
      |
      v
More health checks fail
      |
      v
More targets removed
```

This can amplify a small problem.

Health checks require thoughtful:

* Interval
* Timeout
* Healthy threshold
* Unhealthy threshold
* Endpoint design

The goal is to remove genuinely unhealthy targets quickly enough without turning momentary latency into a cascading outage.

---

# Question 45: What is the danger of making health checks too tolerant?

## Interview Answer

The opposite problem occurs.

A broken target may remain in rotation for too long.

For example:

```text
Target starts failing
      |
      v
Health check requires many failures
      |
      v
Load balancer keeps routing users
      |
      v
Users continue receiving errors
```

So health-check configuration is a balance between:

```text
Fast failure detection
        versus
Tolerance of transient problems
```

There is no universal number that works for every application.

# Final Production Scenario

## Question 46: After a deployment, approximately 30 percent of users receive intermittent 502 and 504 errors. Other users are unaffected. Walk through your investigation.

The architecture is:

```text
Users
  |
  v
DNS
  |
  v
CDN
  |
  v
Load Balancer
  |
  v
Nginx
  |
  v
Application
  |
  +----> Database
  |
  +----> Redis
  |
  +----> Payment API
```

## Interview Answer

I would first establish whether the 30 percent failure rate correlates with a specific path.

I would not restart everything.

---

## Step 1: Establish the timeline

I want:

```text
Deployment started
Deployment completed
Errors started
502 rate
504 rate
Affected regions
Affected clients
```

If errors began immediately after deployment, the deployment is a strong suspect but not yet proven as the cause.

---

## Step 2: Check DNS consistency

I would verify whether users are resolving the same frontend.

Suppose DNS has two records:

```text
api.example.com

203.0.113.10
203.0.113.20
```

If:

```text
203.0.113.10 -> healthy
203.0.113.20 -> problematic
```

that could explain partial impact.

If DNS is consistent, I continue inward.

---

## Step 3: Check CDN and load-balancer metrics

I would inspect:

```text
Request count
5xx rate
Target response time
Healthy target count
Target-specific errors
```

Suppose I discover:

```text
App A -> healthy
App B -> healthy
App C -> errors
App D -> healthy
```

Now the incident is no longer "30 percent of users."

It is potentially one bad backend receiving approximately that portion of traffic.

---

## Step 4: Compare the bad target

I would inspect:

```bash
ss -lntp
```

application logs, proxy logs, resource usage, configuration, and deployment version.

Suppose App C has the new release while the other servers are still on the previous version.

That becomes a strong deployment hypothesis.

---

## Step 5: Explain the 502

Suppose Nginx logs show:

```text
upstream prematurely closed connection
```

and application logs show the process crashing on certain requests.

The path becomes:

```text
Client
  |
  v
LB
  |
  v
Nginx
  |
  v
Application
  |
  X crash/reset

Nginx -> 502
```

Now the 502 is explained.

---

## Step 6: Explain the 504

But some requests return 504 rather than 502.

I would investigate those separately.

Suppose those requests involve the payment API.

The new application release introduced aggressive retries.

```text
Payment API slow
      |
      v
Application waits
      |
      v
Retry
      |
      v
Waits longer
      |
      v
Proxy timeout exceeded
      |
      v
504
```

Now one deployment created two different failure modes.

That is realistic production troubleshooting.

Do not force every symptom into one explanation when evidence shows multiple causes.

---

## Step 7: Mitigate

If the deployment is clearly responsible and rollback is safe, I would roll back the affected version or remove problematic targets from rotation.

I would ensure connection draining is respected.

```text
Stop new traffic
      |
      v
Drain active requests
      |
      v
Rollback
      |
      v
Start
      |
      v
Pass health/readiness checks
      |
      v
Restore traffic
```

---

## Step 8: Verify

I would verify:

```text
502 rate -> baseline
504 rate -> baseline
Healthy targets -> expected
Application latency -> normal
Payment API traffic -> normal
Retry volume -> normal
User success rate -> normal
```

I would not declare recovery because the deployment command completed successfully.

Recovery must be visible in production behavior.

# Interviewer Follow-Up: Why didn't the health check catch the broken version?

## Interview Answer

I would inspect what the health endpoint actually tested.

Suppose:

```text
GET /health

returns:

200 OK
```

as long as the process is running.

But the failure only occurs when:

```text
POST /payment
```

uses a new code path.

Then the health check is behaving exactly as designed.

It simply does not cover the failing behavior.

I would evaluate whether readiness should test additional critical conditions, but I would avoid making the endpoint dependent on every downstream service without considering the consequences.

# Interviewer Follow-Up: Why not increase the proxy timeout to stop the 504 errors?

## Interview Answer

Because the timeout may be exposing a deeper latency problem.

If the application waits 45 seconds because a dependency is overloaded, increasing the timeout from 30 seconds to 60 seconds changes:

```text
504 after 30 seconds
```

into:

```text
User waits 45 seconds
```

That is not necessarily recovery.

Worse, longer-running requests may increase:

```text
Open connections
Worker occupancy
Memory usage
Connection pool pressure
Queue depth
```

and contribute to cascading failure.

I would fix the latency source first unless there is evidence that the existing timeout is genuinely inappropriate.

---

# Interviewer Follow-Up: Why not disable sticky sessions?

## Interview Answer

I would first determine whether stickiness is actually contributing to the incident.

If certain users are pinned to broken targets, disabling affinity might distribute failures differently, but it does not fix the broken targets.

If the application depends on local session state, disabling stickiness could introduce new failures.

I would understand the session architecture before changing affinity behavior.

# Production Investigation Framework

When users report an application failure, move through the request path deliberately.

```text
1. DNS
   |
   | Correct answer?
   v

2. ROUTING
   |
   | Correct destination?
   v

3. TCP
   |
   | Connection established?
   v

4. TLS
   |
   | Certificate and handshake valid?
   v

5. HTTP
   |
   | What status/behavior?
   v

6. CDN / LOAD BALANCER
   |
   | Which backend?
   | Healthy?
   v

7. REVERSE PROXY
   |
   | Upstream connection successful?
   v

8. APPLICATION
   |
   | Request processed?
   v

9. DEPENDENCIES
   |
   | DB, cache, queue, APIs?
   v

10. RESPONSE PATH
    |
    | Did response return correctly?
    v

11. CLIENT
    |
    | What did the user actually experience?
```

The central question is:

```text
What is the last layer I can prove worked?

What is the first layer I can prove failed?
```

# What a Mid-Level Candidate Should Demonstrate

A junior candidate may say:

```text
"DNS is not working."
```

A mid-level candidate should determine:

```text
"Authoritative DNS returns the correct record,
but one recursive resolver intermittently
returns SERVFAIL."
```

A junior candidate may say:

```text
"The SSL certificate is broken."
```

A mid-level candidate should determine:

```text
"The leaf certificate is valid, but the
load balancer is not presenting the required
intermediate certificate, causing clients
without the intermediate cached locally
to fail chain validation."
```

A junior candidate may say:

```text
"We have 502 errors."
```

A mid-level candidate should ask:

```text
Which component generated the 502?

Which upstream was selected?

Did TCP connect?

Did TLS succeed upstream?

Did the application reset the connection?

Did the upstream return a valid HTTP response?
```

A junior candidate may say:

```text
"Increase the timeout."
```

A mid-level candidate should ask:

```text
Which timeout?

Connection timeout?

Read timeout?

Idle timeout?

What is actually consuming the time?

What resources remain occupied while we wait?

Will increasing this value hide or amplify
the underlying failure?
```

A junior candidate may say:

```text
"The load balancer says the server is healthy."
```

A mid-level candidate understands:

```text
A health check proves only
what the health check actually tests.
```

That distinction is the purpose of Part 3.
