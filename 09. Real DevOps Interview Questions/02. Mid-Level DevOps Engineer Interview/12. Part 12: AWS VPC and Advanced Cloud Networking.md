# Part 12: AWS VPC and Advanced Cloud Networking

At mid-level, AWS networking interviews should move far beyond:

* What is a VPC?
* What is a subnet?
* What is a security group?
* What is a NAT Gateway?

The candidate should be able to trace traffic across AWS networks and identify exactly where connectivity fails.

The interviewer should expect you to reason about:

* Routing decisions
* Public and private subnet design
* Internet access
* NAT failures
* Stateful and stateless filtering
* Private AWS service access
* Multi-VPC architecture
* Hybrid connectivity
* Route propagation
* DNS across VPC boundaries
* Cross-AZ traffic
* Network observability

A useful mental model is:

```text
Application
    |
    v
ENI
    |
    v
Security Group
    |
    v
Subnet Route Table
    |
    v
Network Path
    |
    +----> Internet Gateway
    |
    +----> NAT Gateway
    |
    +----> VPC Endpoint
    |
    +----> VPC Peering
    |
    +----> Transit Gateway
    |
    +----> VPN / Direct Connect
    |
    v
Destination Network
    |
    v
Destination Security Controls
    |
    v
Destination Resource
```

The strongest networking answer is not:

```text
"The VPC is broken."
```

It is:

```text
"The source subnet sends 10.20.0.0/16
to the Transit Gateway, but the Transit
Gateway route table has no route toward
the destination VPC attachment."
```

That is the level expected in Part 12.

# Question 1: How does AWS decide where to send a packet from an EC2 instance?

## Interview Answer

I think about routing from the resource's network interface outward.

Suppose an EC2 instance has:

```text
Private IP:
10.10.1.25

Destination:
10.30.8.40
```

The subnet's route table determines the next hop for that destination.

Conceptually:

```text
EC2
 |
 v
Subnet Route Table
 |
 +---- 10.10.0.0/16 -> local
 |
 +---- 10.30.0.0/16 -> Transit Gateway
 |
 +---- 0.0.0.0/0 -> NAT Gateway
```

AWS uses the most specific matching route.

So:

```text
10.30.0.0/16
```

takes precedence over:

```text
0.0.0.0/0
```

because `/16` is more specific.

When troubleshooting, I want to know:

```text
Source subnet
Destination address
Applicable route table
Most specific route
Next hop
Return path
```

Routing is directional.

A valid route from A to B does not prove B can return traffic to A.

# Question 2: What is longest-prefix matching, and why does it matter?

## Interview Answer

AWS route selection generally prefers the most specific route matching the destination.

Suppose a route table contains:

```text
10.0.0.0/8       -> Transit Gateway
10.20.0.0/16     -> VPC Peering
0.0.0.0/0        -> NAT Gateway
```

Traffic to:

```text
10.20.5.10
```

matches all three logically except default is broadest.

The most specific relevant route is:

```text
10.20.0.0/16
```

so that route wins.

This matters during migrations.

A team may add a specific route without realizing it overrides a broader route already handling traffic.

Suddenly:

```text
Some destinations work
Some destinations use new path
```

even though the default route did not change.

# Question 3: What makes a subnet public?

## Interview Answer

A subnet is commonly considered public when resources in that subnet can route directly toward an Internet Gateway and have the necessary public addressing and security configuration.

A typical public subnet route table contains:

```text
10.0.0.0/16 -> local
0.0.0.0/0   -> Internet Gateway
```

Architecture:

```text
Internet
   |
   v
Internet Gateway
   |
   v
Public Subnet
   |
   +---- ALB
   |
   +---- NAT Gateway
```

But having a route to an Internet Gateway alone does not automatically make every resource publicly reachable.

The resource also needs appropriate public addressing and network controls.

# Question 4: What makes a subnet private?

## Interview Answer

A private subnet normally does not have a direct default route to an Internet Gateway for its workloads.

For outbound internet access, it might use:

```text
Private Subnet
     |
     v
NAT Gateway
     |
     v
Internet Gateway
     |
     v
Internet
```

A typical private route table might contain:

```text
10.0.0.0/16 -> local
0.0.0.0/0   -> NAT Gateway
```

The application instance itself does not need a public IP.

That is useful for workloads such as:

* Application servers
* Internal services
* Databases
* Kubernetes worker nodes

depending on architecture.

# Question 5: Why shouldn't application servers automatically live in public subnets?

## Interview Answer

Because many application servers do not need direct inbound internet exposure.

A common design is:

```text
Internet
   |
   v
Public ALB
   |
   v
Private Application Subnets
   |
   v
Database Subnets
```

The ALB handles public ingress.

Application instances remain privately addressed.

This reduces unnecessary exposure and makes the traffic path more deliberate.

Public subnet placement should exist because the resource needs that network relationship, not because it is easier during initial setup.

# Question 6: A private EC2 instance cannot reach the internet. How do you troubleshoot it?

## Interview Answer

I trace the full egress path.

```text
EC2
 |
 v
Private Subnet Route Table
 |
 v
NAT Gateway
 |
 v
Public Subnet Route Table
 |
 v
Internet Gateway
 |
 v
Internet
```

I verify:

* EC2 security group egress
* Private subnet route
* NAT Gateway state
* NAT Gateway subnet
* NAT public addressing
* Public subnet route to IGW
* NACLs
* DNS if hostname-based test fails

I also separate:

```text
DNS failure
```

from:

```text
Internet routing failure
```

If:

```text
curl https://example.com
```

fails, I should not automatically blame NAT.

I need to determine whether the hostname resolved first.

# Question 7: What is a NAT Gateway actually doing?

## Interview Answer

For IPv4 internet access, a NAT Gateway allows resources using private source addresses to initiate connections outward while translating those connections through the NAT's public-facing path.

Conceptually:

```text
EC2
10.0.2.20
   |
   v
NAT Gateway
   |
   v
Translated source
   |
   v
Internet
```

The remote service sees the translated source address instead of the EC2 private IP.

The NAT maintains state for those flows so responses can return.

It does not normally provide unsolicited inbound internet connectivity to private instances.

# Question 8: Why should you usually deploy NAT Gateways per Availability Zone?

## Interview Answer

One reason is failure-domain alignment.

Suppose:

```text
AZ-A private subnet
     |
     v
NAT Gateway in AZ-A

AZ-B private subnet
     |
     v
NAT Gateway in AZ-B
```

If AZ-A has problems, AZ-B's outbound path remains independent.

A weaker architecture might be:

```text
AZ-A private
      \
       \
AZ-B private ---> NAT in AZ-A
```

Now workloads in AZ-B depend on AZ-A for internet egress.

That creates:

* Cross-AZ dependency
* Cross-AZ traffic
* Additional failure coupling

Multi-AZ application architecture should consider egress architecture too.

# Question 9: NAT Gateway is `Available`, but applications cannot reach external services. What could still be wrong?

## Interview Answer

`Available` only tells me the NAT resource exists and is operational from the service perspective.

I would still inspect:

* Private subnet route
* NAT subnet route
* Internet Gateway attachment
* NACL
* Application security group
* Source subnet association
* Destination restrictions
* DNS
* Port exhaustion or NAT capacity symptoms
* External service allowlist

For example:

```text
Private subnet route:

0.0.0.0/0 -> nat-AAA
```

could be correct.

But NAT Gateway lives in a subnet whose route table lacks:

```text
0.0.0.0/0 -> igw-AAA
```

Now the path stops after the NAT.

# Question 10: Only workloads in one AZ cannot reach the internet. What does that suggest?

## Interview Answer

I would compare the AZ-specific egress paths.

Suppose:

```text
AZ-A -> NAT-A -> works
AZ-B -> NAT-B -> fails
AZ-C -> NAT-C -> works
```

Now I investigate:

* NAT-B
* AZ-B private route tables
* NAT-B public subnet
* NACLs
* Associated routes

The external service is unlikely to be globally unavailable if two other zones consistently work.

Failure patterns across AZs are extremely useful.

# Question 11: Why can NAT port exhaustion create intermittent failures?

## Interview Answer

NAT needs translated source-port combinations for outbound connections.

A high number of simultaneous connections toward the same external destination can pressure available translation resources.

Typical contributors include:

```text
High connection rate
No keep-alive
Poor connection pooling
Retry storms
Large container fleets
```

Symptoms might be:

```text
Existing connections work
New connections intermittently fail
Peak traffic is worst
```

I would investigate connection behavior rather than immediately creating more EC2 instances.

More instances can produce even more outbound connections.

# Question 12: What is an Internet Gateway?

## Interview Answer

An Internet Gateway provides connectivity between a VPC and the public internet when routing, addressing, and security configuration allow it.

Conceptually:

```text
Internet
   |
   v
Internet Gateway
   |
   v
VPC
```

It is highly available as an AWS-managed VPC component.

But attaching an IGW to a VPC does not automatically make every subnet or resource public.

Route tables still control whether traffic uses it.

# Question 13: Why might an EC2 instance with a public IP still be unreachable from the internet?

## Interview Answer

I would inspect:

* Subnet route to Internet Gateway
* Security group
* NACL
* Application listener
* OS firewall
* Public IP association
* Correct port

For example:

```text
Public IP exists
```

but route table has no:

```text
0.0.0.0/0 -> IGW
```

The network path is incomplete.

Similarly, if the application listens only on:

```text
127.0.0.1:8080
```

network configuration can be perfect and remote users still cannot connect.

# Question 14: Explain security groups in production terms.

## Interview Answer

Security groups act as stateful network filters associated with resources such as ENIs.

I think in terms of:

```text
Source
Destination
Protocol
Port
```

For example, an application security group might allow:

```text
Inbound TCP 8080
from ALB security group
```

rather than:

```text
0.0.0.0/0
```

This creates a relationship:

```text
Internet
   |
   v
ALB SG
   |
   v
Application SG
```

The application tier trusts the ALB tier rather than the entire internet.

# Question 15: What does stateful mean for security groups?

## Interview Answer

If inbound traffic is allowed, response traffic for that established flow is automatically allowed through the security-group state model.

Conceptually:

```text
Client
  |
  | allowed inbound
  v
EC2

EC2
  |
  | return traffic recognized
  v
Client
```

I do not normally need to create a separate return rule merely for established response traffic in the opposite direction.

This differs from NACL behavior.

# Question 16: Explain NACLs.

## Interview Answer

Network ACLs are stateless subnet-level network controls.

They evaluate inbound and outbound traffic separately.

Conceptually:

```text
Internet
   |
Inbound NACL rules
   |
   v
Subnet
   |
   v
Resource

Response
   |
Outbound NACL rules
   |
   v
Internet
```

Because they are stateless, return traffic must also be allowed explicitly.

This is why ephemeral port behavior matters when troubleshooting NACLs.

# Question 17: Security group allows port 443, but traffic still times out. How could the NACL be responsible?

## Interview Answer

Suppose inbound HTTPS is allowed:

```text
Inbound:
TCP 443 -> ALLOW
```

But return traffic to the client's ephemeral port range is blocked outbound.

The request may reach the server.

The response is dropped.

Conceptually:

```text
Client:53000
      |
      | -> Server:443
      v
Server

Server:443
      |
      X outbound NACL blocks
      |
Client:53000
```

The security group can be correct while the stateless subnet ACL breaks the flow.

# Question 18: Why should NACLs not be the first place you make random troubleshooting changes?

## Interview Answer

Because they operate at subnet scope and can affect many workloads simultaneously.

Opening:

```text
0.0.0.0/0
ALL TRAFFIC
```

may hide the root cause and weaken security across the entire subnet.

I prefer to determine:

```text
Source
Destination
Protocol
Source port
Destination port
Direction
```

and inspect the specific NACL rule path.

# Question 19: What is a VPC endpoint?

## Interview Answer

A VPC endpoint allows private connectivity from a VPC to supported services without requiring the traffic to traverse a traditional internet/NAT path.

Two important categories are:

```text
Gateway endpoints
Interface endpoints
```

Architecture example:

```text
Private EC2
    |
    v
VPC Endpoint
    |
    v
AWS Service
```

This can reduce dependence on NAT for certain service calls.

# Question 20: What is a gateway endpoint typically used for?

## Interview Answer

Gateway endpoints are associated with supported services such as S3 and DynamoDB.

They work through route table integration.

Conceptually:

```text
Private Subnet
     |
     v
Route Table
     |
     +---- S3 prefix/service route -> Gateway Endpoint
     |
     +---- 0.0.0.0/0 -> NAT
```

Traffic to the supported service can use the endpoint rather than NAT.

# Question 21: What is an interface endpoint?

## Interview Answer

An interface endpoint uses AWS PrivateLink and creates elastic network interfaces with private IPs inside selected subnets.

Conceptually:

```text
Application
    |
    v
Private IP
Interface Endpoint ENI
    |
    v
AWS service / PrivateLink service
```

Private DNS can often make normal service hostnames resolve to the private endpoint addresses.

Interface endpoints have security groups, which become part of the path.

# Question 22: An EC2 instance cannot access Secrets Manager after you added an interface endpoint. What do you check?

## Interview Answer

I inspect:

* Endpoint state
* Endpoint subnets
* Endpoint security group
* Private DNS
* VPC DNS settings
* Endpoint policy
* Application security group
* IAM authorization

A common mistake is:

```text
Application SG allows outbound
```

but endpoint security group does not permit inbound HTTPS from the application.

Another possibility is DNS still resolving to a public path that no longer works.

# Question 23: Why can a VPC endpoint policy create `AccessDenied`?

## Interview Answer

Because an endpoint policy can restrict which API actions or resources are allowed through that endpoint.

Authorization can therefore involve several layers:

```text
IAM identity policy
       |
       v
VPC Endpoint Policy
       |
       v
Service resource policy
       |
       v
KMS if encrypted
```

A user may have IAM permission but still be denied by the endpoint path.

That is why cloud authorization troubleshooting is rarely just "check IAM."

# Question 24: What is AWS PrivateLink conceptually?

## Interview Answer

PrivateLink allows consumers to access a service privately through interface endpoints without requiring broad network-level connectivity between the consumer and provider networks.

Conceptually:

```text
Consumer VPC
     |
     v
Interface Endpoint
     |
     v
PrivateLink
     |
     v
Provider Service
```

This is very different from connecting entire address spaces.

The consumer accesses the exposed service, not arbitrary resources in the provider VPC.

# Question 25: PrivateLink versus VPC peering, how do you decide?

## Interview Answer

I ask what needs connectivity.

If VPC A needs broad private IP connectivity to resources in VPC B:

```text
VPC Peering
```

may fit.

If consumers only need a specific service:

```text
PrivateLink
```

can provide a narrower service-oriented boundary.

Conceptually:

```text
PEERING

VPC A <------> VPC B
network relationship
```

versus:

```text
PRIVATELINK

Consumer -> specific published service
```

PrivateLink can be especially useful when I do not want to expose the provider's wider network.

# Question 26: What is VPC peering?

## Interview Answer

VPC peering provides private network connectivity between two VPCs.

Conceptually:

```text
VPC A
10.10.0.0/16
      |
      v
Peering Connection
      |
      v
VPC B
10.20.0.0/16
```

Both sides need appropriate routes.

For example:

VPC A:

```text
10.20.0.0/16 -> pcx-123
```

VPC B:

```text
10.10.0.0/16 -> pcx-123
```

Security controls also need to permit the traffic.

# Question 27: VPC A can send traffic to VPC B, but responses never return. What would you inspect?

## Interview Answer

I inspect the reverse route.

Perhaps VPC A has:

```text
10.20.0.0/16 -> peering
```

but VPC B has no:

```text
10.10.0.0/16 -> peering
```

The request reaches B.

The response follows another route or fails.

This is a classic asymmetric connectivity problem.

For every network path, I think:

```text
Forward path
+
Return path
```

# Question 28: Is VPC peering transitive?

## Interview Answer

No, I should not assume transitive routing.

Suppose:

```text
VPC A <--> VPC B <--> VPC C
```

A peering relationship between A and B and another between B and C does not automatically turn B into a transit router allowing A to reach C.

For larger multi-VPC architectures, Transit Gateway is often more appropriate.

# Question 29: Why do overlapping CIDR ranges cause problems with VPC peering?

## Interview Answer

Routing must uniquely determine where traffic belongs.

Suppose:

```text
VPC A:
10.0.0.0/16

VPC B:
10.0.0.0/16
```

Now addresses overlap.

A source in VPC A cannot cleanly distinguish:

```text
10.0.1.20 local
```

from:

```text
10.0.1.20 remote
```

in VPC B.

Address planning becomes crucial once many VPCs, accounts, regions, and on-prem networks need interconnection.

# Question 30: What is Transit Gateway?

## Interview Answer

Transit Gateway provides centralized routing between multiple connected networks.

Conceptually:

```text
           VPC A
             |
             v
VPC B --> Transit Gateway <-- VPC C
             |
             v
          VPN / DX
```

Instead of building a large peering mesh:

```text
A-B
A-C
A-D
B-C
B-D
C-D
```

multiple networks attach to a central transit architecture.

The Transit Gateway has its own routing behavior, which becomes critical during troubleshooting.

# Question 31: Why is Transit Gateway more scalable than a large peering mesh?

## Interview Answer

Because connection topology is centralized.

Suppose I have:

```text
50 VPCs
```

A full peering mesh creates a large number of individual relationships and route-management points.

With Transit Gateway:

```text
VPC 1 \
VPC 2  \
VPC 3 ---> TGW
...     /
VPC 50/
```

I can centralize routing policies and connectivity.

But this also makes Transit Gateway a critical network control plane that must be designed carefully.

# Question 32: VPC is attached to Transit Gateway but cannot reach another attached VPC. What do you inspect?

## Interview Answer

Attachment existence alone does not prove routing.

I inspect:

```text
Source subnet route table
        |
        v
TGW attachment
        |
        v
TGW route table association
        |
        v
TGW route
        |
        v
Destination attachment
        |
        v
Destination VPC route table
```

I also inspect security groups, NACLs, and destination application state.

The source may route traffic into TGW while TGW itself has no destination route.

# Question 33: What is the difference between Transit Gateway route table association and propagation?

## Interview Answer

At a conceptual level:

Association determines which Transit Gateway route table an attachment uses for routing decisions.

Propagation allows an attachment's routes to be learned into selected TGW route tables when configured.

Think:

```text
ASSOCIATION

Which routing table
does this attachment consult?
```

```text
PROPAGATION

Which routing tables
learn routes from this attachment?
```

Misunderstanding these can create surprising one-way connectivity.

# Question 34: What is a route conflict in AWS networking?

## Interview Answer

A route conflict occurs when route design causes traffic to follow an unintended path or makes desired paths ambiguous or unavailable.

Examples include:

* Overlapping CIDRs
* More-specific route introduced unexpectedly
* Static route overriding propagated behavior
* Incorrect TGW propagation
* VPN and Direct Connect advertising overlapping prefixes
* Default route pointed at wrong appliance

For example:

```text
10.0.0.0/8 -> Transit Gateway
10.20.0.0/16 -> Firewall appliance
```

Traffic to `10.20.5.5` uses the `/16` route.

If the firewall route was added accidentally, only that network may break.

# Question 35: Why are broad RFC1918 routes dangerous in large environments?

## Interview Answer

A route such as:

```text
10.0.0.0/8 -> TGW
```

looks convenient.

But as the architecture grows, it can unintentionally capture traffic intended for:

* Local services
* VPN
* Peering
* Inspection appliances

More-specific routes may later override parts of it, making behavior difficult to reason about.

I prefer intentional IP planning and route ownership.

# Question 36: What is hybrid connectivity?

## Interview Answer

Hybrid connectivity connects AWS networks with on-premises or other private infrastructure.

Common approaches include:

```text
Site-to-Site VPN
Direct Connect
```

A typical architecture:

```text
On-Premises
     |
     v
VPN / Direct Connect
     |
     v
Transit Gateway / VGW
     |
     v
AWS VPCs
```

The key challenges include:

* Route exchange
* Address overlap
* Redundancy
* Encryption requirements
* Failure behavior
* DNS

# Question 37: What is a Site-to-Site VPN?

## Interview Answer

It creates encrypted IPsec tunnels between AWS and another network.

Conceptually:

```text
On-Prem Router
     |
     v
Encrypted Tunnel
     |
     v
AWS
```

A production design should account for tunnel redundancy.

But having multiple tunnels does not guarantee failover works correctly.

Routing and customer gateway behavior also matter.

# Question 38: VPN tunnel shows `UP`, but application connectivity fails. What does that tell you?

## Interview Answer

Tunnel state proves only part of the network.

I still inspect:

```text
Route advertisements
VPC route tables
TGW routes
On-prem routes
Security groups
NACLs
Firewalls
Application port
Return path
```

A VPN can be operational at the tunnel level while the required prefix is not routed across it.

# Question 39: What is Direct Connect conceptually?

## Interview Answer

Direct Connect provides dedicated private connectivity between customer infrastructure and AWS through supported connectivity arrangements.

Conceptually:

```text
Data Center
    |
    v
Dedicated Connection
    |
    v
AWS Network
```

It can provide more predictable private connectivity than relying entirely on internet-based VPN paths.

But production designs still need redundancy.

A single physical Direct Connect path can itself become a single point of failure.

# Question 40: Would you use only one Direct Connect connection for a critical workload?

## Interview Answer

Not if the business requires high availability.

I would consider redundant connectivity through:

* Multiple connections
* Separate facilities/devices where appropriate
* VPN backup

The architecture should survive failure of the connectivity component itself.

A dedicated connection is not the same as a redundant connection.

# Question 41: Direct Connect goes down. How can VPN provide backup?

## Interview Answer

If routing is designed correctly, a VPN path can advertise or provide access to the same required prefixes with different routing preference.

Normal:

```text
On-Prem
   |
   v
Direct Connect
   |
   v
AWS
```

Failure:

```text
Direct Connect
      X

On-Prem
   |
   v
VPN
   |
   v
AWS
```

But failover needs testing.

A backup path that has never been tested is an assumption.

# Question 42: Why is BGP important in hybrid AWS networking?

## Interview Answer

BGP can dynamically exchange routes between network systems.

It helps determine:

```text
Which prefixes are reachable
Which path is preferred
What happens when a path disappears
```

In Direct Connect and dynamic VPN designs, routing behavior can depend on BGP attributes and advertisements.

At mid-level, I do not need to act like a carrier network engineer, but I should understand that:

```text
Tunnel/connection up
```

does not necessarily mean:

```text
Correct routes are being advertised.
```

# Question 43: What are VPC Flow Logs?

## Interview Answer

VPC Flow Logs capture metadata about network flows at supported VPC network interfaces and scopes.

They can provide evidence such as:

```text
Source IP
Destination IP
Source port
Destination port
Protocol
Accept / reject
Traffic volume
```

They are very useful for answering:

```text
Did traffic reach this network interface?

Was it accepted or rejected?
```

But Flow Logs are not packet captures.

They do not contain full packet payloads.

# Question 44: Flow Logs show `REJECT`. What does that prove?

## Interview Answer

It tells me the recorded flow was rejected by the relevant filtering path represented by the Flow Log context.

I would then inspect security-group and NACL configuration as appropriate.

For example:

```text
Source:
10.20.1.15

Destination:
10.30.2.40

Port:
5432

Action:
REJECT
```

This is much stronger evidence than:

```text
"The database network might be blocked."
```

I now have the actual flow tuple.

# Question 45: Flow Logs show `ACCEPT`, but the application still times out. Does that prove networking is healthy?

## Interview Answer

No.

`ACCEPT` does not prove the application completed the connection successfully.

Potential issues still include:

* Application not listening
* Return path problem
* Route issue elsewhere
* NACL later in path
* Target overloaded
* TLS failure
* Application timeout

Flow Logs are one source of evidence, not a complete end-to-end proof.

# Question 46: What is Reachability Analyzer?

## Interview Answer

Reachability Analyzer analyzes network configuration to determine whether a network path is reachable between supported source and destination resources.

It can reason about things such as:

* Routes
* Security groups
* NACLs
* Gateways
* Other AWS networking components

Conceptually:

```text
Source ENI
   |
   v
Analyze AWS configuration
   |
   v
Destination
```

It is especially useful when the question is:

```text
Does the AWS configuration
permit this path?
```

# Question 47: Does Reachability Analyzer send real production traffic?

## Interview Answer

It is a configuration-analysis capability, not simply an application-level synthetic request.

So I still need runtime tests.

Reachability analysis may show the configured network path is possible while:

```text
Application process is down
```

or:

```text
TLS is broken
```

I combine configuration analysis with live evidence.

# Question 48: Reachability Analyzer says path is reachable, but application still fails. What next?

## Interview Answer

I move upward or outward from configuration.

I check:

```text
Application listener
Operating-system firewall
Load
TLS
Protocol
DNS
Application logs
Return behavior
```

The network configuration being valid is valuable evidence.

It lets me stop randomly changing AWS routing and security rules.

# Question 49: Why does cross-AZ traffic matter?

## Interview Answer

Cross-AZ traffic can affect:

* Latency
* Cost
* Failure dependencies
* Network design

For example:

```text
Application in AZ-A
      |
      v
NAT in AZ-B
```

creates a cross-AZ dependency for egress.

Or:

```text
App in AZ-A
      |
      v
Cache node in AZ-B
```

every request may cross zones.

Some cross-AZ traffic is intentional for resilience.

The important point is to know it exists and understand the trade-offs.

# Question 50: How would you detect unintended cross-AZ architecture?

## Interview Answer

I would map:

```text

Route target
Dependency placement
```

and correlate with traffic metrics and architecture.

Questions include:

```text

Where are interface endpoints?

Where are load-balancer targets?

```

# Question 51: What DNS services are important inside a VPC?

## Interview Answer

AWS VPC networking includes DNS resolution capabilities, commonly involving the Amazon-provided resolver and Route 53 Resolver features.

Applications may need to resolve:

* EC2 private hostnames
* Private hosted zones
* AWS service names
* On-premises domains
* Other VPC private zones

DNS becomes part of network architecture.

A route can be perfect while hostname resolution still sends the application to the wrong destination.

# Question 52: What is a Route 53 private hosted zone?

## Interview Answer

It allows private DNS records to be resolved from associated VPCs.

For example:

```text
database.internal.example
        |
        v
10.20.5.40
```

may exist only for private networks.

VPC association matters.

A VPC not associated with the private hosted zone may receive:

```text
NXDOMAIN
```

or a different public answer.

# Question 53: Application works in VPC A but cannot resolve the same private hostname in VPC B. Why?

## Interview Answer

I would investigate DNS scope.

Possible causes include:

* Private hosted zone associated only with VPC A
* Resolver rules not shared
* Wrong DHCP/DNS configuration
* Different DNS view
* Hybrid DNS forwarding problem

The network connection between the VPCs does not automatically mean they share all DNS resolution behavior.

Networking and name resolution are separate problems.

# Question 54: How do on-premises systems resolve private AWS names?

For AWS workloads resolving on-premises names:

```text

    |
    v

```

The exact design depends on DNS ownership and forwarding requirements.

Because an application may report:

Engineers may then spend time inspecting VPN routes.

I always separate:

```text

```

from:


# Question 57: VPC A and VPC B are connected through Transit Gateway. Ping fails. Is that enough to conclude routing is broken?

## Interview Answer

A failed ping may indicate:

* ICMP blocked
* Host does not respond
* Network issue

but it does not prove the application path is unavailable.

# Question 58: One application can reach another VPC by IP but not hostname. What layer is broken?

```text

VPC associations
Resolver rules
Resolver endpoints
DNS record
```

I would not modify TGW routing when the IP connection already proves cross-VPC transport works.

# Question 59: What is a network inspection VPC?

## Interview Answer

Some organizations centralize network inspection using dedicated VPCs and security appliances.

Conceptually:

```text

      |
      v

      |
      v
Inspection VPC
      |
      v

      |
      v

```

Traffic may need to traverse the same stateful inspection path in both directions.

Asymmetric routing can become a major issue.

# Question 60: Why is asymmetric routing dangerous with stateful firewalls?

## Interview Answer

Suppose:

```text
REQUEST:

VPC A
 |
 v
Firewall A
 |
 v
VPC B
```

but return traffic uses:

```text
VPC B
 |
 v
Firewall B
 |
 v
VPC A
```

Firewall B may not have seen the original connection.

Depending on the firewall architecture, it may drop the response.

The result:

```text
Request reaches destination
Destination responds
Client times out
```

This can be difficult to diagnose without examining both directions.

The private endpoint introduced a new path that was never permitted.

That explains the third symptom.

# Interviewer Follow-Up: Why not open every security group during the incident?

## Interview Answer

Because that creates uncontrolled security exposure and does not help isolate routing problems.

The failures include:

```text

NAT
Endpoint security
Asymmetric firewall path
```

Opening every security group fixes none of those with confidence.

I would change only the control I can prove is blocking the relevant flow.

# Interviewer Follow-Up: Why not route every VPC through the Transit Gateway using `0.0.0.0/0`?

## Interview Answer

Because broad routing reduces clarity and can accidentally centralize unrelated traffic.

I want explicit architectural intent.

For example:

```text

Inspection
Internet egress
Hybrid traffic
```

may need different paths.

A huge default transit route can hide dependencies and create unexpected blast radius.

# Interviewer Follow-Up: If Direct Connect exists, why keep VPN?

## Interview Answer

For resilience.

Direct Connect can be a preferred private path, while VPN can provide an independent backup path where requirements justify it.

But both the connection and the routing failover need to be tested.

A backup route that has never carried production traffic is not proven resilience.

Reachability Analyzer reasons about configured network paths.

I can combine:

```text
+
Observed traffic metadata
+
Live application testing
```

to build stronger evidence.
