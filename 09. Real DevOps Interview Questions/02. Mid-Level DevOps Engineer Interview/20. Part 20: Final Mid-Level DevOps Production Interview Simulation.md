There are no isolated questions such as:

```text
What is Kubernetes?

What is Terraform state?

What is an ALB?
```

The interviewer is testing one question:


# Scenario 1: Deployment Succeeds, but 15% of Requests Return 502

## Interviewer

A new version is deployed.

Kubernetes reports:

```text
deployment successfully rolled out
```

Five minutes later:

```text
HTTP 502:
0.2% -> 15%
```

What do you do?

## Strong Interview Answer

First, I would separate deployment success from application health.

Kubernetes saying the Deployment completed tells me the desired Pods became available according to Kubernetes.

It does not prove that every production request works.

I would first scope the 502s.

I want to know whether they correlate with:

```text
Version
Pod
Node
AZ
Endpoint
Request type
Target group
```

I would check ALB target health and compare it with Kubernetes endpoints.

Commands may include:

```bash
kubectl get pods -o wide
kubectl get endpoints
kubectl get endpointslices
kubectl describe deployment <deployment>
kubectl logs <pod>
```

I would also inspect ALB metrics and logs.

### Evidence I am looking for

If only Pods running the new version produce 502s, the deployment becomes a strong suspect.

If only one AZ produces failures, I investigate infrastructure or network differences.

If failures occur across both versions, the deployment may only be coincidental.

---

## Interviewer Challenge

The deployment shows 100% healthy Pods.

Does that rule out Kubernetes?

## Answer

No.

A Pod can satisfy its readiness probe while still failing real requests.

For example:

```text
/readiness
    |
    v
200 OK

Real request
    |
    v
Dependency call
    |
    v
Failure
```

I would compare the readiness probe with the actual request path.

# Scenario 2: Only Pods in One AZ Fail

You discover:

```text
AZ-A: 0.2% errors

AZ-B: 38% errors

AZ-C: 0.3% errors
```

## Interviewer

What changes now?

## Answer

The AZ correlation significantly narrows the investigation.

I would compare AZ-B against the healthy zones.

Check:

```text
Nodes
Subnets
Routes
NACLs
Security groups
NAT paths
CNI behavior
DNS
Pod placement
Dependencies
```

First:

```bash
kubectl get nodes -L topology.kubernetes.io/zone
kubectl get pods -o wide
```

I want to establish whether the failing Pods consistently map to nodes in AZ-B.

---

## Interviewer Challenge

Would you restart the Pods?

## Answer

Not as my first action.

If the failure follows the AZ rather than the Pod, restarting may simply recreate Pods inside the same failure domain.

A potentially safer mitigation is removing unhealthy capacity from traffic or preventing new workloads from scheduling there while investigating.

```text

      |

```

Another possibility is that the deployment changed connection-pool behavior.

## Answer

```text

Concurrency
CPU pressure
Lock contention
```

I need to understand why connections increased before deciding whether a higher limit is safe.

# Scenario 5: Terraform Wants to Replace a Production Resource

During the incident, another engineer runs:

```bash
terraform plan
```

Terraform reports:

```text
-/+ resource must be replaced
```

The resource is production-critical.

## Interviewer

What do you do?

## Answer

I do not apply it blindly.

First determine why Terraform wants replacement.

I inspect:

```text
Which attribute changed?
Was configuration changed?
Was infrastructure changed manually?
Is state incorrect?
Did provider behavior change?
```

Useful commands may include:

```bash
terraform plan
terraform state show <resource>
terraform providers
```

I compare Terraform's expected state with the actual AWS resource.

---

## Interviewer Challenge

The engineer says, "Terraform knows what it's doing."

## Answer

Terraform knows how to converge infrastructure toward configuration.

It does not know whether destroying and recreating a critical production resource during an incident is acceptable.

The engineer owns the production consequence.

```text
External dependency?
```

```bash

```

For Kubernetes:

```bash

```

where the image supports the required tooling.

I inspect:

```text
DNS records
TTL
Resolver differences
Caching
Route 53 configuration
CoreDNS
Split-horizon behavior
```

## Interviewer Challenge

Why does intermittent behavior matter?

## Answer

Because intermittent DNS problems often indicate multiple answers, caches, resolvers, or paths.

If:

```text
Resolver A -> correct

Resolver B -> incorrect
```

then repeated tests from one machine may miss the problem.

# Scenario 14: The Primary Engineer Wants to Restart Everything

## Interviewer

What do you say?

## Answer

I would ask what evidence suggests a broad restart will help.

Restarting everything can:

```text
Destroy evidence
Increase simultaneous load
```

A platform-wide restart without understanding the failure domain is dangerous.

This is no longer ordinary troubleshooting.

```text

        +--> Kubernetes
        |
        +--> AWS / Network
        |
        +--> Database
        |
        +--> Application
        |
        +--> Communications
```

# Step 2: Establish Customer Impact

Determine:

```text
Who is affected?
Which regions?
Which endpoints?
Which operations?
How severe?
```

Do not start with CPU.

Start with users.

---

# Step 3: Build the Timeline

```text
14:00 Deployment
14:04 502 increase
14:06 AZ-B correlation
14:08 RDS saturation
14:10 OOMKills

14:15 Dependency slowdown

```

```text

```

# Step 4: Find the Earliest Strong Signal

The earliest abnormal signal after deployment is:

```text

```

Then:

```text

```

That is more useful than beginning with the later queue backlog.

---

# Step 5: Contain the Failure Domain

If evidence strongly shows AZ-B is unhealthy, safely remove or reduce traffic to that failure domain.

Then verify that remaining capacity can survive the shift.

---

Consider:

```text

```

```text
Major customer impact

Cross-team dependency failure

Recovery action carries high risk
```

Escalation is not failure.

Delayed escalation can be.

# 30. Recovery Challenge

## Interviewer

Error rate returns to normal.

Are we done?

## Answer

Not necessarily.

I verify:

```text
Critical user journeys
Latency

Dependencies
Regional health
Synthetic tests
```

An error-rate graph can recover while a two-million-message queue continues creating hours of delayed customer impact.
