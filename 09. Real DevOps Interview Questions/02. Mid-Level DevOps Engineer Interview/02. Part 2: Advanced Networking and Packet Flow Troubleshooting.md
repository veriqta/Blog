# Mid-Level DevOps Engineer Interview

## Part 2: Advanced Networking and Packet Flow Troubleshooting

At mid-level, networking interviews should move beyond questions such as "What is DNS?" or "What does ping do?"

A mid-level DevOps engineer should be able to follow a packet.

When an application cannot connect to another service, you should be able to reason through:

```text
Application
    |
    v
Socket
    |
    v
Source IP + Ephemeral Port
    |
    v
Routing Decision
    |
    v
Firewall / Security Controls
    |
    v
NAT
    |
    v
Network
    |
    v
Destination Interface
    |
    v
Destination Port
    |
    v
Application
```

The interviewer is testing whether you can identify where communication breaks, what evidence would prove it, and how to investigate without randomly changing firewall rules.

This part focuses on packet-level production troubleshooting.

---

# Question 1: Walk me through what happens when a Linux server connects to `10.20.30.40:443`.

## Interview Answer

Assuming the address is already known and we are focusing on TCP/IP rather than DNS resolution, the application first asks the operating system to create a socket and connect to:

```text
Destination IP:   10.20.30.40
Destination Port: 443
```

The kernel selects an appropriate source IP and normally an ephemeral source port.

For example:

```text
Source:
10.10.1.25:49152

Destination:
10.20.30.40:443
```

The kernel performs a routing lookup to determine how the packet should leave the host.

I can inspect that decision with:

```bash
ip route get 10.20.30.40
```

I might see:

```text
10.20.30.40 via 10.10.1.1 dev eth0 src 10.10.1.25
```

That tells me:

* Destination
* Next hop
* Interface
* Source address

Then TCP establishes the connection.

```text
Client                           Server

SYN ---------------------------->

    <---------------------- SYN-ACK

ACK ---------------------------->

        CONNECTION ESTABLISHED
```

After that, application-layer communication can begin.

For HTTPS, TLS negotiation occurs after the TCP connection has been established.

That distinction matters.

A failure before TCP establishment is different from a TLS handshake failure, which is different again from an HTTP application error.

# Question 2: Explain the TCP three-way handshake and how you would troubleshoot it.

## Interview Answer

TCP normally establishes a connection using:

```text
Client                     Server

SYN
-------------------------->

                      SYN-ACK
<--------------------------

ACK
-------------------------->

ESTABLISHED
```

If the handshake fails, I want to determine which stage fails.

For example:

```text
Client                     Server

SYN
-------------------------->

SYN
-------------------------->

SYN
-------------------------->

X
```

If I observe SYN retransmissions with no SYN-ACK returning, possibilities include:

* Packet dropped before reaching server
* Firewall dropping traffic
* Incorrect route
* Security policy
* NAT issue
* Server unreachable
* Return-path problem
* SYN-ACK generated but dropped on return

I could capture traffic:

```bash
sudo tcpdump -ni any host 10.20.30.40 and port 443
```

If I control both ends, packet captures on both hosts are even more useful.

For example:

```text
CLIENT CAPTURE:
SYN -------->

SERVER CAPTURE:
SYN received
SYN-ACK sent

CLIENT CAPTURE:
No SYN-ACK received
```

Now I know the server received the request and responded.

The problem is likely somewhere in the return path.

That is much more precise than saying:

"The network is blocking it."

# Question 3: What is the difference between "Connection refused" and "Connection timed out"?

## Interview Answer

They usually suggest different failure modes.

### Connection refused

Suppose I run:

```bash
curl http://10.20.30.40:8080
```

and receive:

```text
Connection refused
```

This commonly means the destination was reachable, but nothing accepted the connection on that port, or a device actively rejected it.

At the TCP level, I may see:

```text
Client                    Server

SYN --------------------->

    <----------------- RST
```

Possible causes include:

* Application not running
* Application listening on another port
* Application bound to the wrong interface
* Explicit firewall rejection

I would inspect:

```bash
ss -lntp
```

on the destination.

### Connection timeout

A timeout more commonly means packets are disappearing somewhere.

For example:

```text
Client                    Server

SYN ---------------------> ?

SYN ---------------------> ?

SYN ---------------------> ?

TIMEOUT
```

Possible causes include:

* Firewall silently dropping packets
* Missing route
* Network ACL
* Broken NAT
* Return-path failure
* Unreachable network
* Remote host unavailable

The important interview distinction is:

```text
REFUSED
Someone responded negatively.

TIMEOUT
Expected response never arrived.
```

That is not absolute in every architecture, but it gives me a useful starting hypothesis.

# Question 4: A client sends SYN packets, but no SYN-ACK returns. How would you locate the failure?

## Interview Answer

I would trace the packet from source to destination.

First, verify the route:

```bash
ip route get <destination-ip>
```

Then inspect the source interface:

```bash
ip addr
ip route
```

Capture traffic:

```bash
sudo tcpdump -ni any host <destination-ip> and port <port>
```

If I control the destination, I would capture there too.

There are several possibilities.

### Scenario A

Source sees:

```text
SYN ->
SYN ->
SYN ->
```

Destination sees nothing.

The packet is being lost before reaching the destination.

### Scenario B

Destination sees:

```text
-> SYN
```

but sends nothing back.

I would investigate:

* Listening socket
* Host firewall
* Kernel behavior
* Service state

### Scenario C

Destination sees:

```text
-> SYN
<- SYN-ACK
```

but source never receives the SYN-ACK.

Now I have a return-path problem.

This could involve:

* Asymmetric routing
* Firewall
* NAT
* Security policy
* Network ACL
* Intermediate device

Packet capture at multiple points helps establish the exact failure boundary.

# Question 5: How would you troubleshoot intermittent packet loss?

## Interview Answer

Intermittent failures require repeated measurements rather than a single connectivity test.

I would establish:

* Source
* Destination
* Frequency
* Duration
* Whether loss affects all traffic
* Whether it affects one path or service
* Whether it correlates with load

I might begin with:

```bash
ping <destination>
```

where ICMP is meaningful and permitted.

Then:

```bash
mtr <destination>
```

`mtr` combines aspects of ping and traceroute and can help identify patterns across the path.

However, I would interpret intermediate-hop packet loss carefully.

Some routers deprioritize or rate-limit ICMP responses while still forwarding production traffic correctly.

So:

```text
Intermediate hop shows 40% loss
```

does not automatically mean:

```text
40% of application traffic is being dropped there.
```

I would correlate network observations with:

* TCP retransmissions
* Application errors
* Interface counters
* Load balancer metrics
* Packet captures
* Destination behavior

I might inspect interfaces:

```bash
ip -s link
```

and:

```bash
ethtool -S eth0
```

where applicable.

The goal is to prove whether packets are actually being lost and where.

# Question 6: `mtr` shows 70% packet loss on hop 5, but hop 6 and the destination show 0% loss. Is hop 5 broken?

## Interview Answer

Not necessarily.

If hop 5 were actually dropping 70% of transit traffic, downstream hops would normally also reflect the impact.

Instead, hop 5 may be rate-limiting or deprioritizing responses to diagnostic packets directed at itself.

Conceptually:

```text
Hop 4
  |
  v
Hop 5  -> rarely answers probes
  |
  v
Hop 6  -> answers normally
  |
  v
Destination -> answers normally
```

The forwarding path may be healthy.

This is why `traceroute` and `mtr` require interpretation.

I care more about loss that continues through subsequent hops and reaches the destination.

# Question 7: What is the difference between `traceroute` and `mtr` during an incident?

## Interview Answer

`traceroute` gives me a path-oriented snapshot.

For example:

```bash
traceroute example.com
```

It helps identify the sequence of hops toward a destination.

`mtr` continuously measures the path and provides statistics such as latency and apparent loss over time.

For intermittent problems, `mtr` can be particularly useful because a single traceroute may occur while the network is healthy.

For example:

```bash
mtr -rw <destination>
```

can produce a report over multiple probes.

But neither tool replaces packet capture.

I might use:

```text
traceroute
```

to understand the path,

```text
mtr
```

to identify patterns,

and:

```text
tcpdump
```

to see what packets actually reach an interface.

# Question 8: Two servers are in different subnets and cannot communicate. How would you troubleshoot routing?

## Interview Answer

I would inspect routing from both directions.

On server A:

```bash
ip route
```

Then:

```bash
ip route get <server-B-IP>
```

On server B:

```bash
ip route get <server-A-IP>
```

I need to understand both:

```text
Forward path

A
|
v
B
```

and:

```text
Return path

B
|
v
A
```

A valid forward route does not guarantee a valid return route.

I would also inspect:

* Subnet routes
* Network gateways
* Cloud route tables
* Firewalls
* Network ACLs
* NAT
* VPN routes
* Peering routes
* Transit routing

One common mistake is checking only whether server A knows how to reach server B.

TCP communication requires the response to return successfully as well.

# Question 9: What is asymmetric routing?

## Interview Answer

Asymmetric routing occurs when traffic follows different paths in each direction.

For example:

```text
REQUEST

Client
  |
  v
Firewall A
  |
  v
Server


RESPONSE

Server
  |
  v
Firewall B
  |
  v
Client
```

Asymmetric routing is not inherently invalid at the IP layer.

But it can cause problems when stateful network devices expect both directions of a connection to pass through the same device.

Suppose Firewall A sees:

```text
SYN
```

and records connection state.

But the return:

```text
SYN-ACK
```

goes through Firewall B.

Firewall B may have no state for that connection and may drop the response.

This can create confusing behavior where:

```text
Destination receives request
Destination responds
Client never receives response
```

I would compare routing decisions in both directions and inspect stateful devices along the path.

# Question 10: How would `tcpdump` help prove asymmetric routing?

## Interview Answer

If I can capture at relevant points, I can determine where each packet appears.

For example, on the server:

```bash
sudo tcpdump -ni any host <client-ip>
```

Suppose I see:

```text
Client -> Server SYN
Server -> Client SYN-ACK
```

The server is receiving and responding.

But the client sees:

```text
Client -> Server SYN
```

with no returning SYN-ACK.

That strongly suggests the response disappears after leaving the server.

I would then inspect:

* Server routing
* Multiple interfaces
* Policy routing
* Gateways
* NAT
* Firewalls
* Load balancers

The packet capture does not automatically tell me "asymmetric routing."

It provides evidence that allows me to narrow the path.

# Question 11: Explain MTU and why it causes strange production failures.

## Interview Answer

MTU defines the maximum packet size that can be transmitted over a network link without requiring fragmentation at that link layer.

A common Ethernet MTU is:

```text
1500 bytes
```

But paths may contain links with smaller MTUs.

Problems can appear when packets larger than the path supports cannot be delivered correctly.

This becomes especially interesting with tunnels and overlays because encapsulation adds headers.

For example:

```text
Original Packet
     |
     v
VPN / VXLAN / Tunnel Header Added
     |
     v
Packet exceeds underlying MTU
```

Symptoms can be confusing:

* Small requests work
* Large requests fail
* SSH connects but file transfers hang
* HTTP headers work but larger responses stall
* TLS handshake behaves strangely
* Certain application calls timeout

This is why MTU problems can masquerade as application problems.

---

# Question 12: How would you investigate a suspected MTU problem?

## Interview Answer

I would first look for the symptom pattern.

If small packets succeed but larger packets consistently fail, MTU becomes a reasonable hypothesis.

On Linux, I can inspect interface MTUs:

```bash
ip link
```

I might test packet sizes with ping where ICMP is permitted and the environment supports the relevant behavior.

For example:

```bash
ping -M do -s 1472 <destination>
```

For IPv4 over Ethernet with a 1500-byte MTU, 1472 bytes of ICMP payload plus IP and ICMP headers is a common test point.

Then reduce the payload until it succeeds.

I would also investigate:

* VPN overhead
* VXLAN
* GRE
* Cloud networking
* Container networking
* Load balancers
* Path MTU Discovery behavior
* ICMP filtering

Blocking the ICMP messages needed by Path MTU Discovery can create black-hole behavior.

# Question 13: What is an ephemeral port, and how can ephemeral port exhaustion cause an outage?

## Interview Answer

When a client initiates an outbound TCP connection, the operating system normally assigns a temporary source port from an ephemeral port range.

For example:

```text
Application server:

10.0.1.20:49152 -> 10.0.2.30:443
10.0.1.20:49153 -> 10.0.2.30:443
10.0.1.20:49154 -> 10.0.2.30:443
```

At high connection rates, available source-port combinations can become constrained.

I can inspect the configured range:

```bash
sysctl net.ipv4.ip_local_port_range
```

I would inspect socket usage:

```bash
ss -s
```

and:

```bash
ss -tan
```

I would look for large numbers of connections, especially in states such as `TIME-WAIT`.

But I would not immediately modify the ephemeral port range.

First I want to know why so many connections are being created.

Potential causes include:

* No connection reuse
* Disabled keep-alive
* Aggressive retries
* High request volume
* Poor connection pooling
* NAT concentration
* Downstream instability

The real fix may be application connection management rather than kernel tuning.

# Question 14: Why can NAT make ephemeral port exhaustion worse?

## Interview Answer

NAT may cause many internal clients to share a smaller set of external source addresses.

Imagine:

```text
App 1 \
App 2  \
App 3   \
App 4 ----> NAT IP ----> External API
App 5   /
App 6  /
```

Thousands of internal connections may be translated through one external IP.

The NAT device must maintain mappings that distinguish the flows.

Under sufficiently high connection volume, available translation resources can become constrained.

This can cause symptoms such as:

* Intermittent outbound connection failures
* Timeouts
* New connections failing while existing ones continue
* Problems appearing only during peak traffic

This is why I would not only inspect the application's host.

I would also inspect the NAT layer and connection metrics where available.

# Question 16: Explain stateful versus stateless filtering using a real troubleshooting scenario.

## Interview Answer

A stateful firewall tracks connection state.

If an outbound connection is permitted, return traffic associated with that established connection can generally be recognized as part of the same flow.

Conceptually:

```text
Client ---- SYN ----> Server

Firewall records state

Client <--- SYN-ACK -- Server

Firewall recognizes return traffic
```

A stateless filter evaluates packets independently according to configured rules.

This means I may need explicit rules that permit the required traffic in both directions, including return traffic.

This distinction becomes important when troubleshooting:

```text
Request leaves successfully
but response never returns
```

If a stateless control is involved, I would verify rules in both directions and consider ephemeral return ports.

---

# Question 17: Why do network ACLs sometimes create confusing TCP failures?

## Interview Answer

In environments where network ACLs are stateless, engineers may permit the destination service port but forget return traffic requirements.

For example:

```text
Client -> Server TCP 443
```

is allowed.

But the response is sent toward the client's ephemeral port.

Conceptually:

```text
Client:53024 ----------> Server:443
             SYN

Client:53024 <---------- Server:443
            SYN-ACK
```

A stateless filter must allow the relevant return traffic.

This is different from a stateful security control that tracks the established flow.

That is why understanding the full connection tuple matters:

```text
Protocol
Source IP
Source Port
Destination IP
Destination Port
```

# Question 18: What is a TCP retransmission?

## Interview Answer

TCP expects acknowledgments for transmitted data.

If expected acknowledgment behavior does not occur, TCP may retransmit data.

Retransmissions can indicate:

* Packet loss
* Congestion
* Network instability
* Receiver problems
* Path problems

But retransmissions are a symptom.

They do not automatically identify the cause.

I might use:

```bash
ss -ti
```

for detailed TCP information.

Packet captures can also reveal retransmission patterns.

For example:

```bash
sudo tcpdump -ni eth0 host <destination>
```

For deeper analysis, the capture could be inspected in a packet-analysis tool.

I would correlate retransmissions with application latency and network conditions.

# Question 19: Users report that an API is slow. CPU and memory look normal. How could TCP retransmissions explain it?

## Interview Answer

Application response time includes network behavior.

Suppose:

```text
Application generates response quickly
        |
        v
Packet lost
        |
        v
TCP waits
        |
        v
Retransmission
        |
        v
Response eventually delivered
```

The application itself may report fast processing time while the client experiences high latency.

This creates an important discrepancy:

```text
Server application latency: 40 ms

Client-observed latency: 2.5 seconds
```

That tells me to investigate what happens outside the application processing window.

I would examine:

* TCP retransmissions
* Packet loss
* Load balancer behavior
* Network path
* TLS
* Proxies

This is why end-to-end latency measurements matter.

# Question 20: What is connection tracking?

## Interview Answer

Connection tracking, commonly associated with Linux netfilter, maintains state information about network flows.

It can track connections such as:

```text
TCP
UDP
ICMP
```

For a TCP connection, the system can understand that packets belong to an existing flow.

This capability supports features such as:

* Stateful firewalling
* NAT
* Connection-state matching

I can inspect relevant connection-tracking limits and usage on systems where this subsystem is in use.

For example:

```bash
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
```

If connection tracking reaches capacity, new connections can fail.

This can create a production outage even when:

```text
CPU is fine
Memory appears fine
Application processes are running
Ports are listening
```

That makes it a useful mid-level troubleshooting scenario.

# Question 21: What would conntrack exhaustion look like in production?

## Interview Answer

Symptoms may include:

* New connections intermittently failing
* Existing connections continuing to work
* Packet drops
* NAT failures
* Firewall-related connectivity problems

I would inspect kernel logs:

```bash
journalctl -k
```

or:

```bash
dmesg -T
```

for conntrack-related messages.

Then inspect:

```bash
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
```

Suppose:

```text
nf_conntrack_count = 262100
nf_conntrack_max   = 262144
```

That is strong evidence that the table is near capacity.

But again, increasing the maximum is not automatically the root fix.

I would investigate why connection volume increased.

Possibilities include:

```text
Traffic spike
Retry storm
DDoS or abusive traffic
Connection leak
Very long timeouts
Poor connection reuse
Unexpected architecture change
```

# Question 22: How do you use `ss` during production network troubleshooting?

## Interview Answer

`ss` is one of the tools I use to understand socket state.

To show listening TCP sockets:

```bash
ss -lntp
```

To inspect TCP connections:

```bash
ss -tan
```

To summarize:

```bash
ss -s
```

To inspect a particular destination or port, I can filter the output.

I use `ss` to answer questions such as:

```text
Is the service listening?

What address is it bound to?

How many active connections exist?

Are connections accumulating?

Are there many sockets in CLOSE-WAIT?

Are there excessive TIME-WAIT sockets?

Which process owns the socket?
```

At mid-level, the command itself is not the skill.

Interpreting socket state is.

# Question 23: You find 30,000 connections in `TIME-WAIT`. Is that automatically a problem?

## Interview Answer

No.

`TIME-WAIT` is a normal part of TCP connection lifecycle.

Its existence protects against delayed packets from an old connection being confused with a newer connection using the same tuple.

A large number of `TIME-WAIT` sockets becomes interesting when it correlates with actual resource exhaustion or connection failures.

I would investigate:

* Connection rate
* Connection reuse
* Keep-alive configuration
* Ephemeral port availability
* NAT behavior
* Application architecture

I would avoid immediately applying random kernel tuning from the internet simply because `TIME-WAIT` looks large.

The question is:

```text
Is TIME-WAIT causing the incident,
or is it evidence of how the application
is creating connections?
```

# Question 24: You find thousands of connections in `CLOSE-WAIT`. What does that suggest?

## Interview Answer

`CLOSE-WAIT` generally means the remote side has initiated connection closure and the local TCP stack has acknowledged it, but the local application has not yet fully closed its side.

A continuously increasing number of `CLOSE-WAIT` sockets can therefore suggest an application connection-handling problem.

I would identify the owning process:

```bash
ss -tanp state close-wait
```

Then correlate with file descriptor usage:

```bash
ls /proc/<PID>/fd | wc -l
```

and:

```bash
lsof -p <PID>
```

The potential causal chain is:

```text
Application fails to close sockets
        |
        v
CLOSE-WAIT accumulates
        |
        v
File descriptors accumulate
        |
        v
Process reaches descriptor limit
        |
        v
New requests fail
```

This connects networking knowledge with Linux resource troubleshooting.

# Question 25: How would you safely use `tcpdump` on a busy production server?

## Interview Answer

I would avoid capturing everything without a filter.

This:

```bash
tcpdump -i any
```

on a high-traffic server could generate overwhelming output and create unnecessary overhead.

Instead, I would define exactly what I need.

For example:

```bash
sudo tcpdump -ni eth0 host 10.20.30.40
```

or:

```bash
sudo tcpdump -ni eth0 port 443
```

or more specifically:

```bash
sudo tcpdump -ni eth0 host 10.20.30.40 and port 443
```

If I need a capture file:

```bash
sudo tcpdump -ni eth0 host 10.20.30.40 and port 443 -w incident.pcap
```

I would also limit duration or packet count when appropriate.

For example:

```bash
sudo tcpdump -ni eth0 -c 1000 host 10.20.30.40
```

The principle is:

```text
Know the question
      |
      v
Create narrow filter
      |
      v
Capture minimum useful traffic
      |
      v
Analyze
```

# Question 26: What can packet capture tell you that application logs cannot?

## Interview Answer

Application logs tell me what the application believes happened.

Packet capture tells me what packets appeared at the observed network interface.

For example, an application may log:

```text
Connection to payment API timed out.
```

That does not tell me why.

A packet capture might show:

### Pattern A

```text
SYN
SYN
SYN
```

No response.

### Pattern B

```text
SYN
SYN-ACK
ACK
```

TCP succeeded.

### Pattern C

```text
SYN
RST
```

Connection rejected.

### Pattern D

```text
TCP connection established
Data sent
Repeated retransmissions
```

Each pattern sends my investigation in a different direction.

Packet capture helps separate application interpretation from network reality.

# Question 27: A service is listening on port 8080, but remote clients cannot connect. Local `curl` works. What would you check?

## Interview Answer

First I would determine what address the service is bound to.

```bash
ss -lntp | grep ':8080'
```

If I see:

```text
127.0.0.1:8080
```

then the application only listens on loopback.

Local requests can work:

```bash
curl http://127.0.0.1:8080
```

while remote requests cannot reach that listener directly.

If I see:

```text
0.0.0.0:8080
```

then I would continue investigating:

* Host firewall
* Route
* Cloud security rules
* Network ACL
* NAT
* Upstream firewall
* Client routing
* Packet arrival

I could run:

```bash
sudo tcpdump -ni any port 8080
```

while a remote client attempts the connection.

If no SYN reaches the server, the failure is upstream.

If SYN arrives but no expected response leaves, the investigation moves onto the server.

## Interview Answer

That is valuable evidence because the destination is not universally unavailable.

I would compare working and failing clients.

Specifically:

```text
Source subnet
Source IP
Route
NAT path
Firewall policy
DNS answer
MTU
Security group
Network ACL
Proxy
IPv4 versus IPv6
```

I would avoid focusing only on the server.

For example:

```text
Subnet A clients -> works
Subnet B clients -> fails
```

suggests I should compare the network paths and policies for those subnets.

Similarly:

```text
AZ-A -> works
AZ-B -> fails
```

points toward an AZ-specific path, route, appliance, or infrastructure issue.

Production troubleshooting becomes much faster when you compare what differs between success and failure.

It could still involve networking, but the evidence strongly moves DNS toward the top of the investigation.

```text
Name resolution
```

from:

```text
IP connectivity
```

If:

```bash
curl http://10.20.30.40:8080
```

works,

but:

```bash
curl http://api.internal:8080
```

fails,

I would inspect:

```bash
dig api.internal
```

```bash

```

I would check whether the hostname resolves to:

* Old IP
* Multiple addresses
* IPv6 address unexpectedly
* No address

This is another example of using evidence to narrow the failure domain.

# Question 30: What is a retry storm, and how can it make a networking incident worse?

## Interview Answer

Suppose an upstream service normally handles:

```text
10,000 requests/second
```

It becomes slow.

Clients begin retrying each failed request three times.

Now the struggling dependency may receive:

```text
Original traffic
+
Retry 1
+
Retry 2
+
Retry 3
```

Instead of helping recovery, retries increase load.

The sequence can become:

```text
Dependency slows
      |
      v
Requests timeout
      |
      v
Clients retry
      |
      v
Traffic increases
      |
      v
Dependency slows further
      |
      v
More timeouts
      |
      v
More retries
```

At the network level, I may observe:

* Increased connections
* NAT pressure
* Ephemeral port pressure
* Conntrack growth
* Higher packet rates

This is why retry behavior needs:

* Appropriate timeouts
* Backoff
* Jitter
* Retry limits

Retries are not automatically resilience.

Poorly designed retries can amplify outages.

# Question 32: How would you troubleshoot a network problem when ping works?

## Interview Answer

I would remember that ping primarily tests ICMP reachability.

It does not prove:

* TCP port is open
* Application is listening
* TLS works
* HTTP works
* Database accepts connections
* Load balancer is healthy

For example:

```text
ping server
```

may work while:

```bash
curl https://server
```

fails.

I would test the actual protocol and port.

For TCP:

```bash
nc -vz server 443
```

or use the real client where possible.

Then I would inspect:

```bash
ss -lntp
```

on the server and use packet capture if needed.

The rule is:

```text
Test the protocol that is actually failing.
```

# Question 33: What if ping fails but the application works?

## Interview Answer

That is completely possible.

ICMP may be blocked or deprioritized while TCP 443 remains permitted.

For example:

```text
ICMP
Client --------X--------> Server

HTTPS
Client -----------------> Server:443
```

Therefore:

```text
Ping failed
```

does not automatically mean:

```text
Host unreachable for all protocols.
```

I would test the service itself.

This is another reason network troubleshooting should not depend on one tool.

```text
DNS

 v

 |
 v

 |
 v

 |
```

# Question 35: Why is packet direction important when reading `tcpdump`?

## Interview Answer

Because I need to understand who sent what and whether the expected response returned.

Suppose I capture:

```text
10.0.1.20.53000 > 10.0.2.30.443: Flags [S]
10.0.2.30.443 > 10.0.1.20.53000: Flags [S.]
10.0.1.20.53000 > 10.0.2.30.443: Flags [.]
```

I can recognize:

```text
SYN
SYN-ACK
ACK
```

The TCP handshake succeeded.

If I instead see:

```text
10.0.1.20.53000 > 10.0.2.30.443: Flags [S]
10.0.1.20.53000 > 10.0.2.30.443: Flags [S]
10.0.1.20.53000 > 10.0.2.30.443: Flags [S]
```

then I am seeing retransmitted SYNs with no visible response.

Packet direction converts raw capture output into a network conversation.

# Question 36: What is your packet-level troubleshooting methodology?

## Interview Answer

I start with the failing application flow.

For example:

```text
Source Application
      |
      v
Source Socket
      |
      v
Source Host
      |
      v
Gateway
      |
      v
Firewall / NAT
      |
      v
Network
      |
      v
Destination Host
      |
      v
Listening Socket
      |
      v
Destination Application
```

Then I ask:

### 1. Does the source generate the packet?

Capture at source.

### 2. Does the packet leave through the expected interface?

Check:

```bash
ip route get <destination>
```

### 3. Does it arrive at the destination?

Capture there.

### 4. Does the destination respond?

Inspect packet capture and listening socket.

### 5. Does the response leave?

Capture destination egress.

### 6. Does the response return to the source?

Capture source.

### 7. Does TCP establish?

Inspect SYN, SYN-ACK, ACK.

### 8. Does the application-layer exchange succeed?

Move upward into TLS, HTTP, database protocol, or whatever application protocol is involved.

This approach turns:

```text
"The network doesn't work."
```

into:

```text
"The client SYN reaches the server,
the server sends SYN-ACK,
but the SYN-ACK never returns to
the client."
```

The second statement is actionable.

## Question 37: Users report intermittent API timeouts after a network architecture change. Walk through the investigation.

```text

   |
   v
```

The symptoms are:

```text
Payment API timeouts: increasing
Traffic: normal
```

A network architecture change was completed 30 minutes before the incident.

What do you do?

## Interview Answer

I would first establish whether the timeout affects:

```text
All payment requests

or

Only some requests
```

Suppose only approximately 50 percent fail.

That immediately makes me ask whether multiple paths or network devices exist.

---

## Step 1: Identify source distribution

Suppose there are four application servers.

I would determine whether failures correlate with a particular server.

Imagine:

```text
app-01 -> works
app-02 -> fails
app-03 -> works
app-04 -> fails
```

Now the incident has structure.

I would compare:

* Subnets
* Routes
* NAT path
* Firewall path
* Availability Zone
* Source IP

---

## Step 2: Check routes

On a failing server:

```bash
ip route get <payment-api-ip>
```

Then compare it with a working server.

Suppose:

```text
Working servers:
via Gateway A

Failing servers:
via Gateway B
```

That becomes a strong lead.

---

## Step 3: Capture the handshake

On a failing server:

```bash
sudo tcpdump -ni any host <payment-api-ip> and port 443
```

Suppose I see:

```text
SYN ->
SYN ->
SYN ->
```

No SYN-ACK.

On a working server:

```text
SYN ->
<- SYN-ACK
ACK ->
```

Now I know the problem occurs before TCP establishment on the failing path.

---

## Step 4: Inspect the new network path

Suppose the architecture change introduced a second NAT/firewall path.

```text
                    /-> NAT-A -> works
Application Servers
                    \-> NAT-B -> fails
```

I would inspect NAT-B and its routing.

---

## Step 5: Capture closer to the destination

Suppose packet analysis shows:

```text
Payment API receives SYN from NAT-B.

Payment API sends SYN-ACK.

SYN-ACK reaches Firewall B.

Firewall B drops it.
```

Now the problem is no longer:

```text
Payment API timeout
```

It is:

```text
Return traffic through the new path
is being dropped.
```

# Question 38: What could cause the firewall to drop the return traffic?

## Interview Answer

One possibility is asymmetric routing combined with stateful filtering.

For example:

```text
REQUEST

App
 |
 v
Firewall B
 |
 v
Payment API


RESPONSE

Payment API
 |
 v
Firewall A
 |
 v
App
```

If Firewall A did not observe the connection establishment, it may reject return traffic depending on the architecture and policy.

Another possibility is incorrect stateless filtering, NAT translation, or routing.

I would prove which case applies rather than assuming.

# Final Takeaway

Advanced network troubleshooting is not about knowing the largest number of commands.

It is about being able to follow the conversation between two systems.

When a connection fails, think:

```text
WHO SENT THE PACKET?

        |
        v

WHERE DID IT GO?

        |
        v

DID IT ARRIVE?

        |
        v

DID THE DESTINATION RESPOND?

        |
        v

WHERE DID THE RESPONSE GO?

        |
        v

DID TCP ESTABLISH?

        |
        v

WHAT HAPPENED ABOVE TCP?
```

Use `ss` to understand sockets.

Use `ip route` to understand routing decisions.

Use `traceroute` and `mtr` to investigate paths.

Use `tcpdump` to observe packets.

Use logs and metrics to correlate what happened over time.

But above all, follow the packet.

A mid-level DevOps engineer should be able to turn:

```text
"The network is broken."
```

into a precise statement about where the communication failed, what evidence proves it, what the safest mitigation is, and what should change so the same failure is easier to detect next time.
