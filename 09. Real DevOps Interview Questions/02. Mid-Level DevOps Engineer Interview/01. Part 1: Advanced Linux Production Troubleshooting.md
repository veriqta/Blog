# Mid-Level DevOps Engineer Interview

## Part 1: Advanced Linux Production Troubleshooting

A mid-level Linux interview should feel very different from a junior interview.

At this level, an interviewer is unlikely to be satisfied because you know `top`, `df`, `free`, or `ps`. They want to know whether you can investigate a degraded production server, interpret conflicting signals, form hypotheses from evidence, and recover the system without making the incident worse.

The questions below focus on realistic Linux production incidents.

---

# Question 1: A production server has a load average of 25, but CPU utilization is only 20%. How would you investigate?

## Interview Answer

I would not assume that a high load average means high CPU usage.

Linux load average includes tasks that are runnable and tasks stuck in uninterruptible sleep, commonly associated with I/O waits. So a server can have a high load average while the CPUs are relatively idle.

I would first establish the pattern:

```bash
uptime
```

Example:

```text
03:12:48 up 87 days, 4:21, 250 users,
load average: 25.42, 24.98, 19.67
```

Then I would check CPU states and process behavior:

```bash
top
```

I would pay particular attention to:

```text
us  user CPU
sy  system CPU
id  idle CPU
wa  I/O wait
st  steal time
```

Next:

```bash
vmstat 1
```

I would look at the `r` and `b` columns.

`r` represents runnable processes.

`b` represents processes blocked waiting for resources.

If `b` is consistently high while CPU remains relatively idle, I would investigate I/O or another blocking resource.

I would also check:

```bash
ps -eo state,pid,ppid,cmd | grep '^D'
```

Processes in `D` state are in uninterruptible sleep.

If many processes are stuck in `D`, I would investigate what they are waiting for.

Then:

```bash
iostat -xz 1
```

I would examine device latency, queueing, utilization, and throughput.

I might also use:

```bash
pidstat -d 1
```

to determine which processes are generating I/O.

If the problem involves network storage such as NFS, I would investigate that dependency rather than assuming the local disk is responsible.

The troubleshooting path is:

```text
High Load
    |
    v
CPU actually saturated?
   / \
 Yes  No
      |
      v
Blocked processes?
      |
      v
Disk / NFS / storage / kernel wait
      |
      v
Identify responsible workload
```

The key point is that load average represents demand for execution and certain blocked tasks, not simply CPU percentage.

# Question 2: `top` shows high `%wa`. What does that tell you?

## Interview Answer

High I/O wait suggests CPUs are spending significant time idle while outstanding I/O operations are being serviced.

I would not stop at saying:

"Disk is slow."

I need to determine which device, which workload, and why.

I would start with:

```bash
iostat -xz 1
```

Then correlate that with:

```bash
pidstat -d 1
```

and potentially:

```bash
iotop
```

if available and appropriate.

I would investigate:

* Read/write latency
* Queue depth
* Device utilization
* Throughput
* Which processes generate I/O
* Whether the workload recently changed
* Whether storage performance changed
* Whether swapping is contributing
* Whether network-attached storage is involved

For example, a database could suddenly begin performing large scans because an index was removed.

The Linux symptom is I/O pressure.

The root cause could actually be an application or database change.

# Question 3: The server has 64 GB of RAM, and `free -h` shows only 2 GB "free." Is the server almost out of memory?

## Interview Answer

Not necessarily.

Linux deliberately uses otherwise unused memory for caches.

I would run:

```bash
free -h
```

and pay more attention to the `available` value than the raw `free` value.

For example:

```text
               total    used    free   shared  buff/cache  available
Mem:            62Gi    40Gi   2.0Gi     1Gi        20Gi       18Gi
```

Only 2 GB may be completely unused, but approximately 18 GB may still be available for new workloads without significant swapping.

I would investigate actual memory pressure rather than treating low `free` memory as an incident by itself.

Useful evidence includes:

```bash
vmstat 1
```

particularly:

```text
si = swap in
so = swap out
```

I would also examine:

```bash
cat /proc/meminfo
```

and process consumption:

```bash
ps aux --sort=-%mem | head -20
```

The important distinction is:

```text
Low free memory
        !=
Memory exhaustion
```

# Question 4: A server has started swapping heavily. How would you investigate it?

## Interview Answer

First, I would determine whether swapping is actively occurring or whether swap simply contains pages from earlier activity.

I would use:

```bash
vmstat 1
```

The `si` and `so` columns show swap-in and swap-out activity.

If they are consistently active while application latency is increasing, I have stronger evidence of memory pressure.

I would then inspect:

```bash
free -h
```

and:

```bash
ps aux --sort=-%mem | head -20
```

For more detailed process information:

```bash
cat /proc/<PID>/status
```

I would investigate:

* Recent deployment
* Memory leak
* Increased workload
* Unexpected process
* Too many worker processes
* Container memory behavior
* Cache growth
* Database memory configuration
* JVM heap configuration
* Memory limits

I would not immediately run:

```bash
swapoff -a
```

on a production machine under severe memory pressure.

That can force swapped pages back into RAM and potentially make the situation significantly worse.

# Question 5: Explain how you would investigate an OOMKilled process.

## Interview Answer

First, I would distinguish between a system-level OOM event and a workload constrained by something like a cgroup or container memory limit.

For system evidence, I would check:

```bash
journalctl -k
```

or:

```bash
dmesg -T
```

I could search for relevant messages:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

I might see something resembling:

```text
Out of memory: Killed process 18432 (java)
```

I would establish:

* Which process was killed?
* How much memory was it consuming?
* Was the entire machine under memory pressure?
* Did memory consumption grow gradually?
* Did workload increase?
* Was this inside a container?
* Did a memory limit change?
* Did multiple processes compete for memory?

Then I would correlate with historical metrics.

This is important because after the OOM killer terminates a process, current memory usage may look completely normal.

The evidence I need may exist in:

```text
Kernel logs
Historical monitoring
Application metrics
Container metrics
Deployment history
```

A common interview mistake is investigating only the server's current state.

Production troubleshooting often requires reconstructing what happened before the failure.

# Question 6: An application slowly consumes more memory every day until it crashes. How would you prove it is a memory leak?

## Interview Answer

I would first avoid declaring a memory leak solely because memory usage increased.

Some applications legitimately grow caches or maintain larger working sets as workload increases.

I would establish a time series.

For example:

```text
Monday      4 GB
Tuesday     7 GB
Wednesday  11 GB
Thursday   16 GB
Friday     23 GB
```

Then I would correlate memory growth with:

* Request volume
* Number of connections
* Cache size
* Worker count
* Queue depth
* Application releases
* Runtime behavior

At the OS level I could monitor:

```bash
ps -o pid,rss,vsz,%mem,cmd -p <PID>
```

and inspect:

```bash
cat /proc/<PID>/status
```

I might also use:

```bash
pmap -x <PID>
```

depending on the application and environment.

If memory continually increases under a relatively stable workload and is not released over expected lifecycle boundaries, I would escalate the investigation to application-specific profiling.

For example, JVM, Go, Python, Node.js, and native applications require different memory-analysis techniques.

Linux can tell me that memory is growing.

It may not tell me which object in the application is leaking.

That distinction matters.

# Question 7: What is the difference between a zombie process and an orphan process?

## Interview Answer

A zombie is a process that has finished execution but still has an entry in the process table because its parent has not yet collected its exit status.

I could find zombie processes with:

```bash
ps -eo pid,ppid,state,cmd | awk '$3=="Z"'
```

A zombie does not continue executing application code.

Its primary concern is the retained process-table entry.

A large number of zombies can indicate a poorly behaving parent process.

An orphan is different.

An orphan is a running process whose parent has exited. The operating system reparents it, typically to an appropriate subreaper or PID 1 depending on the environment.

So:

```text
Zombie
Process finished
Parent has not reaped it

Orphan
Process still running
Original parent exited
```

I would investigate why large numbers of either are being created rather than simply trying to remove them individually.

# Question 8: Production has thousands of zombie processes. What would you do?

## Interview Answer

I would identify their parent processes.

```bash
ps -eo pid,ppid,state,cmd | awk '$3=="Z"'
```

Then group or inspect PPIDs.

The zombies themselves cannot simply be killed because they have already terminated.

The real issue is that their parent has not called the appropriate wait operation to reap them.

I would identify the responsible parent:

```bash
ps -fp <PPID>
```

Then determine:

* What service owns it?
* Is this a known application bug?
* Is the parent still functioning?
* Can it be safely signaled or gracefully restarted?
* Is the process count approaching a system limit?

If production impact is low, I would avoid restarting the entire server merely to clear zombies.

The remediation should target the faulty process lifecycle.

# Question 9: An application starts returning "Too many open files." What happened?

## Interview Answer

The process likely reached a file descriptor limit.

On Linux, file descriptors are used for more than regular files.

They can represent:

* Files
* TCP sockets
* Unix sockets
* Pipes
* Devices
* Other kernel objects

So a web server experiencing:

```text
Too many open files
```

may actually have exhausted descriptors because of network connections.

I would identify the process and check:

```bash
ls /proc/<PID>/fd | wc -l
```

Then:

```bash
cat /proc/<PID>/limits
```

I could inspect what the descriptors represent:

```bash
lsof -p <PID>
```

I would also check system-level usage and limits where relevant:

```bash
cat /proc/sys/fs/file-nr
cat /proc/sys/fs/file-max
```

The investigation is not complete when I discover the limit.

I need to determine why descriptor usage is high.

Possibilities include:

* Legitimate increase in traffic
* Connection leak
* File handle leak
* Incorrect connection timeout
* Application bug
* Too-low configured limit

Simply increasing the limit may delay the next failure without fixing the leak.

# Question 10: How would you distinguish file descriptor exhaustion from a connection leak?

## Interview Answer

I would inspect the descriptors.

```bash
lsof -p <PID>
```

and socket state:

```bash
ss -tanp
```

Suppose most descriptors correspond to TCP connections.

I would examine states such as:

```text
ESTABLISHED
CLOSE-WAIT
TIME-WAIT
SYN-SENT
```

A very large number of connections in `CLOSE-WAIT`, for example, can suggest the remote side closed connections but the local application is not closing its sockets correctly.

I would correlate:

```text
File descriptor growth
        +
Socket-state growth
        +
Application behavior
```

If descriptor count rises continuously with a particular socket state and does not recover, that provides useful evidence of a connection lifecycle problem.

# Question 11: When would you use `lsof` during a production incident?

## Interview Answer

`lsof` helps answer:

"What resources does this process currently have open?"

Examples include:

```bash
lsof -p <PID>
```

to inspect a process.

```bash
lsof -i :8080
```

to determine what is using a port.

```bash
lsof /var/log/application.log
```

to determine which process has a file open.

One particularly useful production case involves deleted files.

Suppose:

```bash
df -h
```

reports a filesystem is full, but:

```bash
du -sh /var/log/*
```

does not explain the usage.

I would check:

```bash
lsof +L1
```

A process may still have a deleted file open.

Deleting the directory entry does not necessarily release the blocks until the final open file descriptor is closed.

This can explain:

```text
df says disk full
du cannot find the data
```

That is a classic production troubleshooting scenario.

# Question 12: How would you use `strace` to troubleshoot a production process?

## Interview Answer

`strace` lets me observe system calls made by a process.

For example:

```bash
strace -p <PID>
```

But on a busy production process, I would use it carefully because tracing can add overhead and produce enormous output.

I would narrow the scope where possible.

For example:

```bash
strace -p <PID> -e trace=file
```

could help investigate file-related operations.

Or:

```bash
strace -p <PID> -e trace=network
```

could help inspect network-related system calls.

Suppose an application appears frozen.

`strace` might reveal repeated attempts to connect to an unavailable dependency.

Or it may reveal:

```text
openat(...) = -1 EACCES
```

which points toward a permissions problem.

Another process might repeatedly return:

```text
ENOENT
```

because a required file does not exist.

I would use `strace` to answer a specific question, not simply attach it to every production process.

# Question 13: An application is hanging, but its logs contain nothing useful. How would you investigate?

## Interview Answer

I would inspect the process from the outside.

First:

```bash
ps -fp <PID>
```

Then:

```bash
top -p <PID>
```

I would check what files and sockets it has open:

```bash
lsof -p <PID>
```

Then network connections:

```bash
ss -tanp
```

If appropriate:

```bash
strace -p <PID>
```

Suppose `strace` shows repeated:

```text
connect(...)
```

calls toward a database address.

I would investigate database connectivity.

If it shows repeated reads from a file or blocked I/O, I would follow that evidence instead.

This is a good example of why Linux troubleshooting cannot depend entirely on application logs.

# Question 14: Explain how `vmstat` helps during a production incident.

## Interview Answer

`vmstat` gives a compact view across several system dimensions.

For example:

```bash
vmstat 1
```

I can observe:

```text
r   runnable processes
b   blocked processes

si  swap in
so  swap out

bi  blocks received
bo  blocks sent

us  user CPU
sy  system CPU
id  idle
wa  I/O wait
st  steal
```

That means one command can help me distinguish between:

```text
CPU pressure
Memory pressure
Swap activity
I/O blocking
Virtualization contention
```

The value is not memorizing each column.

The value is correlating them.

For example:

```text
High load
+
High b
+
High wa
```

suggests a very different investigation from:

```text
High load
+
High r
+
High us
```

# Question 15: When would you use `sar` instead of `top`?

## Interview Answer

`top` is primarily useful for observing the current system.

`sar`, when historical collection is configured, can help answer:

"What was happening at 2:17 a.m. when the incident occurred?"

That is extremely valuable in production.

For example:

```bash
sar -u
```

for CPU history.

```bash
sar -r
```

for memory statistics.

```bash
sar -q
```

for load and queue information.

```bash
sar -n DEV
```

for network interface statistics.

The production incident may already be over when I log in.

Current CPU usage of 5 percent does not tell me what happened during the outage.

Historical telemetry does.

# Question 16: A server becomes slow every day at approximately 02:00. How would you investigate?

## Interview Answer

The consistent timing immediately makes scheduled activity a strong hypothesis.

I would inspect:

* Cron jobs
* systemd timers
* Backup schedules
* Log rotation
* Database maintenance
* Security scans
* Batch processing
* Snapshot jobs
* Scheduled application workloads

I could inspect:

```bash
systemctl list-timers
```

and relevant cron configuration.

Then I would correlate historical resource data around 02:00.

For example:

```bash
sar -u
sar -r
sar -q
sar -n DEV
```

I would check storage metrics and application monitoring for the same window.

Suppose I discover:

```text
01:59 backup begins
02:00 disk latency increases
02:01 application latency increases
02:03 database timeouts begin
03:10 backup completes
03:11 application recovers
```

That correlation is far stronger than saying:

"The server is slow because the disk is busy."

I now have a timeline and a plausible causal chain.

# Question 17: `df -h` reports 100% disk usage. What do you do in production?

## Interview Answer

First, I determine which filesystem is full.

```bash
df -h
```

Then I investigate usage without blindly deleting files.

For example:

```bash
du -xhd1 /var
```

and progressively narrow down.

I would check common sources:

```text
Application logs
System logs
Container data
Temporary files
Database files
Core dumps
Package caches
Backups
```

I would also check:

```bash
lsof +L1
```

for deleted files that remain open.

I would investigate whether log rotation failed.

If I need immediate space to restore service, I would remove or truncate only data that I have confirmed is safe to modify.

Then I would fix the underlying cause.

A production engineer should not respond to a full filesystem with:

```bash
rm -rf /var/log/*
```

without understanding what is being removed.

# Question 18: The filesystem has 40% free space, but applications receive `No space left on device`. What do you investigate?

## Interview Answer

One of my first checks would be inode usage:

```bash
df -i
```

A filesystem can have available blocks but no available inodes.

This often happens when an application creates enormous numbers of tiny files.

For example:

```text
Disk capacity:
60% used

Inodes:
100% used
```

The application cannot create another file.

I would locate directories with excessive file counts and determine what generated them.

Potential sources include:

* Session files
* Cache files
* Temporary files
* Mail queues
* Container layers
* Application-generated artifacts

Then I would fix both the immediate exhaustion and the lifecycle problem that allowed unbounded file creation.

# Question 19: What is `ulimit`, and why can it cause production failures?

## Interview Answer

`ulimit` relates to per-process resource limits exposed by the shell.

Examples can include:

* Open files
* Number of processes
* Stack size
* Core dump size
* Locked memory

I might inspect:

```bash
ulimit -a
```

But there is an important production detail.

The limits in my interactive shell may not be the same limits applied to a systemd service.

For a running process, I would inspect:

```bash
cat /proc/<PID>/limits
```

For systemd services, I would inspect the unit configuration and relevant limit directives.

For example:

```ini
LimitNOFILE=65535
```

If an application receives:

```text
Too many open files
```

I need to inspect the actual running process limit, not assume my shell's `ulimit` represents the service.

# Question 20: A service works when started manually but fails under systemd. How would you investigate at mid-level?

## Interview Answer

I would compare the execution environments.

First:

```bash
systemctl status myapp
```

Then:

```bash
journalctl -u myapp
```

And:

```bash
systemctl cat myapp
```

I would inspect:

```text
User
Group
WorkingDirectory
Environment
EnvironmentFile
ExecStart
Dependencies
Resource limits
Permissions
```

The interactive shell may contain:

```text
PATH
HOME
Credentials
Environment variables
Shell initialization
```

that the systemd unit does not have.

I would also verify that the application is not relying on relative paths or shell-specific behavior.

The question is not merely:

"Why did systemd fail?"

It is:

"What is different between the successful execution context and the failing execution context?"

# Question 21: A systemd service fails because another service is unavailable during boot. How would you troubleshoot it?

## Interview Answer

I would inspect the unit:

```bash
systemctl cat myapp.service
```

Then examine dependencies:

```bash
systemctl list-dependencies myapp.service
```

I would check the boot logs:

```bash
journalctl -b
```

and service-specific logs:

```bash
journalctl -u myapp.service -b
```

I would determine whether the unit correctly expresses its ordering and dependency requirements.

For example:

```ini
[Unit]
Requires=network-online.target
After=network-online.target
```

But I would not blindly add dependencies until I understand what the application actually requires.

A common mistake is confusing:

```text
Ordering
```

with:

```text
Dependency
```

`After=` controls ordering.

It does not by itself mean the other unit must successfully exist or remain active.

Understanding that distinction is important when debugging systemd startup behavior.

# Question 22: A filesystem that should mount during boot is missing. How would you investigate?

## Interview Answer

I would first determine whether the mount is configured in:

```bash
cat /etc/fstab
```

Then:

```bash
findmnt
```

and:

```bash
mount
```

I could test the configuration carefully with:

```bash
mount -a
```

while watching for errors.

I would also inspect:

```bash
journalctl -b
```

and kernel messages.

Potential causes include:

* Incorrect UUID
* Missing block device
* Filesystem corruption
* Incorrect filesystem type
* Invalid mount options
* Permission problems
* Network filesystem unavailable
* Dependency ordering
* Storage device failure

For UUID-related problems:

```bash
blkid
```

can help compare actual devices with `/etc/fstab`.

For network mounts, I would also verify that networking and the remote storage endpoint are actually available.

# Question 23: An NFS mount becomes unresponsive and several application processes enter `D` state. Why can this be dangerous?

## Interview Answer

`D` usually indicates uninterruptible sleep, commonly while a process is waiting on I/O.

If an application performs filesystem operations against an unresponsive NFS mount, those operations can become blocked.

The result can spread.

For example:

```text
NFS unavailable
      |
      v
Filesystem calls block
      |
      v
Application workers block
      |
      v
Request queue increases
      |
      v
Application latency rises
      |
      v
Load average rises
```

CPU may still look relatively normal.

I would investigate:

* NFS server health
* Network connectivity
* Mount options
* Kernel logs
* Number of blocked processes
* Application dependency on the mount

This is another reason high load with low CPU can be misleading.

This is where historical observability becomes critical.

* CPU
* Memory
* Swap
* Load
* Disk latency
* Network throughput
* Network errors
* Process count
* File descriptors
* Application latency
* Error rate

Tools may include:

```text
sar
Monitoring platform
Application metrics
Centralized logs
Cloud metrics
```

I would establish the exact timestamps of reported degradation.

Then compare them against:

```text
Deployments
Cron jobs
Backups
Traffic spikes
Auto Scaling activity
Database maintenance
Storage snapshots
External dependency failures
```

Intermittent incidents require a timeline.

Without one, engineers often inspect a healthy system after the problem disappears and incorrectly conclude there is no infrastructure issue.

# Question 25: How would you investigate a suspected CPU resource leak?

## Interview Answer

I would first establish whether CPU consumption grows progressively.

I would identify processes:

```bash
ps -eo pid,ppid,%cpu,%mem,etime,cmd --sort=-%cpu | head
```

Then observe the process over time.

I could use:

```bash
pidstat -p <PID> 1
```

I would determine whether:

* One thread is consuming CPU
* All threads are busy
* CPU increases with traffic
* CPU remains high after traffic falls
* A background task is looping
* Error handling is causing retries
* The process is repeatedly failing system calls

Depending on the application, I might inspect threads:

```bash
top -H -p <PID>
```

If appropriate, I could use application-specific profilers.

Again, Linux identifies the resource symptom.

Application profiling often identifies the code-level cause.

# Question 26: `top` reports high `%st` steal time on a virtual machine. What does that mean?

## Interview Answer

Steal time represents time when the virtual CPU was ready to execute but the hypervisor was servicing other workloads instead.

If `%st` becomes significantly elevated and correlates with application degradation, I would investigate the virtualization or cloud layer.

The server itself might not have a runaway process.

This demonstrates why CPU troubleshooting requires understanding:

```text
User CPU
System CPU
I/O wait
Idle
Steal
```

rather than only looking at the headline CPU percentage.

# Question 27: Network connections keep increasing until the application fails. How would you investigate?

## Interview Answer

I would inspect connection counts and states.

```bash
ss -s
```

Then:

```bash
ss -tan
```

I could summarize states:

```bash
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
```

I would look for abnormal growth in states such as:

```text
ESTAB
CLOSE-WAIT
TIME-WAIT
SYN-SENT
```

Then I would identify owning processes:

```bash
ss -tanp
```

I would correlate connection growth with:

* File descriptor usage
* Traffic
* Dependency latency
* Application release
* Timeout settings
* Connection pool configuration

Suppose `CLOSE-WAIT` increases indefinitely.

That points me toward an application that is not closing sockets after the remote endpoint closes them.

Increasing `ulimit` might temporarily postpone failure.

It does not fix the underlying connection leak.

# Question 28: A service suddenly cannot bind to port 8080 after deployment. How would you troubleshoot it?

## Interview Answer

I would check whether another process already owns the port:

```bash
ss -lntp | grep ':8080'
```

or:

```bash
lsof -i :8080
```

If another process owns it, I would identify why.

Possible scenarios include:

* Old application process did not terminate
* Two versions started simultaneously
* Deployment script failed
* Duplicate service definition
* Unexpected application occupies the port

I would not kill the process simply because it owns port 8080.

First I would identify what it is and whether terminating it is safe.

# Question 29: Kernel logs show repeated I/O errors for a block device. What would you do?

## Interview Answer

I would treat repeated block-device I/O errors as potentially serious.

I would inspect:

```bash
journalctl -k
```

and:

```bash
dmesg -T
```

Then determine:

* Which device is affected?
* What filesystem uses it?
* Is the application actively using it?
* Is this physical hardware, virtual storage, or cloud block storage?
* Are errors increasing?
* Is the filesystem becoming read-only?
* Is redundancy available?
* Are backups healthy?

I would prioritize data safety.

Depending on the infrastructure, the correct response may involve failing over, detaching a problematic device safely, replacing storage, restoring from a replica, or escalating to the infrastructure provider.

Repeated I/O errors are not something I would "fix" by repeatedly restarting the application.

# Question 30: A filesystem suddenly becomes read-only. What could cause this?

## Interview Answer

One possibility is that the kernel detected filesystem or underlying storage problems and remounted the filesystem read-only to protect against further damage.

I would inspect:

```bash
dmesg -T
```

and:

```bash
journalctl -k
```

I would look for:

```text
Filesystem errors
I/O errors
Journal errors
Device failures
```

I would not immediately run:

```bash
mount -o remount,rw ...
```

without understanding why it became read-only.

If the underlying problem remains, forcing it writable could increase the risk of corruption.

The priority is understanding the storage condition and protecting data.

# Question 31: An engineer wants to restart a production server because "that usually fixes it." What would you do?

## Interview Answer

I would first determine whether restarting is necessary for immediate recovery.

If the outage is severe and restart is the safest known mitigation, it may be justified.

But if the server is still accessible and we have time to investigate, restarting immediately destroys valuable evidence.

For example, we could lose:

```text
Process state
Open connections
Memory state
Current resource contention
Temporary files
Kernel symptoms
Exact failure conditions
```

Before restart, where safe, I would capture:

```bash
uptime
free -h
df -h
df -i
ps aux
ss -s
vmstat
```

along with relevant logs and metrics.

The principle is:

```text
Do not restart because you have
run out of troubleshooting ideas.
```

Restart should be a deliberate mitigation.

# Question 32: How would you troubleshoot a production Linux server without restarting it?

## Interview Answer

I would work from observation toward increasingly invasive actions.

### Stage 1: Establish impact

What is failing?

```text
Entire host?
One application?
One endpoint?
One filesystem?
One dependency?
```

### Stage 2: Check overall system health

I would inspect:

```text
Load
CPU
Memory
Swap
Disk capacity
Inodes
I/O
Network
Processes
```

### Stage 3: Identify the affected process

I would inspect:

```text
PID
CPU
Memory
Threads
File descriptors
Sockets
Logs
System calls
```

### Stage 4: Check dependencies

```text
Database
DNS
Network
Storage
External APIs
Authentication
```

### Stage 5: Check recent changes

```text
Deployment
Configuration
Kernel/package update
Scheduled job
Traffic change
Infrastructure change
```

### Stage 6: Mitigate narrowly

Instead of rebooting an entire server, I might:

* Stop one problematic worker
* Reload configuration
* Restart one application process
* Redirect traffic
* Remove a safe temporary file
* Fix a mount
* Roll back a deployment
* Disable a problematic scheduled job

The goal is to minimize blast radius while preserving evidence.

# Question 33: What is your general approach when multiple Linux metrics look abnormal at the same time?

## Interview Answer

I try to identify which metric is the cause and which metrics are consequences.

Suppose I see:

```text
Load average: HIGH
I/O wait: HIGH
Application latency: HIGH
CPU usage: LOW
Blocked processes: HIGH
```

I would not create five separate incidents.

A plausible relationship is:

```text
Storage latency
      |
      v
Processes block on I/O
      |
      v
Load increases
      |
      v
Application latency increases
```

Similarly:

```text
Memory leak
    |
    v
Memory pressure
    |
    v
Swap activity
    |
    v
Disk I/O
    |
    v
Application latency
```

The job is to build a causal chain from correlated evidence.

# Question 34: How do you decide whether the problem belongs to Linux, the application, or an external dependency?

## Interview Answer

I trace the failure boundary.

Suppose an API is slow.

I would ask:

```text
Is CPU saturated?
No.

Memory pressure?
No.

Disk latency?
No.

Network errors?
No.

Application threads blocked?
Yes.

What are they waiting for?
Database connections.
```

Now the investigation moves toward the database path.

Another example:

```text
Application errors
       |
       v
Connection timeout
       |
       v
Network route healthy
       |
       v
Destination port unreachable
```

That moves the investigation toward the remote service.

DevOps troubleshooting is not about proving that "Linux is healthy."

It is about finding where the request stops behaving correctly.

# Question 35: A Linux server has been running normally for six months and suddenly starts degrading. What questions would you ask before touching anything?

## Interview Answer

My first questions would be:

1. When exactly did degradation begin?
2. What changed immediately before it?
3. Is the degradation constant or intermittent?
4. Is one service affected or the whole server?
5. Did traffic change?
6. Was there a deployment?
7. Was configuration changed?
8. Did a scheduled job run?
9. Did storage behavior change?
10. Did an external dependency change?
11. Is the issue isolated to one server?
12. Do historical metrics show gradual degradation?

The fact that a system was stable for months is useful evidence.

Something may have changed in:

```text
Code
Configuration
Traffic
Data volume
Dependencies
Infrastructure
Certificates
Resource consumption
```

Or a slow leak may finally have crossed a threshold.

# Final Production Scenario

## Question 36: A revenue-critical API becomes extremely slow. CPU is 18%, memory is 70%, and disk capacity is 45%. Load average is 32. Walk through the investigation.

## Interview Answer

I would avoid assuming the server is healthy because CPU, memory, and disk capacity appear acceptable.

The load average of 32 requires explanation.

### Step 1: Establish host context

I would determine the number of CPUs and current load:

```bash
uptime
nproc
```

Load needs context.

A load of 32 means something very different on a 2-vCPU machine versus a 64-vCPU machine.

### Step 2: Examine scheduler and blocking behavior

```bash
vmstat 1
```

Suppose I see:

```text
r = 2
b = 35
wa = 61%
```

Now I have a major clue.

Only a small number of tasks are runnable, while many are blocked and I/O wait is high.

### Step 3: Investigate storage

```bash
iostat -xz 1
```

Suppose one device shows dramatically increased latency.

I would determine which workloads use that device.

### Step 4: Identify processes

```bash
pidstat -d 1
```

Suppose the database process generates the majority of I/O.

I would not immediately conclude the disk itself is defective.

I would investigate why the database I/O changed.

### Step 5: Correlate with recent activity

Suppose the timeline shows:

```text
14:00 deployment completed
14:04 database read IOPS increased
14:05 disk latency increased
14:06 API latency increased
14:07 load average increased
```

Now the deployment becomes a strong hypothesis.

### Step 6: Investigate application/database behavior

Suppose the new application release introduced a query that no longer uses an index.

The causal chain becomes:

```text
Application release
       |
       v
Expensive DB query
       |
       v
Large disk reads
       |
       v
Storage latency
       |
       v
Processes blocked
       |
       v
High Linux load
       |
       v
API latency
```

The Linux server was showing the consequence of a database workload problem.

### Step 7: Mitigate

Depending on severity and evidence, I might roll back the application release or otherwise remove the problematic workload.

I would then monitor:

```text
Database query behavior
Disk latency
I/O wait
Blocked processes
Load average
API latency
Error rate
```

### Step 8: Verify

Recovery should be demonstrated through metrics.

For example:

```text
I/O wait       61% -> 3%
Blocked tasks   35 -> 0
Load average    32 -> 4
API p95        8s  -> 180ms
```

Only then would I consider the immediate mitigation successful.

# Interviewer Follow-Up: Why didn't you restart the server?

## Interview Answer

Because the evidence did not indicate that a reboot addressed the underlying problem.

Restarting might temporarily interrupt the workload and make the system appear better, but when the expensive queries resumed, the degradation would likely return.

Worse, rebooting could remove evidence that helped identify the causal chain.

I prefer:

```text
Observe
   |
   v
Correlate
   |
   v
Identify failure boundary
   |
   v
Mitigate narrowly
   |
   v
Verify
```

rather than:

```text
Problem
   |
   v
Restart
   |
   v
Hope
```

# Interviewer Follow-Up: What if production is completely unavailable and investigation is taking too long?

## Interview Answer

Then restoration takes priority.

Production incident response and root-cause analysis are related but different activities.

If I have a safe, fast mitigation such as:

* Rollback
* Failover
* Traffic diversion
* Removing a failing instance from rotation
* Restarting a specific service

I may use it before proving the complete root cause.

I would capture as much useful evidence as practical without delaying critical recovery.

The priority becomes:

```text
Customer impact
      |
      v
Safe mitigation
      |
      v
Verify recovery
      |
      v
Deep investigation
```

Mid-level engineering judgment means knowing when continued diagnosis is useful and when it is delaying recovery.

# Mid-Level Linux Troubleshooting Framework

A useful mental model for production Linux incidents is:

```text
1. IMPACT
   What is actually broken?

        |
        v

2. SCOPE
   Host, process, service,
   dependency, or network?

        |
        v

3. TIMELINE
   When did it begin?

        |
        v

4. CHANGE
   What changed?

        |
        v

5. EVIDENCE
   Metrics, logs, process state,
   kernel state, historical data

        |
        v

6. HYPOTHESIS
   What explains all the evidence?

        |
        v

7. TEST
   Can I prove or disprove it safely?

        |
        v

8. MITIGATE
   Smallest safe intervention

        |
        v

9. VERIFY
   Did the system actually recover?

        |
        v

10. PREVENT
    Why was this possible?
```

# Commands You Should Understand at Mid-Level

You should not simply memorize these commands. You should know what question each one helps answer.

| Command              | Production Question                                            |
| -------------------- | -------------------------------------------------------------- |
| `uptime`             | What is the load trend and how long has the host been running? |
| `vmstat`             | Are tasks runnable, blocked, swapping, or waiting on I/O?      |
| `iostat`             | Which storage devices show latency or saturation?              |
| `sar`                | What was happening before I connected to the server?           |
| `ss`                 | What is happening with sockets and network connections?        |
| `lsof`               | What files, sockets, or resources does a process hold?         |
| `strace`             | Which system calls is the process making or blocking on?       |
| `pidstat`            | Which processes are responsible for CPU or I/O activity?       |
| `journalctl`         | What did services and the system report?                       |
| `dmesg`              | What is the kernel reporting?                                  |
| `df -h`              | Is filesystem capacity exhausted?                              |
| `df -i`              | Are inodes exhausted?                                          |
| `findmnt`            | What is actually mounted and where?                            |
| `ps`                 | What processes exist and what state are they in?               |
| `/proc/<PID>/limits` | What limits actually apply to this process?                    |
| `/proc/<PID>/fd`     | How many descriptors does this process currently hold?         |

# What a Mid-Level Candidate Should Demonstrate

A junior engineer may see:

```text
High load
```

and immediately check CPU.

A mid-level engineer should ask:

```text
What is contributing to the load?
```

A junior engineer may see:

```text
Too many open files
```

and increase `ulimit`.

A mid-level engineer should ask:

```text
Why is descriptor usage growing?
```

A junior engineer may see:

```text
Disk full
```

and delete files.

A mid-level engineer should determine:

```text
Which filesystem?

Capacity or inodes?

Deleted-open files?

What created the growth?

Can anything be removed safely?

Why did monitoring not catch this earlier?
```

A junior engineer may see a broken server and think:

```text
Restart it.
```

A mid-level engineer should think:

```text
What evidence will the restart destroy?

Can I mitigate more narrowly?

Will restart actually remove the cause?

What is the risk of not restarting?

What is the risk of restarting?
```

That is the standard this Mid-Level DevOps Engineer Interview series should maintain.

Part 1 is not testing whether a candidate knows Linux commands.

It is testing whether they can use Linux as an investigative environment during real production failures.
