# Part 13: Terraform State, Modules, and Production Infrastructure

At mid-level, Terraform interview questions should not focus on:

```text
What is Terraform?
What is HCL?
What does terraform init do?
```

The candidate should already understand basic Terraform syntax, resources, variables, outputs, providers, and the standard workflow.

This section should test whether the engineer can safely operate Terraform when infrastructure is already in production.

The interviewer should expect you to reason about:

* Remote state
* State locking
* Drift
* Imports
* Resource replacement
* Refactoring
* Modules
* Provider and module versioning
* State recovery
* CI/CD
* Plan review
* Environment isolation
* Sensitive data
* Failed applies
* Protection against accidental destruction

A useful production model is:

```text
Git Repository
      |
      v
Terraform Configuration
      |
      v
terraform plan
      |
      v
State + Provider APIs
      |
      v
Proposed Infrastructure Change
      |
      v
Review / Approval
      |
      v
terraform apply
      |
      v
Cloud Infrastructure
      |
      v
Updated State
```

The most important thing to understand is:

```text
Terraform configuration
+
Terraform state
+
Actual infrastructure

must remain logically aligned.
```

Terraform does not manage infrastructure based only on `.tf` files.

State is a critical part of the system.

---

# Question 1: Why should production Terraform state normally be remote?

## Interview Answer

Local state creates operational risks when multiple engineers or CI systems manage the same infrastructure.

With local state:

```text
Engineer A laptop
terraform.tfstate

Engineer B laptop
terraform.tfstate

CI runner
terraform.tfstate
```

Now there may be multiple competing versions of infrastructure state.

A remote backend provides a shared source of Terraform state.

Conceptually:

```text
Engineer A
    |
    |
Engineer B -----> Remote State
    |
    |
CI Pipeline
```

Benefits include:

* Shared state
* Centralized access control
* Backup/versioning depending on backend
* State locking where supported
* Better CI/CD integration
* Reduced dependency on individual workstations

The state backend should itself be treated as production infrastructure.

If the state is lost or corrupted, Terraform's understanding of managed resources can be damaged.

---

# Question 2: What information is stored in Terraform state?

## Interview Answer

Terraform state maps Terraform resource addresses to real infrastructure objects.

For example:

```text
aws_instance.api
```

may correspond to:

```text
i-0123456789abcdef0
```

State can also contain:

* Resource attributes
* Dependencies
* Resource IDs
* Provider-related metadata
* Output values
* Sensitive values in some cases

Conceptually:

```text
Terraform Address
        |
        v
State
        |
        v
Real Infrastructure Object
```

Without this mapping, Terraform may not know that an existing EC2 instance belongs to:

```text
aws_instance.api
```

in the configuration.

That is why state should never be treated like an unimportant cache file.

---

# Question 3: Why is Terraform state sensitive?

## Interview Answer

Because state may contain infrastructure details and potentially sensitive values.

Depending on the resources involved, state can contain information such as:

```text
Resource IDs
IP addresses
Database configuration
Secret values
Credentials generated by resources
Connection strings
```

Marking an output as:

```hcl
sensitive = true
```

prevents casual display in some Terraform output contexts.

It does not mean the value disappears from state.

Therefore, state storage should have:

```text
Encryption
Access control
Audit
Backup
Restricted IAM
```

Production state should never be casually committed into Git.

# Question 4: What is state locking?

## Interview Answer

State locking prevents multiple Terraform operations from modifying the same state concurrently when the backend supports locking.

Without locking:

```text
Pipeline A
reads state
     |
     v
plans change A

Pipeline B
reads same state
     |
     v
plans change B

Both apply
```

Now both processes may attempt to update infrastructure and state simultaneously.

That creates race conditions.

With locking:

```text
Pipeline A
     |
     v
Acquire state lock
     |
     v
Apply

Pipeline B
     |
     X
Wait for lock
```

Only one mutating operation manages that state at a time.

For production Terraform, this is extremely important.

---

# Question 5: A Terraform pipeline says the state is locked. What do you do?

## Interview Answer

I do not immediately force-unlock it.

First, I determine whether another Terraform process is genuinely running.

I would check:

* CI pipelines
* Other deployment jobs
* Recent Terraform operations
* Lock metadata
* Operator activity

Suppose:

```text
Pipeline A:
terraform apply
still running
```

Then the lock is protecting state correctly.

If I force-unlock it and start Pipeline B:

```text
Pipeline A
      |
      v
still modifying infrastructure

Pipeline B
      |
      v
also modifying infrastructure
```

I have created concurrent mutation.

Only if I can prove the original operation is dead and the lock is stale would I consider removing the lock using the backend-supported process.

The principle is:

```text
A lock is evidence.

Investigate why it exists
before removing it.
```

# Question 6: What is Terraform drift?

## Interview Answer

Drift occurs when actual infrastructure differs from the Terraform-managed desired state.

Suppose Terraform defines:

```hcl
instance_type = "t3.medium"
```

but someone manually changes production to:

```text
t3.large
```

Now:

```text
Terraform configuration:
t3.medium

Actual AWS:
t3.large
```

That is drift.

The next Terraform plan may propose:

```text
t3.large -> t3.medium
```

depending on the resource behavior.

Drift can come from:

* Console changes
* CLI changes
* Other automation
* Incident responses
* Provider-side behavior
* External controllers

The goal is not to pretend manual changes never happen.

The goal is to detect and reconcile them safely.

---

# Question 7: How do you detect Terraform drift?

## Interview Answer

A normal Terraform planning or refresh process compares configured state with provider-observed infrastructure.

I might run:

```bash
terraform plan
```

or an appropriate CI drift-detection workflow.

I want to distinguish:

```text
Configuration change
```

from:

```text
Infrastructure changed outside Terraform
```

A scheduled drift-detection pipeline can be useful.

For example:

```text
Every night
   |
   v
terraform plan
   |
   v
No changes?
   |
   +---- Yes -> healthy
   |
   +---- No -> investigate
```

But I would avoid automatically applying every detected drift.

The manual change may have been an emergency mitigation that needs to be incorporated into code first.

---

# Question 8: A production engineer manually increases an Auto Scaling group's capacity during an incident. Terraform later wants to undo it. What do you do?

## Interview Answer

First, determine whether the manual change is still required.

Suppose Terraform defines:

```hcl
desired_capacity = 10
```

but production was manually changed to:

```text
20
```

during an outage.

The next plan shows:

```text
20 -> 10
```

I would not blindly apply.

If 20 is now the intended state, I would update the Terraform configuration.

Then:

```text
Code desired state:
20

Actual infrastructure:
20
```

Terraform and production are reconciled.

If the incident has ended and 10 is again correct, Terraform may safely return it to 10.

The important point is:

```text
Manual emergency changes
must eventually be reconciled
with infrastructure as code.
```

---

# Question 9: When would you use `ignore_changes`?

## Interview Answer

I would use lifecycle `ignore_changes` only when another system is intentionally authoritative for specific attributes.

For example:

```hcl
lifecycle {
  ignore_changes = [
    desired_capacity
  ]
}
```

might be appropriate if Auto Scaling continuously manages desired capacity and Terraform should not reset it.

But `ignore_changes` can also hide meaningful drift.

If I ignore:

```text
security group rules
```

without strong reason, Terraform may stop showing important unauthorized changes.

The question is:

```text
Who owns this attribute?
```

If Terraform owns it, I generally want Terraform to detect drift.

If another system owns it, ignoring that attribute may be appropriate.

---

# Question 10: What does importing a resource into Terraform accomplish?

## Interview Answer

Import associates an existing infrastructure object with a Terraform resource address.

Suppose an RDS instance already exists:

```text
prod-db-001
```

and I create configuration:

```hcl
resource "aws_db_instance" "production" {
  ...
}
```

Import tells Terraform:

```text
aws_db_instance.production
corresponds to
prod-db-001
```

The import does not automatically guarantee the configuration matches the actual resource.

After import, I still need to run:

```bash
terraform plan
```

and reconcile configuration.

---

# Question 11: Why is import dangerous if you do not review the next plan?

## Interview Answer

Because the resource may be associated with state while the configuration differs substantially.

Suppose the real database is:

```text
Multi-AZ
encrypted
deletion protection enabled
```

but the Terraform configuration incorrectly describes:

```text
single-AZ
different storage
different settings
```

After import, Terraform may propose large changes.

Potentially:

```text
Update
Replace
Destroy/Create
```

So my workflow is:

```text
Write or generate accurate configuration
      |
      v
Import
      |
      v
Plan
      |
      v
Review every difference
      |
      v
Correct configuration
      |
      v
Only then consider apply
```

An import is the beginning of reconciliation, not the end.

---

# Question 12: You import an existing production resource and Terraform wants to replace it. What do you do?

## Interview Answer

I stop and determine which attribute causes replacement.

Terraform plans often show replacement indicators.

I would inspect the relevant provider schema and plan.

Perhaps:

```text
availability_zone
```

is configured differently.

Or:

```text
name
```

may be a ForceNew-style attribute for that resource.

I would ask:

```text
Is the Terraform configuration wrong?

Is the infrastructure wrong?

Does this attribute truly require replacement?

Would replacement cause downtime or data loss?
```

I would not apply until the desired behavior is clear.

---

# Question 13: What does Terraform mean when it plans to replace a resource?

## Interview Answer

It means the current resource cannot be changed in place for one or more planned attributes.

Terraform may need to:

```text
destroy old
+
create new
```

or:

```text
create new
+
destroy old
```

depending on lifecycle and provider behavior.

For example:

```text
aws_instance.api must be replaced
```

does not necessarily mean the entire configuration is wrong.

One changed attribute may require recreation.

Replacement risk depends heavily on the resource.

Replacing:

```text
temporary EC2 instance
```

may be routine.

Replacing:

```text
production database
```

may be extremely serious.

---

# Question 14: What is `create_before_destroy`?

## Interview Answer

It changes replacement order where Terraform and the provider can support it.

Default conceptual replacement may be:

```text
Destroy old
     |
     v
Create new
```

With:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Terraform may attempt:

```text
Create new
     |
     v
Switch dependencies
     |
     v
Destroy old
```

This can reduce downtime.

But it is not universally safe.

Potential issues include:

* Unique-name constraints
* Quotas
* IP limitations
* Duplicate resources
* Database identity
* External dependencies

I would not add it automatically to every resource.

---

# Question 15: What is `prevent_destroy`?

## Interview Answer

`prevent_destroy` blocks Terraform from destroying the resource through normal planning while the lifecycle rule is in effect.

Example:

```hcl
lifecycle {
  prevent_destroy = true
}
```

This can provide an additional safety barrier for critical resources such as:

```text
Production database
Important storage
Critical networking components
```

But it is not a substitute for:

* Backups
* IAM controls
* Change review
* Cloud deletion protection

It is one layer of defense.

---

# Question 16: Can `prevent_destroy` make operations difficult?

## Interview Answer

Yes.

Suppose infrastructure must legitimately be replaced.

Terraform will block the operation until the lifecycle configuration is intentionally changed.

That friction may be desirable for critical systems.

It forces the engineer to acknowledge:

```text
Yes, destruction is intentional.
```

The key is to use it where accidental destruction would be severe, not everywhere without thought.

---

# Question 17: `count` versus `for_each`, how do you decide?

## Interview Answer

I think about resource identity.

`count` creates index-based addresses:

```text
aws_instance.api[0]
aws_instance.api[1]
aws_instance.api[2]
```

`for_each` creates key-based addresses:

```text
aws_instance.api["payments"]
aws_instance.api["orders"]
aws_instance.api["users"]
```

If instances have meaningful stable identities, I generally prefer `for_each`.

That reduces the risk that changing list ordering changes resource addresses.

---

# Question 18: Why can `count` cause accidental resource replacement?

## Interview Answer

Suppose:

```hcl
servers = [
  "api",
  "payments",
  "orders"
]
```

with `count`.

Addresses become:

```text
[0] api
[1] payments
[2] orders
```

Now remove `payments`:

```hcl
servers = [
  "api",
  "orders"
]
```

The index mapping changes.

Conceptually:

```text
Before:
[1] payments
[2] orders

After:
[1] orders
```

Terraform may interpret this as resource identity changes rather than just removing one logical item.

With:

```hcl
for_each = toset(var.servers)
```

addresses can remain:

```text
["api"]
["payments"]
["orders"]
```

Removing `payments` only removes:

```text
["payments"]
```

This is one reason stable keys matter.

---

# Question 19: When is `count` still appropriate?

## Interview Answer

When resources are truly interchangeable and index-based identity is acceptable.

For example:

```text
Create 3 identical temporary resources
```

may fit `count`.

But for production infrastructure with meaningful names and roles, I usually prefer identity that survives ordering changes.

The key question is:

```text
Does this resource have stable logical identity?
```

---

# Question 20: What makes a good Terraform module?

## Interview Answer

A strong module should represent a meaningful infrastructure abstraction.

For example:

```text
VPC module
Application service module
RDS module
EKS node group module
```

It should have:

* Clear inputs
* Clear outputs
* Reasonable defaults
* Minimal hidden behavior
* Versioning
* Documentation
* Validation
* Predictable resource ownership

I avoid modules that simply wrap one resource with no useful abstraction unless there is a strong governance reason.

I also avoid giant modules that create:

```text
VPC
RDS
EKS
IAM
CloudFront
S3
DNS
Monitoring
```

all through one tightly coupled interface.

---

# Question 21: What is wrong with a "mega-module"?

## Interview Answer

Large modules create high coupling.

Suppose:

```text
company_platform_module
```

manages 80 unrelated resources.

Now a minor network change may require interacting with a module that also manages databases, IAM, and compute.

Problems include:

* Large plans
* Difficult testing
* Hard upgrades
* High blast radius
* Too many inputs
* Poor ownership boundaries

I prefer composable modules.

For example:

```text
network module
database module
service module
observability module
```

then combine them at the environment/root level.

---

# Question 22: What should a root Terraform configuration do?

## Interview Answer

The root configuration should compose modules and environment-specific infrastructure.

For example:

```hcl
module "network" {
  source = "../../modules/network"
}

module "database" {
  source = "../../modules/database"

  vpc_id = module.network.vpc_id
}
```

Conceptually:

```text
Root Configuration
      |
      +---- Network Module
      |
      +---- Database Module
      |
      +---- Application Module
```

The root defines how components fit together.

Modules encapsulate reusable implementation.

---

# Question 23: How would you version internal Terraform modules?

## Interview Answer

I would use immutable versions.

For example:

```hcl
module "vpc" {
  source = "git::https://example.com/network.git?ref=v3.4.1"
}
```

or a private registry version.

I would avoid production configurations depending directly on:

```text
main
```

because module behavior could change without the consuming infrastructure configuration changing.

A versioned module creates:

```text
Environment A -> module v3.2
Environment B -> module v3.4
```

and allows controlled upgrades.

---

# Question 24: Why is using a module from `main` dangerous?

## Interview Answer

Because `main` is mutable.

Yesterday:

```text
main -> commit A
```

Today:

```text
main -> commit B
```

A pipeline rerun may consume different module code even though the root configuration was unchanged.

That weakens reproducibility.

Production dependencies should be versioned intentionally.

---

# Question 25: How do you introduce a breaking module change?

## Interview Answer

I would release a new major or otherwise clearly incompatible version according to the team's versioning standard.

For example:

```text
v3
-> current interface

v4
-> breaking input/output change
```

Then:

```text
Develop
   |
   v
Module tests
   |
   v
Release v4
   |
   v
Canary environment
   |
   v
Plan review
   |
   v
Gradual adoption
```

I would not silently break every environment consuming a shared module.

---

# Question 26: Why should provider versions be constrained?

## Interview Answer

Provider behavior can change.

If configuration uses:

```hcl
provider "aws" {
}
```

without appropriate version constraints and dependency lock behavior, a future initialization may select a newer provider with changed behavior.

I prefer intentional version constraints.

For example:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

The exact policy depends on the organization.

The objective is:

```text
Provider upgrades
should be deliberate,
reviewed,
and tested.
```

---

# Question 27: What is the Terraform dependency lock file for?

## Interview Answer

`.terraform.lock.hcl` records provider selections and checksums.

This helps different environments use consistent provider versions according to configured constraints.

It should normally be version controlled.

Conceptually:

```text
required_providers
      |
      v
terraform init
      |
      v
Selected provider version
      |
      v
Lock file
```

This improves reproducibility.

---

# Question 28: How do Terraform resource dependencies work?

## Interview Answer

Terraform builds a dependency graph.

Implicit dependencies arise from references.

For example:

```hcl
subnet_id = aws_subnet.private.id
```

creates a dependency:

```text
Subnet
  |
  v
EC2 Instance
```

Terraform knows the subnet must exist before it can create the instance.

Explicit dependencies can use:

```hcl
depends_on = [...]
```

when a dependency exists but is not visible through ordinary references.

I prefer implicit dependencies when possible because they communicate data relationships directly.

---

# Question 29: Why is excessive `depends_on` problematic?

## Interview Answer

Because it can create unnecessary serialization and hidden coupling.

Suppose I make:

```text
Application module
depends_on
entire network module
```

even though it only needs one output.

Terraform may wait on unrelated changes.

It can also make dependency reasoning harder.

I use explicit dependencies when Terraform cannot infer a real operational dependency, not as a general troubleshooting tool.

---

# Question 30: Terraform state is corrupted or missing. What do you do?

## Interview Answer

I stop all Terraform writers immediately.

I do not continue applying.

Then I determine:

```text
Is state unavailable?

Is it corrupted?

Is there a prior state version?

Does the backend support versioning/backups?
```

Potential recovery sources include:

* Remote backend version history
* Backend snapshots
* State backups
* Known-good previous state

The priority is to restore the most accurate state possible.

If no usable state exists, resources may need to be carefully reconstructed into state using import.

That can be a major recovery operation.

---

# Question 31: Why should you not simply run `terraform apply` when state is missing?

## Interview Answer

Because Terraform may think managed resources do not exist.

Suppose configuration defines:

```text
VPC
RDS
ALB
IAM
```

but state is empty.

Terraform may plan:

```text
+ create VPC
+ create RDS
+ create ALB
+ create IAM
```

even though they already exist.

This can create:

* Duplicate infrastructure
* Naming conflicts
* Unexpected dependencies
* Costs
* Outages

State recovery comes before normal apply.

# Question 32: What is `terraform state list` useful for?

## Interview Answer

It shows which resource addresses Terraform currently tracks.

For example:

```bash
terraform state list
```

might return:

```text
aws_vpc.main
aws_subnet.private["a"]
aws_subnet.private["b"]
aws_db_instance.production
```

This helps answer:

```text
Does Terraform believe this resource
belongs to this state?
```

It is extremely useful during state troubleshooting and refactoring.

# Question 33: What is `terraform state show` useful for?

## Interview Answer

It shows state data associated with a specific resource address.

For example:

```bash
terraform state show aws_db_instance.production
```

I can compare:

```text
Terraform state
```

with:

```text
Terraform configuration
```

and:

```text
Actual provider infrastructure
```

during troubleshooting.

# Question 34: What is the risk of manually manipulating Terraform state?

## Interview Answer

State operations can change Terraform's ownership mapping without changing the actual infrastructure.

For example:

```text
terraform state rm
```

does not necessarily delete the real cloud resource.

It removes Terraform's association with it.

After that:

```text
Infrastructure still exists
but
Terraform no longer manages it.
```

State commands are powerful.

I use them only with:

* Backup
* Plan review
* Clear resource mapping
* Change control

---

# Question 35: When would you use `terraform state rm`?

## Interview Answer

When I intentionally want Terraform to stop managing a resource without destroying it.

For example:

```text
Resource ownership moves
to another Terraform state
```

or:

```text
Resource becomes externally managed
```

The safe flow might be:

```text
Backup state
      |
      v
Remove resource from old state
      |
      v
Import into new state
      |
      v
Plan both sides
```

I would carefully prevent a window where both states think they own the same infrastructure.

---

# Question 36: What are `moved` blocks?

## Interview Answer

`moved` blocks tell Terraform that a resource or module address changed without requiring recreation.

Suppose I originally have:

```hcl
resource "aws_instance" "api" {
}
```

and refactor to:

```hcl
module "compute" {
}
```

Without state mapping, Terraform may interpret:

```text
old resource removed
new resource added
```

Potential result:

```text
Destroy old
Create new
```

A moved block can express:

```hcl
moved {
  from = aws_instance.api
  to   = module.compute.aws_instance.api
}
```

Conceptually:

```text
Old Terraform address
      |
      v
Same real infrastructure
      |
      v
New Terraform address
```

This makes refactoring much safer.

---

# Question 37: Why are `moved` blocks better than casually deleting and recreating resources?

## Interview Answer

Because the infrastructure identity stays intact.

Suppose I reorganize code only.

I do not want:

```text
Code structure changed
      |
      v
Production EC2 destroyed
```

A moved block tells Terraform:

```text
The resource did not change.

Only its Terraform address changed.
```

That separates configuration refactoring from infrastructure mutation.

---

# Question 38: How would you safely rename a Terraform resource?

## Interview Answer

Suppose:

```hcl
resource "aws_s3_bucket" "logs" {}
```

becomes:

```hcl
resource "aws_s3_bucket" "application_logs" {}
```

Terraform may otherwise interpret:

```text
aws_s3_bucket.logs
destroy

aws_s3_bucket.application_logs
create
```

I would use a moved block:

```hcl
moved {
  from = aws_s3_bucket.logs
  to   = aws_s3_bucket.application_logs
}
```

Then run:

```bash
terraform plan
```

I expect no infrastructure recreation solely due to the rename.

---

# Question 39: How do you safely move a resource into a module?

## Interview Answer

I establish the old and new addresses.

Before:

```text
aws_security_group.api
```

After:

```text
module.network.aws_security_group.api
```

Then:

```hcl
moved {
  from = aws_security_group.api
  to   = module.network.aws_security_group.api
}
```

I run a plan.

My expected result is:

```text
Infrastructure:
unchanged

State address:
updated
```

If Terraform proposes replacement, I stop and investigate.

---

# Question 40: Why should large Terraform refactors be separated from infrastructure changes?

## Interview Answer

Because otherwise it becomes difficult to understand the plan.

Bad pull request:

```text
Move 200 resources into modules
+
Change VPC CIDRs
+
Upgrade AWS provider
+
Replace RDS instance class
```

If the plan contains unexpected changes, isolating the cause becomes difficult.

A safer sequence is:

```text
Refactor addresses
      |
      v
Plan = no functional change
      |
      v
Merge
      |
      v
Then make infrastructure changes
```

This preserves causality.

---

# Question 41: How can sensitive data enter Terraform state even if you never hardcode it?

## Interview Answer

Resources and data sources can return sensitive values.

For example:

```text
Generated password
Database credential
Private key
Secret string
```

Terraform may store those values because they are part of resource state.

Therefore:

```text
No secret in Git
```

does not mean:

```text
No secret in Terraform state.
```

The backend must be protected accordingly.

---

# Question 42: Would you generate long-lived private keys with Terraform?

## Interview Answer

I would be cautious.

If Terraform creates the private key, the key material may end up in state.

That may violate security expectations.

I prefer secrets to be generated and stored using systems designed for secret lifecycle management when appropriate.

If Terraform must manage sensitive material, state security becomes even more critical.

---

# Question 43: How do you keep sensitive values out of Terraform plan logs?

## Interview Answer

I use Terraform sensitivity features where appropriate and make sure CI does not indiscriminately dump sensitive values.

For variables:

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}
```

But I remember:

```text
Sensitive display masking
!=
state encryption
```

# Question 60: What is the difference between Terraform recovery and service recovery?

## Interview Answer

They are related but not identical.

```text

```

using an emergency operational action.

Terraform state reconciliation may follow.

Conversely, if Terraform state is corrupted but production is healthy:

```text
Do not disturb production
```

while repairing state.

The priority depends on:

```text
Customer impact
Infrastructure correctness
State integrity
```

Terraform is a management system.

Production availability remains the higher-level objective.

## Question 61: A Terraform release creates unexpected replacements, a failed apply, and state inconsistencies in production. Walk through your response.

Architecture is managed through:

```text

     |
     v

     |
     v
AWS infrastructure
```

At 14:00, a Terraform pull request contains:

```text

```


At 14:12:

```text

```

At 14:13:

```text
terraform apply exits non-zero
```

Users begin seeing intermittent 503 errors.

What do you do?

## Interview Answer

First, I stop additional Terraform operations.

I want only one recovery process interacting with this state.

---

## Step 1: Stabilize customer traffic

I determine whether the new EC2 and ALB changes caused the 503s.

Suppose:

```text
Old target group:
8 healthy

New target group:
3 healthy
5 failing
```

If safe, I may restore traffic to the known-good target group or previous application infrastructure.

Customer recovery comes first.

I do not wait for Terraform cleanup if a fast safe traffic rollback exists.

---

## Step 2: Determine what Terraform actually changed

I review the apply log and current state.

I separate:

```text
Completed actions
Failed action
Not-yet-attempted actions
```

For example:

```text
EC2 replacement      COMPLETE
ALB listener change  COMPLETE
Security group       COMPLETE
RDS change           FAILED
Remaining actions    NOT RUN
```

A failed apply is not an all-or-nothing transaction.

---

## Step 3: Run a fresh plan after stabilization

After ensuring no conflicting Terraform process exists, I run:

```bash
terraform plan
```

The new plan represents:

```text
Current configuration
+
Current state
+
Current AWS infrastructure
```

not the original pre-apply situation.

I compare carefully.

---

## Step 4: Investigate why resources were replaced

Suppose the module refactor changed addresses from:

```text
aws_instance.api["a"]
```

to:

```text
module.compute.aws_instance.api["a"]
```

but no `moved` blocks were added.

Terraform treated old resources as removed and new resources as unrelated.

That explains some replacement.

Another cause:

```text
count
->
for_each
```

changed resource addresses.

Again, Terraform interpreted identity changes.

The infrastructure replacement was caused by state-address refactoring, not an actual need to recreate servers.

---

## Step 5: Investigate provider upgrade

Suppose the provider upgrade also changed the interpretation of an RDS argument.

That created an additional unexpected RDS update.

Now one pull request contained three independent risk categories:

```text
State address refactor
Provider behavior change
Infrastructure modification
```

This should never have been one production change.

---

## Step 6: Correct state mapping

For resources that should remain the same, I introduce correct `moved` blocks or perform an approved state migration.

For example:

```hcl
moved {
  from = aws_instance.api["a"]
  to   = module.compute.aws_instance.api["a"]
}
```

I repeat for the relevant logical resources.

My goal is:

```text
Terraform addresses change
while
real infrastructure remains.
```

---

## Step 7: Resolve RDS safely

I do not simply retry the failed database modification.

I determine:

* What change was requested?
* Did AWS partially apply anything?
* Is replacement involved?
* Is data safe?
* Is rollback possible?
* Is a maintenance window relevant?

The database has a different risk profile from stateless EC2.

---

## Step 8: Verify state integrity

I compare:

```text
terraform state list
```

with:

```text
AWS infrastructure
```

for critical resources.

I make sure:

* No orphan resources exist
* No duplicate resources exist
* No important infrastructure is missing from state
* Resource addresses point to the intended objects

---

## Step 9: Produce a clean recovery plan

I want the next plan to be small and understandable.

For example:

```text
0 to add
3 to change
0 to destroy
```

rather than:

```text
27 replacements
```

for a supposed refactor.

Then the plan receives fresh review.

---

## Step 10: Apply the minimum corrective changes

I apply only after:

```text
State mapping understood
Provider version controlled
Customer service stable
Database risk understood
Plan reviewed
```

---

## Step 11: Verify production

I monitor:

```text
ALB healthy targets
503 rate
EC2 health
RDS health
Application latency
Terraform state
```

Recovery means both:

```text
Production healthy
```

and:

```text
Terraform accurately represents production.
```

## Step 12: Prevent recurrence

I would introduce process changes such as:

```text

Destroy/replacement warnings

Production approval for replacements

```

The original failure was not simply:

```text

```

It was change-design failure.

Too many independent infrastructure risks were combined into one release.

```text
does not remove
the value from state.
```

A junior candidate may say:

```text
"Use one state
for everything."
```

A mid-level candidate asks:

```text
What is the blast radius?

Who owns it?

How often does it change?

Will state locks block unrelated teams?
```

That is the standard for Part 13.

# Final Takeaway

At mid-level, Terraform is not mainly about writing HCL.

It is about safely managing infrastructure ownership over time.

You should be able to reason about:

```text
CONFIGURATION
     |
     v
MODULES
     |
     v
PROVIDERS
     |
     v
PLAN
     |
     v
STATE
     |
     v
LOCK
     |
     v
APPLY
     |
     v
REAL INFRASTRUCTURE
     |
     v
DRIFT
     |
     v
RECONCILIATION
```

A strong mid-level DevOps engineer understands that the most dangerous Terraform problems are often not syntax errors.

They are identity problems, state problems, dependency problems, ownership problems, and change-management problems.

Before applying production Terraform, the engineer should always be able to answer:

```text
What will change?

Why will it change?

Which resources will be replaced?

Which state owns them?

What happens if apply fails halfway?

Can we recover without destroying production?
```

If those questions cannot be answered clearly, the infrastructure change is not ready to apply.
