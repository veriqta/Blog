# Part 17: DevSecOps, IAM, Secrets, and Supply Chain Security

At mid-level, security questions should move beyond:

```text
What is IAM?

What is a secret?

What is RBAC?

What is image scanning?
```

The candidate should understand how identity, credentials, artifacts, infrastructure, CI/CD, Kubernetes, and software dependencies create a connected production security boundary.

The real question is:

```text
Can you design secure delivery systems,
recognize dangerous trust relationships,
limit blast radius,
and respond correctly when
production credentials or artifacts are compromised?
```

A useful model is:

```text
Developer
    |
    v
Git Repository
    |
    v
CI/CD Pipeline
    |
    +--> Dependencies
    |
    +--> Build
    |
    +--> Security Scans
    |
    +--> Artifact
    |
    v
Registry
    |
    v
Deployment
    |
    v
Production Workload
    |
    +--> Workload Identity
    |
    +--> Secrets
    |
    +--> KMS
    |
    +--> Cloud APIs
    |
    +--> Kubernetes RBAC
```

Security must exist across the entire path.

---

# 1. Workload Identity

## Question 1: What is workload identity, and why is it preferable to static cloud credentials?

### Interview Answer

Workload identity allows an application or workload to authenticate using its runtime identity rather than storing permanent access keys.

Instead of:

```text
Application
   |
   v
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
   |
   v
AWS
```

I prefer:

```text
Application
   |
   v
Workload Identity
   |
   v
IAM Role
   |
   v
Temporary Credentials
   |
   v
AWS
```

This reduces the need to distribute and store long-lived credentials.

---

## Question 2: How would you provide AWS permissions to a Kubernetes workload?

### Interview Answer

I would prefer a workload identity mechanism that maps the workload to an IAM role.

Conceptually:

```text
Pod
 |
 v
ServiceAccount
 |
 v
Workload Identity
 |
 v
IAM Role
 |
 v
Temporary Credentials
 |
 v
AWS Service
```

The application should receive only the permissions required for its function.

I would avoid putting permanent AWS access keys inside Kubernetes Secrets when workload identity is available.

---

## Question 3: Why should two applications normally have separate workload identities?

### Interview Answer

Because they usually need different permissions.

Suppose:

```text
Payment Service
needs:
KMS decrypt
Secrets Manager read

Reporting Service
needs:
S3 read
```

Giving both the same broad role increases blast radius.

If Reporting is compromised, an attacker should not automatically gain Payment permissions.

---

# 2. Short-Lived Credentials

## Question 4: Why are short-lived credentials safer than long-lived credentials?

### Interview Answer

A long-lived credential may remain useful to an attacker until it is manually revoked.

Short-lived credentials expire automatically.

```text
Compromised static key
        |
        v
Potentially valid for months

Compromised temporary credential
        |
        v
Expires automatically
```

Expiration does not eliminate risk, but it reduces the exposure window.

---

## Question 5: Where would you prefer temporary credentials?

### Interview Answer

Where supported, I prefer temporary credentials for:

```text
CI/CD pipelines
Cloud workloads
Kubernetes workloads
Cross-account access
Developer administrative sessions
Automation
```

The principle is:

```text
Authenticate identity
        |
        v
Issue temporary permission
        |
        v
Perform operation
        |
        v
Credential expires
```

# 3. IAM Role Design

## Question 6: How do you design an IAM role for a production application?

### Interview Answer

I start with what the application actually needs to do.

Suppose a service needs:

```text
Read:
one S3 bucket

Decrypt:
one KMS key
```

I do not give:

```text
s3:*
kms:*
Resource: *
```

I scope:

```text
Actions
Resources
Conditions
Trust relationships
```

as narrowly as practical.

---

## Question 7: What is the difference between an IAM permission policy and a trust policy?

### Interview Answer

The permission policy answers:

```text
What can this role do?
```

The trust policy answers:

```text
Who can assume this role?
```

Both matter.

A tightly restricted permission policy with an overly broad trust relationship can still create risk.

---

## Question 8: What would you investigate if an application suddenly receives `AccessDenied` after an IAM change?

### Interview Answer

I would determine:

```text
Which principal is making the request?

Which action is denied?

Which resource is targeted?

Which policy should allow it?
```

Then inspect:

```text
Identity policy
Resource policy
Permission boundary
Organization controls
Session policy
Relevant conditions
```

I avoid solving the problem by attaching administrator access.

---

# 4. Cross-Account Access

## Question 9: How would you securely design access between two AWS accounts?

### Interview Answer

I prefer role assumption.

```text
Account A
Application
    |
    v
AssumeRole
    |
    v
Account B
IAM Role
    |
    v
Required Resource
```

The destination account defines which trusted identity can assume the role.

The role then contains the required permissions.

This avoids sharing permanent credentials between accounts.

---

## Question 10: What could make cross-account access dangerous?

### Interview Answer

Examples include:

```text
Overly broad trust policies
Wildcard principals
Excessive permissions
No conditions
Long session durations
Weak external identity controls
Poor monitoring
```

The trust relationship deserves as much review as the permission policy.

# 5. Secrets Management

## Question 11: What qualifies as a production secret?

### Interview Answer

Examples include:

```text
Database passwords
API credentials
Signing keys
Private keys
OAuth client secrets
Service credentials
Tokens
Encryption-related secrets
```

Secrets should not be treated as ordinary configuration.

---

## Question 12: Where should production secrets not be stored?

### Interview Answer

I avoid storing secrets in:

```text
Git repositories
Dockerfiles
Container images
Plain Terraform variables
CI/CD logs
Application logs
Wiki pages
Shell history
Unencrypted configuration files
```

Once a secret enters Git history or a container layer, deleting the visible line may not remove the historical exposure.

# 6. Secrets Rotation

## Question 13: What does proper secret rotation involve?

### Interview Answer

Rotation is more than generating a new password.

A safe process may require:

```text
Create new credential
        |
        v
Make application accept it
        |
        v
Deploy/update consumers
        |
        v
Verify new credential works
        |
        v
Revoke old credential
        |
        v
Verify old credential fails
```

Poorly coordinated rotation can create an outage.

---

## Question 14: Why can secrets rotation break production?

### Interview Answer

Suppose the database password changes first.

Some application instances still use the old value.

Now:

```text
New Pods:
SUCCESS

Old Pods:
AUTHENTICATION FAILED
```

The result can be intermittent production failures.

Rotation needs coordination between secret issuance, consumers, rollout, and revocation.

---

# 7. KMS

## Question 15: What role does KMS play in a production platform?

### Interview Answer

A key management service can centrally manage encryption keys used to protect data.

Examples include encryption for:

```text
Storage
Databases
Secrets
Object storage
Application data
```

Access to encrypted data and permission to use the corresponding key are separate security considerations.

---

## Question 16: Why should access to a KMS key be tightly controlled?

### Interview Answer

Because access to encrypted storage alone may not be enough to expose the plaintext.

But if an attacker can access both:

```text
Encrypted data
+
Required decryption capability
```

the protection may effectively disappear.

I consider both resource access and key-use permissions when analyzing blast radius.

# 8. CI/CD Credential Exposure

## Question 17: How are credentials commonly exposed through CI/CD?

### Interview Answer

Examples include:

```text
Secrets printed during debugging
Environment variables dumped
Shell tracing enabled
Artifacts containing credentials
Untrusted pull requests accessing secrets
Overprivileged runners
Credentials embedded in pipeline files
Long-lived cloud keys
```

CI/CD systems are high-value security targets because they often have deployment privileges.

---

## Question 18: Why are long-lived AWS keys dangerous in CI/CD?

### Interview Answer

If the pipeline secret store or runner is compromised, the attacker may obtain credentials that remain usable outside the CI/CD system.

I prefer:

```text
CI/CD identity
      |
      v
Federated authentication
      |
      v
Temporary cloud role
      |
      v
Deployment
```

where supported.

---

## Question 19: A pipeline accidentally prints a secret. Is deleting the log enough?

### Interview Answer

No.

I treat the secret as potentially compromised.

I would:

```text
Revoke or rotate it
Determine who could access the log
Check whether logs were exported or archived
Review audit activity
Remove unnecessary exposure
Fix the pipeline
```

Deleting visible evidence does not make the exposed credential trustworthy again.

# 9. Container Image Scanning

## Question 20: What should container image scanning detect?

### Interview Answer

Common targets include:

```text
Known vulnerable packages
OS package vulnerabilities
Application dependencies
Misconfigurations
Embedded secrets
Risky package versions
```

Scanning should happen before production deployment where practical.

---

## Question 21: Should every image vulnerability block deployment?

### Interview Answer

Not automatically.

I would consider:

```text
Severity
Exploitability
Whether the vulnerable component is reachable
Available fixes
Environment
Business impact
Compensating controls
```

A blanket policy can create security-gate fatigue.

Security gates should focus on meaningful risk.

---

## Question 22: Why should images be scanned again after they are built?

### Interview Answer

Because vulnerability knowledge changes.

An image that was clean on Monday may contain a package that receives a critical CVE on Friday.

Therefore:

```text
Build-time scanning
+
Registry/rescan capability
+
Runtime inventory
```

provides stronger coverage.

# 10. Dependency Vulnerabilities

## Question 23: Why are application dependencies a supply-chain risk?

### Interview Answer

Applications may depend on hundreds or thousands of external packages.

The dependency tree can look like:

```text
Application
   |
   +--> Package A
   |      |
   |      +--> Package C
   |
   +--> Package B
          |
          +--> Package D
```

A vulnerability or compromise in a transitive dependency may affect the application even if the team never directly selected that package.

---

## Question 24: How would you reduce dependency risk?

### Interview Answer

Controls can include:

```text
Dependency scanning
Version pinning where appropriate
Lock files
Trusted repositories
Update processes
SBOM generation
Artifact verification
Dependency review
Removing unused dependencies
```

The objective is to know what software enters production and where it came from.

---

# 11. SBOM

## Question 25: What is an SBOM?

### Interview Answer

An SBOM, Software Bill of Materials, describes software components included in an artifact.

Conceptually:

```text
Application v4.8
    |
    +--> Library A 2.1
    +--> Library B 7.4
    +--> OpenSSL X
    +--> Runtime Y
```

It provides an inventory of components.

---

## Question 26: Why is an SBOM useful during a new vulnerability disclosure?

### Interview Answer

Suppose a critical vulnerability is announced in:

```text
Library X version 3.2
```

Without inventory, teams may ask:

```text
Which applications use it?
```

With an SBOM inventory, they can identify affected artifacts faster.

That improves vulnerability response.

---

# 12. Artifact Integrity

## Question 27: What is artifact integrity?

### Interview Answer

Artifact integrity provides confidence that the artifact being deployed is the artifact that was expected and has not been modified unexpectedly.

Conceptually:

```text
Source
  |
  v
Trusted Build
  |
  v
Artifact
  |
  v
Integrity Verification
  |
  v
Deployment
```

Hashes, signatures, provenance information, and controlled registries can contribute to this assurance.

---

## Question 28: Why is "build once, deploy many" useful for security?

### Interview Answer

Because rebuilding separately for each environment can create different artifacts.

I prefer:

```text
Build
  |
  v
Artifact A
  |
  +--> Development
  +--> Staging
  +--> Production
```

with environment-specific configuration applied separately.

The artifact tested in staging should ideally be the same artifact promoted to production.

---

# 13. Least Privilege

## Question 29: Explain least privilege in a production context.

### Interview Answer

Least privilege means providing only the access necessary for the required task.

It applies to:

```text
Humans
Applications
CI/CD
Kubernetes workloads
Cloud roles
Databases
Automation
```

For example:

```text
Deployment pipeline
```

may need permission to deploy one application.

It does not automatically need:

```text
AdministratorAccess
```

to the entire cloud account.

---

## Question 30: Why is least privilege difficult in practice?

### Interview Answer

Because broad permissions are easier initially.

Teams may respond to:

```text
AccessDenied
```

by adding:

```text
*
```

until the system works.

Over time, permissions accumulate.

Good IAM requires understanding actual operations, reviewing access, and removing unnecessary permissions.

---

# 14. Kubernetes RBAC

## Question 31: How would you design Kubernetes RBAC for an application team?

### Interview Answer

I would start from the team's actual responsibilities.

They may need:

```text
get
list
watch
```

for Pods and Deployments in their namespace.

They may need controlled deployment permissions.

They probably do not need:

```text
cluster-admin
```

I scope:

```text
Verbs
Resources
Namespaces
Subjects
```

as narrowly as practical.

---

## Question 32: Why is giving CI/CD `cluster-admin` dangerous?

### Interview Answer

A compromised pipeline could potentially control the entire cluster.

That may include:

```text
Deploying malicious workloads
Reading accessible secrets
Changing RBAC
Modifying workloads
Creating persistence
Disrupting production
```

The deployment identity should have only the Kubernetes permissions necessary for its deployment process.

# 15. NetworkPolicy

## Question 33: What security problem does Kubernetes NetworkPolicy address?

### Interview Answer

Without network restrictions, workloads may have broader east-west connectivity than necessary.

A compromised Pod could potentially probe other workloads.

NetworkPolicy can restrict communication.

For example:

```text
Frontend
   |
   v
API
   |
   v
Database
```

I may allow the API to reach the database while preventing unrelated workloads from doing so.

---

## Question 34: Why is default-deny useful?

### Interview Answer

A default-deny approach changes the model from:

```text
Everything allowed
unless blocked
```

to:

```text
Nothing allowed
unless required
```

Then explicit policies allow legitimate communication.

It reduces accidental network exposure.

It must be introduced carefully to avoid breaking required dependencies.

# 16. Terraform Security

## Question 35: What security risks can Terraform introduce?

### Interview Answer

Terraform can create security problems through:

```text
Public resources
Overly broad IAM
Open security groups
Unencrypted storage
Secrets in configuration
Secrets in state
Unsafe modules
Unreviewed changes
```

Because Terraform can modify large portions of infrastructure, its execution identity is itself sensitive.

---

## Question 36: Why is Terraform state security important?

### Interview Answer

Terraform state can contain sensitive infrastructure information and, depending on the resources involved, sensitive values.

Therefore remote state should have appropriate:

```text
Access control
Encryption
Locking
Versioning/recovery
Auditability
```

State should not be treated like a harmless text file.

---

## Question 37: How would you secure Terraform CI/CD?

### Interview Answer

I would consider:

```text
Short-lived cloud credentials
Protected execution environments
Plan review
Restricted apply permissions
State protection
Module controls
Security scanning
Environment separation
Audit logs
Approval for sensitive production changes
```

A pull request should not automatically receive unrestricted production credentials.

# 18. Secret Scanning

## Question 40: Where should secret scanning happen?

### Interview Answer

Ideally at several layers:

```text
Developer workflow
Pre-commit where appropriate
Pull request
Repository
CI/CD
Artifact/image scanning
```

Earlier detection is usually cheaper.

But repository-wide monitoring remains useful because credentials may enter through multiple paths.

---

## Question 41: A developer commits an AWS access key and deletes it one minute later. Is the problem solved?

### Interview Answer

No.

The key may exist in:

```text
Git history
Developer clones
CI systems
Repository mirrors
Caches
Notifications
```

I treat it as compromised.

The first priority is credential invalidation or rotation.

Git cleanup is secondary.

# 19. Supply-Chain Compromise

## Question 42: What is a software supply-chain attack?

### Interview Answer

Instead of directly attacking the production server, an attacker compromises something used to create or deliver software.

Potential targets include:

```text
Source repository
Developer account
Dependency
CI/CD runner
Build system
Artifact registry
Container image
Deployment tooling
```

If the trusted delivery path is compromised, malicious software may enter production through normal deployment mechanisms.

---

## Question 43: Why is CI/CD a particularly powerful attack target?

### Interview Answer

Because CI/CD may have:

```text
Source access
Build permissions
Registry access
Cloud credentials
Deployment permissions
Production connectivity
```

Compromising the delivery system can be more valuable than attacking one production server.

---

## Question 44: How can artifact signing help?

### Interview Answer

Signing can help verify that an artifact came from an expected signing identity and has not been modified after signing.

The deployment process can enforce:

```text
Artifact
   |
   v
Verify signature
   |
   +-- Valid --> Continue
   |
   +-- Invalid --> Reject
```

This becomes stronger when combined with trusted build provenance and protected signing identities.

# 20. Responding to Exposed Production Credentials

## Question 45: A production AWS credential appears in a public repository. What do you do first?

### Interview Answer

I treat it as compromised immediately.

The first priority is containment.

```text
EXPOSED CREDENTIAL
        |
        v
DISABLE / REVOKE / ROTATE
        |
        v
IDENTIFY PERMISSIONS
        |
        v
REVIEW AUDIT ACTIVITY
        |
        v
CONTAIN IMPACT
        |
        v
RECOVER
        |
        v
INVESTIGATE
```

I do not wait to prove that someone used it before revoking it.

---

## Question 46: Why shouldn't you delete the Git commit first?

### Interview Answer

Because deleting the visible secret does not invalidate the credential.

While engineers clean the repository:

```text
Attacker
   |
   v
Still-valid credential
   |
   v
Production
```

Containment comes first.

Repository cleanup follows.

---

## Question 47: What would you investigate after revoking the credential?

### Interview Answer

I would establish:

```text
When was it exposed?

What permissions did it have?

Was it used unexpectedly?

From which identities or locations?

What resources were accessed?

Were new credentials created?

Were IAM policies changed?

Were workloads modified?

Was data accessed or copied?
```

Cloud audit logs become critical evidence.

---

## Question 48: Why should you look for persistence?

### Interview Answer

An attacker who obtained temporary access may have created another access path before the original credential was revoked.

Examples might include unauthorized:

```text
IAM users
Access keys
Roles
Policy changes
Workloads
Automation
```

Revoking the original credential does not automatically remove changes made with it.

An engineer enables shell debugging.

Pipeline output includes:

```text

AWS_SECRET_ACCESS_KEY=...
```

The logs are visible to hundreds of developers.

Correct response:

```text
Rotate/revoke credentials
        |
        v
Review access logs
        |
        v
Determine exposure scope
        |
        v
Check cloud audit activity
        |
        v
Remove leaked logs where appropriate
        |
        v
Fix pipeline secret handling
```

Do not simply hide the pipeline log and continue using the credential.

The application compromise became a cluster-level security incident because RBAC expanded the blast radius.

# Production Scenario 4: Secret Exists in Docker Image Layer

Dockerfile:

```text
COPY credentials.txt /tmp/
RUN use-credentials
RUN rm /tmp/credentials.txt
```

The final filesystem may not show the file.

But an earlier image layer may still contain it.

Removing a secret in a later layer does not necessarily remove it from image history.

Secrets should not be copied into build layers unnecessarily.

# Production Scenario 15: Production Credential Compromise

At 09:15, security discovers an AWS access key in a public repository.

The key belongs to a production automation account.

Permissions include:

```text
EC2
S3
IAM
ECR
EKS
```

## Step 1: Contain

Immediately revoke or disable the compromised credential.

Do not wait for the full investigation.

---

## Step 2: Preserve evidence

Capture:

```text
Repository exposure timeline
Credential identity
Relevant audit logs
CI/CD activity
Registry activity
Kubernetes activity
```

before evidence disappears due to retention.

---

## Step 3: Determine blast radius

Ask:

```text
What could this identity do?

Which resources?

Which accounts?

Could it modify IAM?

Could it create credentials?

Could it push images?

Could it deploy workloads?
```

Permissions define potential blast radius.

Audit evidence helps determine observed activity.

---

## Step 4: Review cloud activity

Build a timeline:

```text
09:02 Credential committed
09:03 CI pushes repository
09:05 Repository becomes public
09:11 Unknown API request
09:12 IAM role created
09:13 ECR image pushed
09:15 Exposure detected
09:16 Credential revoked
```

Now the incident is larger than a leaked key.

The credential appears to have been used.

---

## Step 5: Search for persistence

Investigate:

```text
New IAM identities
New roles
New access keys
Policy modifications
New workloads
Scheduled automation
Registry changes
Kubernetes changes
```

---

## Step 6: Validate artifact integrity

Because the credential had ECR permissions:

```text
Registry
   |
   v
Review image pushes
   |
   v
Compare digests
   |
   v
Verify provenance/signatures
```

Determine whether production images were replaced.

---

## Step 7: Review Kubernetes

Because the credential had EKS-related access, investigate:

```text
Deployments
DaemonSets
Pods
ServiceAccounts
RBAC
Secrets
ConfigMaps
Jobs
CronJobs
```

for unauthorized changes.

---

## Step 8: Recover from trusted state

If production integrity cannot be established confidently, recovery should use known-good:

```text
Source
Dependencies
Build environment
Artifacts
Credentials
Infrastructure configuration
```

A compromised artifact should not be promoted simply because it passes functional tests.

---

## Step 9: Rotate affected trust

The exposed credential may not be the only secret requiring action.

If it accessed other credentials or secrets, those may need rotation too.

Think in terms of:

```text
Credential A compromised
        |
        v
Could access Secret B
        |
        v
Secret B may now be compromised
```

This is credential chaining.

---

## Step 10: Prevent recurrence

Possible improvements:

```text
Replace static cloud keys
with workload identity

Add secret scanning

Reduce IAM permissions

Protect CI/CD runners

Require artifact verification

Improve audit alerts

Use short-lived credentials

Review repository visibility controls
```

# Final Takeaway

DevSecOps is not:

```text
Add scanner
        |
        v
Pipeline secure
```

A secure production delivery model connects:

```text
IDENTITY
    |
    v
SHORT-LIVED CREDENTIALS
    |
    v
LEAST PRIVILEGE
    |
    v
SOURCE SECURITY
    |
    v
DEPENDENCY SECURITY
    |
    v
SECURE BUILD
    |
    v
SBOM
    |
    v
ARTIFACT INTEGRITY
    |
    v
SECURITY GATES
    |
    v
WORKLOAD IDENTITY
    |
    v
RUNTIME CONTROLS
    |
    v
AUDITABILITY
```

A strong mid-level DevOps engineer should be able to answer:

```text
Who is this workload?

What credentials does it use?

How long are they valid?

What can this identity access?

Who can assume this role?

Where are secrets stored?

How are they rotated?

Can CI/CD expose them?

What dependencies are inside this artifact?

Can we prove where the artifact came from?

Can we verify it was not modified?

What happens if the build system is compromised?

What is the blast radius of this identity?

What do we revoke first after credential exposure?

Could the attacker have created persistence?

Can we still trust the deployed artifacts?
```

The goal is not to add security tools everywhere.

The goal is to make compromise harder, limit what a compromised identity can do, detect dangerous changes, and restore trust quickly when security controls fail.
