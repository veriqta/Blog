# Part 7: Docker Images, Runtime, and Container Production Failures

At mid-level, Docker interview questions should go well beyond:

* What is a container?
* What is a Dockerfile?
* What is the difference between an image and a container?

The candidate should be able to troubleshoot production container failures, reason about image construction, understand runtime behavior, and identify problems that come from the host, network, storage, image, registry, or process model.

The interviewer should expect you to understand this path:

```text
Dockerfile
   |
   v
Build Context
   |
   v
Image Layers
   |
   v
Registry
   |
   v
Pull
   |
   v
Container Runtime
   |
   v
Process PID 1
   |
   +----> CPU / Memory
   |
   +----> Network
   |
   +----> Storage
   |
   +----> DNS
   |
   +----> Signals
```

The important question is not:

"Can you run `docker ps`?"

It is:

"Can you explain why this container is failing in production and fix it without creating a second problem?"

---

# Question 1: Why would you use a multi-stage Docker build?

## Interview Answer

A multi-stage build separates build-time dependencies from runtime dependencies.

Suppose a Java application requires:

```text
JDK
Maven
Source code
Build tools
```

to create the application artifact.

But production may only require:

```text
JRE
Application JAR
Runtime configuration
```

A multi-stage Dockerfile could look like:

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /src
COPY pom.xml .
RUN mvn dependency:go-offline

COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre

WORKDIR /app
COPY --from=build /src/target/app.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

The final image does not need Maven or the source tree.

The architecture becomes:

```text
BUILD STAGE

Source
  |
  v
Compiler / Build Tools
  |
  v
Artifact
  |
  v
----------------------------

RUNTIME STAGE

Small Runtime
  |
  v
Artifact
  |
  v
Application
```

Benefits include:

* Smaller final image
* Reduced attack surface
* Faster pulls
* Less unnecessary software in production
* Cleaner separation between build and runtime

But I would not assume smaller always means better.

The runtime image still needs everything required to operate the application correctly.

# Question 2: Why can an extremely minimal image make production troubleshooting harder?

## Interview Answer

Because it may contain almost no diagnostic tooling.

For example, a minimal image may not include:

```text
sh
bash
curl
ping
dig
ss
ps
cat
```

This is good from an attack-surface perspective, but during an incident engineers may try:

```bash
docker exec -it app sh
```

and receive:

```text
executable file not found
```

The solution is not necessarily to install dozens of debugging tools into every production image.

Instead, I might use:

* Runtime inspection from the host
* `docker inspect`
* `docker logs`
* `docker top`
* Namespace-aware debug tooling
* A dedicated debug container
* Ephemeral containers in Kubernetes
* Separate troubleshooting images

A production image should be minimal enough to reduce unnecessary risk, but the platform should still provide a supported debugging path.

# Question 3: How would you optimize Docker image layers?

## Interview Answer

I would first understand what is making the image large.

I might inspect:

```bash
docker history <image>
```

I would look for:

* Large `COPY` instructions
* Package caches
* Build tools
* Temporary files
* Large dependency layers
* Repeated package installation
* Unnecessary source files

For example:

```dockerfile
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

creates multiple layers.

A better pattern is:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

The important detail is that deleting a file in a later layer does not necessarily remove the bytes from previous layers.

Conceptually:

```text
Layer 1:
Add 500 MB file

Layer 2:
Delete 500 MB file

Final filesystem:
File gone

Image history:
500 MB still exists in Layer 1
```

That is why image-layer awareness matters.

# Question 4: Why does Dockerfile instruction order affect build performance?

## Interview Answer

Because Docker can reuse cached layers until something invalidates them.

Suppose I write:

```dockerfile
COPY . .

RUN npm install
```

Any source-code change invalidates the `COPY` layer.

That means:

```text
Source changed
     |
     v
COPY invalidated
     |
     v
npm install reruns
```

even if `package-lock.json` did not change.

A better pattern is:

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci

COPY . .
```

Now dependency installation can remain cached when only application source changes.

Conceptually:

```text
Dependency files unchanged
        |
        v
Reuse dependency layer
        |
        v
Copy changed source
        |
        v
Build application
```

The principle is:

```text
Put stable inputs earlier.
Put frequently changing inputs later.
```

# Question 5: What causes Docker build cache invalidation?

## Interview Answer

Cache behavior depends on the build engine and instruction inputs, but common causes include:

* Dockerfile instruction changes
* Changed copied files
* Changed build arguments
* Changed base image
* Changed dependency files
* Explicit no-cache build
* Different build context

Suppose:

```dockerfile
COPY . .
RUN make build
```

A modification to:

```text
README.md
```

could invalidate the `COPY` layer even though the application code did not change.

This is why `.dockerignore` is important.

For example:

```text
.git
node_modules
logs
coverage
tmp
*.md
```

where appropriate.

I would avoid sending huge unnecessary build contexts.

# Question 6: What is dangerous about blindly relying on build cache?

## Interview Answer

Cache can hide assumptions.

Suppose a build succeeds only because a cached dependency layer exists.

A clean build may fail.

That means the cache has become hidden state.

I want this:

```text
Clean inputs
     |
     v
Build succeeds

Cache
     |
     v
Build faster
```

not:

```text
Cache exists
     |
     v
Build works

No cache
     |
     v
Build fails
```

CI should periodically prove reproducibility with clean builds.

# Question 7: What is PID 1 inside a container?

## Interview Answer

The main process started inside the container usually becomes PID 1 within that container's PID namespace.

For example:

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

may result in:

```text
PID 1
java -jar app.jar
```

PID 1 has special process-management responsibilities.

Two important ones are:

* Signal handling
* Reaping child processes

If the container's PID 1 does not handle these correctly, production problems can appear during shutdown or child-process management.

# Question 8: Why is using a shell wrapper as PID 1 sometimes a problem?

## Interview Answer

Suppose:

```dockerfile
ENTRYPOINT ["sh", "-c", "java -jar app.jar"]
```

Now:

```text
PID 1
sh
 |
 v
java
```

When the container runtime sends a termination signal to PID 1, the shell may not forward it to the Java process as expected.

Then:

```text
SIGTERM
  |
  v
shell
  |
  X
java never receives it
```

Eventually the runtime may forcefully kill the container.

A better wrapper may use:

```sh
exec java -jar app.jar
```

so the shell is replaced by the application.

Then:

```text
PID 1
java
```

This makes signal delivery much more predictable.

# Question 9: Why does signal handling matter in production?

## Interview Answer

Because container platforms do not usually begin graceful shutdown with `SIGKILL`.

They typically send a graceful termination signal first.

Conceptually:

```text
Container stop requested
       |
       v
SIGTERM
       |
       v
Grace period
       |
       v
Application exits?
   /         \
 Yes          No
 |            |
 v            v
Done        SIGKILL
```

If the application ignores `SIGTERM`, it may be killed abruptly.

That can interrupt:

* HTTP requests
* Database transactions
* Queue processing
* File writes
* Background jobs

This becomes especially important during deployments and scaling events.

# Question 10: How would you design graceful shutdown for a containerized web application?

## Interview Answer

I would coordinate several layers.

A good lifecycle might be:

```text
Deployment begins
      |
      v
Stop sending new traffic
      |
      v
Application receives SIGTERM
      |
      v
Stop accepting new work
      |
      v
Finish in-flight requests
      |
      v
Close DB / queue connections
      |
      v
Exit
```

I would verify:

* Application handles SIGTERM
* Readiness changes before termination
* Load balancer stops sending traffic
* Grace period is long enough for expected requests
* Long-running requests are bounded
* Background workers stop safely

The shutdown timeout should reflect real workload behavior.

# Question 11: A container takes 30 seconds to stop and is then killed. How would you investigate?

## Interview Answer

I would determine whether the application receives and handles the termination signal.

I might inspect:

```bash
docker stop <container>
```

and application logs.

I would also inspect how the container is launched:

```bash
docker inspect <container>
```

I want to know:

```text
What is PID 1?

Does it receive SIGTERM?

Does it forward signals?

What shutdown work occurs?

Is the application blocked on a dependency?
```

Possible causes include:

* Shell wrapper not forwarding signal
* Application ignores SIGTERM
* Shutdown hook hangs
* Long-running request
* Database connection close stalls
* Child process remains alive

I would not simply increase the stop timeout before understanding why shutdown takes so long.

# Question 12: What are zombie processes inside containers?

## Interview Answer

The concept is the same as on Linux.

A child process exits but its parent does not reap it.

If PID 1 is poorly designed and repeatedly launches child processes without collecting them, zombies can accumulate.

This is one reason lightweight init processes are sometimes used.

For example:

```text
PID 1
tiny init
   |
   v
application
```

The init process can help with:

* Signal forwarding
* Child reaping

But I would not add one automatically if the application itself correctly handles PID 1 responsibilities.

# Question 13: How does container DNS normally work?

## Interview Answer

Docker provides DNS behavior depending on the network mode.

On user-defined networks, containers can typically resolve other containers or services by name through Docker's embedded DNS mechanisms.

For example:

```text
frontend
   |
   v
api
```

The application may connect to:

```text
api:8080
```

rather than hardcoding a container IP.

Container IPs are often ephemeral.

Service names are more stable.

I would inspect:

```bash
docker inspect <container>
```

and:

```bash
docker network inspect <network>
```

when troubleshooting.

# Question 14: A container can reach an IP but cannot resolve a hostname. What do you investigate?

## Interview Answer

I separate DNS from connectivity.

If:

```bash
curl http://10.20.30.40:8080
```

works,

but:

```bash
curl http://api.internal:8080
```

fails,

I would inspect:

```text
Container resolver configuration
Docker network
Host DNS
Custom DNS settings
Search domains
Split DNS
VPN behavior
```

Inside a container, I might inspect:

```bash
cat /etc/resolv.conf
```

if the image supports it.

If the image has no shell, I would use a debug container attached to the same network namespace or equivalent tooling.

The important point is:

```text
IP connectivity works
+
Hostname fails
=
DNS is a strong suspect
```

# Question 15: What is Docker bridge networking?

## Interview Answer

Bridge networking provides a virtual Layer 2/Layer 3 networking environment on a Docker host.

Conceptually:

```text
Container A
10.0.0.2
    |
    v
Docker Bridge
    |
    +------> Container B
    |
    v
Host Interface
    |
    v
External Network
```

The host typically provides forwarding and NAT behavior for outbound traffic.

Containers on the same user-defined bridge network can communicate according to network configuration.

Operationally, I would think about:

* Container IP
* Bridge interface
* Host routing
* NAT
* Port publishing
* Firewall rules
* DNS

# Question 16: What is the difference between `EXPOSE` and publishing a port?

## Interview Answer

`EXPOSE` documents that the containerized application expects to use a particular port.

For example:

```dockerfile
EXPOSE 8080
```

It does not automatically publish that port to the host.

Publishing might be:

```bash
docker run -p 8080:8080 app
```

which creates a host-to-container mapping.

Conceptually:

```text
Host :8080
   |
   v
Container :8080
```

A candidate who confuses `EXPOSE` with actual host port publishing can misdiagnose connectivity failures.

# Question 17: The application works inside the container but not from the host. What would you check?

## Interview Answer

I would verify:

```bash
docker ps
```

and port mappings.

Then inspect the application listener.

A common mistake is:

```text
Application listens:
127.0.0.1:8080
inside container
```

rather than:

```text
0.0.0.0:8080
```

If the application only listens on container loopback, the published container interface may not accept the connection.

I would also inspect:

* Docker network
* Host firewall
* Port conflicts
* Mapping direction
* Application logs

# Question 18: What is overlay networking conceptually?

## Interview Answer

Overlay networking allows containers on different hosts to communicate through a virtual network built over the underlying physical or cloud network.

Conceptually:

```text
Host A                          Host B

Container A                    Container B
   |                              |
   v                              v
Overlay endpoint              Overlay endpoint
   |                              |
   +-------- encapsulated --------+
            underlay network
```

Technologies may use mechanisms such as VXLAN.

The important operational consequence is that additional networking layers now exist.

Troubleshooting may involve:

```text
Container network
Overlay network
Host network
Underlay network
Firewall
MTU
Encapsulation
```

This can make MTU issues especially relevant.

It strongly suggests a cross-host networking problem.

Same-host communication proves much of the local container network works.

I would investigate:

* Overlay network
* Host routes
* Encapsulation traffic
* Firewall
* Underlay connectivity
* MTU
* Network driver
* Host-to-host communication

The comparison is valuable:

```text
Same host
works

Different hosts
fails
```

That narrows the failure domain.

# Question 20: What is the difference between a Docker volume and a bind mount?

## Interview Answer

A Docker-managed volume is managed by the container runtime.

For example:

```bash
docker volume create app-data
```

Then:

```bash
docker run -v app-data:/data app
```

A bind mount maps a specific host path into the container.

For example:

```bash
docker run -v /srv/app:/data app
```

Conceptually:

```text
Volume:

Docker-managed storage
       |
       v
Container /data
```

versus:

```text
Bind mount:

Host /srv/app
      |
      v
Container /data
```

Bind mounts tightly couple the container to host filesystem structure.

Volumes generally offer cleaner abstraction for runtime-managed persistent data.

# Question 21: A container starts, but the application says a configuration file is missing even though the image contains it. What could be wrong?

## Interview Answer

A mount may be hiding the file.

Suppose the image contains:

```text
/app/config/default.yaml
```

but the container starts with:

```bash
docker run -v /host/config:/app/config app
```

The mount overlays `/app/config`.

The image's original directory contents are no longer visible at that path.

Conceptually:

```text
Image:

/app/config/default.yaml
```

After bind mount:

```text
Host /host/config
       |
       v
/app/config
```

Now the mounted directory determines what the container sees.

This is a classic production issue after deployment changes.

# Question 22: A container cannot write to a mounted volume. What would you investigate?

## Interview Answer

I would inspect:

* Host filesystem ownership
* Container runtime user
* UID/GID
* Mount permissions
* Read-only flag
* SELinux/AppArmor where relevant
* Filesystem state
* Disk capacity
* Inode capacity

For example, the image may run as:

```dockerfile
USER 10001
```

while the mounted directory belongs to:

```text
root:root
0700
```

The process may receive:

```text
Permission denied
```

The correct fix is not necessarily:

```bash
chmod -R 777
```

I would align permissions safely.

# Question 23: Why are bind mounts risky for portability?

## Interview Answer

Because they depend on the host filesystem.

Suppose a container expects:

```text
/srv/company/config
```

That path may exist on Host A but not Host B.

Now:

```text
Same image
+
Different host
=
Different behavior
```

This weakens portability.

Bind mounts are useful, but the dependency should be explicit.

---

# Question 24: A database container is deleted. Is the database data necessarily lost?

## Interview Answer

It depends on where the data was stored.

If it lived only in the container's writable layer, removing the container can remove that data.

If it lived in a persistent volume:

```text
Container
   |
   v
Volume
```

then the data may remain after container removal.

This is why stateful workloads need explicit storage architecture.

Containers should generally be treated as replaceable.

Persistent data should not accidentally depend on a specific container instance.

---

# Question 25: What is CPU throttling in a container?

## Interview Answer

A container may have CPU limits enforced by cgroups.

When the workload tries to consume more CPU than its configured quota allows, the scheduler may throttle it.

The important production symptom is:

```text
Host CPU not fully utilized
but
container latency high
```

For example:

```text
Host:
CPU 40%

Container:
CPU limit 1 core
Workload wants 2 cores
```

The container can be throttled even though the host has unused CPU.

This is why host-level CPU alone can be misleading.

---

# Question 26: How would CPU throttling appear in an application?

## Interview Answer

Possible symptoms include:

* Increased request latency
* Slow garbage collection
* Slow builds
* Worker backlog
* Timeouts
* Throughput plateau

The application may appear:

```text
CPU-bound
```

inside its limit while the physical or virtual host has capacity.

I would inspect cgroup/container metrics rather than only host `top`.

In orchestrated platforms, metrics such as throttled CPU time can be particularly useful.

# Question 27: Why can a very low CPU limit make a container unstable?

## Interview Answer

Because processes may require bursts of CPU.

Suppose:

```text
Normal:
200m CPU

Startup:
800m CPU
```

If limit:

```text
250m
```

then startup can become very slow.

This may lead to:

```text
Slow startup
    |
    v
Health check timeout
    |
    v
Restart
    |
    v
Slow startup again
```

which creates a loop.

Resource limits should reflect real workload behavior, including startup and peak periods.

# Question 28: What happens when a container exceeds its memory limit?

## Interview Answer

Unlike CPU, which can be throttled, memory cannot simply be slowed indefinitely.

If the process exceeds the effective cgroup memory limit and the system cannot satisfy the allocation, it may be killed.

In orchestration environments this commonly appears as:

```text
OOMKilled
```

The process exits.

The container may then restart according to policy.

---

# Question 29: How would you investigate an OOMKilled container?

## Interview Answer

I would first confirm the termination reason.

In Docker, I might inspect:

```bash
docker inspect <container>
```

and relevant runtime/host logs.

I would correlate:

```text
Configured memory limit
Actual memory usage
Application working set
Traffic
Deployment changes
Cache growth
Runtime heap
```

Questions include:

```text
Was the limit recently reduced?

Did traffic increase?

Is there a memory leak?

Did application heap settings ignore container limits?

Did a new feature load large data sets?
```

I would not immediately double the memory limit.

Increasing the limit may be correct if the workload is legitimately undersized.

But if memory grows without bound, increasing the limit only postpones failure.

# Question 30: Why can JVM applications historically be tricky in containers?

## Interview Answer

Because runtime memory ergonomics need to understand container limits rather than assuming host-level resources.

Modern JVMs have improved container awareness, but I still verify:

* JVM version
* Heap sizing
* Container memory limit
* Native memory
* Metaspace
* Thread stacks
* Direct buffers

For example:

```text
Container limit:
2 GB

Java heap:
1.8 GB
```

leaves relatively little room for:

```text
Metaspace
Native memory
Threads
Buffers
JIT
```

The application may be OOMKilled even when the Java heap itself has not exceeded its configured maximum.

# Question 31: Container memory usage increases slowly over several days. How do you determine whether the container or host is leaking?

## Interview Answer

I separate:

```text
Container process memory
```

from:

```text
Host-level memory growth
```

I would compare container metrics over time.

If one container grows:

```text
Day 1: 500 MB
Day 2: 900 MB
Day 3: 1.3 GB
Day 4: 1.8 GB
```

while other containers remain stable, I investigate that application.

If host memory grows while containers do not, I might investigate:

* Page cache
* Container runtime
* Kernel memory
* Filesystem cache
* Other host processes

The location of the growth matters.

# Question 33: Why should base images be pinned and regularly updated?

## Interview Answer

If I use:

```dockerfile
FROM ubuntu:latest
```

the meaning can change over time.

That weakens reproducibility.

A pinned version or digest improves traceability.

For example:

```dockerfile
FROM ubuntu:24.04
```

or an approved digest.

But pinning creates another responsibility.

If I never update the pinned base image, known vulnerabilities remain forever.

The lifecycle should be:

```text
Pin
  |
  v
Scan
  |
  v
Review updates
  |
  v
Test
  |
  v
Rebuild
```

Reproducibility and patching both matter.

---

# Question 34: Would you install package updates during every container startup?

## Interview Answer

Generally, no.

A container should ideally run an immutable image.

Doing:

```bash
apt-get update && apt-get upgrade
```

at runtime means two containers launched from the same image may behave differently depending on when they start.

A stronger pattern is:

```text
Base image update
      |
      v
Build new image
      |
      v
Scan
      |
      v
Test
      |
      v
Deploy
```

Runtime mutation weakens reproducibility.

# Question 35: What is a rootless container?

## Interview Answer

Rootless container operation allows container tooling and workloads to run without requiring a root-privileged daemon or root-level runtime context in the traditional sense.

The goal is to reduce the consequences of runtime compromise.

Conceptually:

```text
Traditional:

Container process
      |
      v
Privileged runtime context
      |
      v
Host
```

versus:

```text
Rootless model:

Unprivileged user
      |
      v
Container runtime
      |
      v
Container
```

It can reduce certain risks, but may have limitations around:

* Networking
* Privileged ports
* Filesystems
* Device access
* Performance
* Some kernel capabilities

Rootless is a security control, not a complete isolation solution.

---

# Question 36: What is the difference between running as root inside a container and having root on the host?

## Interview Answer

They are not automatically identical because namespaces and runtime isolation change the context.

However, container root can still increase risk, especially when combined with dangerous settings such as:

* Privileged mode
* Host filesystem mounts
* Docker socket mount
* Excessive Linux capabilities
* Weak runtime isolation

I prefer applications to run as a non-root user when practical.

For example:

```dockerfile
RUN useradd -r -u 10001 appuser

USER 10001
```

But I also verify that filesystem permissions and runtime requirements support it.

---

# Question 37: Why is mounting `/var/run/docker.sock` into a container dangerous?

## Interview Answer

Because access to the Docker daemon can often provide extremely powerful control over the host.

A container with Docker socket access may be able to:

```text
Create containers
Mount host paths
Start privileged workloads
Access other container data
```

That can effectively defeat the isolation boundary.

I treat Docker socket access as highly privileged.

# Question 39: Why can using `latest` create intermittent deployment behavior?

## Interview Answer

Because nodes may not all resolve or pull the same underlying image at the same time, depending on pull policy and caching behavior.

Suppose:

```text
latest
```

used to point to:

```text
sha256:AAA
```

and now points to:

```text
sha256:BBB
```

One host may already have `AAA`.

Another may pull `BBB`.

Now the environment can unintentionally run mixed versions.

For production, I prefer immutable versions or digests.

# Question 41: Why can disk exhaustion cause Docker failures in surprising ways?

## Interview Answer

Docker needs local storage for:

* Image layers
* Container writable layers
* Logs
* Build cache
* Volumes
* Metadata

If Docker storage fills, you may see:

```text
Image pull failure
Container start failure
Build failure
Log write errors
```

even though the application itself is healthy.

I would inspect:

```bash
docker system df
```

and host filesystem usage.

I would be careful with cleanup commands.

For example:

```bash
docker system prune
```

can remove unused resources, but I would understand exactly what is considered unused before running it in production.

```text
      |

Central log platform
```

* Logging driver

* Application log volume
* Log retention

It may be:

# Question 46: What is an architecture mismatch?

## Interview Answer

An image may contain binaries built for a different CPU architecture.

For example:

```text
Image:
linux/arm64

Host:
linux/amd64
```

Depending on platform support, the container may fail with errors such as:

```text
exec format error
```

This becomes common when developers build images on ARM laptops and deploy to x86 servers without multi-platform build configuration.

I would inspect image metadata and host architecture.

# Question 47: How would you design multi-architecture images?

## Interview Answer

I would build platform-specific images and publish them under a manifest list or OCI image index.

Conceptually:

```text
app:v5

 |
 +----> linux/amd64 image
 |
 +----> linux/arm64 image
```

The registry provides the appropriate image for the target platform.

The build pipeline should test each supported architecture rather than assuming a successful x86 build proves ARM compatibility.

# Question 49: A container works when run as root but fails when run as non-root. How do you troubleshoot it?

## Interview Answer

I inspect permissions.

* Cannot bind privileged port
* Cannot write mounted directory
* Cannot read configuration
* Cannot execute binary
* Cannot create temp files

I would inspect image ownership during build.

For example:

```dockerfile

```

may be required.

# Production Scenario 1: Multi-Stage Build Breaks Runtime

A developer converts the Dockerfile to a multi-stage build.

Old image:

```text
1.8 GB
```

New image:

```text
180 MB
```

Deployment succeeds.

Application crashes with:

```text
libxyz.so: cannot open shared object file
```

What happened?

## Interview Answer

The build stage contained a runtime library that the final stage does not.

The image became smaller but incomplete.

The lesson is:

```text
Smaller image
!=
Correct image
```

I would identify all runtime dependencies and install or copy only what the final application actually needs.

# Production Scenario 2: Build Cache Hides Broken Build

CI uses warm cache.

Build passes.

A new runner performs a clean build.

It fails because a generated file was never declared in the Dockerfile.

The cached layer had preserved it.

Root cause:

```text
Build depended on hidden cache state.
```

Corrective action:

```text
Make build inputs explicit
and periodically test clean builds.
```

# Production Scenario 3: Deployment Causes 30-Second 502 Spike

Every new container receives SIGTERM during replacement.

But PID 1 is:

```text
sh
```

and the application never sees the signal.

Old containers remain active until forced termination.

Requests are interrupted.

The path is:

```text

   |
   v

   |
   X

   |
   v
Grace period expires
   |
   v
SIGKILL
   |
   v

   |
   v
```

* Correct PID 1 behavior
* Signal forwarding
* Graceful shutdown
* Connection draining

# Production Scenario 4: Container DNS Fails Only on One Host

Containers on Host A:

```text
api.internal -> resolves
```

Containers on Host B:

```text
api.internal -> SERVFAIL
```

Direct IP connectivity works from both.

This is host-specific container DNS behavior.

I would compare:

* Docker daemon DNS configuration
* Host `/etc/resolv.conf`
* VPN
* Firewall
* Docker network
* Resolver reachability

The DNS infrastructure itself may be healthy.

# Production Scenario 5: Cross-Host Container Traffic Fails

Same-host traffic:

```text
works
```

Cross-host traffic:

```text
fails
```

Overlay uses VXLAN.

Recent network change reduced underlay MTU.

The overlay adds encapsulation overhead.

Now larger packets fail.

The causal chain:

```text
Underlay MTU reduced
       |
       v
Overlay packet exceeds path MTU
       |
       v
Fragmentation / black-hole behavior
       |
       v
Cross-host application failures
```

This is why container networking cannot be separated from the physical/cloud network.

# Production Scenario 6: Volume Mount Hides Configuration

```text
/app/config/default.yml
```

Production starts with:

```text
-v /srv/config:/app/config
```

Host directory is empty.

Application reports:

```text

```

The image is correct.

The mount hides the image directory.

The fix is to correct the mounted content, not rebuild the image.

# Production Scenario 7: Container Is OOMKilled Only During Peak Traffic

```text

```



## Question 51: A new container release causes intermittent 502 errors, OOMKills, and slow shutdowns. Walk through your investigation.

Architecture:

```text
Users
  |
  v
Load Balancer
  |
  v
Docker Hosts
  |
  v
Application Containers
  |
  +----> Redis
  |
  +----> PostgreSQL
```

Previous release:

```text
v8.4.1
```

New release:

```text
v8.5.0
```

Timeline:

```text
14:00 deployment starts
14:03 502 rate begins increasing
14:05 containers restart
14:06 OOM events appear
14:08 deployment continues replacing hosts
```

How do you respond?

## Interview Answer

I would first stop or slow the rollout if customer impact is increasing.

I do not want more unhealthy containers introduced while I investigate.

---

## Step 1: Compare old and new containers

I would compare:

```text
Image digest
Entrypoint
Resource limits
Environment
Mounts
Runtime user
Application version
```

Suppose the new image changed:

```text
Memory limit:
1 GB -> 512 MB
```

and changed:

```text
ENTRYPOINT
```

from:

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

to:

```dockerfile
ENTRYPOINT ["sh", "-c", "java -jar app.jar"]
```

Now I have two major differences.

---

## Step 2: Investigate OOM behavior

I inspect container state and metrics.

Suppose:

```text
Normal application memory:
700 MB
```

New container limit:

```text
512 MB
```

That explains the OOMKilled events.

The host may have plenty of memory.

The container limit does not.

---

## Step 3: Investigate 502 behavior

When containers are OOMKilled:

```text
Load Balancer
    |
    v
Container
    X
```

active requests may reset.

The proxy or load balancer may return:

```text
502
```

The 502 may therefore be a consequence of the container dying.

---

## Step 4: Investigate shutdown

During normal replacement, the shell is PID 1.

Suppose the shell does not correctly forward SIGTERM.

Application shutdown becomes:

```text
SIGTERM
  |
  v
Shell
  |
  X
Java
```

The application does not gracefully finish requests.

After timeout:

```text
SIGKILL
```

This creates another path to 502 errors.

We now have two distinct mechanisms:

```text
OOMKilled
    |
    v
Abrupt connection loss
```

and:

```text
Bad signal forwarding
    |
    v
Forced shutdown
```

Both can produce similar customer symptoms.

---

## Step 5: Mitigate

If v8.4.1 is known good and rollback is safe, I would restore it.

```text
Stop rollout
    |
    v
Drain unhealthy/new targets
    |
    v
Deploy v8.4.1
    |
    v
Verify
```

I would monitor:

```text
502 rate
OOM events
Container restart count
Memory usage
Shutdown duration
Application success rate
```

---

## Step 6: Correct v8.5.0

I would fix:

```text
Memory sizing
PID 1 / ENTRYPOINT
Signal handling
```

Then validate:

* Clean startup
* Peak memory
* Graceful termination
* In-flight request completion
* Load-balancer behavior

Only then would I redeploy.

## Interview Answer

That may be part of the solution, but I first want to know whether:

```text

```

is expected application usage or evidence of a new memory regression.

If v8.4.1 used:

```text

```

and v8.5.0 uses:


# Interviewer Follow-Up: Why not increase the load-balancer timeout?

## Interview Answer

Because the primary failures are container termination and OOM behavior.

A longer timeout does not stop the backend from being killed.

It may simply make the load balancer wait longer before reporting failure.

I would fix the failing backend lifecycle.

## Interview Answer

Because debugging convenience should not automatically increase the production image's attack surface.

I would use a supported debug image or namespace-aware debugging mechanism.

The runtime image can remain minimal.
