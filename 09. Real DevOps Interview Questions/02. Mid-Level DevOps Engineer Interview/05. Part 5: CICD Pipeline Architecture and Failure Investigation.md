# Part 5: CI/CD Pipeline Architecture and Failure Investigation

At mid-level, CI/CD questions should move beyond:

"What is continuous integration?"

"What is continuous deployment?"

"What stages would you put in a pipeline?"

The candidate should be able to design, troubleshoot, secure, and improve pipelines that teams actually depend on.

The interviewer should expect you to understand:

* How a pipeline should be structured.
* Where artifacts should be created.
* How environments should differ without rebuilding the application.
* How to detect and isolate bottlenecks.
* How to investigate flaky failures.
* How to reduce pipeline time without weakening controls.
* How approvals and rollback should work.
* How secrets should be handled.
* How to observe and debug production release failures.
* How to make the pipeline itself reliable.

A useful mental model is:

```text
Commit
  |
  v
Validate
  |
  v
Build
  |
  v
Test
  |
  v
Scan
  |
  v
Package
  |
  v
Publish Artifact
  |
  v
Deploy to Staging
  |
  v
Verify
  |
  v
Approval / Policy
  |
  v
Deploy to Production
  |
  v
Observe
  |
  +---- healthy ----> continue
  |
  +---- unhealthy --> rollback / stop rollout
```

The important principle is:

```text
A pipeline is not just automation.

It is part of the production control system.
```

# Question 1: How would you design a production-grade multi-stage CI/CD pipeline?

## Interview Answer

I would first separate concerns.

A production pipeline should not have one giant script that:

```text
checks out code
builds
tests
deploys
changes infrastructure
creates secrets
restarts production
```

all in one stage.

I would structure the pipeline into clear stages.

For example:

```text
1. Source Validation
2. Dependency Resolution
3. Build
4. Unit Tests
5. Static Analysis
6. Security Scanning
7. Package Artifact
8. Publish Artifact
9. Deploy to Staging
10. Integration Tests
11. Approval / Policy Gate
12. Production Deployment
13. Post-Deployment Verification
14. Rollback if required
```

Each stage should have a clear purpose.

For example:

```text
BUILD

Question:
Can we create the deployable artifact?
```

```text
TEST

Question:
Does the application behave as expected?
```

```text
SECURITY

Question:
Does this release violate defined security policy?
```

```text
DEPLOY

Question:
Can this approved artifact be safely introduced
into the target environment?
```

This separation helps troubleshooting.

If the pipeline fails during:

```text
container image scanning
```

I should not investigate the deployment system.

If it fails during:

```text
production health verification
```

the build stage is probably not where I start.

---

# Question 2: Why should pipeline stages be independently observable?

## Interview Answer

Because pipeline failures need a clear failure boundary.

Suppose a pipeline takes 45 minutes and reports only:

```text
Pipeline failed.
```

That is operationally weak.

I want to know:

```text
Checkout      30 sec  ✓
Build          4 min  ✓
Unit Tests     6 min  ✓
Security Scan 18 min  ✓
Image Push     2 min  ✓
Staging        3 min  ✓
Integration   10 min  X
```

Now I know:

```text
The pipeline is not generally broken.

The integration test stage failed.
```

I also want:

* Stage duration
* Queue time
* Failure reason
* Runner/agent
* Commit
* Artifact version
* Environment
* Deployment result

This makes CI/CD itself observable.

# Question 3: A pipeline used to take 12 minutes and now takes 35 minutes. How do you investigate?

## Interview Answer

I would compare stage timings.

I would not start by buying faster runners.

Suppose:

```text
Before:

Checkout      30 sec
Build          3 min
Tests          5 min
Image build    2 min
Push           1 min

Total         11.5 min
```

Now:

```text
Checkout      35 sec
Build          3 min
Tests         24 min
Image build    2 min
Push           1 min

Total         30+ min
```

The bottleneck is clearly the test stage.

I would investigate:

* Number of tests
* Test runtime
* New slow tests
* External dependencies
* Database setup
* Parallelization
* Runner capacity
* Network latency
* Test retries
* Flaky tests
* Dependency initialization

Another example:

```text
Queue time:
15 minutes
```

Now the problem may not be the pipeline code.

It may be insufficient runner capacity.

I distinguish:

```text
Execution time
```

from:

```text
Queue time
```

That distinction matters.

# Question 4: How would you identify pipeline bottlenecks systematically?

## Interview Answer

I would measure each stage over time.

For example:

```text
Median
p95
Failure rate
Queue time
Execution time
```

A pipeline stage may have:

```text
Median: 4 minutes
p95:    18 minutes
```

That suggests intermittent degradation.

I would ask:

```text
Which stages dominate total pipeline duration?

Which stages have high variance?

Which stages fail most often?

Which stages wait for scarce resources?
```

I would not optimize a 20-second lint step while a 15-minute integration test is responsible for most of the delay.

The process is:

```text
Measure
  |
  v
Rank
  |
  v
Find bottleneck
  |
  v
Understand cause
  |
  v
Change one thing
  |
  v
Measure again
```

# Question 5: What is a flaky build?

## Interview Answer

A flaky build fails intermittently without a meaningful source-code change causing the failure.

For example:

```text
Same commit
Run 1 -> PASS
Run 2 -> PASS
Run 3 -> FAIL
Run 4 -> PASS
```

That is different from:

```text
Commit A -> PASS
Commit B -> FAIL consistently
```

Common causes include:

* Race conditions
* Timing assumptions
* Shared test state
* External APIs
* Unstable networks
* Dependency downloads
* Random test ordering
* Shared databases
* Insufficient resources
* Time-sensitive tests
* Port conflicts
* Improper cleanup
* Non-deterministic test data

Flaky pipelines are dangerous because teams stop trusting failures.

Once engineers routinely click:

```text
Retry
```

without investigating, real failures can be ignored.

---

# Question 6: How would you investigate a flaky pipeline?

## Interview Answer

I would first establish a pattern.

I want to know whether failures correlate with:

```text
Specific test
Specific runner
Specific time
Specific branch
Specific environment
Parallel execution
External dependency
```

I would compare successful and failed runs of the same commit.

For example:

```text
Commit: abc123

Run 44 -> pass
Runner: agent-7

Run 45 -> fail
Runner: agent-3

Run 46 -> pass
Runner: agent-7
```

That makes `agent-3` worth investigating.

Another pattern:

```text
Parallel tests enabled -> intermittent failures
Parallel tests disabled -> stable
```

That suggests shared-state or race problems.

I would preserve:

* Logs
* Test reports
* Runner metadata
* Environment variables excluding secrets
* Dependency versions
* Timing
* Resource usage

The goal is to make the intermittent behavior reproducible.

---

# Question 7: Is automatically retrying flaky tests a good solution?

## Interview Answer

Retries can reduce false failures temporarily, but they are not a complete fix.

Suppose:

```text
Test fails
Retry
Pass
```

If the pipeline silently marks it green, the instability becomes hidden.

A better temporary approach might record:

```text
Passed after retry
```

as a separate metric.

I would track:

```text
First-run pass rate
Retry rate
Tests requiring retries
```

The long-term objective is to remove the source of flakiness.

Otherwise the organization develops:

```text
Pipeline failed?
Just retry it.
```

That destroys confidence in CI.

# Question 8: What is dependency caching?

## Interview Answer

Dependency caching avoids downloading or rebuilding unchanged dependencies on every pipeline execution.

For example, without caching:

```text
Pipeline 1:
Download 2 GB dependencies

Pipeline 2:
Download same 2 GB

Pipeline 3:
Download same 2 GB
```

With caching:

```text
Cache key
   |
   v
Dependencies found
   |
   v
Reuse
```

Typical examples include:

* Maven repository cache
* npm package cache
* pip cache
* Go module cache
* Docker build cache

Caching can significantly reduce build times.

But incorrect cache design can create stale or unpredictable builds.

---

# Question 9: How would you create a safe dependency cache key?

## Interview Answer

The cache should change when the dependency definition changes.

For example:

```text
package-lock.json
pom.xml
requirements.txt
go.sum
```

A better cache key might incorporate a hash of the dependency lock file.

Conceptually:

```text
linux-node20-<hash(package-lock.json)>
```

If the lock file changes:

```text
Old cache key
      X

New cache key
      |
      v
New dependency cache
```

I would avoid using one permanent key such as:

```text
dependencies-cache
```

for every branch and every dependency version.

That increases stale-cache risk.

---

# Question 10: Can caching make builds non-reproducible?

## Interview Answer

Yes.

If the cache contains untracked state that the build depends on, two identical commits may produce different outputs.

That is a problem.

A healthy cache should accelerate work without becoming the source of truth.

The build should still be reproducible from declared inputs.

For example:

```text
Git source
+
Dependency lock file
+
Build tool version
+
Base image
=
Reproducible build inputs
```

Cache:

```text
optional performance optimization
```

not:

```text
hidden dependency
```

---

# Question 11: What does "build once, deploy many" mean?

## Interview Answer

It means I build the application artifact once and promote that same artifact through environments.

For example:

```text
Git Commit
    |
    v
Build
    |
    v
Artifact:
app@sha256:abc123
    |
    +----> Development
    |
    +----> Staging
    |
    +----> Production
```

I do not rebuild separately for staging and production.

Why?

Because separate builds can differ.

Suppose staging build occurs Monday:

```text
Base image version A
Dependency version X
```

Production build occurs Friday:

```text
Base image version B
Dependency version Y
```

Even with the same source commit, the artifacts may not be identical.

Then:

```text
We tested staging
```

does not necessarily mean:

```text
We tested what reached production.
```

Build once, deploy many improves artifact traceability and reproducibility.

---

# Question 12: How do environment-specific values work if you build only once?

## Interview Answer

Environment-specific configuration should generally be injected at deployment or runtime rather than compiled into separate artifacts.

For example:

```text
Same image:

app:v5.3.1
```

Development:

```text
DB_HOST=dev-db
LOG_LEVEL=debug
```

Staging:

```text
DB_HOST=staging-db
LOG_LEVEL=info
```

Production:

```text
DB_HOST=prod-db
LOG_LEVEL=info
```

The artifact stays the same.

Configuration changes.

I would manage environment-specific values through mechanisms such as:

* Environment variables
* ConfigMaps
* Parameter stores
* Secret managers
* Deployment values
* Environment configuration repositories

The principle is:

```text
Code artifact
should be environment-neutral
where practical.
```

# Question 13: What should never be handled as ordinary environment configuration?

## Interview Answer

Secrets should not be treated as casual plaintext configuration.

For example:

```text
DB_HOST
```

is configuration.

But:

```text
DB_PASSWORD
AWS_SECRET_ACCESS_KEY
PRIVATE_KEY
```

are secrets.

They need stronger handling around:

* Storage
* Access
* Rotation
* Audit
* Masking
* Lifetime

I would avoid placing secrets directly in:

```text
Git repository
Dockerfile
Pipeline YAML
Build logs
Artifact metadata
```

# Question 14: What is artifact promotion?

## Interview Answer

Artifact promotion means moving an already-built artifact through trust levels or environments without rebuilding it.

For example:

```text
Build
  |
  v
Candidate Artifact
  |
  v
Development
  |
  v
Staging
  |
  v
Approved
  |
  v
Production
```

The underlying artifact identity remains:

```text
sha256:abc123
```

What changes is its promotion status or where it is deployed.

This gives traceability.

I can answer:

```text
Which exact artifact passed staging?

Which exact artifact reached production?
```

with the same identifier.

# Question 15: Why is using only mutable tags such as `latest` dangerous?

## Interview Answer

Because the meaning of the tag can change.

For example:

```text
09:00
latest -> sha256:AAA

13:00
latest -> sha256:BBB
```

If production deployment references:

```text
latest
```

I may not know which image actually ran.

For production, I prefer immutable identifiers or version tags tied to digests.

For example:

```text
app:v6.2.1
digest:
sha256:9f...
```

The artifact identity should be unambiguous.

# Question 16: What parts of a pipeline would you parallelize?

## Interview Answer

Independent work.

For example:

```text
Build complete
      |
      +----> Unit tests
      |
      +----> Static analysis
      |
      +----> Dependency scan
      |
      +----> License scan
```

If all four stages are independent, running them sequentially may waste time.

Sequential:

```text
5m + 4m + 6m + 3m = 18m
```

Parallel:

```text
max(5m,4m,6m,3m) ≈ 6m
```

But I would not parallelize stages that depend on each other's results.

For example:

```text
Build Artifact
   |
   v
Deploy
```

Deployment cannot happen before the artifact exists.

---

# Question 17: Can parallelization make pipelines worse?

## Interview Answer

Yes.

It can introduce:

* Shared-state conflicts
* Resource contention
* Port collisions
* Test race conditions
* Database conflicts
* Higher runner usage
* Harder log interpretation

Suppose 20 test jobs all use:

```text
test_database
```

and modify the same rows.

Parallel execution may create flaky tests.

The correct solution may involve isolated test databases, schemas, namespaces, or unique resources per worker.

Parallelization should preserve determinism.

# Question 18: How would you reduce pipeline duration safely?

## Interview Answer

I would optimize based on measured bottlenecks.

Possible actions include:

* Dependency caching
* Build caching
* Parallel independent tests
* Test splitting
* Faster runners where justified
* Reusing immutable artifacts
* Avoiding repeated dependency installation
* Shallow clones where appropriate
* Removing redundant work
* Running expensive tests conditionally when safe
* Moving non-blocking analysis outside the critical path when policy allows

But I would not simply remove:

```text
Security scans
Tests
Approvals
Verification
```

to make the dashboard greener.

The goal is:

```text
Less waiting
without
less confidence.
```

# Question 19: Would you run every test on every commit?

## Interview Answer

It depends on cost and risk.

A layered testing strategy can be useful.

For example:

```text
Every commit:
Lint
Unit tests
Fast security checks

Pull request:
Broader integration tests

Merge to main:
Full test suite

Release candidate:
End-to-end tests
Performance tests where required
```

But the strategy needs to account for what changes.

If a supposedly unrelated change can break deployment behavior, skipping required tests may be risky.

I prefer policy based on risk and architecture rather than arbitrary speed goals.

# Question 20: What is pipeline security at a practical level?

## Interview Answer

Pipeline security means treating CI/CD as privileged infrastructure.

A pipeline may have permission to:

* Read source code
* Access secrets
* Push images
* Deploy production
* Modify cloud infrastructure
* Assume IAM roles
* Publish packages

That makes it a valuable attack target.

I would consider:

```text
Runner isolation
Secret exposure
Permissions
OIDC / workload identity
Branch protection
Artifact integrity
Dependency security
Pull request trust boundaries
Script injection
Log leakage
Approval controls
```

The pipeline should have only the permissions it needs.

---

# Question 21: Why is giving a CI runner AdministratorAccess dangerous?

## Interview Answer

Because a compromised pipeline or malicious workflow change can inherit that access.

Imagine:

```text
Pull request
   |
   v
Pipeline executes
   |
   v
Admin cloud role
```

If untrusted code can influence that pipeline, the blast radius is enormous.

I would separate permissions.

For example:

```text
Build role:
No production access

Staging deploy role:
Staging only

Production deploy role:
Production deployment permissions only
```

The pipeline identity model should reflect the pipeline stages.

---

# Question 22: How should cloud authentication work in CI/CD?

## Interview Answer

Where supported, I prefer short-lived credentials through workload identity or federation over long-lived static access keys.

For example:

```text
GitHub Actions
      |
      v
OIDC
      |
      v
Cloud STS
      |
      v
Temporary Deployment Role
```

This reduces the need to store:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

as permanent CI secrets.

The role should also have narrow permissions and trust conditions.

---

# Question 23: A secret appears in CI logs. What do you do?

## Interview Answer

I treat it as potentially compromised.

Immediate actions include:

```text
1. Revoke or rotate secret
2. Restrict access to affected logs if possible
3. Determine exposure window
4. Identify who or what could access the logs
5. Remove unsafe logging
6. Check whether other pipelines have same issue
```

I would not consider log masking alone sufficient after exposure.

If the plaintext secret was visible, rotation matters.

---

# Question 24: Why can `set -x` be dangerous in pipeline shell scripts?

## Interview Answer

Because shell tracing can print expanded commands and variables.

For example:

```bash
set -x
curl -H "Authorization: Bearer $TOKEN" ...
```

may cause the token to appear in logs depending on masking and shell behavior.

Debugging convenience must not leak credentials.

I would use targeted logging and avoid dumping:

```bash
env
printenv
```

without considering what sensitive values are present.

# Question 25: What are deployment approvals for?

## Interview Answer

Approvals provide an explicit control before high-impact changes reach an environment.

For example:

```text
Build
  |
  v
Tests
  |
  v
Staging
  |
  v
Approval
  |
  v
Production
```

Approvals may be appropriate when:

* Production changes require human authorization.
* Compliance requires separation of duties.
* Release timing must be coordinated.
* Business owners need to authorize high-risk releases.

But approvals should not become a substitute for weak automation.

A person clicking:

```text
Approve
```

without evidence is not a meaningful control.

# Question 27: How would you design rollback architecture into a pipeline?

## Interview Answer

Rollback should not be improvised after deployment fails.

The pipeline should know:

```text
Current artifact
Previous known-good artifact
Deployment mechanism
Rollback procedure
Health criteria
```

For example:

```text
Deploy v10.4.0
      |
      v
Health check
      |
      X
      |
      v
Stop rollout
      |
      v
Restore v10.3.2
      |
      v
Verify
```

For rolling or canary deployments, rollback may mean:

```text
Shift traffic back
```

rather than redeploying everything.

For GitOps:

```text
Revert desired state
```

may trigger reconciliation.

Database changes require special consideration.

---

# Question 28: Why isn't "git revert" a complete rollback strategy?

## Interview Answer

Because the production release may include more than code.

For example:

```text
Code
Database migration
Configuration
Secrets
Feature flags
Infrastructure
```

A Git revert may reverse source changes while the database has already changed.

Suppose release v4 drops a column.

Reverting code to v3 may fail because v3 expects that column.

Rollback architecture must consider the complete system state.

---

# Question 29: When would you prefer roll-forward instead of rollback?

## Interview Answer

When reverting is unsafe or slower than applying a small corrective fix.

Examples include:

* Irreversible database migration
* Data already written in a new format
* External side effects
* Backward incompatibility
* Rollback artifact unavailable
* Small obvious configuration fix

For example:

```text
Release breaks because:
TIMEOUT=0
```

If changing it to:

```text
TIMEOUT=5
```

is safe and faster than reverting a complex release, roll-forward may be better.

The decision should be based on risk, not habit.

# Question 30: A production deployment fails halfway through. What would you do?

## Interview Answer

First, determine what "halfway" means.

For example:

```text
10 replicas total

5 running v6
5 running v7
```

Now production is mixed-version.

I would determine:

* Are both versions compatible?
* Are users affected?
* Did database migration occur?
* Is the deployment controller still progressing?
* Can rollout be paused?
* Is rollback safe?

I would not immediately restart all instances.

The priority is to stop uncontrolled progression and understand the state.

In Kubernetes:

```bash
kubectl rollout status deployment/app
```

and:

```bash
kubectl rollout pause deployment/app
```

may be relevant depending on the deployment process.

The broader principle is:

```text
Stop introducing more change
while state is uncertain.
```

# Question 31: A deployment pipeline says "successful," but users immediately see failures. How is that possible?

## Interview Answer

Pipeline success proves only that the pipeline's success criteria passed.

Perhaps the pipeline checked:

```text
Deployment API returned success
Pods Running
```

but did not check:

```text
Readiness
Error rate
Latency
Checkout transaction
Database connectivity
External API behavior
```

This is why post-deployment verification matters.

A better flow is:

```text
Deploy
  |
  v
Infrastructure health
  |
  v
Application readiness
  |
  v
Synthetic test
  |
  v
Business transaction
  |
  v
Observe metrics
```

Deployment success should reflect service health, not merely automation completion.

# Question 34: What is a synthetic transaction?

## Interview Answer

A synthetic transaction actively tests an important user flow.

For example:

```text
Synthetic user
   |
   v
Login
   |
   v
Add product
   |
   v
Checkout test
   |
   v
Verify result
```

It is useful because infrastructure can look healthy while a business flow is broken.

For deployment verification, a safe synthetic transaction can detect failures before many real users encounter them.

# Question 36: Why is deployment failure rate useful?

## Interview Answer

Because faster deployment is not valuable if releases fail more often.

Suppose:

```text
Before optimization:

Deployment time: 20 min
Failure rate:     2%
```

After:

```text
Deployment time: 8 min
Failure rate:    18%
```

That is not necessarily an improvement.

I want to evaluate speed and reliability together.

Useful indicators may include:

```text
Lead time
Deployment frequency
Change failure rate
Recovery time
```

The goal is sustainable delivery.

* Stage start/end
* Runner identity
* Tool versions
* Exit code
* Resource usage
* Dependency versions
* Network failures
* Test reports

* Dependency updates

* Package repository maintenance
* Credential rotation
* Runner cleanup
* Certificate renewal
* Weekly database reset
* Scheduled infrastructure maintenance

# Question 40: Why should pipeline tool versions be pinned?

## Interview Answer

Because unpinned tools can change unexpectedly.

For example:

```text
terraform: latest
node: latest
python: latest
ubuntu: latest
```

can make the same source commit behave differently over time.

I prefer explicit versions where practical.

For example:

```text
Node 22.4
Terraform 1.x pinned to approved range
Base image digest
```

Updates should be deliberate and tested.

Otherwise:

```text
No code changed
but pipeline broke
```

becomes much more common.

# Question 43: What is a pipeline trust boundary?

## Interview Answer

A trust boundary is where code or users with different levels of trust interact with privileged pipeline capabilities.

A classic example is external pull requests.

Suppose:

```text
Untrusted fork PR
      |
      v
CI workflow
      |
      v
Production secret
```

That is dangerous.

Untrusted code should not automatically gain access to secrets or deployment credentials.

I would separate:

```text
Untrusted validation jobs
```

from:

```text
Trusted deployment jobs
```

and ensure privileged workflows only run after appropriate controls.

# Question 44: Why can pipeline YAML itself be security-sensitive?

## Interview Answer

Because changing the pipeline definition can change what commands execute and what credentials are used.

For example:

```yaml
steps:
  - run: deploy-production.sh
```

could be changed to:

```yaml
steps:
  - run: printenv
```

If the job has production secrets, that is a security problem.

Pipeline configuration should receive the same review and protection as application code, often more.

# Question 45: A pipeline occasionally fails while pulling dependencies from the internet. What would you do?

## Interview Answer

I would distinguish:

```text
External availability issue
```

from:

```text
Local runner issue
```

I would collect:

* DNS result
* Connection time
* HTTP status
* Repository mirror health
* Runner region
* Failure frequency
* Dependency registry status

Possible improvements include:

* Dependency caching
* Internal mirrors
* Retry with bounded backoff
* Pinned dependencies
* Better timeout behavior

But I would avoid infinite retries.

If the external repository is down, retrying every second from 500 runners can make things worse.

# Question 46: What is a good retry policy in a pipeline?

## Interview Answer

Retries should be used for failures that are plausibly transient.

Examples:

```text
Temporary network error
Temporary registry 503
Transient cloud API throttling
```

They should not be used to hide deterministic failures such as:

```text
Compilation error
Failed unit test
Invalid manifest
Missing variable
```

A useful retry policy includes:

```text
Limited attempts
Backoff
Jitter where useful
Specific retry conditions
```

I want to know:

```text
Why are we retrying?
```

not simply:

```text
Retry everything three times.
```

---

# Question 47: What is the danger of rerunning an entire pipeline when only deployment failed?

## Interview Answer

If the build stage is rerun, I may create a different artifact.

For example:

```text
First pipeline:
artifact sha256:AAA
deployment fails

Retry pipeline:
artifact sha256:BBB
deployment succeeds
```

Now I did not deploy the same artifact that originally passed earlier tests.

A stronger architecture supports restarting from the failed stage using the already-built artifact.

For example:

```text
Build once
    |
    v
Artifact A
    |
    +----> staging
    |
    +----> retry production deployment
```

This is another benefit of artifact promotion.

# Question 48: How do feature flags affect CI/CD design?

## Interview Answer

Feature flags separate code deployment from feature activation.

For example:

```text
Deploy code
with new feature disabled
      |
      v
Verify production health
      |
      v
Enable feature for 5%
      |
      v
Observe
      |
      v
Increase rollout
```

This can reduce deployment risk.

But feature flags introduce operational complexity.

They need:

* Ownership
* Expiration
* Audit
* Testing
* Cleanup
* Safe defaults

Old flags left forever can make code paths difficult to understand.

# Question 49: What is a pipeline rollback versus application rollback?

## Interview Answer

Pipeline rollback means the deployment process restores a previous desired release state.

Application rollback refers to returning the running application to a previous version.

They may be implemented differently.

For example:

```text
GitOps:

Revert image tag in Git
      |
      v
Controller reconciles
      |
      v
Old version restored
```

Versus:

```text
Deployment platform:

Promote previous image directly
      |
      v
Production restored
```

The pipeline architecture should define the authoritative rollback mechanism.

# Question 50: What is the biggest mistake teams make when trying to make pipelines faster?

## Interview Answer

Treating safety controls as wasted time.

For example:

```text
Tests are slow -> remove tests
Security scan slow -> skip scan
Approval slow -> bypass approval
Verification slow -> remove verification
```

That may improve:

```text
pipeline duration
```

while degrading:

```text
release reliability
```

The better question is:

```text
Why is this stage slow,
and how do we preserve its value
while reducing unnecessary work?
```

Architecture:

```text

 |
 v

 |
 v

 v

 |
 v

 v

 v

 |
 v

 v

 |
 v

 |
 v
Application
 |
 +----> Database
 |
 +----> Redis
 |
 +----> External API
```

Timeline:

```text
13:00 merge completed
13:02 pipeline started
13:12 build completed
13:20 staging deployment completed
13:25 staging tests passed
13:30 production approved
13:33 production deployment completed
13:36 HTTP 5xx rises to 18%
```

How do you proceed?

## Interview Answer

First I establish the production artifact.

I want:

```text
Git commit

Pipeline run
Deployment version
```

Suppose:

```text

a81f221
```

I confirm staging used exactly:

```text
sha256:ABC
```

---

## Step 1: Determine scope

I ask:

```text
All users?

One endpoint?

One AZ?

Only new Pods?

Only certain requests?
```

Suppose:

```text
Old Pods:
healthy

New Pods:
intermittent errors
```

Now the release is strongly implicated.

---

## Step 2: Correlate with application behavior

New Pod logs show:

```text
connection timeout to Redis
```

But only some Pods fail.

I compare configuration.

Suppose production Deployment accidentally injects:

```text
REDIS_TIMEOUT=100ms
```

while staging uses:

```text
REDIS_TIMEOUT=1000ms
```

Now I have discovered that the artifact was identical but environment-specific configuration was not.

This is exactly why configuration should be versioned, validated, and tested as part of release promotion.

---

## Step 3: Mitigate

If the old version/configuration is known good, I may:

```text
Stop rollout
Restore previous configuration
or
Rollback deployment
```

depending on the safest option.

I would avoid rebuilding unnecessarily.

The artifact itself may be fine.

---

## Step 4: Verify

I monitor:

```text
HTTP 5xx
Latency
Redis timeout errors
Pod readiness
Business transactions
```

Suppose:

```text
5xx:
18% -> 0.3%

p95:
3.8s -> 220ms
```

Now the mitigation is working.

---

## Step 5: Investigate why staging did not catch it

The pipeline used:

```text
Staging config
```

and:

```text
Production config
```

but had no configuration validation between environments.

The release gate proved the code artifact.

It did not prove production-specific configuration.

Corrective actions could include:

* Validate config schema.
* Compare required keys.
* Test production-like configuration patterns.
* Version environment configuration.
* Add deployment-time validation.
* Add post-deployment synthetic tests.
* Improve canary rollout.

## Interview Answer

Not if the artifact is unchanged.

If:

```text
sha256:ABC
```

already passed the build and tests, and the defect is solely deployment configuration, I would prefer correcting the configuration and redeploying the same artifact.

Rebuilding unnecessarily introduces another variable.

The strongest recovery changes the smallest necessary thing.

# Interviewer Follow-Up: Would you disable production approvals because the bad release was approved?

No.

The failure does not automatically prove approvals are useless.

```text
Was the approval evaluating the right risks?
```

If the issue was production-specific configuration that no pre-production check validated, the stronger improvement is to improve the evidence and validation before approval.

Not removing the security scan.

# Mid-Level CI/CD Troubleshooting Framework

When a pipeline fails, think in this order:

```text
1. TRIGGER

      |
      v

2. SOURCE

Which exact commit?

      |
      v

3. STAGE

Where did failure occur?

      |
      v

4. RUNNER

Which agent/environment?

      |
      v

5. INPUTS

Dependencies?
Secrets?
Configuration?
Tool versions?

      |
      v

6. ARTIFACT

Was it built successfully?
What is its immutable identity?

      |
      v

7. ENVIRONMENT

Which environment failed?

      |
      v

8. DEPLOYMENT

Did deployment complete technically?

      |
      v

9. SERVICE HEALTH

Did the application actually work?

      |
      v

10. RECOVERY

Retry?
Rollback?
Roll forward?
Stop rollout?

      |
      v

11. VERIFY

Did customer behavior recover?

      |
      v

12. PREVENT

How do we make this failure
less likely or easier to detect?
```

Owning CI/CD means more than writing pipeline YAML.

You should be able to reason about the complete delivery path:

```text
SOURCE
   |
   v

   |
   v
TEST
   |
   v
SECURITY
   |
   v
ARTIFACT
   |
   v
PROMOTION
   |
   v
DEPLOYMENT
   |
   v
VERIFICATION
   |
   v
OBSERVABILITY
   |
   v
RECOVERY
```

A strong mid-level DevOps engineer knows how to make that path:

```text

Reproducible
Secure
Observable
Recoverable
```

without sacrificing one simply to improve another.

The goal is not to create a pipeline that turns green quickly.

The goal is to create a delivery system the engineering team can trust.
