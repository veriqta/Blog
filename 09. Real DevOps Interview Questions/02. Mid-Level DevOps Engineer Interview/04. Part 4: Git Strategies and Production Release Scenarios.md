# Part 4: Git Strategies and Production Release Scenarios

At mid-level, Git interview questions should not ask whether you know `git add`, `git commit`, or `git push`.

The interviewer should assume you already know how Git works at a basic level.

What they want to know is whether you can use Git safely when:

* Multiple engineers are changing the same codebase.
* Production needs an emergency fix.
* A bad merge reaches `main`.
* Release history becomes difficult to understand.
* A hotfix must reach several branches.
* Teams disagree on rebase versus merge.
* A secret appears in repository history.
* Protected branches slow an urgent release.
* A release tag points to the wrong commit.
* Git becomes part of the deployment process.

The questions should test judgment.

A useful mental model is:

```text
Change created
    |
    v
Review
    |
    v
Integrate
    |
    v
Release
    |
    v
Deploy
    |
    v
Observe
    |
    +---- healthy ----> continue
    |
    +---- broken -----> revert / hotfix / rollback
```

Git is not just a source-control tool in production environments.

It is often part of the change-management and release-control system.

---

# Question 1: When would you choose merge over rebase?

## Interview Answer

I would choose based on what history I need to preserve and whether the commits are already shared.

A merge preserves the existing branch histories and creates an explicit integration point.

For example:

```text
main

A---B---C
     \
      D---E
           \
            M
```

The merge commit `M` clearly records that the feature branch was integrated.

That can be useful when:

* The branch has already been shared.
* Several engineers worked on it.
* I want to preserve branch context.
* The organization values explicit integration history.
* Rewriting commit hashes would create unnecessary coordination risk.

I would be cautious about rebasing commits that other people are already using.

The important operational principle is:

```text
Public/shared history
should not be casually rewritten.
```

Merge is often the safer choice once commits are widely shared.

---

# Question 2: When would you choose rebase over merge?

## Interview Answer

I might use rebase to update my private or controlled feature branch with the latest target branch while keeping a cleaner linear history.

Suppose:

```text
main:

A---B---C

feature:

A---B---D---E
```

Meanwhile `main` receives `C`.

I could rebase:

```bash
git checkout feature
git rebase main
```

Conceptually:

```text
A---B---C---D'---E'
```

The feature commits are replayed on top of the current `main`.

This can make review easier because the feature appears as if it was developed from the current base.

But rebase changes commit hashes.

So I generally prefer it when:

* The branch is mine.
* The commits are not broadly shared.
* I understand the conflict implications.
* The team workflow allows it.

The key rule is not:

```text
Rebase is better than merge.
```

It is:

```text
Use rebase intentionally
when rewriting that history is safe.
```

---

# Question 3: Why can rebasing a shared branch create problems?

## Interview Answer

Because rebase rewrites commit history.

Suppose two developers share:

```text
A---B---C
```

Developer A rebases and creates:

```text
A---B'---C'
```

Developer B may still have references to the old:

```text
B
C
```

Now Git sees two histories that represent similar logical work but have different commit IDs.

This can lead to:

* Duplicate-looking commits.
* Complicated merges.
* Force pushes.
* Confusion during incident investigation.
* Difficulty determining what actually shipped.

This becomes particularly dangerous if the shared branch is used for release automation.

I would avoid history rewriting on release branches or protected shared branches unless the workflow explicitly expects it.

---

# Question 4: Your team requires a clean commit history. Does that mean you should rebase everything?

## Interview Answer

No.

A clean history is useful, but "clean" should not mean rewriting production-relevant history carelessly.

There are multiple ways to maintain understandable history:

* Rebase private branches before integration.
* Squash merge.
* Merge with meaningful merge commits.
* Enforce commit conventions.
* Remove noisy temporary commits before review.

For example, a feature branch may contain:

```text
fix typo
fix tests
try again
more fixes
actual feature
```

Before integration, the team may squash that into a meaningful commit.

But once the commit is used for a production release, preserving traceability can be more important than making the graph aesthetically perfect.

Production history is an audit trail.

---

# Question 5: A bad merge has already landed on `main`. What do you do?

## Interview Answer

I first determine whether the merge has been deployed.

If it has not been deployed, I have more flexibility.

If it is already in production, I treat this as a release incident rather than merely a Git cleanup task.

I would identify the merge commit:

```bash
git log --oneline --graph
```

Suppose:

```text
9f2c011 Merge feature/payment-refactor
```

If reverting is appropriate:

```bash
git revert -m 1 9f2c011
```

For a merge commit, the `-m` option tells Git which parent should be considered the mainline.

I would not run that blindly.

I would verify:

* Which parent represents the branch we want to preserve?
* Has additional work landed after the merge?
* Does the merge include database changes?
* Will the revert itself conflict?
* Does production need immediate rollback instead of waiting for Git remediation?

Git recovery and production recovery are related but not identical.

---

# Question 6: Why would you use `git revert` instead of `git reset` for a production branch?

## Interview Answer

Because `git revert` creates a new commit that reverses the effects of an earlier commit.

It preserves shared history.

For example:

```text
A---B---C---D
            |
          bad change
```

After:

```bash
git revert D
```

history becomes:

```text
A---B---C---D---R
```

where `R` reverses `D`.

This is generally much safer for shared or protected branches.

By contrast:

```bash
git reset --hard C
```

moves the branch pointer backward.

If followed by a force push, it rewrites shared branch history.

For a production branch, that can disrupt:

* CI/CD references.
* Other developers.
* Tags.
* Release automation.
* Auditability.

So my default for already-shared production history is:

```text
Revert, don't erase.
```

---

# Question 7: When might `git reset` still be appropriate?

## Interview Answer

For local or unshared work.

For example, if I made three local commits and realize they should not exist:

```bash
git reset --hard HEAD~3
```

may be reasonable if those commits were never pushed or shared.

I would distinguish:

```text
Local history cleanup
```

from:

```text
Shared production history modification
```

The command is not inherently dangerous.

Its risk depends on where the history is already being consumed.

---

# Question 8: A production deployment from commit `abc123` is broken. Do you revert Git first or rollback production first?

## Interview Answer

If customers are significantly affected, production recovery usually comes first.

For example:

```text
Production v7.4.0
        |
        X
        |
Rollback to known-good v7.3.8
```

Then I would correct source-control history so that future deployments do not reintroduce the broken state.

The order may be:

```text
Incident confirmed
      |
      v
Rollback deployed artifact
      |
      v
Verify recovery
      |
      v
Revert bad source change
      |
      v
Run pipeline
      |
      v
Prepare corrected release
```

I do not want to wait ten minutes for CI/CD to build a revert if the deployment platform can safely restore a known-good artifact immediately.

Source control is the desired state.

Production recovery may need to happen faster.

---

# Question 9: What is the danger of rolling production back without updating Git?

## Interview Answer

Git and production become inconsistent.

Suppose:

```text
Git main:
v7.4.0 broken code

Production:
v7.3.8 rollback
```

If the next engineer sees `main` and runs the normal deployment pipeline, the broken version may return.

This creates configuration or release drift.

After emergency rollback, I want the repository and release process to reflect the intended state.

The rule is:

```text
Emergency operational change
must eventually be reconciled
with source-controlled desired state.
```

---

# Question 10: What is cherry-picking, and when is it useful during an emergency fix?

## Interview Answer

Cherry-picking applies the changes introduced by a specific commit onto another branch.

For example:

```text
main
A---B---C---D

release/2.4
A---B---R
```

Suppose commit `D` contains a critical security fix that also needs to reach `release/2.4`.

I could:

```bash
git checkout release/2.4
git cherry-pick <commit-D>
```

This creates a new commit on the release branch containing the equivalent change.

Cherry-picking is useful when:

* A specific fix must move between branches.
* I do not want to merge all changes from another branch.
* A production hotfix needs to reach multiple maintained versions.

But I use it carefully because the same logical change now exists under different commit hashes.

That can complicate later merging if not managed properly.

---

# Question 11: What can go wrong when cherry-picking the same hotfix into multiple branches?

## Interview Answer

The branches may have diverged.

A patch that applies cleanly to:

```text
main
```

may conflict or behave differently in:

```text
release/2.3
```

because surrounding code changed.

Even if Git applies the patch cleanly, that does not prove the fix is functionally safe.

I would run branch-specific tests.

The process should be:

```text
Identify minimal fix
      |
      v
Apply to branch
      |
      v
Resolve conflicts carefully
      |
      v
Run tests
      |
      v
Build release artifact
      |
      v
Deploy safely
```

Emergency speed should not eliminate validation.

---

# Question 12: What is a release branch, and when would you use one?

## Interview Answer

A release branch is typically used to stabilize a specific version while development continues elsewhere.

For example:

```text
main
 |
 +----> future development

release/4.2
 |
 +----> stabilization
       bug fixes
       release-specific changes
```

It can be useful when:

* Release testing takes time.
* Multiple versions must be supported.
* Production stabilization must be isolated from new features.
* The organization has a scheduled release process.

But release branches introduce coordination overhead.

Fixes may need to move in both directions:

```text
release fix
   |
   +----> release/4.2
   |
   +----> main
```

If teams forget the second step, the same bug may reappear in a later release.

---

# Question 13: What problem occurs when a hotfix is applied only to the production release branch?

## Interview Answer

The next mainline release may not contain it.

For example:

```text
release/4.2
    |
    +--- hotfix H

main
    |
    +--- feature work
```

Production is fixed.

Three weeks later, `main` becomes version 4.3.

If hotfix `H` never reached `main`, the bug can return.

A mature hotfix workflow includes reconciliation.

For example:

```text
Hotfix branch
     |
     +----> production release branch
     |
     +----> main
```

or an equivalent process appropriate to the team's branching model.

---

# Question 14: What is trunk-based development?

## Interview Answer

Trunk-based development emphasizes frequent integration into a primary branch, usually with short-lived feature branches or direct commits under strong controls.

Conceptually:

```text
main
 |
 +-- small change
 |
 +-- small change
 |
 +-- small change
 |
 +-- release
```

Instead of maintaining long-lived branches:

```text
feature-A 3 months
feature-B 2 months
release-X 6 weeks
```

changes are integrated more frequently.

This can reduce large integration conflicts and support continuous delivery.

But it requires engineering practices such as:

* Strong automated testing.
* Small changes.
* Feature flags.
* Fast code review.
* Reliable CI.
* Good rollback.
* Branch protection.

Trunk-based development is not:

```text
"Everyone pushes anything directly to main."
```

It is a workflow that depends on strong controls.

---

# Question 15: What are the advantages of trunk-based development?

## Interview Answer

Potential advantages include:

* Smaller integration changes.
* Less long-lived branch divergence.
* Faster feedback.
* Easier continuous delivery.
* Reduced merge complexity.
* More frequent integration testing.

A long-lived feature branch may accumulate:

```text
500 changed files
90 commits
multiple months of divergence
```

and then become difficult to merge.

A trunk-based approach tries to integrate work incrementally.

However, the model works best when incomplete functionality can be hidden safely, often using feature flags or similar mechanisms.

---

# Question 16: What risks come with trunk-based development?

## Interview Answer

Because changes reach the shared branch frequently, weak controls can quickly affect everyone.

Risks include:

* Broken `main`.
* Incomplete features leaking.
* Insufficient review.
* Poorly designed feature flags.
* Too much trust in weak tests.
* Frequent deployment of regressions.

So trunk-based development requires strong:

```text
CI
Review
Testing
Feature isolation
Observability
Rollback
```

The branching model itself does not create safety.

The engineering system around it does.

---

# Question 17: Explain GitFlow and its trade-offs.

## Interview Answer

GitFlow typically uses multiple long-lived branch types, such as:

```text
main
develop
feature/*
release/*
hotfix/*
```

A simplified lifecycle might be:

```text
feature
   |
   v
develop
   |
   v
release
   |
   v
main
```

and urgent production fixes:

```text
main
 |
 v
hotfix
 |
 +----> main
 |
 +----> develop
```

Potential advantages include:

* Clear release separation.
* Structured hotfix workflow.
* Support for scheduled releases.
* Multiple stabilization phases.

Trade-offs include:

* More merge complexity.
* Long-lived divergence.
* More branch management.
* Slower continuous delivery.
* Greater risk of fixes being forgotten across branches.

GitFlow can be appropriate for some release models, but it is not automatically ideal for teams doing frequent production deployments.

---

# Question 18: Trunk-based development or GitFlow, which would you choose?

## Interview Answer

I would ask about the release model first.

If the organization deploys continuously or many times per day, trunk-based development often aligns well with that workflow.

If the organization maintains multiple supported versions with lengthy stabilization and scheduled releases, release branches or a GitFlow-like model may be useful.

I would evaluate:

```text
Deployment frequency
Release cadence
Number of supported versions
Team size
Testing maturity
Feature flag capability
Compliance requirements
Rollback model
```

The mistake is selecting a branching strategy based on popularity rather than operational needs.

---

# Question 19: How would you manage an emergency production hotfix?

## Interview Answer

I would first determine whether the immediate production issue can be mitigated by rollback or configuration change.

If code must be fixed urgently, I want the smallest possible change.

A possible workflow:

```text
Known production commit
        |
        v
Create hotfix branch
        |
        v
Implement minimal fix
        |
        v
Focused tests
        |
        v
Review
        |
        v
Build artifact
        |
        v
Deploy controlled hotfix
        |
        v
Verify
        |
        v
Merge fix back into required branches
```

For example:

```bash
git checkout -b hotfix/payment-timeout
```

The hotfix should not become an excuse to include unrelated cleanup.

Avoid:

```text
Critical payment fix
+
Dependency upgrade
+
Refactor
+
Formatting
```

in one emergency change.

Small blast radius matters.

---

# Question 20: Why should hotfixes be small?

## Interview Answer

Because emergency production changes carry high risk.

A small hotfix is easier to:

* Review.
* Test.
* Understand.
* Revert.
* Attribute.
* Compare with production behavior.

If a one-line configuration validation bug can be fixed with a small patch, I do not want the same emergency release to contain a 1,500-line refactor.

The operational principle is:

```text
During incidents,
minimize change surface.
```

---

# Question 21: What are protected branches?

## Interview Answer

Protected branches apply controls to critical branches such as `main`.

Possible protections include:

* No direct pushes.
* Required pull requests.
* Required reviews.
* Required CI checks.
* Signed commits.
* Restricted force pushes.
* Restricted deletion.
* Required status checks.
* Deployment approval integration.

The objective is not bureaucracy.

It is to prevent high-impact changes from bypassing the normal safety mechanisms.

For example:

```text
Developer
   |
   v
Pull Request
   |
   v
Review
   |
   v
CI Checks
   |
   v
Merge
   |
   v
Release
```

---

# Question 22: Production is down, but branch protection requires two reviewers. Do you bypass protection?

## Interview Answer

I would follow the organization's emergency change process.

If there is a documented break-glass mechanism for urgent incidents, that may allow faster approval under controlled conditions.

I would not casually disable branch protection globally.

A good emergency process might provide:

```text
Incident declared
     |
     v
Emergency reviewer
     |
     v
Minimal hotfix
     |
     v
Audit trail
     |
     v
Post-incident review
```

The tension is real:

```text
Speed
versus
Change safety
```

A mature organization designs an emergency workflow before the outage occurs.

---

# Question 23: Why is allowing force pushes to `main` dangerous?

## Interview Answer

Because force pushing can rewrite the branch's visible history.

That can disrupt:

* Pull requests.
* Release references.
* CI builds.
* Deployment automation.
* Audit trails.
* Other developers' clones.

Suppose production release `v5.2.0` came from:

```text
commit ABC
```

and history is rewritten so that branch references move away from that structure.

Investigating how the release was created can become harder.

For critical branches, I generally want history to be append-oriented.

# Question 24: Commit history contains hundreds of meaningless commits. Why is this an operational problem?

## Interview Answer

Because Git history is often used during production investigation.

Suppose I run:

```bash
git log --oneline
```

and see:

```text
fix
fix again
test
oops
try again
final
really final
another fix
```

That makes it harder to understand what changed.

During an incident, I may need to answer:

```text
Which change introduced this behavior?

Why was this configuration changed?

Which release contains the fix?
```

Clear commits improve:

* Review.
* `git bisect`.
* Root-cause analysis.
* Reverts.
* Release notes.
* Auditability.

Commit quality becomes an operational capability.

---

# Question 25: What makes a good production-relevant commit?

## Interview Answer

A good commit should represent a coherent change.

It should have:

* Clear purpose.
* Understandable message.
* Minimal unrelated changes.
* Tests where appropriate.
* Traceability to issue or change request where required.

For example:

```text
fix(checkout): restore connection timeout to 5s
```

is more useful than:

```text
changes
```

The message should help an engineer six months later understand why the change exists.

---

# Question 26: How would you use `git bisect` during a regression investigation?

## Interview Answer

`git bisect` helps find the commit that introduced a behavior using binary search.

Suppose:

```text
v5.1 works
v5.8 fails
```

I could start:

```bash
git bisect start
git bisect bad v5.8
git bisect good v5.1
```

Git checks out commits between them.

For each candidate commit, I test:

```text
Good
or
Bad
```

Git progressively narrows the range.

This is especially powerful if the test can be automated.

For example:

```bash
git bisect run ./test-regression.sh
```

But I would use it in a reproducible test environment rather than repeatedly changing production.

---

# Question 27: Why is `git bisect` easier when commits are small and coherent?

## Interview Answer

Because one commit should ideally represent one logical change.

If commit `X` contains:

```text
New payment logic
Database migration
Nginx config
Dependency upgrades
Refactoring
```

and `git bisect` identifies `X`, I still have a large investigation.

If the commits are separated logically:

```text
Commit 1: payment timeout
Commit 2: logging
Commit 3: dependency bump
Commit 4: proxy config
```

the identified regression point becomes much more useful.

Good Git hygiene improves debugging.

---

# Question 28: How would you handle a repository that has become extremely large?

## Interview Answer

First I would understand why.

Large repositories can come from:

* Binary artifacts.
* Videos.
* Generated files.
* Vendor dependencies.
* Large logs.
* Database dumps.
* Accidental secrets or archives.
* Long history with deleted large files.

I would inspect repository size and history.

Potential improvements may include:

* Git LFS for appropriate large binary files.
* Moving build artifacts to artifact storage.
* Cleaning accidental large blobs from history.
* Better `.gitignore`.
* Shallow clones for some CI use cases.
* Sparse checkout where appropriate.
* Repository restructuring if justified.

I would avoid simply deleting a large file in the latest commit if it exists throughout history.

The object may still remain in Git history.

---

# Question 29: Why should CI build artifacts not normally be committed into Git?

## Interview Answer

Because source control and artifact storage solve different problems.

Git should generally store the source and configuration required to build the artifact.

Built binaries should normally go into:

```text
Artifact repository
Container registry
Package registry
Object storage
```

Committing generated artifacts can cause:

* Repository growth.
* Merge conflicts.
* Duplicate data.
* Unclear source-to-artifact relationships.
* Slow clones.

A stronger pattern is:

```text
Git commit
    |
    v
CI build
    |
    v
Immutable artifact
    |
    v
Artifact registry
```

Then the artifact can be promoted through environments.

---

# Question 30: A secret was committed six months ago and removed one commit later. Is it still a problem?

## Interview Answer

Yes.

If the secret existed in Git history, anyone with access to that history may still recover it.

The first response is not history cleanup.

The first response is credential containment.

I would:

```text
1. Treat secret as compromised
2. Revoke or rotate it
3. Determine exposure scope
4. Review audit logs
5. Remove historical secret if required
6. Add prevention controls
```

The critical point is:

```text
History cleanup
does not revoke credentials.
```

A secret becomes safe because it is no longer valid, not because it becomes harder to find.

---

# Question 31: How would you remove sensitive data from Git history?

## Interview Answer

If organizational requirements call for rewriting the history, I would use an appropriate history-rewriting tool and carefully coordinate the change.

Examples may include:

```text
git filter-repo
```

or other approved repository tooling.

This operation is disruptive because historical commit IDs change.

After rewriting, teams may need to:

* Force update remote branches.
* Re-clone repositories.
* Recreate references.
* Check forks.
* Review cached copies.
* Invalidate credentials regardless.

I would treat it as a coordinated repository migration, not a casual command.

And again:

```text
Rotate first.
Rewrite second.
```

# Question 32: What is secret scanning, and where would you implement it?

## Interview Answer

Secret scanning attempts to identify credentials or secret-like values entering source control.

I would consider controls at several points:

```text
Developer workstation
      |
      v
Pre-commit checks
      |
      v
Pull request scanning
      |
      v
CI scanning
      |
      v
Repository platform scanning
```

Defense in depth matters because one control may be bypassed.

But scanning is not perfect.

Good secret architecture should also reduce the likelihood that engineers handle long-lived credentials in the first place.

# Question 33: What is a release tag?

## Interview Answer

A release tag gives a stable reference to a specific commit associated with a release.

For example:

```text
v4.7.2
   |
   v
commit 7c218f3
```

This helps answer:

```text
Exactly which source version
produced this release?
```

That is important for:

* Rollback.
* Audit.
* Debugging.
* Release notes.
* Artifact traceability.

I prefer release tags to be immutable once published.

Changing what `v4.7.2` points to after production deployment destroys trust in that reference.

---

# Question 34: What is the difference between a Git tag and a branch?

## Interview Answer

A branch is a movable reference that usually advances as new commits are added.

A tag is typically used as a fixed reference to a particular commit.

For example:

```text
main
 |
 v
A---B---C---D
        ^
        |
      v2.4.0
```

`main` may later move to `E`.

The tag should still refer to `C`.

That makes the release reproducible.

---

# Question 35: A release tag was created on the wrong commit. What would you do?

## Interview Answer

I would first determine whether the tag has already been published or deployed.

If the tag has not left my local environment, correcting it is straightforward.

If it has already been used for release automation or production deployment, I would avoid silently moving it.

I would prefer creating a new corrected release identifier, for example:

```text
v4.5.1
```

rather than rewriting:

```text
v4.5.0
```

to point somewhere else.

Production release identifiers should be trustworthy.

If `v4.5.0` meant commit `ABC` yesterday, it should not mean commit `XYZ` tomorrow.

---

# Question 36: Should CI build the same tag more than once?

## Interview Answer

Ideally, release artifacts should be immutable.

A strong release process is:

```text
Git commit
    |
    v
Build once
    |
    v
Artifact digest
    |
    v
Test
    |
    v
Promote
```

If the same Git tag is rebuilt later using newer:

* Dependencies.
* Base images.
* Compiler versions.
* Build tools.

the output could differ.

That weakens reproducibility.

I prefer to associate a release tag with an immutable artifact identity, such as:

```text
Container image digest
Artifact checksum
Package version
```

# Question 38: What is dangerous about deploying directly from a developer branch?

## Interview Answer

Developer branches may:

* Change frequently.
* Be force-pushed.
* Contain unreviewed work.
* Be deleted.
* Have incomplete testing.
* Contain multiple unrelated commits.

Production should normally deploy from a controlled, reproducible source reference.

For example:

```text
Protected commit
Release tag
Approved main branch state
Immutable artifact
```

not:

```text
Whatever happens to be on
feature/ann-test today.
```

Production references need stability.

# Question 39: What is GitOps at a practical level?

## Interview Answer

At a practical level, GitOps uses Git as the source of truth for desired system state, with automated reconciliation applying that desired state.

For example:

```text
Git
 |
 v
Deployment manifest says:
replicas = 5
image = app:v7.3.1
 |
 v
GitOps Controller
 |
 v
Kubernetes
```

If the cluster differs from Git:

```text
Actual replicas = 3
```

the controller may reconcile it toward:

```text
Desired replicas = 5
```

depending on the tool and configuration.

This means emergency manual production changes must eventually be reflected in Git or they may be automatically reverted.

---

# Question 40: During an incident, an engineer manually edits a Kubernetes Deployment, but GitOps changes it back. Why?

## Interview Answer

Because the GitOps controller sees the manual change as drift from the declared desired state.

For example:

```text
Git:
image = v8.1

Manual cluster edit:
image = v8.0

Controller:
Git says v8.1
      |
      v
Restore v8.1
```

If the emergency mitigation is rollback to `v8.0`, the proper GitOps-aware action is to update the desired state in Git or temporarily manage reconciliation according to the organization's incident process.

Otherwise the automation may fight the responder.

This is why incident responders must understand the deployment model.

# Question 41: Two engineers are preparing different production changes at the same time. What risks exist?

## Interview Answer

Concurrent production changes make causality and rollback harder.

Suppose:

```text
Engineer A:
changes application timeout

Engineer B:
changes load-balancer configuration
```

Both deploy at 14:00.

At 14:05 latency increases.

Now:

```text
Which change caused it?
```

is harder to answer.

Other risks include:

* Merge conflicts.
* One change built on stale assumptions.
* One rollback undoing part of another change.
* Database migration conflicts.
* Configuration drift.
* Release-order dependency.

Production change coordination is therefore part of DevOps work.

## Interview Answer

The exact process depends on the organization, but I want clear visibility and ownership.

I would consider:

* Change queue.
* Deployment calendar.
* Release coordination channel.
* Automated environment locks.
* Clear ownership.
* Dependency identification.
* Deployment sequencing.
* Feature flags.
* Canary rollout.

# Question 43: Why is "one change at a time" useful during incidents?

## Interview Answer

Because simultaneous changes destroy evidence.

Suppose we have a production error and perform:

```text
Restart app
Change timeout
Modify firewall
Roll back code
Restart database
```

all within two minutes.

Then the system recovers.

We do not know why.

A stronger incident approach is:

```text
Hypothesis
   |
   v
One controlled change
   |
   v
Observe effect
   |
   v
Continue
```

The same reasoning applies to release coordination.

Controlled changes preserve causality.

# Question 44: How would you handle two pull requests that both modify the same production configuration?

## Interview Answer

I would determine whether the changes are logically compatible.

Suppose PR A changes:

```text
DB_POOL_SIZE=50
```

to:

```text
100
```

while PR B changes it to:

```text
200
```

A merge conflict may alert us.

But not all logical conflicts create Git conflicts.

For example:

PR A:

```text
timeout=30
```

PR B:

```text
retry_count=10
```

Git may merge them cleanly, but together they could create long-running retry behavior that overloads the system.

So code review needs to consider semantic interaction, not only whether Git reports conflict markers.

---

# Question 45: What is a semantic conflict?

## Interview Answer

A semantic conflict occurs when two changes merge successfully at the text level but create incorrect behavior together.

For example:

Engineer A:

```text
Increase retry attempts from 2 to 10.
```

Engineer B:

```text
Increase timeout from 5 seconds to 30 seconds.
```

Git sees different lines and merges them cleanly.

Production now potentially waits:

```text
10 retries x 30 seconds
```

under some failure conditions.

The code merged without a Git conflict.

The system behavior is still dangerous.

This is a critical mid-level distinction.

---

# Question 46: A revert causes another production issue. Why can that happen?

## Interview Answer

Because production changes may depend on later changes.

Suppose:

```text
Commit A
Introduces new config structure

Commit B
Uses new config structure

Commit C
Fixes unrelated bug
```

If I revert `A` while `B` remains, the application may break.

Similarly, database migrations may make old code incompatible.

Before reverting, I want to understand dependencies.

The question is:

```text
Can this change be reversed
independently?
```

not simply:

```text
Can Git generate a revert commit?
```

Git can syntactically revert something that is operationally unsafe to revert.

---

# Question 47: How should database migrations influence Git rollback strategy?

## Interview Answer

Database changes require special care.

Suppose release 7 introduces:

```text
DROP COLUMN legacy_status
```

and new code no longer uses it.

Rolling code back to release 6 may fail if release 6 expects that column.

This is why safer deployment patterns often use backward-compatible migrations.

For example:

```text
Step 1
Add new schema

Step 2
Deploy code supporting both

Step 3
Migrate data

Step 4
Switch behavior

Step 5
Remove old schema later
```

This makes rollback easier.

A Git revert does not automatically restore database state.

---

# Question 48: What is a release rollback plan?

## Interview Answer

A rollback plan defines how we return to a known-good state if the release fails.

It should answer:

```text
Which artifact is known good?

How do we restore it?

What happens to database changes?

What happens to configuration?

What happens to feature flags?

How long does rollback take?

How do we verify recovery?
```

A release should not enter production with the assumption:

```text
"We can just revert the commit."
```

That may be insufficient for stateful systems.

I want traceability from:

```text

     |
     v

     |
     v

     |
```

For example:

That makes incident analysis significantly easier.

# Question 50: What is the biggest mistake engineers make when treating Git as part of production operations?

## Interview Answer

Treating source-control operations as isolated developer actions.

A production Git action can trigger:

```text
Build
Deploy
Infrastructure change
Configuration reconciliation
Database migration
Release notification
```

For example:

```text

```

may automatically mean:

```text
Deploy to production.
```

That changes the risk of the merge.

The engineer should understand not just:

```text
What will this Git command do?
```

but:

```text
What automation will this Git event trigger?
```

# Production Scenario 1: Bad Merge Breaks Production

At 10:00:

```text
PR #1042 merged into main.
```

At 10:03:

```text
Deployment begins.
```

At 10:07:

```text
Checkout errors rise from 0.3% to 24%.
```

The merge contains five feature commits from a long-lived branch.

What do you do?

## Interview Answer

I would first prioritize production recovery.

I would identify the currently deployed artifact and previous known-good artifact.

If rollback is safe:

```text
v8.6.0
   |
   X
   |
Rollback
   |
   v
v8.5.3
```

Then verify:

```text
Checkout success
HTTP 5xx
Latency
Critical dependencies
```

After stabilization, I would determine which changes in the merge caused the problem.

Possible tools include:

```text
git log
git diff
git bisect
```

in a test environment.

If the entire merge should be undone, I could prepare a merge revert.

But I would ensure later commits do not depend on it.

The production rollback and Git correction should be coordinated.

# Production Scenario 2: Hotfix Applied to Wrong Branch

Production runs:

```text
release/4.7
```

An engineer fixes a severe issue on:

```text
main
```

CI passes.

Nothing changes in production.

Why?

## Interview Answer

Because production is not built from `main`.

The hotfix exists in a branch that the production release process does not consume.

I would:

```text
Identify hotfix commit
      |
      v
Apply to release/4.7
      |
      v
Test
      |
      v
Build release artifact
      |
      v
Deploy
      |
      v
Verify
```

Then make sure the fix remains in `main` as well.

This scenario tests whether the candidate understands the organization's release topology rather than assuming every branch maps directly to production.

# Production Scenario 3: Cherry-Pick Creates a Hidden Regression

Git reports:

```text

```

Production crashes after deployment.

Investigation shows the fix depends on a helper function introduced three weeks later on `main`.

The patch applied cleanly but was not semantically compatible with the older branch.

The lesson:

```text
Git applied successfully
!=
Release is valid.
```

Branch-specific testing is required.

# Final Production Simulation

## Question 51: A payment release fails during peak traffic. You discover three engineers merged changes into `main` within ten minutes. Walk through your response.

Timeline:

```text
14:00 PR #201 merged
14:03 PR #202 merged
14:06 PR #203 merged
14:08 production deployment completed
14:10 payment failures begin
```

Architecture:

```text
Git main
   |
   v
CI/CD
   |
   v
Container image
   |
   v
Kubernetes
   |
   v
Payment API
   |
   v
Database
```

How do you investigate?

## Interview Answer

I would first stabilize production.

### Step 1: Identify deployed artifact

I want the exact:

```text
Image digest
Git commit
Release tag
Deployment timestamp
```

Suppose production runs:

```text
commit:
9f88d12
```

That commit includes all three merged PRs.

---

### Step 2: Roll back if safe

If the previous artifact is known good:

```text
v9.8.1
```

and the current release:

```text
v9.9.0
```

is severely affecting payments, I would rollback while preserving incident evidence.

Then verify payment recovery.

---

### Step 3: Compare change set

I would inspect:

```bash
git diff <previous-good>..<failed-release>
```

and review the three PRs.

Suppose:

```text
PR #201
Logging change

PR #202
Payment retry increase

PR #203
HTTP timeout increase
```

None may look catastrophic independently.

But together:

```text
Retry count:
2 -> 8

Timeout:
5s -> 30s
```

This dramatically changes failure behavior.

---

### Step 4: Build causal chain

Suppose payment provider latency increased slightly during peak traffic.

Before:

```text
2 retries
x
5 seconds
```

After:

```text
8 retries
x
30 seconds
```

Now requests remain active much longer.

The application experiences:

```text
Long request duration
      |
      v
Worker saturation
      |
      v
Connection pool pressure
      |
      v
Payment latency
      |
      v
503 / 504 errors
```

The incident involved both external conditions and concurrent application changes.

---

### Step 5: Correct source state

After rollback, I would not leave `main` containing the unsafe release indefinitely.

I would revert or correct the responsible changes.

For example:

```text
Revert retry increase
Revert timeout increase
```

or prepare a corrected configuration.

---

### Step 6: Prevent recurrence

Corrective actions might include:

* Deployment serialization for high-risk payment changes.
* Configuration interaction tests.
* Canary rollout.
* Better release grouping.
* PR risk labels.
* Release change summary.
* Automated checks for dangerous timeout/retry combinations.
* Improved payment SLO monitoring.

The lesson is:

```text
Git conflict
!=
Only kind of change conflict.
```

Production systems can fail because independently valid changes interact badly.

# Git Commands a Mid-Level DevOps Engineer Should Understand

| Command                          | Production Use                                       |
| -------------------------------- | ---------------------------------------------------- |
| `git log --graph --oneline`      | Understand integration history                       |
| `git diff A..B`                  | Determine what changed between releases              |
| `git revert <commit>`            | Safely reverse shared changes                        |
| `git revert -m 1 <merge>`        | Revert a merge carefully                             |
| `git cherry-pick <commit>`       | Apply a specific fix elsewhere                       |
| `git rebase`                     | Rework private branch history                        |
| `git merge`                      | Integrate histories without rewriting shared commits |
| `git bisect`                     | Find a regression-causing commit                     |
| `git tag`                        | Create stable release references                     |
| `git show <commit>`              | Inspect a specific change                            |
| `git reflog`                     | Recover or inspect local reference movement          |
| `git branch --contains <commit>` | Determine which branches contain a change            |

The command is not the interview answer.

The judgment around when and why to use it is.
