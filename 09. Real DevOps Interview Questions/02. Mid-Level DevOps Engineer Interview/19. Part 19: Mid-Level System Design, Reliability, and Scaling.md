# Part 19: Mid-Level System Design, Reliability, and Scaling

At mid-level, system design is no longer about drawing:

```text
User -> Load Balancer -> Server -> Database
```

and calling it highly available.

The candidate should understand how architecture behaves when traffic grows, dependencies fail, an availability zone disappears, queues accumulate, databases saturate, and the business demands lower infrastructure cost.

The interviewer should repeatedly change the conditions.

A strong answer should survive questions such as:

```text
Now traffic increases 10x.

Now the database becomes unavailable.

Now one AZ fails.

Now your cache fails.

Now your queue has two million messages.

Now reduce infrastructure cost by 30%.
```

The goal is not to design an architecture that can never fail.

The goal is to design one where failures are anticipated, contained, detected, and recoverable.

---

# 1. Designing a Production Platform

## Question 1: Design a production platform for a customer-facing web application.

### Interview Answer

I would first clarify:

```text

Availability target
Latency requirements
Data consistency requirements
Read/write ratio
Geographic distribution
Security requirements
RTO
RPO
Expected growth
Budget
```

Without those constraints, there is no single correct architecture.

A starting architecture might be:

```text
                   USERS
                     |
                     v
                DNS / CDN
                     |
                     v
               LOAD BALANCER
                     |
          +----------+----------+
          |                     |
          v                     v
        AZ-A                  AZ-B
          |                     |
     Application           Application
      Instances             Instances
          |                     |
          +----------+----------+
                     |
          +----------+----------+
          |                     |
          v                     v
        CACHE                 QUEUE
          |                     |
          |                  WORKERS
          |                     |
          +----------+----------+
                     |
                     v
                  DATABASE
                     |
                     v
              READ REPLICAS
```

I would avoid unnecessary state in the application layer so instances can scale horizontally.

# 2. Multi-AZ Architecture

## Question 2: Why would you deploy across multiple availability zones?

### Interview Answer

To reduce dependence on one physical failure domain.

Instead of:

```text
Region
  |
  v
AZ-A
  |
  +-- Application
  +-- Database
  +-- Cache
```

I want critical services distributed where appropriate:

```text
               Region
                  |
        +---------+---------+
        |                   |
        v                   v
      AZ-A                AZ-B
        |                   |
      App A               App B
        |                   |
        +--------+----------+
                 |
                 v
           Multi-AZ Data
```

If AZ-A fails, traffic should have a path to healthy capacity.

But simply placing servers in two AZs does not automatically make the application resilient.

Dependencies must also be considered.

---

## Question 3: Now one AZ fails. What happens?

### Interview Answer

First, traffic should stop reaching unhealthy instances.

The load balancer or routing layer should direct traffic toward healthy capacity.

But the next question is:

```text
Can the remaining AZs
handle the additional traffic?
```

Suppose normal distribution is:

```text
AZ-A: 50%
AZ-B: 50%
```

If AZ-A disappears:

```text
AZ-B: 100%
```

AZ-B needs enough headroom or scaling capability to absorb the load.

Otherwise:

```text
AZ failure
    |
    v
Traffic shifts
    |
    v
Remaining capacity saturates
    |
    v
Regional outage
```

High availability requires capacity planning.

# 3. Failure Domains

## Question 4: What is a failure domain?

### Interview Answer

A failure domain is a group of components that may fail together because they share a dependency.

Examples include:

```text
Process
Host
Rack
Availability Zone
Region
Database cluster
Network path
Cloud account
External provider
```

A system may look distributed but still contain hidden shared failure domains.

For example:

```text
App A -> AZ-A
App B -> AZ-B
App C -> AZ-C
```

looks resilient.

But if all three depend on:

```text
One database
```

the database remains a shared failure domain.

# 4. Stateless Versus Stateful Workloads

## Question 5: Why are stateless application workloads easier to scale?

### Interview Answer

A stateless instance does not depend on unique local application state to serve the next request.

Therefore:

```text
Request
   |
   v
Load Balancer
   |
   +--> App 1
   +--> App 2
   +--> App 3
   +--> App 4
```

Any healthy instance can process the request.

This makes:

```text
Scaling
Replacement
Failover
Rolling deployment
```

much easier.

---

## Question 6: Where should application state go?

### Interview Answer

Depending on the type of state:

```text
Persistent relational data -> Database

Session state -> External session store
                 or appropriately designed tokens

Objects/files -> Object storage

Temporary shared data -> Cache

Asynchronous work -> Queue
```

I avoid storing important persistent data on ephemeral application instances.

# 5. Horizontal Scaling

## Question 7: Traffic increases from 10,000 requests per second to 100,000. What do you do?

### Interview Answer

I would not immediately say:

```text
Add 10x more servers.
```

First I determine where saturation occurs.

Check:

```text
Load balancer
Application
Cache
Database
Queue
External dependencies
Network
```

If the application layer is stateless and CPU-bound, horizontal scaling may work well.

But:

```text
10x App Instances
        |
        v
10x DB Connections
        |
        v
Database collapse
```

is possible.

Scaling one layer changes pressure on downstream layers.

## Question 8: What would you examine before horizontally scaling an application?

I would examine:

```text

Latency
Connection pools
Database capacity
Cache capacity
Queue capacity
External API limits
Startup time
Autoscaling signals
```

The bottleneck determines whether additional instances help.

# 7. Cache Failure

## Question 11: Your cache fails completely. What happens?

### Interview Answer

That depends heavily on architecture.

A dangerous design is:

```text
Cache fails
    |
    v
100% requests hit database
    |
    v
Database overload
    |
    v
Application outage
```

This is a cache stampede or dependency amplification scenario.

I would consider:

```text
Cache redundancy
Request coalescing
Rate limiting
Stale data where acceptable
Controlled fallback
Database protection
```

The database must not automatically receive unlimited fallback traffic.

---

## Question 12: Your Redis cluster disappears during peak traffic. What do you do?

### Interview Answer

### Minute 0 to 5

Confirm:

```text
Cache availability
Cache hit rate
Database QPS
Database latency
Application error rate
```

### Minute 5 to 10

Protect the database.

Potential actions:

```text
Rate limiting
Load shedding
Serving stale data
Disabling expensive features
Restoring cache capacity
```

### After stabilization

Determine why cache failure was able to threaten the primary database.

# 8. Queueing

## Question 13: Why introduce a queue?

### Interview Answer

Queues decouple producers from consumers.

Instead of:

```text
API
 |
 v
Slow Worker
```

I can use:

```text
API
 |
 v
QUEUE
 |
 +--> Worker 1
 +--> Worker 2
 +--> Worker 3
```

The API does not necessarily need to wait for asynchronous work to finish.

Queues also help absorb bursts.

---

## Question 14: Does a queue solve overload?

### Interview Answer

Not automatically.

A queue can delay the effect of overload.

Suppose:

```text
Producer:
20,000 msg/sec

Consumers:
15,000 msg/sec
```

Backlog grows:

```text
+5,000 msg/sec
```

The queue buys time.

It does not eliminate the capacity mismatch.

# 10. Backpressure

## Question 16: What is backpressure?

### Interview Answer

Backpressure prevents upstream components from overwhelming slower downstream systems.

Conceptually:

```text
Producer
   |
   | 100k/sec
   v
Consumer
   |
   | capacity 20k/sec
   v
Database
```

Without controls, the system may accumulate unlimited work.

Backpressure can involve:

```text
Queue limits
Rate limiting
Load shedding
Concurrency limits
Producer throttling
```

The goal is controlled overload rather than uncontrolled collapse.

# 13. Read Replicas

## Question 20: When are read replicas useful?

### Interview Answer

When significant workload is read-heavy and can tolerate replica behavior.

For example:

```text
                 PRIMARY
                /       \
               /         \
              v           v
        Read Replica  Read Replica
             |            |
             v            v
         Reporting      Search/API
```

This can move read traffic away from the writer.

---

## Question 21: What problem can replica lag create?

### Interview Answer

The application may write data to the primary and immediately read from a replica that has not received the change.

Example:

```text
WRITE:
Order = CREATED
      |
      v
Primary

Immediate READ
      |
      v
Replica

Result:
Order not found
```

Architecture must account for consistency requirements.

---

# 14. Connection Pooling

## Question 22: Why is connection pooling important?

### Interview Answer

Opening database connections has cost, and databases support finite concurrent connections.

Suppose:

```text
100 application Pods

100 connections each

= 10,000 potential DB connections
```

The database may not support that safely.

A connection pool limits and reuses connections.

---

## Question 23: Now traffic increases 10x. Should you increase the connection pool 10x?

### Interview Answer

Not automatically.

That could simply move overload into the database.

I consider:

```text
Database connection capacity
Query duration
Concurrency
Application instance count
Queueing behavior
```

Connection limits are often a protective boundary.

# 15. Circuit Breakers

## Question 24: What problem does a circuit breaker solve?

### Interview Answer

It prevents repeated calls to a dependency that is already failing.

Without one:

```text
Dependency fails
     |
     v
Requests continue
     |
     v
Timeout
     |
     v
Retry
     |
     v
More pressure
```

With a circuit breaker:

```text
Dependency unhealthy
      |
      v
Circuit opens
      |
      v
Calls fail fast
      |
      v
Dependency gets recovery time
```

# 17. Retry Storms

## Question 26: How does a retry storm happen?

### Interview Answer

Suppose:

```text
10,000 original requests
```

Each retries three times.

Potential attempts:

```text
40,000
```

Now imagine multiple service layers retry independently.

```text
Client retries
      |
      v
API retries
      |
      v
Service retries
      |
      v
Database/dependency
```

A small dependency failure can become massive internal traffic amplification.

---

## Question 27: How would you prevent retry storms?

### Interview Answer

I consider:

```text
Exponential backoff
Jitter
Retry limits
Circuit breakers
Retry budgets
Appropriate timeouts
Load shedding
Centralized retry responsibility
```

Retries must be treated as additional load.

# 18. Database Becomes Unavailable

## Question 28: Now the primary database becomes unavailable. What happens?

### Interview Answer

First, architecture determines whether automatic failover exists.

The application should not continuously hammer an unavailable database.

I want controlled behavior:

```text
Database unavailable
       |
       v
Failover / Detection
       |
       +--> Recover DB
       |
       +--> Degrade application
       |
       +--> Queue safe operations
       |
       +--> Reject unsafe operations
```

Not every request can necessarily continue.

---

## Question 29: Would you queue all database writes during the outage?

### Interview Answer

Not automatically.

I need to consider:

```text
Ordering
Idempotency
Durability
Maximum backlog
Replay behavior
Business semantics
Consistency
```

Queueing can turn an immediate outage into a delayed data integrity problem if replay is poorly designed.

# 19. Graceful Degradation

## Question 30: What is graceful degradation?

### Interview Answer

It means preserving important functionality when non-critical dependencies fail.

Example:

```text
Recommendation Engine
        X

Product browsing:
AVAILABLE

Checkout:
AVAILABLE

Recommendations:
UNAVAILABLE
```

A recommendation outage should not necessarily make the entire e-commerce platform unavailable.

---

## Question 31: Give another example.

### Interview Answer

Suppose analytics fails.

Poor design:

```text
Analytics unavailable
       |
       v
Checkout unavailable
```

Better design, where business requirements allow:

```text
Analytics unavailable
       |
       v
Buffer/drop non-critical telemetry
       |
       v
Checkout continues
```

Dependency criticality should influence architecture.

# 20. RTO and RPO

## Question 32: What is RTO?

### Interview Answer

RTO, Recovery Time Objective, describes how quickly a service must be restored after disruption.

Example:

```text
Failure:
10:00

RTO:
30 minutes

Target recovery:
by 10:30
```

---

## Question 33: What is RPO?

### Interview Answer

RPO, Recovery Point Objective, describes how much data loss is acceptable in time terms.

Example:

```text
RPO:
5 minutes
```

means recovery should aim to lose no more than approximately five minutes of data, according to the defined recovery design.

---

## Question 34: Why do RTO and RPO affect cost?

### Interview Answer

Because:

```text
Faster recovery
+
Less acceptable data loss
```

generally requires more infrastructure, replication, automation, and operational preparation.

For example:

```text
RTO = 24 hours
RPO = 24 hours
```

can often be supported more cheaply than:

```text
RTO = 1 minute
RPO ≈ 0
```

Reliability requirements have economic consequences.

# Final Takeaway

Mid-level system design is not about adding more services to an architecture diagram.

It is about understanding how the architecture behaves when assumptions stop being true.

A strong production design should answer:

```text
Can it scale?

Where is the state?

Where is the bottleneck?

What is the failure domain?

What happens at 10x traffic?

What happens when the database fails?

What happens when the cache fails?

What happens when an AZ fails?

What happens when queues grow?

How are dependencies protected?

How do we prevent retry storms?

How does the system degrade?

How quickly can it recover?

How much data can we lose?

Can we prove DR works?

How much spare capacity do we need?

What does reliability cost?

Where can cost be reduced safely?
```

The strongest mid-level candidate does not try to make every component infinitely scalable or impossible to fail.

They understand the trade-offs between:

```text
RELIABILITY
     |
     +-------- COST
     |
     +-------- COMPLEXITY
     |
     +-------- PERFORMANCE
     |
     +-------- CONSISTENCY
     |
     +-------- RECOVERY
```

And every time the interviewer says:

```text
"Now something fails."
```

the candidate should be able to explain what happens next, what they protect first, and why.
