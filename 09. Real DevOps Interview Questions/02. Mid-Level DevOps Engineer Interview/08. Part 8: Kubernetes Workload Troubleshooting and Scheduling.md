# Part 8: Kubernetes Workload Troubleshooting and Scheduling

At mid-level, Kubernetes interview questions should assume the candidate already understands Pods, Deployments, Services, and basic `kubectl` usage.

The interviewer should expect you to reason about why workloads fail, why Pods land on certain nodes, how resource controls affect runtime behavior, and how deployment policies interact with availability.

The focus is not:

```text
What is a Pod?
```

It is:

```text
Why is this workload unstable,
why did the scheduler place it here,
what is preventing rollout,
and what is the safest fix?
```

A useful mental model is:

```text
Workload Definition
      |
      v
Scheduler
      |
      v
Node Selection
      |
      v
Resource Admission
      |
      v
Container Startup
      |
      v
Readiness
      |
      v
Traffic
      |
      v
Runtime
      |
      +----> CPU
      +----> Memory
      +----> Storage
      +----> Dependencies
      +----> Sidecars
      |
      v
Termination / Restart / Eviction
```

At this level, troubleshooting means understanding where in that lifecycle the failure occurs.

# Question 1: A Pod is in `CrashLoopBackOff`. What does that actually mean?

## Interview Answer

`CrashLoopBackOff` means Kubernetes is repeatedly restarting a container that exits, then applying increasing delays between restart attempts.

It is not the root cause.

The real failure could be:

* Application crash
* Missing configuration
* Bad command
* Failed dependency
* Permission problem
* OOMKilled
* Probe-induced restart
* Volume issue
* Secret issue
* Runtime exception

I would begin with:

```bash
kubectl get pods
kubectl describe pod <pod>
```

Then inspect current and previous logs:

```bash
kubectl logs <pod>
kubectl logs <pod> --previous
```

If there are multiple containers:

```bash
kubectl logs <pod> -c <container>
kubectl logs <pod> -c <container> --previous
```

I would also inspect termination state:

```bash
kubectl get pod <pod> -o yaml
```

I want:

```text
Exit code
Reason
Signal
Restart count
Last termination
Events
```

The important point is:

```text
CrashLoopBackOff
=
restart behavior

not
root cause
```

# Question 2: A Pod keeps restarting, but application logs are empty. What would you investigate?

## Interview Answer

I would inspect container state rather than relying only on application logs.

For example:

```bash
kubectl describe pod <pod>
```

may show:

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
```

or:

```text
Reason: Error
Exit Code: 1
```

If there are no application logs, possible causes include:

* Process fails before logger initializes
* Entrypoint is invalid
* Binary missing
* Permission denied
* OOMKill
* Bad architecture
* Missing volume
* Init container failure

I would also inspect:

```bash
kubectl get events --sort-by=.lastTimestamp
```

and container configuration.

The absence of logs is itself evidence.

It may indicate the process never reached normal application startup.

# Question 3: How would you troubleshoot a complex `CrashLoopBackOff` where the application starts successfully for 60 seconds and then restarts?

## Interview Answer

If the container runs for a period before restarting, I would investigate what changes after startup.

Possible causes include:

* Liveness probe failure
* Memory growth
* Dependency timeout
* Background worker crash
* Configuration reload
* Health endpoint failure
* Sidecar interaction

I would inspect:

```bash
kubectl describe pod <pod>
```

and look for probe-related events.

Suppose:

```text
Liveness probe failed:
HTTP probe failed with statuscode: 500
```

Then I would test what the liveness endpoint actually checks.

If `/health` depends on a database, and a brief database slowdown returns 500, Kubernetes may restart an otherwise healthy application.

That can create:

```text
Database slowdown
      |
      v
Liveness fails
      |
      v
Container restarted
      |
      v
More cold starts
      |
      v
More load
```

A liveness probe should generally answer:

```text
Should this container be restarted?
```

not:

```text
Is every dependency perfectly healthy?
```

# Question 4: What is the difference between readiness and liveness from an operational perspective?

## Interview Answer

Readiness determines whether the Pod should receive traffic.

Liveness determines whether the container should be restarted.

Conceptually:

```text
READINESS FAILS

Pod continues running
but
traffic stops
```

versus:

```text
LIVENESS FAILS

Container restarted
```

This distinction is critical.

If a database becomes unavailable temporarily:

```text
Readiness failure
```

may be appropriate if the application cannot serve useful requests.

But using the same dependency-heavy check for liveness can cause every Pod to restart at once.

That can amplify an incident.

# Question 5: A container is `OOMKilled`. How do you investigate it at Kubernetes level?

## Interview Answer

I would confirm the termination reason:

```bash
kubectl describe pod <pod>
```

I would inspect resource configuration:

```bash
kubectl get pod <pod> -o yaml
```

For example:

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

Then correlate runtime usage.

I want to know:

* Normal memory
* Peak memory
* Limit
* Traffic
* Application version
* Cache behavior
* Heap configuration
* Sidecar usage

Suppose:

```text
Normal memory:
430 MiB

Peak:
600 MiB

Limit:
512 MiB
```

The OOM is expected under peak load.

But I would still ask whether:

```text
600 MiB
```

is legitimate or a regression.

Increasing memory may be correct.

It may also just hide a leak.

# Question 6: Why can a Pod be OOMKilled even when the node has lots of free memory?

## Interview Answer

Because the container's cgroup memory limit can be reached independently of node capacity.

For example:

```text
Node free memory:
20 GiB

Container limit:
512 MiB

Container usage:
650 MiB
```

The container can still be killed.

The effective boundary is the container limit.

This is why node-level memory alone is insufficient during container troubleshooting.

# Question 7: How would you distinguish container OOM from node memory pressure?

## Interview Answer

I would inspect both the container termination reason and node condition.

Container-level OOM may show:

```text
Reason: OOMKilled
```

while the node remains healthy.

Node pressure may show:

```bash
kubectl describe node <node>
```

with:

```text
MemoryPressure=True
```

and possibly eviction events.

Conceptually:

```text
Container OOM

One container exceeds its limit
```

versus:

```text
Node pressure

Entire node running out of memory
      |
      v
Kubelet begins evictions
```

The remediation is different.

# Question 8: What is CPU throttling in Kubernetes?

## Interview Answer

CPU limits are enforced using Linux cgroup scheduling mechanisms.

If a container tries to use more CPU than its limit permits, it can be throttled.

For example:

```yaml
resources:
  requests:
    cpu: "250m"
  limits:
    cpu: "500m"
```

The application may want:

```text
1.5 CPU
```

but be constrained to:

```text
0.5 CPU
```

Symptoms may include:

* Higher latency
* Slower startup
* Slow garbage collection
* Queue backlog
* Lower throughput

And importantly:

```text
Node CPU may still be low.
```

# Question 9: How would you detect CPU throttling?

## Interview Answer

I would use container-level metrics.

I would compare:

```text
CPU usage
CPU limit
CPU throttled time
Request latency
```

If the application repeatedly reaches its CPU limit and throttling increases while latency rises, that is strong evidence.

I would also inspect resource configuration.

The pattern might be:

```text
Traffic increases
      |
      v
App wants more CPU
      |
      v
CPU limit reached
      |
      v
Throttling
      |
      v
Latency increases
```

I would not immediately increase the limit before checking whether the application is inefficient or legitimately under-resourced.

# Question 10: What is the difference between resource requests and limits?

## Interview Answer

Requests influence scheduling.

Limits constrain runtime consumption.

For example:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    cpu: "1"
    memory: "2Gi"
```

The scheduler uses requests when deciding where the Pod can fit.

The runtime enforces limits.

So a Pod may request:

```text
500m CPU
```

but use up to:

```text
1 CPU
```

if available.

This means requests affect cluster packing and scheduling behavior.

Limits affect runtime behavior.

# Question 11: Why can incorrect requests create cluster inefficiency?

## Interview Answer

If requests are too high:

```text
Application uses:
200m CPU

Request:
4 CPU
```

the scheduler reserves capacity based on 4 CPUs.

Nodes may appear full from a scheduling perspective even though real usage is low.

This can cause:

```text
Pods Pending
+
low actual node utilization
```

If requests are too low, too many workloads may be packed onto one node.

Then actual usage can create contention.

Requests should reflect realistic expected workload.

# Question 12: A Pod is `Pending`. How do you investigate a scheduling failure?

## Interview Answer

I would begin with:

```bash
kubectl describe pod <pod>
```

The scheduler events are often the fastest source of truth.

For example:

```text
0/10 nodes are available:
6 Insufficient memory,
2 node(s) had untolerated taint,
2 node(s) didn't match Pod's node affinity.
```

This immediately tells me there may be multiple constraints.

I would inspect:

```text
Requests
Taints
Tolerations
Affinity
Node selectors
Topology constraints
Volumes
```

I would not assume every Pending Pod means the cluster needs more nodes.

# Question 13: What is the scheduler actually trying to satisfy?

## Interview Answer

It must find a node that satisfies the workload's hard requirements.

Examples include:

* Resource requests
* Node selector
* Required node affinity
* Taints/tolerations
* Volume topology
* Pod affinity/anti-affinity
* Topology spread constraints
* Scheduling policies

Conceptually:

```text
Pod
 |
 v
Candidate Nodes
 |
 +---- Node A insufficient CPU -> reject
 |
 +---- Node B untolerated taint -> reject
 |
 +---- Node C affinity mismatch -> reject
 |
 +---- Node D valid -> schedule
```

A Pod can be unschedulable even when the cluster has plenty of total resources.

The problem may be where those resources exist.

# Question 14: Explain taints and tolerations in production terms.

## Interview Answer

Taints repel Pods from nodes unless the Pod has an appropriate toleration.

For example:

```text
Node:
dedicated=gpu:NoSchedule
```

A normal workload without toleration cannot schedule there.

A Pod with:

```yaml
tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```

is allowed to be considered.

But toleration does not force the Pod onto that node.

It only removes the taint restriction.

That distinction matters.

# Question 15: What are common production uses for taints?

## Interview Answer

Examples include:

* Dedicated GPU nodes
* Production-only nodes
* Special hardware
* System-critical nodes
* Sensitive workloads
* Spot/preemptible separation
* Nodes undergoing certain conditions

The goal is to control which workloads may use specific node pools.

# Question 16: A Pod tolerates a taint but still schedules elsewhere. Why?

## Interview Answer

Because toleration is permission, not attraction.

If I want the Pod to prefer or require a specific node pool, I may also need:

```text
nodeSelector
```

or:

```text
nodeAffinity
```

Conceptually:

```text
Toleration:
You MAY enter.

Affinity:
You SHOULD or MUST go there.
```

# Question 17: What is node affinity?

## Interview Answer

Node affinity lets Pods express scheduling rules based on node labels.

For example:

```text
Nodes:

node-a
zone=us-east-1a
disk=ssd

node-b
zone=us-east-1b
disk=hdd
```

A workload requiring SSD might use required node affinity.

Conceptually:

```text
Pod
 |
 v
Requires disk=ssd
 |
 v
node-a
```

Affinity can be:

```text
requiredDuringSchedulingIgnoredDuringExecution
```

or:

```text
preferredDuringSchedulingIgnoredDuringExecution
```

Required rules are hard constraints.

Preferred rules are scoring preferences.

# Question 18: What problem can overly strict node affinity create?

## Interview Answer

It can make workloads unschedulable unnecessarily.

Suppose a cluster has 100 nodes, but affinity requires:

```text
node-type=payments-v2
```

and only two nodes have that label.

Now application capacity depends on two nodes even though plenty of general capacity exists.

This may create:

```text
Pending Pods
while
cluster has free CPU
```

Affinity should express genuine infrastructure requirements, not arbitrary preferences.

# Question 19: What is Pod anti-affinity?

## Interview Answer

Pod anti-affinity discourages or prevents related Pods from being placed together.

Suppose a Deployment has three replicas.

Without anti-affinity:

```text
Node A

Pod 1
Pod 2
Pod 3
```

Node A fails.

All replicas disappear.

With anti-affinity:

```text
Node A   Node B   Node C

Pod 1    Pod 2    Pod 3
```

This reduces correlated failure.

I would often use topology-based scheduling instead of hardcoding specific nodes.

# Question 20: Why can hard Pod anti-affinity cause scheduling problems?

## Interview Answer

Because it may become impossible to satisfy.

Suppose:

```text
Replicas:
10

Eligible nodes:
5

Required:
No two replicas may share a node
```

Only five can schedule.

The rest remain Pending.

The stricter the rule, the more scheduler flexibility is reduced.

I would decide whether:

```text
must not
```

or:

```text
prefer not
```

is the actual requirement.

# Question 21: What are topology spread constraints?

## Interview Answer

Topology spread constraints control how Pods are distributed across topology domains such as:

* Nodes
* Availability Zones
* Regions where applicable

For example:

```text
AZ-A: 3 Pods
AZ-B: 3 Pods
AZ-C: 3 Pods
```

is more balanced than:

```text
AZ-A: 7 Pods
AZ-B: 1 Pod
AZ-C: 1 Pod
```

A topology constraint might use:

```text
topology.kubernetes.io/zone
```

to spread replicas.

This improves resilience against larger failure domains.

# Question 22: Why are topology spread constraints often better than simple anti-affinity?

## Interview Answer

Because they can express distribution goals more flexibly.

Anti-affinity might say:

```text
Do not place two replicas together.
```

Topology spreading can say:

```text
Keep the replica count reasonably balanced
across zones.
```

That provides more scheduler flexibility.

It can improve both:

* Availability
* Scheduling success

when designed appropriately.

# Question 23: A Deployment has six replicas across three AZs. All six end up in one AZ. What would you change?

## Interview Answer

I would inspect current scheduling rules.

If no topology policy exists, the scheduler may legally place Pods based on available resources.

I could consider topology spread constraints using:

```text
topology.kubernetes.io/zone
```

or appropriate anti-affinity.

The goal could be approximately:

```text
AZ-A: 2
AZ-B: 2
AZ-C: 2
```

I would also make sure all three AZs have sufficient node capacity.

A scheduling policy cannot create capacity where none exists.

# Question 24: What is a PodDisruptionBudget?

## Interview Answer

A PodDisruptionBudget, PDB, limits disruption from voluntary operations.

Examples include:

* Node drain
* Cluster maintenance
* Node replacement

For example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 3
```

If the application has four replicas, voluntary eviction should preserve at least three where the PDB applies.

It protects availability during controlled disruptions.

It does not guarantee protection from:

* Node crash
* OOMKill
* Application crash
* Hardware failure

Those are involuntary failures.

# Question 25: How can a PDB block node maintenance?

## Interview Answer

Suppose:

```text
Application replicas:
3

PDB:
minAvailable: 3
```

Now Kubernetes cannot voluntarily evict any replica without violating the budget.

A node drain may stall.

You might see:

```text
Cannot evict pod as it would violate
the pod's disruption budget.
```

The PDB is technically working.

The problem is that its availability requirement leaves zero voluntary disruption capacity.

The fix may involve:

* Increasing replicas
* Adjusting PDB
* Changing maintenance plan

I would not simply delete the PDB without understanding why it exists.

# Question 26: What are Kubernetes QoS classes?

## Interview Answer

Kubernetes assigns Pods to QoS classes based on resource request and limit configuration.

The main classes are:

```text
Guaranteed
Burstable
BestEffort
```

Conceptually:

```text
Guaranteed
Strongest resource definition

Burstable
Some requests/limits defined

BestEffort
No requests or limits
```

These classes can influence eviction priority under node resource pressure.

A mid-level engineer should understand that resource configuration affects more than scheduling.

It also affects runtime resilience.

# Question 27: What makes a Pod `Guaranteed`?

## Interview Answer

For a Pod to be in the Guaranteed QoS class, every container must have CPU and memory requests and limits specified appropriately, with requests equal to limits for those resources.

Conceptually:

```yaml
requests:
  cpu: "1"
  memory: "1Gi"

limits:
  cpu: "1"
  memory: "1Gi"
```

for every container.

This provides a very explicit resource contract.

But that does not mean every application should automatically use equal requests and limits.

It depends on workload behavior.

# Question 28: Why might `BestEffort` Pods be evicted first?

## Interview Answer

Because they have made no explicit resource reservation.

During node pressure, Kubernetes needs a way to choose which workloads to reclaim first.

BestEffort workloads generally have weaker guarantees than Burstable or Guaranteed workloads.

This is why critical production services should not accidentally run with no resource configuration at all.

# Question 29: What is a Kubernetes eviction?

## Interview Answer

Eviction removes a Pod from a node, often because of:

* Node memory pressure
* Disk pressure
* PID pressure
* Node maintenance
* Policy-driven disruption

I would inspect:

```bash
kubectl describe node <node>
```

and:

```bash
kubectl describe pod <pod>
```

to understand why.

An eviction is different from an application crash.

The kubelet or control plane may be intentionally removing the workload due to node conditions.

# Question 30: A node has `DiskPressure=True`. What problems might that cause?

## Interview Answer

The kubelet may start evicting Pods or refuse scheduling depending on conditions and taints.

I would investigate:

* Container image storage
* Logs
* Writable layers
* EmptyDir volumes
* Node filesystem capacity
* Inodes

The causal chain might be:

```text
Container logs grow
      |
      v
Node filesystem fills
      |
      v
DiskPressure
      |
      v
Evictions
      |
      v
Application capacity drops
```

The root cause may be unbounded logs, not Kubernetes itself.

# Question 31: What is an init container?

## Interview Answer

An init container runs before the main application containers start.

Each init container must complete successfully before the next stage continues.

For example:

```text
Init 1
Download configuration
      |
      v
Init 2
Run preparation
      |
      v
Main application
```

Useful cases include:

* Preparing files
* Waiting for prerequisites
* Generating configuration
* Running setup logic

But I would avoid using init containers to create unbounded dependency waiting.

# Question 32: A Pod is stuck in `Init:0/1`. How would you troubleshoot it?

## Interview Answer

I would identify the init container:

```bash
kubectl describe pod <pod>
```

Then inspect its logs:

```bash
kubectl logs <pod> -c <init-container>
```

Possible causes include:

* DNS failure
* Dependency unavailable
* Permission problem
* Volume issue
* Bad command
* Missing Secret
* Image pull issue

Suppose the init container repeatedly runs:

```text
wait until database:5432 responds
```

and the database DNS name is incorrect.

The main application never starts.

The issue is not with the application container.

# Question 33: Why can "wait-for-database" init containers be dangerous?

## Interview Answer

Because they can create tightly coupled startup behavior.

Suppose 500 Pods restart.

Every Pod waits for the database.

Once the database returns, all 500 start simultaneously.

This can create a startup surge.

Also, if the application itself already supports retry and graceful dependency recovery, a strict init dependency may unnecessarily prevent startup.

I would use dependency waiting carefully and with:

* Timeouts
* Backoff
* Clear failure behavior

# Question 34: What is a sidecar container?

## Interview Answer

A sidecar runs alongside the main application container and supports it.

Examples include:

* Logging
* Proxies
* Service mesh
* Configuration reloaders
* Security agents

Conceptually:

```text
Pod
 |
 +----> Application
 |
 +----> Sidecar
```

They share aspects of the Pod environment such as network namespace and potentially volumes.

Operationally, the Pod is not healthy simply because the main application container is healthy.

The sidecar can also fail.

# Question 35: How can a sidecar cause production problems?

## Interview Answer

Many ways.

For example:

* Sidecar consumes excessive memory
* Sidecar uses too much CPU
* Proxy sidecar breaks network traffic
* Logging sidecar fills storage
* Sidecar readiness blocks Pod readiness
* Sidecar shutdown delays termination

Suppose:

```text
Application:
300 MiB

Sidecar:
800 MiB
```

and Pod memory expectations were based only on the application.

The sidecar becomes the actual resource bottleneck.

I always inspect all containers in the Pod.

# Question 36: Application container is healthy, but Pod never becomes Ready. What could be wrong?

## Interview Answer

Possible causes include:

* Readiness probe failure
* Sidecar not ready
* Readiness gate
* Dependency check failure
* Incorrect port
* Service mesh sidecar issue

I would inspect:

```bash
kubectl describe pod <pod>
```

and each container state.

A Pod-level status must be interpreted as a combination of its containers and readiness conditions.

# Question 37: A Deployment rollout is stuck. How do you investigate it?

## Interview Answer

I would start with:

```bash
kubectl rollout status deployment/<name>
```

Then:

```bash
kubectl describe deployment <name>
```

and:

```bash
kubectl get rs
kubectl get pods
```

I would determine:

* Are new Pods being created?
* Are they scheduling?
* Are they starting?
* Are they Ready?
* Are old Pods terminating?
* Is a PDB blocking termination?
* Is resource capacity insufficient?
* Are image pulls failing?

The flow is:

```text
Deployment
   |
   v
ReplicaSet
   |
   v
Pod creation
   |
   v
Scheduling
   |
   v
Startup
   |
   v
Readiness
   |
   v
Old replica removal
```

I want the exact stage where rollout stops.

# Question 38: What is `ProgressDeadlineExceeded`?

## Interview Answer

It indicates the Deployment did not make expected progress within its configured progress deadline.

It is not the root cause.

I would investigate why new replicas failed to become available.

Potential causes:

* Failed scheduling
* Image pull failure
* CrashLoopBackOff
* Readiness failure
* Resource shortage
* Configuration error

The Deployment status tells me rollout is stuck.

Pod and event evidence tells me why.

# Question 39: New Pods are healthy, but old Pods are not terminating. What would you inspect?

## Interview Answer

I would inspect:

* PodDisruptionBudget
* Termination grace period
* PreStop hook
* Finalizers where relevant
* Application shutdown
* Connection draining
* Replica counts
* Deployment strategy

If old Pods remain:

```text
Terminating
```

for a long time, graceful shutdown may be hanging.

If Kubernetes cannot evict them, a PDB may be involved.

# Question 40: Explain RollingUpdate deployment strategy.

## Interview Answer

RollingUpdate gradually replaces old replicas with new ones.

For example:

```text
V1 V1 V1 V1

   ↓

V2 V1 V1 V1

   ↓

V2 V2 V1 V1

   ↓

V2 V2 V2 V1

   ↓

V2 V2 V2 V2
```

Important settings include:

```text
maxUnavailable
maxSurge
```

These control how many replicas can be unavailable and how many extra replicas can temporarily exist.

This affects:

* Capacity
* Rollout speed
* Resource requirements
* Availability

# Question 41: How can `maxSurge` cause scheduling failures?

## Interview Answer

Suppose:

```text
Current replicas:
100

maxSurge:
25%
```

Kubernetes may need capacity for up to:

```text
125 Pods
```

during rollout.

If the cluster only has enough capacity for 105, new Pods may remain Pending.

The rollout stalls.

This is why deployment strategy must account for real cluster headroom.

# Question 42: How can `maxUnavailable` make deployment risky?

## Interview Answer

If it allows too many replicas to disappear at once, application capacity can drop below safe levels.

Suppose:

```text
10 replicas
maxUnavailable: 50%
```

Up to five may be unavailable during rollout.

If the remaining five cannot handle traffic, users may experience errors.

The right value depends on:

* Traffic
* Per-Pod capacity
* Startup time
* Failure tolerance

# Question 43: Rolling deployment succeeds technically, but error rate rises during every rollout. What do you investigate?

## Interview Answer

I would inspect lifecycle behavior.

Potential causes include:

* Readiness too early
* Old Pods terminated before draining
* Bad shutdown
* Cache warmup
* Connection pool initialization
* Service discovery lag
* Startup traffic surge

For example:

```text
New Pod starts
   |
   v
Readiness returns true immediately
   |
   v
Traffic arrives
   |
   v
Cache empty / DB pool not ready
   |
   v
Errors
```

The Pod may need better readiness semantics.

# Question 44: When might you choose blue-green instead of rolling deployment?

## Interview Answer

Blue-green can be useful when I want two complete environments or versions available simultaneously.

Conceptually:

```text
Blue
v1
currently serving

Green
v2
fully prepared

Traffic switch
      |
      v

Green serves production
```

Potential benefits:

* Fast traffic switch
* Fast rollback
* Full pre-cutover validation

Trade-offs include:

* More temporary capacity
* Data compatibility
* More environment coordination

I choose based on release risk and infrastructure cost.

# Question 45: What is a canary deployment?

## Interview Answer

A canary introduces a new version to a small subset of traffic first.

For example:

```text
95% -> v1
 5% -> v2
```

Then:

```text
75% -> v1
25% -> v2
```

and eventually:

```text
100% -> v2
```

if health remains good.

I would monitor:

* Error rate
* Latency
* Saturation
* Business metrics
* Version-specific logs

Canary deployment is useful only if I can distinguish canary behavior from stable behavior.

# Question 46: Why can canary deployment give false confidence?

## Interview Answer

If traffic is too small or unrepresentative.

For example:

```text
Canary:
1% traffic
```

may receive no high-value customer flows.

Or sticky sessions may cause the same small user population to hit it repeatedly.

I would ensure:

* Sufficient sample size
* Relevant traffic
* Correct metrics
* Version labeling
* Enough observation time

A canary is a controlled experiment.

# Question 47: What is a Kubernetes Job?

## Interview Answer

A Job manages Pods that run to completion.

Examples:

* Batch processing
* Data migration
* One-time task
* Report generation

Conceptually:

```text

 |

Pod
 |
 v
Task completes
 |
 v
Success
```

Unlike a Deployment, the goal is not to keep the process running forever.

# Question 48: A Job keeps creating failed Pods. How would you investigate?

## Interview Answer

I would check:

* `backoffLimit`
* Exit code
* Application failure
* Resource failure
* Image
* Dependency
* Permissions

If the task is not idempotent, retries may be dangerous.

For example:

```text
Charge customer
```

should not blindly execute five times because the Job retries.

Batch jobs need retry-safe design.

# Question 49: What is a CronJob?

## Interview Answer

A CronJob schedules Jobs based on a time schedule.

For example:

```text

      |
      v

      v
```

* Long-running Jobs
* Failed Jobs
* Timezone behavior

# Question 50: How can overlapping CronJobs create production problems?

## Interview Answer

Suppose a Job should run every 10 minutes but sometimes takes 30 minutes.

Without appropriate concurrency control:

```text
00:00 Job A starts
00:10 Job B starts
00:20 Job C starts
```

Now three copies operate simultaneously.

If they all:

```text
Process same records
Run same backup
Modify same data
```

you may get duplication or contention.

I would consider:

```text
concurrencyPolicy
```

such as preventing overlapping executions where appropriate.

# Question 54: How would you safely move workloads away from a suspicious node?

## Interview Answer

Depending on the incident, I might:

```bash

```

to prevent new scheduling.

Then, if safe:


with appropriate options.


```text
Cluster-wide scheduling incident
```

# Question 55: What is the difference between `cordon` and `drain`?

## Interview Answer

`cordon` marks a node unschedulable for new Pods.

Existing Pods remain.

```text
Node
Existing workloads stay
New workloads blocked
```

`drain` attempts to evict eligible workloads from the node while respecting relevant disruption controls.

Conceptually:

```text
CORDON
Stop new placements

DRAIN
Move existing workloads away
```

They serve different purposes.

# Question 56: Why might draining a node fail?

## Interview Answer

Possible causes include:

* PodDisruptionBudget
* Local storage
* Unmanaged Pod
* DaemonSet
* No capacity elsewhere
* Eviction constraints

I would read the drain error carefully rather than using aggressive flags immediately.

The blocking condition may exist to protect production availability.

# Question 57: A deployment has 20 replicas, but only 10 can schedule after a rollout. Cluster CPU utilization is only 40%. Why?

# Question 58: A Pod requests 4 CPU but usually uses 300m. What problem can that create?



Resource requests should reflect realistic workload behavior.


```text

```

```text

```
