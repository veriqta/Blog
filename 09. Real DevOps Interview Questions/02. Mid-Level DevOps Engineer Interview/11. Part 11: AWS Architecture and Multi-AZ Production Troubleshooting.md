# Part 11: AWS Architecture and Multi-AZ Production Troubleshooting

At mid-level, AWS interview questions should move beyond naming services.

The interviewer should expect you to explain how the pieces interact under failure.

The important questions are:

* What happens when one Availability Zone fails?
* Why are healthy EC2 instances still returning 503s?
* Why did Auto Scaling add capacity without fixing latency?
* Why did RDS failover complete but the application still fail?
* Why are read replicas healthy but users still see stale data?
* Why did one bad dependency bring down an otherwise redundant system?
* Where are the hidden single points of failure?

A useful production architecture might look like this:

```text
Users
  |
  v
Route 53
  |
  v
ALB
 / \
v   v
AZ-A        AZ-B
 |            |
EC2          EC2
 |            |
 +------Auto Scaling------+
             |
             v
        Application
          /      \
         v        v
       RDS     ElastiCache
    Multi-AZ
         |
         v
         S3
```

At mid-level, you should understand not only how to build this architecture, but how it behaves when components fail.

# Question 1: What does Multi-AZ architecture actually mean?

## Interview Answer

Multi-AZ means critical workloads are distributed across more than one Availability Zone so that failure of one zone does not automatically remove the entire service.

For an application tier:

```text
Region
  |
  +---- AZ-A
  |      |
  |      +---- EC2
  |      +---- EC2
  |
  +---- AZ-B
         |
         +---- EC2
         +---- EC2
```

An ALB can distribute requests across targets in multiple enabled Availability Zones.

The design goal is:

```text
AZ-A fails
    |
    v
Traffic continues
through
AZ-B
```

But simply placing resources in two AZs does not guarantee resilience.

Dependencies also need to be considered.

For example:

```text
App:
Multi-AZ

Database:
Single AZ
```

still gives me a database-related single point of failure.

The whole request path needs redundancy.

# Question 2: What would you check before calling an architecture truly Multi-AZ?

## Interview Answer

I would check every critical dependency.

For example:

```text
Ingress
Application
Database
Cache
NAT
Storage
Message queue
Secrets
DNS
```

I would ask:

```text
Can the application run if AZ-A disappears?

Where does traffic go?

Can new instances start in AZ-B?

Can the database fail over?

Can the application reach dependencies?

Does each private subnet have working egress?

Are caches or queues zonally constrained?
```

A system can have EC2 instances in three AZs and still depend on one NAT gateway, one database instance, or one external endpoint.

That is why Multi-AZ is an architectural property, not just an EC2 placement choice.

# Question 3: One Availability Zone fails. What should happen to a properly designed web application?

## Interview Answer

Assuming the architecture has enough remaining capacity, traffic should shift toward healthy resources in other zones.

For example:

```text
Before:

ALB
 |
 +---- AZ-A -> 4 instances
 |
 +---- AZ-B -> 4 instances
```

If AZ-A fails:

```text
ALB
 |
 X---- AZ-A
 |
 +---- AZ-B -> 4 instances
```

The remaining application capacity needs to handle the traffic.

Auto Scaling may then add additional instances if capacity thresholds or desired capacity require it.

But several dependencies could still break the application:

* Database availability
* NAT
* Cache
* External service connectivity
* Private subnet routes
* EBS
* Secrets retrieval

I would validate actual end-to-end behavior rather than assuming the ALB alone guarantees resilience.

# Question 4: Why does Multi-AZ architecture still need spare capacity?

## Interview Answer

Because after losing one failure domain, remaining resources must absorb the displaced load.

Suppose:

```text
AZ-A:
50% capacity

AZ-B:
50% capacity
```

Under normal traffic, both operate at:

```text
70% utilization
```

If AZ-A disappears, AZ-B may need to handle approximately double its previous traffic.

If it is already at 70%, it cannot simply take 140% utilization.

The architecture needs:

```text
Headroom
Auto Scaling
Load redistribution
Dependency capacity
```

Multi-AZ without failure headroom may turn a zone failure into an overload failure.

# Question 6: What is the difference between EC2 system status checks and instance status checks?

## Interview Answer

System status checks relate to underlying AWS infrastructure affecting the instance.

Examples may include:

```text
Physical host
Networking
Power
Underlying platform
```

Instance status checks relate more to the guest operating system and instance-level reachability.

For example:

```text
OS networking
Boot issues
Filesystem
Kernel problems
```

Operationally:

```text
System check fails
```

pushes me toward AWS infrastructure.

Whereas:

```text
Instance check fails
```

pushes me more toward the operating system or instance itself.

I would still validate with logs and console/system information.

# Question 7: One EC2 instance becomes unhealthy behind the ALB. What should happen?

## Interview Answer

The ALB should stop routing new traffic to that target once it fails the configured health thresholds.

Conceptually:

```text
ALB
 |
 +---- EC2-A healthy
 |
 X---- EC2-B unhealthy
 |
 +---- EC2-C healthy
```

Traffic continues through healthy targets.

If the instance belongs to an Auto Scaling group and health-check integration is configured appropriately, Auto Scaling may replace it.

The important distinction is:

```text
Load balancer removes bad target
```

and:

```text
Auto Scaling replaces capacity
```

are related but separate behaviors.

# Question 8: Why could an EC2 instance pass ALB health checks but still fail user traffic?

## Interview Answer

The health endpoint may be too shallow.

For example:

```text
GET /health
-> 200
```

may only confirm that the web server process is running.

Real requests may require:

```text
RDS
ElastiCache
External payment API
Secrets
```

The instance can therefore be:

```text
ALB healthy
```

while:

```text
checkout broken
```

I would use multiple layers of observability.

Health checks should be meaningful but should not necessarily depend on every downstream dependency, because that can cause cascading removal of all targets.

# Question 9: What is an Auto Scaling group responsible for?

## Interview Answer

An Auto Scaling group manages the desired number and lifecycle of EC2 instances according to its configuration.

It can:

* Launch instances
* Replace unhealthy instances
* Scale out
* Scale in
* Maintain desired capacity
* Distribute instances across enabled Availability Zones

Conceptually:

```text
Demand rises
    |
    v
Scaling policy
    |
    v
Desired capacity increases
    |
    v
New EC2 instances
    |
    v
Register with load balancer
```

Auto Scaling is a capacity mechanism.

It does not automatically solve application bottlenecks.

## Interview Answer

I would inspect:

* Scaling policy
* Target metric
* Alarm state
* Minimum capacity
* Maximum capacity
* Desired capacity
* Cooldowns or instance warmup
* Launch template
* Subnet capacity
* EC2 quota

For example:

```text
Desired: 10
Max:     10
```

means the group cannot scale beyond 10 even if CPU is 100%.

Another case:

```text
Scale-out triggered
```

but instance launch fails because a launch template uses an unavailable instance type.

I would trace:

```text
Metric
 |
 v
Policy
 |
 v
Desired capacity
 |
 v
Launch
 |
 v
Healthy instance
```

# Question 11: Auto Scaling added 20 instances, but application latency remains high. Why?

## Interview Answer

The bottleneck may not be EC2 CPU.

For example:

```text
More application instances
       |
       v
More database connections
       |
       v
RDS connection saturation
       |
       v
Latency remains high
```

Other bottlenecks include:

* Database
* Cache
* External API
* Network
* Lock contention
* Queue
* Application serialization
* Shared filesystem

Scaling one tier can increase pressure on another tier.

I would find the limiting resource before assuming more EC2 capacity is useful.

# Question 12: How can Auto Scaling itself create an outage?

## Interview Answer

Aggressive scale-out can create dependency storms.

For example:

```text
Traffic spike
    |
    v
100 instances launch
    |
    v
100 instances:
download dependencies
pull container images
retrieve secrets
open DB connections
warm caches
```

This can overload:

* Container registry
* Database
* Secrets Manager
* NAT gateway
* Third-party API

The architecture needs controlled initialization and dependency capacity.

# Question 13: Why does instance warmup matter?

## Interview Answer

A new instance may be technically running but not ready to handle production traffic efficiently.

It may need to:

* Pull images
* Start the application
* Compile or warm runtime
* Populate caches
* Establish connections

If Auto Scaling immediately evaluates new instances as fully contributing capacity, it may make poor scaling decisions.

Warmup helps scaling logic account for startup time.

Application readiness also needs to align with load-balancer registration.

# Question 14: What is the operational difference between an ALB and NLB?

## Interview Answer

At a high level:

ALB operates at the application layer for HTTP/HTTPS-oriented routing.

It can make decisions based on:

* Host
* Path
* HTTP headers and application-level behavior

NLB operates at the transport layer and is suited to high-performance TCP, UDP, and TLS traffic patterns.

Conceptually:

```text
ALB:

HTTP request
 |
 v
Host / path routing
 |
 v
Target
```

```text
NLB:

TCP/UDP/TLS flow
 |
 v
Target
```

I choose based on protocol and routing requirements rather than simply performance reputation.

# Question 15: When would you choose ALB over NLB?

## Interview Answer

For HTTP/HTTPS workloads needing features such as:

* Host-based routing
* Path-based routing
* HTTP-aware health checks
* TLS termination
* Application routing

For example:

```text
api.example.com -> API target group
shop.example.com -> Store target group
```

ALB is a natural fit.

# Question 16: When would you choose NLB?

## Interview Answer

For workloads requiring transport-level handling such as:

* TCP
* UDP
* High-throughput connections
* Static IP requirements in relevant designs
* Certain source IP behavior
* Non-HTTP protocols

Examples might include:

```text
Database proxy
Custom TCP service
UDP workload
```

The exact choice still depends on the service requirements.

# Question 17: ALB returns 503. What does that suggest?

## Interview Answer

One important possibility is that the target group has no usable healthy targets.

I would inspect:

```text
HealthyHostCount
UnHealthyHostCount
Target health reason
```

I would verify:

* Target registration
* Health-check path
* Health-check port
* Security groups
* Application listener
* Target readiness

The ALB itself may be healthy while it has nowhere valid to send the request.

# Question 18: ALB returns 502. What do you investigate?

## Interview Answer

I would investigate communication between the ALB and target.

Possible causes include:

* Target resets connection
* Malformed response
* Backend protocol mismatch
* Application crashes
* TLS mismatch to backend
* Connection closure behavior

I would correlate:

```text
ALB logs
Application logs
Target health
```

and test the target directly where appropriate.

A 502 is not the same as a 503.

# Question 19: Users receive 504s from the ALB. What do you investigate?

## Interview Answer

A 504 often means the load balancer waited too long for the target to respond.

I would investigate:

* Application response time
* Database latency
* Dependency latency
* Connection pools
* CPU throttling
* Queue backlog
* ALB idle timeout

The causal chain might be:

```text
Slow RDS query
    |
    v
Application waits
    |
    v
ALB timeout
    |
    v
504
```

Increasing the ALB timeout may only make users wait longer.

I want to identify why the backend is slow.

# Question 20: How do target health checks become dangerous if configured poorly?

## Interview Answer

If they are too aggressive, brief dependency problems can remove healthy application capacity.

For example:

```text
Database latency spike
      |
      v
Health endpoint fails
      |
      v
ALB removes instances
      |
      v
Traffic concentrates
      |
      v
Remaining instances overload
```

If they are too tolerant, broken instances continue serving users.

Health-check design requires balance.

# Question 21: Explain RDS Multi-AZ.

## Interview Answer

RDS Multi-AZ provides database availability by maintaining a standby in another Availability Zone for supported configurations.

Conceptually:

```text
Primary
AZ-A
  |
  | synchronous replication
  v
Standby
AZ-B
```

During certain failures, RDS can fail over to the standby.

Applications continue using the database endpoint rather than hardcoding an instance IP.

The important point is:

```text
Multi-AZ
=
availability
```

not primarily:

```text
read scaling.
```

# Question 22: Does the standby in traditional RDS Multi-AZ normally serve application reads?

## Interview Answer

Not in the traditional Multi-AZ DB instance model.

Its main purpose is high availability.

For read scaling, I would use read replicas where supported and appropriate.

This distinction is frequently tested.

# Question 23: RDS fails over successfully, but the application still fails. Why?

## Interview Answer

A successful database failover does not guarantee the application handles it correctly.

Possible problems include:

* Stale DNS caching
* Existing DB connections broken
* Connection pool not reconnecting
* Long retry intervals
* Application caches the old IP
* Transaction failures
* Read/write assumptions

The sequence may be:

```text
RDS failover
     |
     v
Endpoint now resolves to new primary
     |
     v
Old application connections break
     |
     v
Application fails to reconnect
```

I would test application failover behavior, not only database failover.

# Question 24: Why should applications connect to RDS using the endpoint instead of IP?

## Interview Answer

Because the underlying database instance can change during failover or maintenance.

The endpoint is the stable abstraction.

Hardcoding the current IP defeats that abstraction.

Conceptually:

```text
db.example endpoint
      |
      v
Current primary
```

After failover:

```text
same endpoint
      |
      v
New primary
```

The application should re-resolve and reconnect appropriately.

# Question 25: What is a read replica?

## Interview Answer

A read replica is a separate database instance receiving replicated data from a source database.

It can be used for:

* Read scaling
* Reporting
* Analytics
* Some disaster-recovery designs

Conceptually:

```text
Primary
 |
 +----> Read Replica A
 |
 +----> Read Replica B
```

Writes go to the primary.

Read traffic may be directed to replicas.

# Question 26: What problem does replica lag create?

## Interview Answer

Replication is not necessarily instantaneous.

Suppose:

```text
User writes:
order_status=PAID
```

to the primary.

Immediately after, the user reads from a replica that has not received the update.

They see:

```text
order_status=PENDING
```

This is a consistency issue.

Architecture must account for read-after-write requirements.

Not every read can safely be routed to an asynchronous replica.

# Question 27: Read replica CPU is low, but replica lag is increasing. What could cause it?

## Interview Answer

Possible causes include:

* Heavy writes on primary
* Slow I/O
* Long-running replica queries
* Replication bottleneck
* Network issues
* Storage performance

I would inspect the actual replication metrics rather than using CPU alone as a health signal.

# Question 28: Can a read replica be used for failover?

## Interview Answer

Depending on database engine and architecture, a read replica can often be promoted, but this is different from automatic Multi-AZ failover.

Promotion may involve:

* Manual or automated orchestration
* DNS/application changes
* Data-loss considerations based on lag

I would distinguish:

```text
Multi-AZ standby
```

from:

```text
read replica.
```

They serve different primary purposes.

# Question 29: What role does ElastiCache play in production architecture?

## Interview Answer

ElastiCache provides managed in-memory caching using supported engines such as Redis-compatible or Memcached-based offerings.

Common use cases include:

* Session caching
* Database query caching
* Frequently accessed objects
* Rate-limit state
* Distributed locks in some designs

Conceptually:

```text
Application
    |
    +---- cache hit ----> ElastiCache
    |
    +---- cache miss ---> Database
```

A good cache reduces downstream load.

A poorly designed cache can become a new dependency bottleneck.

# Question 30: What is a cache stampede?

## Interview Answer

Suppose a popular cached item expires.

Thousands of requests simultaneously miss the cache.

They all query the database.

```text
Cached key expires
      |
      v
10,000 cache misses
      |
      v
10,000 DB queries
      |
      v
Database overload
```

Mitigation patterns may include:

* TTL jitter
* Request coalescing
* Locks
* Refresh-ahead
* Stale-while-revalidate patterns

Cache design influences database resilience.

# Question 31: ElastiCache becomes unavailable. Should the entire application go down?

## Interview Answer

It depends on how critical the cached data is.

For many caches, a resilient application should degrade gracefully.

For example:

```text
Cache available
-> fast

Cache unavailable
-> database fallback
```

But this can create a second problem.

If every request suddenly falls back to the database:

```text
Cache outage
   |
   v
DB load 10x
   |
   v
Database outage
```

The architecture needs rate controls and dependency capacity.

# Question 32: Why can a cache outage create a cascading failure?

## Interview Answer

Because the cache may be absorbing most read traffic.

Example:

```text
Normal:

Cache handles 90%
DB handles 10%
```

Cache fails:

```text
DB suddenly handles 100%
```

If the database was sized for 10%, it may collapse.

The correct resilience design includes understanding fallback load.

# Question 33: What role does S3 play in scalable architectures?

## Interview Answer

S3 is commonly used for durable object storage such as:

* User uploads
* Static assets
* Logs
* Backups
* Build artifacts
* Data lakes

It removes large binary/object storage from application instance disks.

Instead of:

```text
User upload
    |
    v
EC2 local disk
```

I prefer:

```text
User upload
    |
    v
Application
    |
    v
S3
```

or direct controlled uploads to S3 where architecture allows.

This makes EC2 instances more replaceable.

# Question 34: Why should application instances not store important uploads on local EC2 disk?

## Interview Answer

Because instances in Auto Scaling environments should be replaceable.

Suppose:

```text
User uploads file
      |
      v
EC2-A local disk
```

Auto Scaling terminates EC2-A.

The file disappears.

Local disks can be useful for temporary/cache data, but durable user content should be stored in appropriate persistent services.

# Question 35: How would you secure S3 access from EC2?

## Interview Answer

I would prefer IAM roles associated with the workload rather than storing long-lived access keys on the instance.

For example:

```text
EC2
 |
 v
IAM Role
 |
 v
Permission:
s3:GetObject
s3:PutObject
on required bucket/prefix
```

This provides temporary credentials through AWS identity mechanisms.

I would also consider:

* Bucket policies
* KMS permissions
* Block Public Access
* Network architecture
* Logging

# Question 36: What is the biggest security mistake with S3?

## Interview Answer

Treating bucket access as one-dimensional.

Security can involve:

```text
IAM identity policy
Bucket policy
Object ownership
Public access settings
KMS
VPC endpoint policy
```

A user may have:

```text
s3:GetObject
```

but still fail because the object is encrypted with a KMS key they cannot decrypt.

I would evaluate the full authorization chain.

# Question 37: What is EBS typically used for?

## Interview Answer

EBS provides block storage for EC2.

Common uses include:

* OS/root volumes
* Database volumes
* Application persistent disks
* Filesystems

Conceptually:

```text
EC2
 |
 v
EBS volume
```

Many EBS volumes are Availability Zone scoped.

That matters during failover.

# Question 38: An EC2 instance fails but its EBS data is intact. How can you recover?

## Interview Answer

Depending on the failure and architecture, I may:

* Stop/replace instance
* Detach the EBS volume
* Attach it to another appropriate instance in the same AZ
* Mount and recover data
* Restore from snapshot

I would verify:

* Filesystem consistency
* Attachment state
* Encryption permissions
* Application consistency

For production systems, replacing instances from automation is usually preferable to manually resurrecting pet servers.

# Question 39: Why can EBS become an application bottleneck?

## Interview Answer

Storage performance may constrain:

* IOPS
* Throughput
* Queue depth
* Latency

An application can have:

```text
CPU 30%
Memory 50%
```

while database latency is high because EBS is saturated.

I would correlate:

```text
Volume IOPS
Throughput
Queue
Latency
Application latency
```

not only instance metrics.

# Question 40: EBS volume is full. What can happen?

## Interview Answer

The filesystem may stop accepting writes.

Applications may experience:

* Log write failures
* Database failures
* Temporary-file failures
* Package/update failures
* Application crashes

I would check both:

```text
Filesystem utilization
```

and:

```text
Inode utilization
```

inside the instance.

Cloud volume size and filesystem usable capacity are related but not identical.

# Question 41: What is an IAM role in an AWS workload architecture?

## Interview Answer

An IAM role provides an identity with permissions that can be assumed by workloads or AWS services.

For EC2:

```text
Application
   |
   v
EC2 instance role
   |
   v
Temporary credentials
   |
   v
AWS API
```

This is preferable to embedding:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

in configuration files.

Roles reduce long-lived credential management.

# Question 42: An EC2 application receives `AccessDenied` calling S3. How do you troubleshoot it?

## Interview Answer

I would determine the full authorization path.

I check:

```text
Which role is actually assumed?
Which action?
Which resource?
Identity policy?
Bucket policy?
KMS?
SCP if applicable?
VPC endpoint policy?
```

For example:

```text
s3:GetObject allowed
```

may not be enough if the object is encrypted with a KMS key and:

```text
kms:Decrypt
```

is denied.

I would not simply attach `AdministratorAccess`.

# Question 43: What is KMS used for in this architecture?

## Interview Answer

AWS KMS manages cryptographic keys used by AWS services and applications.

It can protect:

* EBS
* S3
* RDS
* Secrets Manager
* Application data

Conceptually:

```text
Application
   |
   v
AWS service
   |
   v
KMS key authorization
```

Encryption introduces another authorization layer.

The caller may need permission both to access the resource and to use the relevant key.

# Question 44: Why can a KMS policy break an otherwise correct IAM policy?

## Interview Answer

Because the KMS key has its own authorization model.

Suppose the EC2 role can:

```text
s3:GetObject
```

but cannot:

```text
kms:Decrypt
```

for the key protecting the object.

The result is access failure.

The resource exists.

S3 access is allowed.

Decryption is not.

Mid-level troubleshooting must account for layered permissions.

# Question 45: What is Secrets Manager used for?

## Interview Answer

Secrets Manager stores and manages sensitive values such as:

* Database credentials
* API keys
* Service credentials

Applications can retrieve secrets using IAM-based authorization.

Conceptually:

```text
Application
   |
   v
IAM Role
   |
   v
Secrets Manager
   |
   v
Secret
```

It can also support rotation workflows for certain types of secrets.

# Question 46: Secrets Manager is healthy, but the application cannot start. What could be wrong?

## Interview Answer

Possible causes include:

* IAM role lacks permission
* KMS key denies decrypt
* Secret name/ARN incorrect
* Network path unavailable
* VPC endpoint configuration
* Application timeout
* Secret version issue

The dependency path is:

```text
Application
 |
 v
Network
 |
 v
Secrets Manager
 |
 v
IAM
 |
 v
KMS
 |
 v
Secret
```

Any one of these can break startup.

# Question 47: Why can retrieving secrets during every request be a poor design?

## Interview Answer

It adds latency and dependency load to the request path.

For example:

```text
Every HTTP request
      |
      v
Secrets Manager API call
      |
      v
Application continues
```

This makes Secrets Manager availability and latency part of every customer request.

Often the application retrieves secrets at startup or caches them safely according to rotation requirements.

The exact strategy depends on the secret lifecycle.

# Question 49: Why is `HealthyHostCount` useful?

## Interview Answer

Because user-facing capacity can disappear even while the EC2 instances themselves remain running.

Suppose:

```text
ASG instances:
10

ALB healthy targets:
3
```

The group looks mostly alive.

The load balancer sees only 30% useful capacity.

That discrepancy is important.

# Question 50: What is the danger of alerting only on average CPU?

## Interview Answer

Average values can hide failure.

Suppose:

```text
10 instances
```

Five:

```text
CPU 10%
```

Five:

```text
CPU 100%
```

Average:

```text
55%
```

The average looks acceptable.

Half the fleet is saturated.

I want percentiles, per-target visibility, and application metrics.

# Question 51: What is a scaling bottleneck?

## Interview Answer

A scaling bottleneck is a dependency or limit that prevents capacity from increasing effectively.

Examples include:

* RDS connection limits
* NAT capacity
* External API rate limits
* Subnet IP exhaustion
* EC2 quota
* Container registry
* Cache
* SQS consumers
* EBS performance

The application tier may scale horizontally while the shared dependency does not.

# Question 52: How can subnet IP exhaustion break Auto Scaling?

## Interview Answer

New EC2 instances require private IP addresses.

If the target subnet has insufficient free IPs:

```text
Scale-out request
      |
      v
Launch instance
      |
      X
No usable IP capacity
```

The Auto Scaling policy works.

The subnet capacity prevents execution.

Capacity planning should include addresses, not only CPU.

# Question 53: Why can a NAT gateway become an architectural dependency?

## Interview Answer

Private application instances may depend on NAT for outbound internet access.

For example:

```text
Private EC2
   |
   v
NAT
   |
   v
External API
```

If multiple AZs route through one NAT path, that can create a dependency on another AZ or create unnecessary cross-AZ traffic.

A resilient design typically aligns egress architecture with failure domains.

# Question 54: How would an external API failure affect an AWS application?

## Interview Answer

It depends on application resilience.

A poor design:

```text
External API slow
      |
      v
All requests wait
      |
      v
Workers exhausted
      |
      v
Application outage
```

A stronger design may include:

* Timeouts
* Retry with backoff
* Circuit breaker
* Queueing
* Graceful degradation
* Caching

Cloud architecture cannot make an unreliable external dependency reliable automatically.

Application failure handling matters.

# Question 55: What is a circuit breaker in this context?

## Interview Answer

A circuit breaker stops repeatedly calling a dependency that is clearly failing.

Conceptually:

```text
Dependency healthy
      |
      v
Calls allowed

Failures cross threshold
      |
      v
Circuit opens
      |
      X
Calls temporarily blocked
```

This can protect:

* Application threads
* Connection pools
* Dependency
* User latency

After a period, controlled test requests may determine whether the dependency recovered.

# Question 56: Why can retries create a bigger AWS outage?

## Interview Answer

Suppose an RDS query starts failing.

Every application instance retries each request five times.

Auto Scaling then doubles the number of instances.

The result:

```text
Original DB traffic
x
5 retries
x
2 instance count
```

The database receives dramatically more load.

The causal chain becomes:

```text
Database degraded
      |
      v
Retries
      |
      v
More DB load
      |
      v
Auto Scaling adds instances
      |
      v
Even more DB connections
      |
      v
Database collapses
```

Resilience mechanisms must be coordinated.

# Question 57: What are common hidden single points of failure in "highly available" AWS architectures?

## Interview Answer

Examples include:

* One NAT gateway for all AZs
* One database without Multi-AZ
* One cache node
* One EC2 instance holding local state
* One deployment runner
* One Secrets retrieval path
* One external API
* One shared filesystem
* One Availability Zone with all healthy capacity
* One hardcoded IP

A diagram can look distributed while a dependency remains centralized.

## Interview Answer


For example:

```text

 |
 v

 |
 +---- RDS
 |

 +---- Secrets
 |
 +---- External API
```

Then for each component:


If the answer is:


* Redundancy
* Graceful degradation
* Failover
* Queueing
* Caching
* Alternate path

Not every component needs full redundancy, but critical dependencies should be intentional.

## Question 61: A major AWS application starts returning intermittent 502, 504, and database errors during peak traffic. Walk through your investigation.

Architecture:

```text
Users
  |
  v
Route 53
  |
  v
ALB
  |
  +----------+
  |          |
  v          v
AZ-A        AZ-B
ASG         ASG
  |          |
  +-----+----+
        |
        v
      API
      / | \
     /  |  \
    v   v   v
  RDS Redis External API
 Multi-AZ
```

At 18:00:

```text
Traffic +80%
```

At 18:03:

```text
ASG scales:
12 -> 30
```

At 18:06:

```text
ALB 502 increases
```

At 18:08:

```text
ALB 504 increases
```

At 18:10:

```text
RDS connections reach 98%
```

At 18:12:

```text
Redis latency increases
```

How do you proceed?

## Interview Answer

I would first establish that this is a cascading-capacity incident rather than several unrelated alarms.

The timeline already suggests a possible relationship.

# Step 1: Check target health

I inspect:

```text
HealthyHostCount
UnHealthyHostCount
Target response time
ALB 5xx
```

Suppose:

```text
30 EC2 launched
22 healthy
8 unhealthy
```

I investigate why those eight are failing.

# Step 2: Examine application startup

Logs show the new instances are timing out connecting to RDS.

Now scaling is increasing database connection pressure.

Each instance opens:

```text
80 connections
```

Potential pool size:

```text
30 x 80
=
2,400
```

RDS safe capacity:

```text
1,500
```

The scale-out event itself is worsening the database bottleneck.

# Step 3: Explain 504s

RDS latency rises.

Application requests wait on queries.

ALB waits on application responses.

Eventually:

```text
ALB timeout
```

produces 504.

# Step 4: Explain some 502s

Some application processes become unstable when database connection acquisition repeatedly fails and reset upstream connections.

ALB receives failed backend responses.

That can produce 502.

Now two HTTP symptoms have the same underlying dependency pressure but different immediate failure paths.

# Step 5: Investigate Redis

Cache latency rises because traffic increases and new instances perform cache warmup.

Cache misses increase database load further.

The feedback loop becomes:

```text
Traffic increase
      |
      v
Auto Scaling
      |
      v
More DB connections
      |
      v
RDS saturation
      |
      v
Application latency
      |
      v
504

Meanwhile

New instances
      |
      v
Cold cache
      |
      v
More Redis/DB load
```

# Step 6: Mitigate

Depending on evidence, I might:

* Limit or reduce per-instance DB pool
* Stop unnecessary scale-out
* Increase database capacity if safe and timely
* Reduce expensive traffic
* Enable graceful degradation
* Rate-limit noncritical work
* Protect critical transactions

The goal is not necessarily:

```text
Add more EC2.
```

Compute is no longer the limiting tier.

# Step 7: Verify

I monitor:

```text
RDS connections
RDS latency
ALB 502
ALB 504
Target response time
HealthyHostCount
Redis latency
Application p95
Business success rate
```

I want a causal recovery sequence.

For example:

```text
RDS connections:
98% -> 60%

DB latency:
900ms -> 80ms

ALB 504:
12% -> 0.2%

Checkout success:
82% -> 99.8%
```

# Step 8: Prevent recurrence

Corrective actions might include:

* Global connection budget
* Smaller application pools
* RDS Proxy where appropriate
* Cache warmup design
* More meaningful scaling metrics
* Dependency-aware autoscaling
* Load testing
* Capacity modeling
* Retry controls
* Circuit breakers

The lesson is:

```text
Horizontal compute scaling
does not automatically
scale shared dependencies.
```

# Interviewer Follow-Up: Would you increase the Auto Scaling maximum from 30 to 100?

## Interview Answer

Not while the database is the bottleneck.

That could make the incident worse.

More instances could create:

```text
More DB connections
More cache load
More NAT traffic
More external API calls
```

I would first remove or increase the actual bottleneck.

# Interviewer Follow-Up: Would you increase the ALB timeout to reduce 504s?

## Interview Answer

Not as the primary fix.

If requests are waiting because RDS is saturated, a longer timeout means requests consume application resources for longer.

That can increase:

```text
Concurrent requests
Worker occupancy
Connection use
Memory
```

and amplify the failure.

I would fix the dependency latency.

# Interviewer Follow-Up: Would RDS Multi-AZ prevent this incident?

## Interview Answer

No.

Multi-AZ primarily addresses availability and failover.

Both primary and standby architecture do not magically eliminate connection saturation or slow queries.

This is a capacity problem, not simply an availability-zone failure.
