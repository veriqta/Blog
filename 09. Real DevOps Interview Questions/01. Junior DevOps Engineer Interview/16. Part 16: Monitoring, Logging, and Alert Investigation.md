# Part 16: Monitoring, Logging, and Alert Investigation

A monitoring tool tells you something happened.

A production engineer needs to determine what happened, why it happened, whether users are affected, and what to do next.

That difference is exactly what interviewers test.

You may hear questions such as:

> "CPU utilization suddenly reaches 95 percent on several production servers. What do you investigate?"

> "The application is slow, but CPU and memory look normal. What would you check next?"

> "Your monitoring dashboard looks healthy, but customers report failures. How is that possible?"

> "An alert fires every night at 2:00 a.m. What would you investigate before changing the threshold?"

> "Disk usage is 95 percent. What do you do?"

> "Your application returns HTTP 500 errors, but the infrastructure dashboards look normal. Where do you investigate?"

> "Prometheus stops receiving metrics from one Kubernetes application. Walk me through your troubleshooting."

A weak answer is:

"I would check Grafana."

A stronger answer explains what signals you would inspect, how you would correlate them, how you would determine impact, and how you would separate symptoms from root cause.

This part focuses on that thinking.

---

# 1. What is monitoring?

## Strong interview answer

Monitoring is the process of collecting and evaluating information about systems and applications so that we can understand their health, performance, availability, and behavior.

For example, I may monitor:

```text
CPU utilization
Memory utilization
Disk utilization
Disk I/O
Network traffic
Request rate
Error rate
Latency
Application health
Database connections
Queue depth
Pod restarts
Service availability
```

Monitoring helps answer questions such as:

```text
Is the application available?

Is performance degrading?

Are errors increasing?

Are resources approaching capacity?

Did something change after deployment?
```

Monitoring should not simply produce dashboards.

The objective is operational visibility.

---

# 2. What is observability, and how is it different from monitoring?

## Strong interview answer

Monitoring usually focuses on known conditions and predefined signals.

For example:

```text
CPU > 90%
Disk > 85%
HTTP 5xx rate > threshold
Pod restarting
```

Observability is broader.

It is the ability to understand what is happening inside a system by examining the signals the system produces.

The three commonly discussed signals are:

```text
Metrics
Logs
Traces
```

For example:

```text
Customer request is slow
        |
        v
Metrics
Latency increased
        |
        v
Trace
Database call consumed 4.8 seconds
        |
        v
Logs
Database connection pool exhausted
```

Monitoring may tell me:

```text
Something is wrong.
```

Observability should help me investigate:

```text
Where is it wrong?

What changed?

Which component is responsible?

Which users are affected?
```

---

# 3. What are metrics?

## Strong interview answer

Metrics are numerical measurements collected over time.

Examples include:

```text
CPU utilization = 87%

Memory utilization = 72%

HTTP requests = 4,200 requests/sec

HTTP 5xx rate = 3.4%

p95 latency = 820 ms

Available disk = 18 GB
```

Metrics are useful because they can be aggregated and compared over time.

For example:

```text
09:00  CPU 35%
09:05  CPU 40%
09:10  CPU 92%
09:15  CPU 96%
```

That immediately tells me something changed around 09:10.

I would then correlate that time with deployments, traffic changes, jobs, logs, and other metrics.

---

# 4. What are logs?

## Strong interview answer

Logs are event records produced by applications, operating systems, services, containers, network devices, and other components.

For example:

```text
2026-08-15T10:22:31Z
ERROR
payment-service
database connection timeout
request_id=abc123
```

A log can provide context that a metric cannot.

A metric may show:

```text
HTTP 500 errors increased.
```

Logs may show:

```text
ERROR database connection timeout
```

The metric identifies the pattern.

The log helps explain individual events.

---

# 5. What are distributed traces?

## Strong interview answer

Distributed tracing follows a request as it moves across multiple services.

For example:

```text
User
 |
 v
API Gateway
  20 ms
 |
 v
Checkout Service
  40 ms
 |
 v
Payment Service
  120 ms
 |
 v
Database
  4,300 ms
```

Total request:

```text
4.48 seconds
```

Without tracing, I may know that checkout latency increased.

With tracing, I can see that most of the delay occurred in the database call.

This becomes particularly useful in microservice architectures where one customer request may cross many services.

---

# 6. What is the difference between metrics, logs, and traces?

## Strong interview answer

I think of them as complementary signals.

```text
METRICS

What is happening at scale?

Error rate increased.
CPU increased.
Latency increased.
```

```text
LOGS

What happened during specific events?

Connection timeout.
Authentication failed.
Process crashed.
```

```text
TRACES

Where did a request spend its time?

API
 |
 v
Service A
 |
 v
Service B
 |
 v
Database
```

During an incident, I often correlate all three rather than treating them as separate systems.

# 7. What is Prometheus?

## Strong interview answer

Prometheus is a monitoring and time-series system commonly used to collect and query metrics.

A common architecture is:

```text
Applications / Exporters
          |
          | expose metrics
          v
      Prometheus
          |
          v
        PromQL
          |
          +------> Grafana
          |
          +------> Alerting
```

Prometheus commonly uses a pull model.

Targets expose metrics endpoints, and Prometheus scrapes them periodically.

For example:

```text
http://application:8080/metrics
```

Prometheus retrieves the metrics and stores the resulting time series.

---

# 8. What is Grafana?

## Strong interview answer

Grafana is a visualization and dashboarding platform.

It can query data sources such as Prometheus and display information through graphs, tables, gauges, and other panels.

For example:

```text
Prometheus
    |
    v
Grafana

Dashboard:
CPU
Memory
Latency
Traffic
Error rate
Pod health
```

Grafana does not automatically create observability just because dashboards exist.

The dashboards need to show signals that help engineers understand the system.

---

# 9. Is Grafana a monitoring system?

## Strong interview answer

Grafana is primarily a visualization and observability platform.

In a common Prometheus setup:

```text
Application
    |
    v
Prometheus
collects/stores metrics
    |
    v
Grafana
queries and visualizes them
```

Grafana can also participate in alerting workflows, but I would distinguish the visualization layer from the underlying telemetry sources.

An exporter exposes metrics from a system in a format Prometheus can scrape.

A common example is Node Exporter.

Conceptually:

```text
Linux Server
     |
     v
Node Exporter

     | /metrics
     v
Prometheus
```

Node Exporter exposes host-level metrics such as:

```text
CPU
Memory
Filesystem
Network

```

Other exporters exist for different technologies.

# 11. What is the difference between infrastructure monitoring and application monitoring?

## Strong interview answer

Infrastructure monitoring focuses on resources supporting the application.

For example:

```text
CPU
Memory
Disk
Network
Node health
VM health
Container resources
```

Application monitoring focuses more directly on application behavior.

For example:

```text
Request rate
Response latency
HTTP errors
Failed transactions
Queue depth
Database query latency
Business transactions
```

This distinction matters because:

```text
Infrastructure healthy
!=
Application healthy
```

A server can have:

```text
CPU 20%
Memory 40%
Disk 30%
```

while every checkout request fails because of an application bug.

# 12. What are the four golden signals?

## Strong interview answer

A commonly used model focuses on:

```text
Latency
Traffic
Errors
Saturation
```

Latency asks:

```text
How long are requests taking?
```

Traffic asks:

```text
How much demand is the system receiving?
```

Errors ask:

```text
How much work is failing?
```

Saturation asks:

```text
How close is the system to its capacity?
```

For a web application:

```text
Latency
p95 = 850 ms

Traffic
5,000 requests/sec

Errors
4% HTTP 5xx

Saturation
Database connection pool = 98%
```

Together these provide much more context than CPU alone.

# 13. What is RED monitoring?

## Strong interview answer

RED focuses on services using:

```text
Rate
Errors
Duration
```

Rate:

```text
How many requests are being processed?
```

Errors:

```text
How many requests fail?
```

Duration:

```text
How long do requests take?
```

For example:

```text
Checkout Service

Rate:
2,800 requests/sec

Errors:
0.8%

Duration:
p95 420 ms
```

It is useful for service-oriented monitoring.

---

# 14. What is USE monitoring?

## Strong interview answer

USE focuses on resources:

```text
Utilization
Saturation
Errors
```

For example, for a CPU:

```text
Utilization
How busy is it?

Saturation
Is work waiting?

Errors
Are hardware/system errors occurring?
```

RED is often useful when thinking about services.

USE is useful when thinking about resources.

They are complementary approaches.

# 15. What is an alert?

## Strong interview answer

An alert is a notification triggered when a defined condition indicates something may require attention.

For example:

```text
HTTP 5xx > 5%
for 5 minutes
```

or:

```text
Disk available < 10%
```

A useful alert should normally answer:

```text
What happened?

Which system is affected?

How severe is it?

What should the responder investigate?
```

An alert that simply says:

```text
PRODUCTION ERROR
```

without context is much less useful.

---

# 16. What is the difference between an alert and an incident?

## Strong interview answer

Not every alert is an incident.

An alert is a signal.

An incident is an operational event that affects or threatens service reliability, security, or business operations and requires response.

For example:

```text
Alert:
CPU 90%

No customer impact.
Temporary batch job.
```

That may not become an incident.

But:

```text
Checkout failure rate 35%
Customers cannot pay
```

is clearly an incident.

---

# 17. What makes a good alert?

## Strong interview answer

A good alert is actionable.

It should have enough context to help the responder understand what requires investigation.

For example:

```text
Critical: Checkout 5xx Rate High

Environment: production
Service: checkout-api
Current 5xx rate: 12.8%
Threshold: 5%
Duration: 10 minutes
Dashboard: checkout-service
Runbook: checkout-5xx
```

Compare that with:

```text
ALERT: ERROR RATE HIGH
```

The first gives the engineer a starting point.

---

# 18. What is alert fatigue?

## Strong interview answer

Alert fatigue occurs when responders receive so many noisy, low-value, duplicate, or non-actionable alerts that important alerts become easier to miss.

For example:

```text
02:01 CPU alert
02:02 CPU alert
02:03 memory alert
02:03 pod alert
02:04 application alert
02:05 another CPU alert
```

All five may represent the same underlying incident.

Too many alerts reduce signal quality.

A good monitoring system should help engineers identify meaningful conditions rather than simply notify them about every metric fluctuation.

---

# 19. An alert fires and then resolves 30 seconds later. It happens repeatedly. What is this called?

## Strong interview answer

This is commonly called a flapping alert.

For example:

```text
Threshold = CPU > 80%

79%
81% ALERT
78% RESOLVED
82% ALERT
79% RESOLVED
```

I would investigate the actual behavior before simply increasing the threshold.

Possible improvements include:

```text
Require condition to persist
Use better aggregation
Choose a more meaningful signal
Adjust thresholds based on normal behavior
```

For example:

```text
CPU > 80%
for 10 minutes
```

may be more meaningful than alerting on a single short spike, depending on the workload.

---

# 20. Why is using `for` useful in Prometheus alerts?

## Strong interview answer

It can require the alert condition to remain true for a specified duration before firing.

For example:

```yaml
expr: cpu_usage > 90
for: 10m
```

This means:

```text
CPU > 90%
continuously for 10 minutes
```

rather than:

```text
CPU briefly touches 91%
→ wake someone up
```

However, the appropriate duration depends on the signal.

For some conditions, waiting ten minutes would be unacceptable.

---

# 21. What is an SLI?

## Strong interview answer

An SLI, or Service Level Indicator, is a measurable indicator of service behavior.

Examples:

```text
Availability
Latency
Error rate
Successful request percentage
```

For example:

```text
Successful HTTP requests
------------------------
Total valid HTTP requests
```

could be an availability SLI.

SLIs should reflect something meaningful about service reliability.

---

# 22. What is an SLO?

## Strong interview answer

An SLO, or Service Level Objective, defines a target for an SLI.

For example:

```text
99.9% successful requests
over 30 days
```

The SLI is the measurement.

The SLO is the target.

```text
SLI:
99.94% availability

SLO:
>= 99.9%
```

---

# 23. What is an SLA?

## Strong interview answer

An SLA is a service-level agreement, typically a formal agreement defining expected service levels and potentially consequences if they are not met.

I distinguish:

```text
SLI
What we measure

SLO
What reliability target we aim for

SLA
What has been formally agreed
```

---

# 24. What is an error budget?

## Strong interview answer

An error budget represents the amount of unreliability allowed by an SLO.

For example, if the objective is:

```text
99.9% availability
```

then some unavailability is still permitted within the measurement period.

Teams can use the remaining error budget to make decisions about:

```text
Release velocity
Reliability work
Risk
Operational changes
```

The idea is to balance reliability with development rather than assuming the target must always be 100 percent.

---

# 25. What is the difference between average latency and percentile latency?

## Strong interview answer

An average can hide poor experiences affecting a subset of users.

Suppose:

```text
900 requests = 100 ms
100 requests = 4 seconds
```

The average gives some information, but it does not clearly describe the slower tail.

Percentiles help.

For example:

```text
p50 = 110 ms
p95 = 1.2 sec
p99 = 4 sec
```

This tells me that the slowest portion of requests has a much worse experience.

For production systems, p95 and p99 are often more useful than relying only on averages.

# 26. CPU reaches 95 percent. What do you do?

## Strong interview answer

I do not immediately restart the server.

First I determine:

```text
Which server?

Which process?

How long?

Is it one server or the fleet?

Did traffic increase?

Did a deployment occur?

Are users affected?
```

On Linux I might start with:

```bash
top
```

or:

```bash
ps aux --sort=-%cpu | head
```

I also inspect historical metrics.

I want to know whether this is:

```text
Normal workload
Traffic spike
Runaway process
Scheduled job
Application bug
Autoscaling problem
Attack
Resource undersizing
```

CPU utilization is a symptom, not automatically the root cause.

---

# 27. CPU is 100 percent, but users are not affected. Is it an incident?

## Strong interview answer

Not necessarily.

High utilization alone does not prove customer impact.

I would check:

```text
Latency
Error rate
Request throughput
Queueing
Load
Saturation
Application health
```

A CPU-intensive batch workload may legitimately use available capacity.

On the other hand, 100 percent CPU combined with:

```text
Latency rising
Requests timing out
Queue growing
```

is much more concerning.

# 28. CPU is only 40 percent, but the application is extremely slow. What could cause that?

## Strong interview answer

Many bottlenecks do not require high CPU.

I would investigate:

```text
Database latency
Disk I/O
Network latency
External APIs
Locks
Connection pools
Thread pools
Queue depth
DNS
Memory pressure
Garbage collection
Downstream services
```

For example:

```text
Application CPU
40%

Database query
8 seconds
```

The application may spend most of its time waiting rather than computing.

Low CPU does not prove good performance.

---

# 29. Memory utilization is 95 percent. What do you investigate?

## Strong interview answer

First I determine what the number actually means.

On Linux, memory usage needs context because memory may be used for caches and buffers.

I would inspect:

```bash
free -h
```

and:

```bash
ps aux --sort=-%mem | head
```

I would also check:

```text
Available memory
Swap activity
OOM events
Process growth
Container limits
Application behavior
```

I would not assume that:

```text
95% memory shown
=
95% dangerous memory pressure
```

without understanding how the metric is calculated.

---

# 30. How do you investigate an Out Of Memory event?

## Strong interview answer

I would inspect kernel and application evidence.

For example:

```bash
dmesg | grep -i oom
```

or system logs.

I want to identify:

```text
Which process was killed?

How much memory was it using?

Was memory usage gradually increasing?

Was there a sudden workload spike?

Was the container limit too low?

Was there a memory leak?

Did another process consume the node?
```

For containers or Kubernetes, I would also distinguish:

```text
Container memory limit
```

from:

```text
Node memory exhaustion
```

because they require different investigation paths.

---

# 31. Disk usage reaches 95 percent. What do you do?

## Strong interview answer

First identify which filesystem is affected.

```bash
df -h
```

Then determine what is consuming the space.

For example:

```bash
du -xhd1 /var
```

or more targeted inspection.

Common causes include:

```text
Application logs
System logs
Container logs
Old releases
Temporary files
Core dumps
Backups
Database files
Container images
```

I also check inode usage:

```bash
df -i
```

because a filesystem can fail to create files even when byte capacity remains if the inodes are exhausted.

---

# 32. Why might `df -h` and `du` show different disk usage?

## Strong interview answer

One common reason is deleted files that are still open by a running process.

For example:

```text
Application writes 50 GB log

Engineer deletes log

Process still holds file descriptor

du:
file gone

df:
space still allocated
```

I might investigate with:

```bash
lsof +L1
```

or appropriate `lsof` queries.

Restarting the process may release the file descriptor, but I would understand the application impact before doing so.

---

# 33. What is inode exhaustion?

## Strong interview answer

A filesystem has a finite number of inodes used to represent files and directories.

A system can therefore have:

```text
20 GB free
```

but still fail to create new files because:

```text
0 free inodes
```

I check:

```bash
df -i
```

This can happen when an application creates huge numbers of tiny files.

---

# 34. Disk space is fine, but the application is slow. Could disk still be the problem?

## Strong interview answer

Yes.

Capacity and performance are different.

The disk could have:

```text
High I/O wait
High latency
High queue depth
Low IOPS capacity
Storage throttling
```

while still having plenty of free space.

I would inspect storage performance metrics rather than only:

```text
df -h
```

---

# 35. What is load average?

## Strong interview answer

Linux load average gives information about demand for CPU and tasks waiting in relevant states over time.

Commands such as:

```bash
uptime
```

may show:

```text
load average: 2.1, 4.8, 9.3
```

I interpret load relative to the system.

A load of 8 means something very different on:

```text
2 CPU system
```

versus:

```text
64 CPU system
```

I also correlate load with CPU, I/O, process state, and workload rather than treating load average as a standalone health score.

---

# 36. A server has high load but low CPU utilization. What might be happening?

## Strong interview answer

Tasks may be waiting rather than actively consuming CPU.

For example:

```text
Disk I/O
Network filesystem
Storage latency
Uninterruptible sleep
```

I would inspect process states and I/O metrics.

This is why:

```text
High load
!=
Automatically high CPU
```

---

# 37. What is a health check?

## Strong interview answer

A health check evaluates whether a service or application is functioning sufficiently for a specific purpose.

For example:

```text
GET /health
```

may return:

```text
200 OK
```

But health checks should be designed carefully.

A health endpoint that always returns 200 even when the application cannot reach its database is not necessarily useful.

---

# 38. What is the difference between liveness and readiness?

## Strong interview answer

In Kubernetes:

Liveness asks:

```text
Should this container be restarted?
```

Readiness asks:

```text
Should this Pod currently receive traffic?
```

For example:

```text
Application process alive
but database migration still running
```

The Pod may be:

```text
Live
but
Not Ready
```

Restarting it may be unnecessary.

It simply should not receive production traffic yet.

---

# 39. Customers report errors, but every health check is green. How is that possible?

## Strong interview answer

Health checks may be too shallow.

For example:

```text
/health
returns 200
```

because the application process is running.

But:

```text
Payment API
X

Database
X

Authentication service
X
```

may still be broken.

Other possibilities include:

```text
Only one customer path affected
Specific region affected
Specific API endpoint affected
Cached health response
Load balancer checking different behavior
```

Green health checks do not prove every user journey works.

# 40. What is synthetic monitoring?

## Strong interview answer

Synthetic monitoring simulates user or system interactions to verify functionality.

For example:

```text
Open website
        |
        v
Log in
        |
        v
Search product
        |
        v
Add to cart
        |
        v
Checkout test
```

This can detect problems that basic infrastructure metrics or shallow health checks miss.

# 41. What is black-box monitoring?

## Strong interview answer

Black-box monitoring evaluates a system from the outside without relying on internal implementation details.

For example:

```text
Can I reach the website?

Does HTTPS work?

Does DNS resolve?

Does the endpoint return expected status?

How long does the request take?
```

This represents the external experience.

---

# 42. What is white-box monitoring?

## Strong interview answer

White-box monitoring uses internal system information.

For example:

```text
CPU
Heap
Thread count
Database connections
Queue depth
Application metrics
Garbage collection
```

Both are valuable.

A service may look internally healthy while being unreachable externally.

Or it may be externally available while an internal resource approaches exhaustion.

# 44. HTTP 500 errors suddenly increase. What do you investigate?

## Strong interview answer

First determine:

```text
Which service?
Which endpoint?
Which users?
When did it start?
How large is the increase?
```

Then correlate:

```text
Application logs
Deployment history
Database errors
Dependency failures
Resource metrics
Traces
```

For example:

```text
14:02 deployment completed
14:04 HTTP 500 rises
14:04 database errors appear
```

That correlation gives me a strong investigation direction.

# 45. What is correlation in incident investigation?

## Strong interview answer

Correlation means examining signals and events together to find relationships.

For example:

```text
10:00 deployment
10:02 memory increases
10:04 latency increases
10:06 error rate increases
```

This is more useful than viewing each graph independently.

Important events to correlate include:

```text
Deployments
Configuration changes
Autoscaling
Traffic
Infrastructure changes
Dependency incidents
Scheduled jobs
Feature flags
```

---

# 46. Does correlation prove causation?

## Strong interview answer

No.

If an error begins immediately after deployment, the deployment becomes a strong suspect.

But I still need evidence.

For example:

```text
Deployment at 12:00
Database outage at 12:01
Application errors at 12:01
```

The timing alone could incorrectly blame the deployment.

I use correlation to prioritize investigation, not as automatic proof.

---

# 47. What should you check first when an alert fires?

## Strong interview answer

My first priorities are:

```text
1. Is the alert valid?

2. What is affected?

3. Are users affected?

4. How severe is the impact?

5. Is the problem getting worse?

6. What changed recently?
```

Then I investigate the relevant technical signals.

I avoid spending twenty minutes finding root cause while ignoring an obvious mitigation that could restore service.

---

# 48. What is the difference between mitigation and root-cause resolution?

## Strong interview answer

Mitigation reduces or removes immediate impact.

Root-cause resolution fixes the underlying cause.

For example:

```text
Bad release
      |
      v
Checkout failing
```

Mitigation:

```text
Rollback release
```

Customers recover.

Root-cause work:

```text
Find defective code
Fix it
Test it
Improve deployment controls
```

During a serious incident:

```text
Restore service
```

often takes priority over:

```text
Perfectly understand every detail.
```

# 49. An alert says a production server is down. How do you verify it?

## Strong interview answer

I would verify using independent evidence.

Depending on the environment:

```text
Monitoring target state
Cloud instance state
Network reachability
SSH
Load balancer target health
Application health check
Logs
```

I want to distinguish:

```text
Server actually down
```

from:

```text
Monitoring cannot reach server.
```

Those are different incidents.

# 50. Prometheus says a target is DOWN. What does that mean?

## Strong interview answer

It generally means Prometheus cannot successfully scrape the target.

That does not automatically mean the application itself is completely down.

I investigate:

```text
Is the target correct?

Does DNS resolve?

Can Prometheus reach the endpoint?

Is the metrics port open?

Does /metrics respond?

Is authentication required?

Did network policy change?

Did service discovery change?
```

The monitoring path itself can fail.

# 51. How would you troubleshoot a missing Prometheus target?

## Strong interview answer

I follow the collection path:

```text
Application
     |
     v
Metrics endpoint
     |
     v
Service discovery
     |
     v
Prometheus target
     |
     v
Scrape
     |
     v
Stored metric
```

I determine where the chain breaks.

For Kubernetes I might inspect:

```bash

kubectl get svc
kubectl get endpoints
```

Then verify the metrics endpoint from an appropriate location.

I also inspect Prometheus target information and configuration.

# 60. What is cardinality in Prometheus?

## Strong interview answer

Cardinality refers to the number of unique time series created by metric label combinations.

For example:

```text
http_requests_total{
  method="GET",
  status="200"
}
```

has controlled label values.

But adding:

```text
user_id
request_id
email
```

can create huge numbers of unique series.

For example:

```text
10 million users
→ potentially millions of label values
```

High cardinality can increase memory, storage, and query costs.

Identifiers such as request IDs generally belong in logs or traces rather than metric labels.

# 61. Why is `request_id` usually a bad Prometheus label?

## Strong interview answer

Because request IDs are highly unique.

If every request creates a new label value:

```text
request_id=a1
request_id=a2
request_id=a3
...
```

the number of time series can explode.

Metrics should normally use bounded dimensions such as:

```text
service
environment
method
status
region
```

High-uniqueness identifiers are better suited to logs and traces.

# How to Answer Monitoring Questions in a Real Interview

If the interviewer says:

> "CPU is 95 percent. What would you do?"

Do not answer only:

> "I would check top and restart the process."

A stronger answer is:

> "I would first establish whether the CPU increase is sustained, which hosts and processes are affected, and whether there is customer impact through latency or error rates. I would correlate the start time with traffic, deployments, scheduled jobs, and other changes. On the host I could use tools such as top or ps to identify the consuming process. Then I would determine whether the utilization represents legitimate demand, a runaway process, application regression, insufficient scaling, or another condition. If users are affected, I would choose the safest mitigation while continuing root-cause investigation."

If the interviewer asks:

> "Grafana shows no data. What do you do?"

A stronger answer is:

> "I would separate the visualization layer from the collection layer. First I would verify whether Prometheus is scraping the targets and whether the expected metric exists directly in Prometheus. If it does, I would investigate the Grafana data source, PromQL query, time range, dashboard variables, and label filters. If Prometheus does not contain the metric, I would move backward through the scrape path, including service discovery, connectivity, the metrics endpoint, and application instrumentation."

If the interviewer asks:

> "Customers report the application is down, but your dashboard is green."

A stronger answer is:

> "I would treat the customer report as evidence that our monitoring may not represent the user journey. I would verify the application externally, inspect traffic, errors, latency, and business-level signals, and follow the complete request path through DNS, load balancers, services, and dependencies. I would also review why the existing health checks remained green and determine whether synthetic monitoring or stronger application-level SLIs are needed."
