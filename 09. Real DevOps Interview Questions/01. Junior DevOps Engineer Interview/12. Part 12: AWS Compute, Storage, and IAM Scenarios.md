# Part 12: AWS Compute, Storage, and IAM Scenarios

AWS interviews become much more interesting when the interviewer stops asking:

"What is EC2?"

"What is S3?"

"What is IAM?"

Those questions test definitions.

Real technical interviews often sound more like this:

> "Your EC2 instance is running, but nobody can SSH into it. Walk me through your investigation."

Or:

> "An application running on EC2 suddenly receives AccessDenied when uploading objects to S3. Nothing changed in the application code. What would you check?"

Or:

> "A production EC2 instance is running out of disk space. The EBS volume was expanded from 100 GB to 200 GB, but Linux still reports 100 GB. Why?"

Or:

> "A developer says they have AdministratorAccess but still cannot perform an action. How is that possible?"

These questions test whether you can connect AWS infrastructure concepts to actual production symptoms.

A useful mental model is:

```text
Application
    ↓
EC2 / Compute
    ↓
Operating System
    ↓
IAM Identity / Role
    ↓
AWS API
    ↓
S3 / EBS / Other AWS Service
```

When something fails, your job is not to randomly change security groups or attach AdministratorAccess.

Your job is to identify which layer is failing.

---

# 1. An EC2 instance shows Running, but you cannot SSH into it. How would you troubleshoot?

## Strong interview answer

I would troubleshoot from the outside toward the instance.

First, I would verify that I am connecting to the correct destination.

```text
ssh
 ↓
Public IP / DNS
 ↓
Route
 ↓
Internet Gateway
 ↓
Security Group
 ↓
Network ACL
 ↓
EC2 network interface
 ↓
sshd
 ↓
Linux user / key
```

I would check:

1. Does the instance have the expected public IPv4 address or reachable private address?
2. Is it in the expected subnet?
3. Does the route table provide the required path?
4. Does the security group allow TCP 22 from my source?
5. Are NACLs permitting the traffic?
6. Is the instance healthy?
7. Is SSH actually running?
8. Am I using the correct username?
9. Am I using the correct private key?
10. Is the OS firewall blocking the connection?

The error itself helps narrow the problem.

```text
Connection timeout
```

makes me think about networking first.

```text
Connection refused
```

suggests that the destination may be reachable, but SSH may not be listening or something is rejecting the connection.

```text
Permission denied (publickey)
```

means I have probably progressed much further through the network path and should investigate authentication.

I would not treat all three errors as the same problem.

---

# 2. What would cause an SSH timeout to an EC2 instance?

## Strong interview answer

Possible causes include:

* Security group does not allow TCP 22
* Incorrect source CIDR
* Missing public IP
* Incorrect route table
* No Internet Gateway for the intended public path
* NACL blocking traffic
* Corporate firewall blocking outbound SSH
* Instance networking issue
* Wrong IP address
* Private instance being accessed directly from the internet

I would first determine whether the architecture even intends the instance to be publicly reachable.

For example:

```text
Internet
   ↓
Public subnet
   ↓
EC2 with public IP
```

is different from:

```text
Internet
   X
Private subnet
   ↓
EC2
```

A private EC2 instance may require:

```text
VPN
Direct Connect
Bastion
SSM Session Manager
Other private connectivity
```

depending on the environment.

---

# 3. What is the difference between an EC2 public IP and private IP?

## Strong interview answer

The private IP is used within the VPC networking environment.

A public IPv4 address, when assigned, enables internet-routable addressing through AWS networking, assuming the rest of the network configuration supports it.

Having a public IP alone is not enough.

You may still need:

```text
Public IP
    +
Internet Gateway
    +
Correct route
    +
Security Group
    +
NACL
    +
Running service
```

So:

```text
EC2 has public IP
≠
EC2 is automatically reachable
```

---

# 4. An EC2 instance is in a public subnet. Does that automatically mean it is publicly accessible?

## Strong interview answer

No.

A subnet is generally considered public when its routing allows traffic toward an Internet Gateway.

But the instance also needs the appropriate addressing and security configuration.

For example:

```text
EC2
 ↓
Subnet route table
 ↓
0.0.0.0/0
 ↓
Internet Gateway
```

Even then, security groups and NACLs can restrict traffic.

The application itself must also be listening on the expected interface and port.

---

# 5. Your EC2 application works on localhost but cannot be reached remotely. What do you check?

## Strong interview answer

This is an important clue.

Suppose:

```bash
curl http://localhost:8080
```

works.

But:

```text
http://EC2-IP:8080
```

fails.

The application process is running.

Now I would check whether it is listening only on loopback.

For example:

```text
127.0.0.1:8080
```

instead of:

```text
0.0.0.0:8080
```

I would inspect:

```bash
ss -lntp
```

Then I would verify:

* Security group
* NACL
* Host firewall
* Route
* Application bind address

This prevents me from blaming AWS networking when the application itself is bound only to localhost.

---

# 6. What is the difference between an EC2 Security Group and a Network ACL?

## Strong interview answer

Security groups operate at the resource or network-interface level and are stateful.

Network ACLs operate at the subnet level and are stateless.

A simplified comparison:

```text
Security Group
Resource / ENI level
Stateful
Allow rules

Network ACL
Subnet level
Stateless
Allow and deny rules
```

Because NACLs are stateless, return traffic must also be permitted appropriately.

In normal troubleshooting, I usually inspect security groups first because they are commonly responsible for resource-level access.

But if the security group appears correct and traffic still fails, the subnet's NACL becomes part of the investigation.

---

# 7. Why does "the security group allows it" not prove connectivity should work?

## Strong interview answer

Because the security group is only one layer.

The complete path could include:

```text
Client
 ↓
Route
 ↓
Internet Gateway / NAT / VPN
 ↓
NACL
 ↓
Security Group
 ↓
EC2
 ↓
OS firewall
 ↓
Application
```

Any one of those layers can break communication.

A correct security group proves only that the security group is not intentionally blocking the specific allowed traffic.

It does not prove the rest of the path.

# 8. An EC2 instance passed the system status check but failed the instance status check. What does that suggest?

## Strong interview answer

AWS EC2 status checks help distinguish underlying AWS infrastructure problems from instance-level problems.

Broadly:

```text
System status check
→ underlying AWS infrastructure

Instance status check
→ guest instance / operating system reachability
```

An instance-level failure could relate to:

* OS boot problems
* Network configuration
* Exhausted memory
* Filesystem problems
* Kernel problems
* Incorrect network configuration

I would inspect the instance console information, system logs, monitoring data, and recovery options appropriate to the environment.

# 9. CPU usage on an EC2 instance suddenly stays near 100 percent. What would you do?

## Strong interview answer

First, I would confirm whether the CPU saturation is real and determine when it started.

Then I would correlate:

```text
CPU spike
with
deployment?
traffic increase?
scheduled job?
runaway process?
attack?
autoscaling failure?
```

At the operating system level:

```bash
top
```

or:

```bash
ps aux --sort=-%cpu | head
```

could help identify the process.

I would also check CloudWatch metrics.

Then determine whether the problem is:

```text
Application inefficiency
Traffic growth
Bad deployment
Undersized instance
Infinite loop
Background process
CPU credit exhaustion on burstable instances
```

The fix depends on the cause.

Scaling up without understanding the reason may temporarily hide the problem.

# 10. What are CPU credits on burstable EC2 instances?

## Strong interview answer

Burstable instance families can operate around a baseline CPU level and use accumulated CPU credits to burst above that baseline.

This matters because an application may initially perform well under sustained CPU demand but later experience different behavior when its credit situation changes, depending on the instance type and mode.

If a burstable instance shows performance degradation during sustained CPU usage, I would inspect the relevant CPU credit metrics and configuration.

This is different from assuming:

```text
CPU problem
=
application bug
```

The instance family's performance model matters.

# 11. How would you choose an EC2 instance type?

## Strong interview answer

I would choose based on workload characteristics rather than simply selecting a large instance.

I would consider:

* CPU
* Memory
* Network throughput
* Storage requirements
* Architecture compatibility
* Accelerators
* Traffic patterns
* Baseline versus burst behavior
* Cost
* Availability requirements

For example:

```text
CPU-intensive workload
→ compute-oriented family may fit

Memory-heavy database/cache
→ memory-oriented family may fit

General web application
→ general-purpose may fit
```

Then I would validate the decision using actual metrics.

# 12. A production EC2 server runs out of memory. What happens?

## Strong interview answer

The symptoms depend on the operating system and workload.

Linux may invoke the OOM killer and terminate processes.

I would investigate:

```bash
free -m
```

```bash
top
```

and relevant system logs.

I would identify whether memory usage came from:

* Memory leak
* Traffic growth
* Incorrect application configuration
* Oversized cache
* Too many worker processes
* New deployment
* Undersized instance

CloudWatch provides standard EC2 metrics, but detailed guest memory metrics normally require an agent or another monitoring mechanism because AWS cannot infer all operating system memory details from outside the instance.

That distinction is important.

---

# 13. Why doesn't standard EC2 CloudWatch monitoring automatically show Linux memory utilization?

## Strong interview answer

Because CPU usage can be observed at the hypervisor/infrastructure level, while guest OS memory utilization requires information from inside the operating system.

For detailed metrics such as:

```text
Memory utilization
Disk filesystem utilization
Swap
Process-level information
```

teams commonly install and configure the CloudWatch Agent or another monitoring agent.

This is a common interview question because candidates often assume every Linux metric automatically appears in CloudWatch.

---

# 14. An EC2 root filesystem is 100 percent full. What do you do?

## Strong interview answer

First, I would determine what consumed the space.

```bash
df -h
```

Then:

```bash
du -xsh /* 2>/dev/null
```

and progressively inspect the large directories.

Common causes include:

* Application logs
* Container images
* Temporary files
* Package caches
* Core dumps
* Old artifacts
* Database files
* Deleted files still held open by processes

I would avoid immediately deleting random files.

I would identify the growth source, safely recover space, then correct the underlying retention or capacity problem.

---

# 15. You expanded an EBS volume from 100 GB to 200 GB, but `df -h` still reports 100 GB. Why?

## Strong interview answer

Increasing the EBS volume size does not necessarily automatically expand the partition and filesystem inside Linux.

Conceptually:

```text
EBS volume
100 GB → 200 GB
       ↓
Block device sees additional space
       ↓
Partition may need expansion
       ↓
Filesystem may need expansion
```

I would first inspect:

```bash
lsblk
```

Then determine the partition and filesystem type.

Depending on the layout, commands might involve tools such as:

```bash
growpart
```

and for ext4:

```bash
resize2fs
```

or for XFS:

```bash
xfs_growfs
```

But I would verify the actual disk, partition, mount point, and filesystem before running expansion commands.

Disk operations in production should not be guessed.

---

# 16. What is EBS?

## Strong interview answer

Amazon Elastic Block Store provides block storage commonly used with EC2.

From the operating system's perspective, an EBS volume behaves similarly to a block device.

Typical uses include:

```text
Root filesystem
Application data
Database storage
Persistent block storage
```

EBS volumes have characteristics such as:

* Volume type
* Size
* IOPS
* Throughput
* Availability Zone placement

The last point matters operationally.

---

# 17. Can you attach an EBS volume in one Availability Zone to an EC2 instance in another AZ?

## Strong interview answer

Normally, an EBS volume and the EC2 instance it attaches to must be in the same Availability Zone.

For example:

```text
EC2
us-east-1a

EBS
us-east-1b

Direct attachment
X
```

If I need to move the data, one approach may involve creating a snapshot and then creating a new volume in the required Availability Zone.

That distinction frequently appears in AWS interviews.

---

# 18. What is an EBS snapshot?

## Strong interview answer

An EBS snapshot is a point-in-time backup mechanism for EBS volumes stored and managed by AWS.

Snapshots can be used for:

* Backup
* Recovery
* Creating new EBS volumes
* Copying data across regions
* Migration workflows
* Disaster recovery

Snapshots are incremental after the initial snapshot, meaning AWS stores changed blocks relative to previous snapshots rather than duplicating the entire volume every time.

---

# 19. Does taking an EBS snapshot guarantee application-consistent database backups?

## Strong interview answer

Not automatically.

A storage-level snapshot captures block storage state, but applications such as databases may have in-flight writes or cached data.

For stronger application consistency, the backup process may need to coordinate with the database or application.

For example:

```text
Quiesce writes
or
Use database-native backup mechanism
or
Coordinate application consistency
      ↓
Snapshot
```

The exact method depends on the workload.

"Snapshot completed" does not automatically mean "database recovery has been fully validated."

---

# 20. An EBS volume has enough capacity, but the application experiences high disk latency. What would you investigate?

## Strong interview answer

Capacity and performance are different dimensions.

I would investigate:

* Volume type
* Provisioned IOPS
* Throughput
* Queue depth
* Workload pattern
* Instance EBS bandwidth limits
* Filesystem behavior
* Application I/O pattern

For example:

```text
500 GB free space
```

does not tell me whether the volume can deliver the required:

```text
IOPS
Throughput
Latency
```

A storage volume can have plenty of free capacity while being performance constrained.

---

# 21. What is the difference between EBS and instance store?

## Strong interview answer

EBS provides persistent block storage independent of the lifecycle of a specific EC2 host in ways instance store does not.

Instance store provides temporary block storage physically associated with the host.

A simplified distinction:

```text
EBS
Persistent block storage

Instance Store
Ephemeral local storage
```

Instance store can be useful for temporary data, caches, buffers, or workloads designed for ephemeral local storage.

I would not place irreplaceable data there without an architecture that replicates or persists it elsewhere.

---

# 22. What happens to EBS when an EC2 instance is terminated?

## Strong interview answer

It depends on the volume's `DeleteOnTermination` configuration.

Root volumes are commonly configured to be deleted on termination, although this behavior can be configured.

Additional volumes can have different settings.

Therefore I would not assume:

```text
Instance terminated
=
every attached EBS volume deleted
```

or:

```text
Instance terminated
=
every EBS volume preserved
```

I would verify the actual configuration.

---

# 23. A company accidentally terminated an EC2 instance. Can you recover it?

## Strong interview answer

The terminated EC2 instance itself cannot simply be started again like a stopped instance.

Recovery depends on what persisted outside the instance.

I would investigate:

* EBS volumes that survived
* EBS snapshots
* AMIs
* Infrastructure as Code
* Application deployment artifacts
* Database backups
* Auto Scaling configuration

A well-designed system should allow the compute instance to be recreated rather than treating the instance itself as irreplaceable.

---

# 24. What is the difference between stopping and terminating EC2?

## Strong interview answer

Stopping preserves the instance so it can generally be started again.

Termination removes the EC2 instance.

With EBS-backed instances:

```text
Stop
→ instance can later restart
→ EBS generally remains

Terminate
→ instance is deleted
→ volume behavior depends on DeleteOnTermination
```

Public IPv4 addressing can also change across stop/start depending on the addressing setup.

Persistent identity should not depend on an automatically assigned public IPv4 address.

---

# 25. What is an AMI?

## Strong interview answer

An Amazon Machine Image provides the information needed to launch EC2 instances.

It can represent a standardized machine baseline containing:

* Operating system
* Packages
* Configuration
* Application components, depending on the image strategy

Organizations often create standardized images to make server creation repeatable.

A good infrastructure model is:

```text
AMI
+
Launch configuration
+
User data / configuration
+
IAM role
+
Networking
=
Reproducible EC2 instance
```

rather than manually configuring every server.

---

# 26. What is EC2 user data?

## Strong interview answer

User data can provide initialization instructions to an EC2 instance, commonly executed through cloud-init on Linux images.

It can perform tasks such as:

```text
Install packages
Write configuration
Start services
Register application
Bootstrap agents
```

A common troubleshooting issue is:

> "The instance launched successfully, but the application was never installed."

I would inspect cloud-init/user-data logs and confirm whether the script actually completed.

EC2 `Running` does not mean user data succeeded.

---

# 27. Your EC2 user-data script did not work. What would you check?

## Strong interview answer

I would check:

* User-data content
* Script syntax
* cloud-init logs
* Network availability
* Package repository availability
* IAM permissions
* DNS
* Script exit codes
* Whether the script expected environment variables that were unavailable

Common Linux locations include cloud-init logs such as:

```text
/var/log/cloud-init.log
/var/log/cloud-init-output.log
```

The key distinction is:

```text
EC2 successfully launched
≠
bootstrap successfully completed
```

---

# 28. Why should you avoid putting AWS access keys directly into EC2 user data?

## Strong interview answer

Because long-lived credentials should not be embedded in bootstrap scripts or instance configuration.

For applications running on EC2, IAM roles are usually the preferred mechanism for obtaining temporary AWS credentials.

Instead of:

```text
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

I would prefer:

```text
EC2
 ↓
IAM Role
 ↓
Temporary credentials
 ↓
AWS API
```

This reduces the need to distribute and rotate static credentials manually.

---

# 29. What is an IAM role for EC2?

## Strong interview answer

An IAM role can be associated with an EC2 instance through an instance profile.

Applications on the instance can then obtain temporary credentials and call AWS APIs according to the role's permissions.

For example:

```text
EC2 application
      ↓
IAM role
      ↓
s3:GetObject
      ↓
S3 bucket
```

This is preferable to hardcoding an IAM user's access key into the application.

---

# 30. Your application on EC2 needs to read files from S3. How should you grant access?

## Strong interview answer

I would normally attach an appropriate IAM role to the EC2 instance.

The role should grant only the required S3 permissions.

For example, if the application only needs to read from:

```text
arn:aws:s3:::company-config/*
```

then I would avoid giving:

```text
s3:*
Resource: *
```

and instead grant something closer to:

```json
{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject"
  ],
  "Resource": "arn:aws:s3:::company-config/*"
}
```

The exact policy depends on the application's operations.

---

# 31. An EC2 instance has an IAM role allowing S3 access, but `aws s3 ls` still returns AccessDenied. What would you check?

## Strong interview answer

I would not immediately add more permissions.

First, determine:

```text
Which identity is actually making the request?
```

I could use:

```bash
aws sts get-caller-identity
```

Then investigate:

* Role policy
* Bucket policy
* Permission boundary
* Organizations SCP
* Explicit deny
* KMS permissions if encryption is involved
* S3 VPC endpoint policy if applicable
* Requested resource ARN
* Requested action
* Credentials being used by the CLI

A local AWS credentials file may cause the CLI to use credentials different from the EC2 role.

That is a common production issue.

---

# 32. Why is `aws sts get-caller-identity` so useful?

## Strong interview answer

Because before debugging authorization, I want to know who AWS thinks I am.

```bash
aws sts get-caller-identity
```

can help reveal the active identity.

This catches problems such as:

```text
Expected:
EC2 production role

Actual:
old developer IAM user
```

or:

```text
Expected:
deployment role

Actual:
different assumed role
```

Authorization troubleshooting begins with identity.

---

# 33. Explain IAM authentication versus authorization.

## Strong interview answer

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

For example:

```text
IAM user authenticates successfully
        ↓
Attempts s3:DeleteObject
        ↓
IAM evaluates permissions
        ↓
Allowed or denied
```

Successful authentication does not imply authorization to every AWS resource.

---

# 34. How does IAM decide whether an API request is allowed?

## Strong interview answer

At a high level, AWS evaluates the applicable policy context.

A useful simplified mental model is:

```text
Default
Implicit deny

Matching Allow
can permit request

Applicable Explicit Deny
overrides Allow
```

But real authorization can involve multiple policy types:

* Identity-based policies
* Resource-based policies
* Permissions boundaries
* Service Control Policies
* Session policies
* Resource-specific controls
* VPC endpoint policies in relevant architectures

So I avoid saying:

```text
"The IAM policy says Allow, therefore it must work."
```

That may be incomplete.

---

# 35. A user has AdministratorAccess but still receives AccessDenied. How is that possible?

## Strong interview answer

Because AdministratorAccess is not necessarily the final authority in every AWS organization or session context.

Possible causes include:

* Organizations SCP with an explicit deny
* Permissions boundary
* Session policy
* Resource-based policy behavior
* KMS key policy
* VPC endpoint policy
* Wrong identity
* Explicit deny elsewhere

For example:

```text
IAM identity policy
AdministratorAccess
       ↓
SCP
Deny ec2:TerminateInstances
       ↓
Request denied
```

The administrator policy cannot override an applicable explicit deny.

---

# 36. What is an IAM permissions boundary?

## Strong interview answer

A permissions boundary defines the maximum permissions that an identity-based policy can grant to an IAM user or role.

Suppose the role policy says:

```text
Allow:
s3:*
ec2:*
```

but its permissions boundary permits only:

```text
s3:GetObject
s3:ListBucket
```

The broader identity policy does not automatically escape the boundary.

A useful mental model is:

```text
Identity policy
"What permissions are granted?"

Boundary
"What is the maximum this identity can receive?"
```

---

# 37. What is an AWS Organizations Service Control Policy?

## Strong interview answer

SCPs provide permission guardrails for accounts in an AWS Organization.

They do not normally grant permissions by themselves.

Instead, they define what permissions can potentially be used within affected accounts or organizational units.

For example, an organization might deny:

```text
Leaving approved regions
Disabling security services
Deleting certain resources
```

Even an IAM administrator in the account can be constrained by an applicable SCP.

---

# 38. What is the principle of least privilege?

## Strong interview answer

Least privilege means granting only the permissions required to perform the intended task.

Instead of:

```text
Action: "*"
Resource: "*"
```

I would ask:

```text
Which service?
Which action?
Which resource?
Which environment?
Under what conditions?
```

For example:

```text
Production reporting application
needs:
s3:GetObject

for:
reports bucket

not:
s3:DeleteBucket
```

Least privilege reduces the blast radius of mistakes and compromised credentials.

---

# 39. Why is `Action: "*", Resource: "*"` dangerous?

## Strong interview answer

Because it gives extremely broad authority.

If those credentials are compromised, the attacker may gain access to many AWS operations and resources.

It also increases the impact of human mistakes.

Broad permissions sometimes appear during troubleshooting because someone says:

> "Just give it admin so we can see whether IAM is the problem."

That may temporarily answer a question, but it is risky and can become permanent technical debt.

I prefer to inspect the exact denied action and authorization context.

---

# 40. What is the difference between an IAM user and IAM role?

## Strong interview answer

An IAM user is an identity that can represent a person or workload, though AWS increasingly recommends federation and temporary credentials for human access.

An IAM role is assumed and provides temporary security credentials.

Roles are heavily used for:

* EC2
* Lambda
* ECS
* Cross-account access
* CI/CD
* Federated human access

For workloads, roles are generally preferable to distributing long-lived IAM user access keys.

---

# 41. Why are temporary credentials better than long-lived access keys?

## Strong interview answer

Temporary credentials expire.

That reduces the useful lifetime of leaked credentials.

With roles:

```text
Workload
 ↓
Assume / receive role credentials
 ↓
Temporary access
 ↓
Credentials expire
```

With long-lived static keys:

```text
Key created
 ↓
Stored somewhere
 ↓
Copied
 ↓
Possibly forgotten
 ↓
Potentially valid for months or years
```

Long-lived credentials require stronger rotation and secret-management discipline.

---

# 42. A developer accidentally commits an AWS access key to GitHub. What should happen?

## Strong interview answer

I would treat the credential as compromised.

The immediate priority is not simply deleting the Git commit.

The key may already have been copied.

The response should include:

1. Disable or delete the exposed credential.
2. Replace it where necessary.
3. Investigate CloudTrail and other relevant logs for unauthorized activity.
4. Determine the credential's permissions and blast radius.
5. Remove the secret from the repository history where appropriate.
6. Improve secret scanning and development controls.
7. Move the workload toward temporary credentials or a proper secrets mechanism.

The key principle is:

```text
Secret removed from Git
≠
Secret no longer compromised
```

# 43. What is S3?

## Strong interview answer

Amazon S3 is AWS object storage.

It stores data as objects inside buckets.

Common uses include:

* Static assets
* Backups
* Logs
* Data lakes
* Build artifacts
* Media
* Application files
* Archive workflows

S3 is object storage, not a normal block filesystem like EBS.

That distinction matters architecturally.

---

# 44. What is the difference between S3 and EBS?

## Strong interview answer

S3 is object storage.

EBS is block storage.

```text
S3
Bucket
 └── Objects

EBS
Block device
 ↓
Filesystem
 ↓
Files/directories
```

Use EBS when an EC2 workload needs block-level storage.

Use S3 when the application architecture fits object storage.

They solve different problems.

---

# 45. What is the difference between S3 and EFS?

## Strong interview answer

At a high level:

```text
S3
Object storage

EFS
Managed shared file storage

EBS
Block storage
```

EFS can provide a shared filesystem accessible by multiple compatible clients.

EBS commonly attaches as block storage to EC2.

S3 exposes object-storage APIs.

The right service depends on how the application reads and writes data.

---

# 46. An application uploads files to an EC2 local filesystem. Auto Scaling launches another instance and users cannot find their files. Why?

## Strong interview answer

The architecture treats local instance storage as if it were shared application storage.

Suppose:

```text
User uploads image
       ↓
EC2-A
/var/uploads/photo.jpg
```

The next request reaches:

```text
EC2-B
```

That server does not have the file.

In a horizontally scaled architecture, persistent shared data should normally be externalized.

Depending on requirements:

```text
Object files
→ S3

Shared filesystem
→ EFS

Database data
→ managed/persistent database architecture
```

Compute instances should ideally be replaceable.

---

# 47. An application receives `AccessDenied` when uploading to S3. What do you check?

## Strong interview answer

I would determine:

1. Which identity made the request?
2. Which S3 action failed?

# 48. Why might `s3:ListBucket` and `s3:GetObject` require different resource ARNs?

## Strong interview answer

Because bucket-level operations and object-level operations target different resources.

For example:

```text
s3:ListBucket
```

targets the bucket:

```text
arn:aws:s3:::company-data
```

while:

```text
s3:GetObject
```

targets objects:

```text
arn:aws:s3:::company-data/*
```

A common policy mistake is using the object ARN for a bucket-level action or vice versa.

```text
   ↓
```

```text
≠

```

# 54. What is S3 versioning?

## Strong interview answer

S3 Versioning allows multiple versions of an object to be preserved.

Versioning can help protect against:

I would inspect the object's versions rather than assuming the data is gone.

# 58. Why can S3 versioning unexpectedly increase storage cost?

## Strong interview answer

# 86. What is the EC2 Instance Metadata Service?

Organizations can enforce IMDSv2 for EC2 instances as part of their security baseline.

# 100. Production Scenario: EC2 Can Reach S3 but Cannot Download One Specific Object

The interviewer says:

> "The application can list an S3 bucket and download most files. One file consistently returns AccessDenied."

That evidence immediately tells me this is probably not a general EC2 networking failure.

```text
EC2 → S3
WORKS

List bucket
WORKS

Most GetObject requests
WORK

One object
FAILS
```

I would investigate what is unique about that object.

Possibilities include:

```text
Different encryption key
Different object ownership/history
Specific bucket-policy condition
Different prefix
Different object permissions
```

Suppose the object is encrypted with a customer-managed KMS key while the other objects use another encryption configuration.

The role has:

```text
s3:GetObject
```

but lacks permission to use the relevant KMS key.

The request becomes:

```text
EC2 role
   ↓
S3 GetObject
   ✓
Encrypted object
   ↓
KMS Decrypt
   X
AccessDenied
```

The correct fix is not:

```text
AmazonS3FullAccess
```

because S3 itself may already be correctly authorized.

The missing permission exists at another layer.

# Production Scenario 2: EC2 Disk Was Expanded but Production Is Still Full

At 09:00, monitoring reports:

```text
/var/lib/application
98% full
```

An engineer increases EBS from:

```text
100 GB
```

to:

```text
300 GB
```

The AWS console now reports:

```text
300 GB
```

but:

```bash
df -h
```

still reports approximately:

```text
100 GB
```

The engineer says:

> "AWS didn't resize the disk."

Not necessarily.

Check:

```bash
lsblk
```

Suppose the block device now shows 300 GB, but the partition and filesystem remain 100 GB.

The path is:

```text
EBS
100 → 300 GB
      ✓

Partition
100 GB
      X

Filesystem
100 GB
      X
```

The remaining expansion steps depend on the actual partition and filesystem layout.

The lesson:

```text
EBS volume size
≠
Filesystem size
```

# Production Scenario 3: The Security Group Was Correct

Users cannot reach:

```text
https://api.example.com
```

The EC2 security group allows:

```text
TCP 8080
from ALB security group
```

The team spends 30 minutes changing security-group rules.

Nothing works.

Eventually:

```bash
ss -lntp
```

shows:

```text
127.0.0.1:8080
```

The application is bound only to localhost.

The actual path:

```text
ALB
 ↓
EC2 network interface
 ↓
8080
 ↓
Application only listening on loopback
 X
```

The AWS network configuration was not the root cause.

This is why good cloud troubleshooting crosses the boundary between AWS and Linux.

# Production Scenario 4: The IAM Role Was Correct Too

An application should upload reports to:

```text
s3://production-reports
```

The EC2 role clearly allows the required S3 operation.

But:

```bash
aws sts get-caller-identity
```

returns an old IAM user.

Someone had placed credentials in:

```text
~/.aws/credentials
```

months earlier.

The AWS CLI credential provider chain selected those credentials instead of the expected instance-role credentials.

The team had been debugging the wrong IAM identity.

The lesson:

```text
Expected role
≠
Actual caller
```

Always establish identity before debugging authorization.

# Production Scenario 5: Auto Scaling Replacement Loop

An Auto Scaling Group should maintain four instances.

Monitoring shows:

```text
Launch
 ↓
Unhealthy
 ↓
Terminate
 ↓
Launch
 ↓
Unhealthy
 ↓
Terminate
```

The EC2 instances themselves boot correctly.

The ALB health check expects:

```text
/health
```

on:

```text
port 8080
```

But a new application version changed the endpoint to:

```text
/healthz
```

The ASG keeps replacing perfectly functional instances because the target group cannot verify them.

The actual failure:

```text
EC2
Running
✓

Application
Running
✓

Health-check path
Wrong
X

ALB marks target unhealthy
      ↓
ASG replacement
```

The correct fix is the health-check configuration, not increasing desired capacity.

# Production Scenario 6: The Administrator Who Wasn't Allowed

A cloud engineer has:

```text
AdministratorAccess
```

but cannot terminate an EC2 instance.

They assume AWS IAM is malfunctioning.

The organization has an SCP:

```text
Deny:
ec2:TerminateInstances
```

for the production OU.

The authorization model becomes:

```text
IAM identity policy
Allow
   ↓
SCP
Explicit Deny
   ↓
DENIED
```

AdministratorAccess does not override the organization's guardrail.

# Production Scenario 7: The S3 Bucket That "Lost" Files

A developer reports:

> "Yesterday there were 20,000 objects. Today many disappeared."

Before declaring data loss, investigate:

```text
Versioning
Lifecycle policies
Delete markers
Recent API calls
CloudTrail
Replication
Application deletion logic
```

Suppose a lifecycle rule was changed from:

```text
Expire after 365 days
```

to:

```text
Expire after 30 days
```

The storage system worked exactly as configured.

The incident was a configuration change.

This is why infrastructure configuration deserves the same review discipline as application code.

# Production Scenario 8: Private EC2 Lost S3 Access

The team moves EC2 instances from public subnets to private subnets.

Immediately:

```text
S3 requests timeout
```

IAM has not changed.

The role still allows S3.

But the old network path depended on internet connectivity that no longer exists in the new architecture.

The solution may involve:

```text
NAT
```

or preferably for appropriate S3 access:

```text
S3 Gateway VPC Endpoint
```

depending on requirements.

The lesson:

```text
IAM permission
≠
network connectivity
```

# Production Scenario 9: One Instance Behaves Differently

Four EC2 instances sit behind an ALB.

Users report intermittent failures.

Analysis shows:

```text
EC2-A ✓
EC2-B ✓
EC2-C X
EC2-D ✓
```

Compare EC2-C.

You discover:

```text
A → application v4.7
B → application v4.7
C → application v4.5
D → application v4.7
```

EC2-C was manually patched months ago and is no longer built from the standard image.

The incident is caused by configuration drift.

This is why production compute should be reproducible.

# Production Scenario 10: CPU Wasn't the Real Bottleneck

Traffic increases 200 percent.

The team doubles the number of EC2 instances.

Performance becomes worse.

Why?

All instances connect to the same database.

```text
Before

4 EC2
  ↓
Database
80% capacity
```

After scaling:

```text
12 EC2
  ↓
More connections
  ↓
Database
100% capacity
```

EC2 scaling increased pressure on the real bottleneck.

The lesson:

```text
More compute
≠
more application capacity
```

unless downstream systems can support the additional load.


```bash

```


# The AWS Troubleshooting Pattern to Remember

For EC2 connectivity:

```text
Client
 ↓
DNS / IP
 ↓
Route
 ↓
IGW / NAT / VPN
 ↓
NACL
 ↓
Security Group
 ↓
EC2
 ↓
OS Firewall
 ↓
Listening Port
 ↓
Application
```

For storage:

```text
Application
 ↓
Filesystem
 ↓
Partition
 ↓
Block Device
 ↓
EBS
 ↓
Volume performance
```

For S3:

```text
Application
 ↓
AWS credentials
 ↓
IAM authorization
 ↓
Network path
 ↓
S3 bucket
 ↓
Object
 ↓
KMS if encrypted
```

For IAM:

```text
Caller identity
 ↓
API action
 ↓
Resource
 ↓
Identity policy
 ↓
Resource policy
 ↓
Boundary
 ↓
SCP
 ↓
Session policy
 ↓
Other applicable controls
 ↓
Allow / Deny
```

The important interview habit is to stop saying:

```text
"It must be IAM."
```

or:

```text
"It must be the security group."
```

Instead say:

> "I would establish which layer is failing and use the evidence from each successful test to narrow the next step."

That sounds like someone who has actually operated infrastructure.

# What Junior DevOps Candidates Should Take From Part 12

You should be able to explain why:

```text
EC2 Running
≠
Application healthy
```

```text
Public subnet
≠
Instance automatically publicly reachable
```

```text
Security Group allows traffic
≠
End-to-end connectivity works
```

```text
EBS resized
≠
Filesystem automatically resized
```

```text
EBS has free capacity
≠
EBS has enough performance
```

```text
EC2 role has S3 permission
≠
Application is actually using that role
```

```text
s3:GetObject allowed
≠
KMS-encrypted object can necessarily be decrypted
```

```text
AdministratorAccess
≠
Every AWS API call must be allowed
```

```text
IAM Allow
≠
Applicable Explicit Deny disappears
```

```text
S3 access allowed
≠
Network path to S3 exists
```

```text
Auto Scaling launches instances
≠
Application becomes healthy
```

```text
More EC2 instances
≠
More end-to-end application capacity
```

A weak candidate says:

> "I would check the security group."

A stronger candidate says:

> "I would first identify whether the failure is DNS, routing, network filtering, host-level connectivity, or the application listener. If the request times out, I would inspect the network path. If I receive connection refused, I would verify the process and listening port. If SSH reaches authentication and returns public-key failure, I know much of the network path is already working."

A weak candidate says:

> "I would give the EC2 role S3FullAccess."

A stronger candidate says:

> "I would first run `aws sts get-caller-identity` to verify the actual caller. Then I would identify the denied API action and resource, inspect the identity policy and bucket policy, check for explicit denies, permissions boundaries, SCPs, endpoint policies, and KMS authorization where applicable. I would change only the permission proven to be missing."

That difference is what this series should teach.
