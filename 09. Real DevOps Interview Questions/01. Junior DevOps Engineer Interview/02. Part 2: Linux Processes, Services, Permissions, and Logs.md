# Part 2: Linux Processes, Services, Permissions, and Logs

Linux processes, services, permissions, and logs come up constantly in DevOps interviews because they sit at the center of day-to-day operations.

A junior DevOps engineer may not be expected to diagnose every complex kernel issue, but they should understand how Linux runs applications, how services are managed, how processes behave, how access is controlled, and where to look when something fails.

In a real interview, you may hear questions like:

* Why is this process still running?
* Why did the service fail?
* Why does the application work as root but fail as its service account?
* Why is the log file empty?
* Why does a process become a zombie?
* Why does a systemd service start manually but fail at boot?
* Why does a user have permission on a file but still cannot access it?

These questions test whether you understand how Linux behaves, not whether you memorized commands.

---

# Question 1: What is the difference between a process and a service in Linux?

## What the interviewer is testing

The interviewer wants to know whether you understand the basic relationship between running programs and long-running managed applications.

## Strong interview answer

A process is an instance of a running program.

For example, if I run:

```bash
python3 app.py
```

Linux creates a process for that command.

The process receives a PID, or process ID.

I can inspect it with:

```bash
ps aux
```

or:

```bash
ps -ef
```

A service is usually a long-running application or background process that is managed by the operating system, commonly through systemd on modern Linux distributions.

Examples include:

```text
sshd
nginx
docker
cron
postgresql
```

A service may consist of one or more processes.

For example:

```bash
systemctl status nginx
```

may show the main Nginx process and its worker processes.

So the relationship is:

```text
Program
   ↓
Process
   ↓
May be managed as a service
```

Not every process is a service.

For example:

```bash
ls
```

runs as a process briefly and exits.

But:

```text
nginx
```

usually runs continuously and is managed as a service.

## Interviewer follow-up

### "Can a service exist without a process?"

A service definition can exist even when the service is stopped.

For example:

```bash
systemctl status nginx
```

could show:

```text
inactive (dead)
```

The service is known to systemd, but there is currently no running Nginx service process.

# Question 2: How do you identify running processes on a Linux server?

## Strong interview answer

I can use several tools depending on what I am trying to learn.

A common starting point is:

```bash
ps aux
```

or:

```bash
ps -ef
```

To search for a specific process:

```bash
ps aux | grep nginx
```

A better option in many cases is:

```bash
pgrep nginx
```

or:

```bash
pgrep -a nginx
```

For a live interactive view:

```bash
top
```

If installed:

```bash
htop
```

To see process relationships:

```bash
pstree
```

or:

```bash
pstree -p
```

## What I would look for

I may want to know:

* PID
* Parent PID
* User running the process
* CPU usage
* Memory usage
* Process state
* Command
* Start time

For example:

```bash
ps -eo pid,ppid,user,%cpu,%mem,state,cmd
```

## Why parent process matters

Each process usually has a parent process.

The parent PID is called PPID.

For example:

```bash
ps -o pid,ppid,cmd -p 4821
```

might show:

```text
PID    PPID   CMD
4821   1      /usr/bin/python3 /opt/app/server.py
```

If the PPID is `1`, systemd or init may be the parent.

Understanding process relationships becomes useful when investigating:

* Services
* Child processes
* Zombie processes
* Restarting applications
* Shell jobs
* Supervisors

# Question 3: What is a PID, and why is it important during troubleshooting?

## Strong interview answer

PID means Process ID.

Linux assigns a unique PID to each running process.

If I need to inspect or control a process, I usually identify it by PID.

For example:

```bash
ps aux | grep java
```

Suppose I find:

```text
appuser  7421  95.0  21.2 ... java -jar app.jar
```

The PID is:

```text
7421
```

I can then inspect the process:

```bash
ps -fp 7421
```

View its environment where permissions allow:

```bash
tr '\0' '\n' < /proc/7421/environ
```

Inspect file descriptors:

```bash
ls -l /proc/7421/fd
```

Inspect open files:

```bash
lsof -p 7421
```

Check its command line:

```bash
tr '\0' ' ' < /proc/7421/cmdline
```

## Important interview point

A PID identifies the current process instance.

If the application restarts, it may receive a new PID.

So scripts that depend on a permanently fixed PID are usually fragile unless PID management is handled correctly.

# Question 4: What is the difference between `kill`, `kill -15`, and `kill -9`?

## Strong interview answer

The `kill` command sends a signal to a process.

By default:

```bash
kill PID
```

sends `SIGTERM`, signal 15.

So:

```bash
kill 7421
```

is typically equivalent to:

```bash
kill -15 7421
```

`SIGTERM` asks the process to terminate gracefully.

The application may be able to:

* Close connections
* Flush buffers
* Finish current operations
* Remove temporary files
* Shut down safely

`kill -9` sends `SIGKILL`.

```bash
kill -9 7421
```

SIGKILL cannot be caught or ignored by the process.

The kernel terminates the process immediately.

## Which should you use first?

Normally, I would try graceful termination first.

For example:

```bash
kill 7421
```

Then verify:

```bash
ps -p 7421
```

If the process does not terminate and I have confirmed that forceful termination is appropriate:

```bash
kill -9 7421
```

may be used.

## Why not always use `kill -9`?

Because it gives the application no opportunity to clean up.

That can potentially cause:

* Incomplete writes
* Temporary state left behind
* Interrupted transactions
* Improper shutdown
* Lost diagnostic information

A strong operational habit is:

```text
Understand
→ graceful stop
→ verify
→ force only when necessary
```

# Question 5: A process has become a zombie. What does that mean?

## Strong interview answer

A zombie process is a process that has finished executing but still has an entry in the process table because its parent has not yet collected its exit status.

A zombie is already dead in terms of execution.

It is not consuming CPU.

It usually consumes only a small process-table entry.

You may see a process state such as:

```text
Z
```

with:

```bash
ps aux
```

or:

```bash
ps -eo pid,ppid,state,cmd
```

Example:

```text
PID   PPID   S   CMD
5412  5100   Z   [worker] <defunct>
```

## Can you kill a zombie?

Normally, sending a signal to the zombie itself will not solve the problem because the process has already exited.

The problem is usually with the parent process not reaping the child correctly.

I would identify the parent:

```bash
ps -o pid,ppid,state,cmd -p 5412
```

Then inspect the parent process.

In some cases, restarting or correcting the parent application may be necessary.

## Why do interviewers ask this?

They want to see whether you understand process lifecycle rather than just knowing how to run `ps`.

# Question 6: What is an orphan process?

## Strong interview answer

An orphan process is a child process whose parent has exited while the child is still running.

Linux will normally re-parent the orphan to another process, traditionally PID 1 or a designated subreaper.

This is different from a zombie.

A zombie:

```text
Child has exited
Parent has not collected status
```

An orphan:

```text
Parent has exited
Child is still running
```

The distinction matters because candidates sometimes confuse the two.

# Question 7: A service is failing. How do you troubleshoot it with systemd?

## Strong interview answer

I would begin with:

```bash
systemctl status myservice
```

For example:

```bash
systemctl status nginx
```

This usually gives me:

* Whether the unit is loaded
* Whether it is active
* Main PID
* Exit code
* Recent log messages

Then I would inspect logs:

```bash
journalctl -u myservice
```

For the latest entries:

```bash
journalctl -u myservice -n 100
```

Follow live logs:

```bash
journalctl -u myservice -f
```

Current boot only:

```bash
journalctl -u myservice -b
```

If the service fails during startup, I would look for messages such as:

```text
Permission denied
Address already in use
Configuration syntax error
File not found
Environment variable missing
Dependency failed
```

## I would also inspect the unit definition

```bash
systemctl cat myservice
```

This tells me what systemd is actually trying to execute.

I may inspect:

* `ExecStart`
* `User`
* `Group`
* `WorkingDirectory`
* `Environment`
* `EnvironmentFile`
* `Restart`
* Dependencies

## Example

Suppose:

```bash
systemctl status myapp
```

shows:

```text
status=203/EXEC
```

I would inspect the `ExecStart` path.

Maybe the binary:

```text
/opt/myapp/server
```

does not exist.

Or it lacks execute permission.

Check:

```bash
ls -l /opt/myapp/server
```

Then continue from evidence.

# Question 8: What is the difference between `start`, `stop`, `restart`, `reload`, `enable`, and `disable` in systemd?

## Strong interview answer

Start:

```bash
systemctl start nginx
```

Starts the service now.

Stop:

```bash
systemctl stop nginx
```

Stops it now.

Restart:

```bash
systemctl restart nginx
```

Stops and starts the service.

Reload:

```bash
systemctl reload nginx
```

Asks the service to reload configuration without performing a full restart, if the service supports reload.

Enable:

```bash
systemctl enable nginx
```

Configures the service to start automatically according to its systemd target dependencies, commonly during boot.

Disable:

```bash
systemctl disable nginx
```

Removes that automatic startup configuration.

## Important distinction

This:

```bash
systemctl enable nginx
```

does not necessarily start the service immediately.

And:

```bash
systemctl start nginx
```

does not necessarily enable it for future boots.

If I want both:

```bash
systemctl enable --now nginx
```

can enable and start the service.

# Question 9: A service starts manually but does not start after reboot. What would you investigate?

## Strong interview answer

First, I would check whether the service is enabled:

```bash
systemctl is-enabled myservice
```

If it returns:

```text
disabled
```

that may explain why it does not automatically start.

But I would not stop there.

I would also inspect:

```bash
systemctl status myservice
```

and previous/current boot logs:

```bash
journalctl -u myservice -b
```

I would investigate startup dependencies.

For example, the service may require:

* Network availability
* Mounted filesystem
* Database
* Secret file
* Environment file
* Another service

The systemd unit might contain incorrect or missing dependency declarations.

For example:

```ini
After=network.target
```

or a more appropriate network-online dependency depending on the application.

Another possibility is that something exists when I start the service manually later but does not exist during early boot.

For example:

```text
/opt/app/config.env
```

may be created by another startup process.

This question is really testing whether I understand that boot-time execution and manual execution happen under different conditions.

# Question 10: An application works when you run it as root but fails when systemd starts it as `appuser`. Why?

This is a very common real-world scenario.

## Strong interview answer

If an application works as root but fails as a non-root service account, I immediately suspect permissions, ownership, environment differences, or access to privileged resources.

I would check the service account:

```bash
systemctl cat myapp
```

Look for:

```ini
User=appuser
Group=appuser
```

Then identify which file or operation fails from the logs:

```bash
journalctl -u myapp -n 100
```

Possible causes include:

* `appuser` cannot read configuration
* Cannot write logs
* Cannot access application directory
* Cannot bind to a privileged port
* Cannot read certificates
* Cannot access secrets
* Cannot write temporary files
* Different environment variables
* Different working directory
* Different `PATH`

## Example

Suppose the application needs:

```text
/etc/myapp/config.yaml
```

Check:

```bash
ls -l /etc/myapp/config.yaml
```

Then:

```bash
sudo -u appuser cat /etc/myapp/config.yaml
```

If that fails with permission denied, I have reproduced the problem under the service identity.

## Strong troubleshooting principle

Do not test only as root.

Test using the same user and environment as the failing application.

# Question 11: Explain Linux file permissions such as `rwxr-x---`.

## Strong interview answer

Linux permissions are generally represented for:

* Owner
* Group
* Others

Consider:

```text
rwxr-x---
```

Break it into:

```text
Owner:  rwx
Group:  r-x
Others: ---
```

Meaning:

Owner can:

* Read
* Write
* Execute

Group can:

* Read
* Execute

Others have no permission.

If I run:

```bash
ls -l script.sh
```

I might see:

```text
-rwxr-x--- 1 deploy devops 1200 Aug 11 09:00 script.sh
```

The owner is:

```text
deploy
```

The group is:

```text
devops
```

## Numeric representation

Permissions can also be represented numerically.

```text
read    = 4
write   = 2
execute = 1
```

So:

```text
rwx = 7
r-x = 5
--- = 0
```

Therefore:

```text
rwxr-x---
```

becomes:

```text
750
```

Example:

```bash
chmod 750 script.sh
```

# Question 12: What is the difference between `chmod`, `chown`, and `chgrp`?

## Strong interview answer

`chmod` changes permissions.

Example:

```bash
chmod 640 config.yaml
```

`chown` changes ownership.

Example:

```bash
chown appuser config.yaml
```

It can also change owner and group:

```bash
chown appuser:appgroup config.yaml
```

`chgrp` changes only the group.

Example:

```bash
chgrp appgroup config.yaml
```

## Real troubleshooting example

Suppose:

```bash
ls -l application.log
```

returns:

```text
-rw-r----- 1 root root 4052 Aug 11 10:00 application.log
```

But the application runs as:

```text
appuser
```

and needs to append to the file.

Changing permissions blindly to:

```bash
chmod 777 application.log
```

is not the right first response.

I would determine the intended ownership and access model.

For example:

```bash
chown appuser:appgroup application.log
```

might be more appropriate.

The exact fix depends on the application design.

# Question 13: A user owns a file but still gets permission denied. What else would you check?

## Strong interview answer

I would check the entire path, not only the file.

For example:

```text
/opt/apps/prod/config.yaml
```

The file may be readable:

```text
-rw-r----- appuser appgroup config.yaml
```

But if one parent directory does not allow traversal, the user still cannot access it.

I could inspect:

```bash
namei -l /opt/apps/prod/config.yaml
```

This shows permissions for each component in the path.

I would also consider:

* ACLs
* SELinux
* AppArmor
* Mount options
* Filesystem state
* User and group membership

## ACL check

If ACLs are used:

```bash
getfacl /path/to/file
```

A file can have permissions that appear correct through `ls -l` but still have additional ACL rules affecting access.

# Question 14: What is the difference between file permissions and directory permissions?

## Strong interview answer

The meaning of permissions changes slightly for directories.

For a file:

```text
r = read file contents
w = modify file contents
x = execute file
```

For a directory:

```text
r = list directory contents
w = create, remove, or rename entries
x = traverse or access items inside the directory
```

That execute permission on directories is especially important.

For example, a user may know that:

```text
/secure/config.yaml
```

exists.

The file itself may be readable.

But if the user lacks execute permission on:

```text
/secure
```

they may not be able to access the file.

This is why troubleshooting file access requires checking both the file and parent directories.

# Question 15: What are SUID, SGID, and the sticky bit?

For junior roles, interviewers may not expect deep security expertise, but basic understanding is useful.

## SUID

SUID on an executable allows the program to execute with the effective privileges of the file owner.

Example:

```text
-rwsr-xr-x
```

The `s` in the owner execute position indicates SUID.

A classic example historically involves utilities such as `passwd`, which may need controlled privileged access to update protected system files.

## SGID

On an executable, SGID can cause the program to run with the effective group of the file.

On a directory, SGID commonly causes newly created files to inherit the directory's group.

This can be useful for shared team directories.

Example:

```bash
chmod g+s /shared/devops
```

## Sticky bit

The sticky bit is commonly seen on shared writable directories such as:

```text
/tmp
```

Example:

```text
drwxrwxrwt
```

It prevents users from deleting files owned by other users simply because the directory is writable.

## Interview point

These special permissions affect access behavior beyond normal `rwx` permissions.

# Question 16: A user was added to a group, but still cannot access the files. What could be wrong?

## Strong interview answer

First, I would verify the user's groups:

```bash
id username
```

or:

```bash
groups username
```

If the user was recently added:

```bash
sudo usermod -aG devops username
```

the current login session may not immediately recognize the new supplementary group membership.

The user may need to log out and back in.

Another option in some cases is:

```bash
newgrp devops
```

But I would also verify the actual file group and permissions.

For example:

```bash
ls -l /shared/deployment.yaml
```

If the file is:

```text
-rw------- root root deployment.yaml
```

adding the user to `devops` does nothing because the file is not associated with that group and grants no group access.

Group membership is only useful if permissions are configured to use it.

# Question 17: Where do Linux logs usually come from?

## Strong interview answer

Logs can come from multiple sources.

Modern Linux systems commonly use `journald`, which can be queried with:

```bash
journalctl
```

Applications may also write directly to files under:

```text
/var/log
```

Examples may include:

```text
/var/log/syslog
/var/log/messages
/var/log/auth.log
/var/log/secure
```

The exact files depend on the Linux distribution and logging configuration.

Applications may also write their own logs:

```text
/var/log/nginx/
/var/log/apache2/
/var/log/myapp/
```

Containers and orchestrators may store or expose logs differently.

So I should not assume every application error will be in the same file.

The first question should be:

"How is this application configured to log?"

# Question 18: How would you use `journalctl` during troubleshooting?

## Strong interview answer

I would filter rather than reading the entire journal.

For a service:

```bash
journalctl -u nginx
```

Latest 100 lines:

```bash
journalctl -u nginx -n 100
```

Follow logs:

```bash
journalctl -u nginx -f
```

Current boot:

```bash
journalctl -b
```

Previous boot:

```bash
journalctl -b -1
```

Kernel messages:

```bash
journalctl -k
```

Only errors:

```bash
journalctl -p err
```

Since a specific time:

```bash
journalctl --since "2026-08-11 09:00:00"
```

Between two times:

```bash
journalctl \
  --since "2026-08-11 09:00:00" \
  --until "2026-08-11 09:30:00"
```

## Why time filtering matters

Suppose monitoring says the incident started at 09:17.

Instead of reviewing a full day of logs, I would focus around that time.

Troubleshooting improves when logs, deployments, alerts, and user reports are aligned on a timeline.

# Question 19: An application log file exists but remains empty even though the application is running. What could be happening?

## Strong interview answer

There are several possibilities.

The application may be:

* Logging to stdout instead
* Logging to journald
* Writing to another file
* Using a different environment-specific log path
* Unable to write because of permissions
* Buffering output
* Running with a logging level that suppresses messages
* Using log rotation and writing to another file descriptor

I would first inspect the application's configuration.

Then:

```bash
systemctl status myapp
```

and:

```bash
journalctl -u myapp
```

If it is running under systemd, stdout and stderr may be captured by journald.

I would also inspect file ownership:

```bash
ls -l /var/log/myapp/app.log
```

and directory permissions:

```bash
ls -ld /var/log/myapp
```

If necessary, I might inspect the process's open files:

```bash
lsof -p PID
```

That can tell me where the process is actually writing.

# Question 20: A log file keeps growing very quickly. How would you investigate?

## Strong interview answer

First, I would confirm the growth.

```bash
ls -lh application.log
```

Then monitor it:

```bash
watch -n 2 ls -lh application.log
```

or:

```bash
tail -f application.log
```

I would inspect what is being repeated.

For example:

```bash
tail -n 200 application.log
```

Maybe the application is repeatedly logging:

```text
Database connection failed
Retrying connection
Database connection failed
Retrying connection
```

Now the disk problem is only a symptom.

The real issue may be a retry loop caused by a database outage.

I would also check whether log rotation is configured.

Commonly:

```text
/etc/logrotate.conf
/etc/logrotate.d/
```

For example:

```bash
cat /etc/logrotate.d/myapp
```

## What I would avoid

I would not simply delete the file and consider the problem solved.

I need to answer two questions:

```text
Why did the log grow?
Why didn't retention or rotation control it?
```

# Question 21: What is log rotation and why is it important?

## Strong interview answer

Log rotation prevents log files from growing indefinitely.

A rotation policy may:

* Rename the current log
* Compress older logs
* Keep only a set number
* Remove old logs after a defined retention period
* Create a new active log file

Linux environments commonly use `logrotate`.

Example configuration:

```text
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
}
```

This could mean:

* Rotate daily
* Keep seven rotated logs
* Compress older logs
* Ignore missing files
* Do not rotate empty logs

## Production importance

Without log rotation, a noisy application can fill a filesystem.

Once the filesystem is full, unrelated services may start failing.

A simple logging issue can therefore become a larger outage.

# Question 22: A service keeps restarting every few seconds. How would you investigate?

## Strong interview answer

I would first check:

```bash
systemctl status myservice
```

Then:

```bash
journalctl -u myservice -n 200
```

I would inspect the systemd unit:

```bash
systemctl cat myservice
```

I would specifically look at:

```ini
Restart=
RestartSec=
```

For example:

```ini
Restart=always
RestartSec=5
```

could cause systemd to restart a failing process every five seconds.

But the restart policy is not necessarily the problem.

I need to determine why the application exits.

Possible causes:

* Bad configuration
* Missing secret
* Port conflict
* Permission problem
* Application crash
* Dependency unavailable
* Incorrect command
* Missing working directory

The correct investigation is:

```text
Why does the process exit?
```

not:

```text
Why does systemd keep restarting it?
```

unless the restart behavior itself is misconfigured.

# Question 23: What happens when a service reaches its restart limit in systemd?

## Strong interview answer

If a service repeatedly fails too quickly, systemd may stop attempting to restart it because of start-rate limiting.

You might see a message similar to:

```text
Start request repeated too quickly
```

I would inspect:

```bash
systemctl status myservice
```

and:

```bash
journalctl -u myservice
```

After fixing the underlying problem, I may need to reset the failed state:

```bash
systemctl reset-failed myservice
```

Then:

```bash
systemctl start myservice
```

But resetting the state without fixing the cause simply restarts the failure cycle.

# Question 24: What is the difference between foreground and background processes?

## Strong interview answer

A foreground process is attached to the current terminal session and normally receives input from it.

For example:

```bash
python3 server.py
```

runs in the foreground.

A background process can run without occupying the shell prompt.

For example:

```bash
python3 server.py &
```

The shell returns control while the process continues.

I can inspect shell jobs with:

```bash
jobs
```

Bring a job to the foreground:

```bash
fg
```

Send a suspended job to the background:

```bash
bg
```

## Important DevOps point

Running:

```bash
python3 server.py &
```

is not a good replacement for proper service management in production.

For production applications, tools such as systemd, containers, Kubernetes, or dedicated supervisors provide better lifecycle management, restart behavior, logging, and boot integration.

# Question 25: Why can a process terminate when you close your SSH session?

## Strong interview answer

A process started directly from an interactive shell may remain associated with that terminal session.

When the session ends, it may receive a hangup signal or otherwise lose its controlling terminal.

For temporary administrative tasks, tools such as:

```bash
nohup
```

can be used.

Example:

```bash
nohup ./long-running-job.sh > job.log 2>&1 &
```

Other tools such as:

```text
screen
tmux
```

can maintain interactive sessions across SSH disconnections.

But for production services, I would still prefer proper service management rather than relying on `nohup`.

# Question 26: How do you determine which user is running a process?

## Strong interview answer

I can use:

```bash
ps aux
```

or:

```bash
ps -o pid,user,group,cmd -p PID
```

For example:

```bash
ps -o pid,user,group,cmd -p 7821
```

might show:

```text
PID   USER      GROUP      CMD
7821  appuser   appgroup   /usr/bin/java -jar app.jar
```

This matters because permissions, file access, ports, secrets, and environment behavior depend on the process identity.

If an application is failing to read:

```text
/etc/myapp/secret
```

I should test using the user running the application, not my own administrative account.

For example:

```bash
sudo -u appuser cat /etc/myapp/secret
```

# Question 27: A process is running but the application is not responding. Does "running" mean "healthy"?

## Strong interview answer

No.

A running process only tells me that the operating system has not terminated that process.

The application could still be:

* Deadlocked
* Waiting on a dependency
* Stuck on I/O
* Listening on the wrong interface
* Returning errors
* Unable to connect to a database
* Out of worker threads
* Extremely slow
* Partially initialized

So:

```bash
systemctl status myapp
```

showing:

```text
active (running)
```

is not enough.

I would test the application itself.

For example:

```bash
curl -v http://localhost:8080/health
```

Then inspect logs:

```bash
journalctl -u myapp -n 100
```

Check listening ports:

```bash
ss -lntp
```

And investigate dependencies if necessary.

## Important interview principle

Process health and application health are not the same thing.

# Question 28: How would you find which process has a file open?

## Strong interview answer

I can use:

```bash
lsof /path/to/file
```

For example:

```bash
lsof /var/log/myapp/app.log
```

This may show:

```text
COMMAND  PID   USER     FD
java     8421  appuser  12w
```

I can also inspect file descriptors under:

```text
/proc/PID/fd
```

For example:

```bash
ls -l /proc/8421/fd
```

This is useful when investigating:

* Deleted files still consuming disk space
* Log rotation problems
* Files that cannot be unmounted
* Applications holding configuration or data files open

# Question 29: How would you find which process is listening on a port?

## Strong interview answer

I would commonly use:

```bash
ss -lntp
```

For port 8080:

```bash
ss -lntp | grep :8080
```

If permitted, the output may identify:

* Listening address
* Port
* PID
* Process name

Another option:

```bash
lsof -i :8080
```

For example:

```bash
lsof -iTCP:8080 -sTCP:LISTEN
```

This is useful if an application fails with:

```text
Address already in use
```

because I can determine which existing process owns that port.

# Question 30: A service failed immediately after a configuration change. What should you do?

## Strong interview answer

First, I would avoid making additional random changes.

I would identify exactly what changed.

If possible, I would validate the configuration syntax before restarting.

For example, Nginx provides:

```bash
nginx -t
```

A typical workflow might be:

```text
Configuration changed
        ↓
Validate configuration
        ↓
Review diff
        ↓
Reload/restart
        ↓
Check service status
        ↓
Check logs
        ↓
Test application
```

If the new configuration is invalid and service is unavailable, I would restore the last known working configuration through the organization's change or rollback process.

## Why `diff` matters

Suppose I have:

```text
nginx.conf
nginx.conf.backup
```

I can compare:

```bash
diff -u nginx.conf.backup nginx.conf
```

In real production environments, configuration should ideally be version controlled, making this even easier.

The important point is that troubleshooting should include recent changes.

# Question 31: How do you investigate authentication or permission failures using logs?

## Strong interview answer

I would first identify the exact operation and user.

For SSH authentication, relevant information may be available through:

```bash
journalctl -u sshd
```

or:

```bash
journalctl -u ssh
```

Depending on the distribution, authentication information may also be stored in files such as:

```text
/var/log/auth.log
```

or:

```text
/var/log/secure
```

I would correlate:

* Timestamp
* Username
* Source
* Authentication method
* Failure reason

For application permission failures, I would inspect application logs and system security logs where relevant.

I would not change permissions before understanding why access was denied.

# Question 32: What is the difference between standard output and standard error?

## Strong interview answer

Linux processes commonly have three standard streams:

```text
0 = stdin
1 = stdout
2 = stderr
```

Standard output is normally used for regular program output.

Standard error is normally used for error messages.

For example:

```bash
command > output.txt
```

redirects standard output.

This:

```bash
command 2> error.txt
```

redirects standard error.

This:

```bash
command > output.txt 2>&1
```

redirects both stdout and stderr into the same file.

This becomes especially useful when troubleshooting scripts, cron jobs, systemd commands, and CI/CD pipelines.

# Final Production Interview Scenario

An interviewer gives you this situation:

> "A Java application running as a systemd service suddenly stops serving traffic after a deployment. `systemctl status` shows the service is repeatedly restarting. The application works when an administrator manually runs the JAR as root. Walk me through your investigation."

A strong junior candidate should not jump directly to one conclusion.

A good investigation may look like this.

First:

```bash
systemctl status myapp
```

Determine:

* Is the service actually restarting?
* What is the exit status?
* What command is being executed?
* Which user runs it?

Then:

```bash
journalctl -u myapp -n 200
```

Look for the actual error.

Suppose the log says:

```text
java.nio.file.AccessDeniedException:
/opt/myapp/config/application.yaml
```

Now inspect the systemd unit:

```bash
systemctl cat myapp
```

Suppose it contains:

```ini
User=appuser
Group=appuser
```

Now inspect the configuration:

```bash
ls -l /opt/myapp/config/application.yaml
```

Suppose you see:

```text
-rw------- 1 root root application.yaml
```

That explains why:

```bash
java -jar app.jar
```

works as root but fails when systemd runs it as `appuser`.

Before changing anything, verify:

```bash
sudo -u appuser cat /opt/myapp/config/application.yaml
```

If that returns permission denied, you have reproduced the issue.

The correct fix should reflect the intended security model.

For example, the file may need appropriate ownership or group access.

After correcting the access:

```bash
systemctl restart myapp
```

Then validate:

```bash
systemctl status myapp
```

Check logs:

```bash
journalctl -u myapp -n 50
```

Confirm listening port:

```bash
ss -lntp | grep :8080
```

Finally test the application:

```bash
curl -f http://localhost:8080/health
```

The strongest interview explanation sounds like:

> "The fact that the application runs as root but fails under systemd makes me compare the execution environments. I would check the service user, permissions, working directory, environment variables, configuration paths, and privileged operations. I would use the service logs to determine which difference is actually causing the failure."

That is a troubleshooting answer.

Saying:

> "I would chmod 777 everything."

is not.

# What Junior DevOps Candidates Should Learn From Part 2

Linux operational troubleshooting becomes much easier when you understand the relationship between:

```text
Application
    ↓
Process
    ↓
Process identity
    ↓
Permissions
    ↓
Service manager
    ↓
Logs
    ↓
Actual application health
```

When a Linux application fails, ask:

1. Is the process running?
2. Who is running it?
3. Who started it?
4. Is it managed by systemd?
5. What exit status did it return?
6. What do the logs say?
7. Can the service user access the required files?
8. Is the working directory correct?
9. Are required environment variables available?
10. Is the process listening where expected?
11. Is the application actually responding?
12. Did something change recently?

Useful commands from this part include:

```bash
ps
pgrep
pstree
top
kill
systemctl
journalctl
ls
id
groups
chmod
chown
chgrp
getfacl
namei
lsof
ss
tail
grep
diff
sudo
```

Do not memorize these as an isolated list.

Learn what question each command helps answer.

`ps` helps answer:

```text
What is running?
```

`systemctl` helps answer:

```text
What does the service manager think is happening?
```

`journalctl` helps answer:

```text
What happened around the failure?
```

`id` helps answer:

```text
Who is this user and what groups do they belong to?
```

`ls -l` helps answer:

```text
Who owns this file and what access is permitted?
```

`lsof` helps answer:

```text
Which process has this resource open?
```

`ss` helps answer:

```text
What is listening on the network?
```

That mindset is far more valuable in a technical interview than memorizing hundreds of commands.
