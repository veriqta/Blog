# Part 18: Production Incidents and Troubleshooting Scenarios

Production incident questions are some of the most important questions in a DevOps interview because they reveal how you think under pressure.

The interviewer is not only testing whether you know Linux, AWS, Docker, Kubernetes, Terraform, Ansible, networking, monitoring, or CI/CD.

They want to know whether you can combine all of them when something breaks.

You may hear questions like:

> "Production is down. What do you do first?"

> "A new deployment completed successfully, but customers immediately started receiving 500 errors. Walk me through your response."

> "Only one Availability Zone is failing. How would you investigate?"

> "The application is slow, CPU is normal, and no alerts are firing. What do you do?"

> "Your Kubernetes Pods are Running, the Service exists, but users cannot reach the application."

> "Terraform applied successfully, but the production environment is broken. What does that tell you?"

These questions test whether you troubleshoot systematically or randomly.

A strong incident response usually follows this path:

```text
Alert / User Report
        |
        v
Confirm the problem
        |
        v
Determine customer impact
        |
        v
Identify scope
        |
        v
Build timeline
        |
        v
Check recent changes
        |
        v
Follow request path
        |
        v
Correlate metrics, logs, traces
        |
        v
Form hypotheses
        |
        v
Mitigate impact
        |
        v
Verify recovery
        |
        v
Find root cause
        |
        v
Prevent recurrence
```

The most important rule is simple:

Do not change five things at once.

Every change should either restore service or test a clear hypothesis.

---

# Question 1: Production is down. What do you do first?

## Strong interview answer

I first establish whether there is a real incident and determine the impact.

I want to answer:

```text
What is failing?
Who is affected?
When did it start?
How severe is it?
Is it still happening?
```

For example:

```text
Homepage unavailable?
Checkout unavailable?
API latency high?
Only one region?
Only some customers?
Entire platform?
```

Then I check whether there is an obvious safe mitigation.

For example:

```text
Bad deployment
→ rollback

One unhealthy instance
→ remove from traffic

Feature causing failures
→ disable feature

Capacity exhausted
→ scale if safe
```

I would not spend thirty minutes searching for perfect root cause while customers remain unable to use the service.

The incident priorities are:

```text
Understand impact
        |
        v
Stabilize service
        |
        v
Investigate root cause
```

---

# Question 2: What is the difference between an incident, problem, and root cause?

## Strong interview answer

An incident is the active service-impacting event.

For example:

```text
Customers cannot complete checkout.
```

The problem is the underlying issue that requires investigation.

For example:

```text
Checkout service cannot connect to the database.
```

The root cause is the fundamental reason the problem occurred.

For example:

```text
A Terraform change replaced the database security group rule
that allowed traffic from the application subnet.
```

So:

```text
Incident
Customers cannot checkout.

Problem
Application cannot reach database.

Root Cause
Incorrect security-group change.
```

---

# Question 3: What is mitigation?

## Strong interview answer

Mitigation reduces customer impact without necessarily fixing the underlying cause.

For example:

```text
Bad release causes HTTP 500 errors.
```

Mitigation:

```text
Rollback to previous version.
```

Root-cause fix:

```text
Correct defective code,
test it,
improve deployment validation.
```

Mitigation answers:

```text
How do we restore service now?
```

Root-cause resolution answers:

```text
Why did this happen and how do we prevent it again?
```

---

# Question 4: What is blast radius?

## Strong interview answer

Blast radius describes how much of the system or customer base is affected.

For example:

```text
One Pod
One node
One Availability Zone
One service
One region
All production
```

This is extremely useful in troubleshooting.

If:

```text
One Pod fails
```

I investigate Pod-specific differences.

If:

```text
Every Pod on one node fails
```

I investigate that node or its networking.

If:

```text
Every service in one region fails
```

I investigate shared regional dependencies.

Blast radius helps identify what the failing systems have in common.

---

# Question 5: Why is determining scope one of the first incident-response tasks?

## Strong interview answer

Because scope narrows the possible causes.

For example:

```text
Only checkout fails
→ checkout or dependency-specific issue.

Every API fails
→ shared application dependency.

One AZ fails
→ zone-specific networking or infrastructure.

Every region fails
→ shared global dependency or deployment.
```

Without scope, engineers may investigate unrelated systems.

It is valuable both during the incident and during the postmortem.

# Question 8: Should you always blame the latest deployment?

## Strong interview answer

No.

A deployment that happened immediately before an incident is a strong hypothesis, but not proof.

For example:

```text
14:00 deployment
14:01 external payment provider outage
14:02 checkout failures
```

The deployment timing may be coincidental.

I correlate deployment changes with:

```text
Logs
Metrics
Traces
Error patterns
Affected components
Rollback behavior
```

If rollback restores service, that increases confidence that the release contributed to the incident.

---

# Question 9: A deployment completes successfully, but production immediately breaks. How is that possible?

## Strong interview answer

Deployment-system success usually proves only that the deployment mechanism completed.

For example:

```text
CI/CD
✓

Image deployed
✓

Pods Running
✓
```

But:

```text
Application configuration wrong
Database credentials invalid
Health check too weak
External dependency unavailable
Business logic broken
```

may still exist.

So:

```text
Deployment successful
!=
Application healthy
```

Production deployments need post-deployment verification.

# Question 11: A new release causes HTTP 500 errors. What do you do?

## Strong interview answer

I first establish:

```text
Which endpoints?
How many users?
All instances or some?
When did it begin?
```

Then compare the timeline with the deployment.

I check:

```text
Application logs
Error metrics
Traces
Database errors
Dependency failures
Configuration changes
```

If impact is significant and the previous version is known healthy, rollback may be the safest mitigation.

Then I investigate the release offline or in a safer environment.

---

# Question 12: When should you rollback?

## Strong interview answer

Rollback is appropriate when:

```text
Recent change is strongly associated with incident
Previous version is known good
Rollback is safe
Customer impact is significant
```

I would be more cautious if rollback includes:

```text
Irreversible database migration
Changed data format
External side effects
Breaking schema changes
```

Rollback should be designed before the incident, not invented during one.

---

# Question 13: What is rollback versus roll-forward?

## Strong interview answer

Rollback returns to a previous known-good state.

```text
Version 5
broken
  |
  v
Version 4
healthy
```

Roll-forward fixes the problem through a new change.

```text
Version 5
broken
  |
  v
Version 5.1
fix
```

Rollback is often faster when a previous version is safe.

Roll-forward may be necessary when stateful changes make rollback unsafe.

---

# Question 14: What is a canary deployment, and why does it help incident prevention?

## Strong interview answer

A canary deployment exposes a new version to a small portion of production first.

For example:

```text
95% traffic
Version 10

5% traffic
Version 11
```

Monitor:

```text
Error rate
Latency
CPU
Memory
Business metrics
```

If the canary behaves badly:

```text
Stop rollout.
```

This limits blast radius.

---

# Question 15: What is a blue-green deployment?

## Strong interview answer

Blue-green maintains two environments.

```text
Blue
current production

Green
new version
```

You deploy and test Green.

Then switch traffic:

```text
Users
  |
  v
Green
```

If something fails and the old environment remains compatible, traffic can potentially be switched back to Blue.

This can reduce deployment risk, although databases and shared state still require careful handling.

# Question 26: Application works through localhost but not remotely. What do you investigate?

## Strong interview answer

I verify the application listener.

For example:

```bash
ss -lntp
```

If I see:

```text
127.0.0.1:8080
```

the application is bound only to loopback.

Remote clients need it listening on an appropriate network interface such as:

```text
0.0.0.0:8080
```

subject to architecture and security controls.

# Question 27: What is the difference between timeout and connection refused?

## Strong interview answer

A timeout often suggests:

```text
Traffic dropped
No return path
Firewall
Routing
NetworkPolicy
Unreachable destination
```

Connection refused usually tells me I reached the destination host or network stack but nothing accepted the connection on that port, or something actively rejected it.

For example:

```text
Timeout
→ inspect path.

Refused
→ inspect listener/process/port.
```

They are clues, not absolute proof.

# Question 39: Pod is OOMKilled. What does that mean?

## Strong interview answer

The container exceeded its available memory limit or encountered memory exhaustion under its execution context.

I investigate:

```text
Memory limit
Application memory usage
Traffic
Deployment changes
Memory leak
Caching
Workload growth
```

I do not automatically increase the limit without understanding the trend.

# Question 41: All Pods become NotReady because an external API is down. What might be wrong?

## Strong interview answer

The readiness design may depend too strongly on a noncritical external dependency.

That can turn:

```text
One external API outage
```

into:

```text
Entire application removed from service.
```

Health checks should reflect whether a Pod can serve useful traffic, not whether every dependency is perfect.

---

# Question 42: Liveness probe restarts all Pods when the database fails. What is wrong?

## Strong interview answer

The liveness probe is likely checking the wrong thing.

If the database is unavailable, restarting every application Pod usually does not repair the database.

It may create:

```text
Restart storm
Connection storm
Longer recovery
```

Liveness should generally answer:

```text
Is this local process unhealthy in a way a restart can fix?
```

# Question 45: EC2 disk is full. What is your incident response?

## Strong interview answer

First assess impact.

Then:

```bash

df -i
```

Find the growth source.

Common causes:

```text
Logs
Container images
Temporary files
Old deployments
Database files
Deleted open files
```

I free space safely if necessary, then fix the growth source.

Deleting random files is not a production strategy.

# Question 78: What is a retry storm?

## Strong interview answer

A retry storm occurs when many clients repeatedly retry failed operations and create more load on an already failing dependency.

Example:

```text
Database slows
   |
   v
Application requests timeout
   |
   v
Every service retries immediately
   |
   v
Database receives even more traffic
   |
   v
Failure worsens
```

Retries need:

```text
Backoff
Jitter
Limits
```

# Question 79: What is exponential backoff?

## Strong interview answer

Instead of retrying immediately at the same interval, wait progressively longer.

For example:

```text
Retry 1
1 second

Retry 2
2 seconds

Retry 3
4 seconds

Retry 4
8 seconds
```

Adding jitter helps prevent many clients from retrying simultaneously.

# Question 80: What is a circuit breaker?

## Strong interview answer

A circuit breaker temporarily stops calls to a failing dependency after repeated failures.

Conceptually:

```text
Dependency healthy
CLOSED

Failures exceed threshold
        |
        v
OPEN
        |
        v
Stop sending normal requests

After recovery period
        |
        v
HALF-OPEN
        |
        v
Test limited requests
```

This can help prevent cascading failures.

# Question 81: What is a cascading failure?

## Strong interview answer

A cascading failure occurs when one component failure causes additional components to fail.

```text

   |
   v

   |
   v
API latency increases
   |
   v
Clients retry
   |
   v
Traffic increases
   |
   v

```

Understanding dependencies and backpressure helps prevent cascades.

# Question 82: What is backpressure?

## Strong interview answer

Backpressure limits incoming work when downstream systems cannot keep up.

Instead of allowing unlimited requests to accumulate:

```text
Incoming work
       |
       v
Bounded queue / rejection / rate limit
       |
       v
Downstream service
```

This helps prevent resource exhaustion.

Instead of:


the application may:

```text

without recommendations.
```

This reduces incident impact.


# Question 90: What should a good incident postmortem avoid?

## Strong interview answer

# Question 91: What is root cause analysis?

## Strong interview answer

Root cause analysis investigates the deeper conditions that allowed the incident to occur.

Example:

```text
Incident:
Nginx failed on all servers.

Immediate cause:
Invalid configuration.

Deeper cause:
Configuration not validated.

Contributing factor:
Ansible deployed to all hosts simultaneously.

Systemic issue:
No canary or staged rollout.
```

The goal is not simply naming the first broken component.

---

# Question 92: What is the Five Whys technique?

## Strong interview answer

The Five Whys repeatedly asks why an event occurred to uncover deeper causes.

Example:

```text
Why was the site unavailable?
Because Nginx stopped.

Why did Nginx stop?
Invalid config.

Why was invalid config deployed?
No syntax validation.

Why was it deployed everywhere?
No canary rollout.

Why were those controls missing?
Deployment process did not require them.
```

The exact number of questions does not have to be five.

The value is pushing beyond the immediate symptom.

# Question 93: What is a contributing factor?

## Strong interview answer

A contributing factor makes an incident more likely or increases its impact without necessarily being the primary cause.

Example:

```text
Root cause:
Bad application release.

Contributing factors:
No canary deployment
Weak health check
Slow alerting
Rollback process unclear
```

Production incidents often have multiple contributing factors.

# How to Answer Production Incident Questions in an Interview

If the interviewer says:

> "Production is down. What would you do?"

A strong answer is:

> "I would first verify the incident and determine customer impact and scope. I would establish when the issue began and check recent application, infrastructure, configuration, security, and database changes. Then I would follow the request path and correlate metrics, logs, traces, and events to identify the first failing layer. If there is an obvious safe mitigation such as rolling back a bad release, removing an unhealthy target, failing over, or restoring a known-good configuration, I would prioritize restoring service while preserving enough evidence for root-cause investigation. After recovery I would verify customer-facing transactions, monitor for secondary effects, then perform root-cause analysis and define corrective actions."

If the interviewer asks:

> "Would you restart the service?"

A stronger answer is:

> "Only if the evidence suggests a restart is a useful mitigation. I would first understand what symptom I am addressing. Restarting a stuck process may help, but restarting application servers during a database or network outage may provide no benefit and could cause connection storms or erase useful evidence."

If the interviewer asks:

> "How do you know the incident is over?"

A strong answer is:

> "I would verify more than the alert state. I would check that customer transactions succeed, error rates and latency have returned to normal, traffic is flowing correctly, dependencies are healthy, and any backlogs or delayed jobs are recovering. I would continue monitoring long enough to confirm stability."
