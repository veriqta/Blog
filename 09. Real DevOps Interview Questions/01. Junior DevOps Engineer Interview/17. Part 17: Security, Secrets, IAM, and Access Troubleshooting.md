# Part 17: Security, Secrets, IAM, and Access Troubleshooting

Security problems in DevOps interviews are rarely limited to questions such as:

"What is IAM?"

"What is a Secret?"

"What is least privilege?"

Real interviews are more likely to give you a situation:

> "An application running in production suddenly receives AccessDenied from AWS S3, but nobody changed the application code. How would you troubleshoot it?"

Or:

> "A Kubernetes Pod cannot retrieve a Secret, but another Pod in the same cluster can. What would you check?"

Or:

> "A developer accidentally committed an AWS access key to GitHub. They deleted the commit. What should happen next?"

The interviewer wants to know whether you understand authentication, authorization, credentials, policies, roles, secrets, access paths, and how to investigate failures without creating a larger security problem.

The strongest answers usually follow a pattern:

```text
Who is making the request?
        |
        v
How are they authenticated?
        |
        v
What identity are they using?
        |
        v
What action are they attempting?
        |
        v
Which resource are they accessing?
        |
        v
Which policies apply?
        |
        v
Is anything explicitly denying access?
        |
        v
What changed?
        |
        v
What do the audit logs show?
```

This part focuses on that reasoning.

---

# 1. What is the difference between authentication and authorization?

## Strong interview answer

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

For example:

```text
Developer
   |
   | username + MFA
   v
Authenticated
   |
   | IAM policies
   v
Authorized to read S3
```

A user can authenticate successfully but still receive:

```text
AccessDenied
```

because authentication succeeded while authorization failed.

That distinction is one of the first things I establish during access troubleshooting.

---

# 2. A user can log in to AWS but cannot access an S3 bucket. What does that tell you?

## Strong interview answer

It tells me authentication is probably working.

I would focus primarily on authorization.

I would determine:

```text
Which IAM principal?
Which AWS account?
Which S3 bucket?
Which action?
Which object?
Which policies apply?
```

For example, the user may be allowed:

```text
s3:ListBucket
```

but not:

```text
s3:GetObject
```

Or an identity policy may allow access while the bucket policy explicitly denies it.

I would troubleshoot the complete authorization path rather than simply attaching broader permissions.

# 3. What is IAM?

## Strong interview answer

AWS Identity and Access Management, IAM, controls identities and permissions for AWS resources.

The important operational concepts include:

```text
Users
Groups
Roles
Policies
Temporary credentials
Trust relationships
```

In troubleshooting, I usually think about IAM as:

```text
Principal
   |
   v
Authentication
   |
   v
Policy evaluation
   |
   v
Action
   |
   v
Resource
```

The key question is:

```text
Who is trying to perform what action on which resource?
```

---

# 4. What is an IAM principal?

## Strong interview answer

A principal is an entity that can make a request to AWS.

Examples can include:

```text
IAM user
IAM role
Federated identity
AWS service
Root user
```

During troubleshooting, identifying the actual principal matters because engineers sometimes inspect the wrong policy.

For example:

```text
Developer assumes:
Application uses IAM user
```

But actually:

```text
EC2
 |
 v
Instance profile
 |
 v
IAM role
```

Changing the IAM user's permissions would therefore accomplish nothing.

---

# 5. What is an IAM role?

## Strong interview answer

An IAM role is an AWS identity with permissions that can be assumed by authorized principals.

Unlike a traditional IAM user, a role is commonly used with temporary credentials.

Examples include:

```text
EC2 instance role
Lambda execution role
ECS task role
EKS workload identity
Cross-account role
CI/CD deployment role
```

For workloads, I generally prefer roles and temporary credentials instead of embedding long-lived access keys.

---

# 6. Why are IAM roles better than hardcoded AWS access keys?

## Strong interview answer

Hardcoded long-lived credentials create significant security and operational risk.

For example:

```text
Application
   |
   v
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

If those credentials are:

```text
Committed to Git
Copied into logs
Included in container images
Shared between engineers
Exposed in configuration
```

they may be compromised.

With a role:

```text
Application
   |
   v
IAM Role
   |
   v
Temporary Credentials
   |
   v
AWS API
```

credential management and rotation are handled through the AWS identity mechanism rather than application code containing permanent credentials.

---

# 7. What is least privilege?

## Strong interview answer

Least privilege means granting only the permissions required to perform the intended task.

For example, if an application only needs to read objects from:

```text
arn:aws:s3:::production-reports/*
```

I would not automatically grant:

```text
s3:*
Resource: *
```

A more limited permission might permit only:

```text
s3:GetObject
```

against the required resource.

Least privilege reduces the potential impact of:

```text
Credential compromise
Application bugs
Human mistakes
Misconfiguration
```

---

# 8. An engineer gets AccessDenied and asks for AdministratorAccess. What do you do?

## Strong interview answer

I would not use AdministratorAccess as the default troubleshooting solution.

First determine:

```text
Who is the principal?

What exact API call failed?

What resource?

What permissions are currently granted?

Is there an explicit deny?

Did something recently change?
```

Then I would grant or correct the specific permission required.

Using AdministratorAccess may hide the actual configuration problem while unnecessarily increasing security exposure.

---

# 9. How does AWS evaluate an Allow versus an explicit Deny?

## Strong interview answer

A useful simplified model is:

```text
Default
DENY

        |
        v

Applicable Allow?
        |
       Yes
        |
        v

Potentially ALLOWED

        |
        v

Applicable explicit Deny?
        |
       Yes
        |
        v

DENIED
```

An explicit deny takes precedence over an allow.

So if I see:

```text
Identity policy:
ALLOW s3:GetObject
```

but another applicable policy says:

```text
DENY s3:GetObject
```

the request can still fail.

That is why simply finding one Allow statement does not finish IAM troubleshooting.

# 10. What can cause an AWS AccessDenied error even when the IAM policy contains Allow?

## Strong interview answer

Several controls may affect authorization.

Depending on the environment, I would investigate:

```text
Identity-based policies
Resource-based policies
Permissions boundaries
Service Control Policies
Session policies
Role trust relationships
KMS permissions
VPC endpoint policies
Resource ownership
Conditions
```

The key lesson is:

```text
"I found an Allow"
```

does not automatically mean:

```text
"The request must be allowed."
```

# 11. What is a resource-based policy?

## Strong interview answer

A resource-based policy is attached to a resource and defines which principals can perform specified actions.

Examples include policies associated with resources such as:

```text
S3 buckets
KMS keys
SQS queues
SNS topics
```

During troubleshooting, I evaluate both the caller's permissions and relevant resource policies.

For example:

```text
IAM Role
ALLOW
   |
   v
S3 Bucket Policy
DENY
   |
   v
AccessDenied
```

---

# 12. What is an IAM trust policy?

## Strong interview answer

A role trust policy determines which principals are allowed to assume the role.

This is different from the role's permissions policy.

Think of it as:

```text
Trust Policy

Who may become this role?
```

versus:

```text
Permissions Policy

What may this role do after being assumed?
```

This distinction is important when troubleshooting `sts:AssumeRole`.

---

# 13. A user has permission to assume a role but still receives AccessDenied. What do you investigate?

## Strong interview answer

I would check both sides of the relationship.

```text
Caller
   |
   | sts:AssumeRole permission
   v
Target Role
   |
   | trust policy
   v
Assume Role
```

The caller may have permission to call `sts:AssumeRole`, but the target role's trust relationship may not trust that caller.

I would also inspect:

```text
Role ARN
External ID requirements
MFA conditions
Organization/account restrictions
Session policies
SCPs
```

---

# 14. How would you verify which AWS identity your terminal is actually using?

## Strong interview answer

One of the first commands I may run is:

```bash
aws sts get-caller-identity
```

This helps identify:

```text
Account
User ID
ARN
```

This is extremely useful because many IAM investigations begin with the wrong assumption about which identity is active.

For example:

```text
Engineer thinks:
production-admin
```

but:

```text
aws sts get-caller-identity

shows:
development-readonly
```

Now the AccessDenied makes much more sense.

# 16. What is AWS STS?

## Strong interview answer

AWS Security Token Service provides temporary security credentials.

It is commonly involved when:

```text
Assuming IAM roles
Federating identities
Using temporary sessions
Cross-account access
```

Temporary credentials typically include:

```text
Access key ID
Secret access key
Session token
Expiration
```

The expiration aspect is important during troubleshooting.

---

# 17. An application worked yesterday but now receives ExpiredToken. What do you investigate?

## Strong interview answer

I would determine how the application obtains credentials.

If it uses temporary credentials, I would check whether:

```text
Credentials expired
Refresh mechanism failed
Application cached old credentials
Metadata endpoint is unreachable
STS request failed
Clock is incorrect
```

I would not replace the temporary credential mechanism with a permanent access key just to make the error disappear.

The correct fix is restoring credential refresh.

---

# 18. Why is system time important for authentication?

## Strong interview answer

Many authentication mechanisms depend on timestamps and expiration.

If a system clock is significantly incorrect, requests may fail even when the credential itself is valid.

Possible symptoms can include:

```text
Signature validation failures
Token expiration problems
TLS problems
Authentication failures
```

I would verify time synchronization when failures suggest timestamp or signature issues.

---

# 19. What is credential rotation?

## Strong interview answer

Credential rotation replaces existing credentials with new credentials according to security requirements or in response to exposure.

For example:

```text
Old credential
     |
     v
Create/obtain replacement
     |
     v
Update dependent systems
     |
     v
Verify
     |
     v
Disable old credential
     |
     v
Remove old credential
```

For a compromised credential, the response may need to be much faster, including immediate revocation depending on the situation.

---

# 20. A developer accidentally commits an AWS access key to a public GitHub repository. They delete the commit. Is the problem solved?

## Strong interview answer

No.

I would treat the credential as compromised.

Deleting the visible commit does not prove nobody obtained the credential.

The response should include actions such as:

```text
Revoke or deactivate exposed credential
        |
        v
Replace credential if required
        |
        v
Review audit activity
        |
        v
Determine what the credential could access
        |
        v
Investigate unauthorized activity
        |
        v
Remove secret from repository history where appropriate
        |
        v
Prevent recurrence
```

The critical principle is:

```text
Exposed secret
=
Compromised secret
```

Do not rely on deletion alone.

# 23. IAM permissions look correct, but an S3 object encrypted with KMS still cannot be read. Why?

## Strong interview answer

Accessing the S3 object and decrypting the object's encryption are separate authorization concerns.

The request path may effectively involve:

```text
Application
   |
   v
S3 GetObject
   |
   v
KMS Decrypt
```

The principal may have sufficient S3 permissions but lack appropriate KMS permissions.

I would inspect:

```text
IAM permissions
KMS key policy
Key ARN
Encryption configuration
Relevant conditions
```

---

# 24. What is a permissions boundary?

## Strong interview answer

A permissions boundary limits the maximum permissions that an IAM user or role can receive through identity-based permissions.

For troubleshooting, imagine:

```text
IAM Policy:
Allows S3 and EC2

Permissions Boundary:
Allows only S3
```

The effective permissions do not simply become everything listed in the identity policy.

So if an engineer says:

> "But I attached an EC2 Allow policy."

I would still inspect the permissions boundary.

---

# 25. What is an AWS Organizations Service Control Policy?

## Strong interview answer

An SCP can establish permission guardrails for accounts within AWS Organizations.

An IAM administrator inside an account may therefore attach an Allow policy while an organizational control still prevents the action.

Troubleshooting path:

```text
IAM Allow
   |
   v
Looks correct

But

Organization SCP
   |
   v
Restricts action
   |
   v
AccessDenied
```

This becomes especially important in enterprise AWS environments.

# 27. What is a secret?

## Strong interview answer

A secret is sensitive information used to authenticate or authorize systems or protect data.

Examples include:

```text
Passwords
API keys
Database credentials
Private keys
Tokens
Certificates with private keys
```

Secrets require controls around:

```text
Storage
Access
Distribution
Rotation
Auditing
Revocation
```

---

# 28. Why should secrets not be stored directly in source code?

## Strong interview answer

Source code is commonly:

```text
Copied
Forked
Backed up
Reviewed
Cached
Built into artifacts
Shared with developers
Stored indefinitely in Git history
```

A secret committed to Git can remain recoverable even after the visible line is removed.

Instead, applications should retrieve secrets from an appropriate secure secret-management mechanism.

---

# 29. Is a `.env` file automatically secure?

## Strong interview answer

No.

A `.env` file is simply a method of providing configuration.

Its security depends on:

```text
Where it is stored
Who can read it
Whether it enters Git
File permissions
Backup behavior
Deployment process
Secret rotation
```

Adding `.env` to `.gitignore` helps prevent accidental commits, but it does not transform the file into a full secret-management system.

# 30. What is AWS Secrets Manager?

## Strong interview answer

AWS Secrets Manager is designed to store and manage secrets such as application credentials.

A typical pattern is:

```text
Application
    |
    | IAM Role
    v
Secrets Manager
    |
    v
Retrieve Secret
    |
    v
Use credential
```

The application should receive only the permissions required to retrieve the specific secrets it needs.

# 31. What is the difference between Secrets Manager and Parameter Store?

## Strong interview answer

Both can be used for application configuration and sensitive values depending on requirements.

Rather than giving a simplistic "one is secure and one is not" answer, I would consider capabilities such as:

```text
Secret lifecycle requirements
Rotation
Integration requirements
Cost
Parameter hierarchy
Encryption
Access patterns
```

The important interview point is choosing the mechanism based on the workload rather than hardcoding sensitive values.

# 33. The application retrieves the secret successfully but authentication to the database still fails. What next?

## Strong interview answer

That tells me secret retrieval and database authentication are separate stages.

I would investigate:

```text
Is the retrieved secret current?

Correct username?

Correct password?

Correct database host?

Correct port?

Correct database?

Was credential rotation completed?

Did the application cache the old secret?
```

The secret manager working does not prove the secret value is accepted by the database.

---

# 34. A database password was rotated, and applications immediately started failing. What probably happened?

## Strong interview answer

I would investigate synchronization between the stored secret, database credential, and application.

Possible sequence:

```text
Database password changed
        |
        v
Secret updated
        |
        v
Application still caches old value
        |
        v
Authentication failures
```

Or the reverse:

```text
Secret updated
        |
        v
Database password not updated correctly
        |
        v
Authentication failures
```

Rotation must be treated as a coordinated lifecycle, not simply changing a string.

---

# 35. Should an application log the secret value when secret retrieval fails?

## Strong interview answer

No.

Logs should provide enough information to diagnose the problem without exposing sensitive values.

For example:

```text
ERROR:
Unable to retrieve database credential
Secret: production/database
AccessDenied
```

is very different from:

```text
ERROR:
Password = SuperSecret123
```

Troubleshooting must not create a new credential exposure.

# 36. What is Kubernetes RBAC?

## Strong interview answer

Kubernetes Role-Based Access Control determines what authenticated subjects can perform against Kubernetes API resources.

Core objects include:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
```

Conceptually:

```text
Subject
   |
   v
RoleBinding
   |
   v
Role / ClusterRole
   |
   v
Permissions
```

# 37. What is the difference between a Kubernetes Role and ClusterRole?

## Strong interview answer

A Role defines permissions within a namespace.

A ClusterRole can define permissions for cluster-scoped resources or be used across namespaces depending on how it is bound.

For example:

```text
Role
Namespace: development

get pods
list pods
```

versus a ClusterRole that may define permissions applicable more broadly.

The binding determines who receives those permissions and where.

---

# 38. What is a RoleBinding?

## Strong interview answer

A RoleBinding grants permissions from a Role or ClusterRole to subjects within a namespace.

Subjects may include:

```text
Users
Groups
ServiceAccounts
```

When troubleshooting RBAC, I check both:

```text
What permissions exist?
```

and:

```text
Were those permissions bound to the correct subject?
```

---

# 39. What is a ClusterRoleBinding?

## Strong interview answer

A ClusterRoleBinding grants a ClusterRole to subjects at cluster scope.

Because this can provide broad permissions, it should be used carefully.

For example:

```text
ClusterRole
cluster-admin
      |
      v
ClusterRoleBinding
      |
      v
User
```

can provide extremely powerful access.

Using `cluster-admin` to fix every RBAC error defeats least privilege.

# 41. What does `kubectl auth can-i` do?

## Strong interview answer

It helps determine whether a given action is authorized.

For example:

```bash
kubectl auth can-i get pods
```

or:

```bash
kubectl auth can-i delete deployments -n production
```

This is useful for quickly testing authorization without actually performing a destructive operation.

# 42. A user can list Pods but cannot view Pod logs. Why?

## Strong interview answer

These are different Kubernetes API permissions.

Permission to:

```text
get pods
list pods
```

does not automatically grant access to:

```text
pods/log
```

I would inspect the Role or ClusterRole rules and verify permissions with an appropriate authorization check.

This is a good example of why broad statements such as:

```text
"They have Pod access."
```

are not precise enough.

# 47. Are Kubernetes Secrets encrypted just because they are Base64 encoded?

## Strong interview answer

No.

Base64 is encoding, not encryption.

For example:

```text
password
   |
   v
Base64
   |
   v
cGFzc3dvcmQ=
```

Anyone who obtains the encoded value can decode it.

Security depends on controls such as:

```text
RBAC
Encryption at rest configuration
Cluster security
Secret-management architecture
```

# 50. The Secret exists, but the application says the expected key is missing. What do you check?

## Strong interview answer

I compare the Secret's keys with the Pod specification.

For example:

```yaml
secretKeyRef:
  name: database-secret
  key: password
```

But the actual Secret contains:

```text
db_password
```

The Secret exists.

The requested key does not.

This is a configuration mismatch, not a secret-storage failure.

# 51. Should Kubernetes Secrets be committed to Git?

## Strong interview answer

Not as plaintext secret values.

Even if the manifest contains Base64 data, that is not meaningful protection.

For GitOps environments, teams commonly use approaches designed to keep sensitive values protected while maintaining declarative workflows.

The principle is:

```text
Git repository
should not become
your plaintext password database.
```

# 52. What would you do if a Kubernetes Secret was accidentally committed to a public repository?

## Strong interview answer

I would treat the underlying secret as compromised.

Actions may include:

```text
Rotate/revoke secret
Assess exposure
Review access/activity
Remove exposed value from repository/history where appropriate
Update workload safely
Verify new credential
Add preventive controls
```

Simply deleting the Kubernetes YAML file is insufficient.

---

# 53. What are environment variables versus mounted secret files?

## Strong interview answer

Both are common mechanisms for supplying configuration or secrets to applications.

The correct choice depends on application and security requirements.

I would consider:

```text
Application support
Rotation behavior
Process visibility
Logging risk
Runtime behavior
File permissions
Operational complexity
```

The important point is not assuming one method is universally safe in every environment.

---

# 54. Why can secret rotation be harder when secrets are injected as environment variables?

## Strong interview answer

A process generally receives environment variables when it starts.

If the underlying Secret changes, the running application may continue using the old environment value until the process is restarted or otherwise refreshed.

That creates an important operational question:

```text
Secret rotated
      |
      v
How does application learn?
```

Secret rotation is only useful if consumers actually begin using the new credential.

---

# 55. What is secret sprawl?

## Strong interview answer

Secret sprawl occurs when credentials become distributed across many uncontrolled locations.

For example:

```text
Git
Developer laptops
CI variables
Slack
Wiki
Container image
Shell history
Config files
Logs
```

This makes:

```text
Rotation
Revocation
Auditing
Ownership
Incident response
```

much harder.

Centralized secret management helps reduce this problem.

---

# 56. Why is putting a secret into a Docker image dangerous?

## Strong interview answer

Docker image layers can preserve data even when later layers appear to delete it.

For example:

```dockerfile
COPY credentials.txt /app/
RUN use-credentials
RUN rm /app/credentials.txt
```

does not necessarily mean the credential never existed in an earlier image layer.

Images may also be:

```text
Pushed to registries
Cached
Copied
Downloaded
Shared
```

Secrets should not be baked into images.

# 83. What is an access review?

# 84. What is privilege creep?

## Strong interview answer

Privilege creep occurs when users or workloads accumulate permissions over time without old permissions being removed.

For example:

```text
Month 1:
Read S3

Month 4:
Read + Write S3

Month 8:
EC2 access

Month 12:
Admin troubleshooting permission
never removed
```

Eventually the identity may have far more access than its current role requires.

# 85. Why are wildcard permissions risky?

## Strong interview answer

Permissions such as:

```text

Resource: "*"
```

can provide far more capability than the workload requires.

If the identity is compromised, the attacker inherits that broad access.

Wildcards are not universally forbidden, because some APIs or designs may require broader resource definitions, but they should be justified rather than used for convenience.

```text
AccessDenied
```

Investigation:

```text
Local identity:
Administrator role

CI identity:
Deployment role
```

The two environments do not use the same permissions.

The correct question is not:

```text
"Why does Terraform behave differently?"
```

It is:

```text
"What authorization does each execution environment have?"
```



# How to Answer Security Questions in a Real Interview

If the interviewer says:

> "The application gets AccessDenied from AWS. What would you do?"

Do not answer only:

> "I would check the IAM policy."

A stronger answer is:

> "I would first identify the exact API operation, target resource, and actual AWS principal making the request. I would verify the identity using something such as `aws sts get-caller-identity` where appropriate. Then I would inspect the applicable identity and resource policies and check for restrictions such as explicit denies, permissions boundaries, SCPs, trust conditions, session policies, or KMS permissions depending on the operation. I would also check CloudTrail and recent configuration changes. I would correct the smallest required permission rather than temporarily attaching AdministratorAccess."

If the interviewer asks:

> "A secret was accidentally committed to Git. What do you do?"

A stronger answer is:

> "I would treat the secret as compromised rather than assuming deleting the commit makes it safe. I would revoke or rotate the credential, determine its permissions and exposure window, review relevant audit logs for suspicious activity, update dependent workloads safely, and remove the exposed value from repository history where appropriate. I would then add controls such as secret scanning and improve the workflow that allowed the secret to enter source control."

If the interviewer asks:

> "A Kubernetes user can list Pods but cannot read their logs."

A stronger answer is:

> "I would treat those as separate RBAC permissions. I would identify the user, namespace, verb, and subresource involved, then use `kubectl auth can-i` to verify authorization. I would inspect the applicable Role, ClusterRole, RoleBinding, or ClusterRoleBinding and grant only the required `pods/log` permission if the user's responsibilities require it, rather than giving cluster-admin access."
