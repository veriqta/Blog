# Part 5: Git and Real-World Version Control Scenarios

Git is one of the most important tools in DevOps because nearly every modern delivery workflow starts with source control.

Application code, infrastructure code, Kubernetes manifests, Terraform files, CI/CD pipelines, Ansible playbooks, Helm charts, scripts, and configuration often live in Git repositories.

For junior DevOps interviews, the questions are rarely only:

```text
What is Git?
What is a branch?
What is a commit?
```

Those are basic definitions.

Real interviews often focus on situations such as:

* You committed to the wrong branch.
* You pushed a secret accidentally.
* Your branch is behind `main`.
* A merge conflict appears.
* A bad commit reached production.
* You need to recover a deleted commit.
* Someone force-pushed and history changed.
* Your CI pipeline runs on the wrong branch.
* Git says your local and remote branches have diverged.
* You need to identify exactly when a configuration broke.

The interviewer wants to know whether you can use Git safely during real engineering work.

---

# Question 1: You accidentally committed changes to the wrong branch. What would you do?

## What the interviewer is testing

The interviewer wants to know whether you understand commits, branches, and safe recovery.

The answer depends on one important question:

```text
Has the commit already been pushed?
```

## Strong interview answer

First, I would inspect the repository.

```bash
git status
```

Then:

```bash
git log --oneline --decorate -n 10
```

I would identify the commit I accidentally created.

Suppose I am currently on:

```text
main
```

but the work should have been on:

```text
feature/payment-timeout
```

If the commit has not been pushed, one approach is to create the intended branch from the current commit.

```bash
git switch -c feature/payment-timeout
```

Now the commit exists on the correct branch.

Then I can move `main` back to the appropriate commit.

For example, if only the latest commit was accidental:

```bash
git switch main
git reset --hard HEAD~1
```

But I would only use a hard reset if I understand that I am discarding the local state and the commit has not been shared.

## Safer reasoning

Another possible approach is:

```bash
git branch feature/payment-timeout
```

Then restore `main` to the expected state.

The exact commands depend on whether the commit is local, pushed, or already shared with other developers.

## If it was already pushed

I would avoid rewriting shared history unless the team explicitly allows it.

Instead, I might revert the commit on `main`:

```bash
git revert <commit-hash>
```

Then keep or cherry-pick the original work into the correct branch.

## Interview takeaway

The important distinction is:

```text
Local unpublished history
→ rewriting may be acceptable

Shared published history
→ prefer safer history-preserving operations
```

# Question 2: What is the difference between `git reset` and `git revert`?

## Strong interview answer

Both can undo changes, but they work differently.

`git reset` moves a branch reference to another commit.

For example:

```bash
git reset --hard HEAD~1
```

moves the current branch back one commit and resets the working tree and index to match.

This rewrites local branch history.

`git revert` creates a new commit that reverses the changes introduced by another commit.

For example:

```bash
git revert abc123
```

does not remove `abc123` from history.

Instead, Git creates another commit that applies the opposite change.

## Simple comparison

```text
git reset
→ moves history pointer
→ can rewrite history

git revert
→ creates new undo commit
→ preserves shared history
```

## Real-world rule

If a bad commit has already been pushed to a shared branch such as `main`, `git revert` is usually the safer choice.

If the mistake exists only locally and has not been shared, `git reset` may be appropriate.

# Question 3: A bad commit was deployed to production. How would you handle it?

## Strong interview answer

I would separate application recovery from Git cleanup.

The first priority is restoring service safely.

Depending on the deployment process, that might mean:

* Roll back to the previous release
* Revert the bad commit
* Redeploy the last known good version
* Disable the problematic feature

If the organization deploys directly from `main`, I might revert the bad commit:

```bash
git revert <bad-commit>
```

Then push the revert:

```bash
git push origin main
```

The CI/CD pipeline could then deploy the corrected version.

## Why revert is useful

It preserves the fact that:

```text
Commit A introduced the change
Commit B reversed it
```

That creates a clear audit trail.

## Interviewer follow-up

### "Would you always debug the bug before rolling back?"

No.

If the change is causing a serious production incident, restoration may be more important than immediately finding the exact root cause.

A common operational approach is:

```text
Stabilize
→ Restore service
→ Investigate
→ Fix properly
→ Redeploy
```

The exact decision depends on impact and rollback safety.

# Question 4: Your local branch is behind `main`. How do you update it?

## Strong interview answer

First, I would fetch the latest remote state.

```bash
git fetch origin
```

Then I would inspect the relationship.

```bash
git status
```

and possibly:

```bash
git log --oneline --graph --decorate --all
```

If I am on:

```text
feature/login-fix
```

I have two common approaches.

### Merge

```bash
git merge origin/main
```

This integrates `main` into my branch and may create a merge commit.

### Rebase

```bash
git rebase origin/main
```

This reapplies my branch commits on top of the latest `main`.

## Which should you use?

That depends on the team's workflow.

Rebase can create a cleaner linear history, but it rewrites commit hashes.

Therefore, I would be cautious rebasing commits that other people are already using.

## Interview takeaway

Do not answer:

```text
I always use rebase.
```

or:

```text
I always merge.
```

A stronger answer is:

```text
I follow the team's history policy and avoid rewriting shared history unexpectedly.
```

# Question 5: What is the difference between `git fetch` and `git pull`?

## Strong interview answer

`git fetch` downloads new commits and remote branch updates without automatically modifying my current branch.

Example:

```bash
git fetch origin
```

After fetching, I can inspect what changed.

For example:

```bash
git log HEAD..origin/main --oneline
```

`git pull` generally performs a fetch followed by an integration step such as merge or rebase, depending on configuration and options.

For example:

```bash
git pull origin main
```

## Why `fetch` can be useful

In production-related repositories, I often want to inspect incoming changes before integrating them.

A safe pattern can be:

```text
fetch
→ inspect
→ merge/rebase deliberately
```

instead of immediately changing my branch.

# Question 6: What is a merge conflict?

## Strong interview answer

A merge conflict happens when Git cannot automatically determine how to combine changes.

For example, two branches may modify the same lines differently.

Suppose `main` contains:

```text
timeout=30
```

and my branch changes it to:

```text
timeout=60
```

while another developer changes it to:

```text
timeout=45
```

When Git attempts to combine those histories, it may require a human decision.

The conflicted file may contain markers such as:

```text
<<<<<<< HEAD
timeout=60
=======
timeout=45
>>>>>>> origin/main
```

I must decide the intended final value.

Then remove the conflict markers.

After resolving:

```bash
git add config.env
```

If I am merging:

```bash
git commit
```

If I am rebasing:

```bash
git rebase --continue
```

## Strong interview point

Do not simply delete one side without understanding the business or technical intent.

A conflict is not only a Git syntax problem.

It may represent two competing engineering changes.

# Question 7: How would you safely resolve a merge conflict in a production configuration file?

## Strong interview answer

I would first understand why both sides changed the file.

Suppose the conflict is in:

```text
terraform/prod/variables.tf
```

I would inspect:

```bash
git status
```

Then examine the conflict.

I would compare both versions and determine whether the changes are:

* Mutually exclusive
* Both required
* Environment-specific
* Related to different incidents or features

I might use:

```bash
git diff
```

and inspect the relevant commit history:

```bash
git log --oneline -- terraform/prod/variables.tf
```

Once I understand the intended final configuration, I would edit carefully.

Then:

```bash
git add terraform/prod/variables.tf
```

and continue the merge or rebase.

## Before pushing

For production infrastructure code, I would also validate the result.

For example:

```bash
terraform fmt -check
terraform validate
```

and run whatever plan or CI checks the repository requires.

## Interview takeaway

Resolve the technical conflict and validate the operational meaning.

# Question 8: What is `git cherry-pick`, and when would you use it?

## Strong interview answer

`git cherry-pick` applies the changes introduced by a specific commit onto the current branch.

Example:

```bash
git cherry-pick a1b2c3d
```

This creates a new commit on the current branch containing equivalent changes.

## Real-world scenario

Suppose a bug fix exists on:

```text
develop
```

but production runs:

```text
release/2.4
```

and I need only that specific fix.

Rather than merging all of `develop`, I might cherry-pick the relevant commit into the release branch.

## Important limitation

Cherry-picking creates a new commit with a different commit hash.

Overusing it can make history harder to understand.

I would use it deliberately rather than as the default way of moving work between branches.

# Question 9: You deleted a branch by mistake. Can you recover it?

## Strong interview answer

Usually, yes, if the commits still exist and have not been garbage-collected.

Suppose I accidentally run:

```bash
git branch -D feature/payment
```

I could inspect the reflog:

```bash
git reflog
```

The reflog records recent movements of references and `HEAD`.

Suppose I find:

```text
abc123 HEAD@{3}: commit: add payment retry logic
```

I can recreate the branch:

```bash
git branch feature/payment abc123
```

or:

```bash
git switch -c feature/payment abc123
```

## Why reflog matters

A commit can become unreachable from a normal branch but still exist in the local repository for some time.

`git reflog` is extremely useful for recovering from local mistakes.

---

# Question 10: What is `git reflog`, and why should DevOps engineers know it?

## Strong interview answer

`git reflog` records updates to local references such as `HEAD`.

It helps answer:

```text
Where did my branch or HEAD point recently?
```

For example:

```bash
git reflog
```

might show:

```text
8ce90b1 HEAD@{0}: reset: moving to HEAD~1
fa42c12 HEAD@{1}: commit: update production variables
```

If I accidentally reset away a commit, I can often find the previous commit in reflog.

Then recover it:

```bash
git switch -c recovery fa42c12
```

## Important distinction

Reflog is local.

It is not a replacement for remote backups or proper Git hosting.

But it is one of the most useful tools for recovering from local history mistakes.

# Question 11: Someone accidentally committed a password or API key. What should you do?

## Strong interview answer

I would treat the credential as compromised once it has entered Git history, especially if the repository was pushed or accessible to others.

The first priority is not simply deleting the line.

The first priority is credential rotation.

For example:

```text
1. Revoke or rotate the secret
2. Remove it from current files
3. Remove it from repository history if necessary
4. Investigate exposure
5. Add controls to prevent recurrence
```

## Why deleting the file is not enough

Suppose commit A contains:

```text
AWS_SECRET_ACCESS_KEY=...
```

and commit B deletes it.

The secret may still exist in commit A.

Anyone with access to repository history could still retrieve it.

## Prevention

I would use:

* `.gitignore`
* Secret managers
* Environment variables
* CI/CD secret stores
* Pre-commit secret scanning
* Repository secret scanning
* Least privilege and credential rotation

## Critical interview point

The correct first response is not:

```text
git rm secrets.env
```

The correct first response is:

```text
Assume the secret is exposed and rotate it.
```

# Question 12: What is `.gitignore`, and what does it not do?

## Strong interview answer

`.gitignore` tells Git which untracked files or patterns should generally be ignored.

Example:

```text
.env
*.log
node_modules/
terraform.tfstate
```

This helps prevent accidental commits of:

* Local environment files
* Build artifacts
* Logs
* Dependency directories
* Certain generated files

## Important limitation

`.gitignore` does not automatically stop tracking a file that is already committed.

Suppose `.env` is already tracked.

Adding:

```text
.env
```

to `.gitignore` does not remove it from Git history or automatically untrack it.

To stop tracking while keeping the local file:

```bash
git rm --cached .env
```

Then commit that change.

## Security point

`.gitignore` is not a secret-management system.

Secrets should not depend solely on developers remembering to ignore files.

# Question 13: Your local and remote branches have diverged. What does that mean?

## Strong interview answer

It means both the local branch and remote branch contain commits that the other does not have.

For example:

```text
      B---C local
     /
A---X
     \
      D---E remote
```

My branch contains:

```text
B, C
```

while the remote contains:

```text
D, E
```

I need to integrate the histories.

Possible approaches include:

* Merge
* Rebase

depending on the team's workflow.

I would first:

```bash
git fetch origin
```

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

I would not blindly run a force push.

# Question 14: What is a force push, and why is it dangerous?

## Strong interview answer

A force push can update the remote branch even when the update is not a normal fast-forward.

Example:

```bash
git push --force origin feature
```

This can overwrite remote history.

If other developers based work on commits that are removed, they may have to recover or reconcile their branches.

## Safer option

When force pushing is legitimately necessary, such as after rebasing my own feature branch, I would prefer:

```bash
git push --force-with-lease
```

`--force-with-lease` adds a safety check so Git refuses the overwrite if the remote branch changed unexpectedly since my last known state.

## Strong interview rule

Never casually force-push shared branches such as:

```text
main
master
release
production
```

Team policies and branch protections should normally prevent dangerous operations there.

# Question 15: What is the difference between a fast-forward merge and a merge commit?

## Strong interview answer

Suppose the history is:

```text
A---B main
     \
      C---D feature
```

If `main` has not changed since the feature branch was created, Git can move `main` directly forward to `D`.

That is a fast-forward.

```text
A---B---C---D
```

No separate merge commit is required.

If both branches changed:

```text
A---B---E main
     \
      C---D feature
```

Git may create a merge commit:

```text
A---B---E------M
     \        /
      C------D
```

The merge commit records the combination of the two histories.

---

# Question 16: What is rebase, and why can it be useful?

## Strong interview answer

Rebase reapplies commits on top of another base commit.

Suppose:

```text
A---B---C main
     \
      D---E feature
```

If I rebase the feature branch onto the latest `main`, Git creates new versions of `D` and `E` after `C`.

Conceptually:

```text
A---B---C---D'---E'
```

This can produce a cleaner linear history.

## Important warning

Because the rebased commits are new commits with new hashes, rebase rewrites history.

I would avoid rebasing shared commits that other developers already depend on unless the team has a coordinated workflow for it.

---

# Question 17: A developer says, "I rebased my branch and now Git rejects my push." Why?

## Strong interview answer

Rebase rewrites commit history.

The local branch now contains new commit hashes that do not match the remote branch history.

A normal push may be rejected because Git sees the remote update as non-fast-forward.

If it is the developer's own feature branch and rewriting that branch is acceptable, they may need:

```bash
git push --force-with-lease
```

I would prefer `--force-with-lease` over `--force`.

But I would verify that nobody else is using that branch first.

# Question 18: What is detached HEAD?

## Strong interview answer

Normally, `HEAD` points to the current branch.

For example:

```text
HEAD → feature/login
```

In detached HEAD state, `HEAD` points directly to a commit rather than a branch.

This can happen if I run:

```bash
git checkout abc123
```

or:

```bash
git switch --detach abc123
```

I can inspect the repository or build that commit.

But if I create commits while detached and then move away without creating a branch, those commits may become difficult to find later.

## Safe approach

If I decide I want to keep work created while detached:

```bash
git switch -c investigation-fix
```

This attaches the work to a branch.

# Question 19: You changed several files but want to temporarily switch branches without committing. What would you do?

## Strong interview answer

One option is to use Git stash.

```bash
git stash
```

Then switch branches.

Later:

```bash
git stash pop
```

or:

```bash
git stash apply
```

## Difference

`git stash pop` applies the stash and removes it from the stash list if successful.

`git stash apply` applies it but leaves the stash entry available.

I can inspect stashes:

```bash
git stash list
```

For a named stash:

```bash
git stash push -m "work in progress on retry logic"
```

## Caution

Stash is useful for temporary work, but I would not use it as long-term storage for important work.

# Question 20: You accidentally modified a tracked file and want to discard the changes. What would you do?

## Strong interview answer

First, I would inspect the changes.

```bash
git diff
```

If I am certain I want to discard the unstaged changes in one file:

```bash
git restore path/to/file
```

For example:

```bash
git restore nginx.conf
```

If I had already staged the file:

```bash
git restore --staged nginx.conf
```

That removes it from the staging area while keeping the working-tree changes.

Then, if I want to discard the working changes too:

```bash
git restore nginx.conf
```

## Important rule

I would inspect before discarding.

Commands that remove local work can be destructive.

# Question 21: What is the staging area, and why does Git have it?

## Strong interview answer

The staging area, or index, represents what will be included in the next commit.

Suppose I modified:

```text
main.tf
variables.tf
README.md
```

but I only want the Terraform change in the next commit.

I can stage:

```bash
git add main.tf variables.tf
```

Then:

```bash
git status
```

shows what is staged and what is not.

Commit:

```bash
git commit -m "Update production network variables"
```

The README change remains uncommitted.

## Why this matters

The staging area allows me to create focused commits rather than committing every local change at once.

Focused commits make:

* Reviews easier
* Reverts safer
* History easier to understand
* Troubleshooting easier

# Question 22: What makes a good Git commit?

## Strong interview answer

A good commit should represent one coherent change.

For example:

```text
Add retry timeout to payment API
```

is better than:

```text
updates
```

A good commit should ideally:

* Have a clear purpose
* Avoid unrelated changes
* Be reviewable
* Build or validate when possible
* Have a meaningful message

For infrastructure repositories, I would avoid mixing:

```text
Terraform VPC changes
README formatting
CI pipeline changes
Random script cleanup
```

into one large commit if they are unrelated.

That makes rollback and review unnecessarily difficult.

# Question 23: How would you find which commit introduced a particular line?

## Strong interview answer

I could use:

```bash
git blame path/to/file
```

For example:

```bash
git blame nginx.conf
```

This shows which commit last changed each line.

I could then inspect the relevant commit:

```bash
git show <commit-hash>
```

## Important point

`git blame` is a technical investigation tool.

It should not be treated as a tool for blaming people.

The purpose is to understand:

* Why a line changed
* Which commit introduced it
* What context existed at the time

# Question 24: How would you determine when a production configuration changed?

## Strong interview answer

Suppose:

```text
terraform/prod/main.tf
```

is behaving differently.

I would inspect its history:

```bash
git log --oneline -- terraform/prod/main.tf
```

For patches:

```bash
git log -p -- terraform/prod/main.tf
```

I could inspect a particular commit:

```bash
git show <commit-hash>
```

If I know a particular line or value changed:

```bash
git blame terraform/prod/main.tf
```

This helps correlate configuration changes with incident timing.

## Production reasoning

A strong incident timeline might become:

```text
09:10 config commit merged
09:15 pipeline deployed
09:19 errors began
```

That does not automatically prove causation, but it gives me a strong hypothesis to investigate.

# Question 25: What is `git bisect`, and when would it be useful?

## Strong interview answer

`git bisect` helps find the commit that introduced a bug using a binary-search approach.

Suppose:

```text
Commit A = known good
Commit Z = known bad
```

I can start:

```bash
git bisect start
```

Mark the current bad version:

```bash
git bisect bad
```

Mark the known good commit:

```bash
git bisect good <good-commit>
```

Git checks out a commit approximately halfway between.

I test it and mark it:

```bash
git bisect good
```

or:

```bash
git bisect bad
```

Git continues narrowing the range until it identifies the first bad commit.

When finished:

```bash
git bisect reset
```

## Why DevOps engineers should know this

It can be extremely useful when a configuration, script, pipeline, or application regression appeared somewhere across many commits.

# Question 26: A CI pipeline started failing after a recent merge. How would you use Git to investigate?

## Strong interview answer

I would first inspect the merge commit and recent changes.

```bash
git log --oneline -n 20
```

Then:

```bash
git show <merge-commit>
```

If the pipeline failure relates to a specific file, I might inspect:

```bash
git log -p -- .github/workflows/deploy.yml
```

or:

```bash
git log -p -- Jenkinsfile
```

I would compare the last successful commit with the first failing commit.

For example:

```bash
git diff <good-commit> <bad-commit>
```

This helps answer:

```text
What changed between working and broken?
```

If many commits exist between them, `git bisect` may help.

# Question 27: Your CI pipeline runs when you push to a feature branch, but it should only deploy from `main`. Where would you investigate?

## Strong interview answer

I would inspect the CI/CD trigger configuration.

The issue may not be Git itself, but Git branch events are controlling pipeline behavior.

For GitHub Actions, for example, I might inspect:

```yaml
on:
  push:
    branches:
      - main
```

If the configuration instead contains:

```yaml
on:
  push:
    branches:
      - "*"
```

then every matching branch may trigger it.

I would check:

* Branch filters
* Pull request triggers
* Deployment conditions
* Environment protections
* Workflow rules

## Important interview point

A successful Git push should not automatically mean production deployment.

Production deployment should normally have deliberate controls around branch, approval, environment, and permissions.

# Question 28: What is a protected branch?

## Strong interview answer

A protected branch is configured with repository rules that restrict dangerous or uncontrolled changes.

For example, `main` may require:

* Pull request before merge
* Code review
* Passing CI checks
* No force push
* No direct push
* Signed commits in some environments
* Required approvals

This reduces the risk of someone directly changing production-tracked code.

## DevOps relevance

Infrastructure-as-code repositories are especially important to protect because a Git merge may eventually change actual infrastructure.

# Question 29: Why is committing directly to `main` risky?

## Strong interview answer

Direct commits can bypass:

* Peer review
* Automated tests
* Security scans
* Policy checks
* Approval workflows

In a repository connected to deployment automation, a direct commit could potentially reach production quickly.

A safer workflow commonly looks like:

```text
Feature branch
     ↓
Pull request
     ↓
Review
     ↓
CI checks
     ↓
Approval
     ↓
Merge
     ↓
Deployment process
```

The exact workflow depends on the organization, but the principle is controlled change.

# Question 30: What is a pull request or merge request?

## Strong interview answer

A pull request or merge request proposes integrating changes from one branch into another.

It provides a place for:

* Code review
* Discussion
* CI validation
* Security checks
* Approval
* Change history

For DevOps work, the pull request may include changes to:

* Terraform
* Kubernetes manifests
* Helm charts
* CI pipelines
* Shell scripts
* Ansible
* Monitoring configuration

The review should focus not only on syntax but operational impact.

For example:

```text
Will this Terraform change destroy a resource?
Will this Kubernetes change reduce replicas?
Will this firewall change expose a port?
```

# Question 31: A pull request contains 2,000 changed lines across 40 unrelated files. What problem does that create?

## Strong interview answer

Large unrelated pull requests are difficult to review safely.

Reviewers may miss:

* Security issues
* Configuration mistakes
* Unintended changes
* Production impact

They are also harder to:

* Test
* Revert
* Troubleshoot
* Understand later

I would prefer smaller logical changes where practical.

For example:

```text
PR 1
Update Terraform networking

PR 2
Update CI deployment workflow

PR 3
Update documentation
```

rather than combining unrelated work into one change.

# Question 32: What is Git tagging, and how is it useful in deployments?

## Strong interview answer

A Git tag gives a name to a specific commit.

For example:

```bash
git tag v1.4.0
```

Push it:

```bash
git push origin v1.4.0
```

Tags are commonly used to identify releases.

For example:

```text
v1.3.0
v1.3.1
v1.4.0
```

A deployment system may deploy a particular tag rather than whatever happens to be at the latest branch tip.

This improves traceability.

I can answer:

```text
Which exact source version is running in production?
```

with a specific release tag or commit.

# Question 33: Production is broken. How would you find the exact code version currently deployed?

## Strong interview answer

Ideally, the deployment system should expose a release identifier.

That might be:

* Git commit SHA
* Git tag
* Container image tag
* Build number

For example:

```text
Git commit:
9ad83c1
```

I can inspect it:

```bash
git show 9ad83c1
```

Then compare it with the previous known-good version.

```bash
git diff <previous-commit> 9ad83c1
```

## Strong operational principle

Every deployment should be traceable back to immutable source and build identifiers.

Otherwise incident investigation becomes much harder.

# Question 34: Why is deploying from a Git commit SHA often safer than deploying from a moving branch name?

## Strong interview answer

A commit SHA identifies a specific immutable commit.

A branch name such as:

```text
main
```

moves as new commits are added.

If I say:

```text
Deploy main
```

the exact code represented by `main` depends on when that command runs.

If I say:

```text
Deploy commit 9ad83c1
```

the source version is specific.

This improves:

* Reproducibility
* Rollback
* Auditability
* Incident investigation

Branches are useful for workflows, but immutable identifiers are valuable for releases.

# Question 35: A file exists locally but does not appear in Git. How would you troubleshoot it?

## Strong interview answer

First:

```bash
git status
```

If it does not appear, I would check whether it is ignored.

```bash
git check-ignore -v path/to/file
```

This can show which ignore rule matched.

I would inspect:

```text
.gitignore
.git/info/exclude
```

and any global Git ignore configuration.

Another possibility is that I am in the wrong repository or directory.

I might check:

```bash
git rev-parse --show-toplevel
```

to confirm the repository root.

# Question 36: What happens if two people edit different lines in the same file?

## Strong interview answer

Git can often merge the changes automatically if they do not overlap in a conflicting way.

For example:

Developer A changes line 10.

Developer B changes line 80.

Git may successfully combine both changes.

A merge conflict is not automatically caused just because two people changed the same file.

Conflicts occur when Git cannot safely determine how the changes should be combined.

---

# Question 37: A teammate force-pushed a shared branch and your commits seem to have disappeared. What would you do?

## Strong interview answer

First, I would avoid making more destructive changes.

I would fetch the remote state:

```bash
git fetch origin
```

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

I would also check local reflog:

```bash
git reflog
```

My previous commits may still exist locally even though the remote branch no longer references them.

If I find the missing commit:

```text
abc123
```

I could create a recovery branch:

```bash
git switch -c recovery abc123
```

Then coordinate with the team before restoring or reapplying the changes.

## Production lesson

This is exactly why force pushes should be restricted on shared branches.

# Question 38: What is a remote in Git?

## Strong interview answer

A remote is a named reference to another Git repository location.

The common default name is:

```text
origin
```

I can inspect remotes:

```bash
git remote -v
```

Example:

```text
origin  git@github.com:company/platform.git (fetch)
origin  git@github.com:company/platform.git (push)
```

I can have multiple remotes.

For example:

```text
origin
upstream
```

This is common when working with forks.

# Question 39: What is the difference between `origin/main` and `main`?

## Strong interview answer

`main` is my local branch.

`origin/main` is my local remote-tracking reference representing the last known state of the remote `main` branch after fetching.

For example:

```bash
git fetch origin
```

updates information such as:

```text
origin/main
```

It does not automatically make my local `main` identical unless I integrate or reset appropriately.

This distinction is important when someone says:

```text
My main branch is up to date.
```

I need to know whether they fetched the latest remote state first.

# Question 40: How would you compare your current branch with `main` before opening a pull request?

## Strong interview answer

First, fetch:

```bash
git fetch origin
```

Then:

```bash
git diff origin/main...HEAD
```

I might also inspect commits:

```bash
git log origin/main..HEAD --oneline
```

This tells me which commits my branch adds.

I would also run:

```bash
git status
```

and whatever project validation is required.

For infrastructure work, that could include:

```bash
terraform fmt -check
terraform validate
```

or YAML validation, tests, linting, and security checks.

# Question 41: You need to temporarily inspect an old production release. How would you do it?

## Strong interview answer

If I know the tag:

```bash
git switch --detach v1.8.2
```

or older syntax:

```bash
git checkout v1.8.2
```

Now I can inspect that release without changing the current branch history.

If I need to create a fix based on that release:

```bash
git switch -c hotfix/v1.8.2
```

from the appropriate commit.

## Important point

I would not accidentally commit production fixes in detached HEAD state without attaching them to a branch.

# Question 42: What is a hotfix branch?

## Strong interview answer

A hotfix branch is commonly used to prepare an urgent correction for a released or production version.

For example:

```text
main
  ↓
v2.4.0

hotfix/payment-timeout
```

The exact branching model varies between organizations.

The important principle is that urgent production fixes should still be:

* Version controlled
* Reviewed when possible
* Tested
* Traceable
* Merged back into relevant development lines

A hotfix should not become a permanent undocumented difference between production and source control.

---

# Question 43: Someone changed a production file manually on the server but did not commit the change to Git. Why is this dangerous?

## Strong interview answer

The server now contains configuration that does not match the declared source of truth.

For example:

```text
Git:
timeout=30

Production server:
timeout=90
```

The next automated deployment may overwrite the manual change.

Or another engineer may investigate Git and incorrectly believe production still uses 30.

This creates configuration drift.

A better approach is to make the intended change through version-controlled configuration and the established deployment process.

## DevOps principle

```text
Production state should be reproducible from controlled source.
```

Manual emergency changes may sometimes be necessary, but they should be reconciled back into the source of truth.

---

# Question 44: What is configuration drift?

## Strong interview answer

Configuration drift occurs when the actual environment differs from the intended version-controlled configuration.

For example:

```text
Git says:
replicas = 3

Production actually has:
replicas = 5
```

or:

```text
Git says:
port 8080

Server manually changed to:
port 9000
```

Drift makes systems harder to:

* Reproduce
* Troubleshoot
* Audit
* Recover

Infrastructure as Code and Git-based workflows help reduce this problem, but only if teams avoid unmanaged manual changes.

# Question 45: Why should Terraform state files be handled carefully in Git?

## Strong interview answer

Terraform state can contain sensitive infrastructure information and may sometimes contain sensitive values depending on resources and configuration.

It is also a shared state mechanism that should normally be managed with an appropriate remote backend rather than casually committed to a repository.

A common `.gitignore` entry may include:

```text
*.tfstate
*.tfstate.*
```

But `.gitignore` alone is not sufficient if state was already committed.

The larger point is that infrastructure repositories must distinguish:

```text
Configuration that belongs in Git
```

from:

```text
Runtime state or secrets that require dedicated storage
```

# Question 46: Why should `.env` files usually not be committed?

## Strong interview answer

`.env` files often contain environment-specific or sensitive values such as:

* Database passwords
* API keys
* Access tokens
* Secret keys

Committing them risks exposing credentials through repository history.

Instead, I would generally use secure environment injection or secret-management systems.

A `.gitignore` rule might include:

```text
.env
.env.*
```

while providing a safe template such as:

```text
.env.example
```

containing variable names without real secret values.

For example:

```text
DATABASE_URL=
API_TOKEN=
```

# Question 47: How would you identify who changed a production deployment file and why?

## Strong interview answer

Suppose the file is:

```text
k8s/prod/deployment.yaml
```

I would inspect:

```bash
git log --oneline -- k8s/prod/deployment.yaml
```

Then:

```bash
git show <commit>
```

If I need line-specific context:

```bash
git blame k8s/prod/deployment.yaml
```

I would also inspect the pull request or merge request associated with the commit where available.

That provides:

* Author
* Review discussion
* Reason for change
* CI results
* Approval history

The goal is not to find someone to blame.

It is to reconstruct the change context.

# Question 48: A deployment script worked yesterday, but Git shows no change to the script. What else would you investigate?

## Strong interview answer

I would not assume Git must contain the cause.

Possible changes could include:

* Environment variables
* Secrets
* Dependency versions
* Runner image
* External service
* Operating system package
* Branch or tag used
* CI configuration
* Generated artifacts
* Infrastructure state

I would still verify the script's source:

```bash
git log -p -- deploy.sh
```

But if there is no relevant code change, I would expand the investigation.

## Important interview lesson

Git history is one source of evidence.

Not every production change originates in Git unless the environment is fully controlled through Git-based workflows.

# Question 49: How would you find all changes between two releases?

## Strong interview answer

If the releases are tagged:

```text
v2.3.0
v2.4.0
```

I can list commits:

```bash
git log v2.3.0..v2.4.0 --oneline
```

See file changes:

```bash
git diff --stat v2.3.0 v2.4.0
```

See detailed differences:

```bash
git diff v2.3.0 v2.4.0
```

This is useful during:

* Release review
* Incident investigation
* Rollback analysis
* Change auditing

# Question 50: A production incident started after the latest release. Walk me through how you would use Git during the investigation.

## Strong interview answer

I would first identify exactly which version is running in production.

Suppose the deployed commit is:

```text
8a41d2c
```

I would inspect it:

```bash
git show 8a41d2c
```

Then determine the previous known-good version.

Suppose:

```text
71bc903
```

I would compare:

```bash
git diff 71bc903 8a41d2c
```

I would review:

* Application changes
* Configuration
* Infrastructure code
* Dependency files
* CI/CD changes

If the incident is isolated to a specific component, I would narrow the history.

For example:

```bash
git log -p 71bc903..8a41d2c -- config/
```

If many commits exist and I can reliably test whether each version is good or bad, `git bisect` may help.

But Git investigation should be correlated with runtime evidence.

I would compare:

```text
Deployment time
Error start time
Application logs
Monitoring
Git changes
```

A Git change is a hypothesis until runtime evidence supports it.

# Final Production Interview Scenario

The interviewer gives you this situation:

> "A deployment completed successfully at 14:05. At 14:12, customers started reporting that the application cannot connect to Redis. The previous release worked. The pipeline deployed commit `9f48a21`. You are asked to investigate. What do you do?"

A weak answer would be:

> "I would immediately reset the branch."

That risks modifying source history before we even know what failed.

A stronger junior DevOps answer begins with evidence.

First, identify what `9f48a21` changed.

```bash
git show 9f48a21
```

Suppose the output shows:

```diff
- REDIS_HOST=redis.internal.example.com
+ REDIS_HOST=redis-prod.internal.example.com
```

Now I have a strong hypothesis.

I would verify the actual running application's configuration rather than assuming the Git change is definitely responsible.

I would inspect application logs.

Suppose they show:

```text
Unable to resolve redis-prod.internal.example.com
```

Now the evidence aligns.

Check the DNS name:

```bash
getent hosts redis-prod.internal.example.com
```

Suppose no address is returned.

Now the likely failure path is:

```text
Git change
   ↓
Deployment
   ↓
Application uses new Redis hostname
   ↓
Hostname does not resolve
   ↓
Redis connections fail
   ↓
Customer errors
```

At that point, depending on the incident response strategy, the fastest safe recovery may be to revert the configuration change.

```bash
git revert 9f48a21
```

Push through the normal review/deployment process as appropriate.

If this is a high-impact incident and the organization's process supports automated rollback to the previous release, that may be even faster.

After recovery, I would investigate why the change passed validation.

Questions include:

* Was the hostname mistyped?
* Was DNS supposed to be created first?
* Did CI validate only syntax?
* Could the pipeline test DNS or dependency connectivity?
* Was the change reviewed?
* Was the wrong environment value used?

## Strong interview response

A strong candidate might say:

> "I would first identify the exact deployed commit and compare it with the previous working release. I would look for changes affecting Redis configuration, then correlate those changes with application logs and runtime behavior. If the latest release introduced an invalid Redis hostname and that is confirmed by DNS testing, I would restore service using the safest rollback or revert process. I would preserve the Git history rather than casually rewriting shared `main`, then investigate why the bad configuration passed review and CI."

That demonstrates three important skills:

```text
Git knowledge
+
Production troubleshooting
+
Change-management judgment
```

# What Junior DevOps Candidates Should Learn From Part 5

Git is not just a tool for saving files.

In DevOps, Git often becomes part of the operational control system for infrastructure and deployments.

A useful mental model is:

```text
Engineer
   ↓
Branch
   ↓
Commit
   ↓
Pull Request
   ↓
Review
   ↓
CI
   ↓
Merge
   ↓
Build
   ↓
Deploy
   ↓
Production
```

A Git mistake can therefore become a production problem.

Junior DevOps engineers should be comfortable answering questions such as:

```text
What changed?

Which commit introduced it?

Which version is deployed?

Can I safely undo it?

Has the history been shared?

Will this command rewrite history?

Can I recover the previous commit?

Did a secret enter Git history?

Can I compare the broken release with the last good one?
```

Useful commands from this part include:

```bash
git status
git log
git show
git diff
git fetch
git pull
git merge
git rebase
git revert
git reset
git reflog
git restore
git stash
git cherry-pick
git blame
git bisect
git branch
git switch
git tag
git remote
git check-ignore
```

But once again, memorizing commands is not enough.

You should know what problem each command helps solve.

`git status` helps answer:

```text
What state is my working tree in?
```

`git log` helps answer:

```text
What happened in this repository?
```

`git diff` helps answer:

```text
What changed?
```

`git show` helps answer:

```text
What exactly did this commit do?
```

`git revert` helps answer:

```text
How do I safely reverse a shared change?
```

`git reflog` helps answer:

```text
Where did my local history point before I made this mistake?
```

`git bisect` helps answer:

```text
Which commit introduced this regression?
```

`git blame` helps answer:

```text
Which change last modified this line?
```

A junior engineer who understands those relationships is much more useful than someone who only knows how to run:

```bash
git add .
git commit -m "update"
git push
```

The real skill is using version control safely when production changes, incidents, collaboration, and automation are involved.
