# Part 10: Kubernetes Workloads and Pod Troubleshooting

Kubernetes interview questions become much more interesting when the interviewer stops asking:

"What is a Pod?"

and starts asking:

"A deployment should have six replicas. `kubectl get pods` shows four Running, one Pending, and one CrashLoopBackOff. Customers are reporting intermittent failures. Walk me through exactly what you would do."

That is the level this part focuses on.

A junior DevOps engineer does not need to know every Kubernetes internals detail. But you should be able to look at a workload, understand its desired state, inspect what Kubernetes actually created, follow events and logs, and isolate whether the problem is scheduling, image retrieval, configuration, startup, health checks, resources, storage, networking, or the application itself.

A useful mental model is:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
    ↓
Containers
    ↓
Application Process
```

But production traffic has a longer path:

```text
User
 ↓
Load Balancer / Ingress
 ↓
Service
 ↓
Endpoints
 ↓
Ready Pods
 ↓
Containers
 ↓
Application
 ↓
Dependencies
```

A Pod being `Running` proves only part of that chain.

---

# Question 1: A production Pod is not working. What is your first troubleshooting approach?

## Strong interview answer

I would avoid immediately deleting or restarting the Pod.

First, I want to understand the symptom and preserve evidence.

I would start with:

```bash
kubectl get pods -n production
```

Then inspect the affected Pod:

```bash
kubectl describe pod <pod-name> -n production
```

Then retrieve logs:

```bash
kubectl logs <pod-name> -n production
```

If the Pod contains multiple containers:

```bash
kubectl logs <pod-name> \
  -c <container-name> \
  -n production
```

I would also inspect recent events:

```bash
kubectl get events -n production \
  --sort-by='.lastTimestamp'
```

My first objective is to classify the failure.

```text
Pod problem
   ↓
Scheduling?
   ↓
Image?
   ↓
Configuration?
   ↓
Container startup?
   ↓
Health probe?
   ↓
Resources?
   ↓
Storage?
   ↓
Networking?
   ↓
Application?
```

The Pod status gives me a starting point, not necessarily the root cause.

# Question 2: What information does `kubectl get pods` actually give you?

## Strong interview answer

For example:

```bash
kubectl get pods -n production
```

might show:

```text
NAME                       READY   STATUS             RESTARTS   AGE
payments-76d8f9c7d-abc12   1/1     Running            0          4h
payments-76d8f9c7d-def34   0/1     CrashLoopBackOff   8          20m
payments-76d8f9c7d-ghi56   0/1     Pending            0          3m
```

I immediately look at several things.

`READY` tells me how many containers in the Pod are considered ready.

`STATUS` gives me the current high-level state.

`RESTARTS` can reveal repeated container failures.

`AGE` can help correlate the Pod with a recent deployment or event.

I would normally get additional information:

```bash
kubectl get pods -n production -o wide
```

This can show:

* Pod IP
* Node
* Readiness gates
* Additional scheduling information

I use this to look for patterns.

For example:

```text
Every failing Pod
    ↓
Node worker-03
```

is a very different investigation from:

```text
Failing Pods
    ↓
distributed across every node
```

# Question 3: What is the difference between a Pod being Running and being Ready?

## Strong interview answer

This is one of the most important Kubernetes distinctions.

A Pod can be:

```text
STATUS = Running
```

while:

```text
READY = 0/1
```

`Running` generally means the Pod has been scheduled and its containers have been created, with at least one container running or starting/restarting.

`Ready` relates to whether the workload should be considered ready to receive traffic.

For example:

```text
payments-abc   0/1   Running
```

The application process may be running, but the readiness probe may be failing.

That means:

```text
Pod exists
Container runs
Application not ready
```

For a Service-backed workload, an unready Pod will normally not be used as a ready endpoint for normal Service traffic.

So:

```text
Running
≠
Ready
```

and:

```text
Running
≠
Healthy application
```

# Question 4: A Pod is Pending. What does that mean?

## Strong interview answer

`Pending` means Kubernetes has accepted the Pod, but one or more containers have not yet been set up and started.

A common reason is that the scheduler cannot place the Pod on a suitable node.

I would start with:

```bash
kubectl describe pod <pod-name> -n production
```

The Events section may show something like:

```text
0/5 nodes are available:
3 Insufficient memory,
2 node(s) didn't match Pod's node affinity.
```

Now the problem is much clearer.

Possible causes of Pending Pods include:

* Insufficient CPU
* Insufficient memory
* Node selectors
* Node affinity
* Taints and tolerations
* Persistent volume binding
* Scheduling constraints

I would not begin by troubleshooting application logs because the application may not have started.

---

# Question 5: A Pod is Pending because of insufficient CPU. How would you investigate?

## Strong interview answer

First:

```bash
kubectl describe pod <pod-name> -n production
```

Suppose the event says:

```text
0/4 nodes are available:
4 Insufficient cpu
```

I would inspect the Pod's resource requests.

```bash
kubectl get pod <pod-name> \
  -n production \
  -o yaml
```

I might find:

```yaml
resources:
  requests:
    cpu: "4"
    memory: "2Gi"
```

If each node has only 2 CPU cores available for scheduling, the Pod cannot fit.

I would then investigate node capacity and allocations:

```bash
kubectl describe nodes
```

If metrics are available:

```bash
kubectl top nodes
```

But I would be careful with an important distinction.

The scheduler primarily uses resource requests and allocatable capacity for scheduling decisions. Current CPU utilization alone does not determine whether the Pod can be scheduled.

For example:

```text
Node actual CPU usage:
20%

Requested CPU already allocated:
95%
```

The scheduler may still reject another large Pod.

# Question 6: What is the difference between resource requests and limits?

## Strong interview answer

Requests are important for scheduling and resource guarantees.

Limits define a maximum resource boundary for the container.

For example:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Conceptually:

```text
Request
250m CPU
256Mi memory
    ↓
Scheduler considers this
when placing the Pod

Limit
1 CPU
512Mi memory
    ↓
Runtime resource boundary
```

CPU and memory behave differently when limits are reached.

CPU usage above the allowed CPU limit can be throttled.

Memory exceeding the effective container memory limit can result in the process being killed, commonly appearing as an OOM-related termination.

# Question 7: A container was OOMKilled. What does that mean?

## Strong interview answer

It means the container process was killed because of an out-of-memory condition, commonly because it exceeded its configured memory limit.

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

I may see:

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
```

Then inspect resource configuration:

```bash
kubectl get pod <pod-name> \
  -n production \
  -o yaml
```

And metrics:

```bash
kubectl top pod <pod-name> -n production
```

if Metrics Server or another metrics pipeline is available.

I would not immediately increase the memory limit.

First, I want to know why memory increased.

Possibilities include:

* Legitimate workload growth
* Memory leak
* Incorrect limit
* Large request payload
* Cache growth
* Application regression
* Runtime tuning issue

The correct fix depends on the cause.

---

# Question 8: Why might simply increasing the memory limit be a bad fix?

## Strong interview answer

Because it can hide the underlying problem.

Suppose:

```text
Normal application memory:
300 MiB

Current limit:
512 MiB

New release memory:
grows continuously until OOM
```

Changing:

```text
512 MiB
→
2 GiB
```

may only make the crash happen later.

I would compare:

```text
Previous version
vs.
Current version
```

and look at memory over time.

If memory grows continuously after the new deployment, I would suspect a regression or memory leak.

If the application legitimately requires 700 MiB under normal production load, then 512 MiB may simply be unrealistic.

Evidence determines the fix.

---

# Question 9: What is CrashLoopBackOff?

## Strong interview answer

CrashLoopBackOff means a container repeatedly starts, fails, and Kubernetes is delaying subsequent restart attempts.

Conceptually:

```text
Container starts
      ↓
Application fails
      ↓
Container exits
      ↓
Kubernetes restarts it
      ↓
Fails again
      ↓
Backoff delay increases
```

CrashLoopBackOff is a symptom.

It is not the root cause.

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

Then:

```bash
kubectl logs <pod-name> -n production
```

But if the container has restarted, one of the most useful commands is:

```bash
kubectl logs <pod-name> \
  -n production \
  --previous
```

That retrieves logs from the previous terminated container instance when available.

---

# Question 10: Why is `kubectl logs --previous` important?

## Strong interview answer

Because the current container may have just restarted.

Suppose:

```text
Container 1
starts
 ↓
throws database exception
 ↓
exits

Container 2
starts
 ↓
currently initializing
```

Running:

```bash
kubectl logs <pod-name>
```

may show only the new container's startup logs.

But:

```bash
kubectl logs <pod-name> --previous
```

may show the failure that caused the previous restart.

For CrashLoopBackOff troubleshooting, that can be critical evidence.

---

# Question 11: Give me common causes of CrashLoopBackOff.

## Strong interview answer

Possible causes include:

* Application crash
* Invalid command or arguments
* Missing configuration
* Missing secret
* Invalid environment variable
* Database connection failure
* Permission problem
* Missing file
* Failed startup migration
* Liveness probe repeatedly killing the container
* OOM termination
* Application exits after completing unexpectedly

I would not guess from the status alone.

I would correlate:

```text
describe
+
current logs
+
previous logs
+
events
+
termination reason
```

# Question 12: The Pod is CrashLoopBackOff after a deployment. Logs say `DATABASE_URL environment variable required`. What would you investigate?

## Strong interview answer

I would inspect how the variable should be supplied.

For example:

```bash
kubectl get deployment payments \
  -n production \
  -o yaml
```

I may find:

```yaml
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: payments-db
        key: database-url
```

Then verify the Secret exists:

```bash
kubectl get secret payments-db -n production
```

I would also verify the referenced key exists without exposing secret values unnecessarily.

The failure path may be:

```text
Deployment
    ↓
references Secret
    ↓
wrong key/name
    ↓
environment variable unavailable
    ↓
application exits
    ↓
CrashLoopBackOff
```

The correct fix is the configuration reference, not increasing replicas or restarting Pods repeatedly.

# Question 13: What is ImagePullBackOff?

## Strong interview answer

It means Kubernetes is unable to pull the container image and is backing off repeated pull attempts.

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

Events may reveal:

```text
Failed to pull image
```

Possible causes include:

* Incorrect image name
* Incorrect tag
* Image does not exist
* Private registry authentication failure
* Registry unavailable
* Network/DNS problem
* Rate limiting
* Architecture/platform mismatch in some cases

Again:

```text
ImagePullBackOff
```

is the visible state.

The event message usually provides the more useful reason.

---

# Question 14: A Pod shows `ErrImagePull` and then `ImagePullBackOff`. What is happening?

## Strong interview answer

Kubernetes attempts to retrieve the image.

The pull fails.

You may initially see:

```text
ErrImagePull
```

As Kubernetes retries with increasing delay, the Pod may show:

```text
ImagePullBackOff
```

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

If the event says:

```text
manifest unknown
```

I would check whether the specified tag actually exists.

If it says:

```text
unauthorized
```

I would investigate registry authentication and image pull secrets.

Different event messages point to different root causes.

---

# Question 15: How do you configure Kubernetes to pull from a private registry?

## Strong interview answer

One common mechanism is an image pull Secret.

For example, after creating the appropriate registry Secret, the Pod specification can reference:

```yaml
spec:
  imagePullSecrets:
    - name: registry-credentials
```

Then:

```yaml
containers:
  - name: api
    image: registry.example.com/payments:4.8.2
```

If the Secret is missing, invalid, expired, or in the wrong namespace, image pulls may fail.

I would check:

```bash
kubectl get secret registry-credentials \
  -n production
```

and inspect Pod events for authentication errors.

---

# Question 16: Why does namespace matter for Secrets and ConfigMaps?

## Strong interview answer

Many Kubernetes resources are namespace-scoped.

A Pod in:

```text
production
```

cannot simply reference a Secret that exists only in:

```text
staging
```

as though it were local to production.

For example:

```text
Namespace: staging
Secret: payments-db

Namespace: production
Pod: payments-api
```

The production Pod needs the required Secret available in the appropriate namespace.

This is a common source of deployment failures when manifests are promoted between environments.

---

# Question 17: What is CreateContainerConfigError?

## Strong interview answer

It commonly indicates Kubernetes cannot create the container because something in its configuration is invalid or unavailable.

Examples include:

* Missing Secret
* Missing ConfigMap
* Invalid referenced key
* Configuration issue in the Pod specification

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

The Events section often tells me exactly what Kubernetes could not find or configure.

For example:

```text
Error: secret "payments-secret" not found
```

That is much more actionable than the high-level Pod status.

---

# Question 18: A ConfigMap was updated, but the application still uses the old value. Why?

## Strong interview answer

It depends on how the ConfigMap is consumed.

If values are injected as environment variables, existing container processes do not automatically receive updated environment variables.

The Pod normally needs to be replaced or restarted through an appropriate rollout process.

If the ConfigMap is mounted as files, updates may eventually be reflected in the mounted data, but the application itself may not automatically reload the file.

So I ask:

```text
How is the ConfigMap consumed?
```

and:

```text
Does the application reload configuration dynamically?
```

Updating Kubernetes configuration does not necessarily mean the running application has consumed the update.

---

# Question 19: How would you trigger a controlled restart of a Deployment?

## Strong interview answer

For a Deployment:

```bash
kubectl rollout restart deployment/payments \
  -n production
```

Then monitor:

```bash
kubectl rollout status deployment/payments \
  -n production
```

I would still verify the application after the rollout.

A successful rollout command does not automatically prove customer-facing functionality is correct.

---

# Question 20: What is a Deployment?

## Strong interview answer

A Deployment manages the desired state for replicated stateless application Pods through ReplicaSets.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments
spec:
  replicas: 3
```

Conceptually:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pod 1
Pod 2
Pod 3
```

If one Pod disappears, the controller works to restore the desired replica count.

Deployments also support controlled rollouts and rollbacks.

---

# Question 21: Why does Kubernetes create a ReplicaSet when I create a Deployment?

## Strong interview answer

The Deployment manages ReplicaSets, and ReplicaSets maintain the desired number of matching Pods.

During an update, you may temporarily have:

```text
Deployment
   ↓
Old ReplicaSet
   ↓
old Pods

and

New ReplicaSet
   ↓
new Pods
```

The Deployment controls the transition between them according to the rollout strategy.

I can inspect:

```bash
kubectl get deployments -n production
kubectl get replicasets -n production
kubectl get pods -n production
```

Understanding this hierarchy helps troubleshoot failed rollouts.

---

# Question 22: A Deployment says 5 desired replicas but only 3 are available. What would you do?

## Strong interview answer

I would inspect the Deployment:

```bash
kubectl describe deployment <deployment-name> \
  -n production
```

Then ReplicaSets:

```bash
kubectl get rs -n production
```

Then Pods:

```bash
kubectl get pods -n production
```

I want to identify what happened to the missing two.

For example:

```text
Desired: 5

Running Ready: 3
Pending: 1
CrashLoopBackOff: 1
```

Now I have two separate problems.

The Pending Pod requires scheduling investigation.

The CrashLoopBackOff Pod requires container/application investigation.

I would troubleshoot them separately rather than treating "3 available" as a single root cause.

# Question 23: What is a StatefulSet?

## Strong interview answer

A StatefulSet is designed for workloads that require stable identities and often stable persistent storage.

Examples can include certain databases or clustered stateful systems.

Unlike interchangeable Deployment Pods such as:

```text
payments-7db6f6c88b-xk2sd
payments-7db6f6c88b-p7x92
```

StatefulSet Pods typically have ordered identities:

```text
database-0
database-1
database-2
```

They can also be associated with persistent volume claims in a predictable way.

I would not automatically use StatefulSet for every database. Managed database services may be operationally preferable depending on the environment.

---

# Question 24: What is a DaemonSet?

## Strong interview answer

A DaemonSet ensures that a Pod runs on all or selected nodes.

Typical uses include:

* Node monitoring agents
* Log collectors
* Security agents
* Networking components

Conceptually:

```text
Node 1 → Agent Pod
Node 2 → Agent Pod
Node 3 → Agent Pod
Node 4 → Agent Pod
```

If a new eligible node joins the cluster, the DaemonSet controller can place the Pod there automatically.

---

# Question 25: What is a Job?

## Strong interview answer

A Job is designed for workloads that should run to completion.

Examples:

```text
Database migration
Batch processing
Data transformation
One-time maintenance task
```

Unlike a Deployment, which normally aims to keep application Pods continuously running, a Job considers successful completion a valid end state.

For example:

```bash
kubectl get jobs -n production
```

might show:

```text
NAME          STATUS     COMPLETIONS
migration     Complete   1/1
```

---

# Question 26: What is a CronJob?

## Strong interview answer

A CronJob creates Jobs on a schedule.

Examples include:

* Scheduled reports
* Cleanup
* Data synchronization
* Periodic maintenance

Conceptually:

```text
CronJob
   ↓
Schedule
   ↓
Job
   ↓
Pod
   ↓
Task completes
```

I would also think about:

* Overlapping executions
* Failed Jobs
* History retention
* Idempotency
* Time zones where relevant
* Long-running Jobs

---

# Question 27: A CronJob runs twice and causes duplicate financial transactions. What is the deeper problem?

## Strong interview answer

The problem is not simply:

```text
Kubernetes ran the Job twice.
```

Critical scheduled operations should be designed with duplicate execution in mind.

I would investigate:

* Concurrency policy
* Job history
* Scheduling behavior
* Application idempotency
* Transaction identifiers

For example, the application should ideally recognize:

```text
transaction_id = 928381
```

has already been processed rather than blindly creating another transaction.

Infrastructure controls can reduce duplicate execution, but application-level idempotency is often important for high-value operations.

---

# Question 28: What is a liveness probe?

## Strong interview answer

A liveness probe helps Kubernetes determine whether a container is unhealthy in a way that warrants restarting it.

Example:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
```

Conceptually:

```text
Liveness succeeds
    ↓
Container remains running

Liveness repeatedly fails
    ↓
Container restarted
```

The liveness check should be designed carefully.

A bad liveness probe can create an outage.

---

# Question 29: How can a liveness probe create an outage?

## Strong interview answer

Suppose the application takes 90 seconds to initialize.

But the probe begins after:

```yaml
initialDelaySeconds: 10
```

and repeatedly fails.

Kubernetes may restart the container before initialization completes.

Then:

```text
Start
 ↓
10 seconds
 ↓
Probe fails
 ↓
Restart
 ↓
Start again
 ↓
Probe fails
 ↓
Restart
```

The application may never become ready.

A startup probe can be useful for applications with long initialization times.

---

# Question 30: What is a readiness probe?

## Strong interview answer

A readiness probe determines whether a Pod should currently receive traffic.

For example:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
```

If readiness fails:

```text
Pod may remain Running
      ↓
but becomes NotReady
      ↓
should not receive normal Service traffic
```

This is useful when the application process is alive but temporarily unable to serve requests safely.

---

# Question 31: What is a startup probe?

## Strong interview answer

A startup probe is useful for applications that need significant time to start.

For example:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
```

This allows up to approximately:

```text
5 seconds × 30
=
150 seconds
```

for startup before Kubernetes considers startup to have failed.

While the startup probe has not succeeded, liveness and readiness behavior is handled so slow startup does not get mistaken for a permanently unhealthy application.

---

# Question 32: Explain liveness, readiness, and startup probes in one interview answer.

## Strong interview answer

I think of them as three different questions.

```text
Startup:
Has the application finished starting?

Liveness:
Is the application alive enough to continue running?

Readiness:
Should this instance receive traffic?
```

They solve different problems.

Using the same aggressive endpoint and timing for all three without thinking about semantics can create production instability.

---

# Question 33: All Pods show Running, but the Service has no endpoints. What would you investigate?

## Strong interview answer

I would immediately check readiness and label selection.

First:

```bash
kubectl get pods -n production --show-labels
```

Then:

```bash
kubectl get service payments -n production -o yaml
```

Check the selector.

For example, Service:

```yaml
selector:
  app: payments
```

but Pods:

```yaml
labels:
  app: payment
```

The selector does not match.

I would also inspect EndpointSlices:

```bash
kubectl get endpointslices -n production \
  -l kubernetes.io/service-name=payments
```

Depending on cluster version and tooling, I may also inspect:

```bash
kubectl get endpoints payments -n production
```

The important lesson is:

```text
Running Pods
≠
Service has usable backends
```

# Question 34: A Service selector is correct, but there are still no ready endpoints. What next?

## Strong interview answer

I would inspect Pod readiness.

```bash
kubectl get pods -n production
```

If:

```text
payments-abc   0/1   Running
payments-def   0/1   Running
payments-ghi   0/1   Running
```

then all containers may be running but none are ready.

I would describe a Pod:

```bash
kubectl describe pod payments-abc -n production
```

and inspect readiness probe failures.

For example:

```text
Readiness probe failed:
HTTP probe failed with statuscode: 503
```

Now the Service is not necessarily the root cause.

The application readiness state is.

---

# Question 35: What is the difference between Pod IP and Service IP?

## Strong interview answer

A Pod receives an IP associated with that Pod instance.

Pods are replaceable, so applications should generally not depend on a specific Pod IP.

A Service provides a stable logical access point for a set of Pods.

Conceptually:

```text
Client
   ↓
Service
   ↓
Pod A
Pod B
Pod C
```

If Pod B disappears and a replacement receives a different IP, the client still uses the Service.

This provides service discovery and stable access independent of individual Pod lifecycle.

---

# Question 36: Why should applications avoid hardcoding Pod IP addresses?

## Strong interview answer

Because Pod IPs can change when Pods are replaced.

For example:

```text
Before restart:
payments Pod
10.244.2.17

After replacement:
payments Pod
10.244.3.42
```

A dependency hardcoded to:

```text
10.244.2.17
```

will eventually fail.

Applications should normally use Kubernetes Services or another appropriate service-discovery mechanism.

---

# Question 37: How would you test DNS resolution from inside a Pod?

## Strong interview answer

If the application image contains the required tool:

```bash
kubectl exec -it <pod-name> \
  -n production \
  -- nslookup database
```

or:

```bash
kubectl exec -it <pod-name> \
  -n production \
  -- getent hosts database
```

But production application images are often intentionally minimal and may not contain diagnostic tools.

In that case, I may use an approved temporary debugging Pod or ephemeral debugging container rather than modifying the production image simply to add troubleshooting utilities.

# Question 38: A Pod can reach another Pod by IP but not through the Service name. What does that suggest?

## Strong interview answer

It narrows the problem toward:

* Kubernetes DNS
* Service configuration
* Service selector/endpoints
* Namespace/name resolution
* Service port mapping

I would check:

```bash
kubectl get svc -n production
```

Then:

```bash
kubectl describe svc <service-name> \
  -n production
```

Then EndpointSlices:

```bash
kubectl get endpointslices -n production \
  -l kubernetes.io/service-name=<service-name>
```

Then DNS from a Pod.

If direct Pod-IP communication works, I have evidence that basic Pod-to-Pod connectivity may be functioning.

# Question 39: A Service works using its ClusterIP but not by DNS name. Where would you focus?

## Strong interview answer

That strongly suggests a DNS-related issue rather than the Service backend itself.

I would test:

```bash
nslookup kubernetes.default.svc.cluster.local
```

from an appropriate troubleshooting Pod.

Then inspect DNS components, commonly CoreDNS:

```bash
kubectl get pods -n kube-system
```

I might inspect:

```bash
kubectl logs -n kube-system \
  -l k8s-app=kube-dns
```

depending on the cluster configuration.

I would also inspect the Pod's resolver configuration:

```bash
cat /etc/resolv.conf
```

inside the Pod.

# Question 40: What does `kubectl describe pod` give you that `kubectl logs` does not?

## Strong interview answer

Logs primarily show what the containerized application writes to stdout and stderr.

`kubectl describe pod` gives Kubernetes-level information such as:

* Scheduling
* Node
* Pod IP
* Container state
* Previous container state
* Exit code
* Restart count
* Probe failures
* Mounts
* Conditions
* Events

For example, an application may never start because Kubernetes cannot mount a volume.

There may be no useful application logs.

But `kubectl describe pod` might show:

```text
FailedMount
```

That is why I normally use both.

# Question 47: How do you roll back a Kubernetes Deployment?

# Question 48: Why can a Kubernetes rollback fail even if `kubectl rollout undo` succeeds?

## Strong interview answer

Because application compatibility may already have changed.

For example:

```text
Version 5
expects database column:
customer_name
```

Version 6 deploys a migration that permanently removes that column.

Rolling the Deployment back to Version 5 may create Pods successfully.

But the application can still fail because the database schema is incompatible.

So:

```text
Kubernetes rollback succeeded
```

does not necessarily mean:

```text
Application recovery succeeded
```

# Question 49: What is `maxUnavailable` during a rolling update?

## Strong interview answer

It controls how many desired replicas can be unavailable during the update.

For example:

```yaml
strategy:
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1
```

For a Deployment with four replicas, Kubernetes can manage the rollout while respecting these availability and surge constraints.

`maxSurge` controls how many extra Pods can exist above the desired replica count during the update.

These settings affect rollout speed, capacity requirements, and availability.

---

# Question 50: How can a rolling update cause resource pressure?

## Strong interview answer

Because `maxSurge` can temporarily create more Pods than the normal replica count.

Suppose:

```text
Normal:
10 Pods

maxSurge:
25%
```

During deployment, the cluster may temporarily need capacity for additional Pods.

If nodes are already nearly fully allocated, new Pods may remain Pending.

Then the rollout may stall.

So rollout strategy and cluster capacity must be considered together.

---

# Question 51: A new Deployment version is failing readiness checks. Will Kubernetes necessarily continue replacing every old Pod?

## Strong interview answer

The Deployment controller follows its rolling-update strategy and availability constraints.

If new Pods fail to become available, the rollout can stall rather than successfully replacing the entire old ReplicaSet.

That is one of the benefits of readiness and controlled rollout behavior.

But I still need monitoring and deployment timeout logic so the team knows the rollout has failed.

I would inspect:

```bash
kubectl rollout status deployment/<name> \
  -n production
```

rather than assuming a deployment completed just because the manifest was accepted.

# Question 52: What is the difference between `kubectl apply` succeeding and the application deployment succeeding?

## Strong interview answer

`kubectl apply` succeeding means Kubernetes accepted the desired-state change.

It does not mean the resulting workload became healthy.

The actual process is:

```text
kubectl apply
     ↓

     ↓
Controllers reconcile
     ↓
Scheduler places Pods
     ↓
Images pulled
     ↓
Containers start
     ↓
Probes pass
     ↓
Pods become Ready
     ↓
Service sends traffic
     ↓
Application works
```

A production pipeline should verify the later stages too.

# Question 57: Why can binding an application to `127.0.0.1` cause Kubernetes connectivity problems?

## Strong interview answer

If the application listens only on loopback:

```text
127.0.0.1:8080
```

it may be reachable from within the same container but not through the Pod's network interface as expected.

For a network-facing workload, the application commonly needs to listen on:

```text
0.0.0.0:<port>
```

or the appropriate interface.

This is a classic situation where:

```bash
curl localhost:8080
```

inside the container works, but Service traffic fails.

# Question 58: What is a NetworkPolicy?

## Strong interview answer

NetworkPolicy allows network communication rules to be defined for Pods when the cluster's networking implementation supports enforcement.

Conceptually:

```text
Frontend
    ↓ allowed
API
    ↓ allowed
Database

Frontend
    X
Database
```

Policies can restrict ingress and egress based on Pod selectors, namespaces, ports, and other supported criteria.

The exact behavior depends on the CNI/networking implementation.

```text

 ↓
```

```text

 ↓
```

# Question 60: Why is DNS important when designing NetworkPolicies?

## Strong interview answer

Applications frequently depend on DNS before they can connect to services by name.

If egress is restricted but DNS traffic is not allowed appropriately, applications may fail with name-resolution errors even though the actual destination port would otherwise be permitted.

The observed symptom might be:

```text
database.production.svc.cluster.local
cannot resolve
```

rather than:

```text
connection refused
```

That distinction points me toward DNS.

# Question 61: A Pod is repeatedly being evicted. What would you investigate?

## Strong interview answer

I would inspect:

```bash
kubectl describe pod <pod-name> -n production
```

and node conditions:

```bash
kubectl describe node <node-name>
```

Possible causes include node pressure such as:

* Memory pressure
* Disk pressure
* Ephemeral storage pressure

I would also inspect resource requests, limits, and ephemeral storage usage.

Eviction is different from an application voluntarily exiting.

---

# Question 62: What is ephemeral storage in Kubernetes?

## Strong interview answer

Containers can consume local ephemeral storage for writable container layers, logs, `emptyDir` volumes, and related node-local storage usage.

It is not the same as durable persistent storage.

If an application writes huge temporary files or logs, it can contribute to node disk pressure.

That can eventually affect other workloads and potentially trigger eviction behavior.

Production monitoring should therefore include node filesystem and workload storage usage, not only CPU and memory.

---

# Question 63: What happens to an `emptyDir` volume when the Pod is deleted?

## Strong interview answer

An `emptyDir` volume exists for the lifetime of the Pod.

Containers within the Pod can share it.

If an individual container restarts while the Pod remains, the `emptyDir` data can remain.

But when the Pod itself is removed, the `emptyDir` data is removed with it.

Therefore:

```text
emptyDir
≠
persistent storage
```

It is useful for:

* Temporary files
* Shared scratch space
* Cache
* Inter-container data

but not for data that must survive Pod replacement.

---

# Question 64: An application stores uploaded customer files in `/uploads` inside the container. What problem do you see?

## Strong interview answer

If `/uploads` is only part of the container's ephemeral writable filesystem, the files are tied to that Pod/container lifecycle.

A replacement may lose them.

Also, with multiple replicas:

```text
Request 1
→ Pod A
→ file saved locally

Request 2
→ Pod B
→ file not present
```

That creates inconsistent behavior.

Persistent/shared object storage or an appropriate persistent storage architecture should be considered depending on the application's requirements.

# Question 65: What is a node selector?

## Strong interview answer

A node selector constrains a Pod to nodes with matching labels.

For example:

```yaml
spec:
  nodeSelector:
    workload: payments
```

Then eligible nodes need:

```text
workload=payments
```

If no node has the required label, the Pod may remain Pending.

I would inspect:

```bash
kubectl get nodes --show-labels
```

and Pod events.

---

# Question 66: What are taints and tolerations?

## Strong interview answer

Taints allow nodes to repel Pods that do not tolerate the taint.

For example:

```text
Node:
dedicated=database:NoSchedule
```

A Pod without the corresponding toleration will not normally be scheduled there.

Conceptually:

```text
Node says:
"Only workloads that tolerate this condition."
```

A toleration allows the Pod to be considered for that node.

But a toleration does not necessarily force the Pod onto that node.

---

# Question 67: A Pod says `0/5 nodes are available: 5 node(s) had untolerated taint`. What is wrong?

## Strong interview answer

Every candidate node has a taint the Pod does not tolerate.

I would inspect node taints:

```bash
kubectl describe nodes
```

Then inspect the Pod's tolerations:

```bash
kubectl get pod <pod-name> \
  -n production \
  -o yaml
```

The fix depends on intent.

I would not automatically remove the node taints.

They may exist deliberately to protect dedicated infrastructure.

The correct question is:

```text
Should this workload run on these nodes?
```

If yes, configure the appropriate toleration and scheduling rules.

If no, provide eligible node capacity.

---

# Question 68: What is node affinity?

## Strong interview answer

Node affinity provides more expressive scheduling rules than a simple node selector.

It can define required or preferred placement based on node labels.

For example:

```text
Required:
must run in a certain class of node

Preferred:
try to run in a certain zone or node type
```

Overly restrictive affinity can make Pods unschedulable.

During troubleshooting, I always compare scheduling constraints with the labels and capacity actually available in the cluster.

---

# Question 69: Why can anti-affinity improve availability?

## Strong interview answer

Suppose I have three replicas.

Without placement controls:

```text
Node 1
Pod A
Pod B
Pod C
```

If Node 1 fails, all three replicas disappear.

Anti-affinity or topology-spread mechanisms can encourage or require distribution:

```text
Node 1 → Pod A
Node 2 → Pod B
Node 3 → Pod C
```

This reduces correlated failure risk.

But overly strict rules can also make scheduling difficult when cluster capacity is limited.

---

# Question 70: One node fails. What happens to Deployment Pods on that node?

## Strong interview answer

Kubernetes detects node unavailability according to its node lifecycle mechanisms.

The exact timing depends on cluster configuration and conditions.

For a Deployment, the system eventually works to restore the desired replica count by creating replacement Pods on healthy eligible nodes.

Conceptually:

```text
Desired replicas:
3

Node failure:
Pod B unavailable

Controller:
desired 3
actual available fewer
    ↓
replacement scheduled
```

But recovery requires enough healthy cluster capacity.

---

# Question 71: What if there is no spare cluster capacity after a node failure?

## Strong interview answer

Replacement Pods may remain Pending.

That means Kubernetes knows the desired state but cannot satisfy it.

For example:

```text
Desired:
10 replicas

Healthy nodes can currently fit:
7
```

Kubernetes cannot manufacture CPU and memory.

High availability therefore requires capacity planning, not just replica configuration.

---

That strongly suggests a node-specific issue.

I would compare:

* Node conditions
* CNI/networking

* DNS behavior
* Runtime
* Disk
* Memory
* Kernel

If metrics are available:


A healthy Node A gives me a useful comparison point.

# Question 75: What is the purpose of labels in Kubernetes?

## Strong interview answer

Labels are key-value metadata used to organize and select Kubernetes objects.

Example:

```yaml
labels:
  app: payments
  tier: backend
  environment: production
```

Selectors can then identify objects.

For example, a Service may select:

```yaml
selector:
  app: payments
```

Labels therefore affect actual application behavior, not just organization.

A wrong label can break traffic routing.

---

# Question 76: What happens if a Service selector accidentally matches Pods from the wrong application?

## Strong interview answer

The Service may route traffic to those Pods if they are otherwise eligible endpoints.

For example:

```text
Service selector:
app=payments
```

But another workload was accidentally labeled:

```text
app=payments
```

Now traffic can reach unintended Pods.

This is why label conventions need discipline.

I would inspect:

```bash
kubectl get pods \
  -n production \
  -l app=payments \
  --show-labels
```

and compare the results with the expected workload.

# Question 77: How do you inspect environment variables inside a running Pod?

## Strong interview answer

If appropriate:

```bash
kubectl exec <pod-name> \
  -n production \
  -- env
```

# Question 78: A Secret is correct in Kubernetes, but the running application still has the old secret value. Why?

## Strong interview answer

If the Secret was injected as an environment variable, the running process does not automatically receive a new environment after the Secret changes.

The Pod normally needs to be replaced through the appropriate deployment process.

If the Secret is mounted as a volume, file updates behave differently, but the application may still need to reload the data.

So again:

```text
Kubernetes object updated
≠
Application automatically consumed update
```

# Question 79: What is an init container?

## Strong interview answer

An init container runs before the main application containers.

It can perform setup tasks such as:

* Waiting for a dependency
* Preparing files
* Performing initialization
* Fetching configuration
* Setting permissions

Conceptually:

```text
Pod created
   ↓
Init Container 1
   ↓
Init Container 2
   ↓
Main Application Container
```

If an init container fails repeatedly, the main application container may never start.

# Question 81: What is a sidecar container?

## Strong interview answer

A sidecar is an additional container in the same Pod that provides supporting functionality to the main application.

Examples may include:

* Proxy
* Log processing
* Service mesh proxy
* Supporting synchronization process

Containers in the same Pod share certain resources, including the Pod network namespace.

Conceptually:

```text
Pod
 ├── Application Container
 └── Sidecar Container

Shared Pod IP
```

A sidecar failure can sometimes affect the application even when the main container itself is healthy.

# Question 82: A Pod shows `1/2 Running`. What does that tell you?

It tells me the Pod contains two containers but only one is currently considered ready.

```bash
kubectl get pod <pod-name> \
```

# Question 87: What is a Pod Disruption Budget?

## Strong interview answer

A PodDisruptionBudget, or PDB, helps limit how many replicas of an application can be voluntarily disrupted at the same time.

For example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payments-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payments
```

If there are three replicas, the PDB can help ensure voluntary operations such as node draining do not intentionally reduce availability below the configured threshold.

A PDB does not prevent every type of failure.

It does not stop hardware crashes or other involuntary disruptions.

---

# Question 88: What does `kubectl drain` do?

## Strong interview answer

It prepares a node for maintenance by marking it unschedulable and evicting eligible workloads according to Kubernetes rules and policies.

For example:

```bash
kubectl drain <node-name> \
  --ignore-daemonsets
```

The exact options depend on the workloads and environment.

Before draining a production node, I would check:

* Available capacity
* PDBs
* Stateful workloads
* DaemonSets
* Local storage
* Maintenance impact

Draining should not be treated as a harmless command.

---

# Question 89: What is the difference between `cordon` and `drain`?

## Strong interview answer

`cordon` marks a node unschedulable for new Pods:

```bash
kubectl cordon <node-name>
```

Existing workloads normally remain.

`drain` goes further and attempts to evict eligible workloads from the node:

```bash
kubectl drain <node-name> \
  --ignore-daemonsets
```

Conceptually:

```text
cordon
→ stop new scheduling

drain
→ stop new scheduling
  + move eligible workloads away
```

# Question 90: Give me your complete Kubernetes Pod troubleshooting workflow.

## Strong interview answer

I use a layered approach.

### 1. Establish impact

Ask:

```text
What is broken?

How many users?

Which service?

When did it start?

What changed?
```

### 2. Check workload state

```bash
kubectl get deployments -n production
kubectl get pods -n production
kubectl get pods -n production -o wide
```

### 3. Classify Pod state

```text
Pending
ImagePullBackOff
CreateContainerConfigError
CrashLoopBackOff
Running but NotReady
OOMKilled
Evicted
Terminating
```

# Production Scenario 1: Five Pods Are Running, but Customers Still Receive Errors

The interviewer says:

> "Your payments Deployment has five replicas. `kubectl get pods` shows all five as Running. Customers report that roughly 20 percent of payment requests fail. CPU and memory are normal. How would you investigate?"

A strong candidate should notice:

```text
5 replicas

approximately 20% failures
```

One hypothesis is that one of the five backends is unhealthy.

But I would verify it.

Start with:

```bash
kubectl get pods \
  -n production \
  -o wide
```

Suppose:

```text
NAME          READY   STATUS    NODE
payments-a    1/1     Running   worker-1
payments-b    1/1     Running   worker-2
payments-c    1/1     Running   worker-3
payments-d    1/1     Running   worker-4
payments-e    1/1     Running   worker-5
```

Everything appears healthy.

Now inspect application metrics or logs by Pod.

Suppose:

```text
payments-a → 0.1% errors
payments-b → 0.2%
payments-c → 0.1%
payments-d → 0.2%
payments-e → 97% errors
```

Now we have a specific unhealthy instance.

Inspect:

```bash
kubectl logs payments-e \
  -n production \
  --tail=200
```

Suppose the logs show:

```text
TLS certificate validation failed
when connecting to payment-gateway.internal
```

Now compare configuration with a healthy Pod.

The image digest is identical.

ConfigMap is identical.

But `payments-e` is running on:

```text
worker-5
```

Every other healthy Pod is on other nodes.

Now I would investigate whether this is a node-specific problem.

Perhaps worker-5 has an outdated node-level certificate or networking configuration.

The important troubleshooting progression was:

```text
20% user failures
      ↓
Possible one-of-five backend issue
      ↓
Verify errors by Pod
      ↓
Identify payments-e
      ↓
Compare healthy and failing Pods
      ↓
Same application artifact
      ↓
Different node
      ↓
Investigate worker-5
```

I would not solve this by randomly increasing replicas.

# Production Scenario 2: Deployment Completed, but No New Pods Receive Traffic

The interviewer says:

> "A new version of the checkout service was deployed. `kubectl apply` succeeded. The new Pods are Running, but all traffic continues going to the old Pods. Why?"

First:

```bash
kubectl get pods -n production
```

Suppose:

```text
checkout-old-a   1/1   Running
checkout-old-b   1/1   Running
checkout-new-a   0/1   Running
checkout-new-b   0/1   Running
```

The new Pods are Running.

They are not Ready.

Inspect:

```bash
kubectl describe pod checkout-new-a \
  -n production
```

Events show:

```text
Readiness probe failed:
HTTP probe failed with statuscode: 404
```

Inspect the Deployment.

The readiness probe uses:

```yaml
path: /health
```

But the new application version changed the endpoint to:

```text
/health/ready
```

The application runs.

Kubernetes correctly keeps it out of Service traffic because the configured readiness check fails.

The failure path is:

```text
New image
   ↓
Container starts
   ↓
Application runs
   ↓
Readiness probe requests /health
   ↓
Application returns 404
   ↓
Pod remains NotReady
   ↓
Service continues using old ready Pods
```

The correct fix is the probe configuration.

This is why:

```text
Running
≠
Ready
```

matters so much.

# Production Scenario 3: Pods Suddenly Enter CrashLoopBackOff After Secret Rotation

The interviewer says:

> "The database password was rotated at 11:00. Ten minutes later, application Pods started entering CrashLoopBackOff. What would you investigate?"

I would correlate the timing immediately.

```text
11:00
Secret rotation

11:10
Application failures
```

Then:

```bash
kubectl logs <pod-name> \
  -n production \
  --previous
```

Suppose:

```text
FATAL:
database authentication failed
```

Now inspect how credentials are supplied.

The application receives:

```text
DATABASE_PASSWORD
```

from a Kubernetes Secret as an environment variable.

The Secret was updated.

But the existing Pods still have the previous environment value.

Then a liveness check begins failing because the application cannot function correctly, causing restarts.

The new container instances receive the updated Secret.

But suppose the database password rotation was incorrectly performed in this order:

```text
Database password changed
      ↓
Old Pods still have old password
      ↓
Connections fail
      ↓
Application becomes unhealthy
```

A safer rotation process needs to consider application compatibility and credential rollout sequencing.

The incident is not simply:

```text
Kubernetes Secret problem.
```

It is a credential-rotation coordination problem across:

```text
Database
+
Kubernetes Secret
+
Running Pods
+
Application connection behavior
```

# Production Scenario 4: Deployment Is Stuck With Pending Pods

The interviewer says:

> "Your API Deployment is scaling from 10 to 20 replicas because of increased traffic. The new ten Pods remain Pending. Existing Pods are at 80 percent CPU. What do you do?"

Start with one Pending Pod:

```bash
kubectl describe pod <pending-pod> \
  -n production
```

Suppose:

```text
0/5 nodes are available:
5 Insufficient cpu
```

Now the issue is cluster capacity.

Check nodes:

```bash
kubectl top nodes
```

and:

```bash
kubectl describe nodes
```

Suppose each application Pod requests:

```yaml
resources:
  requests:
    cpu: "1"
```

and existing resource requests consume almost all allocatable CPU.

The scheduler cannot place the additional Pods.

The desired architecture is:

```text
Traffic rises
     ↓
Application needs more replicas
     ↓
HPA increases desired Pods
     ↓
Scheduler needs node capacity
     ↓
No capacity available
     ↓
Pods Pending
```

Horizontal Pod Autoscaling alone cannot solve node capacity shortages.

The environment may also require node autoscaling or enough pre-provisioned spare capacity.

This is a strong production interview lesson:

```text
Pod autoscaling
≠
cluster capacity autoscaling
```

# Production Scenario 5: Every Pod on One Node Starts Failing

The interviewer says:

> "Your application has twelve replicas across four nodes. Suddenly, three Pods start failing at almost exactly the same time. All three are on the same node. What does that tell you?"

That is a major clue.

```text
12 Pods
4 Nodes

3 failures
      ↓
all on Node 3
```

I would shift investigation toward the node.

First:

```bash
kubectl describe node <node-3>
```

Look for:

```text
Ready
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

Then inspect events.

If metrics are available:

```bash
kubectl top node <node-3>
```

Suppose Node 3 has:

```text
DiskPressure=True
```

Further investigation shows its filesystem is almost full because container logs grew unexpectedly.

The application itself may be healthy.

The shared infrastructure beneath those Pods is failing.

The reasoning is:

```text
Multiple independent Pods
      ↓
fail simultaneously
      ↓
same node
      ↓
shared dependency = node
```

This is exactly why `kubectl get pods -o wide` is so useful.

# Production Scenario 6: The Pod That Kubernetes Keeps Killing

The interviewer says:

> "An application takes about two minutes to initialize. Kubernetes continuously restarts it after deployment. Developers say it works perfectly when they run the same image locally."

Inspect:

```bash
kubectl describe pod <pod-name> \
  -n production
```

Suppose events show repeated:

```text
Liveness probe failed
Killing container
```

The configuration is:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 3
```

The application needs:

```text
120 seconds
```

to start.

But Kubernetes begins liveness checking after:

```text
10 seconds
```

and can kill the container after repeated failures long before startup completes.

The application never gets enough time to initialize.

A startup probe may be appropriate.

For example:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 30

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
```

Now startup can take up to approximately:

```text
5 × 30
=
150 seconds
```

before being considered failed.

The deeper lesson is:

```text
Bad health checks
can make a healthy application
look unhealthy.
```

The interviewer says:

> "All Pods are Running and Ready. The Deployment is available. The Service has endpoints. Yet checkout requests return HTTP 500. Where do you look?"

At this point, Kubernetes workload health may not be the problem.

I would inspect application logs:

```bash
kubectl logs \
  -l app=checkout \
  -n production \
  --tail=200
```

Suppose:

```text
ERROR:
payment-provider request timed out
```

Now I would test the downstream path.

```text
Checkout Pod
     ↓
Payment Provider
```

The readiness probe might test only:

```text
/health/ready
```

which verifies the application can accept requests.

It does not necessarily prove every external dependency works.

I would investigate:

* DNS resolution
* Egress
* NetworkPolicy
* External API
* TLS
* Credentials
* Dependency latency

The important interview answer is:

```text
Kubernetes healthy
does not mean
the entire distributed system is healthy.
```

# Production Scenario 8: A Rollout Broke Only Half the Users

The interviewer says:

> "After deploying version 8.2, approximately half of users experience errors. Kubernetes shows old and new Pods running simultaneously. What do you suspect?"

During a rolling deployment, multiple application versions can coexist.

Suppose:

```text
Old ReplicaSet
Version 8.1
3 Pods

New ReplicaSet
Version 8.2
3 Pods
```

If 8.2 contains a problem, approximately half of traffic could fail.

I would compare metrics and logs by version.

For example:

```text
8.1:
0.1% errors

8.2:
48% errors
```

Now the release is clearly implicated.

I would stop or reverse the rollout according to incident procedures.

Then determine why the new Pods passed readiness.

Perhaps:

```text
/health/ready
```

worked, but a production business operation failed.

This highlights why progressive delivery should monitor application and business metrics, not only Kubernetes readiness.

# Production Scenario 9: A Pod Cannot Reach the Database After a Security Change

The interviewer says:

> "Security introduced default-deny NetworkPolicies. Immediately afterward, the API can no longer connect to PostgreSQL. Both Pods are Running and Ready. How do you investigate?"

I would inspect policies:

```bash
kubectl get networkpolicy \
  -n production
```

Then:

```bash
kubectl describe networkpolicy \
  -n production
```

The required path is:

```text
API Pod
   ↓
TCP 5432
   ↓
PostgreSQL Pod
```

The policy must permit that intended traffic.

But I also need DNS:

```text
API
 ↓
DNS lookup
 ↓
postgres.production.svc.cluster.local
```

If DNS is blocked, the application may never reach the database connection stage.

I would test separately:

```text
DNS resolution
```

then:

```text
TCP connectivity
```

then:

```text
Database authentication
```

Do not collapse all three into:

```text
Database connection problem.
```

# Production Scenario 10: The Deployment That Passed CI/CD but Failed Production

The interviewer says:

> "The pipeline successfully built the image, pushed it to the registry, and ran `kubectl apply`. The deployment job is green. Production is down. What is wrong with the pipeline design?"

The pipeline validated:

```text
Build succeeded
      ↓
Push succeeded
      ↓
kubectl apply succeeded
```

It did not necessarily validate:

```text
Rollout completed
      ↓
Pods Ready
      ↓
Service has endpoints
      ↓
Application responds
      ↓
Critical transaction works
```

A stronger pipeline may include:

```bash
kubectl apply -f deployment.yaml
```

Then:

```bash
kubectl rollout status deployment/payments \
  -n production \
  --timeout=5m
```

Then controlled application verification.

For example:

```text
Health check
      ↓
Smoke test
      ↓
Critical API request
      ↓
Observe error rate
```

If verification fails:

```text
Stop rollout
      ↓
Alert
      ↓
Rollback or roll forward
according to incident policy
```

The deployment pipeline should not define success as:

```text
Kubernetes accepted my YAML.
```

Production success means the intended service is actually functioning.

# The Troubleshooting Pattern to Remember

Do not memorize Kubernetes troubleshooting as hundreds of unrelated commands.

Think in layers.

```text
1. Desired State
Deployment / StatefulSet / Job
          ↓
2. Controller
ReplicaSet
          ↓
3. Scheduling
Node / CPU / Memory / Taints / Affinity
          ↓
4. Pod Creation
Image / Secret / ConfigMap / Volume
          ↓
5. Container Startup
Command / Arguments / Application
          ↓
6. Health
Startup / Liveness / Readiness
          ↓
7. Service Discovery
Service / Selector / EndpointSlice / DNS
          ↓
8. Connectivity
Ports / NetworkPolicy / CNI
          ↓
9. Dependencies
Database / API / Storage
          ↓
10. User Experience
Errors / Latency / Business Transactions
```

When you know which layer is failing, the number of possible causes becomes much smaller.

# What Junior DevOps Candidates Should Take From Part 10

The most important Kubernetes interview skill is not remembering every `kubectl` command.

It is learning to interpret evidence.

When you see:

```text
Pending
```

think:

```text
Why can't Kubernetes place or initialize this Pod?
```

When you see:

```text
ImagePullBackOff
```

think:

```text
Why can't Kubernetes retrieve this image?
```

When you see:

```text
CreateContainerConfigError
```

think:

```text
What required configuration cannot be resolved?
```

When you see:

```text
CrashLoopBackOff
```

think:

```text
Why does the container keep terminating?
```

When you see:

```text
OOMKilled
```

think:

```text
Why did this workload exceed available or configured memory?
```

When you see:

```text
Running 0/1
```

think:

```text
Why is the application not Ready?
```

When you see:

```text
Running 1/1
```

but users still report failures, think beyond the Pod:

```text
Service?
Ingress?
Network?
Dependency?
Application?
Production data?
```

And remember these distinctions:

```text
Pod Running
≠
Pod Ready
```

```text
Pod Ready
≠
Every application function works
```

```text
kubectl apply succeeded
≠
Deployment succeeded
```

```text
Deployment succeeded
≠
Production is healthy
```

```text
More replicas
≠
More cluster capacity
```

```text
Restarting a Pod
≠
Fixing the root cause
```

```text
Kubernetes automation
≠
automatic reliability
```

The strongest junior candidate can move from a vague symptom such as:

```text
"The Kubernetes application is down."
```

to a precise diagnosis such as:

```text
"The new Deployment created three Pods successfully, but all three remain NotReady because the readiness probe still checks `/health`, while the new application exposes `/health/ready`. The Service therefore has no ready endpoints for the new ReplicaSet. I would correct the probe configuration, redeploy, verify rollout status and EndpointSlices, test the application through the Service, and monitor the error rate before considering the incident resolved."
```

That is the difference between knowing Kubernetes terminology and being able to troubleshoot a Kubernetes workload in production.
