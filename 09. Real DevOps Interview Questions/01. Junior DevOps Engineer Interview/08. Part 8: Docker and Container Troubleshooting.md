# Part 8: Docker and Container Troubleshooting

Docker interview questions often begin with simple concepts such as images, containers, Dockerfiles, volumes, and networks.

Real technical interviews usually go further.

An interviewer may give you a running production scenario and ask you to diagnose it:

* A container starts and immediately exits.
* The image builds successfully, but the application does not start.
* The application works locally but fails inside Docker.
* The container is running, but users cannot reach it.
* Two containers cannot communicate.
* DNS resolution fails inside a container.
* Data disappears whenever the container is recreated.
* A container receives `Permission denied`.
* The application is killed because it consumes too much memory.
* A container constantly restarts.
* Docker reports that a port is already allocated.
* The image is unexpectedly several gigabytes.
* A new image was pushed, but production still runs the old application.
* A health check reports `unhealthy` even though the process is running.
* The Docker host runs out of disk space.

The interviewer is usually testing whether you understand what is actually happening between:

```text
Dockerfile
    ↓
Image
    ↓
Container
    ↓
Process
    ↓
Network
    ↓
Storage
    ↓
Application
    ↓
User
```

A container being `Up` does not automatically mean the application is healthy.

That distinction is fundamental to production container troubleshooting.

---

# Question 1: What is the difference between a Docker image and a container?

## Strong interview answer

A Docker image is an immutable template used to create containers.

It contains the application and the filesystem content required by the image, such as:

* Runtime
* Libraries
* Application code
* Configuration defaults
* Metadata

A container is a runtime instance created from an image.

For example:

```bash
docker pull nginx:1.27
```

downloads an image.

Running:

```bash
docker run -d --name web nginx:1.27
```

creates and starts a container from that image.

Conceptually:

```text
Dockerfile
    ↓
docker build
    ↓
Image
    ↓
docker run
    ↓
Container
```

Multiple containers can be created from the same image.

The image itself does not become the running container.

# Question 2: A Docker container starts and immediately exits. How would you troubleshoot it?

## Strong interview answer

I would not repeatedly restart the container first.

I would determine why its main process exited.

Start with:

```bash
docker ps -a
```

Unlike:

```bash
docker ps
```

which shows running containers, `docker ps -a` also shows stopped containers.

I would inspect the status and exit code.

Then check the logs:

```bash
docker logs <container-name>
```

For recent output:

```bash
docker logs --tail 100 <container-name>
```

Then inspect the container:

```bash
docker inspect <container-name>
```

I would look for:

* Exit code
* Entrypoint
* Command
* Environment variables
* Mounts
* Network configuration

Common causes include:

```text
Wrong CMD or ENTRYPOINT
Application crash
Missing environment variable
Missing configuration file
Permission failure
Dependency unavailable
Incorrect working directory
Application finishes normally
```

The key point is that a container normally remains running only while its main process remains running.

---

# Question 3: Why does a container stop when its main process exits?

## Strong interview answer

A container's lifecycle is tied to its primary process, normally PID 1 inside the container.

Suppose the container runs:

```dockerfile
CMD ["node", "server.js"]
```

Conceptually:

```text
Container
   ↓
PID 1
node server.js
```

If `node server.js` exits, the container stops.

Docker is not a virtual machine that needs to remain running independently of the application process.

This also explains why something like:

```dockerfile
CMD ["echo", "Hello"]
```

creates a container that prints the message and exits.

That is expected behavior.

The command completed.

---

# Question 4: How would you determine why a container exited?

## Strong interview answer

I would combine status, logs, and inspection.

First:

```bash
docker ps -a
```

Then:

```bash
docker logs <container>
```

Then:

```bash
docker inspect <container>
```

If I only want relevant state information, I can use formatting:

```bash
docker inspect \
  --format='{{.State.Status}} {{.State.ExitCode}} {{.State.Error}}' \
  <container>
```

Example:

```text
exited 1
```

A non-zero exit code usually indicates that the process encountered an error.

But I would still inspect application logs because the exit code alone rarely tells me the complete root cause.

---

# Question 5: A container exits with code 0. Is something wrong?

## Strong interview answer

Not necessarily.

Exit code `0` generally means the process completed successfully.

For example:

```bash
docker run --rm alpine echo "backup complete"
```

The container runs the command, finishes successfully, and exits.

That is normal.

But if the container is supposed to host a long-running API, exit code 0 can still indicate a configuration or design problem.

For example, the entrypoint might execute:

```bash
./setup.sh
```

successfully and terminate without ever starting the server.

So I would ask:

```text
Was this container expected to be long-running?
```

rather than assuming every stopped container is broken.

---

# Question 6: A container exits with code 137. What does that suggest?

## Strong interview answer

Exit code 137 means the process received `SIGKILL`.

A common container scenario is memory exhaustion, including an out-of-memory kill, although I would verify rather than assume.

I would inspect:

```bash
docker inspect <container>
```

and check whether:

```text
OOMKilled
```

is true.

For example:

```bash
docker inspect \
  --format='{{.State.OOMKilled}}' \
  <container>
```

I would also inspect resource usage and configured limits.

```bash
docker stats
```

Possible causes include:

* Memory leak
* Memory limit too low
* Unexpected workload
* Host memory pressure
* Application memory configuration

The correct fix is not automatically to give the container unlimited memory.

I would determine why memory usage reached the limit.

---

# Question 7: A container is running, but the application cannot be reached. What would you check?

## Strong interview answer

First, I would separate container state from application reachability.

```bash
docker ps
```

may show:

```text
STATUS
Up 20 minutes
```

That only tells me the main process is still running.

I would investigate:

1. Is the application actually listening?
2. Which port is it listening on?
3. Which interface is it bound to?
4. Was the container port published?
5. Is the host port correct?
6. Is a firewall blocking traffic?
7. Is the application healthy?

I would inspect the port mapping:

```bash
docker ps
```

or:

```bash
docker port <container>
```

Then inspect the application inside the container.

For example:

```bash
docker exec -it <container> sh
```

Then:

```bash
ss -lntp
```

if available in the image.

I may also test locally inside the container:

```bash
curl http://127.0.0.1:8080/health
```

This helps determine whether the problem is:

```text
Application
```

or:

```text
Docker networking / port publishing
```

# Question 8: Explain Docker port mapping.

## Strong interview answer

Suppose an application listens on port 8080 inside its container.

I run:

```bash
docker run -d \
  --name api \
  -p 8081:8080 \
  myapp:1.0
```

The mapping is:

```text
Host Port : Container Port

8081      : 8080
```

The request path becomes:

```text
Client
  ↓
Host:8081
  ↓
Docker port publishing
  ↓
Container:8080
  ↓
Application
```

A common interview mistake is reversing those numbers.

If the application listens on container port 8080, then:

```bash
-p 8081:8080
```

means clients connect to port 8081 on the host.

---

# Question 9: The Dockerfile contains `EXPOSE 8080`, but the application cannot be accessed from the host. Why?

## Strong interview answer

`EXPOSE` does not automatically publish the port to the host.

For example:

```dockerfile
EXPOSE 8080
```

documents that the image expects to use port 8080.

But I still need to publish the port when starting the container if host access is required.

For example:

```bash
docker run -d \
  -p 8080:8080 \
  myapp:1.0
```

The distinction is:

```text
EXPOSE
→ image metadata/documentation

-p
→ publish host-to-container port mapping
```

---

# Question 10: The port is published correctly, but the application is still unreachable. What could be wrong?

## Strong interview answer

I would check what interface the application binds to.

Suppose the application starts with:

```text
Listening on 127.0.0.1:8080
```

Inside a container, binding only to loopback can prevent connections arriving through the container's external network interface.

The application may need to listen on:

```text
0.0.0.0:8080
```

depending on the application.

I would inspect:

```bash
ss -lntp
```

inside the container.

The difference matters:

```text
127.0.0.1
→ loopback only

0.0.0.0
→ all IPv4 interfaces
```

A correct Docker port mapping cannot fix an application that is listening only on an inappropriate interface.

---

# Question 11: Docker says `port is already allocated`. What does that mean?

## Strong interview answer

Another process or container is already using the requested host port.

For example:

```bash
docker run -p 8080:80 nginx
```

may fail if host port 8080 is already occupied.

I would check:

```bash
docker ps
```

and on Linux:

```bash
ss -lntp
```

or:

```bash
lsof -i :8080
```

where available.

The fix may be:

* Stop the conflicting service
* Remove the old container
* Use another host port

For example:

```bash
docker run -p 8081:80 nginx
```

I would not randomly kill processes without first identifying what owns the port.

---

# Question 12: Two Docker containers need to communicate. Should they use `localhost`?

## Strong interview answer

Usually not when they are separate containers.

Inside:

```text
Container A
```

`localhost` refers to Container A itself.

It does not automatically refer to Container B.

For example:

```text
API container
DATABASE_HOST=localhost
```

would tell the API to look for the database inside the API container.

If the database is another container on the same user-defined Docker network, the application can normally use the other container's resolvable name.

For example:

```text
DATABASE_HOST=db
```

Conceptually:

```text
api container
     ↓
Docker network
     ↓
db container
```

This is one of the most common container networking interview scenarios.

---

# Question 13: How would you create a Docker network for two containers?

## Strong interview answer

Create a user-defined network:

```bash
docker network create app-network
```

Start the database:

```bash
docker run -d \
  --name db \
  --network app-network \
  postgres:16
```

Then start the application:

```bash
docker run -d \
  --name api \
  --network app-network \
  -e DATABASE_HOST=db \
  myapp:1.0
```

Now the application can use:

```text
db
```

as the database hostname through Docker's network name resolution.

I can inspect the network with:

```bash
docker network inspect app-network
```

# Question 14: Two containers cannot communicate. Walk me through your investigation.

## Strong interview answer

I would verify both containers are running:

```bash
docker ps
```

Then inspect their networks:

```bash
docker inspect api
```

```bash
docker inspect db
```

or:

```bash
docker network inspect app-network
```

I would verify they share the intended network.

Then test name resolution from the application container.

For example:

```bash
docker exec -it api sh
```

Then, depending on available utilities:

```bash
getent hosts db
```

I would test the destination port:

```bash
nc -vz db 5432
```

if `nc` is available.

Then I would verify the database is actually listening.

The troubleshooting path is:

```text
Is destination running?
        ↓
Same network?
        ↓
DNS works?
        ↓
Port reachable?
        ↓
Service listening?
        ↓
Application authentication/configuration?
```

# Question 15: DNS resolution fails inside a container. What would you investigate?

## Strong interview answer

I would first determine whether the problem affects:

```text
Container-to-container names
```

or:

```text
External domain names
```

I would inspect:

```bash
cat /etc/resolv.conf
```

inside the container.

I would inspect the Docker network:

```bash
docker network ls
```

```bash
docker network inspect <network>
```

Then test resolution with available tools:

```bash
getent hosts example.com
```

or:

```bash
nslookup example.com
```

if installed.

Possible causes include:

* Docker network configuration
* Host DNS problems
* Custom DNS settings
* Upstream DNS outage
* Container attached to wrong network

I would avoid treating every connection failure as DNS.

First confirm that name resolution itself fails.

# Question 16: The application works using an IP address but fails using a hostname. What does that suggest?

## Strong interview answer

That strongly suggests investigating name resolution.

For example:

```bash
curl http://172.18.0.5:8080
```

works, but:

```bash
curl http://api:8080
```

fails.

I would check:

```bash
getent hosts api
```

Then inspect network membership:

```bash
docker network inspect <network>
```

If the containers are not attached to the same appropriate network, Docker's internal name resolution may not work as expected.

This is a good example of using comparison to narrow the failure:

```text
IP works
Hostname fails
       ↓
Investigate DNS/name resolution
```

---

# Question 17: Why is using a container IP address directly often a bad idea?

## Strong interview answer

Container IP addresses are generally runtime details and may change when containers are recreated.

For example:

```text
Old container
172.18.0.4

Recreated container
172.18.0.7
```

Hardcoding:

```text
DATABASE_HOST=172.18.0.4
```

makes the application fragile.

On a suitable Docker network, using service or container names provides more stable service discovery.

For example:

```text
DATABASE_HOST=db
```

Production container platforms use similar service-discovery concepts rather than expecting applications to permanently hardcode individual container IP addresses.

---

# Question 18: Data disappears whenever a container is deleted and recreated. Why?

## Strong interview answer

The application is probably storing important data only inside the container's writable layer.

Containers should generally be treated as replaceable.

If persistent data needs to survive container recreation, it should be stored outside that writable layer.

For Docker, that commonly means:

* Named volume
* Bind mount
* External storage

For example:

```bash
docker volume create postgres-data
```

Then:

```bash
docker run -d \
  --name db \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16
```

Now:

```text
Container
   ↓
can be removed

Volume
   ↓
persists independently
```

---

# Question 19: What is the difference between a volume and a bind mount?

## Strong interview answer

A Docker-managed volume is managed through Docker and stored in Docker's storage area.

Example:

```bash
docker volume create app-data
```

Then:

```bash
docker run \
  -v app-data:/data \
  myapp
```

A bind mount maps a specific host filesystem path into the container.

Example:

```bash
docker run \
  -v /srv/app/config:/app/config \
  myapp
```

Conceptually:

```text
Named volume
Docker manages storage location

Bind mount
Specific host path is mapped
```

The correct choice depends on the workload.

# Question 20: How would you inspect a container's mounts?

## Strong interview answer

I can inspect the entire container:

```bash
docker inspect <container>
```

and review:

```text
Mounts
```

Or format the result:

```bash
docker inspect \
  --format='{{json .Mounts}}' \
  <container>
```

I would verify:

* Source
* Destination
* Mount type
* Read-only state

If an application says a file is missing, I would confirm whether a mount is hiding content that originally existed inside the image.

# Question 21: How can a bind mount unexpectedly hide files from an image?

## Strong interview answer

Suppose the image contains:

```text
/app/config/default.yml
```

Then I start the container with:

```bash
docker run \
  -v /empty-host-directory:/app/config \
  myapp
```

The mounted host directory is now presented at `/app/config`.

The image's original content at that path is obscured by the mount.

The application may now report:

```text
default.yml not found
```

even though the file exists in the image.

I would inspect the container's mounts before concluding that the image was built incorrectly.

# Question 22: A container receives `Permission denied` when writing to a mounted directory. How would you troubleshoot it?

## Strong interview answer

I would determine:

* Which user runs the process?
* Who owns the mounted directory?
* What permissions exist?
* Is the filesystem mounted read-only?
* Are additional host security controls involved?

Inside the container:

```bash
id
```

Then:

```bash
ls -ld /data
```

and:

```bash
ls -l /data
```

I would inspect the mount:

```bash
docker inspect <container>
```

A common mismatch is:

```text
Container process UID: 1001

Mounted directory owner UID: 1000
```

The application may not have write permission.

I would fix ownership or permission according to the intended security model.

I would not use:

```bash
chmod -R 777 /data
```

as my default production solution.

---

# Question 23: Why is running containers as root potentially dangerous?

## Strong interview answer

Running as root increases the impact of certain container vulnerabilities or configuration mistakes.

A better image may define a dedicated application user.

For example:

```dockerfile
FROM node:20-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

RUN addgroup -S appgroup \
    && adduser -S appuser -G appgroup \
    && chown -R appuser:appgroup /app

USER appuser

CMD ["node", "server.js"]
```

The application now runs as:

```text
appuser
```

rather than root.

This is one layer of container hardening.

It does not eliminate the need for other security controls.

---

# Question 24: The application worked as root but fails after changing to a non-root user. What would you investigate?

## Strong interview answer

I would check which resources the application needs.

Common problems include:

* Cannot read application files
* Cannot write logs
* Cannot write temporary files
* Cannot access mounted volume
* Cannot bind to a privileged port
* Incorrect ownership

I would inspect:

```bash
id
```

```bash
ls -la /app
```

and relevant runtime directories.

The goal is not to revert immediately to root.

The goal is to grant the application user the specific access it requires.

# Question 25: How would you enter a running container to troubleshoot it?

## Strong interview answer

For an image containing Bash:

```bash
docker exec -it <container> bash
```

For smaller images that only contain `sh`:

```bash
docker exec -it <container> sh
```

Then I may inspect:

```bash
pwd
```

```bash
env
```

```bash
ps
```

```bash
cat /etc/resolv.conf
```

```bash
ls -la
```

However, I would be careful when displaying environment variables because they may contain secrets.

Interactive troubleshooting is useful, but I should eventually fix the Dockerfile, configuration, or deployment definition rather than relying on manual changes inside a running container.

# Question 26: Why is manually fixing files inside a running container a bad permanent solution?

## Strong interview answer

Because the change is not reproducible.

Suppose I run:

```bash
docker exec -it api sh
```

and manually modify:

```text
/app/config.yml
```

The application may start working.

But when the container is recreated:

```text
manual change disappears
```

because the new container is created from the original image and configuration.

The real fix should usually go into:

* Source code
* Dockerfile
* Configuration management
* Environment configuration
* Mounted configuration

This keeps the desired state reproducible.

# Question 27: An application works on the developer's laptop but fails inside Docker. How would you approach it?

## Strong interview answer

I would compare environments.

I would not accept:

```text
It works on my machine.
```

as proof that the application is correct.

I would compare:

* Runtime version
* Operating system
* Architecture
* Environment variables
* Files
* Working directory
* Network access
* DNS
* Permissions
* Dependency versions
* Listening interface

For example:

```text
Laptop:
Node 22

Container:
Node 18
```

or:

```text
Laptop:
DATABASE_HOST=localhost

Container:
DATABASE_HOST=localhost
```

but the database is actually another container.

The purpose of containerization is partly to reduce environmental differences, but the image and runtime configuration must still be correct.

# Question 28: A Docker build fails during `COPY`. What could cause it?

## Strong interview answer

Suppose the Dockerfile contains:

```dockerfile
COPY package.json .
```

and Docker reports that the file cannot be found.

I would inspect:

* Build context
* File path
* `.dockerignore`
* Case sensitivity
* Current build directory

If I run:

```bash
docker build -t myapp .
```

the final:

```text
.
```

is the build context.

Docker can only copy appropriate files from that context.

If the file is outside the build context, `COPY` cannot access it in the normal build process.

---

# Question 29: What is Docker build context?

## Strong interview answer

The build context is the set of files Docker makes available to the build.

For example:

```bash
docker build -t myapp .
```

uses the current directory as the context.

If the repository contains:

```text
project/
  Dockerfile
  package.json
  src/
```

and I run the build from `project`, those files can be part of the context unless excluded.

A huge build context can also slow builds.

That is one reason `.dockerignore` matters.

---

# Question 30: What is `.dockerignore`, and why is it important?

## Strong interview answer

`.dockerignore` excludes unnecessary files from the build context.

Example:

```text
.git
node_modules
*.log
coverage
tmp
.env
```

Benefits can include:

* Smaller build context
* Faster builds
* Reduced accidental inclusion of sensitive files
* Better caching behavior

For example, copying a local `.env` file containing secrets into an image can create a serious security problem.

`.dockerignore` helps reduce that risk, although secret handling still requires deliberate design.

# Question 31: A Docker image is 2.5 GB. How would you investigate it?

## Strong interview answer

I would inspect the image and Dockerfile.

Useful commands include:

```bash
docker images
```

and:

```bash
docker history <image>
```

I would look for large layers caused by:

* Large base image
* Build tools retained in final image
* Package caches
* Unnecessary application files
* Large artifacts
* Poor Dockerfile structure

For example:

```dockerfile
FROM ubuntu:24.04
```

plus compilers and development tools may create a much larger image than necessary.

A multi-stage build can separate build dependencies from the runtime image.

---

# Question 32: What is a multi-stage Docker build?

## Strong interview answer

A multi-stage build uses multiple `FROM` stages so build tools do not have to remain in the final runtime image.

For example:

```dockerfile
FROM node:20 AS builder

WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine

WORKDIR /app
COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]
```

Conceptually:

```text
Builder stage
Source + build tools
        ↓
Build artifact
        ↓
Runtime stage
Only what production needs
```

This can reduce image size and attack surface.

---

# Question 33: Why does Dockerfile instruction order matter?

## Strong interview answer

Docker builds use layers and cache.

Suppose I write:

```dockerfile
COPY . .
RUN npm ci
```

Every source-code change can invalidate the `COPY` layer and therefore the dependency installation layer.

A better structure may be:

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
```

Now dependency installation can remain cached when application source changes but dependency files do not.

This can significantly improve build speed.

---

# Question 34: A Docker build suddenly stops using cache. What would you investigate?

## Strong interview answer

I would identify which layer first became uncached.

Possible causes include:

* Earlier Dockerfile instruction changed
* Build argument changed
* Dependency file changed
* Base image changed
* Build context changed
* Cache was removed
* Builder changed

I would inspect the build output and Dockerfile ordering.

The key idea is:

```text
When an earlier layer changes,
later dependent layers may need rebuilding.
```

I would optimize the Dockerfile based on which files change frequently.

---

# Question 35: What is the difference between `CMD` and `ENTRYPOINT`?

## Strong interview answer

Both help define what runs when a container starts, but they serve different purposes.

A common pattern is:

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

which results in:

```text
python app.py
```

`ENTRYPOINT` commonly defines the main executable, while `CMD` can provide default arguments or a default command.

The exact interaction depends on exec form versus shell form and how runtime arguments are supplied.

For troubleshooting, I would inspect the final configuration with:

```bash
docker inspect <container>
```

because incorrect `ENTRYPOINT` or `CMD` configuration is a common reason containers immediately exit.

---

# Question 36: Why is exec-form `CMD` often preferred for application containers?

## Strong interview answer

Exec form looks like:

```dockerfile
CMD ["node", "server.js"]
```

rather than:

```dockerfile
CMD node server.js
```

The exec form runs the executable directly without an intermediate shell being introduced by Docker for that command.

This can improve signal handling and process behavior.

That matters for operations such as:

```bash
docker stop
```

where the application should receive termination signals and shut down gracefully.

---

# Question 37: `docker stop` takes a long time and then kills the container. What could be happening?

## Strong interview answer

Docker normally sends a termination signal and gives the process time to exit before forcefully killing it after the configured timeout.

If the application does not handle termination correctly, it may remain alive until Docker kills it.

I would investigate:

* PID 1
* Signal handling
* Entrypoint scripts
* Graceful shutdown logic
* Open connections
* Application termination timeout

For production services, graceful termination matters because the application may need to:

* Stop accepting requests
* Finish active requests
* Close database connections
* Flush buffers

A container stopping is not just a Docker concern. The application must cooperate.

---

# Question 38: What is a Docker health check?

## Strong interview answer

A health check allows Docker to test whether an application inside a running container is functioning according to a defined check.

Example:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
```

The container may then have states such as:

```text
starting
healthy
unhealthy
```

A health check is different from merely checking whether the process exists.

The process may still be running while the application cannot serve requests.

---

# Question 39: A container is `Up` but `unhealthy`. What does that mean?

## Strong interview answer

The primary process is running, but the configured health check is failing.

I would inspect:

```bash
docker ps
```

Then:

```bash
docker inspect <container>
```

I would examine health-check output.

Possible causes include:

* Wrong health endpoint
* Wrong port
* Application not ready
* Dependency unavailable
* Health-check command missing
* Timeout too short
* Application genuinely unhealthy

I would reproduce the health check from inside the container.

For example:

```bash
docker exec <container> \
  curl -f http://localhost:8080/health
```

if `curl` is installed.

---

# Question 40: The health check uses `curl`, but the image does not contain `curl`. What happens?

## Strong interview answer

The health check itself fails because the required command is unavailable.

For example:

```dockerfile
HEALTHCHECK CMD curl -f http://localhost:8080/health || exit 1
```

but:

```bash
docker exec <container> which curl
```

returns nothing.

The application might be healthy while the health-check implementation is broken.

I would make sure the health check uses a tool actually available in the runtime image or implement the check another appropriate way.

This is why I troubleshoot the health-check command itself rather than assuming `unhealthy` always means the application has failed.

# Question 41: A container keeps restarting. How would you investigate?

## Strong interview answer

I would check:

```bash
docker ps
```

and:

```bash
docker ps -a
```

Then inspect logs:

```bash
docker logs --tail 100 <container>
```

Then:

```bash
docker inspect <container>
```

I would check:

* Exit code
* Restart policy
* OOM status
* Application errors
* Environment variables
* Dependency failures

For example:

```text
Application starts
      ↓
Cannot connect to database
      ↓
Process exits
      ↓
Restart policy restarts container
      ↓
Application starts again
      ↓
Failure repeats
```

The restart policy is not the root cause.

The application failure is.

# Question 42: What is a Docker restart policy?

## Strong interview answer

A restart policy controls when Docker should restart a stopped container.

For example:

```bash
docker run -d \
  --restart unless-stopped \
  --name api \
  myapp:1.0
```

Policies can be useful for long-running services.

But they should not hide persistent application failures.

If the application crashes every five seconds, automatically restarting it forever does not solve the root cause.

I would still investigate why it exits.

# Question 43: Why can aggressive automatic restarts make troubleshooting harder?

## Strong interview answer

Because the container may fail so quickly that the symptoms become a repeating loop.

For example:

```text
Start
 ↓
Crash
 ↓
Restart
 ↓
Start
 ↓
Crash
```

Logs may rotate or become noisy, and external dependencies may receive repeated connection attempts.

I would inspect:

```bash
docker logs
```

and the container's state.

If necessary in a controlled environment, I may reproduce the image without the restart loop so I can inspect the failure more clearly.

# Question 44: How would you troubleshoot missing environment variables?

## Strong interview answer

I would first confirm what configuration the application expects.

Then inspect the container configuration:

```bash
docker inspect <container>
```

I can also inspect selected non-sensitive variables inside the container:

```bash
docker exec <container> printenv APP_ENV
```

I would avoid printing all variables when secrets may be present.

A common problem is:

```text
Application expects:
DATABASE_URL

Deployment defines:
DB_URL
```

The application starts without the required value and fails.

The fix is to align the configuration contract.

---

# Question 45: Why should secrets not be baked into Docker images?

## Strong interview answer

Anything placed into an image may become accessible to people or systems that can retrieve or inspect that image or its build history.

This is dangerous:

```dockerfile
ENV DB_PASSWORD=ProductionPassword
```

So is copying a credentials file:

```dockerfile
COPY .env /app/.env
```

for production secrets.

Secrets should generally be supplied securely at runtime using an appropriate secret-management mechanism.

If a secret has already been committed or baked into a distributed image, I would treat it as potentially compromised and rotate it.

# Question 46: A developer deleted a secret from the latest Dockerfile. Is that enough?

## Strong interview answer

Not necessarily.

If the secret existed in:

* Source-control history
* Previous image versions
* Registry layers
* Build logs
* CI logs

it may still be exposed.

The response should include rotating or revoking the secret.

Deleting the line only prevents that exact new build from adding it again.

It does not make an already exposed credential safe.

# Question 47: A container cannot connect to an external API, but the host can. What would you check?

From the host:

From the container:

if `curl` is available.

Then investigate:

* DNS

* Proxy settings
* Firewall
* TLS certificates
* Routing
* Application configuration

If hostname resolution fails:

```bash
getent hosts api.example.com
```

If DNS succeeds but connection fails, I would investigate connectivity and TLS separately.

The key is narrowing the layer.

# Question 48: HTTPS requests fail inside the container with a certificate error, but work on the host. What could cause that?

## Strong interview answer

The container may have an outdated or missing CA certificate bundle.

This is common with very minimal images or improperly built runtime images.

I would inspect the exact TLS error.

Possible causes include:

* Missing CA certificates
* Outdated CA bundle
* Corporate internal CA not installed
* Wrong system time
* TLS interception
* Application trust-store configuration

I would not disable certificate verification as the production fix.

For example, using:

```text
--insecure
```

may hide the problem while removing important TLS protection.

I would correct trust configuration.

# Question 50: How do Docker memory limits work conceptually?

## Strong interview answer

A container can be started with a memory limit.

For example:

```bash
docker run -d \
  --memory=512m \
  myapp:1.0
```

This limits the container's memory usage according to the configured runtime controls.

If the application requires substantially more memory, it may be killed.

But removing the limit is not always the right answer.

I would determine:

* Expected memory requirement
* Peak usage
* Memory leaks
* Application runtime settings
* Host capacity

Resource limits should reflect realistic workload behavior.

# Question 56: What is the difference between `docker logs` and `docker exec`?

## Strong interview answer

`docker logs` retrieves logs exposed through the container's configured logging mechanism, commonly output written by the process to stdout and stderr.

Example:

```bash
docker logs api
```

`docker exec` runs a new command inside an already running container.

Example:

```bash
docker exec -it api sh
```

I use logs to understand what the application reported.

I use exec to inspect the live runtime environment.

They answer different questions.

# Question 57: `docker exec` fails because the container is stopped. What do you do?

## Strong interview answer

`docker exec` requires a running container.

If the container immediately exits, I would first use:

```bash
docker ps -a
```

```bash
docker logs <container>
```

```bash
docker inspect <container>
```

If I need an interactive environment based on the image, I may start a separate debugging container with an overridden entrypoint when appropriate.

For example:

```bash
docker run --rm -it \
  --entrypoint sh \
  myapp:1.0
```

if the image contains `sh`.

This lets me inspect the image without relying on the broken default startup command.

# Question 58: An image does not contain Bash. Is the image broken?

## Strong interview answer

No.

Minimal images may intentionally not include Bash.

For example, they may contain:

```text
/bin/sh
```

instead.

Some highly minimal or distroless images may contain no shell at all.

That can improve image minimalism and reduce attack surface, but it changes debugging techniques.

I should not assume:

```bash
docker exec -it container bash
```

will always work.

# Question 59: What is a distroless image, and how does it affect troubleshooting?

## Strong interview answer

A distroless image is designed to contain the application and necessary runtime components without a full general-purpose Linux distribution and many common utilities.

That can reduce:

* Image size
* Unnecessary packages
* Attack surface

But commands such as:

```text
bash
curl
ping
ps
```

may not exist.

Troubleshooting therefore relies more heavily on:

* Application logs
* Runtime metadata
* Observability
* External debugging tools
* Purpose-built debug containers

Production observability becomes especially important when the runtime image intentionally contains few debugging utilities.

# Question 60: Why should Docker images be tagged with specific versions rather than only `latest`?

## Strong interview answer

`latest` is mutable.

For example:

```text
myapp:latest
```

could refer to one image today and another tomorrow.

Specific tags improve traceability:

```text
myapp:2.4.1
```

or:

```text
myapp:84d72bf
```

where `84d72bf` corresponds to a Git commit.

Then I can trace:

```text
Git commit
84d72bf
   ↓
Docker image
myapp:84d72bf
   ↓
Production
```

This makes troubleshooting and rollback easier.

# Question 61: A new image was pushed, but the server still runs the old application. What would you check?

## Strong interview answer

I would identify the exact image expected and the exact image actually running.

Check:

```bash
docker ps
```

Then inspect:

```bash
docker inspect <container>
```

I would verify:

* Image tag
* Image ID or digest
* Whether the new image was pulled
* Whether the old container was recreated
* Deployment logic

A common mistake is:

```text
Push new myapp:latest
```

but leave the existing container running.

An already running container does not automatically transform into a new image just because a tag in the registry changed.

The deployment process must update the runtime appropriately.

# Question 62: What is an image digest, and why can it be useful?

## Strong interview answer

A digest identifies image content using a cryptographic content reference.

A tag can move:

```text
myapp:production
```

may point to different images over time.

A digest identifies specific image content.

This can improve:

* Reproducibility
* Traceability
* Deployment certainty

In highly controlled environments, deployments may reference immutable digests rather than relying only on mutable tags.

I would compare image IDs or digests.

I would also compare runtime configuration:

* Environment variables
* Volumes
* Networks
* Host architecture
* Resource limits

For example:

```text

myapp:production
Digest A

Server B

```

That would immediately explain why the same human-readable tag does not mean the servers run the same artifact.

# Question 65: A container cannot connect to `localhost:5432`, but PostgreSQL runs on the Docker host. Why?

## Strong interview answer

Inside the container, `localhost` refers to the container itself.

It does not normally mean the Docker host.

So:

```text
localhost:5432
```

means:

```text
Port 5432 inside this container
```

not automatically:

```text
Port 5432 on the host
```

The correct host-access mechanism depends on the platform and Docker configuration.

I would design the network explicitly rather than assume localhost crosses the container boundary.

# Question 66: Why can hardcoding host-specific addresses make containerized applications fragile?

## Strong interview answer

Because containers are intended to run in environments where runtime details may change.

Hardcoding:

```text
192.168.1.50
```

may work on one host but fail elsewhere.

Better configuration generally comes from:

* Environment-specific configuration
* DNS/service discovery
* Deployment configuration

The application should not need source-code changes every time infrastructure changes.

# Question 67: The application writes logs only to `/app/logs/app.log` inside the container. What operational problem can that create?

## Strong interview answer

If the logs exist only in the container's writable filesystem:

* They may disappear when the container is removed.
* `docker logs` may not show them.
* Centralized logging may not collect them automatically.

For many containerized applications, writing operational logs to stdout and stderr works well with container logging systems.

For example:

```text
Application
   ↓
stdout / stderr
   ↓
Container runtime
   ↓
Logging system
```

The exact logging architecture depends on the platform, but container logs should be intentionally designed.

Application-level signals include:

# Question 71: Production users receive 502 errors immediately after a new container deployment. Walk me through your investigation.

## Strong interview answer

I would first establish the request path.

For example:

```text
User
 ↓
Load Balancer
 ↓
Docker Host
 ↓
Container
 ↓
Application
```

A 502 from a reverse proxy or load balancer often means it could not successfully communicate with its upstream application.

I would identify the new release.

```text
Expected image:
checkout:84d72bf
```

Then verify what is running:

```bash
docker ps
```

Suppose I see:

```text
checkout:84d72bf
Up 5 minutes
```

That does not prove the application is reachable.

I would check logs:

```bash
docker logs --tail 100 checkout
```

Suppose the log says:

```text
Server started on 127.0.0.1:9000
```

Now inspect port mapping:

```bash
docker port checkout
```

Suppose Docker reports:

```text
8080/tcp -> 0.0.0.0:8080
```

There are now two possible mismatches.

The application listens on:

```text
9000
```

but the deployment expects:

```text
8080
```

and it binds to:

```text
127.0.0.1
```

rather than the expected container interface.

The failure chain becomes:

```text
New application release
       ↓
Application listens on 127.0.0.1:9000
       ↓
Container/deployment expects 8080
       ↓
Proxy cannot reach backend
       ↓
HTTP 502
```

The immediate response may be to restore the previous known-good image if production impact is significant.

Then I would correct:

* Application listening port
* Bind address
* Container configuration
* Health check

Finally, verify through the real request path.

```bash
curl -f https://checkout.example.com/health
```

I would not mark the incident resolved simply because:

```bash
docker ps
```

says the container is `Up`.

* Environment

# Final Production Interview Scenario

The interviewer gives you the following situation:

> "At 10:00, version 4.8.0 of a payment API is deployed as a Docker container. The deployment pipeline reports success. Monitoring initially looks normal. At 10:20, customers begin reporting intermittent payment failures. The load balancer has four backend Docker hosts. Approximately 25 percent of requests fail. All four containers appear to be running. Walk me through your investigation."

The percentage is an important clue.

Approximately:

```text
25%
```

of traffic fails.

There are:

```text
4 backends
```

A reasonable hypothesis is that one backend may be unhealthy while three are healthy.

But I would verify rather than immediately assume.

First, identify the intended release:

```text
Version:
4.8.0

Expected image:
payments:4.8.0

Expected commit:
84d72bf
```

Then inspect each backend.

Suppose:

```text
Host 1
payments:4.8.0
healthy

Host 2
payments:4.8.0
healthy

Host 3
payments:4.8.0
healthy

Host 4
payments:4.8.0
running but unhealthy
```

Now investigate Host 4.

```bash
docker ps
```

Then:

```bash
docker inspect payments
```

Suppose the health status shows failures.

Check logs:

```bash
docker logs --tail 200 payments
```

The logs show:

```text
ERROR: Unable to write transaction cache
Permission denied: /app/cache
```

Now compare mounts and user identity between healthy and unhealthy containers.

Healthy host:

```text
/app/cache
Owner UID: 1001
Container UID: 1001
```

Failing host:

```text
/app/cache
Owner UID: 1000
Container UID: 1001
```

The deployment recently changed the application to run as a non-root user:

```dockerfile
USER 1001
```

Three hosts have correctly prepared storage.

One host has an old bind-mounted directory owned by UID 1000.

The application process starts successfully, so the container remains:

```text
Up
```

But payment requests requiring writes to the cache fail on that host.

The request pattern becomes:

```text
Load Balancer
   │
   ├── Host 1 → success
   ├── Host 2 → success
   ├── Host 3 → success
   └── Host 4 → permission failure
```

This explains the approximate 25 percent failure rate.

The immediate recovery could involve removing the unhealthy backend from traffic while correcting its filesystem ownership according to the deployment design.

Then verify the application locally on that backend.

For example:

```bash
curl -f http://127.0.0.1:<published-port>/health
```

Then test a real transaction path if a safe production validation mechanism exists.

After correction:

```text
Host 1 → healthy
Host 2 → healthy
Host 3 → healthy
Host 4 → healthy
```

Then verify through the load balancer.

The incident should not end there.

I would ask:

```text
Why could deployment succeed when one backend was not operationally ready?
```

The deployment process should validate more than:

```text
docker run succeeded
```

It should validate:

```text
Container started
       ↓
Health check passed
       ↓
Required storage writable
       ↓
Dependencies reachable
       ↓
Application endpoint healthy
       ↓
Backend added to traffic
```

The configuration process should also ensure host filesystem ownership is consistent before deploying the non-root container.

## Strong interview response

A strong candidate could summarize the investigation like this:

> "Because roughly one quarter of requests fail across four backends, I would first determine whether one backend differs from the others. I would verify the image digest and runtime configuration on all four hosts, inspect health status and application logs, and compare the failing backend with healthy ones. I would restore service by removing an unhealthy backend from traffic or rolling back if necessary, then fix the underlying configuration. Finally, I would improve deployment validation so a container is not considered ready simply because its process started."

That answer demonstrates:

```text
Docker knowledge
+
Linux permissions
+
Load-balancer reasoning
+
Production troubleshooting
+
Incident mitigation
+
Deployment improvement
```

# What Junior DevOps Candidates Should Learn From Part 8

Docker troubleshooting becomes much easier when you stop treating the container as one black box.

Think in layers.

```text
Docker Host
    ↓
Docker Engine
    ↓
Image
    ↓
Container Configuration
    ↓
Main Process
    ↓
Filesystem
    ↓
Network
    ↓
Application
    ↓
Dependencies
    ↓
User Request
```

A failure at one layer produces symptoms at another.

For example:

```text
Wrong environment variable
       ↓
Application cannot reach database
       ↓
Process exits
       ↓
Container restarts
```

The visible symptom is:

```text
Container keeps restarting
```

but the root cause is:

```text
Configuration
```

Another example:

```text
Application binds to 127.0.0.1
       ↓
Docker publishes correct port
       ↓
External traffic cannot reach application
```

The visible symptom is:

```text
Container is running but unreachable
```

The root cause is:

```text
Application bind address
```

Another:

```text
Container runs as UID 1001
       ↓
Volume owned by UID 1000
       ↓
Application cannot write
```

The visible symptom is:

```text
Permission denied
```

The root cause is:

```text
Filesystem ownership mismatch
```

Another:

```text
Application memory grows
       ↓
Memory limit reached
       ↓
Process killed
       ↓
Container exits 137
```

The visible symptom is:

```text
Container suddenly dies
```

The root cause may be:

```text
Memory behavior
```

The most useful troubleshooting question remains:

```text
What evidence tells me which layer is failing?
```

A junior engineer should be able to move from:

```text
"The container doesn't work."
```

to something precise such as:

```text
"The container starts successfully, but its health check fails because
the application listens on port 9000 while the health check targets
port 8080."
```

Or:

```text
"The application can resolve the database hostname and establish a TCP
connection to port 5432, so basic container networking is working. The
failure is now at the database authentication layer."
```

Or:

```text
"The process is being OOM-killed after reaching its configured memory
limit. I would investigate application memory growth before deciding
whether the limit itself should change."
```

That precision is what makes an interview answer sound like it comes from someone who can troubleshoot a real system.
