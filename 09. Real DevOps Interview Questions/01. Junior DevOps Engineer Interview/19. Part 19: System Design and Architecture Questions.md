# Part 19: System Design and Architecture Questions

System design questions are not reserved for senior engineers.

A junior DevOps candidate may not be expected to design a global platform serving hundreds of millions of users, but interviewers still want to know whether you understand how production systems fit together.

They want to see whether you can reason about:

* Users and traffic flow
* DNS
* Load balancing
* Compute
* Application tiers
* Databases
* Caching
* Networking
* High availability
* Scalability
* Security
* Monitoring
* Deployment
* Failure handling
* Backup and recovery
* Cost
* Trade-offs

The important part is not drawing the most complicated architecture.

A strong candidate can explain why each component exists.

A useful system-design thinking pattern is:

```text
Requirements
     |
     v
Traffic & Scale
     |
     v
Request Flow
     |
     v
Compute
     |
     v
Data
     |
     v
Networking
     |
     v
Availability
     |
     v
Security
     |
     v
Observability
     |
     v
Deployment
     |
     v
Failure & Recovery
     |
     v
Trade-offs
```

Before choosing technologies, understand the problem.

# Question 1: How would you approach a system design question in a DevOps interview?

## Strong interview answer

I would not immediately start naming AWS services, Kubernetes components, or databases.

I would first clarify the requirements.

I would ask questions such as:

```text
What are we building?

Who uses it?

How much traffic do we expect?

Is the application read-heavy or write-heavy?

What availability is required?

Is the application stateful or stateless?

What data needs to be stored?

Are there compliance requirements?

What happens if one component fails?

Do we need multiple regions?

What are the expected growth patterns?
```

Then I would design the simplest architecture that satisfies those requirements.

My reasoning would generally cover:

```text
Client
   |
   v
DNS
   |
   v
Edge / CDN / WAF
   |
   v
Load Balancer
   |
   v
Application
   |
   +------> Cache
   |
   +------> Database
   |
   +------> Queue
   |
   +------> Object Storage
```

After the basic request path is clear, I would discuss:

```text
High availability
Scaling
Security
Observability
Deployment
Backup
Disaster recovery
Cost
Trade-offs
```

The architecture should come from the requirements rather than from a list of technologies I know.

# Question 2: What is the difference between system design and system architecture?

## Strong interview answer

System design is the process of deciding how a system should satisfy its requirements.

System architecture is the resulting structure of that system.

For example, the design problem might be:

```text
Build an online application
that must remain available
during an instance failure.
```

The architecture might include:

```text
Route 53
   |
   v
Application Load Balancer
   |
   +----------------+
   |                |
   v                v
EC2-A            EC2-B
AZ-A             AZ-B
   \                /
    \              /
     v            v
      Multi-AZ RDS
```

The design explains the decisions.

The architecture shows how the components are organized.

# Question 3: Design a simple highly available web application.

## Strong interview answer

For a basic AWS architecture, I might start with:

```text
                    Internet
                       |
                       v
                  Route 53
                       |
                       v
                      ALB
                  /         \
                 /           \
                v             v
            EC2/App       EC2/App
              AZ-A          AZ-B
                 \           /
                  \         /
                   v       v
                  RDS Multi-AZ
```

The load balancer distributes traffic across application instances in at least two Availability Zones.

The application instances should ideally be stateless so that requests can be handled by any healthy instance.

The database can use Multi-AZ deployment for database availability.

The architecture should also include:

```text
Auto Scaling
Monitoring
Centralized logs
Backups
Security groups
Private subnets where appropriate
Secrets management
```

The main principle is removing obvious single points of failure.

# Question 4: Why would you deploy application servers across multiple Availability Zones?

## Strong interview answer

Because deploying everything in one Availability Zone creates a larger failure domain.

For example:

```text
Single AZ

ALB
 |
 +---- App 1
 |
 +---- App 2
 |
 +---- App 3

All in AZ-A
```

If AZ-A experiences a significant failure, all three application instances may become unavailable.

Instead:

```text
                ALB
           /            \
          v              v
       AZ-A             AZ-B
      App 1            App 2
      App 3            App 4
```

Now the architecture can potentially continue serving traffic when one Availability Zone becomes unavailable.

However, simply placing servers in multiple AZs is not enough.

Shared dependencies such as databases, NAT gateways, storage, and application configuration must also be considered.

# Question 5: What is a single point of failure?

## Strong interview answer

A single point of failure is a component whose failure can make the entire service unavailable.

For example:

```text
Internet
   |
   v
One EC2 instance
   |
   v
Database
```

If that single EC2 instance fails:

```text
Application unavailable
```

A more resilient design might use:

```text
             Load Balancer
              /        \
             v          v
          App A       App B
```

But I would also examine the database and other shared dependencies.

High availability means looking for single points of failure throughout the request path.

# Question 6: What is the difference between scalability and high availability?

## Strong interview answer

Scalability is the system's ability to handle increasing workload.

High availability is the system's ability to remain accessible despite failures.

For example:

```text
One huge server
```

may handle large traffic.

That gives capacity, but it can still be a single point of failure.

Similarly:

```text
Two tiny servers
```

may provide redundancy but not enough capacity.

A good production architecture often needs both.

```text
Scalability
=
Handle more load

High Availability
=
Survive failures
```

# Question 7: What is vertical scaling?

## Strong interview answer

Vertical scaling means increasing the resources of an existing machine.

For example:

```text
Before

2 CPU
4 GB RAM

        |
        v

After

8 CPU
32 GB RAM
```

It is simple, but there are limits.

Eventually the machine cannot be made larger, and a single large machine can still represent a failure risk.

# Question 8: What is horizontal scaling?

## Strong interview answer

Horizontal scaling means adding more instances.

```text
Before

App 1
App 2

       |
       v

After

App 1
App 2
App 3
App 4
App 5
```

A load balancer can distribute traffic across them.

Horizontal scaling works particularly well when application instances are stateless.

# Question 9: Why are stateless applications easier to scale?

## Strong interview answer

Because any application instance can process a request.

Suppose session data exists only on App-1:

```text
User
 |
 v
App-1

Session stored locally
```

If the next request reaches App-2:

```text
User
 |
 v
App-2

Session missing
```

That creates a problem.

Instead, session state could be stored externally:

```text
           Load Balancer
             /       \
            v         v
         App-1      App-2
            \         /
             \       /
              v     v
                Redis
```

Now either application instance can access the session.

This makes horizontal scaling and failover easier.

# Question 10: Where should application session data be stored?

## Strong interview answer

For a scalable application, I generally avoid relying exclusively on local instance memory or local disk for important session state.

Depending on the application, options might include:

```text

External session store
Signed client-side token
```

The correct choice depends on:

```text
Security
Consistency
Performance
Expiration
Application design
```

The important architectural principle is avoiding unnecessary coupling between a user and one application server.

# Question 11: What is load balancing?

## Strong interview answer

Load balancing distributes traffic across multiple healthy backend systems.

```text
               Users
                 |
                 v
          Load Balancer
          /     |      \
         v      v       v
      App-1   App-2   App-3
```

A load balancer can provide:

* Traffic distribution
* Health checking
* TLS termination
* Routing
* Failover from unhealthy targets
* Host-based routing
* Path-based routing

Load balancing is not simply about distributing traffic evenly.

It is also an important availability component.

---

# Question 12: How does a load balancer know whether a backend is healthy?

## Strong interview answer

Usually through health checks.

For example:

```text
GET /health
```

If App-1 responds successfully:

```text
App-1
Healthy
```

If App-2 repeatedly fails:

```text
App-2
Unhealthy
```

The load balancer can stop routing normal traffic to App-2.

But the health check needs to represent useful application health.

A weak health endpoint might return 200 even when the application cannot perform critical work.

# Question 13: Would you put a database behind a normal web application load balancer?

## Strong interview answer

Not as a default architecture.

Web load balancers such as an ALB are designed primarily for HTTP and HTTPS application traffic.

Database availability is normally handled using database-specific mechanisms such as:

```text
Primary/standby
Replication
Managed database endpoints
Database proxies
Clustering
```

The correct architecture depends on the database technology.

# Question 14: Why do architectures often separate public and private subnets?

## Strong interview answer

To control direct network exposure.

For example:

```text
Internet
   |
   v
Internet Gateway
   |
   v
Public Subnet
   |
   v
Load Balancer
   |
   v
Private Subnet
   |
   v
Application
   |
   v
Private Database
```

The load balancer needs to accept internet traffic.

The database normally does not.

The application may also not require direct inbound internet access.

Subnet placement should reflect which components actually need public connectivity.

# Question 15: What makes a subnet public?

## Strong interview answer

In AWS, I would not define a subnet as public merely because a resource inside it has a public IP.

A typical public subnet has a route that allows appropriate internet-bound traffic through an Internet Gateway.

For example:

```text
0.0.0.0/0
      |
      v
Internet Gateway
```

Whether a particular resource is reachable still depends on other controls, including its addressing and security rules.

# Question 16: How can instances in private subnets access the internet?

## Strong interview answer

A common IPv4 design uses a NAT Gateway.

```text
Private EC2
    |
    v
Private Route Table
    |
    v
NAT Gateway
    |
    v
Internet Gateway
    |
    v
Internet
```

This allows outbound connections without making the private instance directly internet-accessible for inbound connections.

For AWS services, I would also consider VPC endpoints when appropriate rather than routing all service traffic through NAT.

# Question 17: Why might you use VPC endpoints?

## Strong interview answer

VPC endpoints can allow private connectivity to supported AWS services without requiring the traffic to traverse the normal public internet path.

For example:

```text

     |
     v
VPC Endpoint
     |
     v
S3
```

This can help with:

* Private connectivity
* Security architecture
* Network control
* NAT cost reduction in some designs

Whether it makes sense depends on the service and traffic pattern.

# Question 18: What is the purpose of a CDN?

## Strong interview answer

A Content Delivery Network caches appropriate content closer to users.

Without a CDN:

```text
User in Asia
     |
     v
Origin in US
```

With a CDN:

```text
User
 |
 v
Nearby Edge Location
 |
 v
Origin only when necessary
```

Benefits may include:

* Lower latency
* Reduced origin traffic
* Better static-content delivery
* Improved global user experience
* Additional edge capabilities

On AWS, CloudFront is a common example.

# Question 20: What is caching, and why is it useful?

## Strong interview answer

Caching stores frequently needed data closer to where it is consumed so the system does not repeatedly perform expensive work.

For example:

```text
Application
    |
    v
Redis Cache
    |
    | cache miss
    v
Database
```

Without caching:

```text
10,000 repeated reads
        |
        v
Database
```

With caching:

```text
10,000 reads
    |
    v
Cache
    |
Small percentage
    |
    v
Database
```

Caching can improve latency and reduce backend load.

But it introduces challenges such as invalidation, stale data, memory management, and consistency.

# Question 21: What is a cache miss?

## Strong interview answer

A cache miss occurs when the requested data is not available in the cache.

Typical flow:

```text
Request
   |
   v
Cache
   |
 MISS
   |
   v
Database
   |
   v
Return data
   |
   v
Populate cache
```

Later requests may then be served from the cache.

---

# Question 22: What is cache invalidation?

## Strong interview answer

Cache invalidation removes or expires cached data when it should no longer be used.

For example:

```text
Product price:
$100
```

The database changes to:

```text
$80
```

If the cache still returns:

```text
$100
```

users receive stale data.

Caching strategy therefore needs to consider:

```text
TTL
Explicit invalidation
Write patterns
Consistency requirements
```

# Question 24: Why not store user uploads on an EC2 instance's local disk?

## Strong interview answer

Because local instance storage creates coupling to that specific server.

Suppose:

```text
User uploads image
        |
        v
      App-2
        |
        v
Local disk
```

Later:

```text
App-2 terminated
```

The application may lose access to that file.

It also becomes difficult for App-1 and App-3 to serve the same file.

Shared durable storage such as object storage is usually a better fit for that type of data.

# Question 28: What is database replication?

## Strong interview answer

Replication copies data between database systems.

A simplified architecture might be:

```text
             Primary
             Database
             /      \
            v        v
       Replica-1  Replica-2
```

Depending on the database and architecture, replicas may support:

* Availability
* Read scaling
* Disaster recovery

But replication behavior, lag, consistency, and failover need to be understood.

---

# Question 29: What is replication lag?

## Strong interview answer

Replication lag is the delay between a change on the primary database and that change becoming available on a replica.

For example:

```text
12:00:00
Primary updated

12:00:03
Replica updated
```

That is approximately three seconds of lag.

If the application writes to the primary and immediately reads from a lagging replica, it may temporarily receive older data.

---

# Question 30: What is read scaling?

## Strong interview answer

If an application has heavy read traffic, some architectures distribute reads across replicas.

```text
Writes
  |
  v
Primary
  |
  +--------+
  |        |
  v        v
Replica  Replica
  ^        ^
  |        |
 Reads    Reads
```

This can reduce read pressure on the primary.

But the application must account for replication lag and consistency requirements.

# Question 31: What is database sharding?

## Strong interview answer

Sharding divides data across multiple database partitions or systems.

For example:

```text
Users A-H
   |
   v
Shard 1

Users I-P
   |
   v
Shard 2

Users Q-Z
   |
   v
Shard 3
```

It can help with very large-scale workloads, but it adds complexity.

Challenges include:

```text
Shard selection
Rebalancing
Cross-shard queries
Transactions
Operational complexity
```

I would not introduce sharding unless the requirements justify it.

# Question 32: What is a message queue?

## Strong interview answer

A message queue allows producers and consumers to communicate asynchronously.

```text
Producer
   |
   v
 Queue
   |
   v
Consumer
```

For example:

```text
User places order
       |
       v
Application
       |
       v
Order Queue
       |
       v
Email Worker
```

The user does not necessarily need to wait for the email to be sent before receiving an order confirmation.

Queues can help decouple systems and absorb traffic spikes.

# Question 33: Why would you use asynchronous processing?

## Strong interview answer

Some work does not need to happen inside the user's request.

For example:

```text
Upload video
     |
     v
Return success
     |
     v
Queue
     |
     v
Background processing
```

Benefits can include:

```text

Retry handling
Traffic smoothing
Independent scaling
```

But asynchronous systems also introduce eventual consistency, queue monitoring, duplicate processing, and failure-handling concerns.

# Question 34: What happens if a queue consumer fails?

## Strong interview answer

The exact behavior depends on the queue technology.

Generally, I would design for messages to remain available or become visible again when processing fails.

I would also consider:

```text
Retries
Visibility timeout
Dead-letter queue
Idempotency
Monitoring
```

Repeatedly failing messages should not be allowed to create an endless failure loop.

---

# Question 35: What is a dead-letter queue?

## Strong interview answer

A dead-letter queue stores messages that repeatedly fail processing.

```text
Main Queue
    |
    v
Consumer
    |
 failure
    |
 retry
    |
 failure
    |
    v
Dead-Letter Queue
```

This prevents problematic messages from continuously blocking or consuming resources in the main processing flow.

The DLQ must also be monitored.

---

# Question 36: What is idempotency?

## Strong interview answer

An idempotent operation can be repeated without creating unintended duplicate effects.

For example, a payment-processing system should not charge a customer twice simply because the client retried the same request.

Conceptually:

```text
Request ID: ABC123

First request
→ payment created

Retry ABC123
→ recognize existing operation
→ do not charge again
```

Idempotency becomes particularly important in distributed systems because retries are common.

# Question 40: Rolling deployment versus blue-green deployment?

## Strong interview answer

A rolling deployment gradually replaces old instances with new ones.

```text
V1 V1 V1 V1

       ↓

V2 V1 V1 V1

       ↓

V2 V2 V1 V1

       ↓

V2 V2 V2 V2
```

Blue-green maintains two environments:

```text
Blue
Version 1
Current traffic

Green
Version 2
New environment
```

Traffic is then switched to Green after verification.

Both approaches have trade-offs involving:

```text
Cost
Rollback
Capacity
Database compatibility
Deployment speed
Operational complexity
```

Scaling policies might use signals such as:

```text

Queue depth
Latency
Custom workload metrics
```

The scaling metric should reflect the actual bottleneck.

# Question 42: Why might CPU be a bad Auto Scaling metric?

## Strong interview answer

Because not every workload becomes CPU-bound.

For example:

```text
CPU
25%

Request queue
10,000
```

The application might be waiting on I/O or external dependencies.

Another application might have:

```text
CPU
40%

Queue depth
rapidly increasing
```

For worker systems, queue depth may be more useful.

Scaling should be based on workload behavior.

# Question 43: Can Auto Scaling make an outage worse?

## Strong interview answer

Yes.

Suppose the database is overloaded.

The application becomes slow.

Auto Scaling adds 50 application instances.

Each opens new database connections.

```text
Database overloaded
       |
       v
App latency
       |
       v
Scale applications
       |
       v
More DB connections
       |
       v
Database more overloaded
```

Scaling one tier without considering downstream capacity can amplify an incident.

# Question 49: How would you secure communication between users and the application?

## Strong interview answer

For a public web application, I would normally use HTTPS.

# Question 72: What is exponential backoff with jitter?

## Strong interview answer

Exponential backoff increases the delay between retry attempts.

For example:

```text

2 sec
4 sec
8 sec
```

Jitter adds randomness.

Instead of 10,000 clients all retrying exactly after four seconds, their retries become distributed.

That reduces synchronized retry storms.

# Question 74: What is backup versus replication?

## Strong interview answer

Replication maintains copies of changing data, often continuously or near-continuously.

Backup creates recoverable historical copies.

They solve different problems.

If corrupted data is replicated:

```text
Primary corrupted
       |
       v
Replica receives corruption
```

Replication alone may not protect against that scenario.

Backups may allow restoration from an earlier point.

A resilient data strategy often considers both.

A backup that cannot be restored does not meet its purpose.

# Question 81: What is eventual consistency?

## Strong interview answer

Eventual consistency means replicas or distributed components may temporarily contain different versions of data, but they are expected to converge.

For example:

```text

Status = PAID

Replica:
Status = PENDING

3 seconds later

Replica:
Status = PAID
```

Some applications can tolerate this.

Others, especially certain financial or transactional operations, may require stronger consistency guarantees.

## Strong interview answer

Strong consistency generally means a read reflects the required latest committed state according to the system's consistency model.

For example:

```text

Balance = $500
```

Stronger consistency can simplify some application logic but may involve trade-offs in distributed architectures.

# Question 83: What is the CAP theorem at a junior interview level?

When network partitions happen, a distributed system cannot always provide both perfect availability and perfect consistency simultaneously.

For a junior interview, I would explain the concept rather than pretending every architecture can be classified with one simple label.

```text
ALB
 |
 v
3 EC2 instances
 |
 v
RDS
```

At first glance, there are three application servers.

But investigation shows:

```text
EC2-A
EC2-B
EC2-C

All in AZ-A
```

and the database is also effectively dependent on the same failure domain.

The architecture has multiple servers but weak failure isolation.

A better design distributes appropriate resources across Availability Zones.

The lesson:

```text
Multiple resources
!=
High availability
```

# Real-World Architecture Scenario 2: Auto Scaling Overloads the Database

Traffic doubles.

Application latency increases.

Auto Scaling responds:

```text
10 application instances
        |
        v
40 application instances
```

Each instance creates:

```text
50 database connections
```

Before:

```text
500 connections
```

After:

```text
2,000 connections
```

Database capacity:

```text
1,000 connections
```

The database becomes unavailable.

The lesson:

```text
Scaling one layer
can overload another.
```

System design requires thinking about the entire dependency chain.

Architecture:


Improved architecture:


Use the appropriate component for the workload.

# Real-World Architecture Scenario 5: Queue Protects the Application During Traffic Spike

Normally:

```text
1,000 jobs/minute
```

Suddenly:

```text
50,000 jobs/minute
```

Without a queue:

```text
Requests
   |
   v
Workers
   |
   X
Overloaded
```

With a queue:

```text
Requests
   |
   v
Queue
   |
   v
Workers
```

The queue absorbs temporary workload growth.

Workers process the backlog at a controlled rate.

The lesson:

Decoupling can improve resilience.

# Real-World Architecture Scenario 6: Multi-AZ Application With Single-AZ Dependency

Application:

```text

```

Looks highly available.

But both depend on:

```text
Single NAT path
```

High availability must include dependencies.

# Real-World Architecture Scenario 8: Database Read Traffic Becomes the Bottleneck

Application traffic grows.

Database writes remain moderate.

Reads increase dramatically.

Possible architecture:

```text
             Application
             /         \
            v           v
        Writes         Reads
            |           |
            v           v
         Primary      Replicas
```

But before adding replicas, I would confirm the workload and evaluate caching and query performance.

The lesson:

Scale based on evidence.

# Real-World Architecture Scenario 10: Microservices Create More Problems Than They Solve

A small team has eight engineers.

They build:

```text

```


# System Design Mistakes Junior Candidates Should Avoid

Do not start every answer with:

```text
"We need Kubernetes."
```

Start with requirements.

Do not assume:

```text
More services
=
Better architecture
```

Do not assume:

```text
More replicas
=
High availability
```

if every replica shares the same failure domain.

Do not assume:

```text
Auto Scaling
=
Unlimited scalability
```

Downstream systems still have limits.

Do not assume:

```text
Multi-region
=
Automatically better
```

It introduces major complexity.

Do not assume:

```text
NoSQL
=
Always more scalable
```

Database selection depends on workload requirements.

Do not assume:

```text
Microservices
=
Modern
=
Correct
```

A monolith may be the better design.

Do not assume:

```text
CPU monitoring
=
Application monitoring
```

Do not assume:

```text
Backup created
=
Recovery guaranteed
```

Do not assume:

```text
Private subnet
=
Automatically secure
```

Do not assume:

```text
HTTPS
=
Complete application security
```

Do not assume:

```text
Terraform
=
Correct architecture
```

Terraform automates the architecture you define, including bad architecture.

# How to Answer a System Design Question During the Interview

If the interviewer says:

> "Design a highly available web application on AWS."

A weak answer sounds like:

> "I will use Route 53, CloudFront, ALB, EC2, Auto Scaling, RDS, S3, Redis, Terraform, Kubernetes, Jenkins, Prometheus, Grafana, and CloudWatch."

That is a technology list.

A stronger answer sounds like:

> "Before choosing services, I would clarify the expected traffic, availability target, data requirements, and whether the application is stateful. Assuming this is a typical internet-facing web application that needs to survive an instance or Availability Zone failure, I would place an internet-facing load balancer across multiple Availability Zones and run stateless application instances across at least two AZs. I would keep the database private and use an appropriate high-availability database configuration. Static assets could be stored in object storage and delivered through a CDN. I would then add Auto Scaling based on workload characteristics, centralized monitoring and logging, secrets management, least-privilege IAM, infrastructure as code, automated deployments with health verification, and tested backup and recovery procedures."

Notice the difference.

The candidate is explaining architecture rather than reciting services.

# If the Interviewer Challenges Your Design

A good interviewer may deliberately challenge you.

They may say:

> "Now traffic increases ten times."

Do not redesign everything immediately.

Ask:

```text
Which layer reaches capacity?
```

They may say:

> "Now one Availability Zone fails."

Walk through the request path.

```text
DNS
 |
 v
Load Balancer
 |
 v
Healthy AZ
 |
 v
Application
 |
 v
Database
```

Ask whether every dependency survives.

They may say:

> "Now the database fails."

Discuss:

```text
Failover
Application timeouts
Retries
Connection recovery
Customer impact
```

They may say:

> "Now the external payment provider is down."

Discuss:

```text
Timeout
Circuit breaker
Retry policy
Queueing
Graceful degradation
Customer messaging
```

They may say:

> "Now reduce the cost by 40%."

Discuss measurements and trade-offs.

They may say:

> "Now deploy without downtime."

Discuss:

```text
Multiple replicas
Readiness
Rolling/canary/blue-green
Database compatibility
Connection draining
Rollback
```

System design interviews often evolve this way.

The interviewer is testing whether your architecture survives changing requirements.

# Final Interview Challenge

## Question: Design a scalable, highly available application that can survive failures, handle traffic spikes, deploy safely, and recover from disasters.

## Strong interview answer

I would begin with the requirements rather than immediately selecting technology.

Assuming this is a public web application with significant traffic, I would design the request path first.

```text
Users
  |
  v
DNS
  |
  v
CDN / WAF
  |
  v
Load Balancer
  |
  v
Stateless Application Tier
  |
  +----------+----------+----------+
  |          |          |          |
  v          v          v          v
Cache     Database    Queue      Object
                                Storage
              |
              v
           Backups
```

I would distribute the application across multiple failure domains.

```text
AZ-A
Application

AZ-B
Application
```

The load balancer would route traffic only to healthy instances.

The application tier would be horizontally scalable.

Application state would be stored outside individual instances where appropriate.

Frequently accessed data could use caching when consistency requirements allow it.

Long-running or asynchronous work could be moved through queues to independently scalable workers.

The database architecture would be selected according to transaction, consistency, query, availability, and scale requirements.

Static assets and user files would use appropriate durable object storage rather than application-local disks.

For security:

```text
TLS
Private networking
Least privilege
Workload identity
Secrets management
Encryption
WAF where appropriate
Audit logging
```

For deployment:

```text
Git
 |
 v
CI
 |
 v
Tests
 |
 v
Artifact
 |
 v
Controlled rollout
 |
 v
Health verification
 |
 v
Production
```

For observability:

```text
Metrics
Logs
Traces
Synthetic checks
Business SLIs
Alerts
```

For resilience:

```text
Timeouts
Bounded retries
Backoff
Jitter
Circuit breakers
Graceful degradation
Health checks
```

For disaster recovery:

```text
Backups
Restore testing
Infrastructure as Code
Defined RTO/RPO
Failover procedures
DR exercises
```

Finally, I would test the design against failure scenarios.

```text
What if one instance dies?

What if one node dies?

What if one AZ dies?

What if the database becomes slow?

What if the cache disappears?

What if the queue grows?

What if an external API fails?

What if traffic increases ten times?

What if a deployment is bad?

What if credentials expire?

What if the primary region becomes unavailable?
```

If I cannot explain what happens when those components fail, then the architecture is not finished.

# What Junior DevOps Candidates Should Take From Part 19

System design is not about drawing the biggest diagram.

It is about answering five fundamental questions:

```text
How does the system work?

How does the system scale?

How does the system fail?

How does the system recover?

How does the team operate it?
```

A weak candidate says:

> "I would use Kubernetes, Terraform, Jenkins, AWS, Prometheus, and Grafana."

A stronger candidate says:

> "I would first understand the requirements and failure tolerance. Then I would design the request path, separate stateless compute from persistent state, distribute critical workloads across appropriate failure domains, remove unnecessary single points of failure, design scaling around measured bottlenecks, secure each layer using least privilege, add observability around customer-facing behavior, automate reproducible deployments, and define how the system recovers when dependencies fail."

That is what the interviewer wants to hear.

Tools matter.

Architecture is knowing where those tools belong, why they belong there, what happens when they fail, and what trade-offs you accepted by choosing them.
