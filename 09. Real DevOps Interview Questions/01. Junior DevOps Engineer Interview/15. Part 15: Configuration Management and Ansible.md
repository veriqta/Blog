# Part 15: Configuration Management and Ansible

Knowing how to write an Ansible playbook is useful.

But that is rarely enough in a practical DevOps interview.

An interviewer may give you a situation like this:

> "You manage 150 Linux servers with Ansible. A playbook succeeds on 145 servers and fails on five. What do you do?"

Or:

> "Someone manually changed SSH configuration on several production servers. How would you detect and correct the drift?"

Or:

> "Your playbook runs successfully every time, but it restarts Nginx on all servers even when nothing changed. What is wrong with the design?"

Or:

> "An Ansible deployment changed every production server at the same time and caused an outage. How would you redesign the deployment?"

These questions test more than Ansible syntax.

They test whether you understand configuration management, idempotency, inventory design, secrets, privilege escalation, failure handling, deployment safety, configuration drift, and production operations.

A useful mental model is:

```text
Control Node
     |
     v
Inventory
     |
     v
Playbook
     |
     v
SSH / WinRM
     |
     v
Managed Nodes
     |
     v
Desired Configuration
```

The objective is not simply:

```text
Run commands on servers
```

It is:

```text
Define desired configuration
        |
        v
Apply it consistently
        |
        v
Detect differences
        |
        v
Change only what is necessary
        |
        v
Keep systems in a known state
```

---

# Question 1: What is configuration management?

## Strong interview answer

Configuration management is the process of defining, applying, and maintaining the desired configuration of systems in a consistent and repeatable way.

For example, suppose I manage 100 Linux servers.

Each application server should have:

```text
Nginx installed
Application user created
Required directories present
Correct configuration file
Correct file permissions
Application service running
Monitoring agent installed
Firewall configured
```

Without configuration management, engineers might configure these servers manually.

That creates inconsistency.

```text
Server 1
Nginx 1.24
Correct config

Server 2
Nginx 1.22
Old config

Server 3
Missing monitoring agent

Server 4
Wrong permissions
```

Configuration management allows me to define what those systems should look like and automate bringing them into that state.

---

# Question 2: What is Ansible?

## Strong interview answer

Ansible is an automation and configuration management tool commonly used to configure systems, deploy applications, orchestrate operational tasks, and manage infrastructure.

One important characteristic is that Ansible is generally agentless for standard Linux management.

Instead of installing an Ansible agent on every managed Linux server, the control node commonly connects through SSH.

Conceptually:

```text
Ansible Control Node
        |
        | SSH
        |
   +----+----+
   |    |    |
   v    v    v
 Web1  Web2  Web3
```

For Windows systems, Ansible can use technologies such as WinRM.

---

# Question 3: What is the difference between Terraform and Ansible?

## Strong interview answer

They overlap in automation capabilities, but I normally think about them differently.

Terraform primarily focuses on infrastructure provisioning and lifecycle management.

For example:

```text
Terraform

Create VPC
Create subnets
Create EC2
Create load balancer
Create RDS
Create IAM resources
```

Ansible commonly focuses on configuring systems and applications after infrastructure exists.

```text
Ansible

Install Nginx
Create users
Configure packages
Deploy configuration files
Start services
Install monitoring agents
Configure application servers
```

A common workflow is:

```text
Terraform
   |
   v
Provision EC2
   |
   v
Servers become available
   |
   v
Ansible
   |
   v
Configure operating system
   |
   v
Deploy application configuration
```

However, the boundary is not absolute.

Both tools can perform tasks outside those simplified categories.

The important thing is to give each tool clear ownership.

---

# Question 4: What does agentless mean in Ansible?

## Strong interview answer

Agentless means Ansible generally does not require a permanently installed Ansible-specific agent on managed Linux hosts.

The control node connects to hosts, commonly through SSH.

For example:

```text
Control Node
     |
     | SSH
     v
Managed Server
```

The managed node normally needs the runtime and system capabilities required by the modules being used.

This reduces the need to maintain a separate Ansible daemon on every Linux host.

---

# Question 5: What is an Ansible inventory?

## Strong interview answer

The inventory defines the hosts and groups Ansible manages.

A simple inventory might look like:

```ini
[webservers]
web01.example.com
web02.example.com

[databases]
db01.example.com
db02.example.com
```

Then I can target a group:

```bash
ansible webservers -m ping
```

Instead of managing every server independently, inventory lets me organize systems according to roles or environments.

For example:

```text
production
    |
    +-- webservers
    +-- databases
    +-- monitoring

staging
    |
    +-- webservers
    +-- databases
```

---

# Question 6: What is static inventory versus dynamic inventory?

## Strong interview answer

Static inventory is explicitly maintained.

For example:

```ini
[webservers]
10.0.1.10
10.0.1.11
10.0.1.12
```

This can work for small or relatively stable environments.

But imagine an autoscaling environment:

```text
09:00
20 EC2 instances

12:00
80 EC2 instances

18:00
30 EC2 instances
```

Maintaining those addresses manually would be unreliable.

Dynamic inventory obtains hosts from an external source such as cloud infrastructure.

Conceptually:

```text
Ansible
   |
   v
AWS inventory plugin
   |
   v
EC2 API
   |
   v
Current instances
```

This is much more appropriate for dynamic cloud environments.

---

# Question 7: What is an Ansible playbook?

## Strong interview answer

A playbook defines automation tasks using YAML.

For example:

```yaml
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Ensure Nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

This describes the desired configuration.

The important distinction is that I prefer Ansible modules over arbitrary shell commands where appropriate.

---

# Question 8: What is an Ansible module?

## Strong interview answer

A module performs a specific automation operation.

Examples include modules for:

```text
Packages
Files
Services
Users
Git
Templates
Cloud resources
Commands
Repositories
```

For example:

```yaml
- name: Install Git
  ansible.builtin.package:
    name: git
    state: present
```

The package module understands package management semantics.

This is generally better than writing:

```yaml
- name: Install Git
  ansible.builtin.shell: apt-get install -y git
```

when the module can perform the task directly.

---

# Question 9: Why should you prefer Ansible modules over shell commands?

## Strong interview answer

Modules are generally designed to understand the state of the resource they manage.

For example:

```yaml
ansible.builtin.package:
  name: nginx
  state: present
```

means:

```text
Nginx should exist.
```

If Nginx is already installed, Ansible may not need to change anything.

A shell task such as:

```bash
apt-get install nginx
```

does not communicate desired state as clearly.

Modules generally provide better:

* Idempotency.
* Change reporting.
* Error handling.
* Portability.
* Readability.

I still use `command` or `shell` when there is no appropriate module or when the operation genuinely requires it.

---

# Question 10: What is idempotency in Ansible?

## Strong interview answer

Idempotency means running automation repeatedly should not keep making unnecessary changes after the system reaches the desired state.

Suppose:

```yaml
- name: Ensure Nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

First run:

```text
changed
```

because Nginx needs to be installed.

Second run:

```text
ok
```

because the desired state already exists.

Conceptually:

```text
First run

Current State
Nginx absent

Desired State
Nginx present

Result
CHANGE
```

Then:

```text
Second run

Current State
Nginx present

Desired State
Nginx present

Result
NO CHANGE
```

That behavior is fundamental to reliable configuration management.

---

# Question 11: Your playbook reports "changed" every time it runs. What would you investigate?

## Strong interview answer

I would identify which task repeatedly reports changed.

Possible causes include:

* Non-idempotent shell commands.
* Files regenerated with changing values.
* Timestamps embedded in configuration.
* Incorrect `changed_when`.
* Command modules that cannot determine state.
* External systems modifying the same configuration.

For example:

```yaml
- name: Restart application
  ansible.builtin.shell: systemctl restart myapp
```

will restart the application whenever that task runs.

Instead, the restart may need to happen only when configuration changes.

That is where handlers become useful.

---

# Question 12: What is an Ansible handler?

## Strong interview answer

A handler is a task that runs when notified by another task that reports a change.

Example:

```yaml
tasks:
  - name: Deploy Nginx configuration
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart Nginx

handlers:
  - name: Restart Nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

Now:

```text
Configuration unchanged
        |
        v
No restart
```

But:

```text
Configuration changed
        |
        v
Notify handler
        |
        v
Restart Nginx
```

This avoids unnecessary service disruption.

---

# Question 13: Why is restarting a service on every Ansible run bad?

## Strong interview answer

Because configuration management may run frequently.

If every run causes:

```text
Restart Nginx
Restart application
Restart database
```

even when nothing changed, automation itself becomes a source of instability.

Unnecessary restarts can cause:

* Connection interruption.
* Temporary downtime.
* Cache loss.
* Application warm-up.
* Failed requests.
* Database disruption.

Services should normally restart only when a relevant change requires it.

---

# Question 14: What is a role in Ansible?

## Strong interview answer

A role organizes related automation into a reusable structure.

For example:

```text
roles/
  nginx/
    tasks/
    handlers/
    templates/
    files/
    defaults/
    vars/
```

Instead of one giant playbook containing hundreds of unrelated tasks, I can create reusable roles such as:

```text
common
nginx
docker
monitoring
application
security
```

Then:

```yaml
roles:
  - common
  - nginx
  - monitoring
```

This improves maintainability and reuse.

---

# Question 15: What would you put in a `common` role?

## Strong interview answer

Only configuration genuinely common to the relevant systems.

For example:

```text
Baseline packages
Time synchronization
Standard users
Logging configuration
Monitoring agent
Security baseline
Common directories
```

I would avoid turning `common` into a dumping ground for unrelated configuration.

If everything goes into `common`, the role becomes difficult to test and changes gain a large blast radius.

---

# Question 16: What is an Ansible template?

## Strong interview answer

Templates allow configuration files to be generated using variables, commonly through Jinja2.

For example:

```nginx
server {
    listen {{ nginx_port }};
    server_name {{ server_name }};
}
```

Variables might be:

```yaml
nginx_port: 80
server_name: app.example.com
```

Ansible renders:

```nginx
server {
    listen 80;
    server_name app.example.com;
}
```

This allows the same template to support different environments without duplicating entire configuration files.

---

# Question 17: What is the difference between `copy` and `template`?

## Strong interview answer

`copy` is appropriate when the destination file should essentially match a static source file.

For example:

```yaml
- name: Copy banner
  ansible.builtin.copy:
    src: motd
    dest: /etc/motd
```

`template` is appropriate when the file contains variables or conditional logic.

```yaml
- name: Deploy Nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
```

A simple rule is:

```text
Static file
→ copy

Variable-driven configuration
→ template
```

---

# Question 18: What are Ansible variables?

## Strong interview answer

Variables allow configuration to change according to environment, host, role, or other context.

For example:

```yaml
app_port: 8080
environment: production
```

Then:

```yaml
- name: Configure application
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/myapp/app.conf
```

The template might contain:

```text
PORT={{ app_port }}
ENVIRONMENT={{ environment }}
```

Variables allow reusable automation rather than copying a separate playbook for every environment.

---

# Question 19: What are `group_vars` and `host_vars`?

## Strong interview answer

They allow variables to be associated with inventory groups or individual hosts.

For example:

```text
group_vars/
  production.yml
  webservers.yml

host_vars/
  web01.yml
  web02.yml
```

`group_vars/webservers.yml` might contain:

```yaml
nginx_port: 80
```

while a specific host could override something through:

```text
host_vars/web01.yml
```

I try to keep variable design understandable because excessive overrides can make it difficult to determine where a final value came from.

---

# Question 20: What is variable precedence in Ansible?

## Strong interview answer

Ansible can obtain variables from multiple sources, and some sources have higher precedence than others.

In an interview, I would not try to recite every precedence level from memory unless asked.

The operational point is more important.

If:

```text
Expected:
app_port = 8080

Actual:
app_port = 9090
```

I investigate where the value is being defined.

Possible sources include:

```text
Role defaults
Inventory
group_vars
host_vars
Play variables
Extra variables
```

A common troubleshooting problem is that a variable is correct in one file but overridden somewhere else.

---

# Question 21: What are facts in Ansible?

## Strong interview answer

Facts are information collected about managed systems.

Examples include:

```text
Operating system
Hostname
IP addresses
CPU
Memory
Network interfaces
Architecture
```

A playbook can use facts to make decisions.

For example:

```yaml
when: ansible_facts['os_family'] == "Debian"
```

This allows automation to adapt according to the managed system.

---

# Question 22: What does `gather_facts` do?

## Strong interview answer

Fact gathering collects system information before tasks run.

For example:

```yaml
- hosts: all
  gather_facts: true
```

Those facts can then be used by tasks and templates.

However, fact gathering has overhead.

For automation that does not need facts, it may be disabled:

```yaml
gather_facts: false
```

I would make that decision based on what the playbook actually requires.

---

# Question 23: What is a conditional in Ansible?

## Strong interview answer

Conditionals control whether a task executes.

For example:

```yaml
- name: Install package on Debian systems
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == "Debian"
```

This is useful when different systems require different behavior.

But if a playbook contains huge numbers of deeply nested conditionals, I would consider whether the role or inventory design should be simplified.

---

# Question 24: What are loops in Ansible?

## Strong interview answer

Loops allow the same task to operate on multiple items.

For example:

```yaml
- name: Install required packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop:
    - git
    - curl
    - nginx
```

This is cleaner than duplicating the same task three times.

For some modules, passing a list directly can also be appropriate.

---

# Question 25: What does `become` mean?

## Strong interview answer

`become` enables privilege escalation.

For example:

```yaml
- hosts: webservers
  become: true
```

Ansible may connect as a normal user and elevate privileges for tasks requiring administrative access.

Conceptually:

```text
SSH as:
ansible-user

        |
        v

Privilege escalation

        |
        v

root-level operation
```

This is preferable to casually using direct root SSH access everywhere.

---

# Question 26: Should your Ansible user have unrestricted sudo access?

## Strong interview answer

Not automatically.

The automation account should have the privileges required for its responsibilities.

The design depends on the environment.

I consider:

```text
Which commands need elevation?
Which hosts can the account access?
Can it become root?
How are credentials protected?
Can production and development use different identities?
Is activity audited?
```

An automation account is powerful and should be treated like a production service identity.

---

# Question 27: How would you manage passwords and secrets in Ansible?

## Strong interview answer

I would not store plaintext production passwords directly in Git.

Ansible Vault can encrypt sensitive values.

For example:

```bash
ansible-vault encrypt group_vars/production/vault.yml
```

Secrets may also come from dedicated secret-management systems depending on the architecture.

The broader principle is:

```text
Git repository
should not contain
plaintext production secrets.
```

---

# Question 28: What is Ansible Vault?

## Strong interview answer

Ansible Vault encrypts sensitive Ansible data or files.

For example:

```yaml
db_password: SuperSecretPassword
```

should not simply be committed as plaintext.

It can be stored in encrypted form using Vault.

But encryption is only part of the security model.

I still need to protect:

```text
Vault password
CI/CD credentials
Decryption permissions
Logs
Backups
```

If everyone has unrestricted access to the decryption key, encryption provides limited practical separation.

---

# Question 29: Should the Ansible Vault password be stored in the same Git repository?

## Strong interview answer

No.

That would defeat much of the purpose.

It would be like storing:

```text
Encrypted secret
+
Decryption key
```

together.

The decryption credential should be obtained securely, for example from a protected CI/CD secret or another approved credential-management mechanism.

---

# Question 30: What is an ad hoc Ansible command?

## Strong interview answer

An ad hoc command performs a task without creating a full playbook.

For example:

```bash
ansible webservers -m ping
```

or:

```bash
ansible webservers -m ansible.builtin.command -a "uptime"
```

They are useful for quick checks and operational tasks.

For repeatable production configuration, I prefer playbooks because they provide version-controlled automation.

---

# Question 31: What does the Ansible `ping` module actually test?

## Strong interview answer

It is not simply an ICMP ping.

For typical Linux management, it verifies that Ansible can connect to the host and execute the module successfully.

So:

```bash
ansible all -m ping
```

returning:

```text
pong
```

provides evidence that the Ansible connection and execution path is working.

A host may respond to network ICMP ping but still fail Ansible because:

```text
SSH blocked
Wrong user
Wrong SSH key
Python/runtime issue
Privilege problem
Inventory mistake
```

---

# Question 32: Ansible says a host is UNREACHABLE. What do you check?

## Strong interview answer

I troubleshoot from connectivity outward.

First:

```text
Is the hostname/IP correct?
```

Then:

```text
Can the control node reach the server?
```

Then:

```text
Is SSH port accessible?
```

For example:

```bash
ssh ansible-user@server
```

Then investigate:

```text
DNS
Route
Firewall
Security group
SSH service
SSH key
Username
Proxy/bastion configuration
```

`UNREACHABLE` usually means Ansible could not establish the required connection to execute the task.

That is different from a task executing and returning `FAILED`.

---

# Question 33: What is the difference between UNREACHABLE and FAILED?

## Strong interview answer

`UNREACHABLE` generally means Ansible could not successfully connect to or execute through the normal connection path.

For example:

```text
SSH timeout
Authentication failure
Host unreachable
```

`FAILED` means Ansible reached the host and attempted a task, but the task failed.

For example:

```text
Package not found
Permission denied
Invalid configuration
Service restart failed
```

That distinction immediately narrows troubleshooting.

---

# Question 34: A playbook works on 95 servers but fails on five. What do you do?

## Strong interview answer

I do not immediately rerun against all 100.

I first identify the failure pattern.

Ask:

```text
Are the five servers in the same subnet?

Same OS version?

Same application version?

Same inventory group?

Same SSH key?

Same package repository?

Same availability zone?

Were they recently created?
```

Then inspect the failed task and error.

For example:

```text
95:
changed/ok

5:
FAILED package not found
```

Maybe those five servers run a different operating system.

The fact that most servers succeeded tells me the playbook is not universally broken.

I investigate what distinguishes the failing hosts.

---

# Question 35: How would you rerun a playbook only against failed servers?

## Strong interview answer

Depending on the workflow, I can limit execution to specific hosts or groups.

For example:

```bash
ansible-playbook site.yml --limit web17,web22
```

But I only rerun after understanding why they failed.

Blind retries can hide persistent configuration problems.

---

# Question 36: What does `--limit` do?

## Strong interview answer

It restricts the playbook to selected inventory hosts or groups.

For example:

```bash
ansible-playbook deploy.yml --limit staging
```

or:

```bash
ansible-playbook deploy.yml --limit web01
```

This is extremely useful operationally.

It can also be dangerous.

Running:

```text
--limit production
```

instead of:

```text
--limit staging
```

can have serious consequences.

Environment selection should therefore have additional controls.

---

# Question 37: What are Ansible tags?

## Strong interview answer

Tags allow selected portions of a playbook to be executed.

For example:

```yaml
- name: Install Nginx
  ansible.builtin.package:
    name: nginx
    state: present
  tags:
    - nginx
```

Then:

```bash
ansible-playbook site.yml --tags nginx
```

Tags can be useful for targeted operations.

But I do not rely on tags as the only safety mechanism for production.

Partial execution can sometimes violate assumptions made by the full playbook.

---

# Question 38: What is check mode?

## Strong interview answer

Check mode attempts to show what Ansible would change without actually applying supported changes.

For example:

```bash
ansible-playbook site.yml --check
```

This is useful before production changes.

Conceptually:

```text
Playbook
   |
   v
Check mode
   |
   v
Expected changes
```

But check mode is not a perfect simulation.

Some modules and commands cannot accurately predict behavior without actually executing.

So:

```text
Check mode passed
```

does not guarantee:

```text
Production apply will succeed.
```

---

# Question 39: What does `--diff` do?

## Strong interview answer

Diff mode can show changes to supported files and templates.

For example:

```bash
ansible-playbook site.yml --check --diff
```

This can help reviewers see:

```text
Old configuration
        |
        v
New configuration
```

But I would be careful with sensitive files because diff output can expose secrets in logs.

---

# Question 40: Your CI system logs an Ansible diff containing a database password. What went wrong?

## Strong interview answer

The automation exposed sensitive data through output.

Even if the source secret was encrypted, runtime rendering may reveal it.

I would:

1. Treat the exposed credential as compromised.
2. Rotate it.
3. Restrict access to affected logs.
4. Review how the secret reached output.
5. Use mechanisms such as `no_log` where appropriate.
6. Review pipeline logging policies.

Secret protection is not finished when the value is encrypted at rest.

---

# Question 41: What is `no_log`?

## Strong interview answer

`no_log` prevents sensitive task information from being displayed in normal Ansible output.

Example:

```yaml
- name: Configure sensitive credential
  ansible.builtin.some_module:
    password: "{{ db_password }}"
  no_log: true
```

This can reduce secret exposure through logs.

However, overusing `no_log` can make troubleshooting difficult.

I use it for genuinely sensitive operations rather than hiding every task.

---

# Question 42: What are Ansible return statuses such as `ok`, `changed`, `failed`, and `skipped`?

## Strong interview answer

They describe task outcomes.

```text
ok
Desired state already existed.

changed
Ansible modified something.

failed
Task execution failed.

skipped
Task was intentionally not executed.

unreachable
Ansible could not successfully reach/manage the host.
```

Understanding these statuses is important when troubleshooting large runs.

---

# Question 43: What is `changed_when`?

## Strong interview answer

`changed_when` allows me to define when Ansible should consider a task changed.

This is particularly useful for commands where Ansible cannot automatically determine whether state changed.

For example:

```yaml
- name: Check application version
  ansible.builtin.command: /opt/app/bin/version
  register: app_version
  changed_when: false
```

The command only reads information.

It should not report a change.

Accurate change reporting matters because handlers and operational decisions may depend on it.

---

# Question 44: What is `failed_when`?

## Strong interview answer

`failed_when` allows custom failure conditions.

Suppose a command returns behavior that needs application-specific interpretation.

I can register its result and define when the task should fail.

This is useful when:

```text
Exit code alone
does not represent
the operational success condition.
```

But I avoid using it to hide genuine failures.

---

# Question 45: What does `register` do?

## Strong interview answer

`register` stores a task's result in a variable.

For example:

```yaml
- name: Check application status
  ansible.builtin.command: systemctl is-active myapp
  register: app_status
  changed_when: false
```

Then I can inspect:

```yaml
app_status.stdout
app_status.rc
```

and use the result in later conditions.

---

# Question 46: What is the difference between `command` and `shell`?

## Strong interview answer

`command` executes a command directly without invoking a shell.

`shell` runs through a shell, allowing features such as:

```text
Pipes
Redirection
Shell variables
&&
||
```

For example:

```bash
cat file | grep ERROR
```

requires shell behavior.

If I do not need shell features, I generally prefer `command`.

That reduces shell interpretation and potential security issues.

---

# Question 47: Why can the `shell` module be dangerous?

## Strong interview answer

Because it introduces shell interpretation.

If untrusted or poorly validated variables enter a shell command, there can be command-injection risk.

For example, constructing:

```text
rm -rf {{ user_supplied_path }}
```

without appropriate safeguards can be dangerous.

Shell tasks can also be less idempotent and harder for Ansible to reason about.

I use purpose-built modules when available.

---

# Question 48: What is configuration drift?

## Strong interview answer

Configuration drift happens when a managed system no longer matches its intended configuration.

For example:

```text
Ansible desired state:

PermitRootLogin no
```

Someone manually changes:

```text
PermitRootLogin yes
```

Now:

```text
Desired configuration
!=
Actual configuration
```

The next Ansible run can restore the desired state if the configuration is properly managed.

---

# Question 49: Someone manually changes `/etc/ssh/sshd_config` in production. What happens on the next Ansible run?

## Strong interview answer

# Question 57: Why is `ignore_errors: true` dangerous?

## Strong interview answer

Because it can convert a serious failure into something the playbook continues past.

Suppose:


Now the playbook may report later tasks while part of the infrastructure remains incorrectly configured.

There are legitimate uses for controlled error handling, but:

```text

```

is not a troubleshooting strategy.

# Question 61: How do retries work in Ansible?

## Strong interview answer

Retries are useful for operations that may temporarily fail.

For example, waiting for an application to become healthy:

```yaml
- name: Wait for application
  ansible.builtin.uri:
    url: http://localhost:8080/health
    status_code: 200
  register: health
  until: health.status == 200
  retries: 10
  delay: 5
```

Conceptually:

```text
Check
 |
 X
Wait
 |
Check
 |
 X
Wait
 |
Check
 |
 ✓
Continue
```

This is better than assuming a service becomes ready immediately after restart.

# Question 65: What is the difference between `started` and `restarted` in the service module?

## Strong interview answer

`started` means ensure the service is running.

If it is already running, Ansible generally does not need to restart it.

`restarted` explicitly restarts the service.

For desired-state configuration:

```yaml
state: started
```

is often appropriate.

For a handler responding to a configuration change:

```yaml
state: restarted
```

or a reload may be appropriate depending on the service.

# Question 66: When would you prefer reload over restart?

## Strong interview answer

If the service supports safe configuration reloads and a full restart is unnecessary.

For example:

```text
Reload
→ reread configuration
→ existing service continues

Restart
→ stop process
→ start process
```

Reload can reduce disruption.

But whether it is safe depends on the application.

I do not assume every service supports meaningful reload behavior.

```text

Recovery procedures
```

# Question 69: How would you make an Ansible playbook safer to rerun after partial failure?

## Strong interview answer

I design tasks to be idempotent.

For example:

```text
Task 1 already completed
→ Ansible sees desired state
→ no unnecessary change

Task 2 already completed
→ no unnecessary change

Task 3 failed
→ retry after root cause fixed
```

This is much safer than a script that blindly repeats every action.

# Question 92: What is the difference between concurrency and rolling deployment?

## Strong interview answer

Concurrency controls how much work Ansible can perform in parallel.

```text
+

```

to maintain availability.

The fastest deployment is not necessarily the safest deployment.

## Strong interview answer

I troubleshoot Ansible systematically.

### Step 1: Confirm the target

Before running anything:

```text
Which inventory?

Which environment?

Which group?

Which hosts?

```

I do not assume.

---

Test:

```bash
ansible webservers -m ping
```

If unreachable, investigate:

```text
DNS
Network
SSH
Authentication
Inventory
Bastion
```

---

### Step 3: Identify the exact failed task

Do not troubleshoot:

```text
"Ansible is broken."
```

Troubleshoot:

```text
"Template deployment fails
on web03 because
/etc/nginx is not writable."
```

Specific failures are easier to solve.

---

### Step 4: Classify the problem

Is it:

```text
Connectivity?

Authentication?

Privilege?

Variable?

Template?

Package?

Service?

Application?

Inventory?

Dependency?

Configuration drift?
```

---

### Step 5: Compare successful and failed hosts

If:

```text
95 succeed
5 fail
```

ask:

```text
What is different about those five?
```

---

### Step 6: Inspect variables

Check whether the host receives the expected values.

Look at:

```text
group_vars
host_vars
role defaults
inventory variables
extra vars
```

---

### Step 7: Verify actual host state

Use appropriate system tools:

```bash
systemctl status nginx
journalctl -u nginx
ss -lntp
ls -l
id
df -h
```

Ansible error output is only one part of the evidence.

---

### Step 8: Validate configuration

For example:

```bash
nginx -t
```

before restarting Nginx.

---

### Step 9: Fix the root cause

Do not hide the failure using:

```yaml
ignore_errors: true
```

unless continuation is explicitly part of the design.

---

### Step 10: Test against limited scope

Use a development environment or limited host set.

```bash
ansible-playbook site.yml --limit test-host
```

---

### Step 11: Check idempotency

Run again.

Expected:

```text
No unnecessary changes.
```

---

### Step 12: Roll out gradually

For production:

```text
Canary
   |
   v
Small batch
   |
   v
Health check
   |
   v
Next batch
```

---

### Step 13: Monitor

Check:

```text
Application health
Error rate
Logs
CPU
Memory
Load balancer targets
Dependencies
```

# Production Scenario 1: 5 of 150 Servers Fail

The interviewer says:

> "Your Ansible playbook succeeds on 145 servers and fails on five. How do you troubleshoot it?"

Start by grouping the failure.

Suppose all five show:

```text
FAILED:
No package matching 'nginx' is available
```

Compare those hosts.

You discover:

```text
145 servers:
Ubuntu 24.04

5 servers:
RHEL
```

The playbook assumed a Debian-based package environment.

The solution is not:

```text
Run the playbook repeatedly.
```

The solution is to make the configuration support the actual host population or correct the inventory/system inconsistency.

# Production Scenario 2: The Playbook Restarts Nginx Every Time

Playbook:

```yaml
- name: Deploy config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf

- name: Restart Nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

Every run:

```text
Nginx restart
```

even when the configuration did not change.

Better:

```yaml
- name: Deploy config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart Nginx
```

Now:

```text
Config unchanged
→ no restart

Config changed
→ handler
→ restart
```

That is a more reliable configuration-management pattern.

# How to Answer Ansible Questions in a Real Interview

Avoid saying:

> "I would rerun the playbook."

A stronger answer is:

> "I would first identify whether the failure is targeting, connectivity, authentication, privilege escalation, variable resolution, task execution, or application validation. If most hosts succeeded, I would compare the failed hosts against successful ones to identify what differs. I would fix the root cause, test against limited scope, confirm idempotency, and then continue the rollout."

Avoid:

> "I would use `ignore_errors` so the deployment continues."

A stronger answer is:

> "I would determine whether that failure is genuinely recoverable. For expected conditions I can define explicit failure logic or recovery behavior. For mandatory production configuration, I would rather stop the rollout than allow automation to silently leave part of the fleet incorrectly configured."

Avoid:

> "Ansible successfully restarted the service, so deployment succeeded."

A stronger answer is:

> "A successful service restart only proves the service manager accepted the operation. I would validate the application itself through health checks, logs, monitoring, and relevant dependency checks before considering the deployment successful."

```text

```


```text

```


```text

web02  ok=20 changed=5 failed=0
```

> "I would identify the exact failed task on web03 and compare that server with the successful hosts. I would check its inventory membership, variables, OS, connectivity, privileges, package sources, and current configuration depending on the error. Once I understand and fix the root cause, I would rerun only the affected scope, verify idempotency, and confirm application health before continuing."

That is what practical Ansible interviews are really testing.

Not whether you memorized YAML.

Whether you can use configuration management safely when real production systems do not behave exactly as expected.
