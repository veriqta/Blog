# Part 3: Networking and Connectivity Troubleshooting

Networking problems are some of the most common issues junior DevOps engineers are expected to troubleshoot.

An application may be healthy, the server may be running normally, and the deployment may have completed successfully, yet users still cannot reach the service.

The reason might be:

* DNS failure
* Wrong IP address
* Incorrect port
* Firewall rule
* Cloud security rule
* Routing problem
* Application binding issue
* Proxy configuration
* Load balancer failure
* TLS certificate problem
* Network latency
* Packet loss
* Broken dependency
* Misconfigured `/etc/hosts`
* Service listening only on localhost

The biggest mistake candidates make in networking interviews is jumping directly to one layer.

For example:

"The website is down, so I would check the firewall."

That is too narrow.

A better engineer isolates the problem step by step.

A useful mental model is:

```text
Client
  ↓
DNS
  ↓
Network path
  ↓
Firewall / security controls
  ↓
Load balancer / proxy
  ↓
Server
  ↓
Listening port
  ↓
Application
  ↓
Downstream dependency
```

The goal is to discover where communication stops working.

---

# Question 1: A user says they cannot reach your application. What would you check first?

## What the interviewer is testing

The interviewer wants to see whether you can turn a vague complaint into a structured investigation.

"Cannot reach the application" could mean many different things.

The user might be experiencing:

* DNS failure
* Connection timeout
* Connection refused
* TLS failure
* HTTP 404
* HTTP 500
* HTTP 502
* HTTP 503
* Slow response
* Browser-only issue

Those are very different problems.

## Strong interview answer

I would start by getting the exact symptom.

I would ask:

* What URL are they accessing?
* What exact error do they see?
* Is everyone affected or only one user?
* Did it ever work?
* When did the problem start?
* Was there a recent deployment or network change?

Then I would try to reproduce it.

For example:

```bash
curl -v https://app.example.com
```

The verbose output can show:

* DNS resolution
* IP address selected
* TCP connection attempt
* TLS negotiation
* HTTP response

That gives me far more information than simply saying "the website is down."

## Troubleshooting flow

I would isolate the layers.

```text
Can hostname resolve?
        ↓
Can destination IP be reached?
        ↓
Can required port be reached?
        ↓
Is something listening?
        ↓
Does application respond locally?
        ↓
Does proxy/load balancer work?
        ↓
Is application returning expected response?
```

## Common candidate mistake

Jumping straight to restarting the application.

The application may be perfectly healthy.

Always determine where communication fails first.

# Question 2: What is the difference between "Connection refused" and "Connection timed out"?

This is one of the most important networking interview questions for junior DevOps candidates.

## Strong interview answer

These errors suggest different failure patterns.

### Connection refused

A connection refused error generally means the client successfully reached the destination host, but the connection was rejected because nothing was accepting connections on that destination port, or the host actively rejected it.

For example:

```bash
curl http://192.168.1.20:8080
```

might return:

```text
curl: (7) Failed to connect to 192.168.1.20 port 8080:
Connection refused
```

Possible causes include:

* Application is stopped
* Application is listening on another port
* Application is listening only on localhost
* Service failed during startup
* Host firewall actively rejected the connection

### Connection timed out

A timeout means the client sent traffic but did not receive the expected response within the allowed time.

Possible causes include:

* Firewall silently dropping traffic
* Cloud security rule blocking traffic
* Incorrect routing
* Wrong IP address
* Unreachable network
* Network ACL
* Broken path
* Severe network congestion

## Interview takeaway

A good engineer uses the error itself as evidence.

```text
Refused
→ destination probably reachable
→ investigate listening service/port

Timeout
→ investigate network path/security/routing
```

It is not absolute in every environment, but it is a strong starting point.

# Question 3: An application works on localhost but cannot be accessed remotely. What would you investigate?

## Strong interview answer

First I would confirm that it really works locally.

```bash
curl http://localhost:8080
```

Then check the listening socket:

```bash
ss -lntp | grep :8080
```

Suppose I see:

```text
LISTEN 0 128 127.0.0.1:8080
```

That tells me the application is bound only to the loopback interface.

Remote systems cannot connect directly to that listener.

If the application is intended to accept external connections, I would expect an appropriate network interface binding.

For example:

```text
0.0.0.0:8080
```

means listening on all IPv4 interfaces.

I would confirm the intended configuration before changing it.

## If the application is listening correctly

Then I would investigate:

* Host firewall
* Cloud security group
* Network ACL
* Routing
* Load balancer
* Reverse proxy
* DNS
* Container networking if applicable

## Important interview point

This situation demonstrates why application health and network reachability are separate things.

# Question 4: How would you check whether a port is open and reachable?

## Strong interview answer

Locally, I can check what the server is listening on with:

```bash
ss -lntp
```

For a specific port:

```bash
ss -lntp | grep :443
```

From another machine, I can test reachability using:

```bash
nc -vz server.example.com 443
```

If `nc` is available.

Another useful test is:

```bash
curl -v https://server.example.com
```

For TCP connectivity specifically, tools such as:

```bash
telnet server.example.com 443
```

may sometimes be used if installed, although `nc` is often more flexible.

## What these tools tell me

`ss` answers:

```text
Is something listening locally?
```

`nc` helps answer:

```text
Can I establish a TCP connection from here?
```

`curl` goes further:

```text
Can I connect and communicate using HTTP/HTTPS?
```

These are different levels of testing.

# Question 5: How would you troubleshoot DNS resolution failure?

## Strong interview answer

I would first determine whether the problem is actually DNS.

For example:

```bash
curl -v https://example.com
```

If I see something like:

```text
Could not resolve host
```

I would test name resolution directly.

```bash
dig example.com
```

or:

```bash
nslookup example.com
```

I could also use:

```bash
getent hosts example.com
```

`getent` is useful because it uses the system's configured name resolution mechanisms.

Then I would inspect DNS configuration.

```bash
cat /etc/resolv.conf
```

On systems using systemd-resolved:

```bash
resolvectl status
```

I would ask:

* Which resolver is configured?
* Can the server reach it?
* Does another hostname resolve?
* Is the issue only one DNS record?
* Is the expected record correct?
* Has the record recently changed?
* Is DNS caching involved?

## Important distinction

If this works:

```bash
ping 8.8.8.8
```

but this fails:

```bash
ping google.com
```

assuming ICMP is permitted, I would strongly suspect name resolution rather than general IP connectivity.

# Question 6: A DNS record was changed, but some users still reach the old server. Why?

## Strong interview answer

DNS responses can be cached.

DNS records commonly have a TTL, or Time To Live, which tells resolvers how long the record may be cached.

Suppose:

```text
app.example.com
```

previously pointed to:

```text
10.10.1.20
```

and now points to:

```text
10.10.1.30
```

Some recursive resolvers or clients may continue using the previously cached result until its TTL expires.

I would verify the record:

```bash
dig app.example.com
```

And possibly query a specific DNS server:

```bash
dig @8.8.8.8 app.example.com
```

I would compare responses from different resolvers.

## Other possible causes

It is not always caching.

I would also consider:

* Multiple DNS records
* Split-horizon DNS
* Local `/etc/hosts`
* Proxy caching
* CDN behavior
* Browser DNS cache
* Incorrect authoritative DNS update

## Strong interview response

I would not immediately say:

"DNS propagation takes 24 to 48 hours."

That is too simplistic.

I would inspect the record, TTL, authoritative response, and resolver behavior.

# Question 7: What is `/etc/hosts`, and how can it create connectivity problems?

## Strong interview answer

`/etc/hosts` provides static hostname-to-IP mappings on Linux systems.

Example:

```text
10.10.10.20 app.internal
```

Depending on the system's name-service configuration, this entry may be used before DNS.

Suppose DNS correctly points:

```text
app.internal
```

to:

```text
10.10.10.30
```

but the server has:

```text
10.10.10.20 app.internal
```

inside `/etc/hosts`.

The application may still connect to the old IP.

I would inspect:

```bash
cat /etc/hosts
```

and compare:

```bash
getent hosts app.internal
```

with:

```bash
dig app.internal
```

If they return different addresses, local name resolution configuration may be overriding DNS.

# Question 8: What is the difference between an IP address and a port?

## Strong interview answer

An IP address identifies a network interface or host location within an IP network.

A port identifies a particular service or application endpoint on that host.

For example:

```text
192.168.10.20:443
```

means:

```text
IP address = 192.168.10.20
Port       = 443
```

Multiple services can run on the same server because they listen on different ports.

For example:

```text
22   SSH
80   HTTP
443  HTTPS
5432 PostgreSQL
3306 MySQL
```

Those are common defaults, although applications can use different ports.

## Interview follow-up

### "Can two applications use the same port?"

They generally cannot bind the exact same IP address and transport protocol combination in the usual way unless the operating system/application uses specific socket-sharing mechanisms.

If one process already listens on:

```text
0.0.0.0:8080
```

another normal process trying to bind the same socket may receive:

```text
Address already in use
```

## Strong interview answer

I would use:

```bash
ip addr
```

or the shorter:

```bash
ip a
```

I might see multiple interfaces:

```text
lo
eth0
ens5
docker0
```

depending on the environment.

I could also use:

```bash
hostname -I
```

for a quick view of assigned addresses.

## Important interview point

A machine can have multiple IP addresses.

It may have:

* Loopback address
* Private address
* Public address
* Container bridge address
* Multiple network interfaces

So asking for "the server's IP" can sometimes be ambiguous.

# Question 10: How would you check the routing table on Linux?

## Strong interview answer

I would use:

```bash
ip route
```

Example:

```text
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.25
```

The default route tells the system where to send packets when there is no more specific matching route.

If a server can communicate with systems in its own subnet but cannot reach external networks, I would inspect the default route.

## Useful follow-up command

To determine which route Linux would use for a destination:

```bash
ip route get 8.8.8.8
```

This can show:

* Interface
* Gateway
* Source IP

That is often very useful during troubleshooting.

# Question 11: A server can reach systems on its own subnet but cannot access the internet. What could be wrong?

## Strong interview answer

I would investigate several possibilities.

First:

```bash
ip route
```

Check whether there is a valid default route.

Then test basic connectivity to the gateway if appropriate.

I would also consider:

* NAT configuration
* Cloud internet gateway
* Firewall rules
* Security groups
* Network ACLs
* DNS
* Proxy requirement
* Routing table configuration

If:

```bash
curl https://example.com
```

fails, I would distinguish DNS from connectivity.

For example, if direct IP connectivity works but hostname resolution fails, DNS becomes the stronger suspect.

If neither works, I would investigate the routing and security path.

# Question 12: What is a subnet?

## Strong interview answer

A subnet is a logical subdivision of an IP network.

For example:

```text
192.168.10.0/24
```

represents a network containing a range of IP addresses.

The `/24` represents the prefix length.

In IPv4, a `/24` generally leaves 8 bits for host addressing.

A subnet helps determine whether a destination is local or needs to be reached through a router.

## Why DevOps engineers need this

Subnetting matters when working with:

* VPCs
* Kubernetes networks
* Load balancers
* Private networks
* VPNs
* Firewalls
* Routing
* Cloud architecture

A junior candidate does not need to perform complex subnet calculations instantly, but should understand why networks are divided and routed.

---

# Question 13: What is a default gateway?

## Strong interview answer

A default gateway is the router a host uses when sending traffic to destinations that do not match a more specific local route.

On Linux, I can inspect it using:

```bash
ip route
```

Example:

```text
default via 192.168.1.1 dev eth0
```

That means traffic without a more specific route is sent through:

```text
192.168.1.1
```

If the default gateway is missing or incorrect, the host may still communicate with systems on the local subnet while failing to reach external networks.

# Question 14: What does `ping` actually test?

## Strong interview answer

`ping` commonly uses ICMP Echo Request and Echo Reply messages to test IP-level reachability and measure round-trip time.

Example:

```bash
ping 192.168.1.10
```

It can help identify:

* Whether ICMP reaches the destination
* Round-trip latency
* Packet loss

But successful ping does not prove the application works.

A server could respond to ping while:

```text
HTTPS is down
SSH is down
Application is crashed
Database is unavailable
```

Likewise, failed ping does not always prove the host is unavailable because ICMP may be blocked.

## Interview takeaway

`ping` is one signal, not a complete health check.

# Question 15: If ping works but the website does not, what does that tell you?

## Strong interview answer

It tells me that at least some IP-level connectivity exists between the client and destination.

I would then move higher in the network stack.

For example:

```bash
curl -v https://example.com
```

I would inspect:

* DNS
* TCP connection
* Port 443
* TLS handshake
* HTTP response

I would also check:

```bash
ss -lntp | grep :443
```

on the server if I have access.

Possible causes include:

* Web server stopped
* Wrong port
* Firewall blocking TCP 443
* Reverse proxy problem
* TLS problem
* Application problem

# Question 16: If ping fails, does that mean the server is down?

## Strong interview answer

No.

ICMP may be blocked by:

* Host firewall
* Cloud security rules
* Network firewall
* Router
* Organizational security policy

The server may still accept application traffic.

For example:

```bash
ping server.example.com
```

could fail while:

```bash
curl https://server.example.com
```

works successfully.

I would use a test relevant to the actual service.

If I am troubleshooting HTTPS, I care more about reaching TCP port 443 than whether ICMP is allowed.

# Question 17: What does `traceroute` help you investigate?

## Strong interview answer

`traceroute` helps show the path packets take toward a destination by revealing intermediate network hops where responses are available.

Example:

```bash
traceroute example.com
```

or in some environments:

```bash
tracepath example.com
```

It can help identify where connectivity appears to stop or where latency increases.

## Important limitation

Routers do not always respond to traceroute probes.

So seeing:

```text
* * *
```

does not automatically prove that router is broken.

Some devices simply do not return the expected responses.

I would use traceroute alongside other evidence rather than treating it as definitive.

# Question 18: A connection works from one server but fails from another. What does that suggest?

## Strong interview answer

That suggests the destination service may be healthy, and the difference may exist in the source environment or network path.

I would compare:

* Source IP
* Subnet
* Routing table
* DNS resolution
* Firewall rules
* Security groups
* Network ACLs
* Proxy settings
* `/etc/hosts`
* Source interface

For example:

Server A:

```bash
getent hosts api.internal
```

Server B:

```bash
getent hosts api.internal
```

If they resolve to different IPs, DNS or local resolution may explain the difference.

Or both resolve correctly, but Server B's subnet may not have a route to the destination.

Comparison is a powerful troubleshooting technique.

# Question 19: What is the difference between TCP and UDP?

## Strong interview answer

TCP is connection-oriented.

It provides mechanisms for:

* Reliable delivery
* Ordering
* Retransmission
* Flow control

Common TCP-based protocols include:

```text
HTTP
HTTPS
SSH
PostgreSQL
MySQL
```

UDP is connectionless and has lower protocol overhead, but it does not provide the same built-in delivery guarantees.

Common uses include:

```text
DNS
Streaming
VoIP
Telemetry
```

although some protocols can operate over multiple transports.

## DevOps troubleshooting relevance

The testing method may depend on the protocol.

For example:

```bash
nc -vz host 443
```

tests TCP connectivity.

Testing UDP requires different behavior and interpretation because there is no TCP-style connection handshake.

---

# Question 20: Explain the TCP three-way handshake.

## Strong interview answer

TCP typically establishes a connection using three steps:

```text
Client → SYN
Server → SYN-ACK
Client → ACK
```

After that, the connection is established.

This matters in troubleshooting.

If the client sends SYN packets but never receives SYN-ACK, the problem may exist somewhere between the client and server or at the server's security/network layer.

If the server immediately sends a reset, there may be no service accepting the connection.

## Why this matters

Understanding the handshake helps explain the difference between:

* Timeout
* Refused connection
* Successful connection

even if the candidate is not using packet captures during a junior interview.

# Question 21: How would you inspect active network connections on Linux?

## Strong interview answer

I would commonly use:

```bash
ss -tunap
```

Depending on permissions, this can show:

* TCP connections
* UDP sockets
* Local addresses
* Remote addresses
* Connection states
* Process information

For listening TCP sockets:

```bash
ss -lntp
```

For established TCP connections:

```bash
ss -tn state established
```

This can help when investigating:

* Unexpected connections
* Port usage
* Application dependencies
* Connection buildup
* Listening services

# Question 22: What do TCP states such as LISTEN and ESTABLISHED mean?

## Strong interview answer

`LISTEN` means a socket is waiting for incoming connection requests.

For example:

```text
0.0.0.0:443 LISTEN
```

indicates a service is waiting for TCP connections on port 443.

`ESTABLISHED` means a TCP connection has successfully been set up between endpoints.

Other states can include:

```text
SYN-SENT
SYN-RECV
FIN-WAIT
TIME-WAIT
CLOSE-WAIT
```

A junior engineer should at least understand LISTEN and ESTABLISHED and know that unusual numbers of connections in particular states may help indicate networking or application problems.

---

# Question 23: What is TIME_WAIT, and should you panic when you see many TIME_WAIT connections?

## Strong interview answer

TIME_WAIT is a normal part of TCP connection termination.

The endpoint that actively closes a connection may remain in TIME_WAIT for a period so delayed packets from the previous connection are not confused with a new connection using the same addressing tuple.

Seeing TIME_WAIT connections is not automatically a problem.

I would consider context.

For example:

* Is application traffic unusually high?
* Are connections being created excessively instead of reused?
* Is the system actually exhausting ports or resources?
* Is latency affected?

I would not tune kernel settings just because I see many TIME_WAIT entries.

---

# Question 24: A web application returns HTTP 404. Is that a network failure?

## Strong interview answer

Usually not.

A 404 means I successfully reached an HTTP server and received a valid HTTP response stating that the requested resource was not found.

That already tells me several things worked:

```text
DNS possibly worked
TCP connection worked
HTTP server responded
```

I would investigate:

* Wrong URL
* Wrong path
* Reverse proxy routing
* Application route
* Deployment version
* Virtual host configuration

The exact HTTP status code helps identify which layer is failing.

---

# Question 25: What does HTTP 500 usually indicate?

## Strong interview answer

HTTP 500 means the server encountered an internal error while processing the request.

The network connection itself has generally succeeded.

I would investigate:

* Application logs
* Exceptions
* Database connection
* Missing configuration
* Dependency failure
* Recent deployment
* Internal server errors

I would correlate the request timestamp with application logs.

Example:

```bash
journalctl -u myapp --since "10 minutes ago"
```

or inspect the application's own log files.

# Question 26: What do HTTP 502, 503, and 504 commonly indicate?

These codes are frequently tested in DevOps interviews.

## HTTP 502 Bad Gateway

A proxy or gateway received an invalid response from an upstream service.

Possible causes:

* Upstream application crashed
* Incorrect upstream address
* Port mismatch
* Protocol mismatch
* Broken proxy configuration

## HTTP 503 Service Unavailable

The service is currently unavailable.

Possible causes include:

* No healthy backends
* Application overloaded
* Service intentionally unavailable
* Failed deployment
* Load balancer has no healthy targets

## HTTP 504 Gateway Timeout

A gateway or proxy did not receive a response from the upstream service within the allowed time.

Possible causes:

* Slow application
* Slow database
* Network latency
* Upstream timeout
* Dependency hanging
* Incorrect timeout settings

## Interview point

Do not memorize only definitions.

Use the status code to decide where to investigate next.

# Question 27: Users receive 502 errors after a deployment. What would you investigate?

## Strong interview answer

I would first determine which component is generating the 502.

It might be:

* Nginx
* Load balancer
* API gateway
* Reverse proxy

Then I would inspect whether the upstream application is reachable.

Suppose Nginx proxies to:

```text
127.0.0.1:8080
```

I would test locally:

```bash
curl -v http://127.0.0.1:8080
```

Check listening sockets:

```bash
ss -lntp | grep :8080
```

Check application status:

```bash
systemctl status myapp
```

Check logs:

```bash
journalctl -u myapp -n 100
```

Possible deployment problems include:

* Application failed to start
* Application now listens on a different port
* Wrong environment variable
* Broken configuration
* Startup takes longer than expected

## Strong interview reasoning

A 502 from a reverse proxy often tells me:

```text
Client reached proxy successfully
Proxy had trouble communicating with upstream
```

So I would investigate the proxy-to-application path.

---

# Question 28: Users receive 504 errors only during peak traffic. What might be happening?

## Strong interview answer

I would suspect that upstream responses are exceeding the gateway or proxy timeout during high load.

I would investigate:

* Application latency
* CPU and memory
* Database query performance
* Connection pools
* Thread or worker exhaustion
* External APIs
* Network latency
* Load balancer timeout
* Proxy timeout

I would correlate:

```text
Traffic
Latency
Resource usage
Error rate
```

during the same time window.

The solution may not be to simply increase the timeout.

A longer timeout could hide an overloaded or slow backend.

I would first identify why requests become slow.

# Question 29: What is a firewall, and how can it affect troubleshooting?

## Strong interview answer

A firewall controls network traffic based on rules.

Rules may consider things such as:

* Source address
* Destination address
* Port
* Protocol
* Connection state

A firewall can exist at multiple layers:

```text
Linux host firewall
Cloud security group
Network firewall
Router ACL
Load balancer rules
```

On Linux systems, depending on the environment, I may encounter:

```text
iptables
nftables
firewalld
ufw
```

I would not assume that because the application is listening, the port is reachable externally.

For example:

```bash
ss -lntp | grep :8080
```

may confirm the application is listening, but a firewall may still block incoming traffic.

# Question 30: How would you inspect Linux firewall rules?

## Strong interview answer

The exact command depends on the firewall tooling in use.

For systems using `ufw`:

```bash
sudo ufw status
```

For `firewalld`:

```bash
sudo firewall-cmd --list-all
```

For nftables:

```bash
sudo nft list ruleset
```

Older or compatible environments may use:

```bash
sudo iptables -L -n -v
```

I would understand which firewall system the host actually uses before making changes.

## Important operational rule

I would be extremely careful changing firewall rules remotely.

A bad rule could cut off my own SSH session or block production traffic.

# Question 31: A developer says "Port 8080 is open." What exactly should you verify?

## Strong interview answer

"Open" can mean several things, so I would clarify.

I would verify:

1. Is the application listening on port 8080?

```bash
ss -lntp | grep :8080
```

2. Which interface is it bound to?

```text
127.0.0.1:8080
0.0.0.0:8080
10.0.1.20:8080
```

3. Can another host reach it?

```bash
nc -vz server-ip 8080
```

4. Is the application actually responding?

```bash
curl -v http://server-ip:8080
```

A port being listened on does not automatically mean the full application path is working.

# Question 32: What is a reverse proxy?

## Strong interview answer

A reverse proxy accepts requests from clients and forwards them to backend applications.

For example:

```text
Client
  ↓
Nginx
  ↓
Application on port 8080
```

Nginx might accept:

```text
HTTPS on port 443
```

and forward traffic internally to:

```text
127.0.0.1:8080
```

Reverse proxies can provide:

* TLS termination
* Routing
* Load balancing
* Headers
* Caching
* Compression
* Access control

## Troubleshooting relevance

If users cannot access an application, I need to determine whether the problem is:

```text
Client → proxy
```

or:

```text
Proxy → application
```

That distinction is essential.

# Question 33: What is a load balancer?

## Strong interview answer

A load balancer distributes requests across multiple backend servers or application instances.

Example:

```text
               ┌→ App Server 1
Client → LB ───┼→ App Server 2
               └→ App Server 3
```

It can improve:

* Availability
* Scalability
* Traffic distribution

Load balancers often perform health checks.

If a backend fails its health check, the load balancer may stop sending traffic to it.

## Interview follow-up

### "All servers are running, but the load balancer says they are unhealthy. Why?"

Possible causes include:

* Wrong health-check path
* Wrong health-check port
* Application not listening
* Firewall rule
* Health endpoint returns error
* Authentication required
* Slow health check
* Wrong protocol

"Server is running" does not mean "load balancer health check succeeds."

This is a realistic DevOps troubleshooting scenario.

# Question 35: How would you troubleshoot HTTPS or TLS problems?

## Strong interview answer

I would start with:

```bash
curl -v https://example.com
```

This can expose:

* DNS resolution
* TCP connection
* TLS handshake
* Certificate verification
* HTTP response

For certificate details, I could use:

```bash
openssl s_client -connect example.com:443 -servername example.com
```

I would inspect:

* Certificate expiration
* Hostname mismatch
* Certificate chain
* TLS protocol
* Correct certificate being served

## Common TLS failures

* Expired certificate
* Wrong hostname
* Missing intermediate certificate
* Wrong certificate deployed
* Client does not trust issuing CA
* TLS version mismatch

## Important distinction

If the TCP connection itself fails, I would not start by debugging the certificate.

TLS happens after TCP connectivity is established.

# Question 36: The browser reports a certificate hostname mismatch. What does that mean?

## Strong interview answer

The hostname the user requested does not match the names covered by the certificate.

For example, the user accesses:

```text
api.example.com
```

but the certificate is valid only for:

```text
www.example.com
```

The certificate may not be valid for the requested hostname.

I would inspect the certificate's Subject Alternative Names.

Using:

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com
```

and appropriate certificate inspection commands can help verify what certificate is actually served.

Possible causes include:

* Wrong certificate
* Wrong virtual host
* Load balancer configuration
* Proxy configuration
* DNS pointing to wrong endpoint

# Question 37: An application can connect to a database using its IP address but not its hostname. Where is the likely problem?

## Strong interview answer

If direct IP connectivity works but hostname-based connectivity fails, DNS or local name resolution becomes a strong suspect.

I would check:

```bash
getent hosts database.internal
```

and:

```bash
dig database.internal
```

I would inspect:

```bash
cat /etc/resolv.conf
```

and:

```bash
cat /etc/hosts
```

I would also verify whether the application is using the expected hostname.

This is a good example of isolating layers.

```text
Database reachable by IP
→ network path probably works
→ investigate hostname resolution
```

# Question 38: The hostname resolves correctly, but the application still cannot connect. What next?

## Strong interview answer

DNS is only one layer.

I would test the required port.

For example, if PostgreSQL runs on 5432:

```bash
nc -vz database.internal 5432
```

If the port connection fails, investigate:

* Firewall
* Routing
* Security groups
* Database listening address
* Service state

If TCP succeeds, I would move higher:

* Authentication
* TLS
* Database credentials
* Application configuration

The troubleshooting flow should continue upward one layer at a time.

---

# Question 39: What is NAT?

## Strong interview answer

NAT means Network Address Translation.

It translates IP addresses as traffic moves between networks.

A common cloud example is allowing systems with private IP addresses to initiate internet connections through a NAT device or managed NAT gateway without exposing those systems directly to unsolicited inbound internet traffic.

Example:

```text
Private Server
10.0.2.15
     ↓
NAT
     ↓
Public Internet
```

## Troubleshooting scenario

A server in a private subnet suddenly cannot download packages from the internet.

I may investigate:

* Route to NAT
* NAT availability
* Security rules
* Network ACL
* DNS

The private server does not necessarily need its own public IP to make outbound connections if NAT is configured.

# Question 40: A server has internet access but cannot reach one internal service. How would you approach it?

## Strong interview answer

Internet connectivity does not prove internal routing works.

I would investigate the specific destination.

First:

```bash
getent hosts internal-service.example
```

Then:

```bash
ip route get destination-ip
```

Then test the port:

```bash
nc -vz destination-ip 443
```

I would investigate:

* Internal DNS
* Private routing
* Firewall
* Network segmentation
* Security groups
* Service state

I would avoid thinking:

"The internet works, so networking is fine."

Different destinations can follow completely different routes and security paths.

# Final Production Interview Scenario

The interviewer gives you this situation:

> "Customers report that your web application is unavailable. The application team says the service is running. Monitoring shows that CPU, memory, and disk are healthy. When you SSH into the server and run `curl http://localhost:8080`, the application responds successfully. But users still cannot access `https://app.example.com`. Walk me through your investigation."

This is the type of question where your troubleshooting structure matters more than any single command.

A strong junior candidate might respond:

"I already know that the application responds locally, so I would avoid immediately changing the application. I would move outward through the network path."

First, check how the application is listening:

```bash
ss -lntp | grep :8080
```

Suppose I see:

```text
127.0.0.1:8080
```

That may be fine if Nginx is acting as the reverse proxy.

Now check the reverse proxy:

```bash
systemctl status nginx
```

Check whether Nginx listens on HTTPS:

```bash
ss -lntp | grep :443
```

Check logs:

```bash
journalctl -u nginx -n 100
```

Test locally through Nginx:

```bash
curl -vk https://localhost
```

If that succeeds, move outward.

Check DNS:

```bash
dig app.example.com
```

or:

```bash
getent hosts app.example.com
```

Confirm it resolves to the expected endpoint.

From an external machine:

```bash
curl -v https://app.example.com
```

Suppose it times out.

Now I would investigate:

* Host firewall
* Cloud security group
* Network ACL
* Routing
* Load balancer rules
* Public/private network configuration

Suppose instead it connects and returns:

```text
502 Bad Gateway
```

That changes the investigation.

The client can clearly reach the proxy or load balancer.

Now I would investigate the upstream application path.

That is the key lesson.

The error determines the next layer.

A strong answer sounds like:

> "I would avoid treating 'application unavailable' as one problem. Because localhost works, I know the application itself is at least responding on the server. I would then test each hop between the user and the application, DNS, external reachability, firewall or cloud security controls, load balancer or reverse proxy, listening ports, and TLS. I would stop when I find the first layer where expected communication fails."

That demonstrates troubleshooting ability.

# What Junior DevOps Candidates Should Learn From Part 3

Networking troubleshooting becomes easier when you stop treating "the network" as one giant system.

Break the path into layers.

```text
User
 ↓
DNS
 ↓
IP routing
 ↓
Firewall
 ↓
TCP/UDP
 ↓
Port
 ↓
TLS
 ↓
Proxy / Load Balancer
 ↓
Application
 ↓
Dependency
```

When something fails, ask:

1. Can the hostname resolve?
2. Does it resolve to the correct address?
3. Is there a route to that address?
4. Can I reach the required port?
5. Is something listening on that port?
6. Which interface is it listening on?
7. Is a firewall blocking traffic?
8. Is a cloud security control blocking traffic?
9. Does TLS succeed?
10. Does the proxy or load balancer respond?
11. Can the proxy reach the application?
12. Does the application return the correct HTTP response?
13. Can the application reach its own dependencies?
14. Is the issue global or only from one network?
15. What changed before the problem started?

Useful commands from this part include:

```bash
ip addr
ip route
ip route get
ss
ping
traceroute
tracepath
curl
dig
nslookup
getent
nc
openssl
hostname
cat
journalctl
systemctl
```

But just like Linux troubleshooting, the commands themselves are not the skill.

The skill is knowing which question each command answers.

`dig` helps answer:

```text
What does DNS say?
```

`getent hosts` helps answer:

```text
What address will this Linux system actually resolve?
```

`ip route` helps answer:

```text
Where will Linux send this traffic?
```

`ss` helps answer:

```text
What is listening or connected?
```

`nc` helps answer:

```text
Can I establish a TCP connection to this port?
```

`curl` helps answer:

```text
Can I communicate with the application protocol?
```

`openssl s_client` helps answer:

```text
What is happening during TLS?
```

A junior DevOps engineer does not need to know every networking concept at CCNP level.

But they should be able to isolate a connectivity problem instead of guessing.

That is what interviewers want to see.
