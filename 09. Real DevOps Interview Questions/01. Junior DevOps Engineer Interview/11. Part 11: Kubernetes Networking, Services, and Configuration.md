# Part 11: Kubernetes Networking, Services, and Configuration

A Kubernetes networking interview rarely stays at:

"What is a Service?"

A more realistic interviewer will give you a production symptom:

> "The Pods are Running and Ready. The application works when you curl the Pod IP directly, but it fails when you use the Service name. What do you check?"

Or:

> "Frontend Pods can reach the API, but the API cannot connect to the database after a NetworkPolicy change. Walk me through your investigation."

Or:

> "A ConfigMap was updated, but the application still behaves as if it has the old configuration. Why?"

These questions test whether you understand how traffic and configuration actually move through Kubernetes.

A useful request path is:

```text
Client
  ↓
DNS
  ↓
Ingress / Load Balancer
  ↓
Service
  ↓
EndpointSlice
  ↓
Ready Pod
  ↓
Container Port
  ↓
Application
```

Configuration follows a different path:

```text
Deployment
   ↓
Pod specification
   ↓
ConfigMap / Secret
   ↓
Environment variable or mounted file
   ↓
Application
```

When troubleshooting Kubernetes, your job is to determine exactly where one of these chains breaks.

---

# Question 1: Explain Kubernetes networking at a practical level.

## Strong interview answer

At a practical troubleshooting level, I think about Kubernetes networking in several layers:

```text
External client
      ↓
External DNS
      ↓
Load Balancer / Ingress
      ↓
Kubernetes Service
      ↓
EndpointSlice
      ↓
Pod IP
      ↓
Container
```

Inside the cluster, every Pod normally receives its own IP address.

Pods can communicate across nodes through the cluster networking implementation.

Services provide stable discovery and access to groups of Pods because Pod IPs are temporary.

DNS allows workloads to use names instead of hardcoded IP addresses.

NetworkPolicies can restrict which Pods or namespaces can communicate.

When troubleshooting, I test these layers independently rather than simply saying:

```text
"The network is broken."
```

---

# Question 2: Why does Kubernetes need Services if Pods already have IP addresses?

## Strong interview answer

Because Pods are ephemeral.

Suppose an API Pod currently has:

```text
10.244.2.17
```

The Pod crashes and Kubernetes replaces it.

The replacement might receive:

```text
10.244.4.31
```

If another application had hardcoded:

```text
http://10.244.2.17:8080
```

communication would break.

A Service provides a stable abstraction:

```text
Application
    ↓
payments-service
    ↓
10.244.2.17
10.244.3.21
10.244.4.31
```

The backend Pods can change while clients continue using the Service.

---

# Question 3: What happens when a client sends traffic to a Kubernetes Service?

## Strong interview answer

Suppose a client accesses:

```text
payments.production.svc.cluster.local
```

DNS resolves the Service name.

For a normal ClusterIP Service, that resolves to the Service's virtual IP.

The cluster networking components then direct the traffic toward an eligible backend Pod represented through the Service's EndpointSlices.

Conceptually:

```text
Client Pod
    ↓
DNS lookup
    ↓
Service ClusterIP
    ↓
Service networking
    ↓
EndpointSlice
    ↓
Ready backend Pod
```

The exact packet handling depends on the cluster networking implementation and configuration.

For troubleshooting, I separate:

```text
DNS resolution
Service definition
Endpoint discovery
Network path
Application listener
```

---

# Question 4: What are the main Kubernetes Service types?

## Strong interview answer

The common Service types are:

```text
ClusterIP
NodePort
LoadBalancer
ExternalName
```

`ClusterIP` provides internal cluster access and is the default.

`NodePort` exposes the Service on a port on cluster nodes.

`LoadBalancer` asks the underlying infrastructure or integration to provision an external load balancer where supported.

`ExternalName` maps a Service to an external DNS name using DNS behavior rather than proxying traffic to normal Pod endpoints.

The appropriate type depends on how the application should be accessed.

---

# Question 5: What is ClusterIP?

## Strong interview answer

ClusterIP is the default Service type.

For example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payments
spec:
  selector:
    app: payments
  ports:
    - port: 80
      targetPort: 8080
```

Clients inside the cluster can access:

```text
payments:80
```

The Service directs traffic toward matching backend Pods.

Conceptually:

```text
Client
  ↓
payments:80
  ↓
Service
  ↓
Pod A:8080
Pod B:8080
Pod C:8080
```

ClusterIP is normally intended for internal cluster communication.

---

# Question 6: Explain `port`, `targetPort`, and `nodePort`.

## Strong interview answer

This distinction causes many real production issues.

Suppose:

```yaml
ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080
```

Think of it as:

```text
Service port
80
 ↓
Target Pod port
8080
```

With NodePort:

```text
NodeIP:30080
      ↓
Service
      ↓
Pod:8080
```

`port` is the port exposed by the Service.

`targetPort` is the destination port on the backend Pod.

`nodePort` is the port exposed on nodes when using NodePort behavior.

A mismatch between `targetPort` and the application's actual listening port is a common connectivity failure.

# Question 7: The Service exists, but requests receive `connection refused`. What would you check?

## Strong interview answer

First, I would determine whether the Service has backends.

```bash
kubectl get svc payments -n production
```

Then:

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=payments
```

I would inspect:

```bash
kubectl describe svc payments -n production
```

Then verify the application listener.

Suppose the Service uses:

```yaml
targetPort: 8080
```

but the application listens on:

```text
9000
```

The request reaches the Pod IP but targets the wrong port.

The path becomes:

```text
Service:80
    ↓
Pod:8080
    ↓
No application listening
```

I would therefore verify:

```text
Service port
targetPort
container configuration
actual application listener
```

# Question 8: A Service has no endpoints. What are the first things you check?

## Strong interview answer

I immediately check the Service selector and Pod labels.

```bash
kubectl get svc payments \
  -n production \
  -o yaml
```

Suppose:

```yaml
selector:
  app: payments
```

Then:

```bash
kubectl get pods \
  -n production \
  -l app=payments
```

If no Pods are returned, the selector may not match.

For example:

```text
Service:
app=payments

Pods:
app=payment
```

That one-character difference breaks the association.

I would also check Pod readiness and EndpointSlices.

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=payments
```

The troubleshooting chain is:

```text
Service
   ↓
Selector
   ↓
Pod labels
   ↓
Pod readiness
   ↓
EndpointSlice
```

---

# Question 9: Why are EndpointSlices important?

## Strong interview answer

EndpointSlices represent network endpoints associated with Services and are the modern scalable mechanism Kubernetes uses for tracking Service backends.

If a Service exists but traffic is not reaching Pods, inspecting its EndpointSlices helps determine whether Kubernetes has identified usable backend addresses.

For example:

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=payments
```

If I expect five ready backend Pods but find no usable endpoints, I investigate:

```text
Service selector
Pod labels
Pod readiness
Service configuration
```

This helps separate:

```text
"The Service object exists"
```

from:

```text
"The Service actually has backends."
```

# Question 10: The Pods are Running, but the Service has no ready endpoints. Why?

## Strong interview answer

Running does not mean Ready.

Suppose:

```text
payments-a   0/1   Running
payments-b   0/1   Running
payments-c   0/1   Running
```

The containers are running, but their readiness probes are failing.

I would inspect:

```bash
kubectl describe pod payments-a \
  -n production
```

Suppose:

```text
Readiness probe failed:
HTTP probe failed with statuscode: 503
```

The Service may have matching Pods, but those Pods are not currently ready to receive normal traffic.

This is why:

```text
Running
≠
Ready
```

matters at the networking layer too.

---

# Question 11: How does Kubernetes DNS work from an application developer's perspective?

## Strong interview answer

Kubernetes provides DNS-based service discovery.

Suppose there is a Service:

```text
payments
```

in namespace:

```text
production
```

A Pod in the same namespace can commonly use:

```text
payments
```

A more explicit name is:

```text
payments.production
```

The fully qualified service name follows the cluster DNS domain convention, commonly:

```text
payments.production.svc.cluster.local
```

The exact cluster domain can be customized.

Applications should normally use service names rather than Pod IP addresses.

---

# Question 12: A Pod can reach a Service by ClusterIP but not by Service name. What does that suggest?

## Strong interview answer

That strongly points toward DNS resolution.

Suppose:

```bash
curl http://10.96.45.20
```

works, but:

```bash
curl http://payments
```

fails.

The Service and backend path may be healthy.

I would test DNS:

```bash
nslookup payments
```

or:

```bash
getent hosts payments
```

from an appropriate Pod.

Then inspect:

```bash
cat /etc/resolv.conf
```

I would also check the cluster DNS components, commonly CoreDNS:

```bash
kubectl get pods -n kube-system
```

The evidence narrows the problem from:

```text
General network failure
```

to:

```text
Name resolution failure
```

---

# Question 13: What is CoreDNS?

## Strong interview answer

CoreDNS is commonly used as the DNS server for Kubernetes clusters.

It enables service discovery by resolving Kubernetes Service names.

Conceptually:

```text
Application
   ↓
payments.production.svc.cluster.local
   ↓
CoreDNS
   ↓
Service address
```

If CoreDNS is unhealthy, many applications can appear to have networking problems even though direct IP connectivity still works.

That can produce widespread symptoms because many services depend on DNS.

---

# Question 14: How would you troubleshoot Kubernetes DNS?

## Strong interview answer

I would test from inside the cluster.

First:

```bash
nslookup kubernetes.default
```

or use an approved DNS troubleshooting Pod if the application image lacks tools.

Then test the specific Service:

```bash
nslookup payments.production.svc.cluster.local
```

Inspect resolver configuration:

```bash
cat /etc/resolv.conf
```

Then check DNS components:

```bash
kubectl get pods \
  -n kube-system
```

Depending on labels and cluster setup:

```bash
kubectl logs \
  -n kube-system \
  -l k8s-app=kube-dns
```

I would also inspect the DNS Service itself.

The goal is to determine:

```text
Can the Pod reach DNS?
      ↓
Can DNS resolve Kubernetes names?
      ↓
Can it resolve the specific Service?
      ↓
Does the resolved Service actually work?
```

# Question 15: Why might `payments` resolve in one namespace but not another?

## Strong interview answer

Short names depend on namespace search behavior.

Suppose the Service is:

```text
payments
```

in:

```text
production
```

A Pod in `production` may use:

```text
payments
```

A Pod in `frontend` may need:

```text
payments.production
```

or the fully qualified name:

```text
payments.production.svc.cluster.local
```

So if an application works in one namespace but not another, I check whether it incorrectly assumes same-namespace DNS resolution.

---

# Question 16: What is a headless Service?

## Strong interview answer

A headless Service is typically created by setting:

```yaml
clusterIP: None
```

Instead of providing a normal virtual ClusterIP, DNS can return addresses associated with the Service's backing endpoints.

Headless Services are useful when clients need to discover individual backend instances rather than communicate through a normal Service virtual IP.

They are commonly associated with some StatefulSet and clustered application patterns.

---

# Question 17: What is a Kubernetes Ingress?

## Strong interview answer

Ingress provides HTTP and HTTPS routing rules for traffic entering the cluster.

A typical flow is:

```text
Internet
   ↓
External Load Balancer
   ↓
Ingress Controller
   ↓
Ingress Rule
   ↓
Service
   ↓
Pods
```

An Ingress resource defines routing intent.

An Ingress controller implements that routing.

Creating an Ingress resource without a functioning compatible controller does not magically create working traffic routing.

---

# Question 18: What is the difference between an Ingress resource and an Ingress controller?

## Strong interview answer

The Ingress resource defines rules.

For example:

```text
api.example.com
      ↓
api-service
```

The Ingress controller watches those resources and configures the actual traffic-handling infrastructure.

Examples of implementations can include NGINX-based controllers, cloud-provider integrations, and other ingress technologies.

So:

```text
Ingress resource
=
desired routing configuration
```

while:

```text
Ingress controller
=
component implementing that routing
```

---

# Question 19: The application works through the Service but fails through Ingress. Where do you focus?

## Strong interview answer

That tells me the backend Service path is probably functioning.

I focus on the layers added by Ingress.

```text
Client
   ↓
DNS
   ↓
Load Balancer
   ↓
Ingress Controller
   ↓
Ingress Rule
   ↓
Service
```

I would inspect:

```bash
kubectl get ingress -n production
```

Then:

```bash
kubectl describe ingress <name> \
  -n production
```

I would verify:

* Hostname
* Path
* Path type
* Backend Service name
* Backend Service port
* Ingress class
* Controller
* TLS configuration

This is a good example of using a successful lower-layer test to narrow the investigation.

# Question 20: An Ingress returns 404, but the application is healthy. What could be wrong?

## Strong interview answer

The 404 could come from the ingress layer rather than the application.

Possible causes include:

* Wrong host
* Wrong path
* Incorrect path matching
* Request reaching a default backend
* Wrong IngressClass
* Controller not recognizing the rule
* Application path rewrite mismatch

For example, the Ingress expects:

```text
/api
```

but the request is:

```text
/payment
```

or the host rule expects:

```text
api.example.com
```

while the request uses another hostname.

I would determine which component generated the 404 before changing the application.

---

# Question 21: An Ingress returns 502. What would you investigate?

## Strong interview answer

A 502 often indicates that the proxy or ingress layer could not successfully communicate with an upstream backend.

I would inspect:

```text
Ingress
   ↓
Service
   ↓
EndpointSlice
   ↓
Pod
   ↓
Application port
```

Check:

```bash
kubectl describe ingress <name> \
  -n production
```

```bash
kubectl describe svc <service> \
  -n production
```

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=<service>
```

Then verify the backend application port and protocol.

Possible issues include:

```text
Wrong Service port
Wrong targetPort
No ready endpoints
Backend process unavailable
HTTP/HTTPS mismatch
Application closing connection
```

# Question 22: An Ingress returns 503. What could that mean?

## Strong interview answer

One possibility is that there are no usable upstream backends.

For example:

```text
Ingress
   ↓
Service
   ↓
No ready endpoints
```

I would check:

```bash
kubectl get pods -n production
```

and:

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=<service>
```

But I would not assume every 503 has the same cause.

I would identify which layer returned it and inspect the specific ingress/controller implementation.

# Question 23: What is a NetworkPolicy?

## Strong interview answer

NetworkPolicy defines allowed network communication for selected Pods when supported and enforced by the cluster networking implementation.

It can control:

```text
Ingress
Traffic entering selected Pods

Egress
Traffic leaving selected Pods
```

For example:

```text
Frontend
   ↓ allowed
API

Frontend
   X blocked
Database

API
   ↓ allowed
Database
```

NetworkPolicy is useful for reducing unnecessary lateral communication.

---

# Question 24: Does creating a NetworkPolicy always enforce traffic restrictions?

## Strong interview answer

Not by itself in every environment.

The cluster networking implementation must support and enforce NetworkPolicy.

So if I create a policy and nothing changes, I would check whether the CNI/networking solution actually implements the required NetworkPolicy behavior.

Kubernetes defines the policy model, but the network implementation performs enforcement.

---

# Question 25: What is a default-deny NetworkPolicy?

## Strong interview answer

A default-deny policy establishes a restrictive baseline for selected traffic so communication must then be explicitly permitted.

Conceptually:

```text
Before:

Pod A → Pod B
Pod A → Pod C
Pod A → Pod D

After default deny:

Pod A ✕ Pod B
Pod A ✕ Pod C
Pod A ✕ Pod D

Then explicitly allow required paths.
```

This improves network isolation, but incomplete policies can break applications.

Before implementing default deny, I want a clear dependency map.

---

# Question 26: Security added default-deny egress and applications immediately started failing. What would you check first?

## Strong interview answer

I would identify which outbound dependencies the application requires.

For example:

```text
Application
 ├── DNS
 ├── PostgreSQL
 ├── Redis
 ├── Payment API
 └── Authentication service
```

Then compare those dependencies with the egress policy.

One commonly overlooked dependency is DNS.

If DNS is blocked:

```text
Application
   ↓
Cannot resolve database hostname
   ↓
Database connection fails
```

The application team may report:

```text
"Database is unavailable."
```

when the real issue is DNS egress.

---

# Question 27: How would you distinguish DNS failure from TCP connectivity failure?

## Strong interview answer

Test them separately.

First:

```bash
nslookup database.production.svc.cluster.local
```

If that fails, investigate DNS.

If resolution succeeds and returns an address, test the destination port.

Depending on available tools:

```bash
nc -vz database 5432
```

or use another approved connectivity test.

Then test the actual application protocol.

The troubleshooting sequence is:

```text
Name resolution
      ↓
IP connectivity
      ↓
TCP connection
      ↓
TLS if applicable
      ↓
Application protocol
      ↓
Authentication
```

A generic:

```text
"connection failed"
```

is not specific enough.

---

# Question 28: What is a CNI plugin?

## Strong interview answer

CNI stands for Container Network Interface.

In Kubernetes, CNI-compatible networking components are responsible for key parts of Pod networking, such as configuring network interfaces and connectivity.

Different Kubernetes environments use different networking implementations.

From a troubleshooting perspective, the important point is that Pod networking depends on more than Kubernetes objects.

If Pods cannot communicate across nodes, I may need to investigate the underlying CNI implementation and node networking.

---

# Question 29: Pods on the same node can communicate, but Pods on different nodes cannot. What does that suggest?

## Strong interview answer

That strongly suggests a cross-node networking issue.

The application itself becomes less likely because same-node communication works.

I would investigate:

* CNI health
* Node routes
* Encapsulation or routing configuration
* Host firewall rules
* Security groups or cloud firewall rules
* MTU problems
* Node network interfaces

The evidence is:

```text
Pod A → Pod B
same node
WORKS

Pod A → Pod C
different node
FAILS
```

That pattern is extremely valuable.

---

# Question 30: What is MTU, and why can it matter in Kubernetes?

## Strong interview answer

MTU is the maximum transmission unit, which controls the maximum packet size transmitted on a network link without fragmentation or other handling.

Kubernetes networking may introduce encapsulation overhead depending on the CNI.

Incorrect MTU configuration can create confusing symptoms where:

```text
Small requests work
Large requests fail
```

or connections behave intermittently.

This is not normally my first hypothesis for every network failure.

But if simple connectivity succeeds while larger transfers consistently fail, MTU becomes worth investigating.

---

# Question 31: A Pod can ping another system but the application cannot connect to port 443. Is the network healthy?

## Strong interview answer

Not necessarily.

Ping tests ICMP connectivity.

The application needs TCP port 443.

The fact that:

```text
ICMP works
```

does not prove:

```text
TCP 443 works
```

I would test the actual protocol and port.

For example:

```bash
curl -v https://service.example.com
```

This may reveal:

```text
DNS failure
TCP timeout
Connection refused
TLS failure
HTTP error
```

Each points to a different layer.

---

# Question 32: Explain connection refused versus connection timeout.

## Strong interview answer

`Connection refused` often means the destination was reachable, but nothing accepted the connection on the requested port, or something actively rejected it.

A timeout more commonly suggests that traffic or responses are being dropped or cannot complete the path.

For example:

```text
Connection refused
→ wrong port?
→ application not listening?
→ process down?
```

Whereas:

```text
Timeout
→ NetworkPolicy?
→ firewall?
→ routing?
→ unreachable destination?
→ severe network issue?
```

These are clues, not absolute proof.

I still verify with evidence.

---

# Question 33: What is the difference between ConfigMap and Secret?

## Strong interview answer

ConfigMaps store non-confidential configuration data.

Secrets are designed for sensitive data such as:

* Passwords
* API tokens
* Credentials
* Certificates or key material where appropriate

For example:

```text
ConfigMap
APP_ENV=production
LOG_LEVEL=info
FEATURE_X=true
```

and:

```text
Secret
DATABASE_PASSWORD
API_TOKEN
```

But Kubernetes Secret data should not automatically be treated as fully protected simply because the object type is called `Secret`.

Security also depends on RBAC, encryption at rest configuration, secret-management architecture, audit controls, and access practices.

---

# Question 34: Is Kubernetes Secret data encrypted just because it appears as Base64 in YAML?

## Strong interview answer

No.

Base64 encoding is not encryption.

For example:

```text
password
↓
Base64
↓
cGFzc3dvcmQ=
```

Anyone who obtains that encoded value can decode it.

For production clusters, I would consider:

* Encryption at rest
* RBAC
* Least privilege
* External secret-management solutions where appropriate
* Audit logging
* Rotation
* Avoiding accidental exposure in logs and CI/CD output

This is a common interview trap.

# Question 35: How can a Pod consume a ConfigMap?

## Strong interview answer

Common approaches include:

```text
Environment variables
```

or:

```text
Mounted files
```

For example:

```yaml
envFrom:
  - configMapRef:
      name: payments-config
```

Or configuration can be mounted into the filesystem.

The method matters during troubleshooting because updates behave differently.

---

# Question 36: A ConfigMap was updated, but the running application still has the old environment variable. Why?

## Strong interview answer

Environment variables are established when the container starts.

Updating the ConfigMap does not rewrite the environment of an already-running process.

For example:

```text
10:00
Pod starts
LOG_LEVEL=info

11:00
ConfigMap changed
LOG_LEVEL=debug

Existing process:
still LOG_LEVEL=info
```

A controlled Pod replacement or rollout may be required.

For example:

```bash
kubectl rollout restart deployment/payments \
  -n production
```

Then verify:

```bash
kubectl rollout status deployment/payments \
  -n production
```

---

# Question 37: What if the ConfigMap is mounted as a volume?

## Strong interview answer

Mounted ConfigMap data can be updated in the mounted filesystem, subject to Kubernetes behavior and timing.

However, that still does not guarantee the application automatically reloads the configuration.

The application may read the file only at startup.

So:

```text
ConfigMap updated
      ↓
Mounted file eventually updated
      ↓
Application still using cached configuration
```

is possible.

I always ask:

```text
How does Kubernetes deliver the configuration?
```

and:

```text
How does the application consume or reload it?
```

---

# Question 38: How can a Pod consume a Secret?

## Strong interview answer

Secrets can be exposed to workloads through mechanisms such as:

* Environment variables
* Mounted files
* Image pull configuration
* Other integrations depending on the platform

For example:

```yaml
env:
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: database-secret
        key: password
```

I would avoid displaying secret values during troubleshooting unless absolutely necessary and authorized.

# Question 39: The Secret exists, but the Pod says the Secret cannot be found. Why?

## Strong interview answer

I would immediately check the namespace.

Suppose:

```text
Secret:
database-secret
Namespace:
staging
```

but the Pod is:

```text
Namespace:
production
```

The production Pod cannot simply reference that staging Secret as though it existed locally.

Check:

```bash
kubectl get secret database-secret \
  -n production
```

Also verify the exact Secret name.

Typos and namespace mismatches are common deployment problems.

# Question 40: The Secret exists, but the Pod fails because a key is missing. How would you troubleshoot safely?

## Strong interview answer

Suppose the Deployment references:

```yaml
secretKeyRef:
  name: payments-secret
  key: database-password
```

I would verify the Secret's key names without casually printing secret values.

For example:

```bash
kubectl describe secret payments-secret \
  -n production
```

can provide metadata without directly exposing decoded secret contents.

I want to determine whether:

```text
Secret exists
but
expected key does not exist
```

This is different from the Secret itself being missing.

# Question 41: What is `CreateContainerConfigError`, and how can configuration cause it?

## Strong interview answer

It can occur when Kubernetes cannot create the container because required configuration cannot be resolved.

Examples:

```text
Missing Secret
Missing ConfigMap
Missing referenced key
Invalid container configuration
```

I would start with:

```bash
kubectl describe pod <pod-name> \
  -n production
```

The Events section often identifies the missing object.

For example:

```text
configmap "payments-config" not found
```

That is more useful than repeatedly restarting the Pod.

---

# Question 42: What are environment variables useful for in Kubernetes applications?

## Strong interview answer

Environment variables are commonly used to supply runtime configuration such as:

```text
APP_ENV
LOG_LEVEL
DATABASE_HOST
DATABASE_PORT
FEATURE_FLAG
```

They help separate application configuration from the container image.

A single immutable image can potentially run in:

```text
development
staging
production
```

with environment-specific configuration supplied externally.

Sensitive values should be handled through appropriate secret mechanisms rather than plain ConfigMaps.

---

# Question 43: Why should you avoid building environment-specific configuration directly into container images?

## Strong interview answer

Because it couples the artifact to one environment.

A better model is:

```text
One tested image
      +
Environment-specific configuration
      ↓
Different environments
```

For example:

```text
payments:v4.2.7
```

can be promoted from staging to production while production-specific configuration is supplied separately.

This improves traceability because the application artifact remains unchanged.

# Question 83: How can readiness probes protect Services from unhealthy backends?

# Question 84: Why is a readiness endpoint that always returns HTTP 200 dangerous?

## Strong interview answer

```text

```

but:

```text

→ 200 OK
```

The Pod remains Ready.

The Service keeps sending traffic.

Users continue receiving failures.

# Question 85: Should readiness always check every external dependency?

## Strong interview answer

Not necessarily.

If readiness fails whenever any downstream dependency has a brief problem, every application Pod might simultaneously become NotReady.

That can turn a dependency issue into a complete service outage.

For example:

```text

      ↓
Every Pod readiness fails
      ↓
Every Pod removed from traffic
      ↓
Entire application unavailable
```

Health endpoints need to distinguish:

```text

```

from:

```text
Is every dependency in the entire system perfect?
```

This requires application-specific design.

# Question 86: What is the danger of using liveness to test external dependencies?

## Strong interview answer

It can create restart storms.

Suppose every Pod's liveness probe checks the database.

The database has a temporary outage.

Then:

```text

      ↓
Liveness fails on every Pod
      ↓
Kubernetes restarts every application Pod
      ↓
Database recovers
      ↓
Applications all reconnect simultaneously
```

Now a database incident has triggered an application restart storm.

Liveness should generally answer whether restarting the local container is likely to help.

* Error rate
* Latency

I would also correlate network symptoms with application and node metrics.

Monitoring should follow the actual request path.

# Question 96: A production API suddenly cannot resolve any Service names. What would you do first?

## Strong interview answer

```text

One node?
All workloads?
Entire cluster?
```

Scope is one of the fastest ways to narrow an incident.

# Question 97: Why is determining blast radius important?

## Strong interview answer

Because the scope tells me which components are likely shared.

For example:

```text
One Pod fails
→ Pod-specific configuration?

All Pods in one Deployment fail

All Pods on one node fail
→ node/CNI?

All Pods in one namespace fail
→ namespace policy/configuration?

Entire cluster fails
→ shared cluster service?
```

Blast radius converts a vague incident into a smaller set of hypotheses.

# Question 100: Give me a complete troubleshooting answer if an interviewer says, "The frontend cannot reach the backend Service."

## Strong interview answer

I would not immediately assume the Service is broken.

First, I would establish the exact failure.

Suppose:

```text
Frontend:
frontend.production

Backend Service:
api.production

Expected:
http://api:8080
```

I would verify frontend and backend Pods:

```bash
kubectl get pods \
  -n production \
  -o wide
```

Then inspect the Service:

```bash
kubectl describe svc api \
  -n production
```

Verify:

```text
Selector
port
targetPort
```

Then inspect its endpoints:

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=api
```

If endpoints exist, test DNS from the frontend environment:

```text
nslookup api
```

If DNS resolves, test:

```text
curl api:<service-port>
```

If that fails, test one backend Pod directly.

Then inspect NetworkPolicies:

```bash
kubectl get networkpolicy \
  -n production
```

If the problem affects only frontend Pods on one node, I would investigate node/CNI networking.

If every source fails, I would look for shared Service or policy issues.

If direct Pod access works but Service access fails, I focus on the Service path.

If both Service and Pod access fail, I move lower into network policy, CNI, node, or application-listener troubleshooting.

My goal is to transform:

```text
Frontend cannot reach backend
```

into something precise such as:

```text
"The frontend resolves the API Service correctly and the Service has three ready endpoints. Direct connections to the backend Pods succeed, but connections through the Service time out only from frontend Pods. A NetworkPolicy introduced in the latest deployment selects the API Pods and allows ingress from `role=frontend`, but the frontend Deployment was recently relabeled `role=web`. The traffic is therefore no longer allowed by the policy. I would correct the label or policy according to the intended security model, deploy the change through the controlled configuration process, verify connectivity, and monitor error rates."
```

That is a production-quality troubleshooting answer.

# Production Scenario 1: The Service That Suddenly Had No Backends

The interviewer says:

> "A production deployment completed successfully. All new API Pods are Running. The Service exists, but users receive 503 errors."

Start with:

```bash
kubectl get pods \
  -n production
```

Suppose:

```text
api-a   1/1   Running
api-b   1/1   Running
api-c   1/1   Running
```

Then:

```bash
kubectl get endpointslices \
  -n production \
  -l kubernetes.io/service-name=api
```

No expected endpoints appear.

Inspect the Service:

```yaml
selector:
  app: api
  version: v3
```

Now inspect Pod labels:

```bash
kubectl get pods \
  -n production \
  --show-labels
```

The new Pods have:

```text
app=api,release=v3
```

not:

```text
version=v3
```

The Service selector no longer matches.

The incident path is:

```text
Deployment succeeds
      ↓
Pods Running
      ↓
Service selector mismatch
      ↓
No expected backends
      ↓
Ingress has no healthy upstream
      ↓
503
```

The fix is not restarting the Pods.

The Service and workload labels must be made consistent.

# Production Scenario 2: The NetworkPolicy That Broke DNS

The interviewer says:

> "Security introduced a default-deny egress policy. Minutes later, multiple services reported database connection failures."

Application logs show:

```text
could not resolve host:
postgres.production.svc.cluster.local
```

That wording matters.

This is not yet evidence of PostgreSQL being down.

Test DNS.

It fails.

The policy allows:

```text
API → PostgreSQL:5432
```

but does not allow the necessary DNS traffic.

The application cannot determine the PostgreSQL Service address.

The actual path is:

```text
Application
   ↓
DNS query
   X
blocked
   ↓
Database hostname unresolved
   ↓
Application reports database failure
```

The database itself was healthy.

The security policy broke service discovery.

# Production Scenario 3: Half the Requests Fail After a Configuration Update

The interviewer says:

> "A ConfigMap was changed at 14:00. After that, roughly half of requests began failing. All Pods are Ready."

There are six replicas.

Three were created before 14:00.

Three were restarted afterward.

The ConfigMap is consumed through environment variables.

Old Pods:

```text
API_ENDPOINT=https://old-api.internal
```

New Pods:

```text
API_ENDPOINT=https://new-api.internal
```

Now traffic is distributed across two configurations.

```text
Service
 ├── Pod A → old endpoint
 ├── Pod B → old endpoint
 ├── Pod C → old endpoint
 ├── Pod D → new endpoint
 ├── Pod E → new endpoint
 └── Pod F → new endpoint
```

If the old endpoint is no longer valid, failures appear intermittent.

The root cause is mixed runtime configuration.

The ConfigMap update alone did not update environment variables inside existing processes.

# Production Scenario 4: Service Works, Ingress Fails

The interviewer says:

> "Developers can access the application using its Service from another Pod, but external users receive 404."

That immediately narrows the scope.

```text
Pod
 ↓
Service
 ↓
Application

WORKS
```

So I focus above the Service.

Inspect:

```bash
kubectl describe ingress application \
  -n production
```

Suppose the rule is:

```text
Host:
api.example.com

Path:
/api
```

but external traffic is sent to:

```text
https://api.example.com/v1
```

and the configured path rules do not match that request as intended.

The ingress controller routes the request to its default handling path and returns 404.

The application never receives the request.

The lesson:

```text
HTTP response exists
≠
application generated response
```

Identify which layer produced the error.

# Production Scenario 6: The Secret Rotation Incident

The interviewer says:

> "Database credentials were rotated. Kubernetes Secret was updated. Existing application Pods continue failing authentication."

The Secret is injected through:

```yaml
env:
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: database-secret
        key: password
```

Existing processes retain the environment values they received at startup.

The Secret object changed.

The process environment did not.

The correct rollout process must account for:

```text
Database credential change
      ↓
Secret update
      ↓
Application Pod replacement
      ↓
New connection establishment
      ↓
Verification
```

Credential rotation is a coordinated distributed-system operation, not simply:

```text
kubectl update secret
```

# Production Scenario 9: The Readiness Probe That Caused a Total Outage

The interviewer says:

> "The team changed readiness so that every Pod checks an external payment provider. The provider had a five-minute outage. Your entire API disappeared from Service endpoints."

The sequence is:

```text
Payment provider unavailable
      ↓
Every readiness probe fails
      ↓
Every API Pod becomes NotReady
      ↓
Service has no ready backends
      ↓
Entire API unavailable
```

The external dependency already caused degraded functionality.

The health-check design amplified it into complete unavailability.

The team needs to reconsider what readiness means for this application.

A Pod should become NotReady when it cannot safely serve useful traffic, not necessarily whenever one optional or degradable downstream dependency has a temporary issue.
