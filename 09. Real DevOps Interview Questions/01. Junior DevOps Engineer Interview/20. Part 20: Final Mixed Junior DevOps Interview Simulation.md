# Part 20: Final Mixed Junior DevOps Interview Simulation

Part 20 is different from the previous parts.

Until now, the questions were grouped by subject. In a real interview, that structure usually disappears.

An interviewer may ask you about Linux, move directly to Kubernetes, give you an AWS outage, ask you to troubleshoot a failed CI/CD pipeline, then finish with a system-design scenario.

You do not know what comes next.

That is what this final simulation is designed to reproduce.

This interview combines:

* Linux
* Processes and services
* Networking
* DNS
* HTTP and HTTPS
* Git
* CI/CD
* Jenkins
* GitHub Actions
* Docker
* Kubernetes
* AWS
* Terraform
* Ansible
* Monitoring and logging
* Security and IAM
* Production incidents
* System design
* Troubleshooting methodology
* Behavioral and operational judgment

The goal is not to memorize 100 perfect answers.

The goal is to demonstrate that you can think like an engineer.

---

# Interview Scenario

Imagine you have reached the technical stage for a Junior DevOps Engineer position.

The interviewer tells you:

> "This interview will be scenario-based. I am less interested in definitions and more interested in how you investigate problems. Explain your reasoning as you work through each question."

That sentence matters.

A strong candidate does not simply say:

```text
Restart the service.
```

A stronger candidate says:

```text
First, I would determine whether the service
is actually the source of the failure.

I would check its status, logs, resource usage,
recent changes, dependencies, and network
connectivity before deciding whether restarting
it is appropriate.
```

The second answer demonstrates troubleshooting.

Let's begin.

# Round 1: Linux and Command-Line Troubleshooting

## Question 1: A developer says, "The Linux server is slow." What do you do?

### Strong interview answer

I would first clarify what "slow" means.

I would ask whether:

* SSH is slow.
* The application is slow.
* Commands are slow.
* Disk operations are slow.
* The problem affects all users.
* It started after a deployment or configuration change.

Then I would inspect the system.

```bash
uptime
top
free -h
df -h
df -i
ps aux --sort=-%cpu | head
ps aux --sort=-%mem | head
```

I would look for CPU saturation, memory pressure, swapping, disk exhaustion, inode exhaustion, or processes consuming unusual resources.

If I suspect disk I/O:

```bash
iostat -xz 1
```

If available, I might also use:

```bash
vmstat 1
```

I would check recent system messages:

```bash
journalctl -p err
dmesg
```

The important point is that I would not immediately restart the server.

"Server is slow" is a symptom, not a root cause.

---

# Question 2: `df -h` shows plenty of disk space, but applications cannot create new files. What could be wrong?

### Strong interview answer

I would check inode usage.

```bash
df -i
```

A filesystem can have available storage capacity while having no available inodes.

For example:

```text
Filesystem     Size    Used    Avail
/dev/xvda1      50G     25G      25G

Filesystem     Inodes   IUsed   IFree   IUse%
/dev/xvda1     500000  500000       0    100%
```

The disk is only 50 percent full by capacity, but no new files can be created because the filesystem has exhausted its inodes.

I would then identify directories containing unusually large numbers of files.

I would not blindly delete files. I would determine what generated them and whether they are safe to remove.

---

# Question 3: A process is consuming 100 percent CPU. Would you kill it?

### Strong interview answer

Not immediately.

First I would identify it.

```bash
ps aux --sort=-%cpu | head
```

or:

```bash
top
```

Then I would determine:

* What application owns the process?
* Is the CPU usage expected?
* Is traffic unusually high?
* Did something recently change?
* Is the process stuck?
* Are other processes affected?

I could inspect:

```bash
ps -fp <PID>
```

Depending on the environment, I might inspect open files:

```bash
lsof -p <PID>
```

If the process genuinely needs termination, I would prefer graceful termination first:

```bash
kill <PID>
```

I would use:

```bash
kill -9 <PID>
```

only when necessary because SIGKILL does not allow the process to perform normal cleanup.

# Round 2: Services, Logs, and Permissions

## Question 4: NGINX is not starting after a configuration change. How would you troubleshoot it?

### Strong interview answer

First:

```bash
systemctl status nginx
```

Then:

```bash
journalctl -u nginx
```

Before attempting repeated restarts, I would validate the NGINX configuration:

```bash
nginx -t
```

If it reports something like:

```text
syntax error in /etc/nginx/nginx.conf
```

I would inspect the relevant configuration.

I would also consider whether another process is already using the required port:

```bash
ss -lntp
```

or:

```bash
lsof -i :80
lsof -i :443
```

The investigation would therefore be:

```text
Service status
      |
      v
Logs
      |
      v
Configuration validation
      |
      v
Port conflicts
      |
      v
Permissions / dependencies
      |
      v
Fix
      |
      v
Restart
      |
      v
Verify
```

# Question 5: An application works when you run it manually but fails when started by systemd. Why?

### Strong interview answer

I would compare the environments.

When I start the application manually, it may inherit my:

```text
PATH
Environment variables
Working directory
User permissions
Shell configuration
Credentials
```

A systemd service may run as a different user with a different environment.

I would inspect:

```bash
systemctl cat myapp
```

and:

```bash
journalctl -u myapp
```

I would specifically check:

```text
User=
Group=
WorkingDirectory=
Environment=
EnvironmentFile=
ExecStart=
```

A common mistake is assuming a command that works in an interactive shell must behave identically under systemd.

# Round 3: Networking

## Question 6: You can ping a server, but the application on port 8080 is unreachable. What does that tell you?

### Strong interview answer

Ping success proves some IP connectivity using ICMP.

It does not prove that TCP port 8080 is reachable or that the application is healthy.

I would test the application port:

```bash
curl -v http://server:8080
```

or:

```bash
nc -vz server 8080
```

On the destination:

```bash
ss -lntp | grep 8080
```

I would check whether the application is:

* Running.
* Listening on port 8080.
* Listening on the expected interface.
* Blocked by a host firewall.
* Blocked by a security group.
* Blocked by a network ACL.
* Failing internally.

For example:

```text
127.0.0.1:8080
```

would mean the service is only listening on localhost.

Another machine would not be able to connect directly to that listener.

---

# Question 7: What is the difference between `127.0.0.1:8080` and `0.0.0.0:8080`?

### Strong interview answer

`127.0.0.1:8080` means the application is bound to the loopback interface.

It can normally only be reached locally.

```text
Remote Client
     X
     |
127.0.0.1:8080
```

`0.0.0.0:8080` generally means the application listens on all available IPv4 interfaces.

```text
Remote Client
      |
      v
Server Interface
      |
      v
Application :8080
```

That does not automatically mean the service is publicly reachable. Firewalls, routing, security groups, and other controls still matter.

# Round 4: DNS, HTTP, and HTTPS

## Question 8: Users say `app.example.com` is unavailable, but accessing the server by IP works. Where do you investigate?

### Strong interview answer

That immediately makes DNS one of my primary suspects.

I would run:

```bash
dig app.example.com
```

and possibly:

```bash
dig +trace app.example.com
```

I would check:

* Does the hostname resolve?
* Does it resolve to the correct destination?
* Was the DNS record recently changed?
* Is an old answer cached?
* What is the TTL?
* Are the authoritative name servers correct?

I might also use:

```bash
nslookup app.example.com
```

If the IP works but the hostname does not, I would investigate DNS before changing application infrastructure.

---

# Question 9: Users receive HTTP 502 from a load balancer. What does that suggest?

### Strong interview answer

A 502 generally suggests the proxy or load balancer had a problem receiving a valid response from an upstream backend.

I would investigate the complete path:

```text
Client
  |
  v
Load Balancer
  |
  v
Target
  |
  v
Application
```

I would check:

* Target health.
* Application process.
* Application port.
* Listener and target configuration.
* Security rules.
* Application logs.
* Upstream response behavior.
* Recent deployments.

I would not assume the load balancer itself is broken simply because it returned the error.

---

# Question 10: HTTPS suddenly stops working, but HTTP still works. What would you check?

### Strong interview answer

I would investigate the TLS layer.

I would check:

* Certificate expiration.
* Certificate hostname.
* Certificate chain.
* TLS listener configuration.
* Port 443.
* Recent certificate changes.

For example:

```bash
openssl s_client -connect app.example.com:443 \
-servername app.example.com
```

I could also use:

```bash
curl -Iv https://app.example.com
```

If HTTP works but HTTPS fails, that narrows the investigation significantly.

# Round 5: Git

## Question 11: A developer accidentally committed a secret to Git. They deleted the line in the next commit. Is the secret safe?

### Strong interview answer

No.

The secret may still exist in Git history.

More importantly, I would treat the credential as compromised.

My first priority would be:

```text
Revoke or rotate the secret
```

Then I would address repository history if required.

I would also investigate how it happened and prevent recurrence using mechanisms such as:

* Secret scanning.
* `.gitignore` where appropriate.
* Pre-commit checks.
* CI secret scanning.
* External secrets management.
* Developer education.

Removing the secret from the latest file does not invalidate a credential that may already have been exposed.

---

# Question 12: You run `git pull` and get a merge conflict. What do you do?

### Strong interview answer

I would inspect:

```bash
git status
```

Then identify the conflicted files.

Inside a conflict, Git may show:

```text
<<<<<<< HEAD
current branch
=======
incoming branch
>>>>>>> feature
```

I would understand both changes rather than blindly choosing one side.

After resolving:

```bash
git add <file>
```

Then complete the merge or rebase depending on the workflow.

The important point is that a merge conflict requires understanding the intended final state.

# Round 6: CI/CD

## Question 13: A pipeline worked yesterday. Today it fails. The application code did not change. What could have changed?

### Strong interview answer

Many things outside application code can change.

I would investigate:

```text
Pipeline configuration
Runner/agent
Base container image
Dependencies
Package repositories
Credentials
Certificates
Network access
Environment variables
Cloud permissions
External services
Tool versions
```

For example:

```dockerfile
FROM node:latest
```

can introduce an unexpected runtime change even when the repository code is unchanged.

Similarly, an unpinned dependency could change.

I would compare the last successful execution with the first failing execution.

---

# Question 14: The build succeeds, but deployment fails. Where do you look?

### Strong interview answer

I would separate build from deployment.

A successful build proves the artifact was created. It does not prove the deployment environment can accept or run it.

I would investigate:

```text
Artifact availability
Registry access
Deployment credentials
Environment configuration
Cloud permissions
Kubernetes access
Manifest validity
Resource capacity
Network connectivity
Deployment logs
```

The failure boundary matters.

```text
Source
  |
  v
Build        ✓
  |
  v
Test         ✓
  |
  v
Artifact     ✓
  |
  v
Deployment  X
```

I would focus on the deployment stage rather than rebuilding repeatedly.

---

# Question 15: What should happen if production deployment health checks start failing?

### Strong interview answer

I would want the deployment process to stop further rollout.

For example:

```text
Deploy 10%
    |
    v
Health Check
    |
    X
Error rate increases
    |
    v
STOP
    |
    v
Rollback
```

Depending on the deployment strategy, automated rollback may be appropriate.

I would preserve logs and deployment information for investigation.

A pipeline should not continue deploying an unhealthy release simply because earlier pipeline stages passed.

# Round 7: Jenkins and GitHub Actions

## Question 16: A Jenkins job is stuck waiting for an executor. What would you investigate?

### Strong interview answer

I would check whether suitable agents are available.

Possible causes include:

* All executors are busy.
* Agent is offline.
* Label requirements do not match available agents.
* Agent provisioning failed.
* Queue is overloaded.

If the job requires:

```groovy
agent {
    label 'docker'
}
```

but no online agent has the `docker` label, it can remain queued.

I would inspect Jenkins queue and node status before assuming there is a problem with the pipeline code.

---

# Question 17: A GitHub Actions workflow works on `main` but never runs on feature branches. Why?

### Strong interview answer

I would inspect its trigger configuration.

For example:

```yaml
on:
  push:
    branches:
      - main
```

That configuration only triggers for pushes to `main`.

If feature branches should also trigger it, the event configuration needs to reflect that requirement.

This is an example where the pipeline is not necessarily broken. It may be behaving exactly as configured.

# Round 8: Docker

## Question 18: A Docker container immediately exits after starting. How do you troubleshoot it?

### Strong interview answer

First:

```bash
docker ps -a
```

Then:

```bash
docker logs <container>
```

I would inspect:

```bash
docker inspect <container>
```

I would determine:

* Exit code.
* Entrypoint.
* Command.
* Environment variables.
* Mounted files.
* Resource limits.
* Application errors.

A container normally exists while its main process is running.

If PID 1 exits, the container stops.

---

# Question 19: The application works inside the container but cannot be reached from the host. What do you check?

### Strong interview answer

I would check:

```bash
docker ps
```

and verify port publishing.

For example:

```bash
docker run -p 8080:80 nginx
```

means:

```text
Host :8080
    |
    v
Container :80
```

I would also check what address the application is listening on inside the container.

Then I would inspect host firewall rules and the wider network path if necessary.

---

# Question 20: Why should you avoid huge Docker images?

### Strong interview answer

Large images can cause:

* Slower builds.
* Slower registry transfers.
* Slower deployments.
* More storage consumption.
* Larger potential attack surface.

I would use techniques such as:

```dockerfile
FROM node:22 AS builder
```

followed by a smaller runtime stage where appropriate.

I would also avoid unnecessary packages and files.

But I would not sacrifice maintainability or required debugging capabilities solely to make the image as tiny as possible.

# Round 9: Kubernetes

## Question 21: A Pod shows `CrashLoopBackOff`. What do you do?

### Strong interview answer

I would begin with:

```bash
kubectl get pods
```

Then:

```bash
kubectl describe pod <pod>
```

and:

```bash
kubectl logs <pod>
```

If the container restarted:

```bash
kubectl logs <pod> --previous
```

I would investigate:

* Application startup failure.
* Missing environment variables.
* Missing Secret or ConfigMap.
* Incorrect command.
* Permission failure.
* Failed dependency.
* Liveness probe.
* Resource limits.
* OOMKilled.
* Volume problems.

`CrashLoopBackOff` describes Kubernetes repeatedly attempting to restart a failing container. It does not tell me the root cause.

---

# Question 22: A Pod is `Running`, but users cannot access the application. Is the Pod healthy?

### Strong interview answer

Not necessarily.

`Running` tells me the Pod has running containers. It does not prove the application is usable.

I would check:

```bash
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
```

Then inspect:

```text
Readiness
Service
Endpoints
TargetPort
Ingress
NetworkPolicy
Application listener
```

For example:

```bash
kubectl get svc
kubectl get endpoints
```

A Running Pod that is not Ready may not receive Service traffic.

---

# Question 23: A Kubernetes Service exists but has no endpoints. What does that suggest?

### Strong interview answer

I would suspect that the Service selector does not match any Ready Pods.

I would inspect:

```bash
kubectl describe svc <service>
kubectl get pods --show-labels
kubectl get endpoints <service>
```

For example:

Service:

```yaml
selector:
  app: payment
```

Pod:

```yaml
labels:
  app: payments
```

Those do not match.

The Service exists, but Kubernetes has no matching backend Pods.

---

# Question 24: A Pod is `Pending`. What are some likely causes?

### Strong interview answer

I would run:

```bash
kubectl describe pod <pod>
```

and inspect scheduler events.

Possible causes include:

* Insufficient CPU.
* Insufficient memory.
* Node selector mismatch.
* Taints and tolerations.
* Affinity rules.
* Persistent volume problems.
* Scheduling constraints.

For example:

```text
0/3 nodes are available:
3 Insufficient memory
```

That immediately gives me a strong direction.

# Round 10: AWS

## Question 25: An EC2 instance is running but you cannot SSH into it. Walk me through your investigation.

### Strong interview answer

I would check the path layer by layer.

```text
My machine
    |
    v
Internet
    |
    v
Public IP / Bastion / SSM
    |
    v
Route
    |
    v
Security Group
    |
    v
Network ACL
    |
    v
EC2
    |
    v
sshd
```

I would verify:

* Correct IP or hostname.
* Whether direct SSH is actually intended.
* Route table.
* Internet Gateway where applicable.
* Security group inbound rule.
* Network ACL.
* Instance health.
* SSH service.
* Correct username.
* Correct key.
* Host firewall.
* Disk availability.

I would not immediately add:

```text
0.0.0.0/0 -> TCP 22
```

just to test connectivity, because that unnecessarily increases exposure.

# Question 26: An application in a private subnet cannot download packages from the internet. Why?

### Strong interview answer

I would inspect its outbound path.

A common IPv4 architecture is:

```text
Private EC2
    |
    v
Private Route Table
    |
    v
NAT Gateway
    |
    v
Internet Gateway
    |
    v
Internet
```

I would check:

* Private route table.
* NAT Gateway state.
* NAT Gateway placement.
* Public subnet route.
* Internet Gateway.
* Security rules.
* Network ACLs.
* DNS.

If it only needs access to certain AWS services, I would also consider whether a VPC endpoint is a better architecture.

---

# Question 27: Your ALB reports all targets as unhealthy, but the EC2 instances are running. What do you investigate?

### Strong interview answer

Instance state and application health are different things.

I would inspect:

* Health-check protocol.
* Health-check port.
* Health-check path.
* Expected response.
* Security groups.
* Application listener.
* Application logs.

For example:

```text
Health check:
GET /health

Application:
404 /health
```

The server is running, but the load balancer correctly marks it unhealthy.

---

# Question 28: An IAM user receives `AccessDenied`. What do you check?

### Strong interview answer

I would identify:

```text
Who?
Tried what action?
Against which resource?
Under which policy context?
```

Then inspect:

* Identity policies.
* Resource policies.
* Explicit denies.
* Permission boundaries.
* Service Control Policies where applicable.
* Role assumptions.
* Resource ARN.
* Conditions.

I would not automatically attach AdministratorAccess.

An `AccessDenied` error should be investigated and the required permission granted as narrowly as practical.

# Round 11: Terraform

## Question 29: Terraform wants to recreate a production resource unexpectedly. What do you do?

### Strong interview answer

I stop before applying.

I would inspect:

```bash
terraform plan
```

carefully.

I would determine why replacement is required.

Possible reasons include:

* Immutable property changed.
* Resource renamed.
* State mismatch.
* Provider behavior.
* Configuration changed.
* Resource moved outside Terraform.
* Incorrect environment or workspace.

For production, unexpected replacement deserves investigation before execution.

---

# Question 30: Someone manually changed an AWS resource that Terraform manages. What problem does this create?

### Strong interview answer

It creates configuration drift.

Terraform configuration says one thing while the real infrastructure says another.

I would use:

```bash
terraform plan
```

to understand the difference.

Then decide whether:

```text
The manual change should be reverted

or

The Terraform configuration should be updated
```

I would not blindly run `terraform apply` without understanding what it intends to change.

---

# Question 31: Two engineers run Terraform against the same infrastructure simultaneously. What could happen?

### Strong interview answer

Concurrent operations can create conflicting changes or state problems.

For team environments, I would use an appropriate remote backend and state-locking mechanism.

Conceptually:

```text
Engineer A ----\
                \
                 Remote State
                /
Engineer B ----/
```

The broader lesson is that Terraform state is shared operational data and must be managed carefully.

# Round 12: Ansible

## Question 32: An Ansible playbook works on nine servers but fails on one. What would you investigate?

### Strong interview answer

Because most servers succeed, I would first compare the failing host with the working hosts.

I would investigate:

* Connectivity.
* SSH configuration.
* User.
* Privilege escalation.
* OS distribution/version.
* Python availability.
* Package repositories.
* Disk space.
* Host variables.
* Group variables.
* Existing configuration.

I might test:

```bash
ansible <host> -m ping
```

The fact that only one server fails is useful evidence.

---

# Question 33: What does idempotency mean in Ansible?

### Strong interview answer

An idempotent task can run repeatedly without unnecessarily changing a system that is already in the desired state.

For example:

```yaml
- name: Ensure nginx is installed
  package:
    name: nginx
    state: present
```

If NGINX is already installed, running the task again should not reinstall it unnecessarily.

Configuration management should describe desired state rather than repeatedly forcing arbitrary changes.

# Round 13: Monitoring and Logging

## Question 34: CPU, memory, and disk all look normal, but customers say checkout is failing. What now?

### Strong interview answer

Infrastructure metrics are not enough.

I would check application and business-level signals.

For example:

```text
HTTP error rate
Request latency
Checkout success rate
Payment failures
Database errors
External payment API
Queue backlog
Recent deployment
```

I would inspect logs and traces for failing checkout requests.

This is why monitoring should include the service from the customer's perspective.

```text
Healthy infrastructure
does not necessarily mean
healthy application.
```

---

# Question 35: What would you alert on for a web application?

### Strong interview answer

I would prioritize symptoms that indicate customer impact or imminent failure.

Examples:

* Elevated error rate.
* High latency.
* Availability drop.
* Critical endpoint failures.
* Queue backlog.
* Database connection exhaustion.
* Disk approaching critical levels.
* Certificate expiration.
* Failed production deployments.

I would avoid creating alerts for every metric merely because the metric exists.

An alert should generally require meaningful action.

---

# Question 36: Your monitoring system generates 500 alerts every night and nobody reads them anymore. What is the problem?

### Strong interview answer

That is alert fatigue.

If engineers receive too many noisy or non-actionable alerts, important alerts can be ignored.

I would review:

* Alert thresholds.
* Duplicate alerts.
* Routing.
* Severity.
* Ownership.
* Whether alerts are actionable.
* Whether symptoms should be grouped.

The goal is not maximum alert volume.

The goal is reliable detection of conditions that require action.

---

# Round 14: Security and Secrets

## Question 37: You find AWS access keys hardcoded inside an application repository. What do you do first?

### Strong interview answer

I treat the credentials as potentially compromised.

First:

```text
Disable or rotate the credentials.
```

Then:

* Determine exposure.
* Review relevant audit logs.
* Remove the credentials from the application.
* Remove them from repository history where required.
* Move the workload to an appropriate IAM role or secrets mechanism.
* Add preventive secret scanning.

The first response should not be:

```text
Delete the Git line.
```

because the exposed credential may still work.

---

# Question 38: Why are IAM roles preferable to long-lived AWS access keys for workloads?

### Strong interview answer

Roles can provide temporary credentials that are automatically managed.

For example:

```text
EC2 / Pod / Lambda
        |
        v
     IAM Role
        |
        v
Temporary credentials
```

This avoids distributing long-lived static credentials to applications.

It also supports better credential lifecycle management and least-privilege design.

---

# Question 39: A developer asks you to give an application AdministratorAccess because permissions are difficult to configure. What would you do?

### Strong interview answer

I would identify what the application actually needs.

For example:

```text
Application needs:

s3:GetObject
s3:PutObject

on:

specific application bucket
```

Then I would create permissions around those requirements rather than granting broad administrative access.

Convenience should not automatically override least privilege.

---

# Round 15: Production Incident

## Question 40: It is 2:00 a.m. Production is down. What is your first priority?

### Strong interview answer

My first priority is restoring service safely and reducing customer impact.

I would quickly establish:

```text
What is broken?
Who is affected?
When did it start?
What changed?
What is the blast radius?
```

Then I would use the fastest safe mitigation.

That could include:

* Rollback.
* Failover.
* Traffic shift.
* Disabling a failing feature.
* Scaling a constrained resource.

Deep root-cause analysis can continue after service is stabilized.

During an active incident:

```text
Stabilize
   |
   v
Recover
   |
   v
Verify
   |
   v
Investigate deeply
   |
   v
Prevent recurrence
```

---

# Question 41: A deployment happened five minutes before the outage. Do you immediately conclude the deployment caused it?

### Strong interview answer

No.

The timing makes the deployment a strong hypothesis, but correlation is not proof.

I would compare:

```text
Deployment timestamp
Error-rate timestamp
Logs
Metrics
Configuration changes
Dependency health
```

If rollback is low-risk and customer impact is severe, rolling back may still be a sensible mitigation before complete proof.

But the incident analysis should remain evidence-based.

---

# Question 42: Production is down and you believe restarting the database will fix it. Do you restart it?

### Strong interview answer

Not casually.

A production database restart can have significant impact.

I would determine:

* What evidence suggests a restart is necessary?
* Is there an approved procedure?
* What connections or transactions will be affected?
* Is there a safer mitigation?
* Is failover available?
* Do I have authorization?
* Is backup/recovery status known?

Production troubleshooting requires technical judgment and change discipline.

---

# Question 43: The incident is resolved. Are you finished?

### Strong interview answer

No.

After recovery I would:

* Confirm stability.
* Monitor for recurrence.
* Document the timeline.
* Identify root cause.
* Identify contributing factors.
* Review detection.
* Review response.
* Create corrective actions.

A useful post-incident analysis should ask:

```text
Why did it happen?

Why did the system allow it?

Why didn't we detect it sooner?

Why was recovery difficult?

What prevents recurrence?
```

The purpose is learning and improving the system.

# Round 16: Mixed Troubleshooting Challenge

## Question 44: Users receive intermittent 503 errors from an application running on Kubernetes behind a load balancer. How do you approach it?

### Strong interview answer

Because the failure is intermittent, I would look for differences between requests.

Potential causes include:

* One unhealthy Pod.
* Readiness problems.
* Pod restarts.
* Resource saturation.
* One unhealthy node.
* Load-balancer target issue.
* Deployment in progress.
* Dependency failures.

I would inspect:

```bash
kubectl get pods -o wide
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl get endpoints
```

I would correlate timestamps between:

```text
503 errors
Pod restarts
Deployments
CPU/memory
Readiness failures
Load-balancer health
Application logs
```

Intermittent failures often mean only part of the request path is unhealthy.

# Question 45: Only one of five Pods returns errors. What does that tell you?

### Strong interview answer

That strongly suggests the problem is specific to that Pod, its node, or something unique about its configuration or state.

I would compare the unhealthy Pod with healthy replicas.

```text
Image
Environment variables
Node
Configuration
Secrets
Mounted volumes
Resource usage
Logs
Startup time
```

If all five Pods were created from the same Deployment, I would also ask why one behaves differently.

That difference may reveal the root cause.

# Question 46: The bad Pod disappears before you can inspect it. What should your platform have captured?

### Strong interview answer

This is where observability matters.

Even ephemeral workloads should leave useful evidence outside themselves.

I would want:

```text
Centralized logs
Metrics
Kubernetes events
Deployment history
Audit logs where appropriate
Traces
Container termination information
```

If troubleshooting evidence disappears with the Pod, the observability architecture is incomplete.

# Question 48: Why not put everything in one Availability Zone to save money?

### Strong interview answer

That may reduce some cost or complexity, but it creates a larger shared failure domain.

If the business requires high availability, distributing critical components across Availability Zones reduces the risk that one AZ failure takes down the entire application.

But I would connect the design to actual requirements.

Not every internal development environment needs the same resilience as a revenue-critical production system.

Architecture involves trade-offs.

# Question 49: Your application servers Auto Scale, but the database does not. What problem could occur?

### Strong interview answer

For example:

```text

Traffic increases

       |
       v
Same Database
```

Now the database may experience:

```text

High CPU
Lock contention
Slow queries
High latency
```

Horizontal scaling of one layer does not guarantee scalability of the complete system.

# Question 72: A senior engineer suggests a fix you believe is dangerous. What do you do?

### Strong interview answer

I would explain my concern respectfully and use evidence.

For example:

> "I'm concerned that restarting all database nodes simultaneously could increase the outage. Could we confirm the failover behavior and consider restarting one component at a time?"

Seniority does not remove the need for safe production changes.

But I would challenge the decision professionally, not competitively.

# Question 73: You make a production mistake. What do you do?

### Strong interview answer

I would report it quickly rather than hiding it.

I would explain:

```text
What I changed
When I changed it
What I observed
What systems may be affected
```

Then I would help restore service.

Afterward, I would participate in understanding why the system allowed the mistake and how to reduce the chance of recurrence.

Hiding production mistakes increases incident duration and risk.

# Question 76: The Production Application Is Down. Investigate It.

You receive this alert:

```text
CRITICAL

checkout-api

Latency p95: 8.4 seconds
```

The architecture is:

```text

  |
  v

  |
  v

  |
  v
Kubernetes Service
  |
  v
checkout-api Pods
  |
  +------> Redis
  |
  +------> RDS
  |
  +------> Payment API
```

Ten minutes earlier, version `v2.7.0` was deployed.

The interviewer asks:

> "Walk me through exactly what you would do."

---

## Step 1: Establish impact

I would confirm:

```text
When did the problem begin?

Does it affect every user?

Which endpoints fail?

Is checkout completely unavailable?

Did the failure begin immediately after v2.7.0?
```

I would compare the deployment timestamp with the metrics.

---

## Step 2: Check the external symptom

I could test:

```bash
curl -v https://example.com/checkout
```

I want to confirm what customers actually receive.

---

## Step 3: Check load-balancer health

I would determine whether:

```text
All targets unhealthy?

Some targets unhealthy?

Targets healthy but returning application errors?
```

That distinguishes load-balancer routing problems from application-level failures.

---

## Step 4: Check Kubernetes workloads

```bash
kubectl get pods
```

Suppose I see:

```text
checkout-api-1    1/1 Running
checkout-api-2    0/1 Running
checkout-api-3    1/1 Running
checkout-api-4    0/1 CrashLoopBackOff
```

Now I have useful evidence.

---

## Step 5: Inspect failing Pods

```bash

```

Then:

```bash
kubectl logs checkout-api-4
```

```bash

```

Suppose the logs show:

```text
ERROR:
Database connection pool exhausted
```

Now I investigate database connectivity and connection usage.

---

## Step 6: Check application metrics

Suppose:

```text
DB connections before deployment:
180

DB connections after deployment:
950

DB maximum:
1000
```

That is a major clue.

---

## Step 7: Compare v2.7.0 with the previous release

Suppose the previous version used:

```text
maxPoolSize=20
```

The new version uses:

```text
maxPoolSize=200
```

There are multiple replicas.

Potential database connections increased dramatically.

Now I have a strong hypothesis.

---

# Question 77: What do you do next?

### Strong interview answer

Because production is severely degraded and the issue began immediately after a deployment that appears to have introduced dangerous database connection behavior, I would prioritize mitigation.

If rollback is safe:

```text
v2.7.0
   |
   X
Rollback
   |
   v
v2.6.4
```

Then monitor:

```text

Latency
Pod readiness
Database connections
Checkout success
```

# Question 78: After rollback, error rate falls from 58 percent to 0.2 percent. Is the incident over?

### Strong interview answer

Service is recovering, but I would continue monitoring.

I would verify:

* All Pods healthy.
* Database connections normalized.
* Checkout transactions succeeding.
* Queue backlogs recovered if applicable.
* No secondary problems remain.

Then the incident can move from active mitigation to post-incident analysis.

# Question 79: What was the root cause?

### Strong interview answer

Based on the evidence:

```text
v2.7.0 increased the database
connection pool configuration
from 20 to 200 per application instance.
```

With multiple replicas, the potential connection demand approached or exceeded database capacity.

That caused:

```text
Connection exhaustion
        |
        v
Application latency
        |
        v
Request failures
        |
        v
Pod instability
        |
        v
HTTP 5xx
```

But I would distinguish root cause from contributing factors.

---

# Question 80: What were the contributing factors?

### Strong interview answer

Possible contributing factors include:

* No validation of connection-pool configuration.
* No load test before production.
* No deployment guardrail for database connections.
* Rollout reached too many replicas before health degradation stopped it.
* Alerting may have detected the problem only after significant customer impact.
* Database capacity limits may not have been considered during application configuration.

This matters because simply saying:

```text
Developer configured pool incorrectly
```

does not improve the engineering system.

---

# Question 81: How would you prevent recurrence?

### Strong interview answer

I would consider several controls.

### Configuration

Validate sensible connection-pool limits.

### Testing

Test connection behavior under realistic replica counts.

### Deployment

Use gradual rollout.

```text
5%
 |
 v
Observe
 |
 v
25%
 |
 v
Observe
 |
 v
100%
```

### Monitoring

Monitor:

```text
DB active connections
DB connection utilization
Connection errors
Application latency
HTTP 5xx
```

### Alerting

Alert before database connection capacity reaches a critical level.

### Architecture

Evaluate connection pooling or proxy mechanisms where appropriate.

The goal is not only to fix `v2.7.0`.

The goal is to make this class of failure harder to introduce again.
