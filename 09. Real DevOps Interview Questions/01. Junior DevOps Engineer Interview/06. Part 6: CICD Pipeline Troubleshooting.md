# Part 6: CI/CD Pipeline Troubleshooting

CI/CD is one of the areas where junior DevOps candidates are often expected to move beyond definitions.

An interviewer may ask what continuous integration means, but the stronger questions usually come from realistic situations:

* The pipeline worked yesterday but fails today.
* The build passes locally but fails in CI.
* A deployment stage is stuck.
* A pipeline cannot access a secret.
* An artifact is missing from the deployment job.
* A runner is offline.
* Tests pass sometimes and fail sometimes.
* A job runs on the wrong branch.
* A deployment succeeds, but production is broken.
* A pipeline keeps using an old image.
* A rollback fails.
* A job times out after 30 minutes.
* One stage never runs.
* The pipeline reports permission denied.
* The deployment uses the wrong environment variables.

The important skill is not knowing one CI/CD platform.

The important skill is understanding how a pipeline executes and how to isolate where it failed.

A simplified pipeline may look like this:

```text
Developer Push
      ↓
Source Repository
      ↓
Pipeline Trigger
      ↓
Runner / Agent
      ↓
Checkout Code
      ↓
Install Dependencies
      ↓
Build
      ↓
Test
      ↓
Security Scan
      ↓
Package Artifact
      ↓
Deploy
      ↓
Verify
      ↓
Production
```

Each stage introduces a different class of failure.

A junior DevOps engineer should learn to answer:

```text
Which stage failed?

What changed?

Is the problem code, environment, credentials, infrastructure, or pipeline configuration?

Can I reproduce it?

What evidence does the job log provide?

Can I safely retry?

Should I roll back?
```

---

# Question 1: A CI/CD pipeline that worked yesterday is failing today. How would you troubleshoot it?

## What the interviewer is testing

The interviewer wants to see whether you start with evidence rather than immediately editing pipeline configuration.

## Strong interview answer

I would first identify exactly where the pipeline fails.

I would check:

* Which stage failed?
* Which job failed?
* What is the exact error message?
* Did the pipeline configuration change?
* Did application code change?
* Did dependencies change?
* Did the runner change?
* Did credentials expire?
* Did an external service become unavailable?

I would compare the last successful pipeline with the first failing pipeline.

For example:

```text
Last successful pipeline
Commit: a17bc82
Time: 09:10

First failing pipeline
Commit: b93dd41
Time: 10:05
```

Then I would inspect:

```bash
git diff a17bc82 b93dd41
```

I would also compare the CI logs.

The failure might not be related to code.

Possible causes include:

* Dependency repository outage
* Expired token
* Runner disk full
* Docker registry failure
* DNS problem
* Changed base image
* External API failure
* Secret removed
* Permission change
* Pipeline configuration change

## Strong troubleshooting flow

```text
Pipeline failed
      ↓
Which job?
      ↓
What exact error?
      ↓
What changed?
      ↓
Code?
Pipeline?
Runner?
Secret?
Dependency?
Infrastructure?
      ↓
Reproduce if possible
      ↓
Fix root cause
      ↓
Rerun
      ↓
Validate
```

# Question 2: A build works on your laptop but fails in CI. Why?

## Strong interview answer

The most important thing is to compare the environments.

"My machine works" does not prove the CI environment is wrong.

The local environment and CI runner may differ in:

* Operating system
* Package versions
* Runtime versions
* Environment variables
* Working directory
* Permissions
* Network access
* Secrets
* Installed tools
* CPU architecture
* Dependency cache
* Shell
* File paths

For example, locally:

```bash
python --version
```

might show:

```text
Python 3.12
```

while CI uses:

```text
Python 3.10
```

The application may depend on a feature that is unavailable in Python 3.10.

Another example:

A developer's laptop contains:

```text
DATABASE_URL
API_TOKEN
```

in the local environment.

The CI runner does not.

The build fails because the pipeline never defined them.

## Strong interview point

I would compare:

```text
Local environment
vs.
CI environment
```

and make the pipeline environment explicit and reproducible.

# Question 3: The pipeline says `command not found`. What would you investigate?

## Strong interview answer

I would first identify which command is missing.

Suppose the log says:

```text
terraform: command not found
```

I would check whether Terraform is installed on the runner or whether the pipeline is expected to install it.

I would also check `PATH`.

For example:

```bash
echo "$PATH"
```

and:

```bash
command -v terraform
```

If the job runs in a container, I would inspect the image used by the job.

For example:

```yaml
image: ubuntu:24.04
```

A generic Ubuntu image does not automatically include Terraform.

The fix may be:

* Use an image that contains the required tool
* Install the tool during the job
* Use a dedicated setup action or plugin
* Correct the PATH

## Interview lesson

The same pipeline definition may behave differently if the underlying runner image changes.

# Question 4: A CI job fails with `Permission denied`. What could cause it?

## Strong interview answer

I would first inspect exactly what operation failed.

For example:

```text
./deploy.sh: Permission denied
```

I would check whether the file has execute permission.

```bash
ls -l deploy.sh
```

If it shows:

```text
-rw-r--r--
```

then it is not executable.

I may need:

```bash
chmod +x deploy.sh
```

and importantly, if the execute bit should be part of the repository:

```bash
git update-index --chmod=+x deploy.sh
```

then commit the permission change.

Other permission failures may involve:

* Docker socket
* Workspace directory
* SSH key
* Artifact directory
* Cloud credentials
* Kubernetes kubeconfig
* Protected deployment environment

## Important distinction

"Permission denied" can mean:

```text
Linux filesystem permission
```

or:

```text
Platform authorization
```

Those are different problems.

# Question 5: The pipeline cannot read a secret. How would you troubleshoot it?

## Strong interview answer

I would first confirm the variable name and whether the secret is configured for the environment where the job runs.

For example, the script expects:

```bash
echo "$AWS_ACCESS_KEY_ID"
```

but the CI platform defines:

```text
AWS_ACCESS_KEY
```

That simple naming mismatch can break the job.

I would check:

* Is the secret defined?
* Is the name correct?
* Is it available to this branch?
* Is it restricted to protected branches?
* Is it available to pull requests?
* Is the environment correct?
* Has the secret expired?
* Is the credential still valid?

I would not print the real secret into the pipeline log.

Instead, I might verify that it exists without exposing it.

For example:

```bash
if [ -n "$AWS_ACCESS_KEY_ID" ]; then
  echo "AWS_ACCESS_KEY_ID is set"
else
  echo "AWS_ACCESS_KEY_ID is missing"
fi
```

## Security point

Never debug secrets by doing:

```bash
echo "$PASSWORD"
```

into CI logs.

# Question 6: A pipeline can access a secret on `main` but not on a feature branch. Why?

## Strong interview answer

The secret may be restricted to protected branches or protected environments.

This is a common security control.

For example:

```text
main
→ trusted
→ production secret available

feature/*
→ untrusted
→ production secret unavailable
```

That prevents someone from creating a feature branch that simply prints production credentials.

I would inspect:

* Secret protection settings
* Branch protection
* Environment restrictions
* Pull request security model

The correct solution is not necessarily to expose the production secret to every branch.

The pipeline may need a different credential for feature environments.

---

# Question 7: A pipeline stage is stuck in "pending." What could cause that?

## Strong interview answer

A pending job often means it has not yet been assigned to a runner or agent.

Possible causes include:

* No runner available
* Runner offline
* Runner tags do not match
* Queue capacity exhausted
* Required environment unavailable
* Concurrency limit reached
* Runner not authorized for project
* Runner resource pool unavailable

I would inspect the job's runner requirements.

For example:

```yaml
tags:
  - linux
  - docker
```

If no runner has both required tags, the job may remain pending.

## Strong reasoning

A pending job is different from a running job that is hanging.

```text
Pending
→ likely scheduling/runner allocation

Running but stuck
→ investigate job command/environment
```

# Question 8: A runner is offline. What would you investigate?

## Strong interview answer

I would inspect the runner host and runner service.

Possible checks include:

```bash
systemctl status gitlab-runner
```

or the equivalent for the platform.

I would check:

* Runner service state
* Network connectivity
* DNS
* Authentication token
* Disk space
* CPU
* Memory
* Docker daemon if used
* Certificate validity
* Platform availability

For example:

```bash
df -h
```

A runner with a full disk may become unusable.

If Docker is required:

```bash
systemctl status docker
```

The CI platform may report the runner offline even though the underlying server is technically running.

# Question 9: A CI job hangs for 30 minutes and then times out. How would you troubleshoot it?

## Strong interview answer

I would find the exact command where the job stopped making progress.

Suppose the log ends at:

```text
Running integration tests...
```

I would determine whether the test process is:

* Waiting on network
* Waiting on database
* Waiting for user input
* Deadlocked
* Retrying indefinitely
* Downloading a dependency slowly

One classic CI failure is a command asking for interactive confirmation.

For example:

```text
Proceed? [y/N]
```

In a non-interactive CI runner, the job may wait forever.

Another example is:

```bash
ssh server
```

waiting for host verification.

Or:

```text
terraform apply
```

waiting for approval when automation expected non-interactive behavior.

## Better approach

CI commands should normally be non-interactive.

For example:

```bash
terraform apply -auto-approve
```

only in appropriately controlled automated workflows.

# Question 10: A pipeline uses the wrong branch. What would you check?

## Strong interview answer

I would inspect pipeline trigger and checkout configuration.

For example, a pipeline may be triggered by:

```text
feature/login
```

but the checkout step explicitly pulls:

```bash
git checkout main
```

Now the pipeline runs because of one branch but builds another.

I would inspect:

* Trigger branch
* Checkout branch
* Detached HEAD behavior
* Merge request refs
* Environment branch filters
* Deployment rules

## Strong interview point

The branch that triggered the pipeline and the commit actually built should be traceable.

---

# Question 11: A production deployment runs from a feature branch. Why is that dangerous?

## Strong interview answer

It can bypass normal controls.

Production deployment should usually require deliberate conditions such as:

* Approved branch
* Pull request review
* Passing tests
* Security checks
* Environment approval
* Protected credentials

A dangerous workflow might look like:

```text
Any branch
   ↓
Push
   ↓
Deploy production
```

A safer workflow might be:

```text
Feature branch
   ↓
Pull request
   ↓
Review
   ↓
CI
   ↓
Merge to main
   ↓
Production approval
   ↓
Deploy
```

The exact design varies by organization, but production should not normally be deployable casually from arbitrary branches.

# Question 12: The pipeline succeeds, but the deployment uses an old artifact. What could cause that?

## Strong interview answer

I would inspect artifact and cache behavior.

Possible causes include:

* Old artifact reused
* Artifact path wrong
* Cache mistaken for artifact
* Docker image tag reused
* Deployment references `latest`
* Build stage did not upload new artifact
* Deploy stage downloads artifact from previous run

I would verify the artifact identifier.

For example:

```text
build-9f48a21.tar.gz
```

is more traceable than:

```text
build-latest.tar.gz
```

For container images:

```text
myapp:9f48a21
```

is safer for traceability than:

```text
myapp:latest
```

## Strong principle

Build outputs should be immutable and identifiable.

---

# Question 13: What is the difference between a cache and an artifact?

## Strong interview answer

A cache usually exists to improve pipeline performance.

Examples:

* Maven dependencies
* npm packages
* Python packages
* Build tool caches

An artifact is usually a produced output that later jobs or deployment stages consume.

Examples:

```text
application.jar
package.zip
test-report.xml
container metadata
compiled binary
```

A useful simplification:

```text
Cache
→ speed up repeated work

Artifact
→ output of the pipeline
```

Using a cache as if it were an authoritative build artifact can create unexpected behavior.

# Question 14: A pipeline says an artifact is missing. What would you check?

## Strong interview answer

I would verify:

* Did the previous job create the file?
* Is the path correct?
* Was the artifact uploaded?
* Has the artifact expired?
* Is the next job configured to download it?
* Did the previous job actually succeed?

For example:

```yaml
artifacts:
  paths:
    - build/app.jar
```

But the build may actually create:

```text
target/app.jar
```

The artifact configuration is wrong.

I would inspect:

```bash
find . -name "*.jar"
```

during debugging to verify the actual path.

# Question 15: What is a flaky test?

## Strong interview answer

A flaky test passes sometimes and fails sometimes without a meaningful code change.

For example:

```text
Run 1 → pass
Run 2 → pass
Run 3 → fail
Run 4 → pass
```

Possible causes include:

* Timing assumptions
* Race conditions
* External services
* Shared test data
* Resource pressure
* Random ordering
* Network instability
* Improper cleanup

## Why this matters in CI

Teams may begin ignoring failures because:

```text
"Just rerun it."
```

That destroys confidence in the pipeline.

The right goal is to identify and fix the nondeterministic behavior.

---

# Question 16: Is rerunning a failed pipeline a valid troubleshooting step?

## Strong interview answer

Yes, but only if used carefully.

A rerun can help determine whether the failure is transient.

For example:

```text
Pipeline 1:
External registry timeout

Pipeline 2:
Success
```

That suggests a transient dependency issue.

But repeatedly rerunning until something passes is not a fix.

If:

```text
Fail
Fail
Pass
Fail
Pass
```

then the pipeline is unreliable.

I would investigate why.

---

# Question 17: Tests pass locally but fail only in CI. What could be causing it?

## Strong interview answer

I would compare:

* Runtime version
* Dependency version
* Environment variables
* Database state
* Timezone
* Locale
* File system case sensitivity
* CPU/memory constraints
* Parallel execution
* Test ordering

For example, a developer may run tests sequentially.

CI may run them in parallel.

Two tests might accidentally use the same database record or port.

That creates a race condition visible only in CI.

Another example:

```text
Developer laptop:
UTC+1

CI runner:
UTC
```

A poorly written time-sensitive test may behave differently.

# Question 18: A build suddenly becomes much slower. How would you investigate?

## Strong interview answer

I would compare job timing between a normal pipeline and the slow pipeline.

For example:

```text
Normal:
Dependencies  2 min
Build         4 min
Tests         5 min

Slow:
Dependencies 18 min
Build         4 min
Tests         5 min
```

Now I know the problem is dependency retrieval, not compilation.

Possible causes include:

* Cache miss
* Dependency repository latency
* Network problem
* Larger dependency tree
* Runner performance
* Container image pull
* Storage performance

## Strong interview habit

Measure stage duration.

Do not treat total pipeline duration as one metric.

---

# Question 19: A Docker build in CI is very slow. What could improve it?

## Strong interview answer

I would inspect the Dockerfile and build context.

Possible problems include:

* Large build context
* Poor layer ordering
* Cache constantly invalidated
* Downloading dependencies every build
* Huge base image
* Unnecessary files included

For example:

```dockerfile
COPY . .
RUN npm install
```

may invalidate the dependency installation layer whenever any source file changes.

A more cache-friendly pattern can be:

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
```

I would also use `.dockerignore` to exclude unnecessary content.

Example:

```text
.git
node_modules
logs
tmp
```

The exact optimizations depend on the application.

---

# Question 20: A pipeline fails because Docker cannot connect to the daemon. What would you check?

## Strong interview answer

The error might look like:

```text
Cannot connect to the Docker daemon
```

I would investigate:

* Is Docker installed?
* Is Docker daemon running?
* Does the runner have permission to access it?
* Is Docker-in-Docker configured if required?
* Is the Docker socket mounted?
* Is the runner executor compatible?

On the runner host:

```bash
systemctl status docker
```

Check socket permissions:

```bash
ls -l /var/run/docker.sock
```

I would avoid fixing the problem by broadly granting dangerous permissions without understanding the security model.

# Question 21: The build stage passes, but the test stage never runs. What could cause that?

## Strong interview answer

I would inspect stage dependencies and conditional rules.

Possible causes include:

* Test job disabled
* Branch condition does not match
* `if` expression evaluates false
* Build artifact not produced
* Previous job status prevents downstream execution
* Manual gate
* Wrong stage order

For example:

```yaml
if: github.ref == 'refs/heads/main'
```

means the job may not run on a feature branch.

I would inspect the pipeline graph to understand whether the job was:

```text
Skipped
Blocked
Pending
Cancelled
```

Those are different states.

---

# Question 22: What is the difference between a failed job and a skipped job?

## Strong interview answer

A failed job started and encountered an error.

A skipped job did not run because pipeline logic determined that it should not execute.

For example:

```text
Job A → failed
```

means there is usually a command or environment error.

```text
Job B → skipped
```

may mean:

* Branch condition false
* Previous job did not meet requirement
* Rule excluded it
* Environment condition not satisfied

I would troubleshoot those differently.

---

# Question 23: A deployment job is waiting for approval. Is that necessarily a problem?

## Strong interview answer

No.

Manual approval may be an intentional production control.

For example:

```text
Build
 ↓
Test
 ↓
Security scan
 ↓
Production approval
 ↓
Deploy
```

Approval gates can prevent accidental deployment.

I would determine whether the job is:

```text
intentionally waiting
```

or:

```text
unexpectedly blocked
```

The pipeline status should make that clear.

# Question 24: What is a deployment environment in CI/CD?

## Strong interview answer

An environment represents a deployment target such as:

```text
development
staging
production
```

Different environments may have different:

* Credentials
* URLs
* Approval rules
* Variables
* Infrastructure
* Branch restrictions

For example:

```text
feature branches
→ development

main
→ staging

approved release
→ production
```

This separation reduces the risk of using production credentials or endpoints during development.

---

# Question 25: A pipeline deploys successfully to staging but fails in production. Why?

## Strong interview answer

I would compare the environments.

Possible differences include:

* Secrets
* Network access
* Permissions
* Infrastructure size
* DNS
* Database schema
* External integrations
* Deployment approvals
* Environment variables

For example:

```text
Staging:
DATABASE_HOST=staging-db.internal

Production:
DATABASE_HOST=prod-db.internal
```

If production DNS or firewall configuration is broken, the same application build may work in staging but fail in production.

## Important principle

Same artifact does not mean same environment.

# Question 26: Why is "build once, deploy many" a useful practice?

## Strong interview answer

The idea is to build one artifact and promote that exact artifact across environments.

For example:

```text
Source
  ↓
Build
  ↓
Artifact: myapp:9f48a21
  ↓
Development
  ↓
Staging
  ↓
Production
```

Instead of rebuilding separately for every environment.

Why?

Because rebuilding can produce different outputs.

For example:

```text
Staging build
dependency version A

Production rebuild
dependency version B
```

Now production is not running the exact artifact that was tested.

An immutable artifact improves confidence and traceability.

---

# Question 27: A deployment says "successful," but production users receive errors. Did the pipeline succeed?

## Strong interview answer

The deployment step may have completed, but that does not mean the release is healthy.

For example:

```text
kubectl apply
```

returning success only means the API accepted the configuration.

It does not prove:

* Pods became ready
* Health checks passed
* Application serves traffic
* Database migrations succeeded
* Customer transactions work

A strong pipeline should include post-deployment verification where appropriate.

For example:

```bash
curl -f https://app.example.com/health
```

or deployment status checks.

## Key distinction

```text
Deployment command succeeded
≠
Application release succeeded
```

---

# Question 28: What is a smoke test?

## Strong interview answer

A smoke test is a small set of important checks performed after a build or deployment to verify that critical functionality works.

For example:

```bash
curl -f https://app.example.com/health
curl -f https://app.example.com/api/version
```

A smoke test does not replace full testing.

Its purpose is to quickly detect obvious release failures.

For example:

```text
Application starts
Critical API responds
Database connection works
```

---

# Question 29: How would you design a basic rollback step?

## Strong interview answer

The rollback method depends on the deployment technology.

The important thing is that the previous known-good release should be identifiable.

For example:

```text
Current:
myapp:2.4.1

Previous:
myapp:2.4.0
```

If the new version fails health checks, the deployment process may restore:

```text
myapp:2.4.0
```

The pipeline should know:

* What version was previously running?
* How to redeploy it?
* How to verify rollback?
* Whether database changes are backward-compatible?

## Important point

Rollback is not always simple.

A database migration may make application rollback unsafe.

Deployment and data compatibility should be considered together.

---

# Question 30: A rollback succeeds, but the application is still broken. What could explain that?

## Strong interview answer

The problem may not have been caused solely by the application release.

Possible causes include:

* Database migration already changed schema
* Infrastructure changed separately
* Secret rotated
* External service outage
* DNS change
* Cache state
* Message format changed
* Data corruption

This is why rollback is a recovery tool, not proof of root cause.

---

# Question 31: What is blue-green deployment?

## Strong interview answer

Blue-green deployment keeps two application environments.

For example:

```text
Blue
Version 1
Currently receiving traffic

Green
Version 2
New release
```

After validating Green:

```text
Traffic
Blue → Green
```

If Green fails, traffic may be switched back to Blue.

This can make rollback faster.

But it requires:

* Additional capacity
* Traffic switching
* Data compatibility
* Careful state management

---

# Question 32: What is a canary deployment?

## Strong interview answer

A canary deployment sends a small portion of production traffic to the new version first.

For example:

```text
Version 1 → 95%
Version 2 → 5%
```

If the new version behaves well:

```text
Version 2 → 25%
Version 2 → 50%
Version 2 → 100%
```

This reduces the blast radius of a bad release.

The pipeline or deployment platform should monitor:

* Error rate
* Latency
* Health
* Business metrics

before increasing traffic.

---

# Question 33: A pipeline keeps deploying even when tests fail. What is wrong?

## Strong interview answer

The pipeline may not correctly enforce job dependencies or exit status.

For example, a shell script may run:

```bash
npm test
echo "Tests complete"
exit 0
```

Even if `npm test` fails, the script forces success.

Another example:

```bash
npm test || true
```

intentionally ignores failure.

That may be appropriate in some reporting jobs, but not when tests are supposed to block deployment.

I would inspect:

* Exit codes
* `continue-on-error`
* Allowed failures
* Stage dependencies
* Pipeline conditions

A production deployment should not silently ignore required test failures.

---

# Question 34: Why are exit codes important in CI/CD?

## Strong interview answer

CI systems often determine whether a command succeeded using its exit code.

By convention:

```text
0
→ success

non-zero
→ failure
```

For example:

```bash
terraform validate
```

returning non-zero should cause the job to fail.

A poorly written script might hide the error.

For Bash automation, options such as:

```bash
set -e
```

can cause the script to exit on certain command failures, though shell error handling must be understood carefully.

A more robust script may explicitly check critical commands.

# Question 35: A shell script works manually but fails in the pipeline. What would you investigate?

## Strong interview answer

I would compare:

* Shell
* PATH
* Working directory
* Environment variables
* User
* Permissions
* Installed tools
* File locations

For example:

```bash
./scripts/deploy.sh
```

may assume the current directory is the repository root.

But CI may run it from another directory.

A safer script can determine its own location or use explicit paths.

Another common difference:

```text
Local shell:
bash

CI shell:
sh
```

A Bash-specific script may fail if invoked using a POSIX shell.

For example:

```bash
bash deploy.sh
```

may behave differently from:

```bash
sh deploy.sh
```

# Question 36: Why should pipeline configuration be stored in Git?

## Strong interview answer

Version controlling pipeline configuration provides:

* Change history
* Review
* Rollback
* Auditability
* Reproducibility

Examples include:

```text
Jenkinsfile
.github/workflows/deploy.yml
.gitlab-ci.yml
azure-pipelines.yml
```

If a pipeline breaks after a change, I can inspect:

```bash
git log --oneline -- Jenkinsfile
```

or:

```bash
git diff <good-commit> <bad-commit> -- Jenkinsfile
```

That makes troubleshooting much easier than manually changing pipeline settings without history.

---

# Question 37: A pipeline works on `main` but fails in a pull request. Why?

## Strong interview answer

Pull request pipelines may intentionally run with reduced privileges.

For security reasons, they may not receive:

* Production secrets
* Write tokens
* Deployment permissions
* Protected environment access

This becomes especially important for pull requests from forks.

An untrusted contributor should not be able to submit:

```yaml
run: echo "$PRODUCTION_PASSWORD"
```

and obtain production secrets.

I would inspect the CI platform's pull-request security model.

---

# Question 38: A pipeline needs SSH access to a deployment server. What should you configure carefully?

## Strong interview answer

I would consider:

* Private key storage
* Public key authorization
* Known hosts
* Least privilege
* File permissions
* Secret masking

The private key should be stored securely in the CI secret store.

It should not be committed to Git.

The deployment server should authorize a limited deployment account where possible.

I would also avoid blindly disabling host-key checking without understanding the security trade-off.

---

# Question 39: Why can SSH deployment jobs hang unexpectedly?

## Strong interview answer

One common reason is SSH asking for interactive input.

For example:

```text
The authenticity of host cannot be established.
Are you sure you want to continue connecting?
```

A CI runner cannot respond interactively unless explicitly handled.

Another reason is authentication failure causing repeated attempts.

Or the remote command itself may never terminate.

I would use verbose SSH debugging where appropriate:

```bash
ssh -v deploy@server
```

and configure host trust correctly.

# Question 40: A Docker image builds successfully but cannot be pushed to the registry. What would you investigate?

## Strong interview answer

I would inspect the push error.

Possible causes include:

* Not authenticated
* Token expired
* Repository does not exist
* Wrong registry URL
* Permission denied
* Network issue
* Registry unavailable

For example:

```bash
docker login registry.example.com
```

must succeed using CI credentials.

Then:

```bash
docker push registry.example.com/team/app:9f48a21
```

I would verify:

* Registry path
* Tag
* Credential
* Push permission

I would not expose the registry password in logs.

# Question 41: The pipeline pushes `latest`, but production keeps running the old image. Why?

## Strong interview answer

Using mutable tags such as `latest` can create ambiguity.

For example:

```text
myapp:latest
```

may refer to different image content over time.

A node or runtime may also have an older cached image depending on pull policy.

A safer deployment pattern often uses immutable version identifiers such as:

```text
myapp:9f48a21
```

or:

```text
myapp:2.4.0
```

Then the deployment explicitly changes from:

```text
2.3.9
```

to:

```text
2.4.0
```

That improves traceability and rollback.

# Question 42: A pipeline deploys the wrong version. How would you investigate?

## Strong interview answer

I would trace the release identity from source to runtime.

I would ask:

```text
Which commit triggered the pipeline?

Which artifact did the build create?

Which image tag was pushed?

Which image did the deployment reference?

Which image is actually running?
```

The expected flow should be traceable:

```text
Git commit
9f48a21
   ↓
Build
   ↓
Image
myapp:9f48a21
   ↓
Deploy
   ↓
Production
myapp:9f48a21
```

If production shows:

```text
myapp:812bd34
```

then somewhere the release chain selected the wrong artifact.

# Question 43: Why should every deployment have a unique release identifier?

## Strong interview answer

Because it allows me to answer:

* What is running?
* What code produced it?
* When was it deployed?
* What was running before?
* What do I roll back to?

A release identifier may be:

* Git SHA
* Version tag
* Build number
* Container digest

Without traceability, incident investigation becomes harder.

# Question 44: A pipeline runs successfully but deploys to the wrong environment. What could cause that?

## Strong interview answer

I would inspect environment selection logic.

Possible causes include:

* Incorrect branch mapping
* Wrong variable
* Misnamed environment
* Reused credentials
* Wrong deployment target
* Script defaults

For example:

```bash
ENVIRONMENT=${ENVIRONMENT:-production}
```

is dangerous if a missing environment variable silently defaults to production.

A safer pipeline should require explicit environment selection.

---

# Question 45: What is a pipeline variable?

## Strong interview answer

A pipeline variable stores information used during execution.

Examples:

```text
APP_VERSION
DEPLOY_ENV
REGISTRY_URL
AWS_REGION
```

Some variables are non-sensitive.

Others may contain secrets.

I would distinguish between:

```text
Configuration
```

and:

```text
Secret
```

Sensitive values should use protected secret storage rather than plain-text pipeline files.

---

# Question 46: Why should secrets not be stored directly inside pipeline YAML?

## Strong interview answer

Because the pipeline configuration is usually stored in Git.

If I write:

```yaml
env:
  PASSWORD: SuperSecretPassword
```

then the secret enters repository history.

Even if removed later, it may still exist in older commits.

Instead, I would reference secure CI variables or a secrets manager.

For example:

```yaml
env:
  PASSWORD: ${{ secrets.PRODUCTION_PASSWORD }}
```

using the platform's secure secret mechanism.

---

# Question 47: A credential expired overnight and all deployments fail. How should this have been prevented?

## Strong interview answer

The immediate response is to restore valid authentication safely.

But the longer-term problem is credential lifecycle management.

I would consider:

* Short-lived credentials
* Automatic rotation
* Expiration monitoring
* Workload identities
* Cloud-native identity mechanisms
* Avoiding long-lived static keys

Where supported, CI systems should authenticate using temporary identities rather than manually rotated permanent credentials.

---

# Question 48: Why is least privilege important for CI/CD?

## Strong interview answer

A pipeline credential should have only the permissions required for that pipeline.

For example, a pipeline that deploys one application should not automatically have:

```text
Administrator access to the entire cloud account
```

If the pipeline credential is compromised, excessive permissions increase the blast radius.

Better:

```text
Pipeline
   ↓
Can push app image
Can update specific deployment
Cannot delete unrelated infrastructure
```

Least privilege limits damage from mistakes or credential compromise.

---

# Question 49: A job was cancelled halfway through deployment. What would you check?

## Strong interview answer

I would determine whether the deployment operation was transactional or partially applied.

Questions include:

* Did any resources change?
* Did some hosts receive the new version?
* Did database migration start?
* Did traffic already shift?
* Can deployment resume safely?
* Should I roll back?

A cancelled pipeline does not necessarily mean:

```text
Nothing happened.
```

For example:

```text
10 servers total
5 updated
job cancelled
5 old
5 new
```

Now production may contain mixed versions.

I would inspect actual runtime state before retrying.

---

# Question 50: A deployment pipeline runs against five servers, but fails after updating the third server. What do you do?

## Strong interview answer

First, determine actual deployment state.

```text
Server 1 → v2
Server 2 → v2
Server 3 → v2
Server 4 → v1
Server 5 → v1
```

Then determine whether mixed versions are safe.

If the versions are compatible, I may repair the pipeline and complete the rollout.

If they are not, I may need to roll back the updated servers.

The correct decision depends on:

* Application compatibility
* Database schema
* Traffic routing
* Severity
* Rollback capability

The important interview lesson is:

```text
Never blindly rerun a partially completed deployment without checking state.
```

# Question 51: The CI server disk is full. What symptoms might you see?

## Strong interview answer

A full runner disk can cause seemingly unrelated errors.

For example:

* Cannot checkout repository
* Docker build fails
* Cannot write artifact
* Temporary files fail
* Package installation fails
* Runner crashes

I would check:

```bash
df -h
```

and:

```bash
df -i
```

I would inspect:

* Old workspaces
* Docker images
* Build artifacts
* Logs
* Caches

For Docker hosts:

```bash
docker system df
```

I would clean resources according to operational policy rather than blindly deleting everything.

# Question 52: Docker images keep filling the runner disk. What would you do?

## Strong interview answer

I would identify unused Docker resources.

```bash
docker system df
```

Potential cleanup commands include:

```bash
docker image prune
```

or broader pruning where safe and approved.

But long-term prevention matters more.

I would consider:

* Scheduled cleanup
* Ephemeral runners
* Artifact retention
* Image caching policy
* Monitoring disk utilization

The runner should not depend on someone manually cleaning it after every outage.

# Question 53: What is an ephemeral runner?

## Strong interview answer

An ephemeral runner is created for a job or short period and then destroyed.

Conceptually:

```text
Pipeline job
   ↓
Create runner
   ↓
Execute job
   ↓
Destroy runner
```

Benefits can include:

* Cleaner environments
* Reduced state leakage
* Easier scaling
* Less accumulated disk garbage

It also helps reduce problems where one job affects another through leftover files or dependencies.

---

# Question 54: Why can shared runners cause inconsistent pipeline behavior?

## Strong interview answer

A shared persistent runner may retain state from previous jobs.

For example:

* Cached dependencies
* Old containers
* Files
* Environment modifications
* Credentials
* Workspace content

A pipeline may accidentally succeed because something left behind already exists.

Then it fails on a clean runner.

Good pipelines should aim to be reproducible from a clean environment.

---

# Question 55: The first pipeline run fails, but rerunning immediately succeeds. What might cause that?

## Strong interview answer

Possible causes include:

* Dependency service temporarily unavailable
* Race condition
* Artifact not immediately available
* Eventually consistent infrastructure
* Startup timing
* Flaky test
* DNS propagation
* Runner issue

I would not assume the problem is solved.

I would inspect the first failure and determine whether retry logic is appropriate.

For example, waiting for a new service to become ready may require:

```text
retry with bounded timeout
```

rather than:

```text
sleep 60
```

without checking actual readiness.

---

# Question 56: Why is `sleep 60` often a weak deployment strategy?

## Strong interview answer

Because it waits a fixed amount of time without checking whether the system is actually ready.

Maybe the service is ready after:

```text
5 seconds
```

or maybe it still is not ready after:

```text
60 seconds
```

A better approach is polling with a timeout.

For example:

```bash
for i in {1..30}; do
  if curl -fsS https://app.example.com/health; then
    echo "Application is healthy"
    exit 0
  fi

  sleep 5
done

echo "Application did not become healthy"
exit 1
```

Now the pipeline checks the actual condition.

# Question 57: What logs would you look at when a deployment fails?

## Strong interview answer

I would inspect logs from all relevant layers.

Pipeline logs:

```text
What command failed?
```

Runner logs:

```text
Did the agent have a problem?
```

Deployment platform logs:

```text
Did Kubernetes, systemd, Docker, or cloud service reject the operation?
```

Application logs:

```text
Did the new application start?
```

Load balancer or health logs:

```text
Did traffic routing succeed?
```

A deployment failure can span multiple systems.

I would correlate timestamps.

# Question 58: A pipeline log contains thousands of lines. How do you troubleshoot efficiently?

## Strong interview answer

I would find the first meaningful failure, not only the final line.

For example:

```text
Step 8:
authentication failed

Step 9:
artifact not found

Step 10:
deployment skipped
```

The root cause may be Step 8.

The later messages are consequences.

I would search for:

```text
ERROR
FAILED
exit code
permission denied
timeout
unauthorized
not found
```

But I would also understand the job sequence.

The first failure often matters more than the last error.

# Question 59: Why can the final error message be misleading?

## Strong interview answer

Because one failure can cause many downstream failures.

For example:

```text
Secret missing
   ↓
Registry login fails
   ↓
Image push fails
   ↓
Artifact missing
   ↓
Deployment fails
```

The final message may say:

```text
Deployment artifact not found
```

but the real root cause was:

```text

```

Strong troubleshooting follows the failure chain backward.

# Question 60: A production deployment fails. Walk me through your full investigation.

## Strong interview answer

I would first determine the pipeline state.

```text
Which stage?
Which job?
Which command?
What error?
```

Then establish recent changes.

```text
What commit triggered it?
Was the pipeline file changed?
Were secrets or infrastructure changed?
```

I would inspect the job log.

Suppose the failed stage is:

```text
deploy-production
```

and the error is:

```text
Error from server (Forbidden):
deployments.apps is forbidden
```

That tells me the build probably succeeded.

The failure is Kubernetes authorization.

I would verify which identity the pipeline uses.

For example:

```text
ci-deployer
```

Then inspect its permissions.

I would ask:

```text
Did RBAC change?
Did the service account change?
Did kubeconfig change?
Did the cluster change?
```

I would not debug the application code because the application was never deployed.

That is the core of CI/CD troubleshooting.

Use the stage and error to decide which layer deserves attention.

# Final Production Interview Scenario

The interviewer gives you the following scenario:

> "At 15:20, a developer merges a pull request into `main`. The CI pipeline starts automatically. Build passes. Unit tests pass. The Docker image builds successfully. The image is pushed to the registry. The production deployment job reports success. Five minutes later, users begin receiving HTTP 503 errors. The load balancer shows all new application instances as unhealthy. Walk me through exactly how you would investigate."

A weak answer would be:

> "The pipeline says success, so I would check the load balancer."

That is too shallow.

A stronger junior DevOps candidate first reconstructs what happened.

```text
Git merge
   ↓
Build success
   ↓
Tests success
   ↓
Image build success
   ↓
Image push success
   ↓
Deployment command success
   ↓
New instances unhealthy
   ↓
Users receive 503
```

The important observation is:

```text
The delivery system successfully changed production.

The application release itself appears unhealthy.
```

First, identify the deployed version.

For example:

```text
Commit:
9f48a21

Image:
registry.example.com/shop/app:9f48a21
```

Verify that production actually runs that image.

If Kubernetes is used:

```bash
kubectl get deployment shop-app -o wide
```

Then:

```bash
kubectl get pods
```

Suppose the Pods show:

```text
Running
```

That still does not prove readiness.

Check:

```bash
kubectl describe pod <pod-name>
```

and:

```bash
kubectl logs <pod-name>
```

Suppose logs show:

```text
Application started on port 9000
```

Now inspect the deployment.

Suppose its Service or load balancer target expects:

```text
port 8080
```

The new application version changed its listening port from:

```text
8080
```

to:

```text
9000
```

but deployment configuration was not updated.

The load balancer health check attempts:

```text
backend:8080/health
```

Nothing responds.

The target becomes unhealthy.

Users receive:

```text
503 Service Unavailable
```

The failure chain is:

```text
Application change
      ↓
New listener port
8080 → 9000
      ↓
Deployment configuration unchanged
      ↓
Health checks target 8080
      ↓
All targets unhealthy
      ↓
Load balancer has no healthy backend
      ↓
HTTP 503
```

Now decide how to restore service.

If the previous release is known good, the fastest safe response may be rollback.

For example:

```text
Current:
myapp:9f48a21

Previous:
myapp:71bc903
```

Roll back using the organization's deployment mechanism.

Then verify.

```bash
curl -f https://shop.example.com/health
```

After service recovery, investigate why CI did not catch the problem.

Possible improvements include:

* Integration test for expected listening port
* Deployment readiness checks
* Post-deployment smoke test
* Health-check validation
* Configuration contract between app and deployment manifests

## Strong interview answer

A strong candidate might explain it like this:

> "I would separate pipeline execution success from release health. The build, tests, image push, and deployment command succeeded, but the new instances became unhealthy. I would identify the exact deployed version, inspect the runtime status, application logs, listening port, health-check configuration, and recent deployment changes. If the new release is clearly responsible, I would restore the previous known-good version before continuing a deeper investigation. Then I would improve the pipeline so future deployments verify application readiness and the actual health endpoint rather than assuming that a successful deployment command means the release is healthy."

That answer demonstrates:

```text
CI/CD knowledge
+
Production troubleshooting
+
Rollback judgment
+
Verification
+
Prevention
```

# What Junior DevOps Candidates Should Learn From Part 6

A CI/CD pipeline is not one command.

It is a chain.

```text
Trigger
  ↓
Runner
  ↓
Checkout
  ↓
Dependencies
  ↓
Build
  ↓
Test
  ↓
Package
  ↓
Artifact
  ↓
Authentication
  ↓
Deployment
  ↓
Runtime
  ↓
Verification
```

When the pipeline fails, do not troubleshoot the entire chain at once.

Find the first broken stage.

Ask:

1. Did the pipeline trigger?
2. Was a runner assigned?
3. Did the runner start?
4. Was the correct commit checked out?
5. Were dependencies installed?
6. Did the build succeed?
7. Did tests run?
8. Did tests genuinely pass?
9. Was the artifact produced?
10. Was the artifact uploaded?
11. Was the correct version selected?
12. Did authentication work?
13. Did the deployment command execute?
14. Did production actually change?
15. Did the new version become healthy?
16. Did users successfully use the application?
17. Can we safely roll back?
18. What changed compared with the last successful release?

A useful debugging mindset is:

```text
Pipeline failure
      ↓
Locate exact stage
      ↓
Read first meaningful error
      ↓
Determine dependency
      ↓
Compare with last successful run
      ↓
Reproduce if possible
      ↓
Fix
      ↓
Rerun
      ↓
Verify outcome
```

Useful commands and tools from this part include:

```bash
git status
git log
git diff

echo
env
command -v

df -h
df -i

systemctl

docker build
docker push
docker system df

curl

ssh

kubectl get
kubectl describe
kubectl logs
```

But CI/CD troubleshooting is not about memorizing commands.

It is about understanding what every stage is responsible for.

For example:

```text
Pipeline never starts
→ investigate trigger

Job pending
→ investigate runner allocation

Job running but hangs
→ investigate command or dependency

Build fails
→ investigate code, dependencies, toolchain

Test fails
→ investigate application or test behavior

Artifact missing
→ investigate build output and artifact handling

Authentication fails
→ investigate identity and secrets

Deployment command fails
→ investigate deployment permissions and target

Deployment succeeds but application fails
→ investigate runtime health

Users fail after healthy deployment
→ investigate real request path and dependencies
```

The most important lesson is this:

```text
A green pipeline is not the same as a healthy production system.
```

A good pipeline should help answer:

```text
What changed?

What was built?

What was tested?

What was deployed?

Where was it deployed?

Did it become healthy?

Can we roll it back?

Can we trace production back to source?
```

A junior DevOps engineer who can reason through those questions is already moving beyond basic CI/CD definitions and into real operational thinking.
