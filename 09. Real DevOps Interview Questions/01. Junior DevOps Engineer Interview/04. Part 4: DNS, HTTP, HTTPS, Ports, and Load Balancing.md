# Part 4: DNS, HTTP, HTTPS, Ports, and Load Balancing

A web application can be running perfectly on a server and still be completely unavailable to users.

That is because reaching an application usually involves much more than the application process itself.

A typical request might travel through several components:

```text
User
  ↓
DNS
  ↓
Public IP or Load Balancer
  ↓
Port 443
  ↓
TLS
  ↓
Reverse Proxy / Load Balancer
  ↓
Backend Target
  ↓
Application
  ↓
Database or Other Dependencies
```

A failure at any point can produce a different symptom.

Users might see:

* DNS resolution failures
* Connection refused
* Connection timeout
* TLS certificate warnings
* HTTP 301 or 302 redirects
* HTTP 404
* HTTP 500
* HTTP 502
* HTTP 503
* HTTP 504
* Intermittent failures
* Requests reaching the wrong backend
* Healthy servers marked unhealthy by a load balancer

For a junior DevOps engineer, the goal is not to memorize every HTTP status code or every DNS record type.

The goal is to understand how a request moves from a client to an application and how to determine which layer failed.

---

# Question 1: Explain what happens when a user enters `https://app.example.com` into a browser.

## What the interviewer is testing

This question tests whether you understand how DNS, networking, TLS, HTTP, and application infrastructure fit together.

A strong answer should describe the request as a sequence rather than treating "opening a website" as one operation.

## Strong interview answer

At a simplified level, the client first needs to determine where `app.example.com` is located.

DNS resolves the hostname to an IP address or another DNS target that eventually resolves to an address.

The client then establishes network connectivity to that destination.

Because the URL uses HTTPS, the client normally connects to TCP port 443.

A TCP connection is established.

Then the TLS handshake occurs.

During TLS negotiation, the server presents its certificate and the client validates things such as:

* Certificate trust
* Hostname
* Validity period
* Certificate chain

After TLS succeeds, the browser sends an HTTP request.

For example:

```http
GET / HTTP/1.1
Host: app.example.com
```

The request may reach a:

* Load balancer
* Reverse proxy
* CDN
* Web server
* Application server

If there is a load balancer, it chooses an eligible backend and forwards the request.

The application processes the request and returns an HTTP response.

## Simplified flow

```text
app.example.com
      ↓
DNS resolution
      ↓
Destination IP
      ↓
TCP connection to 443
      ↓
TLS handshake
      ↓
HTTP request
      ↓
Load balancer / proxy
      ↓
Backend application
      ↓
HTTP response
```

## Interviewer follow-up

### "At which points could the request fail?"

Potentially every stage.

For example:

```text
DNS
→ hostname does not resolve

TCP
→ connection timeout or refused

TLS
→ certificate validation failure

Load balancer
→ no healthy backend

Application
→ HTTP 500

Dependency
→ application waits on database and gateway returns 504
```

That is why troubleshooting should identify the failing layer first.

# Question 2: What is DNS, and why does DevOps need to understand it?

## Strong interview answer

DNS, the Domain Name System, translates names such as:

```text
api.example.com
```

into information needed to locate services, commonly IP addresses.

Without DNS, users and applications would frequently need to reference services directly by IP address.

For example:

```text
api.example.com
        ↓
203.0.113.20
```

DNS becomes especially important in DevOps because applications often communicate using hostnames.

DNS is involved in:

* Websites
* APIs
* Databases
* Service discovery
* Cloud load balancers
* Kubernetes
* Internal networks
* Email
* CDNs
* Multi-region systems

A DNS problem can look like an application outage even when the application itself is completely healthy.

---

# Question 3: What are A, AAAA, CNAME, MX, TXT, and NS records?

## Strong interview answer

These DNS records serve different purposes.

### A record

Maps a hostname to an IPv4 address.

Example:

```text
app.example.com → 203.0.113.20
```

### AAAA record

Maps a hostname to an IPv6 address.

### CNAME record

Makes one DNS name an alias of another DNS name.

For example:

```text
www.example.com
        ↓
app.example.net
```

The target name then resolves through DNS.

### MX record

Identifies mail servers responsible for receiving email for a domain.

### TXT record

Stores text information.

TXT records are commonly used for:

* Domain verification
* SPF
* DKIM-related configuration
* Security validation
* Service ownership verification

### NS record

Identifies authoritative name servers for a DNS zone.

## Interview point

For DevOps roles, A, AAAA, and CNAME are especially common in application troubleshooting.

---

# Question 4: What is the difference between an A record and a CNAME?

## Strong interview answer

An A record maps a DNS name directly to an IPv4 address.

Example:

```text
api.example.com
        ↓
203.0.113.10
```

A CNAME maps one DNS name to another DNS name.

Example:

```text
api.example.com
        ↓
service.example.net
        ↓
203.0.113.10
```

The important distinction is:

```text
A
Name → IPv4 address

CNAME
Name → another DNS name
```

This matters in cloud environments because many managed services provide DNS names rather than fixed public IP addresses.

# Question 5: What is DNS TTL?

## Strong interview answer

TTL means Time To Live.

It tells DNS resolvers how long they may cache a DNS response before they should query again.

Suppose:

```text
app.example.com
TTL = 300
```

That is 300 seconds, or five minutes.

If the record changes from:

```text
203.0.113.10
```

to:

```text
203.0.113.20
```

a resolver that already cached the previous answer may continue using it until the cached entry expires.

## Why this matters operationally

DNS changes are frequently involved in:

* Migrations
* Blue-green deployments
* Failovers
* Load balancer changes
* CDN changes
* Disaster recovery

If you expect to make a DNS cutover, TTL should be considered before the change, not only after users report stale DNS results.

# Question 6: DNS was changed, but some users still reach the old application. How would you troubleshoot it?

## Strong interview answer

I would first verify the authoritative DNS configuration rather than assuming the problem is simply "DNS propagation."

I could query:

```bash
dig app.example.com
```

Then inspect:

```bash
dig app.example.com +trace
```

when appropriate.

I might query specific resolvers:

```bash
dig @8.8.8.8 app.example.com
```

and another resolver:

```bash
dig @1.1.1.1 app.example.com
```

I would compare:

* Returned address
* TTL
* Resolver used
* Authoritative nameservers

I would also check whether the affected machine has a local override:

```bash
cat /etc/hosts
```

and compare system resolution:

```bash
getent hosts app.example.com
```

Possible causes include:

* Cached DNS response
* Wrong authoritative record
* Local `/etc/hosts`
* Split DNS
* Multiple records
* CDN caching
* Proxy caching
* Browser caching
* DNS change made in the wrong zone

## Strong interview point

Do not use "DNS propagation" as a universal explanation.

Collect evidence about which resolver is returning which answer.

# Question 7: What is recursive DNS versus authoritative DNS?

## Strong interview answer

An authoritative DNS server stores the actual DNS records for a zone and provides authoritative answers for those records.

A recursive resolver performs DNS lookups on behalf of clients.

A simplified flow looks like:

```text
Client
  ↓
Recursive Resolver
  ↓
DNS hierarchy
  ↓
Authoritative Name Server
  ↓
Answer
  ↓
Recursive Resolver caches answer
  ↓
Client
```

For troubleshooting, this distinction matters because an authoritative server may already have the new record while a recursive resolver is still serving a cached older answer.

# Question 8: What is HTTP?

## Strong interview answer

HTTP is an application-layer protocol used for communication between clients and servers.

A client sends a request.

The server returns a response.

For example:

```http
GET /health HTTP/1.1
Host: app.example.com
```

The server might respond:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

with:

```json
{
  "status": "healthy"
}
```

HTTP requests contain things such as:

* Method
* Path
* Headers
* Optional body

Responses contain:

* Status code
* Headers
* Optional body

Understanding this becomes important when troubleshooting APIs, reverse proxies, health checks, and load balancers.

---

# Question 9: What are the common HTTP methods?

## Strong interview answer

Common HTTP methods include:

### GET

Retrieve a resource.

```http
GET /users/123
```

### POST

Commonly used to create or submit data.

```http
POST /users
```

### PUT

Often used to replace or fully update a resource.

### PATCH

Often used for partial updates.

### DELETE

Delete a resource.

### HEAD

Similar to GET but returns headers without the response body.

### OPTIONS

Can describe supported communication options and is commonly encountered with browser CORS behavior.

## DevOps relevance

A reverse proxy or firewall may allow GET but block another method.

So if someone says:

"The endpoint works in the browser but the application cannot POST data,"

I should not assume basic reachability proves every request type works.

# Question 10: What do the major HTTP status-code groups mean?

## Strong interview answer

HTTP status codes are grouped by their first digit.

```text
1xx = Informational
2xx = Successful
3xx = Redirection
4xx = Client-side request problem
5xx = Server-side or upstream problem
```

Common examples include:

```text
200 OK
201 Created
301 Moved Permanently
302 Found
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
429 Too Many Requests
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

The status code gives me an important clue about how far the request traveled.

For example, receiving an HTTP 404 means the client successfully reached an HTTP-speaking endpoint.

That is very different from a TCP timeout.

---

# Question 11: What is the difference between HTTP 401 and 403?

## Strong interview answer

`401 Unauthorized` generally indicates that authentication is required or the supplied authentication is invalid.

Despite the wording "Unauthorized," it is primarily associated with authentication.

`403 Forbidden` means the server understood the request but refuses to authorize it.

A useful simplification is:

```text
401
Who are you?
Authentication problem

403
I know who you are, but you cannot do this.
Authorization problem
```

In practice, applications can implement these codes differently, so I would still inspect application behavior and logs.

---

# Question 12: What does HTTP 404 tell you during troubleshooting?

## Strong interview answer

A 404 indicates that an HTTP server received the request and could not find the requested resource or route.

That tells me basic connectivity has progressed significantly.

I probably do not need to begin by asking whether DNS or TCP connectivity is completely broken.

I would investigate:

* Requested path
* Application routing
* Reverse proxy routing
* Deployment version
* Virtual host
* URL rewrite rules

For example:

```bash
curl -v https://app.example.com/api/users
```

may return 404 while:

```bash
curl -v https://app.example.com/api/v1/users
```

returns 200.

That would point toward a path or routing problem.

---

# Question 13: What is the difference between HTTP and HTTPS?

## Strong interview answer

HTTPS is HTTP transported over TLS.

HTTP traffic is not protected by TLS.

HTTPS provides properties such as:

* Encryption in transit
* Server authentication through certificates
* Integrity protection

Typical default ports are:

```text
HTTP  → TCP 80
HTTPS → TCP 443
```

The HTTPS flow is roughly:

```text
TCP connection
      ↓
TLS handshake
      ↓
Encrypted HTTP communication
```

The HTTP request itself occurs after the secure TLS connection has been established.

---

# Question 14: What happens during a TLS handshake?

## Strong interview answer

At a simplified level, the client and server negotiate how to establish a secure connection.

The server presents its certificate.

The client validates important properties such as:

* Trusted issuer
* Hostname
* Validity period
* Certificate chain

The client and server then establish cryptographic session keys.

After the handshake succeeds, application traffic such as HTTP can be encrypted.

For a junior DevOps interview, I would explain the operational importance rather than trying to reproduce every cryptographic detail.

The key point is:

```text
TCP works
   ↓
TLS negotiation
   ↓
Certificate validation
   ↓
Secure session
   ↓
HTTP request
```

---

# Question 15: A website's TLS certificate expired. What will users experience?

## Strong interview answer

Browsers and clients that perform certificate validation will usually reject or warn about the connection because the certificate is outside its valid time period.

I would verify the certificate.

For example:

```bash
openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com
```

I can also use:

```bash
curl -v https://app.example.com
```

The investigation should determine:

* Which certificate is being served?
* When does it expire?
* Where is TLS terminated?
* Was certificate renewal supposed to be automated?
* Did renewal fail?
* Was the renewed certificate actually deployed?

## Production lesson

Replacing the certificate solves the immediate problem.

The follow-up question should be:

"Why was an expiring production certificate not detected earlier?"

Monitoring should normally warn before expiration.

---

# Question 16: The certificate is valid, but users get a hostname mismatch. What happened?

## Strong interview answer

The certificate does not cover the hostname being requested.

For example:

```text
User requests:
api.example.com
```

but the certificate covers only:

```text
www.example.com
```

The certificate may still be cryptographically valid and unexpired, but it is not valid for that hostname.

I would inspect the certificate's Subject Alternative Names.

Possible causes include:

* Wrong certificate deployed
* Wrong load balancer listener
* DNS points to wrong endpoint
* Incorrect virtual host
* Reverse proxy serving default certificate

---

# Question 17: What is a port, and why does it matter?

## Strong interview answer

A port identifies a network service endpoint on a host.

A server can run many network services on the same IP because they use different ports.

Examples commonly include:

```text
22    SSH
53    DNS
80    HTTP
443   HTTPS
3306  MySQL
5432  PostgreSQL
```

These are common defaults, not mandatory values.

An application could listen on:

```text
8080
8443
3000
5000
```

or another configured port.

When troubleshooting, I need to know both:

```text
Destination IP
Destination port
```

because reaching the host does not prove the required service port is reachable.

---

# Question 18: How do you determine what is listening on a port?

## Strong interview answer

On Linux:

```bash
ss -lntp
```

For a specific port:

```bash
ss -lntp | grep :8080
```

Another option:

```bash
lsof -iTCP:8080 -sTCP:LISTEN
```

Suppose I see:

```text
LISTEN 0 128 127.0.0.1:8080
```

The application is listening only on loopback.

If I see:

```text
LISTEN 0 128 0.0.0.0:8080
```

it is listening on all IPv4 interfaces.

That distinction can completely explain why an application works locally but not remotely.

---

# Question 19: An application should listen on port 8080, but `ss` shows nothing. What next?

## Strong interview answer

I would check whether the application process is actually running.

For a systemd-managed application:

```bash
systemctl status myapp
```

Then:

```bash
journalctl -u myapp -n 100
```

Possible causes include:

* Application failed during startup
* Wrong configured port
* Port already occupied
* Configuration missing
* Dependency unavailable
* Permission problem
* Application still initializing

I would also search configuration for the expected port.

The key point is that a process appearing in `ps` does not guarantee the application successfully created its listening socket.

---

# Question 20: What does "Address already in use" mean?

## Strong interview answer

It usually means another socket is already bound to the address and port the application is trying to use.

For example, an application tries:

```text
0.0.0.0:8080
```

but another process already owns that listener.

I would check:

```bash
ss -lntp | grep :8080
```

or:

```bash
lsof -i :8080
```

Then identify the existing process.

I would not immediately kill it.

First I need to know:

* Is it the old application instance?
* Is another legitimate service using that port?
* Did a deployment start two copies?
* Is systemd already managing the application?

The fix depends on why the conflict exists.

---

# Question 21: What is a reverse proxy, and why would you use one?

## Strong interview answer

A reverse proxy sits in front of backend applications and accepts requests on their behalf.

For example:

```text
Internet
   ↓
Nginx
Port 443
   ↓
Application
Port 8080
```

The reverse proxy may handle:

* TLS termination
* Request routing
* Load balancing
* Headers
* Compression
* Caching
* Access controls

This means the backend application does not necessarily need to listen directly on public port 443.

It may listen privately on 8080 while the reverse proxy exposes HTTPS.

---

# Question 22: What is a load balancer?

## Strong interview answer

A load balancer accepts traffic and distributes requests among multiple backend targets.

For example:

```text
                    ┌→ App 1
Client → Load Balancer → App 2
                    └→ App 3
```

The purpose is not simply to "share traffic."

A load balancer can also contribute to:

* Availability
* Horizontal scaling
* Health checking
* TLS termination
* Routing
* Failure isolation

If App 2 becomes unhealthy, the load balancer may temporarily stop sending new traffic to it while continuing to use healthy targets.

---

# Question 23: What is the difference between Layer 4 and Layer 7 load balancing?

## Strong interview answer

Layer 4 load balancing operates primarily using transport-level information such as:

* IP addresses
* TCP
* UDP
* Ports

Layer 7 load balancing understands application protocols such as HTTP and can make routing decisions based on information such as:

* Hostname
* URL path
* HTTP headers
* HTTP methods

For example:

```text
/api/*
     ↓
API servers

/images/*
     ↓
Image service
```

or:

```text
api.example.com
     ↓
API targets

shop.example.com
     ↓
Shop targets
```

That kind of HTTP-aware routing requires application-layer understanding.

---

# Question 24: What is a load balancer health check?

## Strong interview answer

A health check determines whether a backend target should receive traffic.

For an HTTP application, a load balancer might periodically request:

```text
/health
```

on:

```text
port 8080
```

If the expected response is received, the target is considered healthy.

If health checks repeatedly fail, the load balancer may remove that target from normal traffic distribution.

## Important distinction

A server being powered on does not mean it is healthy.

Even this:

```bash
systemctl status myapp
```

showing:

```text
active (running)
```

does not prove the load balancer health check will pass.

The health endpoint itself must respond as expected.

---

# Question 25: All backend servers are running, but the load balancer marks every target unhealthy. What would you check?

## Strong interview answer

If every target suddenly becomes unhealthy, I would look for something common across all targets.

I would verify:

* Health-check protocol
* Health-check port
* Health-check path
* Expected status codes
* Firewall or security rules
* Application listener
* Recent load balancer change
* Recent application deployment

Suppose the health check uses:

```text
GET /health
```

but the application changed the endpoint to:

```text
GET /healthz
```

Now:

```bash
curl http://backend:8080/health
```

returns:

```text
404
```

while:

```bash
curl http://backend:8080/healthz
```

returns:

```text
200
```

The servers are running.

The health-check configuration is stale.

## Interview reasoning

When every target fails at the same time, look for shared dependencies and shared configuration before assuming every machine independently failed.

---

# Question 26: One backend is unhealthy while all other backends are healthy. What does that suggest?

## Strong interview answer

Because the other backends are healthy, I would focus initially on what is different about that target.

I would investigate:

* Application process
* Listening port
* Local firewall
* Configuration
* Deployment version
* Resource exhaustion
* Disk space
* Health endpoint
* Dependencies
* Network interface

For example:

```bash
curl http://unhealthy-server:8080/health
```

If that fails while the same request succeeds against other servers, I have narrowed the problem to that backend or its path.

Comparison with a known-good server is extremely useful.

---

# Question 27: What is TLS termination at a load balancer?

## Strong interview answer

TLS termination means the load balancer handles the TLS connection from the client.

For example:

```text
Client
   ↓
HTTPS :443
   ↓
Load Balancer
TLS terminates here
   ↓
Backend
```

The load balancer holds or references the certificate and decrypts incoming traffic.

Depending on the architecture, communication from the load balancer to the backend may use:

```text
HTTP
```

or:

```text
HTTPS
```

If HTTPS is used again between the load balancer and backend, TLS is established for that connection too.

## Troubleshooting relevance

When investigating a certificate problem, I need to know where TLS terminates.

The certificate may not even exist on the application server.

It may be configured entirely on the load balancer.

---

# Question 28: What is host-based routing?

## Strong interview answer

Host-based routing sends requests to different backends based on the requested hostname.

For example:

```text
api.example.com
       ↓
API Target Group

shop.example.com
       ↓
Shop Target Group
```

A single load balancer may therefore serve multiple applications.

## Troubleshooting scenario

Suppose:

```text
api.example.com
```

accidentally routes to the shop target group.

Users may receive valid HTTP responses but from the wrong application.

That is why "I got HTTP 200" does not always mean the system is correct.

The content and routing must also be correct.

---

# Question 29: What is path-based routing?

## Strong interview answer

Path-based routing sends requests to different backends depending on the URL path.

For example:

```text
/api/*
    ↓
API Service

/images/*
    ↓
Image Service

/payments/*
    ↓
Payment Service
```

This is common with Layer 7 load balancers and reverse proxies.

## Interview scenario

Users report:

```text
/api/orders
```

works, but:

```text
/payments/checkout
```

returns 503.

Because only one path is affected, I would investigate the routing rule and backend serving `/payments/*`.

I would not immediately assume the entire load balancer is broken.

---

# Question 30: What is the difference between 502, 503, and 504 from a load balancer or reverse proxy?

## Strong interview answer

These codes often point toward different upstream problems.

### 502 Bad Gateway

The proxy or gateway could not get a valid response from the upstream service.

Potential causes:

* Application crashed
* Wrong backend port
* Protocol mismatch
* Invalid upstream response
* Connection reset

### 503 Service Unavailable

The requested service is currently unavailable.

In a load-balanced environment, this can happen when there are no usable healthy backends.

### 504 Gateway Timeout

The proxy or gateway waited for the upstream service but did not receive a response before its timeout.

Potential causes:

* Slow application
* Database delay
* External API delay
* Network latency
* Worker exhaustion
* Backend hanging

A good interview answer should use these codes to determine the next investigation rather than simply defining them.

---

# Question 31: The load balancer returns 503, but all EC2 or VM instances are running. Why?

## Strong interview answer

Running infrastructure does not mean healthy application targets.

I would check the load balancer's target health.

Then verify the health check manually.

For example:

```bash
curl -v http://backend-ip:8080/health
```

Possible causes include:

* Application stopped
* Health-check path wrong
* Health-check port wrong
* Firewall blocking load balancer
* Application bound only to localhost
* Health endpoint returns non-success response
* Target registered on wrong port

The key distinction is:

```text
Instance state
≠
Application health
≠
Load balancer target health
```

# Question 32: The load balancer returns 502 immediately after deployment. What would you investigate?

## Strong interview answer

Because the failure started immediately after deployment, I would correlate it with the new application version.

I would inspect:

* Application status
* Application logs
* Listening port
* Backend protocol
* Deployment configuration
* Target health

For example:

```bash
ss -lntp | grep :8080
```

Suppose nothing is listening.

Then:

```bash
systemctl status myapp
```

and:

```bash
journalctl -u myapp -n 100
```

Suppose the deployment changed the application from port:

```text
8080
```

to:

```text
9000
```

but the load balancer still forwards to 8080.

The application may be completely healthy on 9000, but the traffic path is broken.

## Strong troubleshooting principle

Always compare:

```text
Expected configuration
vs.
Actual configuration
```

after a deployment.

# Question 33: Users get 504 errors only during peak traffic. What would you investigate?

## Strong interview answer

The fact that the issue correlates with traffic volume is important.

I would correlate:

* Request rate
* Response latency
* Error rate
* CPU
* Memory
* Worker utilization
* Connection pools
* Database latency
* External API latency

The request path might be:

```text
Load Balancer
      ↓
Application
      ↓
Database
```

The load balancer may wait 30 seconds for the application.

The application may be waiting 40 seconds for a database query.

The user receives 504.

Increasing the load balancer timeout to 60 seconds may reduce 504s, but it does not necessarily fix the underlying performance problem.

The real investigation should determine why the backend becomes slow under load.

---

# Question 34: Some users receive 200 responses while others receive 500 errors. What might cause this?

## Strong interview answer

If traffic is distributed across multiple backend instances, one backend may be unhealthy or misconfigured.

For example:

```text
Load Balancer
   │
   ├── App 1 → 200
   ├── App 2 → 200
   └── App 3 → 500
```

Users routed to App 3 experience failures.

I would compare:

* Application versions
* Configuration
* Environment variables
* Logs
* Dependencies
* Health-check behavior

This is why deployment consistency matters.

## Interview follow-up

### "Why hasn't the load balancer removed App 3?"

Perhaps the health check is too shallow.

For example:

```text
GET /health
→ 200
```

but actual requests fail because the database configuration is wrong.

That introduces an important concept.

A health check must test something meaningful enough to represent the application's ability to serve traffic without becoming so deep that every minor dependency issue causes unnecessary removal.

# Question 35: What is a redirect?

## Strong interview answer

An HTTP redirect tells the client to request another location.

Common redirect codes include:

```text
301
302
307
308
```

For example:

```text
http://example.com
```

might redirect to:

```text
https://example.com
```

I can inspect redirects using:

```bash
curl -I http://example.com
```

I might see:

```text
HTTP/1.1 301 Moved Permanently
Location: https://example.com/
```

To follow redirects:

```bash
curl -L http://example.com
```

## Troubleshooting relevance

Bad redirect configuration can create:

* Redirect loops
* Wrong domains
* HTTP-to-HTTPS problems
* Broken login flows
* Unexpected paths

# Question 36: Users report "too many redirects." What would you investigate?

## Strong interview answer

I would suspect a redirect loop.

For example:

```text
Load Balancer
HTTP → HTTPS redirect
```

while the backend application incorrectly believes the request is HTTP and redirects again.

The flow might become:

```text
Client
  ↓
HTTPS
  ↓
Load Balancer terminates TLS
  ↓
HTTP to backend
  ↓
Backend thinks request is HTTP
  ↓
Redirect to HTTPS
  ↓
Repeat
```

I would inspect:

* Load balancer redirect rules
* Reverse proxy configuration
* Application HTTPS detection
* Forwarded headers
* `X-Forwarded-Proto`

I could inspect headers with:

```bash
curl -I https://app.example.com
```

and follow the chain:

```bash
curl -IL https://app.example.com
```

The important point is to inspect where each redirect originates.

# Question 37: What are `X-Forwarded-For` and `X-Forwarded-Proto`?

## Strong interview answer

When traffic passes through a reverse proxy or load balancer, the backend may otherwise see information about the proxy rather than the original client.

`X-Forwarded-For` is commonly used to pass information about the original client IP through proxies.

`X-Forwarded-Proto` commonly indicates the original protocol, such as:

```text
http
```

or:

```text
https
```

These headers can affect:

* Logging
* Redirects
* Security rules
* Application URL generation

However, applications should trust forwarded headers only from trusted proxies because clients can otherwise spoof such headers.

# Question 38: What is session persistence or sticky sessions?

## Strong interview answer

Sticky sessions cause requests from a particular client or session to continue being routed to the same backend for some period.

For example:

```text
User A → App 1
User A → App 1
User A → App 1

User B → App 2
User B → App 2
```

This can be useful for applications that keep session state locally.

However, it can also hide architectural problems.

If App 1 fails and session state exists only on App 1, the user may lose that state.

Modern scalable architectures often try to externalize session state where appropriate so backend instances can remain more stateless.

For a junior interview, I would understand what stickiness does and why an application might depend on it.

# Question 39: One backend is receiving much more traffic than the others. What would you investigate?

## Strong interview answer

I would inspect:

* Load-balancing algorithm
* Sticky sessions
* Target weights
* Backend health
* Connection reuse
* Long-lived connections
* Unequal target capacity
* Routing rules

For example, if only two of four targets are healthy:

```text
App 1 → Healthy
App 2 → Healthy
App 3 → Unhealthy
App 4 → Unhealthy
```

App 1 and App 2 naturally receive more traffic.

Alternatively, sticky sessions may concentrate traffic.

I would not immediately conclude that the load balancer is malfunctioning.

# Question 40: How would you troubleshoot intermittent HTTP failures behind a load balancer?

## Strong interview answer

Intermittent failures often suggest that only part of the infrastructure is unhealthy.

I would correlate failed requests with individual backend targets.

Suppose:

```text
Request 1 → App 1 → 200
Request 2 → App 2 → 200
Request 3 → App 3 → 500
Request 4 → App 1 → 200
Request 5 → App 3 → 500
```

That pattern strongly suggests App 3.

I would compare:

```text
Application version
Configuration
Environment variables
Logs
Resource usage
Dependencies
```

between App 3 and healthy targets.

This is a useful production troubleshooting principle:

```text
Intermittent failure
+
Multiple backends
=
Compare the backends
```

# Question 41: A backend works directly by IP, but fails through the load balancer. What does that tell you?

## Strong interview answer

It tells me that the backend application is at least capable of responding directly.

I would then investigate what is different in the load-balancer path.

Possible causes include:

* Health-check failure
* Listener rule
* Wrong target port
* Wrong protocol
* Host header behavior
* Security rule
* TLS configuration
* Path-based routing
* Target registration

For example:

```bash
curl http://10.0.2.15:8080/health
```

returns:

```text
200
```

but:

```bash
curl https://app.example.com/health
```

returns:

```text
503
```

The investigation should now focus on the components between the client and backend rather than immediately changing the application.

# Question 42: The load balancer health check succeeds, but real users still fail. How is that possible?

## Strong interview answer

A health check usually tests only a specific request.

For example:

```text
GET /health
```

may return 200.

But users might request:

```text
POST /checkout
```

which depends on:

* Database
* Payment service
* Authentication
* Session store

The health endpoint may not test those dependencies.

Another possibility is that the health check uses:

```text
HTTP :8080
```

while users access:

```text
HTTPS :443
```

and the TLS listener is misconfigured.

Health checks confirm only what they are designed to test.

They do not prove every user journey works.

# Question 43: What is the difference between liveness and readiness conceptually?

## Strong interview answer

Although these terms are strongly associated with container platforms, the concepts apply broadly.

Liveness asks:

```text
Is the application alive?
```

Readiness asks:

```text
Is the application ready to receive traffic?
```

An application process might be alive but still loading configuration, warming caches, establishing database connections, or performing startup work.

During that period:

```text
Alive = yes
Ready = no
```

Sending production traffic too early could cause errors.

Load balancer health checks often need to reflect readiness rather than simply whether a process exists.

# Question 44: Why is `curl` so useful in DevOps troubleshooting?

## Strong interview answer

`curl` allows me to test application endpoints directly and inspect different parts of HTTP and HTTPS communication.

Basic request:

```bash
curl https://app.example.com
```

Verbose:

```bash
curl -v https://app.example.com
```

Headers only:

```bash
curl -I https://app.example.com
```

Follow redirects:

```bash
curl -L https://app.example.com
```

Test a specific path:

```bash
curl -v https://app.example.com/health
```

Send a header:

```bash
curl -H "Host: app.example.com" http://10.0.1.20
```

Measure response information:

```bash
curl -o /dev/null -s \
  -w "HTTP: %{http_code} Total: %{time_total}s\n" \
  https://app.example.com
```

`curl` helps me answer more than:

"Is the website up?"

It can help determine:

* Does DNS resolve?
* Can TCP connect?
* Does TLS work?
* What HTTP status is returned?
* Are redirects happening?
* How long did the request take?

# Question 45: How would you test a backend directly while bypassing DNS or the load balancer?

## Strong interview answer

If the backend exposes HTTP directly and the architecture allows direct testing, I might request its private address:

```bash
curl http://10.0.2.15:8080/health
```

If the application uses virtual-host routing and expects a particular Host header:

```bash
curl \
  -H "Host: app.example.com" \
  http://10.0.2.15:8080/health
```

This can help distinguish:

```text
Application problem
```

from:

```text
Load balancer / DNS / proxy problem
```

I would perform such tests only where network access and operational policy permit them.

# Question 46: DNS resolves correctly and port 443 is reachable, but HTTPS still fails. What layer should you investigate next?

## Strong interview answer

If DNS works and TCP port 443 is reachable, I would investigate TLS.

I could run:

```bash
curl -v https://app.example.com
```

and:

```bash
openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com
```

I would inspect:

* Certificate
* Hostname
* Expiration
* Chain
* TLS negotiation

The troubleshooting progression is:

```text
DNS ✓
TCP 443 ✓
TLS ?
HTTP ?
Application ?
```

This is exactly how layer-by-layer troubleshooting prevents guessing.

# Question 47: HTTPS works, but the application returns HTTP 500. Is the certificate the problem?

## Strong interview answer

Probably not.

If I successfully established HTTPS and received an HTTP 500 response, TLS already completed sufficiently for HTTP communication.

The investigation should move toward the application or its dependencies.

I would check:

* Application logs
* Exceptions
* Database connectivity
* Environment variables
* Secrets
* Recent deployment

This is an important troubleshooting habit.

Once a layer has been reasonably proven to work, move forward rather than repeatedly troubleshooting it without evidence.

# Question 48: Users can reach the homepage but API calls fail. How would you investigate?

## Strong interview answer

I would determine whether the homepage and API follow the same path.

For example:

```text
/
    ↓
Frontend

/api/*
    ↓
API backend
```

The load balancer may have separate path-based routing.

I would test:

```bash
curl -v https://app.example.com/
```

and:

```bash
curl -v https://app.example.com/api/health
```

Then compare the results.

If:

```text
/ → 200
/api/health → 503
```

I would investigate the API target group, health checks, backend application, and routing rule.

The working homepage proves only that one path works.

# Question 49: A deployment succeeds, but users still see the previous application version. What could cause this?

## Strong interview answer

I would consider:

* CDN caching
* Browser caching
* Reverse proxy cache
* DNS still directing some users elsewhere
* Old backend still registered
* Deployment did not reach every backend
* Sticky sessions
* Multiple environments
* Incorrect load balancer target group

For example:

```text
App 1 → Version 2
App 2 → Version 2

```

Users hitting App 3 may still see the old version.

I would verify the deployed version across every target rather than assuming a successful pipeline means every runtime instance is identical.

# Question 50: How would you troubleshoot a complete web application outage from DNS to backend?

This is the kind of question that brings the entire Part 4 together.

## Strong interview answer

I would work from the outside toward the application and test each layer.

### Step 1: DNS

```bash
dig app.example.com
```

or:

```bash
getent hosts app.example.com
```

Confirm:

* Does it resolve?
* Is the returned destination expected?

### Step 2: TCP connectivity

```bash
nc -vz app.example.com 443
```

Can I reach the HTTPS port?

### Step 3: TLS

```bash
openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com
```

Is the correct certificate presented?

### Step 4: HTTP

```bash
curl -v https://app.example.com
```

What status code is returned?

### Step 5: Load balancer

Check:

* Listener
* Routing rules
* Target registration
* Target health
* Health-check configuration

### Step 6: Backend

Test the backend directly where appropriate:

```bash
curl http://backend-ip:8080/health
```

### Step 7: Application

```bash
systemctl status myapp
```

Then:

```bash
journalctl -u myapp -n 100
```

Check listening port:

```bash
ss -lntp | grep :8080
```

### Step 8: Dependencies

If the application is running but unhealthy, investigate:

* Database
* Cache
* Message queue
* External API
* Secrets
* Configuration

This turns one vague statement:

```text
"The website is down."
```

into a series of testable questions.

# Final Production Interview Scenario

The interviewer gives you the following scenario:

> "At 09:10, monitoring reports that checkout is unavailable. Users can open the homepage, but clicking Checkout eventually returns `504 Gateway Timeout`. The application runs behind a load balancer with three backend servers. All three targets are reported healthy. CPU and memory appear normal. A deployment completed at 08:30. Walk me through your investigation."

A weak answer would be:

> "I would restart the servers."

A stronger junior DevOps answer begins with what the evidence already tells us.

The homepage works.

Therefore, the entire site is not unreachable.

Users receive an HTTP 504.

Therefore, they are reaching a gateway or load balancer capable of returning an HTTP response.

All three targets are healthy.

That does not prove checkout works.

Now reproduce the failing request.

```bash
curl -v https://shop.example.com/checkout
```

Measure response time:

```bash
curl -o /dev/null -s \
  -w "HTTP: %{http_code} Total: %{time_total}s\n" \
  https://shop.example.com/checkout
```

Suppose it consistently fails after approximately 30 seconds.

That timeout duration is useful evidence.

Now determine how `/checkout` is routed.

Perhaps:

```text
/
    ↓
Frontend target group

/checkout
    ↓
Checkout target group
```

If so, the homepage and checkout may not even use the same backend.

Test the checkout backend directly where appropriate.

```bash
curl -v http://checkout-backend:8080/health
```

Suppose:

```text
200 OK
```

But remember:

```text
/health works
```

does not mean:

```text
/checkout works
```

Test the actual application route if safe and appropriate.

Then inspect application logs around the request.

```bash
journalctl -u checkout \
  --since "2026-08-11 09:00:00"
```

Suppose the logs show:

```text
Database query timeout
Database query timeout
Database query timeout
```

Now the investigation moves downstream.

The request path may actually be:

```text
User
 ↓
Load Balancer
 ↓
Checkout Application
 ↓
Database
```

The load balancer is waiting for checkout.

Checkout is waiting for the database.

Eventually, the load balancer reaches its timeout and returns:

```text
504 Gateway Timeout
```

Now correlate the problem with the 08:30 deployment.

Perhaps the new version introduced:

* An inefficient query
* Wrong database endpoint
* Reduced connection-pool size
* Missing index dependency
* Incorrect timeout
* Retry behavior

The deployment timestamp does not prove the deployment caused the incident, but it is highly relevant evidence.

The strongest answer would sound something like:

> "Because users receive 504 rather than a DNS or connection error, I know the request is reaching a gateway. I would identify which component returns the 504, reproduce the failing path, measure how long it takes, verify its routing and target group, and then test the actual checkout backend rather than relying only on its health check. If the backend receives the request but waits on a dependency, I would trace that dependency. I would also correlate the issue with the 08:30 deployment and compare the new version with the previous working version."

That is the reasoning interviewers want.

Not:

```text
504 = restart Nginx
```

But:

```text
504
 ↓
Which gateway?
 ↓
Which upstream?
 ↓
Did upstream receive request?
 ↓
What was upstream waiting for?
 ↓
What changed?
 ↓
What evidence confirms root cause?
```

# What Junior DevOps Candidates Should Learn From Part 4

When troubleshooting web traffic, think about the request as a journey.

```text
DNS
 ↓
IP
 ↓
Port
 ↓
TCP
 ↓
TLS
 ↓
HTTP
 ↓
Load Balancer
 ↓
Routing Rule
 ↓
Health Check
 ↓
Backend
 ↓
Application
 ↓
Dependency
```

Every layer gives you evidence.

If DNS fails:

```text
Do not troubleshoot the application first.
```

If TCP port 443 times out:

```text
Do not troubleshoot HTTP status codes yet.
```

If TLS fails:

```text
Do not start debugging database queries.
```

If you receive HTTP 500:

```text
Basic HTTP communication succeeded.
Investigate the server/application.
```

If you receive 502:

```text
Investigate gateway-to-upstream communication.
```

If you receive 503:

```text
Investigate service availability and healthy backends.
```

If you receive 504:

```text
Investigate why the upstream response did not arrive in time.
```

Useful tools from this part include:

```bash
dig
getent
nslookup
curl
ss
nc
openssl
lsof
systemctl
journalctl
```

But again, commands are only tools.

The more important skill is knowing what each result proves and what it does not prove.

For example:

```text
dig succeeds
```

proves DNS returned an answer.

It does not prove the application works.

```text
nc reaches port 443
```

shows TCP connectivity to that port.

It does not prove TLS works.

```text
TLS succeeds
```

does not prove the application is healthy.

```text
HTTP 200 from /health
```

does not prove checkout works.

```text
Load balancer target = healthy
```

does not prove every user workflow works.

This distinction between infrastructure availability and actual application behavior is one of the most important habits a junior DevOps engineer can develop.
