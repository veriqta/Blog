# Part 1: Linux and Command-Line Troubleshooting

Linux troubleshooting is one of the most common areas tested in DevOps interviews because Linux sits underneath a large part of modern infrastructure. Virtual machines, container hosts, Kubernetes nodes, CI/CD runners, monitoring servers, databases, and cloud workloads frequently run on Linux.

For a junior DevOps engineer, an interviewer usually does not expect you to know every Linux command from memory. What matters more is whether you can investigate a problem logically.

If someone tells you, "The server is slow," immediately running ten unrelated commands is not a strong troubleshooting strategy.

A better engineer starts by asking:

What changed?

When did the problem begin?

Is the problem affecting the entire server or one application?

Is the bottleneck CPU, memory, disk, network, or something inside the application?

What evidence supports the conclusion?

The following questions are representative of the scenario-based Linux problems a junior DevOps candidate should be prepared to reason through.

---

# Question 1: A Linux server suddenly becomes very slow. How would you troubleshoot it?

## What the interviewer is testing

The interviewer wants to see whether you can troubleshoot systematically instead of guessing.

A strong junior candidate should understand that "the server is slow" is a symptom, not a diagnosis.

Possible causes include:

* High CPU utilization
* Memory pressure
* Swap activity
* Disk exhaustion
* Inode exhaustion
* Heavy disk I/O
* Too many processes
* A runaway application
* Network problems
* A failing dependency
* Recent deployments
* Scheduled jobs
* Hardware or virtual infrastructure problems

## Strong interview answer

I would first establish the scope and timing of the problem. I would ask when the slowdown started, whether every application on the server is affected, and whether anything changed recently, such as a deployment, configuration change, package update, backup, or scheduled job.

Then I would check the server's overall health.

I might begin with:

```bash
uptime
```

This gives me the current uptime and load averages.

Next:

```bash
top
```

or:

```bash
htop
```

if `htop` is installed.

I would look at CPU consumption, memory usage, process states, load average, and which processes are consuming the most resources.

For memory:

```bash
free -h
```

For filesystem capacity:

```bash
df -h
```

For inode usage:

```bash
df -i
```

For processes consuming CPU:

```bash
ps aux --sort=-%cpu | head
```

For processes consuming memory:

```bash
ps aux --sort=-%mem | head
```

If I suspect disk I/O:

```bash
iostat -xz 1
```

If available, I could also use:

```bash
vmstat 1
```

I would then investigate whichever subsystem shows abnormal behavior instead of continuing to run commands without a hypothesis.

For example, if one Java process is consuming most of the CPU, my investigation shifts toward that process and the application it belongs to.

If CPU utilization is normal but I/O wait is high, I investigate storage.

If memory is exhausted and swap usage is increasing, I investigate memory pressure.

If system resources look healthy, I start looking at the application, network connections, dependencies, and logs.

## Why `uptime` matters

Example:

```text
10:32:11 up 31 days, 4:16, 3 users, load average: 8.20, 7.91, 6.70
```

The three load averages roughly represent the average system load over the last 1, 5, and 15 minutes.

A high load average does not automatically mean high CPU usage.

Processes waiting for CPU contribute to load, but processes waiting in uninterruptible sleep, commonly because of I/O, can also contribute.

That distinction becomes important during troubleshooting.

## Production scenario

Imagine a server normally has a load average around 1 to 2.

At 02:00, monitoring shows the load suddenly increasing to 12.

You check:

```bash
top
```

CPU utilization is not particularly high.

You then run:

```bash
vmstat 1
```

and notice significant I/O wait.

You investigate disk activity and discover that a backup job started at 02:00 and is generating heavy disk activity.

The important interview point is not knowing a magical command.

It is demonstrating the reasoning:

```text
Slow server
    |
    +-- CPU?
    |
    +-- Memory?
    |
    +-- Disk capacity?
    |
    +-- Disk I/O?
    |
    +-- Network?
    |
    +-- Application?
    |
    +-- External dependency?
```

## Interviewer follow-up

### "CPU utilization is only 25 percent, but the server is still slow. What would you investigate?"

I would not conclude that the server is healthy just because CPU utilization is low.

I would investigate memory pressure, swap, disk I/O, network latency, blocked processes, filesystem capacity, and application dependencies.

I would also inspect load average and process states.

## Common candidate mistake

Saying:

"I would restart the server."

Restarting may temporarily remove the symptom, but it can also destroy useful evidence and does not explain the root cause.

A restart should not be the first troubleshooting step unless the situation specifically requires immediate recovery and the operational procedure supports it.

# Question 2: The filesystem is 100 percent full. What would you do?

## Strong interview answer

First, I would identify which filesystem is full.

```bash
df -h
```

For example:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/xvda1       40G   40G     0 100% /
```

Now I know the root filesystem is full.

Next, I would determine which directories are consuming space.

For example:

```bash
sudo du -xhd1 / 2>/dev/null | sort -h
```

If `/var` is unusually large:

```bash
sudo du -xhd1 /var 2>/dev/null | sort -h
```

Then continue narrowing the search.

If `/var/log` is responsible:

```bash
sudo du -sh /var/log/*
```

I could also search for unusually large files:

```bash
sudo find / -xdev -type f -size +1G -ls 2>/dev/null
```

But I would not immediately delete the largest file.

First I need to understand what created it.

It could be:

* Application logs
* System logs
* Database files
* Container data
* Temporary files
* Backups
* Core dumps
* Package caches
* Build artifacts

Deleting a production database file because it is large would obviously be disastrous.

## What if logs caused the problem?

Suppose:

```bash
du -sh /var/log/*
```

reveals:

```text
27G /var/log/application.log
```

I would investigate why the application generated 27 GB of logs.

The immediate issue is disk capacity.

The underlying issue might be:

* Debug logging accidentally enabled
* Repeated application exceptions
* Broken log rotation
* A retry loop
* An application generating excessive requests
* Misconfigured retention

A complete fix therefore might involve both recovering space safely and fixing the logging behavior.

## Interviewer follow-up

### "How would you prevent this from happening again?"

Depending on the environment, I would consider:

* Proper log rotation
* Log retention policies
* Disk usage monitoring
* Alerts before the filesystem becomes critical
* Centralized logging
* Application log-level controls
* Investigating abnormal log growth

The goal is to detect the condition before the filesystem reaches 100 percent.

# Question 3: `df` says the disk is full, but `du` cannot find enough files to explain the usage. What could be happening?

This is a particularly useful Linux troubleshooting question because it tests whether the candidate understands how Linux handles open files.

## Strong interview answer

One possibility is that a large file was deleted while a running process still has the file open.

On Linux, removing the filename does not necessarily immediately release the disk blocks if a process still holds an open file descriptor to that file.

I would check for deleted but still open files using:

```bash
sudo lsof +L1
```

Another common approach is:

```bash
sudo lsof | grep deleted
```

If I find something like:

```text
java  4271 app  12w  REG  ... /var/log/application.log (deleted)
```

then process 4271 still has the deleted file open.

## Why does this happen?

Consider an application writing to:

```text
/var/log/application.log
```

The file grows to 20 GB.

Someone deletes it:

```bash
rm /var/log/application.log
```

The filename disappears.

But the application still has an open file descriptor pointing to the underlying file.

`du` may no longer see the deleted pathname in its normal directory traversal.

The filesystem, however, may still have those blocks allocated.

Therefore:

```bash
df -h
```

continues reporting high usage.

## What would you do?

I would identify the process and understand the service before taking action.

Depending on the application, the safe solution might involve:

* Making the application reopen its logs
* Properly rotating the logs
* Gracefully restarting the affected service during an appropriate operational window

I would not blindly kill the process.

## Interviewer follow-up

### "Why is deleting a massive active log file with `rm` sometimes not enough?"

Because the running process may still hold an open file descriptor to the deleted file, so the filesystem cannot reclaim the blocks yet.

This is exactly the kind of explanation that demonstrates Linux understanding rather than command memorization.

# Question 4: An application service was working yesterday, but today it will not start. Walk me through your investigation.

## Strong interview answer

I would first determine how the service is managed.

If it is a systemd service:

```bash
systemctl status myapp
```

This gives me an initial view of whether the service is active, failed, or repeatedly restarting.

Then I would inspect its logs:

```bash
journalctl -u myapp
```

For recent entries:

```bash
journalctl -u myapp -n 100
```

For logs from the current boot:

```bash
journalctl -u myapp -b
```

I would look for specific errors rather than immediately restarting the service.

Possible causes include:

* Invalid configuration
* Missing configuration file
* Incorrect permissions
* Missing environment variable
* Port conflict
* Expired certificate
* Disk full
* Dependency unavailable
* Failed package update
* Application binary missing
* Incorrect ownership
* Database unavailable
* Secret or credential problem

## Suppose the logs say:

```text
bind: address already in use
```

Now I have a specific hypothesis.

If the application should listen on port 8080:

```bash
sudo ss -lntp | grep :8080
```

I can determine whether another process already owns the port.

## Suppose the logs say:

```text
Permission denied: /etc/myapp/config.yaml
```

Then I investigate:

```bash
ls -l /etc/myapp/config.yaml
```

I would check the service's user:

```bash
systemctl cat myapp
```

and determine whether that user can access the file and its parent directories.

## The important troubleshooting pattern

Do not do this:

```text
Service failed
→ restart
→ restart again
→ reboot
```

Do this:

```text
Service failed
→ inspect status
→ inspect logs
→ identify error
→ form hypothesis
→ verify hypothesis
→ fix underlying cause
→ start service
→ validate application
```

# Question 5: A user says they cannot SSH into a Linux server, but other users can. How would you troubleshoot it?

## What the interviewer should hear

The fact that other users can connect changes the investigation.

If everyone could not connect, I would suspect the server, network, firewall, SSH daemon, or port.

But if only one user is affected, I would initially focus more heavily on user-specific authentication and authorization.

## Strong interview answer

I would first get the exact error.

There is a big difference between:

```text
Connection timed out
```

and:

```text
Permission denied (publickey)
```

For additional client-side detail:

```bash
ssh -v user@server
```

For even more verbosity:

```bash
ssh -vvv user@server
```

If the connection reaches the SSH server but authentication fails, I would check:

* Correct username
* Account existence
* Account status
* SSH key
* `authorized_keys`
* File ownership
* File permissions
* SSH configuration restrictions
* Authentication logs

On the server:

```bash
id username
```

Check the account:

```bash
getent passwd username
```

Check SSH directory permissions:

```bash
ls -ld /home/username
ls -ld /home/username/.ssh
ls -l /home/username/.ssh/authorized_keys
```

Typical secure permissions commonly include:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Ownership must also be correct.

For example:

```bash
chown -R username:username /home/username/.ssh
```

I would inspect SSH logs as appropriate for the distribution.

For example:

```bash
journalctl -u sshd
```

or:

```bash
journalctl -u ssh
```

Some distributions also maintain authentication logs under `/var/log`.

## Interviewer follow-up

### "What if the user receives `Connection timed out`?"

That changes my investigation.

A timeout suggests that I may need to investigate network reachability, routing, firewall rules, security controls, the destination address, and whether the SSH service is reachable on the expected port.

The exact error message matters.

# Question 6: A process is using almost 100 percent CPU. What would you do?

## Strong interview answer

I would first identify the process.

```bash
top
```

or:

```bash
ps aux --sort=-%cpu | head
```

Suppose I find:

```text
appuser  4728 ... 98.7 ... java ...
```

I now know which process deserves investigation.

But I would not immediately run:

```bash
kill -9 4728
```

I would first determine:

* What application owns the process?
* Is this CPU usage expected?
* When did it begin?
* Is customer traffic unusually high?
* Was there a recent deployment?
* Is the process stuck in a loop?
* Are multiple instances affected?
* What do the application logs show?

I can inspect the process:

```bash
ps -fp 4728
```

Check its command line:

```bash
cat /proc/4728/cmdline
```

Check open files if needed:

```bash
lsof -p 4728
```

## Why `kill -9` should not be your first response

`SIGKILL` immediately terminates the process and cannot be handled by the process.

A graceful termination normally gives an application the opportunity to clean up.

For example:

```bash
kill 4728
```

sends `SIGTERM` by default.

If a process genuinely needs to be terminated and does not respond to graceful termination, stronger measures may eventually be required.

But in an interview, saying "I always use `kill -9`" suggests poor operational judgment.

# Question 7: The server is running out of memory. How would you determine what is happening?

## Strong interview answer

I would start with:

```bash
free -h
```

But I would be careful interpreting Linux memory statistics.

Linux uses available memory for filesystem caching, so seeing a small value under `free` memory does not automatically mean the system is in trouble.

I would pay particular attention to available memory and swap behavior.

Then:

```bash
ps aux --sort=-%mem | head
```

This identifies processes consuming significant memory.

I could also inspect:

```bash
top
```

and:

```bash
vmstat 1
```

If swap is configured, I can check:

```bash
swapon --show
```

I would also investigate whether the kernel has invoked the Out Of Memory killer.

For example:

```bash
journalctl -k | grep -i -E "oom|out of memory|killed process"
```

or inspect kernel messages where appropriate.

## What could cause memory pressure?

Possibilities include:

* Memory leak
* Unexpected traffic
* Oversized application cache
* Too many worker processes
* Incorrect application memory limits
* Multiple applications competing for memory
* Large batch job
* Database workload
* Misconfigured service
* Capacity that is simply too small for the workload

## Interviewer follow-up

### "What is swap?"

Swap is disk-backed space that Linux can use as part of virtual memory management when memory pages are moved out of RAM.

Because storage is much slower than RAM, heavy swapping can seriously affect performance.

I would not treat "add more swap" as the automatic solution to every memory problem. I would investigate why the system is under memory pressure.

# Question 8: You kill a process, but a few seconds later it comes back. Why?

## Strong interview answer

Something may be supervising and restarting the process.

For example:

* systemd
* A process supervisor
* Docker
* Kubernetes
* Another orchestration system
* A cron job or scheduled mechanism
* A parent process
* Application-specific watchdog

If I kill the process without understanding what manages it, the supervisor may simply create another instance.

I would inspect the process:

```bash
ps -fp PID
```

and its parent:

```bash
ps -o pid,ppid,cmd -p PID
```

I could inspect the process tree:

```bash
pstree -p
```

If it is managed by systemd:

```bash
systemctl status service-name
```

The correct operational action usually involves managing the service through its supervisor rather than repeatedly killing child processes.

## Interviewer follow-up

### "Why is the PID different after it returns?"

Because the original process terminated and a new process was created. The new process receives a new process ID.

# Question 9: A cron job works when you execute the command manually but fails when cron runs it. Why?

This is a classic Linux interview scenario.

## Strong interview answer

Cron executes commands in a different environment from an interactive shell.

The command may depend on:

* `PATH`
* Environment variables
* Current working directory
* Shell configuration
* Credentials
* File permissions
* Relative paths
* User context

For example, suppose this works manually:

```bash
python backup.py
```

But cron fails.

The script might rely on the shell's current directory.

A more reliable cron entry might use absolute paths:

```bash
/usr/bin/python3 /opt/scripts/backup.py
```

I would also redirect output for troubleshooting:

```bash
/usr/bin/python3 /opt/scripts/backup.py >> /var/log/backup-job.log 2>&1
```

Then I have evidence about what happened.

I would check the cron configuration and logs available on the distribution.

## Another common problem

The interactive shell may have:

```bash
PATH=/usr/local/bin:/usr/bin:/bin
```

while the cron environment may have a more limited `PATH`.

A command available interactively may therefore not resolve the same way under cron.

## Strong takeaway

When automation behaves differently from manual execution, always compare the execution environments.

This lesson extends beyond cron to CI/CD pipelines, containers, systemd services, and Kubernetes workloads.

# Question 10: A developer says "Permission denied" when accessing a file. How would you investigate?

## Strong interview answer

I would identify:

1. Which user is performing the operation
2. Which file or directory is involved
3. Whether the operation is read, write, or execute
4. Ownership and group membership
5. Permissions on the target and parent directories

First:

```bash
whoami
```

or:

```bash
id
```

Then:

```bash
ls -l /path/to/file
```

Example:

```text
-rw-r----- 1 appuser appgroup 2048 Aug 11 10:00 config.yaml
```

This tells me:

* Owner: `appuser`
* Group: `appgroup`
* Owner permissions: read and write
* Group permissions: read
* Others: no permissions

I would check whether the affected user belongs to the appropriate group:

```bash
id username
```

I would also inspect parent directory permissions:

```bash
namei -l /path/to/file
```

if `namei` is available.

## Why parent directories matter

A user may have permission on a file but still be unable to reach it because they lack the necessary directory permissions somewhere in the path.

That is an important distinction.

## What I would not do

I would not immediately run:

```bash
chmod 777 file
```

`777` grants read, write, and execute permissions to everyone.

That may hide the immediate symptom while creating an unnecessary security problem.

A DevOps engineer should determine the required access and grant only the permissions that are actually needed.

# Question 11: A service is running, but nothing is listening on the port you expect. How would you troubleshoot it?

## Strong interview answer

First, I would confirm the service state:

```bash
systemctl status myapp
```

Then determine what is listening:

```bash
ss -lntp
```

If I expect port 8080:

```bash
ss -lntp | grep :8080
```

If nothing is listening, I would inspect the application logs and configuration.

The service process existing does not necessarily mean the application initialized successfully.

For example, the process may be:

* Still starting
* Waiting for a dependency
* Listening on another port
* Bound to a different interface
* Partially initialized
* Running a wrapper process while the actual application failed

## Binding matters

Consider:

```text
127.0.0.1:8080
```

versus:

```text
0.0.0.0:8080
```

An application listening only on `127.0.0.1` is bound to the loopback interface.

That can explain why:

```bash
curl http://localhost:8080
```

works locally while remote clients cannot connect.

I would confirm the intended binding before changing anything.

# Question 12: The load average is high, but CPU utilization is low. How can that happen?

## Strong interview answer

Load average is not simply CPU utilization.

Linux load includes tasks that are runnable and tasks in certain uninterruptible waiting states, commonly associated with I/O.

Therefore, a system can have high load while CPUs are not fully utilized.

I would investigate process states and I/O.

Useful commands include:

```bash
top
```

```bash
vmstat 1
```

```bash
iostat -xz 1
```

and:

```bash
ps -eo state,pid,ppid,comm,wchan:32
```

depending on the investigation.

If many processes are stuck waiting for storage, the system may feel extremely slow while CPU utilization remains relatively low.

## Production example

Imagine a database server whose storage suddenly experiences severe latency.

Application processes wait for database or filesystem operations.

Requests accumulate.

Load increases.

CPU usage remains moderate.

Looking only at CPU would lead you in the wrong direction.

This is why good troubleshooting uses multiple signals.

# Question 13: An application works locally on the Linux server, but users on other machines cannot reach it. What would you check?

## Strong interview answer

I would separate application health from network reachability.

First, from the server itself:

```bash
curl -v http://localhost:8080
```

If that succeeds, I know the application is at least responding locally.

Then I would check what address and port it is listening on:

```bash
ss -lntp | grep :8080
```

If I see:

```text
127.0.0.1:8080
```

the application is listening only on loopback.

If it is correctly listening on an externally reachable interface, I would continue investigating:

* Host firewall
* Cloud security rules
* Network ACLs where applicable
* Routing
* Load balancer configuration
* DNS
* Proxy configuration
* Container networking if applicable

I would test from another machine:

```bash
curl -v http://server-ip:8080
```

If basic reachability needs investigation, I could use appropriate network tools such as:

```bash
ping server-ip
```

where ICMP is permitted, and:

```bash
nc -vz server-ip 8080
```

where `nc` is available and such testing is appropriate.

## Why this is a strong answer

It isolates layers.

```text
Application
    ↓
Listening socket
    ↓
Host
    ↓
Firewall/security controls
    ↓
Network path
    ↓
Load balancer/proxy
    ↓
DNS
    ↓
Client
```

That is much stronger than saying, "I would check the firewall."

# Question 14: DNS resolution is failing on a Linux server. How would you investigate?

## Strong interview answer

First, I would establish whether the problem is DNS specifically or general network connectivity.

For example:

```bash
curl -v https://example.com
```

If the error indicates that the hostname cannot be resolved, DNS becomes a strong suspect.

I could test resolution using tools available on the machine:

```bash
dig example.com
```

or:

```bash
nslookup example.com
```

I could also use:

```bash
getent hosts example.com
```

which can be useful because applications often rely on the system's configured name-service resolution rather than calling `dig`.

I would inspect resolver configuration.

On many systems:

```bash
cat /etc/resolv.conf
```

On systems using systemd-resolved, I might inspect:

```bash
resolvectl status
```

I would determine:

* Which DNS server is configured?
* Can the server reach it?
* Is the problem affecting one hostname or all hostnames?
* Does another DNS server return an answer?
* Is the application using cached DNS information?
* Was DNS configuration recently changed?

## Interviewer follow-up

### "The server can reach `8.8.8.8`, but `google.com` does not resolve. What does that suggest?"

It suggests basic IP connectivity may exist while name resolution is failing.

I would investigate the configured DNS resolver and the path to that resolver.

I would still avoid concluding too much from one test, but it significantly narrows the problem.

# Question 15: You have five minutes to determine whether a Linux server is healthy. What do you check?

This is an excellent closing question because it forces the candidate to prioritize.

## Strong interview answer

If I truly had only five minutes, I would perform a fast health assessment rather than attempting a complete audit.

I would start with:

```bash
uptime
```

I want uptime and load.

Then:

```bash
top
```

I want an immediate picture of CPU, memory, processes, and system activity.

Then:

```bash
free -h
```

I want to understand memory availability and swap.

Then:

```bash
df -h
```

I want to know whether any important filesystem is approaching capacity.

Then:

```bash
df -i
```

because a filesystem can have free disk capacity but run out of inodes.

I would check failed services:

```bash
systemctl --failed
```

I would inspect recent high-priority logs where appropriate:

```bash
journalctl -p err -n 50
```

I would inspect the most resource-intensive processes:

```bash
ps aux --sort=-%cpu | head
```

and:

```bash
ps aux --sort=-%mem | head
```

If the machine hosts a known application, I would also check that application's actual health endpoint or service.

For example:

```bash
curl -f http://localhost:8080/health
```

if that is the application's documented health endpoint.

## But there is an important distinction

A server looking healthy does not prove that the service is healthy.

Imagine:

```text
CPU: 10%
Memory: healthy
Disk: 45%
Load: normal
No failed systemd services
```

Everything appears fine.

But customers are receiving HTTP 500 responses because the application cannot connect to its database.

Infrastructure health and application health are related, but they are not the same thing.

A good DevOps engineer learns to distinguish them.

# Bonus Question 16: A command returns "command not found." How would you troubleshoot it?

## Strong interview answer

I would first determine whether the program is installed and whether the shell can find it through `PATH`.

Check:

```bash
echo "$PATH"
```

Then:

```bash
command -v commandname
```

or:

```bash
which commandname
```

where appropriate.

If the binary exists but its directory is not in `PATH`, calling the binary with its full path may work.

For example:

```bash
/usr/local/bin/mytool
```

I would not blindly modify the global `PATH` before understanding how the application or user environment is configured.

This issue frequently appears in automation because interactive and non-interactive environments may have different environment variables.

# Bonus Question 17: How would you find a specific error inside a very large log file?

## Strong interview answer

I would avoid opening a multi-gigabyte log file in an editor if I only need specific information.

If I know the error text:

```bash
grep -i "connection refused" application.log
```

For line numbers:

```bash
grep -in "connection refused" application.log
```

For surrounding context:

```bash
grep -in -B 5 -A 10 "connection refused" application.log
```

I could inspect the latest entries:

```bash
tail -n 100 application.log
```

Or follow new entries:

```bash
tail -f application.log
```

If I am investigating a specific time window, I would narrow the search using the timestamp format used by the application.

## What matters in an interview

The strongest answer is not:

"I know `grep`."

It is:

"I reduce the amount of data until I can correlate the error with the time the incident occurred."

That is troubleshooting.

# Bonus Question 18: How would you find a file on a Linux server when you do not know where it is?

## Strong interview answer

If I know the filename:

```bash
find / -name "application.conf" 2>/dev/null
```

For case-insensitive matching:

```bash
find / -iname "application.conf" 2>/dev/null
```

If I want to search only under `/etc`:

```bash
find /etc -name "*.conf" 2>/dev/null
```

If `locate` is installed and its database is current:

```bash
locate application.conf
```

The difference matters because `find` searches the filesystem hierarchy directly, while `locate` typically searches an indexed database and may therefore not immediately know about newly created files.

# Bonus Question 19: A Linux server rebooted unexpectedly. How would you investigate what happened?

## Strong interview answer

I would first confirm the reboot and establish when it happened.

```bash
uptime
```

Then:

```bash
last reboot
```

I would inspect logs from the previous boot if they are available:

```bash
journalctl -b -1
```

For kernel messages from the previous boot:

```bash
journalctl -k -b -1
```

I would look for evidence of:

* Kernel problems
* Out-of-memory events
* Shutdown requests
* Service failures
* Infrastructure events
* Automation
* Administrative actions

I would also correlate the reboot time with monitoring, cloud platform events, deployment systems, and change records where those systems exist.

## Why this answer matters

The Linux machine is only one source of evidence.

If the server is an EC2 instance, VM, or part of another infrastructure platform, events outside the guest operating system can matter too.

That broader thinking is something a junior engineer should begin developing early.

# Bonus Question 20: A production command accidentally generates thousands of lines of output. How would you handle large command output safely?

## Strong interview answer

I would avoid letting huge output flood the terminal when I only need a small portion.

For example:

```bash
command | head
```

or:

```bash
command | tail
```

For interactive reading:

```bash
command | less
```

For filtering:

```bash
command | grep "pattern"
```

If I need to preserve the output:

```bash
command > output.txt
```

To redirect both standard output and standard error in Bash:

```bash
command > output.txt 2>&1
```

To append rather than overwrite:

```bash
command >> output.txt 2>&1
```

This leads into an important Linux concept for DevOps engineers.

Linux commands commonly work with three standard streams:

```text
0 = standard input
1 = standard output
2 = standard error
```

Understanding pipes and redirection becomes extremely useful when building shell scripts, CI/CD jobs, operational tooling, and troubleshooting workflows.

# Final Interview Scenario

The interviewer gives you the following situation:

> "At 10:15 AM, monitoring reports that a production Linux server is responding slowly. Customers say the application sometimes times out. You SSH into the server. You have not been told what is wrong. Walk me through exactly what you do."

A strong junior DevOps candidate should resist the temptation to guess.

Your response might begin:

"I would first establish the scope and timeline. I want to know whether the problem began suddenly, whether all users are affected, and whether a deployment or infrastructure change occurred around 10:15."

Then begin your investigation.

```bash
uptime
```

Check load and uptime.

```bash
top
```

Check overall CPU, memory, process activity, and process states.

```bash
free -h
```

Check memory availability.

```bash
df -h
```

Check filesystem capacity.

```bash
df -i
```

Check inode capacity.

```bash
ps aux --sort=-%cpu | head
```

Identify CPU-heavy processes.

```bash
ps aux --sort=-%mem | head
```

Identify memory-heavy processes.

If storage performance looks suspicious:

```bash
vmstat 1
```

and, where available:

```bash
iostat -xz 1
```

Check the affected service:

```bash
systemctl status myapp
```

Check recent logs:

```bash
journalctl -u myapp -n 100
```

Check whether the application is listening:

```bash
ss -lntp
```

Test the application locally:

```bash
curl -v http://localhost:8080/health
```

But the commands are not the answer.

The investigation is the answer.

A candidate who simply recites 15 commands has demonstrated command familiarity.

A candidate who says:

> "If the local health endpoint responds quickly but customers still experience timeouts, I would start moving outward from the application. I would investigate the listening socket, reverse proxy or load balancer, network path, DNS, and downstream dependencies. If the local request is also slow, I would continue investigating the application and host resources."

has demonstrated troubleshooting reasoning.

That distinction matters in a technical interview.

# What Junior DevOps Candidates Should Learn From Part 1

You do not need to memorize every Linux command available.

You should understand how to move from a vague symptom to evidence.

When something fails, think in this order:

```text
1. What exactly is the symptom?

2. When did it start?

3. What changed?

4. What is affected?

5. Can I reproduce it?

6. Which layer appears unhealthy?

7. What evidence confirms that?

8. What is the safest corrective action?

9. Did the corrective action actually restore service?

10. What caused the problem, and how can we prevent recurrence?
```

That troubleshooting process is more important than memorizing a long list of commands.

Linux gives you tools such as:

```text
uptime
top
ps
free
df
du
find
grep
journalctl
systemctl
ss
lsof
vmstat
iostat
curl
dig
```

But tools only provide evidence.

The engineer still has to interpret that evidence.

A junior candidate who understands this principle is already moving beyond "I know Linux commands" toward "I can troubleshoot Linux systems."

That is the skill interviewers are ultimately trying to uncover.
