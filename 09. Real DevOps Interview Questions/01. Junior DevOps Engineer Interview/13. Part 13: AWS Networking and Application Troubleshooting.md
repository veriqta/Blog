# Part 13: AWS Networking and Application Troubleshooting

AWS networking interview questions become much more practical when the interviewer stops asking:

"What is a VPC?"

"What is a subnet?"

"What is a route table?"

Instead, you may hear:

> "The application works from inside the EC2 instance, but users cannot reach it through the ALB. Walk me through your investigation."

Or:

> "Instances in a private subnet can reach the database but cannot download packages from the internet. What would you check?"

Or:

> "The ALB reports healthy targets, but users intermittently receive 502 errors. Where do you start?"

These questions test whether you understand the complete request path.

A useful mental model is:

```text
User
 ↓
DNS
 ↓
Route 53
 ↓
Internet
 ↓
Application Load Balancer
 ↓
Security Group
 ↓
Target Group
 ↓
EC2 / Container
 ↓
Application
 ↓
Database / Cache / API
```

When production fails, do not immediately change the security group.

Determine how far the request travels successfully.

---

# 1. A user cannot reach an application running on EC2. How would you troubleshoot it?

## Strong interview answer

I would troubleshoot layer by layer.

First, establish the symptom.

```text
Does DNS resolve?
      ↓
Can the client reach the endpoint?
      ↓
Does the ALB receive the request?
      ↓
Does the target receive it?
      ↓
Is the application listening?
      ↓
Can the application reach dependencies?
```

I would check:

1. DNS resolution.
2. Route 53 record.
3. ALB listener.
4. ALB security group.
5. Target group health.
6. EC2 security group.
7. Network ACL.
8. Route table.
9. Application port.
10. Application process.
11. Host firewall.
12. Application logs.
13. Downstream dependencies.

The error also matters.

```text
DNS failure
→ investigate name resolution

Connection timeout
→ investigate network path

Connection refused
→ investigate listener/application

HTTP 502
→ investigate load balancer-to-target/application behavior

HTTP 503
→ investigate target availability/capacity

HTTP 5xx from application
→ investigate application/dependencies
```

The goal is to narrow the failure domain before making changes.

---

# 2. What is an AWS VPC?

## Strong interview answer

A Virtual Private Cloud is a logically isolated network environment in AWS where you define networking for resources.

A VPC contains components such as:

```text
VPC
├── CIDR ranges
├── Subnets
├── Route tables
├── Security groups
├── Network ACLs
├── Internet Gateway
├── NAT Gateway
├── VPC endpoints
└── Other connectivity components
```

I think of the VPC as the network boundary within which AWS resources communicate according to the routing and security controls we configure.

---

# 3. What is a subnet?

## Strong interview answer

A subnet is a range of IP addresses within a VPC.

Resources such as EC2 instances are launched into subnets.

For example:

```text
VPC
10.0.0.0/16

├── Public Subnet A
│   10.0.1.0/24
│
├── Private Subnet A
│   10.0.2.0/24
│
├── Public Subnet B
│   10.0.3.0/24
│
└── Private Subnet B
    10.0.4.0/24
```

Subnets also belong to individual Availability Zones.

That becomes important when designing highly available architectures.

---

# 4. What actually makes a subnet public?

## Strong interview answer

A subnet is generally considered public when its route table provides a route to an Internet Gateway.

For example:

```text
Destination        Target

10.0.0.0/16        local
0.0.0.0/0          igw-xxxx
```

But this does not mean every resource in the subnet is automatically accessible from the internet.

An EC2 instance may still require:

```text
Public IPv4 address
        +
Correct route
        +
Security Group
        +
NACL
        +
Listening application
```

So:

```text
Public subnet
≠
Publicly accessible EC2
```

---

# 5. What makes a subnet private?

## Strong interview answer

A private subnet does not provide its resources with a direct inbound path from the public internet through an Internet Gateway.

A typical application architecture might look like:

```text
Internet
   ↓
Public ALB
   ↓
Private EC2 instances
   ↓
Private database
```

The EC2 instances can still initiate outbound internet connections through mechanisms such as a NAT Gateway if required.

Private does not mean isolated from everything.

It describes the network architecture and available paths.

---

# 6. An EC2 instance is in a public subnet but cannot access the internet. What would you check?

## Strong interview answer

I would verify the entire outbound path.

```text
EC2
 ↓
Public IP?
 ↓
Security Group egress?
 ↓
NACL?
 ↓
Route table?
 ↓
Internet Gateway?
 ↓
Internet
```

I would check:

* Public IPv4 address or appropriate public addressing.
* Route table.
* Internet Gateway attachment.
* Security group egress.
* NACL rules.
* DNS if the failure occurs only with domain names.
* OS firewall.
* Proxy configuration.

For IPv4 internet access through an Internet Gateway, simply placing an instance in a subnet named "public-subnet" proves nothing.

The routing and addressing must actually support the traffic.

---

# 7. An EC2 instance in a private subnet cannot access the internet. What would you investigate?

## Strong interview answer

If outbound internet access is required, I would investigate the NAT path.

Typical architecture:

```text
Private EC2
    ↓
Private subnet route table
    ↓
0.0.0.0/0
    ↓
NAT Gateway
    ↓
Public subnet
    ↓
Internet Gateway
    ↓
Internet
```

I would verify:

* NAT Gateway exists.
* NAT Gateway is available.
* NAT Gateway is in a public subnet.
* Public subnet has a route to the Internet Gateway.
* Private route table points to the NAT Gateway.
* Security group egress permits the traffic.
* NACLs permit outbound and return traffic.
* DNS works.

---

# 8. What is the difference between an Internet Gateway and NAT Gateway?

## Strong interview answer

An Internet Gateway enables communication between a VPC and the internet for appropriately configured resources.

A NAT Gateway is commonly used so resources in private subnets can initiate outbound IPv4 connections without accepting unsolicited inbound connections through that NAT path.

Compare:

```text
Public EC2
   ↓
Internet Gateway
   ↓
Internet
```

with:

```text
Private EC2
   ↓
NAT Gateway
   ↓
Internet Gateway
   ↓
Internet
```

The NAT Gateway does not turn the private EC2 instance into a directly internet-accessible server.

---

# 9. Where should a NAT Gateway normally be placed?

## Strong interview answer

A public NAT Gateway is placed in a public subnet.

It needs the appropriate internet connectivity, including an Elastic IP and a public subnet route toward the Internet Gateway.

Then private subnet route tables can direct internet-bound IPv4 traffic to it.

```text
Private Subnet
0.0.0.0/0
     ↓
NAT Gateway

Public Subnet
0.0.0.0/0
     ↓
Internet Gateway
```

Putting the NAT Gateway in a subnet without the required Internet Gateway route would break the intended path.

---

# 10. You have NAT Gateway configured, but private EC2 instances still cannot reach the internet. What do you check?

## Strong interview answer

I would check both sides of the NAT path.

```text
Private EC2
 ↓
Private route table
 ↓
NAT Gateway
 ↓
Public subnet route table
 ↓
Internet Gateway
```

Then:

* NAT state.
* Elastic IP configuration.
* NACLs.
* DNS.
* EC2 security group egress.
* Destination-specific restrictions.
* Whether the private subnet is associated with the route table I think it is.

That last point matters.

A correctly configured route table does nothing for a subnet that is not associated with it.

---

# 11. What is a route table?

## Strong interview answer

A route table determines where network traffic from a subnet or gateway should be directed based on destination routes.

For example:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         nat-12345
```

This means traffic destined for the VPC CIDR stays within the local VPC routing domain, while other IPv4 traffic uses the NAT Gateway.

Routing answers:

```text
"Where should this packet go next?"
```

It does not answer:

```text
"Is this packet authorized?"
```

That is where security controls become relevant.

---

# 12. Two EC2 instances are in the same VPC but cannot communicate. What would you check?

## Strong interview answer

I would check:

1. IP addresses.
2. Security groups.
3. NACLs.
4. Application port.
5. Host firewall.
6. Application listener.
7. Routing if different routing constructs are involved.
8. Whether they are actually in the VPC/subnets I expect.

The VPC automatically provides local routing for its CIDR ranges, but security controls and the applications themselves can still prevent communication.

For example:

```text
EC2-A
10.0.1.10
   ↓ TCP 8080
EC2-B
10.0.2.20
```

If EC2-B's security group does not permit the required traffic, being in the same VPC does not override that restriction.

---

# 13. What is the difference between a Security Group and a Network ACL?

## Strong interview answer

Security groups are stateful and are associated with resources through network interfaces.

NACLs operate at the subnet level and are stateless.

```text
Security Group
----------------
Resource / ENI level
Stateful
Allow rules
Return traffic automatically recognized


Network ACL
----------------
Subnet level
Stateless
Allow and deny rules
Return traffic must also be permitted
Rules evaluated by number
```

I use them differently.

Security groups normally provide the primary resource-level traffic control.

NACLs can provide an additional subnet-level control layer.

---

# 14. What does stateful mean for a Security Group?

## Strong interview answer

If traffic is allowed into a resource through a security group, response traffic for that established connection is automatically allowed back, regardless of a separate outbound rule that would otherwise block a new connection of that type.

Conceptually:

```text
Client
  ↓
Allowed inbound request
  ↓
EC2
  ↓
Response
  ↑
Automatically recognized
```

This differs from NACLs, where inbound and outbound rules must independently permit the traffic.

---

# 15. Why do ephemeral ports matter with Network ACLs?

## Strong interview answer

Because NACLs are stateless.

Suppose a client connects to:

```text
EC2:443
```

The return traffic goes back to a client-side ephemeral port.

If the NACL permits inbound 443 but blocks the required outbound ephemeral port range, the connection can fail.

The exact ephemeral ranges depend on the systems involved, so I would verify the relevant client and architecture rather than blindly copying a port range.

---

# 16. A Security Group allows port 443, but HTTPS still times out. Why?

## Strong interview answer

Because the Security Group is only one component.

I would inspect:

```text
Client
 ↓
DNS
 ↓
Routing
 ↓
Internet Gateway / ALB
 ↓
NACL
 ↓
Security Group
 ↓
Application listener
 ↓
Application
```

Possible causes include:

* Wrong DNS record.
* Missing route.
* NACL.
* Application not listening on 443.
* ALB listener misconfiguration.
* Target group problem.
* OS firewall.
* Application failure.

"Port 443 is open" is not proof of end-to-end connectivity.

---

# 17. What is an Application Load Balancer?

## Strong interview answer

An Application Load Balancer distributes HTTP and HTTPS traffic across targets.

It operates at Layer 7 and understands application-level concepts such as:

```text
Host
Path
HTTP
HTTPS
Headers
```

A typical architecture:

```text
Users
  ↓
ALB
  ↓
Target Group
 ├── EC2-A
 ├── EC2-B
 └── EC2-C
```

The ALB provides a stable application entry point while backend targets can scale or be replaced.

---

# 18. What is a Network Load Balancer?

## Strong interview answer

A Network Load Balancer operates primarily at Layer 4 and handles TCP, UDP, and TLS traffic depending on configuration.

A simplified distinction is:

```text
ALB
Layer 7
HTTP / HTTPS
Content-based routing

NLB
Layer 4
TCP / UDP / TLS
High-performance network traffic
```

I choose based on application protocol and architectural requirements rather than assuming one is universally better.

---

# 19. When would you choose an ALB instead of an NLB?

## Strong interview answer

I would generally consider an ALB when I need HTTP-aware functionality such as:

```text
Path-based routing
Host-based routing
HTTP redirects
Application-layer routing
Web application targets
```

For example:

```text
example.com/api/*
       ↓
API Target Group

example.com/images/*
       ↓
Image Target Group
```

An NLB is more appropriate when Layer 4 characteristics are required.

---

# 20. What is a target group?

## Strong interview answer

A target group defines the backend targets that receive traffic from a load balancer.

Targets may include resources such as EC2 instances or IP addresses depending on the target type.

```text
ALB
 ↓
Listener Rule
 ↓
Target Group
 ├── Target A
 ├── Target B
 └── Target C
```

Target groups also define health-check behavior.

That means target group configuration is often central to load balancer troubleshooting.

---

# 21. Your ALB is running, but all targets are unhealthy. What would you check?

## Strong interview answer

I would check:

* Target registration.
* Health-check protocol.
* Health-check port.
* Health-check path.
* Expected status codes.
* EC2 security group.
* Application listening port.
* Application process.
* Application startup time.
* Host firewall.
* Dependency failures affecting the health endpoint.

Then test directly from the instance:

```bash
curl -v http://localhost:8080/health
```

If that fails, I have an application-side problem.

If it succeeds, I continue investigating the ALB-to-target path.

---

# 22. The application works with `curl localhost`, but the ALB says the target is unhealthy. What does that tell you?

## Strong interview answer

It tells me the application is at least responding locally.

Now I would investigate the path between the ALB and the target.

```text
ALB
 ↓
ALB Security Group
 ↓
EC2 Security Group
 ↓
Target Port
 ↓
Application
```

I would also verify whether the application is bound to:

```text
0.0.0.0
```

or only:

```text
127.0.0.1
```

An application bound only to loopback can respond to localhost while remaining unreachable from the ALB.

---

# 23. What does HTTP 502 from an ALB usually make you investigate?

## Strong interview answer

A 502 generally makes me investigate communication between the load balancer and the target, or an invalid response from the target.

Possible causes include:

* Application closing connections.
* Protocol mismatch.
* Malformed response.
* Backend connection problem.
* Application crash.
* Port mismatch.
* TLS/backend configuration issue.

I would correlate:

```text
ALB metrics/logs
       +
Target health
       +
Application logs
       +
OS/network evidence
```

I would not treat every 502 as an ALB failure.

---

# 24. What does an HTTP 503 from an ALB make you investigate?

## Strong interview answer

I would investigate whether the load balancer has usable healthy targets or sufficient backend availability.

For example:

```text
ALB
 ↓
Target Group

EC2-A X
EC2-B X
EC2-C X
```

If no targets are available to serve traffic, the ALB cannot successfully route requests.

I would inspect target health and determine why targets became unavailable.

---

# 25. Users intermittently receive errors through the ALB. How would you investigate?

## Strong interview answer

Intermittent behavior often suggests that only part of the target fleet is unhealthy or inconsistent.

Suppose:

```text
ALB
 ├── EC2-A ✓
 ├── EC2-B ✓
 ├── EC2-C X
 └── EC2-D ✓
```

Some requests succeed because they reach healthy targets.

Others fail when they reach EC2-C.

I would compare:

* Application versions.
* AMIs.
* Environment variables.
* IAM roles.
* Logs.
* CPU/memory.
* Dependencies.
* Availability Zones.
* Deployment history.

This is why per-target investigation matters.

---

# 26. An ALB health check returns 404. What could be wrong?

## Strong interview answer

The configured health-check path may not exist.

For example:

```text
Configured:
/health

Application exposes:
/healthz
```

The application itself may be healthy, but the ALB requests the wrong endpoint.

I would verify:

```bash
curl -i http://localhost:8080/health
```

and:

```bash
curl -i http://localhost:8080/healthz
```

Then align the target group health-check configuration with the intended endpoint.

---

# 27. Why should a health-check endpoint be designed carefully?

## Strong interview answer

Because health checks determine whether traffic should be sent to an application instance.

A weak health endpoint might always return:

```text
200 OK
```

even when critical dependencies are unavailable.

An overly strict endpoint might mark the application unhealthy because a noncritical dependency has a temporary problem.

I would distinguish between concepts such as:

```text
Process alive?
Application ready?
Critical dependencies available?
```

The exact health strategy depends on the application's architecture.

---

# 28. The ALB can reach EC2, but users cannot reach the ALB. What do you investigate?

## Strong interview answer

I would focus on the client-to-ALB side.

```text
User
 ↓
DNS
 ↓
ALB
```

Check:

* DNS record.
* ALB scheme, internet-facing or internal.
* ALB subnets.
* ALB security group.
* Listener.
* Certificate for HTTPS.
* Routing.
* Client network restrictions.

If targets are healthy, I would not start by changing backend EC2 settings.

---

# 29. What is the difference between an internet-facing ALB and an internal ALB?

## Strong interview answer

An internet-facing ALB is designed to receive traffic from internet clients through publicly routable load balancer addresses.

An internal ALB is intended for private connectivity.

For example:

```text
Internet-facing ALB

Internet
   ↓
ALB
   ↓
Private application
```

versus:

```text
Internal ALB

Internal service
   ↓
ALB
   ↓
Backend service
```

If someone tries to access an internal ALB directly from the public internet, I would question the architecture before modifying security groups.

---

# 30. Why should EC2 instances behind an ALB often remain private?

## Strong interview answer

Because users generally need to reach the application through the load balancer, not directly through individual backend servers.

A common design is:

```text
Internet
 ↓
Public ALB
 ↓
Private EC2
```

The EC2 security group can allow application traffic from the ALB security group rather than the entire internet.

This reduces direct backend exposure and makes the load balancer the controlled ingress point.

---

# 31. What is Route 53?

## Strong interview answer

Amazon Route 53 is AWS's DNS service.

It can map domain names to AWS resources and other endpoints.

For example:

```text
app.example.com
      ↓
Route 53
      ↓
ALB
      ↓
Application
```

Route 53 also supports routing policies and health-related DNS architectures.

But DNS resolution and application health are separate concepts.

---

# 32. Users say the website is down. How do you determine whether DNS is the problem?

## Strong interview answer

I would test name resolution first.

Commands may include:

```bash
dig app.example.com
```

or:

```bash
nslookup app.example.com
```

I want to know:

```text
Does the name resolve?
What record is returned?
Is it the expected destination?
```

Then I would test the application endpoint.

If DNS resolves correctly but HTTP requests fail, I move down the request path.

---

# 33. What is DNS TTL?

## Strong interview answer

TTL tells DNS resolvers how long they may cache a DNS record before refreshing it.

Suppose:

```text
TTL = 3600 seconds
```

A resolver may retain the previous answer for up to that caching period.

This matters during migrations.

If you change:

```text
old endpoint
      ↓
new endpoint
```

some users may temporarily continue receiving the cached old answer.

---

# 34. You changed a Route 53 record, but some users still reach the old server. Why?

## Strong interview answer

DNS caching is one possible explanation.

Different resolvers may have cached the previous record according to its TTL.

I would check:

* Current Route 53 record.
* TTL.
* Resolver results from different locations.
* Local DNS cache.
* CDN/proxy caching if relevant.
* Whether multiple DNS records exist.

I would avoid immediately changing the record repeatedly because that can make diagnosis harder.

---

# 35. What is an Alias record in Route 53?

## Strong interview answer

Route 53 Alias records allow DNS names to point to supported AWS resources.

For example:

```text
app.example.com
      ↓
Alias
      ↓
Application Load Balancer
```

Alias records are commonly used for AWS resources such as load balancers.

They also allow useful behavior at the zone apex where a traditional CNAME would not be appropriate.

---

# 36. What is the difference between an A record and CNAME?

## Strong interview answer

An A record maps a name to an IPv4 address.

```text
app.example.com
→
203.0.113.10
```

A CNAME maps one hostname to another hostname.

```text
www.example.com
→
app.example.net
```

Route 53 Alias records add AWS-specific capabilities for pointing names to supported AWS resources.

---

# 37. Route 53 resolves correctly, but the browser shows a certificate warning. Is that DNS?

## Strong interview answer

Probably not.

DNS has successfully resolved the hostname.

Now I would investigate TLS.

```text
DNS
 ✓
 ↓
TLS handshake
 X
```

Possible causes include:

* Wrong certificate.
* Certificate expired.
* Hostname not included in certificate.
* Incorrect ALB listener certificate.
* Certificate chain issue.
* Client trust issue.

This is a good example of using successful layers to eliminate unrelated causes.

---

# 38. Where is an HTTPS certificate commonly configured when using an ALB?

## Strong interview answer

A common architecture terminates TLS at the ALB.

```text
Client
 ↓ HTTPS
ALB
Certificate
 ↓
Backend
```

The certificate can be managed through AWS Certificate Manager.

Backend traffic may use HTTP or HTTPS depending on security and architecture requirements.

---

# 39. The ALB certificate is valid, but HTTPS requests still fail. What else could be wrong?

## Strong interview answer

I would check:

* HTTPS listener exists.
* Listener port is 443.
* Security group allows required inbound traffic.
* Listener rule forwards correctly.
* Target group works.
* Certificate matches requested hostname.
* DNS points to the correct ALB.
* Backend targets are healthy.

A valid certificate solves only one part of the request path.

---

# 40. What is VPC peering?

## Strong interview answer

VPC peering provides private connectivity between two VPCs.

Conceptually:

```text
VPC-A
10.0.0.0/16
   ↓
Peering
   ↓
VPC-B
10.1.0.0/16
```

Routes must be configured appropriately.

Security groups and NACLs must also permit the desired traffic.

Creating the peering connection alone does not automatically make every resource communicate.

---

# 41. Two peered VPCs cannot communicate. What would you check?

## Strong interview answer

I would verify:

1. Peering connection state.
2. CIDR overlap.
3. Route tables in both directions.
4. Security groups.
5. NACLs.
6. DNS requirements.
7. Application listener.
8. Correct source/destination IPs.

A common failure is configuring the route in only one VPC.

```text
VPC-A → VPC-B ✓

VPC-B → VPC-A X
```

Networking frequently requires a valid return path.

---

# 42. Can you peer two VPCs with overlapping CIDR ranges?

## Strong interview answer

No, overlapping CIDR ranges prevent normal VPC peering between those networks.

For example:

```text
VPC-A
10.0.0.0/16

VPC-B
10.0.0.0/16
```

The routing system cannot cleanly determine which overlapping network destination should receive the traffic.

CIDR planning matters before environments grow.

---

# 43. Why is IP address planning important in AWS?

## Strong interview answer

Poor CIDR planning becomes painful when networks later need to connect.

You may eventually need:

```text
VPC Peering
Transit Gateway
VPN
Direct Connect
Hybrid networking
Multi-account connectivity
```

If many environments use overlapping ranges, connectivity becomes significantly harder.

Networking architecture begins before the first EC2 instance is launched.

---

# 44. What is Transit Gateway?

## Strong interview answer

AWS Transit Gateway provides centralized connectivity between multiple VPCs and supported external networks.

Without centralized transit, many VPC-to-VPC relationships can become difficult to manage.

Conceptually:

```text
VPC-A ─┐
VPC-B ─┤
VPC-C ─┼── Transit Gateway
VPC-D ─┤
VPN   ─┘
```

It is useful in larger multi-VPC and hybrid architectures.

---

# 45. What is a VPC endpoint?

## Strong interview answer

A VPC endpoint allows private connectivity from a VPC to supported services without requiring the traffic to use the normal public internet path.

Two important categories are:

```text
Gateway endpoints
Interface endpoints
```

S3 and DynamoDB support gateway endpoints.

Many AWS services can be reached through interface endpoints powered by AWS PrivateLink.

---

# 46. Why would you use an S3 Gateway Endpoint?

## Strong interview answer

Suppose private EC2 instances need S3 access.

Without an endpoint, an architecture might use:

```text
Private EC2
 ↓
NAT Gateway
 ↓
S3
```

With an S3 Gateway Endpoint:

```text
Private EC2
 ↓
Route table
 ↓
S3 Gateway Endpoint
 ↓
S3
```

This can avoid requiring NAT for that S3 traffic and keeps the path within AWS networking.

Endpoint policies can also control access through the endpoint.

---

# 47. An S3 Gateway Endpoint exists, but EC2 still cannot access S3. What do you check?

## Strong interview answer

I would verify:

* Endpoint state.
* Correct route-table association.
* Endpoint policy.
* IAM permissions.
* S3 bucket policy.
* DNS and application behavior.
* Whether the application is actually connecting to the expected AWS service endpoint.

Again:

```text
Endpoint exists
≠
Correctly configured access
```

---

# 48. What is an Interface VPC Endpoint?

## Strong interview answer

An Interface Endpoint creates elastic network interfaces in selected subnets and provides private connectivity to supported services through AWS PrivateLink.

Conceptually:

```text
Private EC2
    ↓
Private IP
    ↓
Interface Endpoint
    ↓
AWS Service
```

Security groups can be associated with interface endpoints, which introduces another layer to troubleshoot.

---

# 49. EC2 cannot reach an AWS service through an Interface Endpoint. What would you check?

## Strong interview answer

I would check:

```text
DNS
 ↓
Endpoint ENI
 ↓
Endpoint Security Group
 ↓
Endpoint policy
 ↓
AWS service
```

Specifically:

* Private DNS configuration.
* Endpoint subnets.
* Endpoint security group.
* EC2 security group egress.
* NACLs.
* Endpoint policy.
* IAM authorization.
* Correct region/service endpoint.

---

# 50. What is an Elastic Network Interface?

## Strong interview answer

An ENI is a virtual network interface within a VPC.

It can have properties such as:

* Private IP addresses.
* Security groups.
* MAC address.
* IPv6 addresses where configured.

An EC2 instance uses ENIs for network connectivity.

Thinking in terms of ENIs helps explain why security groups operate at the network-interface level.

---

# 51. What happens when a Security Group is attached to an EC2 instance?

## Strong interview answer

Technically, security groups are associated with the instance's elastic network interfaces.

# 60. What is the difference between `0.0.0.0` and `127.0.0.1` for an application listener?

## Strong interview answer

`127.0.0.1` is the loopback interface.

```text

→ local access
```

An application listening on:

```text
0.0.0.0:8080
```

is listening on all IPv4 interfaces, subject to firewall and network controls.

This distinction causes many real production connectivity incidents.

# 62. What is asymmetric routing, and why can it cause problems?

## Strong interview answer

Asymmetric routing occurs when traffic takes one path toward the destination and a different path on return.

Some architectures and stateful network appliances depend on seeing both directions of a connection.

If the return traffic bypasses the expected appliance or route, connections may fail.

Conceptually:

```text
Request:

A → Firewall → B

Response:

B → Different Route → A
```

In complex VPC architectures, I would examine both forward and return paths.

```text
Which destination?
Which port?
```

They are useful for network troubleshooting and security analysis.

They do not contain full application payloads.

# 69. What is Route 53 weighted routing?

## Strong interview answer

Weighted routing lets DNS responses be distributed according to configured weights.

```text

Weight 90
```

This can support controlled traffic distribution.

# 70. What is Route 53 failover routing?

## Strong interview answer

Failover routing can support active-passive DNS architectures where traffic is directed toward a secondary endpoint when the primary is considered unhealthy according to the configured health model.

Conceptually:

```text

   ↓
Health failure
   ↓
Route 53
   ↓
Secondary
```

DNS TTL and health-check design affect failover behavior.

# 71. Why isn't DNS failover instantaneous?

## Strong interview answer

Because DNS answers can be cached.

Even after Route 53 changes the response, some clients or resolvers may continue using previously cached records until their TTL behavior allows refresh.

Therefore:

```text
Health check detects failure
≠
Every user instantly uses secondary endpoint
```

DNS failover architecture must account for caching.

# 72. What is connection draining or deregistration delay?

## Strong interview answer

When a target is removed from service, existing requests or connections may need time to complete before the target is fully deregistered.

For example:

```text

      ↓
Deployment begins
      ↓
Stop new traffic
      ↓
Allow existing work to finish
      ↓
Terminate/replace
```

Without graceful draining, deployments can interrupt active requests.

# Production Scenario 8: The Route 53 Change "Didn't Work"

At 10:00, the team changes:

```text
app.example.com
```

from:

```text
Old ALB
```

to:

```text
New ALB
```

Some users immediately reach the new environment.

Others continue reaching the old environment.

The old DNS TTL was:

```text
3600 seconds
```

Different recursive resolvers still have cached answers.

The lesson:

```text
Route 53 updated
≠
Every DNS cache immediately updated
```

DNS behavior must be considered during deployment and migration planning.

The application health endpoint returns:

```text

```

A deployment replaces EC2 instances.

Sequence:

```text
 ↓

 ↓

 ↓
ALB sends production traffic
 ↓
Application still warming caches
 ↓
```

# Production Scenario 14: Old Instances Are Killed Too Quickly

During every deployment, a small percentage of requests fail.

The old instance receives:

```text
SIGTERM
```

and immediately exits.

But it still has active requests.

```text
User request
    ↓
EC2-A
    ↓
Deployment terminates EC2-A
    ↓
Request interrupted
```

A more graceful lifecycle is:

```text

 ↓
Drain existing requests
 ↓
Gracefully stop application
 ↓
Terminate instance
```

Load-balancer deregistration and application shutdown behavior should work together.

```text

 ↓

 ↓

 ↓

```

```text

 ↓

?
```

```text
?
```

Then:

```text

```

# Production Scenario 16: One Security Group Rule Exposed Production

```text
 ↓
```

The security rule should express the intended architecture.

# How to Answer AWS Networking Questions in an Interview

Avoid answers like:

> "I would check the security group, restart EC2, and check CloudWatch."

That sounds like random troubleshooting.

A stronger answer establishes a sequence.

> "I would first identify whether the failure is DNS resolution, TCP connectivity, load-balancer routing, target health, or application behavior. I would test DNS separately, then the required port, then inspect the ALB listener and target health. If the application works on localhost but not through the ALB, I would verify the bind address, target port, security-group relationship, health-check configuration, and host firewall. I would use VPC Flow Logs and application logs when I need evidence about the network and application layers."

That demonstrates structured reasoning.
