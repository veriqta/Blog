# Part 14: Terraform and Infrastructure as Code Scenarios

Terraform interview questions often start with:

"What is Terraform?"

"What is Infrastructure as Code?"

"What is a Terraform state file?"

Those questions matter, but real technical interviews usually go further.

You may be asked:

> "Terraform says it wants to recreate a production database. What do you do before running `terraform apply`?"

Or:

> "A resource exists in AWS, but Terraform does not know about it. How would you bring it under Terraform management?"

Or:

> "Two engineers ran Terraform at the same time and one deployment corrupted the expected state. How would you prevent that?"

Or:

> "Someone manually changed a security group in AWS. Terraform now shows drift. What should happen next?"

These questions test whether you understand Terraform as an operational system, not just a configuration language.

A useful mental model is:

```text
Terraform Code
     ↓
Provider
     ↓
Terraform State
     ↓
terraform plan
     ↓
Desired vs Actual Infrastructure
     ↓
terraform apply
     ↓
Cloud API
     ↓
Infrastructure
```

Production Terraform troubleshooting is mostly about answering four questions:

```text
What does the code say should exist?

What does Terraform state think exists?

What actually exists in the cloud?

What change is Terraform proposing?
```

If those four views do not agree, you need to understand why before applying anything.

---

# Question 1: What is Infrastructure as Code?

## Strong interview answer

Infrastructure as Code means defining infrastructure using version-controlled configuration rather than relying primarily on manual console changes.

For example, instead of manually creating:

```text
VPC
Subnets
Security Groups
EC2
Load Balancer
IAM Roles
```

I define the desired infrastructure in code.

A simplified Terraform example:

```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "company-production-logs"
}
```

Benefits include:

* Reproducibility
* Version control
* Peer review
* Change history
* Automation
* Consistency
* Easier environment recreation

The important point is that IaC is not just about automation.

It also creates a controlled record of intended infrastructure state.

---

# Question 2: What is Terraform?

## Strong interview answer

Terraform is an Infrastructure as Code tool that uses declarative configuration to manage infrastructure through providers.

The workflow is commonly:

```text
Write configuration
      ↓
terraform init
      ↓
terraform plan
      ↓
Review proposed changes
      ↓
terraform apply
```

Terraform compares configuration with its current state and provider information, then determines what changes are required.

Terraform can manage many platforms, not only AWS.

---

# Question 3: What does declarative mean in Terraform?

## Strong interview answer

Declarative means I describe the desired result rather than writing every procedural step required to reach it.

For example:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-123456"
  instance_type = "t3.micro"
}
```

I am describing:

```text
"I want an EC2 instance
with these properties."
```

Terraform determines the API operations needed to create, update, or destroy the resource.

This differs from a procedural script such as:

```text
Call API
Wait
Check response
Call another API
Configure resource
```

Terraform handles much of that lifecycle through the provider.

---

# Question 4: What is a Terraform provider?

## Strong interview answer

A provider allows Terraform to interact with an external platform or API.

Examples include providers for:

```text
AWS
Azure
Google Cloud
Kubernetes
GitHub
Cloudflare
```

For AWS:

```hcl
provider "aws" {
  region = "us-east-1"
}
```

Terraform uses the provider to translate resource configuration into API interactions.

Provider versions matter because behavior, schemas, and supported features can change.

---

# Question 5: What does `terraform init` do?

## Strong interview answer

`terraform init` initializes a Terraform working directory.

It can:

* Download providers.
* Initialize the backend.
* Download referenced modules.
* Prepare the directory for Terraform operations.

Example:

```bash
terraform init
```

If the backend configuration changes, I may need:

```bash
terraform init -reconfigure
```

or migration-related options depending on the situation.

I would be careful when changing state backends because state is critical production data.

---

# Question 6: What does `terraform plan` do?

## Strong interview answer

`terraform plan` calculates the changes Terraform expects to make.

For example:

```bash
terraform plan
```

The plan may show:

```text
+ create

~ update in-place

-/+ destroy and recreate

- destroy
```

Before production apply, I care especially about:

```text
-/+
```

because replacement may cause downtime or destroy important state.

A Terraform plan should be reviewed as an infrastructure change proposal, not just treated as output to scroll past.

---

# Question 7: What does `terraform apply` do?

## Strong interview answer

`terraform apply` executes the proposed infrastructure changes.

For example:

```bash
terraform apply
```

Terraform calls provider APIs to create, modify, or destroy resources and then updates state.

In production, I normally expect:

```text
Code review
      ↓
Plan
      ↓
Plan review
      ↓
Approval
      ↓
Apply
      ↓
Verification
```

I would avoid using `-auto-approve` casually in interactive production workflows.

---

# Question 8: What is Terraform state?

## Strong interview answer

Terraform state records Terraform's mapping between configuration and real managed infrastructure.

It answers questions such as:

```text
Which real AWS resource
corresponds to
aws_instance.web?
```

State may contain:

* Resource IDs.
* Attributes.
* Dependencies.
* Output values.
* Sensitive values in some cases.

That makes state operationally sensitive.

Terraform state should be treated like production infrastructure data.

---

# Question 9: Why does Terraform need state?

## Strong interview answer

Terraform configuration alone says what infrastructure should exist.

It does not always contain enough information to know which existing real-world object Terraform manages.

For example:

```hcl
resource "aws_security_group" "app" {
  name = "production-app"
}
```

Terraform needs to know that this logical resource corresponds to something like:

```text
sg-0abc12345
```

State provides that mapping.

Without it, Terraform may not know whether it should update an existing resource or create another one.

---

# Question 10: Why should a team not keep production Terraform state only on one engineer's laptop?

## Strong interview answer

Because that creates multiple problems:

* Single point of failure.
* No shared authoritative state.
* Concurrent engineers can produce conflicting state.
* Laptop loss can cause serious recovery problems.
* CI/CD cannot reliably use the state.
* Collaboration becomes difficult.

For production teams, I normally use a remote backend.

For AWS, a common design is:

```text
Terraform
   ↓
S3 backend
   +
state locking mechanism
```

The specific locking implementation depends on the Terraform and backend version in use.

The main principle is:

```text
One authoritative remote state
+
controlled concurrent access
```

---

# Question 11: Why is Terraform state sensitive?

## Strong interview answer

State may contain infrastructure details and, depending on the resources and providers involved, sensitive values.

Examples can include:

```text
Resource IDs
IP addresses
Database configuration
Generated credentials
Secret values
Connection strings
```

Marking an output as:

```hcl
sensitive = true
```

hides it from normal CLI display in some contexts.

It does not automatically remove the underlying value from state.

Therefore state storage needs strong access control and encryption.

---

# Question 12: A developer accidentally commits `terraform.tfstate` to Git. What would you do?

## Strong interview answer

I would treat the state as potentially exposed.

First:

1. Remove it from version control.
2. Determine whether sensitive values exist in the state.
3. Rotate any exposed credentials or secrets.
4. Review repository access.
5. Move state to an approved remote backend.
6. Add appropriate ignore rules.
7. Review Git history if necessary.

For example, `.gitignore` commonly includes:

```text
*.tfstate
*.tfstate.*
.terraform/
```

But deleting the latest file is not enough if sensitive state remains in Git history.

---

# Question 13: What is a Terraform backend?

## Strong interview answer

The backend controls where Terraform stores state and how certain state operations are performed.

A local backend stores state locally.

A remote backend stores state in shared infrastructure.

For example:

```hcl
terraform {
  backend "s3" {
    bucket = "company-terraform-state"
    key    = "production/network/terraform.tfstate"
    region = "us-east-1"
  }
}
```

A production backend should be designed for:

* Durability.
* Access control.
* Encryption.
* Versioning or recovery.
* Locking or concurrency protection.

---

# Question 14: Why is state locking important?

## Strong interview answer

State locking prevents multiple Terraform operations from modifying the same state concurrently.

Without locking:

```text
Engineer A
terraform apply

Engineer B
terraform apply
```

could both operate from similar but changing assumptions about state.

That creates race conditions.

Conceptually:

```text
Engineer A
      ↓
Acquire lock
      ↓
Apply
      ↓
Release lock

Engineer B
      ↓
Wait
```

For shared infrastructure, concurrent state modification should be prevented.

---

# Question 15: Terraform says the state is locked. What do you do?

## Strong interview answer

First, I would not immediately force-unlock it.

I would determine:

```text
Who owns the lock?

Is an apply still running?

Did CI/CD crash?

Is another engineer actively working?
```

If the lock belongs to a valid running process, I wait.

If the process is definitely dead and the lock is stale, I may use:

```bash
terraform force-unlock <LOCK_ID>
```

but only after confirming no legitimate operation still owns it.

Force-unlocking a live operation can create serious state problems.

---

# Question 16: What is infrastructure drift?

## Strong interview answer

Drift occurs when real infrastructure differs from the infrastructure Terraform expects.

For example, Terraform defines:

```hcl
ingress {
  from_port   = 443
  to_port     = 443
  protocol    = "tcp"
  cidr_blocks = ["10.0.0.0/16"]
}
```

Someone manually changes AWS to:

```text
443 from 0.0.0.0/0
```

Now:

```text
Terraform configuration
≠
Actual AWS configuration
```

Terraform may detect that difference during planning or refresh operations.

The team then needs to decide whether the manual change was legitimate or should be reverted.

---

# Question 17: Someone manually changes an AWS security group. What should happen next?

## Strong interview answer

I would determine whether the manual change was:

```text
Intentional emergency change
or
Unapproved drift
```

If it should not exist, the next Terraform deployment should restore the desired configuration.

If the manual change is now the new desired configuration, it should be represented in Terraform code rather than left only in AWS.

For an emergency:

```text
Manual mitigation
      ↓
Restore service
      ↓
Update Terraform code
      ↓
Review
      ↓
Reconcile infrastructure
```

The goal is to eliminate unmanaged drift.

---

# Question 18: Terraform says it will change a resource that nobody modified manually. Why might drift still appear?

## Strong interview answer

Possible causes include:

* AWS default behavior changed.
* Provider behavior changed.
* Provider version changed.
* API returns normalized values differently.
* Another automation tool changed the resource.
* A cloud service changed a managed attribute.
* Computed fields differ.
* Configuration changed indirectly.

I would inspect:

```bash
terraform plan
```

carefully and identify the exact attribute causing the change.

Not every diff is caused by a human using the console.

---

# Question 19: What is `terraform refresh`?

## Strong interview answer

Historically, `terraform refresh` updated state to reflect real infrastructure without changing infrastructure.

Modern Terraform workflows typically rely on planning and related refresh behavior rather than using refresh casually as a standalone operational command.

The important concept is that Terraform can query providers to compare:

```text
State
vs.
Actual infrastructure
```

I would be cautious with any operation that changes state because state changes influence future plans.

---

# Question 20: What is `terraform import`?

## Strong interview answer

Import allows an existing resource to be brought under Terraform state management.

Suppose a security group exists:

```text
sg-0123456789
```

but was created manually.

I first define the resource in Terraform:

```hcl
resource "aws_security_group" "legacy_app" {
  name = "legacy-app"
}
```

Then import it using the appropriate Terraform import workflow.

Conceptually:

```text
Existing AWS resource
      ↓
Terraform import
      ↓
Terraform state now maps
aws_security_group.legacy_app
to
sg-0123456789
```

Import does not automatically create perfect configuration for you.

The Terraform code still needs to match the real resource.

---

# Question 21: Why is import not finished after the import command succeeds?

## Strong interview answer

Because import primarily establishes state association.

I still need to ensure Terraform configuration accurately represents the resource.

After import:

```bash
terraform plan
```

may show many proposed changes.

For example:

```text
Existing resource:
encrypted = true

Terraform code:
encrypted = false
```

If I immediately apply without reviewing, Terraform may modify the imported infrastructure.

The workflow should be:

```text
Define resource
      ↓
Import
      ↓
Plan
      ↓
Reconcile code
      ↓
Plan until expected
      ↓
Apply only when safe
```

---

# Question 22: What does `terraform state list` do?

## Strong interview answer

It lists resources currently tracked in Terraform state.

Example:

```bash
terraform state list
```

Output may look like:

```text
aws_vpc.main
aws_subnet.public_a
aws_subnet.private_a
aws_security_group.app
aws_instance.web[0]
```

This is useful when I need to understand:

```text
What does Terraform currently think it manages?
```

---

# Question 23: What does `terraform state show` do?

## Strong interview answer

It displays the state information for a specific managed resource.

Example:

```bash
terraform state show aws_security_group.app
```

This helps compare:

```text
Terraform state
vs.
Terraform configuration
vs.
Cloud resource
```

It is especially useful during import, drift, and state-repair investigations.

---

# Question 24: What does `terraform state rm` do?

## Strong interview answer

It removes a resource from Terraform state without destroying the real infrastructure.

For example:

```bash
terraform state rm aws_instance.legacy
```

After that:

```text
EC2 instance still exists
```

but:

```text
Terraform no longer manages it
```

This is a powerful and potentially dangerous command.

If the resource remains in configuration, the next plan may propose creating another one.

I would use state commands only with a clear understanding of the consequences.

---

# Question 25: What does `terraform destroy` do?

## Strong interview answer

It destroys infrastructure managed by the Terraform configuration and state.

Example:

```bash
terraform destroy
```

In production, this is obviously high risk.

I would expect:

* Appropriate access controls.
* Strong review.
* Environment separation.
* Protection of critical resources.
* Backups.
* Approval.

The fact that Terraform can destroy infrastructure is one reason IaC permissions must be tightly controlled.

---

# Question 26: What is `prevent_destroy`?

## Strong interview answer

Terraform lifecycle configuration can use `prevent_destroy` to reject plans that would destroy a protected resource.

Example:

```hcl
resource "aws_db_instance" "production" {
  # configuration

  lifecycle {
    prevent_destroy = true
  }
}
```

This can help protect critical resources such as production databases.

However, it is not a complete disaster-prevention system.

Someone can remove the lifecycle rule in code.

Security, reviews, backups, and cloud-level protections still matter.

---

# Question 27: Terraform wants to replace a production database. What do you do?

## Strong interview answer

I would stop before applying.

A replacement marker such as:

```text
-/+
```

is a major warning for stateful production resources.

I would determine exactly which attribute requires replacement.

For example:

```text
identifier
storage architecture
engine-related property
subnet group
immutable provider field
```

Then I would assess:

```text
Will data be preserved?
Will there be downtime?
Is a snapshot required?
Is migration required?
Can the change be made differently?
```

I would never treat:

```text
Plan: 1 to add, 0 to change, 1 to destroy
```

as harmless when the destroyed resource is a production database.

---

# Question 28: What does "forces replacement" mean in Terraform?

## Strong interview answer

Some resource attributes cannot be changed in place.

When one changes, Terraform may need to:

```text
Destroy old resource
      +
Create new resource
```

or potentially create the replacement first depending on lifecycle configuration and provider capabilities.

In the plan, replacement is usually clearly indicated.

I always inspect which exact field caused it.

---

# Question 29: What is `create_before_destroy`?

## Strong interview answer

It is a lifecycle setting that asks Terraform to create the replacement resource before destroying the existing one when possible.

Example:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Conceptually:

```text
Old resource
      ↓
Create new resource
      ↓
Switch dependencies
      ↓
Destroy old resource
```

This can reduce downtime for some resource types.

But it does not guarantee zero downtime.

Resource naming, quotas, dependencies, and service behavior may make overlapping old and new resources impossible.

---

# Question 30: Why can `create_before_destroy` fail?

## Strong interview answer

Because the cloud platform may not allow both resources to exist simultaneously.

For example:

```text
Global unique name
Single attached resource
Quota limit
Port conflict
Exclusive relationship
```

If both old and new resources cannot coexist, Terraform cannot magically avoid the underlying platform constraint.

Lifecycle rules influence Terraform behavior.

They do not override cloud service limitations.

---

# Question 31: What is `ignore_changes`?

## Strong interview answer

`ignore_changes` tells Terraform not to react to changes in selected attributes after resource creation.

Example:

```hcl
lifecycle {
  ignore_changes = [
    desired_capacity
  ]
}
```

This can be useful when another system legitimately manages an attribute.

For example:

```text
Terraform manages Auto Scaling Group

Autoscaling system manages desired capacity dynamically
```

Without `ignore_changes`, Terraform might constantly try to reset the runtime value.

But overusing `ignore_changes` can hide real drift.

---

# Question 32: Why is broad `ignore_changes` dangerous?

## Strong interview answer

Because Terraform may stop reporting important configuration differences.

For example:

```hcl
lifecycle {
  ignore_changes = all
}
```

would significantly reduce Terraform's ability to reconcile the resource.

That can turn Terraform into:

```text
Resource creator
```

rather than:

```text
Ongoing desired-state manager
```

I use ignore rules only for attributes intentionally controlled elsewhere.

---

# Question 33: What is a Terraform variable?

## Strong interview answer

Variables parameterize Terraform configuration.

Example:

```hcl
variable "environment" {
  type = string
}
```

Then:

```hcl
tags = {
  Environment = var.environment
}
```

This allows the same configuration structure to be reused with different values.

But environment separation should still be designed carefully.

I would not put every production difference into one giant variable file without considering blast radius and state boundaries.

---

# Question 34: What is an output?

## Strong interview answer

Outputs expose useful values from Terraform.

Example:

```hcl
output "load_balancer_dns" {
  value = aws_lb.app.dns_name
}
```

This may allow downstream automation or users to retrieve:

```text
app-prod-alb-123.us-east-1.elb.amazonaws.com
```

Sensitive outputs can be marked:

```hcl
sensitive = true
```

but, again, that does not mean sensitive data disappears from state.

---

# Question 35: What are locals?

## Strong interview answer

Locals allow values or expressions to be defined once and reused within a Terraform module.

Example:

```hcl
locals {
  common_tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

Then:

```hcl
tags = local.common_tags
```

They help reduce repetition and make configuration easier to maintain.

---

# Question 36: What is a Terraform module?

## Strong interview answer

A module is a collection of Terraform configuration used as a reusable unit.

For example:

```text
modules/
  vpc/
  ec2/
  alb/
  rds/
```

A root configuration might use:

```hcl
module "vpc" {
  source = "./modules/vpc"

  cidr_block = "10.0.0.0/16"
}
```

Modules can standardize common infrastructure patterns.

But they should not become giant abstractions that hide every important operational detail.

---

# Question 37: What makes a good Terraform module?

## Strong interview answer

A good module has a clear responsibility.

For example:

```text
VPC module
```

might manage:

```text
VPC
Subnets
Route tables
NAT configuration
```

It should expose meaningful inputs and outputs.

I avoid a module with hundreds of loosely related options such as:

```text
create_vpc
create_database
create_kubernetes
create_dns
create_monitoring
create_everything
```

because that becomes difficult to reason about and test.

---

# Question 38: Why should module versions be pinned?

## Strong interview answer

If a remote module changes unexpectedly, future infrastructure plans may change without the team intentionally modifying application code.

For example:

```hcl
module "vpc" {
  source = "git::https://example.com/vpc.git?ref=v3.2.1"
}
```

is more reproducible than always pulling an uncontrolled moving branch.

The same principle applies to providers.

Production infrastructure should not depend unnecessarily on moving versions.

---

# Question 39: What is `.terraform.lock.hcl`?

## Strong interview answer

The dependency lock file records provider selections and checksums.

It improves reproducibility across:

```text
Developer machines
CI/CD runners
Production automation
```

Teams normally commit the lock file to version control.

That way, running `terraform init` does not arbitrarily choose a newer provider version within allowed constraints without visibility.

---

# Question 40: Why can upgrading a provider cause unexpected Terraform plans?

## Strong interview answer

Provider behavior can change.

A new provider version may:

* Introduce new defaults.
* Change schemas.
* Normalize values differently.
* Add validation.
* Deprecate attributes.
* Change update behavior.

After upgrading:

```bash
terraform plan
```

may show changes even though the Terraform configuration did not otherwise change.

That is why provider upgrades should be treated as infrastructure changes and tested.

---

# Question 41: A provider upgrade suddenly wants to replace several resources. What do you do?

## Strong interview answer

I would stop before applying.

Then compare:

```text
Old provider version
vs.
New provider version
```

and identify the attributes causing replacement.

I would review provider release notes and migration guidance where appropriate.

Options may include:

```text
Correct configuration
Perform provider-specific migration
Pin previous version temporarily
Stage the upgrade
```

I would not approve mass replacement merely because the provider was upgraded.

---

# Question 42: What is the purpose of version constraints?

## Strong interview answer

Version constraints define which Terraform or provider versions are acceptable.

For example:

```hcl
terraform {
  required_version = ">= 1.8.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

Constraints improve compatibility control.

The exact version strategy depends on the organization.

For critical infrastructure, upgrades should be explicit and tested.

---

# Question 43: What is the difference between `count` and `for_each`?

## Strong interview answer

Both can create multiple instances of a resource.

`count` uses numeric indexes.

Example:

```hcl
resource "aws_instance" "web" {
  count = 3
}
```

Addresses become:

```text
aws_instance.web[0]
aws_instance.web[1]
aws_instance.web[2]
```

`for_each` uses keys.

Example:

```hcl
resource "aws_instance" "web" {
  for_each = toset(["a", "b", "c"])
}
```

Addresses become:

```text
aws_instance.web["a"]
aws_instance.web["b"]
aws_instance.web["c"]
```

Stable keys can make `for_each` safer for many resource collections.

---

# Question 44: Why can changing a `count` list cause unexpected resource replacement?

## Strong interview answer

Because count indexes represent resource identity.

Suppose:

```text
[0] app-a
[1] app-b
[2] app-c
```

Then I remove `app-a`.

The list shifts:

```text
[0] app-b
[1] app-c
```

Terraform may now interpret resources differently by index.

With a key-based `for_each`:

```text
"app-a"
"app-b"
"app-c"
```

removing `"app-a"` does not change the identities of `"app-b"` and `"app-c"`.

That can reduce unnecessary replacement.

---

# Question 45: What is a data source?

## Strong interview answer

A data source reads information about infrastructure or external data without Terraform managing the lifecycle of that object.

Example:

```hcl
data "aws_ami" "ubuntu" {
  most_recent = true

  owners = ["099720109477"]
}
```

Terraform can use the result when creating resources.

The important distinction is:

```text
resource
→ Terraform manages it

data source
→ Terraform reads it
```

---

# Question 46: Why can `most_recent = true` be risky in production?

## Strong interview answer

Because the selected value can change over time.

Suppose yesterday:

```text
AMI A
```

was most recent.

Today:

```text
AMI B
```

becomes most recent.

A new plan may now propose replacing or launching infrastructure with a different image even though no explicit AMI ID changed in code.

For production, I often prefer controlled image promotion and explicit versioning.

---

# Question 47: What is a Terraform workspace?

## Strong interview answer

Terraform workspaces allow multiple state instances associated with the same configuration.

For example:

```text
default
dev
staging
prod
```

However, I would not automatically use workspaces as the primary isolation mechanism for every environment.

Production environments often benefit from stronger separation:

```text
Separate state
Separate directories or repositories
Separate accounts
Separate permissions
```

depending on the architecture.

---

# Question 48: Why can using one Terraform configuration and workspaces for everything be risky?

## Strong interview answer

Because the blast radius and operational context can become unclear.

A user might accidentally run:

```bash
terraform workspace select prod
terraform apply
```

when they believed they were working in development.

I prefer controls that make environment mistakes difficult.

For example:

```text
Separate cloud accounts
Separate state backends
Separate CI/CD permissions
Explicit environment directories
```

Workspaces are useful, but they are not a substitute for environment isolation.

---

# Question 49: What is dependency management in Terraform?

## Strong interview answer

Terraform builds a dependency graph.

When one resource references another:

```hcl
subnet_id = aws_subnet.private_a.id
```

Terraform understands that the subnet must exist before the dependent resource can be created.

Conceptually:

```text
VPC
 ↓
Subnet
 ↓
EC2
```

Most dependencies should be expressed through resource references rather than manually forcing order.

---

# Question 50: What is `depends_on`?

## Strong interview answer

`depends_on` creates an explicit dependency when Terraform cannot infer the relationship from configuration.

Example:

```hcl
resource "aws_instance" "app" {
  depends_on = [
    aws_iam_role_policy_attachment.app
  ]
}
```

I use it when there is a real dependency Terraform cannot otherwise detect.

I avoid using `depends_on` everywhere because excessive artificial dependencies can make plans slower and harder to understand.

---

# Question 51: Terraform creates resources in the wrong order. Should you add `depends_on` everywhere?

## Strong interview answer

No.

First, I check whether the configuration expresses the real dependency.

For example, this naturally creates a dependency:

```hcl
subnet_id = aws_subnet.private.id
```

Terraform already knows the subnet is required.

`depends_on` is useful for hidden behavioral dependencies, not as a general ordering system.

---

# Question 52: What is an implicit dependency?

## Strong interview answer

An implicit dependency occurs when one resource references an attribute of another resource.

Example:

```hcl
resource "aws_instance" "app" {
  subnet_id = aws_subnet.private.id
}
```

Terraform understands:

```text
aws_subnet.private
must exist before
aws_instance.app
```

No explicit `depends_on` is required.

# Question 53: Terraform gets an API error halfway through apply. What happens?

## Strong interview answer

Some resources may already have been created or modified before the failure.

For example:

```text

✓

Subnets created
✓

Security Group created
✓

ALB creation
X
```

Terraform updates state for successful operations as it proceeds.

I would fix the root cause and run:

```bash
terraform plan
```

again.

Terraform should then calculate what remains to reach the desired state.

I would not manually destroy everything unless there is a specific reason.

before retrying.

# Question 57: Why can renaming a Terraform resource cause destroy/create behavior?

## Strong interview answer

Terraform identifies resources by their Terraform address.

Suppose:

```hcl
resource "aws_instance" "web" {
}
```

becomes:

```hcl

}
```

Terraform may interpret that as:

```text

removed

aws_instance.frontend
new
```

even if the infrastructure configuration is otherwise identical.

Without state migration, the plan may show:

```text
Destroy old
Create new
```

The infrastructure did not need replacement.

The Terraform address changed.

# Question 58: How do you safely rename or move Terraform resources?

## Strong interview answer

Modern Terraform supports `moved` blocks for many refactoring scenarios.

For example:

```hcl
moved {
  from = aws_instance.web
  to   = aws_instance.frontend
}
```

This tells Terraform:

```text
The same managed object
now has a new Terraform address.
```

Older workflows may use state-moving commands.

The important goal is preserving resource identity during configuration refactoring.

# Question 59: What does `terraform state mv` do?

## Strong interview answer

It changes how an existing managed resource is addressed in Terraform state.

Example:

```bash

  aws_instance.web \
  aws_instance.frontend
```

The real EC2 instance does not need to be recreated.

But state manipulation is high-risk.

```text

Verify source
Verify destination
Run plan afterward
```

before considering the change complete.

# Question 60: What is a Terraform `moved` block better for than a one-time state command?

## Strong interview answer

A moved block records the migration in configuration.

* Other engineers.
* CI/CD.
* Future state migrations.
* Multiple environments.

The infrastructure refactor becomes version controlled.

That is usually preferable for planned code refactoring where supported.

* Restore state backup.
* Restore backend version.
* Reconstruct state through import.

This is why remote state should have strong durability and recovery controls.

# Production Scenario 3: Two Engineers Run Terraform Together

Engineer A runs:

```text
terraform apply
```

at 10:00.

Engineer B runs another apply against the same infrastructure at 10:01.

Without proper concurrency protection:

```text
Engineer A state
      ↓
Cloud changing

Engineer B state
      ↓
Cloud changing differently
```

The result can become difficult to reason about.

Remote state locking exists to prevent this.

The expected workflow is:

```text
Engineer A
locks state
      ↓
Engineer B
cannot apply
      ↓
A completes
      ↓
lock released
      ↓
B replans
```

Importantly:

Engineer B should generate a new plan after Engineer A's changes.

A plan calculated before another infrastructure change may be stale.

# Production Scenario 4: Terraform Changed Production Because of a Manual Fix

At 02:00, an on-call engineer changes an AWS security group manually to restore production.

They allow:

```text
TCP 443
from new internal CIDR
```

Service recovers.

At 09:00, the normal Terraform pipeline runs.

Terraform configuration does not contain the emergency rule.

Terraform sees:

```text
AWS
extra ingress rule

Terraform desired state
no ingress rule
```

So Terraform removes it.

Production breaks again.

Terraform did not malfunction.

It reconciled the declared state.

The real process failure was:

```text
Emergency infrastructure change
      ↓
not reconciled into Terraform
      ↓
Terraform restores old desired state
```

After emergency changes:

```text
Mitigate
      ↓
Document
      ↓
Update IaC
      ↓
Review
      ↓
Reconcile
```

# Production Scenario 6: Terraform Created Half the Infrastructure

```text

✓

Subnets
✓

Route Tables
✓

ALB
✓

EC2
X AccessDenied
```

The apply fails.

A weak response is:

> "Delete everything and start again."

A stronger response is:

1. Inspect the error.
2. Verify execution role.
3. Identify missing permission.
4. Fix the permission.
5. Run a fresh `terraform plan`.

Terraform state should already know the successfully created resources.

The next plan may show:

```text
0 to add for existing resources
+
remaining EC2 resources
```

Terraform is designed to converge toward desired state.

# Production Scenario 7: The CI Pipeline Has Less Access Than the Developer

Developer runs Terraform locally:

```text
Success
```

CI runs:

```text
AccessDenied:
iam:PassRole
```

The developer says:

> "Terraform works locally, so the pipeline is broken."

Not necessarily.

Compare identities.

Developer:

```bash
aws sts get-caller-identity
```

might show:

```text
Administrator role
```

CI uses:

```text
terraform-deployment-role
```

Terraform is attempting to launch EC2 with:

```text

```

CI needs permission to pass that specific approved role.

The correct solution is not AdministratorAccess.

It is a scoped deployment permission model.

# Production Scenario 8: Terraform Shows No Changes but the Application Is Down

Terraform plan says:

```text
No changes.
Infrastructure matches configuration.
```

Yet the application cannot connect to RDS.

Investigation shows Terraform code contains:

```hcl
cidr_blocks = ["10.0.5.0/24"]
```

but the application was recently moved to:

```text
10.0.8.0/24
```

Terraform is doing exactly what it was told.

```text
Configuration
matches
AWS

But configuration
is operationally wrong.
```

IaC guarantees consistency with declared state.

It does not guarantee the declared state is correct.

This is why post-deployment application verification still matters.


# Production Scenario 11: Auto Scaling and Terraform Fight Each Other

Terraform configuration:

```hcl
desired_capacity = 4
```

At midday, autoscaling increases the ASG to:

```text
10 instances
```

Later someone runs Terraform.

Terraform plan says:

```text
desired_capacity
10 → 4
```

If Terraform applies that, capacity drops during peak traffic.

The systems disagree over who owns desired capacity.

A better design may intentionally ignore runtime desired capacity:

```hcl
lifecycle {
  ignore_changes = [
    desired_capacity
  ]
}
```

while Terraform continues managing:

```text
Launch Template
Min capacity
Max capacity
Tags
Networking
```

The issue is ownership, not Terraform drift.

# Production Scenario 14: Manual State Repair Goes Wrong

An engineer notices Terraform wants to recreate an EC2 instance.

They run:

```bash
terraform state rm aws_instance.web
```

thinking:

> "This will reset it."

The EC2 instance remains.

Terraform no longer tracks it.

Next plan:

```text
+ create aws_instance.web
```

Now Terraform wants to create another server.

The state command did exactly what it was designed to do.

The problem was using it without understanding resource identity.

State commands are surgical tools.

Treat them like production database operations.

```text
terraform init
```

## Format Terraform

```bash
terraform fmt -recursive
```

## Validate configuration

```bash
terraform validate
```

## Create a plan

```bash
terraform plan
```

## Save a plan

```bash
terraform plan -out=tfplan
```

## Apply a saved plan

```bash
terraform apply tfplan
```

## Show current workspace

```bash
terraform workspace show
```

## List state resources

```bash
terraform state list
```

## Inspect one resource in state

```bash
terraform state show <resource-address>
```

## Import an existing resource

Use Terraform's supported import workflow for the Terraform version and resource involved.

## Move resource state

```bash
terraform state mv <source> <destination>
```

## Remove a resource from state

```bash
terraform state rm <resource-address>
```

```bash
terraform force-unlock <lock-id>
```

Use only after proving the lock is stale.

```bash
aws sts get-caller-identity
```

# The Terraform Troubleshooting Pattern to Remember

When Terraform behaves unexpectedly, think in four layers.

```text
1. CONFIGURATION
What does the .tf code say?

        ↓

2. STATE
What does Terraform think it manages?

        ↓

3. PROVIDER / CLOUD
What actually exists in AWS?

        ↓

4. PLAN
What change does Terraform think is required?
```

Then add execution context:

```text
Account
Region
Workspace
Backend
Provider version
Credentials
Variables
```

Most dangerous Terraform incidents happen when one of these is wrong.

# How to Answer Terraform Troubleshooting Questions in an Interview

Avoid:

> "I would run terraform apply again."

A stronger answer is:

> "I would first determine whether the problem is configuration, state, provider behavior, credentials, or real infrastructure drift. I would verify the account, region, backend, and workspace, then generate a fresh plan. If the plan is unexpected, I would compare Terraform configuration, Terraform state, and the real cloud resource before changing anything. I would not manipulate state or force-unlock a backend until I understand exactly why Terraform's view differs from the cloud."

Avoid:

> "I would delete the resource and recreate it."

A stronger answer is:

> "If Terraform wants to replace a production resource, I would inspect which attribute forces replacement, assess downtime and data impact, verify backups and recovery, and determine whether the change can be performed in place or through a staged migration. Terraform replacement syntax is a signal to investigate, not permission to approve destruction."
