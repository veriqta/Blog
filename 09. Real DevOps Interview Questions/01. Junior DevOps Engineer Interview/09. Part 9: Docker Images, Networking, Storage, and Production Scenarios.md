# Part 9: Docker Images, Networking, Storage, and Production Scenarios

Knowing how to run `docker build` and `docker run` is useful. In a real DevOps interview, however, the interviewer may want to know whether you understand what happens when Docker becomes part of a production system.

You may be given situations such as:

* The same image works on one server but fails on another.
* Production is running an image that nobody can trace back to a commit.
* Two containers are running but cannot communicate.
* A container can reach another service by IP address but not by hostname.
* A database container loses its data after being recreated.
* A volume is mounted, but the application receives `Permission denied`.
* An application works on the host but cannot reach the internet from inside Docker.
* A container works locally but fails after deployment.
* A new image was pushed, but production still serves the previous version.
* One Docker host behaves differently from the other hosts.
* Disk usage keeps increasing even after old containers are removed.
* A production deployment causes intermittent errors because different hosts run different image versions.

These questions test whether you understand the relationship between:

```text
Source Code
    ↓
Dockerfile
    ↓
Build Context
    ↓
Image Layers
    ↓
Registry
    ↓
Docker Host
    ↓
Container
    ↓
Network
    ↓
Persistent Storage
    ↓
Application
    ↓
Production Traffic
```

Part 8 focused heavily on container-level troubleshooting.

Part 9 goes deeper into Docker images, networking, storage, image distribution, and realistic production scenarios.

---

# Question 1: Walk me through what happens when you run `docker build`.

## Strong interview answer

When I run:

```bash
docker build -t payments-api:1.0 .
```

Docker uses the Dockerfile and the specified build context to construct an image.

The final `.` means the current directory is the build context.

Docker processes instructions such as:

```dockerfile
FROM node:20-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

CMD ["node", "server.js"]
```

Conceptually:

```text
Base image
    ↓
Set working directory
    ↓
Copy dependency files
    ↓
Install dependencies
    ↓
Copy application
    ↓
Configure startup command
    ↓
Final image
```

The build produces image layers.

Docker can reuse cached layers when the inputs for those layers have not changed.

After building, I can inspect the image:

```bash
docker images
```

and:

```bash
docker history payments-api:1.0
```

The important point is that `docker build` creates an image. It does not start the production application.

Running the application is a separate lifecycle step.

# Question 2: What exactly is a Docker image layer?

## Strong interview answer

Docker images are composed of filesystem layers produced during the image build.

For example:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .
```

Conceptually:

```text
Base Python layer
      ↓
Working directory metadata
      ↓
requirements.txt
      ↓
Installed dependencies
      ↓
Application source
```

Layers matter because they affect:

* Build caching
* Image size
* Distribution
* Storage usage
* Reproducibility

If only application source changes, Docker may be able to reuse the dependency installation layer.

That is one reason Dockerfile ordering matters.

---

# Question 3: Why can deleting a large file in a later Dockerfile layer fail to reduce the image size as much as expected?

## Strong interview answer

Because the file may still exist in an earlier image layer.

For example:

```dockerfile
RUN wget https://example.com/huge-file.tar.gz

RUN tar -xzf huge-file.tar.gz

RUN rm huge-file.tar.gz
```

The archive was introduced in an earlier layer.

Deleting it in a later layer does not rewrite the previous layer.

A better approach may combine related operations:

```dockerfile
RUN wget https://example.com/huge-file.tar.gz \
    && tar -xzf huge-file.tar.gz \
    && rm huge-file.tar.gz
```

Or, preferably, use a multi-stage build when build artifacts are involved.

The production lesson is that image layers are additive.

# Question 4: A Docker image is unexpectedly 3 GB. How would you investigate it?

## Strong interview answer

I would start with:

```bash
docker images
```

Then inspect the layer history:

```bash
docker history <image>
```

I would review the Dockerfile for:

* Large base image
* Package-manager caches
* Development dependencies
* Build tools
* Large source directories
* `node_modules`
* Test data
* Logs
* Temporary archives
* Unnecessary binaries

I would also inspect `.dockerignore`.

For example, if this exists:

```dockerfile
COPY . .
```

and `.dockerignore` is missing, the build context might contain:

```text
.git/
node_modules/
coverage/
logs/
tmp/
test-data/
```

Some of those files could end up in the image.

Then I would determine whether a multi-stage build could separate compilation from runtime.

The goal is not simply:

```text
Make the image small.
```

The goal is:

```text
Include what production requires
and exclude what production does not require.
```

# Question 5: What is the difference between an image tag and an image digest?

## Strong interview answer

A tag is a human-readable reference.

For example:

```text
payments-api:1.8.2
```

or:

```text
payments-api:production
```

A tag can be changed to point to different image content.

A digest identifies specific image content.

Conceptually:

```text
Tag
production
    ↓
can move

Digest
sha256:...
    ↓
specific content
```

This matters in production because saying:

```text
We deployed production.
```

does not necessarily tell me exactly which image content was deployed if the tag is mutable.

A digest provides stronger artifact identity.

# Question 6: Why is using only `latest` dangerous in production?

## Strong interview answer

Because `latest` is mutable and ambiguous.

Suppose:

```text
Monday:
payments:latest → Image A

Tuesday:
payments:latest → Image B
```

A server that already has Image A and another server that pulls Image B can potentially behave differently depending on the deployment process.

A better release strategy uses identifiable versions.

For example:

```text
payments:4.8.2
```

or:

```text
payments:a841c29
```

where the tag corresponds to the Git commit.

Then I can trace:

```text
Git commit
a841c29
    ↓
CI build
    ↓
Image
payments:a841c29
    ↓
Registry
    ↓
Production deployment
```

This improves rollback and incident investigation.

# Question 7: How would you prove which image is actually running in production?

## Strong interview answer

I would not rely only on what the deployment pipeline claims it deployed.

I would inspect the runtime.

For example:

```bash
docker ps
```

Then:

```bash
docker inspect <container>
```

I would identify:

* Image reference
* Image ID
* Digest where available
* Container creation time

I could also inspect:

```bash
docker image inspect <image>
```

If the application exposes build metadata, I might check:

```bash
curl http://localhost:8080/version
```

A useful response could be:

```json
{
  "version": "4.8.2",
  "commit": "a841c29"
}
```

That gives me another way to correlate the runtime with source control.

# Question 8: Two production servers show `payments:latest`, but they behave differently. What would you investigate?

## Strong interview answer

I would compare the actual image IDs or digests.

The tag alone is not enough.

For example:

```text
Host A
payments:latest
Digest: sha256:AAA

Host B
payments:latest
Digest: sha256:BBB
```

Now I know the hosts are not actually running identical image content.

I would also compare:

* Environment variables
* Mounts
* Network configuration
* Resource limits
* Host configuration

The key lesson is:

```text
Same tag
does not always prove
same artifact.
```

# Question 9: A new image was pushed to the registry, but the existing container still runs the old application. Why?

## Strong interview answer

Because pushing a new image does not automatically replace a running container.

Suppose:

```text
Running container
    ↓
created from Image A
```

Later:

```text
Registry tag updated
    ↓
points to Image B
```

The existing container remains based on the image from which it was created.

A deployment process normally needs to:

```text
Pull intended image
    ↓
Stop or replace old container
    ↓
Create new container
    ↓
Verify health
```

This is another reason immutable image versions are easier to reason about.

# Question 10: The Docker build works on one developer's machine but fails in CI. What would you compare?

## Strong interview answer

I would compare:

* Docker version
* BuildKit behavior
* Build context
* CPU architecture
* Environment variables
* Build arguments
* Files excluded by `.dockerignore`
* Authentication to private registries
* Network access
* Base image availability

I would also check whether the developer has local files that are not committed.

For example:

```text
Developer laptop:
config.json exists

Git repository:
config.json missing
```

A local build may succeed because:

```dockerfile
COPY config.json .
```

finds the local file.

CI checks out only committed files and fails.

That means the Docker build was accidentally dependent on untracked local state.

# Question 11: What is Docker's default bridge network?

## Strong interview answer

When Docker runs containers without another network configuration, they commonly use Docker's default bridge networking behavior.

Conceptually:

```text
Docker Host

Container A
    │
    ├── Docker bridge
    │
Container B
```

However, for application stacks, I generally prefer explicit user-defined networks because they provide clearer isolation and better service-name-based communication.

For example:

```bash
docker network create backend
```

Then:

```bash
docker run -d \
  --name api \
  --network backend \
  my-api
```

and:

```bash
docker run -d \
  --name database \
  --network backend \
  postgres:16
```

---

# Question 12: Why would you use a user-defined Docker bridge network instead of putting everything on the default network?

## Strong interview answer

A user-defined network provides a clearer application boundary.

It also supports useful container name resolution.

For example:

```text
frontend-network

frontend
   ↓
api
```

and separately:

```text
database-network

api
   ↓
database
```

The frontend does not necessarily need direct access to the database.

This allows network design to follow application architecture.

Instead of:

```text
Every container
can reach
every other container
```

I can design:

```text
Frontend
   ↓
API
   ↓
Database
```

That is easier to reason about and can reduce unnecessary connectivity.

# Question 13: How can a container be connected to multiple Docker networks?

## Strong interview answer

A container can participate in more than one network.

For example:

```bash
docker network create frontend-network
docker network create backend-network
```

Start the API:

```bash
docker run -d \
  --name api \
  --network frontend-network \
  my-api
```

Then connect it to the backend network:

```bash
docker network connect backend-network api
```

Conceptually:

```text
Frontend
    │
frontend-network
    │
   API
    │
backend-network
    │
Database
```

The API acts as the application component that needs connectivity to both sides.

The database does not need to join the frontend network.

# Question 14: Two containers are running but cannot communicate. What commands would you use?

## Strong interview answer

I would start with:

```bash
docker ps
```

Then inspect their network configuration:

```bash
docker inspect container-a
docker inspect container-b
```

I would inspect Docker networks:

```bash
docker network ls
```

Then:

```bash
docker network inspect <network>
```

I want to answer:

```text
Are both containers on the intended network?
```

Then test name resolution from the source container:

```bash
docker exec container-a getent hosts container-b
```

if `getent` is available.

Then test the destination port:

```bash
docker exec container-a \
  nc -vz container-b 8080
```

if `nc` is available.

My troubleshooting sequence is:

```text
Container running?
       ↓
Same intended network?
       ↓
Name resolves?
       ↓
Port reachable?
       ↓
Application listening?
       ↓
Application-level problem?
```

# Question 15: Container A can resolve Container B's name but cannot connect to its port. What does that tell you?

## Strong interview answer

It tells me DNS or service-name resolution is probably working.

For example:

```bash
getent hosts database
```

returns:

```text
172.20.0.3 database
```

but:

```bash
nc -vz database 5432
```

fails.

I would stop focusing on DNS and investigate:

* Is PostgreSQL running?
* Is it listening on port 5432?
* Is it listening on the expected interface?
* Is the container healthy?
* Is there another network or host-level restriction?

The important interview principle is:

```text
Prove one layer
before moving to the next.
```

# Question 16: A container can connect to another service using an IP but not using its name. What does that suggest?

## Strong interview answer

It suggests a name-resolution issue.

For example:

```bash
curl http://172.20.0.5:8080
```

works.

But:

```bash
curl http://api:8080
```

fails.

I would check:

```bash
getent hosts api
```

Then:

```bash
docker network inspect <network>
```

I would verify that the containers are attached to the appropriate user-defined network and that the expected name or alias is available.

---

# Question 17: Why should application containers avoid hardcoded container IP addresses?

## Strong interview answer

Container IP addresses are runtime details.

If a container is recreated:

```text
Before:
172.20.0.4

After:
172.20.0.9
```

A hardcoded dependency on:

```text
172.20.0.4
```

now fails.

Using service discovery or DNS names allows infrastructure to change without requiring the application to know individual runtime addresses.

For example:

```text
DATABASE_HOST=database
```

is generally more robust than:

```text
DATABASE_HOST=172.20.0.4
```

# Question 18: A web container must be accessible from the internet, but the database container should not be. How would you design that?

## Strong interview answer

I would publish only the ports that need host or external access.

For example:

```bash
docker run -d \
  --name web \
  --network app-network \
  -p 80:8080 \
  web-image
```

The database can run on the internal Docker network without publishing its database port to the host:

```bash
docker run -d \
  --name database \
  --network app-network \
  postgres:16
```

Then:

```text
Internet
   ↓
Host:80
   ↓
Web Container
   ↓
Docker Network
   ↓
Database Container
```

The database does not need:

```bash
-p 5432:5432
```

just because the application needs to communicate with it internally.

That reduces unnecessary exposure.

# Question 19: What is the difference between exposing and publishing a port?

## Strong interview answer

In a Dockerfile:

```dockerfile
EXPOSE 8080
```

describes the intended application port in image metadata.

Publishing occurs at runtime.

For example:

```bash
docker run -p 8080:8080 myapp
```

The second operation creates host-to-container connectivity.

So:

```text
EXPOSE
→ describes container port

-p
→ publishes host port to container port
```

This distinction appears frequently in Docker interviews.

# Question 20: A containerized API can reach the database but cannot reach the internet. What would you investigate?

## Strong interview answer

I would determine whether the problem is:

* DNS
* Routing
* Docker networking
* Host forwarding
* Firewall
* Proxy
* External service

Inside the container:

```bash
getent hosts example.com
```

If DNS works, I would test external connectivity:

```bash
curl -v https://example.com
```

If available, I might test an IP endpoint separately to distinguish DNS from routing.

I would inspect:

```bash
docker inspect <container>
```

and:

```bash
docker network inspect <network>
```

I would also check whether the host itself has working outbound connectivity.

The comparison is important:

```text
Host cannot reach internet
→ likely host/upstream issue

Host can reach internet
Container cannot
→ investigate container/host networking path
```

# Question 21: What happens to data stored inside a container's writable layer?

## Strong interview answer

The data belongs to that container's writable filesystem.

If I remove the container:

```bash
docker rm database
```

and create another one from the image, I should not expect important runtime data from the removed container's writable layer to appear automatically.

For persistent workloads such as databases, storage should be designed separately.

Conceptually:

```text
Container
replaceable

Persistent data
must survive replacement
```

This is why Docker volumes exist.

---

# Question 22: What is a Docker named volume?

## Strong interview answer

A named volume is Docker-managed persistent storage.

Create one:

```bash
docker volume create postgres-data
```

Inspect it:

```bash
docker volume inspect postgres-data
```

Use it:

```bash
docker run -d \
  --name database \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16
```

Now the relationship is:

```text
Database Container
       ↓
/var/lib/postgresql/data
       ↓
postgres-data volume
```

The container can be replaced while the volume remains.

---

# Question 23: How would you prove that a Docker volume survives container recreation?

## Strong interview answer

For a simple demonstration:

```bash
docker volume create test-data
```

Create a container and write data:

```bash
docker run --rm \
  -v test-data:/data \
  alpine \
  sh -c 'echo "production-data" > /data/test.txt'
```

Create another container using the same volume:

```bash
docker run --rm \
  -v test-data:/data \
  alpine \
  cat /data/test.txt
```

It should return:

```text
production-data
```

The first container no longer exists.

The data remains because it lives in the volume.

---

# Question 24: Does using a Docker volume mean you no longer need backups?

## Strong interview answer

No.

Persistence and backup solve different problems.

A volume helps data survive container replacement.

It does not automatically protect against:

* Accidental deletion
* Corruption
* Host failure
* Ransomware
* Application errors
* Volume deletion

Conceptually:

```text
Volume
→ persistence

Backup
→ recovery
```

A production database still needs a deliberate backup and recovery strategy.

---

# Question 25: A database container uses a named volume, but someone runs `docker volume rm`. What happens?

## Strong interview answer

If the volume is removed successfully, the persistent data stored in it may be lost.

Docker usually prevents removing a volume that is actively in use, but an unused volume can be removed.

That is why production cleanup must be controlled.

I would never treat:

```bash
docker volume prune
```

as a harmless maintenance command.

Before removing volumes, I need to know:

```text
What application owns this volume?

Is the data needed?

Is it backed up?

Can it be restored?
```

# Question 26: A Docker host is running out of disk space. You remove stopped containers, but almost no disk space is recovered. What next?

## Strong interview answer

I would inspect Docker's storage usage:

```bash
docker system df
```

Then investigate:

```bash
docker images
```

```bash
docker volume ls
```

and build cache where relevant.

Possible consumers include:

```text
Images
Volumes
Build cache
Container writable layers
Container logs
```

Removing stopped containers only addresses one category.

For example:

```text
Containers: 2 GB
Images: 40 GB
Volumes: 100 GB
Build cache: 20 GB
```

Removing containers would barely change disk usage.

I need evidence before cleanup.

---

# Question 27: What is dangerous about `docker system prune -a` in production?

## Strong interview answer

It can remove unused Docker resources broadly, including images not currently associated with running containers.

Those images may still be operationally important.

For example, the previous production image may be needed for fast rollback.

Suppose:

```text
Current:
payments:4.9.0

Previous known-good:
payments:4.8.2
```

If cleanup removes the local copy of `4.8.2` and the registry is unavailable during an incident, rollback becomes harder.

Production cleanup should therefore follow retention and recovery policies rather than blindly removing everything Docker considers unused.

# Question 28: A volume exists, but the application cannot write to it. What would you investigate?

## Strong interview answer

I would check the process identity:

```bash
docker exec <container> id
```

Then inspect the target:

```bash
docker exec <container> \
  ls -ld /data
```

I would inspect the mount:

```bash
docker inspect <container>
```

Questions include:

* Is it mounted read-only?
* Who owns the files?
* What UID/GID runs the application?
* Does the application have write permission?
* Are host security controls involved?

For example:

```text
Application UID:
1001

Volume content owner:
1000
```

That could explain the permission failure.

# Question 29: Why are UID and GID important with container storage?

## Strong interview answer

Linux filesystem permissions ultimately operate using numeric user and group IDs.

The name:

```text
appuser
```

inside a container is less important to the filesystem than the associated UID.

Suppose:

```text
Container:
appuser = UID 1001

Host-mounted directory:
owner = UID 1000
```

Permissions may not match even if the usernames appear reasonable in different environments.

This becomes particularly important with bind mounts.

# Question 30: What is a bind mount?

## Strong interview answer

A bind mount maps a host filesystem path into a container.

For example:

```bash
docker run -d \
  --name api \
  -v /srv/api/config:/app/config:ro \
  my-api
```

Conceptually:

```text
Host
/srv/api/config
       ↓
Container
/app/config
```

The `:ro` makes the mount read-only.

Bind mounts are useful when the application needs direct access to host-managed files.

However, they also create stronger dependency on the host filesystem structure.

---

# Question 31: When would you prefer a named volume over a bind mount?

## Strong interview answer

I would generally prefer a named volume when Docker should manage the persistent storage and the application does not need a specific host path.

For example:

```text
Database data
Application state
Docker-managed persistent files
```

I may use a bind mount when a specific host path needs to be presented to the container.

For example:

```text
Development source directory
Host-managed configuration
Specific certificates
```

The choice should reflect operational requirements rather than habit.

---

# Question 32: A configuration file exists in the image but disappears when the container starts. What could cause this?

## Strong interview answer

A mount may be obscuring the image content.

Suppose the image contains:

```text
/app/config/application.yml
```

Then the container starts with:

```bash
-v /srv/config:/app/config
```

Now `/app/config` reflects the mounted host directory.

If:

```text
/srv/config
```

does not contain `application.yml`, the application may report the file missing.

I would inspect:

```bash
docker inspect <container>
```

before rebuilding the image.

---

# Question 33: A database container has a volume, but data disappears after deployment. What would you investigate?

## Strong interview answer

I would verify that the new container uses the same intended volume.

Old container:

```text
postgres-data:/var/lib/postgresql/data
```

New deployment:

```text
postgres-new:/var/lib/postgresql/data
```

The data may still exist in `postgres-data`, but the new container is looking at an empty volume.

I would inspect:

```bash
docker volume ls
```

and:

```bash
docker inspect <old-container>
```

if available.

Then:

```bash
docker inspect <new-container>
```

I would compare the `Mounts` sections.

This is different from actual data deletion.

The application may simply be attached to the wrong storage.

# Question 34: How would you investigate an apparently empty volume without immediately modifying it?

## Strong interview answer

First:

```bash
docker volume inspect <volume>
```

Then I can mount it read-only into a temporary container where appropriate:

```bash
docker run --rm \
  -v my-volume:/data:ro \
  alpine \
  ls -la /data
```

This allows me to inspect the volume contents without using the application container.

For sensitive production data, I would follow the organization's operational procedures before mounting or manipulating it.

# Question 35: A container uses a bind mount to a host directory. It works on Host A but fails on Host B. Why?

## Strong interview answer

Bind mounts create host-specific dependencies.

For example:

```text
Host A:
/srv/payments/config.yml exists

Host B:
/srv/payments/config.yml missing
```

The container image can be identical while runtime behavior differs.

I would compare:

* Host path
* File contents
* Permissions
* Ownership
* Mount options
* Security controls

This is why configuration drift between Docker hosts can create inconsistent production behavior.

# Question 36: What is Docker Compose?

## Strong interview answer

Docker Compose allows multiple related containers and their configuration to be described declaratively.

For example:

```yaml
services:

  api:
    image: payments-api:1.0
    ports:
      - "8080:8080"
    networks:
      - backend
    depends_on:
      - db

  db:
    image: postgres:16
    volumes:
      - postgres-data:/var/lib/postgresql/data
    networks:
      - backend

networks:
  backend:

volumes:
  postgres-data:
```

This defines:

```text
API
 ↓
backend network
 ↓
Database
 ↓
persistent volume
```

Instead of manually running several long `docker run` commands, the application stack is represented in configuration.

---

# Question 37: `depends_on` exists in Docker Compose. Does that always mean the dependency is ready to serve traffic?

## Strong interview answer

No.

Starting a dependency and having that dependency ready for application traffic are different things.

For example:

```text
PostgreSQL process starts
       ↓
Database initialization still running
       ↓
API starts
       ↓
API immediately attempts connection
       ↓
Connection fails
```

A production-quality design should consider readiness and retry behavior.

The application should not assume that:

```text
Container started
```

means:

```text
Service ready.
```

---

# Question 38: Your API starts before PostgreSQL is ready and crashes. How would you improve the design?

## Strong interview answer

I would consider several layers.

The database should expose meaningful health or readiness information.

The application should also handle temporary dependency unavailability appropriately.

For example:

```text
API starts
   ↓
Database unavailable
   ↓
Retry with controlled backoff
   ↓
Database becomes available
   ↓
API establishes connection
```

I would avoid relying entirely on arbitrary:

```bash
sleep 30
```

because startup time may vary.

Readiness and retry logic are more robust than guessing a fixed delay.

---

## Strong interview answer

I would compare:

* Docker Engine version
* Compose version
* Environment variables
* `.env` configuration
* Host paths
* File permissions
* Architecture
* Network
* Available ports
* Resource capacity
* Image versions

For example:

```yaml
volumes:
  - ./config:/app/config
```

depends on the current host filesystem.

The developer may have:

```text
./config/application.yml
```

while production does not.

Again, identical Compose syntax does not guarantee identical runtime environment.

---

# Question 40: What is the difference between Docker networking and port publishing?

## Strong interview answer

Docker networking allows containers to communicate through Docker-managed networks.

Port publishing exposes a container port through a host port.

For example:

```text
API
 ↓
Docker network
 ↓
Database
```

does not require publishing the database port.

But:

```text
User
 ↓
Docker host:443
 ↓
Web container
```

requires an externally reachable path, often involving host port publishing or another proxy/load-balancer architecture.

Internal communication and external exposure are different concerns.

---

# Question 41: A container can reach another container, but external users cannot reach the application. Where would you investigate?

## Strong interview answer

If internal container communication works, I would move outward through the request path.

For example:

```text
User
 ↓
Firewall
 ↓
Docker Host
 ↓
Published Port
 ↓
Container
 ↓
Application
```

I would verify:

```bash
docker port <container>
```

Then:

```bash
ss -lntp
```

on the host.

Then test locally:

```bash
curl http://127.0.0.1:<host-port>
```

If local host access works but remote access fails, I would investigate:

* Host firewall
* Cloud security controls
* Load balancer
* Routing

This prevents wasting time troubleshooting container-to-container networking when that layer already works.

---

# Question 42: Users receive connection refused when accessing a published Docker port. What does connection refused usually tell you?

## Strong interview answer

`Connection refused` usually means the destination was reachable enough to reject the TCP connection, but nothing appropriate was accepting it at that endpoint.

I would investigate:

* Is the host port actually listening?
* Is the container running?
* Is the application listening?
* Is the mapping correct?
* Is the application bound to the correct interface?

For example:

```text
Host 8080
     ↓
Container 8080
     ↓
Application actually listens on 9000
```

would create a configuration mismatch.

---

# Question 43: Users receive a timeout instead of connection refused. Does that change your investigation?

## Strong interview answer

Yes.

A timeout can suggest that packets are being dropped or that a downstream component is not responding within the expected time.

Possible areas include:

* Firewall
* Routing
* Network path
* Application hang
* Dependency timeout
* Load balancer

I would not treat:

```text
Connection refused
```

and:

```text
Connection timed out
```

as identical symptoms.

The exact failure message provides useful evidence.

# Question 44: Why might `ping` be a poor primary test for a containerized application?

## Strong interview answer

Because successful ICMP connectivity does not prove the application port is reachable.

Likewise, failed ICMP does not necessarily prove application traffic is unavailable because ICMP may be blocked.

If the application uses:

```text

```

I would test that service directly.

For example:

```bash
curl http://api:8080/health
```

or:

```bash
nc -vz api 8080
```

when available.

The best test should match the real application protocol.

It may be unable to resolve or reach the services it needs.

    ↓
web

    ↓

    ↓

I would inspect:

```

and:

# Question 47: A developer manually runs `docker network connect` in production and fixes the problem. Is the issue resolved?

Service may be restored, but the configuration problem is not fully resolved.

If the container is recreated, the manual network connection may disappear unless the deployment configuration contains the correct network definition.

So I distinguish:

connect container to correct network

Permanent fix:
correct Compose/deployment configuration
```

Production changes should be reproducible.

# Question 48: Why is configuration drift dangerous across Docker hosts?

## Strong interview answer

Because identical images can behave differently when hosts have different runtime configuration.

For example:

```text

Docker 28
correct volume ownership
correct network
correct certificates

Host B
different runtime configuration
wrong permissions
missing certificate
```

The image may be identical.

The environment is not.

Configuration drift creates failures that appear random when traffic is distributed across multiple hosts.

# Question 49: How would you detect configuration drift between two Docker containers?

## Strong interview answer

I would compare their runtime definitions.

For example:

```bash
docker inspect container-a > a.json
docker inspect container-b > b.json
```

Then compare relevant fields.

I would focus on:

* Image digest
* Environment variables
* Mounts
* Networks
* Port bindings
* Restart policy
* Resource limits

I would avoid blindly comparing every dynamic field because IDs, timestamps, and IP addresses may legitimately differ.

The goal is to compare configuration that should be identical.

# Question 52: What happens when the Docker daemon stops?

## Strong interview answer

The impact depends on Docker configuration and how containers are managed.

The daemon is responsible for Docker management operations.

If it becomes unavailable, operations such as:

```text
Starting new containers
Stopping containers
Inspecting through Docker CLI
Pulling images
Deploying new versions
```

may be affected.

I would inspect:

```bash
systemctl status docker
```

and:

```bash
journalctl -u docker
```

on a systemd-based Linux host.

I would not restart Docker casually on a production host without understanding the potential workload impact.

# Question 53: Docker commands return `Cannot connect to the Docker daemon`. What would you check?

## Strong interview answer

I would determine whether:

* Docker daemon is running
* The user can access the Docker socket
* `DOCKER_HOST` points somewhere unexpected
* The socket exists
* The daemon is unhealthy

For example:

```bash
systemctl status docker
```

Then:

```bash
ls -l /var/run/docker.sock
```

And:

```bash
echo "$DOCKER_HOST"
```

A permission problem and a stopped daemon require different fixes.

# Question 54: Why is access to `/var/run/docker.sock` security-sensitive?

## Strong interview answer

The Docker socket provides powerful control over the Docker daemon.

A user with unrestricted Docker daemon access may be able to start privileged containers, mount host filesystems, and perform operations that effectively provide extensive control over the host.

Therefore:

```bash
chmod 777 /var/run/docker.sock
```

is not an appropriate general production fix for Docker permission problems.

Docker daemon access should be treated as privileged access.

---

# Question 55: A CI pipeline mounts `/var/run/docker.sock` into a build container. What security concern would you raise?

## Strong interview answer

The build container may gain significant control over the host Docker daemon.

If untrusted build code executes inside that environment, it may potentially interact with the daemon in dangerous ways.

I would ask:

* Is the build code trusted?
* Does it need Docker daemon access?
* Is the runner isolated?
* Are there safer build mechanisms?
* Is the runner ephemeral?

The convenience of building Docker images should not automatically override the security implications.

---

# Question 56: A production container is running with `--privileged`. What would you ask?

## Strong interview answer

I would ask why the application requires privileged mode.

Privileged containers receive substantially broader host capabilities and device access.

If the application only needs a specific capability or device, granting full privileged mode may be excessive.

The principle is:

```text
Give the container
only the privileges
it actually requires.
```

I would not remove privileged mode during an incident without understanding the workload, but I would treat it as something requiring security review.

# Question 57: How can image vulnerabilities enter a Docker image even if your application code is secure?

## Strong interview answer

The image includes more than application code.

Potential vulnerability sources include:

* Base image
* OS packages
* Runtime
* Libraries
* Application dependencies
* Build tools accidentally retained
* Third-party binaries

Conceptually:

```text
Application Code
      +
Dependencies
      +
Runtime
      +
Operating System Packages
      =
Container Image
```

Container security therefore includes software supply-chain management, not just application code review.

# Question 58: Why should base images be updated?

## Strong interview answer

Base images contain operating system packages and runtimes that may develop known vulnerabilities.

For example:

```dockerfile
FROM python:3.12-slim
```

still depends on software maintained outside the application repository.

Organizations should have a process to:

* Monitor vulnerabilities
* Rebuild images
* Test updated dependencies
* Deploy patched artifacts

The image should be reproducible so security updates can be rebuilt and promoted safely.

# Question 59: Would you automatically deploy every new base-image update directly to production?

## Strong interview answer

No.

Security updates matter, but production changes still need testing.

A safer process is:

```text

      ↓

      ↓
Security scan
      ↓
Automated tests
      ↓
Staging validation
      ↓
Production deployment
```

The exact process depends on risk and urgency.

A critical actively exploited vulnerability may require an accelerated response, but skipping validation entirely can introduce another production failure.

# Question 60: A vulnerability scanner reports 500 vulnerabilities in your image. What would you do?

## Strong interview answer

I would not treat the raw number alone as the risk assessment.

I would investigate:

* Severity
* Exploitability
* Whether vulnerable components are present in runtime
* Whether fixes exist
* Whether packages are actually needed
* Base image choice

A multi-stage build may remove unnecessary build dependencies from the production image.

A smaller runtime image often reduces unnecessary software, but "smaller" does not automatically mean "secure."

The vulnerabilities need to be assessed in context.

As a general principle, it should contain what the application needs to run and avoid unnecessary software.

It usually does not need:

This reduces image size and attack surface.

# Question 65: Why are production health checks important during Docker deployments?

## Strong interview answer

Because:

```text
Container started
```

does not mean:

```text
Application ready.
```

A container may be running while:

* Database connection failed
* Migration is incomplete
* Required file is missing
* Application port is wrong
* Dependency is unavailable

A meaningful health check should validate enough application behavior to determine whether the instance is ready for traffic.

# Question 66: Should a health endpoint check every dependency?

## Strong interview answer

Not necessarily.

If a health check becomes too dependent on every downstream system, a failure in one dependency can mark every application instance unhealthy and potentially amplify an incident.

I would distinguish between different health concepts.

For example:

```text
Liveness
Is the process fundamentally alive?

Readiness
Should this instance receive traffic?

Dependency health
Are downstream systems functioning?
```

The exact implementation depends on the architecture.

The important point is that health checks should have deliberate semantics.

# Question 67: Why can a simple `/health` endpoint returning HTTP 200 still be insufficient?

## Strong interview answer

Because it may only prove that the web process can return a hardcoded response.

For example:

```text
API process
→ healthy

Database credentials
→ invalid

Payment processing
→ broken
```

Yet:

```bash
curl /health
```

returns:

```text
200 OK
```

A stronger production design may use appropriate readiness checks, synthetic tests, metrics, and real service-level monitoring.

No single health endpoint proves the entire system works.

# Question 68: What is a rolling Docker deployment conceptually?

## Strong interview answer

A rolling deployment replaces application instances gradually rather than replacing every instance at once.

For example:

```text
Before

A v1
B v1
C v1
D v1
```

Then:

```text
A v2
B v1
C v1
D v1
```

Verify A.

Then:

```text
A v2
B v2
C v1
D v1
```

Continue until:

```text
A v2
B v2
C v2
D v2
```

This can reduce downtime and limit blast radius.

But it also means old and new versions may temporarily coexist.

They must therefore be compatible during the rollout.

---

# Question 69: Why can rolling deployments cause problems with database changes?

## Strong interview answer

Because old and new application versions may run simultaneously.

Suppose:

```text
Version 1
expects column:
customer_name

Version 2 migration
removes customer_name
```

During the rollout:

```text
Some instances → v1
Some instances → v2
```

The v1 instances may fail after the incompatible database change.

Database migrations should therefore be designed with deployment compatibility in mind.

A common strategy is to use backward-compatible schema changes and separate destructive changes into later releases.

---

# Question 70: What is a blue-green deployment?

## Strong interview answer

Blue-green deployment maintains two application environments.

For example:

```text
Blue
Version 4.8

Green
Version 4.9
```

Production traffic initially goes to Blue.

Green is deployed and tested.

Then traffic is switched:

```text
Users
  ↓
Green 4.9
```

If a serious problem appears and the architecture allows it, traffic may be switched back to Blue.

The technique can provide fast rollback, but database compatibility and stateful components still need careful design.

---

# Question 71: What is a canary deployment?

## Strong interview answer

A canary deployment exposes the new version to a small portion of traffic first.

For example:

```text
Version 4.8
95%

Version 4.9
5%
```

Then monitor:

* Error rate
* Latency
* Business transactions
* Resource usage

If the new release behaves correctly, traffic can increase gradually.

For example:

```text
5%
 ↓
20%
 ↓
50%
 ↓
100%
```

If metrics degrade, the rollout can be stopped or reversed.

---

# Question 72: A canary receives 5 percent of traffic. Overall error rate barely changes, but canary error rate is 30 percent. What should you conclude?

## Strong interview answer

The aggregate system metric may hide a severe release-specific problem because the canary receives little traffic.

I would compare versions separately.

For example:

```text
Stable version:
0.2% errors

Canary:
30% errors
```

The new version clearly has a problem even if the total application error rate remains relatively small.

Production observability should allow releases to be compared independently during progressive deployment.

# Question 73: A deployment reports success. What should happen before you consider the release successful?

    ↓

    ↓

    ↓

# Question 76: Your registry is unavailable during a rollback. What production design issue does this expose?

# Question 77: What is the difference between rollback and roll-forward?

## Strong interview answer

Rollback restores a previous known-good version.

```text
4.9.0
 ↓
4.8.2
```

Roll-forward deploys a corrected new version.

```text

 ↓
4.9.1
```

The safest option depends on:

* Database changes
* Data compatibility
* Incident severity
* Time to produce a fix
* Previous artifact availability

Rollback is not always possible, particularly after irreversible state changes.

# Question 80: How should a deployment pipeline handle failure on one Docker host?

# Question 81: What is wrong with this deployment script?

```bash
for host in host1 host2 host3 host4
do
    ssh "$host" "docker pull payments:latest && docker restart payments"
done

echo "Deployment successful"
exit 0
```

## Strong interview answer

Several things concern me.

First, the script uses:

```text
latest
```

which makes artifact identity unclear.

Second:

```bash
docker restart payments
```

does not necessarily recreate the container from the newly pulled image.

Restarting an existing container normally restarts that existing container rather than replacing it with a new container built from the new image.

Third, the script explicitly ends with:

```bash
exit 0
```

which may cause the deployment to report success even if one or more SSH commands fail, depending on shell behavior and error handling.

Fourth, there is no:

* Health validation
* Version validation
* Traffic validation
* Rollback behavior

A better deployment design would identify an immutable artifact, replace containers deliberately, detect failures, and verify application health.

# Question 82: Why does `docker restart` not deploy a newly pulled image?

## Strong interview answer

Because the existing container was created from a particular image configuration.

Pulling a new version of the tag changes what future container creation may reference.

It does not transform the existing container.

Conceptually:

```text
Existing container
    ↓
Image A

docker pull
    ↓
Tag now points to Image B

    ↓
Still existing container
```

To deploy Image B, the deployment process needs to replace or recreate the container appropriately.

This is a very useful real-world Docker interview question.

Production troubleshooting is often about finding the meaningful difference.

# Final Production Interview Scenario

The interviewer tells you:

> "Your company runs an e-commerce checkout API on six Docker hosts behind a load balancer. At 14:00, version 7.3.0 is deployed. The deployment pipeline reports success. At 14:10, monitoring shows approximately one-third of checkout requests returning HTTP 500. CPU and memory look normal. All six containers show `Up`. The application worked correctly in staging. How would you investigate?"

A strong candidate should immediately notice:

```text
6 Docker hosts

Approximately one-third failures
```

One possible hypothesis is:

```text
2 of 6 backends
```

are failing.

But this is only a hypothesis.

I would verify it.

First, establish the release timeline:

```text
14:00
Version 7.3.0 deployed

14:10
HTTP 500 increases to approximately 33%
```

That creates a strong correlation with the deployment.

Next, identify the intended artifact.

```text
Release:
checkout 7.3.0

Commit:
c18f2a7

Expected image:
registry.example.com/checkout:c18f2a7
```

Then inspect every host.

Suppose I discover:

```text
Host 1
c18f2a7
healthy

Host 2
c18f2a7
healthy

Host 3
c18f2a7
healthy

Host 4
c18f2a7
healthy

Host 5
c18f2a7
HTTP 500

Host 6
c18f2a7
HTTP 500
```

All hosts run the same image.

That makes an inconsistent artifact less likely.

Now compare runtime configuration.

For each container:

```bash
docker inspect checkout
```

Suppose Hosts 1 through 4 show:

```text
PAYMENT_API=https://payments-v2.internal
```

Hosts 5 and 6 show:

```text
PAYMENT_API=https://payments-v1.internal
```

Now we have a meaningful difference.

But why?

Suppose the containers use:

```text
/srv/checkout/config:/app/config:ro
```

as a bind mount.

Hosts 1 through 4 contain the current production configuration.

Hosts 5 and 6 contain an old configuration file left from the previous deployment process.

The image is identical.

The runtime configuration is not.

The architecture looks like:

```text
                     Load Balancer
                           │
        ┌──────────┬───────┼───────┬──────────┐
        ↓          ↓       ↓       ↓          ↓
      Host 1     Host 2  Host 3  Host 4     Host 5
      correct    correct correct  correct     stale
                                               
                                               
                                            Host 6
                                             stale
```

The failure is not:

```text
Docker image is broken.
```

The failure is:

```text
Configuration drift across Docker hosts.
```

I would confirm that the failing requests correlate with Hosts 5 and 6.

Then I would determine the safest mitigation.

If possible, remove Hosts 5 and 6 from load-balancer traffic while correcting them.

Now customers are temporarily served by:

```text
Hosts 1 to 4
```

which are known to work.

Then correct the production configuration through the approved configuration or deployment process.

I would avoid simply editing files manually and declaring the incident resolved.

After correction, verify the runtime configuration.

Then test the application directly on Host 5:

```bash
curl -f http://127.0.0.1:<published-port>/health
```

and perform an appropriate checkout smoke test.

Do the same for Host 6.

Then gradually restore them to the load balancer.

Monitor:

```text
HTTP 5xx rate
Latency
Payment success rate
Application logs
Dependency errors
```

After recovery, I would investigate why the deployment pipeline reported success.

The deployment pipeline verified:

```text
Container started
```

but apparently did not verify:

```text
Correct configuration
       ↓
Correct dependency
       ↓
Successful checkout request
```

The permanent improvement may include:

```text
Deploy immutable image
       ↓
Apply controlled configuration
       ↓
Validate configuration version
       ↓
Start container
       ↓
Health check
       ↓
Synthetic checkout test
       ↓
Add backend to traffic
```

I would also consider reducing host-specific bind-mounted configuration if it creates unnecessary drift.

## Strong interview response

A concise but strong interview response could be:

> "Because roughly one-third of traffic is failing across six backends, I would first determine whether the errors correlate with particular Docker hosts. I would confirm the exact image digest on all six containers and compare the failing instances with healthy ones. Since the image worked in staging, I would pay particular attention to production-specific differences such as environment variables, bind mounts, secrets, networking, and host configuration. If two backends are confirmed unhealthy, I would remove them from traffic while investigating, restore a consistent known-good configuration, verify the application directly, and then return them to service. After recovery, I would fix the deployment process so it validates both artifact identity and runtime configuration before a backend receives production traffic."

That demonstrates much more than Docker command knowledge.

It demonstrates production reasoning.

# Second Production Scenario: The Deployment That Never Actually Updated

The interviewer asks:

> "Your CI pipeline builds `inventory:9.2.0`, pushes it to the Docker registry, and triggers deployment. The deployment job reports success. Developers say their fix is not visible in production. `docker ps` shows `inventory:9.2.0`. What do you check?"

Do not immediately assume the developers are wrong.

First inspect the running container.

```bash
docker inspect inventory
```

Then inspect the actual image.

I would compare:

```text
Running image ID
Expected registry image digest
```

Suppose production has:

```text
inventory:9.2.0
Digest A
```

but the registry now contains:

```text
inventory:9.2.0
Digest B
```

This indicates the same tag was reused.

Now inspect the deployment logic.

Suppose it does:

```bash
docker pull inventory:9.2.0
docker restart inventory
```

This is the problem.

The new image was downloaded.

But the existing container was only restarted.

The container was never recreated.

The deployment sequence should instead deliberately replace the runtime with a container based on the intended image.

The deeper production lesson is:

```text
Image pulled
≠
Container updated
```

And:

```text
Container restarted
≠
New image deployed
```

This is exactly the kind of subtle Docker scenario that interviewers use to distinguish someone who memorized commands from someone who understands container lifecycle.

# Third Production Scenario: Database Data Appears to Be Gone

The interviewer asks:

> "A PostgreSQL Docker container is replaced during maintenance. When the new container starts, the application shows an empty database. The team says all production data has been deleted. What do you do?"

I would not immediately conclude that the data was deleted.

First inspect the new container:

```bash
docker inspect postgres
```

Check its mounts.

Suppose it shows:

```text
postgres-data-new:/var/lib/postgresql/data
```

Now list volumes:

```bash
docker volume ls
```

Suppose I see:

```text
postgres-data
postgres-data-new
```

Inspect the old volume:

```bash
docker volume inspect postgres-data
```

Then, following safe operational procedures, inspect its contents.

The likely sequence may be:

```text
Old container
      ↓
postgres-data
      ↓
Production database

Maintenance deployment
      ↓
New container
      ↓
postgres-data-new
      ↓
Empty database initialized
```

The data was not necessarily destroyed.

The new container was attached to the wrong volume.

This distinction matters enormously during an incident.

A panicked engineer might start restoring backups unnecessarily.

A structured engineer asks:

```text
Where is the original data?
```

before:

```text
How do I recreate it?
```

# Fourth Production Scenario: The Docker Host That Slowly Dies Every Week

The interviewer asks:

> "Every seven to ten days, one Docker production host runs out of disk space. Engineers manually clean it, and the problem disappears temporarily. What would you investigate?"

I would first determine what grows.

```bash
df -h
```

Then:

```bash
df -i
```

Then:

```bash
docker system df
```

Suppose:

```text
Images: 18 GB
Containers: 3 GB
Volumes: 22 GB
Build cache: 4 GB
```

But the filesystem is consuming 180 GB.

That suggests Docker's summarized image usage may not explain everything.

I would investigate container logs.

If the default JSON logging mechanism is being used, one application may be generating enormous logs.

Suppose:

```text
checkout container log:
135 GB
```

Now inspect the application.

It turns out production is accidentally running:

```text
LOG_LEVEL=debug
```

and logging every request body and database operation.

The real problem is not:

```text
Docker needs weekly pruning.
```

The problem is:

```text
Excessive production logging
+
No effective log rotation
+
No disk alert before exhaustion
```

The permanent fix should address all three.

# What Junior DevOps Candidates Should Learn From Part 9

Docker production troubleshooting becomes much easier when you understand that a running application is assembled from several independent components.

```text
Source Code
      ↓
Dockerfile
      ↓
Image
      ↓
Registry
      ↓
Image Tag / Digest
      ↓
Docker Host
      ↓
Container
      +
Environment Variables
      +
Secrets
      +
Networks
      +
Volumes
      +
Resource Limits
      ↓
Running Application
      ↓
Production Traffic
```

When production fails, do not ask only:

```text
Is Docker running?
```

Ask:

```text
Is the correct image running?

Is it the correct digest?

Was the container recreated?

Is configuration correct?

Are the containers on the correct network?

Does DNS resolve?

Is the destination port reachable?

Is persistent storage mounted?

Is the correct volume mounted?

Are permissions correct?

Are resources exhausted?

Are all hosts configured consistently?

Does the application actually pass production traffic?
```

The strongest junior candidates also understand several important distinctions:

```text
Image tag
≠
immutable artifact identity
```

```text
docker pull
≠
application deployment
```

```text
docker restart
≠
container recreation
```

```text
Container running
≠
application healthy
```

```text
Persistent volume
≠
backup
```

```text
Same image
≠
same runtime configuration
```

```text
Internal container connectivity
≠
external application reachability
```

```text
Deployment command succeeded
≠
production release succeeded
```

When you can explain those distinctions and troubleshoot them methodically, you are no longer answering Docker questions from memorization.

You are reasoning about Docker as production infrastructure.
