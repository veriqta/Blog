## Part 2: The Operational Burden Behind the Control Plane

*"Kubernetes automates containers. It does not automate responsibility."*

In Part 1, we explored why Kubernetes looks like the answer to everything.

It promises portability.

Scaling.

Resilience.

Automation.

Consistency.

A clean declarative model.

A single platform for modern applications.

Those benefits are real.

But they represent only the visible layer.

The real work begins after the cluster is created, the first application is deployed, and the organization becomes responsible for keeping the platform secure, available, observable, affordable, and upgradeable.

This is where the conversation changes.

During adoption, teams focus on what Kubernetes can do.

During operation, teams discover what Kubernetes requires.

Clusters must be upgraded.

Nodes must be maintained.

Networks must remain healthy.

DNS must resolve correctly.

Storage must persist.

Certificates must not expire.

Resources must be allocated accurately.

Autoscaling must react to the right signals.

Backups must restore successfully.

Incidents must be investigated across multiple layers.

The platform is constantly moving.

Applications change.

Traffic changes.

Dependencies change.

Security requirements change.

Cloud infrastructure changes.

Kubernetes itself changes.

The control plane may be managed.

The responsibility is not.

This is the operational burden behind Kubernetes: the continuous work required to keep a highly dynamic platform reliable over time.

---

# A Cluster Is Never Finished

Many infrastructure projects have a completion point.

A server is provisioned.

A database is configured.

A network is connected.

A Kubernetes platform is different.

It is never truly complete.

A production cluster requires ongoing attention throughout its entire life.

New Kubernetes versions are released.

Old versions become unsupported.

Operating systems need patches.

Container runtimes change.

Plugins evolve.

APIs are deprecated.

Security vulnerabilities are discovered.

Workloads grow.

Capacity assumptions become outdated.

The cluster that worked six months ago may not remain safe or reliable today.

This means Kubernetes is not simply an implementation project.

It is a permanent operational capability.

The organization must be prepared to maintain it for as long as production workloads depend on it.

---

# Cluster Upgrades Are Production Events

Kubernetes upgrades are often described as routine maintenance.

In practice, they are production changes with real risk.

Upgrading a cluster may affect:

* The control plane
* Worker nodes
* Networking plugins
* Storage drivers
* Admission controllers
* Monitoring agents
* Ingress controllers
* Operators
* Custom resources
* Application manifests

Even when a cloud provider manages the control plane, the organization still needs to validate everything that depends on it.

An upgrade may introduce:

* Deprecated API failures
* Incompatible plugins
* Scheduling changes
* Admission-policy failures
* Network disruption
* Storage mounting problems
* Unexpected workload restarts

The danger is rarely the core upgrade alone.

The danger is the ecosystem around it.

A production cluster may depend on dozens of components built by different vendors and open-source projects.

Each has its own release cycle.

Each has its own compatibility requirements.

Each can fail independently.

Successful upgrade processes therefore require:

* Version compatibility reviews
* Staging validation
* Deprecated API scanning
* Backup verification
* Rollback planning
* Controlled node replacement
* Application health checks
* Post-upgrade monitoring

The upgrade is not complete when Kubernetes reports success.

It is complete when customer workloads remain healthy.

---

# Deprecated APIs Become Future Incidents

Kubernetes evolves quickly.

Resources and API versions that work today may be deprecated tomorrow and removed later.

This creates a hidden maintenance obligation.

A Deployment manifest written years ago may stop working after a future upgrade.

A third-party operator may depend on an API that no longer exists.

An old Helm chart may become incompatible.

A custom admission controller may fail unexpectedly.

Teams that ignore deprecation warnings accumulate upgrade debt.

The cluster continues working.

The risk quietly grows.

Eventually, the organization reaches a version it must upgrade to, but cannot.

Now the upgrade becomes a migration project.

Production reliability depends on continuous maintenance, not occasional emergency cleanup.

Strong platform teams treat deprecation warnings as planned work.

They do not wait until support deadlines force action.

---

# Node Lifecycle Management Never Stops

Worker nodes run the workloads.

They are also disposable infrastructure.

Nodes fail.

They become unhealthy.

They need operating-system patches.

They fill with temporary data.

They experience disk pressure.

They run out of memory.

They become incompatible with newer platform versions.

Managing nodes involves much more than creating virtual machines.

Teams must think about:

* Node groups
* Instance types
* Capacity
* Operating systems
* Security patches
* Draining
* Replacement
* Scaling
* Labels
* Taints
* Availability zones

When a node needs replacement, workloads must move safely.

The node is cordoned.

Pods are drained.

Controllers recreate them elsewhere.

That process sounds straightforward.

But draining may fail.

A PodDisruptionBudget may prevent eviction.

A local volume may tie a workload to one node.

A stateful application may take too long to stop.

The remaining nodes may not have enough capacity.

Node maintenance exposes whether the platform was designed for disruption.

---

# Node Failure Is Normal—Poor Recovery Is Not

Kubernetes assumes infrastructure will fail.

That is one of its strengths.

A node disappears.

The scheduler places replacement Pods elsewhere.

Desired state is restored.

But this only works when the platform has enough healthy capacity and the applications tolerate disruption.

If every node is already heavily utilized, there may be nowhere to reschedule workloads.

If applications depend on local storage, they may not move easily.

If startup times are long, customer impact may continue even after rescheduling.

If readiness probes are weak, traffic may reach applications before they are prepared.

Kubernetes can automate recovery.

It cannot guarantee that the recovery will be fast, safe, or invisible.

That depends on application design, capacity planning, and operational preparation.

---

# Networking Is One of the Hardest Layers

Kubernetes networking appears simple at first.

Every Pod gets an IP address.

Services provide stable access.

Ingress routes external traffic.

Network policies restrict communication.

Behind that simplicity is a complex distributed network.

Traffic may pass through:

* External load balancers
* Ingress controllers
* Services
* kube-proxy or eBPF data planes
* CNI plugins
* Node networking
* Pod network namespaces
* Network policies
* Cloud routing

A failure anywhere in that path may look like an application problem.

The Pod may be healthy.

The Service may exist.

The request may still fail.

Networking incidents are difficult because several layers must be investigated at once.

Engineers may need to confirm:

* Is the client reaching the load balancer?
* Is the load balancer healthy?
* Is Ingress routing correctly?
* Does the Service have endpoints?
* Are selectors correct?
* Can the source Pod reach the destination Pod?
* Is a NetworkPolicy blocking traffic?
* Is the CNI functioning?
* Is DNS returning the right address?
* Is the application listening on the expected port?

The platform hides complexity during normal operation.

During failure, engineers must understand every hidden layer.

---

# CNI Failures Can Break Healthy Applications

The Container Network Interface plugin controls how Pods connect to the network.

Without it, workloads may start but remain unreachable.

Different CNI implementations provide different capabilities.

Routing.

IP allocation.

Network policies.

Encryption.

Observability.

Performance.

Each implementation also introduces its own operational model.

CNI failures may cause:

* Pods stuck during creation
* Missing network interfaces
* IP exhaustion
* Cross-node communication failures
* Intermittent packet loss
* Policy enforcement errors
* High network latency

These failures can be difficult to diagnose because the application itself may appear healthy.

The container is running.

The process is listening.

Traffic still cannot reach it.

The incident belongs to the network layer, but the customer experiences it as an application outage.

---

# DNS Is a Critical Dependency

Inside Kubernetes, services rely heavily on DNS.

Applications call names such as:

`payment-service`

`inventory.default.svc.cluster.local`

Those names must resolve quickly and reliably.

When cluster DNS becomes slow or unavailable, the platform may experience widespread failures.

Applications fail to find dependencies.

Startup probes time out.

Requests become slow.

Retries increase traffic.

Queues grow.

Services that are individually healthy begin failing together.

DNS incidents are especially dangerous because they create confusing symptoms.

One team sees connection errors.

Another sees timeouts.

Another sees application startup failures.

The underlying cause may be the same shared dependency.

Production-grade DNS requires attention to:

* CoreDNS capacity
* Caching
* Query volume
* Upstream resolvers
* Network reliability
* Resource limits
* Autoscaling
* Monitoring

DNS is not a minor utility.

It is part of the platform’s critical path.

---

# Ingress and Load Balancers Add More Layers

External traffic must enter the cluster somehow.

This usually involves a cloud load balancer, an Ingress controller, or a gateway.

Now another operational layer appears.

Certificates.

Routing rules.

Hostnames.

Path matching.

Health checks.

TLS termination.

Timeouts.

Connection limits.

Rate limits.

A small configuration mistake can make an application unreachable even when every Pod is healthy.

Ingress failures may come from:

* Incorrect annotations
* Invalid certificates
* Wrong backend ports
* Missing endpoints
* Misconfigured paths
* Load-balancer health checks
* Security-group rules
* Controller failures

The architecture still looks like one arrow:

Client → Application

Production sees every component between them.

---

# Storage Changes the Risk Model

Stateless applications fit Kubernetes naturally.

Stateful workloads are more complicated.

Databases, queues, file systems, and data-processing applications need persistent storage.

Pods are temporary.

Data cannot be.

Kubernetes uses PersistentVolumes and PersistentVolumeClaims to separate application lifecycles from storage lifecycles.

This provides flexibility.

It also introduces new operational responsibilities.

Teams must manage:

* Storage classes
* Volume provisioning
* Access modes
* Performance
* Availability zones
* Snapshots
* Expansion
* Encryption
* Backup
* Restore

A Pod may be rescheduled to another node.

The storage may not be accessible from that location.

A volume may attach slowly.

A disk may reach capacity.

A storage driver may fail.

An application may remain unavailable even though Kubernetes is trying to recover it.

Kubernetes can orchestrate storage resources.

It cannot remove the underlying constraints of storage systems.

---

# Persistent Volumes Can Become Hidden Bottlenecks

Storage performance is often overlooked until production load increases.

A workload may experience:

* High latency
* Low IOPS
* Throughput limits
* Slow volume attachment
* File-system contention
* Capacity exhaustion

Kubernetes sees a mounted volume.

The application sees poor performance.

The customer sees a slow or unavailable service.

Troubleshooting requires understanding both Kubernetes and the storage provider.

The issue may involve:

* The application
* The file system
* The CSI driver
* The cloud disk
* The availability zone
* The node
* The storage class

This is a recurring Kubernetes lesson:

The platform connects multiple systems.

It does not eliminate the need to understand them.

---

# Resource Requests and Limits Decide Placement

Kubernetes schedules workloads using resource requests.

Requests tell the scheduler how much CPU and memory a Pod needs.

Limits define the maximum it can consume.

These values influence:

* Scheduling
* Cluster capacity
* Performance
* Cost
* Stability
* Autoscaling

Incorrect values create serious problems.

Requests that are too high waste capacity.

Requests that are too low allow overcommitment.

Memory limits that are too low cause OOM kills.

CPU limits that are too low cause throttling.

No limits can allow one workload to affect others.

Resource management is not a one-time configuration task.

Workload behavior changes.

Traffic changes.

Code changes.

Dependencies change.

Values must be measured and adjusted.

---

# The Scheduler Cannot Fix Bad Assumptions

The scheduler makes placement decisions based on the information it receives.

If resource requests are inaccurate, the scheduler is working with false assumptions.

A Pod may request 200 MiB of memory but consume 2 GiB under load.

Kubernetes schedules many such Pods onto one node.

The node experiences memory pressure.

Pods are evicted.

Applications restart.

Customers see instability.

The scheduler did not fail.

The capacity model failed.

Kubernetes automation is only as reliable as the configuration behind it.

---

# Autoscaling Is Not Automatic Intelligence

Autoscaling is one of Kubernetes' most attractive features.

The Horizontal Pod Autoscaler can increase workload replicas.

The Cluster Autoscaler can add nodes.

Vertical scaling tools can recommend or adjust resources.

But autoscaling does not understand the business automatically.

It reacts to signals.

If the signals are poor, the decisions will also be poor.

CPU usage may not represent customer demand.

Memory usage may not reflect queue pressure.

Latency may increase before CPU rises.

A sudden traffic spike may arrive faster than new Pods can start.

New Pods may wait because the cluster lacks capacity.

New nodes may take several minutes to become ready.

Autoscaling introduces questions such as:

* Which metric should drive scaling?
* How quickly should replicas increase?
* How slowly should they decrease?
* What is the maximum safe capacity?
* How long does application startup take?
* Can dependencies handle the additional load?
* Will scaling increase database pressure?

Autoscaling can improve resilience.

It can also automate the wrong response.

---

# Scaling One Layer Can Overload Another

Suppose application latency increases.

The autoscaler adds more Pods.

Those Pods create more database connections.

The database reaches its connection limit.

Errors increase.

The autoscaler adds even more Pods.

The incident becomes worse.

The platform scaled exactly as configured.

The system failed because scaling was evaluated locally instead of end to end.

Every scaling decision should consider downstream dependencies.

More application replicas do not always mean more system capacity.

Sometimes they mean more pressure on the real bottleneck.

---

# Observability Must Cover the Entire Platform

Application monitoring is not enough.

A Kubernetes platform requires visibility across several layers.

Organizations must monitor:

* Control-plane health
* Node health
* Pod status
* Scheduling
* Restarts
* CPU and memory
* Network traffic
* DNS
* Storage
* Ingress
* Certificates
* Deployments
* Autoscaling
* Application behavior

This produces enormous amounts of telemetry.

Metrics.

Logs.

Events.

Traces.

Audit records.

The challenge is not collecting everything.

The challenge is knowing what matters.

Poor observability produces dashboards without understanding.

Good observability helps engineers connect customer impact to platform behavior.

---

# Kubernetes Events Are Useful but Temporary

Kubernetes events often provide important clues.

Failed scheduling.

Volume-mount errors.

Image-pull failures.

Probe failures.

Node-pressure warnings.

But events are not permanent.

They expire.

If they are not collected centrally, critical evidence may disappear before the investigation begins.

This can turn a solvable incident into guesswork.

Production platforms should retain events, logs, and audit information long enough to support real investigations.

Operational evidence is part of platform reliability.

---

# Alerts Can Become Noise

Kubernetes produces many signals.

Pod restarts.

Node pressure.

Replica differences.

Failed probes.

Certificate warnings.

API errors.

If every signal creates an alert, engineers quickly become overwhelmed.

Alert fatigue reduces reliability.

Engineers stop trusting notifications.

Real incidents become harder to identify.

Strong alerting focuses on symptoms that require action.

Customer impact.

Sustained service degradation.

Capacity exhaustion.

Critical platform failures.

The goal is not to alert on everything that changes.

Kubernetes changes constantly.

The goal is to alert when the platform is no longer meeting its responsibilities.

---

# Secrets Require Real Security Engineering

Kubernetes Secrets are often misunderstood.

They are not automatically secure simply because they are called Secrets.

By default, they may be encoded but not strongly protected at rest unless encryption is configured.

They can be exposed through:

* Excessive RBAC permissions
* Environment variables
* Pod specifications
* Logs
* Backup files
* Misconfigured dashboards
* Compromised workloads

Production environments need a deliberate secret-management strategy.

This may include:

* Encryption at rest
* External secret managers
* Workload identity
* Short-lived credentials
* Secret rotation
* Strict RBAC
* Audit logging
* Namespace isolation

Kubernetes can store and distribute secrets.

The organization must decide who can access them, how they rotate, and how compromise is contained.

---

# Certificate Expiration Can Become an Outage

Kubernetes platforms rely on certificates.

Control-plane certificates.

Ingress certificates.

Service-mesh certificates.

Internal application certificates.

Webhook certificates.

If a certificate expires, communication may fail suddenly.

Deployments may stop.

APIs may become unavailable.

Traffic may be rejected.

Admission controllers may block resources.

Certificate management must include:

* Ownership
* Renewal
* Monitoring
* Rotation
* Testing
* Emergency procedures

A certificate is a small file with platform-wide consequences.

---

# Backup Is Not Disaster Recovery

Many teams say their cluster is protected because they have backups.

A backup is only one component of recovery.

A Kubernetes disaster may involve:

* Deleted resources
* Lost persistent volumes
* Corrupted application data
* Broken cluster configuration
* Cloud-region failure
* Identity failure
* Network failure
* Compromised credentials

Recovery requires more than restoring YAML.

Teams must know:

* What data is backed up?
* Where are backups stored?
* Are backups encrypted?
* Can they be restored to a clean cluster?
* How long does recovery take?
* Which dependencies must be recreated?
* Who leads the recovery?
* What is the acceptable data loss?

A backup that has never been restored is an assumption.

Disaster recovery requires tested evidence.

---

# Cluster State and Application Data Are Different

Kubernetes resources describe the desired state of workloads.

They do not necessarily contain the application’s data.

A deployment manifest can recreate a database Pod.

It cannot recreate lost customer records.

A disaster-recovery plan must protect both:

* Platform state
* Application state

These require different tools and different recovery procedures.

Confusing them creates false confidence.

---

# Multi-Cluster Does Not Automatically Mean Resilient

Organizations sometimes add more clusters to improve reliability.

One cluster per environment.

One cluster per region.

One cluster per business unit.

Multiple clusters can reduce certain risks.

They also multiply operational work.

Every cluster requires:

* Upgrades
* Monitoring
* Policies
* Networking
* Access controls
* Cost management
* Backup
* Capacity planning

Multi-cluster design also raises new questions.

How is traffic routed?

How is configuration synchronized?

How are secrets replicated?

How is data kept consistent?

How do engineers investigate incidents across clusters?

More clusters can improve isolation.

They can also create more places for inconsistency and failure.

Redundancy only improves reliability when the failover process actually works.

---

# Cost Management Becomes Part of Operations

Kubernetes can improve infrastructure utilization.

It can also hide cost.

Shared clusters make it difficult to know which team or application consumes which resources.

Teams may over-request CPU and memory.

Idle workloads continue running.

Logs and metrics grow.

Unused load balancers remain active.

Persistent volumes outlive applications.

Development namespaces remain forgotten.

The platform bill grows gradually.

Cost management requires:

* Resource ownership
* Requests and limits
* Namespace budgets
* Chargeback or showback
* Idle-resource cleanup
* Storage lifecycle policies
* Observability retention controls
* Capacity reviews

Kubernetes increases infrastructure flexibility.

Without governance, flexibility becomes waste.

---

# On-Call Complexity Grows With Every Layer

A Kubernetes incident can begin anywhere.

The application.

The Pod.

The node.

The network.

DNS.

Storage.

Ingress.

The control plane.

The cloud provider.

Third-party operators.

This creates an ownership problem.

Who responds first?

The application team?

The platform team?

The network team?

The cloud provider?

During an outage, customers do not care which layer failed.

They expect the service to work.

Successful operations require clear incident boundaries.

Application teams need enough platform understanding to investigate basic failures.

Platform teams need enough application context to understand impact.

Both must communicate quickly.

Without this alignment, incidents become a cycle of escalation.

Each team proves that its own layer looks healthy.

The customer remains affected.

---

# Managed Services Reduce Work—They Do Not Remove It

Managed Kubernetes is usually the right choice for organizations that do not need to operate the control plane directly.

It reduces responsibility.

But it does not eliminate platform operations.

Cloud providers may manage:

* Control-plane availability
* Control-plane upgrades
* Etcd operations
* Basic API infrastructure

The organization still manages:

* Applications
* Worker nodes or serverless compute settings
* Networking
* Ingress
* Storage
* Identity
* Security policies
* Observability
* Cost
* Reliability
* Incident response

The shared-responsibility model remains.

The boundary simply moves.

---

# The Operational Tax Appears Slowly

Kubernetes rarely becomes overwhelming on the first day.

The operational tax grows gradually.

The first cluster is simple.

Then teams add:

* More workloads
* More namespaces
* More node groups
* More Ingress rules
* More policies
* More operators
* More storage classes
* More observability tools
* More clusters

Each addition seems reasonable.

Eventually, the platform has become a complex product.

That complexity may be justified.

But it must be recognized and funded.

Organizations often budget for cluster creation.

They fail to budget for years of platform operation.

---

# What Mature Kubernetes Operations Look Like

Mature Kubernetes teams do not rely on individual heroics.

They build repeatable systems.

They standardize:

* Cluster provisioning
* Upgrades
* Application deployment
* Observability
* Security
* Resource management
* Backup
* Disaster recovery
* Incident response

They automate common work.

They document failure modes.

They test recovery.

They monitor platform health.

They reduce unnecessary variation.

They provide clear ownership.

They invest in developer experience.

They also know that not every problem requires another Kubernetes tool.

Sometimes the mature decision is to simplify.

---

# Questions Every Kubernetes Team Should Answer

Before placing critical workloads on Kubernetes, teams should answer:

* Who owns the platform?
* Who performs upgrades?
* How are deprecated APIs identified?
* How are nodes patched and replaced?
* How is DNS monitored?
* How are CNI failures diagnosed?
* How are certificates renewed?
* How are secrets protected?
* How are resource requests determined?
* How are scaling signals validated?
* How is application data backed up?
* Has restore been tested?
* Who leads a platform incident?
* How are platform costs allocated?
* How long can the business tolerate an outage?

If these questions do not have clear answers, the cluster may exist, but the operational model does not.

---

# Conclusion

Kubernetes is powerful because it automates the coordination of distributed workloads.

But the automation sits on top of a large operational system.

Clusters must be upgraded.

Nodes must be replaced.

Networks must be understood.

DNS must remain reliable.

Storage must persist.

Resources must be measured.

Autoscaling must be designed.

Secrets and certificates must be protected.

Backups must be restored.

Incidents must be owned.

None of this makes Kubernetes a bad platform.

It makes Kubernetes a serious platform.

The burden is not evidence of failure.

It is the cost of operating sophisticated infrastructure.

The organizations that succeed are not the ones that avoid this responsibility.

They are the ones that prepare for it.

They build the tools, processes, knowledge, and ownership required to keep the platform reliable over time.
