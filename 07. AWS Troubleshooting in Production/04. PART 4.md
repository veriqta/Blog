# AWS Troubleshooting in Production

## Part 4: Elastic Load Balancing, Route 53, CloudFront, and AWS WAF Troubleshooting

**How senior AWS engineers trace customer requests from DNS to the edge, through security controls and load balancers, and finally into the application**

A customer opens:

```text
https://app.example.com
```

and receives:

```text
503 Service Unavailable
```

Where is the failure?

Route 53?

CloudFront?

AWS WAF?

The Application Load Balancer?

The target group?

EC2?

ECS?

The application?

The database behind the application?

The status code alone does not answer that question.

A modern AWS request path may look like:

```text
Customer
↓
Route 53
↓
CloudFront
↓
AWS WAF
↓
Application Load Balancer
↓
Listener
↓
Listener Rule
↓
Target Group
↓
EC2 / ECS / IP Target
↓
Application
↓
Database or downstream service
```

Every layer has its own health model.

Every layer has its own logs.

Every layer can produce symptoms that appear somewhere else.

This is why experienced engineers do not begin with:

> Why is the website returning 503?

They begin with:

> Which component generated the 503?

That question completely changes the investigation.

---

# 1. Start With the Complete Request Path

Before troubleshooting any load balancer or CDN incident, map the request.

For example:

```text
app.example.com
↓
Route 53 Alias
↓
d123example.cloudfront.net
↓
CloudFront Cache Behavior
↓
AWS WAF Web ACL
↓
production-alb.us-east-1.elb.amazonaws.com
↓
HTTPS Listener :443
↓
Host Rule app.example.com
↓
checkout-target-group
↓
EC2 :8080
↓
Checkout Application
↓
RDS PostgreSQL
```

Now the investigation has boundaries.

Ask:

* Does DNS resolve correctly?
* Does CloudFront receive the request?
* Is the object cached?
* Does WAF allow it?
* Which origin is selected?
* Does the ALB receive it?
* Which listener rule matches?
* Which target group receives it?
* Are targets registered?
* Are targets healthy?
* Does the application respond?
* Is a downstream dependency slow?

Do not jump from:

```text
Customer sees 504
```

directly to:

```text
Increase ALB timeout
```

Follow the path first.

---

# 2. ALB, NLB, and Gateway Load Balancer

AWS Elastic Load Balancing includes several load-balancer types.

They solve different problems.

## Application Load Balancer

ALB operates at the HTTP and HTTPS application layer.

It understands:

* Hostnames
* Paths
* HTTP headers
* HTTP methods
* Cookies
* HTTP status codes
* TLS termination

Typical architecture:

```text
Client
↓
HTTPS
↓
ALB
↓
Listener Rules
↓
Target Group
↓
Application
```

Use ALB when application-aware routing is required.

---

# 3. Network Load Balancer

NLB operates primarily at the transport layer.

It is commonly used for:

* TCP
* TLS
* UDP
* TCP_UDP
* Very high connection volumes
* Static IP requirements
* Lower-level network workloads

Troubleshooting NLB therefore focuses more heavily on:

* Listener port
* target registration
* target health
* connection establishment
* target networking
* source IP behavior
* cross-zone configuration

NLB health states include values such as `initial`, `healthy`, `unhealthy`, `draining`, and `unused`, with reason codes that help explain why a target is not usable.

---

# 4. Gateway Load Balancer

Gateway Load Balancer is designed for network virtual appliances.

Examples include:

* Firewalls
* Intrusion-prevention systems
* Inspection appliances
* Third-party security platforms

The path may look like:

```text
Application traffic
↓
Gateway Load Balancer Endpoint
↓
Gateway Load Balancer
↓
Security Appliance
↓
Return path
```

When troubleshooting GWLB, routing symmetry becomes especially important.

A stateful firewall that sees only one direction of a connection may reject the session.

Do not treat GWLB incidents like ordinary ALB HTTP troubleshooting.

---

# 5. Target Registration

A load balancer cannot route to a target that is not correctly registered.

For ALB:

```bash
aws elbv2 describe-target-health \
  --target-group-arn \
  arn:aws:elasticloadbalancing:REGION:ACCOUNT:targetgroup/example/1234567890
```

## What it checks

This command returns:

* Target ID
* Target port
* Availability Zone
* Health state
* Reason code
* Description

## Why it matters

A target may be:

```text
initial
healthy
unhealthy
unused
draining
unavailable
```

The reason code is often more useful than the state itself. AWS documents codes such as `Target.NotRegistered`, `Target.NotInUse`, `Target.Timeout`, `Target.ResponseCodeMismatch`, and `Target.FailedHealthChecks`.

---

# 6. Healthy Target Example

```json
{
  "TargetHealthDescriptions": [
    {
      "Target": {
        "Id": "i-0123456789abcdef0",
        "Port": 8080
      },
      "TargetHealth": {
        "State": "healthy"
      }
    }
  ]
}
```

This means the target passed the configured load-balancer health check.

It does not mean every customer request succeeds.

That distinction is critical.

---

# 7. Unhealthy Target Example

```json
{
  "TargetHealthDescriptions": [
    {
      "Target": {
        "Id": "i-0123456789abcdef0",
        "Port": 8080
      },
      "TargetHealth": {
        "State": "unhealthy",
        "Reason": "Target.Timeout",
        "Description": "Request timed out"
      }
    }
  ]
}
```

Possible causes:

* Wrong health-check port
* Application not listening
* Security-group block
* NACL problem
* Slow application
* Dependency delay
* Host firewall
* Resource exhaustion

The reason narrows the investigation.

---

# 8. Target Health Is Not Application Health

Suppose the health check is:

```text
GET /health
```

and the application returns:

```text
200 OK
```

But checkout requires:

```text
Application
↓
RDS
↓
Payment service
```

The `/health` endpoint may not test either dependency.

Therefore:

```text
Target = healthy
```

while:

```text
Checkout = failing
```

is completely possible.

Health checks should be:

* Lightweight
* Reliable
* Representative enough to identify whether the target can safely receive traffic

But not so dependent on every downstream service that a small dependency problem removes the whole fleet.

---

# 9. Health-Check Paths

Inspect target-group health configuration:

```bash
aws elbv2 describe-target-groups \
  --target-group-arns \
  arn:aws:elasticloadbalancing:REGION:ACCOUNT:targetgroup/example/1234567890 \
  --query 'TargetGroups[].{
    Protocol:Protocol,
    Port:Port,
    HealthCheckProtocol:HealthCheckProtocol,
    HealthCheckPort:HealthCheckPort,
    HealthCheckPath:HealthCheckPath,
    Matcher:Matcher,
    HealthyThreshold:HealthyThresholdCount,
    UnhealthyThreshold:UnhealthyThresholdCount,
    Interval:HealthCheckIntervalSeconds,
    Timeout:HealthCheckTimeoutSeconds
  }'
```

## What it checks

* Health protocol
* Health port
* Path
* Expected status code
* Thresholds
* Timing

AWS ALB health checks periodically query each registered target. A target must pass health checking before it begins receiving normal traffic.

---

# 10. Health-Check Path Mistakes

Common failure:

```text
Health path:
/health
```

But application actually exposes:

```text
/healthz
```

Result:

```text
Target.ResponseCodeMismatch
```

Another example:

```text
/health
→ HTTP 301
```

while target group's matcher expects only:

```text
200
```

The application may be running correctly.

The configured success criteria are wrong.

---

# 11. Health-Check Host Headers

ALB health checks can send a Host header based on the target IP and health-check port rather than the customer hostname.

AWS notes that applications using strict virtual-host configuration may need a default virtual host capable of responding to the health-check Host header.

This creates a subtle failure.

Customer request:

```text
Host: app.example.com
```

works.

ALB health check:

```text
Host: 10.0.20.45:8080
```

returns:

```text
404
```

The application is healthy.

The health check is not.

---

# 12. Health-Check Ports

A target might serve customer traffic on:

```text
8080
```

but health checking may be configured for:

```text
traffic-port
```

or a dedicated port.

Verify that:

* Application listens on the health port
* Target SG permits ALB traffic
* Host firewall permits it
* NACL permits the path
* Correct process owns the port

From the instance:

```bash
ss -lntp
```

Then:

```bash
curl -v http://127.0.0.1:8080/health
```

If loopback fails, the problem is local.

If loopback succeeds but ALB health fails, move into the target network path.

---

# 13. Listeners

Inspect listeners:

```bash
aws elbv2 describe-listeners \
  --load-balancer-arn \
  arn:aws:elasticloadbalancing:REGION:ACCOUNT:loadbalancer/app/example/1234567890
```

## What it checks

Listeners define:

* Protocol
* Port
* Certificates
* Default action

Typical:

```text
HTTP :80
→ Redirect HTTPS

HTTPS :443
→ Forward production-target-group
```

An application can be perfectly healthy while the listener forwards traffic somewhere else.

---

# 14. Listener Rules

ALB listener rules can route by:

* Host
* Path
* Headers
* Query strings
* Source IP
* HTTP method

Inspect:

```bash
aws elbv2 describe-rules \
  --listener-arn arn:aws:elasticloadbalancing:REGION:ACCOUNT:listener/app/example/abc/def
```

---

# 15. Host-Based Routing

Example:

```text
Host:
api.example.com
→ api-target-group

Host:
admin.example.com
→ admin-target-group
```

A rule mistake can send valid traffic into the wrong application.

Symptoms:

* Only one hostname fails
* Default backend responds unexpectedly
* Users see another application's 404
* One environment receives production traffic

Check actual Host header:

```bash
curl -vk https://load-balancer-name \
  -H 'Host: api.example.com'
```

When testing the load balancer DNS directly, remember TLS certificate validation may differ from testing the actual custom domain.

---

# 16. Path-Based Routing

Example:

```text
/api/*
→ api-target-group

/images/*
→ image-target-group

/*
→ web-target-group
```

Listener rules have priorities.

A broader rule placed before the intended rule may capture traffic unexpectedly.

Troubleshoot:

* Requested path
* Matching rule
* Rule priority
* Forward target group
* Default action

Do not assume that because a target group exists, traffic is actually being sent to it.

---

# 17. TLS Certificates

HTTPS creates another layer.

For:

```text
https://app.example.com
```

you must evaluate:

* DNS hostname
* Listener certificate
* Certificate SANs
* Expiration
* SNI
* TLS policy
* Certificate chain

Test:

```bash
openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com
```

This helps inspect:

* Certificate presented
* Subject
* SAN
* Chain
* TLS negotiation

A browser error such as certificate name mismatch can occur when the certificate does not include the hostname the user requested. AWS includes certificate mismatch among ALB troubleshooting cases.

---

# 18. Curl TLS Investigation

```bash
curl -v https://app.example.com
```

Look for:

```text
Connected to...
TLS handshake...
server certificate...
HTTP/2 200
```

or errors such as:

```text
certificate verify failed
```

```text
SSL connection error
```

```text
connection timed out
```

Each points to a different layer.

---

# 19. Connection Draining

During deployments or scaling, targets may be removed.

The load balancer should stop sending new requests to a deregistering target while allowing existing requests to complete.

AWS calls this deregistration delay or connection draining.

The default ALB deregistration delay is 300 seconds, although it can be configured from 0 to 3600 seconds.

Target state:

```text
draining
```

means deregistration is in progress.

---

# 20. Why Connection Draining Matters

Imagine a request:

```text
POST /generate-report
```

takes 45 seconds.

Deployment process:

```text
Deregister target
↓
Immediately kill application
```

The in-flight connection breaks.

Customer receives a 5xx error.

Correct sequence:

```text
Deregister
↓
Stop new traffic
↓
Allow in-flight work to complete
↓
Terminate application
```

AWS explicitly recommends allowing deregistration to complete before stopping an application to avoid unnecessary 5xx errors.

---

# 21. Sticky Sessions

Sticky sessions can route repeated requests from a client to the same target.

Useful when:

* Application keeps session state locally
* Legacy architecture expects server affinity

But stickiness can hide problems.

Suppose:

```text
Target A healthy
Target B broken
```

Some users stuck to A see no issue.

Users stuck to B fail consistently.

Now the outage is customer-specific.

Symptoms:

* One user fails repeatedly
* Another user always succeeds
* Incognito session behaves differently
* Clearing cookies changes behavior

Sticky sessions should be part of the troubleshooting hypothesis.

---

# 22. Sticky Sessions and Architecture

Sticky sessions are often useful as compatibility mechanisms.

But if an application requires them because important state lives only in one server's memory, consider whether session state should instead live in a shared store.

A production failure caused by:

```text
target disappears
→ session disappears
```

may reveal an application architecture problem rather than a load-balancer problem.

---

# 23. Idle Timeout

Connections that remain inactive longer than the configured idle timeout can be closed.

This matters for:

* Slow API calls
* Long uploads
* Long downloads
* WebSockets
* Long-running requests
* Backend keep-alive behavior

ALB HTTP 504 troubleshooting specifically includes cases where the target establishes a connection but does not respond before the load balancer's idle timeout.

---

# 24. Do Not Automatically Increase Timeout

Suppose:

```text
TargetResponseTime
```

increases from:

```text
300 ms
```

to:

```text
57 seconds
```

and ALB returns 504.

Increasing idle timeout to:

```text
120 seconds
```

may simply allow customers to wait longer for a broken application.

First investigate:

* CPU
* database
* connection pool
* downstream API
* thread pool
* lock contention
* queueing
* dependency latency

Timeout changes should follow understanding.

---

# 25. Cross-Zone Behavior

Load balancing across Availability Zones affects how traffic reaches targets.

NLB target groups expose a cross-zone load-balancing attribute, while ALB behavior and enabled Availability Zones must also be understood when investigating zonal target problems.

A partial outage might look like:

```text
AZ A targets:
healthy

AZ B targets:
unhealthy
```

Ask:

* Is AZ B enabled?
* Are targets registered?
* Does its subnet have equivalent routing?
* Are target security groups identical?
* Is one zonal dependency failing?

---

# 26. HTTP 502, 503, and 504 Are Not the Same

One of the most useful skills in ALB troubleshooting is understanding what different 5xx classes imply.

## 502 Bad Gateway

ALB can return 502 for cases such as:

* Target resets the TCP connection
* Target closes connection unexpectedly
* Malformed HTTP response
* Invalid response headers
* Oversized response header
* SSL handshake problem to HTTPS target
* Deregistration delay expires while request is still being handled

AWS documents these as common ALB-generated 502 causes.

---

# 27. 503 Service Unavailable

A classic ALB-generated 503 condition is:

```text
Target group has no registered usable targets
```

AWS documentation states ALB can generate 503 when target groups have no registered targets or all registered targets are in an unusable state.

Therefore:

```text
EC2 instances = running
```

does not prove:

```text
ALB has targets
```

Check target registration.

---

# 28. 504 Gateway Timeout

ALB 504 can occur when:

* ALB cannot establish a target connection within its connection timeout
* Target does not respond before idle timeout
* NACL interferes with required traffic
* Backend SSL handshake times out
* Target advertises content length but sends less data than expected

AWS lists these among ALB 504 causes.

A 504 is therefore often a latency or connectivity investigation.

---

# 29. Identify Who Generated the 5xx

CloudWatch ALB metrics help separate:

```text
HTTPCode_ELB_5XX_Count
```

from:

```text
HTTPCode_Target_5XX_Count
```

Interpretation:

## ELB 5xx increases

Load balancer generated errors.

Investigate:

* target connectivity
* availability
* protocol
* timeout
* malformed responses
* target registration

## Target 5xx increases

Application targets generated errors.

Move deeper into:

* application logs
* dependencies
* database
* application configuration

Do not keep changing the ALB if the application itself returns the errors.

---

# 30. Route 53 Records

Before investigating application traffic, confirm users resolve the correct endpoint.

Run:

```bash
dig app.example.com
```

Then:

```bash
dig +trace app.example.com
```

## What `dig` checks

DNS resolution.

## What `dig +trace` helps inspect

The delegation path from DNS root toward the authoritative nameserver.

Useful for:

* delegation issues
* wrong nameservers
* stale configuration
* zone mistakes

---

# 31. Route 53 Alias Records

Alias records can route AWS DNS names to resources such as:

* Elastic Load Balancers
* CloudFront
* API Gateway
* S3 website endpoints
* Other supported AWS resources

AWS recommends using alias records instead of CNAME records when possible for supported AWS targets.

Inspect:

```bash
aws route53 list-resource-record-sets \
  --hosted-zone-id Z1234567890
```

Look for:

* Name
* Type
* Alias target
* Hosted-zone target
* Routing policy
* Health evaluation

---

# 32. DNS TTL

DNS changes do not instantly erase information already cached by:

* Recursive resolvers
* ISPs
* Corporate DNS
* Operating systems
* Browsers

A record may change at:

```text
14:00 UTC
```

but clients can continue using the previous answer until the cached TTL expires.

This is normal DNS behavior.

AWS Route 53 best practices explicitly call out the trade-off between TTL length, responsiveness to change, and DNS reliability.

---

# 33. Low TTL Versus High TTL

## Low TTL

Advantages:

* Faster DNS migration
* Faster failover response after changes

Trade-offs:

* More DNS queries
* More reliance on recursive resolution availability

## High TTL

Advantages:

* More caching
* Reduced query volume
* Greater resilience to some DNS-query disruptions

Trade-off:

* Slower propagation of traffic changes to already-caching clients

There is no universally correct TTL.

It should match operational requirements.

---

# 34. Verify Route 53 Changes

When making programmatic Route 53 changes, do not assume an API request being accepted means propagation has completed.

AWS recommends verifying changes using the Route 53 change status API in automated workflows.

Example:

```bash
aws route53 get-change \
  --id /change/C0123456789ABC
```

Look for:

```text
PENDING
```

or:

```text
INSYNC
```

`INSYNC` means Route 53's authoritative DNS infrastructure has propagated the change.

Client caches may still retain previous answers until TTL expiry.

---

# 35. Route 53 Routing Policies

Common policies include:

* Simple
* Weighted
* Latency
* Failover
* Geolocation
* Geoproximity
* Multivalue answer
* IP-based routing

Each changes how Route 53 selects an answer.

For example, weighted routing can distribute traffic in proportions based on configured weights. Latency routing can direct users toward selected regional resources based on latency calculations.

A DNS incident may therefore be a policy incident.

---

# 36. Route 53 Health Checks

Route 53 can use health information to decide whether certain records should continue receiving DNS traffic.

For alias records referencing resources such as ELB, `Evaluate Target Health` can allow Route 53 to use the health status of the target AWS resource.

Important nuance:

Health checks are not performed every time a user submits a DNS query.

Route 53 periodically checks configured endpoints and uses that health state when making routing decisions.

---

# 37. If Everything Is Unhealthy

A surprising Route 53 behavior matters during troubleshooting.

If all records in certain health-checked routing groups are considered unhealthy, Route 53 can treat them as healthy enough to return an answer rather than returning nothing.

Therefore:

> We marked every endpoint unhealthy, so Route 53 will definitely stop returning them.

is not a safe assumption.

Understand the routing-policy behavior.

---

# 38. CloudFront Cache Behaviors

CloudFront cache behaviors determine how requests are handled and which origin receives them.

A behavior can define:

* Path pattern
* Origin
* Allowed methods
* Cache policy
* Origin request policy
* Viewer protocol policy

Example:

```text
/api/*
→ ALB origin

/static/*
→ S3 origin

Default /*
→ ALB origin
```

CloudFront evaluates path patterns in configured order.

A path can therefore reach the wrong origin even when both origins are healthy.

---

# 39. CloudFront TTL

CloudFront caching depends on:

* Minimum TTL
* Default TTL
* Maximum TTL
* `Cache-Control`
* `Expires`

AWS recommends cache policies for TTL configuration.

If Minimum TTL is greater than zero, CloudFront may cache content for at least that duration even if the origin includes directives such as:

```text
Cache-Control: no-cache
```

or:

```text
no-store
```

AWS explicitly warns about this behavior.

---

# 40. Inspect CloudFront Response Headers

Run:

```bash
curl -I https://app.example.com
```

Useful headers can include:

```text
Age
Via
X-Cache
Cache-Control
ETag
Last-Modified
```

You may see:

```text
X-Cache: Hit from cloudfront
```

or:

```text
X-Cache: Miss from cloudfront
```

This helps answer:

> Did CloudFront serve the cached object or go back to the origin?

---

# 41. CloudFront Stale Content

CloudFront can intentionally serve stale content depending on cache behavior and cache-control directives.

AWS supports directives including:

```text
stale-while-revalidate
```

and:

```text
stale-if-error
```

`stale-while-revalidate` allows stale content to be served while CloudFront refreshes in the background.

`stale-if-error` can permit stale content to continue being served during an origin error for a configured period.

Therefore:

> The origin has the new content, but users still see the old version.

does not automatically mean CloudFront is malfunctioning.

It may be behaving according to the cache policy.

---

# 42. CloudFront Origin Failures

For cache misses, CloudFront must contact the origin.

Possible origins include:

* ALB
* S3
* EC2/custom HTTP server
* API endpoint
* Other supported origins

Origin failures may involve:

* DNS
* connection
* TLS
* firewall
* ALB
* application
* timeout

CloudFront 504 means the origin either returned a 504 or failed to respond within the required time. AWS recommends first verifying connectivity to the origin and then investigating application latency before simply increasing timeouts.

---

# 43. CloudFront Origin Timeouts

CloudFront origin configuration includes:

* Connection attempts
* Connection timeout
* Response timeout
* Optional response completion timeout

The response timeout controls how long CloudFront waits for response activity from the origin, while response-completion timeout can cap the total time for receiving the full response.

Timeouts should align with expected application behavior.

But again:

Do not use a longer timeout to hide an application that has become unexpectedly slow.

---

# 44. Testing the Origin Separately

If CloudFront points to an ALB origin:

```text
CloudFront
↓
production-alb-123.us-east-1.elb.amazonaws.com
```

test the origin independently when appropriate.

For HTTP behavior:

```bash
curl -v \
  -H 'Host: app.example.com' \
  http://production-alb-123.us-east-1.elb.amazonaws.com/
```

For HTTPS testing, hostname and certificate considerations matter.

The goal is to compare:

```text
Viewer → CloudFront
```

against:

```text
Direct origin behavior
```

If origin is already failing, CloudFront is not the original cause.

---

# 45. Signed URLs and Signed Cookies

CloudFront signed URLs and signed cookies control access to private content.

AWS recommends signed URLs when restricting individual files or supporting clients that do not handle cookies well.

Signed cookies are useful when granting access to multiple restricted objects without changing each URL.

Troubleshooting problems may involve:

* Expired policy
* Incorrect key
* Invalid signature
* Wrong resource path
* Clock issues
* Missing cookies
* Cookie domain or path
* Signed URL and signed cookie interaction

Important:

If both apply, AWS states signed URLs take precedence for that request.

---

# 46. AWS WAF

AWS WAF can sit in front of:

* CloudFront
* ALB
* API Gateway
* Other supported AWS resources

A simplified request path:

```text
Viewer
↓
AWS WAF
↓
Protected Resource
```

Rules can take actions including:

* Allow
* Block
* Count
* CAPTCHA
* Challenge

AWS WAF's `Count` action records a matching request and allows evaluation to continue, making it useful when testing a new rule before actively blocking production traffic.

---

# 47. WAF Can Generate Customer 403 Errors

For an ALB protected by WAF, AWS documents that an ALB HTTP 403 can occur when a WAF rule blocks a request.

Do not immediately modify the application because:

```text
403
```

appears.

Determine whether it came from:

* WAF
* ALB authentication
* Application
* API authorization

---

# 48. WAF Metrics

Useful AWS WAF metrics include:

```text
AllowedRequests
BlockedRequests
CountedRequests
CaptchaRequests
```

AWS documents these metrics as core signals for web ACL activity.

If:

```text
BlockedRequests
```

increases at exactly the same time customer failures begin, WAF becomes a strong investigation path.

Still inspect the matching rule.

---

# 49. Sampled Requests

AWS WAF can return sampled requests for recent traffic.

The WAFV2 API supports retrieving sampled requests for a rule or default action over a recent UTC time window.

This helps answer:

* Which request matched?
* Which URI?
* Which headers?
* What action occurred?
* Which rule was involved?

Sampling is useful for investigation.

Full logging is stronger when complete evidence is required.

---

# 50. WAF Logging

For production troubleshooting, enable WAF logging to an approved destination and capture fields needed to determine:

* Request
* Rule
* Labels
* Action
* Client IP
* URI
* Headers where appropriate
* Web ACL

Be careful with sensitive data.

Do not log secrets or credentials unnecessarily.

# Real Troubleshooting Lab 1

## ALB Returns 503 Although EC2 Instances Are Running

### Incident

Customers receive:

```text
HTTP/1.1 503 Service Unavailable
```

EC2 console shows:

```text
4 instances
State: running
Status checks: passed
```

Initial assumption:

> ALB is broken.

Do not accept it.

---

## Step 1: Check ALB Metrics

CloudWatch shows:

```text
HTTPCode_ELB_503_Count
↑
```

Target 5xx remains low.

This suggests ALB itself is generating the error.

---

## Step 2: Inspect Target Health

```bash
aws elbv2 describe-target-health \
  --target-group-arn \
  arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/web-production/abc123
```

Result:

```json
{
  "TargetHealthDescriptions": []
}
```

No targets.

---

## Step 3: Check Listener

```bash
aws elbv2 describe-listeners \
  --load-balancer-arn \
  arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/production/abc
```

Listener forwards to:

```text
web-production
```

That target group is empty.

---

## Step 4: Investigate Deployment History

CloudTrail shows a deployment automation action deregistered the old instances.

New instances launched successfully.

But the Auto Scaling group was accidentally attached to:

```text
web-production-v2
```

while the ALB listener still forwarded to:

```text
web-production
```

---

# Root Cause

The servers were running.

They simply were not registered in the target group receiving production traffic.

AWS documents an ALB-generated 503 when the selected target group has no registered usable targets.

---

# Mitigation

Restore correct listener and target-group association through Infrastructure as Code.

Do not restart EC2.

---

# Confirmation

```bash
aws elbv2 describe-target-health ...
```

shows healthy targets.

Then:

```bash
curl -I https://app.example.com
```

returns:

```text
HTTP/2 200
```

Finally, validate the actual business transaction.

# Real Troubleshooting Lab 2

## ALB Returns 502 After Deployment

### Incident

Immediately after a deployment:

```text
502 Bad Gateway
```

appears intermittently.

Old targets succeed.

New targets fail.

---

## Step 1: Compare Target Versions

Application logs show the new version started.

Health endpoint reports 200.

But customer requests return 502.

---

## Step 2: Inspect ALB Access Logs and Metrics

ALB-generated 502 increases.

Target-generated 5xx does not.

This suggests ALB cannot successfully process the backend response rather than the application deliberately returning HTTP 500.

---

## Step 3: Inspect Application Connection Behavior

New application config:

```text
server.keepAliveTimeout = 5 seconds
```

ALB idle timeout:

```text
60 seconds
```

Application closes backend keep-alive connections sooner than ALB expects.

ALB later attempts to reuse an established backend connection.

Target sends TCP FIN or RST.

AWS lists backend connection resets and targets closing connections while ALB has an outstanding request among causes of HTTP 502.

---

# Root Cause

Backend keep-alive behavior introduced in the deployment was shorter than the ALB connection behavior expected by the architecture.

---

# Mitigation

Rollback the application configuration to the known-good setting.

---

# Permanent Fix

Align:

* Application keep-alive
* Reverse proxy behavior
* ALB timeout expectations
* Deployment tests

Monitor:

```text
HTTPCode_ELB_502_Count
```

during canary deployments.

# Real Troubleshooting Lab 3

## HTTP 504 Appears Only During Peak Traffic

### Incident

At normal traffic:

```text
P95 latency = 450 ms
Error rate < 0.1%
```

During peak:

```text
P95 latency = 52 seconds
HTTP 504 rises
```

Infrastructure remains running.

---

## Step 1: Identify Error Generator

ALB metric:

```text
HTTPCode_ELB_504_Count
```

increases.

---

## Step 2: Check Target Response Time

```text
TargetResponseTime
```

rises sharply.

This points behind the ALB.

---

## Step 3: Check Application

Application threads show:

```text
waiting for DB connection
```

Connection-pool pending queue increases.

---

## Step 4: Check RDS

Database CPU:

```text
52%
```

Connections:

```text
near configured maximum
```

Slow transaction volume increased after a feature launch.

---

# Root Cause

ALB was not the original bottleneck.

The application exhausted its database connection pool during peak traffic.

Requests remained open until ALB timing limits were reached.

AWS documents ALB 504 as including cases where the target fails to respond before the load balancer's timeout.

---

# Wrong Fix

Increase ALB idle timeout to five minutes.

This would allow customers to wait longer while the database remains overloaded.

---

# Correct Mitigation

* Reduce expensive traffic path
* Roll back feature if appropriate
* Restore DB connection availability
* Scale safe application capacity only if database can support it

---

# Permanent Fix

* Query optimization
* Connection-pool sizing
* Backpressure
* Capacity planning
* Peak-load test
* SLO-based deployment alarms

# Real Troubleshooting Lab 4

## Route 53 Sends Users to the Old Environment

### Incident

Production migration:

```text
Old ALB
→ blue

New ALB
→ green
```

Route 53 record is updated to green.

Some users still reach blue.

---

## Step 1: Query Authoritative DNS

```bash
dig app.example.com
```

Check authoritative nameserver directly where required.

It returns the new target.

---

## Step 2: Check Route 53 Change Status

```bash
aws route53 get-change \
  --id /change/C0123456789ABC
```

Result:

```text
INSYNC
```

Route 53 authoritative infrastructure has the new configuration.

---

## Step 3: Check TTL

Previous record TTL:

```text
3600 seconds
```

Some recursive resolvers cached the old answer before migration.

Those caches remain valid until their TTL expires.

---

# Root Cause

The DNS migration occurred correctly.

Operational planning failed to lower the TTL sufficiently before the cutover.

---

# Wrong Fix

Change Route 53 repeatedly.

This resets nothing in downstream recursive caches that already hold the old answer.

---

# Corrective Action

Allow cached records to expire while ensuring both environments remain safe during the transition.

For future migrations:

1. Lower TTL before cutover.
2. Wait long enough for old high-TTL answers to age out.
3. Perform change.
4. Validate.
5. Restore normal TTL later.

# Real Troubleshooting Lab 5

## CloudFront Serves Stale Content

### Incident

A frontend deployment updates:

```text
/app.js
```

S3 origin contains the new file.

Developers opening the S3 object directly see the new version.

Users through CloudFront see the old version.

---

## Step 1: Inspect Headers

```bash
curl -I https://app.example.com/app.js
```

Response:

```text
X-Cache: Hit from cloudfront
Age: 2100
Cache-Control: max-age=3600
```

This is a cache hit.

CloudFront is not contacting the origin for this request.

---

## Step 2: Inspect Cache Policy

Object remains valid for its configured caching period.

AWS CloudFront uses cache policies and origin cache headers to determine how long objects remain cached.

---

# Root Cause

The application deploy process replaced a file using the same object name while permitting a long cache lifetime.

CloudFront correctly continued serving the cached object.

---

# Immediate Mitigation

Create an invalidation for the required object path when justified.

---

# Better Permanent Architecture

Use immutable asset names:

```text
app.4f8c93.js
```

instead of repeatedly replacing:

```text
app.js
```

Then HTML references the new object.

This makes caching safer and avoids frequent global invalidations.

# Real Troubleshooting Lab 6

## AWS WAF Blocks Valid API Requests

### Incident

After enabling a managed WAF rule group:

```text
POST /api/search
```

requests from legitimate customers begin returning:

```text
403
```

Only requests containing certain search expressions fail.

---

## Step 1: Check WAF Metrics

```text
BlockedRequests
```

increases at exactly the incident start.

---

## Step 2: Check Logs or Sampled Requests

Affected request matches a SQL-injection detection rule because the legitimate search string resembles SQL syntax.

WAF action:

```text
BLOCK
```

Application logs show no matching request because traffic never reaches the application.

---

## Step 3: Confirm Rule

Inspect:

* Rule group
* Rule name
* Labels
* Request URI
* matched request component
* action

---

# Root Cause

A new managed-rule configuration created a false positive for legitimate API search queries.

---

# Wrong Fix

Disable the entire WAF web ACL.

This removes unrelated protections.

---

# Safer Mitigation

Depending on the verified rule and application security requirements:

* Narrow the exception
* Scope the rule appropriately
* Exclude only the required request component
* Test the specific rule in `Count` mode first where appropriate

AWS WAF's Count action records matches while continuing rule evaluation, which makes it useful for evaluating production impact before switching a new rule to blocking behavior.

---

# Permanent Improvement

For new high-impact WAF controls:

```text
Deploy in Count
↓
Observe
↓
Analyze matches
↓
Tune exclusions
↓
Canary enforcement
↓
Block
```

Security controls should be tested with real application traffic patterns.

# Common Troubleshooting Mistakes

## Restarting targets because ALB returns 503

Check registration first.

## Assuming healthy target equals healthy application

Health checks test only what they are configured to test.

## Increasing every timeout

Find the slow component.

## Changing Route 53 repeatedly

Cached DNS answers do not disappear because you changed the record again.

## Invalidating everything in CloudFront after every deployment

Design immutable static assets instead.

## Disabling WAF because one rule causes false positives

Tune the specific rule.

## Ignoring target-group drainage during deployment

In-flight requests may be destroyed.

## Ignoring stickiness

User-specific failure patterns can result.

## Troubleshooting CloudFront without testing the origin

The origin may already be broken.

## Troubleshooting the application without identifying who generated the status code

A 502 from ALB and a 502 from an application mean different things.

# How Senior Engineers Think About the Edge

They do not ask:

> Why is AWS returning 504?

They ask:

* Which component generated it?
* Did DNS resolve the intended environment?
* Was the response cached?
* Did CloudFront contact the origin?
* Did WAF block the request?
* Which listener rule matched?
* Which target group received the request?
* Were targets actually usable?
* Did the ALB create the error?
* Did the target create the error?
* Was the target slow or unreachable?
* Did a downstream dependency cause the delay?
* Did a deployment change draining, keep-alive, or routing behavior?
* What changed immediately before customer impact?

Each answer eliminates layers.

That is how a complex request path becomes manageable.

# Key Takeaways

* Always trace the request end to end.
* Determine which component generated the HTTP error.
* EC2 running does not mean ALB has registered targets.
* Target health reason codes are valuable evidence.
* Health checks must use the correct path, port, and expected response.
* Listener rules can silently send traffic to the wrong target group.
* Validate certificates with the actual hostname.
* Deregistration delay protects in-flight requests.
* Sticky sessions can create user-specific failure patterns.
* Do not increase idle timeout before understanding latency.
* ALB 502, 503, and 504 represent different failure categories.
* Compare ELB-generated and target-generated error metrics.
* Route 53 DNS changes are affected by caching and TTL.
* `INSYNC` does not clear recursive resolver caches.
* Route 53 routing policies affect which endpoint users receive.
* Health checks and Evaluate Target Health affect routing decisions.
* CloudFront cache policies determine object freshness.
* CloudFront can intentionally serve stale content.
* CloudFront 504 often points toward origin connectivity or origin latency.
* Signed URLs and cookies introduce authorization behavior at the CDN layer.
* WAF metrics and logs can identify false-positive blocks.
* Use WAF Count mode to evaluate rules before aggressive enforcement where appropriate.
* Fix one confirmed layer at a time.
* Validate recovery with the real customer transaction.
