# AWS Troubleshooting in Production

## Part 5: RDS and Aurora Troubleshooting

How senior AWS engineers investigate database failures from the first connection timeout to CPU saturation, lock contention, replication lag, failover, and RDS Proxy problems.

A production application suddenly begins returning:

```text
database connection timed out
```

The RDS console says:

```text
Status: Available
```

The EC2 instances are running.

The security group looks correct.

So why can nobody connect?

This is where weak troubleshooting often becomes dangerous.

Someone reboots the database.

Someone increases `max_connections`.

Someone changes the security group.

Someone scales the instance class.

Someone restarts the application.

Five changes later, connectivity returns.

Nobody knows why.

That is not troubleshooting.

A senior engineer instead asks:

> At which layer does the database request fail?

A simplified RDS path is:

```text
Application
↓
DNS Resolution
↓
VPC Network
↓
RDS Endpoint
↓
Security Controls
↓
Database Listener
↓
Authentication
↓
Connection Admission
↓
Query Execution
↓
Locks / CPU / Memory
↓
Storage / I/O
↓
Database Response
```

With RDS Proxy:

```text
Application
↓
RDS Proxy Endpoint
↓
Proxy Authentication
↓
Connection Pool
↓
RDS / Aurora
↓
Database Engine
```

With Aurora:

```text
Application
↓
Cluster Endpoint / Reader Endpoint
↓
Writer or Aurora Replica
↓
Aurora Storage
```

Each layer can fail independently.

That is how we will troubleshoot Part 5.

---

# 1. Start by Classifying the Failure

Before touching RDS, classify the symptom.

## Connection timeout

Example:

```text
connection to server at
"production-db.example.us-east-1.rds.amazonaws.com"
port 5432 failed:
Connection timed out
```

Think first about:

* DNS
* endpoint
* port
* routing
* security groups
* NACLs
* database availability
* network path

## Connection refused

Think about:

* Wrong port
* Wrong endpoint
* Database listener
* Proxy target
* Engine configuration

## Authentication failed

Example:

```text
password authentication failed for user "appuser"
```

The network probably worked far enough for the database to answer.

Move toward:

* Credentials
* IAM database authentication
* Secrets Manager
* User permissions
* Password rotation
* Authentication configuration

## Too many connections

Think:

* Connection leak
* Pool configuration
* Traffic spike
* Lambda concurrency
* Application scaling
* Long transactions
* Idle sessions
* Database connection limit

## Queries are slow

Think:

* SQL execution
* Locks
* CPU
* memory
* I/O
* indexes
* execution plans
* connection waits
* downstream storage

## Reads are stale

Think:

* Reader endpoint
* Replica lag
* Application read/write routing
* Consistency expectations

The symptom determines the investigation.

---

# 2. Establish Database State

Start with the control plane.

```bash
aws rds describe-db-instances \
  --db-instance-identifier production-db
```

A more focused query:

```bash
aws rds describe-db-instances \
  --db-instance-identifier production-db \
  --query 'DBInstances[0].{
    Status:DBInstanceStatus,
    Engine:Engine,
    EngineVersion:EngineVersion,
    Class:DBInstanceClass,
    Endpoint:Endpoint.Address,
    Port:Endpoint.Port,
    AZ:AvailabilityZone,
    MultiAZ:MultiAZ,
    Public:PubliclyAccessible,
    VPC:DBSubnetGroup.VpcId,
    Subnets:DBSubnetGroup.Subnets[*].SubnetIdentifier
  }'
```

## What it checks

* Database state
* Engine
* Instance class
* Endpoint
* Port
* Availability Zone
* Multi-AZ configuration
* VPC
* Subnets

## Healthy

Typically:

```text
Status = available
```

## Important

`available` does not mean:

* Application can reach it
* Authentication works
* Queries are healthy
* Connections remain available
* Database has enough CPU
* Storage latency is healthy

It is only one piece of evidence.

---

# 3. Verify the Endpoint

AWS explicitly lists an incorrect database endpoint or port among common RDS connection problems.

Retrieve the endpoint instead of relying on an old configuration file:

```bash
aws rds describe-db-instances \
  --db-instance-identifier production-db \
  --query 'DBInstances[0].Endpoint'
```

Possible result:

```json
{
  "Address": "production-db.abc123.us-east-1.rds.amazonaws.com",
  "Port": 5432,
  "HostedZoneId": "..."
}
```

Compare this with the application connection string.

Common production mistake:

```text
Application configuration:
production-db-old.abc123.us-east-1.rds.amazonaws.com
```

Actual database:

```text
production-db-new.abc123.us-east-1.rds.amazonaws.com
```

No amount of security-group editing fixes the wrong endpoint.

---

# 4. Test DNS

From the application host:

```bash
dig production-db.abc123.us-east-1.rds.amazonaws.com
```

or:

```bash
getent hosts production-db.abc123.us-east-1.rds.amazonaws.com
```

## What it checks

Whether the application host can resolve the database endpoint.

## Healthy

The endpoint resolves to expected addresses.

## Abnormal

* Timeout
* Resolver failure
* Unexpected address
* Old endpoint in application configuration

## Next

Investigate:

* VPC DNS
* Route 53 Resolver
* Custom DNS
* Application DNS caching
* Endpoint correctness

Do not replace an RDS instance because DNS resolution is broken.

---

# 5. Test TCP Before Testing Credentials

For PostgreSQL:

```bash
nc -vz \
  production-db.abc123.us-east-1.rds.amazonaws.com \
  5432
```

For MySQL:

```bash
nc -vz \
  production-db.abc123.us-east-1.rds.amazonaws.com \
  3306
```

## Healthy

```text
Connection succeeded
```

## Timeout

Investigate:

* Security group
* Route
* NACL
* VPC connectivity
* Endpoint
* Database state

## Why this matters

If TCP cannot reach PostgreSQL on port 5432, changing the database password will not solve the incident.

Troubleshoot layers in order.

---

# 6. Security-Group Relationships

A strong application-to-RDS pattern is:

```text
Application EC2
Security Group:
sg-app
```

RDS:

```text
Inbound:
TCP 5432
Source:
sg-app
```

rather than:

```text
0.0.0.0/0
```

AWS recommends checking the DB security group when connections fail and ensuring the relevant database port is permitted from the intended source.

Inspect:

```bash
aws ec2 describe-security-groups \
  --group-ids sg-database
```

Ask:

* Is the correct database port allowed?
* Is the correct application SG referenced?
* Did a deployment attach a new SG?
* Is traffic crossing VPCs?
* Are outbound controls relevant?

Do not solve database connectivity by exposing the database broadly.

---

# 7. DB Subnet Groups

RDS subnet groups determine which VPC subnets RDS can use.

Inspect:

```bash
aws rds describe-db-subnet-groups \
  --db-subnet-group-name production-db-subnets
```

Look at:

* VPC
* Subnets
* Availability Zones
* Subnet status

A typical production layout:

```text
VPC
├── Public subnets
│   └── ALB
│
├── Private application subnets
│   └── EC2 / ECS
│
└── Private database subnets
    └── RDS
```

The application does not need the RDS instance to be publicly accessible when both communicate privately through the VPC.

---

# 8. Route and NACL Problems

If the application and RDS are in different VPCs, hybrid networks, or more complicated routing domains, verify:

```text
Source
↓
Source subnet
↓
Route
↓
Peering / TGW / VPN
↓
Destination VPC
↓
Database subnet
```

Then the return path.

AWS RDS troubleshooting guidance specifically identifies network ACLs, VPC peering, and route-table configuration as possible causes of connection failures.

For NACLs:

```bash
aws ec2 describe-network-acls \
  --filters Name=association.subnet-id,Values=subnet-0123456789abcdef0
```

Remember:

Security groups are stateful.

NACLs are stateless.

---

# 9. Use AWS's RDS Connectivity Runbook

AWS provides the Systems Manager Automation runbook:

```text
AWSSupport-TroubleshootConnectivityToRDS
```

It is specifically designed to diagnose connectivity between an EC2 instance and RDS.

AWS states that the automation checks:

* DB availability
* Security-group rules
* Network ACLs
* Route tables

This makes it particularly useful when the architecture is:

```text
EC2
↓
VPC
↓
RDS
```

It should complement engineering investigation, not replace understanding of the network path.

# 10. Authentication Failures

Suppose:

```bash
psql \
  -h production-db.abc123.us-east-1.rds.amazonaws.com \
  -U appuser \
  -d production
```

returns:

```text
password authentication failed
```

This is fundamentally different from:

```text
connection timed out
```

The database answered.

Now investigate:

* Username
* Password
* Secret version
* Secret rotation
* IAM database authentication
* Database user
* Authentication rules
* Application connection configuration

AWS RDS connection guidance distinguishes authentication errors from networking problems.

Do not keep modifying security groups when the database explicitly rejects credentials.

---

# 11. Secrets Rotation Incidents

Consider:

```text
Secrets Manager
↓
Password rotated
↓
RDS password changed
↓
Application still holds old credential
```

Symptoms:

```text
Existing pooled connections:
work

New connections:
authentication failed
```

That pattern is extremely informative.

It suggests:

* Network path works
* Existing DB sessions remain valid
* Newly authenticated sessions fail

Check:

* Secret version
* Rotation timestamp
* Application secret refresh behavior
* Connection-pool lifetime

This is why timelines matter.

---

# 12. TLS Problems

A connection can pass TCP and still fail during TLS.

For PostgreSQL:

```bash
openssl s_client \
  -connect production-db.abc123.us-east-1.rds.amazonaws.com:5432 \
  -starttls postgres
```

For MySQL, use an engine-appropriate client and SSL settings.

Potential issues:

* Certificate validation
* Missing CA bundle
* Expired trust store
* Incorrect SSL mode
* Client incompatibility
* Certificate rotation

If:

```text
nc succeeds
```

but the database client fails during TLS, stop investigating route tables.

The network layer has already proven useful connectivity.

---

# 13. Connection Exhaustion

One of the most common database production failures is not:

```text
Database down
```

but:

```text
Database cannot accept more connections
```

Monitor:

```text
DatabaseConnections
```

Example:

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DatabaseConnections \
  --dimensions Name=DBInstanceIdentifier,Value=production-db \
  --statistics Maximum \
  --period 300 \
  --start-time 2026-08-05T07:00:00Z \
  --end-time 2026-08-05T08:00:00Z
```

## What it checks

Maximum database connection count over the selected interval.

## What to compare

* Normal baseline
* Incident period
* Deployment time
* Application replica count
* Lambda concurrency
* Traffic
* Connection-pool settings

A number without context is not diagnosis.

---

# 14. Why Connections Suddenly Explode

Suppose:

```text
Normal:
120 DB connections

Deployment:
Application scales 10 → 50 pods

Each pod:
30 connection pool

Potential:
1,500 connections
```

The database may support far fewer.

The problem is not necessarily insufficient RDS capacity.

It can be application architecture.

A dangerous response is:

```text
Increase max_connections
```

without understanding:

```text
Why are there so many connections?
```

---

# 15. Find Connection Leaks

Symptoms:

```text
Traffic remains stable
DatabaseConnections continuously increases
Connections never return to baseline
```

Investigate application behavior.

For PostgreSQL:

```sql
SELECT
    state,
    count(*)
FROM pg_stat_activity
GROUP BY state;
```

Then:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    backend_start,
    query_start
FROM pg_stat_activity
ORDER BY backend_start;
```

Questions:

* Who owns the connections?
* Are they active?
* Are they idle?
* Are they idle in transaction?
* Which application opened them?
* When did they begin?

Do not terminate sessions blindly before identifying ownership.

---

# 16. Idle in Transaction

PostgreSQL:

```text
idle in transaction
```

deserves attention.

It can mean:

```text
BEGIN
↓
Application performs work
↓
Never COMMIT / ROLLBACK
↓
Transaction remains open
```

Consequences can include:

* Locks remaining held
* Connection consumption
* Vacuum interference
* Transaction-age problems

The database may appear slow when the actual bug lives in application transaction handling.

---

# 17. Slow Queries

A slow database incident requires distinguishing:

```text
Database is slow
```

from:

```text
One query is slow
```

and:

```text
Queries are waiting
```

Those are different incidents.

Investigate:

* Query latency
* Execution plans
* Rows examined
* Index usage
* Lock waits
* CPU
* I/O
* Memory
* Concurrency

A database can have low CPU while applications remain stuck on locks.

---

# 18. Performance Insights

AWS database performance tooling helps identify database load and the sources contributing to it.

Use performance analysis to investigate:

* Top SQL
* Wait events
* Database load
* Users
* Hosts
* Sessions

Ask:

> What changed when database load increased?

Not merely:

> Is CPU high?

CPU is only one resource.

---

# 19. CPU Saturation

Monitor:

```text
CPUUtilization
```

A sustained value near:

```text
100%
```

requires investigation.

But CPU is a symptom.

Potential causes:

* Expensive query
* Missing index
* Query-plan regression
* Increased traffic
* Connection storm
* Background maintenance
* Batch job
* Too-small instance class

Do not immediately scale vertically.

First determine who consumes the CPU.

---

# 20. CPU and Query Correlation

Suppose:

```text
13:00
CPU = 35%

13:07
Deployment completed

13:10
CPU = 96%

13:12
API latency increases

13:14
Database timeout errors begin
```

Performance analysis shows one new query dominates database load.

That timeline is far more useful than:

> RDS needs a larger instance.

The deployment becomes the primary hypothesis.

---

# 21. Freeable Memory

Monitor:

```text
FreeableMemory
```

But interpret it carefully.

Database engines intentionally use memory for:

* Buffer/cache
* Query processing
* Connections
* Internal structures

Low free memory does not automatically equal memory failure.

Look for correlated signals:

* Swap usage
* Latency
* Connection growth
* CPU
* OOM-related behavior
* Engine logs

The question is:

> Is memory pressure affecting database performance?

not simply:

> Is FreeableMemory low?

---

# 22. Storage Pressure

For RDS storage-backed engines, investigate:

* FreeStorageSpace
* ReadIOPS
* WriteIOPS
* ReadLatency
* WriteLatency
* ReadThroughput
* WriteThroughput
* DiskQueueDepth

A database may have healthy CPU but terrible application latency because storage is the bottleneck.

Example:

```text
CPU:
42%

ReadLatency:
increasing

DiskQueueDepth:
increasing

Application latency:
increasing
```

CPU is not the problem.

Storage waits are.

---

# 23. Free Storage Space

Storage exhaustion can become a serious operational incident.

Monitor:

```text
FreeStorageSpace
```

Potential causes:

* Table growth
* Index growth
* Temporary operations
* Logs
* Binary logs
* Maintenance activity
* Unexpected ingestion

Do not wait until the database has almost no remaining storage before investigating growth.

Capacity trend matters.

---

# 24. IOPS and Throughput

Storage performance has multiple dimensions.

Do not confuse:

```text
IOPS
```

with:

```text
Throughput
```

A workload can perform:

* Many small operations
* Fewer large operations

and stress storage differently.

During an incident compare:

```text
ReadIOPS
WriteIOPS
ReadThroughput
WriteThroughput
ReadLatency
WriteLatency
DiskQueueDepth
```

The goal is to determine whether the database waits on storage.

---

# 25. Lock Contention

Consider:

```text
Transaction A
↓
Locks row

Transaction B
↓
Needs same row
↓
Waits

Transaction C
↓
Needs related resource
↓
Waits
```

Now application latency rises.

CPU may remain moderate.

Scaling RDS might do almost nothing.

For PostgreSQL, investigate blocked activity through engine-native lock and activity views.

Example:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE wait_event IS NOT NULL;
```

Look for:

```text
wait_event_type = Lock
```

---

# 26. Blocking Versus Blocked Sessions

The most important session may not be the one showing the longest wait.

You need to identify:

```text
BLOCKER
↓
BLOCKED SESSION
↓
BLOCKED SESSION
↓
BLOCKED SESSION
```

One long transaction can create a queue behind it.

The incident may look like hundreds of slow queries.

The root cause may be one transaction.

---

# 27. Killing Sessions Is Mitigation, Not Root Cause

During an outage, terminating a confirmed blocking session may restore service.

But then ask:

* Why did it remain open?
* Which code path created it?
* Was a deployment involved?
* Was a batch operation unbounded?
* Was transaction timeout missing?
* Did an engineer run a manual statement?

Otherwise the incident will repeat.

---

# 28. Parameter Groups

RDS parameter groups control database engine configuration.

Inspect:

```bash
aws rds describe-db-parameters \
  --db-parameter-group-name production-postgres
```

Changes can affect:

* Connections
* Logging
* Memory
* Query behavior
* Timeouts
* Replication
* Engine-specific behavior

Some parameters apply immediately.

Others require reboot.

Always know:

```text
ApplyType
```

and:

```text
ApplyMethod
```

before changing production parameters.

---

# 29. Pending Reboot

Inspect:

```bash
aws rds describe-db-instances \
  --db-instance-identifier production-db \
  --query 'DBInstances[0].PendingModifiedValues'
```

Also inspect parameter status.

A configuration may have been changed but not yet activated.

This creates a dangerous troubleshooting assumption:

> We changed the parameter, so the database is using it.

Not necessarily.

# 30. Enhanced Monitoring

Enhanced Monitoring provides operating-system-level visibility for supported RDS environments.

It helps when CloudWatch instance metrics alone do not explain the behavior.

Useful areas include:

* CPU breakdown
* memory
* process activity
* filesystem
* load
* operating-system behavior

This can help distinguish:

```text
Database SQL workload
```

from broader host-level resource pressure.

# 31. Database Logs

Depending on engine and configuration, investigate logs such as:

* PostgreSQL logs
* MySQL error logs
* slow query logs
* general logs where appropriate
* audit logs
* upgrade logs

Retrieve available log files:

```bash
aws rds describe-db-log-files \
  --db-instance-identifier production-db
```

Then download a portion:

```bash
aws rds download-db-log-file-portion \
  --db-instance-identifier production-db \
  --log-file-name postgresql.log \
  --output text
```

Look for:

* Authentication errors
* Deadlocks
* Connection failures
* Restarts
* Recovery activity
* Engine errors
* Long-running queries where logged

Logs should be correlated with the incident timeline.

---

# 32. RDS Events

Control-plane events can reveal:

* Reboots
* Failovers
* Maintenance
* Storage changes
* Instance modifications
* Backups
* Availability changes

Inspect:

```bash
aws rds describe-events \
  --source-type db-instance \
  --source-identifier production-db \
  --duration 1440
```

If an outage began at 03:14, ask:

> What happened to RDS around 03:14?

Do not start with a 24-hour pile of unrelated logs.

Use the timeline.

---

# 33. Multi-AZ Failover

Multi-AZ provides high availability, but failover is still an application event.

During failover:

```text
Primary unavailable
↓
Standby promoted
↓
RDS endpoint follows new primary
↓
Application reconnects
```

Existing connections can break.

Applications must reconnect.

AWS notes that failover involves endpoint/DNS behavior that clients must recognize, and DNS caching can delay how quickly applications follow the new primary.

---

# 34. Why Failover Can Feel Longer Than Expected

Suppose RDS completes infrastructure failover.

But application remains unavailable.

Possible reasons:

* Application caches DNS
* Connection pool retains dead connections
* Retry interval too long
* Application does not reconnect correctly
* Driver configuration
* DNS TTL behavior
* Startup health logic

Therefore:

```text
Database failover duration
```

and:

```text
Customer outage duration
```

are not necessarily the same number.

Measure both.

---

# 35. Test Failover Behavior Before an Incident

A highly available database is not enough.

The application must be highly available too.

Test:

```text
Failover
↓
Old connection breaks
↓
Application detects failure
↓
DNS / endpoint resolves appropriately
↓
New connection established
↓
Transaction resumes safely
```

Measure:

* Detection time
* Retry time
* Reconnection time
* Customer-visible errors
* Total recovery time

High availability is an end-to-end property.

---

# 36. Aurora Architecture Changes the Investigation

Aurora uses a cluster architecture with:

```text
Writer
+
Aurora Replicas
+
Shared distributed storage
```

Applications commonly connect through endpoints rather than hardcoding individual instance endpoints.

Important endpoint types include:

```text
Cluster endpoint
Reader endpoint
Instance endpoint
Custom endpoint
```

The endpoint selected determines workload behavior.

---

# 37. Aurora Cluster Endpoint

The cluster endpoint is typically used for read/write workloads.

Conceptually:

```text
Application writes
↓
Cluster endpoint
↓
Current writer
```

After writer failover, the cluster endpoint follows the new writer.

Do not hardcode the old writer's instance endpoint for normal application write traffic unless there is a deliberate reason.

Otherwise failover behavior can be undermined.

---

# 38. Aurora Reader Endpoint

Aurora's reader endpoint distributes new read-only connections among available Aurora Replicas. It balances connections, not individual queries.

Architecture:

```text
Read application
↓
Reader endpoint
├── Reader 1
├── Reader 2
└── Reader 3
```

This distinction matters.

A single long-lived connection does not have every query distributed among all replicas.

---

# 39. A Subtle Reader Endpoint Behavior

If an Aurora cluster contains no replicas, AWS documents that the reader endpoint can connect to the primary instance.

Therefore do not infer:

```text
Using reader endpoint
=
Definitely running on replica
```

without checking cluster topology.

---

# 40. Aurora Replication Lag

Read replicas can lag behind writes.

This creates:

```text
WRITE
↓
Writer commits
↓
Application immediately reads from replica
↓
Replica has not applied change yet
↓
Old result returned
```

The database is not necessarily broken.

The application's consistency assumption may be wrong.

For Aurora-related replication scenarios, AWS provides replication-lag metrics and troubleshooting guidance.

---

# 41. Read-After-Write Consistency

Imagine checkout:

```text
INSERT order
↓
COMMIT on writer
↓
Immediately query reader endpoint
↓
"Order not found"
```

The application reports:

```text
Order creation failed
```

But the order exists.

This can create duplicate retries.

The real problem is architectural:

A workflow requiring immediate read-after-write consistency was routed to an asynchronous read path.

Possible design approaches include:

* Read from writer for consistency-sensitive operation
* Delay replica-dependent read
* Design application consistency semantics explicitly

Do not treat every stale read as a failed database write.

---

# 42. RDS Proxy

RDS Proxy introduces a managed connection layer:

```text
Application
↓
RDS Proxy
↓
Pooled database connections
↓
RDS / Aurora
```

It can help applications handle large numbers of database connections and improve resilience around database failovers.

But it adds another troubleshooting layer.

---

# 43. RDS Proxy Connectivity

AWS recommends inspecting:

```bash
aws rds describe-db-proxies \
  --db-proxy-name production-proxy
```

Then:

```bash
aws rds describe-db-proxy-target-groups \
  --db-proxy-name production-proxy
```

And:

```bash
aws rds describe-db-proxy-targets \
  --db-proxy-name production-proxy
```

AWS specifically recommends these commands when verifying proxy connectivity.

---

# 44. Proxy Target Health

Possible states include:

```text
AVAILABLE
UNAVAILABLE
REGISTERING
```

AWS documents reasons including:

```text
PENDING_PROXY_CAPACITY
UNREACHABLE
CONNECTION_FAILED
AUTH_FAILURE
```

This gives you a crucial distinction:

```text
Application can reach proxy
```

does not prove:

```text
Proxy can reach database
```

Those are two different connections.

---

# 45. RDS Proxy Security Groups

The full path is:

```text
Application
↓
Proxy Security Group
↓
RDS Proxy
↓
Database Security Group
↓
RDS
```

AWS states that security-group configuration must allow communication from applications to the proxy and from the proxy to the database.

Therefore:

```text
App → Proxy works
```

while:

```text
Proxy → Database fails
```

is entirely possible.

---

# 46. Proxy Authentication

RDS Proxy can use credentials stored through AWS Secrets Manager and can support IAM-related authentication configurations.

A proxy target can report authentication problems.

AWS documents an example where proxy target health reports:

```text
Proxy does not have any registered credentials
```

and recommends verifying the registered credentials and IAM role used to access the Secrets Manager secret.

Do not classify every proxy connection failure as networking.

---

# 47. Proxy Connection Pressure

RDS Proxy itself has operational limits.

AWS documents errors involving:

* Connection-rate limits
* Simultaneous connections
* IAM authentication rates
* Insufficient proxy subnet IP capacity

So:

```text
We use RDS Proxy
```

does not mean:

```text
Connection architecture can no longer fail.
```

Monitor the proxy too.

---

# 48. Proxy Multiplexing and Pinning

One of RDS Proxy's advantages is its ability to multiplex application connections onto database connections when possible.

Certain session behavior can cause a connection to become pinned.

When many sessions become pinned:

```text
Expected:
Many client connections
↓
Fewer reusable DB connections

Actual:
Many client connections
↓
Many pinned DB sessions
```

The expected connection-reduction benefit decreases.

When proxy efficiency changes unexpectedly, investigate application session behavior rather than only scaling the database.

* Cost
* Retention

# REAL TROUBLESHOOTING LAB 2

## Connections Suddenly Reach the Maximum

### Incident

At 10:00:

```text
DatabaseConnections:
180
```

At 10:05:

```text
Application deployment begins
```

At 10:12:

```text
DatabaseConnections:
950
```

New connections fail.

---

## Step 1: Check Traffic

Request volume increased only 8 percent.

Traffic does not explain a 5x connection increase.

---

## Step 2: Check Deployment

Application changed:

```text
Pods:
20 → 50

Connection pool:
10 → 25
```

Potential pool capacity:

```text
Before:
20 × 10 = 200

After:
50 × 25 = 1,250
```

Now the incident makes sense.

---

## Step 3: Inspect Sessions

PostgreSQL:

```sql
SELECT
    application_name,
    state,
    count(*)
FROM pg_stat_activity
GROUP BY application_name, state
ORDER BY count(*) DESC;
```

Hundreds of idle application sessions appear.

---

# Root Cause

Application scaling and connection-pool configuration multiplied database connection demand.

The database did not spontaneously lose capacity.

---

# Mitigation

Rollback pool configuration.

Reduce application replicas where operationally safe.

Restore connection headroom.

---

# Permanent Fix

Establish a connection budget:

```text
Database connection capacity
-
Administrative reserve
-
Background workloads
=
Application connection budget
```

Then divide that budget across application replicas.

Consider RDS Proxy where workload characteristics make it appropriate.

```sql
SELECT *

```

Execution plan now scans a very large table.

## Application Becomes Slow Because of Lock Contention

### Incident

API latency:

```text
normal:
250 ms

incident:
20–40 seconds
```

RDS CPU:

```text
38%
```

Connections:

```text
normal
```

Storage:

```text
normal
```

Yet the application is nearly unusable.

---

## Step 1: Inspect Waits

PostgreSQL:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE wait_event IS NOT NULL;
```

Many sessions:

```text
wait_event_type:
Lock
```

---

## Step 2: Identify Blocker

A maintenance process started:

```text
BEGIN;
UPDATE accounts ...
```

The transaction never committed.

Many application transactions now wait behind it.

---

# Root Cause

One long-running transaction held locks required by customer operations.

---

# Mitigation

After verifying ownership and rollback impact, terminate or resolve the blocking transaction according to incident procedure.

Latency recovers immediately.

---

# Permanent Fix

* Transaction timeouts
* Smaller batch operations
* Better deployment controls
* Lock monitoring
* Runbook for production maintenance
* Safer transaction handling

---

# Lesson

A slow database does not require high CPU.

Waiting is also database load.

# REAL TROUBLESHOOTING LAB 5

## Aurora Readers Return Stale Results

### Incident

Customer creates an order.

API returns:

```text
Order created successfully
```

The frontend immediately requests the order.

Response:

```text
404 Order not found
```

Refreshing two seconds later works.

---

## Architecture

```text
POST /orders
↓
Aurora Writer

GET /orders/{id}
↓
Aurora Reader Endpoint
```

---

## Step 1: Verify Write

Writer contains the row.

The write succeeded.

---

## Step 2: Inspect Read Routing

Immediate read is routed to Aurora reader endpoint.

Aurora reader endpoints distribute read connections across replicas.

---

## Step 3: Check Replication Behavior

The selected replica had not yet reflected the latest write at the instant of the read.

---

# Root Cause

The application assumed immediate read-after-write consistency while sending the read to an asynchronous replica path.

---

# Wrong Fix

Increase the writer instance size.

---

# Correct Architecture

Consistency-sensitive requests should use a path that satisfies their consistency requirement.

For example:

```text
Create order
↓
Writer
↓
Immediate confirmation read
↓
Writer
```

while non-critical reporting can use readers.

# REAL TROUBLESHOOTING LAB 6

## Multi-AZ Failover Takes Longer Than Expected

### Incident

A controlled RDS failover is initiated.

RDS promotes the standby.

But the application remains unavailable substantially longer.

---

## Step 1: Check RDS Events

Failover completes.

New primary becomes available.

---

## Step 2: Test Endpoint From Fresh Client

Fresh shell:

```bash
dig production-db.abc123.us-east-1.rds.amazonaws.com
```

resolves correctly.

Fresh DB connection succeeds.

---

## Step 3: Check Application

Application JVM caches the previous DNS result longer than expected.

Existing pool also contains broken connections to the old primary.

---

# Root Cause

Database failover completed.

Application recovery did not.

DNS caching and connection-pool behavior extended customer-visible downtime.

AWS notes that application DNS caching can delay recognition of database role changes during failover.

---

# Permanent Fix

Test:

* DNS caching behavior
* Driver failover behavior
* Connection validation
* Retry policy
* Pool eviction
* RDS Proxy where appropriate

Measure:

```text
RDS failover time
```

separately from:

```text
Application recovery time
```

### Incident

The database password was manually rotated.

The application could reach RDS Proxy.

# Why `nc` Was Misleading

`nc` proved:

```text

↓
Proxy
```

It did not prove:

```text
Proxy
↓
Database authentication
```

---

# Correct Fix

Synchronize credential state using the approved secret-rotation process.

Validate proxy target health:

```text
AVAILABLE
```

Then execute a real database transaction through the proxy.

# What Not to Do

Do not reboot RDS because you do not understand the failure.

Do not open database security groups to the world.

Do not increase `max_connections` without knowing why connections increased.

Do not scale the instance because CPU is high before identifying the workload.

Do not terminate blocking sessions before understanding what they are doing.

Do not assume low CPU means the database is healthy.

Do not assume `available` means the application can connect.

Do not assume the Aurora reader endpoint provides immediate read-after-write consistency.

Do not assume Multi-AZ means applications automatically recover correctly.

Do not assume reaching RDS Proxy means RDS Proxy can reach the database.

Do not change five parameters during one incident.

# How Senior Engineers Think About Database Incidents

They do not ask:

> Is RDS down?

They ask:

> What exactly stopped working?

Then:

* Can DNS resolve the endpoint?
* Can TCP reach the port?
* Can TLS negotiate?
* Can the user authenticate?
* Can the database accept another connection?
* Are connections leaking?
* Are queries executing or waiting?
* What are they waiting on?
* Is CPU actually the bottleneck?
* Is storage latency rising?
* Is one transaction blocking everyone else?
* Is the application reading from the correct Aurora endpoint?
* Is replica lag compatible with the application's consistency requirement?
* Did failover finish but the application fail to reconnect?
* Can the application reach the proxy?
* Can the proxy reach and authenticate to the database?
* What changed immediately before the incident?

Those questions turn:

# Key Takeaways

* Separate connectivity, authentication, capacity, query, lock, storage, replication, and failover problems.
* `available` does not mean healthy from the application's perspective.
* Verify endpoint and port before changing networking.
* Test DNS before assuming routing failure.
* Test TCP before troubleshooting database credentials.
* Security-group relationships are a common source of RDS connection failures.
* AWS provides `AWSSupport-TroubleshootConnectivityToRDS` for EC2-to-RDS network diagnosis.
* Connection exhaustion is often caused by application architecture.
* Increasing `max_connections` is not a substitute for connection management.
* Slow databases can be waiting rather than consuming CPU.
* Lock contention can create severe latency with moderate CPU.
* Storage metrics matter alongside compute metrics.
* Parameter changes may require reboot.
* RDS events belong in the incident timeline.
* Aurora reader endpoints balance connections across readers, not individual queries.
* Replica lag can create stale reads.
* Application consistency requirements should determine read routing.
* Database failover time and customer recovery time are different measurements.
* DNS caching can extend application recovery after failover.
* RDS Proxy adds another connection layer that must be investigated independently.
* Proxy reachability does not prove proxy-to-database connectivity.
* Proxy target health can reveal connectivity and authentication failures.
* Fix the layer the evidence identifies.
* Validate recovery with the actual business transaction.
