# AWS Troubleshooting in Production

## Part 1: How Senior Engineers Troubleshoot AWS

**How experienced AWS engineers investigate cloud failures without guessing, restarting resources blindly, or changing several things at once**

A production alarm fires.

Customers report intermittent errors.

The application team says the deployment succeeded.

The EC2 instances are running.

The ECS tasks show healthy.

The database is available.

The load balancer still has registered targets.

Nothing appears completely broken.

Yet customers are receiving HTTP 500, 502, 503, and 504 responses.

This is where inexperienced troubleshooting often becomes dangerous.

One engineer restarts the application.

Another replaces EC2 instances.

Someone increases the Auto Scaling group size.

Another person changes a security group.

A database engineer increases the connection limit.

The deployment team begins another release.

Within minutes, the environment has changed in several places.

The original evidence is disappearing.

Nobody knows which action helped.

Nobody knows which action made the incident worse.

The system may recover, but the team has learned almost nothing.

Senior AWS engineers work differently.

They do not begin by changing infrastructure.

They begin by defining the failure.

They identify the customer impact.

They establish the timeline.

They inspect recent changes.

They separate symptoms from causes.

They collect evidence across the request path.

They mitigate carefully.

Only then do they investigate the deeper root cause.

AWS troubleshooting is not the ability to remember hundreds of console pages or CLI commands.

It is the discipline of moving from uncertainty to evidence without destroying the information needed to understand the incident.

# Why AWS Troubleshooting Is Different

Traditional server troubleshooting often begins with one machine.

An engineer connects to the server and checks:

* CPU
* Memory
* Disk
* Processes
* Network connections
* Application logs
* System logs

That approach still matters in AWS, but one server is rarely the entire system.

A customer request may pass through:

```text
Client
↓
Route 53
↓
CloudFront
↓
AWS WAF
↓
Application Load Balancer
↓
EC2 or ECS
↓
RDS
```

The symptom may appear at one layer while the cause exists somewhere else.

An HTTP 504 response may result from:

* CloudFront timing out while waiting for the origin
* The Application Load Balancer waiting for a target
* An application thread waiting for RDS
* RDS lock contention
* Exhausted database connections
* A slow third-party API
* A deployment that changed request behavior
* Resource saturation on only part of the fleet

This is why AWS troubleshooting requires systems thinking.

The engineer must understand:

* The application
* AWS-managed services
* Network paths
* Identity and permissions
* Infrastructure configuration
* Deployment history
* Service dependencies
* Customer behavior

The cloud gives engineers more telemetry and automation, but it also creates more layers through which failure can propagate.

# Operational Excellence Is a Continuous Capability

AWS Well-Architected guidance describes operational excellence as more than reacting to outages. It covers how teams are organized, how workloads are prepared, how systems are operated at scale, and how operations improve over time. AWS groups the operational-excellence discipline into organization, prepare, operate, and evolve.

This distinction matters.

An organization is not operationally mature because it solved one difficult outage.

It is mature when it has repeatable capabilities for:

* Detecting customer impact
* Identifying ownership
* Gathering evidence
* Making safe changes
* Recovering predictably
* Learning from incidents
* Improving architecture and procedures

Troubleshooting begins before the incident.

It begins with logging, monitoring, tagging, access, runbooks, deployment records, and ownership.

# Shared Responsibility During Incidents

AWS operates the cloud infrastructure.

Customers operate their workloads in the cloud.

During an incident, this creates a shared responsibility boundary.

AWS may be responsible for:

* The physical facilities
* The underlying hardware
* Core regional infrastructure
* Managed-service components
* The service control plane

The customer may still be responsible for:

* Workload configuration
* Application behavior
* IAM policies
* Security groups
* Route tables
* Scaling settings
* Database configuration
* Deployment changes
* Logging
* Monitoring
* Recovery procedures

An AWS service event may contribute to an incident, but engineers should not assume every AWS failure is caused by AWS.

Similarly, a healthy public AWS status page does not prove that the customer’s individual account, Availability Zone, resources, or configuration are healthy.

Senior engineers check both sides:

1. Is AWS reporting a service or account-specific event?
2. Is our workload behaving incorrectly because of our own changes, configuration, capacity, or dependencies?

# Control Plane Versus Data Plane

One of the most useful distinctions in AWS troubleshooting is the difference between the control plane and the data plane.

## Control plane

The control plane handles management operations.

Examples include:

* Creating an EC2 instance
* Changing a security group
* Registering an ALB target
* Updating a CloudFront distribution
* Modifying an RDS instance
* Deploying an ECS task definition
* Changing an Auto Scaling policy

These activities are generally performed through:

* AWS Management Console
* AWS CLI
* AWS SDKs
* Infrastructure as Code
* AWS APIs

## Data plane

The data plane handles the workload’s actual traffic and operations.

Examples include:

* A user sending an HTTP request
* An application reading an S3 object
* A service querying RDS
* CloudFront retrieving content from an origin
* An ALB forwarding traffic to a target
* A message being processed from a queue

The distinction matters because one plane can be impaired while the other remains functional.

For example:

* Existing EC2 instances may continue serving traffic even if a management API is temporarily impaired.
* Engineers may be able to modify resources through the control plane while the application data path is broken.
* A deployment API call may succeed even though the newly deployed application cannot serve users.

A successful control-plane operation does not prove that the data plane is healthy.

“Deployment succeeded” means the deployment system completed its operation.

It does not mean customers can successfully complete a transaction.

# Failure Domains in AWS

Senior engineers classify the possible failure domain before investigating deeply.

## Resource-level failure

One instance, task, container, volume, or database node is affected.

Example:

* One EC2 instance has a full root volume.
* One ECS task has a memory leak.
* One ALB target is unhealthy.

## Application-level failure

The infrastructure is healthy, but the software behaves incorrectly.

Example:

* A new code path throws exceptions.
* The application creates too many database connections.
* A feature flag activates incomplete functionality.

## Network-level failure

Traffic cannot reach the correct destination or response traffic cannot return.

Example:

* Incorrect route table
* Security-group change
* Network ACL rejection
* DNS resolution failure
* Target-port mismatch

## Availability Zone failure

Resources in one Availability Zone are degraded while other zones continue working.

Example:

* A subset of targets has increased latency.
* A zonal dependency is impaired.
* One subnet has a routing or capacity problem.

## Regional failure

A service or workload experiences broad impact in one AWS Region.

Example:

* A regional managed-service problem
* Regional network degradation
* A workload deployed only in one Region

## Account-level failure

The issue affects resources because of account configuration.

Example:

* Service Control Policy change
* IAM permission removal
* Account quota exhaustion
* KMS access change
* Organization-wide security control

## Dependency-level failure

The failing component is outside the immediate application.

Example:

* RDS
* S3
* Identity provider
* Third-party payment processor
* External API
* Shared internal service

These domains can overlap.

The goal is not to select the root cause immediately.

The goal is to reduce the investigation space.

# Symptoms Are Not Causes

A symptom describes what the system is doing.

A cause explains why it is doing it.

Examples of symptoms:

* HTTP 500 errors
* HTTP 502 errors
* HTTP 503 errors
* HTTP 504 errors
* High latency
* Failed login
* Slow checkout
* Connection timeout
* Unhealthy target
* ECS task restart
* Database connection error

These symptoms do not identify the cause.

Consider an HTTP 503 response.

Possible causes include:

* No healthy ALB targets
* Target deregistration during deployment
* Service capacity dropping below demand
* An application intentionally returning 503
* A dependency being unavailable
* A routing rule sending requests to the wrong target group

The first visible error is a starting point, not a conclusion.

A useful troubleshooting statement sounds like this:

> Between 14:05 and 14:22 UTC, approximately 7 percent of checkout requests in `us-east-1` returned HTTP 5xx responses. The errors began three minutes after deployment `checkout-api-2026.08.05.3`. Read-only browsing remained healthy.

That statement is far more useful than:

> Production is down.

# Establish Customer Impact First

The first priority is to understand the user impact.

Ask:

* Which customer action is failing?
* Are all users affected?
* Are only certain regions affected?
* Are failures intermittent or continuous?
* Are specific URLs affected?
* Are authenticated and unauthenticated requests affected equally?
* Is one device type or client version affected?
* Did the problem begin suddenly or gradually?
* Is data at risk?
* Is the system unavailable, degraded, or merely noisy?

The answers determine incident severity and investigation priority.

A dashboard may show a large number of errors, but the errors might come from a health-check endpoint.

Another incident may show only a small number of errors, but each error represents a failed payment.

Technical volume and business impact are not always the same.

# Define the Blast Radius

The blast radius describes how much of the system is affected.

Useful dimensions include:

* Account
* Region
* Availability Zone
* VPC
* Subnet
* Load balancer
* Target group
* Service
* Application version
* Customer segment
* Request path
* Dependency

Examples:

```text
All users in all Regions
```

```text
Only traffic routed through us-east-1
```

```text
Only targets in Availability Zone us-east-1b
```

```text
Only checkout requests using the new application version
```

```text
Only requests that require database writes
```

A narrow blast radius is a powerful clue.

If only one Availability Zone is affected, investigate zonal targets, subnets, networking, capacity, and dependencies.

If only the new version is affected, compare the old and new deployments.

If only database-writing operations fail, focus on RDS, transactions, locks, permissions, and connection pools.

# Build an Incident Timeline

The timeline connects customer symptoms with system events.

Start with the earliest reliable time.

Include:

* First customer report
* First alarm
* Deployment start
* Deployment completion
* Infrastructure changes
* Scaling events
* Target-health changes
* Database events
* AWS Health events
* Mitigation actions
* Recovery confirmation

Example:

```text
13:55 UTC  Deployment approved
14:00 UTC  ECS deployment started
14:03 UTC  New tasks registered in target group
14:05 UTC  ALB target 5xx errors increased
14:07 UTC  Checkout latency exceeded SLO
14:09 UTC  First customer-support report
14:12 UTC  Database connections reached 92% of limit
14:15 UTC  Deployment paused
14:18 UTC  Rollback initiated
14:22 UTC  Error rate returned to baseline
14:28 UTC  Customer transaction validation completed
```

A timeline prevents the team from treating unrelated events as causal.

It also helps distinguish the original failure from the effects of mitigation.

# Check Recent Changes

Production incidents frequently follow change.

Examples include:

* Application deployment
* Infrastructure-as-Code update
* Security-group change
* Route-table change
* WAF rule update
* CloudFront behavior change
* Target-group health-check change
* RDS parameter modification
* Secret rotation
* IAM policy update
* Auto Scaling change
* Certificate replacement
* Feature-flag activation

Recent change is not proof of root cause.

However, it is one of the strongest investigation signals.

The engineer should ask:

* What changed shortly before the incident?
* Which resources were affected?
* Who or what made the change?
* Was the change expected?
* Was it tested?
* Can it be reversed safely?
* Did the impact begin immediately or after load increased?

# AWS Health and Service Events

AWS Health provides both public service-health information and account-specific events. The public service-health view reports regional service events, while signed-in account views can show events that affect the customer’s own resources. AWS Health organizational view can centralize affected accounts, Regions, Availability Zones, start times, end times, and event status across an AWS Organization.

Check AWS Health early, but do not stop there.

A useful sequence is:

1. Check for public regional events.
2. Check account-specific events.
3. Check affected resources.
4. Compare the event start time with the incident timeline.
5. Determine whether the AWS event explains the complete blast radius.

An AWS event may be relevant without being the complete cause.

For example, a brief zonal impairment may expose that the application had insufficient healthy capacity in the remaining zones.

The cloud event triggered the incident.

The architecture allowed the incident to become customer-facing.

Both matter.

# CloudTrail Investigation

CloudTrail records AWS account activity from the console, CLI, SDKs, APIs, and AWS services. CloudTrail Event history is available automatically and provides a searchable record of management events from the previous 90 days in each Region.

CloudTrail answers questions such as:

* Who changed the resource?
* Which API action was called?
* When did the change occur?
* Which IAM role or user made it?
* Which source IP initiated it?
* Was the change made through CloudFormation, Terraform, a pipeline, or manually?
* What request parameters were submitted?
* Did AWS return an error?

## CLI investigation

Confirm the active identity first:

```bash
aws sts get-caller-identity
```

Expected output:

```json
{
  "UserId": "AROAXXXXXXXXXXXXX:incident-session",
  "Account": "123456789012",
  "Arn": "arn:aws:sts::123456789012:assumed-role/IncidentResponder/incident-session"
}
```

This prevents investigation in the wrong account.

Confirm the Region:

```bash
aws configure get region
```

List recent CloudTrail events:

```bash
aws cloudtrail lookup-events \
  --start-time 2026-08-05T13:45:00Z \
  --end-time 2026-08-05T14:30:00Z \
  --max-results 50
```

Filter for a specific API operation:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes \
    AttributeKey=EventName,AttributeValue=UpdateService \
  --start-time 2026-08-05T13:45:00Z \
  --end-time 2026-08-05T14:30:00Z
```

Filter by resource name:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes \
    AttributeKey=ResourceName,AttributeValue=checkout-service \
  --start-time 2026-08-05T13:45:00Z \
  --end-time 2026-08-05T14:30:00Z
```

CloudTrail Event history is regional, and AWS notes that CloudTrail events are not an ordered stack trace. Sort and correlate timestamps instead of assuming returned events form a perfect execution sequence.

## What to capture

Preserve:

* `eventTime`
* `eventSource`
* `eventName`
* `awsRegion`
* `sourceIPAddress`
* `userIdentity`
* `requestParameters`
* `responseElements`
* `errorCode`
* `errorMessage`
* `requestID`
* `eventID`

Do not simply record that “someone updated ECS.”

Record the exact task definition, deployment configuration, role, timestamp, and request ID.

# CloudWatch Metrics

Metrics show how system behavior changed over time.

The most useful metrics depend on the architecture.

For the sample path, inspect:

## CloudFront

* `Requests`
* `TotalErrorRate`
* `4xxErrorRate`
* `5xxErrorRate`
* `OriginLatency`

## Application Load Balancer

* `RequestCount`
* `HTTPCode_ELB_5XX_Count`
* `HTTPCode_Target_5XX_Count`
* `TargetResponseTime`
* `HealthyHostCount`
* `UnHealthyHostCount`
* `RejectedConnectionCount`

AWS distinguishes load-balancer-generated 5xx responses from target-generated 5xx responses. Target errors are recorded in `HTTPCode_Target_5XX_Count`, while load-balancer errors are recorded separately. This distinction helps determine whether the failure is at the ALB layer or behind it.

## EC2

* `CPUUtilization`
* `StatusCheckFailed`
* `StatusCheckFailed_Instance`
* `StatusCheckFailed_System`
* `NetworkIn`
* `NetworkOut`
* EBS metrics where relevant

Remember that standard EC2 metrics do not include operating-system memory or disk utilization by default. Those generally require the CloudWatch Agent or another monitoring system.

## ECS

* `CPUUtilization`
* `MemoryUtilization`
* Running task count
* Pending task count
* Deployment state
* Service events

## RDS

* `CPUUtilization`
* `DatabaseConnections`
* `FreeableMemory`
* `FreeStorageSpace`
* `ReadLatency`
* `WriteLatency`
* `ReadIOPS`
* `WriteIOPS`
* `DiskQueueDepth`
* Replica lag where applicable

## Build one timeline, not isolated screenshots

A senior engineer places related metrics on one time axis:

```text
Deployment
↓
Target 5xx increase
↓
Target response time increase
↓
Database connections increase
↓
Application task restarts
↓
Rollback
↓
Recovery
```

Correlation is not proof of causation, but it identifies where to investigate.

# Querying CloudWatch Metrics With the CLI

Example ALB target 5xx query:

```bash
aws cloudwatch get-metric-data \
  --metric-data-queries '[
    {
      "Id": "target5xx",
      "MetricStat": {
        "Metric": {
          "Namespace": "AWS/ApplicationELB",
          "MetricName": "HTTPCode_Target_5XX_Count",
          "Dimensions": [
            {
              "Name": "LoadBalancer",
              "Value": "app/production-alb/1234567890abcdef"
            }
          ]
        },
        "Period": 60,
        "Stat": "Sum"
      },
      "ReturnData": true
    }
  ]' \
  --start-time 2026-08-05T13:45:00Z \
  --end-time 2026-08-05T14:30:00Z
```

What it does:

* Reads ALB target-generated 5xx counts.
* Uses one-minute periods.
* Returns the total errors per period.

What abnormal output looks like:

```json
{
  "Timestamps": [
    "2026-08-05T14:07:00Z",
    "2026-08-05T14:06:00Z",
    "2026-08-05T14:05:00Z"
  ],
  "Values": [
    319,
    241,
    74
  ]
}
```

This indicates that the targets, not necessarily the ALB itself, returned errors.

Check ALB-generated errors separately:

```bash
aws cloudwatch get-metric-data \
  --metric-data-queries '[
    {
      "Id": "elb5xx",
      "MetricStat": {
        "Metric": {
          "Namespace": "AWS/ApplicationELB",
          "MetricName": "HTTPCode_ELB_5XX_Count",
          "Dimensions": [
            {
              "Name": "LoadBalancer",
              "Value": "app/production-alb/1234567890abcdef"
            }
          ]
        },
        "Period": 60,
        "Stat": "Sum"
      },
      "ReturnData": true
    }
  ]' \
  --start-time 2026-08-05T13:45:00Z \
  --end-time 2026-08-05T14:30:00Z
```

Interpretation:

* Target 5xx spike, ALB 5xx stable: investigate application targets and dependencies.
* ALB 5xx spike: investigate target connectivity, malformed responses, unavailable targets, timeouts, and ALB-level conditions.
* Both spike: investigate interactions across both layers.

# CloudWatch Logs and Logs Insights

Metrics tell you that something changed.

Logs help explain what happened.

Potential log sources include:

* CloudFront access logs
* AWS WAF logs
* ALB access logs
* ECS application logs
* EC2 application logs
* RDS logs
* VPC Flow Logs
* CloudTrail logs

CloudFront standard logs contain details such as request time, request path, processing time, and server response. CloudFront real-time logs can be delivered within seconds and are better suited to active incident monitoring.

AWS WAF logging records details about requests evaluated by a web ACL, including matched rules and actions, and logs can be sent to CloudWatch Logs, S3, or Data Firehose.

## Application log query

Example CloudWatch Logs Insights query:

```text
fields @timestamp, @message, @logStream
| filter @message like /ERROR|Exception|timeout|connection refused/
| sort @timestamp desc
| limit 200
```

## Count errors over time

```text
fields @timestamp, @message
| filter @message like /ERROR/
| stats count(*) as errors by bin(1m)
| sort @timestamp asc
```

## Find database connection errors

```text
fields @timestamp, @message, @logStream
| filter @message like /connection pool|too many connections|timeout|SQLSTATE/
| sort @timestamp desc
| limit 200
```

## Compare application versions

Assuming structured JSON logs:

```text
fields @timestamp, status, path, version, requestId
| filter status >= 500
| stats count(*) as errors by version, path
| sort errors desc
```

This can quickly reveal whether errors are concentrated in the newly deployed version.

# Systems Manager

AWS Systems Manager gives responders controlled access to resources and provides tools such as:

* Session Manager
* Run Command
* Automation
* Fleet Manager
* Inventory
* Parameter Store

In a mature environment, responders should not need permanent SSH access to every production instance.

Session Manager can provide audited access without exposing inbound SSH to the internet.

Run Command can execute diagnostics across several managed instances.

Example:

```bash
aws ssm send-command \
  --document-name "AWS-RunShellScript" \
  --targets "Key=tag:Service,Values=checkout-api" \
  --parameters 'commands=[
    "date -u",
    "uptime",
    "free -m",
    "df -h",
    "df -i",
    "systemctl --failed",
    "ss -lntp",
    "journalctl -p err --since \"30 minutes ago\" --no-pager"
  ]' \
  --comment "Collect checkout incident diagnostics" \
  --cloud-watch-output-config \
    CloudWatchOutputEnabled=true,CloudWatchLogGroupName=/aws/ssm/incident-diagnostics
```

What this does:

* Runs the same evidence-gathering commands across tagged instances.
* Avoids checking servers one by one.
* Sends output to a central CloudWatch Logs group.
* Creates an auditable command record.

Use read-only diagnostics first.

Do not combine evidence collection with restarts, package upgrades, or configuration edits.

# AWS Config

AWS Config records resource configuration and relationships. Its resource timeline can show configuration, compliance, and related CloudTrail events over time. AWS Config supports continuous recording and can preserve historical configuration items according to the configured retention period.

CloudTrail tells you that an API call occurred.

AWS Config can help show how the resource configuration changed.

This is useful for investigating:

* Security-group rules
* Load-balancer settings
* CloudFront configuration
* WAF associations
* EC2 properties
* RDS settings
* IAM-related resources where supported
* Subnets and network resources

Example:

```bash
aws configservice get-resource-config-history \
  --resource-type AWS::ElasticLoadBalancingV2::LoadBalancer \
  --resource-id app/production-alb/1234567890abcdef \
  --chronological-order Forward \
  --earlier-time 2026-08-05T13:45:00Z \
  --later-time 2026-08-05T14:30:00Z
```

Use Config to answer:

* Did the resource configuration change?
* What was the previous state?
* Did the change occur before or after the symptoms?
* Was the configuration restored during mitigation?

# VPC Flow Logs

VPC Flow Logs capture information about IP traffic going to and from network interfaces. They can publish to CloudWatch Logs, S3, or Data Firehose. Records can show `ACCEPT` or `REJECT`, helping identify whether traffic was allowed or rejected by controls such as security groups or network ACLs.

Flow Logs are useful for questions such as:

* Did the application attempt to connect to RDS?
* Was traffic rejected?
* Which source and destination were involved?
* Which port was used?
* Did traffic reach only some targets?
* Did the network behavior change after deployment?

Example Logs Insights query for rejected RDS traffic:

```text
fields @timestamp, srcAddr, srcPort, dstAddr, dstPort, protocol, action
| filter action = "REJECT"
| filter dstPort = 5432
| sort @timestamp desc
| limit 200
```

Important limitation:

An `ACCEPT` record does not prove that the application completed a successful transaction.

It proves that the network flow was accepted at the recorded interface.

The application may still reject the connection, time out, fail authentication, or return an error.

Flow Logs are one source of evidence, not the full answer.

# Resource Tagging and Ownership

During an incident, engineers should not spend twenty minutes asking who owns a resource.

Production resources should carry useful metadata.

Recommended tags include:

```text
Service=checkout-api
Environment=production
Owner=commerce-platform
CostCenter=commerce
Criticality=tier-1
Repository=checkout-api
Runbook=checkout-api-production
DataClassification=confidential
```

Tagging supports:

* Ownership
* Cost allocation
* Automation
* Incident routing
* Access control
* Inventory
* Diagnostic targeting

Systems Manager commands, Resource Explorer searches, scripts, and dashboards become more effective when resources are consistently tagged.

A resource without ownership is an incident waiting to become a coordination problem.

# The Senior Engineer’s Investigation Workflow

A disciplined workflow reduces random action.

## Step 1: Confirm the incident

Validate that the alert represents real customer impact.

Check:

* Synthetic monitoring
* Customer reports
* Business transaction metrics
* Error rate
* Latency
* Availability

## Step 2: State the impact

Write one clear sentence.

Example:

> Checkout requests are intermittently returning HTTP 5xx responses in `us-east-1`; browsing and authentication remain healthy.

## Step 3: Define the blast radius

Identify:

* Region
* Availability Zone
* Application version
* Target group
* Customer segment
* Request type
* Dependency

## Step 4: Establish the timeline

Record the first symptom and recent changes.

## Step 5: Check AWS Health

Determine whether AWS is reporting a relevant public or account-specific event.

## Step 6: Check recent changes

Use:

* Deployment system
* CloudTrail
* AWS Config
* Infrastructure repository
* Change-management records

## Step 7: Follow the request path

Investigate from the customer inward:

```text
Client
↓
Route 53
↓
CloudFront
↓
AWS WAF
↓
ALB
↓
EC2 or ECS
↓
RDS
```

## Step 8: Compare healthy and unhealthy dimensions

Examples:

* Old version versus new version
* Availability Zone A versus B
* Healthy target versus unhealthy target
* Read request versus write request
* Cached request versus origin request

Comparison is one of the fastest ways to isolate differences.

## Step 9: Form hypotheses

Examples:

* New application version returns 5xx responses.
* New tasks create too many RDS connections.
* ALB health checks remove targets during startup.
* One Availability Zone has impaired targets.
* WAF blocks a subset of valid requests.

## Step 10: Test one hypothesis at a time

Every command or query should answer a question.

Do not gather random screenshots.

## Step 11: Mitigate safely

Possible actions:

* Pause deployment
* Roll back
* Shift traffic
* Disable a feature flag
* Remove unhealthy capacity
* Rate-limit requests
* Scale a proven bottleneck

## Step 12: Confirm recovery

Validate the complete customer transaction.

Do not close the incident because alarms turned green.

## Step 13: Preserve evidence and continue root-cause analysis

Recovery ends customer impact.

It does not automatically explain the failure.

# Evidence Preservation

Evidence can disappear quickly.

Examples:

* Containers terminate.
* ECS tasks are replaced.
* EC2 instances are recycled.
* Temporary files vanish.
* Kubernetes events expire.
* Log retention removes records.
* A rollback replaces configuration.
* Auto Scaling terminates unhealthy instances.

Before destructive changes, preserve:

* Application logs
* System logs
* Container logs
* Task and deployment details
* ALB target health
* Metric snapshots
* CloudTrail events
* AWS Config history
* Flow Logs
* Database events
* Process state
* Network connections
* Thread or heap data where safe
* Exact timestamps

Create an incident evidence location with restricted access and clear retention.

Do not copy secrets, authentication tokens, personal data, or unnecessary sensitive records into an open incident channel.

# Mitigation Versus Root Cause

Mitigation reduces customer impact.

Root-cause analysis explains why the failure occurred.

These are separate goals.

## Mitigation examples

* Roll back the deployment
* Disable the feature
* Shift traffic
* Reduce request rate
* Restore capacity
* Fail over to a healthy dependency

## Root-cause work

* Reproduce the issue
* Compare versions
* Analyze connection-pool behavior
* Review code changes
* Inspect database locks
* Analyze scaling and startup timing
* Identify missing monitoring
* Improve tests and controls

During active customer impact, do not delay safe mitigation because the team wants intellectual certainty.

However, do not let successful mitigation become the end of the investigation.

“The rollback fixed it” is not a root cause.

# Escalating to AWS Support

Escalate when:

* Evidence suggests an AWS-managed service problem.
* The control plane or data plane behaves contrary to documented expectations.
* Multiple resources show unexplained service-level impact.
* Account-specific AWS Health events are relevant.
* The issue requires internal AWS telemetry.
* Customer impact is severe and the team cannot safely mitigate.
* A service quota or managed component prevents recovery.

Prepare the support case before submitting it.

Include:

* Account ID
* Region
* Availability Zones
* Resource ARNs and IDs
* Incident start time in UTC
* Current status
* Customer impact
* Error messages
* Request IDs
* Trace IDs
* Relevant CloudTrail event IDs
* Metrics
* Log excerpts
* Steps already performed
* Whether the issue is reproducible
* Whether AWS Health shows an event

Avoid vague descriptions such as:

> RDS is broken.

Use:

> From 14:05 to 14:22 UTC in `us-east-1`, connections from ECS tasks in subnets A and B to RDS instance `production-orders` experienced timeouts. Security-group and route configurations were unchanged. VPC Flow Logs show accepted traffic. `DatabaseConnections` rose from 420 to 890 after task definition revision 73. Request IDs and metric screenshots are attached.

A precise case reaches useful investigation faster.

# Real Troubleshooting Lab

## Scenario: Intermittent HTTP 5xx Errors After Deployment

At 14:05 UTC, three minutes after deploying a new checkout service version, the production error-rate alarm fires.

Customers report:

* Some checkouts succeed.
* Others return error pages.
* Browsing remains healthy.
* Retrying sometimes succeeds.

Architecture:

```text
Client
↓
Route 53
↓
CloudFront
↓
AWS WAF
↓
Application Load Balancer
↓
ECS on EC2
↓
Amazon RDS for PostgreSQL
```

Deployment:

```text
Old task definition: checkout-api:72
New task definition: checkout-api:73
```

The deployment replaces tasks gradually.

Both versions are temporarily serving traffic.

---

# Lab Step 1: Define the Impact

Initial incident statement:

> Beginning at 14:05 UTC, approximately 8 percent of checkout POST requests in `us-east-1` return HTTP 5xx responses. GET requests and non-checkout application functions remain within baseline.

Known:

* Incident began after deployment.
* Only checkout is affected.
* Errors are intermittent.
* Some requests succeed.

Unknown:

* Which layer generates the 5xx response?
* Whether one application version is affected.
* Whether one Availability Zone is affected.
* Whether RDS is a bottleneck.
* Whether WAF is blocking requests.
* Whether the ALB has unhealthy targets.

---

# Lab Step 2: Check AWS Health

Check:

* Public regional events
* Account-specific events
* ECS
* EC2
* ELB
* RDS
* CloudFront

Result:

```text
No relevant public or account-specific events.
```

Interpretation:

This reduces the likelihood of a broad AWS service event.

It does not eliminate resource-level, zonal, account-specific configuration, or application failures.

---

# Lab Step 3: Check CloudFront

CloudFront `5xxErrorRate` increased at 14:05 UTC.

That confirms edge-visible errors.

It does not tell us whether CloudFront created the error or received it from the origin.

CloudFront documentation notes that an origin returning 4xx or 5xx responses indicates a problem in communication with or behavior from the origin path, so the next step is to inspect detailed result fields and origin behavior.

Logs Insights or the chosen log-analysis system should group by:

* Status
* Request path
* Edge result type
* Detailed result type
* Origin response
* Request ID

Finding:

```text
Errors are concentrated on POST /checkout.
CloudFront is forwarding origin 5xx responses.
```

CloudFront is exposing the error, not creating the original application failure.

---

# Lab Step 4: Check AWS WAF

Query WAF logs for the affected requests.

Look for:

* `BLOCK`
* `CHALLENGE`
* `CAPTCHA`
* Matching rule IDs
* Rate-based rule behavior
* URI path
* Client IP
* Request headers

Finding:

```text
Affected requests show WAF action ALLOW.
No relevant blocking-rule increase.
```

Interpretation:

AWS WAF is unlikely to be the failure source.

Do not disable WAF merely because it is in the request path.

---

# Lab Step 5: Compare ALB Error Metrics

Metrics show:

```text
HTTPCode_ELB_5XX_Count: no meaningful increase
HTTPCode_Target_5XX_Count: sharp increase at 14:05 UTC
TargetResponseTime: increase from 220 ms to 2.8 s
HealthyHostCount: stable
UnHealthyHostCount: 0
```

Interpretation:

* The ALB is forwarding traffic.
* Targets are returning the errors.
* Health checks remain successful.
* The failure affects application requests that are not represented well by the health-check endpoint.

This is a crucial finding.

A healthy target can still return errors for real customer transactions.

---

# Lab Step 6: Inspect Target Health

```bash
aws elbv2 describe-target-health \
  --target-group-arn \
  arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/checkout-production/abcd1234efgh5678
```

Expected healthy output:

```json
{
  "TargetHealthDescriptions": [
    {
      "Target": {
        "Id": "10.0.21.41",
        "Port": 8080,
        "AvailabilityZone": "us-east-1a"
      },
      "TargetHealth": {
        "State": "healthy"
      }
    }
  ]
}
```

All targets report healthy.

Interpretation:

The health-check path proves only that the configured health endpoint responds successfully.

It does not prove that checkout operations, database writes, or external dependencies are healthy.

---

# Lab Step 7: Compare Application Versions

Application logs include:

* `service`
* `version`
* `requestId`
* `traceId`
* `path`
* `status`
* `durationMs`
* `dbPoolActive`
* `dbPoolPending`

Logs Insights query:

```text
fields @timestamp, version, path, status, durationMs, dbPoolActive, dbPoolPending
| filter path = "/checkout"
| filter status >= 500
| stats
    count(*) as errors,
    avg(durationMs) as avgDuration,
    max(dbPoolPending) as maxPending
  by version
| sort errors desc
```

Result:

```text
version 73: 1,482 errors
version 72: 3 errors
```

Interpretation:

The error is strongly associated with version 73.

This does not yet reveal the exact cause, but it gives a safe mitigation candidate.

---

# Lab Step 8: Inspect Application Errors

Query:

```text
fields @timestamp, @message, requestId, traceId, version
| filter version = "73"
| filter @message like /timeout|connection pool|SQLSTATE|ERROR/
| sort @timestamp desc
| limit 200
```

Finding:

```text
Timeout acquiring database connection
Pool active: 50
Pool idle: 0
Pool pending: 187
Timeout: 3000ms
```

Hypothesis:

The new version exhausts its database connection pool or increases database demand.

---

# Lab Step 9: Check RDS

Relevant RDS metrics:

```text
DatabaseConnections: increased from 420 to 910
CPUUtilization: increased from 38% to 63%
FreeableMemory: stable
WriteLatency: mildly elevated
DiskQueueDepth: normal
FreeStorageSpace: normal
```

RDS is under increased load, but it is not experiencing CPU, storage, or memory exhaustion.

The connection count is the strongest signal.

Check database activity using approved database tooling.

For PostgreSQL:

```sql
SELECT
    application_name,
    state,
    COUNT(*) AS connections
FROM pg_stat_activity
GROUP BY application_name, state
ORDER BY connections DESC;
```

Finding:

```text
checkout-api-v73  idle  470
checkout-api-v73  active 122
checkout-api-v72  idle   84
checkout-api-v72  active 19
```

Version 73 holds far more connections.

Code review reveals that version 73 creates a new connection pool for every tenant context instead of sharing the intended process-level pool.

---

# Lab Step 10: Decide Whether to Roll Back

Evidence:

* Incident began after deployment.
* Target-generated 5xx increased.
* Errors are concentrated in version 73.
* Version 73 logs show pool-acquisition timeouts.
* RDS connection count rose sharply.
* Version 72 remains healthy.
* No irreversible database migration occurred.
* Rollback has a tested procedure.

Decision:

Rollback is safer than attempting a live configuration experiment.

Do not first increase the RDS connection limit.

That might temporarily reduce errors while increasing database memory pressure and hiding the defective connection behavior.

---

# Lab Step 11: Execute a Controlled Rollback

For ECS, update the service to the previous task definition:

```bash
aws ecs update-service \
  --cluster production-commerce \
  --service checkout-api \
  --task-definition checkout-api:72 \
  --force-new-deployment
```

Monitor:

```bash
aws ecs describe-services \
  --cluster production-commerce \
  --services checkout-api \
  --query 'services[0].{
    Running:runningCount,
    Pending:pendingCount,
    Desired:desiredCount,
    Deployments:deployments[*].{
      Status:status,
      TaskDefinition:taskDefinition,
      Running:runningCount,
      Pending:pendingCount,
      RolloutState:rolloutState
    }
  }'
```

Watch:

* Task count
* Target registration
* Healthy host count
* Target 5xx
* Target response time
* RDS connections
* Checkout success rate

Only one change is made: restore the previous application version.

---

# Lab Step 12: Confirm Customer Recovery

At 14:22 UTC:

```text
HTTPCode_Target_5XX_Count returned to baseline.
Checkout success rate returned above 99.9%.
TargetResponseTime returned to 240 ms.
DatabaseConnections began decreasing.
Synthetic checkout completed successfully.
Customer support confirmed new transactions were succeeding.
```

Do not end validation at:

```text
ECS deployment completed.
```

Validate:

1. Edge response
2. ALB behavior
3. Application response
4. Database transaction
5. Business outcome

The true recovery signal is a successful customer transaction.

# Root Cause

Version 73 introduced tenant-scoped database connection pools.

The service created and retained multiple pools inside each ECS task.

During production traffic:

1. New version 73 tasks began serving requests.
2. Each task created multiple connection pools.
3. RDS connections increased rapidly.
4. Application pool waiters increased.
5. Checkout requests timed out waiting for connections.
6. The application returned HTTP 500 responses.
7. ALB forwarded the target-generated errors.
8. CloudFront delivered those errors to customers.

The health endpoint did not access the database.

Targets remained healthy throughout the incident.

---

# Contributing Factors

The root cause alone does not explain why customers were affected.

Contributing factors included:

* Load testing did not model production tenant diversity.
* Health checks did not validate a lightweight critical-dependency path.
* No deployment alarm monitored database connections by application version.
* The canary stage was too short to expose connection accumulation.
* Logs did not initially include pool metrics.
* The deployment system measured task health rather than checkout success.
* The team lacked a predefined maximum connection budget per task.

---

# Permanent Corrective Actions

## Application

* Replace tenant-scoped pools with a bounded shared pool.
* Add pool lifecycle tests.
* Add connection-leak detection.
* Emit active, idle, pending, and timeout metrics.

## Deployment

* Use a longer canary period.
* Compare old and new version error rates.
* Add automatic rollback based on checkout success and target 5xx.
* Stop promotion when RDS connection growth exceeds the expected budget.

## Monitoring

Create alarms for:

* Checkout error rate
* Checkout latency
* `HTTPCode_Target_5XX_Count`
* RDS `DatabaseConnections`
* Connection-pool pending requests
* Connection-acquisition timeout
* Connection count per task revision

## Capacity

Define:

```text
Maximum database connections
− Reserved administrative connections
− Other application connections
= Checkout service connection budget
```

Divide the service budget across maximum task count.

## Testing

Test:

* Production-like tenant count
* Autoscaling
* Deployment overlap
* Task replacement
* Connection cleanup
* Dependency slowdown

# Lessons From the Lab

## Healthy infrastructure does not mean healthy customer transactions

Every target remained healthy.

Checkout still failed.

## The request path matters

The error appeared at CloudFront but originated in the application’s database behavior.

## Recent changes matter

The deployment timestamp narrowed the investigation quickly.

## Compare healthy and unhealthy dimensions

Version 72 versus version 73 revealed the strongest difference.

## Metrics show where to look

Target 5xx and RDS connections pointed toward the application and database boundary.

## Logs explain behavior

Connection-pool logs identified the immediate application failure.

## One controlled change preserves understanding

The rollback restored one known-good version without introducing unrelated modifications.

## Recovery must be validated from the customer perspective

The incident ended only after checkout transactions succeeded.

## Before an incident

* Architecture diagram is current.
* Request path is documented.

* Logs are centralized.
* VPC Flow Logs are enabled where appropriate.

* Confirm customer impact.
* State the blast radius.
* Build the timeline.
* Check AWS Health.
* Review recent changes.
* Follow the full request path.
* Compare healthy and unhealthy dimensions.
* Form explicit hypotheses.
* Run read-only checks first.
* Preserve evidence.
* Make one controlled change at a time.
* Record every action.
* Mitigate customer impact.
* Confirm recovery end to end.

## After recovery

* Preserve logs and timelines.
* Document the root cause.
* Identify contributing factors.
* Create corrective actions.
* Assign owners and deadlines.
* Improve monitoring.
* Improve rollback.
* Test the failure scenario.

# How Senior Engineers Think

Senior engineers do not ask only:

> Which AWS service is broken?

They ask:

* What customer outcome is failing?
* Which failure domain fits the evidence?
* What changed?
* What is different between healthy and unhealthy requests?
* Which layer generated the error?
* Is this the original failure or a cascading symptom?
* Can we mitigate without destroying evidence?
* Is rollback safer than live repair?
* What would prove recovery?
* What allowed this failure to reach customers?

AWS troubleshooting is not a race to execute the first command.

It is a controlled process for reducing uncertainty.

The commands matter.

The dashboards matter.

The logs matter.

But judgment determines how they are used.

# Key Takeaways

* Start with customer impact, not resource status.
* Treat symptoms as clues, not conclusions.
* Separate control-plane success from data-plane health.
* Define the failure domain and blast radius.
* Build an exact UTC timeline.
* Check public and account-specific AWS Health events.
* Use CloudTrail to identify management activity.
* Use AWS Config to reconstruct resource configuration.
* Use CloudWatch metrics to locate behavioral changes.
* Use logs to explain those changes.
* Use VPC Flow Logs to validate network flows.
* Use Systems Manager for controlled, auditable diagnostics.
* Compare healthy and unhealthy versions, zones, resources, and requests.
* Preserve evidence before restarting or replacing resources.
* Mitigation and root-cause analysis are different activities.
* Change one thing at a time during recovery.
* Escalate to AWS Support with precise evidence.
* Confirm recovery through a real customer transaction.
* Improve the system after every incident.
* Good AWS troubleshooting is disciplined reasoning supported by telemetry.
