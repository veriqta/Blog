# AWS Troubleshooting in Production

## Part 2: EC2 Troubleshooting From Boot Failure to Application Outage

**How senior engineers diagnose EC2 failures across the AWS infrastructure, operating system, storage, access, and application layers**

An EC2 instance can be in the `running` state while the application it hosts is completely unavailable.

The instance may have passed both AWS status checks while:

* SSH connections time out.
* Session Manager cannot detect it.
* The web server has stopped.
* The root volume is full.
* The operating system has exhausted its available memory.
* The application is listening on the wrong port.
* EBS latency has increased.
* A host firewall is rejecting traffic.
* The attached IAM role is missing.
* User data failed during startup.
* The instance started successfully but never became ready to serve customers.

This is the first principle of EC2 troubleshooting:

> **An EC2 state tells you what AWS knows about the virtual machine. It does not tell you whether the workload is delivering customer value.**

AWS performs system, instance, and attached EBS status checks to identify certain infrastructure and guest operating-system problems. These checks are valuable, but they are not application health checks. A server can pass every EC2 status check while Nginx, Apache, IIS, Java, Node.js, PostgreSQL, or the customer-facing application is down.

Senior engineers therefore troubleshoot EC2 in layers:

```text
Customer request
↓
DNS and load balancer
↓
Security group and subnet path
↓
Elastic network interface
↓
EC2 host and instance status
↓
Operating system
↓
Storage
↓
Application process
↓
Application dependencies
```

They begin with the failure customers experience.

Then they move inward, one layer at a time.

# Why EC2 Troubleshooting Requires Layered Thinking

An EC2 workload combines responsibilities owned by AWS and responsibilities owned by the customer.

AWS operates the underlying physical infrastructure and virtualization platform.

The customer controls most of what happens inside the instance:

* Operating system configuration
* Packages
* Services
* Users
* SSH configuration
* Windows settings
* Host firewall
* File systems
* Application processes
* Memory usage
* Disk usage
* Logging
* Credentials
* Startup scripts
* Monitoring agents

An incident may therefore originate in several places.

## AWS infrastructure layer

Examples:

* Underlying host problem
* Physical network problem
* Power interruption
* EBS attachment impairment
* Scheduled infrastructure maintenance

## EC2 configuration layer

Examples:

* Incorrect instance type
* Wrong subnet
* Missing public IP
* Incorrect security group
* Missing IAM instance profile
* Incorrect key pair
* Wrong placement or architecture

## Operating-system layer

Examples:

* Failed boot
* Broken file system
* Invalid `/etc/fstab`
* SSH daemon failure
* Windows RDP service failure
* Host firewall block
* Kernel problem
* Full root volume

## Application layer

Examples:

* Service stopped
* Port not listening
* Memory leak
* CPU saturation
* Dependency timeout
* Incorrect configuration
* Failed deployment

The goal is not to guess which layer is responsible.

The goal is to collect enough evidence to eliminate the healthy layers.

# Start With the Customer Impact

Before opening the EC2 console, describe the failure precisely.

Weak incident statement:

> The server is broken.

Better incident statement:

> Beginning at 09:12 UTC, the production API stopped responding through the Application Load Balancer. One of three EC2 targets is unhealthy. Direct SSH access to that instance times out, while the other two instances remain healthy.

This gives the investigation useful dimensions:

* The affected service
* The start time
* The affected instance count
* The load-balancer status
* The access symptom
* The healthy comparison group

Ask:

* Is one instance affected or the whole fleet?
* Is the application unavailable internally and externally?
* Can the instance reach dependencies?
* Can other instances in the same subnet communicate normally?
* Did the problem begin after a deployment, reboot, scaling event, or patch?
* Is the instance replaceable?
* Is important data stored locally?
* Is the system impaired or completely unavailable?

These answers influence whether the team should investigate, replace, fail over, or recover the instance offline.

# EC2 Instance Lifecycle

An EC2 instance moves through a lifecycle.

Common states include:

```text
pending
running
stopping
stopped
shutting-down
terminated
```

A newly launched instance starts in `pending` while AWS prepares the virtual machine. It then enters `running`. A stopped instance can later be started, while a terminated instance cannot be recovered as the same EC2 resource.

The state is important, but it should not be confused with health.

## Pending

AWS is preparing the instance.

Investigate if it remains pending longer than expected.

Possible causes include:

* Capacity constraints
* Launch template problems
* Unsupported configuration
* Instance initialization still in progress
* Encrypted storage or permission-related launch problems
* Auto Scaling activity

## Running

The instance has started at the EC2 layer.

This does not prove that:

* The operating system completed boot.
* SSH or RDP is ready.
* Session Manager is connected.
* The application started.
* The instance passed health checks.
* The network path is correct.

AWS notes that newly launched instances can take several minutes before they are ready to accept connections, and responders should confirm both the running state and status checks before assuming an access failure.

## Stopping

The instance is shutting down.

During this phase:

* New connections may fail.
* The guest operating system may still be terminating services.
* EBS-backed storage remains associated.
* Investigation should confirm who initiated the stop.

## Stopped

The instance is not running.

For EBS-backed instances, the EBS volumes normally remain available.

Starting it again may place it on different underlying AWS hardware. The public IPv4 address can change unless an Elastic IP is used.

## Shutting down and terminated

The instance is being permanently removed or has already been removed.

Before terminating a production instance, confirm:

* Required data has been backed up.
* EBS delete-on-termination settings are understood.
* The instance is not the only source of logs or evidence.
* Auto Scaling or another service will replace it.
* No important local state will be lost.

# Inspect the Instance Before Connecting

Begin with the AWS API.

```bash
aws ec2 describe-instances \
  --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[].Instances[].{
    InstanceId:InstanceId,
    State:State.Name,
    InstanceType:InstanceType,
    AZ:Placement.AvailabilityZone,
    PrivateIP:PrivateIpAddress,
    PublicIP:PublicIpAddress,
    Subnet:SubnetId,
    Vpc:VpcId,
    SecurityGroups:SecurityGroups,
    IAM:IamInstanceProfile.Arn,
    KeyName:KeyName,
    LaunchTime:LaunchTime
  }'
```

## What it checks

This command returns the instance’s current EC2 configuration.

## Why it matters

It immediately answers several basic questions:

* Is this the correct instance?
* Is it running?
* Which Availability Zone contains it?
* Does it have a public address?
* Which subnet and security groups apply?
* Is an instance profile attached?
* Which key pair was configured?
* Was the instance launched recently?

## Healthy output

```json
[
  {
    "InstanceId": "i-0123456789abcdef0",
    "State": "running",
    "InstanceType": "m7i.large",
    "AZ": "us-east-1a",
    "PrivateIP": "10.0.21.41",
    "PublicIP": null,
    "Subnet": "subnet-0123456789abcdef0",
    "Vpc": "vpc-0123456789abcdef0",
    "SecurityGroups": [
      {
        "GroupId": "sg-0123456789abcdef0",
        "GroupName": "production-api"
      }
    ],
    "IAM": "arn:aws:iam::123456789012:instance-profile/ProductionEC2Role",
    "KeyName": "production-operations",
    "LaunchTime": "2026-08-05T08:54:21+00:00"
  }
]
```

## Abnormal findings

* `State` is not `running`.
* `PublicIP` is missing when direct internet SSH was expected.
* The wrong subnet is attached.
* The wrong security group is attached.
* `IAM` is `null`.
* The launch time matches the start of the incident.
* The instance is in a different Availability Zone from the healthy fleet.

## What to investigate next

Move to status checks, scheduled events, networking, or launch history depending on the abnormal field.

# System, Instance, and Attached EBS Status Checks

AWS provides three types of EC2 status checks:

* System status checks
* Instance status checks
* Attached EBS status checks

A failed check increments the related CloudWatch status metric, which can be used for alarms and automated recovery.

Run:

```bash
aws ec2 describe-instance-status \
  --instance-ids i-0123456789abcdef0 \
  --include-all-instances
```

## What it checks

It retrieves:

* Instance lifecycle state
* System status
* Instance status
* Attached EBS status where available
* Scheduled events

## Why it matters

It helps separate an AWS infrastructure problem from an operating-system problem.

## Example healthy output

```json
{
  "InstanceStatuses": [
    {
      "AvailabilityZone": "us-east-1a",
      "InstanceId": "i-0123456789abcdef0",
      "InstanceState": {
        "Code": 16,
        "Name": "running"
      },
      "SystemStatus": {
        "Status": "ok"
      },
      "InstanceStatus": {
        "Status": "ok"
      },
      "AttachedEbsStatus": {
        "Status": "ok"
      },
      "Events": []
    }
  ]
}
```

# System Status Check Failure

A system status check evaluates the AWS infrastructure supporting the instance.

Potential problems include:

* Underlying host failure
* Physical network failure
* Power loss
* Virtualization platform problem
* AWS infrastructure issue

## Typical symptoms

* Instance becomes unreachable.
* Multiple network connections fail.
* Application stops responding.
* The guest operating system may not be responsible.
* `StatusCheckFailed_System` becomes `1`.

## What to do

For an EBS-backed instance, stopping and starting it can move the workload to different underlying hardware.

Before doing this:

* Preserve available evidence.
* Confirm that the instance can be stopped.
* Confirm local instance-store implications.
* Confirm public-IP changes.
* Check whether the workload is in an Auto Scaling group.
* Confirm that replacement is not safer.

If the instance is replaceable and stateless, terminating and replacing it may be more appropriate than repairing it.

---

# Instance Status Check Failure

An instance status check evaluates the guest operating system’s reachability and behavior.

Possible causes include:

* Failed operating-system boot
* Incorrect network configuration
* Exhausted memory
* File-system corruption
* Invalid startup configuration
* Kernel problems
* Broken `/etc/fstab`
* Host firewall changes

AWS recommends retrieving system logs when diagnosing failed instance checks because the boot output may reveal the underlying error.

## Typical symptoms

* System check is `ok`.
* Instance check is `impaired`.
* SSH and Session Manager fail.
* The operating system does not complete startup.
* Serial console or offline repair may be required.

---

# Attached EBS Status Check Failure

An attached EBS check identifies certain problems affecting EBS volumes connected to the instance.

Possible symptoms:

* File-system operations hang.
* Applications wait on storage.
* The root volume becomes unresponsive.
* Status checks show EBS impairment.
* Disk latency increases sharply.

Do not assume every disk problem will trigger this status.

A volume can remain technically available while:

* Its throughput limit is reached.
* Its IOPS limit is reached.
* The file system is full.
* Inodes are exhausted.
* The application generates inefficient I/O.
* Queue depth grows.

Status checks are one signal, not a complete storage diagnosis.

# Boot Failures

An instance can reach the `running` state at the EC2 layer but fail to complete operating-system boot.

Common causes include:

* Invalid `/etc/fstab`
* Missing volume
* Corrupted file system
* Broken kernel
* Incorrect GRUB configuration
* Failed package update
* Network configuration error
* Full root volume
* Invalid cloud-init or startup script
* Windows driver or boot-configuration issue

## Retrieve console output

```bash
aws ec2 get-console-output \
  --instance-id i-0123456789abcdef0 \
  --latest \
  --output text
```

## What it checks

It retrieves recent instance console output.

## Why it matters

When network access is unavailable, console output may reveal:

* Kernel panic
* Mount failure
* Emergency mode
* File-system errors
* Cloud-init failure
* Service startup failures

## Healthy output

A normal boot sequence ends with services starting and a login prompt or equivalent successful startup evidence.

## Abnormal output examples

```text
Dependency failed for /data
You are in emergency mode
```

```text
Kernel panic - not syncing
```

```text
No space left on device
```

```text
Failed to mount /var/lib/application
```

## What to investigate next

* EC2 Serial Console
* EC2Rescue
* Offline root-volume repair
* Snapshot and volume inspection
* Replacement from a known-good image

---

# Incorrect `/etc/fstab`

A common Linux boot failure occurs when `/etc/fstab` references:

* A nonexistent volume
* An incorrect UUID
* An unavailable network file system
* A required mount without failure-tolerant options

The system may enter emergency mode and never become reachable through SSH.

A safer production configuration may use appropriate options such as `nofail` for non-critical volumes, but that decision must reflect the application’s data requirements.

Do not add failure-tolerant mount options blindly to critical storage. A system that boots without required application data may create corruption or incorrect behavior.

# User Data Failures

EC2 user data commonly performs startup work such as:

* Installing packages
* Downloading configuration
* Starting services
* Registering agents
* Mounting storage
* Retrieving secrets
* Joining a cluster

User data normally runs during initial launch according to the image and configuration.

Retrieve it:

```bash
aws ec2 describe-instance-attribute \
  --instance-id i-0123456789abcdef0 \
  --attribute userData \
  --query 'UserData.Value' \
  --output text | base64 --decode
```

## What it checks

It displays the startup script attached to the instance.

## Why it matters

A syntactically valid launch can still create an unusable server if the startup script fails.

## Linux logs to inspect

Depending on the distribution and cloud-init configuration:

```bash
sudo less /var/log/cloud-init.log
sudo less /var/log/cloud-init-output.log
sudo journalctl -u cloud-init
sudo journalctl -u cloud-final
```

## Common failure causes

* Package repository unavailable
* Command not found
* Incorrect interpreter
* IAM permission denied
* Missing network access
* Secret unavailable
* Wrong Region
* Failed mount
* Script exits early
* Dependency starts after the application
* Application binary fails validation

## Healthy evidence

* User-data script exits successfully.
* Required packages are installed.
* Application service starts.
* Registration completes.
* Expected files and configuration exist.

## Abnormal evidence

```text
AccessDeniedException
```

```text
Could not resolve host
```

```text
No space left on device
```

```text
systemctl: command not found
```

## What to investigate next

Do not simply rerun the script manually without understanding whether it is idempotent.

A non-idempotent script could:

* Create duplicate users
* Overwrite data
* Repeat migrations
* Re-register resources
* Duplicate configuration entries

# SSH Failure Investigation

AWS provides detailed procedures for Linux connection failures and recommends first confirming that the instance is running and has passed its checks.

An SSH timeout can be caused by:

* No valid network path
* Security group block
* Network ACL block
* No public IP
* Missing route through an internet gateway
* Bastion or VPN failure
* Operating-system firewall
* SSH daemon stopped
* Wrong SSH port
* CPU or memory exhaustion
* Full disk
* Failed boot

An SSH permission error usually points elsewhere:

* Wrong username
* Wrong key
* Incorrect permissions on the private key
* Missing authorized key
* Incorrect home-directory permissions
* SSH configuration restrictions

These two symptoms should not be investigated in the same way.

## Timeout

```text
ssh: connect to host 203.0.113.10 port 22: Connection timed out
```

Focus first on:

* Address
* Route
* Security group
* NACL
* Firewall
* Instance reachability
* SSH daemon availability

## Connection refused

```text
ssh: connect to host 203.0.113.10 port 22: Connection refused
```

The network reached the destination, but nothing accepted the connection on that port, or the host actively rejected it.

Investigate:

* `sshd` status
* Listening port
* Host firewall
* Custom SSH port
* Failed startup

## Permission denied

```text
Permission denied (publickey)
```

Investigate:

* Username
* Private key
* `authorized_keys`
* File permissions
* SSH configuration
* Account restrictions

# Verify the Network Path

## Security groups

```bash
aws ec2 describe-security-groups \
  --group-ids sg-0123456789abcdef0 \
  --query 'SecurityGroups[].{
    GroupId:GroupId,
    Ingress:IpPermissions,
    Egress:IpPermissionsEgress
  }'
```

## What it checks

It returns the security group’s inbound and outbound rules.

## Why it matters

Direct SSH normally requires inbound TCP access to the configured SSH port from an approved source.

## Healthy example

* TCP 22 allowed from the corporate VPN range.
* Outbound traffic permits required response and service communication.

## Abnormal example

* TCP 22 removed.
* Source range does not include the responder.
* Wrong security group attached.
* A restrictive outbound policy prevents required connectivity.

Security groups are stateful. Return traffic for an allowed connection is automatically permitted by the group.

## What to investigate next

Check the subnet route, public IP or private access path, NACL, and host firewall.

---

# Public and Private Instances

A public subnet alone does not give an instance internet reachability.

Direct public SSH usually requires:

* A public IPv4 address or Elastic IP
* A route to an internet gateway
* Security-group permission
* NACL permission
* Reachable source network
* Listening SSH service

A private instance may instead be reached through:

* Session Manager
* VPN
* Direct Connect
* Bastion host
* EC2 Instance Connect Endpoint
* Private administrative network

Never add a public IP or broad `0.0.0.0/0` SSH rule merely to make troubleshooting easier.

Use the organization’s approved access path.

---

# Network ACLs

```bash
aws ec2 describe-network-acls \
  --filters Name=association.subnet-id,Values=subnet-0123456789abcdef0
```

Network ACLs are stateless.

Both directions must be permitted, including the relevant ephemeral return traffic.

Possible problems:

* Inbound SSH allowed, return traffic blocked
* Explicit deny before an allow rule
* Incorrect ephemeral-port range
* Different NACL associated with one subnet
* Zonal inconsistency between healthy and unhealthy instances

Compare the affected subnet with a healthy subnet rather than reading the rules in isolation.

# Test the Port

From an approved network location:

```bash
nc -vz 203.0.113.10 22
```

Possible outputs:

## Healthy

```text
Connection to 203.0.113.10 22 port [tcp/ssh] succeeded!
```

The path reaches an accepting service.

## Timeout

```text
nc: connect to 203.0.113.10 port 22 (tcp) timed out
```

Investigate:

* Routing
* Security rules
* NACL
* Host failure
* Firewall
* Service unavailable

## Refused

```text
nc: connect to 203.0.113.10 port 22 (tcp) failed: Connection refused
```

Investigate the SSH daemon and host firewall.

# Check the SSH Service

Once another access method is available:

```bash
sudo systemctl status sshd
```

Some distributions use:

```bash
sudo systemctl status ssh
```

## What it checks

It shows whether the OpenSSH server is running.

## Healthy output

```text
Active: active (running)
```

## Abnormal output

```text
Active: failed
```

or:

```text
Unit sshd.service could not be found
```

## Next checks

```bash
sudo journalctl -u sshd --since "30 minutes ago"
sudo sshd -t
sudo ss -lntp | grep ':22'
```

`sshd -t` validates the server configuration without starting a new daemon.

A syntax error in `sshd_config` may prevent the service from starting after a reboot or reload.

# Operating-System Firewall

Linux systems may use:

* `firewalld`
* `iptables`
* `nftables`
* `ufw`

Examples:

```bash
sudo firewall-cmd --list-all
sudo nft list ruleset
sudo iptables -L -n -v
sudo ufw status verbose
```

## What it checks

It shows whether the guest operating system rejects the traffic after AWS networking has delivered it.

## Why it matters

A security group can allow SSH while the operating system blocks it.

## What to investigate next

Compare current firewall rules with:

* Configuration management
* Last known-good state
* Recent package or security changes
* CloudTrail and deployment timeline

# AWSSupport-TroubleshootSSH

AWS provides the `AWSSupport-TroubleshootSSH` Systems Manager Automation runbook.

The runbook installs EC2Rescue for Linux and checks common conditions that prevent SSH access. It runs in read-only mode by default. If explicitly allowed, it can use offline remediation that stops and starts the instance.

Start a read-only execution:

```bash
aws ssm start-automation-execution \
  --document-name AWSSupport-TroubleshootSSH \
  --parameters '{
    "InstanceId":["i-0123456789abcdef0"],
    "Action":["CheckAll"]
  }'
```

Parameter requirements can change, so validate the current runbook schema before production use:

```bash
aws ssm describe-document \
  --name AWSSupport-TroubleshootSSH
```

## Why use it

It can standardize checks and identify common SSH problems without relying only on manual investigation.

## Safety principle

Begin with read-only diagnostics.

Offline remediation may:

* Stop the instance
* Move it to different hardware after restart
* Change the public IPv4 address
* Interrupt the application
* Affect local instance-store data

Use remediation only after understanding the impact.

# EC2 Instance Connect Issues

EC2 Instance Connect can push a temporary SSH public key to supported instances.

Failures may involve:

* Unsupported image or configuration
* Instance Connect package missing
* IAM permission failure
* Wrong operating-system username
* Network path unavailable
* Instance metadata access problems
* Incorrect Availability Zone
* EC2 Instance Connect Endpoint configuration

A successful key push does not prove that port 22 is reachable.

Separate:

1. AWS API authorization
2. Temporary key delivery
3. Network path
4. SSH daemon
5. Operating-system account

Do not treat Instance Connect as a replacement for network troubleshooting.

# Session Manager Failures

Session Manager provides interactive access to managed nodes without requiring inbound ports, bastion hosts, or traditional SSH key management.

For an EC2 instance to appear as a managed node, it generally needs:

* A supported operating system
* SSM Agent installed and running
* An IAM instance profile with the required Systems Manager permissions
* Network connectivity to Systems Manager endpoints
* Correct Region and account configuration

AWS documents minimum SSM Agent versions for specific Session Manager capabilities.

## Check whether the node is registered

```bash
aws ssm describe-instance-information \
  --filters Key=InstanceIds,Values=i-0123456789abcdef0
```

## Healthy output

A record containing:

* Instance ID
* Ping status
* Agent version
* Platform
* Last ping time

## Abnormal output

```json
{
  "InstanceInformationList": []
}
```

The instance is not registered or not visible in the selected account and Region.

# Systems Manager Network Path

A private instance may reach Systems Manager through:

* NAT-based internet egress
* VPC interface endpoints

If using VPC endpoints, confirm the required endpoints and associated DNS and security configuration.

Common problems:

* Private DNS disabled
* Endpoint in the wrong subnets
* Endpoint security group blocks TCP 443
* Instance DNS settings are broken
* Route or NACL problem
* Proxy intercepts TLS
* No NAT route and no endpoints

Test HTTPS resolution and connectivity where appropriate:

```bash
getent hosts ssm.us-east-1.amazonaws.com
```

```bash
curl -I https://ssm.us-east-1.amazonaws.com
```

A service response such as an HTTP error can still prove that DNS and TLS connectivity exist. A timeout or resolution failure suggests a lower-layer problem.

Before executing it:

```bash
aws ssm describe-document \
```

# Windows RDP Failures

Windows EC2 access problems may involve:

* Port 3389 blocked
* Wrong security group
* NACL problem
* Missing network route
* Windows Firewall
* Remote Desktop Services stopped
* Incorrect password
* Password not yet available
* Network Level Authentication
* Domain or account issues
* Full system drive
* CPU or memory exhaustion
* Broken network adapter configuration

AWS provides dedicated Windows connection troubleshooting guidance and the `AWSSupport-TroubleshootRDP` runbook for checking or modifying common RDP-related settings.

## Test the port

From an approved source:

```powershell
Test-NetConnection -ComputerName 203.0.113.20 -Port 3389
```

## Healthy output

```text
TcpTestSucceeded : True
```

## Abnormal output

```text
TcpTestSucceeded : False
```

Investigate the network path before resetting credentials or modifying Windows.

## On-instance checks

```powershell
Get-Service TermService
Get-NetTCPConnection -LocalPort 3389

Get-Counter '\Processor(_Total)\% Processor Time'
```

Each confirms a different layer:

* RDP service
* Listening socket
* Windows Firewall
* Disk capacity
* CPU pressure

# EC2 Serial Console

The EC2 Serial Console provides access that does not depend on the instance’s normal network path. AWS documents it as a tool for diagnosing Linux and Windows boot, network-configuration, and other instance problems.

It is useful when:

* SSH fails
* RDP fails
* Session Manager fails
* Network configuration is broken
* The instance is stuck during boot
* The firewall blocks access
* You need low-level console output

## Important prerequisites

Access must be enabled at the account level, supported by the instance, and authorized through IAM. AWS documents separate steps for enabling or denying account access to the serial console.

## What to inspect

* Boot messages

# CPU Saturation

High CPU can cause:

* Increased latency
* Health-check failures
* SSH delay
* Request timeout
* Queue growth
* Service instability

Inspect CloudWatch `CPUUtilization`, then verify inside the operating system.

```bash

```

```bash

```

```bash

```

## What `uptime` checks

It displays:

* Current time
* System uptime
* Logged-in users
* Load averages

Example:

```text

```

Load should be interpreted relative to:

* vCPU count
* Workload type
* Runnable and blocked processes
* Historical baseline

* One process consumes all available CPU.


```bash

```

* User CPU
* System CPU
* I/O wait
* Per-process pressure
* Per-core imbalance

# CPU Credits and Burstable Instances

T-family instances use burstable CPU behavior.

An application may perform well while CPU credits are available, then slow after credits are depleted.

Investigate CloudWatch metrics such as:

* `CPUCreditBalance`
* `CPUCreditUsage`
* Surplus credit metrics where applicable

Symptoms can include:

* Gradual performance decline
* Stable memory and disk
* No application crash
* Latency increasing under sustained load

The correct fix may involve:

* Changing the workload pattern
* Selecting a non-burstable instance family
* Rightsizing
* Scaling horizontally
* Reviewing Unlimited mode and cost

Do not simply scale up without confirming whether CPU credits explain the behavior.

# Memory Exhaustion

Standard EC2 metrics do not automatically expose guest operating-system memory utilization.

Use the CloudWatch Agent or inspect the instance directly.

```bash
free -m
```

## What it checks

It reports total, used, free, shared, cache, and available memory.

## Healthy interpretation

Focus on `available`, not only `free`.

Linux intentionally uses available memory for cache.

## Abnormal output

```text
              total   used   free  shared  buff/cache  available
Mem:           7820   7412     88      40         320        104
Swap:             0      0      0
```

Only 104 MiB is available, which indicates severe pressure.

Check:

```bash
dmesg -T | grep -i -E 'out of memory|killed process|oom'
```

or:

```bash
journalctl -k | grep -i -E 'out of memory|killed process|oom'
```

## Possible causes

* Memory leak
* Traffic spike
* Oversized cache
* Too many worker processes
* Large payloads
* Deployment regression
* No swap
* Wrong instance size

## What to do

Mitigation may include:

* Removing unhealthy capacity from service
* Rolling back
* Restarting only after evidence is captured
* Scaling out
* Adjusting concurrency
* Increasing memory temporarily

Permanent correction requires identifying why memory grew.

# Disk-Full Incidents

A full root file system can cause:

* SSH failure
* Application crashes
* Logging failure
* Package-manager failure
* Database corruption risk
* SSM Agent failure
* Boot problems
* Inability to create temporary files

Check:

```bash
df -h
```

## What it checks

It reports file-system space usage.

## Healthy output

Adequate free capacity exists on critical file systems.

## Abnormal output

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p1   20G   20G     0 100% /
```

## What to investigate next

```bash
sudo du -xhd1 / | sort -h
```

```bash
sudo du -xhd1 /var | sort -h
```

```bash
sudo find /var/log -type f -size +500M -ls
```

```bash
sudo journalctl --disk-usage
```

Do not immediately run broad deletion commands.

First determine:

* Which files grew
* Whether they are active
* Whether they contain incident evidence
* Whether a process still holds deleted files open
* Whether retention or rotation failed

Check deleted-but-open files:

```bash
sudo lsof +L1
```

A deleted log file can continue consuming disk space until the process closes it.

# Inode Exhaustion

A file system may have free gigabytes but still be unable to create files because it has no free inodes.

Check:

```bash
df -i
```

## Healthy output

A reasonable percentage of inodes remains available.

## Abnormal output

```text
Filesystem       Inodes    IUsed IFree IUse% Mounted on
/dev/nvme0n1p1  1310720  1310720     0  100% /
```

## Common causes

* Millions of small log files
* Session files
* Cache files
* Temporary files
* Application spool directories
* Failed cleanup jobs

## Find inode-heavy directories

```bash
sudo find / -xdev -printf '%h\n' 2>/dev/null \
  | sort \
  | uniq -c \
  | sort -nr \
  | head -30
```

Deletion must be targeted and safe.

After mitigation, fix:

* Rotation
* Retention
* Cleanup jobs
* Application file strategy
* Monitoring

# EC2Rescue

EC2Rescue for Linux is an open-source troubleshooting and remediation tool with a library of modules for common impaired-instance problems.

It can help investigate:

* Boot failures
* Network configuration
* SSH configuration
* File-system conditions
* System configuration
* Operating-system problems

EC2Rescue is appropriate when normal access is unavailable and deeper operating-system inspection is required.

A typical offline recovery model may involve:

1. Stop the affected instance.
2. Snapshot the root volume.
3. Detach the root volume.
4. Attach it to a healthy rescue instance.
5. Mount it safely.
6. Inspect or repair configuration.
7. Detach it from the rescue instance.
8. Reattach it as the original root device.
9. Start the affected instance.
10. Validate the complete workload.

This is a high-risk operation.

Use the AWS-provided runbooks where suitable, and document every resource and attachment change.

# Repairing Versus Replacing an Instance

Senior engineers do not assume every instance should be repaired.

Ask:

* Is it stateless?
* Is it in an Auto Scaling group?
* Can a known-good image replace it?
* Is required data externalized?
* Is the launch process reliable?
* Is investigation needed for root cause?
* Is the instance unique?
* Would repair take longer than replacement?
* Could repair introduce unknown configuration drift?

## Replace when

* The workload is stateless.
* Auto Scaling can create a healthy replacement.
* Configuration is automated.
* Important evidence has been preserved.
* No local data must be recovered.
* Replacement is safer and faster.

## Repair when

* Important local data is not yet recovered.
* The server is unique or legacy.
* Replacement automation is unavailable.
* Root-cause evidence is needed.
* The failure affects the image or launch process and replacement would repeat it.
* Regulatory or forensic requirements require preservation.

The ideal cloud operating model treats instances as replaceable.

Real production environments do not always reach that ideal.

# Real Troubleshooting Lab 1

## EC2 Is Running, but SSH Times Out

### Scenario

A production Linux instance is in the `running` state.

The application target is unhealthy.

SSH returns:

```text
ssh: connect to host 203.0.113.10 port 22: Connection timed out
```

### Step 1: Confirm identity and Region

```bash
aws sts get-caller-identity
aws configure get region
```

Why:

Troubleshooting the wrong account or Region wastes time and can create dangerous changes.

### Step 2: Inspect the instance

```bash
aws ec2 describe-instances \
  --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[].Instances[].{
    State:State.Name,
    AZ:Placement.AvailabilityZone,
    PrivateIP:PrivateIpAddress,
    PublicIP:PublicIpAddress,
    Subnet:SubnetId,
    SecurityGroups:SecurityGroups,
    IAM:IamInstanceProfile.Arn
  }'
```

Finding:

* State is `running`.
* Public IP exists.
* Expected subnet and security group are attached.

### Step 3: Inspect status checks

```bash
aws ec2 describe-instance-status \
  --instance-ids i-0123456789abcdef0 \
  --include-all-instances
```

Finding:

```text
System status: ok
Instance status: ok
```

Interpretation:

AWS infrastructure and guest reachability checks have not detected impairment.

The failure may still involve the network path, host firewall, or SSH service.

### Step 4: Test the port

```bash
nc -vz 203.0.113.10 22
```

Finding:

```text
Connection timed out
```

### Step 5: Inspect security groups

The inbound SSH rule is present and matches the responder’s approved VPN range.

### Step 6: Compare NACLs

The affected subnet’s NACL differs from the healthy subnet.

A recent security change added:

```text
Rule 90 DENY TCP 1024-65535 outbound
```

SSH requests reach the instance, but return traffic is blocked because NACLs are stateless.

### Root cause

An outbound NACL deny blocked ephemeral return traffic.

### Mitigation

Restore the previously approved NACL rule set through the controlled infrastructure pipeline.

### Confirmation

```bash
nc -vz 203.0.113.10 22
```

returns success, followed by a successful audited SSH connection.

### Lesson

A security group allowing port 22 does not prove the whole path works.

# Real Troubleshooting Lab 2

## Instance Passes EC2 Checks but Fails Application Checks

### Scenario

EC2 shows both checks as healthy.

The ALB reports the target as unhealthy.

### Step 1: Inspect target health

```bash
aws elbv2 describe-target-health \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/api-production/abcdef
```

Finding:

```text
Target.FailedHealthChecks
```

### Step 2: Connect through Session Manager

```bash
aws ssm start-session \
  --target i-0123456789abcdef0
```

### Step 3: Check failed services

```bash
systemctl --failed
```

Finding:

```text
api.service loaded failed failed
```

### Step 4: Inspect logs

```bash
journalctl -u api.service --since "30 minutes ago"
```

Finding:

```text
Failed to bind to 0.0.0.0:8080: Address already in use
```

### Step 5: Identify the listener

```bash
ss -lntp | grep ':8080'
```

Finding:

An old application process from the previous deployment still owns the port.

### Root cause

The deployment script started a second process without stopping the previous service cleanly.

### Mitigation

Drain the target from the ALB, preserve process and deployment evidence, stop the orphan process, start the managed service, and revalidate locally.

### Confirmation

```bash
curl -v http://127.0.0.1:8080/health
```

returns `200`, and ALB target health becomes healthy.

### Permanent correction

* Use systemd as the single process owner.
* Make deployment scripts idempotent.
* Add pre-start port validation.
* Replace instances during deployment instead of mutating them in place.

# Real Troubleshooting Lab 3

## EC2 Becomes Unresponsive Because the Root Volume Is Full

### Scenario

The application stops writing logs.

Session Manager disappears.

SSH is slow and eventually fails.

Status checks initially remain healthy.

### Step 1: Use available console or rescue access

Once access is available:

```bash
df -h
df -i
```

Finding:

```text
/dev/nvme0n1p1  20G  20G  0  100% /
```

Inodes remain available.

### Step 2: Locate growth

```bash
sudo du -xhd1 /var | sort -h
sudo du -xhd1 /var/log | sort -h
```

Finding:

```text
15G /var/log/application
```

### Step 3: Inspect large files

```bash
sudo find /var/log/application -type f -size +500M -ls
```

Finding:

A debug log grew continuously after a deployment enabled request-body logging.

### Step 4: Preserve evidence

Copy a limited representative sample to the approved incident evidence location.

Do not copy sensitive request bodies unnecessarily.

### Step 5: Mitigate

* Disable excessive debug logging.
* Rotate or truncate only the confirmed active file safely.
* Restart affected agents only after space is restored.
* Confirm SSM and application recovery.

### Root cause

A deployment enabled verbose request logging, while log rotation did not include the new file path.

### Permanent correction

* Structured logging
* Request-body redaction
* Rotation
* Retention
* Disk alarms
* Separate application-log volume where justified
* Deployment validation for logging changes

# Real Troubleshooting Lab 4

## Application Slows Because of CPU Credits and EBS Limits

### Scenario

The application does not crash.

Latency rises every afternoon.

EC2 status checks remain healthy.

### Evidence

* T-family instance
* `CPUUtilization` remains high for several hours
* `CPUCreditBalance` approaches zero
* EBS queue and latency rise during batch processing
* `iostat` shows sustained disk waits

### Investigation

```bash
uptime
vmstat 1 10
iostat -xz 1 10
ps -eo pid,user,%cpu,%mem,etime,cmd --sort=-%cpu | head -20
```

Finding:

* Batch process consumes sustained CPU.
* CPU credits are depleted.
* Application and batch workload compete for EBS throughput.
* Customer latency grows without an application exception.

### Root cause

A daily batch process was moved onto the customer-facing burstable instance. Sustained CPU depleted its credits, while batch I/O competed with the API.

### Mitigation

Pause or move the batch job and restore customer capacity.

### Permanent correction

* Separate batch and customer-facing workloads.
* Use a suitable instance family.
* Define CPU and EBS capacity requirements.
* Add credit and storage-performance alarms.
* Schedule load tests that include batch activity.

# Real Troubleshooting Lab 5

## Session Manager Cannot See the Instance

### Scenario

SSH is intentionally disabled.

The instance is running and serves customer traffic.

The Session Manager tab reports that the instance is not configured for Session Manager.

### Step 1: Check registration

```bash
aws ssm describe-instance-information \
  --filters Key=InstanceIds,Values=i-0123456789abcdef0
```

Result:

```json
{
  "InstanceInformationList": []
}
```

```bash

  --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[].Instances[].IamInstanceProfile.Arn'
```

Result:

```text
null
```

### Step 3: Check launch template

The current launch-template version accidentally removed the instance profile.

The application remained healthy because it did not require AWS APIs during normal operation.

### Mitigation

Then verify registration and agent communication.

### Permanent correction

* Add launch-template policy validation.
* Require an approved profile for production EC2.
* Alarm when production instances disappear from Systems Manager.
* Compare launch-template versions before deployment.
* Use AWS Config to detect missing profiles.

A running application does not prove that the operational access path is healthy.

# Common EC2 Troubleshooting Mistakes

## Treating `running` as healthy

`running` is a lifecycle state, not an application guarantee.

## Restarting before collecting evidence

The restart may remove the failure state and logs needed for diagnosis.

## Opening SSH to the internet

Broadening access creates security risk and may not solve the actual failure.

## Assuming the security group is the only network control

Routes, NACLs, host firewalls, public addressing, VPNs, and service listeners also matter.

## Increasing disk size without identifying growth

The volume may fill again because the defective process remains.

## Increasing memory without investigating the leak

This delays the next failure.

## Repairing a replaceable instance manually

Manual mutation creates drift and hides weaknesses in the image or launch process.

## Replacing a unique instance without preserving data

Cloud-first thinking does not justify data loss.

## Treating automation as risk-free

Some AWS support runbooks can stop instances, attach volumes, or modify configuration.

Review the steps first.

## Checking only AWS metrics

Guest operating-system and application evidence is equally important.

* Is this one instance or the whole fleet?
* Is the AWS infrastructure impaired?
* Did the operating system finish booting?
* Is there a valid network path?
* Is the service listening?
* Is the instance under resource pressure?
* Is storage available and performing normally?
* Did a recent change introduce the failure?
* Can the instance be replaced safely?
* What evidence will disappear if we restart it?
* What monitoring should have detected this earlier?

They also distinguish access failure from workload failure.

An inaccessible instance may still serve customers.

An accessible instance may still serve nothing.

The customer outcome remains the most important signal.

---

# Key Takeaways

* EC2 lifecycle state is not application health.
* Start with customer impact and blast radius.
* Compare the affected instance with a healthy peer.
* Use `describe-instance-status` to separate system, guest, and EBS impairment signals.
* A failed system check points toward AWS infrastructure.
* A failed instance check often points toward the guest operating system.
* Passing checks do not prove the application works.
* Distinguish SSH timeout, refusal, and authentication failure.
* Validate the whole network path.
* Use Session Manager as a controlled access method.
* Check SSM Agent, IAM, DNS, and endpoint connectivity when Session Manager fails.
* Use the EC2 Serial Console for boot and network problems.
* Use EC2Rescue for impaired or unreachable systems.
* Check memory, disk capacity, inodes, processes, ports, and services.
* Monitor EBS behavior, not only attachment state.
* Investigate CPU credits on burstable instances.
* Treat user data as production code.
* Preserve evidence before restarting.
* Replace stateless instances when replacement is safer.
* Repair instances when unique data or evidence requires it.
* Confirm recovery through the customer-facing application.
