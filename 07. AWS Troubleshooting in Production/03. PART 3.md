# AWS Troubleshooting in Production

## Part 3: VPC and Network Troubleshooting

**How senior AWS engineers trace packets across subnets, route tables, NAT gateways, security groups, DNS, endpoints, peering, and hybrid networks**

An EC2 instance is healthy.

Its operating system is running.

The application process is listening.

CPU and memory look normal.

But the application cannot reach the internet.

Another service cannot connect to RDS.

An application in VPC A cannot reach a service in VPC B.

AWS CLI calls from a private subnet time out.

One Availability Zone works while another fails.

Some connections succeed, but others mysteriously disappear.

This is where AWS network troubleshooting begins.

And this is also where engineers often make one of the most expensive mistakes in cloud operations:

They start changing security groups.

One rule becomes two.

Two become five.

Someone temporarily adds:

```text
0.0.0.0/0
```

The application still fails.

Now the original configuration has been changed, the security posture has weakened, and the team still does not understand the problem.

Senior engineers do not troubleshoot AWS networking by opening ports until something works.

They trace the path.

They ask:

* Where does the packet begin?
* Where should it go?
* Which route should it follow?
* Which controls evaluate it?
* Does the return path exist?
* Does DNS resolve to the expected address?
* Does the destination actually listen?
* Is the failure in AWS configuration or inside the operating system?
* Is the path theoretically reachable?
* Did real packets actually traverse it?

AWS provides several layers of networking controls, and each answers a different question.

The challenge is not knowing that security groups, network ACLs, and route tables exist.

The challenge is knowing which one to investigate first.

---

# The Core AWS Network Troubleshooting Principle

Treat network troubleshooting as a path.

For example:

```text
EC2 Application
↓
Elastic Network Interface
↓
Security Group
↓
Subnet
↓
Network ACL
↓
Route Table
↓
NAT Gateway
↓
Internet Gateway
↓
External API
```

Or:

```text
Application Server
↓
Security Group
↓
Private Subnet
↓
Route Table
↓
RDS Subnet
↓
RDS Security Group
↓
Database Listener
```

Or:

```text
VPC A
↓
Route Table
↓
Transit Gateway
↓
Transit Gateway Route Table
↓
VPC B
↓
Security Group
↓
Application
```

A packet must successfully cross every required layer.

One incorrect component is enough to break the path.

This leads to a fundamental principle:

> A network connection is only as healthy as the complete forward and return path.

---

# Start With the Exact Connection

Do not begin with:

> The network is down.

Define the connection precisely.

For example:

```text
Source:
EC2 instance i-0123456789abcdef0
10.20.10.41

Destination:
RDS PostgreSQL
10.30.18.27

Protocol:
TCP

Destination port:
5432
```

Or:

```text
Source:
Private EC2 instance
10.20.11.50

Destination:
api.example.com

Protocol:
HTTPS

Port:
443
```

Now you can investigate a real path.

Ask:

* What is the source IP?
* What is the destination IP?
* What protocol?
* What destination port?
* Which VPC?
* Which subnet?
* Which Availability Zone?
* Is the destination public or private?
* What return path should exist?

Without these facts, engineers investigate architecture instead of incidents.

---

# Understand the Packet Before Troubleshooting It

Consider a simple HTTPS request:

```text
10.0.2.45:51432
        ↓
203.0.113.20:443
```

The client chooses an ephemeral source port.

The destination listens on TCP 443.

For the connection to succeed:

1. DNS must resolve correctly.
2. The source operating system must have a route.
3. AWS networking must have a valid route.
4. Security controls must permit the connection.
5. Any gateway must process the traffic.
6. The destination must receive the request.
7. The destination must accept TCP 443.
8. Response traffic must return successfully.

This is why:

```bash
curl https://example.com
```

can fail even though:

```bash
dig example.com
```

works.

DNS success only proves name resolution.

It does not prove TCP connectivity.

---

# Build the Network Inventory First

For an affected EC2 instance:

```bash
aws ec2 describe-instances \
  --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[].Instances[].{
    Instance:InstanceId,
    AZ:Placement.AvailabilityZone,
    PrivateIP:PrivateIpAddress,
    PublicIP:PublicIpAddress,
    VpcId:VpcId,
    SubnetId:SubnetId,
    SecurityGroups:SecurityGroups,
    ENI:NetworkInterfaces[0].NetworkInterfaceId
  }'
```

## What it checks

This command identifies the EC2 instance's main network context.

## Why it matters

You need:

* VPC ID
* Subnet ID
* Availability Zone
* Security groups
* Network interface
* Private address
* Public address where applicable

before evaluating the path.

## Abnormal findings

* Instance is in the wrong subnet.
* Wrong security group is attached.
* No public IP exists when direct public connectivity was expected.
* Instance is in a different Availability Zone from healthy peers.
* A replacement instance was launched into an unexpected subnet.

---

# Route Tables: Where Should the Packet Go?

Every subnet is associated with a route table.

The route table decides the next destination for traffic leaving the subnet.

Inspect it:

```bash
aws ec2 describe-route-tables \
  --filters Name=association.subnet-id,Values=subnet-0123456789abcdef0 \
  --query 'RouteTables[].{
    RouteTableId:RouteTableId,
    Routes:Routes
  }'
```

If this does not return the expected table, remember that a subnet without an explicit route-table association uses the VPC's main route table.

Inspect the VPC's route tables when necessary:

```bash
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values=vpc-0123456789abcdef0
```

---

# How to Read a Route Table

A private application subnet might contain:

```text
Destination       Target

10.20.0.0/16      local
0.0.0.0/0         nat-0123456789abcdef0
```

Interpretation:

```text
Traffic inside VPC CIDR
→ local VPC router

Everything else
→ NAT Gateway
```

A public subnet might have:

```text
10.20.0.0/16      local
0.0.0.0/0         igw-0123456789abcdef0
```

A peered VPC might require:

```text
10.20.0.0/16      local
10.30.0.0/16      pcx-0123456789abcdef0
```

If the route does not exist, the packet cannot reach the destination regardless of how permissive the security group is.

AWS specifically recommends Reachability Analyzer for identifying missing or misconfigured route-table paths.

---

# Longest Prefix Match

AWS routing uses the most specific matching route.

Suppose the table contains:

```text
10.0.0.0/8          tgw-aaa
10.30.0.0/16        pcx-bbb
0.0.0.0/0           nat-ccc
```

Traffic destined for:

```text
10.30.25.20
```

uses:

```text
10.30.0.0/16 → pcx-bbb
```

because it is more specific than:

```text
10.0.0.0/8
```

This matters during troubleshooting because an apparently valid broad route can be overridden by a more specific route.

Always inspect the complete route table.

---

# Blackhole Routes

A route can exist while its target is unavailable.

For example:

* Deleted NAT gateway
* Deleted peering connection
* Detached gateway
* Invalid target

AWS can report such routes as:

```text
blackhole
```

Search:

```bash
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values=vpc-0123456789abcdef0 \
  --query 'RouteTables[].Routes[?State==`blackhole`]'
```

A blackhole route is a strong failure signal.

Do not attempt to solve it with security-group changes.

---

# Security Groups: Stateful Instance-Level Controls

AWS recommends security groups as the primary network-access control mechanism inside VPCs. Security groups are stateful, which means response traffic associated with an allowed connection is automatically permitted.

Inspect the source security group:

```bash
aws ec2 describe-security-groups \
  --group-ids sg-0123456789abcdef0
```

For a destination such as RDS, inspect its security groups as well.

---

# Understand Security Group Direction

Suppose:

```text
EC2
10.20.10.41

→

RDS
10.30.18.27:5432
```

The important destination-side rule may be:

```text
Inbound
TCP 5432
Source: sg-application
```

This is often better than using:

```text
Source: 10.20.0.0/16
```

because the rule expresses application identity through the source security group rather than trusting an entire CIDR.

But remember:

The referenced security group does not automatically grant access.

The rule must exist on the destination.

---

# Security Groups Do Not Contain Deny Rules

Security groups support allow rules.

They do not contain explicit deny rules.

If traffic is not allowed by any relevant rule, it is denied.

This is different from network ACL behavior.

A common troubleshooting mistake is searching security groups for a deny rule.

There will not be one.

Instead ask:

> Is there an allow rule matching this actual traffic?

---

# Security Group Return Traffic

Because security groups are stateful:

```text
Inbound connection allowed
→ return traffic automatically allowed
```

You do not generally need an outbound rule specifically matching the client's ephemeral port for return traffic from an already permitted connection.

This differs from network ACLs, which are stateless.

Understanding this difference prevents many unnecessary rule changes.

---

# Network ACLs: Stateless Subnet Guardrails

Network ACLs operate at the subnet boundary.

AWS describes them as stateless, meaning return traffic must be explicitly allowed. Rules are processed in numerical order until a matching rule is found.

Inspect:

```bash
aws ec2 describe-network-acls \
  --filters Name=association.subnet-id,Values=subnet-0123456789abcdef0
```

---

# How a NACL Can Break an Apparently Correct Connection

Imagine:

```text
Client
source port 53144

→

Server
TCP 443
```

The server subnet NACL may allow:

```text
Inbound TCP 443
```

But the response traffic goes to:

```text
TCP 53144
```

If the opposite-direction NACL rules do not permit the relevant ephemeral range, the initial traffic may appear correct while the TCP session fails.

This produces frustrating symptoms:

* Timeout
* Partial handshake
* Intermittent failure
* One subnet works while another fails

The security groups may be perfect.

The stateless subnet rules are not.

---

# NACL Rule Ordering Matters

Example:

```text
Rule 80   DENY   TCP 443   10.20.0.0/16
Rule 100  ALLOW  TCP 443   0.0.0.0/0
```

Traffic from:

```text
10.20.10.41
```

is denied because rule 80 matches first.

The later allow does not matter.

Always inspect:

* Rule number
* Direction
* Protocol
* CIDR
* Port range
* Allow or deny

not merely whether an allow rule exists somewhere.

---

# Internet Gateway Troubleshooting

For an IPv4 EC2 instance to communicate directly with the internet, the architecture normally requires:

```text
EC2
↓
Public IPv4 / Elastic IP
↓
Public subnet route table
↓
Internet Gateway
↓
Internet
```

Check the route:

```text
0.0.0.0/0 → igw-...
```

Check gateway attachment:

```bash
aws ec2 describe-internet-gateways \
  --filters Name=attachment.vpc-id,Values=vpc-0123456789abcdef0
```

Possible problems:

* Internet gateway not attached
* Default route missing
* Wrong route table associated
* Instance lacks a public address
* Security group blocks traffic
* NACL blocks traffic
* Host firewall blocks traffic

A subnet is not "public" because of its name.

A subnet is effectively public when its routing and resource addressing allow direct internet-gateway communication.

---

# NAT Gateway Troubleshooting

Private IPv4 workloads often use a NAT gateway for outbound internet connectivity.

Typical architecture:

```text
Private EC2
↓
Private Subnet
↓
0.0.0.0/0
↓
NAT Gateway
↓
Public Subnet
↓
Internet Gateway
↓
Internet
```

A NAT gateway is created in a specific Availability Zone. AWS recommends zonal NAT designs for resilient multi-AZ workloads because workloads sharing a NAT gateway in another Availability Zone can lose outbound connectivity if that NAT gateway's zone becomes unavailable.

---

# Inspect NAT Gateways

```bash
aws ec2 describe-nat-gateways \
  --filter Name=vpc-id,Values=vpc-0123456789abcdef0 \
  --query 'NatGateways[].{
    NatGatewayId:NatGatewayId,
    State:State,
    SubnetId:SubnetId,
    ConnectivityType:ConnectivityType,
    Addresses:NatGatewayAddresses
  }'
```

Healthy:

```text
State: available
```

Abnormal:

```text
pending
failed
deleted
```

Then inspect the NAT gateway subnet's route table.

A public NAT gateway needs a functioning path to an internet gateway.

---

# The Two Route Tables in NAT Troubleshooting

This is one of the most common AWS networking mistakes.

You must verify both sides.

## Private workload subnet

```text
0.0.0.0/0
→ NAT Gateway
```

## NAT gateway public subnet

```text
0.0.0.0/0
→ Internet Gateway
```

Having the first route without the second does not produce internet access.

The packet reaches the NAT gateway and has nowhere useful to go next.

---

# NAT Gateway Metrics

Useful CloudWatch NAT gateway metrics include signals related to:

* Bytes
* Packets
* Connections
* Port allocation
* Packet drops

During high connection volume, investigate whether the workload is exhausting available NAT translation resources or opening excessive connections.

Do not assume every NAT issue is a route problem.

Application connection behavior matters.

---

# Cross-AZ NAT Design

Architecture:

```text
AZ A private subnet
          \
           → NAT Gateway AZ A

AZ B private subnet
          \
           → NAT Gateway AZ A
```

This works during normal conditions.

But it creates:

* Cross-AZ traffic
* Cross-AZ cost
* Zonal dependency

A more resilient design commonly uses:

```text
AZ A private subnet
→ NAT Gateway AZ A

AZ B private subnet
→ NAT Gateway AZ B
```

with each subnet routed to its local NAT gateway.

AWS specifically warns that workloads in multiple Availability Zones sharing one NAT gateway can lose internet access if that NAT gateway's Availability Zone fails.

---

# DNS Troubleshooting

Many network incidents are actually name-resolution incidents.

Test:

```bash
dig api.example.com
```

or:

```bash
getent hosts api.example.com
```

or:

```bash
nslookup api.example.com
```

## What it checks

Whether the name resolves.

## Healthy output

The expected IP address or addresses are returned promptly.

## Abnormal outputs

```text
NXDOMAIN
```

```text
SERVFAIL
```

Timeout.

Unexpected IP address.

Public address returned where private resolution was expected.

---

# DNS Resolution Is Not Connectivity

Suppose:

```bash
dig database.internal
```

returns:

```text
10.30.10.25
```

That only proves DNS resolution.

You still need:

```bash
nc -vz database.internal 5432
```

or an application-appropriate connection test.

Likewise:

```bash
curl -vk https://api.example.com
```

tests much more of the stack:

* DNS
* TCP
* TLS
* HTTP
* Application response

Use tests progressively.

---

# VPC DNS Attributes

Two important VPC attributes are:

```text
enableDnsSupport
enableDnsHostnames
```

AWS documents `enableDnsSupport` as controlling resolution through the Amazon-provided DNS server, while `enableDnsHostnames` controls DNS hostnames for instances where applicable.

Check:

```bash
aws ec2 describe-vpc-attribute \
  --vpc-id vpc-0123456789abcdef0 \
  --attribute enableDnsSupport
```

```bash
aws ec2 describe-vpc-attribute \
  --vpc-id vpc-0123456789abcdef0 \
  --attribute enableDnsHostnames
```

These values are especially important when using interface VPC endpoints and private DNS.

---

# VPC Endpoints

Private workloads do not always need NAT access to reach AWS services.

VPC endpoints can provide private connectivity.

Two major endpoint categories are:

* Gateway endpoints
* Interface endpoints

Interface endpoints use AWS PrivateLink and create endpoint network interfaces with private IP addresses in selected subnets.

---

# Interface Endpoint Troubleshooting

Architecture:

```text
Private EC2
↓
Private DNS
↓
Interface Endpoint ENI
↓
AWS PrivateLink
↓
AWS Service
```

Check endpoints:

```bash
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values=vpc-0123456789abcdef0 \
  --query 'VpcEndpoints[].{
    Endpoint:VpcEndpointId,
    Service:ServiceName,
    Type:VpcEndpointType,
    State:State,
    PrivateDns:PrivateDnsEnabled,
    Subnets:SubnetIds,
    SecurityGroups:Groups
  }'
```

Healthy:

```text
State = available
```

Possible failures:

* Endpoint is not available.
* Private DNS is disabled.
* Wrong endpoint service Region.
* Endpoint security group blocks TCP 443.
* NACL blocks traffic.
* VPC DNS support is disabled.
* Endpoint policy denies the action.
* IAM policy denies the action.

AWS notes that interface endpoint security groups need to allow expected inbound traffic to the endpoint ENIs, commonly HTTPS on TCP 443 for AWS APIs. Private DNS also requires VPC DNS resolution and hostname support.

---

# Endpoint Connectivity vs Authorization

Suppose:

```bash
aws secretsmanager get-secret-value ...
```

returns:

```text
AccessDeniedException
```

That is very different from:

```text
Connection timed out
```

`AccessDeniedException` generally proves the request reached an AWS API far enough for authorization to be evaluated.

Focus on:

* IAM
* Endpoint policy
* Resource policy
* KMS where relevant

A timeout suggests:

* DNS
* Route
* Endpoint ENI
* Security group
* NACL
* Network path

Do not troubleshoot IAM and TCP connectivity as though they are the same problem.

---

# VPC Peering

VPC peering connects two VPC networks privately.

For working communication, both sides typically need appropriate routes and security controls.

Example:

```text
VPC A: 10.20.0.0/16
VPC B: 10.30.0.0/16
```

VPC A route:

```text
10.30.0.0/16
→ pcx-0123456789abcdef0
```

VPC B route:

```text
10.20.0.0/16
→ pcx-0123456789abcdef0
```

AWS recommends checking route tables, security groups, network ACLs, and then Reachability Analyzer when troubleshooting peering connectivity.

---

# Peering Is Not Transitive

Consider:

```text
VPC A
↔
VPC B
↔
VPC C
```

A connection between A and B and another between B and C does not automatically create:

```text
A ↔ C
```

VPC peering is not a general transit router.

This misunderstanding frequently creates unreachable designs.

For larger hub-and-spoke environments, Transit Gateway is often more appropriate.

---

# Peering CIDR Overlap

Overlapping CIDR ranges prevent ordinary VPC peering designs.

Example:

```text
VPC A = 10.0.0.0/16
VPC B = 10.0.0.0/16
```

Routing cannot unambiguously determine which `10.0.x.x` destination is intended.

Network address planning is therefore part of troubleshooting prevention.

Poor IP planning becomes architectural debt.

---

# DNS Across Peered VPCs

DNS behavior across VPC peering requires correct VPC DNS settings and, where needed, the peering DNS-resolution configuration.

AWS documents that peering DNS settings can cause eligible public hostnames in the peer to resolve to private IPv4 addresses rather than public addresses.

If connectivity by IP works but hostname-based access fails, investigate DNS separately.

---

# Transit Gateway Troubleshooting

Transit Gateway introduces another routing layer.

Typical path:

```text
VPC A subnet route table
↓
Transit Gateway attachment
↓
Transit Gateway route table
↓
VPC B attachment
↓
VPC B subnet route table
↓
Destination
```

Now there are multiple route tables.

Troubleshoot:

1. Source subnet route table.
2. Source Transit Gateway attachment.
3. Transit Gateway route-table association.
4. Transit Gateway route propagation or static route.
5. Destination attachment.
6. Destination VPC subnet route table.
7. Security groups.
8. NACLs.
9. Return path.

The return path deserves special attention.

A forward path that exists without a valid return path still creates failure.

---

# Inspect Transit Gateway Routes

List Transit Gateways:

```bash
aws ec2 describe-transit-gateways
```

List attachments:

```bash
aws ec2 describe-transit-gateway-attachments \
  --filters Name=transit-gateway-id,Values=tgw-0123456789abcdef0
```

Search a TGW route table:

```bash
aws ec2 search-transit-gateway-routes \
  --transit-gateway-route-table-id tgw-rtb-0123456789abcdef0 \
  --filters Name=route-search.exact-match,Values=10.30.0.0/16
```

Investigate:

* Active route
* Blackhole route
* Wrong attachment
* Missing propagation
* Incorrect association

---

# Asymmetric Routing

Asymmetric routing occurs when traffic follows one path outward and another path back.

Some network architectures tolerate this.

Others, particularly those involving stateful appliances or inspection systems, may fail.

Example:

```text
Forward:
VPC A
→ Transit Gateway
→ Firewall
→ VPC B

Return:
VPC B
→ Transit Gateway
→ VPC A
```

The firewall sees only one side of the connection.

A stateful inspection device may reject or mishandle the session.

When the obvious routing looks correct but sessions still fail, draw both the forward and return path.

Never assume they are identical.

---

# VPN and Direct Connect Troubleshooting

Hybrid connectivity introduces additional layers.

A Site-to-Site VPN path might be:

```text
EC2
↓
VPC route table
↓
Transit Gateway / Virtual Private Gateway
↓
VPN tunnel
↓
Customer Gateway
↓
On-premises router
↓
Destination
```

Troubleshoot:

* Tunnel state
* BGP state where applicable
* Advertised routes
* Static routes
* VPC routes
* On-premises routes
* Security rules
* Firewall policies
* NAT
* Overlapping CIDRs
* Return route

The phrase:

> AWS can reach on-premises

is not specific enough.

Identify:

* Source IP
* Destination IP
* Port
* Which tunnel
* Which route
* Which security appliance
* Which return route

---

# Ephemeral Ports

TCP clients normally use temporary source ports for outgoing connections.

Example:

```text
Client:
10.20.10.41:54213

Destination:
10.30.20.15:443
```

If stateless controls block the return path to the temporary client port, the session can fail even though TCP 443 is allowed inbound to the server.

This is especially important when troubleshooting NACLs and hybrid firewalls.

Do not assume "443 is open" means the complete HTTPS conversation is possible.

---

# Path MTU and Packet Size Problems

Some network incidents behave strangely:

* Small requests succeed.
* Large requests fail.
* SSH connects but file transfer stalls.
* HTTPS handshake behaves inconsistently.
* VPN traffic fails only for large payloads.

This can point to packet-size or Path MTU issues.

AWS NAT gateways support Path MTU Discovery and have documented MTU considerations. AWS recommends keeping EC2 MTU appropriate for internet communication and notes that oversized packets can be dropped or fragmented where applicable.

Check interface MTU:

```bash
ip link show
```

Test path behavior carefully using approved diagnostic tools appropriate to the protocol.

The important lesson:

> Not every network failure is a port problem.

---

# VPC Flow Logs

VPC Flow Logs provide records about IP traffic to and from network interfaces.

They can help answer:

* Was traffic observed?
* What was the source?
* What was the destination?
* Which source and destination ports were involved?
* Was the traffic accepted or rejected?

This makes Flow Logs extremely useful for distinguishing configuration hypotheses.

---

# Query Rejected Traffic

Example CloudWatch Logs Insights query:

```text
fields @timestamp, srcAddr, srcPort, dstAddr, dstPort, protocol, action
| filter action = "REJECT"
| sort @timestamp desc
| limit 200
```

For PostgreSQL:

```text
fields @timestamp, srcAddr, srcPort, dstAddr, dstPort, action
| filter dstPort = 5432
| filter action = "REJECT"
| sort @timestamp desc
| limit 200
```

For HTTPS:

```text
fields @timestamp, srcAddr, srcPort, dstAddr, dstPort, action
| filter dstPort = 443
| sort @timestamp desc
| limit 200
```

---

# What ACCEPT Actually Means

A Flow Log showing:

```text
ACCEPT
```

does not prove the application transaction succeeded.

It tells you the observed network traffic was accepted at that networking layer.

The destination may still:

* Refuse the connection
* Fail authentication
* Return HTTP 500
* Time out internally
* Close the socket
* Fail a database transaction

Network evidence must be combined with application evidence.

---

# What No Flow-Log Entry Might Mean

No expected record can indicate:

* Traffic never reached the monitored ENI.
* Wrong network interface is being examined.
* Flow Logs are not configured for that traffic.
* Aggregation or delivery delay.
* The application never attempted the connection.
* Traffic used a different path.

Absence of evidence should generate a hypothesis.

Do not treat it automatically as proof of a firewall block.

---

# Reachability Analyzer

Reachability Analyzer is one of the most important AWS-native network troubleshooting tools.

AWS describes it as a configuration-analysis tool that evaluates the virtual network path between a source and destination and identifies a blocking component when a path is not reachable.

It can reason across components such as:

* EC2 instances
* ENIs
* Route tables
* Security groups
* Network ACLs
* NAT gateways
* Transit gateways
* VPC peering
* Load balancers
* VPC endpoints
* VPN-related components

---

# Reachability Analyzer Is Not a Packet Test

This distinction is critical.

AWS explicitly notes that Reachability Analyzer creates a model of the network configuration. It does not send packets or inspect the live data plane.

Therefore:

```text
Reachability Analyzer = reachable
```

means the AWS configuration supports the path it analyzed.

It does not guarantee:

* Destination application is running.
* Process listens on the port.
* Operating-system firewall is correct.
* DNS resolves correctly.
* Application responds.
* Database authenticates.
* Destination target is healthy.

Combine configuration analysis with real traffic evidence.

---

# When Reachability Analyzer Says Not Reachable

It may identify problems such as:

* Missing route
* Security-group restriction
* NACL restriction
* Wrong gateway
* Broken peering path
* Transit route problem

This is much better than randomly inspecting dozens of VPC resources.

However, AWS notes that there may be additional blocking components beyond the first one reported.

Fix one verified issue.

Then analyze again.

Use this workflow consistently.

## Step 1: Define the flow

Document:

```text
Source
Destination
Protocol
Port
Expected route
```

## Step 2: Confirm customer impact

What business action is failing?

## Step 3: Check recent changes

# Real Troubleshooting Lab 1

## Private EC2 Cannot Reach the Internet

### Scenario

A production application runs in private subnets.

After an infrastructure deployment, EC2 instances in:

```text
us-east-1b
```

can no longer:

* Download packages
* Call third-party APIs
* Reach public HTTPS endpoints

Instances in:

```text
us-east-1a
```

continue working.

Application processes remain healthy.

---

# Step 1: Define the Blast Radius

Affected:

```text
Private subnet:
subnet-prod-b

AZ:
us-east-1b
```

Healthy:

```text
Private subnet:
subnet-prod-a

AZ:
us-east-1a
```

This immediately suggests a zonal or subnet-specific difference.

---

# Step 2: Test DNS

On affected instance:

```bash
dig api.external.example.com
```

Result:

```text
203.0.113.30
```

DNS works.

Test TCP:

```bash
nc -vz api.external.example.com 443
```

Result:

```text
timed out
```

DNS is not the primary problem.

---

# Step 3: Inspect Private Route Tables

Healthy AZ:

```text
subnet-prod-a

0.0.0.0/0
→ nat-aaa
```

Affected AZ:

```text
subnet-prod-b

0.0.0.0/0
→ nat-bbb
```

Architecture appears correct.

---

# Step 4: Inspect NAT Gateways

```bash
aws ec2 describe-nat-gateways \
  --nat-gateway-ids nat-bbb
```

Finding:

```text
State = available
```

Do not conclude the NAT path works.

`available` only confirms the NAT gateway resource state.

---

# Step 5: Inspect NAT Public Subnet

NAT `nat-bbb` resides in:

```text
subnet-public-b
```

Inspect its route table.

Finding:

```text
10.20.0.0/16 → local
```

Missing:

```text
0.0.0.0/0 → igw-production
```

The NAT gateway has no route to the internet gateway.

---

# Root Cause

A Terraform refactor accidentally associated:

```text
subnet-public-b
```

with a private route table.

The NAT gateway remained `available`.

Private workloads correctly routed traffic to it.

But the NAT gateway's subnet no longer had an internet-gateway route.

---

# Mitigation

Restore the correct route-table association through the infrastructure pipeline.

Do not:

* Add public IP addresses to private EC2 instances.
* Open additional security-group ports.
* Move workloads manually.
* Replace healthy instances.

---

# Confirm Recovery

Test:

```bash
curl -I https://api.external.example.com
```

Then validate the actual application dependency.

Confirm:

* Third-party API succeeds.
* Error rate drops.
* No unexpected route changes exist.
* Both Availability Zones are healthy.

---

# Lesson

A NAT gateway reporting `available` does not prove that its complete internet path works.

# Real Troubleshooting Lab 3

## One Subnet Works, Another Fails

### Scenario

Application instances are deployed across two Availability Zones.

```text
AZ A
Healthy

AZ B
Connections to internal API time out
```

Security groups are identical.

Routes are identical.

---

# Step 1: Compare NACL Associations

```bash
aws ec2 describe-network-acls \
  --filters Name=association.subnet-id,Values=subnet-az-b
```

Finding:

AZ B uses a newly created hardened NACL.

---

# Step 2: Inspect Rules

Inbound includes:

```text
ALLOW TCP 443
```

Outbound includes only:

```text
ALLOW TCP 443
```

The return traffic goes to ephemeral client ports.

The NACL is stateless.

AWS security groups would automatically permit return traffic, but the NACL requires the reverse path to be explicitly allowed.

---

# Root Cause

A security hardening change applied stateful-firewall assumptions to a stateless network ACL.

The destination port was allowed.

The return path was not.

---

# Permanent Fix

Define documented NACL requirements for:

* Service destination ports
* Required ephemeral return traffic
* Hybrid routes
* Approved deny controls

Where possible, rely on security groups for fine-grained workload controls and use NACLs as deliberate subnet-level guardrails, consistent with AWS guidance.

# Real Troubleshooting Lab 4

## Security Groups Look Correct but Traffic Still Fails

### Scenario

Two EC2 instances should communicate over TCP 8443.

Security groups clearly permit it.

`nc` times out.

---

# Step 1: Run Reachability Analyzer

Configure:

```text
Source:
application ENI

Destination:
service ENI

Protocol:
TCP

Destination port:
8443
```

Reachability Analyzer returns:

```text
Not reachable
```

Blocking component:

```text
route table
```

The destination is in a peered VPC.

---

# Step 2: Inspect Routes

Source VPC contains:

```text
10.30.0.0/16
→ pcx-aaa
```

Destination VPC does not contain:

```text
10.20.0.0/16
→ pcx-aaa
```

The forward path exists.

The return path does not.

---

# Root Cause

The peering route was added on only one side.

AWS peering troubleshooting guidance specifically calls for verifying routes on each VPC along with security groups and NACLs.

---

# Lesson

Security groups cannot compensate for missing routing.

# Real Troubleshooting Lab 5

## NAT Gateway Exists but Outbound Traffic Fails Intermittently

### Scenario

Hundreds of application workers call the same external service.

At peak traffic:

* Some connections succeed.
* Some time out.
* NAT gateway remains `available`.
* Route configuration is correct.
* DNS works.

---

# Investigation

Correlate:

* NAT gateway metrics
* Application connection count
* New connection rate
* HTTP connection reuse
* External API latency
* Worker scaling

Finding:

Workers open large numbers of short-lived connections and do not reuse HTTP connections effectively.

As concurrency increases, translation pressure and connection churn increase sharply.

The NAT gateway is not "down."

The application traffic pattern is stressing the shared egress path.

---

# Mitigation

Reduce unnecessary connection creation where safe and stabilize application concurrency.

---

# Permanent Fix

Evaluate:

* Connection pooling
* HTTP keep-alive
* Workload distribution
* NAT architecture
* Zonal egress design
* Direct VPC endpoints for AWS services
* Capacity and observability

The lesson:

> Sometimes the network resource is healthy, but the application uses the network inefficiently.

# Linux Network Diagnostic Toolkit

Inside an EC2 Linux instance:

```bash
ip addr
```

Checks addresses and interfaces.

```bash
ip route
```

Checks the operating-system routing table.

```bash
ss -lntp
```

Checks TCP listening sockets.

```bash
ss -ant
```

Shows TCP connections and states.

```bash
dig hostname
```

Checks DNS.

```bash
getent hosts hostname
```

Checks name resolution through the system resolver.

```bash
nc -vz hostname 443
```

Tests TCP connectivity.

```bash
curl -v https://hostname
```

Tests DNS, TCP, TLS, and HTTP.

```bash
openssl s_client \
  -connect hostname:443 \
  -servername hostname
```

Examines TLS connectivity and certificates.

```bash
nft list ruleset
```

Checks modern Linux firewall rules.

```bash
iptables -L -n -v
```

Checks iptables rules where used.

Each command answers a different question.

Never execute them just to "see what happens."

Know what hypothesis you are testing.

# Common AWS Network Troubleshooting Mistakes

## Opening every port

This weakens security and often does nothing to solve missing routes, DNS failures, or failed services.

## Assuming `0.0.0.0/0` solves networking

It does not create routing.

It does not attach an internet gateway.

It does not create a public IP.

It does not start the application.

## Forgetting the return path

A valid forward path is not enough.

## Treating security groups and NACLs identically

Security groups are stateful.

NACLs are stateless.

## Calling a subnet public because of its name

Names have no routing behavior.

## Assuming a NAT gateway's `available` state proves internet access

The NAT gateway subnet still needs appropriate internet routing.

## Assuming DNS success proves connectivity

It proves only name resolution.

## Assuming TCP success proves application health

It proves a TCP session can be established.

## Ignoring Availability Zones

Zonal differences are powerful troubleshooting clues.

## Changing many network resources at once

You lose causality.

## Ignoring application connection behavior

High connection churn can create network pressure even when infrastructure is functioning as designed.

# How Senior Engineers Think About AWS Networking

Senior engineers do not begin with:

> Which port should I open?

They begin with:

> What exact packet flow is failing?

They ask:

* What is the source?
* What is the destination?
* What resolved address is being used?
* Which route should match?
* Which gateway should process the traffic?
* Which security groups apply?
* Which NACLs apply?
* Does the return path exist?
* Does Reachability Analyzer agree with the intended design?
* Do Flow Logs show real traffic?
* Does the operating system allow it?
* Is the destination actually listening?
* What changed?
* Why are some flows healthy and others not?

That sequence turns a vague "network problem" into a finite investigation.

# Key Takeaways

* Always define the exact source, destination, protocol, and port.
* Troubleshoot the complete forward and return path.
* Route tables determine where traffic goes.
* Security groups are stateful workload-level controls.
* Network ACLs are stateless subnet-level controls.
* A permissive security group cannot fix a missing route.
* A NAT gateway needs a complete path through its own subnet.
* Multi-AZ workloads should account for zonal NAT dependencies.
* DNS success does not prove network connectivity.
* TCP success does not prove application health.
* Interface endpoints introduce DNS, ENI, security-group, and endpoint-policy considerations.
* VPC peering requires correct routing on both sides.
* VPC peering is not transitive.
* Transit Gateway adds its own routing and attachment layers.
* Always investigate the return route.
* VPC Flow Logs provide evidence about observed network traffic.
* `ACCEPT` does not prove an application transaction succeeded.
* Reachability Analyzer examines configuration, not live packets.
* Use healthy-versus-unhealthy comparisons aggressively.
* Never fix networking by opening everything.
* Change one verified problem at a time.
* Confirm recovery with the actual customer workflow.
