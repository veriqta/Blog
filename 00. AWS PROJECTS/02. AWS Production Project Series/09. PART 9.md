## Part 9: Bastion Host — Your Secure Gateway to Private Subnets

The bastion host (also called a "jump box") is your only entry point into private subnets. It sits in a public subnet, accepts SSH from your IP only, and lets you hop into application servers that have no public internet exposure.

In modern AWS, there are two approaches:
1. **Traditional Bastion Host** (what we'll build now — foundational knowledge)
2. **AWS Systems Manager Session Manager** (modern, agent-based, no open ports)

I'll show you both. Understanding the traditional bastion is critical for interviews and legacy environments. Session Manager is the modern production standard.

---

### Step 1: Launch the Bastion Host

We'll use Amazon Linux 2023 — AWS's modern, security-focused OS. It's pre-hardened, minimal, and receives frequent updates.

```bash
# Get the latest Amazon Linux 2023 AMI (if you don't have it from Part 7)
AMI_ID=$(aws ssm get-parameters \
    --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
    --query 'Parameters[0].Value' \
    --output text)

echo "AMI ID: $AMI_ID"
```

**Launch the bastion in Public Subnet 1a:**
```bash
aws ec2 run-instances \
    --image-id $AMI_ID \
    --instance-type t3.micro \
    --key-name veriqta-ha-webapp-key \
    --subnet-id $PUBLIC_SUBNET_1A \
    --security-group-ids $BASTION_SG_ID \
    --iam-instance-profile Name=Veriqta-EC2-WebApp-Profile \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=veriqta-bastion},{Key=Tier,Value=Bastion},{Key=Project,Value=Veriqta-HA-WebApp}]' \
    --metadata-options '{"HttpTokens":"required","HttpPutResponseHopLimit":1,"HttpEndpoint":"enabled"}' \
    --count 1
```

**Critical flags explained:**
- `--iam-instance-profile`: Allows the bastion to use Session Manager and CloudWatch
- `--metadata-options '{"HttpTokens":"required"}'`: **Enforces IMDSv2** — blocks IMDSv1, which is vulnerable to SSRF attacks

**Capture the Instance ID and Public IP:**
```bash
BASTION_ID=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=veriqta-bastion" \
    --query 'Reservations[*].Instances[*].InstanceId' \
    --output text)

BASTION_IP=$(aws ec2 describe-instances \
    --instance-ids $BASTION_ID \
    --query 'Reservations[*].Instances[*].PublicIpAddress' \
    --output text)

echo "Bastion ID: $BASTION_ID"
echo "Bastion IP: $BASTION_IP"
```

**Wait for the instance to be running:**
```bash
aws ec2 wait instance-running --instance-ids $BASTION_ID
echo "Bastion is running!"
```

### Step 2: Harden the Bastion Host

SSH into the bastion and apply security hardening:

```bash
ssh -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
```

**Once inside, run these hardening commands:**

```bash
# Update all packages
sudo dnf update -y

# Install essential tools
sudo dnf install -y htop tmux fail2ban

# Configure fail2ban to block brute-force SSH attempts
sudo tee /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/secure
maxretry = 3
bantime = 3600
findtime = 600
EOF

sudo systemctl enable fail2ban
sudo systemctl start fail2ban

# Verify fail2ban is running
sudo fail2ban-client status sshd

# Disable password authentication (force key-based auth only)
sudo sed -i 's/#PasswordAuthentication yes/PasswordAuthentication no/g' /etc/ssh/sshd_config
sudo sed -i 's/PasswordAuthentication yes/PasswordAuthentication no/g' /etc/ssh/sshd_config
sudo sed -i 's/#PermitRootLogin yes/PermitRootLogin no/g' /etc/ssh/sshd_config
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/g' /etc/ssh/sshd_config

# Restart SSH
sudo systemctl restart sshd

# Set up automatic security updates
sudo dnf install -y dnf-automatic
sudo systemctl enable --now dnf-automatic.timer

# Verify
sudo systemctl status dnf-automatic.timer
```

**Exit the bastion:**
```bash
exit
```

### Step 3: SSH Agent Forwarding — Securely Access Private Instances

You have your private key on your local machine. You need to access private instances through the bastion. **Never copy your private key to the bastion** — that's a security risk.

**Solution: SSH Agent Forwarding**

Your local SSH agent holds your key and authenticates on your behalf through the bastion.

**Start the SSH agent on your local machine:**
```bash
# macOS / Linux
eval "$(ssh-agent -s)"

# Add your key to the agent
ssh-add -K veriqta-ha-webapp-key.pem  # macOS (stores in Keychain)
# OR
ssh-add veriqta-ha-webapp-key.pem      # Linux
```

**Test agent forwarding to bastion:**
```bash
ssh -A -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
```

The `-A` flag enables agent forwarding. Once on the bastion, you can SSH to any private instance without copying your key:

```bash
# From the bastion, SSH to a private instance (we'll test this later when we have app servers)
# ssh ec2-user@<PRIVATE_IP>
```

### Step 4: Modern Alternative — AWS Systems Manager Session Manager

Session Manager is AWS's modern replacement for bastion hosts. It uses the AWS Systems Manager agent (pre-installed on Amazon Linux 2023) to create secure shell sessions through AWS APIs — **no open ports, no SSH keys, no bastion instances needed.**

**Why it's better:**
- No inbound ports open (zero attack surface)
- No SSH keys to manage
- Full audit logging in CloudTrail
- IAM-controlled access (who can access which instances)
- Works through the AWS Console, CLI, or SSH proxy

**Verify the SSM agent is running on your bastion:**
```bash
# SSH to bastion first
ssh -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP

# Check SSM agent
sudo systemctl status amazon-ssm-agent

# If not running (it should be by default)
sudo systemctl start amazon-ssm-agent
sudo systemctl enable amazon-ssm-agent
```

**Connect via Session Manager from your LOCAL machine:**
```bash
# Install Session Manager plugin first:
# macOS: brew install --cask session-manager-plugin
# Linux: https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html

# Connect to the bastion via Session Manager
aws ssm start-session --target $BASTION_ID
```

**You should see:**
```
Starting session with SessionId: your-session-id
sh-5.2$
```

**No SSH. No keys. No open ports.** Just an authenticated AWS API call.

**To use Session Manager like SSH (with port forwarding):**
```bash
# Add to your ~/.ssh/config
cat >> ~/.ssh/config << 'EOF'

# AWS Session Manager Proxy
Host i-* mi-*
    ProxyCommand sh -c "aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters 'portNumber=%p'"
    User ec2-user
    IdentityFile ~/.ssh/veriqta-ha-webapp-key.pem
EOF
```

Now you can:
```bash
ssh $BASTION_ID  # Connect via Session Manager using SSH syntax
```

### Step 7: Bastion Host Best Practices

| Practice | Why It Matters |
|----------|---------------|
| **Use t3.micro or smaller** | Bastions don't need compute power — they're just a jump point |
| **Auto-shutdown when not in use** | Save money — use Lambda + CloudWatch to stop bastions nights/weekends |
| **Enable CloudTrail logging** | Every SSH/Session Manager connection is audited |
| **Use Session Manager over SSH** | No open ports = no brute-force attacks |
| **Rotate keys regularly** | Even though keys aren't on the bastion, rotate your local keys quarterly |
| **Monitor with CloudWatch** | Alert on failed SSH attempts, CPU spikes, unusual traffic |

### Step 8: Update Your Security Group if Your IP Changes

If your ISP changes your public IP, you'll be locked out of the bastion.

**To update the Bastion SG with your new IP:**
```bash
# Get your new IP
NEW_IP=$(curl -s https://checkip.amazonaws.com)

# Revoke old rule
aws ec2 revoke-security-group-ingress \
    --group-id $BASTION_SG_ID \
    --protocol tcp \
    --port 22 \
    --cidr "${MY_IP}/32"

# Authorize new rule
aws ec2 authorize-security-group-ingress \
    --group-id $BASTION_SG_ID \
    --protocol tcp \
    --port 22 \
    --cidr "${NEW_IP}/32"

# Update variable
MY_IP=$NEW_IP
```
