## PHASE 4: SECRETS MANAGER & IAM ROLES

Hardcoded database credentials are a security failure. If you embed a password in a Launch Template user data script, that password is visible to anyone with EC2 read access, stored in CloudTrail logs, and potentially committed to version control if the script is checked into Git.

This phase eliminates that risk entirely. You will store the master database password in AWS Secrets Manager, create an IAM role that grants backend EC2 instances permission to retrieve that secret at runtime, and build a trust relationship that ensures no other service or user can access it.

The backend application will authenticate to MySQL using credentials retrieved dynamically from the Secrets Manager API at startup. No password exists in code, in user data, or on disk.

### 4.3 Store the Database Credentials in AWS Secrets Manager

Secrets Manager encrypts secrets at rest using KMS and provides automatic rotation, fine-grained access control, and audit logging through CloudTrail.

```bash
aws secretsmanager create-secret \
    --name veriqta/mysql-credentials \
    --description "Database credentials for VERIQTA three-tier application" \
    --secret-string "{
        \"username\": \"admin\",
        \"password\": \"$MASTER_PASSWORD\",
        \"host\": \"$RDS_ENDPOINT\",
        \"port\": \"3306\",
        \"dbname\": \"veriqta_app\"
    }" \
    --tags Key=Name,Value=veriqta-mysql-credentials Key=Project,Value=Veriqta-Three-Tier Key=Tier,Value=Database
```

**Capture the Secret ARN:**
```bash
SECRET_ARN=$(aws secretsmanager describe-secret \
    --secret-id veriqta/mysql-credentials \
    --query 'ARN' \
```

**Verify the secret was created:**
```bash

    --query '{Name:Name,Created:CreatedDate,ARN:ARN}'
```

**Retrieve and verify the secret contents (without exposing the password in logs):**
```bash

    --secret-id veriqta/mysql-credentials \
```

### 4.4 Create an IAM Role for Backend EC2 Instances

The backend servers need permission to call `secretsmanager:GetSecretValue` on the specific secret you just created. We create a dedicated IAM role with a least-privilege policy.

**Create the trust policy file:**
```bash
cat > backend-trust-policy.json << 'EOF'
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Service": "ec2.amazonaws.com"
            },
            "Action": "sts:AssumeRole"
        }
    ]
}
EOF
```

**Create the IAM role:**
```bash
aws iam create-role \
    --role-name Veriqta-Backend-Role \
    --assume-role-policy-document file://backend-trust-policy.json \
    --description "IAM role for three-tier backend EC2 instances to access Secrets Manager and CloudWatch"
```

**Capture the role ARN:**
```bash
BACKEND_ROLE_ARN=$(aws iam get-role \
    --role-name Veriqta-Backend-Role \
    --query 'Role.Arn' \
    --output text)

echo "BACKEND_ROLE_ARN: $BACKEND_ROLE_ARN"
```

### 4.5 Create the Permission Policy for the Backend Role

This policy grants exactly two permissions:
1. Read the specific database secret from Secrets Manager
2. Write CloudWatch logs for application monitoring

```bash
cat > backend-permission-policy.json << EOF
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "SecretsManagerReadOnly",
            "Effect": "Allow",
            "Action": [
                "secretsmanager:GetSecretValue"
            ],
            "Resource": "$SECRET_ARN"
        },
        {
            "Sid": "CloudWatchLogs",
            "Effect": "Allow",
            "Action": [
                "logs:CreateLogGroup",
                "logs:CreateLogStream",
                "logs:PutLogEvents",
                "logs:DescribeLogGroups",
                "logs:DescribeLogStreams"
            ],
            "Resource": "arn:aws:logs:*:*:log-group:/veriqta/backend/*:*"
        },
        {
            "Sid": "CloudWatchMetrics",
            "Effect": "Allow",
            "Action": [
                "cloudwatch:PutMetricData"
            ],
            "Resource": "*"
        },
        {
            "Sid": "SSMForSessionManager",
            "Effect": "Allow",
            "Action": [
                "ssm:UpdateInstanceInformation",
                "ssmmessages:CreateControlChannel",
                "ssmmessages:CreateDataChannel",
                "ssmmessages:OpenControlChannel",
                "ssmmessages:OpenDataChannel",
                "ec2messages:AcknowledgeMessage",
                "ec2messages:DeleteMessage",
                "ec2messages:FailMessage",
                "ec2messages:GetEndpoint",
                "ec2messages:GetMessages",
                "ec2messages:SendReply"
            ],
            "Resource": "*"
        }
    ]
}
EOF
```

**Attach the policy to the role:**
```bash
aws iam put-role-policy \
    --role-name Veriqta-Backend-Role \
    --policy-name Veriqta-Backend-Permissions \
    --policy-document file://backend-permission-policy.json
```

### 4.8 Verify Least-Privilege Separation

Test that the backend role CAN access the secret, but the frontend role CANNOT.

**Simulate backend role access:**
```bash
# This checks the policy simulation — does the role have permission?
aws iam simulate-principal-policy \
    --policy-source-arn $BACKEND_ROLE_ARN \
    --action-names secretsmanager:GetSecretValue \
    --resource-arns $SECRET_ARN \
    --query 'EvaluationResults[0].EvalDecision'
```

**Expected:** `allowed`

**Simulate frontend role access:**
```bash
aws iam simulate-principal-policy \
    --policy-source-arn $FRONTEND_ROLE_ARN \
    --action-names secretsmanager:GetSecretValue \
    --resource-arns $SECRET_ARN \
    --query 'EvaluationResults[0].EvalDecision'
```

**Expected:** `implicitDeny`

This proves that even if a frontend server is compromised, the attacker cannot retrieve database credentials because the frontend IAM role lacks `secretsmanager:GetSecretValue`.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Secret created without `dbname` field | Forgot to include it | Backend application fails to connect; "Unknown database" error |
| Backend role has `Resource: "*"` for Secrets Manager | Used wildcard instead of specific ARN | Backend can read ALL secrets in the account; privilege escalation |
| Frontend and backend share the same IAM role | Convenience | Frontend compromise exposes database credentials |
| No instance profile created | Forgot the separate step | EC2 instances cannot assume the role; Secrets Manager calls fail |
| Secret stored in plain text in user data | Did not complete Phase 4 | Password visible in CloudTrail, Launch Template, and EC2 user data logs |
| `secretsmanager:GetSecretValue` missing from backend policy | Typo in policy name | Backend cannot authenticate to database; connection timeout |

## 💡 INTERVIEW TIPS

**Q: Why use AWS Secrets Manager instead of environment variables or Parameter Store?**  
**A:** "Secrets Manager provides automatic rotation, fine-grained IAM access control, KMS encryption, and audit logging through CloudTrail. Environment variables are visible in process listings, container inspect output, and crash dumps. Systems Manager Parameter Store is cheaper but lacks automatic rotation and the granular secret versioning that Secrets Manager provides. For database credentials, Secrets Manager is the AWS-recommended approach because it integrates natively with RDS for automatic rotation."

**Q: How does the backend application retrieve the secret at runtime?**  
**A:** "The backend application uses the AWS SDK for JavaScript (or Python, Go, etc.) to call `secretsmanager:GetSecretValue` using the IAM role attached to the EC2 instance. The IAM instance profile provides temporary credentials through the Instance Metadata Service v2. The application parses the JSON response, extracts the username, password, host, and port, and constructs the database connection string dynamically at startup. No credential is ever written to disk, committed to Git, or embedded in user data."

**Q: What happens if someone compromises a frontend server?**  
**A:** "The frontend IAM role does not have `secretsmanager:GetSecretValue` permission. Even if an attacker gains root access to a frontend instance, they cannot retrieve database credentials through the AWS API because the instance's IAM role lacks that permission. The attacker would need to pivot to a backend instance or find an application vulnerability that allows arbitrary AWS API calls with the backend role. This is defense in depth — each tier's compromise does not automatically grant access to the next tier."

**Q: Why separate IAM roles for frontend and backend?**  
**A:** "This follows the principle of least privilege. The frontend serves static content and makes API calls — it needs no access to Secrets Manager, RDS, or internal data stores. The backend processes business logic and queries the database — it needs Secrets Manager read access and CloudWatch write access. By creating separate roles, we ensure that a compromise of the frontend tier does not grant permissions intended for the backend tier. In production, we extend this pattern to separate roles for each microservice."
