This phase creates the persistent data layer. You will build an Amazon RDS MySQL instance in the private database subnets with multi-AZ redundancy, automated backups, encryption at rest, and CloudWatch log exports. The database will be accessible only from the backend security group on port 3306.

RDS instances take **10 to 15 minutes** to provision. Use that time to read ahead.

### 3.2 Create the DB Subnet Group

RDS requires a DB Subnet Group that spans at least two Availability Zones. This tells RDS which subnets it may place database instances in.

```bash
aws rds create-db-subnet-group \
    --db-subnet-group-name veriqta-db-subnet-group \
    --db-subnet-group-description "Subnet group for three-tier RDS MySQL across two AZs" \
    --subnet-ids '["'$DB_SUBNET_1A'","'$DB_SUBNET_1B'"]' \
    --tags Key=Name,Value=veriqta-db-subnet-group Key=Project,Value=Veriqta-Three-Tier Key=Tier,Value=Database
```

**Capture the subnet group name for later use:**
```bash
DB_SUBNET_GROUP_NAME="veriqta-db-subnet-group"
echo "DB_SUBNET_GROUP_NAME: $DB_SUBNET_GROUP_NAME"
```

**Verify the subnet group:**
```bash
aws rds describe-db-subnet-groups \
    --db-subnet-group-name $DB_SUBNET_GROUP_NAME \
    --query 'DBSubnetGroups[*].{Name:DBSubnetGroupName,Status:SubnetGroupStatus,Subnets:Subnets[*].SubnetAvailabilityZone.Name}'
```

**Expected:** Status should be `Complete`, with subnets in `us-east-1a` and `us-east-1b`.

### 3.3 Create a Custom DB Parameter Group

The default parameter group cannot be modified. A custom parameter group allows you to enable query logging, tune performance settings, and enforce security configurations.

```bash
aws rds create-db-parameter-group \
    --db-parameter-group-name veriqta-mysql-params \
    --db-parameter-group-family mysql8.0 \
    --description "Custom parameter group for VERIQTA three-tier MySQL" \
    --tags Key=Name,Value=veriqta-mysql-params Key=Project,Value=Veriqta-Three-Tier Key=Tier,Value=Database
```

**Enable general query log and slow query log for troubleshooting:**
```bash
aws rds modify-db-parameter-group \
    --db-parameter-group-name veriqta-mysql-params \
    --parameters \
        ParameterName=general_log,ParameterValue=1,ApplyMethod=immediate \
        ParameterName=slow_query_log,ParameterValue=1,ApplyMethod=immediate \
        ParameterName=long_query_time,ParameterValue=2,ApplyMethod=immediate
```

**Verify the parameter group:**
```bash
aws rds describe-db-parameter-groups \
    --db-parameter-group-name veriqta-mysql-params \
    --query 'DBParameterGroups[*].[DBParameterGroupName,DBParameterGroupFamily]'
```

**Verify the parameters were set:**
```bash
aws rds describe-db-parameters \
    --db-parameter-group-name veriqta-mysql-params \
    --query 'Parameters[?ParameterName==`general_log` || ParameterName==`slow_query_log` || ParameterName==`long_query_time`].[ParameterName,ParameterValue,ApplyMethod]'
```

### 3.5 Create the RDS MySQL Instance

This command creates the database with production-grade settings. It will take 10–15 minutes to complete.

```bash
aws rds create-db-instance \
    --db-instance-identifier veriqta-mysql-db \
    --db-instance-class db.t3.micro \
    --engine mysql \
    --engine-version 8.0 \
    --allocated-storage 20 \
    --storage-type gp2 \
    --storage-encrypted \
    --master-username admin \
    --master-user-password "$MASTER_PASSWORD" \
    --vpc-security-group-ids $DB_SG_ID \
    --db-subnet-group-name $DB_SUBNET_GROUP_NAME \
    --db-parameter-group-name veriqta-mysql-params \
    --backup-retention-period 7 \
    --preferred-backup-window 03:00-04:00 \
    --multi-az \
    --publicly-accessible false \
    --deletion-protection true \
    --enable-cloudwatch-logs-exports '["error","general","slowquery"]' \
    --auto-minor-version-upgrade true \
    --tags Key=Name,Value=veriqta-mysql-db Key=Project,Value=Veriqta-Three-Tier Key=Tier,Value=Database
```

**Parameters explained:**

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `--db-instance-identifier` | `veriqta-mysql-db` | Unique name for this database instance |
| `--db-instance-class` | `db.t3.micro` | Smallest RDS instance; Free Tier eligible for 12 months |
| `--engine` | `mysql` | Amazon RDS for MySQL |
| `--engine-version` | `8.0` | MySQL 8.0 (latest stable major version) |
| `--allocated-storage` | `20` | 20 GB storage |
| `--storage-type` | `gp2` | General Purpose SSD |
| `--storage-encrypted` | Enabled | AES-256 encryption at rest using AWS KMS |
| `--master-username` | `admin` | Primary database user |
| `--master-user-password` | Generated password | Primary database password |
| `--vpc-security-group-ids` | `$DB_SG_ID` | Only allows traffic from Backend-SG and Bastion-SG |
| `--db-subnet-group-name` | `veriqta-db-subnet-group` | Places instance in private DB subnets |
| `--db-parameter-group-name` | `veriqta-mysql-params` | Custom logging and tuning settings |
| `--backup-retention-period` | `7` | Retains 7 days of automated backups |
| `--preferred-backup-window` | `03:00-04:00` | Daily backup during low-traffic hours |
| `--multi-az` | Enabled | Creates synchronous standby in second AZ for failover |
| `--publicly-accessible` | `false` | No public DNS or IP; accessible only within VPC |
| `--deletion-protection` | `true` | Prevents accidental deletion |
| `--enable-cloudwatch-logs-exports` | `error,general,slowquery` | Streams logs to CloudWatch for analysis |
| `--auto-minor-version-upgrade` | `true` | Automatically applies security patches |

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| DB Subnet Group in only one AZ | Used only `$DB_SUBNET_1A` | RDS creation fails with "DB Subnet Group doesn't meet availability zone coverage" |
| Default parameter group used | Did not create custom group | Cannot enable query logging or modify performance settings later |
| `publicly-accessible true` | Default in some Console wizards | Database gets a public IP and DNS; exposed to internet attacks |
| Weak master password | Used "password123" | RDS accepts it but application is insecure; brute-force risk |
| No backup retention | Set to 0 | Data loss if instance fails; no point-in-time recovery |
| `--multi-az` omitted | Cost concern | No automatic failover; AZ outage causes complete database downtime |
| Wrong security group | Used Frontend-SG or ALB-SG | Database accessible from unauthorized tiers; security breach |
| Deletion protection disabled | Forgot the flag | Accidental `delete-db-instance` destroys production data |
| Not waiting for `available` | Impatience | Subsequent phases fail; backend cannot connect; errors are cryptic |

## 💡 INTERVIEW TIPS

**Q: Why does RDS require a DB Subnet Group spanning two AZs?**  
**A:** "RDS uses the DB Subnet Group to determine where to place the primary instance and the standby replica in a Multi-AZ deployment. By requiring subnets in at least two AZs, AWS ensures that if the primary AZ fails, the standby can be promoted automatically without requiring a subnet in a new AZ. This is a fundamental availability requirement — a database in a single AZ is a single point of failure."

**Q: What is the difference between a DB Parameter Group and a DB Option Group?**  
**A:** "A DB Parameter Group controls engine-level configuration variables — things like `max_connections`, `innodb_buffer_pool_size`, and query logging flags. These are MySQL-specific settings. A DB Option Group is used for optional engine features like Oracle Application Express or SQL Server Transparent Data Encryption. For MySQL, parameter groups are the primary configuration mechanism, while option groups are rarely needed unless using specific plugins."

**Q: Why enable Multi-AZ on a learning project?**  
**A:** "Multi-AZ is not just about high availability — it also impacts maintenance windows and backup behavior. When AWS patches the operating system or underlying hardware, the standby is patched first, then a failover occurs, then the old primary is patched. This means zero-downtime maintenance. Without Multi-AZ, your database is unavailable during every patch cycle. In production, Multi-AZ is non-negotiable for any data-driven application."

**Q: How does RDS encryption at rest work?**  
**A:** "RDS encryption at rest uses AWS KMS to generate data keys that encrypt the underlying storage volumes, automated backups, read replicas, and snapshots. The encryption is transparent to the application — you connect using the same endpoint and credentials. The performance impact is negligible on modern instance classes. In production, encryption is often mandatory for compliance with SOC 2, PCI-DSS, and HIPAA. The key point is that encryption protects against physical media theft or unauthorized snapshot access."

**Q: What happens during an RDS Multi-AZ failover?**  
**A:** "When the primary instance fails — whether due to hardware failure, AZ outage, or manual reboot with failover — AWS automatically promotes the standby to become the new primary. The CNAME record for the database endpoint is updated to point to the new primary's IP address. This DNS update typically propagates within 60–120 seconds. The application must reconnect using the same endpoint name. The old primary is then rebuilt as the new standby. No data is lost because Multi-AZ uses synchronous replication."
