## WHAT YOU'LL BUILD

By the end of this project, you will have deployed a **production-grade three-tier web application** that separates presentation, application, and database concerns into isolated network layers. This is the architecture pattern used by banks, e-commerce platforms, healthcare systems, and enterprise SaaS products.

**The Three Tiers:**

| Tier | Technology | Responsibility | Network Location |
|------|-----------|----------------|------------------|
| **Presentation Tier** | Nginx + HTML/CSS/JS | Serves the user interface, static assets, and client-side code | Private subnets (no direct internet access) |
| **Application Tier** | Node.js + Express | Handles business logic, API endpoints, request validation, and database queries | Private subnets (no direct internet access) |
| **Database Tier** | Amazon RDS (MySQL) | Stores persistent data — user records, application state, transactional data | Private subnets (completely isolated — no internet at all) |

**What makes this "production-grade":**
- **Path-based routing** on the ALB: `your-domain.com/` serves the frontend, `your-domain.com/api/` serves the backend
- **Security group references between tiers:** The database only accepts traffic from the backend. The backend only accepts traffic from the frontend. The frontend only accepts traffic from the ALB.
- **Secrets Manager:** Database credentials are never hardcoded in code or user data scripts. They are retrieved at runtime via IAM-authenticated API calls.
- **No database internet exposure:** The RDS instance lives in subnets with no NAT Gateway route. It cannot reach the internet, and the internet cannot reach it.
- **Multi-AZ redundancy:** Every tier spans two Availability Zones.

**What this looks like when complete:**
You will open your ALB URL in a browser and see a styled web application. That page will load JavaScript that calls `https://your-domain.com/api/users`, the backend will authenticate to MySQL using Secrets Manager, query the database, and return JSON that the frontend renders into a table. All traffic is encrypted. All credentials are secret. All tiers are isolated.

## WHY THIS MATTERS

> *"I architected a three-tier application with a React frontend, Node.js API, and RDS database — each in isolated subnets with security group references between tiers and centralized credential management through AWS Secrets Manager."*

This is one of the most common interview architectures. Hiring managers ask about it because it proves you understand:
- **Separation of concerns:** Each tier does one job and does it well
- **Defense in depth:** Even if the frontend is compromised, the attacker cannot reach the database
- **Least privilege:** Each tier has exactly the network access it needs and nothing more
- **Secrets management:** You do not hardcode passwords in Git repositories or user data scripts

**Real-world equivalents:**
- A bank's online portal (web UI → API → core banking database)
- An e-commerce checkout flow (product page → cart API → order database)
- A healthcare patient portal (dashboard → records API → HIPAA-compliant database)

## COMPLETE PHASE ROADMAP

This project is divided into **11 phases**. Each phase builds on the previous. Do not skip phases.

| Phase | Topic | What You'll Have When Complete |
|-------|-------|-------------------------------|
| **Phase 0** | Prerequisites & Project Overview | Verified tools, AWS CLI configured, SSH key ready, understanding of the full architecture |

| **Phase 8** | Frontend Tier — Launch Template & ASG | An Nginx server serving HTML/JS that calls the backend API, deployed via Auto Scaling Group across 2 AZs |
| **Phase 9** | End-to-End Testing & Verification | Database seeded with data, frontend rendering API responses, path routing verified, auto-healing tested |
| **Phase 10** | DNS, SSL & Monitoring | Custom domain (optional), HTTPS termination, CloudWatch alarms for all tiers, operational dashboard |
| **Phase 11** | Cleanup | Complete resource destruction to stop all charges |

### 0.3 AWS Account Verification

**Step 1: Verify AWS CLI is installed and is version 2**

```bash
aws --version
```

**Expected output:** `aws-cli/2.x.x Python/3.x.x Linux/x86_64 ...`

If you see `aws-cli/1.x.x`, you must upgrade to version 2. Version 1 is in maintenance mode and lacks features required for this project.

**Step 2: Verify AWS CLI is configured**

```bash
aws sts get-caller-identity
```

**Expected output:**
```json
{
    "UserId": "AIDAXXXXXXXXXXXXXXXX",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/your-username"
}
```

If this fails with "Unable to locate credentials," run `aws configure` and enter your Access Key ID, Secret Access Key, region (`us-east-1`), and output format (`json`).

**Step 3: Verify you are NOT using the root account**

Look at the `Arn` field from the output above. If it contains `:root`, you are using the root account. **Stop.** Create an IAM user with programmatic access and use that instead. The root account has unrestricted access to billing and account deletion. Never use it for daily work.

**Step 4: Verify your region**

```bash
aws configure get region
```

**Expected:** `us-east-1`

This project uses `us-east-1` for consistency. If you prefer another region, you can use it, but some AMI IDs and service account IDs will differ. The commands assume `us-east-1`.

### 0.4 Create or Verify Your SSH Key Pair

You need an SSH key pair to access EC2 instances. If you completed Project 1, you may already have `veriqta-ha-webapp-key.pem`. You can reuse it. If not, create one now.

**Create a new key pair:**
```bash
aws ec2 create-key-pair \
    --key-name veriqta-three-tier-key \
    --key-type rsa \
    --key-format pem \
    --query 'KeyMaterial' \
    --output text > veriqta-three-tier-key.pem
```

**Secure the private key immediately:**
```bash
chmod 400 veriqta-three-tier-key.pem
```

> **CRITICAL:** If you lose this `.pem` file, you cannot recover it from AWS. You would need to create a new key pair and replace it on all instances. Store it in a password manager or secure location.

**Verify the key pair exists in AWS:**
```bash
aws ec2 describe-key-pairs --key-names veriqta-three-tier-key
```

### 0.5 Understand How Variables Work in This Project

Throughout this project, you will run commands that create resources and produce output. You will capture IDs, ARNs, and DNS names into **variables** (like `$VPC_ID`) so you can reference them in later commands.

**Example:**
```bash
VPC_ID=$(aws ec2 create-vpc --cidr-block 10.1.0.0/16 ... --query 'Vpc.VpcId' --output text)
echo "VPC_ID: $VPC_ID"
```

This stores the VPC ID in a variable called `VPC_ID`. Later, you can use `$VPC_ID` instead of typing the full ID.

**Important:** If you close your terminal and come back later, variables are lost. Every phase in this project includes a **"Lost a Variable?"** recovery box that shows you exactly how to look up any resource you created. Every resource is tagged with `Project=Veriqta-Three-Tier`, so you can always find it in the AWS Console or by running the recovery command.

## WHAT HAPPENS IN PHASE 1

You will create the **network foundation** for the three-tier architecture:
- A new VPC with CIDR `10.1.0.0/16`
- An Internet Gateway attached to the VPC
- **Eight subnets** across two Availability Zones:
  - 2 Public subnets (for ALB and Bastion)
  - 2 Frontend subnets (for Nginx presentation tier)
  - 2 Backend subnets (for Node.js application tier)
  - 2 Database subnets (for RDS — completely isolated)
- NAT Gateways in public subnets for frontend/backend outbound internet
- Route tables for each tier with precise routing rules

The database subnets will have **no route to the internet** — not even through a NAT Gateway. This is a deliberate security decision.
