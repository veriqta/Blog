## PHASE 1: VPC & NETWORKING FOUNDATION

Every resource you build in this project lives inside a VPC. This phase creates the network backbone: the VPC itself, eight subnets across two Availability Zones, an Internet Gateway, NAT Gateways, and route tables that enforce tier isolation.

The database subnets will have **no route to the internet whatsoever**. This is not an oversight — it is a deliberate security control. Your database cannot initiate outbound connections, and nothing on the internet can initiate inbound connections to your database.

---

### 1.1 Create the VPC

A VPC is an isolated network boundary within AWS. We use `10.1.0.0/16` to keep Project 2 separate from Project 1's `10.0.0.0/16`.

```bash
aws ec2 create-vpc \
    --cidr-block 10.1.0.0/16 \
    --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=veriqta-three-tier-vpc},{Key=Project,Value=Veriqta-Three-Tier},{Key=Environment,Value=Production}]' \
    --enable-dns-support \
    --enable-dns-hostnames
```

**Flags explained:**
- `--cidr-block 10.1.0.0/16`: The IP range for the entire VPC. This provides 65,536 IP addresses.
- `--enable-dns-support`: Allows instances to resolve hostnames to IP addresses within the VPC.
- `--enable-dns-hostnames`: Assigns public DNS hostnames to instances with public IPs.
- `--tag-specifications`: Tags for cost tracking, resource identification, and filtering.

**Capture the VPC ID:**

```bash
VPC_ID=$(aws ec2 describe-vpcs \
    --filters "Name=tag:Name,Values=veriqta-three-tier-vpc" \
    --query 'Vpcs[0].VpcId' \
    --output text)

echo "VPC_ID: $VPC_ID"
```

**Verify the VPC exists and is available:**
```bash
aws ec2 describe-vpcs --vpc-ids $VPC_ID \
    --query 'Vpcs[*].[VpcId,CidrBlock,State]'
```

**Expected output:**
```json
[
    ["vpc-xxxxxxxxxxxxxxxxx", "10.1.0.0/16", "available"]
]
```

> **🔍 LOST YOUR VPC_ID?** Recover it with:
> ```bash
> VPC_ID=$(aws ec2 describe-vpcs --filters "Name=tag:Name,Values=veriqta-three-tier-vpc" --query 'Vpcs[0].VpcId' --output text)
> ```

### 1.2 Create the Internet Gateway

The Internet Gateway (IGW) is the doorway from your VPC to the public internet. Only public subnets will route to it. Frontend, backend, and database subnets will never touch it directly.

```bash
aws ec2 create-internet-gateway \
    --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=veriqta-three-tier-igw},{Key=Project,Value=Veriqta-Three-Tier}]'
```

**Capture the IGW ID:**
```bash
IGW_ID=$(aws ec2 describe-internet-gateways \
    --filters "Name=tag:Name,Values=veriqta-three-tier-igw" \
    --query 'InternetGateways[0].InternetGatewayId' \
    --output text)

echo "IGW_ID: $IGW_ID"
```

**Attach the IGW to your VPC:**
```bash
aws ec2 attach-internet-gateway \
    --internet-gateway-id $IGW_ID \
    --vpc-id $VPC_ID
```

**Verify attachment:**
```bash
aws ec2 describe-internet-gateways --internet-gateway-ids $IGW_ID \
    --query 'InternetGateways[*].[InternetGatewayId,Attachments[0].VpcId,Attachments[0].State]'
```

**Expected:** The `Attachments[0].State` should be `available`.

> **🔍 LOST YOUR IGW_ID?** Recover it with:
> ```bash
> IGW_ID=$(aws ec2 describe-internet-gateways --filters "Name=tag:Name,Values=veriqta-three-tier-igw" --query 'InternetGateways[0].InternetGatewayId' --output text)
> ```

### 1.4 Enable Auto-Assign Public IP on Public Subnets Only

Public subnets need instances to automatically receive public IPs. Private subnets (frontend, backend, database) must never receive public IPs.


**Verify frontend, backend, and database subnets do NOT have public IPs:**

### 1.5 Create Route Tables

Each tier has its own route table. This is what enforces network isolation.

#### 1.5.1 Public Route Table

This route table sends all non-VPC traffic to the Internet Gateway.

```bash
aws ec2 create-route-table \
    --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=route-table,Tags=[{Key:Name,Value=veriqta-public-rt},{Key:Type,Value:Public},{Key:Project,Value:Veriqta-Three-Tier}]'
```

```bash
PUBLIC_RT_ID=$(aws ec2 describe-route-tables \
    --filters "Name=tag:Name,Values=veriqta-public-rt" \
    --query 'RouteTables[0].RouteTableId' \
    --output text)

echo "PUBLIC_RT_ID: $PUBLIC_RT_ID"
```

**Add the route to the Internet Gateway:**
```bash
aws ec2 create-route \
    --route-table-id $PUBLIC_RT_ID \
    --destination-cidr-block 0.0.0.0/0 \
    --gateway-id $IGW_ID
```

**Associate with public subnets:**
```bash
aws ec2 associate-route-table --route-table-id $PUBLIC_RT_ID --subnet-id $PUBLIC_SUBNET_1A
```

**Verify:**
```bash

    --query 'RouteTables[*].{ID:RouteTableId,Routes:Routes[*].[DestinationCidrBlock,GatewayId]}'
```

**Expected routes:**
- `10.1.0.0/16` → `local` (automatic)
- `0.0.0.0/0` → `igw-xxxxxxxxxxxxxxxxx`

### 1.6 Secure the Main Route Table

Every VPC has a default "main" route table. Ensure it does not have an internet route, so any accidentally unassociated subnet remains safe.

```bash
MAIN_RT_ID=$(aws ec2 describe-route-tables \
    --filters "Name=vpc-id,Values=$VPC_ID" \
    --query 'RouteTables[?Associations[?Main==`true`]].RouteTableId' \
    --output text)

echo "MAIN_RT_ID: $MAIN_RT_ID"
```

**Check its routes:**
```bash
aws ec2 describe-route-tables --route-table-ids $MAIN_RT_ID \
    --query 'RouteTables[*].Routes[*].[DestinationCidrBlock,GatewayId]'
```

**If it has a `0.0.0.0/0` route to the IGW, remove it:**
```bash
aws ec2 delete-route --route-table-id $MAIN_RT_ID --destination-cidr-block 0.0.0.0/0
```

This is a **defense-in-depth** measure. If a subnet is accidentally not associated with any route table, it falls back to the main route table. That subnet should not accidentally become public.

#### 1.7.3 Wait for NAT Gateways to Become Available

**Do not proceed until NAT Gateways show `available`.** Adding routes while they are `pending` black-holes traffic.

```bash

echo "NAT Gateways are ready."
```

**Verify:**
```bash
aws ec2 describe-nat-gateways --filter "Name=vpc-id,Values=$VPC_ID" \
    --query 'NatGateways[*].[NatGatewayId,SubnetId,State,NatGatewayAddresses[0].PublicIp]'
```

Both must show `"State": "available"`.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Database subnet has a NAT route | Copy-paste error from frontend RT | Database can reach internet; compliance violation; data exfiltration risk |
| Only 6 subnets created | Forgot database subnets | RDS requires DB subnet group spanning 2 AZs; RDS creation fails |
| Public IP auto-assign enabled on private subnets | Forgot to verify | Frontend/backend instances get public IPs; security model broken |
| NAT Gateway route added while `pending` | Impatience | Outbound traffic from private subnets is black-holed; yum/apt fails |
| CIDR overlap with Project 1 | Using `10.0.0.0/16` instead of `10.1.0.0/16` | Peering or VPN between projects fails; IP conflicts |
| Main route table has IGW route | Forgot to clean default | Unassociated subnets accidentally become public; security gap |
| Single NAT Gateway for production claim | Cost saving on learning project | Inability to say "I built multi-AZ NAT" in interviews; AZ dependency |

## 💡 INTERVIEW TIPS

**Q: Why do you create separate subnets for each tier?**  
**A:** "Subnet separation enforces network boundaries at the infrastructure level. Even if a security group is misconfigured, the database subnet's route table has no path to the internet. This is defense in depth — security controls at multiple layers. In production, we also use separate subnets for audit logging, management traffic, and third-party integrations, each with their own routing and access policies."

**Q: Why does the database subnet have no NAT Gateway route?**  
**A:** "The database contains the most sensitive data in the application. By giving it no route to the internet — not even outbound through a NAT Gateway — we eliminate several attack vectors. The database cannot download malicious software, exfiltrate data to external servers, or be reached by anything except the application tier on port 3306. If the database needs patches, we use RDS maintenance windows or snapshot-and-restore to a patched instance, rather than giving it internet access."

**Q: Why eight subnets instead of six?**  
**A:** "We need two subnets per tier to satisfy RDS requirements and achieve multi-AZ redundancy. RDS requires a DB subnet group with at least two subnets in different AZs. The ALB requires subnets in at least two AZs. By creating dedicated subnets for each tier — Public, Frontend, Backend, Database — we maintain clean separation and can apply tier-specific routing, ACLs, and monitoring. In a larger environment, we might use even more granular subnetting per application or environment."
