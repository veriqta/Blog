## PHASE 2: SECURITY FOUNDATION

Security Groups are stateful virtual firewalls attached to Elastic Network Interfaces. They control all traffic entering and leaving your instances. In a three-tier architecture, Security Groups are your primary enforcement mechanism for tier isolation.

This phase creates five security groups. Four of them form the traffic path from the internet to the database. The fifth provides administrative access. Every rule uses either a CIDR block (for internet-facing entry points) or a Security Group reference (for intra-VPC communication). Security Group references are dynamic — if an instance is replaced, the rule automatically applies to the new instance without any update.

### 2.3 Create the ALB Security Group

This security group is attached to the Application Load Balancer. It is the only security group that faces the public internet.

```bash
aws ec2 create-security-group \
    --group-name veriqta-alb-sg \
    --description "Security group for ALB - accepts HTTP/HTTPS from internet, forwards to frontend and backend" \
    --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=veriqta-alb-sg},{Key:Tier,Value:LoadBalancer},{Key:Project,Value:Veriqta-Three-Tier}]'
```

**Capture the Security Group ID:**
```bash
ALB_SG_ID=$(aws ec2 describe-security-groups \
    --filters "Name=group-name,Values=veriqta-alb-sg" \
    --query 'SecurityGroups[0].GroupId' \
    --output text)

echo "ALB_SG_ID: $ALB_SG_ID"
```

**Add inbound rules for HTTP and HTTPS:**
```bash
aws ec2 authorize-security-group-ingress \
    --group-id $ALB_SG_ID \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

aws ec2 authorize-security-group-ingress \
    --group-id $ALB_SG_ID \
    --protocol tcp \
    --port 443 \
    --cidr 0.0.0.0/0
```

**Remove the default "allow all" outbound rule:**
```bash
aws ec2 revoke-security-group-egress \
    --group-id $ALB_SG_ID \
    --protocol all \
    --port all \
    --cidr 0.0.0.0/0
```

**Add restricted outbound rules — ALB can only reach frontend and backend tiers:**
```bash
# ALB → Frontend on port 80
aws ec2 authorize-security-group-egress \
    --group-id $ALB_SG_ID \
    --protocol tcp \
    --port 80 \
    --source-group $ALB_SG_ID
```

Wait — that references itself. We need Frontend-SG to exist first. We will add this rule in Step 2.8 after all security groups are created.

For now, leave the ALB-SG outbound empty. We will return to it.

**Verify ALB-SG inbound:**
```bash

    --query 'SecurityGroups[*].{Name:GroupName,Inbound:IpPermissions}'
```

**Expected:**

This is the most restrictive security group. The database accepts only MySQL traffic from the backend tier and SSH from the bastion for emergency administrative access.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| DB-SG allows 3306 from `0.0.0.0/0` | Used CIDR instead of SG reference | Anyone on the internet can attempt MySQL connection; immediate security breach |
| Backend-SG has no outbound to DB-SG | Forgot Step 2.8 | Backend cannot initiate database connection; application fails with connection timeout |
| ALB-SG outbound left as "all traffic" | Did not revoke default | ALB can send traffic anywhere if compromised; unnecessary exposure |
| Bastion-SG allows `0.0.0.0/0` on 22 | Convenience or copy-paste | Brute-force SSH attacks within minutes; account compromise risk |
| Frontend-SG allows inbound from Backend-SG | Confused traffic direction | Frontend never initiates to backend; this rule serves no purpose and creates confusion |
| DB-SG has outbound rules added | Belief that RDS needs internet | Database can initiate outbound connections; data exfiltration vector |

## 💡 INTERVIEW TIPS

**Q: Why use Security Group references instead of CIDR blocks between tiers?**  
**A:** "Security Group references create dynamic, self-updating rules. When I reference the Backend-SG in my DB-SG, any EC2 instance attached to the Backend-SG automatically gains access to the database on port 3306. If the Auto Scaling Group replaces an instance, the new instance is covered immediately without any rule changes. CIDR blocks are static — they break when instances change IPs. In production, we use SG references for all intra-VPC communication because they adapt to infrastructure changes automatically."

**Q: Why does the database security group have no outbound rules?**  
**A:** "The database contains the most sensitive data in the application. By removing all outbound rules, we ensure the database cannot initiate any connection to the internet, to other VPCs, or to external APIs. It can only respond to queries that come in from the backend tier. This is a deliberate defense-in-depth measure. If the database were compromised — for example, through a SQL injection that gained OS-level access — the attacker still could not exfiltrate data over the network because the security group blocks all egress."

**Q: What happens if the ALB security group is too permissive outbound?**  
**A:** "If the ALB-SG allows all outbound traffic, a compromised ALB could theoretically send traffic to any instance in the VPC on any port. By restricting ALB outbound to only port 80 to Frontend-SG and port 3000 to Backend-SG, we limit the blast radius. Even if an attacker gains control of the ALB, they cannot use it to reach the database directly or scan internal networks on unauthorized ports."

**Q: Why allow SSH from the bastion to the database tier?**  
**A:** "In production, we prefer to use AWS Systems Manager Session Manager for database access and disable SSH entirely on RDS. However, for learning and troubleshooting, allowing SSH from the bastion to a database subnet provides a fallback path. The key controls are: first, the bastion itself is restricted to a single admin IP; second, the database is in an isolated subnet with no internet route; third, SSH access to RDS is typically through an EC2 jump box in the same subnet rather than direct RDS SSH, since RDS is managed by AWS. In this project, the 22 rule on DB-SG is primarily for defense-in-depth demonstration and for Session Manager proxying if needed."
