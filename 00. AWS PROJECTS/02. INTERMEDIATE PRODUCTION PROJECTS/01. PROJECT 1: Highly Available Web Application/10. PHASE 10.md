### 10.3 Validate the Certificate via DNS

ACM provides CNAME records that you must add to your Route 53 hosted zone. This proves you own the domain.

**Get the validation CNAME records:**
```bash
aws acm describe-certificate --certificate-arn $CERT_ARN \
    --query 'Certificate.DomainValidationOptions[*].{Domain:DomainName,Name:ResourceRecord.Name,Value:ResourceRecord.Value,Type:ResourceRecord.Type}'
```

**Expected output:**
```json
[
    {
        "Domain": "app.yourdomain.com",
        "Name": "_abc123def456.app.yourdomain.com",
        "Value": "_xyz789uvw012.acm-validations.aws",
        "Type": "CNAME"
    }
]
```

**Create the validation record in Route 53:**

```bash
cat > cert-validation.json << 'EOF'
{
    "Changes": [
        {
            "Action": "CREATE",
            "ResourceRecordSet": {
                "Name": "_VALIDATION_NAME_",
                "Type": "CNAME",
                "TTL": 300,
                "ResourceRecords": [
                    {"Value": "_VALIDATION_VALUE_"}
                ]
            }
        }
    ]
}
EOF
```

> **Replace `_VALIDATION_NAME_` and `_VALIDATION_VALUE_`** with the actual values from the `describe-certificate` output above. Then run:

```bash

    --hosted-zone-id $HOSTED_ZONE_ID \
```

### 10.7 Create CloudWatch Alarms

Set up proactive monitoring. You want to know about problems before your users do.

#### Alarm 1: High CPU Utilization

```bash
aws cloudwatch put-metric-alarm \
    --alarm-name veriqta-high-cpu-alarm \
    --alarm-description "CPU utilization above 70% for 5 minutes" \
    --metric-name CPUUtilization \
    --namespace AWS/EC2 \
    --statistic Average \
    --dimensions Name=AutoScalingGroupName,Value=veriqta-app-asg \
    --period 300 \
    --evaluation-periods 2 \
    --threshold 70 \
    --comparison-operator GreaterThanThreshold \
    --treat-missing-data missing \
    --alarm-actions $SNS_TOPIC_ARN
```

**What this does:**
- Evaluates average CPU every 5 minutes (`period 300`)
- Triggers if CPU > 70% for 2 consecutive periods (10 minutes total)
- Sends a notification to the SNS topic

#### Alarm 2: Unhealthy Target Count

```bash
aws cloudwatch put-metric-alarm \
    --alarm-name veriqta-unhealthy-targets-alarm \
    --alarm-description "Target group has unhealthy instances" \
    --metric-name UnHealthyHostCount \
    --namespace AWS/ApplicationELB \
    --statistic Average \
    --dimensions Name=TargetGroup,Value=$(echo $TG_ARN | awk -F/ '{print $NF}') \
    --period 60 \
    --evaluation-periods 2 \
    --threshold 1 \
    --comparison-operator GreaterThanOrEqualToThreshold \
    --treat-missing-data notBreaching \
    --alarm-actions $SNS_TOPIC_ARN
```

> **Note:** The TargetGroup dimension value is the **last part** of the Target Group ARN (the name, not the full ARN).

#### Alarm 3: Zero Healthy Targets (Critical)

```bash
aws cloudwatch put-metric-alarm \
    --alarm-name veriqta-zero-healthy-targets-alarm \

    --statistic Average \

    --period 60 \
    --evaluation-periods 2 \
    --threshold 1 \
    --comparison-operator LessThanThreshold \
    --treat-missing-data breaching \
    --alarm-actions $SNS_TOPIC_ARN
```

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Certificate stuck in `PENDING_VALIDATION` | Wrong CNAME record or DNS propagation delay | HTTPS listener cannot be created; users see certificate errors |
| HTTP listener deleted instead of modified | Used wrong ARN | Complete loss of HTTP traffic; no redirect to HTTPS |
| Alias record points to ALB DNS name as CNAME | Confusing Alias with CNAME | Route 53 charges for queries; root domain cannot use CNAME |
| Wrong ALB Zone ID in Alias record | Copy-paste error | DNS resolution fails intermittently |
| CloudWatch alarm on wrong dimension | Using full ARN instead of suffix | Alarm never triggers; silent failures |
| No `EvaluateTargetHealth` on Alias | Forgotten | Route 53 continues routing to failed ALB during outages |

## 💡 INTERVIEW TIPS

**Q: Why redirect HTTP to HTTPS instead of just blocking port 80?**  
**A:** "Users and bookmarks may still reference HTTP URLs. Blocking port 80 creates a poor user experience — the browser times out or shows a connection error. A 301 redirect preserves the user journey by seamlessly upgrading them to HTTPS. It also maintains SEO value, as search engines treat the redirect as a permanent move and consolidate link equity to the HTTPS version."

**Q: What's the difference between ACM certificates and certificates from traditional CAs?**  
**A:** "ACM certificates are free, automatically renew, and integrate natively with ALB, CloudFront, and API Gateway. Traditional CAs like DigiCert or Let's Encrypt require manual renewal and installation. ACM handles the entire lifecycle — request, validation, deployment, and renewal — without operational overhead. The trade-off is that ACM certificates can only be used on AWS services; you cannot export the private key for use on external servers."

**Q: Why use Route 53 Alias records instead of CNAME records?**  
**A:** "Alias records are AWS-specific and resolve at the DNS level without chargeable lookups. They can point to the zone apex — for example, `yourdomain.com` — which is impossible with CNAME records per RFC 1035. Alias records also integrate with health checks, allowing Route 53 to stop returning IPs for unhealthy endpoints. For AWS resources like ALB, CloudFront, and S3, Alias records are always the correct choice."

**Q: What is the significance of `ELBSecurityPolicy-TLS13-1-2-2021-06`?**  
**A:** "This is AWS's recommended TLS security policy that enforces TLS 1.2 and TLS 1.3 while disabling older, vulnerable protocols like TLS 1.0 and 1.1. It uses strong cipher suites and is compliant with modern security standards. In production, you should always use the latest recommended policy rather than legacy policies that support outdated protocols vulnerable to POODLE, BEAST, or other attacks."

**Q: Walk me through your most complex AWS project.**  
**A:** "I designed and deployed a highly available web application across two AWS Availability Zones. The architecture included a VPC with public and private subnets, NAT Gateways for secure outbound access, an Application Load Balancer with SSL termination, and an Auto Scaling Group that self-heals and scales based on CPU utilization. I implemented least-privilege IAM policies, enforced IMDSv2 on all instances, stored ALB access logs in an encrypted S3 bucket with lifecycle policies, and set up CloudWatch alarms for proactive monitoring. **Q: How would you improve this architecture for a production workload with 10,000 requests per second?**  
**A:** "First, I would move from t3.micro to compute-optimized instances like c6i.xlarge and enable burstable performance where needed. Second, I would add an ElastiCache Redis cluster in front of the application to reduce database load and improve response times. Third, I would implement a Web Application Firewall to protect against SQL injection and XSS. Fourth, I would use CloudFront as a CDN to cache static content at edge locations globally. Fifth, I would separate read and write traffic using RDS read replicas. Finally, I would implement blue/green deployments using CodeDeploy to eliminate downtime during releases."

**Q: What would happen if the NAT Gateway in AZ-a failed?**  
**A:** "Instances in private subnet 1a would lose outbound internet access — they could not download updates or call external APIs. However, inbound traffic from the ALB would continue to work because that flows through the ALB's internal network, not the NAT Gateway. The ASG would eventually detect that instances in AZ-a are unhealthy if the application depends on outbound connectivity, and it would launch replacements. To prevent this, some architectures use a single NAT Gateway with a backup route, but the best practice is to ensure the application can function without outbound internet or to use VPC endpoints for AWS services."
