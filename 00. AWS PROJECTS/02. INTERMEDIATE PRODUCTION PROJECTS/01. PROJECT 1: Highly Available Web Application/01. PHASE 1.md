## WHAT YOU'LL BUILD

By the end of this project, you will have deployed a **production-grade web application** that mirrors how real companies run services on AWS:

- **Survives Availability Zone failures** — if one data center goes down, traffic automatically routes to the other
- **Auto-scales based on demand** — handles traffic spikes without manual intervention, scales down to save costs
- **Runs in private subnets** — application servers are invisible to the internet; only the load balancer faces outward
- **Terminates SSL/TLS** — HTTPS encryption at the load balancer with a valid certificate
- **Logs every request** — access logs stored in S3 with lifecycle policies for cost optimization
- **Monitors health automatically** — CloudWatch alarms notify you when instances fail or CPU spikes
- **Uses Infrastructure as Code patterns** — even though we're using CLI commands, every decision follows IaC principles you'll apply with Terraform in Project 10

**What this looks like in practice:** You'll type a custom domain into your browser and see a live web application. Behind that simple page is a multi-AZ architecture with auto-healing, encrypted traffic, and audit logging.

### Component Reference Table

| Component | AWS Service | Purpose | Why This Matters |
|-----------|-------------|---------|------------------|
| **Network Isolation** | VPC + Subnets | Creates isolated network boundaries | Every production app lives in a VPC; public/private separation is a security non-negotiable |
| **Internet Access** | Internet Gateway | Allows public subnets to reach the internet | The ALB and NAT Gateways need this to communicate externally |
| **Outbound Security** | NAT Gateway | Allows private instances to reach internet for updates without exposure | Your servers can patch themselves; attackers cannot reach them |
| **Traffic Distribution** | Application Load Balancer | Distributes HTTP/HTTPS traffic across healthy instances | Survives instance failures; enables zero-downtime deployments |
| **Auto-Healing** | Auto Scaling Group | Maintains desired instance count across AZs | If an instance dies, it's replaced automatically within minutes |
| **Admin Access** | Bastion Host | Secure jump box for SSH into private instances | Required for troubleshooting; should be the ONLY entry point |
| **Firewall Rules** | Security Groups | Stateful virtual firewalls per instance | Least-privilege access — app servers only accept traffic from the ALB |
| **Identity** | IAM Role + Instance Profile | Gives EC2 instances permissions without hardcoded keys | No credentials to leak; AWS handles rotation automatically |
| **Audit Trail** | S3 + ALB Logs | Stores every HTTP request for analysis | Security incidents, performance debugging, compliance requirements |
| **DNS** | Route 53 | Maps your domain to the ALB | Users type `app.yourdomain.com`, not a long AWS DNS name |
| **Encryption** | ACM + HTTPS | SSL/TLS termination at the load balancer | Data in transit is encrypted; browsers show the green lock |

### 1.8 Create an SSH Key Pair

SSH key pairs use asymmetric cryptography. You keep the private key. AWS keeps the public key.

```bash
aws ec2 create-key-pair \
    --key-name veriqta-ha-webapp-key \
    --key-type rsa \
    --key-format pem \
    --query 'KeyMaterial' \
    --output text > veriqta-ha-webapp-key.pem
```

**Secure the private key immediately:**
```bash
chmod 400 veriqta-ha-webapp-key.pem
```

> **CRITICAL:** If you lose this `.pem` file, you cannot recover it from AWS. Store it in a password manager or secure vault.

**Verify:**
```bash
aws ec2 describe-key-pairs --key-names veriqta-ha-webapp-key
```

### 1.9 Create an IAM Role for EC2 Instances

EC2 instances need permissions (CloudWatch logging, S3 access) without hardcoded credentials. IAM Roles + Instance Profiles solve this.

**Create trust policy file:**
```bash
cat > ec2-trust-policy.json << 'EOF'
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": { "Service": "ec2.amazonaws.com" },
            "Action": "sts:AssumeRole"
        }
    ]
}
EOF
```

**Create the role:**
```bash
aws iam create-role \
    --role-name Veriqta-EC2-WebApp-Role \
    --assume-role-policy-document file://ec2-trust-policy.json \
    --description "IAM role for HA web application EC2 instances"
```

**Create permission policy:**
```bash
cat > ec2-permission-policy.json << 'EOF'
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "CloudWatchLogs",
            "Effect": "Allow",
            "Action": [
                "logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents",
                "logs:DescribeLogGroups", "logs:DescribeLogStreams"
            ],
            "Resource": "*"
        },
        {
            "Sid": "CloudWatchMetrics",
            "Effect": "Allow",
            "Action": [
                "cloudwatch:PutMetricData", "cloudwatch:GetMetricStatistics", "cloudwatch:ListMetrics"
            ],
            "Resource": "*"
        },
        {
            "Sid": "S3AccessForALBLogs",
            "Effect": "Allow",
            "Action": ["s3:PutObject", "s3:GetObject", "s3:ListBucket"],
            "Resource": [
                "arn:aws:s3:::veriqta-alb-logs-*",
                "arn:aws:s3:::veriqta-alb-logs-*/*"
            ]
        },
        {
            "Sid": "SSMForSessionManager",
            "Effect": "Allow",
            "Action": [
                "ssm:UpdateInstanceInformation",
                "ssmmessages:CreateControlChannel", "ssmmessages:CreateDataChannel",
                "ssmmessages:OpenControlChannel", "ssmmessages:OpenDataChannel",
                "ec2messages:AcknowledgeMessage", "ec2messages:DeleteMessage",
                "ec2messages:FailMessage", "ec2messages:GetEndpoint",
                "ec2messages:GetMessages", "ec2messages:SendReply"
            ],
            "Resource": "*"
        }

```

**Attach policy to role:**
```bash
aws iam put-role-policy \
    --role-name Veriqta-EC2-WebApp-Role \

    --policy-document file://ec2-permission-policy.json
```

**Create Instance Profile:**
```bash

aws iam add-role-to-instance-profile \
    --instance-profile-name Veriqta-EC2-WebApp-Profile \
```

**Verify:**


## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Using root account | Laziness | Full account compromise if credentials leak |
| Skipping least-privilege policy | "I'll do it later" | Never gets done; account remains over-permissioned |
| Not securing `.pem` file | Forgetting `chmod 400` | Anyone with file access can SSH into your servers |
| Losing the private key | No backup | Locked out of all EC2 instances; must rebuild |
| Using `us-east-1` blindly | Copying commands | Latency issues if your users are in other regions |

## 💡 INTERVIEW TIPS

**Q: Why is least-privilege important in AWS?**  
**A:** "Least-privilege limits the blast radius of compromised credentials. If an attacker gains access to an account with only EC2 and VPC permissions, they can't access billing, delete the account, or access sensitive data in other services. We implement this through custom IAM policies with explicit Allow statements and regular access reviews."

**Q: What's the difference between IAM Users and IAM Roles?**  
**A:** "IAM Users have long-lived credentials and are for people. IAM Roles have temporary credentials and are for services — EC2 instances, Lambda functions, or cross-account access. Roles use STS to generate tokens that expire automatically, so there are no keys to leak or rotate."

**Q: Why do we use Instance Profiles?**  
**A:** "An Instance Profile is the bridge between an IAM Role and an EC2 instance. You can't attach a role directly to EC2 — you attach an Instance Profile, which contains the role. When the instance boots, it assumes the role through the Instance Metadata Service and gets temporary credentials."
