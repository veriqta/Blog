## PHASE 4: BASTION HOST

The bastion host is your only entry point into private subnets. It sits in a public subnet, accepts SSH from your IP only, and allows you to hop into application servers that have no public internet exposure.

In modern AWS environments, AWS Systems Manager Session Manager has largely replaced traditional bastion hosts. However, understanding the traditional bastion is non-negotiable for legacy systems, compliance environments, and interview scenarios. This phase covers both approaches.

---

### 4.1 Identify the Latest Amazon Linux 2023 AMI

Amazon Linux 2023 is AWS's modern, security-focused operating system. It comes pre-installed with the Systems Manager agent, CloudWatch agent, and receives frequent security updates.

```bash
AMI_ID=$(aws ssm get-parameters \
    --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
    --query 'Parameters[0].Value' \
    --output text)

echo "AMI_ID: $AMI_ID"
```

---

### 4.2 Launch the Bastion Host

```bash
aws ec2 run-instances \
    --image-id $AMI_ID \
    --instance-type t3.micro \
    --key-name veriqta-ha-webapp-key \
    --subnet-id $PUBLIC_SUBNET_1A \
    --security-group-ids $BASTION_SG_ID \
    --iam-instance-profile Name=Veriqta-EC2-WebApp-Profile \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=veriqta-bastion},{Key:Tier,Value:Bastion},{Key:Project,Value:Veriqta-HA-WebApp}]' \
    --metadata-options '{"HttpTokens":"required","HttpPutResponseHopLimit":1,"HttpEndpoint":"enabled"}' \
    --count 1
```

**Critical flags explained:**
- `--iam-instance-profile`: Attaches the IAM role so the bastion can use Session Manager and CloudWatch.
- `--metadata-options '{"HttpTokens":"required"}'`: **Enforces IMDSv2.** This blocks IMDSv1, which is vulnerable to Server-Side Request Forgery (SSRF) attacks. A `t3.micro` with IMDSv2 enforced is the production standard.

**Capture the Instance ID and Public IP:**
```bash
BASTION_ID=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=veriqta-bastion" \
    --query 'Reservations[0].Instances[0].InstanceId' \
    --output text)

BASTION_IP=$(aws ec2 describe-instances \
    --instance-ids $BASTION_ID \
    --query 'Reservations[0].Instances[0].PublicIpAddress' \
    --output text)

echo "BASTION_ID: $BASTION_ID"
echo "BASTION_IP: $BASTION_IP"
```

**Wait for the instance to reach the `running` state:**
```bash
aws ec2 wait instance-running --instance-ids $BASTION_ID
echo "Bastion is running."
```

---

### 4.3 Harden the Bastion Host

SSH into the bastion and apply production hardening.

```bash
ssh -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
```

**Run these commands on the bastion:**

```bash
# Update all packages to latest security patches
sudo dnf update -y

# Install fail2ban to block brute-force SSH attempts
sudo dnf install -y fail2ban

# Configure fail2ban
sudo tee /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/secure
maxretry = 3
bantime = 3600
findtime = 600
EOF

sudo systemctl enable fail2ban
sudo systemctl start fail2ban

# Verify fail2ban is active
sudo fail2ban-client status sshd

# Disable password authentication — force key-based auth only
sudo sed -i 's/#PasswordAuthentication yes/PasswordAuthentication no/g' /etc/ssh/sshd_config
sudo sed -i 's/PasswordAuthentication yes/PasswordAuthentication no/g' /etc/ssh/sshd_config
sudo sed -i 's/#PermitRootLogin yes/PermitRootLogin no/g' /etc/ssh/sshd_config
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/g' /etc/ssh/sshd_config

# Restart SSH daemon to apply changes
sudo systemctl restart sshd

# Enable automatic security updates
sudo dnf install -y dnf-automatic
sudo systemctl enable --now dnf-automatic.timer
```

**Exit the bastion:**
```bash
exit
```

### 4.4 Verify IMDSv2 Enforcement

IMDSv2 requires a session token for all metadata requests. IMDSv1 requests without a token must fail.

```bash
ssh -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
```

**Test IMDSv1 (must fail):**
```bash
curl -s -o /dev/null -w "%{http_code}" http://169.254.169.254/latest/meta-data/iam/info
```
**Expected output:** `401`

**Test IMDSv2 (must succeed):**
```bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/info
```
**Expected output:** JSON containing the IAM role name.

```bash
exit
```

### 4.5 SSH Agent Forwarding

Your private key lives on your local machine. You need to access private instances through the bastion without copying the key to the bastion.

**Start the SSH agent on your local machine:**

```bash
# macOS
eval "$(ssh-agent -s)"
ssh-add -K veriqta-ha-webapp-key.pem

# Linux
eval "$(ssh-agent -s)"
ssh-add veriqta-ha-webapp-key.pem
```

**Connect with agent forwarding enabled:**
```bash
ssh -A -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
```

The `-A` flag forwards your local SSH agent to the bastion. From the bastion, you can now SSH to any private instance that trusts your key, without the private key ever touching the bastion's disk.

**Test from the bastion (no private instances yet, but verify the agent works):**
```bash
# On the bastion
ssh-add -l
# Should list your key fingerprint
```

```bash
exit
```

> **Security note:** Agent forwarding can be risky on untrusted bastions. In production, prefer Session Manager or a dedicated VPN. For this project, agent forwarding is acceptable because the bastion is hardened and single-purpose.

### 4.6 AWS Systems Manager Session Manager

Session Manager provides shell access to EC2 instances without opening port 22, without SSH keys, and without a public IP. It uses the AWS Systems Manager agent and IAM permissions.

**Verify the SSM agent is running:**
```bash
ssh -i veriqta-ha-webapp-key.pem ec2-user@$BASTION_IP
sudo systemctl status amazon-ssm-agent
```
**Expected:** `active (running)`

```bash
exit
```

**Connect via Session Manager from your local machine:**

First, install the Session Manager plugin if you haven't already:
- **macOS:** `brew install --cask session-manager-plugin`
- **Linux:** Follow the [official AWS installation guide](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html)
- **Windows:** Download the MSI installer from AWS

**Connect:**
```bash
aws ssm start-session --target $BASTION_ID
```

**Expected:**
```
Starting session with SessionId: your-session-id
sh-5.2$
```

Type `exit` to close the session.

---

### 4.7 Configure SSH Config for Session Manager

Add this to your local `~/.ssh/config` file to use standard SSH syntax with Session Manager:

```bash
mkdir -p ~/.ssh
cat >> ~/.ssh/config << 'EOF'

# AWS Session Manager Proxy
Host i-* mi-*
    ProxyCommand sh -c "aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters 'portNumber=%p'"
    User ec2-user
    IdentityFile ~/.ssh/veriqta-ha-webapp-key.pem
    StrictHostKeyChecking accept-new
EOF
```

Now you can connect using standard SSH:
```bash
ssh $BASTION_ID
```

### 4.8 Enable Session Logging to CloudWatch

For audit compliance, all Session Manager sessions should be logged.

**Create a CloudWatch Log Group:**
```bash
aws logs create-log-group \
    --log-group-name /veriqta/session-manager-logs \
    --tags Project=Veriqta-HA-WebApp,Tier=Security

aws logs put-retention-policy \
    --log-group-name /veriqta/session-manager-logs \
    --retention-in-days 30
```

> **Note:** Full Session Manager logging configuration requires an SSM Document update or AWS Console configuration. The log group is created here for when you enable it via the console or advanced CLI later.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| IMDSv1 enabled | Forgot `--metadata-options` | SSRF vulnerabilities allow credential theft from metadata service |
| Private key copied to bastion | Convenience | If bastion is compromised, attacker has your key to all instances |
| Bastion left running 24/7 | Forgot to stop | ~$7.50/month wasted; unnecessary attack surface |
| No fail2ban | Didn't harden | Brute-force SSH attacks succeed against weak passwords |
| Session Manager plugin not installed | Skipped step | Cannot use modern, port-less access method |

## 💡 INTERVIEW TIPS

**Q: How do you access instances in private subnets?**  
**A:** "We use a hardened bastion host in a public subnet with security group rules restricting SSH to specific admin IPs. For modern environments, we prefer AWS Systems Manager Session Manager, which requires no open ports, no SSH keys, and provides full audit logging through CloudTrail. Session Manager also integrates with IAM, so access is controlled through policies rather than key distribution."

**Q: What is IMDSv2 and why is it important?**  
**A:** "IMDSv2 is the Instance Metadata Service version 2, which requires a session token for all metadata requests. IMDSv1 had no authentication, making it vulnerable to SSRF attacks where a malicious web application could request instance credentials from `169.254.169.254`. IMDSv2 blocks this by requiring a PUT request to obtain a token before any metadata access. Enforcing IMDSv2 is now a standard security control."

**Q: Why not just put all instances in public subnets?**  
**A:** "Public subnets expose instances directly to the internet. Every open port is an attack surface. By placing application servers in private subnets, we ensure they are unreachable from the internet even if a security group is misconfigured. The load balancer becomes the single, controlled entry point. This is defense in depth — if one layer fails, others still protect the workload."
