## PHASE 5: APPLICATION LOAD BALANCER

The Application Load Balancer (ALB) is the front door of your application. It receives all incoming HTTP and HTTPS traffic, performs health checks on backend instances, and routes requests only to targets that are healthy. If an entire Availability Zone fails, the ALB automatically redirects traffic to the surviving zone.

This is a Layer 7 load balancer. It understands HTTP headers, URL paths, query strings, and hostnames. It terminates SSL/TLS encryption so your backend instances do not need to handle certificate management.

---

### 5.1 Create the Application Load Balancer

```bash
aws elbv2 create-load-balancer \
    --name veriqta-ha-alb \
    --subnets $PUBLIC_SUBNET_1A $PUBLIC_SUBNET_1B \
    --security-groups $ALB_SG_ID \
    --scheme internet-facing \
    --type application \
    --ip-address-type ipv4 \
    --tags Key=Name,Value=veriqta-ha-alb Key=Project,Value=Veriqta-HA-WebApp Key=Tier,Value=LoadBalancer
```

**Flags explained:**
- `--name`: DNS-friendly name. Maximum 32 characters. Must be unique within the region.
- `--subnets`: Must span at least two AZs for high availability. AWS requires this for internet-facing ALBs.
- `--security-groups`: The ALB-SG created in Phase 3. Allows ports 80 and 443 from the internet.
- `--scheme internet-facing`: Accessible from the internet. Use `internal` for private-facing ALBs inside a corporate network.
- `--type application`: Layer 7 HTTP/HTTPS load balancer. Alternative is `network` for Layer 4 TCP/UDP traffic.
- `--ip-address-type ipv4`: Standard IPv4 addressing. Use `dualstack` if you need IPv6 support.

**Capture the ALB ARN and DNS name:**
```bash
ALB_ARN=$(aws elbv2 describe-load-balancers \
    --names veriqta-ha-alb \
    --query 'LoadBalancers[0].LoadBalancerArn' \
    --output text)

ALB_DNS=$(aws elbv2 describe-load-balancers \
    --names veriqta-ha-alb \
    --query 'LoadBalancers[0].DNSName' \
    --output text)

ALB_ZONE_ID=$(aws elbv2 describe-load-balancers \
    --names veriqta-ha-alb \
    --query 'LoadBalancers[0].CanonicalHostedZoneId' \
    --output text)

echo "ALB_ARN: $ALB_ARN"
echo "ALB_DNS: $ALB_DNS"
echo "ALB_ZONE_ID: $ALB_ZONE_ID"
```

**Wait for the ALB to become active:**
```bash
echo "Waiting for ALB to become active..."
aws elbv2 wait load-balancer-available --load-balancer-arns $ALB_ARN
echo "ALB is active."
```

**Verify:**
```bash

    --query 'LoadBalancers[*].{Name:LoadBalancerName,DNS:DNSName,State:State.Code,Type:Type,Scheme:Scheme,AZs:AvailabilityZones[*].ZoneName}'
```

**Expected output:**

### 5.2 Create the Target Group

The Target Group is where the ALB sends traffic. It contains your EC2 instances and performs health checks to ensure only healthy instances receive requests.

```bash
aws elbv2 create-target-group \
    --name veriqta-app-tg \
    --protocol HTTP \
    --port 80 \
    --vpc-id $VPC_ID \
    --health-check-protocol HTTP \
    --health-check-path /health \
    --health-check-port traffic-port \
    --healthy-threshold-count 2 \
    --unhealthy-threshold-count 3 \
    --health-check-timeout-seconds 5 \
    --health-check-interval-seconds 30 \
    --matcher HttpCode=200 \
    --target-type instance \
    --tags Key=Name,Value=veriqta-app-tg Key=Project,Value=Veriqta-HA-WebApp
```

**Health check parameters explained:**

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `--health-check-path /health` | `/health` | The ALB sends HTTP GET requests to this path. Your application must respond with HTTP 200 on this endpoint. |
| `--healthy-threshold-count 2` | 2 checks | An instance is marked healthy after 2 consecutive successful checks. |
| `--unhealthy-threshold-count 3` | 3 checks | An instance is marked unhealthy after 3 consecutive failures. |
| `--health-check-timeout-seconds 5` | 5 seconds | If no response in 5 seconds, the check fails. |
| `--health-check-interval-seconds 30` | 30 seconds | Time between health checks. |
| `--matcher HttpCode=200` | HTTP 200 | Only HTTP 200 counts as healthy. |

> **Important:** Your application must expose a `/health` endpoint that returns HTTP 200 when the application is ready to serve traffic. If the application is starting up, under heavy load, or dependent services are down, it should return a non-200 status. We will implement this endpoint in Phase 9.

**Capture the Target Group ARN:**
```bash
TG_ARN=$(aws elbv2 describe-target-groups \
    --names veriqta-app-tg \
    --query 'TargetGroups[0].TargetGroupArn' \
    --output text)

echo "TG_ARN: $TG_ARN"
```

**Verify:**
```bash
aws elbv2 describe-target-groups --target-group-arns $TG_ARN \
    --query 'TargetGroups[*].{Name:TargetGroupName,Protocol:Protocol,Port:Port,HealthCheckPath:HealthCheckPath,HealthCheckProtocol:HealthCheckProtocol}'
```

### 5.3 Create the HTTP Listener

The Listener defines the port and protocol the ALB listens on, and what action to take with incoming requests.

```bash
aws elbv2 create-listener \
    --load-balancer-arn $ALB_ARN \
    --protocol HTTP \
    --port 80 \
    --default-actions Type=forward,TargetGroupArn=$TG_ARN \
    --tags Key=Name,Value=veriqta-http-listener Key=Project,Value=Veriqta-HA-WebApp
```

**Capture the Listener ARN:**
```bash
LISTENER_ARN=$(aws elbv2 describe-listeners \
    --load-balancer-arn $ALB_ARN \
    --query 'Listeners[?Port==`80`].ListenerArn' \
    --output text)

echo "LISTENER_ARN: $LISTENER_ARN"
```

**Verify:**
```bash
aws elbv2 describe-listeners --listener-arns $LISTENER_ARN \
    --query 'Listeners[*].{Protocol:Protocol,Port:Port,Action:DefaultActions[0].Type,TargetGroup:DefaultActions[0].TargetGroupArn}'
```

### 5.4 Test the ALB (Expect 503 — This Is Correct)

Right now, the ALB has no registered targets. Verify it responds correctly:

```bash
curl -I http://$ALB_DNS
```

**Expected response:**
```
HTTP/1.1 503 Service Unavailable
```

**Why 503?** The ALB is operational, but there are no healthy targets in the target group. A `503` from an ALB with no targets confirms:
- The ALB DNS resolves correctly
- The security group allows traffic on port 80
- The listener is configured and forwarding
- The target group exists

Once instances are registered and healthy, this will return `200 OK`.

**Verify DNS resolution:**
```bash
nslookup $ALB_DNS
```

You should see multiple IP addresses — one per AZ. This is the ALB's multi-AZ nature in action.

### 5.5 Configure ALB Attributes

**Enable deletion protection:**
```bash
aws elbv2 modify-load-balancer-attributes \
    --load-balancer-arn $ALB_ARN \
    --attributes Key=deletion_protection.enabled,Value=true
```

> **Note:** When you clean up this project, you must disable deletion protection before you can delete the ALB.

**Enable HTTP/2:**
```bash
aws elbv2 modify-load-balancer-attributes \
    --load-balancer-arn $ALB_ARN \
    --attributes Key=routing.http2.enabled,Value=true
```

**Configure idle timeout:**
```bash
aws elbv2 modify-load-balancer-attributes \
    --load-balancer-arn $ALB_ARN \
    --attributes Key=idle_timeout.timeout_seconds,Value=60
```

**Verify all attributes:**
```bash
aws elbv2 describe-load-balancer-attributes --load-balancer-arn $ALB_ARN \
    --query 'Attributes[*].[Key,Value]'
```

### 5.6 ALB Pricing Awareness

| Component | Cost (us-east-1) |
|-----------|-----------------|
| ALB per hour | $0.0225 (~$16.43/month) |
| LCU (Load Balancer Capacity Unit) per hour | $0.008 |
| Data processed | Included in LCU calculation |

**What is an LCU?**
LCU measures four dimensions, and you are billed for the highest one:
1. **New connections per second**
2. **Active connections** (concurrent)
3. **Processed bytes** (GB per hour)
4. **Rule evaluations** (per second)

For a typical learning project, you will not exceed the minimum 1 LCU. Total ALB cost: approximately **$16–25 per month**.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| ALB in private subnets | Wrong subnet IDs | ALB is not accessible from the internet; users cannot reach your application |
| Target group in wrong VPC | Copying from another project | Targets cannot be registered; health checks fail permanently |
| Health check path returns 404 | Application lacks `/health` endpoint | ALB marks all instances unhealthy; traffic is not routed |
| Listener on wrong port | Typo | Users connect on port 80 but ALB listens on port 8080; connection refused |
| No deletion protection | Default is disabled | Accidental deletion destroys the entry point to your application |
| Forgetting to wait for `active` state | Impatience | Subsequent commands fail because the ALB is still provisioning |

## 💡 INTERVIEW TIPS

**Q: What is the difference between an ALB and an NLB?**  
**A:** "The Application Load Balancer operates at Layer 7 of the OSI model. It understands HTTP, HTTPS, WebSocket, and gRPC. It can route based on URL paths, host headers, query strings, and HTTP methods. It also terminates SSL/TLS encryption. The Network Load Balancer operates at Layer 4, handling TCP and UDP traffic with extreme performance — millions of requests per second with ultra-low latency. NLB is used for gaming, IoT, and high-frequency trading. ALB is used for web applications and APIs."

**Q: Why does the ALB return 503 when there are no targets?**  
**A:** "A 503 Service Unavailable from an ALB specifically means there are no healthy targets available to handle the request. This is expected behavior during initial setup or when all backend instances fail health checks. It confirms the ALB itself is operational — DNS resolves, the listener is active, and the security group allows traffic. The issue is at the target layer, not the load balancer layer. This distinction is critical for troubleshooting."

**Q: What happens if all instances in one AZ fail health checks?**  
**A:** "The ALB automatically stops routing traffic to the failed AZ and directs 100 percent of traffic to the healthy AZ. Because we configured the ALB with subnets in two AZs, the application remains available even during a complete Availability Zone failure. This is the core of high availability — eliminating single points of failure at the infrastructure level."

**Q: Why do we use a `/health` endpoint instead of just checking if the instance is running?**  
**A:** "An EC2 instance can be running but the application on it can be unhealthy — for example, if the database connection pool is exhausted, the application is in a crash loop, or a dependency is down. The ALB health check verifies application-layer health, not just infrastructure-layer health. A good health check endpoint validates critical dependencies and returns 200 only when the application is truly ready to serve traffic. This prevents the ALB from sending requests to instances that will fail them."
