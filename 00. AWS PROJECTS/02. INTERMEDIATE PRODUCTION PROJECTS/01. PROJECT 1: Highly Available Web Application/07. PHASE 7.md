## PHASE 7: LAUNCH TEMPLATE

The Launch Template is the blueprint for every EC2 instance your Auto Scaling Group creates. It defines the operating system, instance size, security group, IAM role, user data script, and metadata options. Once created, the Auto Scaling Group references this template to launch identical instances across Availability Zones automatically.

**Launch Templates replaced Launch Configurations** in 2017. They support versioning, multiple instance types, Spot Instances, and mixed instance policies. In modern AWS, you should never use Launch Configurations.

### 7.1 Write the User Data Script

User data is a script that runs on first boot. It installs software, configures the application, and starts services. This script must be idempotent — running it multiple times should not break the system.

Create the user data script locally:

```bash
cat > user-data.sh << 'EOF'
#!/bin/bash
set -euo pipefail

# Redirect all output to a log file for debugging
exec > >(tee /var/log/user-data.log) 2>&1

echo "=== Starting user data script at $(date) ==="

# Update system packages
dnf update -y

# Install Nginx and required tools
dnf install -y nginx aws-cli jq

# Create the web application directory
mkdir -p /var/www/html

# Create a health check endpoint
cat > /var/www/html/health << 'HEALTH'
HTTP/1.1 200 OK
Content-Type: text/plain

healthy
HEALTH

# Create the main application page with instance metadata
INSTANCE_ID=$(curl -s -H "X-aws-ec2-metadata-token: $(curl -s -X PUT 'http://169.254.169.254/latest/api/token' -H 'X-aws-ec2-metadata-token-ttl-seconds: 21600')" http://169.254.169.254/latest/meta-data/instance-id)
AVAILABILITY_ZONE=$(curl -s -H "X-aws-ec2-metadata-token: $(curl -s -X PUT 'http://169.254.169.254/latest/api/token' -H 'X-aws-ec2-metadata-token-ttl-seconds: 21600')" http://169.254.169.254/latest/meta-data/placement/availability-zone)
PRIVATE_IP=$(curl -s -H "X-aws-ec2-metadata-token: $(curl -s -X PUT 'http://169.254.169.254/latest/api/token' -H 'X-aws-ec2-metadata-token-ttl-seconds: 21600')" http://169.254.169.254/latest/meta-data/local-ipv4)

cat > /var/www/html/index.html << HTML
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>VERIQTA - Highly Available Web Application</title>
    <style>
        body {
            font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, Oxygen, Ubuntu, Cantarell, sans-serif;
            max-width: 800px;
            margin: 50px auto;
            padding: 0 20px;
            background: linear-gradient(135deg, #667eea 0%, #764ba2 100%);
            color: white;
            min-height: 100vh;
        }
        .container {
            background: rgba(255,255,255,0.1);
            backdrop-filter: blur(10px);
            border-radius: 20px;
            padding: 40px;
            box-shadow: 0 8px 32px rgba(0,0,0,0.2);
        }
        h1 { font-size: 2.5em; margin-bottom: 10px; }
        .meta { 
            background: rgba(0,0,0,0.2); 
            padding: 20px; 
            border-radius: 10px; 
            margin-top: 30px;
            font-family: 'Courier New', monospace;
        }
        .meta p { margin: 8px 0; }
        .badge {
            display: inline-block;
            background: #00d084;
            color: #000;
            padding: 5px 15px;
            border-radius: 20px;
            font-weight: bold;
            font-size: 0.9em;
        }
    </style>
</head>
<body>
    <div class="container">
        <span class="badge">PRODUCTION DEPLOYMENT</span>
        <h1>VERIQTA HA Web Application</h1>
        <p>This application is running on a highly available, auto-scaling infrastructure across multiple AWS Availability Zones.</p>
        
        <div class="meta">
            <p><strong>Instance ID:</strong> $INSTANCE_ID</p>
            <p><strong>Availability Zone:</strong> $AVAILABILITY_ZONE</p>
            <p><strong>Private IP:</strong> $PRIVATE_IP</p>
            <p><strong>Server Time:</strong> $(date)</p>
        </div>
    </div>
</body>
</html>
HTML

# Configure Nginx
cat > /etc/nginx/nginx.conf << 'NGINX'
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log notice;
pid /run/nginx.pid;

events {
    worker_connections 1024;
}

http {
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';

    access_log /var/log/nginx/access.log main;

    sendfile            on;
    tcp_nopush          on;
    keepalive_timeout   65;
    types_hash_max_size 4096;

    include             /etc/nginx/mime.types;
    default_type        application/octet-stream;

    server {
        listen       80;
        listen       [::]:80;
        server_name  _;
        root         /var/www/html;

        location / {
            try_files $uri $uri/ =404;
        }

        location /health {
            access_log off;
            return 200 "healthy\n";
            add_header Content-Type text/plain;
        }

        error_page 404 /404.html;
        error_page 500 502 503 504 /50x.html;
    }
}
NGINX

# Set proper permissions
chown -R nginx:nginx /var/www/html
chmod 644 /var/www/html/*

# Start and enable Nginx
systemctl enable nginx
systemctl start nginx

# Verify Nginx is running
if systemctl is-active --quiet nginx; then
    echo "=== Nginx started successfully ==="
else
    echo "=== ERROR: Nginx failed to start ==="
    exit 1
fi

# Signal CloudWatch that user data completed successfully
echo "=== User data script completed at $(date) ==="
EOF
```

**What this script does:**
- Updates all system packages
- Installs Nginx, AWS CLI, and jq
- Creates a `/health` endpoint that returns HTTP 200 (required by the ALB health check)
- Creates a branded HTML page displaying instance metadata (ID, AZ, private IP)
- Configures Nginx with proper logging and a dedicated health check location
- Uses IMDSv2 to fetch instance metadata securely
- Starts and enables Nginx as a system service

### 7.2 Create the Launch Template

```bash
aws ec2 create-launch-template \
    --launch-template-name veriqta-app-launch-template \
    --version-description "Initial version for HA web application" \
    --launch-template-data '{
        "ImageId": "'$AMI_ID'",
        "InstanceType": "t3.micro",
        "KeyName": "veriqta-ha-webapp-key",
        "SecurityGroupIds": ["'$APP_SG_ID'"],
        "IamInstanceProfile": {"Name": "Veriqta-EC2-WebApp-Profile"},
        "UserData": "'$(base64 -w 0 user-data.sh)'",
        "MetadataOptions": {
            "HttpTokens": "required",
            "HttpPutResponseHopLimit": 1,
            "HttpEndpoint": "enabled"
        },
        "TagSpecifications": [
            {
                "ResourceType": "instance",
                "Tags": [
                    {"Key": "Name", "Value": "veriqta-app-server"},
                    {"Key": "Project", "Value": "Veriqta-HA-WebApp"},
                    {"Key": "Tier", "Value": "Application"},
                    {"Key": "Environment", "Value": "Production"}
                ]
            },
            {
                "ResourceType": "volume",
                "Tags": [
                    {"Key": "Name", "Value": "veriqta-app-volume"},
                    {"Key": "Project", "Value": "Veriqta-HA-WebApp"},
                    {"Key": "Tier", "Value": "Application"}
                ]
            }
        ],
        "BlockDeviceMappings": [
            {
                "DeviceName": "/dev/xvda",
                "Ebs": {
                    "VolumeSize": 20,
                    "VolumeType": "gp3",
                    "DeleteOnTermination": true,
                    "Encrypted": true
                }
            }
        ]
    }'
```

**Critical parameters explained:**

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `ImageId` | `$AMI_ID` | Amazon Linux 2023 — modern, secure, SSM agent pre-installed |
| `InstanceType` | `t3.micro` | Free Tier eligible, sufficient for learning, burstable CPU |
| `SecurityGroupIds` | `$APP_SG_ID` | App-SG: HTTP from ALB, SSH from Bastion only |
| `IamInstanceProfile` | `Veriqta-EC2-WebApp-Profile` | CloudWatch logging, SSM access, no hardcoded credentials |
| `UserData` | Base64-encoded script | Runs on first boot to install and configure Nginx |
| `HttpTokens: required` | IMDSv2 enforced | Blocks SSRF attacks against the metadata service |
| `VolumeSize: 20` | 20 GB root volume | Default is 8 GB; 20 GB provides room for logs and updates |
| `VolumeType: gp3` | General Purpose SSD (gen 3) | 20% cheaper than gp2, better baseline performance |
| `Encrypted: true` | EBS encryption | Data at rest is encrypted using AWS KMS |

**Capture the Launch Template ID and default version:**
```bash
LAUNCH_TEMPLATE_ID=$(aws ec2 describe-launch-templates \
    --launch-template-names veriqta-app-launch-template \
    --query 'LaunchTemplates[0].LaunchTemplateId' \
    --output text)

LAUNCH_TEMPLATE_VERSION=$(aws ec2 describe-launch-templates \
    --launch-template-names veriqta-app-launch-template \
    --query 'LaunchTemplates[0].LatestVersionNumber' \
    --output text)

echo "LAUNCH_TEMPLATE_ID: $LAUNCH_TEMPLATE_ID"
echo "LAUNCH_TEMPLATE_VERSION: $LAUNCH_TEMPLATE_VERSION"
```

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| User data not base64-encoded | Forgot encoding | Instance launches but user data is ignored; application not installed |
| IMDSv1 in user data script | Using old curl syntax | Metadata requests fail; instance ID and AZ not displayed on web page |
| Wrong security group | Using ALB-SG or Bastion-SG | App server cannot receive HTTP from ALB or SSH from bastion |
| Health check path missing | Not creating `/health` | ALB marks instance unhealthy; 503 errors persist |
| `DeleteOnTermination: false` on root volume | Copying from data volume config | Orphaned EBS volumes accumulate; unexpected storage costs |
| Large instance type | Using t3.large or bigger | Unnecessary cost for learning; Free Tier exhausted quickly |

## 💡 INTERVIEW TIPS

**Q: Why use a Launch Template instead of a Launch Configuration?**  
**A:** "Launch Templates are the modern replacement for Launch Configurations. They support versioning, multiple instance types, Spot Instances, and mixed instance policies. You can create new versions of a template without affecting existing Auto Scaling Groups, enabling safe rollouts. Launch Configurations are immutable — to change anything, you must create a new one and update the ASG. AWS now recommends Launch Templates for all new deployments."

**Q: Why encrypt EBS volumes?**  
**A:** "EBS encryption ensures that data at rest is protected. If a volume is detached and accessed by an unauthorized party, the data is unreadable without the KMS key. In production, encryption is often mandatory for compliance with SOC 2, PCI-DSS, and HIPAA. AWS KMS handles key management automatically, and the performance impact of encryption is negligible on modern instance types."

**Q: What happens if user data fails?**  
**A:** "If user data fails, the instance may launch successfully but the application will not be installed or configured. The ALB health check will fail because the `/health` endpoint does not exist, and the instance will be marked unhealthy. We mitigate this by logging user data output to `/var/log/user-data.log` and by testing the Launch Template with a single instance before deploying via Auto Scaling. In production, you should also use configuration management tools like Ansible, Chef, or User Data with error handling and signaling."

**Q: Why `gp3` instead of `gp2` for EBS?**  
**A:** "gp3 is the next-generation General Purpose SSD volume type. It provides a baseline of 3,000 IOPS and 125 MB/s throughput regardless of volume size, whereas gp2 scales IOPS with volume size. gp3 is up to 20 percent cheaper per GB and allows you to provision additional IOPS independently of capacity. For boot volumes, gp3 provides consistent performance at lower cost."
