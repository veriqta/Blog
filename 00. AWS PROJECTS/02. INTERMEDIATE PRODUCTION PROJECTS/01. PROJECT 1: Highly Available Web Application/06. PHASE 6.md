## PHASE 6: LOGGING & AUDIT

Every production load balancer must log every request. These logs are not optional — they are essential for security incident investigation, performance debugging, compliance audits (SOC 2, PCI-DSS, HIPAA), and capacity planning. AWS ALB can deliver access logs to S3 automatically. This phase builds a properly secured, encrypted, lifecycle-managed bucket with the exact permissions the ALB service requires.

---

### 6.1 Create a Unique S3 Bucket Name

S3 bucket names are globally unique across all AWS accounts, all regions, forever. Use your AWS Account ID as a suffix to guarantee uniqueness.

```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
BUCKET_NAME="veriqta-alb-logs-${ACCOUNT_ID}"
echo "BUCKET_NAME: $BUCKET_NAME"
```

---

### 6.2 Create the S3 Bucket

```bash
aws s3api create-bucket \
    --bucket $BUCKET_NAME \
    --region us-east-1
```

> **Note:** In `us-east-1`, you do not need `--create-bucket-configuration`. In other regions, you would add: `--create-bucket-configuration LocationConstraint=your-region`.

**Verify creation:**
```bash
aws s3api head-bucket --bucket $BUCKET_NAME
```
**No output means success.**

---

### 6.3 Block All Public Access

S3 buckets are private by default, but explicit blocks prevent accidental public exposure through bucket policies or ACLs.

```bash
aws s3api put-public-access-block \
    --bucket $BUCKET_NAME \
    --public-access-block-configuration \
        BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

**Verify:**
```bash
aws s3api get-public-access-block --bucket $BUCKET_NAME
```

**Expected:**
```json
{
    "PublicAccessBlockConfiguration": {
        "BlockPublicAcls": true,
        "IgnorePublicAcls": true,
        "BlockPublicPolicy": true,
        "RestrictPublicBuckets": true
    }
}
```

---

### 6.4 Enable Server-Side Encryption

Encrypt logs at rest using AWS-managed keys.

```bash
aws s3api put-bucket-encryption \
    --bucket $BUCKET_NAME \
    --server-side-encryption-configuration '{
        "Rules": [
            {
                "ApplyServerSideEncryptionByDefault": {
                    "SSEAlgorithm": "AES256"
                },
                "BucketKeyEnabled": true
            }
        ]
    }'
```

**Why `BucketKeyEnabled: true`?**
- Reduces KMS API call costs by 99 percent.
- Uses a bucket-level key instead of individual object keys.
- Required for cost-effective encryption at scale.

**Verify:**
```bash
aws s3api get-bucket-encryption --bucket $BUCKET_NAME
```

---

### 6.5 Enable Versioning

Versioning protects against accidental deletion and overwrites.

```bash
aws s3api put-bucket-versioning \
    --bucket $BUCKET_NAME \
    --versioning-configuration Status=Enabled
```

**Why versioning for logs?**
- Prevents accidental overwrites.
- Allows recovery from malicious deletion.
- Required for some compliance frameworks.

---

### 6.6 Configure Lifecycle Policy

Access logs accumulate rapidly. A busy ALB generates gigabytes per day. Auto-transition old logs to cheaper storage and eventually delete them.

```bash
cat > lifecycle-policy.json << 'EOF'
{
    "Rules": [
        {
            "ID": "ALB-Logs-Lifecycle",
            "Status": "Enabled",
            "Filter": { "Prefix": "" },
            "Transitions": [
                { "Days": 30, "StorageClass": "STANDARD_IA" },
                { "Days": 90, "StorageClass": "GLACIER" }
            ],
            "Expiration": { "Days": 365 },
            "NoncurrentVersionTransitions": [
                { "NoncurrentDays": 30, "StorageClass": "STANDARD_IA" },
                { "NoncurrentDays": 90, "StorageClass": "GLACIER" }
            ],
            "NoncurrentVersionExpiration": { "NoncurrentDays": 365 }
        }
    ]
}
EOF

aws s3api put-bucket-lifecycle-configuration \
    --bucket $BUCKET_NAME \
    --lifecycle-configuration file://lifecycle-policy.json

rm lifecycle-policy.json
```

**Lifecycle breakdown:**

| Days | Action | Storage Class | Cost Impact |
|------|--------|---------------|-------------|
| 0–30 | Active access | STANDARD | Full price |
| 30–90 | Infrequent access | STANDARD_IA | ~40 percent cheaper |
| 90–365 | Archive | GLACIER | ~80 percent cheaper |
| 365+ | Deleted | — | Zero cost |

**Verify:**
```bash
aws s3api get-bucket-lifecycle-configuration --bucket $BUCKET_NAME
```

### 6.7 Grant ALB Permission to Write Logs

The ALB service uses a special AWS account to deliver logs. The account ID varies by region. For `us-east-1`, it is `127311923021`.

| Region | ELB Account ID |
|--------|---------------|
| us-east-1 | 127311923021 |
| us-east-2 | 033677994240 |
| us-west-1 | 027434742980 |
| us-west-2 | 797873946194 |
| eu-west-1 | 156460612806 |
| eu-central-1 | 054676820928 |

**Create the bucket policy:**

```bash
cat > bucket-policy.json << EOF
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "ALBAccessLogs",
            "Effect": "Allow",
            "Principal": {
                "AWS": "arn:aws:iam::127311923021:root"
            },
            "Action": "s3:PutObject",
            "Resource": "arn:aws:s3:::${BUCKET_NAME}/veriqta-ha-alb/*"
        }
    ]
}
EOF

aws s3api put-bucket-policy \
    --bucket $BUCKET_NAME \
    --policy file://bucket-policy.json

rm bucket-policy.json
```

**Why `127311923021`?**
This is AWS's Elastic Load Balancing service account for `us-east-1`. AWS uses a dedicated account per region to deliver logs, separate from your account.

**Verify the policy:**
```bash
aws s3api get-bucket-policy --bucket $BUCKET_NAME --query Policy --output text | python3 -m json.tool
```

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Wrong ELB account ID in bucket policy | Copying from a different region | ALB cannot write logs; logs are silently lost |
| Missing prefix in bucket policy resource | Typo | ALB writes are denied with 403 Forbidden |
| No lifecycle policy | Forgotten | Log bucket grows indefinitely; unexpected S3 bills |
| Public access not blocked | Assumed default is sufficient | Accidental public exposure of access logs containing IP addresses and request data |
| Not waiting 5 minutes | Impatience | No logs visible;误以为 logging is broken |

## 💡 INTERVIEW TIPS

**Q: Why store ALB logs in S3 instead of CloudWatch Logs?**  
**A:** "S3 is the native destination for ALB access logs and is significantly cheaper for long-term storage, especially with lifecycle policies transitioning to Glacier. CloudWatch Logs is better for real-time streaming and querying with Logs Insights. In production, we often send ALB logs to S3 for archival and compliance, while also streaming a subset to CloudWatch Logs for operational dashboards. S3 also integrates with Athena for SQL-like analysis of historical logs."

**Q: Why is the ELB service account ID different per region?**  
**A:** "AWS isolates service accounts by region for security and operational boundaries. The ELB service in `us-east-1` uses a different IAM principal than `us-west-2`. This means your bucket policy must explicitly grant access to the correct regional account ID. AWS publishes these IDs in the documentation. Using the wrong ID results in silent log delivery failures because the ALB service lacks write permission."

**Q: What compliance value do ALB access logs provide?**  
**A:** "ALB logs contain complete request records including source IP, timestamp, URL, user agent, SSL cipher, and response codes. For PCI-DSS, they provide evidence of who accessed cardholder data environments. For SOC 2, they demonstrate access controls are functioning. For GDPR, they support data subject access requests and breach investigations. Without logs, you cannot prove what happened during a security incident."
