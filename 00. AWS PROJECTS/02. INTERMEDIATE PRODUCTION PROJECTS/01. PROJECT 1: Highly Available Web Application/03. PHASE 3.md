## PHASE 3: SECURITY FOUNDATION

Security Groups are stateful virtual firewalls attached to Elastic Network Interfaces. They are your first and last line of defense. There are no "deny" rules — only explicit allows. Everything else is implicitly denied.

In production, a misconfigured security group is a data breach waiting to happen. This phase builds three security groups with surgical precision.

---

### 3.1 The Security Architecture

| Security Group | Attached To | Inbound Rules | Outbound Rules |
|----------------|-------------|---------------|----------------|
| **ALB-SG** | Application Load Balancer | HTTP (80) from `0.0.0.0/0`<br>HTTPS (443) from `0.0.0.0/0` | All traffic (default) |
| **Bastion-SG** | Bastion Host | SSH (22) from your IP only | All traffic (default) |
| **App-SG** | EC2 instances (Auto Scaling) | HTTP (80) from ALB-SG<br>SSH (22) from Bastion-SG | Restricted (HTTP, HTTPS, DNS, NTP only) |

**Critical principle:** App servers never accept traffic directly from the internet. Everything flows through the ALB. SSH access is only possible through the bastion.

---

### 3.2 Get Your Public IP

The bastion must only accept SSH from your specific IP address.

### 3.3 Create the ALB Security Group

```bash
aws ec2 create-security-group \
    --group-name veriqta-alb-sg \
    --description "Security group for Application Load Balancer - accepts HTTP/HTTPS from internet" \
    --vpc-id $VPC_ID \
```

**Capture the Security Group ID:**
```bash
ALB_SG_ID=$(aws ec2 describe-security-groups \
```

### 3.5 Create the Application Security Group

This is the most critical security group. It protects your application servers.

```bash
aws ec2 create-security-group \
    --group-name veriqta-app-sg \
    --description "Security group for application servers - HTTP from ALB, SSH from Bastion only" \
    --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=security-group,Tags=[{Key:Name,Value:veriqta-app-sg},{Key:Tier,Value:Application},{Key:Project,Value:Veriqta-HA-WebApp}]'
```

```bash
APP_SG_ID=$(aws ec2 describe-security-groups \
```

**Add HTTP rule from ALB Security Group (reference, not CIDR):**

```bash

    --group-id $APP_SG_ID \
    --protocol tcp \
    --port 22 \
    --source-group $BASTION_SG_ID
```

**Verify:**
```bash
aws ec2 describe-security-groups --group-ids $APP_SG_ID \
    --query 'SecurityGroups[*].{Name:GroupName,Inbound:IpPermissions}'
```

```json

    {
```

**Key observation:** There are no CIDR blocks in the App-SG inbound rules. Only Security Group references. This means:
- Any EC2 instance attached to `veriqta-alb-sg` can reach app servers on port 80.
- Any EC2 instance attached to `veriqta-bastion-sg` can reach app servers on port 22.
- Everything else is silently dropped.

### 3.6 Restrict Outbound Traffic on Application Servers

By default, Security Groups allow all outbound traffic. For production hardening, restrict this.

**Remove the default "allow all" outbound rule:**
```bash
aws ec2 revoke-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol all \
    --port all \
    --cidr 0.0.0.0/0
```

**Add specific outbound rules:**

```bash
# HTTP for software updates and API calls
aws ec2 authorize-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

# HTTPS for secure API calls and package repositories
aws ec2 authorize-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol tcp \
    --port 443 \
    --cidr 0.0.0.0/0

# DNS (UDP)
aws ec2 authorize-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol udp \
    --port 53 \
    --cidr 0.0.0.0/0

# DNS (TCP)
aws ec2 authorize-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol tcp \
    --port 53 \
    --cidr 0.0.0.0/0

# NTP for time synchronization
aws ec2 authorize-security-group-egress \
    --group-id $APP_SG_ID \
    --protocol udp \
    --port 123 \
    --cidr 0.0.0.0/0
```

**Verify outbound rules:**
```bash
aws ec2 describe-security-groups --group-ids $APP_SG_ID \
    --query 'SecurityGroups[*].{Name:GroupName,Outbound:IpPermissionsEgress}'
```

**Expected:**

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| App-SG allows 22 from `0.0.0.0/0` | Copying bastion rule | Anyone on the internet can SSH to app servers |
| Using CIDR instead of SG references | Not knowing the feature | Rules break when ALB or bastion IPs change; brittle architecture |
| Forgetting to restrict outbound | Default is "allow all" | Compromised app server can exfiltrate data on any port |
| Opening ephemeral ports inbound | Confusion about statefulness | Unnecessary — Security Groups are stateful; return traffic is automatic |
| No tags on security groups | Laziness | Impossible to trace ownership or cost in large organizations |

## 💡 INTERVIEW TIPS

**Q: Why use Security Group references instead of CIDR blocks?**  
**A:** "Security Group references create dynamic, self-updating rules. If I reference the ALB security group in my app security group, any instance attached to the ALB SG automatically gains access. If the ALB is replaced or scaled, I don't need to update IP addresses. CIDR blocks are static and brittle — they break when resources change. In production, we always use SG references for intra-VPC communication."

**Q: Are Security Groups stateful or stateless?**  
**A:** "Security Groups are stateful. If I allow inbound HTTP traffic on port 80, the return traffic is automatically allowed without an explicit outbound rule. This is different from NACLs, which are stateless and require rules in both directions. Stateful firewalls are easier to manage and less error-prone."

**Q: What's the difference between Security Groups and NACLs?**  
**A:** "Security Groups operate at the instance level, are stateful, and only support allow rules. NACLs operate at the subnet level, are stateless, and support both allow and deny rules. In production, we use Security Groups as the primary firewall and NACLs as a secondary, coarse-grained layer. For example, a NACL might block a known malicious IP range across an entire subnet, while Security Groups handle fine-grained instance-level access."

**Q: Why restrict outbound traffic?**  
**A:** "If an application server is compromised, unrestricted outbound access allows the attacker to exfiltrate data, establish command-and-control channels, or scan external networks. By restricting outbound to only necessary ports — HTTP, HTTPS, DNS, NTP — we limit the attacker's options and increase the likelihood of detection. This is defense in depth."
