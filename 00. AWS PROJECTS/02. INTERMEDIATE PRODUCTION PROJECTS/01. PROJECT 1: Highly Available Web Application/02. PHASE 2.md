## PHASE 2: VPC & NETWORKING

Every resource you build lives inside a VPC. This phase creates the network foundation: the VPC itself, subnets across two Availability Zones, an Internet Gateway for public access, and NAT Gateways for secure outbound connectivity from private subnets.

Get this phase wrong and you will have routing issues, IP conflicts, and security gaps for the entire project. Get it right and you have a scalable, secure network that mirrors real production environments.

---

### 2.1 Understanding the IP Plan

Before creating anything, you must understand the IP addressing. We use `10.0.0.0/16` as the VPC CIDR.

| CIDR | Total IPs | Usable IPs | Description |
|------|-----------|------------|-------------|
| `/16` | 65,536 | 65,531 | Large VPC with room to grow |
| `/24` | 256 | 251 | Standard subnet size for a tier |

**Subnet allocation:**

| AZ | Type | CIDR | IP Range | Purpose |
|----|------|------|----------|---------|
| us-east-1a | Public | `10.0.1.0/24` | 10.0.1.0 – 10.0.1.255 | ALB, NAT GW, Bastion |
| us-east-1a | Private | `10.0.2.0/24` | 10.0.2.0 – 10.0.2.255 | App servers |
| us-east-1b | Public | `10.0.3.0/24` | 10.0.3.0 – 10.0.3.255 | ALB, NAT GW |
| us-east-1b | Private | `10.0.4.0/24` | 10.0.4.0 – 10.0.4.255 | App servers |

**Design decisions:**
- Odd-numbered subnets are public; even are private. This is a mental model used by senior engineers.
- Each AZ has one public and one private subnet. Symmetric, predictable, balanced.
- `/24` provides 251 usable IPs — more than enough for ALB + NAT GW + bastion in public, and plenty of room for auto-scaling in private.
- 250+ unused `/24` subnets remain in the `/16` for future expansion (RDS, ElastiCache, ECS, EKS).

### 2.2 Create the VPC

```bash
aws ec2 create-vpc \
    --cidr-block 10.0.0.0/16 \
    --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=veriqta-ha-webapp-vpc},{Key=Project,Value=Veriqta-HA-WebApp},{Key=Environment,Value=Production}]' \
    --enable-dns-support \
    --enable-dns-hostnames
```

**Flags explained:**
- `--cidr-block 10.0.0.0/16`: The IP range for the entire VPC.
- `--enable-dns-support`: Allows instances to resolve hostnames to IPs within the VPC.
- `--enable-dns-hostnames`: Assigns public DNS hostnames to instances with public IPs.
- `--tag-specifications`: Tags for cost tracking and resource management.

**Capture the VPC ID:**

```bash
VPC_ID=$(aws ec2 describe-vpcs \
    --filters "Name=tag:Name,Values=veriqta-ha-webapp-vpc" \
    --query 'Vpcs[0].VpcId' \
    --output text)

echo "VPC_ID: $VPC_ID"
```

**Verify:**
```bash
aws ec2 describe-vpcs --vpc-ids $VPC_ID \
    --query 'Vpcs[*].[VpcId,CidrBlock,State]'
```

**Expected output:**
```json
[
    ["vpc-0a1b2c3d4e5f6789a", "10.0.0.0/16", "available"]
]
```

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| Private subnet routes `0.0.0.0/0` to IGW | Confusing public and private route tables | Private instances become publicly accessible; security breach |
| Single NAT Gateway for both AZs | Cost saving | Cross-AZ data charges; single point of failure |
| Wrong AZ names | Copying from another region | Resources fail to launch; subnet-AZ mismatch |
| CIDR overlap with corporate network | Poor planning | VPN peering fails; IP conflicts |
| Not waiting for NAT Gateway `available` | Impatience | Outbound traffic from private subnets is black-holed |
| Public subnet without auto-assign IP | Forgotten step | Instances launch without public IPs; ALB targets fail |

## 💡 INTERVIEW TIPS

**Q: Why use private subnets for application servers?**  
**A:** "Private subnets ensure application servers are never directly accessible from the internet. All inbound traffic flows through the load balancer, which acts as a controlled entry point. This follows defense-in-depth principles — even if an application has a vulnerability, attackers cannot reach it directly because there is no public IP and no route from the IGW."

**Q: Why do we need a NAT Gateway? Can't private instances just use the IGW?**  
**A:** "The Internet Gateway provides bidirectional internet access. If private instances used the IGW, they would need public IPs to receive return traffic, which exposes them to inbound attacks. A NAT Gateway is unidirectional — it allows outbound connections for software updates and API calls while blocking all inbound initiation. The private instances keep their private IPs, and the NAT Gateway translates outbound traffic using its Elastic IP."

**Q: Why separate route tables per AZ for private subnets?**  
**A:** "Each private subnet should route to the NAT Gateway in its own AZ. If AZ-a routes to NAT Gateway in AZ-b, traffic crosses AZ boundaries, incurring data transfer charges and creating a dependency — if AZ-b fails, AZ-a loses internet access. Separate route tables per AZ ensure localized routing and true AZ independence."

**Q: What is the difference between a public and private subnet?**  
**A:** "A public subnet has a route to an Internet Gateway, allowing instances with public IPs to communicate bidirectionally with the internet. A private subnet has no route to an IGW. If it needs outbound internet access, it uses a NAT Gateway, which only allows outbound-initiated traffic. The key distinction is the route table, not the subnet's CIDR or name."
