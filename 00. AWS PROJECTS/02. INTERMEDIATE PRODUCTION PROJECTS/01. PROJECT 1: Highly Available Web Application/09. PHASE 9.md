### 9.7 Simulate Instance Failure and Observe Auto-Healing

This is the most important verification. Terminate one instance and watch the ASG replace it automatically.

**Before termination, note the current instances:**
```bash
echo "Instances before termination:"
aws autoscaling describe-auto-scaling-groups \
    --auto-scaling-group-names veriqta-app-asg \
    --query 'AutoScalingGroups[0].Instances[*].{ID:InstanceId,AZ:AvailabilityZone,State:LifecycleState}'
```

**Terminate the instance in AZ-a:**
```bash
echo "Terminating $APP_INSTANCE_1A..."
aws ec2 terminate-instances --instance-ids $APP_INSTANCE_1A
```

**Watch the ASG respond:**
```bash
echo "Monitoring ASG for replacement (checking every 15 seconds for 3 minutes)..."
for i in {1..12}; do
    echo "--- Check $i ---"
    aws autoscaling describe-auto-scaling-groups \
        --auto-scaling-group-names veriqta-app-asg \
        --query 'AutoScalingGroups[0].Instances[*].{ID:InstanceId,AZ:AvailabilityZone,State:LifecycleState,Health:HealthStatus}' \
        --output table
    sleep 15
done
```

**What you should observe:**
1. The terminated instance shows `LifecycleState: Terminating` or disappears
2. Within 30–60 seconds, a new instance appears with `LifecycleState: Pending`
3. The new instance transitions: `Pending` → `InService`
4. The target group shows the new instance as `healthy` after 2 successful health checks

**Verify the target group health during recovery:**
```bash
aws elbv2 describe-target-health --target-group-arn $TG_ARN \
    --query 'TargetHealthDescriptions[*].{ID:Target.Id,State:TargetHealth.State}'
```

**Verify the ALB still serves traffic throughout the failure:**
```bash
for i in {1..10}; do
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" http://$ALB_DNS)
    echo "Request $i: HTTP $STATUS"
    sleep 5
done
```

> **Expected:** Most requests return `200`. A brief period may return `503` while the new instance is launching and before it passes health checks. This window should be under 2–3 minutes.

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| 503 errors persist after instance replacement | Health check grace period too short or user data failed | ALB never marks new instance healthy; infinite replacement loop |
| Cannot SSH to private instance | Forgot `-A` flag or agent not running | Cannot troubleshoot application issues on private servers |
| Terminated instance not replaced | ASG at minimum capacity with suspended processes | Application runs under capacity; AZ failure causes outage |
| No S3 logs after waiting | Wrong bucket policy or wrong ELB account ID | Complete loss of audit trail; compliance failure |
| Session Manager connection refused | SSM agent not running or IAM role missing SSM permissions | Cannot access instances without bastion; operational paralysis |
| New instance missing tags | `PropagateAtLaunch=false` | Cost allocation breaks; resources untraceable in large accounts |

## 💡 INTERVIEW TIPS

**Q: How do you troubleshoot a 503 error from an ALB?**  
**A:** "First, I check the target group health in the AWS Console or CLI. If targets are unhealthy, I verify the application is running and the `/health` endpoint returns HTTP 200. If targets are healthy but 503 persists, I check the ALB listener rules and security groups. If there are no registered targets at all, I verify the Auto Scaling Group is launching instances successfully and that the Launch Template user data completes without errors. I also check CloudWatch metrics for `TargetConnectionErrorCount` and review application logs via Session Manager or SSH through the bastion."

**Q: What is the expected behavior when an EC2 instance fails in an ASG?**  
**A:** "The ASG detects the failure through the configured health checks — either EC2 status checks or ELB health checks. It marks the instance as unhealthy, terminates it, and immediately launches a replacement instance using the Launch Template. The new instance is registered with the target group, and once it passes two consecutive health checks, the ALB begins routing traffic to it. The entire process typically takes 2–4 minutes, during which the remaining healthy instances continue serving traffic. This is why we maintain a minimum of two instances across two AZs — the application remains available during replacement."

**Q: How do you access logs on an instance with no public IP and no bastion?**  
**A:** "The modern approach is AWS Systems Manager Session Manager. It requires the SSM agent on the instance — which is pre-installed on Amazon Linux 2023 — and an IAM role with SSM permissions. With Session Manager, I can open a shell session through the AWS API without SSH keys, open ports, or a bastion host. For log analysis at scale, I configure the CloudWatch agent to stream logs to CloudWatch Logs, where I can search with Logs Insights without accessing individual instances."
