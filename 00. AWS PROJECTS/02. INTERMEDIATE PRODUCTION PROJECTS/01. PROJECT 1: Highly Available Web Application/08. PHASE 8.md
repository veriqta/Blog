## PHASE 8: AUTO SCALING GROUP

The Auto Scaling Group (ASG) is the self-healing engine of your architecture. It maintains a specified number of EC2 instances across multiple Availability Zones, automatically replaces instances that fail health checks, and scales capacity up or down based on demand. If an entire Availability Zone fails, the ASG launches replacement instances in the healthy zone.

Without an ASG, a failed instance means downtime. With an ASG, a failed instance means a brief blip while a new one launches and passes health checks.

### 8.2 Create the Auto Scaling Group

```bash
aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name veriqta-app-asg \
    --launch-template LaunchTemplateId=$LAUNCH_TEMPLATE_ID,Version=$LAUNCH_TEMPLATE_VERSION \
    --min-size 2 \
    --max-size 4 \
    --desired-capacity 2 \
    --vpc-zone-identifier "$PRIVATE_SUBNET_1A,$PRIVATE_SUBNET_1B" \
    --target-group-arns $TG_ARN \
    --health-check-type ELB \
    --health-check-grace-period 300 \
    --default-cooldown 300 \
    --termination-policies "Default" \
    --tags \
        Key=Name,Value=veriqta-app-server,PropagateAtLaunch=true \
        Key=Project,Value=Veriqta-HA-WebApp,PropagateAtLaunch=true \
        Key=Tier,Value=Application,PropagateAtLaunch=true \
        Key=Environment,Value=Production,PropagateAtLaunch=true
```

**Parameters explained:**

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `--min-size 2` | 2 instances | Minimum healthy capacity. One per AZ for baseline redundancy. |
| `--max-size 4` | 4 instances | Upper limit to prevent runaway scaling and unexpected costs. |
| `--desired-capacity 2` | 2 instances | Current target. The ASG launches this many instances immediately. |
| `--vpc-zone-identifier` | Private subnets | Instances launch in private subnets only. |
| `--target-group-arns` | `$TG_ARN` | Automatically registers new instances with the ALB target group. |
| `--health-check-type ELB` | ELB health checks | Uses the ALB's `/health` endpoint, not just EC2 status checks. |
| `--health-check-grace-period 300` | 5 minutes | Time for user data and application startup before health checks count. |
| `--default-cooldown 300` | 5 minutes | Time between scaling activities to prevent thrashing. |
| `--termination-policies Default` | Default policy | Terminates instances with oldest launch configuration first. |
| `PropagateAtLaunch=true` | Tag propagation | Tags are copied to every EC2 instance created by the ASG. |

**Why `health-check-type ELB` instead of `EC2`?**
- `EC2` only checks if the VM is running (hypervisor-level).
- `ELB` checks if the application is responding correctly on `/health`.
- If Nginx crashes but the VM is still running, `EC2` says healthy while `ELB` says unhealthy. `ELB` is the correct choice for production.

### 8.7 Create a Scaling Policy

Without a scaling policy, the ASG maintains exactly 2 instances regardless of load. Add a target tracking policy to scale based on CPU utilization.

**Create the scaling policy:**
```bash
cat > scaling-policy.json << 'EOF'
{
    "TargetValue": 50.0,
    "PredefinedMetricSpecification": {
        "PredefinedMetricType": "ASGAverageCPUUtilization"
    },
    "ScaleOutCooldown": 300,
    "ScaleInCooldown": 300
}
EOF

aws autoscaling put-scaling-policy \
    --auto-scaling-group-name veriqta-app-asg \
    --policy-name veriqta-cpu-target-tracking \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration file://scaling-policy.json

rm scaling-policy.json
```

**How it works:**
- If average CPU across all instances exceeds 50% for 3 consecutive datapoints, the ASG launches a new instance.
- If average CPU drops below 50% for 15 consecutive datapoints, the ASG terminates an instance (down to the minimum of 2).
- `ScaleOutCooldown` (300s) prevents launching instances too rapidly.
- `ScaleInCooldown` (300s) prevents terminating instances too rapidly.

**Verify the policy:**
```bash
aws autoscaling describe-policies \
    --auto-scaling-group-name veriqta-app-asg \
    --query 'ScalingPolicies[*].{Name:PolicyName,Type:PolicyType,TargetValue:TargetTrackingConfiguration.TargetValue,Metric:TargetTrackingConfiguration.PredefinedMetricSpecification.PredefinedMetricType}'
```

## ⚠️ COMMON MISTAKES

| Mistake | Why It Happens | Impact |
|---------|---------------|--------|
| ASG in public subnets | Wrong subnet IDs | App servers get public IPs; security model is broken |
| `health-check-type EC2` instead of `ELB` | Default is EC2 | ALB marks instances unhealthy but ASG keeps them running; users see errors |
| Health check grace period too short | Impatience | Instances terminated during user data execution before application starts |
| No `PropagateAtLaunch` on tags | Forgotten | Instances lack tags; impossible to trace ownership or allocate costs |
| `desired-capacity` set to 1 | Cost saving | No AZ redundancy; if one AZ fails, the application is down |
| Max size equals min size | Forgot to set max | Scaling policy cannot launch instances; CPU spikes cause downtime |

## 💡 INTERVIEW TIPS

**Q: Why use an Auto Scaling Group instead of manually managing EC2 instances?**  
**A:** "Manual management does not scale and introduces human error. An Auto Scaling Group provides self-healing — if an instance fails a health check, it is automatically terminated and replaced. It provides elasticity — scaling out during traffic spikes and scaling in during quiet periods to optimize costs. It also distributes instances across Availability Zones, ensuring the application survives a data center failure. In production, manually managing instances is considered an anti-pattern."

**Q: What is the difference between `EC2` and `ELB` health checks in an ASG?**  
**A:** "EC2 health checks verify only that the hypervisor reports the instance as running. The VM could be running but the application could be crashed, hung, or unable to connect to the database. ELB health checks verify application-layer health by calling a specific endpoint, such as `/health`. If that endpoint returns a non-200 status, the instance is marked unhealthy and replaced. In production, you should always use ELB health checks because they validate the full application stack, not just the operating system."

**Q: How does the ASG decide which instance to terminate during scale-in?**  
**A:** "By default, the ASG uses the `Default` termination policy, which follows this order: first, select the Availability Zone with the most instances; second, select the instance with the oldest launch configuration or launch template. You can customize this with termination policies such as `OldestInstance`, `NewestInstance`, or `ClosestToNextInstanceHour`. In production, `Default` works well for balanced AZ distribution."

**Q: What happens during an Availability Zone failure?**  
**A:** "If an AZ becomes unavailable, the ALB stops routing traffic to targets in that zone. The ASG detects that instances in the failed zone are unhealthy and attempts to launch replacements in the healthy zones, up to the maximum capacity. Because our subnets span two AZs and the ASG is configured with both, the application remains available. Once the failed AZ recovers, the ASG can rebalance instances across zones if rebalancing is enabled."
