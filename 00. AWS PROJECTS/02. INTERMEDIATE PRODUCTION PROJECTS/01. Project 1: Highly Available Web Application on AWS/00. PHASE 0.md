# 0.2 Project Goal

The goal is to build and operate a secure, scalable, observable, and highly available web application on AWS.

The application must continue serving users when:

* An application container fails.
* An ECS task becomes unhealthy.
* One running application task is stopped.
* Traffic increases suddenly.
* A deployment introduces an unhealthy application version.
* The primary database instance fails.
* Individual infrastructure components require replacement.
* One Availability Zone becomes unavailable.

The application will run across multiple Availability Zones inside one AWS Region.

This project focuses on **regional high availability**.

It does not claim to protect the application from a complete AWS Region outage. Multi-Region disaster recovery would require a separate architecture, data-replication strategy, traffic-routing strategy, recovery plan, and cost model.

AWS recommends distributing production workloads across multiple Availability Zones and planning sufficient remaining capacity to serve traffic when one zone is impaired.

# 0.8 Request Flow

A normal application request will follow this path:

```text
User
  |
  v
Route 53
  |
  v
CloudFront
  |
  v
AWS WAF
  |
  v
Application Load Balancer
  |
  v
Healthy ECS Fargate task
  |
  v
RDS PostgreSQL when database access is required
  |
  v
Application response
  |
  v
Application Load Balancer
  |
  v
CloudFront
  |
  v
User
```

Detailed request flow:

1. A user opens:

```text
https://app.example.com
```

2. Route 53 resolves the application hostname to the CloudFront distribution.

3. CloudFront presents the public TLS certificate.

4. AWS WAF evaluates the request.

5. WAF may block:

* Known malicious requests.
* Requests matching selected AWS managed rules.
* Requests from blocked addresses.
* Excessive request rates.
* Common exploit patterns.
* Requests that violate approved application rules.

6. CloudFront forwards an allowed request to the Application Load Balancer over HTTPS.

7. CloudFront adds a protected custom origin header.

8. The ALB listener evaluates the expected header.

9. Requests without the expected header are rejected.

10. The ALB chooses a healthy ECS target.

11. The ECS task processes the request.

12. When required, the application connects to the RDS PostgreSQL endpoint.

13. The response travels through the ALB and CloudFront to the user.

AWS documents the use of a CloudFront custom origin header and an ALB listener rule to reduce direct access to an internet-facing ALB. The header name and value must remain secret.

The ALB security group will also restrict inbound origin traffic to the AWS-managed CloudFront origin-facing prefix list.

# 0.9 CloudFront Origin Decision

The project will initially use:

```text
CloudFront
    |
    v
Internet-facing Application Load Balancer
```

The ALB will remain internet-facing because this project teaches:

* Public ALB deployment.
* CloudFront custom origin configuration.
* CloudFront origin-facing prefix-list restrictions.
* ALB listener-rule origin validation.
* TLS between CloudFront and the ALB.

Direct access to the ALB will be reduced through both:

1. Security-group restrictions using the CloudFront origin-facing managed prefix list.
2. A protected custom origin header validated by the ALB listener.

CloudFront VPC origins can support private ALB origins, but changing to that model would materially alter the architecture and would require a new ADR. AWS documents VPC origins as a separate design for accessing ALBs in private subnets.

# 0.10 High-Availability Strategy

## Application tier

The initial production ECS service configuration will be:

```text
Desired tasks: 2
Minimum tasks: 2
Maximum tasks: 6
```

Tasks will run in both private application subnets.

The intended steady state will be:

```text
Availability Zone A: 1 task
Availability Zone B: 1 task
```

ECS Availability Zone rebalancing will be enabled.

If an application task fails:

```text
Application or container failure
            |
            v
Task or target becomes unhealthy
            |
            v
ALB stops sending new traffic to the unhealthy target
            |
            v
ECS attempts to maintain the desired task count
            |
            v
A replacement task starts
            |
            v
The replacement passes its health checks
            |
            v
ALB begins routing traffic to the replacement
```

If one Availability Zone becomes unavailable:

```text
Resources in one zone become unavailable
            |
            v
ALB routes requests to healthy targets in the remaining zone
            |
            v
ECS attempts to maintain the desired service capacity
            |
            v
Auto Scaling remains available
            |
            v
Operations investigate and recover normal multi-zone distribution
```

Two tasks do not guarantee that the remaining zone can handle full peak demand. Load testing must determine whether the remaining healthy capacity can serve expected traffic.

## Load-balancing tier

The Application Load Balancer will use:

* Public Subnet A.
* Public Subnet B.
* HTTPS listener on port 443.
* An ECS target group using IP targets.
* Health-based traffic routing.
* Cross-zone load balancing behaviour provided by the ALB service.

## Database tier

Amazon RDS for PostgreSQL will use a Multi-AZ DB instance deployment.

The deployment will contain:

* One primary database instance.
* One synchronous standby instance in another Availability Zone.
* One database endpoint used by the application.
* Automatic failover support.

The standby will not be treated as a read replica.

AWS documents that the standby in a Multi-AZ DB instance deployment supports failover but does not serve normal read traffic.

When qualifying failures occur, RDS can fail over to the standby in another Availability Zone.

# 0.11 Availability Limitations

This project improves availability, but it does not eliminate every failure mode.

The architecture does not automatically protect against:

* A complete AWS Region outage.
* Application-wide logical defects.
* Corrupted database writes.
* Incorrect database migrations.
* Compromised administrator access.
* Accidental deletion where protection is bypassed.
* Exhausted AWS service quotas.
* Incorrect DNS changes.
* Invalid TLS configuration.
* Dependency outages outside AWS.
* A traffic level beyond tested system capacity.
* A deployment that is technically healthy but functionally incorrect.
* Incorrect WAF rules that block legitimate users.
* Shared account-level failures.
* Human operational mistakes.

High availability requires:

* Redundancy.
* Capacity planning.
* Health checks.
* Monitoring.
* Safe deployment.
* Backups.
* Restore testing.
* Failure testing.
* Runbooks.
* Trained operational response.

# 0.14 NAT Gateway Decision

Each environment will use:

* NAT Gateway A in Public Subnet A.
* NAT Gateway B in Public Subnet B.

Private App Subnet A will use NAT Gateway A.

Private App Subnet B will use NAT Gateway B.

This avoids making both application subnets dependent on one NAT Gateway located in one Availability Zone.

NAT Gateways may be used by private ECS tasks to reach:

* Required external APIs.
* Public package endpoints where needed.
* AWS public service endpoints when no VPC endpoint is configured.
* Amazon ECR endpoints.
* CloudWatch Logs.
* Secrets Manager.
* Systems Manager.

The application container must not install packages during normal startup. Runtime package installation would introduce unnecessary external dependencies and inconsistent task startup.

NAT Gateway charges must be included in cost monitoring.

# 0.21 Application Health Model

The application will expose separate liveness and readiness endpoints.

## Liveness endpoint

```text
GET /health
```

Purpose:

Confirm that the application process is running and able to respond.

Expected response:

```json
{
  "status": "healthy"
}
```

Expected status:

```text
HTTP 200
```

The liveness endpoint must not depend on the database.

A temporary database failure should not automatically prove that the Node.js process is dead.

## Readiness endpoint

```text
GET /ready
```

Purpose:

Confirm that the task is ready to receive normal application traffic.

Readiness will evaluate:

* Application startup completion.
* Required configuration validation.
* Database connection-pool availability.
* Database connectivity.
* Required internal initialization.

Expected healthy response:

```json
{
  "status": "ready",
  "database": "connected"
}
```

Expected healthy status:

```text
HTTP 200
```

Expected unavailable response:

```json
{
  "status": "not_ready",
  "database": "unavailable"
}
```

Expected unavailable status:

```text
HTTP 503
```

## Version endpoint

```text
GET /version
```

Expected response fields:

```json
{
  "service": "veriqta-ha-webapp",
  "version": "1.0.0",
  "commitSha": "a38f7c2",
  "environment": "production"
}
```

The endpoint must not expose secrets, internal network details, database credentials, or full environment-variable contents.

# 0.22 ALB Health-Check Design

The target group will initially use:

```text
Protocol: HTTP
Port: traffic-port
Path: /health
Healthy threshold: 2
Unhealthy threshold: 3
Timeout: 5 seconds
Interval: 30 seconds
Success codes: 200
```

These are starting values.

They will be validated through:

* Container startup testing.
* Deployment testing.
* Failure testing.
* Load testing.
* Graceful-shutdown testing.
* Database-outage testing.

The ALB will initially use `/health` rather than `/ready` so that a temporary database interruption does not immediately create uncontrolled task replacement.

Application readiness will still be monitored and used by smoke tests, dashboards, and operational checks.

If later testing proves that target routing should depend on `/ready`, that change must be deliberate and documented.

# 0.60 Common Mistakes

## Mistake 1: Treating two tasks as unlimited availability

Two tasks improve redundancy, but they do not prove that one remaining task can handle peak traffic.

Capacity must be tested.

## Mistake 2: Calling a system highly available while using one NAT Gateway

One NAT Gateway in one Availability Zone creates a zonal dependency for private egress.

This project uses one NAT Gateway per zone.

## Mistake 3: Making the database public for convenience

RDS will remain private.

Administrative convenience does not justify public PostgreSQL exposure.

## Mistake 4: Confusing RDS Multi-AZ with read scaling

The standby in the selected Multi-AZ DB instance design does not serve normal read traffic.

## Mistake 5: Treating Multi-AZ as a backup

Multi-AZ improves availability.

It does not replace point-in-time recovery, retention, and restore testing.

## Mistake 6: Using permanent AWS keys in GitHub

GitHub Actions will use OIDC and short-lived AWS credentials.

## Mistake 7: Creating a new DynamoDB lock table from outdated Terraform examples

The project will use S3-native lockfiles for Terraform state locking.

## Mistake 8: Using one log group for development and production

## Mistake 9: Assuming an ALB is protected merely because CloudFront exists

# 0.62 Interview Tips

## Question: What makes this application highly available?

A strong answer:

> The application distributes traffic and compute across two Availability Zones. An Application Load Balancer sends requests only to healthy ECS Fargate tasks, while the ECS service maintains the desired task count and rebalances tasks across zones. The PostgreSQL database uses an RDS Multi-AZ deployment with a synchronous standby and managed failover. The design also includes health checks, scaling, monitoring, controlled deployment, backups, and tested recovery.

## Question: Why are the ECS tasks in private subnets?

A strong answer:

> The tasks do not need direct inbound internet access. The Application Load Balancer is the controlled entry point and forwards traffic to the task security group. Private tasks reduce direct exposure while NAT Gateways or VPC endpoints provide required outbound connectivity.

## Question: Why use one NAT Gateway per Availability Zone?

A strong answer:

> Each private application subnet uses a NAT Gateway in the same zone. This prevents both application subnets from depending on one zonal NAT Gateway and avoids unnecessary cross-zone routing for normal egress.

## Question: Why is RDS Multi-AZ not a backup strategy?

A strong answer:

> Multi-AZ is primarily an availability mechanism. The standby can receive the same unwanted or corrupt changes as the primary. Backups, point-in-time recovery, retention, and tested restores are still required.

## Question: Why separate liveness and readiness?

A strong answer:

> Liveness answers whether the application process can respond. Readiness answers whether the task can serve normal traffic and may include critical dependency checks. Combining them can cause unnecessary restarts or unstable routing during a temporary dependency failure.

## Question: Why use GitHub Actions OIDC?

A strong answer:

> OIDC allows GitHub workflows to assume restricted AWS roles using short-lived credentials. This avoids storing permanent AWS access keys in GitHub and permits separate trust and permission policies for pull requests, development, and production.

## Question: Why use S3-native Terraform state locking?

A strong answer:

> The S3 backend supports lockfiles to prevent simultaneous state operations. It keeps state and locking within the backend design, while new DynamoDB-based locking is avoided because HashiCorp has deprecated it.

## Question: Why does the architecture still need backups if the database has a standby?

A strong answer:

> A standby helps recover from infrastructure failure, but it does not protect against logical corruption, accidental deletion, bad migrations, or malicious changes. Recovery requires retained backups and verified restore procedures.
