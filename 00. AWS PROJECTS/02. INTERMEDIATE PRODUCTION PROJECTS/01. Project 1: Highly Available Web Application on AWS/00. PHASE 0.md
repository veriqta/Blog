# Phase 0: Prerequisites and Architecture

## 0.1 Project Goal

Build and operate a secure, scalable, highly available web application that continues serving users when:

* An application container fails.
* An ECS task becomes unhealthy.
* Traffic increases suddenly.
* One Availability Zone becomes unavailable.
* The primary database instance fails.
* A deployment introduces an unhealthy application version.
* Individual infrastructure components require replacement.

The application will run across multiple Availability Zones inside one AWS Region.

This project focuses on **regional high availability**. It does not claim to provide complete protection from an entire AWS Region outage. Multi-Region disaster recovery would be a separate advanced project.

AWS recommends deploying production workloads across multiple Availability Zones so resources in the remaining Availability Zones can continue serving requests during an Availability Zone failure.

## 0.3 Final Architecture Decision

The project will use:

* One AWS account.
* One AWS Region.
* Two Availability Zones.
* One custom VPC.
* Two public subnets.
* Two private application subnets.
* Two private database subnets.
* One NAT Gateway per Availability Zone.
* Route 53 for DNS.
* CloudFront for global content delivery.
* AWS WAF for edge protection.
* AWS Certificate Manager for TLS certificates.
* An Application Load Balancer.
* Amazon ECS with AWS Fargate.
* At least two application tasks.
* ECS Availability Zone rebalancing.
* ECS Service Auto Scaling.
* Amazon ECR for Docker images.
* Amazon RDS for PostgreSQL.
* An RDS Multi-AZ deployment.
* AWS Secrets Manager.
* AWS Systems Manager Parameter Store.
* CloudWatch Logs, metrics, dashboards, and alarms.
* Amazon SNS for notifications.
* Amazon S3 for logs, Terraform state, and selected application assets.
* DynamoDB for Terraform state locking when supported by the selected backend design.
* GitHub Actions with AWS OpenID Connect.
* Terraform for infrastructure provisioning.

Amazon ECS recommends running multi-task services across multiple Availability Zones for high availability. Its service scheduler also replaces failed tasks to maintain the configured desired count.

# 0.5 Architecture Request Flow

A normal request will follow this path:

```text
User
  ↓
Route 53
  ↓
CloudFront
  ↓
AWS WAF
  ↓
Application Load Balancer
  ↓
Healthy ECS Fargate task
  ↓
RDS PostgreSQL, when database access is required
  ↓
Application response
  ↓
CloudFront
  ↓
User
```

## Detailed flow

1. A user opens:

```text
https://app.example.com
```

2. Route 53 resolves the domain to the CloudFront distribution.

3. CloudFront terminates the public TLS connection using an ACM certificate.

4. AWS WAF evaluates the request.

5. WAF can reject:

```text
Known malicious requests
Excessive request rates
Common web exploits
Requests matching blocked IP rules
Requests matching selected managed rules
```

6. CloudFront forwards an allowed request to the Application Load Balancer.

7. CloudFront adds a protected origin header.

8. The ALB listener verifies the expected header.

9. The ALB selects a healthy ECS task from its target group.

10. The ECS task processes the request.

11. When required, the application connects to the RDS PostgreSQL endpoint.

12. The response travels back through the ALB and CloudFront.

13. CloudFront may cache eligible static responses.

CloudFront can deliver both static and dynamic web content. AWS documents using protected origin headers and CloudFront origin-facing controls to reduce direct access to an internet-facing ALB.

# 0.6 High-Availability Strategy

## Application tier

The ECS service will start with:

```text
Desired tasks: 2
Minimum tasks: 2
Maximum tasks: 6
```

The tasks will run across two private application subnets.

The intended steady state is:

```text
Availability Zone A: 1 task
Availability Zone B: 1 task
```

ECS Availability Zone rebalancing will remain enabled.

If one task fails:

```text
ALB health check detects the failure
        ↓
ALB stops routing traffic to the task
        ↓
ECS starts a replacement task
        ↓
Replacement passes health checks
        ↓
ALB resumes routing to the healthy capacity
```

If one Availability Zone fails:

```text
Tasks in the affected zone become unavailable
        ↓
ALB routes traffic to healthy tasks in the remaining zone
        ↓
ECS attempts to restore the desired task count
        ↓
Auto Scaling remains available for additional capacity
```

AWS recommends spreading ECS services across Availability Zones. AWS also notes that sufficient remaining capacity must be planned so another Availability Zone can handle demand during a failure.

## Load-balancing tier

The ALB will be attached to two public subnets:

```text
Public Subnet A
Public Subnet B
```

The ALB will have one load-balancer node in each enabled Availability Zone.

AWS requires an Application Load Balancer to use at least two Availability Zones, and recommends healthy registered targets in each enabled zone.

## Database tier

Amazon RDS for PostgreSQL will use a Multi-AZ DB instance deployment.

It will contain:

```text
Primary database instance
Synchronous standby instance
Single database endpoint
Automatic failover capability
```

The application will use the database endpoint instead of a fixed database IP address.

The standby is for availability and failover. It will not be treated as a normal read replica.

RDS Multi-AZ deployments maintain a standby in another Availability Zone and provide failover support. In the standard Multi-AZ DB instance model, the standby does not serve application read traffic.

# 0.8 NAT Gateway Decision

We will use:

```text
One NAT Gateway in Availability Zone A
One NAT Gateway in Availability Zone B
```

Each private application subnet will route internet-bound traffic through the NAT Gateway in the same Availability Zone.

This avoids making both application subnets dependent on one NAT Gateway in one Availability Zone.

The NAT Gateways allow private ECS tasks to reach services such as:

```text
External package repositories
External APIs
Amazon ECR public endpoints
```

Potential endpoints include:


# 0.9 Security Group Design

We will use separate security groups for each tier.

## CloudFront-to-ALB security group

Name:

```text
veriqta-ha-alb-sg
```

Inbound:

```text
TCP 443
Source: CloudFront origin-facing AWS-managed prefix list
```

Outbound:

```text
TCP 3000
Destination: ECS task security group
```

The CloudFront distribution will also send a secret origin header. The ALB listener will forward traffic only when the correct header is present.

The secret header value will not be committed to Git.

AWS recommends restricting an internet-facing ALB to CloudFront origin-facing addresses and using an origin header where appropriate.

## ECS task security group

Name:

```text
veriqta-ha-ecs-sg
```

Inbound:

```text
TCP 3000
Source: veriqta-ha-alb-sg
```

Outbound:

```text
TCP 5432
Destination: veriqta-ha-rds-sg

TCP 443
Destination: required AWS services and external services
```

The ECS tasks will not accept traffic directly from:

```text
0.0.0.0/0
The public subnets
Developer IP addresses
Unrelated security groups
```

## RDS security group

Name:

```text
veriqta-ha-rds-sg
```

Inbound:

```text
TCP 5432
Source: veriqta-ha-ecs-sg
```

The database will not allow:

```text
TCP 5432 from 0.0.0.0/0
Direct public access
Direct developer-laptop access
Inbound SSH
```

# 0.13 Container Design

The application container will:

* Run as a non-root user.
* Use a multi-stage Docker build.
* Contain only runtime dependencies in the final image.
* Expose port `3000`.
* Include a container health check.
* Handle `SIGTERM`.
* Stop accepting new requests during shutdown.
* Complete or terminate active requests safely.
* Log to standard output.
* Avoid storing permanent data inside the container filesystem.
* Use environment variables for nonsecret configuration.
* Receive secrets through the ECS task definition securely.

Container images will be tagged with:

```text
Git commit SHA
Semantic application version
Environment label where required
```

We will avoid deploying only a mutable `latest` tag.


Initial CPU target:

```text

```

Initial memory target:

```text
70 percent
```

The final values will be validated during load testing rather than treated as universal production values.

Scale-out must respond more quickly than scale-in.

Scale-in will use a longer cooldown to reduce unnecessary task termination during temporary traffic changes.

# 0.15 Deployment Strategy

The initial deployment strategy will use ECS rolling deployment with deployment circuit-breaker protection.

The deployment must:

1. Start new tasks.
2. Wait for the tasks to become healthy.
3. Register them with the ALB target group.
4. Gradually stop old tasks.
5. Fail the deployment when replacement tasks cannot become healthy.
6. Roll back when the deployment circuit breaker detects failure.

Later in the project, we will test:

```text
Successful rolling deployment
Application startup failure
Incorrect container port
Failed ALB health check
Bad database configuration
Rollback behavior
```

# 0.16 CI/CD Architecture

GitHub Actions will authenticate to AWS using OpenID Connect.

We will not store long-lived AWS access keys in GitHub.

AWS recommends temporary credentials and IAM roles for human and workload access instead of long-lived credentials.

The pipeline will contain these stages:

```text
1. Checkout repository
2. Install dependencies
3. Run formatting checks
4. Run linting
5. Run unit tests
6. Run application security checks
7. Build Docker image
8. Scan Docker image
9. Authenticate to AWS through OIDC
10. Push image to Amazon ECR
11. Validate Terraform
12. Run Terraform plan
13. Apply approved infrastructure changes
14. Create a new ECS task-definition revision
15. Update the ECS service
16. Wait for service stability
17. Run smoke tests
18. Report deployment result
```

Pull requests will not automatically deploy to production.

# 0.26 Select the AWS Region

The default project Region will be:

```text
us-east-1
```

This is a project decision, not a claim that one Region is best for every application.

Set the Region:

```bash
export AWS_REGION=us-east-1
export AWS_DEFAULT_REGION=us-east-1
```

Verify it:

```bash
aws configure get region --profile "$AWS_PROFILE"
```

When the profile does not yet contain a Region:

```bash
aws configure set region "$AWS_REGION" --profile "$AWS_PROFILE"
```

List available Availability Zones:

```bash
aws ec2 describe-availability-zones \
  --region "$AWS_REGION" \
  --filters Name=state,Values=available \
  --query 'AvailabilityZones[].{Name:ZoneName,State:State,ZoneId:ZoneId}' \
  --output table
```

We will select two available Availability Zones dynamically in Terraform rather than permanently assuming that every AWS account maps Availability Zone letters identically.

# 0.33 What We Will Not Do

This project will not:

* Place ECS tasks in public subnets.
* Assign public IP addresses to application tasks.
* Make RDS publicly accessible.
* allow PostgreSQL from `0.0.0.0/0`.
* Store AWS access keys in GitHub.
* Store passwords in Terraform source files.
* Deploy only one application task.
* Deploy all resources in one Availability Zone.
* use a single NAT Gateway while claiming complete Availability Zone independence.
* Treat Auto Scaling as a replacement for load testing.
* Treat Multi-AZ as a substitute for database backups.
* Treat backups as valid without restore testing.
* Use the AWS root user for normal deployments.
* Commit `.env` files containing real credentials.
* Use SSH access to administer Fargate tasks.
* Depend on container-local storage for persistent application data.
* Claim that single-Region architecture survives every regional failure.
