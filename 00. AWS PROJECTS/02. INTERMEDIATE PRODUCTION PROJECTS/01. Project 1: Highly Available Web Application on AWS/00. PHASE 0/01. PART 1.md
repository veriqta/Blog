# Introduction

Modern web applications must remain available when traffic increases, servers fail, deployments go wrong, or parts of the underlying infrastructure become unavailable.

In this project, you will build a highly available web application on Amazon Web Services. The application will run in containers, use a managed PostgreSQL database, and operate across two Availability Zones.

You will not deploy a single server and call it production-ready. You will build the application as a complete system with:

* Redundant application capacity
* Private application and database networks
* Load balancing
* Automatic task replacement
* Database failover
* Secure traffic handling
* Infrastructure as Code
* Automated delivery
* Logging
* Monitoring
* Alerting
* Backup and recovery procedures

The application is intentionally straightforward so that the main focus remains on production architecture and operations.

By the end of the project, you will understand not only how to deploy an application to AWS, but also how to design it to survive common failures.

# Production Scenario

Assume the application belongs to a growing online service.

Users access the application from different locations. Traffic is usually moderate, but it can increase during campaigns, announcements, or product launches.

The system must continue serving users when:

* One application task crashes.
* A container fails its health check.
* An application deployment is unhealthy.
* The service needs additional capacity.
* One Availability Zone becomes unavailable.
* The primary database instance fails.
* Application tasks are replaced during maintenance.
* A previous application version must be restored.
* Database data must be recovered from backup.

The architecture will therefore avoid depending on:

* One application container
* One Availability Zone
* One public application server
* A publicly accessible database
* Permanent deployment credentials
* Manual infrastructure configuration
* An untested backup

This project focuses on high availability within one AWS Region.

A complete Regional outage is outside the scope of this architecture. Multi-Region recovery would require additional DNS, replication, deployment, data-consistency, and failover decisions.

# Application Overview

The application will be a single Node.js service called:

```text
veriqta-ha-webapp
```

It will use Express to handle HTTP requests and PostgreSQL for persistent storage.

The application will remain stateless at the container level.

This means:

* User data will not be stored permanently inside the container.
* Application tasks can be replaced without losing database records.
* Multiple tasks can serve requests at the same time.
* Scaling does not require copying local files between tasks.
* A failed task can be removed and replaced safely.

Persistent data will be stored in Amazon RDS PostgreSQL.

Application containers will retrieve required configuration when they start. Secrets will not be built into the Docker image or committed to Git.

The same tested container image will be promoted between environments. Environment-specific settings will be supplied at runtime.

# Final Architecture

The final system will use a layered architecture.

## Edge Layer

The edge layer will include:

* Amazon Route 53
* Amazon CloudFront
* AWS WAF
* AWS Certificate Manager

Route 53 will resolve the application domain.

CloudFront will provide the public distribution endpoint and deliver traffic over HTTPS.

AWS WAF will be associated with the CloudFront distribution and inspect requests before they are forwarded to the application origin.

AWS Certificate Manager will provide the certificates required for encrypted traffic.

## Load-Balancing Layer

An internet-facing Application Load Balancer will receive approved origin requests from CloudFront.

The load balancer will:

* Terminate the regional HTTPS connection
* Evaluate the protected origin rule
* Check ECS target health
* Distribute requests across healthy application tasks
* Stop routing to unhealthy targets
* Drain connections during deployments

Although the ALB is internet-facing, it will not be open for unrestricted direct application access. Its network and listener controls will be designed so CloudFront remains the intended public entry point.

## Application Layer

The application layer will use:

* Amazon ECS
* AWS Fargate
* Two private application subnets
* At least two production tasks

The tasks will run across two Availability Zones.

They will not receive public IP addresses.

The Application Load Balancer will send application traffic to port:

```text
3000
```

## Database Layer

The database layer will use:

* Amazon RDS for PostgreSQL
* Two private database subnets
* An RDS Multi-AZ DB instance deployment

The database will not be publicly accessible.

Only the ECS task security group will be allowed to connect to PostgreSQL on port:

```text
5432
```

## Supporting Services

The architecture will also use:

* Amazon ECR for container images
* AWS Secrets Manager for sensitive configuration
* Systems Manager Parameter Store for selected nonsecret configuration
* AWS KMS for encryption where required
* Amazon CloudWatch for logs and metrics
* Amazon SNS for alarm notifications
* Amazon S3 for Terraform state and access logs
* GitHub Actions for automated validation and deployment
* Terraform for Infrastructure as Code

# Architecture Layers

The architecture can be understood as six connected layers.

## Layer 1: DNS and Edge Delivery

```text
Route 53
CloudFront
AWS WAF
```

This layer receives public traffic, provides HTTPS, applies edge security controls, and forwards approved requests to the origin.

## Layer 2: Load Balancing

```text
Application Load Balancer
```

This layer distributes requests across healthy application tasks.

## Layer 3: Application Compute

```text
Amazon ECS
AWS Fargate
```

This layer runs the containerized Node.js application across multiple Availability Zones.

## Layer 4: Persistent Data

```text
Amazon RDS PostgreSQL
```

This layer stores durable application data and provides managed database failover.

## Layer 5: Platform Services

```text
Amazon ECR
Secrets Manager
Parameter Store
KMS
CloudWatch
SNS
S3
```

This layer provides images, configuration, encryption, logs, metrics, alerts, and storage.

## Layer 6: Delivery and Infrastructure Automation

```text
GitHub Actions
Terraform
AWS OIDC
```

This layer validates changes, provisions infrastructure, builds container images, and deploys application versions.

# Request Flow

A normal request travels through the system in the following order:

```text
User
  |
  v
Route 53
  |
  v
CloudFront and AWS WAF
  |
  v
Application Load Balancer
  |
  v
Healthy ECS Fargate task
  |
  v
RDS PostgreSQL, when data is required
  |
  v
Application response
  |
  v
Application Load Balancer
  |
  v
CloudFront
  |
  v
User
```

# Detailed Request Flow

## Step 1: The User Opens the Application

A user enters the application address:

```text
https://app.example.com
```

The domain shown here is an example. The actual project domain will be configured during the Route 53 and TLS phase.

---

## Step 2: Route 53 Resolves the Domain

Amazon Route 53 receives the DNS query.

The application record points to the CloudFront distribution.

Route 53 returns the information required for the user’s browser to connect to CloudFront.

---

## Step 3: CloudFront Receives the HTTPS Request

The user establishes an HTTPS connection with the CloudFront distribution.

CloudFront becomes the public delivery layer for the application.

It can:

* Serve cached content
* Compress supported responses
* Reduce origin traffic
* Use nearby edge locations
* Enforce HTTPS
* Forward dynamic requests to the origin

Dynamic and database-backed application requests will continue to the origin.

---

## Step 4: AWS WAF Evaluates the Request

AWS WAF is associated with the CloudFront distribution.

It evaluates the request using the configured web access control list.

The rule set may inspect:

* Request paths
* Query strings
* Headers
* IP addresses
* Request rates
* Common web attack patterns

A request that violates the WAF policy is blocked at the edge.

An allowed request continues to the Application Load Balancer.

---

## Step 5: CloudFront Sends the Request to the ALB

CloudFront connects to the Application Load Balancer over HTTPS.

It includes a protected origin header that identifies the request as an approved CloudFront origin request.

The Application Load Balancer listener checks for the expected header.

Requests without the expected value are rejected rather than forwarded to the application.

---

## Step 6: The ALB Selects a Healthy Target

The Application Load Balancer maintains a target group containing the private IP addresses of the ECS tasks.

It regularly checks:

```text
GET /health
```

Only targets that pass the health check receive traffic.

The ALB forwards the request over HTTP inside the VPC to:

```text
TCP 3000
```

The ECS task security group permits this traffic only from the ALB security group.

---

## Step 7: The Application Processes the Request

The selected ECS task receives the request.

The Express application:

1. Assigns or accepts a request identifier.
2. Applies middleware.
3. Validates relevant input.
4. Selects the correct route and controller.
5. Runs the required service logic.
6. Queries PostgreSQL when persistent data is needed.
7. Produces a controlled response.
8. Records a structured application log.

Requests that do not require database access can be completed without contacting RDS.

---

## Step 8: The Application Connects to PostgreSQL

For a database-backed operation, the application obtains a connection from its PostgreSQL connection pool.

The task connects to the RDS endpoint on:

```text
TCP 5432
```

The database security group accepts PostgreSQL connections only from the ECS task security group.

The application does not use a fixed database IP address. It uses the managed RDS endpoint so connections can recover after database failover.

---

## Step 9: The Application Returns the Response

The application sends its response to the Application Load Balancer.

The ALB returns it to CloudFront.

CloudFront returns the final HTTPS response to the user.

Eligible content may be cached according to the configured cache policy.

Database-changing operations and other personalized responses will not be cached incorrectly.

# Health Request Flow

The load balancer checks application process health using:

```text
GET /health
```

The intended response is:

```json
{
  "status": "healthy"
}
```

with:

```text
HTTP 200
```

The liveness endpoint does not use the database as its main success condition.

A temporary database interruption should not automatically prove that the Node.js process is dead.

---

# Readiness Request Flow

Deployment validation and operational checks use:

```text
GET /ready
```

The readiness endpoint checks whether the task can serve normal application traffic.

It evaluates:

* Startup completion
* Required configuration
* Database connectivity
* Required internal initialization

A ready task returns:

```json
{
  "status": "ready",
  "database": "connected"
}
```

with:

```text
HTTP 200
```

A task that cannot serve normal traffic returns:

```json
{
  "status": "not_ready",
  "database": "unavailable"
}
```

with:

```text
HTTP 503
```

The target group will initially use `/health`, while deployment validation, smoke tests, dashboards, and operational checks will use `/ready`.

---

# Failure Flow

If an application task stops or becomes unhealthy:

```text
Task failure
    |
    v
ALB target health check fails
    |
    v
ALB stops sending new traffic to the target
    |
    v
ECS detects that the service is below its desired count
    |
    v
ECS launches a replacement task
    |
    v
The replacement completes startup
    |
    v
The replacement passes health checks
    |
    v
ALB begins routing traffic to it
```

If one Availability Zone becomes unavailable, the load balancer continues routing requests to healthy targets in the remaining zone while ECS attempts to restore the desired service capacity.

The final capacity design will be tested. Running two tasks improves redundancy, but it does not automatically prove that one remaining task can handle the full production workload.
