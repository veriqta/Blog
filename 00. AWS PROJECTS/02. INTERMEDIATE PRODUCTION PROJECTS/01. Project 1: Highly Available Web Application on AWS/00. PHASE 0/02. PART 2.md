# High Availability, Network Design, NAT Gateways, Security Groups, TLS, Health Checks, and Database Design

---

# High Availability

A highly available application continues serving users even when individual components fail. Instead of relying on a single server or database, workloads are distributed across multiple Availability Zones (AZs) within the AWS Region.

This project is designed to tolerate common production failures, including:

* An ECS task becoming unhealthy.
* An application container crashing.
* Increased user traffic.
* Failure of a single Availability Zone.
* Failure of the primary database instance.
* Temporary infrastructure interruptions.

To achieve this, the architecture uses:

* Two Availability Zones.
* Multiple ECS tasks.
* Application Load Balancer health checks.
* Amazon RDS PostgreSQL Multi-AZ deployment.
* Automatic ECS service recovery.
* Auto Scaling.
* CloudFront edge locations.
* Redundant NAT Gateways.

The objective is to eliminate single points of failure wherever practical.

# Network Design

The application is deployed inside a dedicated Amazon Virtual Private Cloud (VPC).

The VPC provides complete control over networking, routing, and communication between AWS resources.

The network is divided into separate subnet tiers to improve security and simplify traffic management.

## VPC Layout

The VPC contains six subnets:

* 2 Public Subnets
* 2 Private Application Subnets
* 2 Private Database Subnets

This design distributes resources across two Availability Zones.

```text
Availability Zone A

Public Subnet A
Private Application Subnet A
Private Database Subnet A

Availability Zone B

Public Subnet B
Private Application Subnet B
Private Database Subnet B
```

---

## Public Subnets

Resources deployed in public subnets include:

* Internet Gateway
* Application Load Balancer
* NAT Gateway

Only infrastructure that must communicate directly with the internet is placed in public subnets.

Application containers and databases are never deployed here.

---

## Private Application Subnets

Application workloads run inside private application subnets.

Resources include:

* Amazon ECS
* AWS Fargate Tasks

These resources do not receive public IP addresses.

All inbound traffic reaches them through the Application Load Balancer.

---

## Private Database Subnets

Database resources are isolated inside dedicated private database subnets.

Resources include:

* Amazon RDS PostgreSQL

The database cannot be accessed directly from the internet.

Only approved application services may establish database connections.

---

# NAT Gateways

Although application containers run inside private subnets, they occasionally require outbound internet access.

Examples include:

* Downloading operating system updates.
* Pulling container images.
* Installing application dependencies.
* Connecting to AWS service endpoints.

Instead of exposing private resources directly to the internet, outbound traffic is routed through NAT Gateways.

This project deploys:

* One NAT Gateway in Availability Zone A.
* One NAT Gateway in Availability Zone B.

Each private subnet routes outbound traffic to the NAT Gateway in the same Availability Zone.

This design improves resilience and avoids unnecessary cross-AZ traffic.

---

# Route Tables

Traffic is controlled through separate route tables.

## Public Route Table

Routes:

```text
Destination      Target

VPC CIDR         Local

0.0.0.0/0        Internet Gateway
```

Used by:

* Public Subnet A
* Public Subnet B

---

## Private Application Route Table

Routes:

```text
Destination      Target

VPC CIDR         Local

0.0.0.0/0        NAT Gateway
```

Used by:

* Private Application Subnet A
* Private Application Subnet B

---

## Private Database Route Table

Routes:

```text
Destination      Target

VPC CIDR         Local
```

Database subnets do not require direct internet access.

# Security Groups

Security Groups act as virtual firewalls for AWS resources.

Each layer of the application has its own Security Group with only the minimum required access.

---

## Application Load Balancer Security Group

Inbound

* HTTPS (443) from the internet

Outbound

* ECS Security Group

---

## ECS Security Group

Inbound

* Application traffic from the Load Balancer only.

Outbound

* Amazon RDS
* AWS services
* Internet through the NAT Gateway

No direct internet traffic reaches ECS tasks.

---

## Database Security Group

Inbound

* PostgreSQL (5432) from the ECS Security Group only.

Outbound

* Default AWS response traffic.

The database never accepts connections from the public internet.

---

# TLS Encryption

All external communication uses HTTPS.

AWS Certificate Manager (ACM) provides SSL/TLS certificates for the application domain.

Traffic flow:

```text
User

↓

HTTPS

↓

CloudFront

↓

HTTPS

↓

Application Load Balancer

↓

HTTP or HTTPS (inside the VPC)

↓

ECS Application
```

Encryption protects data exchanged between users and the application.

Sensitive information such as login credentials, API requests, and session data is never transmitted over unencrypted HTTP.

# Health Checks

Health checks allow AWS services to determine whether an application is functioning correctly.

If an application instance becomes unhealthy, it is automatically removed from service until it recovers or is replaced.

---

## Load Balancer Health Checks

The Application Load Balancer periodically sends requests to:

```text
/health
```

A healthy response returns:

```http
HTTP/1.1 200 OK
```

If repeated failures occur, the target is marked unhealthy and no longer receives user traffic.

---

## ECS Service Recovery

Amazon ECS continuously monitors running tasks.

If a task:

* Stops unexpectedly
* Crashes
* Becomes unhealthy

ECS automatically launches a replacement task to maintain the desired service count.

---

## Readiness Endpoint

The application also exposes:

```text
/ready
```

This endpoint verifies that the application is fully prepared to process requests.

Typical readiness checks include:

* Database connectivity.
* Required configuration loaded.
* Essential services available.

A task is considered ready only after all required dependencies are operational.

# Database Design

The application stores persistent data in Amazon RDS for PostgreSQL.

The database is deployed using Amazon RDS Multi-AZ.

---

## Why PostgreSQL?

PostgreSQL is selected because it provides:

* ACID-compliant transactions.
* Strong data integrity.
* Excellent reliability.
* Broad ecosystem support.
* Enterprise-grade performance.

---

## Multi-AZ Deployment

The database consists of:

* One primary database instance.
* One synchronous standby instance in a different Availability Zone.

```text
Primary Database

↓

Synchronous Replication

↓

Standby Database
```

If the primary instance fails, Amazon RDS automatically promotes the standby instance, reducing downtime without requiring manual intervention.

---

## Database Security

The database:

* Runs inside private database subnets.
* Has no public IP address.
* Accepts connections only from ECS tasks.
* Stores credentials securely using AWS Secrets Manager.
* Encrypts storage using AWS Key Management Service (KMS).
* Performs automated backups and supports point-in-time recovery.
