# High-Availability Design

High availability means the application does not depend on a single server, container, database host, or Availability Zone.

This project distributes the application across two Availability Zones in `us-east-1`. Each Availability Zone contains its own public subnet, private application subnet, and private database subnet.

The production environment will begin with two ECS tasks:

```text
Availability Zone A: 1 ECS task
Availability Zone B: 1 ECS task
```

The initial ECS service capacity will be:

```text
Minimum tasks: 2
Desired tasks: 2
Maximum tasks: 6
```

Amazon ECS will maintain the desired number of tasks and use Availability Zone rebalancing to keep the service distributed as evenly as possible. When ECS detects an uneven distribution, it can start tasks in an underrepresented zone before stopping tasks in an overrepresented zone.

If one task fails:

```text
Application task fails
        |
        v
The target becomes unhealthy
        |
        v
The ALB stops sending new requests to it
        |
        v
ECS starts a replacement task
        |
        v
The replacement completes startup
        |
        v
The replacement passes its health check
        |
        v
The ALB begins routing requests to it
```

If one Availability Zone becomes unavailable, the Application Load Balancer continues sending traffic to healthy targets in the remaining zone while ECS attempts to restore the desired service capacity.

Two tasks provide redundancy, but they do not automatically prove that one remaining task can handle the full workload. Later in the project, load testing will determine whether the remaining capacity can serve expected traffic during a zonal failure.

```text
VPC CIDR: 10.30.0.0/16
```

Terraform will discover two available Availability Zones dynamically. The project will not hard-code zone names such as `us-east-1a` and `us-east-1b`, because AWS Availability Zone letters can map differently between accounts.

# Subnet Responsibilities

## Public Subnets

The public subnets contain:

* Application Load Balancer nodes
* NAT Gateways

A public subnet has a route to the Internet Gateway.

The application containers and databases will not run in public subnets.

## Private Application Subnets

The private application subnets contain:

* ECS Fargate tasks

The tasks will not receive public IP addresses.

Inbound application traffic reaches the tasks only through the Application Load Balancer.

Outbound traffic uses the NAT Gateway in the same Availability Zone or an approved VPC endpoint.

## Private Database Subnets

The private database subnets contain:

* Amazon RDS PostgreSQL

The database subnets do not have a default route to the internet.

The RDS database will not be publicly accessible.

---

# Internet Gateway

Each environment VPC will have one Internet Gateway.

The Internet Gateway provides internet connectivity for resources in the public subnets.

It is used by:

* The Application Load Balancer
* NAT Gateway A
* NAT Gateway B

Attaching an Internet Gateway to a VPC does not make every resource public. A resource also needs the correct subnet route, network controls, and public addressing before it can communicate directly with the internet.

# NAT Gateway Design

Each environment will use two NAT Gateways:

```text
NAT Gateway A
NAT Gateway B
```

NAT Gateway A will run in Public Subnet A.

NAT Gateway B will run in Public Subnet B.

Each NAT Gateway will have its own Elastic IP address.

The routing relationship will be:

```text
Private App Subnet A
        |
        v
NAT Gateway A
        |
        v
Internet Gateway
```

```text
Private App Subnet B
        |
        v
NAT Gateway B
        |
        v
Internet Gateway
```

This prevents both application subnets from depending on a NAT Gateway in one Availability Zone.

Private ECS tasks may use outbound connectivity for:

* Pulling container images from Amazon ECR
* Retrieving secrets
* Sending logs to CloudWatch Logs
* Reaching approved external APIs
* Connecting to AWS public service endpoints when a VPC endpoint is not configured

The running application container will not install operating-system packages or Node.js dependencies during startup. Application dependencies will already be included in the tested Docker image.

# Application Load Balancer Security Group

The Application Load Balancer is internet-facing because it is the CloudFront origin.

However, it will not accept unrestricted application traffic from the entire internet.

## Inbound Rule

```text
Protocol: TCP
Port: 443
Source: AWS-managed CloudFront origin-facing prefix list
```

The CloudFront managed prefix list contains the address ranges used by CloudFront origin-facing servers. AWS documents using this prefix list to restrict an AWS-hosted origin so non-CloudFront traffic cannot reach it through the allowed Security Group rule.

## Outbound Rule

```text
Protocol: TCP
Port: 3000
Destination: ECS task Security Group
```

## Protected Origin Header

CloudFront will add a secret custom header to requests sent to the ALB.

The ALB HTTPS listener will contain:

1. A forwarding rule that matches the protected header.
2. A default rule that returns a fixed rejection response.

AWS documents this custom-header pattern as a way to prevent viewers from accessing an internet-facing ALB directly. The header name and value must remain secret.

The real header value must not appear in:

* Git
* Terraform variable defaults
* Blog screenshots
* Documentation examples
* GitHub workflow files
* Application logs
* Pull-request descriptions

# ECS Task Security Group

## Inbound Rule

```text
Protocol: TCP
Port: 3000

```

The ECS tasks will not accept application traffic from:

* `0.0.0.0/0`
* Public subnets generally

* Unrelated Security Groups

## Outbound Rule to PostgreSQL


## Outbound HTTPS

```text

```

The ECS tasks will not receive public IP addresses.

# Network ACL Strategy

The project will initially use the default stateful behaviour of Security Groups as the primary resource-level network control.

Custom Network ACLs will not be introduced without a specific requirement.

Adding complex stateless Network ACL rules too early can create difficult-to-diagnose connectivity failures, especially because return traffic and ephemeral ports must be allowed explicitly.

The private subnet design, route tables, Security Groups, WAF rules, and IAM controls provide the main security boundaries for this project.

# TLS Design

The project uses three communication boundaries.

## User to CloudFront

```text
Protocol: HTTPS
Port: 443
```

CloudFront presents the public application certificate.

HTTP requests will be redirected to HTTPS.

## CloudFront to Application Load Balancer

```text
Protocol: HTTPS
Port: 443
```

CloudFront validates the certificate presented by the ALB origin.

The ALB certificate must match the origin domain configured in CloudFront.

## Application Load Balancer to ECS

```text
Protocol: HTTP
Port: 3000
```

This traffic remains inside the VPC and is permitted only between the ALB and ECS Security Groups.

TLS will not terminate inside each Node.js container in this project.

## ECS to PostgreSQL

```text
Protocol: PostgreSQL over TLS
Port: 5432
```

The application will require an encrypted database connection and validate the RDS certificate chain using the appropriate AWS trust bundle.

# Certificate Design

Two ACM certificate associations are required.

## CloudFront Certificate

The CloudFront viewer certificate must exist in:

```text
us-east-1
```

It will cover the public application hostname, for example:

```text
app.example.com
```

## Application Load Balancer Certificate

The ALB certificate must exist in the same Region as the ALB:

```text
us-east-1
```

It will cover the ALB origin hostname selected for CloudFront, for example:

```text

```

Using separate public and origin hostnames keeps the viewer endpoint and origin endpoint clearly separated.

The final domain names will be supplied during the Route 53 and TLS implementation phase.

# Health-Check Design

The project separates liveness from readiness.

## Liveness Endpoint

```text
GET /health
```

Purpose:

Confirm that the Node.js process is running and able to respond.

Expected response:

```json
{
  "status": "healthy"
}
```

Expected status:

```text
HTTP 200
```

The liveness endpoint will not perform a database query.

A temporary database failure should not automatically prove that the application process is dead.

## Readiness Endpoint

```text
GET /ready
```

Purpose:

Confirm that the task is ready to serve normal application traffic.

The readiness check will validate:

* Startup completion
* Required configuration
* Database connection-pool availability
* Database connectivity
* Required internal initialization

Healthy response:

```json
{
  "status": "ready",
  "database": "connected"
}
```

Healthy status:

```text
HTTP 200
```

Unavailable response:

```json
{
  "status": "not_ready",
  "database": "unavailable"
}
```

Unavailable status:

```text
HTTP 503
```

---

# ALB Target Group Health Check

The target group will initially use:

```text
Protocol: HTTP
Port: traffic-port
Path: /health
Healthy threshold: 2
Unhealthy threshold: 3
Timeout: 5 seconds
Interval: 30 seconds
Success code: 200
```

Application Load Balancer target groups support configurable HTTP health-check paths, and health checks are performed for registered targets used by listener rules.

The target group will use `/health`, not `/ready`.

This prevents a temporary database interruption from causing every running application task to be treated as a dead process.

The `/ready` endpoint will instead be used for:

* Deployment validation
* Post-deployment smoke tests
* Dashboards
* Operational checks
* Database availability monitoring

The starting health-check values will be tested later. They may be adjusted only after observing real startup time and failure behaviour.

---

# Container Health Check

The container will also have a local health check against:

```text
http://localhost:3000/health
```

The container health check confirms that the application process inside the task is responding.

The ALB health check and container health check serve related but different purposes:

* The container check evaluates the application inside the task.
* The ALB check determines whether the target should receive load-balanced traffic.

# RDS Deployment Model

Production will use:

```text
RDS Multi-AZ DB instance deployment
```

This design contains:

* One primary DB instance
* One synchronous standby DB instance
* Two Availability Zones
* One database endpoint
* Managed failover support

The standby exists for high availability and failover. It does not serve normal application read traffic. AWS distinguishes this model from a Multi-AZ DB cluster, whose additional instances can serve reads.

When a qualifying planned or unplanned outage affects the primary, RDS can switch to the standby in another Availability Zone.

Development will follow the same network and security model. Its exact database size and availability settings may be adjusted to control cost, but any difference must be stated clearly during implementation. Production will use the Multi-AZ DB instance design defined here.

The database will contain:

* A dedicated application schema

* A records table
* Required constraints
* Required indexes

All schema changes will use versioned migrations.

# Database Connection Management

The application will use a PostgreSQL connection pool.

The pool will have controlled values for:

* Maximum connections
* Connection timeout
* Idle timeout
* Query timeout where appropriate

The application must avoid creating one permanent database connection for every incoming request.

The pool size will be selected with awareness of:

* Number of ECS tasks
* Maximum Auto Scaling capacity
* RDS connection limits
* Administrative connections
* Migration connections
* Monitoring connections

Scaling the application increases the possible number of database connections. Auto Scaling policies must therefore consider database capacity, not only ECS CPU and memory.

---

# Database Failure Handling

The application will:

* Use connection timeouts
* Return controlled errors
* Avoid infinite retry loops
* Reconnect after temporary failures
* Avoid exposing database details to users
* Record safe operational errors
* Report failed readiness when the database is unavailable

During RDS failover, existing database connections may be interrupted.

The application will use the RDS DNS endpoint and allow the connection pool to establish new connections after failover.

---

# Database Encryption

The RDS database will use:

* Encryption at rest
* AWS KMS
* TLS for application connections
* Encrypted automated backups
* Encrypted snapshots

Secrets Manager will protect database credentials.

Encryption does not replace access control. IAM, Security Groups, private subnets, restricted database roles, and secret-management controls remain necessary.

# Database Backup Foundation

The production database will use:

* Automated backups
* Point-in-time recovery
* A defined retention period
* A controlled backup window
* Deletion protection
* A final snapshot before approved destruction

Multi-AZ improves availability, but it is not a backup.

The synchronous standby can receive the same accidental deletion, invalid migration, or unwanted data change as the primary.

Backup and restore testing will be covered in Part 3 and implemented later in the project.

# Common Architecture Mistakes

## Opening the ALB to the Entire Internet

Allowing HTTPS from `0.0.0.0/0` would permit direct origin access and bypass the intended CloudFront and WAF entry path.

The ALB will accept origin traffic only from the CloudFront managed prefix list and will require the protected origin header.

## Using One NAT Gateway for Both Availability Zones

A single NAT Gateway creates a zonal dependency for private outbound traffic.

This project uses one NAT Gateway per Availability Zone.

## Giving ECS Tasks Public IP Addresses

Fargate tasks do not need direct public exposure.

They receive inbound application traffic only from the ALB.

## Making RDS Public for Convenience

The database remains private.

Administrative convenience is not a valid reason to expose PostgreSQL to the internet.

## Using `/ready` as a Restart Signal Without Considering Dependencies

A temporary database interruption should not trigger uncontrolled replacement of every application task.

The ALB and container liveness checks use `/health`.

## Treating Multi-AZ as Read Scaling

The selected standby supports failover and does not serve normal application reads.

## Treating Multi-AZ as a Backup

Availability and recoverability are separate concerns.

Backups must still be retained and restored during recovery tests.

The application now has a fixed network, security, health, and database design.

The architecture uses:

* Separate development and production VPCs
* Two Availability Zones per environment
* Two public subnets
* Two private application subnets
