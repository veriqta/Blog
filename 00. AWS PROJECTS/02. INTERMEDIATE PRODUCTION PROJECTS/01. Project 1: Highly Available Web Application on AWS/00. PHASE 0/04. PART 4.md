# Terraform Design

Terraform will provision and manage the AWS infrastructure used throughout this project.

Instead of creating production resources manually in the AWS Management Console, the infrastructure will be defined in version-controlled configuration files.

Terraform will manage resources such as:

* VPCs
* Subnets
* Route tables
* Internet Gateways
* NAT Gateways
* Elastic IP addresses
* Security Groups
* VPC endpoints
* Amazon ECR
* Amazon ECS
* AWS Fargate task definitions
* ECS services
* Application Load Balancers
* Target groups
* Amazon RDS
* AWS Secrets Manager
* Systems Manager Parameter Store
* AWS Certificate Manager
* Amazon CloudFront
* AWS WAF
* Route 53 records
* CloudWatch log groups
* CloudWatch dashboards and alarms
* Amazon SNS topics
* IAM roles and policies
* Amazon S3 buckets

Terraform configuration will be reviewed and tested in the same way as application code.

Infrastructure changes should be:

* Repeatable
* Reviewable
* Documented
* Tested
* Traceable to Git
* Applied through controlled workflows

Manual AWS changes can create configuration drift, where the deployed infrastructure no longer matches the Terraform configuration.

Permanent infrastructure changes should therefore be made through Terraform.

# Bootstrap Configuration

The bootstrap configuration will create the resources Terraform needs before it can store remote state.

Planned structure:

```text
infrastructure/
└── bootstrap/
    ├── main.tf
    ├── outputs.tf
    ├── providers.tf
    ├── variables.tf
    └── versions.tf
```

The bootstrap configuration will create:

* An S3 bucket for Terraform state
* S3 bucket versioning
* Server-side encryption
* Public-access blocking
* Ownership controls
* Lifecycle protection
* Required bucket policies

The state bucket must exist before the development and production configurations can initialize their remote backends.

# Terraform Modules

Reusable infrastructure components will be implemented as Terraform modules.

Planned structure:

```text
infrastructure/
└── modules/
    ├── certificates/
    ├── cicd-identity/
    ├── cloudfront/
    ├── database/
    ├── dns/
    ├── ecr/
    ├── ecs-cluster/
    ├── ecs-service/
    ├── load-balancer/
    ├── monitoring/
    ├── networking/
    ├── secrets/
    ├── security/
    └── waf/
```

Each module will have one clear responsibility.

For example:

* `networking` will create the VPC, subnets, Internet Gateway, NAT Gateways, and route tables.
* `security` will create Security Groups and related network controls.
* `database` will create the RDS subnet group, database instance, and database monitoring resources.
* `ecs-cluster` will create the ECS cluster and cluster-level settings.
* `ecs-service` will create the task definition, ECS service, and service Auto Scaling.
* `load-balancer` will create the ALB, listener, target group, and origin-protection rule.
* `monitoring` will create dashboards, alarms, SNS topics, and log-retention settings.

Modules will expose only the outputs required by other components.

# Terraform Remote State

Terraform state records the relationship between the Terraform configuration and the AWS resources it manages.

The state must not be:

* Committed to Git
* Stored permanently on one engineer’s laptop
* Shared through email
* Uploaded to public storage
* Edited manually without a controlled recovery reason

This project will use an Amazon S3 backend.

The state bucket naming pattern will be:

```text
veriqta-ha-terraform-state-ACCOUNT_ID-us-east-1
```

Example:

```text
veriqta-ha-terraform-state-123456789012-us-east-1
```

The AWS account ID will be obtained dynamically during implementation.

---

# Terraform State Keys

Development will use:

```text
development/terraform.tfstate
```

Production will use:

```text
production/terraform.tfstate
```

This keeps the state files separate even though they are stored in the same protected backend bucket.

The environments will not share one state object.

---

# S3 Backend Configuration

The backend configuration will use S3-native state locking.

Example development backend:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-ha-terraform-state-ACCOUNT_ID-us-east-1"
    key          = "development/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

Example production backend:

```hcl
terraform {
  backend "s3" {
    bucket       = "veriqta-ha-terraform-state-ACCOUNT_ID-us-east-1"
    key          = "production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

HashiCorp documents `use_lockfile = true` as the S3 backend setting for state locking and strongly recommends enabling bucket versioning for state recovery.

A new DynamoDB locking table will not be created for this project.

---

# Terraform State Protection

The remote-state bucket will use:

* S3 bucket versioning
* Server-side encryption
* Public-access blocking
* Restricted IAM access
* Ownership controls
* Protected deletion behaviour
* Separate development and production keys

Bucket versioning provides a recovery path if a state object is accidentally deleted or overwritten.

State recovery must still be performed carefully. Restoring the wrong state version can cause Terraform to propose incorrect infrastructure changes.

# Terraform Dependency Lock File

Terraform creates a dependency lock file named:

```text
.terraform.lock.hcl
```

This file records the selected provider versions and checksums.

It will be committed to Git.

The following directory will not be committed:

```text
.terraform/
```

The `.terraform` directory contains downloaded providers, backend initialization data, and other local working files.

HashiCorp documents `.terraform.lock.hcl` as the dependency lock file used to retain provider selections between Terraform runs.

---

# Terraform Version Control Rules

The following files may be committed:

```text
*.tf
*.tfvars.example
backend.hcl.example
.terraform.lock.hcl
```

The following files must not be committed:

```text
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
terraform.tfvars
*.auto.tfvars
backend.hcl
```

Real variable files may contain:

* AWS account identifiers
* Domain names
* Environment-specific settings
* Resource sizes
* Sensitive references

Only safe example files will be included in the repository.

# Terraform Workflow

The normal Terraform workflow will be:

```text
terraform fmt
      |
      v
terraform init
      |
      v
terraform validate
      |
      v
terraform plan
      |
      v
Review the plan
      |
      v
terraform apply
```

Before a production apply, the plan must be reviewed for:

* Resources being created
* Resources being changed
* Resources being replaced
* Resources being destroyed
* Security Group changes
* IAM permission changes
* Database changes
* Route changes
* Public exposure
* Cost impact
* Unexpected drift

The project will not use targeted Terraform operations as the normal deployment method.

Commands such as:

```bash
terraform apply -target=...
```

may create partial changes and should be reserved for controlled recovery situations.

# Confirm Availability Zones

Run:

```bash
aws ec2 describe-availability-zones \
  --profile "$AWS_PROFILE" \
  --region "$AWS_REGION" \
  --filters Name=state,Values=available \
  --query 'AvailabilityZones[].{Name:ZoneName,ZoneId:ZoneId,State:State}' \
  --output table
```

At least two Availability Zones must be available.

Terraform will discover the zones dynamically.

The network configuration will not permanently hard-code names such as:

```text
us-east-1a
us-east-1b
```

Availability Zone letters can map differently between AWS accounts.

```text
Cannot connect to the Docker daemon
```

Start Docker Desktop or the Docker service.

On a Linux system using `systemd`, this may be:

```bash
sudo systemctl start docker
```

Verify:

```bash
docker info
```

## Docker Compose Is Missing

Check:

```bash
docker compose version
```

Docker Desktop includes Compose.

On a supported Linux distribution, install the Compose plugin using Docker’s repository instructions.

## Git Uses the Wrong Branch

Run:

```bash
git branch -M main
```

Verify:

```bash
git branch --show-current
```

---

## AWS Returns AccessDenied

Check:

* The selected AWS profile
* The selected AWS account
* The IAM Identity Center permission set
* Whether the session expired
* The requested AWS action
* Whether an organizational policy blocks the action

Do not solve every permission problem by granting unrestricted administrator access.

Later phases will define the exact permissions needed by application and deployment roles.

---

## Terraform Cannot Acquire the State Lock

Do not immediately disable locking with:

```bash
-lock=false
```

First confirm whether another Terraform process is still running.

State locking exists to prevent simultaneous writes and possible state corruption. HashiCorp does not recommend disabling locking for normal operations.

A force unlock should be used only when:

* The original Terraform process is no longer running
* The lock is confirmed to be stale
* The lock identifier is correct
* No other engineer or workflow is using the state
