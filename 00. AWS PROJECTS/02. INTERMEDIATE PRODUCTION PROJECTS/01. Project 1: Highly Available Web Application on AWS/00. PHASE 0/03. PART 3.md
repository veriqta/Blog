# Container Design

The application will run as a Docker container on Amazon ECS using AWS Fargate.

The container image will package the application and its production dependencies into one versioned deployment artifact. The same tested image will be promoted from development to production. Production will not rebuild the application from different source code or dependency versions.

The container image name will be:

```text
veriqta-ha-webapp
```

The Amazon ECR repository will also be named:

```text
veriqta-ha-webapp
```

The container will listen on:

```text
TCP 3000
```

---

# Production Docker Image

The application will use a multi-stage Docker build.

The build stage will install dependencies, prepare the application, and run any required build steps.

The final runtime stage will contain only the files and dependencies required to run the application.

The production image will:

* Use a supported Node.js LTS runtime.
* Install dependencies from the committed lock file.
* Include only production dependencies.
* Run as a non-root user.
* Expose port `3000`.
* Include a container health check.
* Handle termination signals correctly.
* Write logs to standard output and standard error.
* Avoid unnecessary operating-system packages.
* Avoid storing secrets inside image layers.
* Avoid installing packages during normal container startup.
* Avoid storing permanent application data inside the container.

Application dependencies will be installed while the image is built, not every time an ECS task starts.

---

# Immutable Image Strategy

Container images will be treated as immutable.

Each successful build will produce a uniquely identifiable image.

The image will receive:

* A semantic application version.
* A Git commit SHA tag.
* An immutable ECR image digest.

Example tags:

```text
veriqta-ha-webapp:1.0.0
veriqta-ha-webapp:a38f7c2
```

A production deployment will reference a known image digest or immutable tag.

The project will not depend only on:

```text
latest
```

A mutable tag does not provide enough information to prove which application version is running.

The same approved image will move through the environments:

```text
Build once
    |
    v
Test and scan
    |
    v
Deploy to development
    |
    v
Validate
    |
    v
Promote the same image digest
    |
    v
Deploy to production
```

---

# Amazon ECR Design

Amazon Elastic Container Registry will store the private application images.

The repository will use:

* Encryption at rest.
* Image scanning.
* Immutable deployment references.
* Controlled IAM access.
* Lifecycle rules for old images.
* Retention of recent stable releases.

The lifecycle policy will remove old untagged images after they are no longer required.

Recent stable production images will remain available for rollback.

The project will not delete the only known working image during normal cleanup.

## Secret configuration

Sensitive values will be stored in AWS Secrets Manager.

Examples include:

* Source code.
* Dockerfiles.

* GitHub workflow files.
* Terraform variable defaults.
* Public documentation.
* CloudWatch logs.

The application will validate required configuration during startup. If a critical value is missing or invalid, the process will stop with a controlled error rather than running with incomplete configuration.

# Graceful Shutdown

ECS may stop a task during:

* Rolling deployments.
* Auto Scaling events.
* Health recovery.
* Infrastructure maintenance.
* Manual service updates.

When the Node.js process receives `SIGTERM`, it will:

1. Mark the application as no longer ready.
2. Stop accepting new requests.
3. Allow active requests a limited time to finish.
4. Stop background work.
5. Close the HTTP server.
6. Close PostgreSQL pool connections.
7. Flush pending logs where possible.
8. Exit with a controlled status.

A shutdown timeout will prevent the process from waiting indefinitely.

Graceful shutdown will work together with the Application Load Balancer deregistration delay so active requests have time to complete before an old task is removed.

# ECS Service Capacity

The production ECS service will begin with:

```text
Minimum tasks: 2
Desired tasks: 2
Maximum tasks: 6
```

The minimum capacity remains two so production does not scale down to one application task during normal operation.

The development environment may use a lower running capacity when it is not being used for high-availability testing. Any temporary cost-saving difference will be clearly shown during implementation. Production will keep the two-task minimum defined here.

---

# Auto Scaling Design

Amazon ECS Service Auto Scaling will adjust the desired task count within the configured minimum and maximum.

The project will use target-tracking scaling policies.

Target tracking attempts to keep a selected metric close to its configured target by adding or removing tasks. ECS Service Auto Scaling prioritizes availability by scaling out more aggressively and scaling in more gradually. Scale-in is suspended during ECS deployments, while scale-out can continue.

The initial scaling signals will be:

* Average ECS CPU utilization.
* Average ECS memory utilization.
* Application Load Balancer request count per target, when validated as useful for the workload.

Initial targets:

```text
CPU utilization target: 60 percent
Memory utilization target: 70 percent
```

These values are starting points, not guaranteed production thresholds.

Load testing will determine whether they are appropriate.

---

# Scaling Behaviour

A typical scale-out event will follow this path:

```text
Traffic increases
        |
        v
CPU, memory, or request load rises
        |
        v
The target-tracking policy detects sustained demand
        |
        v
The ECS desired task count increases
        |
        v
New Fargate tasks start
        |
        v
Tasks load configuration and secrets
        |
        v
Tasks pass container and ALB health checks
        |
        v
The ALB begins routing traffic to them
```

When demand falls, the service can scale in gradually without dropping below two production tasks.

---

# Scaling Cooldowns

The scaling policies will use cooldown periods.

The initial design will use:

```text
Scale-out cooldown: 60 seconds
Scale-in cooldown: 300 seconds
```

The shorter scale-out cooldown allows the service to respond to sustained demand.

The longer scale-in cooldown reduces rapid task removal during temporary traffic drops.

These values will be tested against:

* Application startup time.
* Health-check timing.
* Traffic patterns.
* Database capacity.
* Deployment behaviour.

Amazon ECS publishes service CPU and memory metrics to CloudWatch, and Service Auto Scaling supports cooldown periods to allow previous scaling activities to take effect.

---

# Database Capacity During Scaling

Application scaling can increase database pressure.

For example:

```text
Maximum ECS tasks: 6
Maximum pool size per task: 10
Potential application connections: 60
```

This does not include:

* Administrative connections.
* Migration connections.
* Monitoring connections.
* Temporary recovery connections.

The final application connection-pool size must remain within the safe RDS connection capacity.

Auto Scaling will not be considered successful if the application tier scales while exhausting the database.

# Deployment Strategy

The ECS service will use a rolling deployment.

A rolling deployment replaces old tasks with tasks running the new task-definition revision.

The deployment will use:

```text
Minimum healthy percentage: 100
Maximum percentage: 200
```

With a desired count of two tasks, ECS may temporarily run up to four tasks during deployment.

This allows the existing tasks to continue serving requests while the replacement tasks start and become healthy.

---

# Rolling Deployment Flow

```text
A new image is approved
        |
        v
A new ECS task-definition revision is registered
        |
        v
The ECS service starts replacement tasks
        |
        v
The tasks enter RUNNING state
        |
        v
Container health checks pass
        |
        v
ALB target health checks pass
        |
        v
The service reaches stable healthy capacity
        |
        v
Old targets begin connection draining
        |
        v
Old tasks stop
        |
        v
Smoke tests confirm the deployed version
```

The deployment is not considered successful simply because the new containers entered the `RUNNING` state.

The application must also pass health checks and post-deployment validation.

---

# Deployment Circuit Breaker

The ECS deployment circuit breaker will be enabled with rollback.

It evaluates whether replacement tasks can start and remain healthy.

The circuit breaker monitors two broad stages:

1. Whether tasks reach the `RUNNING` state.
2. Whether running tasks pass supported container and load-balancer health checks.

When a deployment fails and rollback is enabled, ECS can return the service to the most recent successfully completed deployment.

The service will also expose deployment failure events for monitoring and alerting.

---

# Connection Draining

The Application Load Balancer target group will use a deregistration delay.

Initial value:

```text
Deregistration delay: 60 seconds
```

When an old task is removed:

1. The ALB stops assigning new requests to it.
2. Existing connections receive time to complete.
3. The application handles `SIGTERM`.
4. The task closes safely.
5. ECS stops the container.

The value will be reviewed after testing actual request durations.

A request that legitimately runs longer than the configured delay may still be interrupted, so long-running operations should not rely on unlimited HTTP connection time.

---

# Deployment Validation

After each deployment, the pipeline will verify:

* The ECS service reached a stable state.
* The expected number of tasks is running.
* ALB targets are healthy.
* `/health` returns `HTTP 200`.
* `/ready` returns `HTTP 200`.
* `/version` reports the expected application version.
* A database read succeeds.
* A controlled database write succeeds where appropriate.
* Application error rates remain acceptable.
* No immediate rollback condition is present.

A deployment is complete only after these checks pass.

---

# Rollback Strategy

The primary application rollback method will be:

```text
Redeploy the last known healthy ECS task-definition revision
```

That revision will reference a previously tested immutable image.

Rollback may be triggered when:

* New tasks cannot start.
* Health checks fail.
* Readiness remains unavailable.
* Error rates increase significantly.
* Critical application operations fail.
* Latency becomes unacceptable.
* Required permissions are missing.
* The new version cannot connect to PostgreSQL.

Database migrations require additional care.

A previous application version may not work after an incompatible schema change. Database migrations will therefore be designed for backward compatibility wherever practical.

---

# Database Deployment Compatibility

Application and schema changes will follow an expand-and-contract approach when possible.

Example:

1. Add a new nullable column or table.
2. Deploy application code that can use both old and new structures.
3. Migrate or backfill data.
4. Confirm the old version is no longer required.
5. Remove obsolete structures in a later controlled change.

The project will avoid combining an irreversible destructive migration with the first deployment that requires it.

# GitHub Actions Authentication

GitHub Actions will authenticate to AWS through OpenID Connect.

OIDC allows a workflow to request short-lived cloud credentials rather than storing long-lived AWS access keys in GitHub. GitHub recommends restricting the AWS trust policy so only approved repositories, branches, tags, or environments can assume the role.

The workflow requires:

```yaml
permissions:
  id-token: write
  contents: read
```

The `id-token: write` permission allows the job to request an OIDC token. It does not, by itself, grant permission to modify AWS resources. AWS permissions come from the IAM role assumed by the workflow.

# Application Logging

The application will write structured JSON logs to standard output and standard error.

Amazon ECS will use the `awslogs` log driver to send container output to CloudWatch Logs. AWS documents that the driver forwards the container’s `STDOUT` and `STDERR` streams, and Fargate task definitions must include the required log configuration.

A typical application log will contain:

```json
{
  "timestamp": "2026-08-03T12:00:00.000Z",
  "level": "info",
  "service": "veriqta-ha-webapp",
  "environment": "production",
  "version": "1.0.0",
  "commitSha": "a38f7c2",
  "requestId": "example-request-id",
  "method": "GET",
  "path": "/records",
  "statusCode": 200,
  "durationMs": 42
}
```

---

# Log Levels

The application will use:

```text

warn

```

## Debug

Detailed diagnostic information.

Disabled by default in production unless temporarily approved.

## Info

Normal application events such as startup, shutdown, and completed requests.

## Warn

## Error

# Backup Strategy

High availability and backups solve different problems.

RDS Multi-AZ provides a standby for infrastructure failover.

It does not protect against:

* Accidental record deletion.
* Invalid application writes.
* Destructive migrations.
* Logical corruption.
* Compromised credentials.
* An administrator deleting correct data.

The project will therefore use both availability controls and recoverable backups.

---

# RDS Automated Backups

Production RDS will use:

```text
Automated backups: enabled
Backup retention: 14 days
Point-in-time recovery: enabled
Storage encryption: enabled
Deletion protection: enabled
Copy tags to snapshots: enabled
Final snapshot on approved deletion: required
```

Development RDS will use:

```text
Automated backups: enabled
Backup retention: 7 days
Storage encryption: enabled
```

Development deletion settings may be less restrictive to control project cost, but production protections will remain enabled.

---

# Backup Window

A defined backup window will be configured outside the expected peak usage period.

The final UTC window will be selected during the RDS implementation phase after the project’s assumed operating schedule is documented.

The maintenance window and backup window will not overlap unnecessarily.

---

# Manual Snapshots

A manual snapshot may be created before:

* A major database migration.
* A database engine upgrade.
* A high-risk production change.
* An approved destructive operation.
* A disaster-recovery exercise.

Manual snapshots will be tagged with:

* Project.
* Environment.
* Purpose.
* Change reference.

* Owner.

A manual snapshot does not replace the migration rollback or forward-recovery plan.

---

# Point-in-Time Recovery

Point-in-time recovery will be used when the required recovery point falls within the automated backup retention window.

RDS restore operations create a new database instance.

They do not overwrite the existing database in place.

The restored instance must be validated before application traffic is directed to it.

---

# Recovery Validation

A backup is not considered proven until it has been restored successfully.

Recovery testing will verify:

* The restored instance starts.
* PostgreSQL accepts TLS connections.
* The expected database exists.
* The application schema exists.
* Migration history is correct.
* Expected records are present.
* Application permissions work.
* The application connects successfully.
* `/ready` becomes healthy.
* Database reads succeed.
* Controlled writes succeed.
* The measured recovery time is documented.

---

# Application Rollback Recovery

If the database is healthy but the application release is faulty, the service can redeploy:

* The previous task-definition revision.
* The previous stable image digest.

This is normally faster than rebuilding the previous application version.

Recent stable ECR images will therefore remain available.

---

# Terraform State Recovery

Terraform state will be stored in a versioned and encrypted S3 bucket.

Separate state keys will be used:

```text
development/terraform.tfstate
production/terraform.tfstate
```

S3 versioning provides a recovery path when a state object is accidentally overwritten or deleted.

State recovery must be performed carefully. Restoring an incorrect state version can cause Terraform to misunderstand the real infrastructure.

Before restoring state:

1. Stop concurrent Terraform operations.
2. Back up the current state object.
3. Confirm the required historical version.
4. Review the infrastructure created after that version.
5. Restore under controlled conditions.
6. Run `terraform plan`.
7. Investigate every unexpected proposed change.

---

# Recovery Objectives

The project will measure:

## Recovery Time Objective

How long it takes to restore the service after a defined failure.

## Recovery Point Objective

How much recent data could be lost under the selected backup and recovery method.

Phase 0 does not claim an untested RTO or RPO.

The recovery exercises will measure the actual result and document it.

---

# Common Operational Mistakes

## Rebuilding the Image During Production Promotion

Production should receive the exact image that was tested in development.

A fresh production build may contain different dependencies or source content.

## Deploying Only the `latest` Tag

A mutable tag makes rollback and incident investigation harder.

Use a unique version, Git SHA, and image digest.

## Scaling ECS Without Reviewing Database Connections

More tasks can create more PostgreSQL connections.

Application and database capacity must be planned together.

## Treating `RUNNING` as Deployment Success

A running task may still fail health checks or application smoke tests.

## Disabling Failed Checks to Complete a Deployment

A failing test or scan must be investigated rather than removed simply to make the pipeline pass.

## Storing AWS Keys in GitHub

GitHub Actions will use OIDC and temporary role credentials.

## Logging Secrets

Secrets and authorization data must never appear in CloudWatch Logs.

## Creating Too Many Alarms

Low-value alarms create alert fatigue and reduce trust in monitoring.

## Assuming Multi-AZ Protects Against Data Loss

Multi-AZ provides failover. Backups and restore testing provide recoverability.

## Trusting a Backup That Has Never Been Restored

A successful backup job does not prove that the application can recover from it.
