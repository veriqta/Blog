# Part 0: Before You Start

## AWS Beginner-Friendly Projects

Learning AWS becomes much easier when you stop treating it like a list of services to memorize.

You can read about EC2, VPC, IAM, S3, RDS, and load balancers for weeks and still feel unsure when you are asked to build something on your own.

Projects change that.

The goal of this series is to help you learn AWS by actually using it. Each project introduces a practical cloud task, then gradually connects that task to the way AWS environments are designed, secured, tested, and troubleshot in the real world.

You do not need to know everything before you begin.

You are expected to make mistakes.

You may launch an instance and discover that you cannot connect to it. You may configure a security group incorrectly. A target may fail its health check. An application may not reach a database. A web page may work from inside a server but fail from your browser.

Those moments are part of the learning process.

The important skill is not avoiding every mistake. It is learning how to investigate what happened.

## What You Will Learn

These projects are designed to build your confidence gradually.

You will work with services such as:

* Amazon EC2
* Amazon VPC
* Amazon S3
* AWS Identity and Access Management
* Amazon RDS
* Elastic Load Balancing
* EC2 Auto Scaling
* Amazon CloudWatch
* Route 53
* Other supporting AWS services where needed

You will also learn concepts that matter beyond individual AWS services, including networking, access control, application connectivity, high availability, monitoring, scaling, and troubleshooting.

The projects become more connected as you progress.

At first, you may launch one resource and test it.

Later, you will connect several AWS services together and begin thinking about how the full architecture behaves.

## Do Not Rush Through the Console

It is tempting to complete an AWS project by clicking through the console as quickly as possible.

Avoid doing that.

Before selecting an option, ask yourself what it controls.

If you are choosing a subnet, understand why the resource needs to be in that subnet.

If you are opening a port in a security group, know what traffic you are allowing and where that traffic should come from.

If AWS gives you a public IP address, understand what that changes.

If you create an IAM permission, ask what that identity can now do.

The objective is not simply to make the project work.

You should understand why it works.

## Build, Test, Break, Fix

A useful way to complete every project is:

1. Build the architecture.
2. Confirm that it works.
3. Change one thing deliberately.
4. Observe what breaks.
5. Troubleshoot the failure.
6. Restore the working configuration.

For example, after creating a web server, you might temporarily remove the HTTP rule from its security group.

Then test the application again.

Instead of only knowing that security groups exist, you will see exactly how they affect traffic.

When you build a load-balanced application later, you can stop one instance and observe what happens to the target group and incoming requests.

This is where AWS starts becoming practical.

## Keep Notes While You Work

Create a simple project journal.

For every project, record:

* What you were trying to build
* Which AWS services you used
* Important configuration choices
* Problems you encountered
* How you diagnosed them
* How you fixed them
* What you would do differently next time

Screenshots can help, but do not rely only on screenshots.

Write down your reasoning.

Six months later, remembering why you configured something is often more valuable than remembering where you clicked.

## Pay Attention to AWS Regions

Before creating resources, check which AWS Region you are using.

Resources created in one Region may not appear when you switch to another Region.

A beginner can easily create an EC2 instance in one Region, switch Regions accidentally, and then think the instance has disappeared.

For this project series, try to use one Region consistently unless a project specifically requires multiple Regions.

Also remember that some AWS services and features may differ by Region.

## Watch Your AWS Costs

AWS projects can create billable resources.

Do not assume that every service you use is covered by the AWS Free Tier.

Pricing, Free Tier eligibility, and service limits can change, so always check the current AWS pricing information before creating resources.

Pay particular attention to resources that can continue generating charges when you are no longer actively using them.

Examples may include:

* Running EC2 instances
* RDS databases
* NAT gateways
* Load balancers
* Elastic IP addresses in certain configurations
* EBS volumes
* Snapshots
* Data transfer
* Other managed services

When you finish a project, clean up resources you no longer need.

Deleting only the main resource may not remove everything associated with it.

For example, terminating an instance does not always mean every related storage, network, or supporting resource has disappeared.

Learn to check.

## Create a Budget Before You Experiment

One of the first habits worth developing in AWS is cost awareness.

Configure AWS Budgets or another appropriate billing alert mechanism for your account.

The purpose is simple.

You should know when your cloud usage starts costing more than expected.

Cloud engineers are responsible for more than making infrastructure work. They also need to understand what that infrastructure costs.

You can start developing that habit from your first project.

## Security Comes First

Do not treat security as something you add after the project works.

Every time you create a resource, think about who should be able to reach it.

Avoid opening services to the entire internet unless the project genuinely requires public access.

For example, a public web server may need HTTP or HTTPS traffic from users.

A database usually should not.

You should also avoid using the AWS root user for normal daily work.

Use appropriate IAM identities and permissions.

As you progress through the projects, you will see security decisions repeatedly because almost every AWS architecture depends on them.

## Understand What You Are Deleting

Cleanup is part of every project.

Before deleting resources, inspect what depends on them.

AWS resources are often connected.

A load balancer may use a target group.

A target group may contain EC2 instances.

An Auto Scaling Group may use a launch template.

An RDS database may use a subnet group and security group.

Understanding those relationships will help you both create and remove infrastructure safely.

## Do Not Copy Commands Blindly

Some projects may include AWS CLI commands, Linux commands, configuration files, or application examples.

Read them before running them.

Try to understand:

* What the command is doing
* Which resource it targets
* Which Region it operates in
* Whether an identifier needs to be replaced
* Whether the action creates, changes, or deletes something

Being able to paste a command is not the same as being able to operate AWS.

The goal is to reach the point where you understand what the command is asking AWS to do.

## Troubleshooting Is Part of Every Project

When something does not work, resist the urge to delete everything immediately and start again.

Investigate first.

Ask questions such as:

Is the resource running?

Is the application listening on the expected port?

Is the security group allowing the traffic?

Is the route table correct?

Is the subnet public or private?

Does the resource have the correct IAM permissions?

Can DNS resolve the hostname?

Is the target healthy?

Can one component reach another component?

Are logs showing an error?

The exact questions will change depending on the architecture, but the habit remains the same.

Start with the symptom, then work through the system logically.

## What Success Looks Like

You do not need to memorize every AWS service by the end of this series.

A better outcome is being able to look at a simple requirement and think:

“I know roughly how I would build this.”

You should also become more comfortable opening an AWS environment you have never seen before, inspecting the resources, understanding how they connect, and finding the most likely place to begin troubleshooting.

That is much closer to real cloud engineering than memorizing service definitions.

Take the projects one at a time.

Build them.

Test them.

Break things carefully.

Fix them.

And most importantly, make sure you understand what AWS is doing underneath every successful click.
