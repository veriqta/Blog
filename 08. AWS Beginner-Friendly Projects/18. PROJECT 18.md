# Project 18: Build a Simple AWS Backup Project

Backups are useful only if you can restore from them.

Creating a snapshot and seeing:

```text
Snapshot completed
```

is not enough.

The real question is:

```text
Can I recover my data when the original storage is lost?
```

That is what Project 18 will test.

You will build this workflow:

```text
EC2 INSTANCE
     |
     |
     v
NEW EBS VOLUME
     |
     | Format and mount
     v
TEST DATA
     |
     | Create backup
     v
EBS SNAPSHOT
     |
     |
     X
SIMULATED DATA LOSS
     |
     v
CREATE NEW VOLUME
FROM SNAPSHOT
     |
     v
ATTACH TO EC2
     |
     v
MOUNT
     |
     v
VERIFY RECOVERED FILES
```

An Amazon EBS snapshot is a point-in-time backup of an EBS volume. AWS can create a new volume from that snapshot and attach the restored volume to an EC2 instance.

# Part 1: Understand EBS

Amazon Elastic Block Store provides block storage volumes that can be attached to EC2 instances.

Think of EBS as:

```text
EC2
 |
 |
 v
Virtual block disk
```

An EBS volume can contain:

```text
Filesystems

Application files

Databases

Logs

User data
```

For this project, we will create a dedicated data disk rather than storing our test files on the root volume.

---

# Part 2: Understand EBS Snapshots

An EBS snapshot is:

```text
A point-in-time backup
of an EBS volume.
```

The basic relationship is:

```text
EBS Volume
    |
    | Snapshot
    v
EBS Snapshot
```

The snapshot can later become:

```text
EBS Snapshot
    |
    | Restore
    v
New EBS Volume
```

AWS documents EBS snapshots specifically as point-in-time backups that can later be used to create replacement or restored volumes.

---

# Part 3: Understand the Recovery Model

We are not going to restore files directly onto the destroyed volume.

Instead:

```text
Snapshot
   |
   v
Create new volume
   |
   v
Attach restored volume
   |
   v
Mount filesystem
   |
   v
Read recovered files
```

AWS's documented recovery pattern is to create a new EBS volume from a snapshot and attach that volume to the target EC2 instance.

---

# Part 4: Important Availability Zone Rule

An EBS volume must be attached to an EC2 instance in the:

```text
same Availability Zone
```

as the volume.

For example:

```text
EC2:
us-east-1a

EBS:
us-east-1a

WORKS
```

But:

```text
EC2:
us-east-1a

EBS:
us-east-1b

DOES NOT ATTACH
```

AWS requires an EBS volume to be in the same Availability Zone as the EC2 instance it is attached to.

# Part 14: Understand Device Names

You asked EC2 for:

```text
/dev/sdf
```

but inside Linux the actual block device can appear under another name.

For Nitro-based EC2 instances, you may see something resembling:

```text
/dev/nvme1n1
```

instead.

AWS notes that the block-device name exposed inside the operating system can differ from the device name supplied when the EBS volume was attached.

Never blindly format a device because you expect its name.

Always inspect first.

# Part 25: Flush Pending Writes

Before snapshotting a filesystem used by an application, application consistency matters.

For this simple text-file lab, run:


For real databases or complex applications, backup consistency can require application-specific quiescing, filesystem freezing, database backup mechanisms, or coordinated multi-volume snapshots.

against the restored disk.


Formatting it would overwrite filesystem structures and defeat the purpose of recovery.

# Part 47: Understand Snapshot Restore Performance

A volume created from a normal snapshot may use lazy loading of blocks.

That means some blocks are fetched from snapshot storage as they are first accessed.

AWS also offers Fast Snapshot Restore for use cases where volumes need to deliver fully initialized performance immediately, but FSR is not required for this beginner project.

For our tiny text files, normal restoration is enough.

# Part 50: Understand RPO

A useful backup concept is:

```text
RPO
```

Recovery Point Objective asks:

```text
How much data could we afford to lose?
```

Suppose snapshots happen every:

```text
24 hours
```

and storage fails just before the next snapshot.

Potential data loss could approach:

```text
24 hours
```

A more frequent backup schedule can reduce the recovery-point gap.

---

# Part 51: Understand RTO

Another concept is:

```text
RTO
```

Recovery Time Objective asks:

```text
How long can the service remain unavailable
while recovery happens?
```

Our Project 18 recovery required:

```text
Find snapshot

Create volume

Wait for volume

Attach volume

Mount filesystem

Verify data
```

That recovery process takes time.

A real disaster-recovery design should know how much recovery time the application can tolerate.

# Part 52: Backup Is Not the Same as High Availability

A snapshot does not automatically make an application highly available.

Backup answers:

```text
Can we recover old or lost data?
```

High availability asks:

```text
Can the service continue operating
when infrastructure fails?
```

These are related but different engineering concerns.

---

# Part 53: Snapshot Is Not the Same as Replication

Replication might maintain another active or near-active copy of data.

A snapshot is:

```text
point-in-time recovery data
```

The distinction matters.

For example:

```text
Replication
may help service continuity.

Backup
may help recover deleted or corrupted data.
```

A resilient system can need both.

# Part 54: Understand Crash Consistency

Our test files are simple static files.

We ran:

```bash
sync
```

before snapshot creation.

For real workloads such as databases, a snapshot taken while writes are occurring might be only crash-consistent unless the application is quiesced or uses a coordinated backup process.

AWS also supports multi-volume snapshot workflows for workloads whose data spans multiple EBS volumes.

# Part 55: Common Troubleshooting Framework

When recovery fails, check:

```text
1. Does the original volume exist?

2. Was the correct volume snapshotted?

3. Did the snapshot reach completed?

4. Is the restored volume created
   from the correct snapshot?

5. Is the restored volume in the
   same AZ as the EC2 instance?

6. Did volume attachment succeed?

7. What device appeared in Linux?

8. Does the restored device already
   contain a filesystem?

9. Did you avoid formatting it?

10. Is the correct device mounted?

11. Are the expected files present?

12. Do checksums match?

13. Was the snapshot created before
    the expected files were written?
```

# What You Should Understand Before Moving On

Do not finish Project 18 thinking:

```text
I know how to create an EBS snapshot.
```

The actual skill is:

```text
BACKUP
+
RESTORE
+
VERIFY
```

The original infrastructure was:

```text
EC2 INSTANCE
      |
      v
EBS VOLUME
      |
      v
XFS FILESYSTEM
      |
      v
APPLICATION DATA
```

You then created:

```text
EBS VOLUME
     |
     v
POINT-IN-TIME
SNAPSHOT
```

AWS defines the snapshot as a point-in-time backup of the EBS volume.

Then something important happened:

```text
ORIGINAL EBS VOLUME
        |
        v
      LOST
```

The application data was no longer available from the original disk.

But:

```text
SNAPSHOT
```

still existed.

Recovery became:

```text
SNAPSHOT
    |
    v
CREATE NEW EBS VOLUME
    |
    v
WAIT FOR AVAILABLE
    |
    v
ATTACH TO EC2
    |
    v
IDENTIFY DEVICE
    |
    v
MOUNT EXISTING FILESYSTEM
    |
    v
RECOVER FILES
```

AWS's documented EBS recovery pattern likewise creates a new volume from the snapshot and attaches it to an EC2 instance.

You also learned one critical difference between:

```text
NEW EMPTY EBS VOLUME
```

and:

```text
RESTORED EBS VOLUME
```

For a new empty volume:

```text
Create filesystem
with mkfs
```

is appropriate.

For a restored volume:

```text
DO NOT FORMAT IT.
```

The filesystem and files already exist in the snapshot.

Your recovery sequence is:

```text
RESTORED VOLUME
      |
      v
lsblk
      |
      v
file / blkid
      |
      v
Existing filesystem?
      |
      v
YES
      |
      v
MOUNT
```

not:

```text
RESTORED VOLUME
      |
      v
mkfs
      |
      v
DATA DESTROYED
```

You also used:

```text
SHA-256 checksums
```

to verify more than the existence of filenames.

The recovery test proved:

```text
Original file
     |
     v
Checksum recorded
     |
     v
Snapshot
     |
     v
Storage loss
     |
     v
Restore
     |
     v
Checksum comparison
     |
     v
MATCH
```

That gives much stronger evidence that the backup actually protected the data.

Your troubleshooting model should now be:

```text
SOURCE VOLUME CORRECT?
        |
        v
DATA WRITTEN?
        |
        v
WRITES FLUSHED?
        |
        v
SNAPSHOT CREATED?
        |
        v
SNAPSHOT COMPLETED?
        |
        v
RESTORE VOLUME CREATED?
        |
        v
SAME AVAILABILITY ZONE?
        |
        v
ATTACHED SUCCESSFULLY?
        |
        v
CORRECT LINUX DEVICE?
        |
        v
EXISTING FILESYSTEM?
        |
        v
MOUNTED?
        |
        v
FILES PRESENT?
        |
        v
CHECKSUMS MATCH?
```

The complete Project 18 architecture is:

```text
                  EC2 INSTANCE
                       |
                       v
               +---------------+
               | ORIGINAL EBS  |
               |               |
               | Test data     |
               +-------+-------+
                       |
                       |
                   Snapshot
                       |
                       v
               +---------------+
               | EBS SNAPSHOT  |
               |               |
               | Backup point  |
               +-------+-------+
                       |
             Original volume lost
                       |
                       X
               +---------------+
               | ORIGINAL EBS  |
               +---------------+

                       |
                       |
                    Restore
                       |
                       v
               +---------------+
               | NEW EBS       |
               | FROM SNAPSHOT |
               +-------+-------+
                       |
                       v
                  EC2 INSTANCE
                       |
                       v
             /recovery/project18
                       |
                       v
                RECOVERED DATA
                       |
                       v
              CHECKSUM VERIFIED
```

That is the lesson to remember:

```text
A backup has not proved its value
until you successfully restore
and verify the data.
```
