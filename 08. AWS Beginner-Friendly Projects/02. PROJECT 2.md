# Project 2: Host a Static Website on Amazon S3

In Project 1, you launched an EC2 instance, installed Apache, and used a running Linux server to serve a webpage.

This project takes a very different approach.

There will be no EC2 instance.

No Linux server.

No Apache process.

No SSH connection.

Instead, you will store HTML and CSS files as objects inside Amazon S3 and configure the bucket itself for static website hosting.

Amazon S3 is an object storage service. Files stored in S3 become objects inside buckets, and each object has a key that identifies it. S3 can also expose a general purpose bucket through a Region-specific static website endpoint when website hosting is enabled.

By the end of this project, the request path will look roughly like this:

```text
Browser
   |
   | HTTP request
   v
S3 Website Endpoint
   |
   v
S3 Bucket
   |
   +-- index.html
   +-- error.html
   +-- css/
       +-- style.css
```

You will learn how to:

* Create an S3 bucket
* Build simple website files
* Upload objects
* Enable static website hosting
* Configure an index document
* Configure an error document
* Understand S3 Block Public Access
* Understand bucket policies
* Grant public read access only to website objects
* Test the S3 website endpoint
* Update website content
* Diagnose common S3 website errors
* Use AWS CLI commands for the same tasks
* Completely clean up the project

This is intentionally a learning architecture.

A directly exposed S3 website endpoint does not support HTTPS. AWS documents CloudFront as an option when HTTPS is required, and private S3 origins behind CloudFront can avoid making the bucket publicly readable. We will cover architectures like that separately.

For this project, we are focusing on S3 itself.

# Step 20: Understand S3 Block Public Access

Open:

```text
S3
→ YOUR_BUCKET_NAME
→ Permissions
```

Find:

```text
Block public access (bucket settings)
```

S3 Block Public Access is designed to provide centralized controls over public access. AWS states that these settings can override policies and permissions that would otherwise allow public access.

That means you could create a bucket policy saying:

```text
Allow everyone to read the website
```

while Block Public Access says:

```text
Do not allow public policies
```

The public access would still be blocked.

For direct S3 static website hosting in this lab, the website objects need anonymous public read access.

That means we need to deliberately change the bucket's Block Public Access configuration.

```text

error.html
css/style.css
```

They need:

```text
s3:GetObject
```

They do not need permission to:

```text

Delete objects
Modify objects
Change policies
Create buckets
Delete buckets
```

We are going to grant only public object-read access.

Conceptually:

```text
Anonymous visitor

CAN:
GET website objects

CANNOT:
PUT new objects
DELETE objects
EDIT bucket configuration
CHANGE permissions
```

This is a fundamental security idea:

Give the required action, not every possible action.

# Step 24: Read the Policy Like an Engineer

Do not simply paste the policy and continue.

Understand it.

## Version

```json
"Version": "2012-10-17"
```

This identifies the IAM policy language version being used.

---

## Statement

```json
"Statement": [...]
```

Contains the permissions being defined.

---

## Sid

```json
"Sid": "PublicReadForStaticWebsite"
```

This is a human-readable identifier for the statement.

---

## Effect

```json
"Effect": "Allow"
```

The statement is granting an action.

---

## Principal

```json
"Principal": "*"
```

This means the statement applies to everyone.

That is what makes this public.

---

## Action

```json
"Action": "s3:GetObject"
```

This allows object retrieval.

It does not grant:

```text
s3:PutObject
s3:DeleteObject
s3:DeleteBucket
```

---

## Resource

```json
"Resource": "arn:aws:s3:::YOUR_BUCKET_NAME/*"
```

The:

```text
/*
```

matters.

We are granting access to objects inside the bucket.

For example:

```text
YOUR_BUCKET_NAME/index.html
YOUR_BUCKET_NAME/error.html
YOUR_BUCKET_NAME/css/style.css
```

---

# Step 25: Do Not Use s3:* Here

You may encounter bad tutorials that solve permissions problems by granting:

```json
"Action": "s3:*"
```

Do not do that.

Our website visitors need to read objects.

The required action is:

```text
s3:GetObject
```

That is enough for this lab's anonymous website requests.

When permissions fail, fix the actual missing permission.

Do not respond by granting every possible S3 permission.

# Step 29: Understand Website Endpoints Versus Object URLs

This distinction confuses many beginners.

An S3 object can be addressed through S3 service interfaces, but static website hosting uses a dedicated website endpoint.

For this project, test using:

```text
Bucket website endpoint
```

from:

```text
Properties
→ Static website hosting
```

AWS explicitly distinguishes S3 website endpoints from REST API endpoints.

The website endpoint understands website behaviors such as your configured index document.

That is the endpoint we care about in this project.

# Step 30: Understand Why HTTPS Does Not Work Directly

Try to notice the protocol on the S3 website endpoint.

Direct S3 static website endpoints do not support HTTPS. AWS recommends another service such as CloudFront when HTTPS delivery is required.

Therefore, do not assume this should work:

```text
https://S3-WEBSITE-ENDPOINT
```

Simply changing:

```text
http
```

to:

```text
https
```

does not create TLS support.

HTTPS requires a different architecture.

A later production-oriented architecture might look like:

```text
User
   |
 HTTPS
   |
   v
CloudFront
   |
   v
Private S3 Bucket
```

That is deliberately outside this beginner project.

```bash
            "Resource": "arn:aws:s3:::$BUCKET_NAME/*"
        }
    ]
}
EOF
```

```bash

```

Pay special attention to:

```text
$BUCKET_NAME
```

Make sure your actual bucket name appears in the resulting JSON.

# Important Production Lesson

Direct S3 website hosting is excellent for learning the fundamentals of buckets, objects, website endpoints, and public access.

But notice what we had to do:

```text
Make website objects publicly readable
```

Also remember:

```text
S3 website endpoint
→ HTTP
→ no direct HTTPS support
```

AWS documents CloudFront as an appropriate option when HTTPS is required, and a CloudFront design can keep the S3 origin private instead of directly publishing the bucket.

That distinction will matter when you move from:

```text
"Can I make this work?"
```

to:

```text
"How should I design this for production?"
```

# What You Should Understand Before Moving On

Do not finish this project thinking only:

```text
"I know where the S3 static website button is."
```

You should understand the architecture.

S3 stores your website files as objects.

The bucket contains those objects.

Object keys identify files such as:

```text
index.html
error.html
css/style.css
```

Static website hosting tells S3 how the bucket should behave when it receives website requests.

The index document tells S3 which object represents the homepage.

The error document gives the website a custom error response.

Block Public Access provides a safety layer that can prevent public access even when another policy attempts to grant it.

The bucket policy for this lab allows anonymous users to perform:

```text
s3:GetObject
```

against the website objects.

The S3 website endpoint gives the browser a public web address for the static site, and that endpoint is different from the normal S3 REST API endpoint.

Direct S3 website endpoints use HTTP rather than HTTPS. A more production-oriented design can introduce CloudFront and keep the S3 origin private.

And finally, cleanup is part of the architecture lifecycle.

You did not merely create a bucket.

You built a small web-hosting system, tested its permissions, deliberately exposed only the content required for the lab, verified its behavior, and then dismantled it when the project was finished.

That is the skill you want to carry into the next AWS project.
