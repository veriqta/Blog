# Project 3: Create a Secure IAM User

Creating an IAM user is easy.

Creating one that has only the permissions it needs, uses MFA, does not carry unnecessary long-term credentials, and predictably receives AccessDenied when attempting unauthorized actions is a much better AWS exercise.

That is what you will build in this project.

The final permission path will look like this:

```text
IAM User
   |
   v
IAM User Group
   |
   v
Customer Managed Policy
   |
   +--> Allowed S3 read actions
   |
   +--> Everything else remains denied
```

The user will also have MFA protecting console authentication.

You will deliberately test two outcomes:

```text
Permitted action
→ succeeds

Unauthorized action
→ AccessDenied
```

That second result matters.

A secure IAM configuration should not merely prove what a user can do.

It should also prove what the user cannot do.

AWS defines IAM as the service used to manage identities, credentials, and permissions controlling access to AWS resources. AWS recommends granting only the permissions required for a task, known as least privilege.

This lab creates:


The user will not receive permissions such as:

That makes the lab useful because you can demonstrate both authorization and denial.

# A Note About Modern AWS Identity Practices

IAM users still exist and remain useful in some scenarios, but AWS recommends that human workforce users use federation through AWS IAM Identity Center where practical rather than accumulating individual long-term IAM credentials.

AWS also recommends temporary credentials over long-term access keys where possible.

So treat this project as an IAM fundamentals lab.

Its purpose is to teach:

* Users
* Groups
* Policies
* Least privilege
* MFA
* Authorization evaluation
* AccessDenied
* Credential cleanup

Do not interpret it as a recommendation to create IAM users for every employee in a large production environment.

# Part 1: Understand IAM Users and Groups

An IAM user represents an identity inside one AWS account.

A user can potentially have:

```text
Console credentials
Access keys
MFA devices
Permissions
Group memberships
Tags
```

But creating a user does not automatically make it an administrator.

Permissions must come from policies.

An IAM group is a collection of IAM users. Permissions attached to a group are inherited by users who belong to that group.

For example:

```text
Group:
S3Readers

Policy:
Allow read-only S3 operations

Users:
Alice
Bob
Charlie
```

Instead of independently attaching the same policy to all three users, you can manage access through the group.

For this project:

```text
veriqta-project-03-user
          |
          v
veriqta-project-03-s3-readers
          |
          v
VERIQTAProject03S3ReadOnly
```

---

# Part 2: Understand Least Privilege

Least privilege means:

```text
Give an identity only the permissions required
to perform its intended task.
```

AWS recommends beginning with a minimum permission set and granting additional permissions only when necessary.

Bad approach:

```text
User needs to view S3 buckets.

Solution:
AdministratorAccess
```

Better approach:

```text
User needs to view S3 buckets.

Solution:
Allow only the S3 read/list operations required.
```

The difference is enormous.

An administrator could potentially:

* Launch resources
* Delete resources
* Modify IAM
* Change network configuration
* Create credentials
* Alter security policies

Our S3 reader should not be able to do those things.

# Part 5: Understand the Policy

Do not continue until you understand what you just created.

The first field is:

```json
"Version": "2012-10-17"
```

This identifies the IAM policy language version.

Then:

```json
"Effect": "Allow"
```

means the listed actions are permitted.

The actions are:

```json
"s3:ListAllMyBuckets",
"s3:GetBucketLocation"
```

They allow the identity to retrieve certain S3 account and bucket information.

Notice what the policy does not contain:

```text
s3:CreateBucket
s3:PutObject
s3:DeleteObject
s3:DeleteBucket
```

Those operations are therefore not granted by this policy.

And:

```json
"Resource": "*"
```

is appropriate here because some account-level listing actions are not scoped to one individual bucket resource.

This is still a narrow policy because the allowed actions themselves are restricted.

# Part 6: Why We Are Not Using AmazonS3FullAccess

You might find a managed policy named:

```text
AmazonS3FullAccess
```

That would make the lab easier.

It would also destroy the purpose of the lab.

The user only needs enough permissions to inspect S3 bucket information.

Granting full S3 access would allow far more actions than necessary.

Least privilege asks:

```text
What does this identity actually need?
```

not:

```text
What policy makes the error disappear fastest?
```

# Part 18: Why AccessDenied Is Good Here

Beginners often interpret:

```text
AccessDenied
```

as:

```text
Something is broken.
```

In a least-privilege test, it can mean exactly the opposite.

If the design says:

```text
S3 viewing:
Allowed

S3 creation:
Denied

IAM administration:
Denied

EC2 launch:
Denied
```

and those are the observed results, IAM is working properly.

A secure authorization test always asks both questions:

```text
Can the user perform the required action?

Can the user perform actions outside the requirement?
```

# Part 22: Understand Authentication Versus Authorization

This project demonstrates two separate security concepts.

Authentication answers:

```text
Who are you?
```

Your password and MFA participate in authentication.

Authorization answers:

```text
What are you allowed to do?
```

IAM policies participate in authorization.

Therefore:

```text
Password + MFA
      |
      v
AUTHENTICATION
      |
      v
Identity confirmed
      |
      v
IAM policies evaluated
      |
      v
AUTHORIZATION
      |
      +--> Allow
      |
      +--> Deny
```

MFA does not automatically make someone an administrator.

A user can successfully authenticate with MFA and still receive:

```text
AccessDenied
```

for an unauthorized operation.

That is expected.

# Part 32: Test the Policy Before Using Credentials

One useful IAM technique is policy simulation.

Get the user ARN:

```bash
USER_ARN=$(aws iam get-user \
    --user-name veriqta-project-03-user \
    --query 'User.Arn' \
    --output text)
```

Check:

```bash
echo "$USER_ARN"
```

Now simulate an allowed action:

```bash
aws iam simulate-principal-policy \
    --policy-source-arn "$USER_ARN" \
    --action-names s3:ListAllMyBuckets
```

Look for a decision similar to:

```text
allowed
```

Now simulate a denied action:

```bash
aws iam simulate-principal-policy \
    --policy-source-arn "$USER_ARN" \
    --action-names s3:CreateBucket
```

The result should not be allowed.

You can test multiple actions:

```bash
aws iam simulate-principal-policy \
    --policy-source-arn "$USER_ARN" \
    --action-names \
        s3:ListAllMyBuckets \
        s3:GetBucketLocation \
        s3:CreateBucket \
        iam:CreateUser \
        ec2:RunInstances
```

The desired pattern is:

```text
s3:ListAllMyBuckets
→ allowed

s3:GetBucketLocation
→ allowed

s3:CreateBucket
→ denied

iam:CreateUser
→ denied

ec2:RunInstances
→ denied
```

# Part 33: Understand Implicit Deny

IAM authorization begins from a restrictive position.

If no applicable policy grants an action, the action is not permitted.

For example, our policy says:

```text
Allow:
s3:ListAllMyBuckets
s3:GetBucketLocation
```

It says nothing about:

```text
s3:CreateBucket
```

Therefore that action remains denied.

You do not need to write:

```json
{
    "Effect": "Deny",
    "Action": "s3:CreateBucket"
}
```

just to prevent the action.

The absence of an Allow is already enough for this simple scenario.

Explicit Deny becomes important in more advanced policy designs because an applicable explicit Deny overrides an Allow.

# Troubleshooting: AccessDenied for an Expected Action

Start with the action itself.

Ask:

```text
Which AWS API action is being denied?
```

Then:

```text
Does the policy actually allow it?
```

Then:

```text
Is the policy attached?
```

Then:

```text
Is the user in the correct group?
```

Then:

```text
Is another policy explicitly denying the action?
```

This is much more effective than randomly adding permissions.

# CLEANUP

IAM resources may not create hourly compute charges like an EC2 instance, but stale identities and credentials are still security risks.

AWS recommends removing users, roles, permissions, and credentials that are no longer needed.

For this lab, cleanup means removing:

```text
MFA assignment

Console credentials

Any accidental access keys

User group membership

IAM user

Policy attachment

IAM group

Customer managed policy

Local JSON files
```

Do not leave the practice user in the account.

---

# Cleanup Step 1: Record the Resources

Before deletion:

```text
User:
veriqta-project-03-user

Group:
veriqta-project-03-s3-readers

Policy:
VERIQTAProject03S3ReadOnly

MFA:
veriqta-project-03-mfa
```

If you accidentally created an access key, record its access key ID as well.

Do not record the secret access key.

---

# Cleanup Step 2: Check for Access Keys

Open:

```text
IAM
→ Users
→ veriqta-project-03-user
→ Security credentials
```

Look for:

```text
Access keys
```

For the lab we intentionally did not need one.

If none exists:

```text
Good.
```

If one was accidentally created, delete it.

Using CLI:

```bash
aws iam list-access-keys \
    --user-name veriqta-project-03-user
```

If a key exists, record only its:

```text
AccessKeyId
```

Then delete it:

```bash
aws iam delete-access-key \
    --user-name veriqta-project-03-user \
    --access-key-id YOUR_ACCESS_KEY_ID
```

Verify:

```bash
aws iam list-access-keys \
    --user-name veriqta-project-03-user
```

There should be no project access keys.

# Cleanup Step 4: Delete the User's Console Login Profile

If the user has console access, remove its login profile.

You can do this through the IAM console.

With AWS CLI:

```bash

    --user-name veriqta-project-03-user
```

If the user has no login profile, AWS may return an appropriate not-found response.

That is fine if you already removed it through the console.

# What You Should Understand Before Moving On

The important outcome of this project is not:

```text
I created an IAM user.
```

It is:

```text
I created an identity with a defined job,
gave it only the permissions required for that job,
protected interactive authentication with MFA,
proved that legitimate operations succeeded,
proved that unauthorized operations failed,
and removed the identity when the lab ended.
```

You should now understand the difference between an IAM user and an IAM group.

The user represents the identity.

The group provides a manageable way to assign common permissions to multiple users.

The policy defines what AWS actions are allowed.

Least privilege keeps that permission set intentionally narrow. AWS recommends granting only the actions required for the task.

MFA strengthens authentication by requiring an additional factor beyond the password.

An allowed operation demonstrates that the user can perform the job it was designed for.

An AccessDenied response on an unauthorized operation demonstrates that the permission boundary is actually working.

And cleanup removes identities, credentials, groups, and policies that no longer have a reason to exist.

That is the beginning of thinking about IAM as a security system rather than simply another AWS console page.
