# Project 1: Launch Your First EC2 Web Server

There is a big difference between knowing that Amazon EC2 provides virtual servers and actually putting a server on the internet yourself.

In this project, you are going to do exactly that.

You will launch a Linux server in AWS, control who can reach it, connect to it remotely, install Apache, replace the default page with your own HTML, and access the site from your browser.

By the end of the project, the traffic path will look like this:

Internet user
→ Public IPv4 address
→ EC2 security group
→ TCP port 80
→ Apache
→ Your HTML page

You will also use SSH for administrative access:

Your computer
→ TCP port 22
→ EC2 security group
→ EC2 instance
→ Linux shell

The project is simple, but several fundamental AWS ideas are hidden inside it. You are working with compute, operating systems, public IP addressing, network filtering, SSH authentication, software installation, processes, ports, and HTTP.

AWS describes EC2 as on-demand, scalable computing capacity in the AWS Cloud. An EC2 instance is effectively a virtual server that you configure and operate.

---

# What You Will Build

We will create:

* One Amazon EC2 instance
* Amazon Linux 2023 as the operating system
* One EC2 key pair
* One security group
* SSH access on port 22
* HTTP access on port 80
* Apache HTTP Server
* A small custom HTML website

We will use a public IPv4 address so that you can reach the server directly from your computer.

This is a learning architecture. It is not yet a production website architecture.

Later projects can introduce load balancers, private subnets, Auto Scaling, DNS, HTTPS, monitoring, and databases.

For now, the objective is to understand one server properly.

# Step 10: Create the Security Group

Under the network settings, create a new security group.

Use a meaningful name:

```text
veriqta-project-01-web-sg
```

Description:

```text
Security group for Project 1 EC2 web server
```

A security group controls allowed network traffic associated with the EC2 instance. AWS security groups allow you to define which traffic can reach or leave protected resources.

We need two inbound rules.

---

# Rule 1: SSH

Add:

```text
Type: SSH
Protocol: TCP
Port: 22
Source: My IP
```

The result should resemble:

```text
SSH | TCP | 22 | your-public-ip/32
```

For example:

```text
SSH | TCP | 22 | 203.0.113.25/32
```

Do not copy that example IP. It is only an example.

Select:

```text
My IP
```

so AWS uses your current public IP address.

AWS recommends that the security group permit incoming SSH traffic from the IP address you are connecting from.

Avoid using:

```text
0.0.0.0/0
```

for SSH simply because it makes connection problems easier.

That would permit SSH connection attempts from every IPv4 address on the internet.

For a beginner lab, restricting SSH to your current public address is a better habit.

---

# Rule 2: HTTP

Add another inbound rule:

```text
Type: HTTP
Protocol: TCP
Port: 80
Source: Anywhere-IPv4
```

This will normally produce:

```text
0.0.0.0/0
```

This is intentional for the web service because we want to test the website from the public internet.

At this point:

```text
Port 22
Purpose: SSH administration
Source: Your IP only

Port 80
Purpose: Website traffic
Source: Internet
```

These two rules do completely different jobs.

Do not confuse them.

SSH allows you to administer the server.

HTTP allows visitors to access the website.

# Step 23: Enable Apache at Boot

Starting Apache makes it run now.

Enabling Apache tells systemd to start it during normal future boots.

Run:

```bash
sudo systemctl enable httpd
```

You can combine the start and enable operations on a new installation with:

```bash
sudo systemctl enable --now httpd
```

Because we already started Apache, either approach is fine.

Confirm:

```bash
sudo systemctl is-enabled httpd
```

Expected:

```text
enabled
```

Check whether it is currently active:

```bash
sudo systemctl is-active httpd
```

Expected:

```text
active
```

# Step 24: Confirm That Apache Is Listening on Port 80

Run:

```bash
sudo ss -tulpn
```

Look for a listening socket associated with port:

```text
:80
```

You can narrow the output:

```bash
sudo ss -ltnp | grep ':80'
```

This gives you an important troubleshooting checkpoint.

The security group may allow port 80, but if nothing inside Linux is actually listening on port 80, your site still will not work.

Think of the connection as several gates:

```text
Browser
   ↓
Internet routing
   ↓
Security group allows TCP 80
   ↓
Operating system
   ↓
Apache listens on TCP 80
   ↓
Website content
```

Every layer must work.

# Step 31: Prove That the Request Is Reaching Apache

```bash

```

Run the command again:

```bash
sudo tail /var/log/httpd/access_log
```

You should see a new request.

For continuous monitoring:

```bash

```

Now refresh your browser several times.

Stop following the log with:

```text

```

This is your first glimpse of server-side observability.

The browser is not magically displaying a file from AWS.

It sends an HTTP request.

Apache receives the request.

Apache records information about the request.

Apache responds with content.

Your browser renders the response.

# Troubleshooting: SSH Connection Times Out

Suppose this fails:

```bash
ssh -i ~/.ssh/aws-projects/veriqta-project-01-key.pem ec2-user@YOUR_PUBLIC_IP
```

and eventually returns a timeout.

Do not immediately recreate the instance.

Work through the path.

First verify that the instance is:

```text
Running
```

Then confirm that it has:

```text
Public IPv4 address
```

Check the associated security group.

It should contain:

```text
SSH
TCP
22
Your current public IP/32
```

AWS specifically identifies incorrect security-group SSH rules as a common cause of EC2 connection timeouts.

Your public IP can change, especially when switching networks.

If your security group contains an old address, update the SSH source to your current IP.

```text
              +---------+---------+
                        |
                        v
              +-------------------+
              |   Amazon EC2      |
              |                   |
              | Amazon Linux 2023 |
              | Apache HTTPD      |
              |                   |
              | /var/www/html/    |
              | index.html        |
              +-------------------+
```

When your browser requests:

```text
http://PUBLIC_IP/
```

the request reaches TCP port 80.

The security group permits it.

Apache is listening on that port.

Apache receives the request for:

```text
/
```

and serves the page from its configured web content.

That is the complete request path behind your first EC2 website.

# Cleanup: Do Not Skip This Section

A cloud project is not finished when the website works.

It is finished when you understand what you created and remove what you no longer need.

Cloud resources can continue to exist after you close your browser or disconnect from SSH.

Stopping an EC2 instance and terminating an EC2 instance are also different actions. AWS documents termination as permanent, and attached EBS volumes configured for deletion on termination are deleted with the instance.

For this lab, if you are completely finished with the server, terminate it rather than merely stopping it.

# What You Should Understand Before Moving On

Do not judge this project only by whether the webpage appeared.

You should now be able to explain what happened.

An EC2 instance gave you virtual compute capacity.

An AMI supplied the operating-system image.

The instance type determined the compute configuration you selected.

A key pair gave you a way to authenticate an SSH connection.

The security group decided which inbound network connections were permitted.

Port 22 was used for SSH.

Port 80 was used for HTTP.

Amazon Linux ran the operating system.

Apache ran as a process on that operating system.

Apache listened for HTTP connections.

`/var/www/html/index.html` supplied the content.

The public IP gave your browser an internet-reachable destination.

And when you were finished, terminating and auditing the associated resources completed the project.

That is much more useful than simply saying, “I know how to launch EC2.”

You now know the path a request takes from your browser to a Linux web server running in AWS.
