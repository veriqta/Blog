# Project 8: Create Your First Application Load Balancer

A single EC2 web server works until that server stops working.

If every request depends on one machine, that machine becomes a single point of failure.

In this project, you will put two EC2 web servers behind an AWS Application Load Balancer.

Instead of users connecting directly to either instance, they will connect to one load-balancer DNS name.

The Application Load Balancer will receive the HTTP request, inspect the health of its registered targets, and forward the request to a healthy EC2 instance.

AWS describes this model directly: a load balancer accepts client traffic, distributes requests to registered targets, monitors their health, stops routing to unhealthy targets, and resumes routing when a target becomes healthy again.

The finished architecture will look like this:

```text
                              INTERNET
                                  |
                                  |
                             HTTP TCP/80
                                  |
                                  v
                    +---------------------------+
                    | APPLICATION LOAD BALANCER |
                    |                           |
                    | veriqta-project-08-alb    |
                    |                           |
                    | Listener: HTTP :80        |
                    |                           |
                    | Security Group: alb-sg    |
                    +-------------+-------------+
                                  |
                                  |
                                  v
                     TARGET GROUP TCP/80
                  veriqta-project-08-tg
                      /                 \
                     /                   \
                    v                     v

          AVAILABILITY ZONE A       AVAILABILITY ZONE B

        PUBLIC SUBNET A            PUBLIC SUBNET B
        10.0.1.0/24               10.0.4.0/24

      +------------------+       +------------------+
      | EC2 WEB SERVER 1 |       | EC2 WEB SERVER 2 |
      |                  |       |                  |
      | Amazon Linux     |       | Amazon Linux     |
      | Apache           |       | Apache           |
      |                  |       |                  |
      | /health.html     |       | /health.html     |
      |                  |       |                  |
      | instance-sg      |       | instance-sg      |
      +------------------+       +------------------+

                   \               /
                    \             /
                     HEALTH CHECKS
                         HTTP /
```

The ALB will use subnets in two Availability Zones. AWS creates a load-balancer node in each enabled zone, and the zones containing your targets should be enabled for the load balancer.

# Part 1: Understand the New Request Path

Without a load balancer:

```text
Browser
   |
   v
EC2
```

With an Application Load Balancer:

```text
Browser
   |
   v
ALB
   |
   v
Target Group
   |
   +----> EC2-1
   |
   +----> EC2-2
```

The target group is an important part of this design.

The ALB does not simply discover arbitrary EC2 instances.

Targets are registered in a target group, and the target group specifies the protocol and port the load balancer uses when forwarding requests. Health checks are also configured on the target group.

---

# Part 2: Why We Need Two Public Subnets

Project 4 originally created:

```text
Public subnet:
10.0.1.0/24
```

in one Availability Zone.

For this project we will create another public subnet:

```text
10.0.4.0/24
```

in another Availability Zone.

The design becomes:

```text
VPC
10.0.0.0/16

├── Public Subnet A
│   10.0.1.0/24
│   Availability Zone A
│
├── Private Subnet A
│   10.0.2.0/24
│
└── Public Subnet B
    10.0.4.0/24
    Availability Zone B
```

We deliberately use:

```text
10.0.4.0/24
```

rather than `10.0.3.0/24` because earlier database projects may have used `10.0.3.0/24` for another private subnet.

# Part 40: Understand ALB Health Checks

The ALB periodically requests:

```text
/health.html
```

from both targets.

Conceptually:

```text
ALB
 |
 +---- GET /health.html ----> EC2-1
 |
 +---- GET /health.html ----> EC2-2
```

If both answer successfully:

```text
EC2-1 → healthy
EC2-2 → healthy
```

If one stops answering correctly:

```text
EC2-1 → healthy
EC2-2 → unhealthy
```

The ALB then stops sending normal requests to the unhealthy target.

# Part 49: Troubleshooting Framework

If the ALB does not work, investigate in this order:

```text
1. Is the ALB active?

2. Does the ALB have two correct public subnets?

3. Does ALB-SG allow HTTP/80 from users?

4. Does the listener exist on HTTP/80?

5. Does the listener forward to the correct target group?

6. Are both EC2 instances registered?

7. Are the EC2 instances running?

8. Is Apache running?

9. Is Apache listening on port 80?

10. Does /health.html exist?

11. Does curl localhost/health.html return success?

12. Does instance-sg permit HTTP/80 from alb-sg?

13. Does the target group use the correct VPC?

14. Does the target group use port 80?

15. Does the health check use the correct path?

16. What health status and reason does AWS show?
```

ALB

Target group

EC2 instances

 v
Security groups
 |
 v
Key pair
 |

Project 8 subnet

# What You Should Understand Before Moving On

The important lesson from this project is not simply:

```text
I created an Application Load Balancer.
```

You should understand how all of the pieces cooperate.

The user sends a request to:

```text
ALB DNS
```

rather than directly to an EC2 address.

The ALB listener accepts:

```text
HTTP TCP/80
```

and forwards the request to:

```text
veriqta-project-08-tg
```

The target group contains two registered EC2 instances and defines how the load balancer communicates with those targets. AWS target groups route requests to their registered targets using the configured protocol and port.

The ALB security group accepts HTTP from the internet.

The EC2 security group accepts HTTP only from the ALB security group.

That produces:

```text
Internet
   |
   v
ALB-SG
   |
   v
ALB
   |
   v
INSTANCE-SG
   |
   +----> EC2-1
   |
   +----> EC2-2
```

The target group continuously health-checks:

```text
/health.html
```

on both servers.

When both servers are healthy:

```text
ALB
 |
 +----> EC2-1
 |
 +----> EC2-2
```

When one fails:

```text
ALB
 |
 X----> EC2-1 unhealthy
 |
 +----> EC2-2 healthy
```

The ALB stops sending normal traffic to the unhealthy target and continues using healthy capacity. When the failed instance begins passing its health checks again, it can return to service.

That is the real purpose of this lab.

You are no longer giving users the address of one server.

You are giving them a service endpoint that can distribute requests across multiple healthy servers and survive the loss of one target.
