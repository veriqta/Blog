# Project 20: Final Project: Build a Beginner Production-Style AWS Architecture

This is the final project in the AWS Beginner-Friendly Projects series.

Until now, most projects focused on one AWS service or one architectural problem at a time.

Project 20 brings those pieces together.

You will build:

```text
CUSTOM VPC
+
PUBLIC SUBNETS
+
PRIVATE APPLICATION SUBNETS
+
PRIVATE DATABASE SUBNETS
+
INTERNET GATEWAY
+
NAT GATEWAY
+
APPLICATION LOAD BALANCER
+
AUTO SCALING
+
EC2 APPLICATION SERVERS
+
RDS MYSQL
+
S3
+
IAM
+
CLOUDWATCH
```

The finished architecture will look like this:

```text
                            INTERNET
                                |
                                |
                                v
                     +---------------------+
                     | INTERNET GATEWAY    |
                     +----------+----------+
                                |
                    +-----------+-----------+
                    |                       |
                    v                       v

              PUBLIC SUBNET A          PUBLIC SUBNET B
              10.20.1.0/24             10.20.2.0/24
                    |                       |
                    +-----------+-----------+
                                |
                                v
                    +-----------------------+
                    | APPLICATION           |
                    | LOAD BALANCER         |
                    |                       |
                    | HTTP :80              |
                    +-----------+-----------+
                                |
                           Target Group
                                |
                  +-------------+-------------+
                  |                           |
                  v                           v

          PRIVATE APP SUBNET A       PRIVATE APP SUBNET B
          10.20.11.0/24              10.20.12.0/24

          +----------------+          +----------------+
          | EC2 INSTANCE   |          | EC2 INSTANCE   |
          |                |          |                |
          | Auto Scaling   |          | Auto Scaling   |
          | Python App     |          | Python App     |
          | Port 8080      |          | Port 8080      |
          +-------+--------+          +-------+--------+
                  |                           |
                  +-------------+-------------+
                                |
                                |
                                v

                  +--------------------------+
                  | RDS MYSQL                |
                  |                          |
                  | PRIVATE DB SUBNETS       |
                  | Multi-AZ subnet group    |
                  | Not publicly accessible  |
                  +--------------------------+

                     PRIVATE DB SUBNET A
                     10.20.21.0/24

                     PRIVATE DB SUBNET B
                     10.20.22.0/24


              EC2 APPLICATION TIER
                     |
          +----------+----------+
          |                     |
          v                     v
         S3                 CLOUDWATCH
   Application Storage     Metrics / Alarms
```

The application instances will not receive public IPv4 addresses.

Users reach:

```text
Application Load Balancer
```

not:

```text
EC2 directly
```

The RDS database will accept MySQL connections only from the application security group.

The application instances will access the internet for package installation through a NAT Gateway.

AWS documents essentially this pattern, public subnets for load-balancing resources and private subnets for application servers, with NAT providing outbound internet connectivity to those private servers.

# Part 37: Create the RDS Credentials

Do not hard-code a real reusable password in a script.

For this disposable lab, create a unique temporary password locally.

Example:

```bash
DB_USER="appadmin"
```

Generate a password:

```bash
DB_PASSWORD=$(python3 - <<'PY'
import secrets
import string

alphabet = (
    string.ascii_letters
    + string.digits
    + "!#$%^&*"
)

print(
    "".join(
        secrets.choice(alphabet)
        for _ in range(24)
    )
)
PY
)
```

Print it only if necessary:

```bash
echo "$DB_PASSWORD"
```

Do not commit it to source control.

A production architecture would normally use a secrets-management workflow rather than leaving database credentials in shell history or application configuration.

```bash
#!/usr/bin/env python3

import json
import logging
import os
import socket

from http.server import (
    BaseHTTPRequestHandler,
    HTTPServer
)


logging.basicConfig(
    level=logging.INFO,
    format=(
        "%(asctime)s "
        "%(levelname)s "
        "%(message)s"
    )
)

logger = logging.getLogger(
    "veriqta-project-20"
)


class Handler(
    BaseHTTPRequestHandler
):

    def response(
        self,
        code,
        body
    ):

        body = json.dumps(
            body
        ).encode()

        self.send_response(
            code
        )

        self.send_header(
            "Content-Type",
            "application/json"
        )

        self.send_header(
            "Content-Length",
            str(len(body))
        )

        self.end_headers()

        self.wfile.write(
            body
        )

    def do_GET(self):

        hostname = socket.gethostname()

        logger.info(
            "request path=%s host=%s",
            self.path,
            hostname
        )

        if self.path == "/health":

            self.response(
                200,
                {
                    "status": "healthy",
                    "host": hostname
                }
            )

            return

        if self.path == "/":

            self.response(
                200,
                {
                    "project": 20,
                    "brand": "VERIQTA",
                    "architecture": (
                        "Beginner Production-Style AWS"
                    ),
                    "host": hostname
                }
            )

            return

        if self.path == "/info":

            self.response(
                200,
                {
                    "host": hostname,
                    "database": os.environ.get(
                        "DB_ENDPOINT",
                        "configured"
                    ),
                    "bucket": os.environ.get(
                        "S3_BUCKET",
                        "configured"
                    )
                }
            )

            return

        self.response(
            404,
            {
                "error": "not found"
            }
        )

    def log_message(
        self,
        format,
        *args
    ):
        return


server = HTTPServer(
    ("0.0.0.0", 8080),
    Handler
)

logger.info(

)
```

# What You Should Understand Before Finishing the Series

Project 20 is not mainly about memorizing twenty pages of AWS CLI commands.

The important skill is understanding how the architecture works as one system.

Start with networking.

```text
VPC
 |
 +---- PUBLIC SUBNETS
 |
 +---- PRIVATE APP SUBNETS
 |
 +---- PRIVATE DB SUBNETS
```

The public tier contains:

```text
Internet Gateway

NAT Gateway

Application Load Balancer
```

The application servers stay private:

```text
Internet
    |
    X
EC2
```

Users reach:

```text
Internet
    |
    v
ALB
    |
    v
Private EC2
```

That is a much stronger design than exposing individual application servers directly.

AWS documents this architecture pattern with a public load balancer and Auto Scaling-managed servers in private subnets.

The load balancer solves:

```text
TRAFFIC DISTRIBUTION
```

Auto Scaling solves:

```text
CAPACITY
+
INSTANCE REPLACEMENT
```

The relationship becomes:

```text
             ALB
              |
              v
        TARGET GROUP
          /       \
         /         \
        v           v
      EC2 A       EC2 B
         \         /
          \       /
         AUTO SCALING
```

When Auto Scaling launches a replacement instance, the attached target group handles registration for the group.

You proved this by deliberately terminating one application instance.

The architecture responded:

```text
INSTANCE A
   |
   X
TERMINATED

INSTANCE B
   |
   v
CONTINUES SERVING TRAFFIC

AUTO SCALING
   |
   v
LAUNCHES REPLACEMENT

TARGET GROUP
   |
   v
HEALTH CHECK

NEW INSTANCE
   |
   v
HEALTHY
```

That is very different from a manually operated server architecture where someone must notice the failure and launch another machine.

The database tier introduced another security boundary.

```text
Internet
   |
   X
RDS
```

RDS receives database traffic only through:

```text
APP SECURITY GROUP
      |
      | TCP 3306
      v
RDS SECURITY GROUP
```

AWS specifically supports using a source security group to control which application tier may connect to an RDS DB instance.

The database subnet group also tells RDS where inside your VPC database resources can be placed.

S3 introduced a different access model.

Instead of embedding:

```text
AWS_ACCESS_KEY_ID

AWS_SECRET_ACCESS_KEY
```

on EC2, the application instances receive:

```text
IAM ROLE
```

The role determines which S3 actions the instances can perform.

That gives you:

```text
EC2 INSTANCE
      |
      v
IAM ROLE
      |
      v
PROJECT 20 S3 BUCKET
```

without maintaining static IAM-user credentials on every application server.

CloudWatch then gives the architecture visibility.

You can monitor:

```text
CPUUtilization

RequestCount

HealthyHostCount

UnHealthyHostCount

TargetResponseTime

Auto Scaling capacity
```

Auto Scaling also publishes group metrics to CloudWatch when collection is enabled.

The failure exercises are especially important.

You tested:

```text
EC2 INSTANCE LOSS
```

and watched Auto Scaling recover capacity.

You tested:

```text
BROKEN SECURITY GROUP
```

and watched targets become unhealthy.

You tested:

```text
BROKEN HEALTH CHECK
```

and learned that:

```text
EC2 running
```

does not automatically mean:

```text
ALB target healthy.
```

You verified that the database is:

```text
PRIVATE
```

and that the application tier is the authorized database client.

Your complete request path is now:

```text
                       INTERNET USER
                            |
                            v
                    INTERNET GATEWAY
                            |
                            v
                 APPLICATION LOAD BALANCER
                            |
                            v
                       LISTENER :80
                            |
                            v
                       TARGET GROUP
                            |
                  +---------+---------+
                  |                   |
                  v                   v
               EC2 A               EC2 B
                  |                   |
                  +---------+---------+
                            |
                       AUTO SCALING
                            |
             +--------------+--------------+
             |                             |
             v                             v
        AMAZON S3                     AMAZON RDS
             |                             |
          IAM ROLE                  DB SECURITY GROUP
             |                             |
             v                             v
      PRIVATE STORAGE               PRIVATE DATABASE

                            |
                            v

                       CLOUDWATCH
                  METRICS / ALARMS
```

Your troubleshooting model should be just as systematic:

```text
DOES DNS RESOLVE?
      |
      v
IS ALB ACTIVE?
      |
      v
IS LISTENER CORRECT?
      |
      v
ARE TARGETS HEALTHY?
      |
      v
DID ASG LAUNCH INSTANCES?
      |
      v
ARE INSTANCES IN PRIVATE SUBNETS?
      |
      v
IS APP PORT 8080 OPEN FROM ALB?
      |
      v
IS APPLICATION RUNNING?
```
