# Project 5: Deploy EC2 Inside Your Custom VPC

In Project 4, you built the network.

You created a custom VPC, divided it into public and private subnets, attached an Internet Gateway, created route tables, and deliberately gave only the public subnet a default route to the internet.

Now we are going to prove that the network works.

You will launch an EC2 instance directly into the public subnet, give it a public IPv4 address, create a dedicated security group, connect to the instance using SSH, verify its private and public addressing, inspect its network path, and deliberately break several parts of the connection so you can learn how to troubleshoot them.

AWS allows resources such as EC2 instances to be deployed into specific subnets inside a VPC.

The finished architecture will look like this:

```text
                         YOUR COMPUTER
                              |
                              |
                         SSH TCP/22
                              |
                              v
                           INTERNET
                              |
                              v
                    INTERNET GATEWAY
                              |
                        0.0.0.0/0
                              |
                              v
+------------------------------------------------------+
|             VERIQTA PROJECT 4 CUSTOM VPC             |
|                    10.0.0.0/16                       |
|                                                      |
|    PUBLIC SUBNET                 PRIVATE SUBNET       |
|    10.0.1.0/24                   10.0.2.0/24          |
|                                                      |
|    +---------------------+                           |
|    | EC2 INSTANCE        |                           |
|    |                     |                           |
|    | Private IPv4        |                           |
|    | 10.0.1.x            |                           |
|    |                     |                           |
|    | Public IPv4         |                           |
|    | x.x.x.x             |                           |
|    |                     |                           |
|    | Amazon Linux 2023   |                           |
|    +----------+----------+                           |
|               |                                      |
|               v                                      |
|    PUBLIC ROUTE TABLE                                |
|                                                      |
|    10.0.0.0/16 → local                               |
|    0.0.0.0/0   → Internet Gateway                    |
|                                                      |
+------------------------------------------------------+
```

This project connects several AWS concepts that beginners often learn separately:

```text
EC2
+
VPC
+
Subnet
+
Public IP
+
Route table
+
Internet Gateway
+
Security group
+
SSH
```

A successful SSH connection depends on all of them working together.

# Part 15: Understand the Two IP Addresses

Your instance might eventually have:

```text
Private IPv4:
10.0.1.45

Public IPv4:
3.90.120.44
```

The private address belongs to:

```text
10.0.1.0/24
```

and is used inside the VPC.

The public address makes the instance reachable through internet networking when the rest of the architecture permits it.

Do not expect the public IP to appear as the primary address directly configured on the Linux network interface in the same way as the private address.

AWS performs the relevant public/private address mapping through its networking infrastructure.

# Part 18: Understand /32

You may see:

```text
YOUR_PUBLIC_IP/32
```

For example:

```text
198.51.100.25/32
```

A `/32` represents one IPv4 address.

That makes it appropriate when you want:

```text
Only this public IP
```

to initiate SSH connections.

Compare:

```text
198.51.100.25/32
```

One address.

Versus:

```text
0.0.0.0/0
```

Every IPv4 address.

The difference matters.

# Part 20: Understand Security Group Outbound Rules

The default outbound security-group configuration commonly permits outbound traffic.

Leave the default outbound configuration in place for this beginner lab.

Security groups are stateful. Return traffic for an allowed connection is tracked by the security-group connection state.

Network ACLs behave differently because they are stateless.

That distinction becomes important during troubleshooting.

# Part 34: Find the Instance's Public IP from Inside Linux

You may want to compare what AWS reports externally.

One option is to query the EC2 Instance Metadata Service for instance metadata.

Use IMDSv2.

Get a token:

```bash
TOKEN=$(curl -sS -X PUT \
  "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
```

Then query the local IPv4 address:

```bash
curl -sS \
  -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/local-ipv4
```

You should see your private IP.

Then query the public IPv4 address:

```bash
curl -sS \
  -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4
```

If the instance has a public IPv4 address, it should be returned.

# Part 38: Understand Existing Connections

If an already-open SSH session does not immediately die after you change the security-group rule, do not assume the rule change failed.

Security groups track connections, and changes do not necessarily terminate already tracked connections immediately.

# Part 41: Troubleshooting Framework

When SSH fails, do not start randomly changing settings.

Use this order:

```text
1. Is the instance running?

2. Did instance status checks pass?

3. Is the instance in the expected VPC?

4. Is it in the expected subnet?

5. Does it have a public IPv4 address?

6. Does the subnet use the public route table?

7. Does the public route table have 0.0.0.0/0 → IGW?

8. Is the Internet Gateway attached?

9. Does the security group allow TCP/22 from my current IP?

10. Does the subnet NACL permit the required traffic?

11. Am I using the correct username?

12. Am I using the correct private key?

13. Are the private-key permissions correct?

14. Is SSH running inside Linux?
```

That is a much better troubleshooting process than:

```text
Delete everything and relaunch.
```

# What You Should Understand Before Moving On

Do not finish this project thinking only:

```text
I launched an EC2 instance inside a VPC.
```

You should now be able to explain why the connection works.

The instance was launched into:

```text
10.0.1.0/24
```

so AWS assigned its primary private IPv4 address from that subnet.

The subnet is associated with a route table containing:

```text
0.0.0.0/0 → Internet Gateway
```

which gives internet-destined IPv4 traffic a route out of the VPC.

The Internet Gateway is attached to the VPC.

The instance has a public IPv4 address.

The security group allows:

```text
TCP 22
```

from your specific public IP.

AWS specifically notes that SSH cannot work if the associated security group does not allow SSH traffic.

The instance's operating system runs:

```text
sshd
```

which listens for the SSH connection.

Therefore the complete path is:

```text
Your computer
      |
      | SSH TCP/22
      v
Internet
      |
      v
Public IPv4
      |
      v
Internet Gateway
      |
      v
Public route table
      |
      v
Public subnet
      |
      v
Security group
      |
      v
EC2 network interface
      |
      v
Amazon Linux
      |
      v
sshd
```

If SSH fails, you now have a sequence of layers to investigate instead of guessing.

That is the real objective of Project 5.

You are no longer simply launching EC2.

You are beginning to understand how an EC2 instance actually becomes reachable through an AWS network.
