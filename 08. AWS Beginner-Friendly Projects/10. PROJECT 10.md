# Project 10: Monitor an EC2 Instance with CloudWatch

Launching an EC2 instance tells you that a server exists.

Monitoring tells you what that server is doing.

A running instance can still have problems.

It might have:

```text
High CPU utilization
Network spikes
Disk activity
Failed status checks
Application performance problems
Unexpected load
```

If nobody is watching those signals, you might discover the problem only after users complain.

In this project, you will use Amazon CloudWatch to monitor an EC2 instance and create an alarm that reacts when CPU utilization exceeds a defined threshold.

The monitoring architecture will look like this:

```text
                    AMAZON EC2
                        |
                        |
                        | CPUUtilization
                        |
                        v
                AMAZON CLOUDWATCH
                        |
                 CloudWatch Metric
                        |
                        v
                  CPU ALARM
                        |
              Threshold exceeded?
                    /       \
                  NO         YES
                  |           |
                  v           v
                  OK        ALARM
                              |
                              v
                       AMAZON SNS
                              |
                              v
                     EMAIL NOTIFICATION
```

We will deliberately create CPU load on our own temporary EC2 instance so that you can observe the metric rise and the alarm change state.

The final workflow will be:

```text
Launch EC2
    |
    v
Observe CPUUtilization
    |
    v
Create SNS topic
    |
    v
Confirm email subscription
    |
    v
Create CPU alarm
    |
    v
Generate temporary CPU load
    |
    v
CPU rises
    |
    v
Alarm enters ALARM
    |
    v
SNS notification arrives
    |
    v
Stop load
    |
    v
CPU falls
    |
    v
Alarm returns to OK
    |
    v
Investigate metric history
    |
    v
Clean up everything
```

AWS supports creating CloudWatch alarms directly against EC2 `CPUUtilization` metrics, and alarm actions can notify an Amazon SNS topic when the alarm changes state.

# Part 1: Understand CloudWatch Metrics

Amazon EC2 publishes operational metrics into:

```text
Amazon CloudWatch
```

The EC2 metric namespace is:

```text
AWS/EC2
```

Metrics include signals such as:

```text
CPUUtilization

NetworkIn

NetworkOut

DiskReadBytes

DiskWriteBytes

StatusCheckFailed

StatusCheckFailed_Instance

StatusCheckFailed_System
```

For this project, our main metric is:

```text
CPUUtilization
```

Each EC2 instance can be identified in the metric using the dimension:

```text
InstanceId
```

For example:

```text
Namespace:
AWS/EC2

Metric:
CPUUtilization

Dimension:
InstanceId=i-0123456789abcdef0
```

CloudWatch dimensions form part of a metric's identity. EC2 metrics commonly use `InstanceId` as a dimension so CloudWatch can distinguish one instance's metric data from another.

---

# Part 2: Understand Standard and Detailed Monitoring

EC2 monitoring can operate at different resolutions.

With standard monitoring, EC2 metric data is normally available in 5-minute periods.

With detailed monitoring enabled, supported EC2 metrics are published at 1-minute intervals.

For a learning lab, detailed monitoring is useful because changes appear more quickly.

You can use:

```text
1-minute metrics
```

instead of waiting for longer 5-minute intervals.

However, detailed monitoring can have additional CloudWatch cost implications depending on your environment.

Always check current AWS pricing when using monitoring features outside a temporary lab.

# Part 3: Our Alarm Logic

We will create this alarm:

```text
Metric:
CPUUtilization

Statistic:
Average

Threshold:
Greater than 50%

Period:
1 minute

Evaluation periods:
1

Datapoints to alarm:
1
```

Conceptually:

```text
CPU <= 50%
    |
    v
   OK

CPU > 50%
    |
    v
 ALARM
```

For production environments, one minute over a threshold may be too sensitive.

You might instead use something like:

```text
3 out of 5 datapoints
```

to avoid reacting to harmless short spikes.

For this lab, a shorter evaluation makes the state transition easier to observe.

# Part 4: Understand CloudWatch Alarm States

A metric alarm can normally appear in one of three states:

```text
OK

ALARM

INSUFFICIENT_DATA
```

Think of them like this:

```text
OK
Metric is currently within
the configured alarm condition.

ALARM
Metric has breached
the configured alarm condition.

INSUFFICIENT_DATA
CloudWatch does not currently have
enough information to determine
whether the condition is satisfied.
```

Alarm state is different from notification delivery.

The metric determines the alarm state.

The SNS configuration determines where state-change notifications go.

# Part 24: Retrieve CPU Data with AWS CLI

From your local computer, define a time range.

On macOS/Linux:

```bash
END_TIME=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
```

For the start time, on GNU/Linux:

```bash
START_TIME=$(date -u -d '15 minutes ago' \
  +"%Y-%m-%dT%H:%M:%SZ")
```

On macOS:

```bash
START_TIME=$(date -u -v-15M \
  +"%Y-%m-%dT%H:%M:%SZ")
```

Then:

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 \
  --metric-name CPUUtilization \
  --dimensions \
    Name=InstanceId,Value="$INSTANCE_ID" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 60 \
  --statistics Average Maximum \
  --region "$REGION" \
  --output table
```

AWS documents `get-metric-statistics` for retrieving EC2 `CPUUtilization` data for a specific `InstanceId`.

# Part 40: Create the Alarm with CLI

Run:

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name \
    veriqta-project-10-high-cpu \
  --alarm-description \
    "Project 10 CPU exceeds 50 percent" \
  --namespace AWS/EC2 \
  --metric-name CPUUtilization \
  --dimensions \
    Name=InstanceId,Value="$INSTANCE_ID" \
  --statistic Average \
  --period 60 \
  --evaluation-periods 1 \
  --datapoints-to-alarm 1 \
  --threshold 50 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions "$SNS_TOPIC_ARN" \
  --treat-missing-data missing \
  --region "$REGION"
```

AWS provides `put-metric-alarm` to create or update alarms and associate them with metrics and alarm actions.

# Part 64: Production Monitoring Lesson

A threshold should not be chosen just because:

```text
80 sounds high.
```

or:

```text
50 is easy.
```

A useful alarm should represent something requiring attention.

For example:

```text
High CPU
+
Slow application
+
Sustained duration
```

may be more meaningful than:

```text
CPU touched 51% once.
```

A good monitoring system tries to reduce both:

```text
Missed incidents
```

and:

```text
Alert noise
```

# Part 65: What You Should Investigate After a CPU Alarm

A practical investigation could follow:

```text
1. Confirm the alarm state.

2. Check CPUUtilization history.

3. Determine when the increase started.

4. Check the EC2 instance health.

5. Inspect processes using CPU.

6. Review application activity.

7. Compare NetworkIn and NetworkOut.

8. Check whether a deployment occurred.

9. Determine whether traffic increased.

10. Decide whether the load is expected.

11. Determine whether capacity is sufficient.

12. Record the root cause.
```

This turns monitoring into operations.

# What You Should Understand Before Moving On

Do not finish this project thinking only:

```text
I created a CloudWatch alarm.
```

You should understand the complete monitoring pipeline.

EC2 generates operational data.

AWS publishes EC2 metrics into CloudWatch automatically. With standard monitoring, EC2 generally provides 5-minute metric data, and with detailed monitoring it provides 1-minute data for supported metrics.

For this project, the important metric was:

```text
AWS/EC2
    |
    v
CPUUtilization
    |
    v
InstanceId
```

The CloudWatch alarm then evaluated that metric against a rule:

```text
Average CPUUtilization > 50%
```

When the condition was false:

```text
OK
```

When CPU remained above the configured threshold for the required evaluation:

```text
ALARM
```

The alarm action pointed to:

```text
Amazon SNS
```

and SNS delivered the notification to a confirmed email subscriber. AWS requires email subscriptions to be confirmed before they receive notifications.

Most importantly, you did not stop at receiving the alert.

You investigated it.

You compared:

```text
CloudWatch CPUUtilization
```

with:

```text
top

ps

uptime
```

inside the operating system.

That allowed you to move from:

```text
SYMPTOM

CPU is high.
```

to:

```text
EVIDENCE

CPU increased during the alert period.

stress-ng is consuming CPU.

The increase started during
the controlled Project 10 test.

No unexplained production workload
caused the spike.
```

That is the real monitoring workflow:

```text
OBSERVE
   |
   v
DETECT
   |
   v
ALERT
   |
   v
INVESTIGATE
   |
   v
UNDERSTAND
   |
   v
RESPOND
```

CloudWatch is not valuable because it draws graphs.

It is valuable because metrics, alarms, notifications, and investigation give you evidence about what your systems are doing and help you respond before a problem becomes larger.
