# Project 13: Build a Serverless API with AWS Lambda and API Gateway

Project 12 introduced serverless functions.

You created Lambda code, invoked it directly, connected an event source, and investigated CloudWatch Logs.

Project 13 changes one important thing.

Instead of another AWS service invoking your Lambda function, users and applications will invoke it through an HTTP endpoint.

You will build this architecture:

```text
CLIENT
Browser / curl / application
        |
        | HTTPS request
        v
+--------------------------+
| AMAZON API GATEWAY       |
|                          |
| HTTP API                 |
|                          |
| GET  /                   |
| GET  /hello              |
| GET  /hello/{name}       |
| POST /messages           |
+------------+-------------+
             |
             | Lambda proxy integration
             v
+--------------------------+
| AWS LAMBDA               |
|                          |
| Python function          |
|                          |
| Reads:                   |
| HTTP method              |
| Path                     |
| Path parameters          |
| Query parameters         |
| JSON body                |
+------------+-------------+
             |
             v
       JSON RESPONSE
             |
             v
        API GATEWAY
             |
             v
           CLIENT
```

Amazon API Gateway HTTP APIs can integrate directly with AWS Lambda. When a client calls the API, API Gateway sends the request to the Lambda integration and returns the backend response to the client.

# Part 1: What Is an API?

An API gives one system a defined way to interact with another system.

For this project, the client sends an HTTP request such as:

```text
GET /hello
```

and receives:

```json
{
  "message": "Hello from VERIQTA Project 13"
}
```

The client does not need to know how Lambda is implemented internally.

It only needs to understand the API contract.

Conceptually:

```text
CLIENT
  |
  | Request
  v
API
  |
  v
APPLICATION LOGIC
  |
  | Response
  v
CLIENT
```

# Part 6: Understand Lambda Proxy Integration

For this project API Gateway will use:

```text

```

integration.

With Lambda proxy integration, API Gateway forwards the incoming request information to Lambda instead of requiring you to manually map every request field.

API Gateway then uses the Lambda response as the basis for the HTTP response sent back to the client.


AWS CLI supports configuring an HTTP API Lambda proxy integration with `AWS_PROXY` and payload format version `2.0`.

# Part 13: Create the Lambda Application

Create:

```text
lambda_function.py
```

Use:

```python
import base64
import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)


def response(status_code, body):
    """
    Create an HTTP API compatible response.
    """

    return {
        "statusCode": status_code,
        "headers": {
            "content-type": "application/json"
        },
        "body": json.dumps(body)
    }


def parse_json_body(event):
    """
    Decode and parse the incoming JSON request body.
    """

    raw_body = event.get("body")

    if not raw_body:
        return {}

    if event.get("isBase64Encoded"):
        raw_body = base64.b64decode(
            raw_body
        ).decode("utf-8")

    try:
        return json.loads(raw_body)

    except json.JSONDecodeError as exc:
        raise ValueError(
            "Request body must contain valid JSON."
        ) from exc


def lambda_handler(event, context):

    logger.info(
        "Request started. request_id=%s",
        context.aws_request_id
    )

    logger.info(
        "Incoming API event=%s",
        json.dumps(event)
    )

    try:
        request_context = event.get(
            "requestContext",
            {}
        )

        http_context = request_context.get(
            "http",
            {}
        )

        method = http_context.get(
            "method",
            ""
        )

        path = event.get(
            "rawPath",
            "/"
        )

        route_key = event.get(
            "routeKey",
            ""
        )

        logger.info(
            "HTTP request method=%s path=%s route=%s",
            method,
            path,
            route_key
        )

        # GET /
        if method == "GET" and path == "/":

            return response(
                200,
                {
                    "project": 13,
                    "service": "VERIQTA Serverless API",
                    "message": (
                        "Your AWS Lambda API is running."
                    ),
                    "routes": [
                        "GET /",
                        "GET /health",
                        "GET /hello",
                        "GET /hello/{name}",
                        "POST /messages"
                    ]
                }
            )

        # GET /health
        if method == "GET" and path == "/health":

            return response(
                200,
                {
                    "status": "healthy",
                    "project": 13
                }
            )

        # GET /hello
        if method == "GET" and path == "/hello":

            query = event.get(
                "queryStringParameters"
            ) or {}

            name = query.get(
                "name",
                "World"
            )

            return response(
                200,
                {
                    "message": f"Hello {name}",
                    "source": "query-string"
                }
            )

        # GET /hello/{name}
        if (
            method == "GET"
            and route_key == "GET /hello/{name}"
        ):

            path_parameters = event.get(
                "pathParameters"
            ) or {}

            name = path_parameters.get(
                "name",
                "World"
            )

            return response(
                200,
                {
                    "message": f"Hello {name}",
                    "source": "path-parameter"
                }
            )

        # POST /messages
        if (
            method == "POST"
            and path == "/messages"
        ):

            body = parse_json_body(
                event
            )

            name = str(
                body.get("name", "")
            ).strip()

            message = str(
                body.get("message", "")
            ).strip()

            if not name:

                return response(
                    400,
                    {
                        "error": (
                            "The name field is required."
                        )
                    }
                )

            if not message:

                return response(
                    400,
                    {
                        "error": (
                            "The message field is required."
                        )
                    }
                )

            if len(name) > 100:

                return response(
                    400,
                    {
                        "error": (
                            "Name cannot exceed "
                            "100 characters."
                        )
                    }
                )

            if len(message) > 500:

                return response(
                    400,
                    {
                        "error": (
                            "Message cannot exceed "
                            "500 characters."
                        )
                    }
                )

            logger.info(
                "Message accepted. "
                "name=%s message_length=%s",
                name,
                len(message)
            )

            return response(
                201,
                {
                    "status": "accepted",
                    "name": name,
                    "message": message,
                    "requestId": (
                        context.aws_request_id
                    )
                }
            )

        return response(
            404,
            {
                "error": "Route not found.",
                "method": method,
                "path": path
            }
        )

    except ValueError as exc:

        logger.warning(
            "Client request failed validation. "
            "error=%s",
            str(exc)
        )

        return response(
            400,
            {
                "error": str(exc)
            }
        )

    except Exception:

        logger.exception(
            "Unhandled API failure."
        )

        return response(
            500,
            {
                "error": (
                    "Internal server error."
                ),
                "requestId": (
                    context.aws_request_id
                )
            }
        )
```

# Part 14: Understand the Response Function

This helper:

```python
def response(status_code, body):
```

creates:

```python
{
    "statusCode": ...,
    "headers": ...,
    "body": ...
}
```

API Gateway expects the Lambda integration to produce a valid response shape. Incorrect output from a Lambda proxy integration can result in an API Gateway `502 Bad Gateway`.

For example:

```python
return response(
    200,
    {
        "message": "Hello"
    }
)
```

becomes an HTTP response with:

```text
Status:
200
```

and JSON content.

These requests look similar:

```text

```

and:

```text

```

But they reach Lambda differently.

Query:

```python
event[
    "queryStringParameters"
]["name"]
```

Path:

```python
event[
    "pathParameters"
]["name"]
```

Understanding this distinction matters when designing APIs.

# Part 69: Troubleshooting Framework

When your serverless API fails, investigate in this order:

```text
1. Is the API endpoint correct?

2. Does the API exist?

3. Does the requested route exist?

4. Is the correct HTTP method being used?

5. Is the route attached to the integration?

6. Does the Lambda integration exist?

7. Does API Gateway have permission
   to invoke Lambda?

8. Is Lambda active?

9. Is the handler correct?

10. Does Lambda run successfully
    when invoked directly?

11. Is the request body valid?

12. Does Lambda return a valid
    API response?

13. Is the function timing out?

14. What do Lambda logs show?

15. What do Lambda metrics show?
```

```text
API Gateway endpoint
```


AWS describes API Gateway as the service that provides HTTP endpoints which route requests to Lambda functions.

# What You Should Understand Before Moving On

Do not finish Project 13 thinking only:

```text
I connected API Gateway to Lambda.
```

You should understand the entire serverless request path.

The client begins with:

```text
HTTPS REQUEST
```

For example:

```text
GET /hello/Ann
```

API Gateway receives that request.

The route:

```text
GET /hello/{name}
```

determines which integration handles it.

HTTP API routes are defined by an HTTP method and resource path.

The Lambda proxy integration then forwards the request information to Lambda.

```text
API GATEWAY
      |
      | AWS_PROXY
      | payload 2.0
      v
LAMBDA
```

AWS documents proxy integration as a direct way to send API request data to a Lambda backend and return the Lambda response to the client.

The Lambda function reads:

```text
HTTP method

Path

Route key

Path parameters

Query parameters

Headers

JSON body
```

It then executes application logic.

For example:

```text
GET /hello/Ann
        |
        v
name = Ann
        |
        v
Lambda
        |
        v
{
  "message": "Hello Ann"
}
```

The function returns an HTTP-compatible response.

API Gateway sends that response to the caller.

```text
CLIENT
   |
   v
API GATEWAY
   |
   v
LAMBDA
   |
   v
APPLICATION LOGIC
   |
   v
LAMBDA RESPONSE
   |
   v
API GATEWAY
   |
   v
CLIENT
```

There are also two separate IAM directions to understand.

First:

```text
LAMBDA EXECUTION ROLE
```

controls what Lambda itself may access.

In this project the function only needs:

```text
CloudWatch Logs
```

Second:

```text
LAMBDA RESOURCE POLICY
```

allows:

```text
API Gateway
```

to call:

```text
lambda:InvokeFunction
```

Those permission directions solve different problems.

You also learned that API errors occur at different layers.

```text
Unknown API Gateway route
→ request may never reach Lambda

HTTP 400 from application
→ Lambda executed but rejected bad input

HTTP 500 from application
→ Lambda ran but application failed

502 Bad Gateway
→ often investigate integration or
   malformed Lambda proxy response
```

AWS specifically notes that an invalid Lambda proxy output format can cause API Gateway to return `502 Bad Gateway`.

Finally, you used CloudWatch Logs to answer the most important troubleshooting question:

```text
How far did the request get?
```

Your troubleshooting flow should now be:

```text
CLIENT REQUEST
      |
      v
API ENDPOINT CORRECT?
      |
      v
ROUTE EXISTS?
      |
      v
INTEGRATION EXISTS?
      |
      v
API GATEWAY CAN INVOKE LAMBDA?
      |
      v
LAMBDA INVOKED?
      |
      v
HANDLER EXECUTES?
      |
      v
REQUEST VALID?
      |
      v
RESPONSE FORMAT VALID?
      |
      v
CLOUDWATCH LOGS
```

That is the foundation of a serverless HTTP API.

You are no longer running a web server just to expose a small endpoint.

You are combining:

```text
API Gateway
+
Lambda
+
IAM
+
CloudWatch
```

to create an event-driven HTTP application without managing an EC2 web server.
