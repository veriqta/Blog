# Project 17: Deploy Infrastructure with AWS CloudFormation

So far, most of the AWS resources in this series have been created manually through the AWS Console or individually with AWS CLI commands.

That works while learning.

But imagine building the same environment repeatedly.

You might need to remember:

```text
Create the bucket.

Enable versioning.

Enable encryption.

Enable Block Public Access.

Add tags.

Configure lifecycle rules.

Create related resources.

Repeat all of it in another account.
```

Manual configuration quickly becomes difficult to reproduce.

Infrastructure as Code changes that.

Instead of describing your infrastructure only in your head or a checklist, you describe it in a file.

For this project, that file will be:

```text
project17.yaml
```

The file will describe the AWS resources we want.

CloudFormation will read the template and create those resources for us.

The architecture is:

```text
               YAML TEMPLATE
                    |
                    |
                    v
           +------------------+
           | CLOUDFORMATION   |
           |                  |
           | Stack            |
           | Resource graph   |
           | State tracking   |
           +--------+---------+
                    |
                    v
             AWS RESOURCES
                    |
                    v
           +------------------+
           | AMAZON S3       |
           |                  |
           | Private bucket   |
           | Encryption       |
           | Versioning       |
           | Public access    |
           | blocked          |
           +------------------+
```

CloudFormation calls the deployed collection of resources a stack. Stack operations include creation, updates, inspection, and deletion.

# Part 1: What Infrastructure as Code Means

Infrastructure as Code, usually shortened to:

```text
IaC
```

means defining infrastructure using machine-readable configuration.

Instead of manually performing:

```text
Create S3 bucket

Enable versioning

Configure encryption

Add tags
```

you write those requirements into a template.

Conceptually:

```text
MANUAL APPROACH

Engineer
   |
   v
AWS Console
   |
   v
Resource
```

versus:

```text
INFRASTRUCTURE AS CODE

Engineer
   |
   v
Template
   |
   v
CloudFormation
   |
   v
Resource
```

The template becomes a reproducible description of the intended infrastructure.



```text

Outputs
```

The most important section is:


```text

```

```text

```


```text

```

# Part 4: Understand Logical IDs and Physical IDs

Inside the template, we will call our bucket:

```text
ProjectBucket
```

That is its:

```text
Logical ID
```

CloudFormation uses logical IDs inside the template.

AWS creates a real resource with a physical identity.

Example:

```text
Logical ID

ProjectBucket
```

might correspond to:

```text
Physical ID

veriqta-project-17-123456789012-us-east-1
```

The logical ID belongs to CloudFormation's template model.

The physical ID belongs to the actual AWS resource.

# Part 9: Write Your First CloudFormation Template

Create:

```text
project17.yaml
```

Run:

```bash
cat > project17.yaml <<'EOF'
AWSTemplateFormatVersion: '2010-09-09'

Description: >
  VERIQTA Project 17.
  Deploy a secure Amazon S3 bucket
  using AWS CloudFormation.

Parameters:

  BucketName:
    Type: String

    Description: >
      Globally unique name for the
      Project 17 S3 bucket.

Resources:

  ProjectBucket:

    Type: AWS::S3::Bucket

    Properties:

      BucketName:
        Ref: BucketName

      BucketEncryption:

        ServerSideEncryptionConfiguration:

          - ServerSideEncryptionByDefault:

              SSEAlgorithm: AES256

      PublicAccessBlockConfiguration:

        BlockPublicAcls: true

        IgnorePublicAcls: true

        BlockPublicPolicy: true

        RestrictPublicBuckets: true

      VersioningConfiguration:

        Status: Enabled

      Tags:

        - Key: Project
          Value: '17'

        - Key: Brand
          Value: VERIQTA

        - Key: ManagedBy
          Value: CloudFormation

Outputs:

  BucketName:

    Description: >
      Name of the S3 bucket.

    Value:
      Ref: ProjectBucket

  BucketArn:

    Description: >
      ARN of the S3 bucket.

    Value:
      Fn::GetAtt:
        - ProjectBucket
        - Arn

  BucketRegionalDomainName:

    Description: >
      Regional S3 domain name.

    Value:
      Fn::GetAtt:
        - ProjectBucket
        - RegionalDomainName
EOF
```

CloudFormation's `AWS::S3::Bucket` resource creates an S3 bucket in the same Region where the stack is deployed.

# Part 13: Understand Parameters

Our template contains:

```yaml

  BucketName:
    Type: String
```

That means we can reuse the same template with different bucket names.

Instead of embedding:

```text
veriqta-project-17-123456789012-us-east-1
```

inside the template, we pass it during deployment.

Conceptually:

```text
TEMPLATE
   |
   | BucketName parameter
   v
DEPLOYMENT
```

# Part 14: Understand Resources

The main section is:

```yaml
Resources:
```

Inside it:

```yaml
ProjectBucket:
```

is the logical ID.

And:

```yaml
Type: AWS::S3::Bucket
```

tells CloudFormation what type of AWS resource to create.

AWS documents `AWS::S3::Bucket` as the CloudFormation resource type for creating S3 buckets.

---

# Part 15: Understand Properties

Inside:

```yaml
Properties:
```

we define the configuration of the resource.

For example:

```yaml
BucketName:
  Ref: BucketName
```

This uses the parameter value passed during deployment.

---

# Part 16: Understand Ref

This:

```yaml
Ref: BucketName
```

references the parameter called:

```text
BucketName
```

But this:

```yaml
Ref: ProjectBucket
```

in an output references the resource.

For an S3 bucket, that returns the bucket name.

CloudFormation intrinsic functions allow different parts of a template to reference other template values.

---

# Part 17: Understand Fn::GetAtt

We use:

```yaml
Fn::GetAtt:
  - ProjectBucket
  - Arn
```

to obtain the bucket ARN.

We also use:

```yaml
Fn::GetAtt:
  - ProjectBucket
  - RegionalDomainName
```

to obtain the bucket's regional domain name.

This lets CloudFormation compute outputs from deployed resources rather than forcing you to hard-code them.

# Part 19: Why Validation Matters

Validation can identify:

```text
Malformed template syntax

Incorrect template structure

Invalid sections
```

before a stack creation attempt.

But validation does not prove every resource will successfully deploy.

For example:

```text
Bucket name already exists
```

can still cause stack creation to fail later.

So think of validation as:

```text
Template structure check
```

rather than:

```text
Guaranteed successful deployment
```

# Part 36: Add a Lifecycle Rule

Edit:


```yaml

    Tags:

      - Key: Project
        Value: '17'

      - Key: Brand
        Value: VERIQTA

      - Key: ManagedBy
        Value: CloudFormation

      - Key: Environment
        Value: Training
```

Keep the rest of the template unchanged.

```text

CloudFormation
       |

       v
UPDATED TEMPLATE
       |
       v
Required changes
       |
       v

```

# Part 47: Detect Configuration Drift Conceptually

Suppose someone manually changes:

```text
Versioning
```

or:

```text
Tags
```

outside CloudFormation.

Then:

```text
Template's expected configuration
```

and:

```text
Actual AWS configuration
```

may no longer match.

This is called:

```text
drift
```

Infrastructure as Code works best when the defined deployment workflow remains the primary source of infrastructure changes.

# Part 52: Understand Rollback

Suppose a stack operation starts but one resource cannot be created.

CloudFormation can roll back changes rather than leaving the intended deployment halfway completed.

AWS also provides stack failure options for cases where you deliberately want successfully provisioned resources preserved instead of automatically removed during failure handling.

Conceptually:

```text
Create Resource A
      |
      v
SUCCESS

Create Resource B
      |
      v
FAILURE
      |
      v
STACK FAILURE
      |
      v
ROLLBACK
```

This transactional behavior is one of the major benefits of managing related infrastructure through a stack.

# Part 54: Understand CloudFormation Resource Dependencies

CloudFormation analyzes relationships between resources.

If one resource references another using constructs such as:

```text
Ref

Fn::GetAtt
```

CloudFormation can infer dependency ordering.

Larger templates may contain:

```text
VPC

Subnets

Security groups

EC2 instances

Load balancers

IAM roles

Databases
```

CloudFormation builds the dependency graph needed to determine what can be created in parallel and what must wait.

# Part 55: Understand DeletionPolicy

CloudFormation supports:

```text
DeletionPolicy
```

to control what happens to a resource when the stack is deleted.

One option is:

```yaml
DeletionPolicy: Retain
```

AWS documents `Retain` as a way to keep a resource after its stack is deleted.

Example:

```yaml
ProjectBucket:

  Type: AWS::S3::Bucket

  DeletionPolicy: Retain
```

would tell CloudFormation:

```text
Delete the stack,
but do not delete this bucket.
```

We will not use `Retain` in the main lab because our goal is complete cleanup.

---

# Part 56: Understand Why Retain Matters for Data

Some infrastructure is disposable.

Some resources contain important data.

For example:

```text
S3 buckets

Databases

Persistent storage
```

might need stronger deletion protection.

Using:

```text
DeletionPolicy: Retain
```

is one CloudFormation mechanism for preserving selected resources.

But remember:

```text
Retained resource
```

does not disappear.

You remain responsible for:

```text
security

cost

maintenance

eventual deletion
```

after CloudFormation stops managing it as part of the deleted stack.


for situations where an update causes a resource to be replaced.

AWS documents options such as:

```text
Delete

Retain

Snapshot
```

depending on the resource and policy.

This is separate from ordinary:

```text
stack deletion
```

and becomes important when infrastructure updates replace stateful resources.

# Cleanup Step 7: Delete Stored Versions

Use Python to build a valid `delete-objects` request.

Run:

```bash
python3 - <<'PY'
import json

source = "project17-object-versions.json"
destination = "project17-delete-objects.json"

with open(source) as f:
    data = json.load(f)

objects = []

for version in data.get("Versions", []):
    objects.append(
        {
            "Key": version["Key"],
            "VersionId": version["VersionId"]
        }
    )

for marker in data.get("DeleteMarkers", []):
    objects.append(
        {
            "Key": marker["Key"],
            "VersionId": marker["VersionId"]
        }
    )

with open(destination, "w") as f:
    json.dump(
        {
            "Objects": objects,
            "Quiet": False
        },
        f,
        indent=2
    )

print(
    f"Prepared {len(objects)} objects for deletion."
)
PY
```

# What You Should Understand Before Moving On

Do not finish Project 17 thinking:

```text
CloudFormation creates S3 buckets.
```

That is only the resource we used for the lab.

The important concept is:

```text
INFRASTRUCTURE
AS
CODE
```

Instead of manually describing your environment through clicks, you write:

```yaml
Resources:

  ProjectBucket:

    Type: AWS::S3::Bucket
```

CloudFormation reads the template.

Then:

```text
TEMPLATE
    |
    v
CLOUDFORMATION
    |
    v
STACK
    |
    v
AWS RESOURCE
```

The:

```text
TEMPLATE
```

defines desired infrastructure.

The:

```text
STACK
```

represents the deployed and CloudFormation-managed infrastructure.

CloudFormation supports stack creation, direct updates, inspection, and deletion as lifecycle operations.

You also learned that:

```text
Logical ID
```

is not the same as:

```text
Physical ID.
```

In our template:

```text
ProjectBucket
```

is CloudFormation's logical identifier.

The actual bucket name is the physical resource identity.

You learned how:

```text
Parameters
```

make templates reusable.

Instead of hard-coding one bucket name:

```text
Template
   |
   v
Parameter
   |
   v
Different deployment values
```

You learned how:

```text
Outputs
```

expose useful resource information after deployment.

For example:

```text
BucketName

BucketArn

RegionalDomainName
```

You learned how stack updates work:

```text
Modify template
       |
       v
Validate
       |
       v
Change Set
       |
       v
Review changes
       |
       v
Execute
       |
       v
CloudFormation updates resources
```

A direct update causes CloudFormation to deploy new template or parameter values against the existing stack, while change sets can be used to inspect the planned modifications first.

You also learned one of the most important concepts for stateful infrastructure:

```text
Deletion behavior.
```

By default, CloudFormation generally attempts to remove managed resources when their stack is deleted.

But you can explicitly use:

```yaml
DeletionPolicy: Retain
```

when a resource should remain after stack deletion. AWS documents `Retain` as a supported deletion policy for resources including S3 buckets.

And you discovered that CloudFormation does not magically make every deletion problem disappear.

For S3:

```text
CloudFormation says:
Delete bucket.

S3 says:
Bucket contains objects.

Result:
DELETE_FAILED
```

The bucket must be emptied before S3 permits deletion.

That gives you a much stronger infrastructure lifecycle model:

```text
              SOURCE CODE
                   |
                   v
             YAML TEMPLATE
                   |
                   v
            CLOUDFORMATION
                   |
                   v
                STACK
                   |
        +----------+----------+
        |                     |
        v                     v
    RESOURCES              OUTPUTS
        |
        v
   AWS SERVICES
        |
        v
   RUNNING STATE

        |

Template update

        |
        v
   CHANGE SET
        |
        v
 STACK UPDATE

        |

Stack deletion

        |
        v
Deletion policies
        |
        v
Resource cleanup
```

Your troubleshooting model should now be:

```text
TEMPLATE VALID?
      |
      v
PARAMETERS CORRECT?
      |
      v
STACK OPERATION STARTED?
      |
      v
STACK EVENTS?
      |
      v
WHICH LOGICAL RESOURCE FAILED?
      |
      v
RESOURCE STATUS REASON?
      |
      v
IAM PERMISSION?
      |
      v
RESOURCE CONSTRAINT?
      |
      v
ROLLBACK?
      |
      v

```

The biggest lesson from Project 17 is that infrastructure now becomes something you can:

```text

validate

deploy

compare

update

reproduce

delete
```

through code rather than relying on a sequence of manual console changes.

That is the foundation of Infrastructure as Code with AWS CloudFormation.
