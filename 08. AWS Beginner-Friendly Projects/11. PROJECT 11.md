# Project 11: Create an SNS Notification System

Applications and infrastructure constantly generate events.

Examples include:

```text
CPU utilization becomes too high.

A server fails.

A deployment completes.

An application reports an error.

A backup fails.

A security event occurs.

A queue becomes overloaded.
```

The system detecting the event should not always need to know exactly who needs to receive the notification.

Instead, it can publish an event to a notification service.

That is where Amazon Simple Notification Service, Amazon SNS, becomes useful.

Amazon SNS provides asynchronous messaging using topics and subscriptions.

The basic architecture is:

```text
Publisher
    |
    | Publish message
    v
SNS Topic
    |
    +------------------+
    |                  |
    v                  v
Email              Other Subscriber
```

A more realistic monitoring architecture is:

```text
EC2 INSTANCE
     |
     | CPUUtilization
     v
CLOUDWATCH
     |
     | Threshold breached
     v
CLOUDWATCH ALARM
     |
     | Publish notification
     v
SNS TOPIC
     |
     +----------------------+
     |                      |
     v                      v
EMAIL SUBSCRIBER      FUTURE CONSUMER
```

SNS topics act as communication channels between publishers and subscribers. Messages published to a topic can be delivered to subscribed endpoints using supported delivery protocols.

# Part 1: Understand the Publish and Subscribe Model

Amazon SNS uses a publish and subscribe model.

A publisher sends a message to:

```text
SNS Topic
```

Subscribers listen to that topic.

For example:

```text
                    SNS TOPIC
                       |
       +---------------+---------------+
       |               |               |
       v               v               v
     Email           SQS            Lambda
```

For this beginner project, we will use:

```text
Email
```

as the subscriber.

The key idea is that the publisher does not need to know the email recipient directly.

It only needs to know:

```text
Publish to this SNS topic.
```

SNS manages delivery to the subscribers attached to that topic.

---

# Part 2: Understand the Components

Our architecture has four important pieces.

## Publisher

The publisher produces the message.

Examples:

```text
AWS CLI

CloudWatch Alarm

Application code

AWS service
```

---

## Topic

The topic is the logical communication channel.

Our topic will be:

```text
veriqta-project-11-alerts
```

AWS SNS supports creating Standard and FIFO topics. For this simple notification system we will use a Standard topic.

---

## Subscription

A subscription connects an endpoint to the topic.

Our subscription will use:

```text
Protocol:
Email
```

and:

```text
Endpoint:
Your email address
```

Email subscriptions must be confirmed before they begin receiving messages.

---

## Message

A message is the information published to the topic.

Example:

```text
Subject:
VERIQTA Project 11 Test

Message:
The SNS notification system is working.
```

When a message is published to a topic, SNS attempts to deliver it to the topic's subscribed endpoints according to their subscription protocols.

Immediately after creating the subscription, you may see:

```text

```

This does not mean SNS is broken.

It means the email owner has not yet confirmed the subscription.

The flow is:

```text
Create subscription
       |
       v
SNS sends confirmation email
       |
       v
Recipient confirms
       |
       v
Subscription becomes active
```

Do not start testing message delivery until confirmation is complete.

# Part 19: Understand Fan-Out

Now imagine your topic eventually has:

```text
Subscriber 1:
Operations email

Subscriber 2:
SQS queue

Subscriber 3:
Lambda function

Subscriber 4:
Another system
```

The publisher still performs one logical action:

```text
Publish to SNS topic.
```

SNS can then fan the message out to multiple subscriptions.

Conceptually:

```text
                  PUBLISHER
                     |
                     v
                 SNS TOPIC
                     |
        +------------+------------+
        |            |            |
        v            v            v
      Email         SQS         Lambda
```

This publish and subscribe decoupling is a core use case of Amazon SNS.

# Part 20: Why This Is Event-Driven

A polling design might repeatedly ask:

```text
Has something happened yet?

Has something happened yet?

Has something happened yet?
```

An event-driven notification design works differently.

Something happens.

That event triggers a message.

The message is delivered to subscribers.

Conceptually:

```text
EVENT
  |
  v
PUBLISH
  |
  v
SNS
  |
  v
SUBSCRIBERS
```

The subscriber reacts because an event occurred rather than continuously checking for it.

# Part 28: Create the Alarm with AWS CLI

Run:

```bash

  --alarm-name \
    veriqta-project-11-test-alarm \
  --alarm-description \
    "Project 11 SNS integration test alarm" \
  --namespace \
    "VERIQTA/Project11" \
  --metric-name \
    ApplicationErrors \
  --statistic Maximum \
  --period 60 \
  --evaluation-periods 1 \
  --datapoints-to-alarm 1 \
  --threshold 1 \
  --comparison-operator \
    GreaterThanOrEqualToThreshold \
  --alarm-actions \
    "$SNS_TOPIC_ARN" \

  --region "$REGION"
```

`put-metric-alarm` creates or updates a CloudWatch alarm and can associate SNS topic ARNs with its alarm actions.

# Part 45: Understand Topic-Based Decoupling

Without SNS:

```text
CloudWatch
    |
    v

```

```text

    |
    v

    |
    +------ Subscriber C
```

You can change subscribers without redesigning the publisher.

That is one of the practical benefits of decoupling.

# Part 46: Troubleshooting Framework

If no notification arrives, check these layers in order:

```text
1. Does the SNS topic exist?

2. Is the topic ARN correct?

3. Does the subscription exist?

4. Is the email subscription confirmed?

5. Can direct sns publish reach the subscriber?

6. Does the CloudWatch metric exist?

7. Is the alarm watching the correct metric?

8. Is the threshold correct?

9. Did the alarm actually enter ALARM?

10. Does AlarmActions contain the SNS topic ARN?

11. Is the SNS topic in the expected Region?

12. What does alarm history show?
```

Do not recreate every resource immediately.

Identify which layer failed.

# Part 49: Security Principle

Do not put sensitive secrets into SNS message bodies merely because the message is being sent to your own topic.

Avoid messages containing items such as:

```text
Passwords

Private keys

Database credentials

Long-lived access keys
```

Alert messages should normally contain enough information to investigate the event without exposing credentials.

Example:

```text
GOOD

Production checkout API error rate
exceeded threshold.

Service:
checkout-api

Environment:
production

Alarm:
checkout-high-errors
```

rather than placing authentication secrets inside the alert.

# What You Should Understand Before Moving On

Do not finish Project 11 thinking only:

```text
SNS sends emails.
```

That is only one visible use of the service.

The important concept is the publish and subscribe architecture.

A publisher does this:

```text
Publish event
     |
     v
SNS Topic
```

The topic then becomes the communication channel between the producer and its subscribers.

The producer does not need to know every consumer directly.

Amazon SNS is designed around asynchronous message delivery between publishers and subscribers through topics.

You first proved SNS itself worked:

```text
AWS CLI
   |
   v
SNS Topic
   |
   v
Confirmed Email
```

Then you connected an event source:

```text
ApplicationErrors metric
        |
        v
CloudWatch
        |
        v
Alarm
        |
        v
SNS Topic
        |
        v
Email
```

CloudWatch alarms can watch metrics and publish notifications to SNS when configured alarm conditions cause state transitions.

That created a simple event-driven alerting system.

The most important troubleshooting lesson is that this architecture has separate layers:

```text
EVENT
  |
  v
METRIC
  |
  v
ALARM
  |
  v
SNS TOPIC
  |
  v
SUBSCRIPTION
  |
  v
DELIVERY
```

If the notification fails, you can test those layers individually.

You can verify the metric.

You can inspect the alarm state.

You can check `AlarmActions`.

You can publish directly to SNS.

You can inspect the subscription status.

That is much stronger than deleting everything and rebuilding whenever an alert does not arrive.

The architecture you should remember is:

```text
                    EVENT PRODUCER
                          |
                          v
                    CLOUDWATCH
                          |
                          v
                        ALARM
                          |
                          v
                      SNS TOPIC
                          |
             +------------+------------+
             |                         |
             v                         v
           HUMAN                FUTURE SYSTEM
        NOTIFICATION               CONSUMER
```

SNS is therefore not merely an email tool.

It is the messaging layer that lets publishers announce events without tightly coupling themselves to every system or person that needs to react.
