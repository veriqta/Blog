# Project 12: Build Your First Serverless Function with AWS Lambda

In the earlier projects, your applications depended on EC2 servers.

You launched virtual machines, installed software, configured networking, monitored servers, and eventually introduced Auto Scaling.

AWS Lambda changes the operating model.

You provide code.

AWS provides and manages the execution environment needed to run that code.

You do not launch an EC2 instance for this project.

The basic architecture starts like this:

```text
TEST EVENT
    |
    v
AWS LAMBDA
    |
    v
PYTHON HANDLER
    |
    +----> RETURN RESPONSE
    |
    +----> WRITE LOGS
              |
              v
       CLOUDWATCH LOGS
```

Then we will add an actual event source:

```text
UPLOAD FILE
    |
    v
AMAZON S3
    |
    | ObjectCreated event
    v
AWS LAMBDA
    |
    v
PROCESS EVENT
    |
    +----> Read object metadata
    |
    +----> Write structured logs
              |
              v
       CLOUDWATCH LOGS
```

AWS documents this S3-to-Lambda pattern directly. S3 can invoke a Lambda function when objects are created, and Lambda can write information about the invocation to CloudWatch Logs.

# Part 3: Understand the Lambda Execution Role

Lambda code does not automatically have unlimited permission to AWS.

Instead, the function assumes an IAM:

```text
Execution Role
```

The role answers:

```text
What is this Lambda function allowed to do?
```

AWS states that Lambda automatically assumes the execution role when the function runs. The role's trust policy must trust:

```text
lambda.amazonaws.com
```

as the service principal.

Our execution role will allow:

```text
CloudWatch Logs:
CreateLogGroup
CreateLogStream
PutLogEvents

Amazon S3:
GetObject
```

The S3 permission will be limited to our Project 12 bucket.

# Part 4: Understand Execution Role Versus Trigger Permission

These are different permission directions.

## Execution Role

Answers:

```text
What can Lambda call?
```

Example:

```text
Lambda
   |
   | s3:GetObject
   v
S3
```

---

## Lambda Resource Policy

Answers:

```text
Who can invoke Lambda?
```

Example:

```text
S3
 |
 | lambda:InvokeFunction
 v
Lambda
```

When S3 invokes Lambda, the function needs a resource-based policy allowing the S3 service to invoke it. AWS explains that S3 must have permission in the Lambda function's resource-based policy before the trigger works.

Do not confuse these two.

# Part 14: Create the Python Function Code

Create:

```text
lambda_function.py
```

Use:

```python
import json
import logging
import os
import urllib.parse

import boto3

logger = logging.getLogger()
logger.setLevel(logging.INFO)

s3 = boto3.client("s3")


def lambda_handler(event, context):
    """
    VERIQTA Project 12 Lambda handler.

    Supports:
    1. Direct/manual test events.
    2. Amazon S3 ObjectCreated events.
    """

    logger.info(
        "Invocation started. request_id=%s",
        context.aws_request_id
    )

    logger.info(
        "Incoming event=%s",
        json.dumps(event)
    )

    try:
        records = event.get("Records", [])

        if records and records[0].get("eventSource") == "aws:s3":
            results = []

            for record in records:
                bucket_name = (
                    record["s3"]["bucket"]["name"]
                )

                encoded_key = (
                    record["s3"]["object"]["key"]
                )

                object_key = urllib.parse.unquote_plus(
                    encoded_key
                )

                event_name = record.get(
                    "eventName",
                    "unknown"
                )

                logger.info(
                    "Processing S3 object. "
                    "bucket=%s key=%s event=%s",
                    bucket_name,
                    object_key,
                    event_name
                )

                response = s3.head_object(
                    Bucket=bucket_name,
                    Key=object_key
                )

                item = {
                    "bucket": bucket_name,
                    "key": object_key,
                    "event": event_name,
                    "size_bytes": response[
                        "ContentLength"
                    ],
                    "content_type": response.get(
                        "ContentType"
                    )
                }

                results.append(item)

                logger.info(
                    "Object processed successfully. "
                    "result=%s",
                    json.dumps(item)
                )

            return {
                "statusCode": 200,
                "source": "s3",
                "requestId": context.aws_request_id,
                "objects": results
            }

        name = event.get("name", "World")
        project = event.get("project", 12)

        message = (
            f"Hello {name}. "
            f"VERIQTA Project {project} Lambda is working."
        )

        logger.info(
            "Direct invocation completed. "
            "message=%s",
            message
        )

        return {
            "statusCode": 200,
            "source": "direct",
            "requestId": context.aws_request_id,
            "message": message
        }

    except Exception:
        logger.exception(
            "Function invocation failed."
        )
        raise
```

# Part 30: Understand Synchronous and Asynchronous Invocation

Your direct CLI test behaves like a direct invocation where the caller can receive the function response.

An S3 event is different.

S3 invokes Lambda asynchronously for supported object event notifications.

Operationally, this means your function should not depend on returning a response to the person uploading the S3 object.

For our S3 trigger, the important output is:

```text

+

CloudWatch Logs
```

```text

3. Is the correct runtime configured?

4. Is the handler correct?

5. Does the deployment package contain
   the correct module?

6. Did the code raise an exception?

7. Did the function time out?

8. Does the execution role have
   required permissions?

9. Does the trigger have permission
   to invoke Lambda?

10. Is the S3 notification configured?

11. Are S3 and Lambda in the expected Region?

12. Does the object key exist?

13. What do CloudWatch Logs show?
```

# Part 55: Understand Stateless Function Design

A Lambda invocation should not assume a specific previous invocation will run on the same execution environment.

Persistent application data should normally live in external systems such as:

```text
Amazon S3

DynamoDB

RDS

ElastiCache

Other durable services
```

Do not design important persistent state around local Lambda memory or temporary runtime reuse.

# Part 56: Understand Cold and Warm Execution Conceptually

Lambda can create execution environments as needed.

A new environment requires initialization.

An environment may later be reused for another invocation.

Code outside:

```python
lambda_handler()
```

can therefore be initialized outside the handler.

For example:

```python
s3 = boto3.client("s3")
```

is created once per execution environment rather than being explicitly created inside every handler call.

This is a common Lambda design technique.

# Part 59: Inspect Lambda Metrics with CLI

Get recent invocation metrics with CloudWatch.

For example:

```bash
END_TIME=$(date -u \
  +"%Y-%m-%dT%H:%M:%SZ")
```

On GNU/Linux:

```bash
START_TIME=$(date -u \
  -d '30 minutes ago' \
  +"%Y-%m-%dT%H:%M:%SZ")
```

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/Lambda \
  --metric-name Invocations \
  --dimensions \
    Name=FunctionName,Value="$FUNCTION_NAME" \
  --start-time "$START_TIME" \
  --end-time "$END_TIME" \
  --period 60 \
  --statistics Sum \
  --region "$REGION" \
  --output table
```

# What You Should Understand Before Moving On

Do not finish Project 12 thinking only:

```text
I wrote a Python function in Lambda.
```

You should understand the full event-driven architecture.

The Lambda function has:

```text
CODE
```

which defines what happens when the function executes.

The:

```text
HANDLER
```

defines where Lambda enters your Python program when an invocation begins.

The:

```text
EXECUTION ROLE
```

controls what the function can access.

In this project:

```text
Lambda
    |
    +----> CloudWatch Logs
    |
    +----> S3 GetObject
```

AWS defines the execution role as the IAM role Lambda assumes to access AWS services and resources.

The:

```text
RESOURCE-BASED POLICY
```

controls who can invoke the function.

For the S3 trigger:

```text
S3
 |
 | lambda:InvokeFunction
 v
Lambda
```

AWS requires S3 to have permission to invoke the function before an S3 Lambda destination can operate.

The:

```text
TRIGGER
```

connects an event source to Lambda.

In our architecture:

```text
S3 ObjectCreated
      |
      v
Lambda
```

Every uploaded object can create an event that automatically invokes the function.

The:

```text
CLOUDWATCH LOG GROUP
```

gives you the operational evidence required to understand what happened during execution.

Lambda automatically captures invocation logs and sends them to CloudWatch Logs when the execution role has the required permissions.

Most importantly, you deliberately broke the function and investigated the failure rather than simply replacing everything.

That gave you this troubleshooting model:

```text
EVENT GENERATED?
       |
       v
TRIGGER CONFIGURED?
       |
       v
INVOKE PERMISSION?
       |
       v
LAMBDA INVOKED?
       |
       v
HANDLER FOUND?
       |
       v
CODE EXECUTES?
       |
       v
EXECUTION ROLE AUTHORIZED?
       |
       v
EXTERNAL SERVICE CALL WORKS?
       |
       v
LOGS + METRICS
```

The complete Project 12 architecture is therefore:

```text
                     AMAZON S3
                         |
                         | ObjectCreated
                         v
                  LAMBDA RESOURCE
                      POLICY
                         |
                         v
                    AWS LAMBDA
                         |
                 Python 3.14 Handler
                         |
          +--------------+--------------+
          |                             |
          v                             v
   EXECUTION ROLE                CLOUDWATCH
          |                         LOGS
          |
          v
   s3:GetObject
          |
          v
     AMAZON S3
```

That is the real foundation of serverless engineering.

You are no longer thinking primarily about:

```text
Which server should I launch?
```

You are thinking about:

```text
What event occurred?

What function should react?

What permissions does it need?

What should invoke it?

What evidence will I use
when the execution fails?
```
