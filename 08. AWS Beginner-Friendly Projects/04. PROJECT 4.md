# Project 4: Build Your First Custom VPC

Most AWS projects eventually depend on networking.

An EC2 instance lives inside a VPC.

A load balancer uses subnets.

An RDS database is deployed into subnets.

Security groups control traffic to resources.

NAT gateways, Internet Gateways, VPN connections, VPC peering connections, Transit Gateways, and VPC endpoints all depend on understanding how traffic moves through a VPC.

So before building more complicated AWS architectures, you need to understand the network underneath them.

In this project, you will build that network manually.

You will create:

* One custom VPC
* One public subnet
* One private subnet
* One Internet Gateway
* One public route table
* One private route table
* Explicit subnet-to-route-table associations
* A default route from the public subnet to the Internet Gateway
* No internet route from the private subnet

AWS describes a VPC as a virtual network in AWS, with subnets providing ranges of IP addresses in which resources can be placed.

The finished architecture will look like this:

```text
                         INTERNET
                            |
                            |
                            v
                  +-------------------+
                  | Internet Gateway  |
                  |   project-04-igw  |
                  +---------+---------+
                            |
                            |
              0.0.0.0/0    |
                            |
+-------------------------------------------------------+
|                 VERIQTA PROJECT 4 VPC                 |
|                                                       |
|                     10.0.0.0/16                       |
|                                                       |
|   +-----------------------+  +----------------------+ |
|   | PUBLIC SUBNET         |  | PRIVATE SUBNET       | |
|   |                       |  |                      | |
|   | 10.0.1.0/24           |  | 10.0.2.0/24          | |
|   |                       |  |                      | |
|   +-----------+-----------+  +----------+-----------+ |
|               |                         |             |
|               v                         v             |
|   +-----------------------+  +----------------------+ |
|   | PUBLIC ROUTE TABLE    |  | PRIVATE ROUTE TABLE  | |
|   |                       |  |                      | |
|   | 10.0.0.0/16 -> local  |  | 10.0.0.0/16 ->local | |
|   | 0.0.0.0/0 -> IGW      |  |                      | |
|   +-----------------------+  +----------------------+ |
|                                                       |
+-------------------------------------------------------+
```

The most important difference is here:

```text
PUBLIC ROUTE TABLE

10.0.0.0/16 → local
0.0.0.0/0   → Internet Gateway
```

versus:

```text
PRIVATE ROUTE TABLE

10.0.0.0/16 → local
```

That single routing difference is what makes our first subnet public and the second subnet private.

---

# Part 2: CIDR Basics

CIDR stands for:

```text
Classless Inter-Domain Routing
```

You will often see addresses written like:

```text
10.0.0.0/16
```

The `/16` represents how many bits identify the network portion of the IPv4 address.

IPv4 addresses contain:

```text
32 bits
```

Therefore:

```text
/16
```

means:

```text
16 network bits
16 remaining address bits
```

The total theoretical address count is:

```text
2^(32 - 16)

2^16

65,536 addresses
```

So:

```text
10.0.0.0/16
```

covers a large range:

```text
10.0.0.0
through
10.0.255.255
```

That gives us plenty of room to divide the VPC into smaller subnets.

---

# Part 3: Understand /24 Subnets

Our public subnet will be:

```text
10.0.1.0/24
```

A `/24` has:

```text
32 - 24 = 8
```

host-address bits.

Therefore:

```text
2^8 = 256
```

total IPv4 addresses exist in the CIDR range.

Similarly:

```text
10.0.2.0/24
```

contains another 256 addresses.

However, AWS reserves the first four addresses and the last address of each normal IPv4 subnet. Therefore, a `/24` subnet does not provide all 256 addresses for ordinary resource assignment.

For:

```text
10.0.1.0/24
```

AWS reserves:

```text
10.0.1.0
Network address

10.0.1.1
VPC router

10.0.1.2
AWS DNS

10.0.1.3
Reserved by AWS

10.0.1.255
Reserved final address
```

The same pattern applies to:

```text
10.0.2.0/24
```

---

# Part 4: Why the Subnets Do Not Overlap

These are valid:

```text
10.0.1.0/24
10.0.2.0/24
```

because they represent separate ranges.

Conceptually:

```text
10.0.1.0 - 10.0.1.255

10.0.2.0 - 10.0.2.255
```

They do not overlap.

This would not be valid:

```text
10.0.1.0/24

10.0.1.128/25
```

inside the same VPC as independent overlapping subnets, because the second range sits inside the first.

AWS does not allow subnet CIDR ranges inside one VPC to overlap.

# Part 12: Understand the Local Route

This route:

```text
10.0.0.0/16 → local
```

means traffic destined for addresses inside the VPC CIDR can route within the VPC.

For example:

```text
Source:
10.0.1.20

Destination:
10.0.2.30
```

Both addresses belong to:

```text

```

Therefore the local route matches the destination.

This provides routing between VPC subnets.

Security groups and network ACLs can still restrict actual traffic, but the network has a routing path.

# Part 18: Understand the Internet Gateway

An Internet Gateway provides a route-table target for internet-routable traffic.

Creating it is only one step.

For it to be useful, you must:

```text
1. Create the Internet Gateway

2. Attach it to the VPC

3. Add a route pointing to it

4. Associate that route table with the intended subnet
```

AWS explicitly requires an Internet Gateway to be attached to a VPC and used in routing before it provides the intended internet path.

A very common beginner mistake is:

```text
I attached an Internet Gateway.

Why can't my server reach the internet?
```

Because attaching the gateway does not automatically create the subnet's route.

# Part 22: What Does 0.0.0.0/0 Mean?

This is one of the most important CIDR values you will encounter:

```text
0.0.0.0/0
```

It represents the entire IPv4 address space.

In routing terms, think:

```text
If no more specific route matches,
use this route.
```

Our public route table contains:

```text
10.0.0.0/16 → local

0.0.0.0/0 → Internet Gateway
```

Suppose the destination is:

```text
10.0.2.25
```

That matches:

```text
10.0.0.0/16
```

so the traffic stays local.

Suppose the destination is:

```text
8.8.8.8
```

It does not belong to:

```text
10.0.0.0/16
```

but it does match:

```text
0.0.0.0/0
```

so AWS sends it toward the Internet Gateway.

AWS route selection generally favors the most specific matching route, known as longest prefix match.

# Part 31: Understand Why the Private Subnet Can Still Reach the Public Subnet

Look again at both tables.

They both contain:

```text
10.0.0.0/16 → local
```

Both:

```text
10.0.1.0/24
```

and:

```text
10.0.2.0/24
```

sit inside:

```text
10.0.0.0/16
```

Therefore traffic between those subnet address ranges has a VPC-local routing path.

For example:

```text
10.0.1.10
        |
        | destination 10.0.2.20
        v
10.0.0.0/16 local
        |
        v
10.0.2.20
```

Actual application traffic can still be blocked by security groups or network ACLs, but the route itself exists.

# Part 32: Understand Route Priority

Suppose the public route table contains:

```text
10.0.0.0/16 → local

0.0.0.0/0 → IGW
```

A packet is going to:

```text
10.0.2.50
```

Both routes technically cover possible IPv4 destinations, because `/0` covers everything.

But:

```text
10.0.0.0/16
```

is more specific than:

```text
0.0.0.0/0
```

Therefore AWS uses the local route.

AWS generally routes using the longest, most specific prefix match.

Think:

```text
/32
more specific

/24
less specific

/16
less specific

/0
least specific
```

This is why:

```text
0.0.0.0/0
```

works well as a default route.

It catches traffic that does not match a more specific route.

because the private subnet is inside the same VPC CIDR.

match?

No.

No.

# Part 60: Why We Did Not Add a NAT Gateway

A common architecture gives private resources outbound internet connectivity using a NAT Gateway in a public subnet.

That architecture might look like:

```text
PRIVATE SUBNET
      |
      | 0.0.0.0/0
      v
NAT GATEWAY
      |
      v
PUBLIC SUBNET
      |
      v
INTERNET GATEWAY
      |
      v
INTERNET
```

AWS documents NAT Gateways as a way for private-subnet resources to initiate outbound internet connections without making those resources directly public.

We are deliberately not creating one yet.

Why?

Because this project is about understanding:

```text
VPC
Subnets
Route tables
Internet Gateway
CIDR
```

Adding NAT now would make the first routing exercise unnecessarily complicated and could introduce additional cost.

For this lab:

```text
Public subnet:
internet route

Private subnet:
no internet route
```

That makes the architecture easy to inspect.

# Part 61: Common Mistake, Calling a Subnet Public Because of Its Name

This:

```text
Name:
public-subnet
```

does not make it public.

This:

```text
0.0.0.0/0 → Internet Gateway
```

in its associated route table is what creates the internet routing characteristic.

AWS defines public and private subnets based on their Internet Gateway routing.

---

# Part 62: Common Mistake, Attaching the IGW Without Adding a Route

Architecture:

```text
VPC
|
+-- Internet Gateway attached

Public route table:
10.0.0.0/16 → local
```

Will internet traffic automatically leave?

No.

There is no route telling the subnet to use the Internet Gateway.

You need:

```text
0.0.0.0/0 → IGW
```

---

# Part 63: Common Mistake, Adding the Route to the Wrong Table

Suppose you accidentally add:

```text
0.0.0.0/0 → IGW
```

to:

```text
veriqta-project-04-private-rt
```

You have changed the intended architecture.

The subnet associated with that table now has an Internet Gateway route.

Always inspect:

```text
Subnet
→ Route table association
→ Routes
```

Do not judge routing by route-table names alone.

---

# Part 64: Common Mistake, Forgetting Route Table Associations

You can create the perfect route table:

```text
10.0.0.0/16 → local
0.0.0.0/0 → IGW
```

but if no public subnet is associated with it, the subnet does not use those routes.

Every subnet uses a route table, either through an explicit association or through the VPC's main route table.

Verify associations.

---

# Part 65: Common Mistake, Overlapping CIDRs

This will fail conceptually:

```text
VPC:
10.0.0.0/16

Subnet A:
10.0.1.0/24

Subnet B:
10.0.1.128/25
```

because Subnet B overlaps Subnet A.

Choose separate ranges.

For example:

```text
10.0.1.0/24

10.0.2.0/24
```

AWS requires multiple subnet CIDRs inside a VPC not to overlap.

---

# Part 66: Common Mistake, Choosing a Subnet Outside the VPC

If the VPC is:

```text
10.0.0.0/16
```

this is not part of that address range:

```text
192.168.1.0/24
```

Your subnet CIDR must come from the VPC's address space.

---

# Part 67: Common Mistake, Public Route but No Public IP

Imagine an EC2 instance in the public subnet.

The subnet has:

```text
0.0.0.0/0 → IGW
```

but the instance has only:

```text
10.0.1.20
```

with no public IPv4 address.

For normal IPv4 internet communication through the Internet Gateway, the instance also needs a public IPv4 address or Elastic IP.

That is why we enabled:

```text
Auto-assign public IPv4
```

for the public subnet.

```bash
aws ec2 delete-vpc \
    --vpc-id "$VPC_ID"
```

and receive a dependency-related error.

That means AWS believes a dependent resource remains.

Investigate:

```bash
aws ec2 describe-subnets \
    --filters "Name=vpc-id,Values=$VPC_ID"
```

Then:

```bash
aws ec2 describe-route-tables \
    --filters "Name=vpc-id,Values=$VPC_ID"
```

Then:

```bash
aws ec2 describe-internet-gateways \
    --filters "Name=attachment.vpc-id,Values=$VPC_ID"
```

Then:

```bash
aws ec2 describe-network-interfaces \
    --filters "Name=vpc-id,Values=$VPC_ID"
```

Then:

```bash
aws ec2 describe-security-groups \
    --filters "Name=vpc-id,Values=$VPC_ID"
```

Do not respond to a dependency error by deleting resources from unrelated VPCs.

Always filter by your project VPC ID.

# What You Should Understand Before Moving On

Do not finish this project thinking:

```text
I know how to click Create VPC.
```

You should now be able to explain the architecture.

The VPC provides the network boundary:

```text
10.0.0.0/16
```

The public subnet uses part of that address space:

```text
10.0.1.0/24
```

The private subnet uses another non-overlapping part:

```text
10.0.2.0/24
```

Both subnets receive the VPC local route:

```text
10.0.0.0/16 → local
```

which provides the routing path between addresses inside the VPC.

The public route table adds:

```text
0.0.0.0/0 → Internet Gateway
```

which provides a route for internet-bound IPv4 traffic that does not match a more specific route.

The private route table does not contain that Internet Gateway route.

Therefore:

```text
PUBLIC

10.0.1.0/24
     |
     v
0.0.0.0/0
     |
     v
Internet Gateway
     |
     v
Internet
```

while:

```text
PRIVATE

10.0.2.0/24
     |
     v
10.0.0.0/16 local

No direct Internet Gateway route
```

Route-table names do not make a subnet public or private.

The routing configuration does.

An Internet Gateway attached to a VPC does not automatically make every subnet public.

A route table must direct appropriate traffic toward it.

And a future EC2 instance using IPv4 also needs an appropriate public IPv4 address if it is expected to communicate directly over that Internet Gateway.

Most importantly, you now understand that AWS networking is not magic.

Traffic follows routes.

Once you learn to inspect the source subnet, destination address, associated route table, matching CIDR, and route target, VPC troubleshooting becomes much more logical.
