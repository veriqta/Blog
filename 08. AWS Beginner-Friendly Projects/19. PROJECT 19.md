# Project 19: Troubleshoot a Broken AWS Application

A user reports:

```text
"The website is down."
```

That sentence tells you almost nothing about the actual failure.

The problem could be:

```text
DNS

Load balancer

Listener rule

Security group

Target group

Health check

EC2 networking

Application process

Application route

Application code
```

Project 19 is about learning how to separate those layers.

You will deliberately build a working application architecture and then introduce several failures:

```text
FAILURE 1
Incorrect EC2 security-group rule

FAILURE 2
Incorrect ALB health-check path

FAILURE 3
Broken ALB listener route

FAILURE 4
Application endpoint failure
```

Then you will troubleshoot each problem using evidence.

The architecture is:

```text
                     INTERNET
                         |
                         |
                         v
                +----------------+
                | APPLICATION    |
                | LOAD BALANCER  |
                |                |
                | Port 80        |
                +-------+--------+
                        |
                        |
                  Target Group
                    Port 8080
                        |
                        v
                +----------------+
                | EC2 INSTANCE   |
                |                |
                | Python App     |
                | Port 8080      |
                +-------+--------+
                        |
                        v
                 APPLICATION LOGS
```

The application exposes:

```text
GET /

GET /health

GET /app

GET /fail
```

You will use:

```text
curl

AWS CLI

describe-target-health

describe-security-groups

describe-listeners

describe-rules

journalctl

ss

systemctl

application logs
```

to determine where each failure occurs.

AWS security groups act as stateful virtual firewalls and control inbound and outbound traffic for resources such as EC2 instances. Application Load Balancer target groups independently perform health checks against their registered targets.

# Part 1: The Troubleshooting Mindset

Do not troubleshoot this way:

```text
Website broken
     |
     v
Change security group
     |
     v
Restart application
     |
     v
Change ALB
     |
     v
Reboot EC2
     |
     v
Hope
```

Instead:

```text
SYMPTOM
   |
   v
COLLECT EVIDENCE
   |
   v
IDENTIFY FAILED LAYER
   |
   v
TEST ONE HYPOTHESIS
   |
   v
MAKE ONE CHANGE
   |
   v
VERIFY
```

The question is not simply:

```text
"How do I make it work?"
```

The better question is:

```text
"Where does the request stop?"
```

# Part 3: Understand ALB Health Checks

An Application Load Balancer does not simply assume an EC2 instance is usable because:

```text
Instance state = running
```

The target group performs health checks.

For this project:

```text
Protocol:
HTTP

Port:
8080

Correct path:
/health

Expected code:
200
```

A target can therefore be:

```text
EC2 running

BUT

ALB target unhealthy
```

AWS documents target health states and reason codes for identifying health-check failures.

---

# Part 4: Understand Security-Group References

We will use two security groups.

```text
ALB SECURITY GROUP
        |
        | HTTP 8080
        v
EC2 SECURITY GROUP
```

The ALB security group allows:

```text
TCP 80
Source 0.0.0.0/0
```

The EC2 security group should eventually allow:

```text
TCP 8080
Source = ALB security group
```

This is preferable to exposing the application port directly to the internet.

AWS specifically documents architectures where the load balancer accepts internet traffic and the web-server security group accepts application traffic from the load balancer security group.

# Part 21: Create the Application User Data

Create:

```text
project19-user-data.sh
```

Run:

```bash
cat > project19-user-data.sh <<'EOF'
#!/bin/bash

set -euxo pipefail

mkdir -p /opt/veriqta

cat > /opt/veriqta/app.py <<'PYEOF'
#!/usr/bin/env python3

from datetime import datetime, timezone
from http.server import BaseHTTPRequestHandler, HTTPServer
import json
import logging


logging.basicConfig(
    level=logging.INFO,
    format=(
        "%(asctime)s "
        "%(levelname)s "
        "%(message)s"
    )
)

logger = logging.getLogger(
    "veriqta-project-19"
)


class ApplicationHandler(
    BaseHTTPRequestHandler
):

    def send_json(
        self,
        status_code,
        body
    ):
        payload = json.dumps(
            body
        ).encode(
            "utf-8"
        )

        self.send_response(
            status_code
        )

        self.send_header(
            "Content-Type",
            "application/json"
        )

        self.send_header(
            "Content-Length",
            str(len(payload))
        )

        self.end_headers()

        self.wfile.write(
            payload
        )

    def do_GET(self):

        logger.info(
            "request method=GET "
            "path=%s client=%s",
            self.path,
            self.client_address[0]
        )

        if self.path == "/":

            self.send_json(
                200,
                {
                    "project": 19,
                    "brand": "VERIQTA",
                    "status": "running",
                    "message": (
                        "Project 19 application "
                        "is reachable."
                    )
                }
            )

            return

        if self.path == "/health":

            self.send_json(
                200,
                {
                    "status": "healthy",
                    "timestamp": (
                        datetime.now(
                            timezone.utc
                        ).isoformat()
                    )
                }
            )

            return

        if self.path == "/app":

            self.send_json(
                200,
                {
                    "application": (
                        "VERIQTA Troubleshooting Lab"
                    ),
                    "route": "/app",
                    "status": "working"
                }
            )

            return

        if self.path == "/fail":

            logger.error(
                "intentional application "
                "failure triggered"
            )

            self.send_json(
                500,
                {
                    "error": (
                        "Intentional Project 19 "
                        "application failure."
                    )
                }
            )

            return

        logger.warning(
            "route not found path=%s",
            self.path
        )

        self.send_json(
            404,
            {
                "error": "Route not found.",
                "path": self.path
            }
        )

    def log_message(
        self,
        format,
        *args
    ):
        return


server = HTTPServer(
    (
        "0.0.0.0",
        8080
    ),
    ApplicationHandler
)

logger.info(
    "VERIQTA Project 19 "
    "application starting on port 8080"
)

server.serve_forever()
PYEOF


chmod +x \
  /opt/veriqta/app.py


cat > \
/etc/systemd/system/veriqta-project19.service \
<<'SERVICEEOF'

[Unit]
Description=VERIQTA Project 19 Application
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/veriqta/app.py
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target

SERVICEEOF


systemctl daemon-reload

systemctl enable \
  veriqta-project19.service

systemctl start \
  veriqta-project19.service
EOF
```

# Part 72: Why a Healthy ALB Target Is Not Enough

Likewise:

```text
TargetHealth = healthy
```

means the configured health check succeeds.

It does not guarantee every application route works.

For example:

```text

/app
200

/fail

```

can coexist while the target remains healthy.

Health checks answer a narrow question:

```text

the configured health check?"
```

not:

```text
"Does every feature in the application work?"
```

# What You Should Understand Before Moving On

Do not finish Project 19 thinking:

```text
I learned how to fix
an ALB.
```

The real lesson is:

```text
I learned how to locate
a failure.
```

The first incident looked like:

```text
WEBSITE DOWN
```

but the application itself was healthy.

You proved that with:

```bash
curl \
  http://localhost:8080/
```

and:

```bash
sudo ss \
  -lntp
```

The actual failure was:

```text
SECURITY GROUP

ALB sends:
8080

EC2 allows:
8081
```

The repair was:

```text
ALB SG
   |
   | TCP 8080
   v
EC2 SG
```

Security groups control which inbound protocol, port, and source can reach an EC2 resource.

Then the target remained unhealthy.

Instead of assuming:

```text
"The security-group fix didn't work."
```

you collected new evidence.

You discovered:

```text
ALB health path:
/broken-health

Application response:
404

Correct application path:
/health

Response:
200
```

The second root cause was therefore:

```text
HEALTH-CHECK CONFIGURATION
```

not networking.

ALB health-check settings belong to the target group, and target-health inspection provides state and reason information when those checks fail.

Then:

```text
/
WORKED

/app
FAILED
```

But:

```text
localhost:8080/app
```

worked.

That isolated the failure to:

```text
ALB ROUTING
```

Inspection showed:

```text
Priority 10
Path /app
Fixed response 404
```

The application never received those requests.

Finally:

```text
/fail
```

returned:

```text
500
```

while:

```text
TargetHealth:
healthy
```

This proved another important distinction:

```text
HEALTHY INFRASTRUCTURE
does not guarantee
EVERY APPLICATION FUNCTION
is healthy.
```

Application logs then supplied the evidence:

```text
request method=GET path=/fail

intentional application failure triggered
```

Your complete troubleshooting model is therefore:

```text
                 USER SYMPTOM
                      |
                      v
                 DNS / CLIENT
                      |
                      v
               LOAD BALANCER
                      |
                      v
                 LISTENER
                      |
                      v
              LISTENER RULES
                      |
                      v
               TARGET GROUP
                      |
                      v
               TARGET HEALTH
                      |
                      v
              SECURITY GROUP
                      |
                      v
                  EC2 OS
                      |
                      v
              LISTENING PORT
                      |
                      v
             APPLICATION PROCESS
                      |
                      v
             APPLICATION ROUTE
                      |
                      v
             APPLICATION LOGS
```

The commands map directly to those layers:

```text
ALB
aws elbv2 describe-load-balancers

LISTENER
aws elbv2 describe-listeners

ROUTES
aws elbv2 describe-rules

TARGET GROUP
aws elbv2 describe-target-groups

HEALTH
aws elbv2 describe-target-health

SECURITY
aws ec2 describe-security-groups

INSTANCE
aws ec2 describe-instances

SOCKET
ss -lntp

PROCESS
systemctl

APPLICATION
curl

LOGS
journalctl
```

That is what a production troubleshooting workflow should give you:

```text
SYMPTOM

→ EVIDENCE

→ FAILED LAYER

→ ROOT CAUSE

→ MINIMUM REPAIR

→ VERIFICATION
```

Not:

```text
SYMPTOM

→ RANDOM CHANGES

→ HOPE
```

That distinction is the core of Project 19.
