# Project 16: Create a Private S3 Website with CloudFront

A static website stored in Amazon S3 does not have to be publicly readable.

In fact, a stronger architecture is:

```text
Internet users
      |
      | HTTPS
      v
+-------------------------+
| AMAZON CLOUDFRONT       |
|                         |
| CDN                     |
| HTTPS                   |
| Edge caching            |
| Origin Access Control   |
+------------+------------+
             |
             | Signed request
             | AWS SigV4
             v
+-------------------------+
| PRIVATE AMAZON S3       |
|                         |
| Public access blocked   |
| No website endpoint     |
| index.html              |
| styles.css              |
| app.js                  |
+-------------------------+
```

The browser accesses:

```text
https://dxxxxxxxx.cloudfront.net
```

The browser does not need direct access to:

```text
https://bucket-name.s3.amazonaws.com
```

CloudFront Origin Access Control lets CloudFront send authenticated requests to a private S3 origin, which allows the bucket to remain inaccessible directly to normal public viewers.

# Part 1: Understand Why the S3 Bucket Stays Private

A common beginner architecture is:

```text
Internet
   |
   v
Public S3 bucket
```

That works for some basic demonstrations, but it exposes the S3 origin directly.

Our architecture is:

```text
Internet
   |
   v
CloudFront
   |
   v
Private S3
```

The S3 bucket remains protected with:

```text
Block Public Access
```

and the bucket policy grants CloudFront permission to retrieve objects.

AWS recommends Origin Access Control for restricting access to S3 origins used by CloudFront.

---

# Part 2: Do Not Enable S3 Static Website Hosting

This distinction is important.

We are storing website files in S3.

But we are not using:

```text
S3 Static Website Hosting
```

The origin will be the normal S3 bucket endpoint.

CloudFront OAC cannot be used with an S3 bucket configured as an S3 website origin.

So our architecture is:

```text
CORRECT

CloudFront
   |
   v
S3 REST origin
   |
   v
OAC
```

Not:

```text
NOT THIS PROJECT

CloudFront
   |
   v
S3 website endpoint
```

# Part 3: Understand Origin Access Control

Origin Access Control is commonly shortened to:

```text
OAC
```

CloudFront uses OAC to authenticate requests sent to the S3 origin.

Our OAC configuration will use:

```text
Origin type:
S3

Signing behavior:
always

Signing protocol:
sigv4
```

AWS documents `sigv4` as the supported signing protocol for OAC, and `always` as the normal configuration when CloudFront should sign origin requests.

Architecture:

```text
VIEWER
   |
   v
CLOUDFRONT
   |
   | Signed origin request
   | AWS Signature Version 4
   v
S3
```

# Part 4: Understand the S3 Bucket Policy

OAC alone is not sufficient.

S3 must also trust the CloudFront distribution.

The bucket policy will conceptually say:

```text
Allow:
cloudfront.amazonaws.com

Action:
s3:GetObject

Resource:
Project 16 bucket objects

Condition:
Only this CloudFront distribution
```

AWS's OAC bucket-policy example uses the CloudFront service principal together with the distribution ARN to restrict S3 access to the intended distribution.

The relationship is:

```text
CloudFront distribution
       |
       | s3:GetObject allowed
       v
Private S3 bucket
```

# Part 5: Understand CloudFront Caching

CloudFront maintains copies of cacheable objects at edge locations.

Conceptually:

```text
FIRST REQUEST

Viewer
  |
  v
Edge Location
  |
  | MISS
  v
S3 Origin
  |
  v
CloudFront Cache
  |
  v
Viewer
```

Later:

```text
SECOND REQUEST

Viewer
  |
  v
Edge Location
  |
  | HIT
  v
Cached Object
  |
  v
Viewer
```

A cache hit occurs when the request generates the same cache key as a previous request and a valid cached object is available.

# Part 24: Why redirect-to-https?

Our distribution uses:

```text
ViewerProtocolPolicy:
redirect-to-https
```

That means:

```text
HTTP viewer request
        |
        v
CloudFront
        |
        v
Redirect
        |
        v
HTTPS request
```

CloudFront supports both `redirect-to-https` and `https-only` behavior for enforcing encrypted viewer connections.

# Part 25: Why Only GET and HEAD?

This is a static website.

Viewers need to retrieve objects.

They do not need:

```text
PUT

DELETE

PATCH

POST
```

through this CloudFront behavior.

We therefore use:

```text
GET

HEAD
```

only.

This reduces the methods available through the public distribution.

# Part 39: Understand Why a Hit Might Not Appear Immediately

CloudFront has many edge locations.

Requests may not always behave identically when:

```text
Different locations are involved

Cache entries expire

The cache key changes

The object was invalidated

The request reaches an edge
without the object cached
```

Caching should be tested by understanding the cache key and TTL, not by assuming every second request globally must produce the same cache state.

# Part 47: Why Forwarding Unnecessary Headers Hurts Caching

Imagine the cache varies by:

```text

Random custom headers

Other unnecessary request values
```

CloudFront can end up maintaining more cache variations.

AWS recommends avoiding forwarding headers that are not needed because unnecessary variation can reduce cache hit ratio.

For a simple static site:


# What You Should Understand Before Moving On

Do not finish Project 16 thinking:

```text
I put a website behind CloudFront.
```

The important architecture is:

```text
PUBLIC EDGE
+
PRIVATE ORIGIN
```

Your S3 bucket remains:

```text
PRIVATE
```

The browser cannot simply retrieve the files anonymously from S3.

Instead:

```text
VIEWER
   |
   | HTTPS
   v
CLOUDFRONT
```

CloudFront determines whether the object is already available in its edge cache.

If it is:

```text
CACHE HIT
     |
     v
Return object
```

A cache hit allows CloudFront to serve the object from an edge cache rather than retrieving it from the origin for that request.

If it is not:

```text
CACHE MISS
     |
     v
OAC
     |
     v
SIGNED ORIGIN REQUEST
     |
     v
PRIVATE S3
```

Origin Access Control makes authenticated CloudFront-to-origin requests possible while the S3 origin remains private.

Then the S3 bucket policy checks:

```text
Who is requesting the object?

Is it CloudFront?

Is it the correct distribution?
```

The critical policy relationship is:

```text
Principal:
cloudfront.amazonaws.com

Action:
s3:GetObject

Condition:
AWS:SourceArn =
Project 16 distribution
```

AWS documents this as the bucket-policy pattern for allowing an OAC-enabled CloudFront distribution to read a private S3 origin.

The viewer side is protected separately:

```text
HTTP
 |
 v
CloudFront
 |
 v
HTTPS REDIRECT
```

CloudFront's `redirect-to-https` policy ensures HTTP viewer requests are redirected to HTTPS.

Caching introduces another operational idea.

Updating:

```text
S3/index.html
```

does not necessarily mean every viewer immediately receives the new version.

CloudFront might still have:

```text
OLD index.html
```

in an edge cache.

You therefore learned to distinguish:

```text
ORIGIN CONTENT
```

from:

```text
CACHED CONTENT
```

and use:

```text
Cache-Control
```

plus:

```text
CloudFront invalidation
```

when appropriate. CloudFront supports cache expiration controls and explicit invalidations for managing cached content.

Your troubleshooting model should now be:

```text
OBJECT EXISTS?
      |
      v
DIRECT S3 PRIVATE?
      |
      v
DISTRIBUTION DEPLOYED?
      |
      v
CORRECT S3 ORIGIN?
      |
      v
OAC ATTACHED?
      |
      v
SIGV4 SIGNING?
      |
      v
BUCKET POLICY CORRECT?
      |
      v
SOURCE ARN CORRECT?
      |
      v
DEFAULT ROOT OBJECT?
      |
      v
HTTPS POLICY?
      |
      v
CACHE HIT OR MISS?
      |
      v
STALE CACHE?
      |
      v
INVALIDATION?
```

The complete Project 16 architecture is:

```text
                     INTERNET
                         |
                         |
                    HTTP / HTTPS
                         |
                         v
                +----------------+
                |   CLOUDFRONT   |
                |                |
                | HTTPS          |
                | CDN            |
                | Edge Cache     |
                +-------+--------+
                        |
                  Cache lookup
                   /        \
                  /          \
               HIT            MISS
                |              |
                |              v
                |       +-------------+
                |       |     OAC     |
                |       |             |
                |       | SigV4       |
                |       +------+------+ 
                |              |
                |              v
                |      +---------------+
                |      |  PRIVATE S3   |
                |      |               |
                |      | index.html    |
                |      | styles.css    |
                |      | app.js        |
                |      +-------+-------+
                |              |
                +--------------+
                        |
                        v
                     VIEWER
```

That is the architecture you should remember:

```text
PRIVATE S3 ORIGIN
+
CLOUDFRONT OAC
+
HTTPS
+
EDGE CACHING
+
DISTRIBUTION-SCOPED S3 POLICY
```

The website is publicly deliverable without making the S3 origin itself publicly readable.
