# Project 9: Build an Auto Scaling Web Application

Project 8 gave you two EC2 servers behind an Application Load Balancer.

That architecture could survive the failure of one instance, but you still created and managed the instances manually.

Project 9 changes that.

Instead of manually launching each EC2 server, you will define what a web server should look like once, using an EC2 Launch Template.

Then you will create an Auto Scaling group that launches, replaces, adds, and removes instances according to the capacity settings and scaling policies you define.

Amazon EC2 Auto Scaling is designed to maintain the number of EC2 instances required by your application. You specify minimum, desired, and maximum capacity, and the Auto Scaling group adjusts its desired capacity within those limits as demand changes.

The finished architecture will look like this:

```text
                              INTERNET
                                  |
                                  |
                                  v
                     APPLICATION LOAD BALANCER
                                  |
                                  |
                         HTTP TCP/80
                                  |
                                  v
                           TARGET GROUP
                                  |
                    +-------------+-------------+
                    |                           |
                    v                           v

             AVAILABILITY ZONE A        AVAILABILITY ZONE B

              PUBLIC SUBNET A            PUBLIC SUBNET B
               10.0.1.0/24               10.0.4.0/24

                    \                          /
                     \                        /
                      \                      /
                       AUTO SCALING GROUP

                      Minimum: 2
                      Desired: 2
                      Maximum: 4

                            |
                            |
                     LAUNCH TEMPLATE
                            |
                   +--------+---------+
                   | Amazon Linux     |
                   | Apache           |
                   | User data        |
                   | Security group   |
                   | Instance type    |
                   +------------------+
```

The difference from Project 8 is important.

In Project 8:

```text
You
 |
 +--> manually launch EC2-1
 |
 +--> manually launch EC2-2
```

In Project 9:

```text
You
 |
 v
Launch Template
 |
 v
Auto Scaling Group
 |
 +--> launches EC2
 +--> replaces EC2
 +--> adds EC2
 +--> removes EC2
```

An Auto Scaling group uses its associated launch template to determine how new instances should be configured.

# Part 1: Understand Minimum, Desired, and Maximum Capacity

These three values control the size of your Auto Scaling group.

We will use:

```text
Minimum:
2

Desired:
2

Maximum:
4
```

## Minimum Capacity

Minimum capacity means:

```text
Do not normally let this group contain
fewer than 2 instances.
```

AWS Auto Scaling ensures that the group does not fall below the configured minimum size.

---

## Desired Capacity

Desired capacity means:

```text
This is the number of instances
the Auto Scaling group currently
tries to maintain.
```

Initially:

```text
Desired = 2
```

so Auto Scaling launches two instances.

If a scaling policy later determines that more capacity is required:

```text
Desired = 3
```

and the ASG launches another instance.

If even more capacity is required:

```text
Desired = 4
```

the ASG can launch another.

---

## Maximum Capacity

Maximum capacity means:

```text
The Auto Scaling group
cannot scale beyond 4 instances.
```

Even if the scaling metric remains high, the desired capacity is constrained by the maximum value. AWS scaling policies change desired capacity only within the minimum and maximum capacity boundaries configured for the group.

```text
CPU falls

4
↓
3
↓
2 instances
```

The ASG does not scale below:

```text
2
```

and does not scale above:

```text
4
```

# Part 3: Auto Scaling Is More Than Scaling Out

Auto Scaling has another extremely important job.

Suppose:

```text
Desired capacity = 2
```

and you currently have:

```text
Instance A
Instance B
```

If Instance A is terminated or determined to be unhealthy, Auto Scaling can launch a replacement so the group returns to its desired capacity. AWS continuously evaluates instance health, and an unhealthy `InService` instance can be replaced using the ASG's current launch template settings.

Conceptually:

```text
BEFORE

Instance A    Instance B
 Healthy       Healthy

       ↓

Instance A fails

       ↓

Instance A    Instance B
 Failed        Healthy

       ↓

ASG launches replacement

       ↓

Instance C    Instance B
 Healthy       Healthy
```

# Part 12: Why User Data Matters

Without user data, the Auto Scaling group could launch a fresh EC2 instance that contains only the base operating system.

That replacement would not automatically know that it should:

```text
Install Apache

Start Apache

Create the website

Create health.html
```

The Launch Template plus user data makes every new instance reproducible.

This becomes especially important during automatic replacement.

When one instance disappears:

```text
ASG
 |
 v
Launch Template
 |
 v
New instance
 |
 v
User data runs
 |
 v
Apache installed
 |
 v
Website ready
```

# Part 38: Understand the Scaling Policy

Our policy says conceptually:

```text
Keep average CPU near 50%
```

If:

```text
Average CPU > target
```

Auto Scaling can increase desired capacity.

For example:

```text
Desired 2
    |
    v
Desired 3
```

Then the ASG launches another instance.

If the metric remains high:

```text
Desired 3
    |
    v
Desired 4
```

But because:

```text
Max = 4
```

the group stops there.

When load decreases, the group can scale back toward:

```text
2
```

because:

```text
Min = 2
```

AWS describes this target-tracking behavior as scaling out when utilization is above the target and scaling in as utilization falls below it, while respecting configured capacity boundaries.

# Part 56: Why the ASG Can Replace It

This works only because we enabled:

```text

```

for the Auto Scaling group.

By default, Auto Scaling does not automatically act on ELB health results. When ELB health checks are enabled for the ASG, an instance reported unhealthy by the load balancer can be marked unhealthy by Auto Scaling and replaced.

The sequence becomes:

```text
Apache stops
   |
   v
/health.html fails
   |
   v
ALB marks target unhealthy
   |
   v
Auto Scaling receives health result
   |
   v
Instance marked unhealthy
   |
   v
Replacement process
   |
   v
New instance launches
```

# Part 60: Understand the Difference Between Scaling and Healing

These are related but different.

## Scaling

```text
Demand rises
   |
   v
Need more capacity
   |
   v
2 → 3 → 4
```

## Healing

```text
Instance fails
   |
   v
Desired capacity unchanged
   |
   v
Replace failed instance
```

Example:

```text
Desired = 2

Before:
A + B

A fails

After:
C + B
```

You still have:

```text
2 instances
```

but one has been replaced.

# Part 61: Troubleshooting Framework

If the Auto Scaling application does not work, use this order:

```text
1. Does the launch template exist?

2. Is the correct AMI configured?

3. Is the instance security group correct?

4. Does user data install Apache?

5. Is the ASG using the correct launch template?

6. Are the correct subnets selected?

7. Is desired capacity greater than zero?

8. Are instances launching?

9. Are instances reaching InService?

10. Is the target group attached?

11. Are instances appearing in the target group?

12. Does /health.html return 200?

13. Does the instance SG allow HTTP from ALB-SG?

14. Does the ALB listener forward to the correct target group?

15. Is the scaling policy attached?

16. Is the metric increasing?

17. Is maximum capacity blocking scale-out?

18. Is minimum capacity blocking additional scale-in?

19. Are scaling processes suspended?

20. What does ASG Activity say?
```

# What You Should Understand Before Moving On

Do not finish Project 9 thinking only:

```text
I created an Auto Scaling group.
```

You should understand the complete control loop.

The Launch Template answers:

```text
What should every new EC2 instance look like?
```

It defines things such as:

```text
AMI
Instance type
Security group
User data
```

The Auto Scaling group answers:

```text
How many instances should exist,
and where should they run?
```

Its capacity limits are:

```text
Minimum = 2
Desired = 2
Maximum = 4
```

AWS keeps the group within those capacity limits and uses desired capacity as the number of instances the group currently attempts to maintain.

The target group connects those changing EC2 instances to the Application Load Balancer.

As the ASG launches instances, they can be registered with the load balancer automatically.

The target-tracking policy watches:

```text
Average CPU utilization
```

with a target near:

```text
50%
```

When demand rises, desired capacity can increase.

When demand falls, desired capacity can decrease.

AWS recommends target tracking for common metrics such as average CPU utilization because it adjusts capacity automatically around a specified target.

The health-check system adds another control loop:

```text
EC2 becomes unhealthy
        |
        v
Auto Scaling detects failure
        |
        v
Replacement instance launched
        |
        v
Launch Template applied
        |
        v
User data runs
        |
        v
Apache becomes healthy
        |
        v
Target joins ALB
```

When Elastic Load Balancing health checks are enabled for the Auto Scaling group, ALB health information can also trigger replacement of unhealthy targets.

That gives you two separate but complementary behaviors:

```text
SCALING

Traffic increases
→ Add capacity

Traffic decreases
→ Remove excess capacity
```

and:

```text
SELF-HEALING

Instance fails
→ Replace capacity
```

The complete architecture is now:

```text
                         USERS
                           |
                           v
                         ALB
                           |
                           v
                     TARGET GROUP
                           |
                           v
                  AUTO SCALING GROUP
                    /             \
                   /               \
                  v                 v
              EC2 INSTANCE      EC2 INSTANCE
                   \               /
                    \             /
                     LAUNCH TEMPLATE

                 MIN 2
                 DESIRED 2
                 MAX 4

                       +
              TARGET TRACKING
                 CPU ≈ 50%

                       +
                HEALTH CHECKS

                       =
             ELASTIC WEB CAPACITY
             + INSTANCE REPLACEMENT
```

This is the point where your web tier stops behaving like a fixed collection of servers and starts behaving like a managed pool of capacity.
