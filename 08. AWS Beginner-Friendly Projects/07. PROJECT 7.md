# Project 7: Build a Two-Tier Web Application

Until now, most of the projects have tested one AWS service at a time.

This project connects the pieces.

You will build a small web application with two separate tiers:

```text
Tier 1:
EC2 application server

Tier 2:
Amazon RDS MySQL database
```

The browser never talks directly to MySQL.

The request path is:

```text
Browser
   |
   | HTTP TCP/80
   v
EC2 Application Server
   |
   | PHP
   |
   | MySQL TCP/3306
   v
Amazon RDS MySQL
```

The EC2 application server will be placed in the public subnet of your custom VPC.

The RDS database will use private subnets.

Internet users will be able to reach the application.

Internet users will not be able to connect directly to the database.

AWS uses essentially this architecture in its EC2-to-RDS connectivity guidance: EC2 is placed in a public subnet, RDS in private networking, and separate security groups control the connection between the two tiers.

# Part 1: Understand the Two Tiers

The application tier handles HTTP requests.

It contains:

```text
Apache
PHP
Application code
```

The database tier stores application data.

It contains:

```text
Amazon RDS
MySQL
Database tables
Application records
```

The browser does not need database credentials.

The browser should not know the database endpoint.

It simply requests:

```text
http://EC2_PUBLIC_IP/
```

Apache receives that request.

PHP executes.

PHP connects privately to RDS.

PHP queries or inserts information.

The resulting HTML is returned to the browser.

This is the key architectural idea:

```text
USER
 |
 v
APPLICATION
 |
 v
DATABASE
```

not:

```text
USER
 |
 +-------> APPLICATION
 |
 +-------> DATABASE
```

# Part 13: What the Security Group Reference Does

The RDS rule does not say:

```text
Allow EC2 private IP 10.0.1.47
```

Instead it says:

```text
Allow eligible TCP/3306 traffic
from resources associated with app-sg
```

AWS evaluates the private addresses of network interfaces associated with the referenced security group when processing such inbound traffic.

This is useful because application-server IP addresses can change.

You are securing the relationship between application roles rather than hardcoding one temporary host address.

    $db = new mysqli(
        DB_HOST,
        DB_USER,
        DB_PASSWORD,
        DB_NAME,
        DB_PORT

    $db->set_charset('utf8mb4');

    if ($_SERVER['REQUEST_METHOD'] === 'POST') {
        $name = trim($_POST['name'] ?? '');
        $message = trim($_POST['message'] ?? '');

        if ($name === '' || $message === '') {
            $error = 'Please enter your name and a message.';

            $error = 'Name is too long.';

            $error = 'Message is too long.';

# Part 45: Understand What Just Happened

Your browser performed:

```text
POST /
```

to EC2.

Apache passed the PHP file to PHP.

PHP opened a MySQL connection to:

```text
RDS_ENDPOINT:3306
```

The RDS security group evaluated the source.

Because the EC2 instance is associated with:

```text
veriqta-project-07-app-sg
```

and the database allows:

```text
3306 from veriqta-project-07-app-sg
```

the database connection was allowed. AWS documents this exact type of application-SG-to-database-SG relationship.

PHP executed:

```sql
INSERT INTO messages ...
```

MySQL stored the row.

PHP then ran:

```sql
SELECT ...
```

The database returned the rows.

PHP generated HTML.

Apache returned the page to your browser.

That is an actual two-tier application request.

# Part 53: Browser-to-Database Troubleshooting Framework

When the application fails, use this order:

```text
1. Can the browser reach EC2?

2. Does EC2 have a public IP?

3. Does the public subnet have an IGW route?

4. Does app-sg allow TCP/80?

5. Is Apache running?

6. Is Apache listening on port 80?

7. Does PHP execute?

8. Does the RDS endpoint resolve?

9. Can EC2 reach TCP/3306?

10. Does rds-sg reference app-sg?

11. Is app-sg actually attached to EC2?

12. Is rds-sg actually attached to RDS?

13. Is RDS available?

14. Is the RDS endpoint correct?

15. Is the port correct?

16. Are database credentials correct?

17. Does the database exist?

18. Does the table exist?

19. Does the application account have required SQL privileges?

20. What do Apache and application errors show?
```

# What You Should Understand Before Moving On

The important achievement is not simply:

```text
I installed PHP on EC2 and connected it to RDS.
```

You should now understand the entire request path.

A browser reaches:

```text
EC2 TCP/80
```

because the EC2 application security group permits HTTP traffic.

Apache receives the request.

PHP executes the application code.

PHP does not expose the database password or database endpoint to the browser.

Instead, the server itself opens a private database connection.

The database tier receives:

```text
TCP/3306
```

only from the EC2 application security-group relationship. AWS recommends separate security groups for EC2 and RDS because this provides more precise control over each tier and avoids accidentally changing the security posture of both resources through one shared group.

RDS remains:

```text
Publicly accessible:
No
```

so internet users cannot directly connect to MySQL through this architecture.

The application uses a dedicated MySQL account rather than the RDS master account.

That account receives only:

```text
SELECT
INSERT
```

for the application database.

Finally, the troubleshooting exercises showed that:

```text
Website unavailable
```

does not identify one specific problem.

It could mean:

```text
Browser → EC2 failed

Apache failed

PHP failed

EC2 → RDS failed

MySQL authentication failed

Database authorization failed

SQL/schema failed
```

A production-minded engineer works through those layers instead of changing several things at once.

The full architecture is:

```text
USER
 |
 | HTTP
 v
EC2
 |
 | Apache
 v
PHP APPLICATION
 |
 | TCP/3306
 v
RDS SECURITY GROUP
 |
 | source = app-sg
 v
PRIVATE RDS MYSQL
 |
 v
veriqtaapp.messages
```

That is your first complete two-tier AWS application.
